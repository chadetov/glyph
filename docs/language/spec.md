# Glyph syntactic spec — D1 through D48

Condensed view of the numbered decisions that drive the grammar (D1–D27 from the original brainstorm; D28–D32 added post-1.0-brainstorm as the interop/type-feature work shipped: `infer_output`, `extern_ts`, string-literal unions, `int`, and `typeof` value-derived types; D33–D35 the 0.1.16 language-completeness features (module visibility, structural interfaces, defer); D36 bitwise operators and shifts; D37 the `new` interop constructor; D38 the `bigint` exact-integer type; D39 `where` refinement types; D40 the `async fn(...)` function type; D41 the project-root marker that decides where a local import path is counted from; D42 value equality for `==`; D43 a `mut` read and written across an `await`; D44 nested patterns in an object pattern's fields; D45 `Nullable<T>` as a boundary type; D46 a `type` whose body is a name; D47 the `never` bottom type; D48 the destructuring `let`; D49 the identity of a declared record or union; D50 the depth limit on a generated runtime check; D51 the pending value of an un-awaited async call; D52 the constant text of a SQL query; D53 a lambda parameter's type is the one written, and an `is` arm narrows its scrutinee; D54 which values may become text; D55 the type an omitted lambda annotation takes from its position; D56 a built-in method that answers absence with `undefined`; D57 the keys an object literal may write; D58 a generic function's own type parameter). Each rule below cites the pillar it serves; the original rationale lives in `archive/SPEC_DECISIONS.md`. The hand-written Rust parser is the normative implementation; if it disagrees with this file, the parser wins, but flag the divergence as a bug.

Principle: **prefer the choice an established language has already validated, unless a Glyph pillar overrides it.** Novelty for its own sake is rejected.

## Lexical

- **D1. Statements end at significant newlines.** A newline terminates a statement only at bracket depth zero (outside `()`, `[]`, `{}`, `<>`). No semicolons, no ASI. The external scanner tracks bracket depth. **Consequence (accepted):** inside a block, statement boundaries come from greedy parsing, not newline tokens, so a statement whose next line *begins* with `[` or `(` glues onto the previous expression as a postfix index/call — exactly JavaScript's ASI leading-bracket behavior (`foo()\n[1,2]` is `foo()[1,2]`). Prefix the line with `return` or a statement keyword to break the chain (`return [a, b, c]`). This is the price of letting multi-line method chains and split expressions live in a block without parentheses, and it keeps the JS-consistent stance. **A `{` cannot begin a statement on the line where the previous statement ended** (0.1.146, G351): greedy parsing would end `return h()` before the brace and read `{ k: 2 }` as a second statement that never runs, so the value written after the name was lost with only an unreachable-code warning. It is E0013, and the help carries D10's guidance, since `return Order { ... }` is the usual way to get there; the `{` a construct opens (`match x {`, `for x in xs {`, `loop {`, a signature's body) is not a statement and is unaffected. **Since 0.1.149 (G370) no statement begins on the line where the previous one ended**, whatever its first token, so inside a block statements end at significant newlines too and the title holds there literally: `let x = h() g` bound `h()` and left `g` a dead statement, `let s = "a" "b"` dropped `"b"`, `let a = 1 let b = 2` put a declaration mid-line, and `return h() as R` was three statements, all compiling. Each is E0013, whose help fits the token: `{` keeps D10's guidance, `as` says there is no cast, a literal says adjacent values are not joined, and anything else is told to start its own line. A token that cannot begin a statement (`)`, `,`, `=`, a binary operator) keeps the error it had. One line still holds one statement and everything inside it, so `let t = match x { A => 1, B => 2 }`, `fn f() -> int { return 1 }` and `for x in xs { f(x) }` are unchanged, and a `//` comment ends a line. The rule is inside blocks; top-level declarations on one line (`pub fn a() {} pub fn b() {}`) are not covered by it yet (G379). *[greppability — every statement in a block starts its own line, and every declaration will start at column 0 once G379 lands; verifiability — a value the author wrote is never silently dropped]*
- **D12. Two string forms: `"..."` and `"""..."""`.** The ordinary form is `"..."`: escapes `\n \t \r \" \\ \u{HEX}` are decoded, embedded raw newlines are preserved, and `${...}` interpolates (D22). The second form is `"""..."""`, a **raw** string: escapes are *not* decoded, so `"""a\nb"""` holds a backslash and an `n` rather than a newline. That is the only difference in the text they hold. `${...}` still interpolates inside `"""..."""`, through the same interpolation split as the `"..."` form, and the lexer accepts `"""` in any expression or type position, not only after `@doc` (D26), which is what it was introduced for. What a `${}` may hold differs between the two, and D22 states it. The formatter copies a multi-line `"""` literal through verbatim, and reprints a single-line one that interpolates in the `"""` spelling with its `${}` interiors normalized (since 0.1.169; before it, that reprint used the `"..."` spelling, which D22 now refuses whenever the interior holds a string literal or a backslash). **Update (session 3): template literals adopted — see D22.** Originally deferred; the forward-compatibility window was used in session 3. *[abstraction; greppability and verifiability for writing both spellings down — two forms with different escape semantics that a reader cannot distinguish from the docs is a file that lies about itself]*
- **Strings are sequences of UTF-16 code units.** `string.len`, `string.slice`, `string.index_of`, `string.split`, `string.pad_start`/`pad_end` and string indexing all count and cut in that space, exactly as TypeScript does. No accessor returns half of a surrogate pair, because the half looks like a character right up to the point where it is written out. `string.char_at(s, i)` and `string.code_point_at(s, i)` take a code-unit index and return the whole code point that starts there (as a one- or two-unit string, or as its scalar value), or `None` when `i` is not an integer, is outside `0 <= i < string.len(s)`, or falls on the second half of a pair or on a lone surrogate; on `"a😀"`, `char_at` at 1 is `Some("😀")` and at 2 is `None`. They are the `Option` forms of `s.at(i)` and `s.codePointAt(i)`, which D56 refuses. `chars` is still not shipped. Amended in 0.1.161 (decision record 154): until then there was no accessor at all. The index space did not change. String indexing (`s[i]`), `s.charAt(i)` and `string.slice(s, i, i + 1)` still hand back half a pair (G428). A program that walks codepoints can also convert to bytes first, `encoding.hex_encode` and then two hex digits at a time, as `examples/apps/shortlink/main.glyph` does. *[verifiability]*
- **D22. Template literals: `"hello ${expr}"`.** `${...}` inside a string literal interpolates an expression. The interior takes the full expression grammar, calls included (`"total: ${format(n)}"`). In a `"..."` string the interior cannot hold another string literal, because the interpolation is scanned before it is parsed and a `"` inside `${...}` closes the outer string, and since 0.1.169 it cannot hold a backslash either (E0002, G441). An escape inside the `${}` of a `"..."` string had one use, `"a${f(\"x\")}"`, a second spelling of the nested literal the rule above keeps out, and it hid the literal from a grep for `"x"`. The expression is parsed from the string's decoded value, where an escape is shorter than in the source, so it also placed every node after it early. Bind the value with `let` first, or write the whole string as `"""..."""`: that form decodes no escapes, so its `${}` reads a string literal and a backslash as written (`"""a${f("x\ty")}"""`). An escape outside the `${}` is unaffected (`"a\n${x}"`, `"\${x}"`). With the rule, every node inside a template string sits on its own bytes. When a full template-literal lexer mode lands, the nested form will be `"${f("x")}"`, with no escaped spelling to keep working. Statements and declarations are excluded because the interior is an expression position, not by a special restriction. Escape via `\${` for a literal dollar-brace. Replaces the previous "`+` concatenation only" idiom. *[abstraction — `"hello " + name + ", count is " + n` becomes `"hello ${name}, count is ${n}"`; the backslash rule: greppability, one spelling for a string literal, and verifiability, exact diagnostic, LSP and `glyph fix` ranges by construction]*
- **D54. Only a text-like value becomes text.** A value turns into text in three places, and one rule judges all three: a `${}` inside a `"..."` or `"""..."""` literal (D12, D22), an operand of `+` whose other operand is a string, and the argument of `string.from`. Text-like is an allowlist: `string`, a string-literal union (D30), `number`, `int`, `bigint`, `bool`, any alias (D46) or `where` refinement (D39) whose base is one of these, `never`, and an inline union of those primitives (`string | number`). Everything else is E0237: a record, a tagged union, `Option`, `Result`, `Array` (even `Array<string>`), a `Record<K, V>` map, `Nullable<T>` (which prints `null`), `Decimal` (an object whose text is its `to_string()`), `Bytes`, a function value, `void`, `unknown`, and a type parameter, since a `T` could be a record. One exception: `string.from` takes a declared `unknown`, because it is the explicit, greppable renderer and the documented way to read a failed task's error; `${}` and `+` refuse an `unknown`, and `string.from` refuses every other type above. What an `unknown` holding a record prints there is an open question (G416). The predicate is written as an allowlist so a type the checker learns later is refused until it is added. The refusal names the conversion as written and the type by its name (``E0237: `${user}` turns a `User` into text, and a record has no text form: it prints `[object Object]` ``), and its help is computed from the type: a text-like field of a record, a `match` bound with `let` for an `Option` or a `Result`, `string.join` for an array, `??` for a `Nullable`, `to_string()` for a `Decimal`, a call for a function with no parameters. A help never puts a string literal inside `${}`, which D22's lexer cannot read, so it binds the text with `let` first. A value Glyph's checker does not type (an arithmetic result until `+` is typed, an npm value with no materialized types, a lambda parameter written without an annotation whose position supplies no type, D53 and D55) is not judged; inside an `is T` arm the scrutinee is a `T` (D53), so `match v { is number => "${v}", else => "?", }` is accepted; `tsc` and the run are what see it. JSX children are not covered, since React's types check them, and the emitted code does not change. Before this, all three spellings printed `[object Object]` for a record and `tsc` accepted every one. *[verifiability: the printed text is part of the program's meaning, and `[object Object]` is a value the type said could not occur; abstraction: one rule for one conversion, however it is spelled]*
- **D13. Numeric literals: integers and decimals.** `/-?\d+(_\d+)*(\.\d+(_\d+)*)?/` with optional `e` exponent. Underscore separators allowed (`1_000_000`). No hex/octal/binary in v1; deferred but forward-compatible. *[baseline]*
- **D14. `//` line comments only.** No block comments (nested-block-comment confusion is a known footgun). No doc-comment syntax yet — `///` is reserved for it, forward-compatible. Because `//` is the only way to document a record field, a union variant, a literal element, an argument, or a `match` arm, the formatter must preserve what a comment sits under: `glyph fmt` emits every comment above the item that followed it in source, including inside a record body, a union variant list, an array or object literal, an argument or parameter list, a `match`, the operands of an operator expression, and the segments of a member/call chain, and a comment inside such a construct forces it to the one-element-per-line form so the comment has an item to sit above (for an operator expression, one operand per line with the operator leading; for a chain, one segment per line with `.` or `?.` leading, a segment being a dot and the calls, indexes and `?` after it; two `?` in a row are written `? ?`). A chain whose head ends in `?` and opens a statement is printed one segment per line, never with a `(` that would continue the line above (0.1.138, G335); a statement headed by a lambda call still is (G343). A comment inside a call's argument list belongs to the list. **`glyph fmt` never moves a comment to another construct** (0.1.137, records 86 and 97). A comment belongs to the innermost construct whose gap holds it, a gap being the source between two of that construct's own children or tokens. Where that construct has no one-per-line form (an index, a unary or `await` operand, a type annotation or a generic argument, a pattern, a JSX tag's attributes, a chain's head and its links, or the gap after a chain segment's first argument list, index or type-argument list), or D1 allows no line break there, `glyph fmt` refuses the file with an error naming the line, the construct and one place to move the comment, and leaves the file unchanged; `fmt --check` fails on it, and the refusal is warning `E0500` in the diagnostics `glyph check`, the editor and MCP share. A comment is always placed on its own line, so one written at the end of a code line moves to the line above the next element of the same construct; it does not cross into another declaration. In JSX children a comment is a comment-only child (`{`, then `// note` on its own line, then `}`), and `//` in JSX text is `E0012` (D6). *[greppability, verifiability — a relocated comment makes the file assert something false about itself]*
- **D17. Trailing commas legal everywhere they're meaningful.** Array/object literals, parameter lists, argument lists, type field lists, generic parameter lists, match arm lists, import name lists, tuple patterns. *[diff stability]*

## Control flow & expressions

- **D3. `match` is the only conditional.** No `if`/`else` statement or expression at the value level. `match` is an expression in all positions. Cost: `match x > 0 { true => a, false => b }` is verbose. Accepted. The `<if>` JSX directive (D6) is separate. Its type is a **join over the arms**: an arm ending in `return`/`break`/`continue` diverges and contributes nothing, every other arm contributes the type of its value, and the `match` has that type when the contributors agree. Identical types agree. So do two applications of the same generic head with the same arity, which join argument-wise with `Unknown` taking whatever the other side says, so `Some(p) => p` on an `Array<string>` and `None => []` on an `Array<Unknown>` agree on `Array<string>` instead of cancelling each other out. Everything else disagrees, and an arm whose own type is undecidable still sinks the whole expression: projecting a known arm's type onto an arm nothing is known about would be a guess, and this join decides how a `for` lowers. When the arms disagree the expression's type is unknown to Glyph's checker and `tsc` is the only thing checking uses of it. There is no widening, no union of arm types, and no bottom type. An arm that produces *no* value while the `match` is used as one is an error (`E0223`), not an implicit `undefined` contributor: an empty block arm (`X => {}`), or a block arm whose last statement is a `let`/`mut`/`for`/`loop`, contributes nothing and diverges from nothing, so the binding it feeds would hold `undefined` at run time with a type saying otherwise. Where the `match` is a statement, such an arm is a legal no-op. Because there is no `if`, a value that came out of a branch is a value that came out of a `match`, so leaving it untyped propagates: it decides whether `for i, x in v.rows` binds a number or a string key (D21) and whether a bad field name is `E0210` or a `tsc` error. Both hold across an import: a record declared in a sibling module keeps its field set and its name in the consuming file, under all three import spellings. *[verifiability — the branch's result stays checkable by Glyph rather than being handed to `tsc`]*
- **D2. `match` arms are comma-separated, trailing comma required.** Holds for both expression arms (`=> Ok(n),`) and block arms (`=> { ... },`). *[diff stability]*
- **D9. `else` is a catch-all arm; `_` is a position-level wildcard; a PascalCase arm head is a variant reference, not a binding.** `else` is a pattern keyword that appears only as the entire pattern of a `match` arm. `_` is a binding wildcard inside a pattern (`Err(_)`, `[..._]`). A bare `match`-arm head is disambiguated by its first letter: a lowercase/underscore-led name (`rest`) is a fresh binding (an irrefutable catch-all), while a PascalCase name (`Loading`) is a *reference* to a variant of the scrutinee's union, not a binding. So a PascalCase head that names no variant of that union is a compile error (E0220, with a nearest-variant suggestion), never a silent catch-all that would mask a missing variant (E0200) and misroute values at runtime. This holds for all three arm shapes: bare `Loading`, payload-bearing `Loading(x)`, and qualified `Feed.Loading`. It also does not depend on how the union reached the module: `import feed { Loading }` with a bare arm and `import feed` with a `feed.Loading` arm are held to the same bar, as is `import feed as f`. **One level down, in a constructor's payload position, the first letter is not what decides.** `Err(Blank)` beside `Err(e)` reads `Blank` as a variant of the payload union and `e` as a binding, and it reads them off that union's own variant list, the same list exhaustiveness is counted over, so a union that declares a lowercase `blank` matches `Err(blank)` rather than binding it. That arm lowers to one `case` on the outer tag with an inner dispatch on the payload's tag. The letter decides only when there is no list to read, which today means a union imported from another module: a capitalized variant of one dispatches, and a lowercase one is `E0305` rather than a wrong arm (G147). `E0305` is the guard under all of this. Two arms of one `match` that would write the same `case` label are refused, because JavaScript runs the first for every value and `tsc` has nothing to say about it, so a lowering that reaches for one tag twice fails the build instead of picking an arm at run time. `Err(e) => .., Err(other) => ..` is that shape written by hand and is refused for the same reason. *[verifiability, abstraction]*
- **D44. An object pattern's field holds a pattern, and a field that tests a value makes the arm refutable.** `{ name }` still binds `name` and `{ name: alias }` still renames it, but the position after the colon takes any pattern: a variant reference (`Node({ color: Black })`), a nested constructor (`Node({ left: Node({ value: v }) })`), a nested destructure (`{ pos: { x, y } }`), a literal (`{ status: 404 }`), or an array pattern (`{ items: [a, b] }`). D8 spells a multi-field variant payload as a record, so this is the only way to write an arm that names a shape more than one level down, and without it the Okasaki red-black `balance` had no spelling at all. The field position was previously a name and nothing else, and a PascalCase name there was rejected outright (E0009, now retired). **The consequence to know is exhaustiveness.** An object pattern is refutable when any field of it is, and a refutable pattern does not cover the variant it sits under: `match t { Leaf => .., Node({ color: Red, .. }) => .. }` is a non-exhaustive match on `Tree` (E0200) until a sibling arm or an `else` takes the rest. The checker proves coverage over a set of tags, not over a product of fields, so it will not conclude that a `Red` arm and a `Black` arm together exhaust `Node`; asking for the catch-all is the reading that cannot accept a match which falls off its end at run time. The same rule reaches a scrutinee with no variants at all: `match p { { x: 0, y: y, } => .. }` over a record type has no tag set to count, and every arm can fail, so it is `E0226` until a catch-all takes the rest. Lowering follows from the same fact: one refutable arm turns the whole `match` into an exclusive `if`/`else if` chain over field tests rather than a `switch` on the discriminant, because two arms can share an outer tag and the second has to run when the first's field test fails, which a `case` that has been entered cannot do. Reaching *through* a payload needs one more fact, since a variant's record payload is spread flat into the tag object while every other payload sits under `value`: the compiler answers it from the matched type, which holds across a module boundary and across the union's arity independently, so a union declared in a sibling module matches exactly as a local one does and `Tree<K>` matches exactly as `Tree` does. Exhaustiveness is the narrower of the two and the difference is worth stating rather than folding in. For a union the matching module declares, the rule above holds across arity for the same reason the payload lookup does: the tag set counted for `Tree<K>` is the tag set counted for `Tree`, so omitting `Leaf` is `E0200` under either spelling, and a missing variant one level down inside a payload is reported through a generic outer union as it is through a plain one. The tag count now holds across a module boundary under both spellings too: omitting `Leaf` from a `match` on an imported `Tree<K>` is `E0200` naming `Leaf`, the same as the imported non-generic `Tree` (G148 closed the gate that was reading the application instead of its base; it used to build clean and throw at run time). What the cross-module check still does not do is reach *inside* a variant's payload: an imported union's payload is never recursed into, whether or not it is generic, so a missing variant one level down goes unreported where the module-local spelling reports it. G143 closed that gate in 0.1.97: an imported union's nested payload is recursed into and a missing variant one level down is reported through a module boundary as it is locally. A third is the payload lookup rather than exhaustiveness: a union reached through a namespace import (`import tree`, matched `tree.Node`) refuses a nested constructor in a field with `E0300` where the named-import spelling of the same union takes it (G140). *[abstraction — the shape a reader sees in the pattern is the shape being matched; verifiability — a pattern that can fail is counted as one that can fail]*
- **D45. `Nullable<T>` is a boundary type: `T | null` in TypeScript and on the wire, its own type in Glyph.** A prelude type constructor for a value a real API sends as JSON `null`. It emits as TypeScript `T | null`, and a record field of it validates as `null` or a `T`: `{"s": null}` and `{"s": 3}` both decode into `type Frame = { s: Nullable<int> }`, and `{"s": {"tag": "Some", "value": 3}}` does not, because a non-null value is checked as the inner type and `int` rejects an object. An absent key is still `missing`, as it is for every other field; `s?: Nullable<int>` is the spelling for absent-or-null-or-value. `f?: T` is an absent key or a `T`; a JSON `null` there is refused, and `f?: Nullable<T>` is the spelling that takes it. Present means an own key whatever it holds, so a key holding `null` is a `type` issue unless `T` is `Nullable`, and a key holding `undefined` is a `type` issue always, in `is` and `parse` alike and on every route that checks the field. This replaced 0.1.68's reading of `null` as absence in 0.1.152 (G391): that reading predated `Nullable`, and it returned `Ok` holding a `null` the type said was a `T`. `json.stringify` of the decoded value is the wire form again, so the round trip holds in both directions. It is not `Option<T>` and is not assignable to or from one (E0204 at a `let`, E0211 at an argument); there is no `match` on it and no `Some`/`None`. The bridge is explicit: `std/nullable` has `to_option(n) -> Option<T>`, `from_option(o) -> Nullable<T>` and `is_null(n) -> bool`, and the call is the greppable record of where null enters the program. **A field of a `Nullable<R>` is read with `?.`, and the read is checked against `R`'s fields (E0210).** `n.f` with the plain dot is E0235, since `n` may be null. `n?.f`, and any chain it starts (`n?.inner.f`), is an `F` or JavaScript's `undefined`, a value Glyph has no type for, so it stands in two places only: as the left operand of `??`, which replaces the absence and gives the expression the type `F` (the inner `T` when `F` is `Nullable<T>`) when the default is one, and as an operand of `==` or `!=`, which compare it without holding it. Anywhere else (a binding, an argument, a `return`, a field value, an interpolation, a JSX child or attribute, a `match` scrutinee) it is E0235. `n ?? d` on the `Nullable<T>` itself is a `T` by the same rule. A `type` whose body is a `Nullable` is checked as that `Nullable`, a generic one included with its arguments substituted (`m: Maybe<Note>` under `type Maybe<T> = Nullable<T>` is a `Nullable<Note>`), local or imported under any spelling. That holds for assignability as well as for `?.` and `??`: a `Maybe<Note>` passes where a `Nullable<Note>` is declared and the reverse (0.1.170, G315; before it both directions were E0204). That is the checker's half: the run-time check does not yet follow a generic alias of `Nullable` or `Option` at a record field, `json.parse` or `is`, which are E0304 until G399 closes. Lowering `n?.f` to `(n?.f ?? null)` typed `Nullable<F>` was refused: it is a type-directed emitter change, and it would give a null `n` and an absent optional field one runtime spelling, which E0227 refuses for the same reason. Refusing `?.` outright was refused too, because `n?.f ?? d` never lets `undefined` reach a binding. `T` may not itself be `Nullable` or `Option` (E0227): the first would give two states one runtime spelling, the second would put a tagged object under a null-tolerant field. **Loosening `Option<T>`'s own decoder to take `null` and bare values was refused because it is ambiguous:** `@open type Meta = { id: int }` under `Option<Meta>` decodes `{"tag": "None", "id": 7}` two ways, both valid against the declared types, and `type Tagged = { tag: string, value: int }` under `Option<Tagged>` has a valid document only a backtracking decoder accepts, so a field's wire format would depend on a property of a type declared in another file. Two designs for `Nullable` itself were refused on the way: a `parse` that decoded `null` into `None` would make `is` and `parse` disagree on what they accept, add a decode twin to every composite check, and stop a Glyph value round-tripping through its own `parse`; a `T | null` that was the same Glyph type as `Option<T>` would need an implicit coercion at every assignment, a type-directed emitter change. A distinct type with an explicit conversion costs one call at the use site and nothing anywhere else. `Option<T>` is untouched, so no program that built before this rejects now. `glyph gen dts` and `glyph gen openapi` map a `nullable` field (a `| null` union member) to `Nullable<T>`, and keep `?` for a field the schema does not require. *[verifiability — the boundary check and the emitted type say the same thing about `null`; greppability — every crossing between the wire's null and `Option` is a named call]*
- **D18. Postfix `?` binds tighter than `.`.** Precedence is normative in `archive/GLYPH.md §2` (originally referenced as `PRECEDENCE.md`, file never materialized). `r.map_err(f)?` parses as `((r.map_err(f))?)`. `await fetch(url)?` parses as `(await fetch(url))?`. `?.` is a separate optional-chaining token. On an `Option` or a `Result` it is refused by the type checker, not the grammar: `result?.field` is `E0236` (0.1.133), because neither is ever null and `?.` would read the tag object, not propagate an `Err`. A plain-dot member on an `Option` is `E0210` (it has none), and on a `Result` only `map` and `map_err` are members (0.1.139, record 87); `tag` and `value` are the runtime encoding (D49), not members. `??` with an `Option` or a `Result` as its left operand is `E0236` too (0.1.162, G429), because neither is ever null or undefined. A left operand that cannot be absent is refused whatever the default is. One that can be absent (a `?.` chain, or a read whose last link is a field declared `f?:`) is refused unless the default is accepted where the container is declared; then the `??` is typed as the container, so `match b.o ?? None { .. }` is held to both arms. An index read is not absent: Glyph's emitted index throws a `RangeError` out of range (record 159), so `xs[i] ?? None` is refused like a name. Not judged: a type parameter (it may be instantiated as a `Nullable`), a `Nullable` (D45 covers it), a value the checker types `Unknown` or `unknown`, and any left operand that is not an `Option` or a `Result`. A `??` whose default disagrees with a `Nullable` or optional left operand is G432's. *[locked]*
- **D21. Two loop constructs: `for x in iter { ... }` and `loop { ... }`.** `for` is for bounded iteration over an iterable, and takes a second form, `for i, x in iter { ... }`, that binds a pair: over an array `i` is the numeric index (the loop lowers to `iter.entries()`), over a record `i` is the string key (`Object.entries(iter)`). It exists so index-carrying iteration does not get hand-rolled into a `loop` with a counter. Over a declared `unknown` the shape is decided at run time and both names are `unknown`, index included, to Glyph's checker and to `tsc` alike, so a use must narrow first. The array form is chosen from the iterand's type as the checker knows it, and a field read off an imported record carries the type that record declares, so the choice does not depend on which file the type lives in. Most stdlib calls carry their return type, so `for i, part in string.split(text, ",")` and `for i, x in array.filter(xs, keep)` bind a numeric index directly, and all six of `std/record` do too, with the value type read off the record you pass. A call the checker does not model yet — anything outside the modeled table — has no type, takes the record lowering, and binds a string index; annotate the binding `Array<T>` in that case (see `docs/dogfooding-gaps.md` G37). `array.map` and `array.slice` were the examples given here and are no longer: both are modeled, and `map` carries the element type its callback returns. An inferred `let` is fine when its value has a type: a `match` whose arms agree carries their type (see D3), and `T.parse` on a type that emits a runtime descriptor is `Result<T, Array<Issue>>`, so `for i, x in w.rows` over a match-bound `w` binds a number with no annotation, as does `for i, hop in path` where `path` came from `match record.get(reached, name) { Some(p) => p, None => [] }`. `loop` is for unbounded retry/server loops; `break` and `continue` are legal inside `loop`. No `while` — use `loop { match cond { false => break, true => ... } }`. (Earlier wording here also offered `iter.take_while(...)`; there is no `std/iter` module and never was, and whether to build one is undecided. See `docs/dogfooding-gaps.md` G50.) Both keywords sit at column 0 inside their function body, so `grep -n "^\s*for "` and `grep -n "^\s*loop\b"` audit iteration sites. Resolved in brainstorm session 1 from Q20. *[greppability — two keywords, two canonical uses]*

## Declarations

- **D4. One `fn` form, name optional.** `fn name(args) -> T { body }` is the declaration; `fn(args) -> T { body }` is the anonymous form. Return type optional in both. Anonymous forms never sit at column 0, so `grep -n "^fn [a-z_]"` is a complete audit of named declarations. *[greppability]*
- **D40. `async fn(A, B) -> T` is a function type.** The type of a function that must be awaited. It emits `(a0: A, a1: B) => Promise<T>`, and `async fn()` with no return type emits `() => Promise<void>`, matching what an `async fn` declaration and an async lambda already produce. Written wherever a type goes: `fn task_for(url: string) -> async fn() -> Fetched`, a record field holding a handler, a parameter taking an async callback. Before this the type could not be spelled at all, so such a signature had to go unannotated. The checker holds the two apart: a plain `fn() -> T` where an `async fn() -> T` is expected is E0211 at a call argument and E0204 at a return, and the reverse direction is caught the same way. Since 0.1.159 a `void` return on either side no longer exempts the pairing, although TypeScript lets any function stand where a `void`-returning one is expected. An async function given where a sync `fn(...) -> void` is declared (`ids.forEach(save)`, an async lambda given to `timers.every` or a socket handler) is E0211: the slot calls it without waiting, so each call runs on its own and its failure is lost. The help offers `for id in ids { await save(id) }` where the slot is an array's `forEach` and the caller can wait, and otherwise a sync callback that starts the work on purpose with `task.detach` (D51). A sync function where an async one is expected is refused whatever it returns, `void` and a return the checker cannot read included (`task.detach(tick)` with a sync `fn tick()`), and an async function where a sync one returning a value is expected is refused whatever its own return is, so an async lambda that writes no return type is refused by `array.map` as the annotated one is (G99). The only return still not judged is one the checker cannot read on the expected side, where nothing is known about what the slot does with the result. A plain `fn() -> T` still emits `() => T`, so an async value does not fit one; write the `async` out. Since 0.1.185 a function value's parameters are compared too (G491). A function given where `fn(Q1, ..., Qm) -> S` is declared may take no more required parameters than the m the slot passes (fewer is fine, as in TypeScript), and each `Qi` the slot passes must be accepted where the function's own i-th parameter is declared, through the whole relation: `takes_cb(fn(x: number) -> string { .. })` where `fn(string) -> string` is declared is E0211, and `fn(string) -> void` where `fn(unknown) -> void` is declared is refused because the slot may pass anything (D65). A generic function value is first instantiated against the slot, its type parameters bound from the slot's parameter types the way a call binds them, so `array.map(xs, id)` with `fn id<T>(x: T) -> T` is accepted; when the slot binds none, the pairing is left undecided rather than refused. A record field that satisfies an interface method member is compared the same way, contravariantly. That is stricter than `tsc`, which compares a member written with method syntax bivariantly, and the bivariant case is the unsound one. A refusal between two function types prints both signatures and names the first position that differs: ``expected `fn(string) -> string`, found `fn(number) -> string`: parameter 1: the slot passes a `string`, which the function's `number` parameter does not take``. *[abstraction — a handler map or a callback parameter can carry a type instead of being left bare; verifiability — an async callback a caller never awaits is refused instead of losing its failures]*
- **D51. A call to an async function is a pending value until it is awaited (E0238).** Calling a function the checker knows is async (an `async fn` declaration, an async lambda, a value of type `async fn(...) -> T`, or a standard-library function modeled as async, such as `http.get` or `time.sleep`) starts it and gives back a pending `T`, which is the `Promise<T>` the emitted TypeScript holds. `await` unwraps it to the `T`. A pending value may stand in four places: the operand of `await`; `return`, or the tail value, of an async function or lambda that returns a value; the initializer of a named, unannotated `let` whose name is read at least once, where each read is a pending value judged by these same rules; and an argument to a function the checker holds no signature for. Everywhere else it is E0238, one code for every position: an expression statement anywhere in a block, the final statement included; `let _ = ...` and a destructuring `let`; a named `let` never read (a `_`-led name included, unlike E0107); a typed `let`; a `match` scrutinee; an operand; a `${}`; a field or element value; a member read; an argument to a Glyph-typed parameter; and `return`, or the tail value, of a function that is not async, a sync lambda included whether or not it writes its return type (a function that hands back a promise is written `async fn() { await save(1) }`). The arms of a `match` take the position of the `match`. A pending `Result` is E0238 and not E0217, whose advice to bind it with `let _ =` would leave the call running unwaited with nothing reporting it. A pending value is never assignable to anything, the `T` it settles to included, and it reaches no other diagnostic: `let n: string = load()` is the missing `await`, not a type mismatch. Work that should run without being waited for is started on purpose with `task.detach(async fn() -> void { ... })` from `std/task`, which reports a failure through `console.error` instead of losing it. That is the only correct spelling inside a sync callback, which cannot wait. A pending value hovers as "a pending `T`". Not judged: a call to a function the checker types `Unknown` (an npm package or a host builtin without a modeled signature) is not pending, so dropping its promise is left to `tsc` and lint tooling. Before this the checker typed an un-awaited call as its result, so `let n: number = load()` passed every Glyph stage and `match try_save(2)` was checked against a `Result` the program never held (G384). *[verifiability: ordering and a lost failure are part of what the program means, and the checker no longer claims a value the program does not hold yet]*
- **D19. `component` is its own top-level keyword.** Grammatically identical to `fn` except for the keyword and an implied JSX-returning body. `grep -n "^component "` audits every UI component. A component takes no parameter or one, and the one is its props record (0.1.125): React calls a component with the single props object its element builds, so a parameter declared as anything else holds that object whatever its type says. A primitive, a string-literal union, a tagged union, an `Array`, a `Nullable` or a function type is E0229; a record, an alias of one, an imported record and an `interface` are props records; a type the checker cannot see into (`unknown`, a bare generic, `Record<K, V>`) draws nothing. Several parameters are E0214. A component is rendered, not called: a function that returns JSX and is called as a function is an `fn`, and the E0229 declaration refuses the direct call with it. *[greppability, verifiability]*
- **D20. `const` is module-level only; `let` is function-level only.** Mixing them is a syntax error caught at the grammar level. `mut` cannot target a `const` (typechecker enforces). A `const` with an annotation has that type. Amended in 0.1.166 (G433, record 158): a `const` with no annotation has the type of its initializer, read the way `tsc` reads the TypeScript `const` the emitter writes for it. A string literal standing as the whole value keeps its one-literal type, and so does a value-position `match` whose every arm is a written string, so `const MODE = "read"` stands where a `"read" | "write"` is declared. A literal inside an object or an array widens, as TypeScript widens a fresh literal in a property or an element even under `const`: `const CFG = { n: 1, }` is a `{ n: number }` and `const ITEMS = [1, 2]` an `Array<number>`. A literal type that reached the value through a name is kept. An initializer the checker cannot type (an npm value, an `extern_ts` result, a `const` whose initializer reads itself back) leaves the `const` untyped, and nothing is checked against it. An imported `pub const` has the type its own module gives it, under `import m { NAME }` and `m.NAME` alike. Before the amendment an unannotated `const` had no type, so every check that reads a receiver's type was silent at one: `ITEMS.push(3)` drew no E0240 and `let x: string = CFG.n` no E0204, where the same values in an annotated `let` drew both. *[greppability; verifiability: a guarantee does not depend on whether the author wrote the annotation]*
- **D48. `let` destructures a fixed-length array, and only one that cannot fail.** `let [count, set_count] = useState(0)` binds each element. The pattern is D9's array pattern, limited to lowercase bindings, `_`, nested array patterns and a trailing `...rest`; a literal, a variant name, a constructor or an `is` guard can fail and is E0230 at parse. The length is proved, never assumed. A written array literal with no spread is counted by Glyph, and each name takes its element's type, widened as a `let` widens (D30); a count that disagrees is E0230. An `Array<T>`, whose length is unknown, is E0230 with `match xs { [a, b] => ..., else => ... }` named in the help. A value only `tsc` can see (an npm import) is emitted as `let [a, b] = (value) satisfies readonly [unknown, unknown];`, which `tsc` refuses for anything but a tuple of that arity and which leaves each name the element type `tsc` infers. Anything else (`unknown`, a record, a union, a `string`) is E0230: it is not an array. Each name is a `let` binding: `mut` reassigns it (D5), and an unused one is E0107 on its own. The clause needs TypeScript 4.9 or later. Not in this decision: object destructuring in a `let` (E0005 until it is designed), `const [a, b]` (E0230: a `const` binds one name, D20), a type annotation on the pattern, and `let owned [..]` (one handle is one binding, D25). *[abstraction: the pair a library returns is written as a pair; verifiability: a destructured name never holds the `undefined` a short array leaves]*
- **D15. Four import forms.** `import std/http` (namespace), `import std/result { Result, Ok }` (named), `import std/http as h` (aliased namespace), and `import express { default as app }` (default). No `import *`, no re-exports, no relative imports. **The default form was added in 0.1.76** for one reason: a CommonJS package whose export *is* a function (`module.exports = f`, so `export = f` in its `.d.ts`) has nothing else to import, and the other three forms all emit a named or namespace import, which `tsc` answers with TS2595 or leaves uncallable. That made express, lodash, debug, chalk@4, commander and most of the pre-ESM registry unreachable. The `as` is legal **only** after `default`, never for an arbitrary imported name, so this does not open general renaming: a name in the file still matches the name at its source, which is what makes an import greppable, and `grep 'default as'` finds every default import. Binding the default through the *aliased* form instead was rejected, because it would give one spelling two meanings depending on the package's module format, which is the class G111 was fixed to remove. Paths are slash-separated from the module root. A path segment may contain hyphens and the first segment may carry an npm scope, so real package specifiers import unchanged: `import react-hook-form { useForm }`, `import @hookform/resolvers/zod { zodResolver }`. This widens what a segment may spell (no pillar cost — greppability and diff stability are unaffected); it does not add a fourth form. Two prefixes are reserved and no project file may declare a module under either (G238): `std/` names the stdlib modules the compiler carries, and `extern/<name>` imports a hand-written TypeScript file placed under `<src>/extern/`: the build stages it into the output and emits a relative specifier for it, so a Glyph module can call local `.ts` (a node-stream loop, a `new Promise`) without a relative import in source. This is the single sanctioned local-`.ts` path; every use is greppable by `import extern/`, and it keeps the no-relative-import rule intact for Glyph source. The root a path is counted from is the *project* root, which D41 defines; D15 is otherwise unchanged (still no relative imports, still slash-separated). *[diff stability]*

## Mutation & types

- **D5. `mut` is a statement prefix for assignments and for calls that change a place.** Legal: `mut x = expr`, `mut x[k] = expr`, `mut x.field = expr`, `mut x.method(args)`, and `mut x?.method(args)` where only the method link is `?.` (a write through an optional field; record 151, F3, amending record 150, because it is the one spelling of that write `tsc` accepts). Assignment through `?.` (`mut a?.b = 1`) stays a syntax error. `mut foo()` (free function call) is a syntax error. `mut` is never an expression operator: `let n = mut xs.pop()` and `mut let n = ...` are parse errors. Amended in 0.1.160 (G380, record 150), reversing Q7, which had left the checker trusting the grammar: a method Glyph knows changes its receiver may stand only as the whole call of a `mut` statement, and on a receiver that is a place, the same places `mut x = expr` writes to (a name, a chain of fields and indexes, no `?.` before the method link). A receiver reached through an index of an `Array<E>` is judged as an `E` (record 151, F2). Anywhere else it is E0240: a statement whose value nothing reads (`glyph fix` inserts the `mut`; a lambda's last expression counts as one when the lambda stands in a `fn(...) -> void` slot, which discards the value, record 152), a `return`, a `let` initializer, an argument, an operand, the receiver of a further member or call, an arm value, the last expression of a block whose value is used (a callable whose declared or position-given return is not `void`, or a block arm of a `match` in value position), a `defer` (whose change goes in a `fn() -> void` the `defer` calls, since `defer` takes no `mut`), and `mut make().push(1)` or `mut ys.filter(f).sort(cmp)`, whose change lands on a value nothing holds. `mut` before a call Glyph knows changes nothing is E0241: a non-mutating method of an `Array<T>`, a `string` or a `number`, a `NonMutating` member of a modeled stdlib type, and any function read through a namespace import of a Glyph module, decided by what the name resolves to. The methods Glyph knows change their receiver are the nine `Array<T>` methods `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`, `fill` and `copyWithin`; no `string` or `number` method does. The split is the `mutates` column of the table generated from TypeScript's library, classified by hand because `lib.d.ts` has no marker, and held by two gates: every method is classified exactly once, and node confirms the array split by calling each method on a fresh array. Amended in 0.1.167 (G423 step 2, record 157, section 2b): every member of a stdlib type whose members the checker models is in one of three classes. `Mutating`: `add` and `remove` on a `set.Set`, `set` and `update` on a `store.Store`, `push_back`, `push_front`, `pop_back` and `pop_front` on a `collections.Deque`; these follow the rule above exactly as the array methods do, so `HITS.set(0)` on `const HITS = store.create(0)` is E0240, `glyph fix` writes the `mut`, and `let _ = q.pop_front()`, whose value is thrown away, is rewritten to `mut q.pop_front()` (for an array too). `NonMutating`: `has`, `size` and `values` on a `Set`, `get` on a `Store`, `peek_front`, `peek_back`, `len` and `values` on a `Deque`, and every member of a `decimal.Decimal`, which is immutable, so `mut d.add(e)` is E0241 with the help `mut d = d.add(e)`. `Outside`: every member of a `sqlite.Db`, whose writes land in a database, not in the program's data; they are never E0240 and never E0241. An array method called on what a `Store`'s `get()` returns (`HITS.get().push(1)`) is E0240, since the store hands back the array it holds and the call changes the store through a value that is not a place; it is written through the store, `mut HITS.update(fn(current) { array.push(current, 1) })`. The classes are written by hand beside the array split, generated into the checker, held to the runtime's declared members, confirmed in node on fresh instances, and a unit test fails when a modeled type has a method with no class. `grep -n "^\s*mut "` is a complete audit of writes to every value whose type Glyph's checker knows. An unannotated module `const` is one of them since 0.1.166 (D20, G433): it has its initializer's type, so `ITEMS.push(3)` on `const ITEMS = [1, 2]` is E0240. It does not cover writes inside npm code, calls on a receiver the checker cannot type (an npm value, an `extern_ts` result, an omitted lambda parameter whose position gives no type), where `mut` is allowed and not required, an unannotated module `const` whose initializer the checker cannot type, a write through a second name for a stdlib value's contents (`let xs = HITS.get()`, then `mut xs.push(1)`, which changes the store under a `mut` line naming `xs`; G394), or a write through a structural interface (`interface Adder { add: fn(number) -> void }` handed a `set.Set`, then `a.add(1)` with no `mut`; G448, awaiting a decision). Amended in 0.1.181 (G505, record 196, section 3): the arguments of a `mut x.method(args)` call are checked exactly as the same call's are in value position, its count as E0213 and each argument against the parameter, with the receiver's `T` put in, as E0211. A built-in method's rest parameter (`push`, `unshift`, the items of `splice`, `string.concat`) checks each argument against its element type, so `mut v.push(5)` on an `Array<string>` is E0211, and so is `mut u.push(5)` in an `is Array<string>` arm, where `tsc`, reading `Array.isArray` as `any[]`, accepts it. A `sort` comparator is held to two parameters and a `number` return; its parameter types are compared once function parameters are (G491). A receiver the checker cannot type is not judged. Changes to state outside the program's data (`Rng.next`, a database, a socket) are not D5's: they belong to the effects questions. A caller does not say that a function it calls changes an argument; the write is a `mut` statement inside that function. Amended in 0.1.179 (G501, record 196): the value `mut P = e` writes is compared with the type of the place P, exactly as `let x: T = e` compares its initializer, as E0204, arm by arm for a `match` and with D57's rules for a written literal. A name's type is its annotation, or under D66 the type its `let` recorded; a parameter's is the one declared. `r.f` holds the field's declared type, through a record or an interface (only the value is compared there; G448 is unchanged). `v[i]` holds `E` on an `Array<E>` and `V` on a `Record<K, V>`; a receiver the checker cannot type is not judged, and nor is a name whose type comes from neither (a `for` binding, an arm's payload, a lambda parameter typed by its slot). Inside an `is Array<string>` arm, `mut u[0] = 5` is refused although `tsc` accepts it, because `Array.isArray` gives `tsc` an `any[]`. The refusal's note says where the place's type came from (`` `y` holds a `number`: the type of its initializer at line 9, and a `mut` does not change a binding's type ``). Glyph has no anonymous union to widen a binding to, so the help is to bind the new value to a new name. *[verifiability, greppability]*
- **D16. `void` is a reserved word, both type and value.** `Ok(void)` and `-> void` both legal. Cannot be used as an identifier. Avoids TS's `null`/`undefined` ambiguity. *[verifiability]*
- **D25. Narrow `owned` modifier for resource handles.** `let owned name: ResourceType = expr` introduces a value the typechecker tracks for single-consumption across every code path. Forgetting to consume = compile error. Double-consume = compile error. Returning without consuming = compile error. Restricted to types declared with the `resource` keyword (`resource type X = ...`; resolving implementation decision I1 — keyword, consistent with `record`/`component`). A handle is **consumed** by *moving* it into an `owned` parameter (`fn close(owned h: X)`); any other use borrows it (resolving the consume-model question in favor of move-into-`owned`-param over a type-declared disposer method). Because `owned` marks both the binding site (`let owned`) and every consuming position (`owned` params), `grep -n "owned"` is a complete audit of the ownership surface, paralleling D5's `grep "mut"`. **Narrow carve-out** from the manifesto's "no linear types" stance, scoped to resource discipline (files, sockets, db connections, locks). NOT a general affine/linear type system. See `docs/manifesto.md` for the carve-out language. *[verifiability, greppability]*
- **D7. Types vs values disambiguated by context.** Types appear only after `:`, after `->`, inside `<...>`, after `as` (if cast survives), and on the RHS of `type X = ...`. Everywhere else `<` is less-than. GLR handles the few ambiguous spots (the `fn` keyword preceding `<T>` is the disambiguator). *[TS compatibility]*
- **D8. Tagged union punctuation: leading `|` required on multi-line, omitted on single-line.** `type X = A | B | C` vs `type Y =\n  | A\n  | B({...})\n  | C`. Lexer rule: if the first token after `=` on the type line is `|`, the union is multi-line. A variant carries **one payload**, and a payload with several fields is a record (`Node({ color: Color, left: Tree<K, V>, right: Tree<K, V> })`), never a positional tuple: `Node(Color, Tree<K, V>, Tree<K, V>)` is E0010, which reports the arity and points at the record form. Named fields are what make a swap of two same-typed arguments a compile error and what give `grep` a name to find. *[diff stability; abstraction — named records over positional tuples]*
- **D46. A `type` whose body is a name is a second name for the declaration it resolves to.** `type B = A`, with `type A = { x: number }`, declares no type of its own: `B` is another name for `A`'s declaration, so a `B` passes where an `A` is declared and the reverse, `b.naem` on a `b: B` is E0210 exactly as it is on an `a: A`, and `B.parse` is `A.parse` (the emitted TypeScript binds `const B = A;` beside the descriptor, so the identity is one greppable line). The chain is followed to its end with a cycle guard, and a field reached through an alias is a site over the record the chain ends at, which is what the cross-module path already did for `pub type Rows = Sheet`. Before this, the module-local spelling was E0211 on a program `tsc --strict` accepts (G203) and gave `b.naem` no field set at all (G206), while the identical two declarations imported from a sibling module answered both correctly: one spelling, two answers, decided by a file boundary. A name is followed however it is spelled: bare (`type B = A`, or `type Page = Doc` under `import a { Doc }`) or qualified by a namespace import (`type Page = a.Doc` under `import a`, `type Page = aa.Doc` under `import a as aa`, `type P = http.RedirectPolicy` under `import std/http`). The qualified spelling reaches the declaration the named-import spelling reaches, so it is the same second name with the same guarantees, and the emitted TypeScript binds `const Page = a.Doc;` where it binds `const Page = Doc;`. **A body that declares no type is read as that body (0.1.170, G315).** A body that is a primitive (`type Id = string`), `unknown`, a type parameter (`type Same<T> = T`) or a generic application (`type Headers = Record<string, string>`, `type Maybe<T> = Nullable<T>`, `type L<T> = Array<T>`) is replaced by its body, with the application's arguments substituted for the parameters, before the checker compares it with anything, at every depth. So `Id` and `Name` (both `= string`) pass for each other, `Maybe<Note>` and `Nullable<Note>` pass both ways, as do `L<string>` and `Array<string>`, and what the body refuses is refused: `Same<string>` given a `number`, `Strs` (`= Array<string>`) given an `Array<number>`, and a `Record<string, Same<number>>` returned as a `Record<string, string>` are E0204 at a `let`, a `const` or a `return` and E0211 at an argument, as `tsc` refuses all three (TS2322). The diagnostic still names the type the way the site wrote it. The same reading applies to a declaration in a sibling module under a named import and under a namespace import, so the answer does not depend on the spelling or the file. Before 0.1.170 these bodies were left unread, which refused `Id` against `Name` and `L<string>` against `Array<string>` while accepting `Same<string>` given a `number`. A body of any other form is the declaration's own type and is not read through: a record and a union of either kind, which are compared by identity (D49), an `extern_ts` or `typeof` body, a function type, and any body carrying a `where`, which is its own type (D39). A transparent declaration whose body refers to itself, directly or through other transparent declarations and second names (`type F = Array<F>`), keeps its name: it is not expanded and is compared by identity, as before 0.1.170 (record 176; comparing two such types by shape is G455). Nominal typing between two records that merely share a shape is untouched (D49): `type C = { x: number }` is still not an `A`. The nominal alternative, reading `type B = A` as a new type distinct from `A`, was refused because the six `Record<string, T>` and `Array<..>` aliases in the corpus would have become nominal with it and Glyph would reject programs `tsc` accepts, while zero bare-path aliases existed to be protected by it. A `where` over an alias of a record or union is E0300 like the inline spelling (D39): the refusal reads the shape the base resolves to, since under this rule the alias and the record are one type. *[verifiability: the guarantees on a type do not depend on which of its names a site reached it by, or on which file the name was declared in]*
- **D49. A declared record or tagged union is its own type: a value of any other declaration is not one.** A `type` whose body is a record (`type User = { id: string }`) or a tagged union (D8) declares a type with an identity, and the checker compares two declarations by that identity, not by their fields. A value whose type is another declaration is refused where this one is declared, E0204 at a `let`, a `const` or a `return` and E0211 at a call argument, even when its fields would satisfy the record. Another declaration is any of: a second record or union of the program, local or imported, whatever its shape (`type C = { x: number }` is not a `type A = { x: number }`); a stdlib type whose shape the checker models (`url.Url`); and the five prelude containers `Array`, `Record`, `Option`, `Result` and `Nullable`, whatever their arguments. So `let user: User = json.parse(body)` is refused, and so is `let s: Sized = xs` with `type Sized = { length: number }` and `xs: Array<string>`. The reason is the runtime: a declared record or union has a descriptor whose `is` and `parse` are the type's own definition of membership, and they refuse what this rule refuses. `Sized.parse(["a", "b"])` is an `Err`, because an array is never a record, and a record is closed unless `@open`, so a map holding other keys fails it. A checker that accepted a value the type's own validator rejects would give one type two answers. What this rule does not decide: an object literal, which has no declaration and is compared field by field (D10), each key it writes being a field the declared record declares (D57); a second name for a declaration, which is that declaration (D46); a record with no fields, which any object satisfies; a `type` whose body is a primitive, `unknown`, a type parameter or a generic application, which is the type its body names with the arguments substituted (D46): `Headers` under `type Headers = Record<string, string>` is that `Record`, and a value is compared with it as with the `Record`; an `interface` (D34), which has no descriptor and is satisfied by any value with its members; and a `type` whose body is `extern_ts` (D29) or `typeof` (D32), which the checker does not read, so a pairing with one on either side is left to `tsc` (G490). The other direction is decided (G536): a value whose type is an interface of the module, written plain (`HasV`) or as an application (`Box<number>`), is another declaration where a record with fields or a tagged union is declared, and is refused there in either spelling, while a record with no fields takes it. `tsc` accepts it against a record of matching fields, so this refusal is Glyph's own, for the reason above: the record's validator is its membership and the interface value never passed it. Where a `Nullable<X>` is declared it is the pairing against `X` (D45). Where `Option`, `Result` or `Array` is declared it is refused in either spelling (G586), since those are prelude containers and so other declarations; an `Option` or a `Result` is not compared member by member against its emitted `{ tag, value }` object, which is the runtime encoding and not a set of members (D18), so an interface that spells `tag: "Some"` is refused too. `tsc` refuses all of these pairings. Where a `Record<K, V>` is declared it is decided as `tsc` decides it: a `string` or `number` key refuses it, since an interface has no implicit index signature (TS2322), unless `V` is a type the checker does not read (an `extern_ts` or `typeof` body, written in place or reached through a name, or a `Nullable` of one). `tsc` may read such a `V` as `any`, and `Record<string, any>` takes any object type, so that pairing is left undecided, as every opaque body is. A string-literal union key accepts it exactly when every literal is a required member holding a `V`. A refined key is left to `tsc`. Before this the verdict turned on the spelling: `HasV` was refused where `Ord` was declared and passed where `Record<string, number>` was, and `Box<number>` the other way round. TypeScript compares all of these by shape, so some programs `tsc` accepts are refused here: declare an `interface` when the members are the contract, and a record when the validator is. The reverse pairing, a declared record or union where `Array`, `Option` or `Result` is declared, falls under the same rule and the checker applies it (G293); where a `Nullable<T>` is declared the pairing is the one against `T`. Where a `Record<string, V>` is declared, a declared record is compared field by field against `V`, because a map's validator accepts a closed record exactly when every value it holds is a `V`: a required field whose type is not a `V` is refused, and a record whose fields are all required `V`s is accepted. An `@open` record is refused unless `V` is `unknown`, since the keys it admits beyond its fields hold values no validator checked. A tagged union is refused wherever any `Record<K, V>` is declared, because a union has no fields in Glyph and its runtime encoding is not a contract. An optional field, and a `K` other than `string`, are not decided here (what an optional field accepts at run time is D45's rule): the map's validator and `tsc` disagree about them, and `tsc` is left to answer. *[verifiability: the checker and the type's own validator agree on what belongs to it; greppability: the declaration a value belongs to is the one its annotation names]*
- **D50. A runtime check refuses a value nested more than 1000 objects and arrays deep.** Every check the compiler generates (`is T` in a pattern, `T.is`, `T.parse`, `T.schema` and its `array()`, `json.parse<T>` and `json.parse_with`) counts the objects and arrays it enters as JSON nests them: the root object or array is depth 1, an `Option` or a tagged-union `{ tag, value }` object counts like any other object, and a part the type does not walk (an `unknown` field) is not entered and not counted. A value that makes the check enter a container deeper than 1000 is refused. `is` and `T.is` answer `false`, which is the true answer to the question they ask: a value past the limit is not one the check for `T` accepts. `parse`, `T.schema.parse` and `json.parse<T>` answer `Err` with one issue, `code: "depth"`, message `nested more than 1000 objects and arrays deep`, at the path a `type` issue for that part would carry (`[]` at the root), and with nothing else beside it. A cyclic value is infinitely deep, so it is refused the same way. The limit is one named constant, `MAX_DEPTH`: defined once in the internal runtime module the emitted checks import, and public as `std/schema`'s `MAX_DEPTH`. The emitted checks name it rather than writing the number, so one grep finds the contract. Each check takes the depth of its value as a parameter (`T.__is(value, depth)`), compares it once per container it enters, and past the limit throws a private sentinel. The sentinel is caught where the issue's path is known: at a public `is`, and at each field of a `parse` whose part can throw it. Every catch rethrows anything that is not the sentinel, and nothing else is caught. The sentinel and the helpers that throw and catch it live in an internal runtime module no Glyph program can import, so Glyph code can neither throw it out of a check nor forge a depth refusal; only `MAX_DEPTH` is public. A `RangeError` is never caught: catching it would hide the caller's own overflow and would make the same value pass or fail depending on what is on the stack above the call, which is a refusal no document can state. Before this, the checks recursed once per level and a document a few thousand levels deep threw `RangeError: Maximum call stack size exceeded` out of `is`, `parse` and `json.parse<T>` alike (G369); 1000 is under a quarter of the shallowest overflow measured, which leaves the caller's own stack its room and holds at half node's default stack. `JSON.parse` has no limit, and the untyped `json.parse(text)` and `json.parse<unknown>` decode any depth and check nothing. `==` is not covered: an equality cannot refuse, so a depth limit would make it answer wrong (G378). *[verifiability: a check answers for every input, and the one refusal it adds is a documented number with its own issue code]*
- **D52. The text of a SQL query is fixed when the program is written.** The `sql` parameter of `std/sqlite`'s `Db.exec`, `Db.run`, `Db.query` and `Db.query_one` is a `sqlite.Sql`, and a value passes where a `sqlite.Sql` is declared (any parameter, `let`, `const` or `return`, so a wrapper declaring `sql: sqlite.Sql` holds its callers to the same rule) only when it is a **constant string expression** or already a `sqlite.Sql`. Constant means: a string literal with no `${}`, triple-quoted included; a literal whose every `${}` holds a constant; `a + b` of constants; a `match` whose every arm value is constant (the column picked from a fixed list: a finite set of texts, all written in the program); a module `const`, or a local `let` that no `mut` anywhere in the module reassigns, whose initializer is constant. A name is followed to its initializer, so the `let` hoist (`let q = "...${name}..."`, then `db.query(q, [])`) is judged by what `q` was built from, not by its shape at the call. A parameter, a call result, a field read, a `mut`-reassigned local and any interpolation or `+` of one is not constant, and is E0239. A constant imported from another module counts only when that module declares it a `sqlite.Sql`, because this module cannot read its initializer. The check reads where the text came from, not its type: as a type, `sqlite.Sql` is `string` in both directions, a value of another type there is E0211, and the emitted TypeScript writes `string` (the runtime declares `export type Sql = string`). E0239's message names where the text is run and the name or expression it is built from, and its help rewrites a literal (or the `let` holding one) at a `Db` call to `?` placeholders with the parameter array, only when every run-time value stands where SQL takes a value: a quoted literal that is exactly `'${x}'`, or an unquoted `${x}` directly after `=`, `==`, `!=`, `<>`, `<`, `>`, `<=`, `>=`, `LIKE`, `GLOB`, `LIMIT` or `OFFSET`, or as an item of a `VALUES (...)` or `IN (...)` list. Anywhere else (`FROM ${table}`, `ORDER BY ${col}`) a `?` would be a syntax error or would silently change the query, so the help says to pick the name with a `match` whose arms are constant strings. `exec` takes no parameters, so its help moves a one-statement literal to `run`; a literal holding several statements is not rewritten, since `run` prepares only the first. Text that must be built at run time and that no `match` can list goes through `sqlite.from_trusted(t: taint.Trusted<string>) -> sqlite.Sql`, whose argument only `taint.sanitize` and `taint.trust_unchecked` produce. A primitive where a `taint.Trusted<T>` or `taint.Tainted<T>` is declared is refused at every position: E0211 at an argument, E0204 at a `let`, a `const`, a `return` and a field. The rule is PEP 675's `LiteralString`, applied by Glyph's checker: a shape check at the argument (refusing only an interpolated literal there) was rejected because the `let` hoist and `+` defeat it, and making the parameter a `Trusted<string>` was rejected because it would make every constant query wrap itself with no safety gained. The other stdlib injection sinks are not covered: `regex` patterns need a `regex.escape` that does not exist yet (G409), `http.html` needs an escaping builder because its body is dynamic by nature (G410), and npm drivers take a plain `string`. *[verifiability: a run-time value cannot become query text without a named, greppable step; greppability: every query that is not a constant passes through `from_trusted`]*
- **D53. A lambda parameter's type is the one written, and an `is` arm narrows its scrutinee.** A lambda parameter may omit its annotation (`fn(p) { .. }`, D4). An omitted annotation means "not typed here": Glyph's checker judges no use of the parameter, the formatter prints it omitted, and the emitter writes the bare name so `tsc` infers it from the call site. A written annotation is the parameter's type, `unknown` included: `fn(p: unknown) -> number { return p + 1 }` keeps its `: unknown` through `glyph fmt`, is emitted as `(p: unknown)`, and `tsc` refuses `p + 1`. The two forms are told apart by whether an annotation was written, never by its spelling or its span. Inside a `match` arm whose pattern is `is T`, a scrutinee that is a name (a parameter, a `let` or a module `const`) has type `T` in that arm's body, when `T` is a primitive, a declared type, or one of the prelude containers an `is` check exists for, `Record<K, V>` and `Array<X>` (0.1.175, G415); the emitted `typeof` or descriptor check establishes it, and `tsc` reads it the same way. The name keeps its own type outside the arm. A name that any `mut` reassigns anywhere in its scope, nested lambdas included, is not narrowed, since a lambda called inside the arm could rebind it while the arm runs; a `const` is never reassigned (E0212). The same predicate, a binding no `mut` reassigns, is the one D52's constant `let` reads. So `match v { is User => v.nmae, else => "?", }` is E0210, and so is `match v { is Array<string> => v.lenght, else => v, }`. A key read on a map, `m[k]` or `m.name`, declared or narrowed, is E0224 unless the map's `V` is `unknown` (directly or through an alias). Both the map and its `V` are read through second names and transparent declarations (D46), so a local alias, a chain of them and a sibling's alias imported by name or through a namespace get the answer the written-out `Record` gets: an absent key yields `undefined`, which `unknown` already admits, so that read is sound and is typed `unknown`, and any use of it has to narrow first (record 134). So `match v { is Record<string, unknown> => v[k], else => v, }` passes and `is Record<string, number> => v[k]` is E0224. An omitted annotation takes a type from its position under D55; where the position supplies none it stays not typed here. *[verifiability: a diagnostic is computed from what the program wrote, and judges the type the program has established]*
- **D55. An omitted lambda annotation takes its type from the position the lambda stands in.** A lambda parameter written without an annotation (D53) has the type of the matching parameter of the function type expected where the lambda stands. Seven positions expect one: a call argument, where the expected type is the callee's parameter type with the callee's type parameters bound from the arguments written before the lambda and from any written type arguments (`array.map<T, U>(xs: Array<T>, f: fn(T) -> U)` binds `T` from `xs`, so `array.map(users, fn(u) -> string { .. })` types `u` as the element of `users`); an annotated `let`; an annotated module `const`; a `return` in a callable with a declared return type; the tail value of such a callable, the last expression of its body, which the emitter writes as a `return` and the checker reads through the same code; a field of a record literal standing in one of these positions where the declared type is a record with that field; and an attribute of a component element, which is a field of the one props object the element passes, when Glyph knows the component's props record. The built-in `Array<T>` methods that take a callback supply its parameter types over the receiver's element type (`(T, number, Array<T>)` for the per-element callbacks, the seed's widened type then `T` for `reduce`, `(T, T)` for a comparator), so `users.map(fn(u) ..)` types `u` as `array.map(users, fn(u) ..)` does; a guarantee must not depend on which spelling calls the function, and the E0238 help reads the same slot. The function type is read through second names and `type` aliases (`type Show = fn(User) -> string`). A seed written as a fresh literal binds its widened type, as a binding does (`array.fold(xs, "", fn(acc, x) ..)` gives `acc` the type `string`, not `""`), and each lambda's own signature binds what it can for the arguments after it. Where the position supplies no function type, or the matching parameter type is one the checker does not know (an element type the checker has not typed, such as `Issue.path`'s, or a DOM element's attribute, whose type is React's), or it names a callee type parameter nothing has bound yet, the parameter stays not typed here, judged by no rule, as D53 left every omitted parameter. A written annotation is the parameter's type whatever the position expects. An omitted annotation still emits the bare name, and `tsc` infers the same type from the same position; where the emitter reads an operand's type, a parameter now typed can take a more direct form with the same behaviour (`===` for two strings where it wrote `__glyph_eq`). So `array.map(users, fn(p) -> string { return p.nmae })` is E0210, and `return "${p}"` there is E0237 (D54), under `check --no-tsc` as well as `check`. A lambda's own type carries its parameters' contextual types, and hover on a use of one shows it. *[verifiability: the checker judges the type `tsc` and the run will give the parameter, so an omitted annotation is no longer a place where Glyph's own rules stop applying; greppability: the type is read off the one declaration the lambda is passed to]*
- **D56. A built-in method that answers absence with `undefined` is refused; `Option` through `std/*` is the one spelling.** A call to a method of an `Array<T>` or a `string` whose TypeScript return type can hold `undefined` or `null` is E0242: `find`, `findLast` and `at` on an array, `at`, `codePointAt` and `match` on a string. The list is the generated `absent` column of the built-in method rows, read off TypeScript's declarations, and the generator fails on an absent method with no named replacement, so a TypeScript that adds one fails CI until it gets an `Option` spelling. It fires in every position (a statement, a `let`, an argument, a `${}`, the operand of `??`, the receiver of `.name` or `?.name`), on a receiver reached through an index or through a `?.` call, and the call's own type stays unknown, so what reads it adds no second diagnostic. Not judged: a call under `mut`, which is E0241 alone; `pop` and `shift`, which change the array and are E0240's (D5); and a receiver the checker types `Unknown`, such as an npm value. The replacements return `Option<T>`: `array.find(xs, f)`, `array.find_last(xs, f)`, `array.get(xs, i)` (which answers `None` for a negative index, so `xs.at(-1)` is `array.get(xs, array.len(xs) - 1)`), `string.char_at(s, i)` and `string.code_point_at(s, i)` (the whole code point at a code-unit index, see the strings rule above), and `regex.matches(p, s)` or `regex.captures(p, s)` for `match`. The help is computed from the call, and a `??` default becomes the `None` arm of a `match`. `glyph fix` writes the array rewrites (`find` and `findLast`, and `at` for an integer literal index, a negative one only on a place) only where the call's value is used up on the spot: an expression statement, a `??` default (written as the `match`), a `match` scrutinee, or a `let`, argument or `return` declared `Option`. Anywhere else (a `let` with no declared type, a member or `?.` read, a slot declared as the element type, an operand, a `${}`) it declines and names the position, because the name would go on holding an `Option` where the program read the element, and a later `??` on it would hand back the `Option` with every check passing (decision record 155, F1). It adds `import std/array` when no other binding has that name, and the help says to import it under another name when one does; it declines the string rewrites, whose `Option` forms answer differently. Rejected: typing the method `Option<T>`, since the method returns a bare `T | undefined` at run time and the same text would mean two things to a TypeScript reader and to Glyph, and one operation would have two spellings; `Nullable<T>`, which is `null`, not `undefined`; and a third "may be missing" type. *[greppability: one spelling for each lookup, so `grep "array.find"` finds every one; verifiability: a value that may be missing is a type the checker holds to a `None` arm]*
- **D57. An object literal names only fields its declared record type declares.** A key written in an object literal must be a field of the record type the literal is written as. A key that type does not declare is E0210 at the key: the same code and the same fact as a read of that field (`b.nik`), with the same "did you mean" when a declared field is close to it. It is judged at every position where the checker relates a written literal to a declared type: a `let` or `const` annotation; a `return` under a declared return type; a call argument, a variant payload (`Loaded({ .. })`, in any import spelling) and a call through a member function included; `mut x = { .. }` and `mut x.f = { .. }`; a field of a literal standing in one of these positions; an element of an array literal under a declared `Array`; the argument of `Some`, `Ok` or `Err` under a declared `Option` or `Result`; an arm of a `match` standing in one of these positions (an arm expression or the tail of an arm block, at any depth); and the values a lambda with no written return type returns where its position declares a return type (D55). A lambda passed where the slot's return is a type parameter the lambda itself binds (`array.map(xs, fn(x) { .. })`) declares nothing, and its tail is not judged, as `tsc` does not judge it. Where nothing compared a written value before, its values are compared too: the argument of `Some`, `Ok` or `Err`, a variant payload, a written object or array arm of such a `match`, and an object or array literal written to a `mut` target. Only a value written out there is compared (an object or array literal, or a string, number or bool literal); a name keeps the treatment it had, because the type the checker records for it does not follow an `is` arm's narrowing. Each is a refusal `tsc` makes (TS2322): E0211 for a variant payload, which is a constructor argument, and E0204 elsewhere; a payload or parameter typed by a type parameter nothing has bound is not compared, and a container the relation already refuses as a whole draws that one refusal. The declared type can be a record (local, imported, or generic with its arguments substituted), an `interface` (D34), an `@open` record, or a stdlib record the checker models; `@open` governs decoding, not construction, and `tsc` refuses the extra key there too. Not judged: a field that arrives through a spread; a value that is not a literal, so a binding holding a wider record is accepted (width subtyping, as `tsc` accepts it); and a declared `Record<K, V>`, `unknown`, type parameter, or type the checker does not know. A call argument is judged against the parameter as declared, so a field typed by the callee's own type parameter is not judged, whatever the call binds it to. `Some({ name: "x", extra: 6 })` where `Option<Opt>` is declared is refused although `tsc` accepts it: `tsc` infers `T` from the literal there, and the field is just as unreadable. The help offers three repairs: rename the key to the declared field, delete it, or declare it in the type. `glyph fix` renames it when exactly one declared field is one character away and the literal does not already write that field. When the literal does, the message leaves the suggestion out and the fix declines, since the rename would write that field twice. Rejected: E0204, which is about the whole value and would underline the whole literal, and a new code for the fact a read already reports. *[verifiability: a misspelled optional field (`nik` for `nick`) used to drop its value silently on every surface that checks without `tsc` (the editor, the MCP tools, the edit gate); it is refused on all of them now]*
- **D58. Inside a generic function, its own type parameter is a type of its own.** In the body of `fn f<T>` (a `component` with type parameters too, and any lambda inside either), `T` is whatever a caller chooses, so the checker assumes nothing about it. A `T` is accepted where `T` itself is declared and where `unknown` is; where a `Nullable<X>` is declared it is compared against `X` as D45 says, so a `T` stands where `Nullable<T>` is declared. Anything else the checker can tell apart from it is refused in both directions and at every depth: a `string`, a `number` or a `bool`, a string-literal union, a record, a function, a tagged union, a prelude container, an interface, a declaration whose body is one of those, and another of the function's parameters. `fn g<T>(x: Array<T>) -> Array<string> { return x }` is E0204, and so is a `Box<T>` whose field is an `Array<T>` where `Record<string, Array<string>>` is declared; `tsc` refuses both (TS2322). A parameter is identified by the declaration that owns it and its name, never by the name alone (G314). A `T` that a callee declares and a call leaves unbound (`wrap([])`) is not the enclosing function's `T`, and nothing is decided about it at that call, as `tsc` infers `never` for it and accepts. A function value typed with the enclosing `T` (`f: fn(T) -> T`) does not choose `T` when it is called, so `f(5)` is E0211. A `type` declaration's own parameter is never decided where a value is checked: it reaches a value only through a generic declaration written without its arguments, which E0233 refuses. A bounded `T: Named` is decided where it is declared, since a caller may choose any `T` the bound admits, so a `Named` returned where `T` is declared is refused. A bound is resolved like any other type annotation (G263): `fn c<T: Nope>` with `Nope` declared nowhere is E0103 and `T: l.Nope` is E0105, as `tsc` reports TS2304 and TS2694, and an import used only in a bound is a use. Inside the declaring function and any lambda inside it, a value of `T: B` passes where `T` or `unknown` is declared, and anywhere else it is compared as a `B` found there, by the same relation at every depth: `T: Named` returned where `Named` is declared passes, where `Other` is declared it is E0204 (TS2322), `Array<T>` passes where `Array<Named>` is declared, a `T: Named` passes where `Nullable<T>` or `Nullable<Named>` is declared (D45), and a bound that is another of the function's parameters (`<T, U: T>`) passes where that parameter is declared. Because the bound is compared as it is, `T: HasName` for a structural interface `HasName` is refused where the record `Named` is declared, as a `HasName` value is (D49); `tsc` accepts that one, and the guarantee for a bounded parameter is the guarantee for its bound. A member read, a method call, an index read and a `for` over a value of `T: B` are checked against `B` as for a value of type `B`: `x.nmae` on `T: Named` is E0210 naming `name` (TS2339). A field of it in a map is compared the same way, so a `Box<T>` passes where `Record<string, Named>` is declared and is refused where `Record<string, string>` is. A chain of bounds that are bare parameters of the same list and comes back to its start (`<T: U, U: T>`, `<T: T>`) resolves to nothing and is E0114, as `tsc` refuses it (TS2313); an F-bound such as `<T: Cmp<T>>` is not a cycle. A bound written as an `extern_ts` or `typeof` type keeps the treatment every bounded parameter had before G263, since the checker does not read either type and `tsc` judges it: the parameter is decided only against another of the function's parameters, nothing is read off it as a receiver, and a field of it keeps the map rule D49 gave every parameter before this (refused where a `Record<string, V>` is declared unless `V` is `unknown` or that parameter). Where a bound is instantiated (a call, a written type argument, a type application, an element of a bounded component) it is checked by D72; inside the declaration, an application `Box<U>` of a bounded declaration reads its own `U` through `U`'s bound, so it passes with `U: HasName` and is E0251 with an unbounded `U`. A value of `unknown` where `T` is declared is refused (D65). Not decided: a `void` and a type the checker does not read (an `extern_ts` or `typeof` type). The rule holds at a tail value as it does at `return` (G457): `fn tail_s<T>(x: T) -> string { x }` and `fn j<T>() -> Array<T> { [1] }` are E0204, as their `return` spellings are. Rejected: deciding a parameter by its name, which made a callee's unbound `T` and the caller's own `T` one type and refused `return wrap([])` inside `fn f<T>`. *[verifiability: a generic function's body is held to what every caller may choose, on every surface that runs without `tsc`]*
- **D65. `unknown` is assignable only to `unknown`.** A value whose type is `unknown` (the written word, a `type` whose body is it under D46, or the unchecked read `json.parse(text)` with no type argument) stands only where `unknown` is declared. Where any other type the checker decides is declared, it is refused at every depth the relation reads: E0204 at a `let`, a `const`, a `return`, the last expression of a body and a record field, E0211 at an argument. `let s: string = u` is refused, and so are `Array<unknown>` where `Array<string>` is declared, `Result<unknown, Array<Issue>>` where `Result<User, Array<Issue>>` or `Result<T, Array<Issue>>` is declared, an `unknown` where an enclosing type parameter (D58), `void`, `never` or a function type is declared, and one where `Nullable<string>` is declared. `Nullable<unknown>` takes one, since it is `unknown | null` (D45). A function type returning `void` still takes a function returning `unknown`, as `tsc` reads it: `fn() -> unknown` stands where `fn() -> void` is declared. The way from `unknown` to a type is a check: `json.parse<T>(text)`, `T.parse(value)`, or a `match` arm with an `is` pattern, and the help says so. Not judged: a value the checker has no type for (a member of a package it does not read), a parameter a callee declares and a call leaves unbound, and a declared type it does not read (`Schema<T>`, `Component<P>`, `infer_output<S>`, an `extern_ts` or `typeof` type, a package type). That last carve-out includes React's types: an `unknown` used as a JSX child (`<p>{u}</p>`) or as an attribute of a DOM element (`href={u}`) is not judged, though `tsc` refuses both (TS2769). An `is` pattern naming a type parameter of the enclosing function (`is T`, `is Array<T>`) is E0304 from the checker, and the arm's name has no type there, so no E0204 follows from it (record 194). The parameter types of a function value are not compared yet (G491), so `fn(string) -> void` where `fn(unknown) -> void` is declared still passes, though `tsc` refuses it. `tsc` refuses every pairing this refuses (TS2322, TS2345); before this rule only `tsc` did, so `glyph check --no-tsc` and the agent gate let them through. *[verifiability: an unchecked value cannot become a checked type on any surface, with or without `tsc`]*
- **D66. A `let` with no annotation holds the type of its initializer, as `tsc` reads it.** `let y = 1` holds a `number` for the rest of its scope, and `mut y = "s"` is E0204 (D5), as `tsc` refuses it (TS2322). The type is the initializer's with each fresh literal widened (`let x = "a"` is a `string`, `let xs = ["a"]` an `Array<string>`), and with the literal an unannotated `const` holds widened too, as `tsc` widens it at the `let` the emitter writes: `const DIR = "out"` then `let d = DIR` is a `string`, and so is a `let` over `const M = match b { true => "read", false => "write" }` (G512). An annotated `const` keeps its type (`const M: Mode = "read"` then `let m = M` is a `Mode`). What the initializer leaves undecided stays undecided: `let o = None` and `let xs = []` take any later value of their shape. Rejected: comparing only an annotated binding, which would make the guarantee depend on whether the author wrote the annotation, and leaves `let y = 1` then `mut y = "s"` to `tsc`. *[verifiability]*
- **D72. A bound is checked where it is instantiated.** With `fn label<T: HasName>(x: T)`, a call binds `T` from its arguments as before, and the type it binds is then compared with the bound with every binding put in, so `T: Cmp<T>` bound to `Ord` checks `Ord` against `Cmp<Ord>`. A binding outside the bound is E0211 at the first argument whose own type is outside it, with the bound as the expected type and a note naming the parameter: `label(o)` with `o: Other` is "expected `HasName`, found `Other`", and the note says "`T` takes `Other` from this argument, and its bound `HasName` requires `name`, which `Other` does not have". `label({ name: "x", extra: 1, })` is accepted, since the inferred `T` is the literal's type, as `tsc` infers it. Two literal candidates join (D92) and the join is compared with the bound, never widened past it: under `T: Mode` with `type Mode = "a" | "b"`, `mb("a", "b")` is accepted and `mb("a", "c")` is E0211 at `"c"`, found `"c"`, since a literal is shown as its literal where the bound is a literal set. A type argument written on a call (`label<Other>(o)`) and a type application in any type position (an annotation, a parameter, a return, a field, an alias body, a bound, nested as in `Array<Box<Other>>`) are E0251: ``type argument `Other` does not satisfy the bound `T: HasName` of `label`: `Other` has no field `name` ``. It is its own code, not E0233's, because E0233 is the wrong number of type arguments, a different mistake with a different fix. `label<HasName>({ name: "x", extra: 1, })` is then judged as the argument of a parameter declared `HasName`, the same verdict `let h: HasName = { name: "x", extra: 1, }` gets. An element of a component whose one parameter is its own bounded parameter (`component Show<T: HasLabel>(p: T)`) is checked against the bound exactly as for `component S2(p: HasLabel)`: `<Show />` is E0211 missing `label`, `<Show other="y" />` is E0210, and `<Show label={5} />` is E0211. The bounds of a project sibling's declaration are read on its side, so both import spellings get the same verdict, and a bound that is a sibling's `interface` is judged by that interface's members as a local one is (D34, G541). Not judged: a binding the checker cannot type, an object literal against a `Record<string, V>` bound (G454's rule), an `extern_ts` or `typeof` bound (record 191), a standard-library function's type parameters, a function referenced and not called, and a component whose bound names its own parameter. `tsc` refuses the same programs (TS2345, TS2344, TS2769). *[verifiability: a bound guarantees at the call what it promises inside the body; greppability: one code for one mistake]*
- **D74. A project can ban an import path, and the `glyph` key is a closed schema.** `glyph.banned_imports` in the project's `package.json` maps an import path as written after `import` (an npm package, scoped included, a `std/` module, or a project module) to an object with `use` (required: the import to write instead), `reason` (optional, one line) and `allow_in` (optional: project modules that may still import it, an entry ending in `/` covering a directory recursively). A key bans its own path and every path under it (`axios` bans `axios/lib/core`, not `axios-retry`). A key is spelled as Glyph spells the import: a scoped package as `@scope/pkg` (which bans `@scope/pkg/sub`), and a Node builtin by its bare name (`fs`), since `node:fs` is not a legal import path; a `node:fs` quoted in an `extern_ts` body counts as `fs`. An import of a banned path from any module other than `use` and those `allow_in` lists is E0115 at the import path, and so is the same specifier quoted (`'`, `"`, or a backtick with no `${`) inside an `extern_ts` body, in either the expression or the type form. E0115 replaces the E0104 the same import would get when the package is not installed. Its help names `use` and never `allow_in`, and adds the `glyph query exports --module` line when `use` is a project or `std/` module, which that query answers for. The nearest marker governs a file (D41), so a nested project is not bound by an outer project's bans. The keys of `glyph` are `src`, `banned_imports`, and `glyph publish`'s `imports` and `audit`; any other key, any unknown field of a ban or of those two, a non-string `src`, a ban key that is empty, ends in `/` or holds a space or `*`, a ban with no `use`, a `use` that names no project module, `std/` module or declared dependency, a `use` that is itself banned, and an `allow_in` entry naming no module or directory under the source root are E0116, reported in `package.json` at the key or value with its JSON path. A `glyph` key with any value still marks the project, so its problems are reported rather than the directory quietly ceasing to be a project. Not seen: a specifier computed inside raw TypeScript, hand-written `.ts` files, npm code importing the package itself, and a `package.json` that does not parse, which is not a marker at all (G551). Rejected: ignoring unknown keys, which lets one typo switch a policy off. *[verifiability: a project rule about which library to use is enforced by the compiler on every surface rather than by review; greppability: the rule lives in one file, and the escape hatch it closes is `grep extern_ts`]*
- **D77. An index read is typed as its element.** `xs[i]` on an `Array<E>` is an `E`, and `m[k]` on a `Record<K, V>` is a `V` where E0224 allows the read (today only where `V` is `unknown`). The container is read through aliases, generic aliases, imports and a bounded type parameter's bound, as a member read is, so `rows[0]` on `type Rows = Array<Row>` is a `Row`. Every use of the element is then checked as any other typed value is: `return xs[0]` under `-> number` with `xs: Array<string>` is E0204, so are `let n: number = rows[0][0]` and `let s = xs[0]` followed by `return s`, `xs[0].lenght` is E0210, and `take(xs[0])` where `take` declares a `number` is E0211. `tsc --strict` refuses each (TS2322, TS2551, TS2345): the generated tsconfig leaves `noUncheckedIndexedAccess` off, so `__glyph_index`'s `C[K]` is `E`, not `E | undefined`, and Glyph's index throws a `RangeError` out of range rather than giving `undefined` (record 159), which is why the element is not an `Option`. Not decided: an index on any other receiver (a `string`, an unbounded type parameter, an interop value, a type whose body the checker does not read), which stays `Unknown`, and the element of an `Array` written with no argument. The write side, the place `mut xs[i] = v` writes, reads the element type from the same helper (G501). *[verifiability: a typo in a field read off `xs[0]` is caught by the editor, `glyph check --no-tsc` and the agent tools, not only by `tsc`]*
- **D92. A type parameter bound by two string-literal candidates holds both.** A call binds each type parameter from its arguments in order, and the first binding stands, with two exceptions. A later `string` candidate replaces a string-literal union bound earlier, and a later string-literal candidate joins one bound earlier: `fn pair<T>(a: T, b: T)` called as `pair("a", "b")` binds `T` to `"a" | "b"` and is accepted, as `tsc` accepts it, where keeping `"a"` refused the second argument. An `int` is a `number` to the checker, so an `int` then a `number` binds a `number`. Any other second candidate is compared against the first, so `array.concat([1, 2], ["a"])` is E0211 at `"a"` (TS2322 under `tsc`). `array.concat` takes two arrays of one element type, the runtime's `concat<T>(a: ReadonlyArray<T>, b: ReadonlyArray<T>)`. An array's own `xs.concat(..)`, which TypeScript declares over `T | ConcatArray<T>`, takes each argument as an element or an array of elements of the receiver's `T` and refuses anything else with E0211, a nested `Array<Array<T>>` included, as `tsc` refuses it (TS2769). Not joined: a named union bound first (`m: Mode`, then `"c"`) keeps first-wins (G648). *[verifiability: an array of the wrong element type is refused by the editor, `glyph check --no-tsc` and the agent tools, not only by `tsc`]*
- **D93. A stdlib row with an optional parameter is published as its call forms.** A Glyph function type cannot spell an optional parameter, so no single signature is true for a stdlib row that has one: `fn(string, number, string) -> string` for `string.pad_end` says the third argument is required while `string.pad_end(s, 4)` is legal. `glyph llms --json` gives such a row `signature: null`, a `signature_absent` naming the parameter that may be left out ("parameter 3 may be left out, and a Glyph function type cannot spell an optional parameter"), and `call_forms`, one complete function type per legal arity, shortest first: `["fn(string, number) -> string", "fn(string, number, string) -> string"]`. A form that carries a `?` keeps it, and the row keeps its `signature_partial` (`json.stringify`). Coverage counts a row by its forms: modeled when every form is complete, partial when any carries a `?`. The rows are read off the checker's table, and a test pins the list, so a row that gains an optional parameter fails until it is published the same way. Today they are `array.slice`, `collections.deque`, `json.stringify`, `set.create`, `string.index_of`, `string.pad_end`, `string.pad_start` and `string.slice`. *[verifiability: an agent reading the published table is not told a legal call is wrong]*

## Composite literals

- **D10. No object literal shorthand.** `{ post, comments }` is a syntax error; write `{ post: post, comments: comments }`. Cost: keystrokes. Benefit: `grep -n "post:"` finds every field assignment. There is also no `TypeName { ... }` prefix on the literal: the value is the braces alone and the annotation on the `let`, the parameter or the return type is what says which record it is. Writing the name in expression position is E0228, and the message names the construction the declaration has; written with the braces on the same line, `Order { ... }` is E0013 at parse (D1). **An object literal is typed as the structural record of the fields it writes**, so the annotation and the value are compared rather than the value being taken on trust: a required field the literal does not write (the diagnostic names the missing fields, and lists them in `missing_fields`), a field whose value has the wrong type, and a record written where a `string`, a `number` or a `bool` is declared are each E0204 at a `let`, a `const` or a `return` and E0211 at a call argument, and the diagnostic names the declared type by its own name. The comparison is structural, which is what TypeScript does with the same pairing: a literal carrying a declaration's fields satisfies it whatever the declaration is called, and the nominal rule (D49) keeps deciding two names, of which a written literal has none. Each field is compared by the same rule at every depth, so a nested record, a declared name and a string-literal union inside a record are decided as they are at the top, and so are a declared record passed where a structural one is declared, an interface's members (an interface declared in the same module; an imported one's member set does not cross a module boundary) and a function's return, though not its parameters. A field the value holds as optional is refused where the declaration requires it, and a record whose fields are all optional refuses a value sharing none of them (TypeScript's weak-type rule, TS2559); a value with no fields at all is accepted there, as TypeScript accepts it. An extra field the declaration does not have is accepted on a value of a record type, since width subtyping is the rule the comparison applies; a key the declaration does not have, written in the literal itself, is E0210 (D57), as TypeScript refuses an undeclared key on a fresh literal. A literal holding a `...spread` has no type at all, because the spread's fields are not written out and a record built without them would report a field missing that the value carries. A binding with no annotation takes the literal's type, with a field whose value is a fresh string literal widened back to `string` exactly as the emitted TypeScript `let` widens it, so the binding carries the type the program that runs has. An unannotated `const` takes the same record type, its fields widened the same way, since a TypeScript `const` widens a property as a `let` does (D20, 0.1.166). *[greppability, verifiability]*
- **D11. Spread allowed in arrays and objects, position-flexible.** `[...xs, a, b]`, `[a, ...xs, b]`, `[a, b, ...xs]`. Same for objects. Multiple spreads in one literal allowed. *[TS compatibility]*
- **Object keys: an identifier or a quoted string.** A key is an identifier/keyword, or a quoted string for names that are not identifiers (`{"Content-Type": x}`). The canonical form quotes a key iff it is not a valid identifier, so `{"foo": x}` formats to `{ foo: x }`. Interpolation in a key (`{"${e}": x}`) is rejected — there are no computed keys. Shorthand is still forbidden (D10): the value is always written.

## JSX

- **D6. JSX is a parallel sub-grammar; directives are regular elements.** JSX is entered after `<` in expression position. Attribute values: string literals or `{expr}`. An attribute may also be a **prop spread** `{...expr}`, which merges the object `expr` into the element's props (the react-hook-form `{...register("name")}` idiom); it lowers to an object spread inside the emitted `createElement` props. Children: elements, text runs, `{expr}`. Names `if`, `else`, `for`, `match`, `case` are reserved as element names — they parse as ordinary elements and the typechecker treats them as compiler directives. Positional attributes allowed before named ones (`<for user in={users}>`). **`<case>` is the one directive whose positional attribute is a pattern, the same pattern a `match` arm takes**, parsed by the arm's own pattern parser: `<case Loading>`, `<case Loaded(items)>` binds a positional payload, `<case Loaded({ users, total })>` binds a record payload's fields (with `{ users: u }` renames and D44 nesting), `<case Loaded(r)>` binds the whole record, and `<case else>` is the catch-all. A `<match value={v}>` is a value-level `match` written in JSX: each `<case>` is an arm whose body is what the case renders, so the bound names are typed from the payload, the pattern is checked against the payload's type (a field the record does not declare is E0210, an object pattern over a non-record payload E0204), coverage and reachability are the arm rules (a refutable `<case Done({ status: 404 })>` alone does not cover `Done`, E0200), and the lowering is the arm lowering. There is no `bind` attribute: `<case Loaded bind={users}>` is E0231, whose help writes the pattern for the payload's shape. `bind={x}` read a field called `x` off the matched value whatever the payload was, so over a positional payload it bound `undefined` under no type, a second spelling of a pattern with weaker guarantees than the first. The pattern form is the original design (`archive/SESSION_1.md` records `bind` as an earlier spelling that was dropped in favour of `<case Variant({ fields })>`); the implementation had shipped `bind` instead until 0.1.129. Attribute (and element) names may contain hyphens, so HTML/ARIA names work unchanged (`aria-label`, `data-testid`); a hyphenated attribute emits as a quoted object key. On an **intrinsic** element (lowercase HTML tag), Glyph's snake_case attribute names map to React's DOM prop names — `class` → `className`, and `on_<event>` → the camelCased `on<Event>` (`on_click` → `onClick`, `on_mouse_down` → `onMouseDown`); hyphenated `data-*`/`aria-*` are left verbatim. On a **component**, every attribute is a user-defined prop and passes through unchanged. An element is a component when its name is dotted (`<ui.Button>`, `<Ctx.Provider>`), whatever the case of its base, which is TypeScript's rule for a member-expression tag, or when an undotted name does not start with a lowercase letter; an undotted lowercase name is intrinsic. A dotted name's base resolves like any other name, and when the base is an imported module the member is checked against that module's exports. A component element's written attributes are compared with its props record (a wrong value is E0211, an undeclared attribute E0210), and a required prop it does not write is E0211 naming the missing props, unless the element holds a spread. A component element with no attributes passes `{}` as its props, never `null`, because React's types accept `null` for any component and would let a missing required prop through to run time. *[abstraction, verifiability; for `<case>`: verifiability, one pattern language with one set of checks wherever a value is matched; greppability, a payload field read in a case is spelled the way it is spelled in an arm]*
  **Text** (0.1.135, records 85 and 93). JSX text is the longest run of characters other than `{` and `<` between a tag or an `{expr}` child and the next one. It may span lines and is read as written: `'`, `"`, `\`, `/*`, `(`, `)`, `[`, `]`, `;` and `=` are text, and so is an `&` that does not begin an entity. The parser asks the lexer to scan it after an opening tag, a child element and an `{expr}` child, so no other component decides where JSX begins. A run is one child whatever the bracket depth, and it renders by Babel's rule: tabs become spaces, whitespace is trimmed only beside a line break (at the end of every line but the last and the start of every line but the first), lines left empty are dropped, and the rest are joined with one space. A run on one line is kept as written, so `{first} {last}` has a `" "` child between the two expressions and `<p>   x   </p>` keeps its spaces; a run that renders nothing, such as the indentation between two tags, is left out. Four things are refused in text, each as `E0012` naming what it refused. `}` and `>` would close an `{expression}` or a tag that is not open, as TSX refuses them; write `{"}"}` or `{">"}`. `//` is refused, which is stricter than TSX: Glyph read it as a comment before 0.1.135 and TSX reads it as text, and either reading would change what some program means; for text write a string child, `{"see http://example.com"}`. An entity (`&amp;`, `&#38;`, `&nbsp;`, an `&` followed by one or more ASCII letters, digits, `_` or `#` and a `;`) is refused because TSX decodes it and Glyph reads text as written, so the same characters would mean different things; write the character itself, or `{"\u{A0}"}` for an invisible one. A comment among children is a comment-only child, `{` newline `// note` newline `}`, which renders nothing; D14's placement rule applies to the child after it, and `glyph fmt` writes it in that form. `{}` with nothing inside is refused (`E0003`), and `{/* */}` is a lex error (`E0001`, D14). A `>=` glued to a tag's `>` is split where text follows the `>`, so `<p>=x</p>` is the text `=x`, as in TSX. No text follows the outermost element's closing `>`, so a `>=` there is still refused (`E0002`): `<p></p>== y` is not a comparison. *[verifiability: text means what TSX would make it mean, or it is refused; greppability: one spelling per character]*

## Annotations (session 3 additions)

- **D27. Annotations are `@<name> <args>` lines above declarations.** Annotations live one-per-line above a `fn`, `type`, `component`, `const`, or `module` declaration. Order is enforced by the formatter: it sorts by annotation *kind*, and repeated annotations of one kind (several `@example` lines, say) keep the order they were written in, since their sequence is the author's and sorting it buys nothing. Recognized v1 annotations: `@example` (D23), `@doc` (D26), `@redact` (D24), `@open` (a record type's runtime descriptor is strict by default — it rejects undeclared keys; `@open` opts out and allows extra keys), `@pure` (cf. D9 JSX purity classifier — required to make user fns JSX-callable), `@public`. The grammar accepts any `@<identifier>` form, so adding new annotations is forward-compatible. Unknown annotations are a hard error at compile time (no silent typos). *[abstraction — annotations carry compile-checked metadata that would otherwise be unverified comments]*
- **D23. `@example expr == expr` inline tests above function declarations.** Multiple `@example` lines per function are allowed. The test passes if the LHS evaluates equal to the RHS. The compiler runs every `@example` on `glyph build`; a failure fails the build. Property tests are a stdlib function (`test.property(predicate, generator)`), not a language primitive. *[verifiability — tests are colocated with functions; agents rewriting bodies cannot bypass them]*
- **D24. `@redact fields: [...]` marks PII fields for masking.** `@redact fields: [diagnosis, notes]` above a `type` declaration adds a `redact(value)` method to that type's runtime descriptor, returning a copy with those fields replaced by a redaction sentinel; you call it before logging or serializing (e.g. `json.stringify(User.redact(u))`). The field names are checked against the type at compile time (`E0219`), so a typo is a hard error, not a silent no-op. It is an opt-in helper you invoke rather than automatic boundary interception — masking every serialize/log site automatically would need a runtime value tag and is future work (`json.stringify(u)` on the raw value still leaks). *[verifiability]*
- **D26. `@doc """ ... """` blocks with `@run` fences are executable documentation.** Triple-quoted `@doc` blocks contain Markdown. ` ```glyph @run ` fenced blocks inside the doc are compiled and executed on every `glyph build`. Failed `assert` inside a `@run` block fails the build. Same compile-time-execution machinery as D23 `@example`. *[verifiability — docs cannot rot]*
- **D73. A name used in a test is a use of it.** A name written in an `@example` (the property form included) or in a `@doc` fence tagged `glyph @run` is an occurrence of the symbol it resolves to, read off the file as the example gate compiles it: the file with each test appended as a function and resolved by the same front end. `glyph_impact`, `glyph_references` and `glyph_dependencies` list it as a `CALLS` or `REFERENCES` site whose `context` is `example` or `doc_run` (null for a site in the program), whose entity is the declaration the annotation is written above, and whose position is where the name is written in the annotation. A rename or a removal breaks it with the code the gate's build raises (E0103 for a bare name, E0105 for a namespace-qualified one); a call in a test is decided per argument under an arity or a parameter-type change, as any call is. A test the analysis cannot read is named under `not_indexed`, never left out. Added in 0.1.186 (G506): before it, the two tools that say they list every site missed every site in a test, while the gate the edit then failed was the one place those names were ever resolved. *[verifiability: a site the build checks is a site the impact answer lists; greppability: one symbol, one list of uses]*

## Type-level operators (0.1.10)

- **D28. `infer_output<S>` derives a record type from a record of parsers.** `infer_output<S>` is a built-in type-level operator: for a record type `S` whose fields are parsers (any type with a `parse(input: unknown) -> Result<V, _>` method — `Schema<V>`, a user's own `Codec<V>`, …), it produces the record `{ field: V, ... }` — each field unwrapped to the type its parser *outputs* (a non-parser field maps to `never`). It matches fields **structurally**, so it is independent of what the validator type is named; there is no hard-coded `Schema`. It is written like an ordinary generic application, so no grammar change is needed; it is recognized by name in the prelude. It exists so a validator combinator's **output type is derived from its input shape** instead of being a second, hand-synced type parameter the caller must keep correct:

  ```glyph
  fn object_schema<Shape: Record<string, Schema<unknown>>>(shape: Shape) -> Schema<infer_output<Shape>> { ... }
  const user_schema: Schema<User> = object_schema({ name: string_schema(), age: number_schema() })
  ```

  Here `User` is now **checked** against the shape (a shape missing a field of `User` fails to compile), where the pre-0.1.10 `<Out>` parameter was merely trusted. `infer_output<S>` lowers to a single per-module TS mapped type that reads the `Ok` payload out of each field's parse result (`{ [K in keyof S]: S[K] extends { parse(input: unknown): infer R } ? (Extract<R, { tag: "Ok" }> extends { value: infer V } ? V : never) : never }`), referencing no in-scope type name, so `tsc` reduces it at each call site; the mapped-type machinery stays hidden behind the one greppable operator name. A combinator that dynamically builds a value of a shape-derived type carries one compiler-inserted boundary cast per `return`, emitted **only** when the return type mentions `infer_output` — the one place the runtime assembles the value from `unknown`. Every `return` the function emits carries it, including the ones a `match` in return position and a tail `E?` lower to. Honest generics (return type is `T`, `Result<T, E>`, `Array<T>`, …) emit with no cast at all. *[verifiability — the shape is the single source of truth and `tsc` enforces the derived type at every call site; greppability — one named operator instead of inline mapped-type syntax]*

  *History: shipped in 0.1.10 as `infer_shape`, welded to the literal name `Schema`; renamed and generalized to structural matching in the following release after review flagged the name overselling a `Schema`-only special case.*

## Interop escape hatch (0.1.14)

- **D29. `extern_ts("<raw TypeScript>")` is the escape hatch, in both type and expression position.** In **type** position it emits its string verbatim as the TypeScript type, chiefly for value-derived types (`type User = extern_ts("z.infer<typeof user_schema>")`) and any conditional/mapped TS type the parked general type machinery would otherwise require. In **expression** position it emits its string verbatim (parenthesized) and is typed `unknown` at the Glyph seam, so a grammar-hostile runtime idiom (`let t = extern_ts("Date.now()")`) stays reachable; being `unknown`, any use must narrow or validate it first. The construct is contained: `tsc` type-checks the raw TypeScript and every use of it (a bogus member inside the string is a real error mapped back to the Glyph source), so the escape is not an unchecked hole in the type system; what it opts out of is only Glyph's own machinery (a type is opaque with no `.parse` descriptor, exactly like an imported `.d.ts` type; a value is `unknown`). It is recognized only in the exact `extern_ts("...")` shape (a string-literal argument), so it never collides with a user identifier or type named `extern_ts` used otherwise, and every escape is greppable by `extern_ts`. The string form keeps the hatch deliberately a little awkward: it is the rare-idiom fallback so no library forces a hand-written adapter file, not a first-class way to write code. The manifesto-native alternative for schemas you own is to materialize them with `glyph gen zod`/`gen dts`; `extern_ts` covers the inline and library-schema cases. *[abstraction — one visible, greppable, `tsc`-checked construct instead of importing the general conditional/mapped-type surface]*

- **D30. String-literal-union types (`type Tier = "free" | "pro"`).** A union of string literals is a type, distinct from a D8 tagged union (whose members are named constructors). It emits as the TypeScript literal union (`"free" | "pro"`), so `tsc` enforces the narrowed type at every use, and a record field of this type gets a **runtime membership check** in its descriptor (the value must be one of the literals, not merely a `string`) — the leaf-value check a bare `string` cannot express. A `match` over this type is **exhaustive without an `else`** when it covers every literal; a missing literal is a compile error (E0200) listing the gaps, so adding a value to the union forces every match to handle it (the enum-exhaustiveness guarantee, extended from tagged unions to string enums). Like D9, this does not depend on how the type reached the module: `import catalog { ColType }`, `import catalog` with a `catalog.ColType` annotation, and `import catalog as c` with `c.ColType` are all held to the same bar, and a match that covers every literal of an imported union needs no `else`. This is what lets `glyph gen dts`/`openapi`/`zod` materialize a string enum faithfully instead of narrowing it to `string`. **v1 scope:** single-line, pure literal unions (`"a" | "b"`); mixing a literal with a named type (`"a" | number`), and the multi-line `|`-per-line form, are not supported. **Assignability is checked by Glyph, not only by `tsc`.** A value where one of these is declared is refused when it is not a string at all (a `number`, a `bool`, a record, a tagged union, a prelude container, an object literal, an imported declaration), when it is a written string literal outside the set, or when it is a `string` the compiler cannot pin to a narrower set; a value of the union stands wherever a `string` is declared, since every literal in the set is one, and two of these compare by literal set, so a subset stands. The refusal is E0204 at a `let`, a `const` or a `return` and E0211 at a call argument, and it carries the accepted literals in `alternatives`. An alias chain is followed and a sibling module's declaration is read the same way, so neither the name a site used nor the file the type was declared in changes the answer, and an imported declaration keeps its own name in the diagnostic rather than printing its literal set. **A written string literal has the one-literal type it spells**, an array literal's element type is the join of its elements' types, and a record literal and an array literal are checked field by field and element by element against the declared type, so a literal reaching the check through a generic argument or a record field is decided rather than left to `tsc`. That type **widens back to `string` at a binding that infers its type from the value**: a `let` with no annotation, whose emitted TypeScript `let` widens the same way, and the element binding of a `for` over a written array. A `const` emits a TypeScript `const` and keeps a literal that stands as its whole value; a literal inside an object or an array still widens (D20). Widening is read off the written form, so a literal type that arrived through a name is not widened, which is what TypeScript's freshness rule does. **A `Record`'s key is invariant (0.1.153).** `Record<K1, V1>` stands where `Record<K2, V2>` is declared only when `K1` and `K2` are the same key domain and `V1` stands where `V2` is; the value stays covariant, as an `Array`'s element is. `string` and every second name of it (D46) are one domain. Two string-literal unions are one domain when their member sets are equal, compared both ways, and a single literal is a one-member set. A refined type (D39) is its own domain, the same declaration through any chain of second names and never its base or another refinement. A type parameter is equal only to itself inside the body that declares it, and at a call the comparison is made after inference. A key the checker cannot decide (an `extern_ts` type, a package type it does not read) refuses nothing. `int` and `number` are compared as one domain until `int` keeps its identity through the checker (G373b). TypeScript writes `Record<string, V>` as an index signature and accepts both directions, so this is stricter than `tsc`, on D49's grounds: a `Record<string, V>` where a `Record<Tier, V>` is declared may hold keys outside `Tier` or lack a member, which the type's validator refuses, and a `Record<Tier, V>` passed on as a `Record<string, V>` is the same object under a wider name, so a write through it puts a stray key into the caller's map. The refusal is E0204 at a `let`, a `const` or a `return` and E0211 at an argument, with a note naming both keys; going from an open map to a closed one is an `is Record<Tier, V>` arm or a `json.parse<Record<Tier, V>>`. The same rule shapes `std/record`: `get`, `set` and `remove` take a key of the record's own `K`, `has` takes any `string`, `keys` is `Array<K>` for a string-like `K` and `Array<string>` for a numeric one, and `record.remove` on a `K` with a fixed member set is E0211, since removing a member leaves a value of no declared type. **A `Record` keyed by one of these holds every member (0.1.148).** The runtime check of `Record<K, V>`, on every path that runs one (`json.parse`, a record field, `parse`/`is`/`schema`, an `is` pattern, a container's part, a generic's argument, a sibling alias), checks each own key against `K` with the check a field of type `K` gets, so `K` is reached however it is spelled. For a string-literal union `K` (an alias chain, imported, namespaced, a single literal) every key is a member and every member is a key: `Record<Tier, int>` refuses `{"a":1}` as it refuses `{"a":1,"z":2}`, which is how `tsc` reads `let r: Record<Tier, int>` when the value is written. For a `where`-refined string `K` (D39) each key passes the predicate and no member set is required. For `int`, `number` or a refinement of either (D31, D39) each key is the canonical spelling of a number (`"" + Number(k) === k`, the only key `m[n] = v` can make) and that number passes `K`'s check, so `"x"`, `"01"` and, for `int`, `"1.5"` are refused. The rule is that a numeric key is accepted exactly when it is a string `m[n] = v` can create for some `n` of `K`. So `"NaN"`, `"Infinity"` and `"-Infinity"` are `number` keys (a program can hold those values and write them, and a map Glyph wrote must pass its own `parse`) but not `int` keys; `"1e+21"` is an `int` key, being the canonical spelling of an integer D31 accepts as an `int` value; and `"1e21"`, `"-0"`, `"01"` and `"9007199254740993"` are no number's spelling and are refused for both. A refined literal union cannot be a key type, since D39 refuses the refinement at its declaration. `string`, or a plain alias of it, checks nothing, and its emitted check is unchanged. A key type with no runtime check refuses the `Record` (E0304: ``cannot validate `Record<H, int>`: its key type `H` has no runtime check``), and so does a generic record with a `Record` field keyed by one of its type parameters applied to anything but `string`, since the checker passed for the parameter tests one key and cannot list the members. E0224 still treats every `Record` read as possibly absent, except where `V` is `unknown` (D53). *[verifiability — the boundary validates enum membership at runtime and a match must cover every case; greppability — the allowed set is spelled at the declaration site]*

- **D31. `int` — a whole `number`.** `int` is a prelude type for an integer. TypeScript has no integer type, so `int` emits as `number` and is a `number` in Glyph's own checker (assignable to and from `number`); its only enforcement is a **runtime `Number.isInteger` check** in a descriptor, so a wire `3.5` fails an `int` field's `.parse` where a `number` field would accept it. It exists so `glyph gen` can materialize a JSON-Schema `integer` with real boundary validation instead of collapsing it to `number`. A `let x: int = 3.5` in ordinary code is *not* a compile error (TS cannot express the constraint); `int` is a boundary-validated refinement, not a static type. As a `Record`'s key type, `int` and `number` admit a key that is the canonical spelling of a number (D30): exactly the strings `m[n] = v` can create for some `n` of the type. `NaN`, `Infinity` and `-Infinity` are `number` keys and not `int` keys, `1e+21` is both (an `int` value as `Number.isInteger` reads it, so key and value agree), and `1e21`, `-0`, `01` and `9007199254740993` are neither. If `int` is ever narrowed to safe integers, that is a decision for values and keys together, made here. *[verifiability — the boundary validates integer-ness at runtime]*

- **D32. `typeof value` type query, for first-class value-derived types.** In type position, `typeof <path>` is the type of a value binding (`user_schema`, or a dotted `a.b.c`). It emits as TypeScript `typeof <path>`, and its operand is resolved as a real value reference (a `typeof` over an undefined name is E0103), so it is greppable and tied to a value that must exist. Combined with an ordinary member-namespaced generic type (`z.infer<...>`, which already parses), it makes the canonical value-derived type first-class: `type User = z.infer<typeof user_schema>` needs no string escape. Glyph's own checker treats a `typeof` type as opaque (`unknown`, no descriptor); `tsc` reduces it (a `z.infer<typeof s>` becomes the schema's inferred type and is enforced at every use), exactly like an imported `.d.ts` type. Validation of a value of this type comes from the library's own parser (`user_schema.parse(...)`), which is how a schema library already works; `typeof` gives you the *type* without the `extern_ts` string. *[abstraction — the common value-derived idiom is first-class and greppable, not a raw-TS string; verifiability — the operand is a checked value reference]*

- **D33. Module visibility: private by default, `pub` to export.** A top-level declaration (`fn`, `type`, `const`, `component`, `interface`) is visible only inside its own module unless marked `pub`, which places it between the annotations and the declaration keyword (`pub fn`, `pub async fn`, `pub type`, `pub resource type`, `pub interface`). A private name is absent from the module's export surface, so importing it from another module is E0105 (not a downstream `tsc` error). That holds for both ways of naming a sibling's type: `import lib { Secret }` reports at the import, and `import lib` with a `lib.Secret` annotation reports at the annotation. Value access through a namespace (`lib.helper()`) is still a `tsc` error rather than an E0105. `pub` emits `export`; a private decl emits without it, and a private record's runtime descriptor and a tagged union's constructors inherit the type's visibility. **`fn main` is always exported** regardless of `pub` — it is the entrypoint the generated runner imports — so single-file programs need no `pub`. An `import` never takes `pub` (it re-binds another module's name; D15 forbids re-export). *[greppability — the public API is `grep '^pub'`; verifiability — safe-by-default, a helper is not exposed unless you say so]*

- **D34. Structural interfaces, usable as generic bounds.** `interface Name<T> { fn method(p: P) -> R  field: T }` declares a named set of member signatures: a `fn` member is a method signature, a `name: T` (or `name?: T`) member is a property. It is **structural**, like a TypeScript `interface` and unlike a declared record (D49): any value with the members satisfies it, whatever declared the value's type, with no explicit `impl`/conformance declaration (the nominal `trait`+`impl` alternative was rejected — it would bolt a second, nominal type-identity model onto a structural language). An interface is usable as an ordinary type and, chiefly, as a **generic bound** (`fn label<T: Named>(x: T) -> string`), which lowers to a TypeScript `extends` clause. Glyph resolves the bound like any annotation, so an undeclared one is refused (E0103), reads it inside the generic body (D58), and checks it where the parameter is bound (D72): `label(o)` with `o: Other` is E0211, and `label<Other>(o)` and `Box<Other>` are E0251. An application reads its members through its arguments (G461): `Cmp<number>` under `interface Cmp<X> { fn cmp(o: X) -> number  v: X }` has `cmp(o: number) -> number` and `v: number`, the interface's members with each parameter replaced by its argument. That one member set is what a member read and a method call on a value of `Cmp<number>` are checked against (E0204 on the member's type, E0210 with the did-you-mean, E0211 on a method's argument), and what a value where `Cmp<number>` is declared is compared against, as for a non-generic interface: a record without `cmp` is refused there, and so is a `Cmp<string>`. A bounded `T: Cmp<T>` is read through its bound with `X` replaced by `T`, so inside `fn f<T: Cmp<T>>(a: T, b: T)` the call `a.cmp(b)` takes a `T` and returns a `number`, and `a.cmp(5)` is E0211. There are no variance markers: two applications of one interface are compared by their substituted member sets, so an argument is compared wherever the interface uses its parameter and nowhere else, and `Sink<string>` passes where `Sink<Mode>` is declared under `interface Sink<X> { fn put(x: X) -> void }`, as `tsc` accepts it. A value of an interface is judged by one rule however its type is spelled (G536): `HasV` and `Box<number>` (under `interface Box<X> { v: X }`) are both refused where a declared record, a tagged union, an `Option`, a `Result` or an `Array` is declared (D49) and where a `Record<string, V>` map is declared (TS2322, unless `V` is opaque to the checker), and both stand where a `Nullable` of their own type is declared. An interface another module of the project declares is the same interface it is in its own module (G541): D34 is a property of the declaration, not of the module that holds it. It keeps its name across the edge (G75's `Ty::Imported`, never its shape), and its members are read on the declaring side, an application's with its arguments put in, so every rule above applies to it unchanged: a value passed, returned, bound with `let`, held in a field or bound to a parameter where a sibling's `HasName` or `Box<number>` is declared is compared with its members, a member read on one is checked (E0210), and its value is refused where a record, a primitive or an array is declared. The named import (`import lib { HasName }`) and the namespace spelling (`lib.HasName`) give one verdict, because the members are read by the declaring module and the declaration's name, never through the consumer's import. A second name for an interface is that interface (D46, G649), whichever module declares either: `type LN = HasName`, `type LN = aa.HasName` and a sibling's `pub type Named = HasName` have `HasName`'s members, so a value carrying them is accepted where `LN` is declared and one missing them is refused, and a generic second name (`type LB<T> = Box<T>`) reads them with its own arguments put in. A sibling's generic interface takes exactly its own number of arguments, as a local one does (G650): `Box` and `Box<number, string>` under `interface Box<X>` are E0233 under either import spelling. It emits an `export interface`/`interface` and has **no runtime descriptor** (it is a compile-time contract, like an imported `.d.ts` type). A primitive and an interface compare the way they do in TypeScript (G502, G460). A `string`, a `number` (`int` included), a `bool`, a string-literal union, a refined `string` or `number` (D39) or an `Array<T>` where an interface is declared is compared through the value's apparent members, read from TypeScript's library by the same generated table that checks a member read (`bool`'s list is read for this rule only): a member the interface requires that the value does not have is refused, a member both have is compared by the relation where the table gives the value's member a type, and a member the table does not type is left undecided. So `"abc"` passes where `interface HasLen { length: number }` is declared and `5` is refused where `interface HasName { name: string }` is, as `tsc` decides both (TS2345, TS2322). The other direction is always refused: an interface's value is an object, so it never stands where a `string`, a `number`, a `bool`, a string-literal union or an `Array<T>` is declared, and a parameter bounded by an interface (`fn p<T: Named>(x: T) -> string { return x }`) is refused there through its bound (D58). E0204 at a `let`, a `const` or a `return`, E0211 at an argument, with the missing member or the object named in the sentence. Not judged yet: an interface whose members are all optional and share none with the value, which `tsc` refuses (TS2559), and an `Option`, a `Result` or a `Record` where an interface is declared (the other direction is G536's rule above). A `bigint` is compared through its own members, never a number's (D38). *[abstraction — a generic can require capability of its parameter; greppability — the required surface is named at the bound]*

- **D35. `defer <expr>` for deterministic scope-exit cleanup.** `defer <expr>` runs its expression on exit of the enclosing block, on **every** path (normal completion, `return`, or a thrown error), lowered to a `try { <the statements after it> } finally { <expr>; }`. The tail expression stays inside the `try`, so the block's value is unchanged and the cleanup runs after it; multiple defers in one block **nest for last-in-first-out order**. It composes with `owned`/`resource` handles for release without a `Symbol.dispose` protocol (`defer file.close()`), and it works with any cleanup expression, not only disposables (the reason `defer` was chosen over a TS `using` binding). *[greppability — `grep defer` finds every cleanup; verifiability — release happens on every exit path, not just the happy one]*

- **D36. Bitwise operators `& | ^ ~` and shifts `<< >> >>>`.** Expression-position bitwise AND (`&`), OR (`|`), XOR (`^`), prefix NOT (`~`), and the shifts left (`<<`), signed-right (`>>`), and unsigned-right (`>>>`) emit verbatim to TypeScript and are number-typed (enforced by `tsc`). Precedence follows JavaScript: `|` looser than `^` looser than `&`, all binding tighter than `&&` and looser than `==`; the shifts sit between comparison (`< > <= >=`) and additive (`+ -`), binding tighter than comparison and looser than `+`. In expression position `|` and `&` are unambiguous, a union/pattern `|` (D8) never appears there, and `&&` is the separate logical-and, so no grammar conflict. The shifts once looked like they collided with a generic-close (`Array<Array<T>>` produces `>>`), but generic type arguments are consumed on the postfix/type-parsing paths before the binary-operator chain runs, so an *adjacent* angle run reaching the shift level is unambiguously a shift; the parser recognizes it from the single `<`/`>` tokens the lexer already emits, with an adjacency check so `Foo<T> > x` never reads as a shift. A pure-Glyph mulberry32 PRNG is now expressible (`state ^ (state >>> 15)`), the case the improve-glyph dogfooding loop surfaced; `math.imul` remains exposed for 32-bit multiply. *[abstraction — real bit manipulation is expressible without an `extern_ts` escape; the shift disambiguation resolves the angle-bracket ambiguity in the parser rather than papering over it]*
- **D37. `new` interop constructor expression.** `new <callee>(<args>)` (with optional `new <callee><T, ...>(<args>)`) instantiates a class that comes from *outside* Glyph: an imported npm package, a `.types` ambient declaration, or `extern_ts`. It emits verbatim as a TypeScript `new` and is type-checked by `tsc` against the real constructor, so a wrong argument is a real error mapped to the Glyph source (e.g. TS2345) and an undefined callee is E0103 at resolve time; every construction is greppable by `new`. It is deliberately **interop-only**: Glyph has no `class` declarations and gains none. `new` exists solely because most database and messaging clients are class-based (`pg`/`new Pool`, `mongodb`/`new MongoClient`, `ioredis`/`new Redis`, `kafkajs`/`new Kafka`) and were otherwise reachable only through the `unknown`-typed `extern_ts("new ...")` string. The callee is parsed as a member/index chain that does *not* swallow a call, so `new a.b.C(x).m()` is `(new a.b.C(x)).m()`; the argument list uses the same comma rules as a call. The instance is `unknown` to Glyph's own checker (no `.parse` descriptor), exactly like an imported `.d.ts` type, with `tsc` supplying the real type. *[abstraction — class-based libraries are reachable with a checked, greppable construct instead of an `extern_ts` escape; verifiability — the construction is `tsc`-checked, not an opaque hole]*

- **D38. `bigint` — an exact arbitrary-precision integer.** `bigint` is a prelude type for a whole number of unbounded magnitude. It emits verbatim as TypeScript `bigint` and `tsc` keeps it distinct from `number` (no mixed `bigint`/`number` arithmetic). A `bigint` literal is written `123n`; the lexer accepts the `n` suffix on an integer literal only, never on a fractional or exponent form (`1.5n` is not a bigint, matching JS). Its runtime descriptor checks `typeof x === "bigint"`, so a wire `number` where a `bigint` is declared **fails `.parse`** (an account id sent as a JSON number is rejected, not silently truncated). Unlike `int` (D31), which is a `number` carrying an integer *check*, `bigint` is a separate runtime type: it holds values past 2^53 exactly, where `number` loses precision. Glyph's own checker holds `bigint` as a primitive of its own (G500): a `123n` literal is a `bigint`, and a `bigint` and a `number` (an `int` included) are not assignable to each other in either direction, as in `tsc` (TS2322, TS2345). An arithmetic, bitwise or shift operator over two bigints gives a `bigint`, and `-x` and `~x` on one do too; one that mixes a `bigint` with a `number`, and `>>>` on a `bigint`, is E0258, which `tsc` refuses as TS2365 and JavaScript throws for. A comparison (`<`, `>`, `<=`, `>=`) between the two is legal. A member read on a `bigint` is checked against TypeScript's `BigInt` members (`toString`, `toLocaleString`, `valueOf`, and `Object`'s), so `n.toFixed(2)` is E0210. Glyph has no conversion between `number` and `bigint` yet (G571). Use `bigint` for exact large whole numbers (ids, counters, 64-bit values); for money use `std/decimal`. *[verifiability — the boundary validates bigint-ness and the value stays exact past the float range]*

- **D43. A `mut` whose read and write straddle an `await` is an error (E0225).** Inside an `async fn`, reading a field of a **parameter**, suspending on an `await`, then writing that same field is rejected. The value written was read before the suspension, so a concurrent task that wrote in between has its write silently discarded: two calls to `bump(c)` that each read `0` and write `1` leave `1`, not `2`, out of a build with no diagnostics and a clean `tsc --strict`. That is the silent class this language exists to remove, and nothing about the source looks wrong. **The rule is deliberately narrow, and the narrowness is the design.** It fires only on the same place, only through a parameter (which is the only thing a caller can also have handed to another task), and only with at least one field or index step (rebinding a whole parameter changes this function's copy, not the caller's record). A place is a parameter followed by fields and indexes: `c.n`, `c[0]`, `m["k"]`, `a[i].balance` (G390). An index counts only when its key is stable, a number or string literal or a name no `mut` reassigns anywhere (the same predicate `is`-arm narrowing reads), and two places are the same when every step is equal as written; `c[i + 1]`, and `c[j]` where some `mut j = ..` exists, are not tracked, since the read and the write can name different elements. A read of `p[k]` counts in three spellings, `p[k]`, `array.get(p, k)` and `record.get(p, k)`, because E0224 refuses the bare read on a `Record`; the message names the call when the read was one. A `mut c.push(x)` reads no element and is not a read-modify-write. A local accumulator across an `await` — `mut rounds = rounds + 1` in an async loop — is ordinary, correct, and not reported; an earlier draft flagged two such lines in `examples/apps/jobq`, and a false positive on a counter is what teaches people a check is noise. Two wider rules were rejected: forbidding `mut` on any binding captured by more than one live task needs escape analysis and would reject correct code, and an `owned`-style marker for shared mutable state is a larger design still available if this proves too narrow. The fix the diagnostic names is to move the read after the `await`, so the value written is the one current when it is written. **D90 (G516): the value has to reach the write.** The rule fires only when the value written mentions, directly or through `let` bindings derived from it, a value read from that place before the `await`. A read taints the `let` it initializes and any `let` initialized from a tainted one, so `let first = c[0]`, `let x = first * 2`, `await`, `mut c[0] = x` is refused. A read after the `await` is current: `let now = c[0]` there, or `mut a.balance = a.balance + f`, is accepted even when the place was also read before it, which until D90 was refused. A binding some `mut` reassigns carries no taint (the same predicate), a stated miss preferred to a false refusal. **D91 (G517): async lambdas.** Every `async fn(..) { .. }` lambda is checked, at any depth, in a sync function, a component, an event handler or an async function. Inside one, a place is rooted at the lambda's own parameters or at any binding it captures from an enclosing scope, that scope's parameter or its local: the lambda can run many times at once and every run shares a captured local, so `let v = count_ref.current`, `await save()`, `mut count_ref.current = v + 1` in a component's handler is refused. A binding the lambda declares itself is per-run and does not count, and a top-level async function's own locals still do not. *[verifiability — a lost update is a wrong answer no test reliably catches, since it depends on interleaving]*

- **D39. `where` refinement types.** `type Name = Base where <predicate>` refines a primitive base type with a boolean predicate over a bound `value`: `type Amount = int where value >= 0`, `type Rating = int where value >= 1 && value <= 5`, `type NonEmpty = string where value.length > 0`. The predicate is woven into the type's runtime descriptor: `Name.parse(x)` and `Name.is(x)` run the base leaf-check *and* the predicate (the base check narrows `value` first, so the predicate sees the base type), so a value that fails the predicate is **rejected at the boundary** where untrusted data enters. The predicate runs wherever the refined type appears, not only at a direct `Name.parse`: a record field typed `Name`, an `Array<Name>` element, an `Option<Name>` payload, a union variant's payload, and `json.parse<Name>` all call the descriptor, and so does a field typed by a refined alias imported from another module. Glyph's own checker treats `Name` as its base type for assignability (the nominal-newtype form: a refinement is boundary-validated, not statically tracked, exactly like `int` in D31), and `tsc` sees the base type. **v1 scope:** the base must be a primitive with a leaf check (`int`, `number`, `string`, `bool`, `bigint`); a `where` on a record, a tagged union or a string-literal union (D30, a single literal included) is a compile error (E0300), not a silent drop (record and cross-field invariants are a planned extension). The base is judged by what it resolves to, so the refusal is the same written inline, through a local alias or an alias chain, imported by name, through a namespace, or through a second name a sibling module declares. A refined literal union is refused rather than narrowed because the predicate is an ordinary expression the compiler does not evaluate: `type T2 = Tier where value != "c"` would emit as all of `Tier` for `tsc` while its run-time check refused `"c"`, so a `Record<T2, V>` had no value both accepted and a `match` on a `T2` lost D30 exhaustiveness (G377, through 0.1.151). The members wanted are written as their own union instead (`type T2 = "a" | "b"`), which stands wherever `Tier` is declared because D30 compares literal sets. A refined `string`, `int`, `number`, `bool` or `bigint` stays legal, including one whose predicate admits only finitely many values (`string where value == "a" || value == "b"`): the values its check accepts are a subset of what `tsc` types, so the two never disagree in the direction that matters. The predicate is an ordinary boolean expression, greppable and emitted verbatim into the descriptor so `tsc` checks it. **The rejection names the constraint:** a failing `Name.parse` returns an `Issue` reading `expected Password (string where value.length >= 8)`, with `code: "refinement"`, so the string that reaches an HTTP 422 body greps straight back to the `type Password = ...` line rather than leaving the caller to re-derive which rule fired. A value that is not of the base type failed something else and says so: `parse(42)` on that same type reports `expected Password (string)` with `code: "type"`, since naming a length rule for a number would blame the wrong thing. Reached through a record field, it arrives with the field name on the issue's `path`. As a `Record`'s key type, a refined type checks each key with its descriptor: a refined string the key itself, a refined number the number the key spells (D30). *[verifiability — an invariant like non-negative or in-range is validated at the boundary instead of being a check a caller must remember; greppability — the constraint is spelled at the type's declaration site and repeated in the rejection]*

## Semantics inherited from the JavaScript runtime (declared, not built)

Glyph transpiles to TypeScript and runs on a JavaScript engine, so several
language-level properties are true by inheritance rather than by Glyph
machinery. They are stated here so they are guarantees a reader can rely on, the
same way the verifiability pillar owns the `tsc` dependency, rather than
accidents to rediscover.

- **Evaluation order is JavaScript's:** left-to-right, arguments before the call.
- **Value vs reference:** primitives (`number`, `string`, `bool`) copy on
  assignment and pass by value; objects, arrays, and records are references
  (assignment and passing alias the same value).
- **Equality:** `==` is JavaScript strict equality (`===`) — identity for
  objects, value for primitives. There is no operator overloading, so `==` never
  runs user code.
- **Concurrency and memory:** a single-threaded event loop, so there are no
  shared-memory data races; scheduling is `async`/`await` over promises (see
  `std/task` for structured joins). Memory is reclaimed by the engine's garbage
  collector, which Glyph does not tune. Manual memory, a non-GC model, and a
  documented memory-visibility model are consequences of this target and are out
  of scope by design, not gaps.

## Evaluation semantics and the prelude (not grammar decisions)

These are normative behaviors that no single D-decision captures. They are facts
an agent needs and previously had to discover by reading the compiler.

- **Implicit tail return.** A non-`void` function, lambda, or block evaluates to
  its final expression; an explicit `return` is optional and equivalent.
  `fn double(n: number) -> number { n * 2 }` and `{ return n * 2 }` mean the same
  thing. `return` is *not* mandatory. *[abstraction]*
- **The prelude — names in scope with no import.** The runtime bootstrap
  installs a few globals so they need no `import`: the values `number`
  (`number.to_string`, `number.parse`), `par` (`par.all`, `par.all_ok`),
  `print`, and `assert`; and the ambient types `Schema<T>` and `Issue`. The
  primitive type names `number`, `string`, `bool`, `void`, `Array<T>`,
  `Record<K, V>` are likewise always available. Everything else — including
  `Result`/`Ok`/`Err`, `Option`/`Some`/`None`, and every `std/*` function — comes
  through an explicit `import`, so the import list is otherwise the complete
  dependency set. *[greppability]*
- **The boolean type is `bool`, not `boolean`.** `boolean` is not a known type.
- **Stdlib wrappers may take a trailing optional argument; Glyph functions may not.** Every parameter of a Glyph `fn` or `component` is required, and calling one with the wrong number of arguments is E0213. The stdlib's TypeScript wrappers are the one exception: `array.slice`, `string.slice`, `string.pad_start`, `string.pad_end`, `string.index_of`, and `json.stringify` each take a trailing argument you may omit, written with a `?` in `docs/reference/stdlib.md`. This is a boundary convenience, not a language feature: you can call those functions both ways and you cannot write one. The checker models all six: the arity check reads a minimum and a maximum, so `array.slice(xs, 1)` and `array.slice(xs, 1, 2)` both pass and a call outside the range is E0213. A Glyph function type cannot spell the optional parameter, so `glyph llms --json` publishes these rows with `signature: null` and one complete type per legal arity under `call_forms`. Whether Glyph gains defaulted parameters is undecided.

- **D42. `==` and `!=` are value equality, on every type.** Two values compare equal when they hold the same data: `Some("a") == Some("a")` is true, and so is `{ x: 1 } == { x: 1 }`. Records, tagged unions (`Option`, `Result`, and any `type X = | A | B`) and arrays compare by structure, recursively; primitives compare as they always did. The emitted TypeScript is `===` whenever both operands are known primitives (a `string`, `number`, `bool`, `int`, `bigint`, a string-literal union, or a local alias for one), which is the overwhelming majority of comparisons, and a prelude `__glyph_eq` call otherwise. That helper's first test is `===`, so an identical reference costs one comparison, and a function-valued property is skipped, because a value's methods are behaviour rather than data. **Reference identity is not expressible.** Nothing in Glyph asks "are these the same object": a language whose values are records and tagged unions has no use for it, and offering both would mean every `==` needed a reader to work out which one was meant. Before this, `==` emitted `===` unconditionally, so it silently meant *reference* equality for every aggregate: `Some("a") == Some("a")` was false, no diagnostic was produced, and the identical expression written as an `@example` compared structurally and passed. A test that reports success on code that does not work is the worst artifact the example gate can produce, and it was reachable by writing the same expression in two places. *[verifiability — an operator means one thing wherever it is written, and the test and the program agree; minimizing ambiguous states — the reading of `==` no longer depends on the static type of its operands]*
- **D47. `never` is the bottom type, spellable in user code.** `never` is a prelude type name. No value has it, so it is assignable to every type and nothing but itself is assignable to it. It emits verbatim as TypeScript `never`. A function declared `-> never` owes no returned value, for the opposite reason `void` does: not that the caller wants nothing back, but that the body does not reach a return (it loops, or it calls another `-> never`). A `match` arm whose value is `never` contributes nothing to the arm join, so the match's type is what the other arms produce. The type already existed on the stdlib side (`std/process.exit` is typed `-> never`) and only user code could not name it, which cost a program that runs until the process is killed three things at once: a doc comment asserting in prose what the signature could state, a `return` that is never reached, and a dead `match` arm kept only to keep a later match exhaustive. Numbered D43 until 0.1.124, when the duplicate number was resolved in favour of the `mut`-across-`await` rule. *[verifiability — a non-returning function says so in its signature and the compiler holds it to that, instead of a comment nobody checks]*
- **D41. A `package.json` with a `"glyph"` key makes its directory a module-resolution root; nearest marker wins.** A local import path is still slash-separated from a root and never relative (D15); D41 only says *which* root. A directory holding a `package.json` whose top-level `"glyph"` key is present is a **project root**, and its resolution root is that key's `src`, else `src/` if it exists, else the directory. That is the same key `glyph init` already writes and `glyph publish` already reads, so this honours an existing concept rather than inventing a marker. Four rules fix which root a file gets. The nearest marked ancestor wins. A marker at the build target makes the target project root at that marker's `src`. With no marker anywhere the root is the build target itself, which is the behaviour every existing project has today. Discovery never looks above the build target, so `glyph build app/src` means `app/src` whether or not `app` carries a marker. A `package.json` with no `"glyph"` key is a plain npm package, not a root. One that will not parse is not a root either, so a malformed manifest somewhere in a tree cannot fail the whole build; the build says which manifest it could not read, because a directory that silently stops being a project is a bad half-hour. **A project's imports resolve within its own root only:** a nested project may not import from an enclosing one, and an enclosing project may not import from a nested one. A nested project's files are not part of the enclosing project's compilation at all, exactly as a package in a pnpm workspace is not part of its parent's. Anything else reintroduces the ambiguity this rule exists to remove; reach another project the way TypeScript already does, by package name through npm. A build over an enclosing tree walks it and builds each project it finds, writing each project's output under `<out>/<project dir relative to the target>`, so building a marked app and building the tree above it compile that app identically. `glyph run`/`glyph check` on a *file* find its project by climbing to the nearest marker (stopping at a directory holding `.git`), comparing canonical paths so a relative and an absolute spelling of the same file find the same project. When that climb finds no marker, the root is the nearest ancestor directory named `src`, and the file's own directory when there is not one of those either. That is the same rule a build over an unmarked directory applies at its target, where the root is the target's `src/` if it has one: a file has no target to apply it to, so it is spelled by climbing. Every surface that publishes a `module::name` identity uses it, so `glyph check`, `glyph query`, the MCP tools and the editor give a nested file in an unmarked tree one name (`src/sub/deep.glyph` is `sub/deep` on all of them, not `sub/deep` on one and `deep` on the rest). *[verifiability: a module path has one meaning regardless of which directory the build was invoked from, or how the path was spelled, so a project verifies the same standalone and inside a monorepo; D15's greppability and diff stability are untouched, still no relative imports, still slash-separated, just from a nearer root]*
