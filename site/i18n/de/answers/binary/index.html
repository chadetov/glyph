Kann ich Binärdaten verarbeiten, oder ist alles ein String?

std/bytes gibt dir eine unveränderliche Folge von Oktetten, und std/fs und std/crypto sprechen sie beide. Bis 0.1.78 taten sie das nicht: Jede Grenze in der Standardbibliothek war String rein, String raus, also ließ sich ein PNG nicht lesen und einem HMAC kein echter Schlüssel geben.

Warum das wichtig ist

Das erste Byte eines PNG ist 0x89, was allein kein gültiges UTF-8 ist. Liest du diese Datei als Text, wird jedes Byte, mit dem der Decoder nichts anfangen kann, zu U+FFFD, also ist die Datei beschädigt, bevor dein Programm sie sieht, und nichts meldet einen Fehler. Dasselbe passiert mit einem Schlüssel: Ein HMAC-Geheimnis besteht aus beliebigen Oktetten, und wenn man es durch einen String schleust, verändert es sich, also berechnest du einen anderen MAC, als die Spezifikation sagt, und jeder Test, den du gegen deinen eigenen Code geschrieben hast, besteht.

Zwei unabhängig voneinander geschriebene Anwendungen, ein PNG-Leser und ein Authenticator, blieben in derselben Woche an genau diesem Satz hängen. Keine von beiden ließ sich innerhalb der Sprache umgehen.

So sieht es aus

Ein Authenticator nach RFC 6238, der auf beiden Seiten des HMAC Bytes braucht. Das Geheimnis kommt Base32-kodiert an, die Nachricht ist ein Acht-Byte-Zähler, der größtenteils null ist, und der Digest wird über sein eigenes letztes Byte indiziert:

Einmalpasswort, von Anfang bis Ende 
module totp

import std/bytes
import std/crypto
import std/math
import std/array
import std/option { Some, None }
import std/result { Result, Ok }

fn at(b: bytes.Bytes, i: int) -> int {
  return match bytes.get(b, i) {
    Some(v) => v,
    None => 0,
  }
}

pub fn code(secret: string, counter: number) -> Result<number, bytes.BytesError> {
  let key = bytes.from_base32(secret)?
  let message = bytes.from_array(array.map(array.range(8), fn(i: int) -> int {
    return math.floor(counter / math.pow(256, 7 - i)) % 256
  }))?

  let mac = crypto.hmac_sha1_bytes(key, message)
  let offset = at(mac, bytes.len(mac) - 1) % 16
  return Ok((((at(mac, offset) % 128) * 16777216)
    + (at(mac, offset + 1) * 65536)
    + (at(mac, offset + 2) * 256)
    + at(mac, offset + 3)) % 100000000)
}

Bytes ist zur Laufzeit ein Uint8Array, also lässt es sich ohne Auspacken an jede Host-API übergeben, die eins nimmt. Die Sequenzoperationen sind nach ihren Gegenstücken in std/array und std/string benannt: len, get, slice, concat, index_of, starts_with. Nichts verändert sein Argument.

Jedes Dekodieren kann ablehnen und sagt, wo

Das ist der Teil, der am meisten Aufwand gekostet hat, und der Grund, es zu verwenden. Nodes Buffer akzeptiert fehlerhafte Eingaben und meldet Erfolg:

Was die Plattform stillschweigend tut 
Buffer.from("zz", "hex")        // an empty buffer, no error
Buffer.from("a-b_", "base64")   // skips - and _, decodes the rest, no error
buf.toString("utf8")            // U+FFFD for anything malformed, no error
Was Glyph tut 
match bytes.from_hex(input) {
  Ok(b) => use(b),
  Err(e) => io.eprintln("${e.message} at ${number.to_string(e.index)}"),
}

// "z" is not a hex digit at 0
// a trailing base64 group cannot be 1 character(s) long at 3
// not valid UTF-8 at 2

Jeder Codec ist ausgeschrieben statt an Buffer delegiert, also lehnen Hex, Base64, Base64url und Base32 alle ein Zeichen außerhalb ihres Alphabets ab, eine abschließende Gruppe, die zu kurz ist, um ein ganzes Byte zu kodieren, und ein letztes Zeichen, das Bits über das Ende der Daten hinaus trägt. to_text sucht das erste Byte, das nicht Teil einer gültigen UTF-8-Sequenz sein kann, also bekommst du eine Position statt eines Urteils. from_array lehnt aus demselben Grund alles außerhalb von 0..255 ab: Ein stilles & 0xff macht aus 256 eine 0 und aus einem Tippfehler Daten.

Die Codecs auszuschreiben hat etwas gebracht, das nicht das Motiv war. Das Modul greift auf überhaupt keine Host-API zurück, nur auf Uint8Array, TextEncoder und TextDecoder, also läuft ein Bundle, das nur std/bytes anfasst, auch in einem Web Worker.

Welchen HMAC du wählst, ändert das Ergebnis

std/crypto hat jetzt beide Formen jedes Algorithmus. Der einfache Name nimmt einen String und gibt Hex zurück, was man zum Hashen eines Passworts will. Die Form mit _bytes nimmt und liefert Bytes, was ein Wire-Protokoll will. Wenn der Schlüssel aus bytes.from_base64 oder crypto.random_bytes kam, hat er Bytes, die ein String nicht halten kann, und die Textform berechnet stillschweigend etwas anderes.

Einen von einem Angreifer gelieferten Wert gegen ein Geheimnis zu prüfen, geht mit crypto.timing_safe_equal, nicht mit bytes.equals. equals kehrt zurück, sobald es einen Unterschied findet, also verrät die Dauer, wie viele führende Bytes richtig waren.

Wo es steht

Heute verfügbar

std/bytes mit 21 Funktionen: die Sequenzoperationen, die Brücke zu UTF-8 und Codecs für Hex, Base64, Base64url und Base32, die ein Result mit der fehlerhaften Position zurückgeben. fs.read_bytes, write_bytes und append_bytes lesen und schreiben eine Datei ohne Dekodierung. std/crypto hat eine _bytes-Form jedes Digests und HMAC, dazu SHA-1 für die Protokolle, die es vorschreiben, random_bytes und timing_safe_equal. Die Codecs sind gegen die Testvektoren aus RFC 4648 festgenagelt und der HMAC gegen RFC 6238, in der eigenen Testsuite des Compilers.

Wird schärfer

Es gibt noch keinen Integer-Codec, also ist das Lesen eines Big-Endian-u32 aus einem Header Arithmetik, die du selbst schreibst: Jenseits von 32 Bit ist ein Shift ohnehin das falsche Werkzeug, also wird dividiert. Hex-Literale lassen sich weiterhin nicht parsen, was eine CRC32-Tabelle mit 256 Einträgen in Dezimalschreibweise schwer lesbar macht. std/websocket dekodiert einen Binär-Frame weiterhin als UTF-8-Text; der Typ, den es brauchte, existiert jetzt, und die Frames sind als Nächstes dran. Und die sechs älteren String-zu-String-Funktionen von std/encoding schweigen weiterhin bei fehlerhaften Eingaben, also nimm die Codecs aus std/bytes für alles, was stimmen muss. Die Codecs sind in TypeScript geschrieben, statt an Nodes Buffer zu delegieren, und deshalb laufen sie in einem Web Worker, und sie sind bei einem Megabyte zwischen 1x und 35x langsamer als die der Plattform. Einen Schlüssel oder ein Token zu kodieren kostet so oder so nichts Messbares; der Performance-Guide hat die Tabelle, falls du Dutzende Megabyte bewegst.
