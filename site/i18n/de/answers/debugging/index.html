Wenn es um 3 Uhr nachts in Produktion kaputtgeht, was sieht die Rufbereitschaft?

Lesbares TypeScript, das dir gehört, mit einer Source Map zurück zu deiner .glyph neben jeder erzeugten Datei. Ein Debugger, ein Bundler oder ein Error-Tracker verfolgt den laufenden Code bis zu deinem Quellcode zurück, und selbst jemand, der Glyph nie gesehen hat, kann das erzeugte TS lesen. Vor all dem melden glyph build und glyph run dieselben Diagnosen für denselben Baum, also kann die schnelle Schleife nichts verstecken, was der Build gefunden hätte. Zwei Einschränkungen, beide auf dem Weg über glyph run, werden unten genannt.

1 · Das erzeugte TypeScript kannst du lesen

Glyph liefert keine undurchsichtige Laufzeit aus. Es erzeugt gewöhnliches, formatiertes TypeScript, das du committest und deployst wie jedes andere TS. Der schlimmste Fall (eine Person in Rufbereitschaft, die Glyph nicht kennt, um 3 Uhr nachts) liest also immer noch einfaches TypeScript, keinen Dialekt. Zwischen deinem Quellcode und der Produktion gibt es keine Blackbox.

2 · Source Maps zurück zu .glyph

Jede erzeugte .ts bringt eine Standard-v3-Source-Map (.ts.map) daneben mit, mit einem sourceMappingURL-Kommentar und deinem eingebetteten Glyph-Quellcode (sourcesContent). Alles, was Source Maps verarbeitet (Chrome DevTools, ein Node-Debugger, ein Error-Tracker wie Sentry, dein Bundler), kann sie verketten und dir die .glyph-Zeile zeigen statt der erzeugten.

dist/main.ts (Ende) 
// ...emitted TypeScript...
//# sourceMappingURL=main.ts.map    // v3 map, .glyph embedded

3 · Build- und Typfehler zeigen schon auf Glyph

Mit einem Typfehler kommst du selten bis in die Produktion, weil glyph build tsc --strict ausführt und jeden tsc-Fehler zurück auf deine .glyph-Quelle abbildet (derselbe Caret, der TypeScript-Fehlercode bleibt erhalten). Der Caret steht auf dem kleinsten Glyph-Ausdruck, dessen Code tsc abgelehnt hat: Ein falsches Argument unterstreicht dieses Argument, ein falsch geschriebenes Feld in einem JSX-Event-Handler unterstreicht diesen Member-Zugriff, nicht das ganze return drumherum. Und glyph build --json gibt jede Diagnose als strukturiertes JSON aus (Code, Schweregrad, Datei, 1-basierte Zeile/Spalte, Hilfe), damit deine CI oder dein Tooling darauf reagieren kann.

4 · glyph run sagt dir dasselbe

Der Befehl, den du den ganzen Tag tippst, ist glyph run, und bis 0.1.40 war er stiller als der Build. Er kompilierte das ganze Verzeichnis, nahm die Liste der erzeugten Dateien aus dem Bericht und warf die Diagnosen weg. Ein Baum, den glyph build bemängelte, lief sauber und endete mit 0. Jetzt meldet er dieselbe Menge: Warnungen eingeschlossen, für die Datei, die du genannt hast, und für ihre Geschwister, nach der Ausgabe des Programms, mit einer einzeiligen Zählung. Der Run-Cache speichert sie, also sagt ein zweiter Lauf über unveränderte Quellen dasselbe wie der erste, statt zu verstummen, und ein Cache-Eintrag ohne Diagnosen zählt als Fehltreffer und wird neu gebaut.

ein unbenutzter Import, einen Schritt vor dem Code hinzugefügt, der ihn verwendet hätte 
$ printf 'look\nquit\n' | glyph run adventure.glyph
...the game plays and exits 0...

Zwei aktuelle Einschränkungen

Der eigene Absturz-Stack von glyph run zeigt noch .ts-Zeilennummern. glyph run führt über tsx aus, und tsx verkettet die Source Map nicht durch seine eigene Transformation .ts→.js, also meldet ein nicht abgefangener Throw während glyph run die erzeugte Zeile. Diesen Stack umzurechnen ist ein Folgeschritt. Es betrifft die lokale run-Schleife; in einem echten Deployment machst du glyph build zu .ts, bundelst es mit deiner normalen Toolchain, und die .ts.map wird wie üblich verkettet, also zeigt der Produktions-Stack, wegen dem du tatsächlich alarmiert wirst, zurück auf .glyph.

Ein Fehler in einem Geschwistermodul ändert den Exit-Code von glyph run nicht. Ein Modul, das nicht kompiliert werden konnte, lässt sich nicht importieren, und ein Programm, das es nie importiert hat, läuft trotzdem. Du siehst den Fehler jetzt, aber der Prozess endet weiterhin mit dem, was main zurückgegeben hat. Ihn mit einem Wert ungleich null enden zu lassen, würde Bäume scheitern lassen, die heute problemlos laufen, also ist das eine offene Entscheidung und kein Versehen. Wenn der Zustand des Baums über den Exit-Code entscheiden soll, ist das glyph build.

Wo es steht

Heute verfügbar

Lesbares, committetes TS, eine v3-.ts.map pro Datei, tsc-Fehler auf .glyph zurückgebildet und Diagnosen per --json. glyph run meldet, was glyph build meldet, auch mit warmem Cache. Die Source-Map-Kette deiner Deployment-Toolchain reicht bis .glyph.

In Arbeit

Den Absturz-Stack von glyph run selbst umzurechnen (damit auch die lokale Run-Schleife .glyph-Frames zeigt), eine Entscheidung, ob der Fehler eines Geschwistermoduls glyph run mit einem Wert ungleich null enden lassen soll, und besseres Debugging im Editor über den LSP.
