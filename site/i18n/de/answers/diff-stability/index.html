02 · Reviewbare Änderungen

Bleiben Änderungen von Agenten sauber, oder formatieren sie meine ganze Datei um?

Eine einzeilige Änderung ist ein einzeiliger Diff, jedes Mal. Glyph hat ein einziges kanonisches Layout, also kann ein Agent eine echte Änderung nicht unter einer Wand aus Umformatierung begraben.

Warum das wichtig ist

Wenn ein Agent einen Pull Request öffnet, ist der Diff das Review. Wenn ein echter einzeiliger Fix als Umformatierung über 200 Zeilen ankommt, kann niemand sehen, was sich tatsächlich geändert hat, und genau in diesem Rauschen schlüpft ein Bug durch.

Stabile Diffs heißt, der Diff zeigt die Änderung und nichts als die Änderung.

Zwei Regeln erledigen den Großteil der Arbeit. Hier ist jede, gezeigt als der Diff, den du reviewen würdest.

Trailing Commas, ein Eintrag pro Zeile

Trailing Commas sind Pflicht, und eine Liste, die nicht in eine Zeile passt, bekommt ein Element pro Zeile, statt neu gepackt zu werden, also stört Einfügen, Entfernen oder Umordnen eines Eintrags nie seine Nachbarn.

Dasselbe gilt für Record-Felder, Parameter, match-Arme und Imports.

Die Schwelle hat ihren Preis: Eine Umbenennung, die einen Aufruf über 100 Spalten schiebt, klappt die ganze Argumentliste auf ein Argument pro Zeile auf.

Ein kanonisches Layout

Es gibt genau eine korrekte Formatierung, erzeugt von glyph fmt. Leerraum, Umbrüche und Ausrichtung sind keine Entscheidungen, die ein Agent “aufräumen” kann, also kann eine inhaltliche Änderung keinen Umbruch mit sich ziehen. Ändere den Typ eines Feldes, und das ist der ganze Diff:

user.glyph: ein Feld ändern, eine Zeile reviewen 
 type User = {
   id: string,
-  age: string,
+  age: number,
   email: string,
 }

Weil das Layout fest ist, erzeugen zwei verschiedene Agenten, die dieselbe Datei bearbeiten, byteidentische Formatierung, kein Umbruch-Rauschen, kein “mein Formatter gegen deinen”, und ein sauberes git blame, das auf den Commit zeigt, der eine Zeile tatsächlich geändert hat, nicht auf den, der sie umformatiert hat.

Ein kanonisches Layout, verschiebt der Formatter also meine Kommentare?

Früher ja, und das war ein Bug, den man beim Namen nennen sollte. Die Regel jetzt: Ein Kommentar wird über dem Element neu ausgegeben, über dem er geschrieben wurde, innerhalb eines Record-Rumpfs, einer Liste von Union-Varianten, eines Array- oder Objektliterals, einer Argument- oder Parameterliste und eines match.

Geschichte wie Kommentare wanderten, und die App, bei der es auffiel

Glyph hat keine Blockkommentare und keine Doc-Comment-Syntax, also ist eine //-Zeile der einzige Weg, ein Record-Feld, eine Union-Variante oder einen match-Arm zu erklären. Der Formatter gab ausstehende Kommentare nur an Grenzen von Deklarationen und Anweisungen aus, was hieß, dass ein Kommentar, der innerhalb eines Konstrukts geschrieben wurde, zur nächsten Deklaration hinunterwanderte und sich als Dokumentation für das las, wo er gelandet war. Aufgefallen ist es beim Schreiben von Minesweeper in Glyph. Diese beiden Deklarationen stammen aus der echten App (Kommentare passend gekürzt), einmal durch den alten Formatter und einmal durch den neuen gelaufen.

Und ein Konstrukt mit einem Kommentar im Inneren nimmt immer die Form mit einem Element pro Zeile an, in jeder Größe, damit der Kommentar ein Element hat, über dem er stehen kann. type Shape = { w: int, h: int } wird also weiterhin auf eine Zeile zusammengezogen, und sobald du h dokumentierst, bleibt der Record aufgeklappt.

Details warum das als Korrektheitsbug zählt

Warum das als Korrektheits-Bug zählt und nicht als kosmetischer: Nichts schlug fehl. Der Build endete mit 0, tsc bestand, und die verunstaltete Ausgabe war selbst ein Fixpunkt, also wurde glyph fmt --check in CI grün für eine Datei, deren Kommentare jetzt etwas Falsches sagten. Das ist dieselbe Klasse von Fehlern, die Glyph beseitigen soll, nur im Formatter statt im Typsystem.

Kann glyph fmt ein Programm kaputtmachen, das baut?

Es konnte, und ein Fall ist noch offen. Ein Formatter, den dein Programm überleben muss, ist schlimmer als ein fehlendes Feature, weil er Code beschädigt, der schon funktioniert hat.

  • Arm-RümpfeDer Printer klammert jetzt einen Arm-Rumpf ein, dessen erstes Token eine { ist, die als Block neu geparst würde, also das leere Objekt und alles, was darauf aufbaut (({}).size kommt als ({}.size) zurück).
  • Der FuzzerDer Fuzzer parst jetzt die formatierte Datei und vergleicht den Baum mit dem des Originals, also scheitert ein Layout, das die Bedeutung einer Datei ändert, beim ersten Durchlauf, statt darauf zu warten, dass es jemand bemerkt.
Geschichte der leere Record, der nicht mehr baute

Zuerst der behobene. Ein Arm, der “der leere Record” bedeutet, wird true => ({}) geschrieben. Die Position des Arm-Rumpfs ist die einzige Stelle in der Grammatik, an der eine führende { mehrdeutig ist, und der Parser löst das, indem er direkt nach der Klammer key: oder ... verlangt. Ein leeres Objekt hat keins von beidem, also kam der Arm, als der Formatter die Klammern wegließ und true => {} neu ausgab, als leerer Block zurück, und die Datei baute nicht mehr: E0223, der Arm erzeugt keinen Wert. Du hast einen Formatter über funktionierenden Code laufen lassen und Code bekommen, der nicht mehr kompilierte.

Ein Arm-Rumpf, der sich schon eindeutig liest, wie false => { a: "x" }, bleibt ohne Klammern, also gibt es nirgendwo sonst neue Satzzeichen zu lesen. fmt ist auf dem Ergebnis ein Fixpunkt, und das erzeugte TypeScript ist unverändert.

Geschichte zwei weitere, behoben in 0.1.138

Zwei weitere wurden in 0.1.138 behoben. Innerhalb eines Blocks setzt eine Zeile, die mit ( beginnt, die Zeile darüber fort, und bis 0.1.137 gab der Formatter load()? gefolgt von .run() als (load()?).run() aus, also bedeutete die formatierte Datei nach let a = 1 let a = 1(…).run(). Jetzt behält er load()? mit .run() eingerückt in der nächsten Zeile bei und schreibt e?(x), e?[0] und e? ? ohne Klammern. Der andere war die where-Verfeinerung einer Union, die der Formatter wegließ, wodurch aus einem Programm, das check ablehnte, eins wurde, das es akzeptierte.

Die Formatierungsregeln dahinter und der Tausch, den sie machen, stehen auf der Seite zur Säule stabile Diffs.

Wo es steht

Heute verfügbar

  • Pflicht-Trailing-Commas, Listen mit einem Eintrag pro Zeile und das eine kanonische Layout von glyph fmt, verlustfrei hin und zurück und idempotent, mit Formatieren beim Speichern im Editor.
  • glyph fmt verschiebt einen Kommentar nie dorthin, wo er nicht hingehört.
  • Kommentare bleiben über dem Element, über dem sie geschrieben wurden
    Details

    Kommentare bleiben über dem Element, über dem sie geschrieben wurden, auch innerhalb eines Records, eines Literals, einer Argumentliste, eines match, zwischen den Operanden eines Operators und zwischen den Schritten einer Methodenkette, die dann einen Schritt pro Zeile mit führendem Punkt bekommt.

Die Grenze, und was als Nächstes kommt

  • Ein Kommentar am Ende einer Codezeile wandert in die Zeile über dem nächsten Element
    Details

    Ein Kommentar wird immer in einer eigenen Zeile ausgegeben, also wandert einer, der am Ende einer Codezeile steht (w: int, // width in cells), in die Zeile über dem nächsten Element. Er überschreitet keine Deklarationsgrenze mehr, aber er bewegt sich; ihn am Zeilenende zu halten, verlangt, dass der Printer verfolgt, welche Zeile ein Kommentar sich teilt.

  • Ein Kommentar, für den das Layout keinen Platz hat, wird abgelehnt, nicht verschobenE0500
    Details

    Ein Kommentar, für den das Layout keinen Platz hat, etwa in einem Index, nach den Argumenten eines Aufrufs mitten in einer Kette oder vor einem Operanden von ! oder await, wird nicht mehr verschoben: glyph fmt lehnt die Datei ab, lässt sie, wie sie war, und nennt die Zeile und wohin der Kommentar gehört, und glyph check meldet dasselbe als Warnung E0500.

  • Ein Kommentar zwischen JSX-Attributen oder zwischen den Feldern eines Objekt-Patterns wird ebenfalls abgelehnt, wo ein Layout mit einem Element pro Zeile ihn unterbringen könnte; diese Layouts stehen auf der Liste.
  • Der Printer hat auch noch keine Regel, um eine lange Methoden- oder +-Kette umzubrechen, also bricht eine zu lange Kette stattdessen die innerste Argumentliste um, was die falsche Stelle ist.
  • Wir bauen außerdem einen Benchmark zur Diff-Größe gegen dieselben Änderungen in TypeScript, damit diese Säule eine Zahl wird, die du prüfen kannst.
