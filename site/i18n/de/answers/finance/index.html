16 · Geld & Sicherheit

Kann ich ihm Geld anvertrauen und Eingaben, die ich nicht kontrolliere?

Ja. Geld ist exakt, eine Invariante wie nicht negativ ist ein Typ, den die Systemgrenze durchsetzt, und nicht vertrauenswürdige Eingaben können ein SQL- oder Shell-Ziel nicht erreichen, ohne bereinigt zu werden. Jedes davon ist ein Compile- oder Parse-Fehler, wenn du es falsch machst, keine Konvention, an die sich jemand drei Funktionen weiter erinnern muss.

Geld ist kein Float

Ein Finanzsystem auf IEEE-754-number ist ein Bug, der darauf wartet, gemeldet zu werden: 0.1 + 0.2 ist nicht 0.3, und Werte jenseits von 253 verlieren stillschweigend an Genauigkeit. std/decimal ist exakter Festkomma-Wert zur Basis 10 über BigInt. Addition, Subtraktion und Multiplikation sind exakt; Division nimmt eine explizite Skala und rundet kaufmännisch (die Hälfte von null weg); ein fehlerhafter Betrag wird zu einem Err geparst, nie zu einem stillen NaN.

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()      # "11.34", exact

decimal("2")?.div(decimal("3")?, 2)   # "0.67", half away from zero
der Bug, den es beseitigt 
// JS number, the default everywhere:
0.1 + 0.2            // 0.30000000000000004
1_000_000_000_000.10 * 1.07   // rounding drift
9007199254740993     // === 9007199254740992

// None of these are your money anymore.

IDs und Zähler bleiben jenseits von 253 exakt

Eine Konto-ID oder ein Buchungszähler, der den Float-Bereich überschreitet und gerundet wird, ist eine andere Art von Katastrophe. bigint ist eine exakte Ganzzahl beliebiger Genauigkeit mit Literalen wie 123n, und ein Record-Feld vom Typ bigint validiert typeof === "bigint" an der Systemgrenze, also wird eine ID, die als JSON-number ankommt, abgelehnt statt stillschweigend abgeschnitten.

Eine Invariante ist ein Typ, kein Kommentar

"Der Betrag ist nicht negativ" und "die Bewertung liegt zwischen 1 und 5" sind die Prüfungen, die einmal geschrieben und später vergessen werden. Eine where-Verfeinerung legt die Invariante in den Typ, und der Deskriptor setzt sie an der Systemgrenze durch. Ein Wert, der das Prädikat nicht erfüllt, wird gar nicht erst zu einem Amount.

refinements.glyph 
type Amount = int where value >= 0
type Rating = int where value >= 1 && value <= 5

Amount.parse(-1)   # Err  (not just "is a number")
Rating.parse(6)    # Err
Amount.parse(3.5)  # Err  (int check too)

Injection ist ein Compile-Fehler

Der klassische Weg zur Remote-Code-Ausführung ist eine nicht vertrauenswürdige Eingabe, die eine SQL-Abfrage, einen Shell-Befehl oder ein HTML-Template erreicht. std/taint macht daraus einen Typfehler. Ein Wert von außen ist Tainted; ein Ziel, das du schützen willst, nimmt Trusted. Die beiden sind strukturell verschieden, also führt der einzige Weg vom einen zum anderen über ein explizites sanitize. Gib einem Ziel den unbereinigten Wert direkt, und tsc weigert sich, es zu kompilieren.

der sichere Weg kompiliert 
fn run_query(sql: Trusted<string>) -> void { ... }

let input: Tainted<string> = taint(req.body)
run_query(sanitize(input, escape))   # ok
der Injection-Weg nicht 
module query

import std/taint { Tainted, Trusted, taint, expose }

fn run_query(sql: Trusted<string>) -> string {
  return expose(sql)
}

pub fn handle(body: string) -> string {
  let input: Tainted<string> = taint(body)
  return run_query(input)
}

// [TS2345] Argument of type 'Tainted<string>'
//   is not assignable to parameter of type
//   'Trusted<string>'. (query.glyph:11)

Wo es steht

Heute verfügbar

std/decimal für exaktes Geld, bigint für exakte große Ganzzahlen, where-Verfeinerungen, damit eine Invariante an der Systemgrenze validiert wird, und std/taint, damit nicht vertrauenswürdige Eingaben ein geschütztes Ziel nicht ohne explizites sanitize erreichen. Jedes davon wird geprüft: Ein ungültiger Betrag oder eine ungültige ID scheitert an parse, eine verletzte Invariante scheitert an parse, und ein unbereinigter Wert scheitert an tsc.

Wo es aufhört

Eine where-Verfeinerung deckt heute primitive Basistypen ab; Invarianten über Records und mehrere Felder (where value.paid <= value.total) sind als Erweiterung geplant. Taint ist eine Disziplin, für die du dich entscheidest, indem du ein Ziel als Trusted typisierst, keine automatische Flussanalyse: Der Compiler setzt die Grenze durch, die du deklarierst, er leitet Taint nicht für dich über das ganze Programm ab.
