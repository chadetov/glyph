Kann ich einen Server schreiben, oder beendet sich der Prozess einfach?

Du kannst einen Server schreiben. main richtet alles ein und kehrt zurück, und der Prozess bleibt am Leben, solange Sockets und Timer noch ausstehen, dieselbe Regel, die Node verwendet. Bis 0.1.63 war das nicht so: Der Runner beendete den Prozess in dem Moment, in dem main zurückkehrte, also band ein Server seinen Port und starb im selben Tick.

Warum das wichtig ist

Das ist der Unterschied zwischen einer Sprache, die ein Skript ausführen kann, und einer, die einen Dienst ausführen kann. Ein Server, ein Datei-Watcher, ein Bot mit einer Gateway-Verbindung, ein Job-Runner: Keiner davon wird innerhalb von main fertig. Sie richten Handler ein und übergeben den Prozess an Events.

Das alte Verhalten scheiterte auf die schlimmstmögliche Art, nämlich still. glyph run app.glyph --serve 4100 gab nichts aus, nicht einmal die Zeile im listen-Callback, und endete mit 0. Nichts im Quellcode sah falsch aus, und die Typprüfung lief durch. Ein Agent, der darauf trifft, hat keinen Fehler zu melden und keinen Grund anzunehmen, dass etwas schiefgegangen ist.

So sieht es aus

Ein vollständiger TCP-Server. main kehrt sofort zurück; die Callbacks laufen, solange der Prozess lebt:

Ein Server, von Anfang bis Ende 
module main

import std/io
import std/process
import net { createServer }

fn main(argv: Array<string>) -> number {
  let server = createServer(fn(socket) {
    mut socket.write("hello\n")
    mut socket.end()
  })

  mut server.on("error", fn(err) {
    io.eprintln("cannot listen: ${err.message}")
    process.exit(1)
  })

  mut server.listen(4000, fn() {
    io.println("listening on 4000")
  })
  return 0
}

net ist ein Node-Builtin, also ein ganz normaler Import, aber es gehört nicht zu den sechs, für die der Compiler ambiente Typen mitliefert (fs, http, path, os, crypto, url). Installier entweder @types/node, dann bevorzugt der Build das, oder leg eine Deklaration in .types/net.d.ts neben deinen Quellcode, und genau das macht die Chat-App, damit sie überhaupt keine Abhängigkeiten braucht.

Zwei Dinge, die man wissen sollte. Das return 0 läuft, bevor sich der erste Client überhaupt verbindet: Es ist der Code, mit dem der Prozess irgendwann endet, keine Aussage darüber, wann er endet. Und alles, was nach der Rückkehr von main fehlschlägt, muss seinen eigenen Exit-Code setzen, weil der Rückgabewert von main schon verbraucht ist. Dafür ist der error-Handler da. Ohne ihn leert ein Server, der seinen Port nicht binden kann, seine Event-Loop und endet mit 0, also mit einer Erfolgsmeldung.

Ein echter

examples/apps/chat ist ein Chat-Server, der mehrere TCP-Clients gleichzeitig hält. Die Teile, die das Netzwerk nicht berühren, bleiben getrennt und testbar: Zeilenzusammensetzung, Routing und die Raum-Engine sind reine Funktionen, die von @example geprüft werden, und eine Datei spricht mit Sockets.

Die andere Richtung: ein lange laufender Client

Ein Bot hat dieselbe Form, nur nach außen gerichtet. examples/apps/discord ist ein Discord-Gateway-Client: Er verbindet sich über einen WebSocket, identifiziert sich, sendet Heartbeats im Intervall, das der Server vorgibt, verfolgt eine Sequenznummer, damit eine abgebrochene Verbindung fortgesetzt statt neu begonnen wird, bemerkt, wenn die Verbindung offen, aber tot ist, und wartet zwischen Wiederverbindungen zunehmend länger.

Kopierenswert ist, wo die Logik lebt. Zu entscheiden, was bei einem RECONNECT, einem verpassten Heartbeat oder einem abgelehnten Token zu tun ist, ist eine reine Funktion von einer Session und einem Event zu einer neuen Session und einer Liste von Aktionen. Ein Modul führt diese Aktionen auf einem echten Socket aus. Deshalb wird die Wiederverbindungslogik, der schwer richtig zu machende Teil, von @example geprüft statt durch das Ziehen eines Netzwerkkabels:

Diese drei Beispiele sind jeweils ein Bug, der zuerst im Code war. Ein Mock-Gateway zu schreiben und den Bot darauf zu richten, hat einen davon gefunden. Die anderen beiden wurden von einem zweiten Mock gefunden, der nach der Discord-Dokumentation statt nach dem Client geschrieben wurde und Dinge schickt, die ein kooperativer Mock nie schickt: eine unaufgeforderte Heartbeat-Anfrage und einen Close-Code, der bedeutet "dein Token ist falsch, hör auf zu fragen". Ein Mock, den der Autor des Clients schreibt, testet nur die Teile des Protokolls, die der Autor gelesen hat.

Wo es steht

Heute verfügbar

Die Rückkehr aus main setzt den Exit-Code, ohne den Prozess zu stoppen, also laufen Server, Watcher und Event-Loops. Ein Programm, das nur rechnet, endet weiterhin in dem Moment, in dem main zurückkehrt, mit demselben Code, also hat sich an kurzen Programmen nichts geändert. Node-Builtins wie net sind ganz normale Imports, und ein Programm, das beim Einrichten wirft, beendet sich weiterhin, jetzt aber erst, nachdem seine Diagnose ein umgeleitetes stderr erreicht hat, statt möglicherweise durch das Beenden abgeschnitten zu werden. std/timers plant Arbeit ein (after, every, cancel, unref), und std/websocket öffnet eine Verbindung, also braucht keins davon eine handgeschriebene Deklaration.

Wird schärfer

Ein Listener, der nach der Rückkehr von main nicht binden kann, endet mit 0, wenn das Programm nichts anderes sagt: process.set_exit_code(1) hält den Fehlschlag fest, ohne laufende Arbeit abzubrechen, und process.exit(1) stoppt sofort. Der Compiler kann noch nicht warnen, dass du es vergessen hast. Und es gibt weiterhin keinen Weg aufzuschreiben, dass eine Funktion nicht zurückkehrt, also trägt das main eines Servers ein return 0, das nie erreicht wird.
