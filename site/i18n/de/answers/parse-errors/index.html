27 · Parse-Fehler

Wenn das Parsen fehlschlägt, erfahre ich warum?

Ja. Jedes Problem nennt das Feld, sagt, welche Regel der Wert verletzt hat, und enthält einen code, auf den du verzweigen kannst. Ein Feld, das durch ein where-Prädikat eingeschränkt ist, meldet das Prädikat selbst, also führt die Ablehnung per grep zurück zu der Zeile, die es festgelegt hat.

Warum das wichtig ist

Ein Validator, der sagt "dieser Payload ist ungültig", hat die halbe Arbeit gemacht. Der Handler muss trotzdem entscheiden: Ist das ein Client, der ein Feld vergessen hat, oder ein Client, der ein Passwort mit vier Zeichen geschickt hat? Das eine ist ein 400, das andere ein 422, und wenn der Validator es nicht sagt, parst du am Ende denselben Body zweimal mit zwei verschiedenen Typen, um eine Information zurückzugewinnen, die der Validator schon hatte.

Genau das ist beim Bau einer Auth-API in Glyph passiert. Eine Registrierung ganz ohne password-Schlüssel kam als weak_password zurück, weil fehlend und zu kurz denselben String erzeugten.

So sieht es aus

Ein Typ, eine Einschränkung:

signup.glyph 
pub type Password = string where value.length >= 8

pub type Signup = {
  email: string,
  password: Password,
}

Vier ungültige Payloads, vier verschiedene Antworten. Jede ist ein Issue, dargestellt als code | path | message:

Signup.parse(...) 
// { "email": "user@example.com" }
missing     ["password"]  field `password` is required

// { "email": "user@example.com", "password": "short" }
refinement  ["password"]  expected Password (string where value.length >= 8)

// { "email": 42, "password": "longenough" }
type        ["email"]     field `email` must be string

// [1, 2, 3]
type        []            expected Signup (an object), got an array

Auf die zweite kommt es an. value.length >= 8 wird einmal geschrieben, am Typ, und die Ablehnung zitiert es wörtlich. Kopier diesen String aus einem HTTP-422-Body in grep, und du landest bei der Deklaration, die ihn erzeugt hat. Niemand muss eine Kopie der Regel in der Schicht für Fehlermeldungen pflegen, und genau so laufen die beiden auseinander.

Die vierte war früher schlimmer als nur eine schlechte Meldung. Für typeof ist ein Array ein Objekt, also akzeptierte ein Record ohne Pflichtfelder eins ohne Weiteres, und ein gepostetes [1, 2, 3] kam als ein verwirrendes Problem pro deklariertem Feld zurück, von denen keins erwähnte, dass du eine Liste geschickt hattest.

Verschachtelte Typen sprechen für sich selbst

Ein Feld, dessen Typ einen eigenen Deskriptor hat, wird vom parse dieses Typs validiert, und seine Probleme kommen mit dem Feldnamen vorn im Pfad zurück. Ein Password zwei Ebenen tief meldet also ["body", "password"] und bringt trotzdem seine eigene Meldung mit. Ort und Grund bekommst du aus demselben Problem, ohne etwas erneut auszuführen.

Der Code, nicht der String

Issue enthält ein optionales code: "missing", "type", "refinement" oder "unexpected". Verzweige darauf. Auf den Meldungstext zu matchen ist genau die Fragilität, die Glyph beseitigen soll, und die Meldung ist für den Menschen, der den Response-Body liest.

Eine Aufteilung in 400/422, die die Meldung nicht liest 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code ist optional, also kompilieren ein Issue, das du von Hand baust, und jeder Konsument, der vor seiner Einführung geschrieben wurde, weiterhin unverändert.

Wo es steht

Heute verfügbar

Records und where-Typen melden die verletzte Regel, nicht nur das fehlerhafte Feld: "missing" für ein fehlendes Pflichtfeld, "type" für die falsche Form (einschließlich eines Nicht-Objekts oder eines Arrays), "refinement" für einen Wert, der seinen Basistyp bestanden und das Prädikat verfehlt hat, und "unexpected" für einen Schlüssel, den der Typ nicht deklariert. Eine Verfeinerung zitiert ihr Prädikat. Ein Feld, dessen Typ einen Deskriptor hat, delegiert an ihn, also kommen verschachtelte Probleme mit dem vollständigen Pfad an. Optionale Felder (f?: T) werden nie als fehlend gemeldet.

Wird schärfer

Zwei Grenzen. Ein Feld, dessen Typ keinen eigenen Deskriptor hat, ein uneingeschränkter Typparameter oder ein Typ aus einer handgeschriebenen .d.ts, bekommt weiterhin die flache Prüfung und ein "type"-Problem; der Compiler erzeugt für diese keinen Deskriptor, und glyph gen dts auf der Deklaration auszuführen gibt ihnen einen. Ein Modul, das einen eigenen Typ namens Issue deklariert, überdeckte früher den aus dem Prelude in der erzeugten Datei und machte jeden Deskriptor in diesem Modul kaputt; seit 0.1.60 ist diese Deklaration E0110 an der Zeile, die den Typ nennt, also erfährst du, wo das Problem liegt, statt einen tsc-Fehler über generierten Code zu lesen.
