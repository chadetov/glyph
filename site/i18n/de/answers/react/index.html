Funktioniert es mit React: Komponenten, Hooks und Context?

Ja. Eine component kompiliert zu einer React-Function-Component, JSX wird zu createElement übersetzt, die eigenen Hooks von React werden über ihren Namen importiert und ihre Paare destrukturiert, und Reducer-Zustand bekommt eine Erschöpfendheitsprüfung, die einfaches TypeScript nicht hat. Die Seite selbst (ihr Titel, der Mount-Punkt, gespeicherter Zustand) wird über std/dom und std/storage erreicht. Die Lücke, die du zuerst kennen solltest: Glyphs eigener Checker typisiert nicht, was ein Hook zurückgibt, also prüft tsc diese Werte.

Warum das wichtig ist

Ein großer Teil des Codes, den Agenten schreiben, ist React. Glyph behandelt es als vollwertiges Ziel, nicht als Anbau: component ist ein eigenes Schlüsselwort (also prüft grep "^component " deine ganze UI). Die Hooks von React werden aus react importiert und mit ihren echten Namen und Typen aufgerufen, von tsc gegen Reacts eigene Deklarationen geprüft.

So sieht es aus

Reacts echtes useReducer mit einem Reducer über einer Tagged Union. Jede Action muss behandelt werden, und der Compiler prüft das:

counter.glyph, gegen react@18 und seine Typen 
import react { useReducer }

type Action = Inc | Dec | Reset

fn reducer(n: number, a: Action) -> number {
  return match a {
    Inc => n + 1,
    Dec => n - 1,
    Reset => 0,
    // add an Action variant and this match is E0200
  }
}

pub component Counter() {
  let [count, dispatch] = useReducer(reducer, 0)
  return <button on_click={fn() { dispatch(Inc) }}>{count}</button>
}

Füg eine Action Double hinzu, und der Reducer kompiliert nicht mehr, mit E0200, das sie nennt, was ein einfacher TypeScript-switch durchgehen lassen würde. Das Paar wird mit let [count, dispatch] destrukturiert, und das erzeugte TypeScript fügt satisfies readonly [unknown, unknown] hinzu, also beweist tsc, dass der Hook ein Paar zurückgegeben hat, und leitet trotzdem den Typ jedes Elements ab. Glyphs eigener Checker typisiert keine Werte, die aus React kommen, also wird ein falsches Argument an dispatch oder einen State-Setter von tsc im Build gemeldet, nicht vom Editor oder von --no-tsc. React-Context funktioniert heute über createContext / useContext, und Elementnamen als Member-Ausdruck (<ThemeContext.Provider>) funktionieren direkt: kein Workaround.

Prop-Spreading in JSX funktioniert auch: <input {...register("email")} /> wird zu einem Objekt-Spread in den Props übersetzt, also braucht das Idiom von react-hook-form keinen Adapter. Die aus Werten abgeleiteten Typen von Zod sind vollwertig: type FormData = z.infer<typeof schema> funktioniert direkt, ohne Hintertür. Der eine Unterschied: Eine Komponente nimmt einen einzigen Props-Record, nicht mehrere positionale Parameter. Siehe deine Bibliotheken verwenden und die Härtungsseite dazu, wo genau diese Grenze liegt.

Werden Props vor tsc geprüft?

Ja. Glyph vergleicht jedes Element selbst mit dem Props-Record seiner Komponente, also sind ein falscher Wert, ein falsch geschriebenes Prop und ein fehlendes Pflicht-Prop Glyph-Fehler, die das Prop nennen. Du siehst sie im Editor und über MCP, nicht nur in einem vollständigen Build. Es funktioniert gleich, ob die Komponente über ihren Namen oder über ihr Modul importiert wurde:

main.glyph, mit Card deklariert in ui.glyph 
import ui

pub component App() {
  return <div>
    <ui.Card title="Q3" />
    <ui.Card title="Q4" cout={2} />
  </div>
}

// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`
// E0210 type `CardProps` has no field `cout`; did you mean `count`?
// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`

--json liefert die fehlenden Namen als Liste missing_fields, also kann ein Agent die Props hinzufügen, ohne die Meldung zu parsen. Eine Komponente muss ihre Props außerdem als einen Record nehmen: component Greeting(name: string) ist E0229 am Parameter, weil React immer nur das Props-Objekt übergibt und dieses Element nie die Typprüfung bestehen könnte. Wenn du sie als Funktion aufrufst, statt sie zu rendern, deklariere sie mit fn.

Wird ein <match> in JSX wie ein match geprüft?

Es ist dasselbe. Jeder <case> nimmt das Pattern, das ein match-Arm nimmt, und der Compiler schickt es durch den Code, den er für den Arm verwendet. Die Namen, die ein Case bindet, haben die Typen des Payloads, ein Feld, das der Payload-Record nicht hat, ist E0210, und eine fehlende Variante ist E0200. Ein Case, der einen Wert testet, deckt nur einen Teil seiner Variante ab, also braucht er einen Geschwister-Case oder ein <case else>, das den Rest nimmt:

results.glyph 
type Page =
  | Loading
  | Loaded({ users: Array<User>, total: number })
  | Failed(string)

component Results(props: { page: Page }) {
  return <match value={props.page}>
    <case Loading><p>Loading...</p></case>
    <case Loaded({ users, totl })><p>{users.length} of {totl}</p></case>
    <case Failed(message)><p>{message}</p></case>
  </match>
}

// E0210 type `{ users: Array<User>, total: number }` has no field `totl`; did you mean `total`?

Wie startet eine Seite es?

Glyph hat keine Anweisungen auf oberster Ebene, also ruft die Seite selbst ein exportiertes main auf. Die App besteht aus zwei Modulen: eins mit den Komponenten und eins, das sie über std/dom und createRoot von react-dom auf #root mountet. Event-Attribute sind in snake_case (on_change erzeugt Reacts onChange), ein Handler ist ein Lambda, und der Text eines Inputs ist e.currentTarget.value.

app.glyph 
module app

import react { useState }

pub component App() {
  let [name, set_name] = useState("")
  return <main>
    <input value={name} on_change={fn(e) { set_name(e.currentTarget.value) }} />
    <p>Hello, {name}</p>
  </main>
}
main.glyph 
module main

import react-dom/client { createRoot }
import std/dom
import std/console
import std/option { Some, None }
import app { App }

pub fn main() -> void {
  match dom.element_by_id("root") {
    Some(root) => createRoot(root).render(<App />),
    None => console.error("the page has no #root element"),
  }
}
index.html, neben den beiden Modulen 
<div id="root"></div>
<script type="module">
  import { main } from "./dist/gen/main.ts";
  main();
</script>

npx glyph build . --out dist/gen prüft die Module, führt tsc --strict gegen Reacts Deklarationen aus und schreibt TypeScript nach dist/gen. npx vite build --outDir dist/web liest dann index.html, folgt dem Import und bundelt es mit React. Dieses main nimmt nichts und gibt nichts zurück, weil das Skript es ohne Argumente aufruft; das main(argv) -> number, das glyph init schreibt, ist das, was glyph run unter Node aufruft. Die vollständige Anleitung, mit der package.json und der Installationszeile, ist Glyph in einer Browserseite ausführen in der Referenz, die glyph llms ausgibt. CI baut examples/apps/todo auf dieselbe Weise und rendert es in einem Headless-Chromium.

Wo es steht

Heute verfügbar

Komponenten, JSX, Fragmente (<>...</>), Elementnamen als Member-Ausdruck (<Ctx.Provider>), Prop-Spread in JSX ({...register()}), Props, die bei jeder Import-Schreibweise vor tsc gegen die Komponente geprüft werden, Reacts eigene Hooks über ihren Namen importiert (useState, useReducer, useEffect), wobei tsc ihre Typen prüft und ihre Paare destrukturiert werden (let [count, set_count] = useState(0)), useReducer mit erschöpfenden Tagged-Union-Actions, <match>/<case> geprüft und als match mit den Patterns des Arms übersetzt, Context über createContext/useContext und die Seite über std/dom (Titel, Mount-Punkt, Adresse), std/storage und std/console. JSX-Text wird gelesen wie TSX ihn liest, also ist <p>Don't stop</p> einfacher Text; }, >, // und eine HTML-Entity wie &amp; werden im Text abgelehnt (E0012), mit der Schreibweise, die stattdessen zu verwenden ist. Ein Member-Zugriff auf ein Array wird geprüft, also ist {items.foo} auf einem Array<string> E0210. examples/apps/todo ist eine ganze App auf React 18, die mit Vite gebundelt wird und im Browser rendert.

In Arbeit

Glyphs Checker typisiert das Ergebnis eines Hooks nicht, also ist set_count("x") auf einem Zahlen-State ein tsc-Fehler im Build statt eines Glyph-Fehlers im Editor. std/dom hört beim Lesen der Seite und Setzen ihres Titels auf: React gehört das DOM, das es rendert, also gibt es keine Element-Setter oder Event-Listener. Ein Effect muss als fn() -> void { ... } geschrieben werden, weil ein Lambda seinen letzten Ausdruck zurückgibt und React ihn als Cleanup aufrufen würde. Ein inline geschriebener Props-Typ erscheint in diesen Meldungen weiterhin als record; ein benannter zeigt seinen Namen. Die Glyph-Ausgabe in eine bestehende Vite-App mit UI in TypeScript einzubetten, steht im Deployment-Guide.
