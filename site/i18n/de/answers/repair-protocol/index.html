23 · Einen roten Build reparieren

Wenn der Build fehlschlägt, sagt der Compiler meinem Agenten, wie er es behebt?

Er sagt dir als Daten, was falsch ist, nicht als Satz, den man parsen muss: die beiden Typen, das schuldige Symbol als module::name und die endliche Liste der Dinge, die zulässigerweise dort stehen könnten, wo das Falsche steht. glyph check --agent ergänzt, was die reparierende Änderung nicht kaputtmachen darf. Wo die Antwort vollständig feststeht, schreibt glyph fix sie.

Warum das wichtig ist

Die Schleife eines Agenten um einen Compiler ist: den Fehler lesen, die Änderung raten, neu bauen. Beim Raten entsteht der Schaden, und er entsteht, weil der Fehler ein String ist. Ein Agent, der "non-exhaustive match on OrderStatus" liest, weiß, dass einem match Arme fehlen. Er weiß nicht, was die fehlenden Varianten mitbringen, also schreibt er Paid("tx_1") und erfährt es aus der nächsten Diagnose. Oder er liest das Wort "exhaustive", fügt einen else-Arm hinzu, und der Build wird grün, nachdem er genau die Garantie weggeworfen hat, die die Diagnose schützen sollte.

Der Compiler wusste das alles. Er kannte die Varianten der Union und ihre Payloads, er wusste, dass ein else die Abgeschlossenheit aufgeben würde, und er ließ beides eine Zeile vor der Antwort fallen.

So sieht es aus

Ein Projekt mit zwei Modulen. orders deklariert die Union; main schreibt ein match darüber und behandelt einen Fall. glyph check --agent, gekürzt auf die Schlüssel, auf die es hier ankommt:

glyph check --agent --no-tsc src 
{
  "code": "E0200",
  "severity": "error",
  "stage": "typecheck",
  "message": "non-exhaustive match on `OrderStatus`: missing variants
              `Paid`, `Cancelled`",
  "help": "Add an arm for each missing variant.",
  "file":   "main.glyph",
  "module": "main",
  "entity": "main::describe",
  "cause":  "orders::OrderStatus",
  "related": ["Pending", "Paid", "Cancelled"],
  "missing_variants": ["Paid", "Cancelled"],
  "expected": null, "actual": null, "alternatives": null,

  "constraints": [
    "preserve exhaustiveness: this match must name every case of
     `OrderStatus`, so add one arm for each of `Paid`, `Cancelled`.",
    "do not add an `else` arm: `OrderStatus` is declared in this project,
     and a catch-all forfeits the guarantee that adding a variant to it
     later forces this match to be updated (D9)."
  ],

  "symbols": [
    { "entity": "orders::OrderStatus", "kind": "union", "pub": true,
      "type": "Pending | Paid({ transaction_id: string }) | Cancelled",
      "exhaustive_match": true,
      "variants": [
        { "name": "Pending", "payload": null, "construct": "Pending" },
        { "name": "Paid",    "payload": "{ transaction_id: string }",
          "construct": "Paid({ transaction_id: string })" },
        { "name": "Cancelled", "payload": null, "construct": "Cancelled" }
      ] }
  ],
  "symbols_absent": [],

  "explain": { "command": "glyph --explain E0200",
               "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200" }
}

Drei Dinge lohnt es sich herauszugreifen. cause ist das schuldige Symbol, und das ist etwas anderes als entity, die Deklaration, in der die Diagnose steht: Hier findet die Änderung in main::describe statt, und die Form, die sie treffen muss, kommt aus orders::OrderStatus. Beides sind Adressen, die die anderen Tools nehmen, also lässt sich eine Antwort verketten, ohne etwas neu herzuleiten.

constraints sind nicht die Reparatur. Jede ist etwas, das der Compiler schon durchsetzt, ausgeschrieben, damit die Änderung, die die Diagnose erfüllt, nicht die Garantie dahinter bricht. Die zweite Constraint ist der Grund, warum es den Schlüssel gibt: Ein else-Arm ist zulässig, er würde den Build grün machen, und die Constraint sagt, was es kostet, ihn zu nehmen.

symbols ist die Antwort von glyph_symbol für jedes Symbol, das die Diagnose nennt, also braucht die nächste Änderung des Agenten keinen zweiten Aufruf. Ein Symbol, das das Tool ablehnt, erscheint in symbols_absent mit dem Grund, was "wir haben nicht nachgesehen" von "wir haben nachgesehen, und es ist nicht da" getrennt hält.

Jeder Schlüssel ist immer vorhanden. Eine Information, die der Compiler nicht hat, kommt als explizites null an, nie als fehlender Schlüssel, also hat Fehlen bei jedem Code und auf der CLI wie auf der MCP-Schnittstelle eine einzige Schreibweise.

Wo die Antwort feststeht, schreibt der Compiler sie

glyph fix wendet nur die Reparaturen an, die der Compiler selbst entscheidet: unbenutzte Imports, einen Arm-Kopf, der keine Variante ist, wenn der Checker genau einen Vorschlag berechnet hat, und ein Feld, das der Record nicht deklariert, wenn genau ein deklariertes Feld ein Zeichen entfernt ist. Das match oben gehört nicht dazu.

glyph fix src, auf dem match oben 
glyph fix: removed 0 unused import(s) across 0 file(s).
glyph fix: declined E0200 in src/main.glyph: the compiler does not
           determine what a missing arm should do, so `glyph fix`
           writes none: add an arm for each of `Paid`, `Cancelled`.
           `glyph check --agent` gives the pattern each case takes.

// src/main.glyph is unchanged, and glyph check still fails with E0200.

Der Compiler weiß, welche Fälle fehlen und welches Pattern jeder nimmt. Er weiß nicht, was das Programm tun soll, wenn eine Bestellung Paid ist, und jeder Rumpf, den er schriebe, wäre eine Vermutung, die kompiliert. Bis 0.1.128 schrieb glyph fix diese Vermutung: ein Arm pro Fall, dessen Rumpf den Fall ausgab und process.exit(1) aufrief. Das Programm bestand dann check, tsc und build, und glyph query variants meldete das match als erschöpfend, also war der fehlende Fall von einem Compile-Fehler zu einem Absturz zur Laufzeit gewandert, und nichts war mehr übrig, um ihn zu melden.

Also lehnt die Regel ab und nennt die Fälle. Alles, was man braucht, um die Arme zu schreiben, steht schon in der --agent-Antwort oben: missing_variants und die construct-Schreibweise jeder Variante unter symbols. Die Arme schreibst du oder dein Agent, genau wie jeden anderen Code, dessen Verhalten der Compiler nicht ableiten kann.

Was glyph fix schreibt, schreibt es ohne zu raten, und jede Regel, die keine Antwort entscheiden kann, gibt die Ablehnung und den Grund in derselben Ausgabe aus wie das, was sie angewendet hat. Zwei Felder, die ein Zeichen von einem Tippfehler entfernt sind, sind zwei, nicht eins, und es sagt das, statt eins auszuwählen.

Die Erklärung des Codes selbst, als Daten

glyph --explain <CODE> --json antwortet mit der ausführlichen Erklärung, der einzeiligen help, der URL der Dokumentation und einem fehlerhaften Programm aus dem Negativ-Korpus des Compilers, gepaart mit der Diagnose, die dieser Compiler dafür auslöst. Die Diagnose wird kompiliert, wenn du fragst, nicht gespeichert, also kann sie nicht von dem abweichen, was der Compiler tatsächlich sagt.

glyph --explain E0200 --json 
{
  "code": "E0200",
  "title": "non-exhaustive match",
  "explanation": "A `match` over a tagged union must handle every variant.
    Unions are sealed (D9): adding a variant later forces every match to be
    updated, so a missing variant cannot silently fall through at runtime ...",
  "help": "Add an arm for each missing variant.",
  "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200",
  "counter_example": {
    "name": "alias_of_local_union_not_exhaustive",
    "expected_error": "E0200",
    "files": [ { "path": "alias_of_local_union_not_exhaustive.glyph",
                 "source": "module main\n\ntype Shape =\n  | Circle\n ..." } ],
    "diagnostic": { "code": "E0200",
                    "message": "non-exhaustive match on `Shape`: missing variants `Tri`",
                    "cause": "alias_of_local_union_not_exhaustive::Shape",
                    "related": ["Circle", "Square", "Tri"],
                    "missing_variants": ["Tri"] },
    "corrected": null,
    "corrected_absent": "`tests/negative/` pairs no repaired program with a case:
      an entry is a wrong program and the code it draws. A fix invented here would
      compile nowhere and be checked by nothing."
  }
}

Ein Code, den der Korpus nicht abdeckt, kommt mit counter_example: null und einem Satz zurück, der sagt, dass der Korpus keinen Fall dafür enthält, statt mit einem erfundenen Beispiel. Der Korpus behauptet, was er abdeckt, und nichts über den Rest.

glyph --explain liefert einen Fall pro Code. Der ganze Korpus ist ebenfalls lesbar: glyph llms --negative E0200 gibt jedes fehlerhafte Programm aus, das den Code auslöst, jedes kompiliert, wenn du fragst, und wo ein zweiter Korpus ein Programm, das tsc --strict akzeptiert, mit dem Glyph paart, das es ablehnt, kommt das daneben zurück. Ohne Code listet es 102 Fälle über 46 der 70 Codes und nennt die 24, die keinen haben, also wird die Abdeckung angegeben, statt aus dem abgeleitet zu werden, was zurückkam. Das und der Rest dessen, was der Compiler über sich selbst veröffentlicht, steht auf einer eigenen Seite.

Wo es steht

Heute verfügbar

Jede Diagnose enthält expected, actual, cause, alternatives (mit alternatives_kind, das sagt, ob es fields, members, variants, literals oder exports listet, gesetzt dort, wo der Fehler ausgelöst wird), related, module, file und explain, befüllt aus dem Fehler, den der Compiler ausgelöst hat, statt neu hergeleitet, und jedes ist ein explizites null, wenn der Compiler keine solche Information hat. file ist ein Pfad relativ zum Resolution-Root, und der Bericht nennt dieses Root in project_root, sodass sie sich öffnen lässt. glyph check --agent ergänzt constraints und symbols pro Diagnose. glyph fix wendet drei Regeln an (E0106, E0210, E0220) und nennt jede Ablehnung mit ihrem Grund, einschließlich jedes E0200, das es meldet und nie schreibt. glyph --explain <CODE> --json liefert die Erklärung mit einem kompilierten Gegenbeispiel, und glyph llms --negative <CODE> liefert den ganzen Korpus fehlerhafter Programme, die ihn auslösen.

Wo es aufhört

cause bei E0211 ist null: Das schuldige Symbol an einem Aufrufargument ist ein Parameter, und module::fn.param lässt sich im Vokabular der Identitäten nicht ausdrücken, also ist das null Absicht und kein Versäumnis. corrected bei einem Gegenbeispiel ist immer null, weil der Negativ-Korpus keinem Fall ein repariertes Programm zuordnet, und 24 der 70 Codes haben überhaupt keinen Fall. glyph fix schreibt drei Regeln und sonst nichts, und es schreibt keinen Arm für ein nicht erschöpfendes match: Die bleiben dir oder deinem Agenten überlassen, mit den Fällen und ihren Patterns in der Diagnose. Alles, was es ablehnt, lehnt es laut ab.
