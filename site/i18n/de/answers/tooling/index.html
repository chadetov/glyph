Wie sieht es mit Editor, Debugging und Fehlermeldungen aus?

glyph lsp spricht das Language Server Protocol über stdio, also bekommt jeder Editor mit LSP-Client Diagnosen, Typen beim Hover, Go-to-Definition, Vervollständigung und Formatieren beim Speichern. Eine VS-Code-Erweiterung liegt im Repository; sie ist noch nicht im Marketplace, also baust du sie aus dem Quellcode. Jeder Fehler hat einen stabilen Code, den Fix und den Grund.

Warum das wichtig ist

Eine Sprache zu bearbeiten, die dein Editor nicht versteht, fühlt sich wie ein Rückschritt an, und anfangs war das ein berechtigter Einwand. Das ist er nicht mehr: Dein Editor gibt dir den modernen Komfort, und die Fehler sind geschrieben, um zu erklären, nicht nur um abzulehnen.

Ist das ein echter LSP oder nur ein VS-Code-Plugin?

Ein echter. Der Compiler liefert einen Language Server mit, den du als glyph lsp startest und der das Language Server Protocol über stdio spricht (der Standard-JSON-RPC-Transport, den jeder LSP-Client versteht).

Die mitgelieferte VS-Code-Erweiterung ist ein dünner Client darum, aber nichts daran ist VS-Code-spezifisch: Richte jeden LSP-fähigen Editor, Neovim, Helix, Zed, Emacs (eglot), auf glyph lsp, und er verhält sich gleich.

Es ist dasselbe Binary, das du schon installiert hast (npx @glyphlang/glyph lsp), also gibt es keinen separaten Server zu holen.

Was der Server implementiert

Der Server implementiert, was ein Editor braucht: Live-Diagnosen mit den stabilen Codes unten, Typen beim Hover, Go-to-Definition (modulübergreifend über einen benannten Import; über einen Namespace liefert ui.Button noch keine Antwort), Vervollständigung, Dokument- und Workspace-Symbole für Gliederung und Symbolsuche, Find-References über den ganzen Workspace, Umbenennen und Formatieren im kanonischen glyph fmt-Layout beim Speichern.

Das Umbenennen ist vollständig: Eine Deklaration auf Modulebene umzubenennen ändert ihre Definition, jede Referenz und das import-Binding jedes importierenden Moduls im ganzen Workspace, und es prüft den neuen Namen (ein echter Bezeichner, kein Schlüsselwort), bevor es etwas anfasst.

Zwei Grenzen, die man kennen sollte: Der dateiübergreifende Index wird bei jeder Anfrage neu aufgebaut statt gecacht (für ein normales Projekt in Ordnung, später lohnt es sich, das zu beschleunigen), und eine Datei, die sich gerade nicht parsen lässt, wird übersprungen, also erreicht ein Umbenennen keine Referenzen in einer Datei, die selbst kaputt ist.

Fehlermeldungen

Wir haben die Meldungen genau dort geschärft, wo Agenten und Neulinge am häufigsten stolpern: Wer if schreibt, wird jetzt auf match verwiesen statt auf ein allgemeines “unerwartetes Token”, und eine falsche Argumentanzahl, ein nicht erschöpfendes match oder eine falsch geschriebene Variante bekommen jeweils einen eigenen Fehler mit Code und Fix.

Typfehler, die nur das TypeScript-Backend finden kann, zeigten früher auf die erzeugte .ts. Jetzt werden sie zurück auf deine .glyph abgebildet (derselbe ariadne-Caret, derselbe stabile Code), also liest sich ein tsc-Fehler wie ein nativer Glyph-Fehler.

Debugging

Du debuggst das erzeugte TypeScript mit den Tools, die du schon verwendest, etwa dem Inspector von Node, den Devtools des Browsers oder dem JS/TS-Debugger deiner IDE.

Jeder Build liefert neben jeder .ts eine Standard-v3-Source-Map (mit eingebettetem Glyph-Quellcode), also führt ein Debugger oder ein Bundler, der Maps verkettet, zurück zu den Zeilennummern deiner .glyph.

Eine Sache deckt es noch nicht ab: Der eigene Absturz-Stack von glyph run gibt weiterhin .ts-Zeilen aus, weil tsx die Map nicht durch seine Transformation verkettet. Diesen Stack umzurechnen kommt als Nächstes.

Fragen, “kompiliert das?”, ohne es auszuführen

glyph check path.glyph prüft die Typen einer Datei oder eines ganzen Verzeichnisses und beendet sich. Es schreibt nichts in deinen Baum, was glyph run nicht versprechen konnte und glyph build überhaupt nicht tun würde (es lehnte alles ab, was kein Verzeichnis war).

--no-tsc--json--no-test
Details was es ausführt, und die Flags

Es führt dieselbe Pipeline aus wie ein Build, einschließlich tsc --strict über das erzeugte TypeScript, in ein temporäres Verzeichnis, das es am Ende löscht. --no-tsc hört nach den Glyph-Stufen auf, wenn du die schnelle Antwort willst; --json gibt einem Agenten dieselbe Form von Diagnosen wie glyph build --json. Eine Datei wird im Kontext ihres eigenen Verzeichnisses geprüft, also lässt ein kaputtes Geschwister die Prüfung trotzdem scheitern. Deine @example- und @doc @run-Tests laufen hier auch, dasselbe Gate, das glyph build verwendet, also kann eine Prüfung keinen sauberen Baum melden, an dem ein Build scheitern würde; --no-test überspringt sie, wenn du eine Antwort willst, die nichts ausführt.

Auch die Ausgabe lügt dich nicht an

Die Zusammenfassung erscheint jetzt nach jeder Stufe, die den Build rot machen kann, also zeigt ein roter Build nie eine grüne Zeile.

Geschichte die Zusammenfassung, die zu früh kam

Ein fehlschlagender Build begann früher mit “no diagnostics” und gab darunter tsc-Fehler aus, weil die Zusammenfassung der Glyph-Stufen geschrieben wurde, bevor die TypeScript-Stufe lief.

Im selben Durchgang fing glyph run app.glyph --min -12.50 an zu funktionieren: Ein führender Bindestrich ließ clap das Argument früher ablehnen, bevor dein main es überhaupt sah.

Flags, die glyph gehören, binden weiterhin an glyph, also setz -- vor ein Programm-Flag, das mit einem davon kollidiert.

Und für den Agenten in der Schleife

glyph build --json gibt jede Diagnose als strukturiertes JSON aus: ein stabiler Code, Schweregrad, Meldung, Datei und 1-basierter Bereich aus Zeile/Spalte, dazu Hilfe und Hinweis, einschließlich der tsc-Fehler, die auf deinen Glyph-Quellcode abgebildet sind. Ein Agent liest sie und handelt direkt danach, statt Terminaltext auszuwerten.

glyph mcp für interaktive Agenten

Für interaktive Agenten gibt es mehr als Batch-Diagnosen: glyph mcp startet einen Model-Context-Protocol-Server über stdio (dasselbe Binary, dieselbe Analyse, die der Editor verwendet), der die Abfragen des Language Servers als MCP-Tools bereitstellt. Ein Agent kann nach den Diagnosen einer Datei fragen, nach dem Typ an einer Position, wo ein Name definiert ist (Imports folgend), nach jeder Referenz auf ein Symbol im ganzen Projekt oder nach einer Symbolsuche, ohne einen vollständigen Build auszuführen oder jede Datei zu lesen.

Es ist ein dünner Adapter über derselben reinen Analyseschicht, keine zweite Implementierung, also kann es nicht von dem abweichen, was Compiler und Editor sehen.

Nicht alles ist ein harter Fehler

Glyph hat eine Warnstufe, die Ballast meldet, ohne den Build scheitern zu lassen: einen unbenutzten Import (E0106), ein unbenutztes let (E0107, ausgenommen Namen, die mit _ beginnen), und unerreichbaren Code nach einem return/break/continue (E0108).

E0106E0107E0108

Diese halten ein Modul ehrlich: Ein toter Import ist genau die Art von Rauschen, die einen Leser nach einer Abhängigkeit suchen lässt, die der Code gar nicht hat. Warnungen erscheinen in derselben gerenderten und --json-Ausgabe, nach Schweregrad markiert, und es wird trotzdem TypeScript erzeugt.

Wo es steht

Heute verfügbar

  • Ein Language Server für jeden Editor, mit Antworten über Modulgrenzen hinwegseit 0.1.124
    Details

    Ein Language Server (glyph lsp über stdio, jeder Editor; VS-Code-Erweiterung mitgeliefert) mit Syntaxhervorhebung, Diagnosen, Hover, Go-to-Definition, Vervollständigung, Symbolen, Find-References und Umbenennen über den ganzen Workspace und Formatieren beim Speichern, mit Antworten über Modulgrenzen hinweg seit 0.1.124: Der Server hält eine Datenbank pro Projekt, in der deine offenen Buffer über den Dateien auf der Platte liegen, also liefert Hover über einer importierten Funktion oder einem Feld eines importierten Records dieselbe Antwort wie glyph query hover, eine ungespeicherte Änderung in einer Datei ist von einer anderen aus sichtbar, und ein Tastendruck kostet ein bis neun Prozent mehr als bei einer einzelnen Datei;

  • Ein Model-Context-Protocol-Server glyph mcp mit elf Tools
    Details

    ein Model-Context-Protocol-Server glyph mcp mit elf Tools, den Abfragen des Editors plus glyph_symbol, glyph_impact, glyph_assignable, glyph_dependencies und glyph_exports, jedes mit einem Verb von glyph query, das dasselbe JSON für einen Agenten ohne MCP-Client ausgibt;

  • Stabile Fehlercodes, glyph --explain, Fehler des tsc-Backends auf .glyph-Quellcode abgebildet, eine Warnstufe (unbenutzter Import/Binding, unerreichbarer Code) und strukturierte Diagnosen per --json.
  • glyph check [path] prüft die Typen einer einzelnen Datei oder eines Baums, ohne ihn auszuführen oder Ausgabe zu schreiben.
  • glyph fmt --check sichert die Formatierung in CI ab: Es schreibt nichts und endet mit einem Wert ungleich null, wenn eine Datei nicht schon im einen kanonischen Layout ist.

In Arbeit

  • Den dateiübergreifenden Index cachen, statt ihn pro Anfrage neu aufzubauen (ein Geschwindigkeitsgewinn bei großen Bäumen).
  • Den eigenen Absturz-Stack von glyph run umrechnen, da tsx die erzeugte Map nicht durch seine Transformation verkettet, sodass dieser Stack weiterhin die erzeugte .ts nennt statt deiner .glyph.
