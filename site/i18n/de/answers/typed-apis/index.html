Muss ich für jede API einen Validator von Hand schreiben?

Nein. In Glyph ist ein Typ sein eigener Validator. Deklariere einen type, und der Compiler erzeugt daneben einen Laufzeit-Deskriptor, also validiert ein nicht vertrauenswürdiger Request- oder Response-Body mit einem Aufruf, ohne separates zod-Schema, das du schreiben und synchron halten musst.

Warum das wichtig ist

In den meisten TypeScript-Stacks wird jeder Payload zweimal beschrieben: einmal als type für den Compiler und noch einmal als handgeschriebener Validator, damit der Wert zur Laufzeit tatsächlich diese Form hat.

Die beiden laufen auseinander, und genau dort rutschen fehlerhafte Daten durch. Glyph legt sie zu einer Deklaration zusammen: Der Typ erzeugt den Validator, also können sie sich nicht widersprechen.

So sieht es aus

Deklariere das DTO einmal. Sein Deskriptor gibt dir .parse (einen nicht vertrauenswürdigen Wert in den Typ validieren) und .is (einen Type Guard), ohne dass du sonst etwas schreiben musst:

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}
was du nicht geschrieben hast 
// No zod schema:
const NewTask = z.object({
  title: z.string(),
  done: z.boolean(),
});
// No drift between the type and
// the validator, because there is
// only one declaration.

// A bad body, {"title": 123},
// takes the Err arm. Only a
// well-formed body reaches Ok.

Den typisierten Wert nach dem match behalten

Du kannst den Wert auch herausziehen, statt die Arbeit im Arm zu erledigen.

api.glyph: Der Wert verlässt das match typisiert 
let task = match NewTask.parse(req.body) {
  Ok(t) => t,
  Err(issues) => { return bad_request(issues) },
}
task.titel   // E0210: type `NewTask` has no field `titel`; did you mean `title`?
seit 0.1.45generische Typen: noch nicht
Details wie der Typ mitgetragen wird, und die generische Ausnahme

T.parse ist als Result<T, Array<Issue>> typisiert, und ein match, dessen Arme übereinstimmen, trägt ihren Typ, also gibt dir let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, } ein NewTask für den Rest der Funktion, mit Feldnamen, die von Glyph geprüft werden statt von tsc am erzeugten TypeScript. Das kam in 0.1.45; davor war der Wert untypisiert, sobald er das match verließ. Das parse eines generischen Typs ist dasjenige, bei dem es noch nicht so ist, weil sein Deskriptor pro Typparameter einen Laufzeit-Checker nimmt.

Das Parse-Ergebnis ist ein gewöhnliches Result

In Glyph gibt T.parse dasselbe Result zurück wie jede andere Funktion der Sprache, die fehlschlagen kann, also reichst du es direkt zurück, schickst es durch map_err, um Validierungsprobleme in deinen eigenen Fehlertyp zu verwandeln, oder reichst es mit ? weiter.

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}

Details die Laufzeitkosten, hier Result zu verwenden

Ein Validator, der dir einen Wert in seiner eigenen privaten Form zurückgibt, ist nur halb nützlich, weil der Rest deiner Fehlerbehandlung nichts damit anfangen kann. An einem Parse-Ergebnis ist nichts Besonderes.

Der Grund, warum es je anders war: Ein Deskriptor wird neben deinem type erzeugt, und das bloße Objekt auszugeben hielt ein Modul, das einen Typ deklariert, frei von einer Laufzeitabhängigkeit auf std/result. Dieser Tausch wird jetzt andersherum gemacht. Ein Modul mit einem pub type trägt einen Import von std/result, ob es je Result schreibt oder nicht, und ein Aufruf von parse allokiert die Kombinator-Closures, die jedes Ok(...) allokiert. Was du dafür bekommst: Die validierte Grenze und der Rest deiner Fehlerbehandlung sind dieselbe API.

Eigene Kombinatoren: Der Ausgabetyp wird abgeleitet, nicht blind übernommen

Glyphs infer_output<Shape> leitet den Ausgabetyp aus der Form ab, und tsc prüft deine Annotation dagegen. Eine Form, der ein Feld des behaupteten Typs fehlt, kompiliert nicht:

schema.glyph 
fn object_schema<Shape: Record<string, Schema<unknown>>>(
  shape: Shape,
) -> Schema<infer_output<Shape>> { ... }

type User = { name: string, age: number }

// The shape must produce a User, or this
// line does not compile:
const user_schema: Schema<User> =
  object_schema({
    name: string_schema(),
    age: number_schema(),
  })
das Auseinanderlaufen, das Glyph beseitigt 
// TS/zod: shape and output type are two
// separate things you keep in sync by hand.

type User = { name: string; age: number };
// `s` is inferred { name }, but nothing
// checks it against User. The `age` you
// forgot is caught at runtime, if ever.

// Glyph: drop `age` from the shape and
// `Schema<User>` fails to compile. The
// shape is the single source of truth.
Details die TypeScript-Falle, und der Cast, der seit 0.1.92 dem Return folgt

Manchmal willst du einen Kombinator im Stil von zod: einen Validator, der aus kleineren zusammengesetzt wird. Die Falle in TypeScript ist, dass der Ausgabetyp des Kombinators und die Form, die du ihm übergeben hast, auseinanderlaufen. Du schreibst die Form und wiederholst dich dann in einem zweiten Typparameter, und nichts prüft, ob sie übereinstimmen.

Der abgeleitete Typ gilt, egal wie der Kombinator zurückkehrt. infer_output braucht einen Cast an der Grenze der Funktion, weil der Rumpf einen Wert baut, von dem das Typsystem nicht beweisen kann, dass er den aus der Form abgeleiteten Typ hat, und der Compiler schreibt diesen Cast für dich. Bis 0.1.91 hing er an einem einfachen return <value>. Setz ein match zwischen das return und den Wert, oder lass den Rumpf mit r? enden, und dieselbe Funktion kompilierte nicht mehr: ein TS2322 am erzeugten TypeScript, für Glyph, das der Compiler schon akzeptiert hatte. Seit 0.1.92 folgt der Cast dem Return statt seiner Schreibweise, also besteht return match strict { ... } die Typprüfung genauso wie die Schreibweise mit einem einzigen return desselben Rumpfs.

Der Rest der nicht vertrauenswürdigen Grenze

Der Deskriptor ist derselbe, der json.parse<T> sicher macht: Gib ihm einen JSON-String, und er parst und validiert in einem Schritt.

EingabeAufrufGibt zurück
Ein JSON-Stringjson.parse<T>(text)Result<T, Array<Issue>>
Ein dekodierter BodyT.parse(value)Result<T, Array<Issue>>
Ein Headerheader(req, name)Option<string>
Ein Query-Parameterquery_param(req, name)Option<string>
Details Request-Bodys, Header und Query-Parameter

Ein Request-Body kommt schon dekodiert als unknown an, also greifst du dort stattdessen zu T.parse(value): dieselbe Garantie, kein Cast.

Der Rest der nicht vertrauenswürdigen Grenze ist genauso typisiert: header(req, name) und query_param(req, name) geben Option<string> zurück, also ist ein fehlender Header oder Query-Parameter None, und das match zwingt dich, das zu behandeln. Lass den None-Arm weg, und es kompiliert nicht. Eine fehlende Eingabe lässt sich nicht so lesen, als wäre sie vorhanden. Für ein Feld im Body gilt dieselbe Regel: timeout_ms?: number ist ein fehlender Schlüssel oder eine Zahl, also ist {"timeout_ms": null} ein Err bei ["timeout_ms"], von T.parse, is T und json.parse<T> gleichermaßen. Deklariere timeout_ms?: Nullable<number>, wenn der Absender null schreibt. Bis 0.1.152 kam dieses null innerhalb des Ok zurück.

Prüft eine Map mit einem Enum als Schlüssel ihre Schlüssel?

Ja, seit 0.1.148. Ein Record<Tier, int> mit type Tier = "free" | "pro" parst nur ein Objekt, dessen Schlüssel genau free und pro sind: Ein überzähliger und ein fehlender Schlüssel sind beide ein Err, und genau das sagt auch tsc über dasselbe Objekt, wenn es als Literal geschrieben ist.

SchlüsseltypWas parse bei jedem Schlüssel prüft
Eine Union aus String-Literalengenau die aufgeführten Schlüssel, keiner fehlt, keiner zu viel
Ein mit where verfeinerter string oder eine verfeinerte Zahldas Prädikat
intdie einfache Schreibweise einer ganzen Zahl; "01" und "1.5" scheitern
stringnichts Neues
Details verfeinerte und int-Schlüssel, und was der Checker festhält

Ein mit where verfeinerter Schlüsseltyp führt sein Prädikat auf jedem Schlüssel aus, und ein int-Schlüssel muss die einfache Schreibweise einer ganzen Zahl sein, also werden "01" und "1.5" abgelehnt. Ein Record<string, V> wird genau wie vorher geprüft. Ein where kann keine Union aus String-Literalen verfeinern (type T2 = Tier where value != "pro" ist seit 0.1.152 E0300); schreib die gemeinten Mitglieder als eigene Union, type T2 = "free", und sie dient als Schlüssel eines Record mit derselben Prüfung auf genau diese Schlüssel. Seit 0.1.153 hält Glyphs eigener Checker auch den Schlüssel eines Werts fest, den du im Code schreibst: Ein Record<string, int> steht nicht dort, wo ein Record<Tier, int> deklariert ist, und umgekehrt auch nicht, also führt der Übergang über ein json.parse oder einen is Record<Tier, int>-Arm, und record.set behält den Schlüssel, den es bekommen hat. Ein generischer Record, dessen Schlüssel sein eigener Typparameter ist, wird abgelehnt, es sei denn, dieser Parameter ist string.

Wenn ich ein Datum parse, bekomme ich ein echtes Datum?

Ja, und der interessante Teil ist, was du für eine Eingabe zurückbekommst, die keins ist. time.parse_iso gibt Option<number> zurück, und es ist None für alles, was nicht ISO-8601 ist.

akzeptiert 
"2026-01-03"              // UTC midnight
"2026-07-25T18:33:08.000Z"
"2026-03-15T09:30:00-05:00"
"2028-02-29"              // a real leap day
None, für jede davon 
"January 5 2026"   // not ISO
"2026-1-3"         // not padded
"2026-13-01"       // no month 13
"2026-02-31"       // no such day
"2026-02-29"       // not a leap year
"2026-01-03T10:00" // no offset

Die letzte überrascht die Leute, und genau darum geht es. Ein Datum mit Uhrzeit ohne Z und ohne +HH:MM-Offset ist nach der ECMAScript-Grammatik Ortszeit, also hieße es zu akzeptieren, dass derselbe String je nach Rechner, auf dem das Programm lief, einen anderen Kalendertag bezeichnet.

Details was Date.parse stattdessen tut, und warum UTC

Das ist eine stärkere Aussage als bei JavaScripts Date.parse, das Freitext nimmt ("January 5 2026"), ein Datum ohne führende Nullen wie "2026-1-3" in der Zeitzone liest, in der der Prozess gerade läuft, und einen unmöglichen Tag als Erfolg meldet, indem es ihn weiterrollt: "2026-02-31" wird zum 3. März, und du bekommst eine Zahl zurück, ohne Hinweis darauf, dass etwas passiert ist.

Glyphs Kalender-Zugriffe (time.year, time.month, time.day) sind UTC und sagen das, und ein Validator, der still die Zeitzone des Hosts übernimmt, würde sie lügen lassen. Also wird der String stattdessen abgelehnt, und du entscheidest, was er bedeuten sollte.

Die Absicherung ist in den Grundbaustein gewandert

Wenn eine Anwendung eine Korrektheits-Absicherung um einen Grundbaustein der Standardbibliothek schreibt, gehört die Absicherung in den Grundbaustein. Hier ist, was die App gelöscht hat:

vorher: Die App sichert die Stdlib ab 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
nachher: Der Grundbaustein hält die Linie 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

Das import std/regex fiel mit weg. Dasselbe Hauptbuch, dieselben abgelehnten Zeilen, derselbe Bericht Byte für Byte.

Geschichte die Spesenabrechnungs-App, aus der das kam

Das kam beim Schreiben einer CLI für Spesenabrechnungen in Glyph heraus. Jede Zeile im Hauptbuch trägt ein Datum, und eine Zeile unter dem falschen Monat abzulegen ist der Bug, auf den es ankommt, also traute die App dem alten parse_iso nicht: Sie prüfte die Form zuerst mit einer Regex und wandelte dann den Zeitstempel zurück in Text, um einen weitergerollten Tag zu erkennen.

Du musst die Typen nicht einmal schreiben

Wenn die Form schon in einer OpenAPI-Spezifikation oder einer TypeScript-Deklarationsdatei existiert, generier die Glyph-Typen daraus: echte, committete, durchsuchbare type-Deklarationen, jede mit ihrem Deskriptor, kein abgeleitetes Phantom:

aus einer OpenAPI- / JSON-Schema-Spezifikation 
glyph gen openapi petstore.yaml \
  --out src/
aus einem installierten Paket, über seinen Namen 
glyph gen dts api-types \
  --out src/types

Ein Wire-Typ wird zu einer validierten Grenze, ohne etwas Handgeschriebenes:

webhook.glyph 
import types/api_types { Customer }

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),
  Err(issues) => reject(issues),
}

Die Generierung ist treu zum Wire-Format: Was die Spezifikation über einen Wert sagt, ist das, was parse prüft.

In der Spezifikation oder .d.tsGeneriertes Glyph
Ein String-Enumeine Union aus String-Literalen; parse prüft die Mitgliedschaft
Ein integer-Feldint; ein 3.5 auf der Leitung scheitert
Ein Objekt-Schemaein mit @open markierter Record; strikt bei additionalProperties: false
interface Page<T>type Page<T>, jedes Element als T geprüft
Eine Union ohne Diskriminatoreingeengt, mit einer ausgegebenen Notiz
Ein Name in zwei erreichbaren Dateienmit einer Notiz markiert, nicht gebunden
Details was heute materialisiert wird, Neugenerierung, generische Typen

Richte glyph gen dts auf eine .d.ts-Datei oder, wie oben, auf ein installiertes npm-Paket über seinen Namen: Es löst den eigenen Deklarations-Einstieg des Pakets aus node_modules auf und schreibt committete Typen, die du importierst.

Was heute materialisiert wird: gen dts liest die interface- und type-Deklarationen, die ein Paket exportiert, auch die innerhalb eines declare namespace-Baums (bloße Querverweise werden über den Scope aufgelöst) und die in Geschwisterdateien, die ein index-Barrel re-exportiert (die Einstiegs-.d.ts plus jede relativ importierte .d.ts wird durchlaufen). Ein Generic bleibt vollwertig: interface Page<T> wird zu type Page<T> und bekommt einen Deskriptor, der jedes Element als sein Typargument validiert, nicht nur auf Vorhandensein. Re-Exports per Alias und export * as werden über eine Binding-Map pro Datei aufgelöst. Den einen Fall, den es nicht sicher machen kann, einen Typnamen, der in zwei erreichbaren Dateien kollidiert, markiert es mit einer Notiz, statt still die falsche Form zu binden. Für alles, was der Materialisierer nicht erreicht, schreib die Formen, mit denen du die Grenze überquerst, von Hand, oder nimm die Hintertür extern_ts.

Neugenerierung ist idempotent, also ist eine Änderung der Spezifikation ein sauberer, reviewbarer Diff. Die Generierung ist treu zum Wire-Format: Ein String-Enum wird zu einer Union aus String-Literalen ("free" | "pro"), also prüft parse die Mitgliedschaft und nicht nur, ob der Wert ein String ist, und ein match darüber ist ohne else erschöpfend. Ein integer-Feld wird zu int, also scheitert ein 3.5 auf der Leitung an parse, wo eine einfache Zahl durchginge. Wo ein Konstrukt keine exakte Glyph-Form hat (eine Union ohne Diskriminator), engt es ein und gibt eine Notiz aus, statt einen Validator zu erzeugen, der echte Daten ablehnen würde. Generierte Records tragen außerdem @open, also toleriert parse ein Feld, das die API später hinzufügt, und validiert trotzdem jedes Feld, das sie deklariert; ein Schema, das additionalProperties: false setzt, bleibt strikt. Records sind in Glyph standardmäßig strikt, und das ist dieselbe durchsuchbare Markierung an der Deklaration, die ein handgeschriebener Record verwenden würde, also ändert sich nichts daran, was ein Record bedeutet.

Generische Typen werden auch validiert. Ein Paginated<T> bekommt einen Deskriptor, dessen parse das Typargument nimmt: Paginated.parse<User>(body) prüft jeden Eintrag in items als User, nicht nur auf Vorhandensein, und match v { is Paginated<User> => ... } engt genauso ein. Das gilt über Modulgrenzen hinweg: Definier Paginated<T> in einer Datei, importiere es in eine andere, und dort prüfen sowohl Paginated.parse<User>(body) als auch is Paginated<User> weiterhin jedes Element als User. Der Compiler baut die Prüfung pro Element aus dem Typargument an der Aufrufstelle, also macht es keinen Unterschied für das, was validiert wird, in welcher Datei der generische Typ lebt.

Wo es aufhört: Deskriptoren decken die Formen ab, aus denen die meisten Payloads bestehen: Objekte, Primitive, Arrays, Referenzen, optionale und nullbare Felder und jetzt auch generische Typen bei einer gegebenen Instanziierung. Ein Typ, den Glyph nicht erzeugt hat (ein externes Paket oder eine .d.ts, die du nur importierst), wird typgeprüft, hat aber keinen Deskriptor, bis du ihn materialisierst, was jetzt ein Befehl gegen das installierte Paket ist (glyph gen dts <package>, für die Interfaces und Typ-Aliase auf oberster Ebene, die es exportiert). Diese Grenze ist Absicht: Ein Typ, den Glyph nicht erzeugt hat, kann keine Validierung zur Laufzeit versprechen, also entscheidest du dich pro Paket dafür, und das Ergebnis ist committet und durchsuchbar, nicht bei jedem Build herbeigezaubert.

Auch die Datenbank ist eine Grenze

Eine Zeile, die aus einer Datenbank gelesen wird, ist genauso wenig vertrauenswürdig wie ein Request-Body. Dasselbe .parse, das du für einen Request-Body verwendest, validiert eine Zeile.

tasks.glyph

type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.

  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}

Details std/sqlite und das Boolean als 0 oder 1

Eine Zeile, die aus einer Datenbank gelesen wird, ist genauso wenig vertrauenswürdig wie ein Request-Body: Das Datenbankschema und die Vorstellung deines Codes von der Zeile können sich widersprechen, und ein Cast (row as Task) kleistert das zu. std/sqlite, das DB-Modul über Nodes eingebautem SQLite, setzt genau da an. Eine Abfrage gibt Array<Record<string, unknown>> zurück, also gibt es keinen Weg, eine Zeile als Task zu behandeln, ohne sie vorher zu validieren.

Das findet einen Bug, den Leute ständig ausliefern. SQLite hat keinen Boolean-Typ, also kommt eine Spalte done als Ganzzahl 0 oder 1 zurück. Cast die Zeile in einen Record mit einem bool-Feld, und task.done === true ist still nie wahr. Das Ganze ist ein funktionierendes Beispiel: examples/apps/tasks/main.glyph ist eine persistente Aufgaben-API, std/sqlite für die Speicherung und std/http für die Routen, mit Daten, die einen Neustart überleben, und Validierung sowohl auf der Leitungs- als auch auf der Datenbankseite. Nirgends ein handgeschriebener Validator.

Auch ein signierter Webhook ist eine Grenze

Die Signatur eines Webhooks zu prüfen braucht genau die Bytes, die der Absender signiert hat, keine neu serialisierte Kopie (einen geparsten Body erneut zu stringifizieren ändert Leerraum und Schlüsselreihenfolge, also würde der HMAC nie passen). http.raw(req) gibt dir diese Bytes, also bleibt die Prüfung in Glyph: 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
Details rohe Bytes für die Signatur, geparster Body für die Form

req.body ist weiterhin der geparste Wert für die Prüfung der Form; raw ist der unveränderte Payload, über den die Signatur berechnet wird. Ein Empfänger, der eine Signatur prüft und den Body validiert, braucht kein handgeschriebenes TypeScript.

Ein Typ kann seine Invarianten validieren, nicht nur seine Form

Eine Prüfung der Form sagt dir, dass ein Feld eine Zahl ist. Sie sagt dir nicht, dass der Betrag nicht negativ ist oder die Bewertung zwischen 1 und 5 liegt. Eine where-Verfeinerung legt diese Invariante in den Typ, und der Deskriptor setzt sie an der Grenze durch:

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
was du nicht schreibst 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.

Wo es steht

Heute verfügbar 10

Deskriptoren

  • Jeder deklarierte Record und jede Tagged Union trägt einen Laufzeit-Deskriptor (.parse, .is, .schema), generische Records eingeschlosseneine generische Tagged Union nicht
  • .parse gibt dasselbe Result zurück, das der Rest der Sprache verwendet, also lässt es sich mit map_err, mit ? und mit jeder Funktion kombinieren, die eins zurückgibt

Generierung

  • glyph gen openapi / glyph gen dts erzeugen committete Typen mit Deskriptoren aus einer Spezifikation, einer .d.ts oder einem installierten Paket über seinen Namen

Grenzen

  • std/sqlite liefert Zeilen als unknown, also ist die Datenbank eine validierte Grenze wie jede andere
  • Ein Empfänger für signierte Webhooks bleibt vollständig in Glyph
    Details

    http.raw(req) stellt den ungeparsten Request-Body bereit, also wird eine Webhook-Signatur über genau die Bytes geprüft, und ein Empfänger für signierte Webhooks bleibt vollständig in Glyph.

  • Nicht vertrauenswürdige Eingaben erreichen kein SQL- oder Shell-Ziel ohne sanitize
    Details

    Die Typen Tainted/Trusted aus std/taint verhindern, dass nicht vertrauenswürdige Eingaben ein SQL- oder Shell-Ziel ohne explizites sanitize erreichen, also lehnt tsc einen Injection-Pfad beim Kompilieren ab.

  • time.parse_iso nimmt ISO-8601 und sonst nichts
    Details

    Die kleineren Grundbausteine an der Grenze halten dieselbe Linie: time.parse_iso nimmt ISO-8601 und gibt None für Freitext, einen unmöglichen Tag und ein Datum mit Uhrzeit ohne Offset zurück, das sonst in der lokalen Zeitzone des Hosts gelesen würde.
