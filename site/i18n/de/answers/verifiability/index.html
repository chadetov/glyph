01 · Das Kernversprechen

Was hindert einen Agenten daran, meinen Code unbemerkt kaputtzumachen?

Eine ganze Klasse von Änderungen, die in TypeScript still kompilieren (ein fehlender Fall, ein unbehandelter Fehler, ein umbenanntes Feld), wird zu einem Compile-Fehler, den der Agent beheben muss, bevor er ausliefern kann.

Warum das wichtig ist

Agenten machen Code meistens nicht laut kaputt. Sie machen ihn selbstsicher kaputt: Sie fügen einen Zustand hinzu, lassen einen Zweig weg oder benennen ein Feld um, alles besteht weiterhin die Typprüfung, und der Bug taucht in Produktion auf.

Die teuren Fehlschläge sind die, die kompiliert haben und falsch waren. Glyph schließt diese Lücke, indem es aus “du hast das wahrscheinlich behandelt” ein “der Compiler hat bewiesen, dass du es behandelt hast” macht.

  • Abgeschlossene UnionsTagged Unions sind abgeschlossen, also muss match jeden Fall abdecken.
  • Fehler als WerteFehler sind Werte, die du auspacken musst, keine Exceptions, die verschwinden.
  • Geprüfte GrenzenUnd jeder Typ trägt einen Laufzeit-Deskriptor, also werden Daten, die eine Grenze überqueren, gegen ihre Form geprüft.

Ein verworfener Fehler ist eine Warnung

Dasselbe gilt für Fehler: Eine Funktion, die Result<T, E> zurückgibt, soll mit match behandelt oder mit ? weitergereicht werden (und der Compiler prüft, dass der Fehlertyp passt). Und wenn du ein Result einfach fallen lässt (es als Anweisung aufrufst und ignorierst, was es zurückgegeben hat), warnt Glyph dich (E0217), weil ein verworfener Fehler ein verschluckter Fehlschlag ist.

glyph check --no-tsc, 0.1.149 (Auszug) 
13 │   save("a")
[E0217] Warning: typecheck: this `Result` is discarded; its `Err` case is silently ignored
    │ Help: Handle it with `match`, propagate it with `?`, or bind it (`let _ = ...`) to say the discard is intentional.

Du bringst die Warnung bewusst mit let _ = ... zum Schweigen, nie versehentlich.

Auch die Unions der Standardbibliothek sind abgeschlossen

Für eine Union, die der Standardbibliothek gehört, gilt derselbe Maßstab. fs.ErrorKind ist eine abgeschlossene Menge von sechs Arten, und der Checker kennt ihre Form, also braucht match e.kind auf einem Dateisystemfehler keinen else-Arm und schlägt mit E0200 fehl, wenn du eine Art weglässt.

E0200 fehlende ArtE0210 unbekanntes FeldE0218 braucht else
Details Tippfehler in Feldern, Rückgabetypen, matches über number und string

e.mesage ist E0210 statt etwas, das tsc weiter hinten findet. Auch Rückgabetypen reisen mit: string.split(text, ",") ist ein Array<string>, also bindet for i, part in string.split(text, ",") i als Zahl statt als String-Schlüssel, den du bei einem untypisierten Iterierten bekämst.

Erschöpfendheit gilt nicht nur für Unions. Ein match über einer number oder einem string mit reinen Literal-Armen kann einen unbegrenzten Wertebereich nicht abdecken, also verlangt Glyph ein else (E0218), statt den nicht abgedeckten Wert zu einem Wurf zur Laufzeit durchfallen zu lassen.

Die Regel ist überall dieselbe: Ein match, das einen Fall nicht berücksichtigt, kompiliert nicht.

Ein falsch geschriebener Arm ist eine Lücke, kein Catch-all

Auch ein Tippfehler kann eine Lücke nicht still überdecken. Ein großgeschriebener Arm-Kopf ist eine Referenz auf eine Variante, kein neues Binding.

status.glyph: Ein falsch geschriebener Arm ist eine Lücke, kein Catch-all 
fn label(s: Status) -> string {
  return match s {
    Loadign => "…",        // typo for Loading, read as a variant, not a binding
    Ready => "done",
    Failed(msg) => msg,
  }
}
glyph build 
[E0220] `Loadign` is not a variant of `Status`; did you mean `Loading`?
   ╰─ a lowercase name would be a binding; a PascalCase name is read as a variant
[E0200] non-exhaustive match on `Status`: missing variant `Loading`
Geschichte was älteres Glyph mit dem Tippfehler gemacht hat

Ein großgeschriebener Arm-Kopf ist eine Referenz auf eine Variante, kein neues Binding, also las älteres Glyph, wenn du Loading als Loadign falsch schriebst, den Tippfehler als Catch-all, der jeden Wert band und das match vollständig aussehen ließ. Jetzt muss der Kopf eine echte Variante der Union nennen, über die du matchst. Wenn er das nicht tut, bricht der Build mit E0220 ab und zeigt auf den nächstliegenden echten Namen, und die Variante, die du tatsächlich übersprungen hast, erscheint weiterhin als E0200 direkt daneben.

Varianten innerhalb eines Payloads

Diese Lesart gilt auch eine Ebene tiefer, wo die Variante der Payload einer anderen ist. Der Arm verzweigt jetzt über den eigenen Tag des Payloads, egal welche äußere Variante es ist.

repl.glyph: Der innere Arm testet den Payload, er bindet ihn nicht 
fn step(z: Zipper, line: string) -> Zipper {
  return match parse_command(line) {
    Err(Blank) => z,                          // a comment or an empty line
    Err(e) => { io.println(explain(e)) z },   // every other parse error
    Ok(command) => execute(z, command),
  }
}
E0305 doppeltes case-Label
Geschichte der tote Arm vor 0.1.93 und der E0305-Schutz

Err(Blank) neben Err(e) liest sich als "eine leere Zeile ignorieren, jeden anderen Parse-Fehler ausgeben", und bis 0.1.93 wurde es zu zwei case "Err":-Labels auf dem äußeren Tag kompiliert, deren erstes den ganzen Payload unter dem Namen Blank band. Jeder Fehler nahm den ersten Arm, der zweite war toter Code, und nichts sagte das: Glyph meldete keine Diagnosen, und tsc --strict akzeptiert ein doppeltes case-Label. Der Arm verzweigt jetzt über den eigenen Tag des Payloads, egal welche äußere Variante es ist, und der Compiler liest den Namen so, wie es der Typchecker tut: Die eigene Variantenliste der Payload-Union entscheidet, und nur wenn diese Liste nicht erreichbar ist, entscheidet die Form des Namens. Bei einer Union, die in derselben Datei deklariert ist, spielt die Großschreibung keine Rolle mehr. Bei einer aus einem anderen Modul importierten ist die Variantenliste heute nicht erreichbar, also verzweigt eine großgeschriebene Variante, und eine kleingeschriebene stoppt den Build.

Er stoppt, weil der switch jetzt geschützt ist. Zwei Arme, die dasselbe case-Label schreiben würden, sind E0305, kein switch, dessen zweites Label nie laufen kann. Das macht die Klasse laut statt still: Eine Übersetzung, die zweimal zum selben Tag greift, lässt den Build scheitern, statt zur Laufzeit den falschen Arm zu wählen.

Die Import-Schreibweise schaltet die Prüfung nie ab

Wie die Union in den Scope gekommen ist, ändert nichts daran. Glyph lässt dich einen Varianten-Arm auf zwei Arten schreiben, und beide werden gleich geprüft: import model { Cond, Yes, No } mit bloßen Armen oder import model (oder import model as m) mit model.Yes(_).

interp.glyph: Die Importliste ist weg, das match wird weiterhin geprüft 
import model { Action, All, Any, AtLeast, Clear, Condition, Context, Counter,
               Equals, Flag, FlagSet, Increment, Not, Set, Slot, Text }
import model
import std/result

pub fn evaluate(ctx: model.Context, c: model.Condition) -> result.Result<bool, SlotError> {
  return match c {
    model.Equals({ key, value }) => result.Ok(read_text(ctx, key, "equals")? == value),
    model.AtLeast({ key, least }) => result.Ok(read_count(ctx, key, "at-least")? >= least),
    model.FlagSet({ key }) => result.Ok(read_flag(ctx, key, "flag-set")?),
    model.All({ of }) => all_of(ctx, of),
    model.Any({ of }) => any_of(ctx, of),
    model.Not({ of }) => result.Ok(!(evaluate(ctx, of)?)),
  }
}
glyph build, nach dem Löschen des letzten Arms 
[E0200] non-exhaustive match on `Condition`: missing variants Not
Details Unions der Standardbibliothek, String-Enums und warum es die Liste gab

Das gilt auch für die Unions der Standardbibliothek, also ist match o { option.Some(s) => … } auf einem option.Option<string> E0200 für das fehlende None, genau wie die bloße Schreibweise Some/None. Bis 0.1.56 übersprang die qualifizierte Schreibweise die Prüfung ganz, und der Build meldete keine Diagnosen für ein match, das zur Laufzeit warf.

Auch ein String-Enum überquert die Grenze. type ColType = "text" | "int" | "real" | "bool", deklariert in catalog.glyph und in ein anderes Modul importiert, behält seine vier Werte, also kompiliert ein match, das alle vier abdeckt, ohne else, und einen wegzulassen ist E0200 mit dem weggelassenen Wert. Bis 0.1.57 war es E0218, mit einem Hilfetext, der sagte, du sollst einen else-Arm hinzufügen. Diese Hilfe lag beim vorliegenden Code falsch, und ihr zu folgen machte aus einem Compile-Fehler ein Durchfallen zur Laufzeit. Alle drei Import-Schreibweisen funktionieren: import catalog { ColType }, import catalog mit catalog.ColType und import catalog as c mit c.ColType.

Aus dieser Importliste stammt das Ganze. Sie wurde in jedem Modul einer Statechart-Engine von Hand geschrieben, mit einem Kommentar darüber, der sagte, dass die Konstruktoren einer Union nicht mit ihrem Typ mitkommen. Der Kommentar lag bei der Syntax richtig und beim Grund falsch: Die Liste war da, weil die kürzere Schreibweise die Prüfung abschaltete, und niemand hatte es bemerkt, weil das Abschalten still passiert. Welche Form du wählst, ist jetzt eine echte Wahl und keine Falle. Die benannte setzt jede Variante, die du behandelst, in die Importliste, und genau das findet ein grep nach Equals. Die qualifizierte sagt an jedem Arm, aus welchem Modul die Variante kam. Keine von beiden kostet dich die Prüfung.

Importierte Records behalten ihre Felder

Records überqueren die Grenze jetzt auch, und bis 0.1.58 taten sie das nicht. Ein Record behält also seine Feldmenge, und ein falsches Feld ist E0210 mit dem Namen des Records statt eines tsc-Fehlers über eine anonyme Form.

glyph build, bei einem Tippfehler in einem Feld eines importierten Records 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
// Before 0.1.58: no Glyph diagnostic at all, only a tsc error downstream.
table.glyph: Die herausgezogenen Bindings und der Kommentar, der sie erklärte, sind weg 
// Both annotations are load-bearing. `for i, x in <record field>` picks its
// lowering from the iterand's type as the checker knows it, and a field
// access is not enough: without the `let`, `i` and `j` come out as strings
// and the row/column numbers in a `BadCell` are wrong.
let raw_rows: Array<Array<string>> = sheet.rows
for i, raw_row in raw_rows {
for i, raw_row in sheet.rows {
  let typed: Array<Value> = []
  let cols: Array<ColumnSpec> = spec.columns
  for j, col in cols {
  for j, col in spec.columns {
    …
  }
}

// sheet: Sheet, declared in catalog.glyph and imported here.
// Emitted TypeScript: sheet.rows.entries(), not Object.entries(sheet.rows).
Details der Bug mit Zeile 11, was tsc übersieht, wie die Identität die Grenze überquert

Ein Typ, der in einer Datei deklariert und in einer anderen verwendet wurde, kam an, ohne dass etwas über ihn bekannt war, und das kostete zwei separate Prüfungen. Ein falsch geschriebenes Feld darauf löste überhaupt keinen Glyph-Fehler aus, also fiel sheet.rowz zu tsc durch und kam als TypeScript-Meldung über eine Form zurück, die du nie geschrieben hast. Und for i, r in sheet.rows konnte nicht erkennen, dass rows ein Array war, also erzeugte es Object.entries(sheet.rows) statt sheet.rows.entries(). Das bindet i an den String "0". i + 1 verkettet dann, statt zu addieren, und eine Zeile, die als line 2 gemeldet werden sollte, wird als line 11 gemeldet.

Wissenswert ist, welche Hälfte tsc findet. Arithmetik auf diesem Index findet es, meldet den Fehler aber am erzeugten TypeScript für eine Variable, die Glyph in deinem Namen gebunden hat. Was es nicht finden kann, ist jede Stelle, an der ein String akzeptiert wird, wo eine Zahl gemeint war: String-Interpolation, Verkettung, ein Schlüssel für record.get. Diese kompilieren unter beiden Checkern sauber und geben die falsche Zahl aus. Das ist genau die Art von Bug, die dieses Projekt beseitigen soll, also ist eine Modulgrenze, die ihn wieder einführt, keine Grenze, die Glyph in Ruhe lassen kann.

Ein importierter Typ trägt jetzt eine Identität über die Grenze, festgemacht an dem Modul, das ihn deklariert, und dem Namen, den es deklariert, also lösen sich alle drei Import-Schreibweisen zum selben Typ auf. Die Deklaration selbst wird bei Bedarf geholt und auf der Seite des deklarierenden Moduls übersetzt, und das ist die Hälfte, die ein Konsument nicht leisten kann: Die Auflösung arbeitet über Spans, und die Spans einer importierten Deklaration gehören zu einer anderen Datei.

Aufgefallen ist das in der Abfrage-Engine in examples/apps/csvql. Sie hatte drei herausgezogene let-Bindings, deren einzige Aufgabe es war, den Typ eines importierten Feldes für den Emitter zu wiederholen, unter einem vierzeiligen Kommentar, der erklärte, dass ohne sie die Zeilen- und Spaltennummern in einer Fehlermeldung falsch herauskommen. Alle drei sind gelöscht, und die App gibt für alle zwölf Abfragen byteidentische Ausgabe aus.

Eine Sache endet noch an der Grenze. Ein catalog.Sheet zu übergeben, wo ein table.Row erwartet wird, ist E0211 mit beiden Typen, aber die Member-Liste eines interface überquert die Grenze nicht, also wird ein Record, der übergeben wird, wo ein importiertes Interface erwartet wird, mit nichts verglichen. Ihm dieselbe Behandlung wie der Feldmenge eines Records zu geben, würde still ändern, was strukturelle Erfüllung bedeutet, und das ist eine Sprachentscheidung und kein Fix.

Das Maskieren personenbezogener Daten lebt am Typ

Derselbe Instinkt, "mach es zur Typfrage, nicht zur Konvention", deckt personenbezogene Daten ab. Setz @redact fields: [ssn, dob] an einen Typ, und der Compiler erzeugt an seinem Deskriptor ein redact(), das diese Felder maskiert, also kann json.stringify(User.redact(u)) sie nicht preisgeben.

E0219 unbekanntes Feld in @redact

Nenn ein Feld, das der Typ nicht hat, und es ist ein Compile-Fehler (E0219), keine Schwärzung, die still nichts tut.

Verfeinerungen werden bis ganz unten geprüft

Ein Deskriptor ist nur etwas wert, wenn er die Prüfung ist, die der Typ deklariert, bis ganz unten. Eine where-Verfeinerung führt ihr Prädikat überall aus, wo der Typ vorkommt, nicht nur bei einem direkten Instant.parse: als Record-Feld, als Array-Element, als Option-Payload, innerhalb einer Union-Variante und über json.parse<T>.

schedule.glyph: Das Prädikat folgt dem Typ in das Feld 
fn is_instant(value: string) -> bool {
  return match time.parse_iso(value) {
    Some(_) => true,
    None => false,
  }
}

type Instant = string where is_instant(value)

type WireBlock = { start: Instant, end: Instant }
type WireParticipant = { name: string, busy: Array<WireBlock> }
type Calendar = { participants: Array<WireParticipant> }

// json.parse<Calendar>(text) on a file holding "start": "no"
//   => Err. It returned Ok before 0.1.41.
Geschichte der selbstsichere falsche Zeitplan vor 0.1.41

Dasselbe gilt für einen Record, der aus einem anderen Modul importiert wird. Bis 0.1.41 fielen beide darauf zurück, nur zu prüfen, ob der Schlüssel vorhanden war, und das ist keine Prüfung von irgendetwas.

Aufgefallen ist das in der Planungs-App unten. Sie liest Kalender aus einer JSON-Datei und braucht jeden Zeitstempel als echten ISO-8601-Zeitpunkt. Vorher hörte die Verfeinerung auf oberster Ebene auf, also wurde eine von Hand bearbeitete Datei mit "start": "no" problemlos geparst, der Zeitpunkt las sich als 0, und die App gab selbstsicher einen Zeitplan aus und endete mit 0.

Tests laufen als Teil des Builds

Tests stehen neben dem Code und laufen als Teil des Kompilierens. Ein @example über einer Funktion oder ein ```glyph @run```-Block innerhalb eines @doc wird von glyph build ausgeführt, ohne Flag, an das man denken muss.

bracket.glyph: Mach die Setzliste kaputt, und der Build bricht ab 
@example seed_order(2) == [1, 2]
@example seed_order(4) == [1, 4, 2, 3]
@example seed_order(8) == [1, 8, 4, 5, 2, 7, 3, 6]
fn seed_order(size: int) -> Array<int> { … }

  "examples": { "total": 23, "ran": true, "skipped": false,

Details warum es sich nicht still überspringen lässt, und der JSON-Kanal

Ein falsches Beispiel lässt den Build genauso scheitern wie ein Typfehler, und darum geht es: Ein Agent, der einen Funktionsrumpf umschreibt, kann den Build nicht bestehen, indem er die Zusicherung zurücklässt. --no-test schaltet es ab und gibt aus, wie viele Tests übersprungen wurden, also ist die Umgehung im Log sichtbar.

Die JSON-Ausgabe, die Agenten lesen, meldet dasselbe Urteil. glyph build --json enthält neben den Diagnosen ein Objekt examples, und ein fehlschlagendes Beispiel macht ok zu false und den Exit-Code ungleich null. Bis 0.1.43 liefen die Beispiele nur unter --test, und der JSON-Pfad kehrte zurück, bevor sie überhaupt liefen, also gab der eine Kanal, den ein Agent lesen kann, "ok": true für ein Projekt aus, dessen eigene Zusicherung falsch war. Wenn tsx nicht im PATH ist, schlägt der Build fehl, statt einen Erfolg zu melden, den er nie geprüft hat.

Die Turnier-App unten enthält 23 davon. seed_order baut die übliche Setzreihenfolge durch Verdoppeln, die Art von Funktion, die man leicht subtil falsch macht und leicht exakt beschreiben kann. Ändere die Verdopplungsregel, und der Build bricht ab, ohne Testdatei, ohne Runner, ohne Flag.

Beim Bauen gefunden

Vier weitere, beim Bauen damit gefunden

Jede davon kompilierte sauber und bestand tsc --strict, und jede wurde beim Schreiben einer Anwendung gefunden statt beim Lesen des Compilers. Es ist derselbe Fehlschlag an drei Stellen: Die Typen sagten das eine, und das Programm tat etwas anderes.

Einen Schlüssel lesen, der vielleicht nicht da ist

einen Schlüssel lesen, der vielleicht nicht da ist: jetzt E0224 
fn name_of(row: Record<string, string>) -> string {
  return row.naem          // a typo. compiled, and returned undefined
}

Das ist jetzt ein Compile-Fehler, der auf record.get verweist, das Option<V> zurückgibt, damit der fehlende Fall irgendwohin kann.

Details warum ein Lesezugriff auf eine Map anders ist als Array-Indizierung

Die Schlüssel einer Map sind beliebig, also kann der Compiler nicht wissen, dass der Schlüssel da ist. Den Lesezugriff als string zu typisieren, behauptete etwas, das nicht geprüft war, und der Wert wurde als Text "undefined" ausgegeben. Das Schreiben eines Schlüssels ist unberührt, und ebenso die Array-Indizierung: Eine Grenze ist ein Wert, den ein Programm prüfen kann, ein Map-Schlüssel nicht.

Eine Methode, die mit undefined antwortet

eine Suche, die vielleicht nichts findet: jetzt E0242 
let name = users.find(fn(u: User) -> bool { return u.id == id }).name
let last = xs.at(-1) ?? 0  // passed tsc --strict too

[E0242] the call to `users.find` returns `User | undefined`; Glyph writes a value that may be missing as an `Option`
Help: pass `users` and the same callback to `array.find`, which returns `Option<User>`, and `match` it

Einige JavaScript-Methoden sagen „nichts da“ mit undefined, und das konnte Glyphs eigener Checker nicht sehen. Deshalb ließen der Editor und die Agent-Tools das Lesen von .name durch. Jetzt verweist jede auf die Funktion der Standardbibliothek, die ein Option zurückgibt, und die Array-Fälle schreibt glyph fix um.

Details welche Methoden, und was sie ersetzt

Die Liste wird aus den Deklarationen von TypeScript gelesen: find, findLast und at auf einem Array, und at, codePointAt und match auf einem String. Die Ersatzfunktionen sind array.find, array.find_last, array.get, string.char_at, string.code_point_at und regex.matches. Ein Standardwert mit ?? wird zum None-Arm eines match. array.get antwortet bei einem negativen Index mit None, daher schreibt die Hilfe für xs.at(-1) array.get(xs, array.len(xs) - 1). Eine Methode auf einem npm-Wert wird nicht geprüft, weil Glyph ihren Typ nicht kennt.

== ist überall Wertgleichheit

ein Test, der bestand, während der Code scheiterte 
@example wrap("a") == wrap("a")   // passed: deep equality
fn same() -> bool {
  return wrap("a") == wrap("a")   // false. no diagnostic
}

== ist jetzt überall Wertgleichheit; Primitive kompilieren weiterhin zu ===, also bleiben gewöhnliche Vergleiche unverändert.

Geschichte wie ein Test bei kaputtem Code bestehen konnte

== war als Wertgleichheit dokumentiert und wurde zu === übersetzt, was Referenzgleichheit ist, sobald eine der Seiten ein Record, eine Tagged Union oder ein Array ist. Derselbe Ausdruck verglich in einem Test strukturell und im Programm daneben nach Identität, also konnte ein Test Erfolg für Code melden, der nicht funktionierte.

Ein Schleifen-Binding behält seinen Elementtyp

Erschöpfendheit, die sich in einer Schleife verflüchtigte 
for t in tiers {
  match t {
    "free" => ...          // "pro" unhandled: once merely a warning to add `else`
  }
}

Es nennt jetzt die Variante, die du nicht behandelt hast, also einen Rat, die Prüfung zu erfüllen, statt sie abzuschalten.

Geschichte der Catch-all-Rat, den es früher gab

Das Schleifen-Binding hatte keinen Elementtyp, also verfiel ein match über einer Union aus String-Literalen zu einem match über string, und der Compiler riet dazu, einen Catch-all hinzuzufügen.

Importierte generische Unions werden geprüft

eine Variante, die in einem match über eine importierte generische Union fehlt 
import tree { Tree, Node }

fn label(t: Tree<string>) -> string {
  return match t {
    Node({ key: k }) => k    // Leaf unhandled: built clean, threw at run time
  }
}

Jetzt ist es so oder so E0200, bei beiden Import-Schreibweisen und bei einem offenen Parameter wie bei einer konkreten Instanziierung.

Geschichte warum die Prüfung nie startete

Eine Union, die dein eigenes Modul deklariert, wird geprüft, ob sie Typparameter nimmt oder nicht. Eine, die aus einem Geschwistermodul importiert wurde, wurde nur geprüft, wenn sie keine nahm. Tree<string> erreicht den Pfad für modulübergreifende Abdeckung als Anwendung einer importierten Union statt als eine solche Union, und die Bedingung, die die Prüfung startet, suchte nach Letzterem, also wurde das match überhaupt nicht gezählt: tsc --strict bestand, und ein Leaf warf. Lösch <K> aus beiden Dateien, und dasselbe Programm war E0200.

Ein parse kann keine Prüfung behaupten, die es nicht gemacht hat

ein parse, das ohne Prüfung Erfolg meldete: jetzt E0304 
type Conn = { id: number, sock: Socket }

Conn.parse(body)   // Ok. `sock` was never checked, and the message said it was

Einen Socket in einem Record zu halten ist normal und kompiliert weiterhin. Einen zu validieren wird jetzt dort abgelehnt, wo es geschrieben ist, und in jedem Modul, das den Record importiert, mit Nennung des Feldes und seines Typs, und die Ablehnung folgt der Form: durch einen verschachtelten Record, ein Array, ein Option.

Details warum Vorhandensein keine Prüfung ist, und der Fix, den es verlangt

Jeder Record-Typ trägt einen Laufzeit-Deskriptor. Für ein Feld, in dessen Typ der Compiler nicht hineinsehen kann, einen Socket oder alles, was über extern_ts erreicht wird, lautete die erzeugte Prüfung "ist es vorhanden", während die gemeldete Meldung field `sock` must be Socket lautete. Ein Boolean, das immer wahr ist, ist nutzlos. Eins, das immer wahr ist, unter einer Meldung, die einen Typ nennt, den nichts geprüft hat, ist schlimmer, weil parse genau das ist, dem eine Grenze vertrauen soll.

Der Fix, den es verlangt, ist die Aufteilung, die du sowieso geschrieben hättest: ein Wire-Typ, dessen Felder alle prüfbar sind, und dann ein Domänen-Record, den du daraus baust. unknown fällt nicht darunter, weil es nichts behauptet und Vorhandensein wirklich die ganze Prüfung ist.

Eine Signaturänderung, unsichtbar an der Aufrufstelle: geschlossen in 0.1.116

Ändere eine Funktion so, dass sie einen Payload statt eines rohen Strings nimmt, und jeder Aufruf, der noch die alte Form übergab, baute sauber.

Details wo die Prüfung anschlägt und wo sie still bleibt

Ein Parameter vom Typ string, number oder bool akzeptierte früher einen Wert einer deklarierten Union oder eines Records ganz ohne Beschwerde, obwohl derselbe Aufruf mit einem unpassenden bool-Argument schon E0211 war.

Die Prüfung liest die Deklaration, also schlägt sie nur an, wo die Antwort sicher ist. Ein primitiver Alias, eine Union aus String-Literalen (D30), ein extern_ts- oder typeof-Rumpf und ein interface sagen weiterhin nichts, weil keins davon nachweislich kein string ist, so wie es eine Tagged Union oder ein Record ist; void ist ebenfalls ausgenommen. Sie erreicht ein Argument, ein return und eine let-Annotation gleichermaßen, da alle drei eine Relation teilen.

Details nicht annotierte consts, und warum beide Fixes Breaking sind

Eine const auf Modulebene mit Typannotation wurde zu Ty::Unknown übersetzt, egal was die Annotation sagte, also war ein Tippfehler in einem Feld darauf genau dort unsichtbar, wo dasselbe annotierte let innerhalb einer Funktion ihn schon meldete.

Eine nicht annotierte const behauptet nichts und bleibt absichtlich Unknown: Den Typ aus dem Initialisierer abzuleiten ist eine andere Frage mit einer anderen Angriffsfläche für Fehlalarme. Beide Fixes sind Breaking unter glyph check --no-tsc, dem Language Server und dem Playground, da jeder anfängt, ein Programm zu finden, das das vorherige Release akzeptiert hat; ein vollständiger glyph build war in beiden Fällen über tsc schon rot.

Ein zusätzliches Feld zu finden bleibt Sache von tsc

Eine Prüfung von Record-Literalen gehört weiterhin tsc und nicht Glyph. glyph build bricht daran ab; glyph check --no-tsc, der Language Server und der Playground sagen nichts (G273).

Ein Literal mit einem Feld, das der deklarierte Record nicht hat, besteht Glyphs Checker, und tsc lehnt es am erzeugten TypeScript als TS2353 ab, zurückgebildet auf das Literal.

Tooling und die Standardbibliothek

  • Neun Funktionen aus std/string und std/array geben weiterhin untypisierte Werte zurück
    Details

    Die Stdlib-Rückgabetypen, die der Checker modelliert, decken die Hälfte von std/string und std/array mit fester Argumentanzahl ab; die sechs Funktionen mit optionalem letztem Argument (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify) und array.map/flat_map/zip sind weiterhin untypisiert, also braucht ein Wert direkt aus einer davon eine Annotation, bevor du ihn mit einem Index durchläufst.

  • Member-Zugriffe auf Primitive und Arrays haben keine Diagnose, wo tsc nicht läuft
    Details

    Member-Zugriffe und Aufrufe auf string, number, bool und Array<T> werden absichtlich tsc überlassen, nicht wegen einer Lücke; Glyph erlaubt dort rohe JS-Member, also kompilieren s.length und xs.length und bestehen tsc --strict, und was fehlt, ist eine Diagnose für die vier Schnittstellen, die nie tsc ausführen: glyph check --no-tsc, den Language Server, den MCP-Server und den Playground.

  • Ein Offline-Build mit Beispielen braucht tsx oder --no-test
    Details

    Der Beispiel-Runner ruft tsx auf, also scheitert der Build eines Projekts, das Beispiele hat und kein tsx im PATH, statt still zu überspringen; das ist Absicht, heißt aber, dass ein Offline-Build ein installiertes tsx oder --no-test braucht.

  • Ein await in einer einfachen fn wird an deinem eigenen Quellcode gefundenE0222
    Details

    Der async-Kontext war früher die eine Regel, die Glyph tsc überließ; ein await in einer einfachen fn ist jetzt E0222 an deinem eigenen Quellcode, wobei der const-Initialisierer auf oberster Ebene der einzige Fall ist, der noch erlaubt ist. Das und zwei weitere Regeln, die eine Stufe nach vorn gerückt sind, stehen unter früher gefunden.
