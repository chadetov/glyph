Kann ich eine Webseite ausliefern oder nur eine JSON-API?

Eine Webseite. std/http setzt Response-Header, also sind eine text/html-Seite, ein 302-Redirect, ein Cache-Header und ein HTML-Formular-Post ganz normales Glyph. Kein Express, kein handgeschriebener TypeScript-Shim.

Warum das wichtig ist

Bis 0.1.46 war eine Response { status, body }, und der Server wählte den Content-Type anhand der Form des Bodys: Ein String war text/plain, alles andere JSON. Für eine API ist das in Ordnung, für alles, was ein Browser rendert, nutzlos. Der Ausweg war, einen eigenen Server auf node:http in einer handgeschriebenen .ts-Datei zu schreiben, was deinen ganzen Request-Pfad außerhalb des Typcheckers legt. Zwei fehlende Konstruktoren kosteten eine ganze Anwendungsgrenze.

So sieht es aus

Das ist der Router von examples/apps/shortlink/main.glyph, einem URL-Shortener, der im Repo liegt. Ein HTML-Formular erzeugt einen Code, ein POST antwortet mit einem Redirect, damit ein Neuladen im Browser nie erneut postet, und das Aufrufen eines Codes ist ein 302 zum Ziel:

shortlink.glyph: eine HTML-Seite, ein Formular-Post und der 302 
fn handle_home(req: Request) -> Response {
  return match req.method {
    "GET" => html(200, home_page(links.get(), query_param(req, "error"))),
    "POST" => {
      let fields = form(req)
      match create_link(form_field(fields, "url"), form_field(fields, "alias")) {
        Ok(link) => redirect(303, "/${link.code}+"),
        Err(message) => redirect(303, "/?error=${url_encode(message)}"),
      }
    },
    else => html(405, page("405", "<h1>405</h1>")),
  }
}

fn route(req: Request) -> Result<Response, string> {
  return match segments(req) {
    [] => Ok(handle_home(req)),
    [one] => match stats_code(percent_decode(one)) {
      Some(code) => Ok(handle_stats(code)),
      None => Ok(handle_code(percent_decode(one))),
    },
    else => Ok(html(404, not_found_page(path(req)))),
  }
}

async fn main(argv: Array<string>) -> number {
  let outcome = await serve(8138, route)
  return match outcome { Ok(_) => 0, Err(_) => 1, }
}

Dieselbe App lag ein Release vorher mit 615 Zeilen im Repo, 121 davon ein handgeschriebener node:http-Server in einer .ts-Datei daneben, weil sich ein Location und ein text/html-Body nicht ausdrücken ließen. Jetzt sind es 494 Zeilen, und sie importiert nichts außerhalb von std. Ein Handler gibt Result<Response, string> zurück, also ist ein 404 ein ganz normales Ok, und ein Err ist für das reserviert, was die App nicht beantworten kann, und der Server macht daraus ein 500. serve bleibt ausstehend, solange er lauscht, also muss nichts den Prozess von Hand am Leben halten, und ein fehlgeschlagenes Binden kommt als Wert zurück.

Response hat ein Pflichtfeld headers: Record<string, string>. Pflicht, nicht optional: Jeder Konstruktor füllt es, also braucht das Lesen von resp.headers nie eine Prüfung auf Fehlen, und der Kanal kann nicht vergessen werden. with_header(resp, "cache-control", "no-store") gibt eine neue Response zurück, statt eine zu verändern, weil Glyph keine Mutation von Record-Feldern hat. Der Typchecker weiß, dass alle drei Konstruktoren eine Response zurückgeben, also wird ein Handler, dessen deklarierter Rückgabetyp Result<Response, string> ist, in Glyph geprüft und nicht von tsc an der erzeugten Ausgabe.

Zwei Details, die du von Hand sonst falsch machen würdest. Jedes Zeichen, das Node in einem Header nicht schreiben will, wird beim Hinausgehen aus dem Wert entfernt, also kann ein location, das aus einem Query-Parameter gebaut wird, keinen zweiten Header oder eine zweite Response einschleusen, und ein Emoji in einer gekürzten URL kann den Server nicht lahmlegen. Und form(req) dekodiert + als Leerzeichen zusammen mit Prozent-Escapes, das Paar, das selbstgebautes Formular-Parsing meistens übersieht; es liest den rohen Body, also bleibt req.body für Handler, die selbst parsen, unberührt.

Wo es steht

Heute verfügbar

html, redirect, with_header, json, text und form; Response-Header auf der Leitung, wobei der Content-Type nur abgeleitet wird, wenn du keinen gesetzt hast; Request-Header, Query-Parameter, Pfadsegmente und der rohe Body auf dem Weg hinein; der Client meldet die Response-Header, die er empfangen hat.

In Arbeit

Prozentkodierung ist die Lücke, die der Schnipsel oben zeigt: form dekodiert einen Formular-Body, aber es gibt kein encode_component zum Bauen einer URL, also schreibt der Shortener sein eigenes. Auf der Client-Seite fehlen außerdem: ein Timeout, eine Redirect-Policy, head und die endgültige URL, auf der ein Redirect gelandet ist. Es gibt keinen Server für statische Dateien und keine Template-Engine, und für beides gibt es keinen Plan.
