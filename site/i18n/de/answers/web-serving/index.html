Kann ich eine Webseite ausliefern oder nur eine JSON-API?

Eine Webseite. std/http setzt Response-Header, also sind eine text/html-Seite, ein 302-Redirect, ein Cache-Header und ein HTML-Formular-Post ganz normales Glyph. Kein Express, kein handgeschriebener TypeScript-Shim.

Warum das wichtig ist

Bis 0.1.46 war eine Response { status, body }, und der Server wählte den Content-Type anhand der Form des Bodys: Ein String war text/plain, alles andere JSON. Für eine API ist das in Ordnung, für alles, was ein Browser rendert, nutzlos.

Der Ausweg war, einen eigenen Server auf node:http in einer handgeschriebenen .ts-Datei zu schreiben, was deinen ganzen Request-Pfad außerhalb des Typcheckers legt. Zwei fehlende Konstruktoren kosteten eine ganze Anwendungsgrenze.

Ein Handler gibt ein Result zurück

Ein Handler gibt Result<Response, string> zurück, also ist ein 404 ein ganz normales Ok, und ein Err ist für das reserviert, was die App nicht beantworten kann, und der Server macht daraus ein 500.

serve bleibt ausstehend, solange er lauscht, also muss nichts den Prozess von Hand am Leben halten, und ein fehlgeschlagenes Binden kommt als Wert zurück.

Jede Response hat Header

Response hat ein Pflichtfeld headers: Record<string, string>. Pflicht, nicht optional: Jeder Konstruktor füllt es, also braucht das Lesen von resp.headers nie eine Prüfung auf Fehlen, und der Kanal kann nicht vergessen werden.

  • Eine neue Response, keine Mutationwith_header(resp, "cache-control", "no-store") gibt eine neue Response zurück, statt eine zu verändern, weil Glyph keine Mutation von Record-Feldern hat.
  • In Glyph geprüftDer Typchecker weiß, dass alle drei Konstruktoren eine Response zurückgeben, also wird ein Handler, dessen deklarierter Rückgabetyp Result<Response, string> ist, in Glyph geprüft und nicht von tsc an der erzeugten Ausgabe.

Zwei Details, die du von Hand sonst falsch machen würdest

  • Header-WerteJedes Zeichen, das Node in einem Header nicht schreiben will, wird beim Hinausgehen aus dem Wert entfernt, also kann ein location, das aus einem Query-Parameter gebaut wird, keinen zweiten Header oder eine zweite Response einschleusen, und ein Emoji in einer gekürzten URL kann den Server nicht lahmlegen.
  • Formular-Bodysform(req) dekodiert + als Leerzeichen zusammen mit Prozent-Escapes, das Paar, das selbstgebautes Formular-Parsing meistens übersieht; es liest den rohen Body, also bleibt req.body für Handler, die selbst parsen, unberührt.

Wo es steht

Heute verfügbar

  • html, redirect, with_header, json, text und form
  • Response-Header auf der Leitung, wobei der Content-Type nur abgeleitet wird, wenn du keinen gesetzt hast
  • Request-Header, Query-Parameter, Pfadsegmente und der rohe Body auf dem Weg hinein
  • Der Client meldet die Response-Header, die er empfangen hat.

In Arbeit

    Details

    Prozentkodierung ist die Lücke, die der Schnipsel oben zeigt: form dekodiert einen Formular-Body, aber es gibt kein encode_component zum Bauen einer URL, also schreibt der Shortener sein eigenes.

  • Auf der Client-Seite fehlen außerdem: ein Timeout, eine Redirect-Policy, head und die endgültige URL, auf der ein Redirect gelandet ist.
  • Es gibt keinen Server für statische Dateien und keine Template-Engine, und für beides gibt es keinen Plan.
