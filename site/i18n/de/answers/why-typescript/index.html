Warum TypeScript und nicht Go oder eine neue Sprache?

Weil Agenten in TypeScript schon den meisten Code schreiben und dort dein Ökosystem (npm, React, Node) lebt. Glyph lässt sich Datei für Datei einführen, nur weil sein Ziel TS ist.

Warum das wichtig ist

Eine neue Sprache steht und fällt damit, wie du von null bis zur Auslieferung kommst. Zu TypeScript zu kompilieren heißt, dass du nie deine Codebasis, deinen Bundler, deinen Test-Runner oder dein Deployment verlässt. Glyph passt neben die .ts-Dateien, die du schon hast, und Imports funktionieren sauber in beide Richtungen:

dasselbe Projekt: .glyph und .ts nebeneinander 
// cart.glyph: new, written in Glyph
import { formatPrice } from "./format.ts"

// checkout.ts: existing, untouched
import { total } from "./cart.glyph"

Go lässt sich nicht Datei für Datei in eine TypeScript-Codebasis einbauen: andere Laufzeit, anderes Modulsystem, anderes Ökosystem. Allein deshalb ist das Ziel TS.

Der berechtigte Punkt zu Go: Sein kleiner, stabiler Sprachumfang gibt einem Agenten weniger Möglichkeiten, falsch zu liegen. Da stimmen wir zu: Genau deshalb hält Glyph bewusst einen kleinen Kern mit einem Weg für jede Sache. Go ist in unserem Dichte-Benchmark für einen direkten Vergleich enthalten.

Wo es steht

Heute verfügbar

Sauberes TypeScript als Ausgabe, Imports in beide Richtungen mit deinen bestehenden .ts-Dateien und ein kleiner Kern, der überall läuft, wo Node oder ein Browser-Bundle läuft.

Wird gemessen

Der sprachübergreifende Benchmark (Glyph, TS, Go, Python, Rust) wächst mit dem Korpus, damit die Aussage “kleiner Sprachumfang” eine Zahl bleibt und keine Behauptung.
