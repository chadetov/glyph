Mitmachen

Wie der Compiler aufgebaut ist und wie du helfen kannst

Der Compiler ist ein Rust-Workspace aus zwölf Crates in einem öffentlichen Repository, lizenziert unter MIT oder Apache-2.0. Am meisten helfen heute Bug Reports mit einer kleinen Reproduktion. Eine Änderung an der Sprache beginnt als Issue, weil jede Regel auf eine nummerierte Design-Entscheidung zurückgeht.

Die Pipeline

glyph build lext, parst, löst Namen auf, prüft Typen und erzeugt TypeScript und führt dann tsc --strict auf dem Geschriebenen aus. Die mittleren Stufen laufen als inkrementelle Abfragen auf salsa, sodass eine erneute Prüfung die Ergebnisse wiederverwendet, die eine Änderung nicht ungültig gemacht hat.

eine .glyph-Datei, durch die Crates 
glyph-lexer → glyph-parser → glyph-resolver → glyph-typechecker → glyph-emit → tsc --strict
                (glyph-ast)        └──────── glyph-db (salsa) ────────┘
CrateWas es tut
glyph-lexerTokens, Schlüsselwörter, signifikante Zeilenumbrüche, Template-Literale
glyph-astTypen für den Syntaxbaum, mit einem Quell-Span an jedem Knoten
glyph-parserPratt-Parser für jede Entscheidung in der Spezifikation, JSX eingeschlossen
glyph-resolverNamensauflösung, der Modulgraph, modulübergreifende Import-Prüfungen, das Prelude
glyph-dbDie salsa-Abfrage-Pipeline und dateiübergreifende Invalidierung
glyph-typecheckerErschöpfendheit, ?, Generics, owned, Laufzeit-Deskriptoren, das Stdlib-Modell
glyph-emitDer TypeScript-Writer, Deskriptor-Erzeugung, Source Maps auf Ausdrucksebene
glyph-formatterglyph fmt: ein Layout, erhält Kommentare, idempotent
glyph-lspDer Language Server und der MCP-Server, die sich eine Analyseschicht teilen
glyph-cliDas glyph-Binary und jeder Unterbefehl
glyph-wasmDer Compiler in WebAssembly, auf dem der Playground läuft
glyph-runtimeEin Stub; Tests laufen stattdessen über den Emitter und tsx

glyph-compiler/README.md enthält die vollständigen Notizen zu den Crates und die aktuelle Anzahl der Tests.

Bauen und testen

Rust 1.95 ist in rust-toolchain.toml gepinnt. Einige Tests rufen tsc und tsx auf, also installiere die ebenfalls. CI führt clippy mit Warnungen als Fehler aus, und weder cargo build noch cargo test tun das, also führ das Skript aus, bevor du pushst.

aus einem Klon 
npm install -g tsx typescript
cd glyph-compiler
cargo build --release -p glyph-cli      # target/release/glyph
cargo test --workspace
cd .. && python3 scripts/check_clippy.py  # the exact clippy command CI runs

# after an intentional syntax-tree change
INSTA_UPDATE=always cargo test -p glyph-parser --test snapshots

Eine neue Diagnose kommt mit einem Programm unter tests/negative/, das mit diesem Code fehlschlagen muss. Eine Aussage, dass Glyph etwas findet, das TypeScript übersieht, gehört nach catches/, wo ein Gate beide Hälften ausführt.

Was geplant ist und was kaputt ist

docs/roadmap/releases.md ist die Release-Roadmap: was jedes veröffentlichte Release gemacht hat und wofür die nächsten gedacht sind. docs/dogfooding-gaps.md ist die Liste der Lücken, jede Einschränkung, die beim Bauen echter Apps gefunden wurde, jede nummeriert (G plus eine Zahl) und mit einer Statusmarkierung. Eine offene Lücke mit Reproduktion ist ein guter Einstieg.

Issues und Pull Requests

Fixes an der Toolchain, Diagnosen, Dokumentation und Beispiele können direkt als Pull Request kommen. Eine Änderung an Syntax oder Semantik beginnt mit einem Issue, und größere gehen durch den RFC-Prozess in docs/rfcs/; ein PR, der eine Regel lockert, "um hilfreich zu sein", wird wahrscheinlich abgelehnt, weil die Einschränkung der Sinn der Sache ist. Beschränke einen Pull Request auf eine Lücke, meist ein bis drei Commits, und signiere jeden Commit (git commit -s). main ist geschützt, und gemergt wird nur per Rebase. CONTRIBUTING.md enthält alle Regeln, und Issues mit dem Label good first issue sind für eine erste Änderung zugeschnitten.

Lizenz

MIT oder Apache-2.0, nach deiner Wahl (LICENSE-MIT, LICENSE-APACHE). Beiträge werden unter derselben Doppellizenz angenommen, bestätigt durch die Sign-off-Zeile.
