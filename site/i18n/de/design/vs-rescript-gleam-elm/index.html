Design · Vergleich

Warum nicht ReScript, Gleam oder Elm?

Alle drei sind typisierte Sprachen, die zu JavaScript kompilieren, und alle drei sind älter, weiter verbreitet und gefestigter als Glyph. Wenn du eine Sprache für eine neue Codebasis wählst und nicht nah an TypeScript bleiben musst, solltest du sie dir zuerst ansehen. Die Unterschiede von Glyph sind enger gefasst: Es erzeugt TypeScript-Quellcode statt JavaScript, es importiert npm-Pakete typisiert aus ihren eigenen .d.ts, es erzeugt Laufzeitvalidatoren aus deinen Typen, und sein Compiler beantwortet Impact-Abfragen für einen Agenten.

Wie sich jede selbst beschreibt

Die Startseite von ReScript beginnt mit "JavaScript Made Simple for Humans and AI" und "Types > Vibes" und sagt, es "compiles to clean, efficient JavaScript" mit "No any, no magic types, no surprise undefined." Es bietet an, "automatically generate TypeScript types" (rescript-lang.org).

Die Startseite von Gleam nennt es "a friendly language for building type-safe systems that scale" mit "No null values, no exceptions, clear error messages". Es läuft auf der Erlang-VM und "can additionally compile to JavaScript", und es "also generates TypeScript definitions" (gleam.run).

Die Startseite von Elm beschreibt "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions" für "reliable web applications" und sagt, dass Elm "detects all API changes automatically", um zu "guarantee that every single Elm package follows semantic versioning" (elm-lang.org).

Diese Zitate wurden am 2026-11-19 gelesen.

Was Glyph anders macht

Jedes davon wurde für diese Seite auf Glyph 0.1.149 ausgeführt.

Es erzeugt TypeScript-Quellcode

glyph build schreibt eine .ts-Datei pro Modul, die tsc --strict anschließend prüft und die du behältst, wenn du Glyph nicht mehr verwendest. ReScript und Gleam erzeugen JavaScript und generieren Typdefinitionen daneben. Das erzeugte TypeScript wird auf der TypeScript-Seite gezeigt.

Es importiert npm-Pakete typisiert aus ihren eigenen Deklarationen

Ein Modul importiert ein Paket über seinen Namen, und die .d.ts des Pakets typisiert jede Verwendung. Es gibt vorher kein Binding zu schreiben. In ReScript ist "external is the primary ReScript feature for bringing in and using JavaScript values" (external), mit den Typen auf der ReScript-Seite deklariert. Die Externals von Gleam brauchen Typannotationen, und der Compiler "cannot verify that the function implemented in the other language returns the specified types" (externals). Elm spricht mit JavaScript über Flags, Ports und Custom Elements (interop). Mit installiertem pg und @types/pg wird das hier abgelehnt:

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

Der Code ist TS2322, weil tsc die Werte einer Bibliothek prüft, zurückübertragen auf die Glyph-Zeile. Glyphs eigener Checker sieht sie nicht, also übersehen glyph check --no-tsc, der Editor und die MCP-Tools diesen Fehler (G257). Ein Typ, der aus einer .d.ts importiert wird, hat außerdem keine Laufzeitprüfung.

Es erzeugt den Validator aus dem Typ

Jeder Record und jede Union bringt eine Laufzeitprüfung mit, die aus ihrer Deklaration erzeugt wird, also gibt json.parse<User> Err zurück, wenn die Daten nicht passen. In Elm schreibst du für jede Form einen Decoder, und sein Guide merkt an, dass "the decoders people write end up working as a validation phase" (JSON).

main.glyph: gibt "refused" aus, weil das JSON keine E-Mail enthält 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

Sein Compiler beantwortet, was eine Änderung kaputtmachen wird

Vor einer Änderung kann ein Agent fragen, welche Stellen eine Änderung erreicht, über MCP (glyph_impact) oder mit glyph query impact. Bei einer Union Plan = Free | Pro | Team mit einem erschöpfenden match und einem, das mit else endet, antwortet die Frage nach einer neuen Variante pro Stelle:

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

Die zweite Stelle würde nach der Änderung nicht mehr kompilieren, und das würde dir jeder dieser Compiler ebenfalls sagen, sobald die Änderung gemacht ist. Die erste würde weiter kompilieren und den neuen Fall an ihr else schicken, und genau die nennt die Abfrage. Für Entwickler von Agenten listet die anderen Tools.

Was diese Seite nicht behauptet

Sie hat weder Fehlermeldungen noch Kompiliergeschwindigkeit oder Laufzeit-Performance verglichen, und sie hat nicht versucht, eine der drei aus Glyph aufzurufen oder umgekehrt. Die Zitate beschreiben jedes Projekt in seinen eigenen Worten; wie gut jedes ihnen gerecht wird, musst du selbst prüfen, genau wie bei Glyphs eigenen Aussagen auf der Seite mit den Belegen.
