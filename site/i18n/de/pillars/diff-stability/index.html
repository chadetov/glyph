Säule 04 · Der Feinschliff

Stabile Diffs

Eine einzeilige Änderung ist ein einzeiliger Diff. Ein kanonisches Format, Trailing Commas und eine Liste, die entweder ganz in einer Zeile oder ganz mit einem Element pro Zeile steht, nie neu umbrochen, sodass ein Review die Änderung zeigt, die gemacht wurde, und nicht das Rauschen drumherum.

Review heißt Diffs lesen

Fast alles, worauf wir uns bei einer Änderung verlassen (das Review, blame, revert, bisect), baut auf dem Diff auf. Das Verhältnis von Signal zu Rauschen im Diff ist also die eigentliche Währung.

Details woher das Rauschen kommt

In den meisten Codebasen ist es furchtbar: Ein Formatter bricht eine umbrochene Zeile neu um, ein Import-Sortierer mischt einen Block durch, eine Umbenennung berührt den Leerraum jeder Aufrufstelle, und die eine Zeile, auf die es ankommt, ist unter fünfzig begraben, auf die es nicht ankommt.

Agenten machen das deutlich schlimmer. Bei einer kleinen Aufgabe schreibt ein Modell bereitwillig eine ganze Funktion oder eine ganze Datei neu, um eine Sache zu ändern, weil Neugenerieren für es leichter ist als chirurgisches Bearbeiten. Dem Reviewer bleibt, einen Rewrite mit dem Original zu vergleichen und zu hoffen, dass die einzige echte Änderung die beabsichtigte ist.

Glyph ist so gebaut, dass das Layout dem Modell nichts zum Umrühren gibt.

01 Ein kanonisches Layout, keine Wahl

glyph fmt gibt jede Datei in einem einzigen festen Layout neu aus: zwei Leerzeichen Einrückung, ein Trailing Comma an jeder mehrzeiligen Liste und eine Liste, die in einer Zeile bleibt, solange sie in 100 Spalten passt, und ein Element pro Zeile bekommt, wenn nicht. Die Wahl ist alles oder nichts.

Details kein Neupacken, eine zulässige Form

Der Formatter packt deine Elemente nie neu, um eine Zeile zu füllen, also steht eine Liste nie teils in einer Zeile und teils in der nächsten, und ein neues Feld ist eine einzige hinzugefügte Zeile. Weil es genau eine zulässige Form gibt, gibt es nichts zu diskutieren und nichts, was ein Tool nebenbei "reparieren" könnte.

Der Preis dafür ist die Breitenschwelle. Benenne ein Binding so um, dass ein Aufruf über 100 Spalten geht, und der Aufruf wird auf ein Argument pro Zeile aufgeklappt: eine Änderung an einem Token, ein Diff über vier Zeilen. Der Ausgleich ist, dass das Layout vom Code und der Spalte, in der er beginnt, abhängt und von nichts anderem, also landen zwei Agenten, die dieselbe Datei bearbeiten, bei denselben Bytes.

Das Trailing Comma leistet stille Arbeit: Weil das letzte Element schon mit einem Komma endet, verändert ein neues Geschwisterelement nie die Zeile darüber. Eine Einfügung, eine Zeile.

02 Die Reihenfolge ist stabil, also bleibt die Historie lesbar

Ein Element pro Zeile heißt, dass Umordnen, Einfügen oder Entfernen eines Eintrags nur die Zeilen dieses Eintrags berührt, nie die seiner Nachbarn.

git blame bleibt aussagekräftig: Der letzte Commit, der eine Zeile berührt hat, ist der Commit, der dieses Element tatsächlich geändert hat, nicht der Formatierungsdurchlauf, der zufällig die Zeile neu gepackt hat, die es sich mit anderen teilte.

03 Keine Barrel-Dateien: kein Import-Rauschen

Weil Imports nie re-exportieren und es keine aggregierenden index.ts-Schichten gibt (E0102), zieht das Hinzufügen oder Verschieben eines Symbols keine Kreise durch ein Barrel, das jeder Konsument importiert. Die Abhängigkeitskanten, die du bearbeitest, sind die, die du gemeint hast; der Rest des Importgraphen bewegt sich nicht.

E0102

04 Generierung ist idempotent, kein Klumpen

Dieselbe Disziplin gilt für generierten Code. glyph gen und glyph regen geben ihre Ausgabe über den kanonischen Formatter aus, also erzeugt das Neugenerieren nach einer Änderung der Spezifikation einen minimalen Diff, den du tatsächlich reviewen kannst, ein paar geänderte Zeilen statt eines vollständigen Austauschs einer maschinell geschriebenen Datei.

ein Feld zur Spezifikation hinzugefügt → der neu generierte Diff 
  type Task = {
    id: number,
    title: string,
+   done: bool,
  }
// glyph regen re-ran the recorded command; this is the whole diff.

Und jede erzeugte .ts bringt eine Source Map mit, also führt selbst die kompilierte Ausgabe sauber zurück zu der Zeile, die du geändert hast.

05 "TypeScript kann das mit Prettier"

Bei vielem an der Formatierung, ja. Prettier mit trailingComma: "all" setzt ein Komma ans letzte Element und gibt lange Listen mit einem Element pro Zeile aus, und das bringt dich durch den Großteil von Abschnitt 01. Die Unterschiede liegen an drei Stellen.

  • Das Layout hängt nur vom Code ab.Prettier lässt ein Objektliteral aufgeklappt, wenn sein Autor nach der { einen Zeilenumbruch gesetzt hat, und klappt es zu, wenn nicht, also kann dasselbe Objekt auf zwei Arten ausgegeben werden, je nachdem, wie es zuerst getippt wurde. Zwei Agenten, die dasselbe schreiben, erzeugen zwei Layouts, und die nächste Änderung an einem davon taucht als Umbruch auf. glyph fmt gibt { a: 1, b: 2 } gleich aus, egal wie die Eingabe umbrochen war.
  • Es gibt nichts zu konfigurieren.Prettiers Ausgabe ist das, was die Konfigurationsdatei des Repositorys sagt, und manche Repositorys haben keine. Ein Agent, der zwischen TypeScript-Projekten wechselt, trifft in jedem auf ein anderes Layout. Eine Glyph-Datei hat in jedem Projekt dasselbe Layout, weil der Formatter keine Optionen hat.
  • Der Formatter kann nicht ändern, was eine Datei sagt.glyph fmt wird getestet, indem seine eigene Ausgabe geparst und der Syntaxbaum mit dem der Eingabe verglichen wird, an jedem Beispiel im Repository und unter einem Fuzzer. Wenn ein Kommentar an einer Stelle steht, für die das Layout keine Zeile hat, lehnt er die Datei ab (E0500), statt den Kommentar neben Code zu verschieben, den er nicht beschreibt.

Ein Punkt auf der Liste ist noch nicht erledigt: glyph fmt sortiert keine Imports, also erzeugen zwei Agenten, die an verschiedenen Stellen einen Import hinzufügen, weiterhin verschiedene Import-Blöcke (G358).

Stabile Diffs machen aus "der Agent hat etwas geändert" ein "der Agent hat genau das geändert". Wenn das Grundrauschen null ist, geht das Review schnell und Vertrauen ist billig.

Der Benchmark: kommt noch

Die Zahl, die das erfasst, ist die Diff-Größe pro logischer Änderung: wie viele Zeilen sich bewegen, wenn du eine beabsichtigte Änderung machst, in Glyph im Vergleich zu einer gleichwertigen TypeScript-Änderung, die durch einen üblichen Formatter läuft.

Glyph ist noch nicht im echten Einsatz, also ist das Diagramm unten ein Platzhalter, der sich mit echten Messungen füllt, sobald es eine echte Historie gibt, aus der man schöpfen kann.
