Säule 01 · Der Kern

Überprüfbarkeit

Glyph schließt die Löcher, durch die ein Agent fällt: Es gibt kein any und kein as, das du schreiben könntest, match ist nachweislich erschöpfend, und die Typen, die du deklarierst, bekommen strikte Laufzeitvalidatoren, alles durchgesetzt als strikte Schicht über tsc. Es verifiziert nicht alles selbst, und unten steht offen, wo genau die Garantie aufhört.

Die Lüge, die ein Typ erzählen kann

In TypeScript ist ein Typ ein Versprechen zur Compile-Zeit, das sich verflüchtigt, bevor dein Code läuft. Eine User-Annotation wird zu nichts gelöscht; das Objekt, das du tatsächlich aus einem Netzwerkaufruf, einem JSON-Parse oder einem Formularfeld bekommst, kann jede beliebige Form haben.

Schlimmer noch, die Sprache gibt dir drei legale Wege, den Checker darüber anzulügen: any, einen as-Cast und ein Non-Null-!. Ein Agent, der schnell arbeitet, greift zu allen dreien, und tsc --strict bleibt grün, während der Bug ausgeliefert wird.

Glyphs erste Aufgabe ist es, diese Löcher zu schließen. Nicht mit mehr Annotationen, sondern indem die Hintertüren entfernt werden und jeder Typ seinen Beweis bis zur Laufzeit mitträgt. Hier ist, was das heißt, eine Garantie nach der anderen.

01 Es gibt kein any

Glyph hat es nicht. Der oberste Typ ist unknown, und unknown ist träge: Du kannst ihn nicht aufrufen, nicht indizieren und nirgendwohin übergeben, wo etwas typisiert ist, bis du bewiesen hast, was er ist.

Details warum ein einziges any so viel kostet

any ist das teuerste Schlüsselwort in TypeScript: Es schaltet das Typsystem für einen Wert ab und für alles, was dieser Wert berührt. Ein einziges any an einer Systemgrenze vergiftet still den Aufrufgraphen dahinter.

Du bekommst keinen typisierten Wert aus unknown ohne eine Prüfung, die der Compiler sehen kann. In Glyph ist das Einengen der Beweis zur Laufzeit. Es gibt keine Syntax, um es zu überspringen.

02 Typen sind zur Laufzeit echt

Wie kann es User.parse geben? Weil jeder Record-Typ und jede nicht generische Tagged Union einen Laufzeit-Deskriptor daneben erzeugt: einen is-Guard, ein parse, das ein unknown in ein Result validiert, und ein zusammensetzbares schema.

der Typ, den du schreibst, und der daraus erzeugte Deskriptor 
type User = {
  id: number,
  name: string,
  email: string,
}

// generated: User.is(v), User.parse(v) -> Result<User, ...>, User.schema

fn create(req: Request) -> Result<Response, string> {
  return match User.parse(req.body) {   // untrusted input, validated
    Ok(user) => Ok(json(201, user)),
    Err(issues) => Ok(json(400, issues)),
  }
}

Das ist die Antwort auf "jede API braucht einen handgeschriebenen Validator". Der Typ ist der Validator.

Details was der Deskriptor prüft

Die Form des Records wird zur Laufzeit tatsächlich untersucht statt angenommen, also ist eine Prüfung is User eine echte Prüfung und kein gelöschter No-op.

Eine Systemgrenze (ein Request-Body, eine Konfigurationsdatei, eine Antwort eines Drittanbieters) wird nur typisiert, indem sie durch eine Prüfung geht, die fehlerhafte Daten tatsächlich ablehnen kann.

Wo das aufhört: Der Deskriptor eines Records ist standardmäßig strikt. Er bestätigt die deklarierten Felder und lehnt einen Wert mit nicht deklarierten Schlüsseln ab (setz @open an den Typ, um zusätzliche zu erlauben). Record-Typen bekommen einen Deskriptor, generische eingeschlossen, also prüft Paginated<User> jedes Element als User, und der Deskriptor einer Tagged Union prüft den Tag und dann die Payload-Felder dieser Variante.

Keinen bekommt weiterhin eine generische Tagged Union (Box<T> = Empty | Full({ value: T }) hat kein Box.parse) oder ein Typ, der aus einer .d.ts importiert und nur referenziert wird. Wo eine Prüfung nur einen Teil einer Form beweisen kann, sagt der Compiler das, statt eine Garantie anzudeuten, die er nicht geben kann.

03 Jeder Fall, oder es kompiliert nicht

Ein match über einer abgeschlossenen Union muss jede Variante behandeln. Füg später eine Variante hinzu, und jedes match, das sie nicht berücksichtigt hat, kompiliert nicht mehr (E0200).

status.glyph 
type Status = Active | Paused | Cancelled

fn label(s: Status) -> string {
  return match s {
    Active => "on",
    Paused => "hold",
    // forgot Cancelled...
  }
}

Der neue Fall kann nicht still zu undefined durchfallen, wie es ein vergessener switch-Zweig tut. Und es geht nicht nur um Unions: Ein match über einer number oder einem string mit Literalwerten verlangt ein else (E0218), weil diese Wertebereiche unbegrenzt sind und eine Menge von Literalen nie vollständig sein kann.

04 Fehler sind Werte, keine Überraschungen

Eine Funktion, die fehlschlagen kann, gibt Result<T, E> zurück. Du behandelst es mit match oder reichst es mit dem Operator ? weiter, und der Fehlertyp muss passen (es gibt keine implizite Umwandlung, die einen Unterschied versteckt).

pipeline.glyph 
fn load(id: string) -> Result<User, AppError> {
  let raw = fetch_user(id)?           // Err short-circuits to the caller
  let user = User.parse(raw.body)?    // validation Err propagates too
  return Ok(user)
}

fn main() -> number {
  save(user)   // E0217: this returns a Result whose Err is dropped
  return 0
}

Ignorier ein Result ganz (ruf es wegen seiner Wirkung auf und verwirf, was es zurückgegeben hat), und Glyph warnt dich (E0217), weil ein verworfener Fehler ein verschluckter Fehlschlag ist. Du bringst die Warnung bewusst mit let _ = ... zum Schweigen, nie versehentlich.

05 Sogar personenbezogene Daten sind eine Typfrage

Derselbe Instinkt, "mach es zur Aufgabe des Compilers, nicht zu einer Konvention", reicht bis zu sensiblen Daten. Setz @redact an einen Typ, und sein Deskriptor bekommt ein redact(), das diese Felder maskiert, also kann ein verirrtes json.stringify(User.redact(u)) sie nicht preisgeben.

patient.glyph 
@redact fields: [diagnosis, notes]
type Patient = {
  name: string,
  diagnosis: string,
  notes: string,
}

// json.stringify(Patient.redact(p)) ->
// {"name":"Ada","diagnosis":"[REDACTED]","notes":"[REDACTED]"}

Nenn ein Feld, das der Typ nicht hat, und es ist ein Compile-Fehler (E0219), keine Schwärzung, die still nichts schützt.

Fünf verschiedene Fehlermodi (ungeprüfte Eingabe, ein übersehener Fall, ein verworfener Fehler, ein geleaktes Geheimnis, ein nicht validierter Schlüssel), und bei jedem hat der Fix dieselbe Form: Der Compiler weigert sich, so zu tun als ob.

Wie es durchgesetzt wird und wo die Garantie aufhört

Genau genommen, weil der Unterschied wichtig ist: Glyph ist ein strikter, durchgesetzter Dialekt über tsc, kein unabhängiger Verifizierer.

  • Von Glyph bewiesenManches beweist es selbst: Erschöpfendheit, den Fehlertyp von ?, das Fehlen von any/as in deinem Quellcode, die Validierung strikter Schlüssel.
  • Über tsc durchgesetztDen Rest der Typkompatibilität setzt es durch, indem es TypeScript erzeugt und tsc --strict ausführt, was den Build fehlschlagen lässt.

Der Kern ist, dass diese Prüfungen die Sprache sind, kein Opt-in-Lint, das der Agent abschalten kann, nicht, dass Glyph einen Typchecker neu implementiert.

Geschichte in 0.1.10 geschlossene Grenzen, tiefe generische Validierung

Zwei frühere Grenzen hier wurden in 0.1.10 geschlossen. Der Emitter fügte früher in jede generische Funktion einen Rückgabe-Cast ein, der von Glyph und nicht von tsc geprüft wurde; jetzt passiert das nur noch dort, wo ein Validator-Kombinator einen Wert eines aus einer Form abgeleiteten Typs zusammensetzt (infer_output<Shape>), und jedes ehrliche Generic wird ganz ohne Cast ausgegeben. Und dem Ausgabetyp eines Validators wird nicht mehr blind vertraut: infer_output leitet ihn aus der Form ab, die du übergibst, und tsc prüft deine Annotation dagegen: Eine Form, der ein Feld des behaupteten Typs fehlt, kompiliert jetzt nicht mehr.

Generische Typen werden jetzt auch tief validiert: Ein Deskriptor für Paginated<User> prüft jedes Element als User, nicht nur auf Vorhandensein.

Eine Grenze bleibt, klar benannt: Ein importierter Typ aus einer externen .d.ts, den du nur referenzierst, hat keinen Deskriptor, bis du ihn mit glyph gen dts materialisierst, also wird ein Feld dieses Typs auf Vorhandensein geprüft, nicht auf seine Form. Diese Grenze ist Absicht (ein Typ, den Glyph nicht erzeugt hat, kann keine Validierung zur Laufzeit versprechen), und das Materialisieren schließt sie.

Der Benchmark: kommt noch

Diese Aussage ist empirisch, also wollen wir sie messen: einen Korpus echter Änderungen von Agenten nehmen, jede durch tsc --strict und durch Glyph laufen lassen und zählen, was jedes tatsächlich findet.

Glyph ist noch nicht im echten Einsatz, also gibt es keine Zahlen zu berichten. Das Diagramm unten ist ein Platzhalter und füllt sich mit echten Daten, sobald es echte Nutzung gibt.

Nichts davon wird mit Zeremonie erkauft. Es gibt keine Beweis-Annotationen, keine Verträge, keinen Verifizierer, den man zufriedenstellen muss. Der Code oben ist einfach gewöhnliches Glyph. Überprüfbarkeit ist kein Feature, das du einschaltest; sie ist das, was übrig bleibt, wenn die Wege zu lügen weg sind.

"Striktes TypeScript und eine Lint-Konfiguration können das auch"

Innerhalb eines Programms kommen sie nah heran. strict, noUncheckedIndexedAccess und eine Regel gegen explizites any fangen das meiste ab, was ein Agent sonst durchrutschen ließe. An den Rändern hören sie auf.

  • An der SystemgrenzeJSON.parse(body) as User kompiliert unter jeder denkbaren Einstellung, und der übliche Fix, ein zod-Schema, ist eine zweite Beschreibung von User, die von Hand mit der ersten synchron gehalten werden muss. In Glyph ist der Typ der Validator: json.parse<User>(body) wird gegen User selbst geprüft, und ein Typ, den Glyph zur Laufzeit nicht prüfen kann, wird abgelehnt statt blind akzeptiert.
  • Über Repositorys hinwegDer andere Unterschied ist, wer sich darauf verlassen kann. Eine Lint-Konfiguration ist eine Entscheidung, die ein Repository getroffen hat. Ein Agent, der eine unbekannte TypeScript-Codebasis öffnet, kann nicht annehmen, dass any dort verboten ist; in Glyph lässt es sich nirgends schreiben.
