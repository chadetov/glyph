¿Puedo manejar datos binarios, o todo es un string?

std/bytes te da una secuencia inmutable de octetos, y tanto std/fs como std/crypto la entienden. Hasta la 0.1.78 no era así: cada frontera de la librería estándar recibía un string y devolvía un string, así que no se podía leer un PNG ni darle a un HMAC una clave de verdad.

Por qué importa

Dos aplicaciones escritas por separado, un lector de PNG y un autenticador, se toparon con esta misma frase la misma semana. Ninguna de las dos podía esquivarlo dentro del lenguaje.

  • Un archivo leído como textoEl primer byte de un PNG es 0x89, que por sí solo no es UTF-8 válido. Si lees ese archivo como texto, cada byte que el decodificador no sabe interpretar se convierte en U+FFFD, así que el archivo está corrupto antes de que tu programa lo vea y nada informa de un error.
  • Una clave que pasa por un stringLo mismo le pasa a una clave: un secreto de HMAC son octetos arbitrarios, y pasarlo por un string lo cambia, así que calculas un MAC distinto del que dice la especificación y todos los tests que escribiste contra tu propio código pasan.

Qué es un valor Bytes

Bytes es un Uint8Array en tiempo de ejecución, así que se pasa a cualquier API del host que reciba uno sin desenvolverlo.

Las operaciones de secuencia se llaman como sus equivalentes en std/array y std/string: len, get, slice, concat, index_of, starts_with. Ninguna modifica su argumento.

Cada decodificación puede rechazar la entrada, y dice dónde

Esta es la parte que más costó construir y la razón para usarlo. El Buffer de Node acepta entrada mal formada e informa de éxito:

Lo que la plataforma hace sin avisar 
Buffer.from("zz", "hex")        // an empty buffer, no error
Buffer.from("a-b_", "base64")   // skips - and _, decodes the rest, no error
buf.toString("utf8")            // U+FFFD for anything malformed, no error
Lo que hace Glyph 
match bytes.from_hex(input) {
  Ok(b) => use(b),
  Err(e) => io.eprintln("${e.message} at ${number.to_string(e.index)}"),
}

// "z" is not a hex digit at 0
// a trailing base64 group cannot be 1 character(s) long at 3
// not valid UTF-8 at 2
Detalles qué rechaza cada codec

Cada codec está escrito a mano en lugar de delegar en Buffer, así que hex, base64, base64url y base32 rechazan un carácter fuera de su alfabeto, un grupo final demasiado corto para codificar un byte entero y un carácter final con bits más allá del final de los datos. to_text recorre los datos hasta el primer byte que no puede formar parte de una secuencia UTF-8 válida, así que obtienes una posición y no solo un veredicto. from_array rechaza cualquier valor fuera de 0..255 por el mismo motivo: un & 0xff silencioso convierte 256 en 0 y una errata en datos.

Escribir los codecs a mano trajo algo que no era el objetivo. El módulo no usa ninguna API del host, solo Uint8Array, TextEncoder y TextDecoder, así que un bundle que solo toca std/bytes también funciona en un Web Worker.

El HMAC que elijas cambia la respuesta

std/crypto tiene ahora las dos formas de cada algoritmo.

  • El nombre simpleEl nombre simple recibe un string y devuelve hex, que es lo que quieres para hashear una contraseña.
  • La forma _bytesLa forma _bytes recibe y devuelve Bytes, que es lo que quiere un protocolo de red.

Si la clave vino de bytes.from_base64 o de crypto.random_bytes, tiene bytes que un string no puede contener, y la forma de texto calculará otra cosa sin avisar.

Para comparar un valor que aporta un atacante con un secreto se usa crypto.timing_safe_equal, no bytes.equals. equals retorna en cuanto encuentra una diferencia, así que lo que tarda revela cuántos bytes iniciales eran correctos.

Dónde está

Disponible hoy

  • std/bytes con 21 funciones: las operaciones de secuencia, el puente con UTF-8 y codecs hex, base64, base64url y base32 que devuelven un Result que indica la posición culpable.
  • fs.read_bytes, write_bytes y append_bytes leen y escriben un archivo sin decodificarlo.
  • std/crypto tiene una forma _bytes de cada digest y HMAC, además de SHA-1 para los protocolos que lo especifican, random_bytes y timing_safe_equal.
  • Los codecs están fijados contra los vectores de RFC 4648 y el HMAC contra RFC 6238, en la propia suite de tests del compilador.

Lo que se está afinando

  • Todavía no hay codec de enteros, así que leer un u32 big-endian de una cabecera es aritmética que escribes tú: por encima de 32 bits un desplazamiento no es la herramienta adecuada de todos modos, así que se divide.
  • Los literales hexadecimales todavía no se parsean, lo que hace difícil de leer una tabla CRC32 de 256 entradas escrita en decimal.
  • std/websocket todavía decodifica un frame binario como texto UTF-8; el tipo que necesitaba ya existe, y los frames son lo siguiente.
  • Y las seis funciones antiguas de string a string de std/encoding siguen sin decir nada ante una entrada mal formada, así que usa los codecs de std/bytes para cualquier cosa que tenga que estar bien.
  • Los codecs están escritos en TypeScript en lugar de delegar en el Buffer de Node, que es lo que les permite funcionar en un Web Worker, y son entre 1x y 35x más lentos que los de la plataforma con un megabyte.
  • Codificar una clave o un token no cuesta nada que se pueda medir en ningún caso; la guía de rendimiento tiene la tabla si mueves decenas de megabytes.
