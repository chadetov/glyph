12 · A partir de tu especificación

¿Puedo generar un cliente y un servidor tipados a partir de la especificación de mi API?

Sí. Apunta glyph gen openapi a una especificación OpenAPI: --client genera un cliente HTTP tipado, una función por operación; --handlers genera stubs de servidor y un dispatcher route que funciona. Si tu fuente de verdad es un esquema de zod, glyph gen zod hace lo mismo. Todo sale como Glyph que se commitea y se puede buscar con grep, tuyo para editar, nunca un paso de generación de código oculto.

Por qué importa

Los clientes de API escritos a mano y sus DTOs se desvían de la especificación, y esa desviación es un tipo de bug que no le gusta a nadie.

Como Glyph genera código de verdad (funciones tipadas, declaraciones type reales con descriptores de runtime), la especificación sigue siendo la fuente de verdad, y regenerar es un diff idempotente y revisable, no una caja negra.

El router de --handlers

El router de --handlers hace coincidir la ruta con patrones de array, así que /tasks/{id} se convierte en ["tasks", id] y enlaza el parámetro por ti.

  1. /tasks/{id}
  2. ["tasks", id]
  3. getTask(req, id)

Cada stub empieza como un 501 con un comentario que muestra cómo parsear el cuerpo; los rellenas y lo conectas con await serve(PORT, route).

A partir de un esquema de zod

Si tu equipo ya define las formas con zod, genera directamente a partir de ellas. El esquema se convierte en un tipo de Glyph de primera clase con su propio descriptor:

schemas.ts 
export const Task = z.object({
  id: z.number(),
  title: z.string(),
  done: z.boolean(),
})
$ glyph gen zod schemas.ts --out src/ 
type Task = {
  id: number,
  title: string,
  done: bool,
}
// + a runtime descriptor, so
// Task.parse(value) validates.

Qué traduce

Una unión discriminada polimórfica (un discriminator de OpenAPI) sale como una unión etiquetada de Glyph de verdad más un parse_<Name> generado que lee la propiedad discriminante y valida hacia la variante correcta.

Detalles por qué se genera un dispatcher

Como Glyph etiqueta por el nombre del constructor y no por una propiedad arbitraria, el dispatcher generado hace de puente entre el objeto que llega por la red y la unión.

Dónde se queda corto

La generación es fiel al formato de la red, así que cubre el 80% habitual: objetos, primitivos, arrays, referencias, campos opcionales y nullable (por separado: un campo nullable se convierte en Nullable<T>, y un campo que el schema no exige recibe ?, que no acepta null), y uniones discriminadas. Lo que no puede representar con exactitud (un enum de strings, una unión no discriminada) lo estrecha con una nota impresa en lugar de con un validador que rechazaría datos reales. Detalles qué necesitan tener instalado los generadores

Y las herramientas tienen dependencias reales: gen dts/gen zod necesitan Node más typescript/zod. gen dts funciona con cualquier TypeScript (5, 6, o el port nativo 7.x), resuelto primero desde tu proyecto, y te dicen exactamente qué instalar si falta.

Mantenerlo sincronizado

Cada archivo generado registra en su cabecera el comando exacto que lo creó. Cuando cambia una especificación, no tienes que buscar qué comandos volver a ejecutar: glyph regen busca esas cabeceras y vuelve a ejecutar cada una, reescribiendo la salida.

Es idempotente, así que un regen sin cambios en la especificación no toca nada; encaja sin problemas en un hook de pre-commit o en una comprobación de CI que falle si el código commiteado se ha desviado de la especificación.

Dónde está

Disponible hoy

  • glyph gen openapi (tipos, --client, --handlers con un router de verdad), glyph gen dts, glyph gen zod y glyph regen para refrescarlo todo desde el origen: cada comando genera Glyph que se commitea, lleva descriptores y se regenera de forma idempotente.
  • Dos tipos que se escribirían con un mismo nombre de Glyph detienen el generador en lugar de producir un archivo que no puede compilar: nombra cada origen en conflicto, no escribe nada, y --rename Source=GlyphName lo resuelve.
  • Esa elección queda registrada en la cabecera generada, así que glyph regen la repite.

En camino

  • Un mapeo de enums más rico y una cobertura más amplia de OpenAPI, cada uno bajo la misma regla de ser fiel al formato de la red y avisar cuando se estrecha.
  • Generar a partir del propio .d.ts de un paquete lee sus declaraciones interface y type, así que una biblioteca cuya API son clases, o cuyos campos usan tipos calculados como Omit, deja referencias que el generador nombra en una nota y que glyph build informa como sin resolver.
  • Importar una clase así y construirla con new no necesita generación y lo comprueba tsc, así que ese camino no se ve afectado.
