28 · Operación

Cuando se rompe en producción a las 3 de la mañana, ¿qué ve la guardia?

TypeScript legible que es tuyo, con un source map que apunta a tu .glyph junto a cada archivo generado. Un depurador, un bundler o un rastreador de errores sigue el código en ejecución hasta tu código fuente, e incluso alguien que nunca ha visto Glyph puede leer el TS generado. Antes de todo eso, glyph build y glyph run informan de los mismos diagnósticos sobre el mismo árbol, así que el ciclo rápido no puede ocultar algo que el build habría detectado. Más abajo se señalan dos limitaciones, las dos en el camino de glyph run.

1 · El TypeScript generado es tuyo y lo puedes leer

Glyph no trae un runtime opaco. Genera TypeScript normal y formateado que commiteas y despliegas como cualquier otro TS. Así que el peor caso (alguien de guardia que no conoce Glyph, a las 3 de la mañana) sigue leyendo TypeScript normal, no un dialecto. No hay ninguna caja negra entre tu código fuente y producción.

2 · Source maps que apuntan a .glyph

Cada .ts generado lleva al lado un source map v3 estándar (.ts.map), con un comentario sourceMappingURL y tu código Glyph incrustado (sourcesContent). Cualquier cosa que consuma source maps (Chrome DevTools, un depurador de Node, un rastreador de errores como Sentry, tu bundler) puede encadenarse a través de él y mostrarte la línea del .glyph, no la generada.

dist/main.ts (final) 
// ...emitted TypeScript...
//# sourceMappingURL=main.ts.map    // v3 map, .glyph embedded

3 · Los errores de build y de tipos ya señalan a Glyph

Rara vez llegas a producción con un error de tipos, porque glyph build ejecuta tsc --strict y traslada cada error de tsc a tu código fuente .glyph (el mismo caret, con el código de error de TypeScript conservado). El caret va sobre la expresión de Glyph más pequeña cuyo código rechazó tsc: un argumento incorrecto subraya ese argumento, un campo mal escrito dentro de un handler de eventos de JSX subraya ese acceso al miembro, no todo el return que lo rodea. Y glyph build --json emite cada diagnóstico como JSON estructurado (código, severidad, archivo, línea/columna empezando en 1, ayuda) para que tu CI o tus herramientas actúen sobre él.

4 · glyph run te dice lo mismo

El comando que tecleas todo el día es glyph run, y hasta la 0.1.40 era más callado que el build. Compilaba todo el directorio, sacaba del informe la lista de archivos generados y tiraba los diagnósticos. Un árbol en el que glyph build señalaba problemas se ejecutaba sin avisos y salía con 0. Ahora informa del mismo conjunto: avisos incluidos, en el archivo que nombraste y en sus hermanos, después de la salida del programa, con un recuento de una línea. La caché de ejecución los guarda, así que una segunda ejecución sobre fuentes sin cambios dice lo mismo que la primera en lugar de quedarse callada, y una entrada de caché a la que le faltan los diagnósticos cuenta como fallo de caché y se recompila.

un import sin usar, añadido un paso antes del código que lo iba a usar 
$ printf 'look\nquit\n' | glyph run adventure.glyph
...the game plays and exits 0...

Dos limitaciones actuales

La traza de pila de un fallo en glyph run todavía muestra números de línea del .ts. glyph run ejecuta mediante tsx, y tsx no encadena el source map a través de su propia transformación de .ts→.js, así que una excepción no capturada durante glyph run informa de la línea generada. Remapear esa traza es una tarea pendiente. Afecta al ciclo local de run; en un despliegue real haces glyph build a .ts, lo empaquetas con tu toolchain habitual, y el .ts.map se encadena como siempre, así que la traza de producción por la que te despiertan apunta a .glyph.

Un error en un módulo hermano no cambia el código de salida de glyph run. Un módulo que no compiló no se puede importar, y un programa que nunca lo importó se ejecuta igualmente. Ahora ves el error, pero el proceso sigue saliendo con lo que devolvió main. Hacer que salga con un código distinto de cero haría fallar árboles que hoy funcionan bien, así que es una decisión abierta y no un descuido. Si quieres que la salud del árbol decida el código de salida, eso es glyph build.

Dónde está

Disponible hoy

TS legible y commiteado, un .ts.map v3 por archivo, errores de tsc trasladados a .glyph y diagnósticos con --json. glyph run informa de lo mismo que glyph build, también con la caché caliente. La cadena de source maps de tu toolchain de despliegue llega hasta .glyph.

En camino

Remapear la propia traza de pila de un fallo en glyph run (para que el ciclo local también muestre frames de .glyph), una decisión sobre si el error de un módulo hermano debe hacer que glyph run salga con un código distinto de cero, y una depuración más rica en el editor a través del LSP.
