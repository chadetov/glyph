¿Por qué Glyph detecta lo mismo que tsc, pero antes?

Porque un error sobre el TypeScript generado es un error sobre código que tú no escribiste. Glyph los informa sobre tu código fuente, con la regla que has incumplido y la edición que lo arregla.

Por qué importa

Glyph compila a TypeScript y luego comprueba los tipos de la salida con tsc --strict, así que un error que Glyph no modela no se pierde. Vuelve una etapa más tarde, expresado en términos del archivo generado: un TS1308 que señala un await en una función que nunca escribiste, o un TS2366 sobre un switch que no escribiste. La línea se traslada de vuelta a tu .glyph, pero la explicación no.

Ese hueco es donde el compilador deja de enseñar. Así que cada regla que Glyph puede decidir por sí mismo sube de etapa: await fuera de un async fn (E0222), un brazo de match que no produce valor cuando el match se usa como valor (E0223) y una asignación escrita sin mut (E0008). Cada uno nombra la regla, cita la decisión que hay detrás y muestra el antes y el después.

Míralo

El caso del brazo es el que antes se escapaba del todo. {} en posición de brazo es un bloque vacío, no un record vacío, así que el brazo se ejecutaba y no producía nada:

status.glyph: un brazo que no produce nada, en una posición que necesita un valor 
fn label(s: Status) -> string {
  let text = match s {
    Loading => {},          // an empty block: the arm produces no value
    Ready => "done",
    Failed(msg) => msg,
  }
  return text
}
glyph build 
[E0223] this `match` arm produces no value, but the `match` is used as a value
   ╰─ End the arm with an expression, or `return` from it. `X => {}` is a no-op
      only where the `match` is a statement.
   note: A value-position arm lowers to `case X: { break; }` when it yields
         nothing, so the value would be `undefined` at run time.

Antes de esto, el switch generado se salía de sus propios casos y text contenía undefined mientras su tipo decía string. tsc detecta algunas formas de eso y otras no. Glyph ahora lo decide siempre que la posición se puede decidir: un let, un mut, un return o el final de una función que declara un tipo de retorno. Un match usado como sentencia mantiene X => {} como la no-operación deliberada que es.

await es el mismo movimiento. Glyph no tiene una Promise visible para el usuario: un async fn -> T se espera hasta obtener un T, así que un await en cualquier otro sitio no tiene nada que suspender. Antes eso era el TS1308 de tsc sobre el archivo generado. Ahora es E0222, y decide la función que lo contiene más de cerca, así que una lambda síncrona dentro de un async fn es su propio contexto, la misma regla que usa TypeScript.

glyph build, sobre `fn total() -> number { return await fetch_count() }` 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

// before: no Glyph diagnostic, then
dist/main.ts:14:18 - error TS1308: 'await' expressions are only allowed
within async functions and at the top levels of modules.

El tercero trata de una regla que la gente incumple el primer día. Glyph marca cada mutación, así que reasignar un binding es mut x = e e introducir uno es let x = e. Un x = e a secas antes informaba "unexpected token: Equals", que nombra un carácter en lugar de la regla. Ahora es E0008, y glyph --explain E0008 explica por qué existe la marca: cada sitio donde cambia un valor empieza con mut, así que grep "mut total" los encuentra todos.

El operador ? recibe el mismo trato desde la otra dirección. ? se expande en un binding más un return anticipado colocado antes de la sentencia en la que está, así que necesita una sentencia en la que expandirse. Funciona en un let, en un return, en un argumento y ahora en el cuerpo de un brazo de match. Donde no puede funcionar, el mensaje dice de qué posición se trata y cómo sacar el valor a un binding (E0302 y E0303) en lugar de afirmar que el operador no está implementado.

El caso peor: cuando tsc también está contento

Un error de tsc en el sitio equivocado es molesto. Un build limpio de un programa que significa otra cosa es el problema de verdad, y Glyph tenía uno. Cada nombre de nivel superior que declaras va tal cual al módulo generado, incluidos los constructores de variantes de una unión etiquetada, así que una variante llamada Error genera export function Error(...) en el nivel superior del módulo. El new Error(...) que el compilador escribe debajo llama entonces a tu variante.

type Key = string | number es el mismo defecto con mejor cara. En Glyph, A | B declara una unión etiquetada cuyos miembros son constructores de variantes, así que esa línea declara variantes llamadas string y number. Compilaba, pasaba tsc --strict y generaba un export const number que ocultaba el namespace number del preludio. Nada fallaba hasta que fallaba una llamada posterior a number.to_string.

glyph build, sobre una unión con una variante `Error` 
[E0110] `Error` cannot name a type, variant, or function: the emitted module
        references the JavaScript global `Error`, and this declaration would
        shadow it
 5 │   | Error(string)
   │     ──────┬─────
   ╰─ Rename it (e.g. `Error` -> `Failure`). The name is legal TypeScript, so
      nothing downstream catches the rebinding.

// before: no Glyph diagnostic, then, twenty lines later
dist/main.ts:31:12 - error TS2345: Argument of type 'string' is not
assignable to parameter of type ...

El span es la declaración, que es donde va el renombrado. La lista protegida se deriva del emisor y no de una lista general de globales de JavaScript, y un test hace grep sobre el emisor y falla cuando aparece una referencia a un global nuevo sin su entrada correspondiente. Ese test es lo importante: Number era inofensivo hasta que salió int y empezó a generar Number.isInteger, que es como esto llegó a una versión publicada. Date, Math y JSON siguen libres, porque nada de lo que genera Glyph los menciona.

El caso de la unión de primitivos tiene su propio código, E0111, porque rechazarlo sin explicarlo no enseña nada. Dice cómo se ha parseado realmente la línea, remite a las variantes con nombre y menciona extern_ts("string | number") para la frontera donde quieres la unión de TypeScript tal cual. Todos los nombres que Glyph no te deja usar están tabulados en docs/reference/reserved-words.md: las 32 palabras clave, las 33 palabras reservadas de TypeScript que hay detrás de E0109 y la lista de ocultación, cada una con el motivo por el que el nombre está ocupado.

Conviene dejar claro lo que esto no hace. Sigues sin poder llamar Error a un tipo o a una variante, y la hoja de cálculo que destapó esto tiene una variante llamada Cellerr por ese motivo. El programa que quería ser sigue sin poder escribirse; lo que ha cambiado es que ahora el compilador lo dice en la declaración en lugar de dejar que el build se ponga en verde y signifique otra cosa. Hacer que el nombre sea utilizable implica transformar los nombres de Glyph al pasar a TypeScript, lo que cambia lo que ven una traza de pila, un grep sobre dist/ y un shim extern/ escrito a mano, así que no es un parche que podamos hacer sin avisar.

Un mensaje equivocado es peor que ningún mensaje

La lista de ocultación empezó con los nombres que el emisor escribe como valores. Le faltaban los que escribe como tipos, y eso produjo la versión más afilada de todo este problema. El parse de cada descriptor devuelve Result<T, Issue[]>, así que el módulo generado escribe Issue lo escribieras tú o no. Declara type Issue = { path: Array<string>, message: string } en tu propio módulo y el tuyo gana, los objetos Issue generados llevan un campo code del que el tuyo no sabe nada, y el build falla con un error de tsc sobre código generado, con un span que apunta a otro sitio.

glyph build, antes: quince como este, ninguno cerca de la causa 
dist/corpus/infer_output.ts:52:9 - error TS2353: Object literal may only
specify known properties, and 'code' does not exist in type 'Issue'.
glyph build, ahora 
[E0110] `Issue` cannot name a type, variant, or function: the emitted module
        references the Glyph prelude global `Issue`, and this declaration
        would shadow it
   ╰─ Rename it. The name is legal TypeScript, so nothing downstream catches
      the rebinding.

Record se unió a la lista al mismo tiempo, archivado con los globales de JavaScript y no con los nombres del preludio, porque es un built-in de TypeScript y decir otra cosa haría que el mensaje se equivocara sobre de dónde viene el nombre. El test de desviación que hace grep sobre el emisor ahora cubre también los tipos ambientales, y tuvo que aprender a ver Issue[] en posición de tipo, que es el motivo por el que esto llegó a una versión publicada. Schema, Component y Option siguen siendo válidos por la misma regla que deja libre a Date: el emisor solo los escribe porque tú los escribiste en una anotación, así que declarar uno no oculta nada.

El otro de esta categoría era un import. La ruta de un import local se resuelve desde la raíz del build, el directorio que le pasas a glyph build, no desde el directorio del archivo que importa. Compila un árbol que lo contenga y import catalog no encuentra nada, y hasta ahora nada lo decía. El tipo se degradaba a unknown, un match sobre él perdía las variantes que estaba comprobando y lo que obtenías era E0218, match no exhaustivo, en un match que cubría todos los casos. Hacer lo que pedía ese mensaje habría añadido un brazo else muerto a código correcto.

glyph build examples/apps, sobre `import catalog` dentro de csvql/ 
[E0104] unresolved import `catalog`: no module `catalog` under the build
        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from
        the importing file's directory (D15)
   ╰─ Build that module's own directory as the root, or spell the import path
      as it reads from the root.

// before: no import diagnostic, then
[E0218] non-exhaustive match on string   // on a match over all four values

El riesgo de una comprobación así es que salte con cosas que están bien, y un comprobador de imports que da falsas alarmas con cada paquete de npm es peor que el silencio al que sustituye. Así que el build primero reúne los nombres de módulo que puede resolver sin un archivo .glyph: cada declare module "X" bajo <root>/.types/ y en el shim de Node incluido, más cada paquete del node_modules del proyecto. Un nombre de esa lista nunca se informa, aunque un archivo local comparta su nombre base. Cuando un proyecto no tiene node_modules, el compilador no puede distinguir una dependencia sin instalar de una errata, así que solo informa de lo que puede demostrar: un import al que responde algún archivo .glyph bajo la raíz.

La resolución en sí no ha cambiado. Compilan los mismos programas y fallan los mismos programas. Lo que ha cambiado es que el fallo ahora nombra el import en lugar de acusar a un match dos archivos más allá, y eso es todo: un compilador que informa de la causa equivocada te cuesta la hora que pasas persiguiéndola, y después el beneficio de la duda en cada mensaje siguiente.

Nombrar la regla, no el token

La versión más discreta del mismo problema es un error que es correcto y aun así no te dice nada. Un agente que escribía un árbol rojo-negro recurrió al constructor posicional que tiene todo lenguaje de la familia ML, y el parser se detuvo en la primera coma con “expected )” y el consejo “add the expected token”. Añadir un ) ahí produce un programa distinto, no uno que funcione. Una variante de Glyph lleva un solo payload, y un payload con varios campos es un record. Ninguna de esas dos frases aparecía en la salida.

glyph check, antes y ahora 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.

Para decir eso, el parser tuvo que leer la lista entera antes de rechazarla, que es también lo que le permite contar. El span subraya los seis campos en lugar del separador en el que casualmente murió, y el record sugerido se construye a partir del nombre de la variante y los seis tipos del archivo, así que el arreglo nombra tu programa y no un ejemplo del de otra persona. Los nombres de los campos son lo único que el compilador no puede aportar, así que los deja como huecos.

La regla detrás del mensaje es una elección, no un hueco. Node(Black, l, x, b, h, r) es el intercambio de argumentos que pasa la comprobación de tipos, y la posición cuatro no le dice nada a quien lee. La forma con record nombra cada campo, un brazo de match nombra solo los campos que usa, y las dos cosas se pueden encontrar con grep.

Dos más de los que se encargó el checker en la 0.1.121

Order { id: "a", total: 1 } es lo que escribe alguien que viene de TypeScript para construir un record, y Glyph no tiene esa forma: un valor se escribe solo y el tipo va en la anotación. Lo que el compilador decía antes sobre esa línea era E0108, código inalcanzable, en un build que salía con 0, porque el nombre se resolvía al tipo y las llaves se parseaban como un bloque después del return. El nombre de un tipo escrito como valor es E0228, y el mensaje se lee de la declaración, así que un record lista sus campos, una unión etiquetada lista sus variantes con la forma de sus payloads y una unión de literales de string lista sus literales. Order.parse(raw) y Order.is(v) siguen siendo válidos, ya que el receptor del propio descriptor de un tipo es la única posición de expresión donde cabe el nombre de un tipo.

Eso arregló el caso en que el nombre era un tipo y dejó el parseo como estaba, así que return h() { k: 2 } seguía devolviendo h() y descartando las llaves con un aviso. Desde la 0.1.146, un { en la línea donde terminó una sentencia es E0013 al parsear, sea cual sea el nombre que lo precede, y su ayuda da la misma reescritura. Desde la 0.1.149 la regla cubre todas las sentencias, no solo las que empiezan con una llave: let s = "a" "b" enlazaba "a" y descartaba "b", y return x as User eran tres sentencias, ya que Glyph no tiene casts. Cada sentencia de un bloque empieza en su propia línea.

glyph check, sobre un record construido al estilo de TypeScript 
[E0013] a statement cannot begin on the line where
        `return Order` ends
   ╰─ Glyph has no `TypeName { ... }` construction form. Write the literal
      alone and put the type on the annotation: `let o: Order = { id: "a" }`.

// 0.1.121 to 0.1.145: [E0228] on `Order`, then [E0108] on the braces
// before that: [E0108] Warning: lint: unreachable code, and exit 0

El otro es un contenedor del preludio asignado a un primitivo. let x: string = o con o: Option<int> no provocaba nada en el checker de Glyph, y tampoco pasar un Nullable<int> a un parámetro declarado int. Ahora hay cinco contenedores cubiertos en las dos direcciones: Option, Result, Array, Record y Nullable nunca son un string, un number ni un bool, sean cuales sean sus argumentos, y Nullable<T> frente a un escalar se decide un nivel más adentro, frente a T, así que let v: Nullable<int> = 3 sigue siendo correcto y let v: Nullable<int> = "three" es E0204. El caso de Nullable pertenece a esta página más que los otros, porque es uno que tsc no puede detectar: el const v: number | null = 3 generado se estrecha de vuelta a number antes de comprobar la llamada, así que un tipo de frontera que existe para hacer visible null pasaba sin avisar donde se declaraba un int, y el checker de Glyph era el único sitio donde se podía detectar.

Después vinieron los mismos contenedores frente a un record o una unión declarados. Desde la 0.1.130, let user: User = json.parse(body) es E0204, se esperaba User y se encontró Result<unknown, Array<Issue>>. Antes solo lo decía tsc, lo que significaba que glyph check --no-tsc, el editor y el playground mostraban un archivo limpio justo en la línea que una frontera existe para hacer bien.

Un miembro mal escrito en un array o un string es el otro caso que antes esperaba a tsc. xs.lenght es E0210 con "did you mean length", comprobado contra los miembros que la librería de TypeScript declara para arrays y strings, igual que la lectura de un campo de un record se comprueba contra sus campos. tsc habría rechazado los dos, así que un build que lo ejecutara ya estaba en rojo; lo que cambia es que el checker, y todo lo que se construye sobre él, los ve primero.

Y tres más, desde la 0.1.133

let up = s.toUpperCase pasa la comprobación de tipos en TypeScript y lanza una excepción cuando se ejecuta up(), porque la lectura pierde el string al que pertenece. Glyph lo rechaza como E0234, y también rechaza .bind(s) sobre él: envuelve la llamada en una lambda. El checker ahora sabe qué devuelve cada método de array y de string, a partir de una tabla generada de las propias declaraciones de TypeScript.

r?.label sobre un Result se lee como "propaga el error y luego lee el campo". Es optional chaining, y un Result nunca es null, así que lee el campo del objeto Result y no propaga nada. Un agente escribió exactamente eso mientras construía una herramienta de consultas CSV. Ahora es E0236, también sobre un Option, y la ayuda dice que primero enlaces con ?.

json.parse(body) sin argumento de tipo es la lectura sin comprobar, un Result<unknown, ...>. Escrito donde se declaraba un Result<User, ...>, tsc antes infería User a partir de la declaración y el programa fallaba en la primera lectura de un campo. El emisor ahora escribe el unknown explícitamente, así que glyph check lo rechaza a través de tsc. El checker propio de Glyph todavía no detecta un unknown que acaba dentro de un tipo declarado, así que --no-tsc y el editor siguen sin ver un Result<unknown, ...> escrito donde se declara Result<User, ...>. (Un let user: User = json.parse(body) a secas es E0204 del checker propio de Glyph, porque el tipo exterior ya es incorrecto.) Rechazar unknown a cualquier profundidad está previsto como G325, en el roadmap de versiones.

Y dos más en la 0.1.122

type Mode = "read" | "write" declara un conjunto finito de strings, y el checker de Glyph no comparaba un valor con él de ninguna manera. Un número, un bool, un record y un string fuera del conjunto pasaban todos glyph check --no-tsc con solo avisos de variables sin usar, mientras tsc rechazaba cada uno sobre el TypeScript generado. Así que un glyph build completo nunca se equivocaba en esto, pero las cuatro superficies que no tienen tsc en el ciclo sí: --no-tsc, el servidor de lenguaje, las herramientas MCP y el playground.

glyph check --no-tsc, sobre un tipo que lista sus strings válidos 
type Mode = "read" | "write"

let a: Mode = 3
let b: Mode = "rw"
let c: Mode = takes_mode(true)
let d: Mode = { x: 1 }
// before: four unused-variable warnings, exit 0
[E0204] type mismatch: expected `Mode`, found `number`
[E0204] type mismatch: expected `Mode`, found `"rw"`
[E0211] argument type mismatch: expected `Mode`, found `bool`
[E0204] type mismatch: expected `Mode`, found `record`

Son los cuatro que informaba tsc, en las mismas cuatro sentencias, sin ejecutar tsc. La regla lee la unión como lo que es en tiempo de ejecución, un string, y le hace al checker la pregunta correspondiente sobre string en cada dirección, así que hereda las reglas que ya rechazan un record o un contenedor frente a un string en lugar de repetirlas forma a forma. Dos conjuntos de literales se comparan como conjuntos, así que una unión más estrecha puede ir donde se declara una más amplia; una cadena de alias se sigue por los dos lados; una unión importada se decide igual que una local; y en Nullable<Mode> se desciende manteniendo la unión intacta.

Una unión anidada en un campo de un record o en un argumento genérico se dejaba a tsc en la 0.1.122 y se decide en la 0.1.123. Ver más abajo.

El segundo no tiene nada que ver con tsc. El parser es de descenso recursivo sin límite de profundidad, así que una expresión anidada dos mil niveles agotaba la pila del proceso y abortaba con código de salida 134. Eso es malo en glyph check y peor en glyph lsp y glyph mcp, que leen todos los archivos bajo la raíz: un solo archivo patológico tumbaba el servidor para todo el workspace. Ahora es E0011, generado en el token que habría abierto el nivel 65.

0.1.123: el literal que es un valor, no el string al que se genera

type Mode = "read" | "write" ponía el conjunto en la declaración y nada en el valor, así que "read" era un string y ["read", "write"] un Array<string>. Eso hacía indistinguibles dos programas: return ["read", "write"] donde se declara un Array<Mode>, que tsc compila, y return xs para un xs: Array<string>, que rechaza. La 0.1.122 renunció a decidir ese emparejamiento en lugar de equivocarse, y así acertaba con el programa correcto a costa de dejar pasar el incorrecto: { mode: "nope" } frente a un { mode: Mode } no provocaba nada.

Un literal de string escrito tiene ahora el tipo de un solo literal que escribe, el tipo de elemento de un literal de array es la unión de los de sus elementos, y un literal de array u objeto escrito se comprueba elemento a elemento y campo a campo frente al tipo declarado, así que el diagnóstico nombra el literal y lo subraya.

glyph check --no-tsc, sobre un literal dentro de un contenedor 
type Mode = "read" | "write"
type Cfg = { mode: Mode }

fn ok() -> Array<Mode> { return ["read", "write"] }
fn bad() -> Array<Mode> { return ["read", "nope"] }
fn wrong() -> Cfg { return { mode: "nope" } }
// 0.1.122: nothing, on all three
[E0204] type mismatch: expected `Mode`, found `"nope"`   (twice)

El literal se ensancha de vuelta a string donde TypeScript lo ensancha: en un let sin anotación, cuyo let de TypeScript generado se ensancha igual, y en el binding de elemento de un for sobre un array escrito. Así que let l = "read" seguido de takes_mode(l) se rechaza aquí y es TS2345 allí. Un const genera un const de TypeScript y mantiene su literal, así que takes_mode(CM) compila en los dos. Un tipo literal que llegó a través de un nombre no se ensancha, que es la propia regla de frescura de TypeScript. Cada fila de esto se decidió ejecutando tsc --strict sobre el TypeScript equivalente, no razonándolo.

Sigue habiendo un emparejamiento que no se decide: el argumento de clave de un Record frente al de otro Record. TypeScript escribe Record<string, V> como una index signature que cubre cada clave que declara un Record<Mode, V> y lo acepta en las dos direcciones, así que rechazarlo rechazaría un programa que compila. Hay dos formas más sobre las que el checker todavía no dice nada: un literal dentro de Some(...), porque aquí un constructor del preludio todavía no tiene tipo, y un literal de record enlazado a un let sin anotación, porque no se sintetiza ningún tipo record para un literal de objeto.

Un módulo bajo std/ era código muerto sin diagnóstico

std/ y extern/ nombran módulos que lleva el compilador, y el resolver los reservaba para los imports. Nada impedía que un archivo del proyecto declarara uno. module std/io en tu propio src/io.glyph compilaba sin errores, y luego import std/io { shout } se resolvía al stub e informaba de que shout no se exporta: tu archivo nunca se leía. Un archivo que no provoca ningún diagnóstico y no ejecuta ningún código es la peor situación en la que te puede dejar un compilador, porque nada en él parece incorrecto.

glyph check --no-tsc, sobre src/io.glyph declarando `module std/io` 
// before: glyph check: 2 module(s) checked, no diagnostics.  (exit 0)

[E0113] `std/io` declares a module under `std/`, a prefix reserved for the
        modules the compiler carries (D15)
 1 │ module std/io
   │ ──────┬──────
   ╰─ Rename the module to a path of your own (`io`, `app/io`).

El prefijo se compara como primer segmento completo, así que standard, externals/io, app/std y app/extern/helper no se ven afectados, e importar bajo cualquiera de los dos prefijos sigue funcionando como siempre.

glyph check, sobre `const x = ` seguido de 2,000 corchetes anidados 
// before: thread 'main' has overflowed its stack
//         fatal runtime error: stack overflow, aborting   (exit 134)

[E0011] this array literal nests deeper than the parser's limit of 64 levels
   ╰─ Name the inner levels: pull them out into `let` bindings, or into a
      `fn` that returns one of them, so no single expression, type or
      pattern is more than 64 levels deep.

El límite es 64 y se midió en lugar de elegirse. Un nivel de la construcción más costosa, un literal de array anidado, cuesta 7,792 bytes de pila en el build de release y 8,810 en el de debug, calculado buscando por bisección la pila de hilo más pequeña en la que se parsea una profundidad dada. La pila más pequeña sobre la que corre el parser es la de 2 MiB de un hilo lanzado, que es la que reciben los workers del servidor de lenguaje, y 64 niveles gastan menos de un tercio en el build más costoso. El anidamiento más profundo entre los 343 archivos .glyph de este repositorio es 16. El límite cubre por igual expresiones, tipos, patrones, bloques e hijos de JSX, y mil arrays hermanos se siguen parseando, porque la profundidad es el anidamiento de cada construcción y no un presupuesto que se gasta a lo largo del archivo.

Cuando ningún compilador se equivoca

Hay una tercera forma, y es la que peor se lee. Glyph no informa de nada, tsc informa de algo cierto, y el programa que escribiste estaba bien. Lo que falló es la traducción entre ambos.

Un binding en Glyph tiene un solo tipo durante toda su vida. TypeScript estrecha un binding a lo último que vio asignado, y su boolean es la unión true | false, así que let done = false llegaba a tsc con el tipo false y el brazo true del switch generado no tenía nada con qué coincidir.

poll.glyph, y lo que tsc decía de él antes de la 0.1.89 
fn classify() -> int {
  let done = false
  match done {
    true => { return 1 },
    false => { return 0 },
  }
}

// no Glyph diagnostic, then
[TS2678] Type 'true' is not comparable to type 'false'.

Un tipo declarado como conjunto de literales de string fallaba igual, y también ==, que volvía como TS2367: dos mensajes, dos códigos, una causa. La app que se topó con ello consultaba periódicamente un flag que establece el callback de un timer, que es como conviertes una API basada en eventos en un valor mientras Glyph no tenga una Promise que puedas construir a mano. Resultó que el callback no tenía nada que ver: cuatro líneas sin callback lo provocan.

El arreglo no es un diagnóstico nuevo, porque no hay nada que diagnosticar. El emisor ahora vuelve a declarar el tipo que el checker ya decidió, en los dos sitios que discriminan sobre un valor: el valor del match y cada lado de un == o !=. Cada lado se decide por su propio tipo e ignora lo que tiene al lado, así que una comparación entre dos bindings queda cubierta igual que una comparación con un literal.

Las comprobaciones que quieres siguen saltando. m == "nope" donde m es un Mode se sigue rechazando, y ahora el mensaje nombra Mode en lugar del único miembro que m casualmente contenía. Hacerlo en la asignación habría sido menos código y habría tirado eso por la borda: un cast a Mode se acepta donde la asignación anotada no, y la comprobación de pertenencia es la parte que Glyph deja a propósito a tsc.

Lo que cuesta es poco y merece nombrarse. Un cast puede estrechar además de confirmar, así que un valor que Glyph tipa como bool cuyo tipo de TypeScript salió unknown ahora pasa donde antes el switch se quejaba. Los dos tipos tienen que seguir siendo comparables, así que un modelo que se ha desviado lo suficiente como para importar, string frente a bool, informa TS2352 en lugar de nada.

La misma errata, dos respuestas

Una función de la librería estándar mal escrita recibía antes una respuesta distinta según cómo hubieras escrito el import, que es el tipo de incoherencia que te enseña a no fiarte de ninguna de las dos respuestas.

el import con nombre, siempre un E0105 
import std/string { repeeat }
[E0105] import: `repeeat` is not exported by `std/string`
la lectura del namespace, antes de la 0.1.72 
import std/string
string.repeeat(s, 2)
[TS2551] Property 'repeeat' does not exist on type ... Did you mean 'repeat'?

La primera forma se comprobaba contra la lista de exports del módulo durante la resolución. La segunda no se comprobaba en absoluto, así que acababa en tsc, que veía un acceso a una propiedad de un objeto y respondía en esos términos. Las dos formas pasan ahora por la lista de exports, y las dos dicen E0105, nombrando el miembro y el módulo del que falta.

Activarlo encontró enseguida algo que nadie estaba buscando: un fixture de tests llevaba tiempo llamando a fs.write, cuando la función es write_text. Había pasado durante meses porque ese fixture se ejecuta con la comprobación de tipos desactivada, y nada más en el compilador miraba los miembros de un namespace. La lista de exports es ahora la autoridad para las dos formas, así que una comprobación aparte la mantiene alineada con lo que el runtime exporta de verdad. Esa comprobación se escribió y luego se rompió a propósito para confirmar que fallaba, y así descubrimos que su primera versión no comprobaba nada sin que nadie se diera cuenta.

Dónde está

Disponible hoy

E0222 para await fuera de un async fn, E0223 para un brazo de match en posición de valor que no produce valor, E0008 para una asignación sin mut, E0010 para una variante con varios campos de payload posicionales cuando la forma que existe es la de record, E0302/E0303 para un ? en una posición desde la que no puede propagar, E0110/E0111 para una declaración que ocultaría un nombre del que ya depende el módulo generado, E0104 para un import local que no nombra ningún módulo bajo la raíz del build, E0105 para un nombre que un módulo no exporta, tanto si llegaste a él con un import con nombre como a través de un namespace, E0228 para el nombre de un tipo escrito donde se espera un valor, E0013 para una sentencia que empieza en la línea donde terminó otra, que antes descartaba el valor que venía después, E0204/E0211 para un contenedor del preludio asignado a o pasado como un primitivo o un record o unión declarados, incluido el caso de Nullable<T> que tsc estrecha y hace desaparecer, E0210 para un miembro que un array o un string no tiene, esos mismos dos códigos para un valor que no está en el conjunto declarado de una unión de literales de string, E0011 para una construcción anidada más allá de 64 niveles, E0101 para una ruta de import relativa, que antes se detenía en el parser con un genérico "expected module path segment", y E0113 para un módulo del proyecto declarado bajo std/ o extern/, que antes compilaba sin errores y quedaba inalcanzable. La lista de ocultación cubre los tipos que el emisor escribe por su cuenta, así que Issue y Record se detectan en la declaración. Cada código tiene un arreglo de una línea, una nota que explica la regla y un texto largo en glyph --explain; docs/error-codes.md lista el catálogo y un test mantiene los dos alineados.

Cada vez más preciso

array.map, flat_map y zip todavía aceptan un callback async sin quejarse y devuelven un array de valores pendientes, que se imprime como [object Promise]; las cinco funciones de array que reciben un predicado sí lo impiden, con E0211 en el callback. Modelar las otras tres de la misma forma también rechazaría par.all(array.map(items, async fn ...)), que es como Glyph ejecuta trabajo en concurrencia, porque un array de valores pendientes no tiene forma de escribirse en el lenguaje. Es una decisión del sistema de tipos y no una entrada que falte, así que sigue abierta. El inicializador de un const a nivel de módulo no tiene una función que lo contenga, así que se permite un await de nivel superior y el ESM generado lo ejecuta; si Glyph quiere inicialización asíncrona implícita de módulos sigue siendo una cuestión abierta de la especificación. E0223 solo puede juzgar un match final cuando la función declara un tipo de retorno, así que un brazo dentro de una lambda sin anotar sigue llegando a tsc. En el lado de la ocultación, hay dos cosas a medias. E0110 te dice que renombres en lugar de dejarte mantener el nombre, así que Error, Number, Object, Array y Promise siguen vetados para un tipo o una variante. Y E0111 impide que type Key = string | number signifique lo que no es sin darte una forma de decirlo: una unión de dos tipos primitivos no tiene forma de escribirse en Glyph salvo con extern_ts, cuyo contenido su propio checker trata como opaco. Las uniones sin etiqueta afectan a la exhaustividad, a los descriptores de runtime y a is, así que es una decisión del sistema de tipos y no está planificada. E0104 llega a glyph build y glyph check pero no al editor: el LSP analiza el texto de un documento sin raíz de build, y la carpeta del workspace tampoco lo es, así que adivinar produciría los falsos positivos que la comprobación se diseñó para evitar. Y un parámetro con una palabra reservada sigue escondiéndose detrás de un error no relacionado en el mismo archivo, porque un fallo en la fase de recolección se salta la fase de resolución que lo habría encontrado. Aparte, la fijación en el punto de lectura que mantiene comparable en un match un binding bool o de unión de literales de string solo sigue un alias de tipo dentro del módulo que se está generando, así que pub type Ready = bool en un módulo y let r: catalog.Ready = false en otro siguen llegando a tsc como TS2678. Las uniones de literales de string están cubiertas entre módulos con las tres formas de import, y desde la 0.1.123 el diagnóstico nombra la declaración (se esperaba Mode) con cualquier forma en lugar de imprimir su conjunto de literales con una de ellas.
