¿Puedo usar mis librerías de TypeScript, JavaScript y npm?

Sí. Glyph compila a TypeScript normal y se apoya en npm: un módulo .glyph importa de cualquier paquete y a su vez se puede importar desde tu .ts existente. Lo adoptas archivo a archivo.

Por qué importa

Nadie reescribe un código para probar un lenguaje. Como la salida de Glyph es TypeScript, un archivo .glyph encaja en un rincón de un proyecto TS/React/Node existente, importa los mismos paquetes y exporta de vuelta al .ts que lo rodea.

Ese camino gradual es justo el motivo de compilar a TypeScript en lugar de publicar un runtime nuevo.

Los paquetes instalados traen sus propios tipos

Si el paquete está instalado y trae sus propios tipos (o tiene un @types/...), no tienes que hacer nada más. Ni stub, ni archivo adaptador.

glyph build encuentra el node_modules de tu proyecto y apunta el comprobador de tipos hacia él, así que los tipos reales del paquete comprueban tu código y una llamada incorrecta es un error real.

Aquí está zod usado directamente, sin nada escrito a mano:

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
una llamada que zod no define 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

glyph run ejecuta el mismo programa con el zod instalado, así que no es solo una comprobación de tipos: la única entrada de configuración que resuelve el paquete para el comprobador de tipos lo resuelve también para el runtime.

Un paquete que no trae tipos y no tiene @types/... sigue necesitando una declaración escrita por ti, y para eso está la carpeta .types/ (el mismo mecanismo de .d.ts que ya usa TypeScript).

Detalles imports de subrutas, y tipos validados a partir de un .d.ts

Los imports de subrutas (pkg/sub) también se resuelven a través del mapa exports del paquete, así que se comprueban los tipos propios de cada subruta.

Y cuando quieres la forma de una librería como un tipo de Glyph de primera clase y validado, en lugar de un import solo de tipos, glyph gen dts materializa un .d.ts en tipos reales con descriptores: consulta ¿tengo que escribir a mano un validador para cada API?

Tipos derivados de valores, spread en JSX y la vía de escape

Los tipos derivados de valores son de primera clase. El spread de props en JSX (<input {...register()} />) también es de primera clase.

Así que una librería nunca te obliga a escribir a mano un archivo adaptador.

Para el raro idioma de TypeScript que Glyph todavía no sabe escribir, extern_ts("...") es la vía de escape acotada y que se puede buscar con grep: tsc lo comprueba, pero seamos precisos, es una frontera de confianza, no una validada en tiempo de ejecución (opaca para Glyph, el valor vuelve como unknown para estrecharlo).

Detalles cómo se resuelve z.infer<typeof s>

type User = z.infer<typeof user_schema> funciona directamente: typeof user_schema es una consulta de tipo sobre una referencia real a un valor (una errata es un error de nombre sin resolver), y z.infer<...> es un tipo genérico miembro normal. Se genera tal cual y tsc lo reduce, así que u.name es un string; la validación viene del propio parse del schema, que es como ya funciona zod.

Cuando necesitas TypeScript entero escrito a mano

A veces la vía de escape no es un tipo ni una expresión, sino código de runtime de verdad: un bucle sobre un stream de node, un new Promise, un worker thread. Pon el .ts en <src>/extern/ y llega a él con import extern/<name>. 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

Los imports relativos siguen sin estar permitidos en el código Glyph (una regla de buscabilidad), así que extern/* es la única ruta reservada, y grep -rn 'import extern/' encuentra cada sitio donde saliste del lenguaje.

Detalles la copia al build, la otra dirección y el shim de node

El build copia <src>/extern/** a la salida y genera un especificador relativo, así que tsc comprueba los tipos del extern junto con tu código Glyph y una recompilación nunca lo elimina.

Es lo contrario de la dirección fácil, un archivo .ts que importa tu Glyph compilado, que no necesita nada. Un extern habitual (un servidor http, fs) se comprueba contra el shim de node incluido sin instalar nada.

Vigilar un subproceso, sin instalar nada

Las declaraciones de node incluidas cubren la mitad asíncrona de child_process, no solo la bloqueante, así que una herramienta que muestra la salida de un comando largo mientras se ejecuta es Glyph y no un extern: 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

io.print y no io.println: un chunk es un trozo del stream, no una línea, y una línea puede llegar repartida en dos.

Las sobrecargas siguen a @types/node, así que las pipes vuelven no nulas con un spawn(command, args) simple y anulables en cuanto pasas stdio. Leer child.stdout después de stdio: "inherit" da TS18047 aquí y TS18047 con los tipos reales, en lugar de dos versiones distintas sobre el mismo valor: 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

Editas el shim, y la siguiente ejecución usa el shim que editaste

Un shim es un archivo sobre el que iteras, así que tiene que contar como código fuente.

glyph run guarda en caché un build bajo una huella de tus fuentes, y esa huella cubre cada .ts y .tsx bajo extern/, tanto por ruta como por contenido.

Detalles qué provoca una recompilación

Edita uno, renombra uno, añade uno, borra uno, y la siguiente ejecución recompila y vuelve a ejecutar tsc. Un shim enlazado con un symlink se sigue, así que un .ts guardado fuera del árbol de fuentes se hashea por lo que contiene de verdad.

Eso es lo que permite que el shim sea el dueño de un tipo en lugar de que los dos archivos declaren su propia copia. Exporta la forma desde el shim, impórtala en el módulo Glyph, y el compilador mantiene los dos alineados en cada ejecución:

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
el shim renombró un campo, y el build lo dice 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3
Historia antes de la 0.1.44, y los archivos que no cuentan

Hasta la 0.1.44 la huella se saltaba extern/ por completo, así que ese renombrado producía un build limpio y con tipos comprobados que ejecutaba la copia anterior del shim. Los archivos bajo extern/ que no son .ts ni .tsx siguen sin afectar a la caché, y es a propósito: un README.md junto a tu shim se copia a la salida con él, pero nada comprueba sus tipos ni lo ejecuta, así que no hay nada que recompilar.

Clientes basados en clases: los de bases de datos y mensajería

La mayoría de los clientes de bases de datos y de mensajería se basan en clases: escribes new Kafka(...), new MongoClient(url), new Redis(), new Pool(cfg). Glyph tiene new justo para esto.

un cliente basado en clases (kafkajs) 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
un cliente con factory no necesita new 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

Genera un new de TypeScript tal cual y tsc lo comprueba contra el constructor real del paquete, así que un argumento incorrecto es un error real y un callee no definido se detecta por su nombre.

Se limita a la interoperabilidad: Glyph no tiene class propio, y new solo construye un tipo que viene de un paquete, de una declaración en .types o de extern_ts.

Dónde está

Disponible hoy

  • Importar cualquier paquete de npm (incluidos los nombres con guiones y con scope).
  • Un paquete instalado que trae sus propios tipos (o tiene @types/...) se comprueba y se ejecuta sin stub.
  • Los clientes basados en clases se construyen con new, que tsc comprueba contra el constructor real; los clientes con factory se importan y se llaman directamente.
  • Los builtins de node se comprueban de serie
    Detalles

    Los builtins de node (fs, path, http, child_process incluido el spawn con streaming, y el resto) se comprueban de serie, con @types/node cargado automáticamente cuando lo instalas, y el CI compila el propio runtime del compilador contra ese paquete en latest, así que una declaración de la que depende la librería estándar no puede desviarse de la real de node.

  • Una declaración a la que solo llega tu código todavía no está cubierta por esa comprobación, y unas pocas siguen siendo más amplias que las de node.
  • Declaraciones ambientales en .types/ para todo lo demás.
  • glyph gen dts para materializar un .d.ts en tipos de Glyph validados.
  • Una salida .ts limpia que tu TypeScript existente importa de vuelta.
  • import extern/<name> llega a TypeScript escrito a mano en <src>/extern/
    Detalles

    Cuando necesitas TypeScript entero escrito a mano, import extern/<name> llega a un .ts en <src>/extern/, que se copia y se comprueba junto con tu código, y que la caché de glyph run sigue, así que editarlo provoca una recompilación.

En camino

  • La materialización maneja las formas que traen los SDK reales, y los tipos derivados de valores son de primera clase
    Detalles

    La materialización ya maneja las formas que traen los SDK reales (namespaces, re-exports entre archivos y con alias o namespace, exports de subrutas y genéricos de primera clase), y los tipos derivados de valores (z.infer<typeof s>) son de primera clase.

  • El principal hueco que queda es que las salidas de un paquete sin materializar se comprueban contra su .d.ts pero no se validan en tiempo de ejecución salvo que las materialices.
  • En el lado de extern/, la raíz de las fuentes es distinta entre glyph run y glyph build
    Detalles

    En el lado de extern/, la raíz de las fuentes es distinta entre los dos comandos: glyph run app.glyph toma como raíz el directorio del propio archivo, glyph build src/ toma el directorio que indicas. Por eso, un programa en un subdirectorio busca su shim en dos sitios distintos, y hasta que elijamos una sola raíz, un proyecto organizado así necesita que el shim sea accesible desde los dos. Si no lo es, falla de forma visible.
