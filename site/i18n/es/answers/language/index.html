¿Es un lenguaje de verdad o un juguete con huecos?

Tiene lo que buscas en un código real: visibilidad de módulos, interfaces para restringir genéricos, defer para la limpieza y helpers de concurrencia. Donde se apoya en JavaScript, lo dice en lugar de fingir lo contrario.

Por qué importa

Un lenguaje en el que puedes escribir un archivo pero no estructurar un proyecto no es uno en el que vayas a apostar un código. Los huecos que importan no son exóticos:

  • Visibilidad¿Puedo ocultar un helper?
  • Restricciones de genéricos¿Puede un genérico exigir una capacidad?
  • Limpieza¿Puedo liberar un handle de archivo en cada camino de salida?
  • Concurrencia¿Puedo ejecutar dos cosas a la vez y esperar a las dos?

Glyph responde a esas cuatro, y lo hace sin reabrir la dirección cargada de anotaciones que abandonó a propósito.

Las interfaces restringen genéricos

Una interface es estructural, como una de TypeScript: es un conjunto de firmas de miembros que un genérico puede exigir. Sin implements, sin ceremonia nominal. Cualquier valor con esos miembros cumple, y tsc lo hace cumplir.

las interfaces restringen genéricos 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer y concurrencia estructurada

defer ejecuta la limpieza cuando el bloque termina, por cualquier camino, incluidos un return anticipado o un error lanzado. Y std/task une trabajo concurrente con un único tiempo de vida en lugar de dejar promesas sueltas.

defer + concurrencia estructurada 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])
Detalles el orden, y los handles owned

Varios defers se ejecutan en orden inverso (el último en entrar, el primero en salir), y se combina con los handles owned.

Lo que hereda de JavaScript

Glyph compila a TypeScript y se ejecuta en un motor de JavaScript, así que hereda el orden de evaluación, la semántica de referencia para la mutación y el modelo de un solo hilo con recolección de basura. La especificación lo establece como garantías en lugar de dejar que lo descubras tú.

La igualdad es donde se diferencia: == compara valores, los records campo por campo, mientras que el === de JavaScript compara referencias.

La memoria manual y un modelo sin recolección de basura no están en el roadmap; quedan fuera de lo que es un lenguaje que transpila a TypeScript.

No hay if, así que match tiene que cargar con todo

Lo primero que pregunta un desarrollador de TypeScript después de oír lo de la exhaustividad es si match es de verdad un condicional de propósito general o solo una forma bonita de desestructurar una unión. Es lo primero, y donde se demuestra es en la asignación.

Un match que es el valor entero de un let o un mut acepta todo lo que acepta una sentencia: un brazo puede ser un bloque, un brazo puede hacer await, un brazo puede hacer break del bucle que lo rodea y un brazo puede leer el binding que está asignando, que es como acumulas estado a lo largo de un bucle sin un if.

del comprobador de enlaces: seguimiento de bloques de código, y un brazo con await 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}
Detalles a qué compila, y de dónde salen los fragmentos

Los dos compilan a un switch normal que asigna el binding en cada brazo, así que el await queda en la función async que lo rodea y el acumulador es una variable normal que TypeScript puede inferir. Los dos fragmentos son de examples/apps/linkcheck/main.glyph, un comprobador de enlaces de Markdown escrito precisamente para encontrar este tipo de cosas.

Un match usado dentro de una expresión más grande, como argumento u operando, sigue convirtiéndose en una closure, lo que significa que sus brazos tienen que ser expresiones simples. Sacarlo a su propio let elimina esa limitación.

Un patrón puede nombrar una forma a más de un nivel de profundidad

Una variante con varios campos lleva un record, así que un brazo que quiere reconocer una forma tiene que llegar a través de los campos del record. Ahora un campo acepta cualquier patrón: una etiqueta de variante, un constructor anidado, una desestructuración anidada, un literal, un patrón de array.

un caso de rotación del rebalanceo de un árbol rojo-negro, como un solo brazo 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}
Historia la solución provisional antes de la 0.1.90

Hasta la 0.1.90 la posición de un campo aceptaba un nombre y nada más: podías renombrarlo, y eso era todo. Hacer match de una etiqueta ahí era un error de compilación, y un constructor anidado se le escapaba al parser. La solución era enlazar cada campo y escribir un match anidado por nivel, lo que para algo como el rebalanceo de un árbol rojo-negro es otro programa: los brazos dejan de alinearse con los casos y cada nivel vuelve a pasar los bindings del nivel superior.

Hay una consecuencia que conviene conocer antes de escribir uno. Un campo que comprueba un valor puede fallar, así que el brazo ya no cuenta como cobertura de su variante, y un match cuyo único brazo Node es Node({ color: Red, ... }) se informa como no exhaustivo hasta que otro brazo o un else se ocupe del resto.

Detalles por qué pide el comodín, y la posición de array

El checker demuestra la cobertura sobre un conjunto de etiquetas, no sobre un producto de campos, así que no deducirá que un brazo Red y un brazo Black juntos agotan Node. Pedir el comodín es la interpretación que no puede dejar que un match se quede sin brazo en tiempo de ejecución. Lo mismo pasa donde no hay variantes que contar: un match sobre un record normal en el que cada brazo comprueba un campo necesita un else detrás.

Un sitio al que llega esto y que quizá no esperas es la posición de array. [Black] como brazo entero contaba antes como match de cualquier array de un elemento, así que un match que se apoyaba en él se certificaba como exhaustivo y luego tomaba ese brazo también para [Red]. Aquí un elemento en PascalCase también es una referencia a una variante, así que un match así es ahora E0208 en arrays de longitud 1. Enlaza el elemento y haz match sobre él por separado. La traducción de debajo sigue siendo la antigua, y por eso la comprobación es la mitad que salió primero.

Y el compilador sabe qué ha producido el match

La siguiente pregunta es la que decide si algo de esto sostiene peso: una vez que enlazas un valor que sale de una bifurcación, ¿Glyph conoce su tipo, o se encoge de hombros y deja que tsc lo resuelva después? Ahora un match toma el tipo de sus brazos cuando coinciden, y se sabe que T.parse devuelve Result<T, Array<Issue>>, que es la forma sobre la que bifurca la mayoría del código real.

del repartidor de gastos: sin anotación, e i es un número

  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...
}
Historia antes de la 0.1.45

Hasta la 0.1.45 se encogía de hombros. Toda expresión match tenía tipo desconocido, así que un valor que salía de la única construcción de bifurcación del lenguaje quedaba sin tipo a partir de ahí.

Detalles qué fallaba sin avisar, y cómo funciona la unión de tipos

Las dos mitades de esto son cosas que antes fallaban sin avisar. El bucle genera wire.expenses.entries(); cuando el tipo de lo que se itera es desconocido, genera Object.entries(...) en su lugar e i es el string "0", lo cual es TypeScript válido, así que el build salía limpio y el programa imprimía 01:a donde quería decir 1:a. Y wire.expensez es ahora [E0210] type WireLedger has no field expensez desde Glyph, en la línea del .glyph, en lugar de un TS2339 sobre el TypeScript generado.

La unión de tipos es igualdad en la cabeza: un brazo que termina en return no vota, y los brazos cuyos tipos no coinciden dejan el resultado desconocido como antes. Solo mira un nivel más abajo en un argumento de tipo, así que None => [] coincide con un brazo Array<string> en lugar de hundir el match entero, y el bucle siguiente sigue enlazando un número. La misma cadena sobre record.get funciona por el mismo motivo: las seis funciones de std/record toman el tipo del valor del record que pasas. El fragmento es de examples/apps/settle/main.glyph, que llevaba la anotación que esto eliminó.

Una búsqueda con un valor vacío por defecto

Esa es la forma a la que más afectaba. record.get sobre un Record<string, Array<string>> es un Option<Array<string>>, y [] es un array de nada en concreto, así que los dos brazos coinciden en Array y el tipo de los elementos sale del brazo que lo tiene.

for i, hop in path {               # i is a number, so the indent nests

Historia las copias que llevaban las apps antes de la 0.1.47

Cinco rondas de dogfooding seguidas registraron la misma lista, y hasta la 0.1.47 seis apps de este repositorio tenían su propio repeat, cinco su propio pad_start, y todas tenían un bucle donde correspondía un fold.

En qué se diferencian de TypeScript

Tres de ellos se separan a propósito de sus homónimos de TypeScript.

  • repeatrepeat devuelve "" con un número negativo donde TS lanza una excepción, y eso es lo que hace seguro repeat(pad, width - len(s)) sobre un string que ya es demasiado largo.
  • index_ofLas dos funciones index_of devuelven Option<number> en lugar de -1, porque -1 es un número que pasa la comprobación de tipos en cualquier sitio donde lo hace un índice real y falla muy lejos de la llamada.
  • replace_allEl reemplazo solo existe como replace_all, así que no hay una forma que solo reemplace la primera aparición y que se pueda confundir con String.prototype.replace, que reemplaza una sola sin avisar.

Por qué importa fold

fold es el que aporta a un pilar en lugar de ahorrar tecleo. mut es el registro, buscable con grep, de cada sitio donde cambia el estado, y sin fold, grep mut devuelve un montón de bucles de conteo que no modifican nada que le importe a quien revisa.

Borrar las versiones hechas a mano bajó examples/apps/ de 192 sitios de mutación a 161.

Detalles cómo se comprobó la reescritura

La reescritura se comprobó por la salida, no revisando: las siete apps se ejecutaron con entradas fijas antes y después, 26 archivos de stdout, códigos de salida y respuestas HTTP, todos idénticos byte a byte.

¿Puedo recorrer un directorio y saber qué ha fallado?

std/fs traía seis funciones y ninguna listaba un directorio.

  • fs.read_dirfs.read_dir devuelve los nombres de las entradas de un nivel.
  • fs.is_dirfs.is_dir responde con un bool igual que fs.exists.
  • fs.statfs.stat devuelve un FileInfo con is_dir, is_file, size en bytes y modified en milisegundos desde epoch, que time.format_iso formatea directamente.

No hay walk recursivo ni glob; un recorrido son esas tres más path.join en unas diez líneas.

Historia la solución provisional que sustituyeron

El comprobador de enlaces de este repositorio salía de la librería estándar para usar el readdirSync de node, y averiguaba qué rutas eran directorios intentando leerlas e inspeccionando el errno que devolvían. Las dos mitades están arregladas.

Los fallos tienen nombre

El lado de los fallos cambió más. Ahora los cinco tipos de los que un programa se recupera de verdad tienen nombre, y un errno sin nombre llega intacto en la cola Other.

El checker sabe que esa clasificación es cerrada, así que un match sobre err.kind se mide con el mismo listón que una unión que declaraste tú: cubre los seis y no necesitas else, deja uno fuera y el build falla con E0200 nombrando fs.ErrorKind.

  fs.ErrorKind.NotADirectory    => io.eprintln("that is a file"),

Detalles la clasificación antigua, los campos comprobados, y cómo probar la comprobación tú mismo

FsError.kind era { tag: string } con NotFound como única categoría, así que distinguir “esa ruta es un directorio” de “esa ruta no existe” significaba comparar un string de errno.

fs.FsError y fs.FileInfo también tienen campos comprobados, así que err.mesage es E0210 sobre tu código Glyph en lugar de un error de tsc sobre el TypeScript generado.

Esa comprobación está activa. Borra el brazo PermissionDenied del match de arriba y glyph check --no-tsc se detiene con E0200: match no exhaustivo sobre fs.ErrorKind, faltan las variantes PermissionDenied. Cuando se escribió el modelo de la librería estándar solo cubría los tipos de retorno, y un match como este compilaba sin errores y lanzaba una excepción en tiempo de ejecución; ahora están modeladas las formas de los campos y las variantes de fs.FsError, fs.FileInfo y fs.ErrorKind.

Dos añadidos más pequeños

Llegaron otras dos más pequeñas, las dos de la misma app.

  • regex.captures_allregex.captures_all te da los grupos de captura de cada coincidencia en lugar de solo el texto coincidente, así que un escaneo plano de key=value deja de ser un bucle hecho a mano.
  • task.pool_settledtask.pool_settled es task.pool con el comportamiento ante fallos de all_settled: concurrencia limitada, un resultado por tarea, y un host caído te cuesta el resultado de ese host en lugar de todos los resultados que el pool había reunido.

¿Cómo sabes que las funciones son las adecuadas?

Porque la app que las pidió tuvo que dejar de rodearlas antes de que la versión se diera por terminada.

Una función de biblioteca que se publica y un rodeo que sobrevive a ella son afirmaciones distintas, así que el mismo cambio que añadió estas cuatro borró las copias del comprobador de enlaces: el import de readdirSync, las dos comparaciones de strings de errno, 97 líneas de escáner hecho a mano y el pool que fallaba al primer error. Salieron 122 líneas.

Dos cambios de comportamiento, medidos

Dos de esos borrados cambiaron lo que hace el programa, y la diferencia se midió en lugar de discutirse.

  • Un directorio ilegibleApunta la versión antigua y la nueva a un árbol que contiene un directorio que no puedes leer: la nueva imprime permission denied y cuenta la ruta como ilegible, y la antigua, que solo podía preguntar si el errno era EISDIR, la dejaba fuera del informe por completo.
  • Una URL que fallaHaz que una de tres URLs lance una excepción: pool_settled imprimió las tres filas y nombró el fallo, y pool no imprimió nada y murió por un rechazo sin manejar, llevándose por delante los dos resultados buenos.
Detalles la reescritura del escáner y la duda sobre la alternancia

La reescritura del escáner también resolvió una duda de diseño. Como un grupo de captura que no participó se lee como "", igual que uno que coincidió con algo vacío, parecía que captures_all no podía decirte qué rama de una alternativa se había activado. Sí puede, si escribes el grupo de cada rama alrededor de toda la construcción y no solo de la parte que quieres: un grupo que se activó empieza entonces por `, [, ! o <, y no puede estar vacío. La parte que puede estar vacía, el destino del enlace, va anidada dentro y nunca es lo que preguntas. Eso convirtió un recorrido carácter a carácter de 180 líneas en dos patrones y un despacho de 12 líneas, con una salida idéntica byte a byte sobre la documentación del propio repositorio y sobre un caso de prueba hecho para romperlo.

El dinero no funciona con floats

El hueco que acabaría en el acto con una evaluación en una fintech es manejar dinero con number IEEE-754, donde 0.1 + 0.2 no es 0.3 y los valores por encima de 253 pierden precisión sin avisar.

std/decimal es punto fijo exacto en base 10 sobre BigInt: un entero de precisión arbitraria con un número fijo de dígitos decimales, así que la suma, la resta y la multiplicación son exactas y la división recibe una escala y un redondeo explícitos. Una cantidad mal formada se parsea como un Err, nunca como un NaN silencioso.

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

Números enteros grandes

Para números enteros grandes exactos, ids de cuenta y contadores, está el tipo bigint: los literales son 123n, se genera como un bigint real de TypeScript, y un campo de record con tipo bigint valida typeof === "bigint" en la frontera, así que un id enviado como number de JSON se rechaza en lugar de redondearse sin avisar por encima de 253.

Un callback async por fin tiene tipo

Un tipo de función era fn(A) -> T y nada más, que se genera como (a: A) => T. Un cuerpo async no encaja ahí, así que una función que devolvía una tarea diferida, o un record de handlers async, tenía que quedarse sin anotar y el checker dejaba de mirar.

async fn(A) -> T es ese tipo que faltaba. Se genera como (a0: A) => Promise<T>, y async fn() sin retorno se genera como () => Promise<void>.

una tarea diferida, y un mapa de handlers 
fn task_for(url: string) -> async fn() -> Fetched {
  return async fn() -> Fetched { return { url: url, body: await fetch_one(url) } }
}

type Handler = async fn(string) -> string

async fn dispatch(routes: Record<string, Handler>, name: string, arg: string) -> string {
  return match record.get(routes, name) {
    Some(h) => await h(arg),
    None    => "no route",
  }
}
Detalles cómo distingue Glyph las funciones normales de las async

Glyph distingue los dos por su cuenta en lugar de dejárselo a tsc: una función normal donde se espera una async es E0204 en un return y E0211 en un argumento de una llamada, y el mensaje nombra los dos lados.

El único caso que no juzga es un retorno void, donde TypeScript acepta cualquier función.

Un tipo recursivo, con match hasta el fondo

Una unión puede nombrarse a sí misma dentro de su propio payload, con sus parámetros de tipo, y un brazo de match puede anidar un patrón de constructor dentro del campo de otro patrón de constructor. Junta las dos cosas y las reglas de equilibrado de un árbol rojo-negro son cuatro brazos: cada uno nombra exactamente la forma que reescribe, y es el compilador quien comprueba la forma, no un comentario encima que la afirma.

uno de los cuatro casos de rotación 
type Tree<K, V> =
  | Leaf
  | Node({ color: Color, left: Tree<K, V>, key: K, value: V, size: int, right: Tree<K, V> })

fn balance<K, V>(t: Tree<K, V>) -> Tree<K, V> {
  return match t {
    Node({ color: Black, left: Node({ color: Red, left: Node({ color: Red, left: a, key: xk, value: xv, right: b }), key: yk, value: yv, right: c }), key: zk, value: zv, right: d }) => node(
      Red,
      node(Black, a, xk, xv, b),
      yk,
      yv,
      node(Black, c, zk, zv, d),
    ),
    // the other three cases, then:
    other => other,
  }
}

    Detalles

    La visibilidad se comprueba en las anotaciones de tipo, no en los valores leídos a través de un namespace: lib.helper() con helper privado sigue siendo un error de tsc y no de Glyph.

Async

  • Se permite un await de nivel superior en el inicializador de un const a nivel de móduloE0222
    Detalles

    El contexto async ya se comprueba (E0222) salvo en un sitio: el inicializador de un const a nivel de módulo no tiene ninguna función que lo envuelva, así que ahí se permite un await de nivel superior y el ESM generado lo ejecuta.

Tipos inferidos

  • Los brazos que no coinciden en la cabeza del tipo dejan el resultado desconocido para Glyph
    Detalles

    La unión de tipos de los brazos sigue necesitando que coincidan en la cabeza del tipo: cuando producen tipos distintos, el resultado es desconocido para Glyph y solo tsc comprueba lo que haces con él.

  • Nueve funciones de la librería estándar están en la misma situación
    Detalles

    Nueve funciones de la librería estándar están en la misma situación. Seis aceptan un argumento final opcional (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify) y la comprobación del número de argumentos compara un número con otro número, así que modelarlas daría un error falso en cada llamada que omite el último argumento; array.map, flat_map y zip toman el tipo de sus elementos de un callback en el que el checker no entra.

    Un valor que sale directamente de esas nueve necesita una anotación antes de recorrerlo con un índice, y un match sobre string.index_of sin brazo None sigue compilando sin errores y lanzando una excepción en tiempo de ejecución. array.index_of sí está modelada e informa de E0200.

  • Los miembros y el número de argumentos sobre un valor al que el checker no pudo dar tipo no se comprueban
    Detalles

    Los miembros y el número de argumentos sobre un valor al que el checker no pudo dar tipo siguen sin comprobarse en esa frontera en lugar de ser un error.

Librería

  • string indexa unidades de código UTF-16, y no hay previsto ningún chars ni char_at
    Detalles

    En la parte de la librería, string indexa unidades de código UTF-16 igual que siempre lo han hecho len y split, y eso está decidido: no hay chars ni char_at y no están previstos, porque una mitad de un par sustituto devuelta parece un carácter hasta el momento en que se escribe. Codifica con encoding.hex_encode y lee los dígitos hexadecimales de dos en dos.

  • captures_all no da posiciones; fs.read_dir mantiene el orden del sistema operativo
    Detalles

    captures_all devuelve grupos y no posiciones, así que un escáner que necesita saber en qué punto de la línea empezó una coincidencia sigue escribiendo su propio bucle, y fs.read_dir te da las entradas en el orden del sistema operativo, así que ordénalas cuando la salida tenga que ser reproducible.

Patrones

  • Un constructor con payload en un campo falla sobre una unión a la que se llega mediante un import de namespaceE0300
    Detalles

    A los patrones de campo anidados les queda un límite: un constructor con payload, en un campo, sobre una unión a la que se llega mediante un import de namespace. import tree { Node } y luego Node({ left: Node({ key: k }) }) compila, e import tree y luego tree.Node({ left: tree.Node({ key: k }) }) da E0300 sobre la misma unión.

  • Una unión genérica sobre su propio parámetro acepta el brazo anidado y se comprueba en busca de variantes que faltanE0200
    Detalles

    El otro límite ya no existe: una unión genérica sobre su propio parámetro (type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> })) antes rechazaba el brazo anidado que la misma unión sin el parámetro aceptaba, y ahora lo acepta, tanto con un parámetro de tipo abierto como con una instanciación concreta. La misma búsqueda decidía si el match se comprobaba siquiera en busca de variantes que faltan, así que hasta esta versión un match sobre Tree<K> podía omitir Leaf, compilar sin errores, pasar tsc --strict y lanzar una excepción en tiempo de ejecución, donde la forma no genérica daba E0200.

    Las dos formas lo informan, y mover la unión a otro módulo ya no cambia la respuesta: un match sobre un Tree<string> importado que omite Leaf da E0200 nombrando Leaf, igual que el Tree no genérico importado. Ese era otro camino del código, comprobado por separado, y hasta esta versión iba en sentido contrario: compilaba sin errores y lanzaba una excepción en tiempo de ejecución.

  • La cobertura de una unión importada nunca comprueba los payloads de sus variantes
    Detalles

    Hay una cosa sobre la cobertura de una unión importada que conviene saber antes de apoyarse en ella: los payloads de sus variantes tampoco se comprueban nunca, así que B(X), siendo X una variante de la propia unión del payload, hace match con cualquier B en lugar de informar de que falta Y, y eso no tiene nada que ver con los genéricos.

    Enlazar un campo, o hacer match de una etiqueta sin payload en él, funciona en todos los casos.
