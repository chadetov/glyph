19 · Servidores y daemons

¿Puedo escribir un servidor, o el proceso simplemente termina?

Puedes escribir un servidor. main prepara las cosas y retorna, y el proceso sigue vivo mientras haya sockets y timers pendientes, la misma regla que usa Node. Hasta la 0.1.63 no era así: el runner terminaba el proceso en cuanto main retornaba, así que un servidor abría su puerto y moría en el mismo tick.

Por qué importa

Es la diferencia entre un lenguaje que puede ejecutar un script y uno que puede ejecutar un servicio. Un servidor, un vigilante de archivos, un bot que mantiene una conexión con un gateway, un ejecutor de trabajos: ninguno termina dentro de main. Preparan sus handlers y dejan el proceso en manos de los eventos.

El comportamiento anterior fallaba de la peor forma posible, en silencio. glyph run app.glyph --serve 4100 no imprimía nada, ni siquiera la línea dentro del callback de listen, y salía con 0. Nada en el código parecía incorrecto y pasaba la comprobación de tipos. Un agente que se topa con eso no tiene ningún error que informar ni motivo para pensar que algo ha fallado.

Míralo

Un servidor TCP completo. main retorna inmediatamente; los callbacks se ejecutan mientras viva el proceso:

Un servidor, de principio a fin 
module main

import std/io
import std/process
import net { createServer }

fn main(argv: Array<string>) -> number {
  let server = createServer(fn(socket) {
    mut socket.write("hello\n")
    mut socket.end()
  })

  mut server.on("error", fn(err) {
    io.eprintln("cannot listen: ${err.message}")
    process.exit(1)
  })

  mut server.listen(4000, fn() {
    io.println("listening on 4000")
  })
  return 0
}

net es un módulo nativo de Node, así que es un import normal, pero no es uno de los seis para los que el compilador incluye tipos ambientales (fs, http, path, os, crypto, url). O instalas @types/node, y el build lo prefiere, o pones una declaración en .types/net.d.ts junto a tu código, que es lo que hace la app de chat para no necesitar ninguna dependencia.

Dos cosas que conviene saber. El return 0 se ejecuta antes de que se conecte el primer cliente: es el código con el que acabará saliendo el proceso, no una indicación de cuándo sale. Y cualquier cosa que falle después de que main haya retornado tiene que fijar su propio código de salida, porque el valor de retorno de main ya se ha usado. Para eso está el handler de error. Sin él, un servidor que no puede abrir su puerto vacía su bucle de eventos y sale con 0, informando de éxito.

Uno de verdad

examples/apps/chat es un servidor de chat que mantiene varios clientes TCP a la vez. La otra dirección: un cliente que se ejecuta indefinidamente

Un bot tiene la misma forma, pero apuntando hacia fuera. examples/apps/discord es un cliente del gateway de Discord: se conecta por WebSocket, se identifica, envía heartbeats con el intervalo que dicta el servidor, lleva un número de secuencia para que una conexión caída se reanude en lugar de empezar de cero, detecta cuándo la conexión está abierta pero muerta y espera cada vez más entre reconexiones.

Lo que merece la pena copiar es dónde vive la lógica. Decidir qué hacer ante un RECONNECT, un heartbeat perdido o un token rechazado es una función pura que va de una sesión y un evento a una sesión nueva y una lista de acciones. Un módulo ejecuta esas acciones sobre un socket real. Por eso la lógica de reconexión, que es la parte difícil de acertar, se comprueba con @example en lugar de desenchufando un cable de red:

Cada uno de esos tres ejemplos es un bug que primero estuvo en el código. Escribir un gateway simulado y apuntar el bot hacia él detectó uno. Los otros dos los detectó un segundo simulador escrito a partir de la documentación de Discord en lugar de a partir del cliente, que envía las cosas que un simulador cooperativo nunca envía: una petición de heartbeat sin que nadie la pida y un código de cierre que significa "tu token es incorrecto, deja de intentarlo". Un simulador escrito por el autor del cliente solo prueba las partes del protocolo que el autor leyó.

Dónde está

Disponible hoy

Retornar de main fija el código de salida sin detener el proceso, así que los servidores, los vigilantes y los bucles de eventos funcionan. Un programa que solo calcula sigue saliendo en cuanto main retorna, con el mismo código, así que nada cambió para los programas cortos. Los módulos nativos de Node como net son imports normales, y un programa que lanza una excepción durante la preparación sigue terminando, ahora después de que su diagnóstico haya llegado a un stderr redirigido en lugar de arriesgarse a quedar cortado por la salida. std/timers programa trabajo (after, every, cancel, unref) y std/websocket abre una conexión, así que ninguno necesita una declaración escrita a mano.

Mejorando

Un listener que no consigue abrir su puerto después de que main haya retornado sale con 0 a menos que el programa diga otra cosa: process.set_exit_code(1) registra el fallo sin cortar el trabajo que sigue en marcha, y process.exit(1) se detiene inmediatamente. El compilador todavía no puede avisarte de que se te olvidó. Y todavía no hay forma de indicar que una función no retorna, así que el main de un servidor lleva un return 0 al que nunca se llega.
