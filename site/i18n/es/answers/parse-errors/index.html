27 · Fallos de parseo

Cuando falla un parseo, ¿me entero de por qué?

Sí. Cada problema nombra el campo, dice qué regla incumplió el valor y lleva un code sobre el que puedes bifurcar. Un campo restringido por un predicado where informa del propio predicado, así que con grep llegas desde el rechazo a la línea que lo impuso.

Por qué importa

Un validador que dice "este payload es incorrecto" ha hecho la mitad del trabajo.

El handler todavía tiene que decidir: ¿es un cliente que olvidó un campo, o un cliente que envió una contraseña de cuatro caracteres? Uno es un 400, el otro es un 422, y si el validador no lo dice, acabas parseando el mismo cuerpo dos veces con dos tipos distintos para recuperar un dato que el validador ya tenía.

Historia dónde surgió esto

Es exactamente lo que pasó al construir una API de autenticación en Glyph. Un registro sin ninguna clave password volvía como weak_password, porque la ausencia y la longitud insuficiente producían el mismo string.

Los tipos anidados responden por sí mismos

Un campo cuyo tipo tiene su propio descriptor se valida con el parse de ese tipo, y sus problemas vuelven con el nombre del campo al principio de la ruta. Así, un Password anidado dos niveles más abajo informa de ["body", "password"] y sigue llevando su propio mensaje.

El código, no el string

Issue lleva un code opcional: "missing", "type", "refinement", "unexpected" o "depth". Bifurca según eso. Hacer match sobre el texto del mensaje es justo la fragilidad que Glyph existe para eliminar, y el mensaje es para la persona que lee el cuerpo de la respuesta.

Una separación entre 400 y 422 que no lee el mensaje 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code es opcional, así que un Issue que construyas a mano, y todo consumidor escrito antes de que existiera, sigue compilando sin cambios.

Detalles el código "depth"

"depth" es la respuesta para un cuerpo anidado más de 1000 niveles de objetos y arrays (MAX_DEPTH en std/schema): un solo problema en el campo donde ocurrió, cuando antes de la 0.1.150 la comprobación lanzaba RangeError: Maximum call stack size exceeded y se llevaba el handler por delante.

Dónde está

Disponible hoy

  • Los records y los tipos where informan de la regla que falla, no solo del campo que fallamissingtyperefinementunexpecteddepth
    Detalles

    Los records y los tipos where informan de la regla que falla, no solo del campo que falla: "missing" para un campo obligatorio ausente, "type" para una forma incorrecta (incluido algo que no es un objeto, o un array), "refinement" para un valor que pasó su tipo base y no cumplió el predicado, "unexpected" para una clave que el tipo no declara, y "depth" para un valor anidado a más de 1000 niveles.

  • Un refinamiento cita su predicado.
  • Un campo cuyo tipo tiene un descriptor delega en él, así que los problemas anidados llegan con la ruta completa.
  • Los campos opcionales (f?: T) nunca se informan como ausentes.

Cada vez más preciso 2

  • Un campo con un tipo que no tiene descriptor propio sigue recibiendo la comprobación plana y un problema "type"
    Detalles

    Dos límites. Un campo con un tipo que no tiene descriptor propio, un parámetro de tipo sin restricciones o un tipo importado de un .d.ts escrito a mano, sigue recibiendo la comprobación plana y un problema "type"; el compilador no sintetiza un descriptor para esos, y lo que les da uno es ejecutar glyph gen dts sobre la declaración.

  • Un tipo propio de un módulo llamado Issue se rechaza en la línea que lo nombraE0110desde la 0.1.60
    Detalles

    Un módulo que declaraba su propio tipo llamado Issue ocultaba el del preludio dentro del archivo generado y rompía todos los descriptores de ese módulo; desde la 0.1.60 esa declaración da E0110 en la línea que nombra el tipo, así que sabes dónde está el problema en lugar de leer un error de tsc sobre código generado.
