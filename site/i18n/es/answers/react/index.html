¿Funciona con React: componentes, hooks y Context?

Sí. Un component compila a un componente de función de React, el JSX se traduce a createElement, los propios hooks de React se importan por su nombre y sus pares se desestructuran, y el estado de un reducer tiene una exhaustividad que TypeScript tal cual no tiene. A la propia página (su título, el punto de montaje, el estado guardado) se llega a través de std/dom y std/storage. El hueco que conviene conocer primero: el checker propio de Glyph no tipa lo que devuelve un hook, así que esos valores los comprueba tsc.

Por qué importa

Buena parte del código que escriben los agentes es React. Glyph lo trata como un destino de primera clase, no como un añadido: component es una palabra clave propia (así que grep "^component " audita toda tu UI). Los hooks de React se importan de react y se llaman con sus nombres y tipos reales, y tsc los comprueba contra las propias declaraciones de React.

Míralo

El useReducer real de React, con un reducer sobre una unión etiquetada. Cada acción tiene que manejarse, y el compilador lo comprueba:

counter.glyph, contra react@18 y sus tipos 
import react { useReducer }

type Action = Inc | Dec | Reset

fn reducer(n: number, a: Action) -> number {
  return match a {
    Inc => n + 1,
    Dec => n - 1,
    Reset => 0,
    // add an Action variant and this match is E0200
  }
}

pub component Counter() {
  let [count, dispatch] = useReducer(reducer, 0)
  return <button on_click={fn() { dispatch(Inc) }}>{count}</button>
}

Añade una acción Double y el reducer deja de compilar con un E0200 que la nombra, algo que un switch de TypeScript normal dejaría llegar a producción. El par se desestructura con let [count, dispatch], y el TypeScript generado añade satisfies readonly [unknown, unknown], así que tsc demuestra que el hook devolvió un par y sigue infiriendo el tipo de cada elemento. El checker propio de Glyph no tipa los valores que vienen de React, así que un argumento incorrecto para dispatch o para un setter de estado lo informa tsc en el build, no el editor ni --no-tsc. El Context de React funciona hoy con createContext / useContext, y los nombres de elemento con expresión de miembro (<ThemeContext.Provider>) funcionan directamente: sin apaños.

El spread de props en JSX también funciona: <input {...register("email")} /> se traduce a un spread de objeto en las props, así que el idioma de react-hook-form no necesita adaptador. Los tipos derivados de valores de zod son de primera clase: type FormData = z.infer<typeof schema> funciona directamente, sin vía de escape. Lo único que cambia: un componente recibe un solo record de props, no varios parámetros posicionales. Consulta usar tus librerías y la página de endurecimiento para ver exactamente dónde está ese límite.

¿Se comprueban las props antes de tsc?

Sí. Glyph compara él mismo cada elemento con el record de props de su componente, así que un valor incorrecto, una prop mal escrita y una obligatoria que falta son errores de Glyph que nombran la prop. Los ves en el editor y por MCP, no solo en un build completo. Funciona igual tanto si el componente se importó por su nombre como a través de su módulo:

main.glyph, con Card declarado en ui.glyph 
import ui

pub component App() {
  return <div>
    <ui.Card title="Q3" />
    <ui.Card title="Q4" cout={2} />
  </div>
}

// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`
// E0210 type `CardProps` has no field `cout`; did you mean `count`?
// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`

--json lleva los nombres que faltan en una lista missing_fields, así que un agente puede añadir las props sin parsear el mensaje. Además, un componente tiene que recibir sus props como un solo record: component Greeting(name: string) da E0229 en el parámetro, porque React solo pasa el objeto de props y ese elemento nunca podría pasar la comprobación de tipos. Si lo llamas como función en lugar de renderizarlo, decláralo con fn.

¿Un <match> en JSX se comprueba como un match?

Es lo mismo. Cada <case> recibe el patrón que recibe un brazo de match, y el compilador lo pasa por el código que usa para el brazo. Los nombres que enlaza un case tienen los tipos del payload, un campo que el record del payload no tiene da E0210, y una variante que falta da E0200. Un case que comprueba un valor solo cubre parte de su variante, así que necesita un case hermano o un <case else> para cubrir el resto:

results.glyph 
type Page =
  | Loading
  | Loaded({ users: Array<User>, total: number })
  | Failed(string)

component Results(props: { page: Page }) {
  return <match value={props.page}>
    <case Loading><p>Loading...</p></case>
    <case Loaded({ users, totl })><p>{users.length} of {totl}</p></case>
    <case Failed(message)><p>{message}</p></case>
  </match>
}

// E0210 type `{ users: Array<User>, total: number }` has no field `totl`; did you mean `total`?

¿Cómo la arranca una página?

Glyph no tiene sentencias de nivel superior, así que la propia página llama a un main exportado. La app son dos módulos: uno con los componentes y otro que los monta en #root a través de std/dom y el createRoot de react-dom. Los atributos de eventos van en snake case (on_change genera el onChange de React), un handler es una lambda y el texto de un input es e.currentTarget.value.

app.glyph 
module app

import react { useState }

pub component App() {
  let [name, set_name] = useState("")
  return <main>
    <input value={name} on_change={fn(e) { set_name(e.currentTarget.value) }} />
    <p>Hello, {name}</p>
  </main>
}
main.glyph 
module main

import react-dom/client { createRoot }
import std/dom
import std/console
import std/option { Some, None }
import app { App }

pub fn main() -> void {
  match dom.element_by_id("root") {
    Some(root) => createRoot(root).render(<App />),
    None => console.error("the page has no #root element"),
  }
}
index.html, junto a los dos módulos 
<div id="root"></div>
<script type="module">
  import { main } from "./dist/gen/main.ts";
  main();
</script>

npx glyph build . --out dist/gen comprueba los módulos, ejecuta tsc --strict contra las declaraciones de React y escribe TypeScript en dist/gen. Después, npx vite build --outDir dist/web lee index.html, sigue el import y lo empaqueta con React. Este main no recibe nada y no devuelve nada, porque el script lo llama sin argumentos; el main(argv) -> number que escribe glyph init es el que llama glyph run bajo node. El recorrido completo, con el package.json y la línea de instalación, es ejecutar Glyph en una página del navegador, en la referencia que imprime glyph llms. El CI compila examples/apps/todo de la misma forma y lo renderiza en Chromium headless.

Dónde está

Disponible hoy

Componentes, JSX, fragmentos (<>...</>), nombres de elemento con expresión de miembro (<Ctx.Provider>), spread de props en JSX ({...register()}), props comprobadas contra el componente antes de tsc con cualquier forma de importarlo, los propios hooks de React importados por su nombre (useState, useReducer, useEffect) con tsc comprobando sus tipos y sus pares desestructurados (let [count, set_count] = useState(0)), useReducer con acciones de unión etiquetada exhaustivas, <match>/<case> comprobados y traducidos como un match con los patrones del brazo, Context mediante createContext/useContext, y la página a través de std/dom (título, punto de montaje, dirección), std/storage y std/console. El texto JSX se lee como lo lee TSX, así que <p>Don't stop</p> es texto normal; }, >, // y una entidad HTML como &amp; se rechazan en el texto (E0012), con la forma que hay que usar en su lugar. La lectura de un miembro sobre un array se comprueba, así que {items.foo} sobre un Array<string> da E0210. examples/apps/todo es una app completa sobre React 18 que se empaqueta con Vite y se renderiza en un navegador.

En camino

El checker de Glyph no tipa el resultado de un hook, así que set_count("x") sobre un estado numérico es un error de tsc en el build y no uno de Glyph en el editor. std/dom se limita a leer la página y fijar su título: React es el dueño del DOM que renderiza, así que no hay setters de elementos ni event listeners. Un efecto tiene que escribirse como fn() -> void { ... }, porque una lambda devuelve su última expresión y React la llamaría como función de limpieza. Un tipo de props escrito en línea sigue apareciendo como record en estos mensajes; uno con nombre muestra su nombre. Incrustar la salida de Glyph en una app Vite existente, con la UI en TypeScript, se explica en la guía de despliegue.
