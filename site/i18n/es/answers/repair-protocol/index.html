23 · Arreglar un build en rojo

Cuando el build falla, ¿el compilador le dice a mi agente cómo arreglarlo?

Te dice qué está mal en forma de datos, no como una frase que haya que parsear: los dos tipos, el símbolo culpable como module::name y la lista finita de cosas que podrían ir legalmente donde está lo que está mal. glyph check --agent añade lo que la edición de reparación no debe romper. Cuando la respuesta está totalmente determinada, glyph fix la escribe.

Por qué importa

El ciclo de un agente alrededor de un compilador es leer el error, adivinar la edición, recompilar. El paso de adivinar es donde se produce el daño, y se produce porque el error es un string. Un agente que lee "non-exhaustive match on OrderStatus" sabe que a un match le faltan brazos. No sabe qué llevan las variantes que faltan, así que escribe Paid("tx_1") y se entera por el siguiente diagnóstico. O lee la palabra "exhaustive", añade un brazo else, y el build se pone en verde habiendo tirado la garantía que el diagnóstico existía para proteger.

El compilador lo sabía todo. Conocía las variantes de la unión y sus payloads, sabía que un else renunciaría a la garantía, y descartaba las dos cosas una línea antes de responder.

Míralo

Un proyecto de dos módulos. orders declara la unión; main escribe un match sobre ella y maneja un caso. glyph check --agent, recortado a las claves que importan aquí:

glyph check --agent --no-tsc src 
{
  "code": "E0200",
  "severity": "error",
  "stage": "typecheck",
  "message": "non-exhaustive match on `OrderStatus`: missing variants
              `Paid`, `Cancelled`",
  "help": "Add an arm for each missing variant.",
  "file":   "main.glyph",
  "module": "main",
  "entity": "main::describe",
  "cause":  "orders::OrderStatus",
  "related": ["Pending", "Paid", "Cancelled"],
  "missing_variants": ["Paid", "Cancelled"],
  "expected": null, "actual": null, "alternatives": null,

  "constraints": [
    "preserve exhaustiveness: this match must name every case of
     `OrderStatus`, so add one arm for each of `Paid`, `Cancelled`.",
    "do not add an `else` arm: `OrderStatus` is declared in this project,
     and a catch-all forfeits the guarantee that adding a variant to it
     later forces this match to be updated (D9)."
  ],

  "symbols": [
    { "entity": "orders::OrderStatus", "kind": "union", "pub": true,
      "type": "Pending | Paid({ transaction_id: string }) | Cancelled",
      "exhaustive_match": true,
      "variants": [
        { "name": "Pending", "payload": null, "construct": "Pending" },
        { "name": "Paid",    "payload": "{ transaction_id: string }",
          "construct": "Paid({ transaction_id: string })" },
        { "name": "Cancelled", "payload": null, "construct": "Cancelled" }
      ] }
  ],
  "symbols_absent": [],

  "explain": { "command": "glyph --explain E0200",
               "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200" }
}

Merece la pena destacar tres cosas. cause es el símbolo culpable, y es algo distinto de entity, que es la declaración en la que está el diagnóstico: aquí la edición ocurre en main::describe y la forma con la que tiene que encajar viene de orders::OrderStatus. Las dos son direcciones que aceptan las demás herramientas, así que una respuesta se encadena sin volver a calcular nada.

Las constraints no son la reparación. Cada una es algo que el compilador ya hace cumplir, escrito para que la edición que satisface el diagnóstico no rompa la garantía que hay detrás. La segunda restricción es la razón de que exista la clave: un brazo else es válido, pondría el build en verde, y la restricción dice lo que cuesta elegirlo.

symbols es la respuesta de glyph_symbol para cada símbolo que nombra el diagnóstico, así que la siguiente edición del agente no necesita una segunda llamada. Un símbolo que la herramienta rechaza aparece en symbols_absent con el motivo, lo que separa "no miramos" de "miramos y no está".

Todas las claves están siempre presentes. Un dato que el compilador no tiene llega como un null explícito, nunca como una clave que falta, así que la ausencia se escribe de una sola forma en todos los códigos y tanto en la CLI como en la superficie MCP.

Cuando la respuesta está determinada, el compilador la escribe

glyph fix aplica solo las reparaciones que el compilador resuelve por su cuenta: imports sin usar, la cabeza de un brazo que no es una variante cuando el checker calculó exactamente una sugerencia, y un campo que el record no declara cuando exactamente un campo declarado está a un carácter de distancia. El match de arriba no es uno de ellos.

glyph fix src, sobre el match de arriba 
glyph fix: removed 0 unused import(s) across 0 file(s).
glyph fix: declined E0200 in src/main.glyph: the compiler does not
           determine what a missing arm should do, so `glyph fix`
           writes none: add an arm for each of `Paid`, `Cancelled`.
           `glyph check --agent` gives the pattern each case takes.

// src/main.glyph is unchanged, and glyph check still fails with E0200.

El compilador sabe qué casos faltan y el patrón que lleva cada uno. No sabe qué tiene que hacer el programa cuando un pedido está Paid, y cualquier cuerpo que escribiera sería una suposición que compila. Hasta la 0.1.128 glyph fix escribía esa suposición: un brazo por caso cuyo cuerpo imprimía el caso y llamaba a process.exit(1). El programa pasaba entonces check, tsc y build, y glyph query variants informaba del match como exhaustivo, así que el caso que faltaba había pasado de error de compilación a fallo en tiempo de ejecución sin nada que lo señalara.

Así que la regla se abstiene, y nombra los casos. Todo lo necesario para escribir los brazos ya está en la respuesta de --agent de arriba: missing_variants, y la forma construct de cada variante bajo symbols. Los brazos los escribes tú o tu agente, igual que cualquier otro código cuyo comportamiento el compilador no puede inferir.

Lo que glyph fix sí escribe, lo escribe sin adivinar, y cada regla que no puede resolver una respuesta imprime que se abstiene y el motivo en la misma salida que lo que aplicó. Dos campos a un carácter de una errata son dos, no uno, y lo dice en lugar de elegir.

La explicación del propio código, como datos

glyph --explain <CODE> --json responde con la explicación larga, la help de una línea, la URL de la documentación y un programa incorrecto del corpus negativo del compilador emparejado con el diagnóstico que este compilador genera para él. El diagnóstico se compila cuando lo pides, no se guarda, así que no puede desviarse de lo que dice el compilador de verdad.

glyph --explain E0200 --json 
{

  "title": "non-exhaustive match",
  "explanation": "A `match` over a tagged union must handle every variant.
    Unions are sealed (D9): adding a variant later forces every match to be
    updated, so a missing variant cannot silently fall through at runtime ...",
  "help": "Add an arm for each missing variant.",
  "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200",
  "counter_example": {
    "name": "alias_of_local_union_not_exhaustive",
    "expected_error": "E0200",
    "files": [ { "path": "alias_of_local_union_not_exhaustive.glyph",
                 "source": "module main\n\ntype Shape =\n  | Circle\n ..." } ],
    "diagnostic": { "code": "E0200",
                    "message": "non-exhaustive match on `Shape`: missing variants `Tri`",
                    "cause": "alias_of_local_union_not_exhaustive::Shape",
                    "related": ["Circle", "Square", "Tri"],
                    "missing_variants": ["Tri"] },
    "corrected": null,
    "corrected_absent": "`tests/negative/` pairs no repaired program with a case:
      an entry is a wrong program and the code it draws. A fix invented here would
      compile nowhere and be checked by nothing."

}

Un código que el corpus no cubre vuelve con counter_example: null y una frase que dice que el corpus no tiene ningún caso para él, en lugar de un ejemplo inventado. El corpus afirma lo que cubre y nada sobre el resto.

glyph --explain entrega un caso por código. El corpus entero también se puede leer: glyph llms --negative E0200 imprime cada programa incorrecto que genera el código, cada uno compilado cuando lo pides, y cuando un segundo corpus empareja un programa que tsc --strict acepta con el Glyph que lo rechaza, vuelve a su lado. Sin código, lista 102 casos sobre 46 de los 70 códigos y nombra los 24 que no tienen ninguno, así que la cobertura se declara en lugar de deducirse de lo que vuelve. Eso y el resto de lo que el compilador publica sobre sí mismo está en su propia página.

Dónde está

Disponible hoy

Cada diagnóstico lleva expected, actual, cause, alternatives (con alternatives_kind indicando si lista fields, members, variants, literals o exports, fijado donde se genera el error), related, module, file y explain, rellenados a partir del error que generó el compilador en lugar de recalculados, y cada uno es un null explícito cuando el compilador no tiene ese dato. file es una ruta relativa a la raíz de resolución, y el informe nombra esa raíz en project_root, así que se puede abrir. glyph check --agent añade constraints y symbols a cada diagnóstico. glyph fix aplica tres reglas (E0106, E0210, E0220) y declara cada abstención con su motivo, incluido cada E0200, que informa y nunca escribe. glyph --explain <CODE> --json devuelve la explicación con un contraejemplo compilado, y glyph llms --negative <CODE> devuelve todo el corpus de programas incorrectos que lo generan.

Dónde se detiene

cause en E0211 es null: el símbolo culpable en un argumento de llamada es un parámetro, y module::fn.param no es algo que el vocabulario de identidades sepa escribir, así que el null es deliberado y no un descuido. corrected en un contraejemplo siempre es null, porque el corpus negativo no empareja ningún programa reparado con un caso, y 24 de los 70 códigos no tienen ningún caso. glyph fix escribe tres reglas y nada más, y no escribe ningún brazo para un match no exhaustivo: esos quedan para ti o tu agente, con los casos y sus patrones en el diagnóstico. Todo aquello de lo que se abstiene, lo dice en voz alta.
