¿Cómo es la experiencia con el editor, la depuración y los errores?

glyph lsp habla el Language Server Protocol por stdio, así que cualquier editor con un cliente LSP tiene diagnósticos, tipos al pasar el ratón, ir a la definición, autocompletado y formateo al guardar. Hay una extensión de VS Code en el repositorio; todavía no está en el Marketplace, así que la compilas desde el código fuente. Cada error lleva un código estable, el arreglo y el motivo.

Por qué importa

Editar en un lenguaje que tu editor no entiende se siente como un paso atrás, y al principio era una queja justa. Ya no lo es: tu editor te da las comodidades modernas, y los errores están escritos para enseñar, no solo para rechazar.

¿Es un LSP de verdad, o solo un plugin de VS Code?

De verdad. El compilador incluye un servidor de lenguaje que lanzas como glyph lsp, que habla el Language Server Protocol por stdio (el transporte JSON-RPC estándar que entiende cualquier cliente LSP).

La extensión de VS Code incluida es un cliente ligero a su alrededor, pero nada es específico de VS Code: apunta cualquier editor con soporte LSP, Neovim, Helix, Zed, Emacs (eglot), a glyph lsp y se comporta igual.

Es el mismo binario que ya instalaste (npx @glyphlang/glyph lsp), así que no hay un servidor aparte que descargar.

Lo que implementa el servidor

El servidor implementa lo que necesita un editor: diagnósticos en vivo con los códigos estables de abajo, tipos al pasar el ratón, ir a la definición (entre módulos a través de un import con nombre; a través de un namespace, ui.Button todavía no responde nada), autocompletado, símbolos del documento y del workspace para el esquema y la búsqueda de símbolos, buscar referencias en todo el workspace, renombrar y formatear con el formato canónico de glyph fmt para el formateo al guardar.

El renombrado es completo: renombrar una declaración de nivel de módulo edita su definición, cada referencia y el binding de import de cada módulo que la importa en todo el workspace, y comprueba el nombre nuevo (un identificador válido, no una palabra clave) antes de tocar nada.

Dos límites que conviene conocer: el índice entre archivos se reconstruye en cada petición en lugar de guardarse en caché (bien para un proyecto normal, merecerá la pena acelerarlo más adelante), y un archivo que en ese momento no se puede parsear se salta, así que un renombrado no llegará a las referencias dentro de un archivo que esté roto.

Mensajes de error

Ajustamos los mensajes justo donde más tropiezan los agentes y quienes empiezan: escribir if ahora te remite a match en lugar de dar un “token inesperado” genérico, y un número de argumentos incorrecto, un match no exhaustivo o una variante mal escrita tienen cada uno su propio error con código y arreglable.

Los errores de tipos que solo puede detectar el back-end de TypeScript antes apuntaban al .ts generado. Ahora se trasladan de vuelta a tu .glyph (el mismo indicador de ariadne, el mismo código estable), así que un error de tsc se lee como uno nativo de Glyph.

Depuración

Depuras el TypeScript generado con las herramientas que ya usas, como el inspector de Node, las devtools del navegador o el depurador de JS/TS de tu IDE.

Cada build incluye un source map v3 estándar junto a cada .ts (con el código fuente de Glyph incrustado), así que un depurador o un bundler que encadena mapas te lleva de vuelta a los números de línea de tu .glyph.

Una cosa que todavía no cubre: la traza de un fallo del propio glyph run sigue mostrando líneas de .ts, porque tsx no encadena el mapa a través de su transformación. Reasignar esa traza es lo siguiente.

Preguntar “¿esto compila?” sin ejecutarlo

glyph check path.glyph comprueba los tipos de un archivo, o de un directorio entero, y termina. No escribe nada en tu árbol, algo que glyph run no podía prometer y que glyph build no hacía en absoluto (rechazaba todo lo que no fuera un directorio).

Detalles qué ejecuta, y los flags

Ejecuta el mismo pipeline que un build, incluido tsc --strict sobre el TypeScript generado, en un directorio temporal que borra al terminar. --no-tsc se detiene después de las etapas de Glyph cuando quieres la respuesta rápida; --json le da a un agente la misma forma de diagnóstico que glyph build --json. Un archivo se comprueba en el contexto de su propio directorio, así que un archivo hermano roto sigue haciendo fallar la comprobación. Tus tests @example y @doc @run también se ejecutan aquí, la misma comprobación que usa glyph build, así que un check no puede dar por limpio un árbol con el que un build fallaría; --no-test se los salta cuando quieres una respuesta que no ejecute nada.

La transcripción tampoco te engaña

Ahora el resumen se imprime después de cada etapa que puede poner el build en rojo, así que un build en rojo nunca muestra una línea en verde.

Historia el resumen que llegaba demasiado pronto

Un build fallido antes empezaba con “no diagnostics” y luego imprimía debajo los errores de tsc, porque el resumen de las etapas de Glyph se escribía antes de que se ejecutara la etapa de TypeScript.

En esa misma pasada, glyph run app.glyph --min -12.50 empezó a funcionar: un guion inicial hacía que clap rechazara el argumento antes de que tu main llegara a verlo.

Los flags propios de glyph siguen asociados a glyph, así que pon -- delante de un flag del programa que choque con uno de ellos.

Y para el agente del ciclo

glyph build --json emite cada diagnóstico como JSON estructurado: un código estable, severidad, mensaje, archivo y rango de línea/columna empezando en 1, además de la ayuda y la nota, incluidos los errores de tsc trasladados a tu código Glyph. Un agente los lee y actúa sobre ellos directamente en lugar de rascar texto de la terminal.

glyph mcp para agentes interactivos

Para los agentes interactivos hay más que diagnósticos por lotes: glyph mcp ejecuta un servidor de Model Context Protocol por stdio (el mismo binario, el mismo análisis que usa el editor), que expone las consultas del servidor de lenguaje como herramientas MCP. Un agente puede pedir los diagnósticos de un archivo, el tipo en una posición, dónde está definido un nombre (siguiendo los imports), cada referencia a un símbolo en todo el proyecto o una búsqueda de símbolos, sin ejecutar un build completo ni leer todos los archivos.

Es un adaptador ligero sobre la misma capa de análisis pura, no una segunda implementación, así que no puede divergir de lo que ven el compilador y el editor.

No todo es un error que bloquea

Glyph tiene un nivel de avisos que señala lo que sobra sin hacer fallar el build: un import sin usar (E0106), un let sin usar (E0107, salvo los nombres que empiezan por _) y código inalcanzable después de un return/break/continue (E0108).

E0106E0107E0108

Mantienen honesto un módulo: un import muerto es justo el tipo de ruido que perjudica la buscabilidad y hace que quien lee busque una dependencia que el código no tiene de verdad. Los avisos aparecen en la misma salida renderizada y en --json, marcados por severidad, y aun así se genera TypeScript.

Dónde está

Disponible hoy

  • Un servidor de lenguaje para cualquier editor, que responde a través de la frontera entre módulosdesde la 0.1.124
    Detalles

    Un servidor de lenguaje (glyph lsp por stdio, cualquier editor; extensión de VS Code incluida) con resaltado, diagnósticos, hover, ir a la definición, autocompletado, símbolos, buscar referencias y renombrar en todo el workspace, y formateo al guardar, que responde a través de la frontera entre módulos desde la 0.1.124: el servidor mantiene una base de datos por proyecto con tus buffers abiertos superpuestos a los archivos del disco, así que pasar el ratón sobre una función importada o un campo de un record importado da la misma respuesta que glyph query hover, una edición sin guardar en un archivo se ve desde otro, y una pulsación de tecla cuesta entre un uno y un nueve por ciento más que con un solo archivo;

  • Un servidor de Model Context Protocol glyph mcp con once herramientas
    Detalles

    un servidor de Model Context Protocol glyph mcp con once herramientas, las consultas del editor más glyph_symbol, glyph_impact, glyph_assignable, glyph_dependencies y glyph_exports, cada una con un verbo de glyph query que imprime el mismo JSON para un agente sin cliente MCP;

  • Códigos de error estables, glyph --explain, errores del back-end tsc trasladados al código .glyph, un nivel de avisos (import o binding sin usar, código inalcanzable) y diagnósticos estructurados con --json.
  • glyph check [path] comprueba los tipos de un solo archivo o de un árbol sin ejecutarlo ni escribir salida.
  • glyph fmt --check controla el formato en CI: no escribe nada y sale con un código distinto de cero cuando un archivo no está ya en el único formato canónico.

En camino

  • Guardar en caché el índice entre archivos en lugar de reconstruirlo en cada petición (una mejora de velocidad en árboles grandes).
  • Reasignar la traza de los fallos del propio glyph run, ya que tsx no encadena el mapa generado a través de su transformación, así que esa traza sigue nombrando el .ts generado en lugar de tu .glyph.
