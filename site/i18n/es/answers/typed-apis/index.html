¿Tengo que escribir a mano un validador para cada API?

No. En Glyph un tipo es su propio validador. Declara un type y el compilador genera a su lado un descriptor de runtime, así que el cuerpo de una petición o una respuesta en el que no confías se valida con una sola llamada, sin un schema de zod aparte que escribir y mantener sincronizado.

Por qué importa

En la mayoría de los stacks de TypeScript cada payload se describe dos veces: una como type para el compilador, y otra como un validador escrito a mano para que el valor tenga de verdad esa forma en tiempo de ejecución.

Los dos se desfasan, y es justo por ese desfase por donde se cuelan los datos incorrectos. Glyph los reduce a una sola declaración: el tipo produce el validador, así que no pueden discrepar.

Míralo

Declara el DTO una vez. Su descriptor te da .parse (valida un valor no fiable convirtiéndolo en el tipo) y .is (un type guard), sin nada más que escribir:

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}
lo que no has escrito 
// No zod schema:
const NewTask = z.object({
  title: z.string(),
  done: z.boolean(),
});
// No drift between the type and
// the validator, because there is
// only one declaration.

// A bad body, {"title": 123},
// takes the Err arm. Only a
// well-formed body reaches Ok.

También puedes sacar el valor en lugar de hacer el trabajo dentro del brazo.

Detalles cómo se mantiene el tipo, y la excepción de los genéricos

T.parse tiene el tipo Result<T, Array<Issue>> y un match cuyos brazos coinciden conserva su tipo, así que let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, } te da un NewTask para el resto de la función, con los nombres de campo comprobados por Glyph y no por tsc sobre el TypeScript generado. Eso llegó en la 0.1.45; antes, el valor perdía el tipo en cuanto salía del match. El parse de un tipo genérico es el único que todavía no lo hace, porque su descriptor recibe un checker de runtime por cada parámetro de tipo.

El resultado del parseo es un Result normal

En Glyph T.parse devuelve el mismo Result que devuelve cualquier función del lenguaje que puede fallar, así que lo devuelves tal cual, lo pasas por map_err para convertir los problemas de validación en tu propio tipo de error o lo propagas con ?.

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}

Detalles el coste en tiempo de ejecución de usar Result aquí

Un validador que te devuelve un valor con su propia forma privada solo sirve a medias, porque el resto de tu manejo de errores no puede tocarlo. Un resultado de parseo no tiene nada de especial.

El motivo de que antes no fuera así: un descriptor se genera junto a tu type, y generar el objeto desnudo evitaba que un módulo que declara un tipo dependiera de std/result en tiempo de ejecución. Ahora ese intercambio se hace al revés. Un módulo con un pub type lleva un import de std/result tanto si escribe Result como si no, y una llamada a parse reserva las closures de los combinadores que reserva cualquier Ok(...). A cambio, la frontera validada y el resto de tu manejo de errores son la misma API.

Componer los tuyos: el tipo de salida se deriva, no se da por bueno

El infer_output<Shape> de Glyph deriva el tipo de salida a partir de la forma, y tsc comprueba tu anotación contra él. Una forma que omite un campo del tipo que afirmas no compila:

Detalles la trampa de TypeScript, y el cast que sigue al return desde la 0.1.92

A veces quieres un combinador al estilo de zod: construir un validador componiendo otros más pequeños. La trampa en TypeScript es que el tipo de salida del combinador y la forma que le pasaste se separan. Escribes la forma, luego te repites en un segundo parámetro de tipo, y nada comprueba que coincidan.

El tipo derivado se mantiene sea cual sea la forma en que retorna el combinador. infer_output necesita un cast en la frontera de la función, porque el cuerpo construye un valor del que el sistema de tipos no puede demostrar que tenga el tipo derivado de la forma, y el compilador escribe ese cast por ti. Hasta la 0.1.91 iba pegado a un return <value> simple. Si ponías un match entre el return y el valor, o terminabas el cuerpo en r?, la misma función dejaba de compilar: un TS2322 sobre el TypeScript generado, para un Glyph que el compilador ya había aceptado. Desde la 0.1.92 el cast sigue al return y no a su forma de escribirlo, así que return match strict { ... } pasa la comprobación de tipos igual que la forma con un solo return del mismo cuerpo.

El resto de la frontera no fiable

El descriptor es el mismo que hace seguro json.parse<T>: dale un string JSON y lo parsea y lo valida en un solo paso.

EntradaLlamadaDevuelve
Un string JSONjson.parse<T>(text)Result<T, Array<Issue>>
Un cuerpo ya decodificadoT.parse(value)Result<T, Array<Issue>>
Una cabeceraheader(req, name)Option<string>
Un parámetro de la queryquery_param(req, name)Option<string>
Detalles cuerpos de petición, cabeceras y parámetros de la query

El cuerpo de una petición llega ya decodificado como unknown, así que ahí usas T.parse(value): la misma garantía, sin cast.

El resto de la frontera no fiable se tipa igual: header(req, name) y query_param(req, name) devuelven Option<string>, así que una cabecera o un parámetro de la query que falta es None y el match te obliga a manejarlo. Omite el brazo None y no compila. Una entrada ausente no se puede leer como si estuviera.

¿Un mapa con claves de un enum comprueba sus claves?

Sí, desde la 0.1.148. Un Record<Tier, int> con type Tier = "free" | "pro" solo parsea un objeto cuyas claves sean exactamente free y pro: una clave de más y una que falta son ambas un Err, que es también lo que dice tsc del mismo objeto escrito como literal.

Tipo de la claveQué comprueba parse en cada clave

Un tipo refinado con whereel predicado
intla forma simple de escribir un número entero; "01" y "1.5" fallan
stringnada nuevo
Detalles claves refinadas e int, y lo que todavía queda para tsc

Un tipo de clave refinado con where ejecuta su predicado sobre cada clave, y una clave int tiene que ser la forma simple de escribir un número entero, así que "01" y "1.5" se rechazan. Un Record<string, V> se comprueba exactamente igual que antes. El checker propio de Glyph sigue dejando a tsc las claves de un valor que escribes en el código, y un record genérico cuyas claves son su propio parámetro de tipo se rechaza salvo que ese parámetro sea string.

Si parseo una fecha, ¿obtengo una fecha de verdad?

Sí, y lo interesante es lo que obtienes con una entrada que no lo es. time.parse_iso devuelve Option<number>, y es None para todo lo que no sea ISO-8601.

aceptado 
"2026-01-03"              // UTC midnight
"2026-07-25T18:33:08.000Z"
"2026-03-15T09:30:00-05:00"
"2028-02-29"              // a real leap day
None, en todos los casos 
"January 5 2026"   // not ISO
"2026-1-3"         // not padded
"2026-13-01"       // no month 13
"2026-02-31"       // no such day
"2026-02-29"       // not a leap year
"2026-01-03T10:00" // no offset

El último es el que sorprende a la gente, y es justo de lo que se trata. Una fecha y hora sin Z ni desplazamiento +HH:MM es hora local según la gramática de ECMAScript, así que aceptarla significaría que el mismo string nombra un día distinto del calendario según la máquina que ejecute el programa.

Detalles qué hace Date.parse en su lugar, y por qué UTC

Es una garantía más fuerte que la de Date.parse de JavaScript, que acepta texto libre ("January 5 2026"), lee una fecha sin ceros a la izquierda como "2026-1-3" en la zona horaria en la que se esté ejecutando el proceso, y da por bueno un día imposible pasándolo al siguiente mes: "2026-02-31" se convierte en el 3 de marzo, y recibes un número sin ninguna indicación de que haya pasado algo.

Los accesores de calendario de Glyph (time.year, time.month, time.day) son UTC y lo dicen, y un validador que importara en silencio la zona horaria de la máquina haría que mintieran. Así que el string se rechaza, y decides tú qué quería decir.

La comprobación pasó a la primitiva

Cuando una aplicación escribe una comprobación de corrección alrededor de una primitiva de la librería estándar, esa comprobación pertenece a la primitiva. Esto es lo que borró la app:

antes: la app protege la librería estándar 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
después: la primitiva se encarga 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

El import std/regex se fue con ella. El mismo libro de cuentas, las mismas filas rechazadas, el mismo informe byte a byte.

Cada fila del libro de cuentas lleva una fecha, y apuntar una fila en el mes equivocado es el bug que importa, así que la app no se fiaba del antiguo parse_iso: primero comprobaba la forma con una regex y luego convertía la marca de tiempo de vuelta a texto para detectar un día desbordado.

Ni siquiera tienes que escribir los tipos

Si la forma ya existe en una especificación OpenAPI o en un archivo de declaraciones de TypeScript, genera los tipos de Glyph a partir de ella: declaraciones type reales, commiteadas y que se pueden buscar con grep, cada una con su descriptor, no un fantasma inferido:

a partir de una especificación OpenAPI / JSON Schema 
glyph gen openapi petstore.yaml \
  --out src/
a partir de un paquete instalado, por su nombre 
glyph gen dts api-types \
  --out src/types

Un tipo de transporte se convierte en una frontera validada, sin nada escrito a mano:

webhook.glyph 
import types/api_types { Customer }

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),
  Err(issues) => reject(issues),
}

La generación es fiel a lo que viaja por la red: lo que la especificación dice de un valor es lo que comprueba parse.

Detalles qué se materializa hoy, regeneración, tipos genéricos

Apunta glyph gen dts a un archivo .d.ts o, como arriba, a un paquete de npm instalado por su nombre: resuelve la entrada de declaraciones del propio paquete en node_modules y escribe tipos commiteados que importas.

Qué se materializa hoy: gen dts lee las declaraciones interface y type que exporta un paquete, incluidas las que están dentro de un árbol declare namespace (las referencias cruzadas sin cualificar se resuelven a través del ámbito) y las de archivos hermanos que reexporta un barrel index (se recorre el .d.ts de entrada más cada .d.ts importado de forma relativa). Un genérico se mantiene como tal: interface Page<T> se materializa como type Page<T> y recibe un descriptor que valida cada elemento como su argumento de tipo, no solo que exista. Las reexportaciones con alias y con export * as se resuelven mediante un mapa de bindings por archivo. El único caso que no puede hacer seguro, un nombre de tipo que coincide en dos archivos alcanzables, lo marca con una nota en lugar de enlazar en silencio la forma equivocada. Para lo que el materializador no alcanza, escribe a mano las formas que cruzan la frontera, o usa la vía de escape extern_ts.

La regeneración es idempotente, así que un cambio en la especificación es un diff limpio y revisable. La generación es fiel a lo que viaja por la red: un enum de strings se materializa como una unión de literales de string ("free" | "pro"), así que parse comprueba la pertenencia, no solo que el valor sea un string, y un match sobre ella es exhaustivo sin else. Un campo integer se convierte en int, así que un 3.5 recibido falla en parse donde un number normal pasaría. Donde una construcción no tiene una forma exacta en Glyph (una unión no discriminada), se estrecha e imprime una nota en lugar de generar un validador que rechazaría datos reales. Los records generados también llevan @open, así que parse tolera un campo que la API añada más adelante y sigue validando cada campo que declara; un schema que fija additionalProperties: false sigue siendo estricto. En Glyph los records son estrictos por defecto, y esta es la misma marca, buscable con grep, en el sitio de la declaración que usaría un record escrito a mano, así que no cambia nada de lo que significa un record.

Los tipos genéricos también se validan. Un Paginated<T> recibe un descriptor cuyo parse acepta el argumento de tipo: Paginated.parse<User>(body) comprueba cada entrada de items como un User, no solo que exista, y match v { is Paginated<User> => ... } estrecha de la misma forma. Esto se mantiene entre módulos: define Paginated<T> en un archivo, impórtalo con import en otro, y tanto Paginated.parse<User>(body) como is Paginated<User> siguen comprobando ahí cada elemento como un User. El compilador construye la comprobación de cada elemento a partir del argumento de tipo en el sitio de la llamada, así que el archivo en el que vive el tipo genérico no cambia nada de lo que se valida.

Dónde se detiene: los descriptores cubren las formas de las que están hechos la mayoría de los payloads: objetos, primitivos, arrays, referencias, campos opcionales y nullables, y ahora tipos genéricos en una instanciación concreta. Un tipo que Glyph no generó (un paquete externo o un .d.ts que solo importas) se comprueba en tiempo de compilación pero no lleva descriptor hasta que lo materializas, que ahora es un solo comando contra el paquete instalado (glyph gen dts <package>, para las interfaces y los alias de tipo de nivel superior que exporta). Esa frontera es deliberada: un tipo que Glyph no generó no puede prometer validación en tiempo de ejecución, así que lo activas paquete a paquete y el resultado queda commiteado y buscable con grep, no conjurado en cada build.

La base de datos también es una frontera

Una fila leída de una base de datos es tan poco fiable como el cuerpo de una petición. El mismo .parse que usas con el cuerpo de una petición valida una fila.

tasks.glyph 
type Task    = { id: int, title: string, done: bool }
type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.
match TaskRow.parse(row) {
  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}
el bug que esto elimina 
// TS, better-sqlite3 / node:sqlite:
const row = stmt.get(id) as Task;
// `row.done` is really 0 or 1, a number.
// Nothing complains. Then:
if (row.done === true) { ... }   // never runs

// The row was `unknown`; the cast invented
// a type. Glyph makes you validate the row
// into TaskRow, and the int-to-bool step is
// a line of code, not a silent lie.
Detalles std/sqlite, y el booleano que es 0 o 1

Una fila leída de una base de datos es tan poco fiable como el cuerpo de una petición: el schema de la base de datos y la idea que tiene tu código de la fila pueden no coincidir, y un cast (row as Task) lo tapa. std/sqlite, el módulo de base de datos sobre el SQLite integrado de Node, va en esa dirección. Una consulta devuelve Array<Record<string, unknown>>, así que no hay forma de tratar una fila como un Task sin validarla antes.

Esto detecta un bug que se publica constantemente. SQLite no tiene tipo booleano, así que una columna done vuelve como el entero 0 o 1. Haz un cast de la fila a un record con un campo bool y task.done === true nunca es verdadero, sin avisar. Sin validadores escritos a mano en ninguna parte.

Un webhook firmado también es una frontera

Verificar la firma de un webhook necesita los bytes exactos que firmó el emisor, no una copia vuelta a serializar (volver a convertir en string un cuerpo parseado cambia los espacios y el orden de las claves, así que el HMAC nunca coincidiría). http.raw(req) te da esos bytes, así que la comprobación se queda en Glyph: 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
Detalles bytes en bruto para la firma, cuerpo parseado para la forma

req.body sigue siendo el valor parseado para comprobar la forma; raw es el payload sin alterar sobre el que se calcula la firma. Un receptor que verifica una firma y valida el cuerpo no necesita TypeScript escrito a mano.

Un tipo puede validar sus invariantes, no solo su forma

Una comprobación de forma te dice que un campo es un número. No te dice que la cantidad no sea negativa ni que la valoración esté entre 1 y 5. Un refinamiento where pone ese invariante en el tipo, y el descriptor lo hace cumplir en la frontera:

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
lo que no estás escribiendo 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.

Dónde está

Disponible hoy 10

Descriptores

  • Cada record y cada unión etiquetada declarados llevan un descriptor de runtime (.parse, .is, .schema), incluidos los records genéricosuna unión etiquetada genérica no

  • json.parse<T> valida JSON
  • infer_output<Shape> deriva el tipo de salida de un combinador a partir de su forma para que los dos no puedan desfasarse

Generación

  • glyph gen openapi / glyph gen dts generan tipos commiteados con descriptor a partir de una especificación, un .d.ts o un paquete instalado por su nombre

Fronteras

  • std/sqlite devuelve las filas como unknown, así que la base de datos es una frontera validada como cualquier otra
  • Un receptor de webhooks firmados se queda entero en Glyph
    Detalles

  • La entrada no fiable no puede llegar a un destino SQL o de shell sin sanitize
