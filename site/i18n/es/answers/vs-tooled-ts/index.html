05 · La comparación

¿Por qué no simplemente TypeScript estricto + zod + eslint + ts-pattern?

Porque cada una de esas garantías es opcional, y un agente puede esquivar cualquiera de ellas en una línea. El rigor de Glyph no es un archivo de configuración que el agente pueda editar. Es el lenguaje. El punto donde se aplica pasa de "¿nos acordamos de pasar el lint a este archivo?" a "¿compila?".

Una configuración de TypeScript bien hecha te lleva lejos, y si tu equipo lo ejecuta todo en CI ya has cerrado la mayoría de los huecos a los que apunta Glyph. Es la alternativa que hay que tomarse en serio, así que esta es la correspondencia:

01 Lo obligatorio gana a lo opcional

Cada una de esas vías de escape es una configuración que el agente puede editar. Glyph no tiene ninguna vía así a mano: no hay as, no hay pragma para ignorar, no hay forma de sacar un valor tipado de unknown sin una comprobación que el compilador pueda ver.

TypeScript: las vías de escape existen handler.ts 
const user = body as unknown as User;
// @ts-ignore
doThing(user.mispelled);
// eslint-disable-next-line
return anything as any;
Glyph: nada que desactivar handler.glyph 
return match User.parse(body) {
  Ok(user) => use(user),
  Err(_) => fallback(),
}
// no `as`, no ignore pragma,
// no lint to switch off.

Un rigor que el agente no puede desactivar con configuración está en un punto de aplicación distinto al de uno que sí puede. Glyph está construido sobre esa diferencia.

Detalles lo que un agente puede colar por delante de eslint

Tu configuración de eslint solo protege el código que el agente hace pasar por ella, y el agente puede escribir as unknown as User, @ts-ignore, // eslint-disable-next-line, o simplemente olvidar el .exhaustive(), y sigue compilando y se mergea.

02 El tipo es el validador: sin un segundo artefacto

En Glyph el tipo es el validador: declarar type User = {...} genera User.parse junto a él. Un solo artefacto, nada que sincronizar, nada que olvidar.

  • zod: primero el schemazod invierte tu fuente de verdad: escribes el schema, derivas el tipo de él, y luego mantienes sincronizados a mano el tipo, el schema y cualquier serializador.
  • Por dónde entra el desajusteMantenerlos alineados es justo donde un agente introduce desajustes: renombra un campo en el tipo y no en el schema, y los dos siguen compilando.

03 Mutación que se puede buscar con grep

En Glyph el estado compartido vive en un store y cada cambio es un .set(/.update( literal; grep 'mut ' encuentra cada mutación local. TypeScript tal cual no tiene nada equivalente.

Detalles dónde se puede esconder una escritura en TypeScript

En TypeScript un cambio de estado puede esconderse detrás de =, .push(), Object.assign, un setter o un spread. No hay un único token que buscar, y ninguna regla de lint lo arregla del todo.

El diff de los modos de fallo

Misma tarea: un agente añade una variante a una unión y se olvida de manejarla en uno de tres sitios:

TS con herramientas 
// ts-pattern .exhaustive() catches it,
// IF every site used ts-pattern and
// nobody wrote a default: case or a
// switch that only logs. Those
// compile green and skip the new case.
Glyph 
[E0200] non-exhaustive match on
`Feed`: missing variant `Archived`
// every unhandled match, everywhere,
// fails the build. No opt-in, no
// escape, no forgotten default.

Dónde TypeScript con herramientas sigue yendo por delante

Cuatro sitios donde hoy va por delante de Glyph:

  • Validación más rica.Los descriptores de Glyph son estrictos por defecto (rechazan claves no declaradas), y un refinamiento where pone un predicado sobre un primitivo (type Email = string where value.includes("@")), que el descriptor ejecuta en cada frontera a la que llega el tipo. zod sigue yendo por delante en dos cosas: trae comprobaciones ya hechas como .email() y .url() que en Glyph escribes tú, y refina objetos enteros, mientras que un where sobre un record (lo <= hi entre dos campos) hoy da E0300.
  • Matching más profundo.Los guards y los patrones estructurales profundos de ts-pattern van más allá de lo que expresa el match de Glyph.
  • La "ausencia demostrable" termina en la frontera con .ts.Las garantías de Glyph valen para el código escrito en Glyph; una excepción lanzada desde una dependencia de npm sigue saltándose Result, y un tipo importado de un .d.ts no lleva descriptor en tiempo de ejecución.
  • Ecosistema y contratación.Las herramientas, la comunidad y la cantera de gente de TypeScript son mucho mayores, con años de uso en producción detrás. Glyph es una versión preliminar.

Si tienes TypeScript con todas las herramientas bien conectado y tus agentes se quedan dentro de él, ya tienes la mayor parte de esto. El argumento de Glyph es que "se quedan dentro" es la frase que lo sostiene todo, y es la frase que un agente rompe. Que no sea opcional, la validación con un solo artefacto y la mutación que se puede buscar con grep son lo que no consigues añadiendo más herramientas opcionales.

    Detalles

    Sin any/as, match exhaustivo (E0200/E0218), aviso por un Result descartado (E0217), validadores generados a partir de los tipos y mutación que se puede buscar con grep: todo obligatorio, nada que sea una regla de eslint que puedas desactivar.
