17 · Servir la web

¿Puedo servir una página web, o solo una API JSON?

Una página web. std/http establece cabeceras de respuesta, así que una página text/html, una redirección 302, una cabecera de caché y el envío de un formulario HTML son Glyph normal. Sin Express, sin un shim de TypeScript escrito a mano.

Por qué importa

Hasta la 0.1.46 una respuesta era { status, body } y el servidor elegía el content type según la forma del cuerpo: un string era text/plain y cualquier otra cosa era JSON. Eso sirve para una API y no sirve para nada que renderice un navegador. La salida era escribir tu propio servidor sobre node:http en un archivo .ts escrito a mano, lo que deja todo el camino de la petición fuera del type checker. Dos constructores que faltaban costaban toda una frontera de la aplicación.

Míralo

Este es el router de examples/apps/shortlink/main.glyph, un acortador de URLs que viene en el repositorio. Un formulario HTML crea un código, un POST responde con una redirección para que recargar el navegador nunca vuelva a enviarlo, y seguir un código es un 302 al destino:

shortlink.glyph: una página HTML, el envío de un formulario y el 302 
fn handle_home(req: Request) -> Response {
  return match req.method {
    "GET" => html(200, home_page(links.get(), query_param(req, "error"))),
    "POST" => {
      let fields = form(req)
      match create_link(form_field(fields, "url"), form_field(fields, "alias")) {
        Ok(link) => redirect(303, "/${link.code}+"),
        Err(message) => redirect(303, "/?error=${url_encode(message)}"),
      }
    },
    else => html(405, page("405", "<h1>405</h1>")),
  }
}

fn route(req: Request) -> Result<Response, string> {
  return match segments(req) {
    [] => Ok(handle_home(req)),
    [one] => match stats_code(percent_decode(one)) {
      Some(code) => Ok(handle_stats(code)),
      None => Ok(handle_code(percent_decode(one))),
    },
    else => Ok(html(404, not_found_page(path(req)))),
  }
}

async fn main(argv: Array<string>) -> number {
  let outcome = await serve(8138, route)
  return match outcome { Ok(_) => 0, Err(_) => 1, }
}

La misma app estaba en el repositorio una versión antes con 615 líneas, 121 de ellas un servidor node:http escrito a mano en un archivo .ts a su lado, porque un Location y un cuerpo text/html no se podían escribir. Ahora tiene 494 líneas y no importa nada fuera de std. Un handler devuelve Result<Response, string>, así que un 404 es un Ok normal y un Err queda para lo que la app no puede responder, que el servidor convierte en un 500. serve sigue pendiente mientras escucha, así que nada tiene que mantener vivo el proceso a mano, y un bind fallido vuelve como un valor.

Response lleva un headers: Record<string, string> obligatorio. Obligatorio, no opcional: cada constructor lo rellena, así que leer resp.headers nunca necesita comprobar si falta, y el canal no se puede olvidar. with_header(resp, "cache-control", "no-store") devuelve una respuesta nueva en lugar de modificar una existente, porque Glyph no permite modificar campos de records. El type checker sabe que los tres constructores devuelven un Response, así que un handler cuyo tipo de retorno declarado dice Result<Response, string> se comprueba en Glyph, no con tsc sobre la salida generada.

Dos detalles que de otro modo harías mal a mano. Cualquier carácter que Node se niega a escribir en una cabecera se elimina del valor al salir, así que un location construido a partir de un parámetro de la query no puede inyectar una segunda cabecera ni una segunda respuesta, y un emoji en una URL acortada no puede tumbar el servidor. Y form(req) decodifica + como espacio junto con los escapes de porcentaje, la pareja que suele olvidar el parseo de formularios hecho a mano; lee el cuerpo en bruto, así que req.body queda intacto para los handlers que lo parsean por su cuenta.

Dónde está

Disponible hoy

html, redirect, with_header, json, text y form; cabeceras de respuesta en la red, con el content type inferido solo cuando no has puesto uno; cabeceras de la petición, parámetros de la query, segmentos de la ruta y el cuerpo en bruto a la entrada; el cliente informa de las cabeceras de respuesta que recibió.

En camino

La codificación con porcentajes es el hueco que muestra el fragmento de arriba: form decodifica el cuerpo de un formulario, pero no hay encode_component para construir una URL, así que el acortador escribe el suyo. También faltan en el lado del cliente: un timeout, una política de redirecciones, head y la URL final a la que llevó una redirección. No hay servidor de archivos estáticos ni motor de plantillas, y no hay planes para ninguno de los dos.
