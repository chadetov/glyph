¿Puedo servir una página web, o solo una API JSON?

Una página web. std/http establece cabeceras de respuesta, así que una página text/html, una redirección 302, una cabecera de caché y el envío de un formulario HTML son Glyph normal. Sin Express, sin un shim de TypeScript escrito a mano.

Por qué importa

Hasta la 0.1.46 una respuesta era { status, body } y el servidor elegía el content type según la forma del cuerpo: un string era text/plain y cualquier otra cosa era JSON. Eso sirve para una API y no sirve para nada que renderice un navegador.

La salida era escribir tu propio servidor sobre node:http en un archivo .ts escrito a mano, lo que deja todo el camino de la petición fuera del type checker. Dos constructores que faltaban costaban toda una frontera de la aplicación.

Un handler devuelve un Result

Un handler devuelve Result<Response, string>, así que un 404 es un Ok normal y un Err queda para lo que la app no puede responder, que el servidor convierte en un 500.

serve sigue pendiente mientras escucha, así que nada tiene que mantener vivo el proceso a mano, y un bind fallido vuelve como un valor.

Cada respuesta lleva cabeceras

Response lleva un headers: Record<string, string> obligatorio. Obligatorio, no opcional: cada constructor lo rellena, así que leer resp.headers nunca necesita comprobar si falta, y el canal no se puede olvidar.

  • Una respuesta nueva, no una modificaciónwith_header(resp, "cache-control", "no-store") devuelve una respuesta nueva en lugar de modificar una existente, porque Glyph no permite modificar campos de records.
  • Comprobado en GlyphEl type checker sabe que los tres constructores devuelven un Response, así que un handler cuyo tipo de retorno declarado dice Result<Response, string> se comprueba en Glyph, no con tsc sobre la salida generada.

Dos detalles que de otro modo harías mal a mano

  • Valores de cabeceraCualquier carácter que Node se niega a escribir en una cabecera se elimina del valor al salir, así que un location construido a partir de un parámetro de la query no puede inyectar una segunda cabecera ni una segunda respuesta, y un emoji en una URL acortada no puede tumbar el servidor.
  • Cuerpos de formularioY form(req) decodifica + como espacio junto con los escapes de porcentaje, la pareja que suele olvidar el parseo de formularios hecho a mano; lee el cuerpo en bruto, así que req.body queda intacto para los handlers que lo parsean por su cuenta.

Dónde está

Disponible hoy

  • html, redirect, with_header, json, text y form
  • Cabeceras de respuesta en la red, con el content type inferido solo cuando no has puesto uno
  • Cabeceras de la petición, parámetros de la query, segmentos de la ruta y el cuerpo en bruto a la entrada
  • El cliente informa de las cabeceras de respuesta que recibió.

En camino

  • La codificación con porcentajes es el hueco que muestra el fragmento de arriba
    Detalles

    La codificación con porcentajes es el hueco que muestra el fragmento de arriba: form decodifica el cuerpo de un formulario, pero no hay encode_component para construir una URL, así que el acortador escribe el suyo.

  • También faltan en el lado del cliente: un timeout, una política de redirecciones, head y la URL final a la que llevó una redirección.
  • No hay servidor de archivos estáticos ni motor de plantillas, y no hay planes para ninguno de los dos.
