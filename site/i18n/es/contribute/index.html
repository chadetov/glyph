Contribuir

Cómo está hecho el compilador y cómo ayudar

El compilador es un workspace de Rust de doce crates en un único repositorio público, con licencia MIT o Apache-2.0. Hoy lo que más ayuda son los informes de bugs con una reproducción pequeña. Un cambio en el lenguaje empieza como un issue, porque cada regla se remonta a una decisión de diseño numerada.

El pipeline

glyph build hace el análisis léxico y sintáctico, resuelve nombres, comprueba tipos y genera TypeScript, y luego ejecuta tsc --strict sobre lo que ha escrito. Las etapas intermedias se ejecutan como consultas incrementales sobre salsa, así que una nueva comprobación reutiliza los resultados que una edición no invalidó.

un archivo .glyph, a través de los crates 
glyph-lexer → glyph-parser → glyph-resolver → glyph-typechecker → glyph-emit → tsc --strict
                (glyph-ast)        └──────── glyph-db (salsa) ────────┘
CrateQué hace
glyph-lexerTokens, palabras clave, saltos de línea significativos, template literals
glyph-astTipos del árbol sintáctico, con un span de código fuente en cada nodo
glyph-parserParser Pratt para cada decisión de la especificación, JSX incluido
glyph-resolverResolución de nombres, el grafo de módulos, comprobaciones de imports entre módulos, el preludio
glyph-dbEl pipeline de consultas de salsa y la invalidación entre archivos
glyph-typecheckerExhaustividad, ?, genéricos, owned, descriptores de runtime, el modelo de la librería estándar
glyph-emitEl generador de TypeScript, la generación de descriptores, source maps a nivel de expresión
glyph-formatterglyph fmt: un solo formato, conserva los comentarios, idempotente
glyph-lspEl servidor de lenguaje y el servidor MCP, que comparten una capa de análisis
glyph-cliEl binario glyph y todos sus subcomandos
glyph-wasmEl compilador en WebAssembly, que hace funcionar el playground
glyph-runtimeUn stub; los tests pasan por el emisor y tsx

glyph-compiler/README.md tiene las notas completas de los crates y el número actual de tests.

Compilar y probar

Rust 1.95 está fijado en rust-toolchain.toml. Algunos tests llaman a tsc y tsx, así que instálalos también. El CI ejecuta clippy con los warnings como errores, y ni cargo build ni cargo test lo ejecutan, así que ejecuta el script antes de hacer push.

desde un clon 
npm install -g tsx typescript
cd glyph-compiler
cargo build --release -p glyph-cli      # target/release/glyph
cargo test --workspace
cd .. && python3 scripts/check_clippy.py  # the exact clippy command CI runs

# after an intentional syntax-tree change
INSTA_UPDATE=always cargo test -p glyph-parser --test snapshots

Un diagnóstico nuevo viene con un programa en tests/negative/ que tiene que fallar con ese código. Una afirmación de que Glyph detecta algo que TypeScript no detecta va en catches/, donde una comprobación ejecuta las dos mitades.

Qué está planificado y qué está roto

docs/roadmap/releases.md es el roadmap de versiones: qué hizo cada versión publicada y para qué son las siguientes. docs/dogfooding-gaps.md es el registro de gaps, cada limitación encontrada al construir apps reales, numerada (G más un número) y con una marca de estado. Un gap abierto con una reproducción es un buen sitio para empezar.

Issues y pull requests

Las correcciones del toolchain, diagnósticos, documentación y ejemplos pueden ir directamente a un pull request. Un cambio de sintaxis o semántica empieza con un issue, y los más grandes pasan por el proceso de RFC en docs/rfcs/; un PR que relaja una regla "para ayudar" probablemente se rechazará, porque la restricción es justo lo que se busca. Limita cada pull request a un gap, normalmente de uno a tres commits, y firma cada commit (git commit -s). main está protegida y los merges solo se hacen con rebase. CONTRIBUTING.md tiene las reglas completas, y los issues con la etiqueta good first issue están acotados para un primer cambio.
