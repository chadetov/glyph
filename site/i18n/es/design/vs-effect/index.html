Diseño · Comparación

Glyph y Effect

Los dos buscan un TypeScript en el que personas y agentes puedan confiar. Effect es una biblioteca: sigues escribiendo TypeScript y obtienes errores tipados, dependencias controladas y una caja de herramientas grande. Glyph es un lenguaje que compila a TypeScript, así que puede rechazar lo que TypeScript permite, incluidos los casts que deshacen las garantías de una biblioteca. Effect es mucho más maduro.

Cómo se describe Effect

La página de inicio de Effect abre con "Reliable TypeScript for the AI era" y dice que sus "declarative patterns and strong type system make it easier for LLMs to generate correct, production-ready code" (effect.website). Su documentación lo llama "an ecosystem of tools that help you build better applications and libraries", construido alrededor de un tipo Effect<Success, Error, Requirements> que registra qué devuelve un cálculo, cómo puede fallar y qué necesita (Why Effect). Pide TypeScript 5.4 o posterior con strict activado (Installation). Estas citas se leyeron el 2026-11-19.

La diferencia que se deriva de biblioteca frente a lenguaje

Los tipos de Effect los comprueba tsc, así que todo lo que tsc permite sigue estando permitido a su lado. Esto compila con tsc --strict usando effect 4.1.4 y TypeScript 6. El cast quita NotFound del canal de error, y el programa informa de un fallo en un efecto cuyo tipo dice que no puede fallar.

eff.ts: tsc --strict sale con 0; al ejecutarlo imprime "Failure undefined" 
import { Effect } from "effect"

class NotFound {
  readonly _tag = "NotFound"
}

const find = (id: string): Effect.Effect<number, NotFound> =>
  id === "1" ? Effect.succeed(1) : Effect.fail(new NotFound())

// The error channel says NotFound can happen. A cast erases it.
const quiet = find("2") as unknown as Effect.Effect<number, never>

// And a parsed body still takes any type you name.
type User = { email: string }
const user = JSON.parse("{}") as User

console.log(Effect.runSyncExit(quiet)._tag, user.email)

La misma función en Glyph devuelve un Result, y no hay ningún cast que escribir. El segundo módulo se rechaza antes de generar nada de TypeScript.

find.glyph: compila, pasa tsc --strict 
module find

pub type NotFound = { id: string }

pub fn find(id: string) -> Result<number, NotFound> {
  return match id == "1" {
    true => Ok(1),
    false => Err({ id: id }),
  }
}
añadir un cast: rechazado 
module find

pub type NotFound = { id: string }

pub fn find(id: string) -> Result<number, NotFound> {
  return match id == "1" {
    true => Ok(1),
    false => Err({ id: id }),
  }
}

pub fn quiet() -> number {
  let n = find("2") as number
  return n
}

La ayuda de E0013 dice: "Glyph has no as cast ... to turn an unknown into a type, validate it with T.parse(v) or narrow it with match and is." Un equipo puede acercarse a esto en un código con Effect usando reglas de lint, y esa comparación explica por qué una regla que alguien puede desactivar es una garantía distinta.

Lo que Glyph hace y una biblioteca no puede

Un lenguaje decide qué se puede escribir. Glyph no tiene any, ni casts, ni aserciones de no nulo, ni comentarios que silencien un error, y todo match sobre una unión tiene que cubrir todos los casos. Los records y las uniones llevan una comprobación en tiempo de ejecución generada a partir de la declaración, así que json.parse<User>(body) valida. El Schema de Effect también deriva un tipo de una sola descripción (Schema.Schema.Type<typeof Person> en su introducción), así que ahí tampoco se desfasan el tipo y el validador; la diferencia es que nada en TypeScript obliga a un código a usarlo. El compilador además responde preguntas sobre un programa para un agente, como qué va a romper un cambio, por MCP o en la línea de comandos.

Esta página no ha probado a usar Effect desde dentro de un módulo de Glyph, así que no afirma nada sobre combinar los dos.
