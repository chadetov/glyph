Diseño · Comparación

¿Por qué no ReScript, Gleam o Elm?

Los tres son lenguajes tipados que compilan a JavaScript, y los tres son más antiguos, más usados y más estables que Glyph. Si estás eligiendo un lenguaje para un código nuevo y no necesitas mantenerte cerca de TypeScript, merece la pena mirarlos primero. Las diferencias de Glyph son más concretas: genera código fuente TypeScript en lugar de JavaScript, importa paquetes de npm tipados con su propio .d.ts, genera validadores en tiempo de ejecución a partir de tus tipos y su compilador responde consultas de impacto para un agente.

Cómo se describe cada uno

La página de inicio de ReScript abre con "JavaScript Made Simple for Humans and AI" y "Types > Vibes", y dice que "compiles to clean, efficient JavaScript" con "No any, no magic types, no surprise undefined." Ofrece "automatically generate TypeScript types" (rescript-lang.org).

La página de inicio de Gleam lo llama "a friendly language for building type-safe systems that scale" con "No null values, no exceptions, clear error messages". Se ejecuta en la máquina virtual de Erlang y "can additionally compile to JavaScript", y "also generates TypeScript definitions" (gleam.run).

La página de inicio de Elm describe "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions", para "reliable web applications", y dice que Elm "detects all API changes automatically" para "guarantee that every single Elm package follows semantic versioning" (elm-lang.org).

Estas citas se leyeron el 2026-11-19.

Lo que Glyph hace de otra manera

Cada uno de estos se ejecutó en Glyph 0.1.149 para esta página.

Genera código fuente TypeScript

glyph build escribe un archivo .ts por módulo, que luego comprueba tsc --strict y que te quedas si dejas de usar Glyph. ReScript y Gleam generan JavaScript y, a su lado, definiciones de tipos. El TypeScript generado se muestra en la página de TypeScript.

Importa paquetes de npm tipados con sus propias declaraciones

Un módulo importa un paquete por su nombre, y el .d.ts del paquete tipa cada uso. No hay que escribir antes ningún binding. En ReScript, "external is the primary ReScript feature for bringing in and using JavaScript values" (external), con los tipos declarados en el lado de ReScript. Los externals de Gleam necesitan anotaciones de tipo, y el compilador "cannot verify that the function implemented in the other language returns the specified types" (externals). Elm se comunica con JavaScript mediante flags, ports y custom elements (interop). Con pg y @types/pg instalados, esto se rechaza:

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

El código es TS2322 porque es tsc quien comprueba los valores de una biblioteca, y se traslada de vuelta a la línea de Glyph. El checker propio de Glyph no los ve, así que glyph check --no-tsc, el editor y las herramientas MCP no detectan este error (G257). Un tipo importado de un .d.ts tampoco tiene comprobación en tiempo de ejecución.

Genera el validador a partir del tipo

Cada record y cada unión llevan una comprobación en tiempo de ejecución generada a partir de su declaración, así que json.parse<User> devuelve Err cuando los datos no encajan. En Elm escribes un decoder para cada forma, y su guía señala que "the decoders people write end up working as a validation phase" (JSON).

main.glyph: imprime "refused", porque el JSON no tiene email 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

Su compilador responde qué va a romper un cambio

Antes de editar, un agente puede preguntar a qué sitios llega un cambio, por MCP (glyph_impact) o con glyph query impact. Sobre una unión Plan = Free | Pro | Team con un match exhaustivo y otro que termina en else, preguntar por una variante nueva responde sitio por sitio:

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

El segundo sitio dejaría de compilar tras el cambio, algo que cualquiera de estos compiladores también te diría una vez hecho el cambio. El primero seguiría compilando y mandaría el caso nuevo a su else, y es la consulta la que lo nombra. Para quien construye agentes lista las demás herramientas.

Lo que esta página no afirma

No ha comparado mensajes de error, velocidad de compilación ni rendimiento en tiempo de ejecución, y no ha probado a llamar a ninguno de los tres desde Glyph ni al revés. Las citas describen cada proyecto con sus propias palabras; hasta qué punto cumple cada uno es algo que te toca comprobar a ti, igual que las afirmaciones de Glyph en la página de pruebas.
