Pruebas

Cómo se comprueba cada afirmación de este sitio

Una afirmación de que Glyph detecta algo es un par de programas en el repositorio, uno en TypeScript y otro en Glyph, y una comprobación de CI ejecuta los dos en cada cambio. Si el TypeScript deja de compilar o el Glyph deja de ser rechazado, el build falla. Puedes ejecutar cualquier caso tú mismo con dos comandos.

Los casos

Cada directorio bajo catches/ contiene ts.ts, glyph.glyph y un case.toml que dice qué hace cada uno. scripts/check_catches.py se ejecuta en CI. Exige que cada ts.ts pase tsc --strict, ya que un programa TypeScript que no compila no demuestra nada, y comprueba la mitad de Glyph según el tipo de caso. {{catches:breakdown}} Según el tipo que comprueba:

TipoCasosQué exige la comprobación al Glyph
refused{{catches:refused-all}}El build falla con el código de case.toml
warned{{catches:warned-all}}El build pasa e informa de ese código como aviso
boundary{{catches:boundary-all}}El programa se ejecuta, y la comprobación en la frontera convierte los datos incorrectos en un Err
runtime{{catches:runtime-all}}El programa compila y luego se detiene al ejecutarse, con la salida indicada
gap{{catches:gap-cases}}Glyph acepta el programa y este hace lo incorrecto. Cuando el hueco se cierra, la comprobación falla y pide mover el caso

Un caso que deja de poder demostrarse se borra en lugar de suavizarse, y el README de catches lista los seis que se borraron y por qué. Resultó que uno también lo detectaba tsc; otro solo funcionaba porque su TypeScript recibía un valor como any.

El TypeScript con el que se compara

Cada caso dice también si un proyecto TypeScript completamente configurado habría detectado el error, y de ahí sale la etiqueta "¿lo detectaría TypeScript?". "Completamente configurado" es tsc --strict más todas las opciones que lo hacen más estricto, y una ejecución de typescript-eslint. La comprobación instala los paquetes desde cero en cada ejecución (TypeScript 6, eslint 9, typescript-eslint 8, tsx 4 y el último @types/node) y, sin red, falla en lugar de saltarse el paso.

La etiqueta de un caso es none, flag: más la opción que lo informa, o lint: más la regla. Cuando el programa corregido también dispara una regla por un motivo que no tiene nada que ver, el caso lleva ts_ok.ts y la etiqueta solo cuenta lo que salta con el error. Por ejemplo, non-exhaustive-match es lint:switch-exhaustiveness-check: typescript-eslint lo detecta si activas esa regla, y la página lo dice.

Los fragmentos de código de este sitio compilan

scripts/check_docs_compile.py se ejecuta en CI y compila cada fragmento de Glyph del sitio que se sostiene por sí mismo (empieza con module y declara algo), más los de la documentación y llms.txt. Un fragmento pensado para fallar tiene que nombrar el error que produce, y tiene que producir exactamente ese. Los fragmentos que necesitan React o un paquete de npm se compilan contra los tipos reales de esos paquetes. Los fragmentos sueltos se cuentan y se saltan, y el recuento se imprime para que la parte saltada siga a la vista.

Lo que todavía no detecta

Los {{catches:gap-cases}} casos gap están en la página de casos, cada uno con su número de gap. Cada gap encontrado al construir apps en Glyph está en el registro, docs/dogfooding-gaps.md, donde una marca entre corchetes es el único estado vigente ([FIXED], [HALF FIXED], o ninguna si está abierto) y scripts/check_gaps.py hace fallar el CI cuando una entrada abierta se reprodujo por última vez hace más de cinco versiones.

Cómo se marca una versión como Breaking

Una versión se marca como Breaking cuando rechaza un programa que la versión anterior aceptaba. Se decide escribiendo el programa afectado más pequeño y ejecutándolo con la versión anterior publicada y con el binario nuevo, y comparando los códigos de salida. No se deduce de la redacción de las notas. Las versiones anteriores a la 0.1.99 nunca se probaron así, así que una sin marcar no está probada, no es segura. El registro está en la página de versiones.
