Glyph cierra los huecos por los que se cuela un agente: no hay ningún any ni ningún as que puedas escribir, match es demostrablemente exhaustivo y los tipos que declaras tienen validadores estrictos en tiempo de ejecución, todo aplicado como una capa estricta encima de tsc. La mentira que puede contar un tipo

En TypeScript un tipo es una promesa en tiempo de compilación que se evapora antes de que se ejecute tu código. Una anotación User se borra por completo; el objeto que realmente recibes de una llamada de red, un parseo de JSON o un campo de formulario puede tener cualquier forma.

Peor aún, el lenguaje te da tres formas legales de mentirle al checker sobre ello: any, un cast con as y un ! de no nulo. Un agente que trabaja deprisa echa mano de los tres, y tsc --strict sigue en verde mientras el bug llega a producción.

La primera tarea de Glyph es cerrar esos huecos. No con más anotaciones, sino eliminando las vías de escape y haciendo que cada tipo lleve su prueba hasta el tiempo de ejecución. Esto es lo que significa, garantía a garantía.

01 No existe any

Glyph no lo tiene. El tipo superior es unknown, y unknown es inerte: no puedes llamarlo, indexarlo ni pasarlo a nada tipado hasta que hayas demostrado lo que es.

Detalles por qué un solo any cuesta tanto

any es la palabra clave más cara de TypeScript: desactiva el sistema de tipos para un valor y para todo lo que ese valor toca. Un solo any en una frontera envenena sin hacer ruido todo el grafo de llamadas que hay detrás.

No puedes sacar un valor tipado de unknown sin una comprobación que el compilador pueda ver. En Glyph, el estrechamiento es la prueba en tiempo de ejecución. No hay sintaxis para saltárselo.

02 Los tipos existen en tiempo de ejecución

¿Cómo existe User.parse? Porque cada tipo record, y cada unión etiquetada no genérica, genera a su lado un descriptor de runtime: un guard is, un parse que valida un unknown y lo convierte en un Result, y un schema que se puede componer.

el tipo que escribes y el descriptor que se genera a partir de él 
type User = {
  id: number,
  name: string,
  email: string,
}

// generated: User.is(v), User.parse(v) -> Result<User, ...>, User.schema

fn create(req: Request) -> Result<Response, string> {
  return match User.parse(req.body) {   // untrusted input, validated
    Ok(user) => Ok(json(201, user)),
    Err(issues) => Ok(json(400, issues)),
  }
}

Esta es la respuesta a "cada API necesita un validador escrito a mano". El tipo es el validador.

Detalles qué comprueba el descriptor

La forma del record se inspecciona de verdad en tiempo de ejecución, no se supone, así que una comprobación is User es una comprobación real, no una operación vacía que se borra.

Una frontera (el cuerpo de una petición, un archivo de configuración, la respuesta de un tercero) solo pasa a estar tipada al atravesar una comprobación que de verdad puede rechazar datos incorrectos.

Dónde se detiene: el descriptor de un record es estricto por defecto. Confirma los campos declarados y rechaza un valor que lleve claves no declaradas (pon @open en el tipo para permitir extras). Los tipos record tienen descriptor, también los genéricos, así que Paginated<User> comprueba cada elemento como un User, y el descriptor de una unión etiquetada comprueba la etiqueta y luego los campos del payload de esa variante.

Lo que todavía no tiene uno es una unión etiquetada genérica (Box<T> = Empty | Full({ value: T }) no tiene Box.parse), ni un tipo importado de un .d.ts al que solo haces referencia. Cuando una comprobación solo puede demostrar parte de una forma, el compilador lo dice en lugar de dar a entender una garantía que no puede ofrecer.

03 Todos los casos, o no compila

Un match sobre una unión cerrada tiene que manejar cada variante. Añade una variante más tarde y todos los match que no la tenían en cuenta dejan de compilar (E0200).

status.glyph 
type Status = Active | Paused | Cancelled

fn label(s: Status) -> string {
  return match s {
    Active => "on",
    Paused => "hold",
    // forgot Cancelled...
  }
}

Detalles match sobre números y strings

El caso nuevo no puede caer sin avisar en undefined como hace una rama de switch olvidada. Y no son solo las uniones: hacer match de un number o un string sobre valores literales exige un else (E0218), porque esos dominios no tienen límite y un conjunto de literales nunca puede estar completo.

04 Los errores son valores, no sorpresas

Una función que puede fallar devuelve Result<T, E>. Lo manejas con match, o lo propagas con el operador ?, y el tipo de error tiene que encajar (no hay conversiones implícitas que oculten una discrepancia).

pipeline.glyph 
fn load(id: string) -> Result<User, AppError> {
  let raw = fetch_user(id)?           // Err short-circuits to the caller
  let user = User.parse(raw.body)?    // validation Err propagates too
  return Ok(user)
}

fn main() -> number {
  save(user)   // E0217: this returns a Result whose Err is dropped
  return 0
}

Ignora un Result por completo (llama a la función por su efecto y descarta lo que devolvió) y Glyph te avisa (E0217), porque un error descartado es un fallo que se traga. Lo silencias a propósito con let _ = ..., nunca por accidente.

05 Hasta los datos personales van en el tipo

El mismo instinto de "que sea trabajo del compilador, no una convención" llega hasta los datos sensibles. Pon @redact en un tipo y su descriptor gana un redact() que enmascara esos campos, así que un json.stringify(User.redact(u)) despistado no puede filtrarlos.

patient.glyph 
@redact fields: [diagnosis, notes]
type Patient = {
  name: string,
  diagnosis: string,
  notes: string,
}

// json.stringify(Patient.redact(p)) ->
// {"name":"Ada","diagnosis":"[REDACTED]","notes":"[REDACTED]"}

Nombra un campo que el tipo no tiene y es un error de compilación (E0219), no un enmascarado que sin avisar no protege nada.

Cinco modos de fallo distintos (entrada sin comprobar, un caso olvidado, un error descartado, un secreto filtrado, una clave sin validar) y en todos el arreglo tiene la misma forma: el compilador se niega a fingir.

Cómo se aplica, y dónde se detiene la garantía

Siendo precisos, porque la diferencia importa: Glyph es un dialecto estricto y obligatorio sobre tsc, no un verificador independiente.

  • Lo demuestra GlyphAlgunas cosas las demuestra él mismo: la exhaustividad, el tipo de error de ?, la ausencia de any/as en tu código, la validación estricta de claves.
  • Se aplica a través de tscEl resto de la compatibilidad de tipos la aplica generando TypeScript y ejecutando tsc --strict, que hace fallar el build.

La cuña es que estas comprobaciones son el lenguaje, no un lint opcional que el agente puede desactivar, no que Glyph reimplemente un type checker.

Historia límites cerrados en la 0.1.10, validación profunda de genéricos

Dos límites anteriores de esta sección se cerraron en la 0.1.10. El emisor antes insertaba un cast de retorno comprobado-por-Glyph-y-no-por-tsc en todas las funciones genéricas; ahora solo aparece donde un combinador de validadores construye un valor de un tipo derivado de una forma (infer_output<Shape>), y cualquier genérico honesto se genera sin ningún cast. Y ya no se confía en el tipo de salida de un validador: infer_output lo deriva de la forma que pasas, y tsc comprueba tu anotación contra él: una forma a la que le falta un campo del tipo que afirmas ahora no compila.

Los tipos genéricos ahora también validan en profundidad: un descriptor de Paginated<User> comprueba cada elemento como un User, no solo que exista.

Queda un límite, dicho claramente: un tipo importado de un .d.ts externo al que solo haces referencia no lleva descriptor hasta que lo materializas con glyph gen dts, así que de un campo de ese tipo se comprueba que exista, no su forma. Esa frontera es deliberada (un tipo que Glyph no generó no puede prometer validación en tiempo de ejecución) y materializarlo la cierra.

Nada de esto se paga con ceremonia. No hay anotaciones de prueba, ni contratos, ni un verificador al que satisfacer. El código de arriba es Glyph normal. La verificabilidad no es una característica que se activa; es lo que queda cuando desaparecen las formas de mentir.

"TypeScript estricto y una configuración de lint ya hacen esto"

Dentro de un programa se acercan. strict, noUncheckedIndexedAccess y una regla contra el any explícito detectan casi todo lo que un agente colaría de otro modo. Se detienen en los bordes.

  • En la fronteraJSON.parse(body) as User compila con cualquier configuración que exista, y el arreglo habitual, un schema de zod, es una segunda descripción de User que hay que mantener sincronizada con la primera a mano. En Glyph el tipo es el validador: json.parse<User>(body) se comprueba contra el propio User, y un tipo que Glyph no puede comprobar en tiempo de ejecución se rechaza en lugar de darse por bueno.
  • Entre repositoriosLa otra diferencia es quién puede contar con ello. Una configuración de lint es una decisión que tomó un repositorio. Un agente que abre un código TypeScript que no conoce no puede dar por hecho que any está prohibido allí; en Glyph no se puede escribir en ningún sitio.

La misma garantía, vista como los errores que comete un agente y los mensajes que los detienen, se responde en ¿Qué impide que un agente rompa mi código sin que nadie lo note?
