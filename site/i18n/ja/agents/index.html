エージェントとツールの開発者向け

エージェントのためのコンパイラのインターフェース

エージェントは Glyph のコンパイラに、シンボルが何なのか、編集が何を壊すのか、ビルドがなぜ失敗したのかを問い合わせ、JSON で答えを受け取れます。glyph mcp は stdio 上で 11 個のツールを提供し、どれも glyph query のサブコマンドとしても使えます。glyph llms は言語リファレンスをオフラインで出力します。

セットアップ

glyph init は新しいプロジェクトにこの .mcp.json を書き出し、glyph agents は既存のプロジェクトにこれを（glyph llms を案内する AGENTS.md と一緒に）書き出します。このファイルを読む MCP クライアントなら、どれでもサーバーを起動します。ポートもデーモンもありません。

.mcp.json（glyph init が書き出すもの） 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp"]
    }
  }
}

1 回の呼び出しと、その実際の答え

あるファイルが、レコードに宣言されていないフィールド（u.naem）を読んでいます。エージェントは glyph_diagnostics を呼び出し、コンパイラ自身の診断を受け取ります。そこにはレコードが実際に宣言しているフィールドと、それを持つレコードが含まれます。これは 0.1.149 でのツールの出力で、印を付けた箇所だけを省略しています。

リクエスト 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": {
      "path": "src/user.glyph"
    }
  }
}
結果 
{
  "diagnostics": [ {
    "code": "E0210",
    "severity": "error",
    "stage": "typecheck",
    "message": "type `U` has no field
      `naem`; did you mean `name`?",
    "alternatives": ["name", "email"],
    "alternatives_kind": "fields",
    "cause": "user::U",
    "entity": "user::greet",
    "file": "user.glyph",
    "range": {
      "start": { "line": 9, "col": 10 },
      "end": { "line": 9, "col": 16 } },
    ...
  } ],
  "member": true,
  "module": "user",
  "not_run": [
    { "what": "tsc", ... },
    { "what": "E0104, ...", ... },
    { "what": "E0400, ...", ... } ],
  "path": "src/user.glyph",
  "project_root": "src",
  "unindexed": []
}

not_run はこの検査で扱わなかった範囲を示すので、空の diagnostics リストを完全なビルドの結果と取り違えることはありません。MCP クライアントがなくても、glyph query diagnostics --path src/user.glyph で同じ JSON が出力されます。全サブコマンドを含むツールの一覧は MCP のページにあります。

編集の前に：何が壊れるか

examples/apps/csvql は 11 ファイルからなる CSV クエリエンジンで、4 つのケースを持つユニオン Value があります。5 つ目のケースを追加するとどうなるかを聞くと、glyph_impact は 4 ファイルにある 10 か所の match を一覧します。8 か所が WILL_FAIL、2 か所が ABSORBS で、後者は catch-all のアームが新しいケースを飲み込み、コンパイルが通り続ける箇所です。実際にケースを追加すると、ちょうどその 8 か所で 8 つの E0200 エラーが出ます。飲み込む 2 か所は何も言わないままなので、答えにはそれらが名指しされています。

コマンドラインで同じことを聞く 
glyph query impact --path value.glyph --entity value::Value \
  --change add_variant --variant Blob

赤いビルドの後で：修正が守るべきものは何か

glyph check --agent は check --json の診断を、それぞれにキーを 2 つ追加して出力します。constraints は修正の編集が壊してはならないものを並べます。上のタイポなら「レコードのフィールドは閉じている：user::U が宣言するのは name と email だけ」となります。symbols は診断が名指しするすべてのシンボルについて glyph_symbol の答えを含むので、次の編集に 2 回目の呼び出しは要りません。修正内容が完全に決まる場合は、glyph fix がそれを書き込みます。

オフラインで言語を読む

glyph llms は言語リファレンスを出力し、このサイトの /llms.txt は同じ文書です。glyph llms --json はその知識をデータとして出力するもので、コンパイラ自身のテーブルから読み出されます：診断コード 77 個、prelude の名前 24 個、エクスポート 340 個を持つ標準ライブラリのモジュール 40 個、言語の設計判断 49 個、そして 11 個のツールです。glyph llms --negative は 0.1.149 で 117 個（次のリリースからは 139 個）の誤ったプログラムを、それぞれが引き起こすコードと一緒に返し、要求した時点でコンパイルします。scripts/check_llms_sync.py は、リファレンスの診断と予約語のテーブルがコンパイラ自身のものとずれると失敗します。

オフラインの入口 
glyph llms                  # the reference, as prose
glyph llms --json           # the same, as data from the compiler's tables
glyph llms --negative E0200 # wrong programs that draw E0200
glyph --explain E0200       # the long explanation of one code
