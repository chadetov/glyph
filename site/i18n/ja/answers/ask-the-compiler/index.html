23 · コンパイラに聞く

エージェントは、コードを書く前にシンボルが何なのかをコンパイラに聞けますか？

1 回の呼び出しで聞けます。glyph_symbol は、診断がすでに出力した module::name か、ファイル内の位置を受け取り、次のことを答えます。レコードのフィールドとその型、ユニオンのバリアントとそのペイロード、そしてそれぞれを構築する構文、呼び出し可能なものの引数と戻り値、インターフェースのメンバー、そしてそれに対する match が網羅的でなければならないかどうかです。

なぜ重要か

自分が宣言していないユニオンに新しいケースを扱うよう頼まれたエージェントは、各バリアントが何を持っているかを知る必要があります。宣言を読むには、まずファイルを探さなければなりません。

コンパイラはその間ずっとペイロードを持っていました。ツールが返答の 1 行手前でそれを捨てていたのです。

経緯 以前のシンボル検索が返していたもの

以前のシンボル検索が返すのは名前とバイト範囲だけで、バリアントの一覧は ["Pending", "Paid", "Cancelled"] だけでした。そこからエージェントは Paid("tx_1") と書きますが、これは正しい形ではなく、診断で初めてそれに気づきます。

エージェント向けの機能は、まさにこのパターンをなくすために作られました。コンパイラがすでに計算してメモ化しているのに、どのツールも渡していない事実です。3 モジュールのプロジェクトを監査したところ、hover が答えられたのは 14 か所中 2 か所だけで、どのユニオンもペイロードなしで返ってきていました。

どの null も理由を示す

一部省略しています。実際の回答には generics、parameters、returns、members、literals、owner、async、examples も含まれます。どれもペアになっています。

キーが null になるのは、その理由を述べる <key>_absent の文が横にあるときだけです。そのため、答えがないことが「シンボルにそれがない」のか「ツールが調べなかった」のかを、エージェントが推測する必要はありません。

詳細 型注釈のない const

型注釈のない const は、このルールに従って型を報告しません。チェッカーは宣言の型を初期化式から推論しないようにしています。そこで初期化式の型を出力すると、その名前の使用箇所が何かに対して検査されていると呼び出し側に伝えることになりますが、実際には何も検査していないからです。

詳細 3 つの判定と、SAFE ではない理由

両辺はそれぞれ module::name か Glyph の型表記で、指定したファイルのスコープで読まれます。判定結果は、3 つのうちどれが起きたかを示します。

語は SAFE ではなく COMPATIBLE です。この違いは一言説明しておく価値があります。SAFE は glyph_impact の用語で、ある特定の箇所が特定の編集のあとも正しいままであることを意味します。こちらの回答は 2 つの型についてのもので、問いには箇所も編集も含まれません。3 つ目の判定は UNDETERMINED で、その組み合わせを扱うルールがないときに返ります。2 つの関数型はこの判定になります。根底にある関係は戻り値を比較しますが、引数については何も言わないからです。そこで何も言わないことは受け入れたことを意味せず、ツールもそれを受け入れとして報告しません。

逆方向：これは何に依存していて、あのモジュールは何を提供しているのか

import を書こうとしているエージェントは、ファイルを開かずに向こう側に何があるかを聞けます。

  • glyph_referencesglyph_references は、誰がシンボルを使っているかに答えます。
  • glyph_dependenciesglyph_dependencies は同じテーブルを反対側から読んだものです。1 つの宣言が何に依存しているか、つまりそのソースが名前を挙げているすべての宣言を、CALLS、REFERENCES、FIELD_ACCESS に分けて返します。各エッジは両端と、その位置を持っています。
  • glyph_exportsglyph_exports は、モジュールが import する側に何を公開しているかに答えます。スキャンではなくコンパイラ自身の export クエリから求め、すべての pub 宣言と、pub なユニオンが引き上げるすべてのバリアントを、識別子、種類、シグネチャ付きのエントリとして返します。
経緯 ミラーが捕まえた PROVED のバグ

関係の逆向きを作ったことで、元の実装のバグが見つかりました。各エッジは出自（provenance）を持ち、PROVED はコンパイラが両端を読んだことを意味するはずです。ところが、パースできないモジュールへのエッジに対しても PROVED を返していました。そこでは何も読まれていません。今は理由付きで UNDETERMINED を返します。glyph_references と glyph_impact は同じ関数を呼んでいるので、どちらも同じように間違っていて、どちらも修正されました。

11 のツール、クライアントは不要

glyph mcp は 11 のツールを提供します。glyph_symbol、glyph_impact、glyph_assignable、glyph_diagnostics、glyph_hover、glyph_definition、glyph_references、glyph_variants、glyph_symbols、glyph_dependencies、glyph_exports です。

それぞれに対応する glyph query のサブコマンドがあり、同じ引数をフラグで受け取って同じ JSON を出力します。クライアントが到達するのと同じエントリポイントを通るので、シェルコマンドしか実行しないエージェントも同じ質問ができます。

詳細 診断と、編集のあとに来るもの

glyph_diagnostics はプロジェクト内のファイルを検査し、glyph check --json が出力するのと同じ Rust の型から作った診断を返します。6 つのプロジェクトで両方の経路を実行し、JSON をキーごとに比較するテストもあります。詳しくは MCP のページを参照してください。

ここまではすべて編集の前に聞くものです。編集のあとは、コンパイラが逆方向に答えます。glyph check --agent は各診断を、修正の編集が守るべき不変条件と、その診断が名前を挙げるすべてのシンボルの glyph_symbol による説明付きで出力します。エージェントが必要とする形は、それを求めたエラーと一緒に届きます。これについては専用のページがあります。

現状

提供中

  • MCP 上の読み取り専用ツールが 11 個あり、それぞれに glyph query のサブコマンドがあります。
  • glyph_symbol は識別子でも位置でも答え、持っていない事実はすべて、その理由を述べる文の横で null になります。
  • 識別子は stdlib にも届く：std/result::Result
    詳細

    識別子は stdlib にも届きます。prelude の Result は std/result::Result で、これはリゾルバがそれを登録するモジュールであり、エミッタが import を書き出すモジュールでもあります。そのため glyph query symbol --entity std/result::Result は Ok(T) と Err(E) を答え、glyph query exports --module std/result は公開されているものを一覧し、それに関する E0200 は cause にその識別子を持ちます。背後に Glyph のソースはないので、path と range は欠けているのではなく、その理由付きで null になります。

  • hover は調べた 14 か所のすべてに答える
    詳細

    hover は、3 モジュールのプロジェクトで監査が調べた 14 か所すべてに答えます。この作業を始める前は 2 か所でした。別のモジュールで宣言された名前は、そのモジュール自身の宣言から答えるので、import の束縛、呼び出し箇所の import した関数、値として使われた import したバリアント、import したレコードから読んだフィールドのどれにも型が付きます。

  • glyph_dependencies と glyph_exports で、G221 が求めていたセットがそろいました。G221
  • glyph_variants は各ペイロードとその構築構文を持ち、glyph_definition と glyph_symbols は module::name を持つので、答えを何も導き直さずに glyph_impact へつなげられます。
  • glyph_impact と glyph_assignable は同じ比較を行う
    詳細

    glyph_impact のシグネチャ型テーブルは、コンテナ同士、構造的レコードと構造的レコードまたは宣言されたレコード（ローカル、import したもの、ジェネリック、別名）、JSX 要素を変換先の呼び出しとして、そしてどちらかの側にある文字列リテラルユニオンを、glyph_assignable と同じ比較で判定します。そのため、1 つの組み合わせについて 2 つのツールの意見が食い違うことはありません。関係が完全に読み取れる組み合わせの引数は、比較の結果がどちらであっても WILL_FAIL です。change_signature_type は置き換え先の型を指定しないので、受け入れられた組み合わせも、置き換え次第で拒否されうるからです。UNDETERMINED になるのは、関係が判定を辞退した組み合わせだけです。

限界

  • ここにあるツールはどれも書き込みません。リネームも、編集の適用もありません。
  • 書き込み側は glyph fix で、修復するのは 3 つのことだけ
    詳細

    書き込み側はコマンドラインの glyph fix で、頼んだことを何でも直すわけではなく、3 つのことだけを修復します。未使用の import、チェッカーが候補をちょうど 1 つだけ持っているアームの先頭、そして宣言されたフィールドのうちちょうど 1 つと 1 文字違いのフィールド名です。

  • 一部の stdlib の export は kind: null を返す
    詳細

    コンパイラが宣言もシグネチャもモデル化していない stdlib の export は、理由付きで kind: null を返します。std/result::all と std/io::println は、コンパイラが配置する TypeScript で型付けされており、Glyph のどのパスもそれを読みません。

  • glyph_diagnostics は glyph check が行う検査のうち 3 つを省き、それを not_run に挙げる
    詳細

    glyph_diagnostics は、glyph check が行う検査のうち 3 つを省きます。tsc、どのモジュールも指していない import に対する E0104 の検査（ビルドから見た node_modules が必要です）、そして失敗する @example に対する E0400（出力したプロジェクトを実行する必要があります）です。これらを実行したかのように答えるのではなく、3 つとも not_run に挙げます。
