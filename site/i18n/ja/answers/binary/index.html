バイナリデータは扱えるのか、それとも何でも文字列なのか

std/bytes は不変のオクテット列を提供し、std/fs と std/crypto はどちらもそれを扱えます。0.1.78 より前はそうではありませんでした。標準ライブラリの境界はすべて文字列を受け取って文字列を返す形だったので、PNG を読むことも、HMAC に本物の鍵を渡すこともできませんでした。

なぜ重要か

PNG の先頭バイトは 0x89 で、これ単体では有効な UTF-8 ではありません。このファイルをテキストとして読むと、デコーダが解釈できないバイトはすべて U+FFFD になります。プログラムが目にする前にファイルは壊れていて、エラーを報告するものは何もありません。鍵でも同じことが起きます。HMAC の秘密鍵は任意のオクテット列で、文字列を経由させると変わってしまいます。その結果、仕様とは違う MAC を計算することになり、しかも自分のコードに対して書いたテストはすべて通ります。

別々に書かれた 2 つのアプリケーション、PNG リーダーと認証アプリが、同じ週にこの同じ問題で止まりました。どちらも言語の中で回避することはできませんでした。

実例

RFC 6238 の認証アプリです。HMAC の両側でバイト列が必要になります。秘密鍵は base32 でエンコードされて届き、メッセージはほとんどがゼロの 8 バイトのカウンタで、ダイジェストは自身の最後のバイトでインデックスされます：

ワンタイムパスワードの最初から最後まで 
module totp

import std/bytes
import std/crypto
import std/math
import std/array
import std/option { Some, None }
import std/result { Result, Ok }

fn at(b: bytes.Bytes, i: int) -> int {
  return match bytes.get(b, i) {
    Some(v) => v,
    None => 0,
  }
}

pub fn code(secret: string, counter: number) -> Result<number, bytes.BytesError> {
  let key = bytes.from_base32(secret)?
  let message = bytes.from_array(array.map(array.range(8), fn(i: int) -> int {
    return math.floor(counter / math.pow(256, 7 - i)) % 256
  }))?

  let mac = crypto.hmac_sha1_bytes(key, message)
  let offset = at(mac, bytes.len(mac) - 1) % 16
  return Ok((((at(mac, offset) % 128) * 16777216)
    + (at(mac, offset + 1) * 65536)
    + (at(mac, offset + 2) * 256)
    + at(mac, offset + 3)) % 100000000)
}

Bytes は実行時には Uint8Array なので、それを受け取るホスト API にそのまま渡せます。列の操作は std/array や std/string の対応する関数にならって名付けられています：len、get、slice、concat、index_of、starts_with。引数を変更するものはありません。

どのデコードも拒否でき、その位置を示す

ここが作るのに最もコストがかかった部分で、使う理由でもあります。Node の Buffer は不正な入力を受け入れ、成功を報告します：

プラットフォームが黙ってすること 
Buffer.from("zz", "hex")        // an empty buffer, no error
Buffer.from("a-b_", "base64")   // skips - and _, decodes the rest, no error
buf.toString("utf8")            // U+FFFD for anything malformed, no error
Glyph がすること 
match bytes.from_hex(input) {
  Ok(b) => use(b),
  Err(e) => io.eprintln("${e.message} at ${number.to_string(e.index)}"),
}

// "z" is not a hex digit at 0
// a trailing base64 group cannot be 1 character(s) long at 3
// not valid UTF-8 at 2

どのコーデックも Buffer に任せずに自前で書いてあります。そのため hex、base64、base64url、base32 はどれも、アルファベット外の文字、1 バイトをエンコードするには短すぎる末尾のグループ、データの終わりを越えるビットを持つ最後の文字を拒否します。to_text は走査して、有効な UTF-8 シーケンスの一部になりえない最初のバイトを見つけるので、判定だけでなく位置がわかります。from_array も同じ理由で 0..255 の範囲外を拒否します。黙って & 0xff をかけると、256 が 0 になり、タイポがデータになってしまうからです。

コーデックを自前で書いたことで、狙っていなかった利点も得られました。このモジュールはホスト API を一切使わず、使うのは Uint8Array、TextEncoder、TextDecoder だけです。そのため std/bytes だけを使うバンドルは Web Worker でも動きます。

どの HMAC を選ぶかで答えが変わる

std/crypto には、どのアルゴリズムにも 2 つの形があります。素の名前のものは文字列を受け取って hex を返し、パスワードのハッシュ化に向いています。_bytes の形は Bytes を受け取って返し、通信プロトコルに向いています。鍵が bytes.from_base64 や crypto.random_bytes から来たものなら、文字列では表せないバイトを含んでいるので、テキスト版は黙って別のものを計算してしまいます。

攻撃者が渡した値を秘密と照合するには、bytes.equals ではなく crypto.timing_safe_equal を使います。equals は不一致を見つけた時点で return するので、かかった時間から先頭の何バイトが合っていたかがわかってしまいます。

現状

提供中

21 個の関数を持つ std/bytes：列の操作、UTF-8 との橋渡し、そして問題の位置を示す Result を返す hex、base64、base64url、base32 のコーデックです。fs.read_bytes、write_bytes、append_bytes はファイルをデコードせずに読み書きします。std/crypto には、すべてのダイジェストと HMAC の _bytes 版に加え、SHA-1 を指定するプロトコル向けの SHA-1、random_bytes、timing_safe_equal があります。コーデックは RFC 4648 のテストベクタで、HMAC は RFC 6238 で、コンパイラ自身のテストスイートの中で固定されています。

改善中

整数のコーデックはまだないので、ヘッダからビッグエンディアンの u32 を読むには自分で計算を書きます。32 ビットを超えるとシフトはそもそも適さないので、割り算を使います。16 進リテラルはまだパースできないので、10 進で書いた 256 要素の CRC32 テーブルは読みにくくなります。std/websocket はまだバイナリフレームを UTF-8 テキストとしてデコードします。必要だった型はもう存在するので、フレームが次の対応対象です。また std/encoding にある古い文字列から文字列への関数 6 つは、不正な入力に対して今も黙ったままなので、正しくなければならない処理には std/bytes のコーデックを使ってください。コーデックは node の Buffer に任せずに TypeScript で書かれています。それが Web Worker で動く理由ですが、1 メガバイトのデータではプラットフォームのものより 1 倍から 35 倍遅くなります。鍵やトークンのエンコードなら、どちらを使っても測れるほどのコストはかかりません。数十メガバイトを扱うなら、パフォーマンスガイドに表があります。
