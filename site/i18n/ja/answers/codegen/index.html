API の仕様から型付きのクライアントとサーバーを生成できるか

できます。glyph gen openapi に OpenAPI の仕様を渡します。--client は型付きの HTTP クライアントを、オペレーションごとに 1 つの関数として出力します。--handlers はサーバースタブと、実際に動く route ディスパッチャを出力します。信頼できる情報源が zod スキーマなら、glyph gen zod が同じことをします。出力はすべて、自分のものとして編集できるコミットされた、grep できる Glyph で、隠れたコード生成ステップにはなりません。

なぜ重要か

手書きの API クライアントと DTO は仕様からずれていきます。このずれは誰にとっても楽しくない種類のバグです。Glyph は本物のコード（型付きの関数、実行時ディスクリプタを持つ本物の type 宣言）を生成するので、仕様が信頼できる情報源であり続け、再生成はブラックボックスではなく、冪等でレビューできる差分になります。

実例：クライアント

各オペレーションは、型付きのパスパラメータと型付きのリクエストボディを持ち、HTTP の Response を返す async fn になります：

$ glyph gen openapi tasks.yaml --out src/ --client 
async fn createTask(
  base: string,
  body: NewTask,
) -> Result<Response, HttpError> {
  return await post(
    "${base}/tasks",
    body,
  )
}

async fn getTask(base: string, id: number)
  -> Result<Response, HttpError> {
  return await get("${base}/tasks/${id}")
}
$ glyph gen openapi tasks.yaml --out src/ --handlers 
fn route(req: Request)
  -> Result<Response, string> {
  return match req.method {
    "GET" => match segments(req) {
      ["tasks"] => listTasks(req),
      // id captured from the path:
      ["tasks", id] => getTask(req, id),
      else => Ok(json(404, {
        error: "not found",
      })),
    },
    else => Ok(json(405, {
      error: "method not allowed",
    })),
  }
}

--handlers のルーターは配列パターンでパスにマッチするので、/tasks/{id} は ["tasks", id] になり、パラメータを束縛してくれます。各スタブは最初、ボディのパース方法を示すコメント付きの 501 になっています。中身を埋めて、await serve(PORT, route) でつなぎます。

zod スキーマから生成する

チームがすでに zod で形を定義しているなら、そこから直接生成できます。スキーマは独自のディスクリプタを持つ、Glyph の第一級の型になります：

schemas.ts 
export const Task = z.object({
  id: z.number(),
  title: z.string(),
  done: z.boolean(),
})
$ glyph gen zod schemas.ts --out src/ 
type Task = {
  id: number,
  title: string,
  done: bool,
}
// + a runtime descriptor, so
// Task.parse(value) validates.

多相的な判別可能ユニオン（OpenAPI の discriminator）は、本物の Glyph のタグ付きユニオンと、生成された parse_<Name> になります。この関数は判別用のプロパティを読み、正しいバリアントとして検証します。Glyph は任意のプロパティではなくコンストラクタ名でタグ付けするので、生成されたディスパッチャが通信上のオブジェクトとユニオンの間を橋渡しします。

足りない点：生成は通信上の形に忠実なので、よくある 80% をマッピングします。オブジェクト、プリミティブ、配列、参照、省略可能なフィールドと nullable なフィールド、判別可能ユニオンです。正確に表せないもの（文字列の enum、判別子のないユニオン）は、実データを拒否してしまうバリデータを作る代わりに、注記を出力したうえで型を狭めます。より豊かな enum が次の対応対象です。また、ツールには実際の依存関係があります。gen dts/gen zod には Node と typescript/zod が必要です。gen dts はどの TypeScript（5、6、7.x のネイティブ移植版）でも動き、まずプロジェクトから解決します。足りないものがあれば、何をインストールすればよいかを正確に教えてくれます。

同期を保つ

生成されたファイルは、それを作った正確なコマンドをヘッダに記録しています。仕様が変わっても、どのコマンドを再実行すればよいかを探す必要はありません。glyph regen がそのヘッダを探して各コマンドを再実行し、出力を書き換えます。冪等なので、仕様に変更がなければ何も変わりません。pre-commit フックにも、コミットされたコードが仕様からずれていたら失敗する CI のチェックにも、そのまま組み込めます。

現状

提供中

glyph gen openapi（型、--client、本物のルーター付きの --handlers）、glyph gen dts、glyph gen zod、そしてソースからすべてを更新する glyph regen。どのコマンドも、コミットされ、ディスクリプタを持ち、冪等に再生成される Glyph を出力します。

Glyph で同じ名前になってしまう 2 つの型があると、ジェネレータはコンパイルできないファイルを作る代わりに停止します。衝突しているソースをすべて名指しし、何も書き出さず、--rename Source=GlyphName で解決できます。この選択は生成されたヘッダに記録されるので、glyph regen でも再現されます。

予定

より豊かな enum のマッピングと、より広い OpenAPI の対応範囲。どちらも、通信上の形に忠実で、型を狭めるときは注記するという同じルールのもとで導入されます。パッケージ自身の .d.ts からの生成は interface と type の宣言を読むので、API がクラスで構成されていたり、フィールドに Omit のような計算された型を使っていたりするライブラリでは、参照が残ります。ジェネレータはそれを注記で名指しし、glyph build は未解決として報告します。そのようなクラスを import して new で生成する場合は生成が不要で、tsc が検査するので、その経路には影響しません。
