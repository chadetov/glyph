深夜 3 時に本番で壊れたとき、オンコール担当には何が見えるのか

自分のものとして持てる読みやすい TypeScript と、出力された各ファイルの横に置かれる .glyph へ戻るソースマップです。デバッガ、バンドラ、エラートラッカーは実行中のコードをソースまでたどれますし、Glyph を見たことがない人でも生成された TS を読めます。それ以前に、glyph build と glyph run は同じツリーに対して同じ診断を報告するので、手軽なループがビルドなら検出したはずのものを隠すことはありません。どちらも glyph run の経路に関する 2 つの制限については、後で説明します。

1 · 生成された TypeScript は自分で読める

Glyph は中身の見えないランタイムを同梱しません。出力するのは普通の整形された TypeScript で、ほかの TS と同じようにコミットしてデプロイします。だから最悪のケース（深夜 3 時に、Glyph を知らないオンコールのエンジニア）でも、読むのは方言ではなく普通の TypeScript です。ソースと本番の間にブラックボックスはありません。

2 · .glyph へ戻るソースマップ

出力されるどの .ts にも、標準の v3 ソースマップ（.ts.map）が隣に付きます。sourceMappingURL コメントがあり、Glyph のソースも埋め込まれています（sourcesContent）。ソースマップを扱えるもの（Chrome DevTools、Node のデバッガ、Sentry のようなエラートラッカー、バンドラ）なら、それをたどって生成された行ではなく .glyph の行を表示できます。

dist/main.ts（末尾） 
// ...emitted TypeScript...
//# sourceMappingURL=main.ts.map    // v3 map, .glyph embedded

3 · ビルドエラーと型エラーはすでに Glyph を指す

型エラーのまま本番に出ることはまずありません。glyph build が tsc --strict を実行し、すべての tsc エラーを .glyph のソースに対応付け直すからです（キャレットも同じで、TypeScript のエラーコードも保たれます）。キャレットは、tsc が拒否したコードに対応する最小の Glyph の式に置かれます。引数が誤っていればその引数に、JSX のイベントハンドラ内でフィールド名を綴り間違えていれば、それを囲む return 全体ではなくそのメンバーアクセスに下線が引かれます。さらに glyph build --json はすべての診断を構造化された JSON（コード、深刻度、ファイル、1 始まりの行と列、ヘルプ）で出力するので、CI やツールがそれをもとに動けます。

4 · glyph run も同じことを伝える

一日中打つコマンドは glyph run で、0.1.40 まではビルドより口数が少ないものでした。ディレクトリ全体をコンパイルし、レポートから出力ファイルの一覧を取り出して、診断は捨てていました。glyph build が指摘するツリーでも、何事もなく実行されて終了コード 0 で終わっていました。今は同じ診断を報告します。警告も含め、指定したファイルにもその兄弟ファイルにも、プログラムの出力の後に、1 行の件数とともに表示します。実行キャッシュが診断も保持するので、変更のないソースを 2 回目に実行しても黙らずに 1 回目と同じことを伝えます。診断が欠けたキャッシュエントリはミスとして扱われ、再ビルドされます。

使われていない import。それを使うはずのコードより 1 ステップ前に追加されたもの 
$ printf 'look\nquit\n' | glyph run adventure.glyph

現在の 2 つの制限

glyph run 自身のクラッシュ時のスタックは、まだ .ts の行番号を表示します。glyph run は tsx 経由で実行し、tsx は自身の .ts→.js 変換を通してソースマップをつなげないので、glyph run 中に捕捉されない throw があると、生成された行が報告されます。このスタックの対応付けは今後の課題です。影響するのはローカルの run ループです。実際のデプロイでは glyph build で .ts を出力し、普段のツールチェーンでバンドルするので、.ts.map はいつもどおりつながり、呼び出しを受ける本番のスタックは .glyph に対応付けられます。

兄弟モジュールのエラーは glyph run の終了コードを変えません。コンパイルに失敗したモジュールは import できなくなりますが、それを import しないプログラムはそのまま実行されます。今はエラーが表示されますが、プロセスは main が返した値で終了します。0 以外で終了するようにすると、今は問題なく動いているツリーが失敗するようになるので、見落としではなく未決定の判断です。ツリーの健全性で終了コードを決めたいなら、それは glyph build の役割です。

現状

提供中

コミットされる読みやすい TS、ファイルごとの v3 .ts.map、.glyph に対応付け直された tsc エラー、--json の診断。glyph run はキャッシュが温まっている場合も含め、glyph build と同じものを報告します。デプロイ用ツールチェーンのソースマップのつながりは .glyph まで届きます。

予定

glyph run のクラッシュ時のスタック自体の対応付け（ローカルの実行ループでも .glyph のフレームが表示されるように）、兄弟モジュールのエラーで glyph run を 0 以外で終了させるかどうかの判断、そして LSP によるより充実したエディタでのデバッグ。
