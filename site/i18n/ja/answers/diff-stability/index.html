02 · レビューしやすい変更

エージェントの編集は差分がきれいなままか、それともファイル全体を整形し直してしまうのか？

1 行の変更は、いつでも 1 行の差分になります。Glyph には正規のレイアウトが 1 つしかないので、エージェントが実際の変更を大量の整形し直しの下に埋もれさせることはできません。

なぜ重要か

エージェントがプルリクエストを出すとき、レビューの対象は差分そのものです。本当は 1 行の修正が 200 行の整形し直しとして届いたら、何が変わったのか誰にも見えません。バグが紛れ込むのはまさにそのノイズの中です。

差分の安定性とは、差分が変更を示し、変更以外は何も示さないということです。

大部分は 2 つのルールで実現しています。それぞれを、レビューするときの差分の形で示します。

末尾カンマと、1 行に 1 要素

末尾カンマは必須です。1 行に収まらないリストは詰め直されず 1 行に 1 要素で並ぶので、要素の挿入、削除、並べ替えで隣の行が乱れることはありません。

レコードのフィールド、パラメータ、match のアーム、import でも同じです。

このしきい値にはコストもあります。名前の変更で呼び出しが 100 桁を超えると、引数リスト全体が 1 行に 1 つの形に展開されます。

正規のレイアウトは 1 つ

正しいフォーマットはただ 1 つで、glyph fmt が生成します。空白、折り返し、揃え位置はエージェントが「整える」ことのできる選択肢ではないので、意味の変更に再フォーマットが付いてくることはありません。フィールドの型を 1 つ変えれば、差分はそれだけです：

user.glyph：フィールドを 1 つ変え、1 行をレビューする 
 type User = {
   id: string,
-  age: string,
+  age: number,
   email: string,
 }

レイアウトが固定されているので、同じファイルを編集する 2 つの別々のエージェントはバイト単位で同一のフォーマットを出力します。再フォーマットによる差分も、「自分のフォーマッタと相手のフォーマッタ」のノイズもなく、git blame は行を整形し直したコミットではなく、実際に変えたコミットを指します。

レイアウトが 1 つに決まっているなら、フォーマッタはコメントを動かすのか？

以前は動かしていて、それは名前を挙げておくべきバグでした。現在のルールでは、コメントは書かれたときに上にあった要素の上に出力し直されます。レコード本体、ユニオンのバリアントの並び、配列やオブジェクトのリテラル、引数やパラメータのリスト、match の中でも同じです。

経緯 コメントが流れていった仕組みと、それを表面化させたアプリ

Glyph にはブロックコメントもドキュメントコメントの構文もないので、レコードのフィールド、ユニオンのバリアント、match のアームを説明する方法は // の行しかありません。フォーマッタは保留中のコメントを宣言と文の境界でしか出力しなかったので、構文要素の内側に書いたコメントは次の宣言まで流れていき、たどり着いた先のドキュメントのように読めてしまいました。これが表面化したのは、Glyph で Minesweeper を書いたときです。次の 2 つの宣言は実際のアプリから取ったもので（コメントは収まるように短くしています）、古いフォーマッタと新しいフォーマッタにかけた結果です。

0.1.37：fmt を 1 回かける 
type Visibility =
  | Hidden
  | Flagged
  | Revealed

// Face down. Prints as `.`.
// Face down and marked by the player.
// Face up. `Cell.adjacent` is what gets printed.
type Cell = { mine: bool, adjacent: int, visibility: Visibility }
// Number of mined neighbours. Only meaningful
// once mines are placed.
バリアントの 3 つのコメントがレコードの説明になってしまう
0.1.38：同じファイル 
type Visibility =
  // Face down. Prints as `.`.
  | Hidden
  // Face down and marked by the player.
  | Flagged
  // Face up. `Cell.adjacent` is what gets printed.
  | Revealed

type Cell = {
  mine: bool,
  // Number of mined neighbours. Only meaningful
  // once mines are placed.
  adjacent: int,
  visibility: Visibility,
}
どのコメントも説明対象の上にある

また、内部にコメントを持つ構文要素は、大きさにかかわらず常に 1 行に 1 要素の形になるので、コメントには上に置く要素があります。そのため type Shape = { w: int, h: int } は今も 1 行にまとまりますが、h にコメントを書いた時点でレコードは展開されたままになります。

詳細 これが正しさのバグに数えられる理由

これが見た目の問題ではなく正しさのバグである理由は、何も失敗しなかったことにあります。ビルドは 0 で終了し、tsc も通り、崩れた出力はそれ自体が不動点だったので、CI の glyph fmt --check は、コメントが誤った内容を語るようになったファイルでも成功しました。Glyph が取り除こうとしている失敗と同じ種類のものが、型システムではなくフォーマッタで起きていたわけです。

glyph fmt がビルドの通るプログラムを壊すことはあるか？

ありえましたし、1 件はまだ残っています。プログラムが耐えなければならないフォーマッタは、機能がないことよりも悪いものです。すでに動いていたコードを壊すからです。

  • アーム本体現在のプリンタは、先頭のトークンがブロックとして再パースされうる { であるアーム本体を丸括弧で囲みます。空のオブジェクトと、それを基にした式が該当します（({}).size は ({}.size) として出力されます）。
  • ファザー現在はファザーが整形後のファイルをパースし、その構文木を元のファイルのものと比較するので、ファイルの意味を変えてしまうレイアウトは、誰かが気づくのを待たずに最初の実行で失敗します。
経緯 ビルドできなくなった空のレコード

まず直したほうから。「空のレコード」を意味するアームは true => ({}) と書きます。文法の中で先頭の { が曖昧になるのはアーム本体の位置だけで、パーサーは波括弧の直後に key: か ... があることを要求して解決しています。空のオブジェクトにはどちらもないので、フォーマッタが丸括弧を外して true => {} と出力し直すと、アームは空のブロックとして読まれ、ファイルはビルドできなくなりました。E0223、アームが値を生成しない、というエラーです。動いているコードにフォーマッタをかけたら、コンパイルできないコードが返ってきたのです。

false => { a: "x" } のようにもともと曖昧さのないアーム本体はそのままなので、それ以外の場所で読む記号が増えることはありません。結果に対して fmt は不動点であり、出力される TypeScript も変わりません。

経緯 0.1.138 で直したさらに 2 件

0.1.138 でさらに 2 件を直しました。ブロックの中では、( で始まる行は直前の行の続きになります。0.1.137 までのフォーマッタは、load()? の後に .run() が続くものを (load()?).run() と出力していたので、let a = 1 の後では、整形後のファイルが let a = 1(…).run() という意味になっていました。現在は load()? を残して .run() を次の行にインデントして置き、e?(x)、e?[0]、e? ? は丸括弧なしで書きます。もう 1 件はユニオンの where による絞り込みで、フォーマッタがこれを落としていたため、check が拒否していたプログラムが受け入れられるようになっていました。

この背後にあるフォーマットのルールと、それが引き換えにしているものは、差分の安定性の柱のページにあります。

現状

提供中

  • 末尾カンマの必須化、1 行に 1 要素のリスト、そして glyph fmt による正規のレイアウト。ラウンドトリップでき、冪等で、エディタでは保存時に整形されます。
  • glyph fmt がコメントを場違いな場所に動かすことはありません。
  • コメントは書かれたときに上にあった要素の上に保たれる
    詳細

    コメントは書かれたときに上にあった要素の上に保たれます。レコード、リテラル、引数リスト、match の中、演算子のオペランドの間、メソッドチェーンのステップの間でも同じです。メソッドチェーンはその場合、ドットを先頭にして 1 行に 1 ステップの形になります。

限界と、次にやること

  • コード行の末尾に書いたコメントは、次の要素の上の行に移動する
    詳細

    コメントは常に独立した行に出力されるので、コード行の末尾に書いたコメント（w: int, // width in cells）は次の要素の上の行に移動します。宣言の境界を越えることはもうありませんが、移動はします。行末に残すには、コメントがどの行を共有しているかをプリンタが追跡する必要があります。

  • レイアウト上置き場所のないコメントは、動かされずに拒否されるE0500
    詳細

    インデックスの中、チェーンの途中にある呼び出しの引数の後、! や await のオペランドの前など、レイアウト上置き場所のないコメントは、もう動かされません。glyph fmt はそのファイルを拒否して元のまま残し、行番号とコメントを置くべき場所を示します。glyph check も同じ内容を警告 E0500 として報告します。

  • JSX の属性の間や、オブジェクトパターンのフィールドの間にあるコメントも拒否されます。これらは 1 行に 1 つのレイアウトなら置ける場所なので、対応予定のリストに入っています。
  • また、プリンタには長いメソッドチェーンや + の連鎖を折り返すルールがまだないため、長すぎるチェーンは代わりに最も内側の引数リストで折り返されます。これは誤った位置です。
  • 同じ編集を TypeScript で行った場合と比べる差分サイズのベンチマークも作っているところなので、この柱は確認できる数値になる予定です。
