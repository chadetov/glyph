10 · アプリに組み込む

既存のアプリの中で Glyph を導入できるか、それとも全面移行しかないのか

書き直しは不要です。アプリは TypeScript のままにして、間違えるわけにいかない部分（モデル、権限、状態遷移、金額計算）を Glyph で書きます。glyph build が出力するモジュールは、ローカルファイルと同じように アプリから import できます。バンドラの設定もパスエイリアスも要りません。

なぜ重要か

たいていのチームはアプリケーションを書き直せませんし、アプリケーションの大部分には Glyph は必要ありません。必要なのはドメインの中核です。来月 AI エージェントが編集することになり、黙って間違っていては誰も困るルールの部分です。

その中核を Glyph にしておけば、網羅的な match、キャストのないコード、検証された境界を、効果のある場所にだけ導入できます。React コンポーネント、スタイル、インフラはふつうの TypeScript のままです。

ホスト側に追加するものはない

出力されたコードが必要とするものは、すべてコードと一緒に運ばれます。

  • 相対パスの importimport は同梱の標準ライブラリも含めてすべて相対パスなので、プロジェクトの tsconfig.json にもバンドラにも何も追加する必要がありません。素の Vite の雛形がそのまま出力をコンパイル・バンドルでき、同じファイルはホスト側の tsc --strict も通ります。
  • pub による公開アプリから import するものには pub を付けます。付いていない宣言はそのモジュール内に閉じます。

これは仮定の話ではありません。外部のエンジニアがこの方法で React のカンバンボードを作りました。RBAC のマトリクス、分析用の計算式、ステータス遷移を 4 つの Glyph モジュールに置き、その上に手書きの React UI を載せています。

現状

提供中

  • 出力はそのままホストのプロジェクトに組み込めます。指定子はすべて相対パスで、prelude の型はコード自身が持ち運びます。
  • 素の Vite の雛形、ホスト側の tsc --strict、esbuild、tsx で検証済みです。
  • ハイブリッド構成はデプロイガイドに記載しています。

予定

  • glyph build --watch は .glyph ファイルを保存するたびに再ビルドしますが、Vite の開発サーバーと並べると、Glyph の変更ではコンポーネントの差し替えではなくページ全体の再読み込みになります。出力は Vite のビルドディレクトリ (デフォルトは dist/) の外に置いてください。開発サーバーはそこを監視しません。
  • std/fs や std/net を使うモジュールは、Node に触れる TypeScript と同じく、ホスト側に @types/node が必要です。
