25 · ずれないドキュメント

エージェントが読むドキュメントは生成されたものですか。それとも手書きで、内容が古くなっていますか。

生成されたものです。glyph llms --json は、診断カタログ、prelude、stdlib のシグネチャ、言語の設計判断、ツールのマニュアルをコンパイラ自身のテーブルから出力します。手書きのコピーと食い違えば、ゲートがビルドを失敗させます。エージェントが最初に読み込むドキュメントにある Glyph の例はすべてコンパイルされます。誤りを示す例も含めてです。

なぜ重要か

これは修辞的な質問ではありません。以前の正直な答えは「手書きで、しかも古い」だったからです。

  • ツールの一覧エージェント向けのブートストラップ文書には、MCP サーバーが「5 つのツールを公開する」と書かれ、5 つが挙げられていました。実際のサーバーは 7 つを提供していました。サーバー自身の説明がエージェントに真っ先に使うよう指示している 2 つは、文書に一度も登場しませんでした。
  • エラーコード58 個のエラーコードは手作業で管理する 3 つのコピーにあり、検査はコード文字列が存在するかどうかだけでした。
  • 例その文書にある 19 個の Glyph の例のうち、コンパイルされていたのは 2 個で、17 個は断片としてスキップされていました。

どれも同じ欠陥です。コンパイラについての文書が、善意の人たちの手でコンパイラと並んで保守されていました。それを読むエージェントには、どの文がまだ正しいのか判断できません。私たちにもできませんでした。

診断のための 1 つのテーブル

診断のエントリには、カタログの説明文、1 行の修正方法、詳しい説明、そしてコンパイラが実際に出した診断から取った help と note が入っています。

77 個のコードのうち 51 個には、そのコードを出す誤ったプログラムも付いていて、問い合わせた時点でコンパイルされます。残りの 26 個には、コーパスにケースがないと書かれています。

詳細 3 つのコピーを 1 つにまとめた

77 個のコードはコンパイラ内の 1 つのテーブルから出力されます。docs/error-codes.md とエージェント向けブートストラップのカタログ表はそこからスクリプトで書き出され、ずれがあればスクリプトが失敗します。以前あった 3 つのコピーを統合したところ、説明はあるのに一覧に載っていないコードが 1 つと、エスケープしたパイプ記号のせいで表を密かに壊していた行が 1 つ見つかりました。

prelude、stdlib、設計判断

詳細 エクスポートの分かれ方

エクスポートは必ず 3 つに分かれ、2 つになることはありません。129 個はすべての位置がモデル化されたシグネチャ、46 個はパラメータの型があるべき場所に ? があり、partially_modeled として数えられて残りの位置の数を示す行が付きます。165 個にはシグネチャがまったくありません。? は unknown を表示したものなので、完全なシグネチャとして公開されることはありません。

経緯 duplicate_numbers がある理由

duplicate_numbers があるのは、生成器が仕様書自身の一覧を読むからです。初めて動かしたとき、どちらも D43 と番号が付いた 2 つの異なる設計判断を見つけ、"duplicate_numbers": [43] と出力しました。重複を勝手にまとめるのではなく衝突として報告したので、誰かが気づけたのです。コンパイラには D 番号をキーにしている箇所がないので、影響を受けたプログラムはありませんでした。影響を受けたのは、引用をたどる読者です。これは修正済みです。D43 は mut-across-await の規則で、never は D47 なので、一覧は空で返ります。現在の設計判断は D1 から D49 までの 49 個です。

誤ったプログラムも読める

コンパイラのネガティブコーパスは、失敗しなければならないプログラムと、それぞれが出すべきコードの集まりです。以前は cargo test からしか見えませんでした。

ある規則が何を拒否するかを学ぼうとするエージェントこそ、このコーパスが想定する読者です。そこで今は問い合わせに答えるようになり、各ケースは問い合わせた時点でコンパイルされるので、横に並ぶ診断はこのコンパイラが出したものです。

glyph llms --negative E0008

  "meaning": "Assignment without `mut` (`x = e` should be `mut x = e`, or

  "fix": "Write `mut x = e`, or `let x = e` for a new binding",
  "negative": [ {

      "source": "module neg\n\nfn count() -> number {\n  let total = 0\n

      "message": "assignment requires `mut`",
      "help": "Glyph marks every mutation (D5): write `mut x = ...` to
               reassign an existing binding, or `let x = ...` to
               introduce a new one.",
      "range": { "start": { "line": 5, "col": 3, "offset": 53 }, ... } } } ],
  "catches": [],
  "catches_absent": "`catches/` pairs no TypeScript-accepted program with E0008"
}
詳細 カバー範囲と、catches/ のコーパス

コードを指定しないと、0.1.149 では 77 個のコードのうち 53 個にわたる 117 件のケースが一覧され、ケースのない 24 個のコードも名前が示されます。返ってきたものからカバー範囲を推測させることはしません。もう 1 つのコーパス catches/ は、tsc --strict が受け入れるプログラムと、それを拒否する Glyph を対にしたもので、該当するものがあれば同じ回答に含まれます。どちらもディレクトリそのものから埋め込まれるので、どちらかにケースを追加すれば、別の箇所を忘れずに編集しなくても回答に反映されます。

誤ったものも含め、すべての例がコンパイルされる

リファレンスを生成するのは半分にすぎません。残りの半分は、エージェントが最初に読み込む文章で、その中の例はエージェントがそのままコピーする部分です。

その文書にある Glyph のコードブロックは、コンパイルが通る完全なプログラムか、名前付きの完全な例の断片として印が付いていて、その例の行の中に含まれていなければならないかのどちらかです。

  • ブートストラップ以前は 19 個のブロックのうち 2 個がコンパイルされていましたが、今は 24 個のうち 20 個がコンパイルされ、4 個に印が付いていて、スキップされるものはありません。
  • stdlib のリファレンスstdlib のリファレンスは 8 個中 4 個から 8 個中 8 個になりました。
  • 誤った書き方コードブロックには、失敗しなければならないプログラムとして、出すコードを指定した印を付けることもできます。文書が警告している 5 つの誤った書き方はこうして載せています。E0228 を出すもの、E0008 を出すもの、ほかに 3 つです。診断と対になった警告は検査できます。文章だけで書いた警告は約束にすぎません。
詳細 文書をコンパイルして見つかった 2 つのこと

文書をコンパイルしたことで、読むだけでは決して見つからなかった問題が 2 つ見つかりました。インラインの三連バッククォートがコードブロックの開始として読まれ、250 行が 1 つのスニペットと数えられて、その中は何も検査されていませんでした。また、stdlib リファレンスにあるサーバーの実例が http.serve を呼んでいましたが、std/http はそれをエクスポートしていません。正しい関数は listen です。

受け渡しのコストと、かからなくなったコスト

11 個の MCP ツールは以前、マニュアル全文を tools/list の応答に載せていて、すべてのセッションが接続時にそのコストを払っていました。45,509 バイトの応答のうち 31,446 バイトが説明でした。今は同じ 11 個のツールで、20,386 バイトの応答のうち 8,627 バイトです。

削除したものはありません。以前の文章はツール名をキーにしてそのまま保持され、glyph llms --json の中で公開されています。呼び出す瞬間に必要な契約は説明に入っていて、残りはすべてのセッションの最初の応答ではなく、コマンド 1 つで取得できます。

詳細 件数を守るテスト

ツール一覧と文書を一緒に読むテストがあり、サーバーが提供していないツールを文書が挙げたり、件数が一覧と食い違ったりすればビルドが失敗します。「5 つのツールを公開する」に必要だったのは、この検査です。

オフラインかつローカル

これはすべてオフラインかつローカルで動きます。glyph llms は文章を、glyph llms --json はデータを、glyph llms --negative は誤ったプログラムを出力します。

同じ文章は、ネットワークはあるがバイナリのないエージェント向けに llms.txt でも提供しています。言語についてではなくあなたのコードについてエージェントが問い合わせるのは、クエリツールです。

限界

  • この文書には誤ったプログラムの件数が 2 つ出てくるが、数えているものが違う
    詳細

    この文書には誤ったプログラムの件数が 2 つ出てきますが、数えているものが違います。77 個のコードのうち 51 個は tests/negative/ の反例を持ち、glyph llms --negative は catches/ の拒否も読むので、0.1.149 では 53 個のコードにわたる 117 件のケースを一覧します。次のリリースでは、その後 catches/ に追加された 22 件の拒否が加わり、55 個のコードにわたる 139 件になります。

  • 0.1.149 では 24 個のコードがどちらのコーパスにも誤ったプログラムを持たず、回答は例をでっち上げずにそのコードの名前を示します。
  • stdlib の 340 個のエクスポートのうち 165 個はシグネチャなしで返る
    詳細

    stdlib の 340 個のエクスポートのうち 165 個はシグネチャなしで返ります。実装は tsc が検査する TypeScript で、コンパイラ自身のテーブルはそれについて何もモデル化していないため、std/result::all や std/io::println に対する glyph_symbol は、その理由とともに kind: null を返します。

  • シグネチャを持つ 175 個のうち 46 個には、まだパラメータの型の位置に ? が残っています。
  • また、この文書は取得するスナップショットであってサービスではありません。検索の仕組みも埋め込みもなく、チャットのインターフェースもありません。
