03 · 検索によるナビゲーション

エージェント（や自分）は、何がどこで定義されているかを見つけられるか

すべての構文には、検索すべき形がちょうど 1 つしかありません。素の grep（エージェントが実際にコードをたどる方法です）が、50 件の似て非なる候補ではなく、1 つの定義にたどり着きます。

なぜ重要か

エージェントはリポジトリ全体を頭に入れているわけではなく、検索します。1 つの概念に 1 つの形しかなければ検索は漏れなく、エージェントは重複を作らずに既存のものを編集します。

ある概念を 5 通りの書き方で書けるなら、検索は取りこぼしますし、既存の定義を見つけられなかったエージェントは、自信を持って 2 つ目を作ってしまいます。

詳細 同じ問いに TypeScript では答えが出ない理由

TypeScript では、変更は =、.push()、Object.assign、setter、スプレッドの陰に隠れられます。grep すべき単一のトークンがないので、「これを変更しているものはあるか」に確実な答えが出ません。

コンパイラが検索の完全さを保つ

配列を変更するメソッド（push、pop、sort、splice など 9 つ）は、mut 文の呼び出し全体としてしか書けません。それ以外の場所では E0240 になります。式の中も同じで、ヘルパーが要素を 1 つ読みながら呼び出し元の配列を並べ替えてしまう、といったケースです:

glyph check 
[E0240] `xs.sort(cmp)` changes `xs` in place, and its value is used here
 4 │   return xs.sort(cmp)[0]
   │ Help: `array.sort(xs, cmp)` returns a sorted copy and leaves `xs` alone

単独の行に書いた xs.push(4) も同じコードになり、glyph fix が mut を書き足します。逆向きは E0241 です。mut xs.concat(ys) は何も変更せず新しい配列を捨てるので、何も書き込まない行が監査に載ることはありません。

カテゴリ全体を 1 回の検索で

同じ「形は 1 つ」のルールによって、カテゴリ全体を監査できるようになります。

1 回の検索 = 1 つの完全な答え 
# every UI component
grep -rn "^component " src/

# every function
grep -rn "^fn " src/

# the entire resource-ownership surface
grep -rn "owned" src/

オブジェクトリテラルの省略記法も、コンポーネントを宣言する 2 つ目の方法も、曖昧さを解消しなければならないオーバーロードされた構文もありません。書き方が少ないのは本当に制約ですが、それが狙いです。それがあるからこそ、エージェントの検索も、あなたの検索も信頼できます。

検索を信頼できるものにするために Glyph が入れなかった構文と、lint ルールでは同じ保証にならない理由は、grep しやすさの柱のページにあります。

現状

提供中

  • 構文ごとに 1 つの正規形。
  • 変更は grep できる 2 つの形（mut）に限定し、それを付けない書き込みは、配列に対してでも標準ライブラリの Set、Store、Deque に対してでも拒否（E0240）。npm パッケージの値はどちらの方向にも判定しません。
  • キーワード 1 つでの監査（fn、component、owned、type）。

その上に重ねるもの

  • 言語サーバーが、ワークスペース全体の定義へのジャンプと参照検索を加えます。同じ保証を、エディタの中で対話的に使えます。
