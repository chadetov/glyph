Q&A

エンジニアが Glyph について聞くこと。

各回答には実例があり、最後にまだ動かないことを書いています。気になるところから読んでください。Glyph が初めてなら、10 分で始めるガイドが最初の一歩として一番早い方法です。

解決する問題

エージェントの編集が誰にも気づかれずに壊しうるものと、それぞれに Glyph がどう対処するか。

01エージェントがコードを気づかれずに壊すのを、何が防ぐのか

any もキャストもなく、match は網羅的、型は実行時に検査され、同じ場所に置いたテストがビルドのたびに実行されます。

 02エージェントの編集は差分がきれいなままか、それともファイル全体を整形し直してしまうのか？

1 行の変更は 1 行の差分になります。正規のレイアウトは 1 つだけで、詰め直しは起きません。

 03エージェント（や自分）は、何がどこで定義されているかを見つけられるか

名前は 1 つ、宣言の書き方も 1 つ。grep で必ずたどり着けます。

導入するかどうかを決める

なぜツールを増やすのではなく言語なのか、そして導入にどんなコストがかかるか。

04なぜ Go や新しい言語ではなく TypeScript なのか

エコシステムがそこにあるからです。だからファイル単位で導入できます。

 05strict な TypeScript と zod、eslint、ts-pattern の組み合わせではなぜ駄目なのか

オプションではないこと。エージェントが設定で無効にできない言語です。

 06AI を使っていなくても Glyph に価値はあるか

あります。保証の内容は、人間がそのまま恩恵を受けるごく普通のエンジニアリング上の利点です。

 07ほとんど見たことのない言語を、AI は確実に書けるのか

モデルが TypeScript について知っていることの大半はそのまま通用し、通用しない箇所はコンパイラが指摘します。

 08Glyph の新しいリリースでビルドが壊れることはないか？

プロジェクトはコンパイラのバージョンを厳密に固定するので、リリースが勝手に入ってくることはありません。glyph doctor が新しいリリースの存在を知らせ、glyph upgrade で取り込みます。

今のスタックで使う

npm パッケージ、既存のアプリ、API の境界、React。

09既存の TypeScript、JavaScript、npm のライブラリは使えますか。

使えます。どの npm パッケージでも import でき、必要な箇所には手書きの .ts シムを置けます。Glyph を .ts から import することもできます。

 10既存のアプリの中で Glyph を導入できるか、それとも全面移行しかないのか

書き直しは不要です。ドメインの中核を Glyph で書き、残りは TypeScript のままにします。出力された TypeScript は、普通の Vite アプリから他のモジュールと同じように import されます。

 11API ごとにバリデータを手書きする必要がありますか？

いいえ。型を宣言すれば、そのバリデータが生成されます。

 12API の仕様から型付きのクライアントとサーバーを生成できるか

glyph gen openapi/zod/dts：コミットされ、grep できるコードです。

 13React で使えるか。コンポーネント、フック、Context は？

JSX とフックを言語として正式にサポートし、reducer のアクションも網羅的に扱います。

 14React で Glyph がまだできないことは？

gap 番号ごとに 1 項目。それまでの書き方を添えています。

 15関数の間で可変の状態をどう共有するか

store を使います。.set/.update が書き込みの窓口になる const です。

何を作れるか

プログラムの種類ごとに見る、言語と標準ライブラリ。

16これは本物の言語ですか。それとも穴だらけのおもちゃですか。

モジュールの可視性、インターフェース境界、defer、どんな値としても使えて型を保つ match、そして slice、pad_start、fold をそろえた標準ライブラリがあります。

 17お金や、自分で制御できない入力を任せられるか

正確な小数と ID、型としての不変条件、そしてインジェクションはコンパイルエラーになります。

 18Web ページを配信できるのか、それとも JSON API だけなのか

HTML、リダイレクト、レスポンスヘッダー、フォームの POST を、サーバーを手書きせずに扱えます。

 19人が入力するプログラムは書けるか

io.read_line は stdin が閉じるのを待たずに、1 行届くたびに応答します。だから REPL やゲームループが動きます。

 20サーバーは書けるのか、それともプロセスはすぐ終了するのか

main は準備をして return します。ソケットやタイマーが残っている間はプロセスが動き続けます。Node と同じルールです。

 21バイナリデータは扱えるのか、それとも何でも文字列なのか

std/bytes はオクテットの列です。コーデックは不正な入力を読み飛ばさずに拒否し、HMAC は本物の鍵を受け取ります。

エージェントと一緒に使う

エージェントが編集の前後にコンパイラに尋ねること。

22変更を加える前に、それが何を壊すかをコンパイラが教えてくれるか？

glyph_impact：ファイルに触れる前に、箇所ごとに 1 つの判定を、決まった選択肢の中から理由付きで返します。

 23エージェントは、コードを書く前にシンボルが何なのかをコンパイラに聞けますか？

glyph_symbol：ユニオンのバリアントと、それぞれを構築する構文を 1 回の呼び出しで返します。ツールは 11 個あり、それぞれに glyph query の動詞があります。

 24ビルドが失敗したとき、コンパイラはエージェントに直し方を教えてくれるか？

診断には、問題のシンボル、正しい代替案、修正の編集が壊してはならないものが含まれます。コンパイラが自力で決められる修正は glyph fix が書き込みます。

 25エージェントが読むドキュメントは生成されたものですか。それとも手書きで、内容が古くなっていますか。

glyph llms --json は、診断、prelude、標準ライブラリのシグネチャ、ツールのマニュアルをコンパイラ自身のテーブルから出力します。手書きのコピーが食い違えば、ゲートが失敗します。

 26ラッパーがあるのに、エージェントがライブラリを直接インポートするのを止められますか？

package.json でインポートパスを禁止し、代わりに使うモジュールを指定します。そのインポートは E0115 になり、ヘルプがラッパーを示します。

エラー、エディタ、本番運用

何かがおかしいときに見えるもの。エディタからオンコール対応まで。

27エディタ、デバッグ、エラーの使い勝手はどうですか？

どの LSP 対応エディタでも使える言語サーバーと、修正方法を示す安定したコード付きのエラーがあります。

 28tsc が検出するものを、なぜ Glyph はより早く検出するのか

await の文脈、値のない match のアーム、mut の付け忘れを、出力された TypeScript ではなくソースコードに対して報告します。

 29パースが失敗したとき、その理由はわかるのか

どのフィールドか、どのルールに違反したか、違反した where 述語、そして分岐に使える code がわかります。

 30深夜 3 時に本番で壊れたとき、オンコール担当には何が見えるのか

自分のものとして読める TS、.glyph に戻るソースマップ、そして build と同じ内容を報告する run です。
