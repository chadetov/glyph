18 · 対話型プログラム

人が入力するプログラムは書けるか

書けます。io.read_line は 1 行が届いた時点で return し、stdin が閉じるのを待ちません。そのため REPL、ゲームループ、チャットクライアントは、次の行を読む前に各行に応答します。0.1.62 までは待っていました。これははっきり書いておく価値があります。それが原因で、対話型のプログラムはどれも書けなかったからです。

なぜ重要か

入力の終わりでしか return しない行リーダーは、行リーダーの名前を付けたファイルリーダーです。ファイルをパイプで通すと完璧に動くので、誰も気づきませんでした。リポジトリで stdin を読むアプリはどれもパイプから読んでいたのです。そこへ誰かがチャットクライアントを書いたところ、入力している間は黙ったままで、Ctrl-D を押した後にすべての応答を一度に出力しました。

そのアプリは、記録した JSON ファイルを再生するセッションリプレイヤーとしてリリースされ、ソースにはその理由を説明するコメントが付いていました。ほかに 3 つのアプリが、誰もそれと名指ししないまま、同じ問題に合わせた形になっていました。マインスイーパーは手番の間に再描画できず、テキストアドベンチャーは look に応答できず、REPL は入力を終えるまで何も評価しませんでした。

実例

チャットアプリのライブセッションのループ全体です。読み、適用し、出力し、繰り返す：

examples/apps/chat/main.glyph 
fn converse(limit: Option<int>) -> Server {
  let state = server.empty()
  io.println(LIVE_BANNER)
  loop {
    let text = match io.read_line() {
      Some(l) => l,
      None => { break },
    }
    match client_line(text) {
      None => { io.println(LIVE_HINT) },
      Some(sent) => {
        let done = turn(state, sent.from, sent.line)
        report(done.lines)
        mut state = done.state
      },
    }
  }
  return state
}

実際のターミナルで、各行を約 0.6 秒間隔で入力し、stdin を開いたままにして動かしたものです。左の列はプロセス開始からのミリ秒です：

glyph run examples/apps/chat/main.glyph --stdin

1826ms |    1  #general <bob> hey, is the build green?
2434ms | alice: green since 9am
2435ms |    2  #general <alice> green since 9am
3042ms | bob: /who
3044ms |       * #general: alice, bob (2)
3648ms | carol: hello?
3649ms |       * ! carol is not in any room, so there is nowhere to send that

入力した行から応答まで 1 から 2 ミリ秒です。修正前は、stdin が閉じた 6460ms まで何も出力されませんでした。通しで実行したときの最初の応答は約 1.6 秒後ですが、これは tsx の起動時間で、読み取りの遅延ではありません。

実際につまずきやすい点

末尾の \r は取り除かれるので、CRLF のファイルでも LF のファイルでも同じ行が得られ、Windows からの入力で見えない文字をデバッグする羽目にはなりません。最後の改行なしで終わる入力も、None の前にその最後の行を一度返すので、末尾に改行のないファイルの最終行が黙って捨てられることはありません。読み取りの境界をまたいで分割されたマルチバイトの UTF-8 は、置換文字にならずに保持されて完成させられます。

read_to_string は同じバッファから読み出すので、2 つは組み合わせられます。ヘッダを read_line で読んでからボディを read_to_string で読むと、2 つ目のコピーでも空文字列でもなく、残りの部分が得られます。最初に呼べば、従来どおり stdin 全体を返します。パイプで渡した 200,000 行を数えるのに約 20ms しかかからないので、1 行ずつ読んでもスループットが犠牲になることはありません。

ヘッダ行を読み、続いてボディを読む 
let header = io.read_line()
let body = io.read_to_string()

現状

提供中

io.read_line はストリームが閉じたときではなく行が届いたときに return するので、プロンプト、読み取り、応答のループはターミナルでもパイプでも同じように動きます。CRLF は正規化され、終端のない最後の行は一度だけ渡され、マルチバイト文字はチャンクの境界をまたいでも壊れず、read_to_string は同じバッファの残りを受け取ります。リグレッションテストは stdin を開いたままにしてエコーが返ってくることを要求します。ファイルをパイプで渡すテストは、壊れた実装に対しても通ってしまうからです。io.print と io.eprint は改行なしで書き込むので、REPL の > プロンプトは答えを入力する行に表示されます。io.is_terminal / io.stdin_is_terminal は、相手が人かパイプかをプログラムに教えるので、チャットアプリの --stdin のようなフラグだけが判断の手段ではなくなりました。

まだ粗い点

画面を再描画したいプログラムには、カーソル制御の手段がありません。std/io にはカーソルや画面の関数がなく、ほかの標準ライブラリのモジュールにもないので、全画面のターミナル UI を作るには、今もエスケープコードを自分で書く必要があります。
