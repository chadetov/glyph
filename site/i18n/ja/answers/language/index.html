15 · 言語としての完成度

これは本物の言語ですか。それとも穴だらけのおもちゃですか。

実際のコードベースで必要になるものは揃っています。モジュールの可視性、ジェネリクスを制約するインターフェース、後始末のための defer、そして並行処理のヘルパーです。JavaScript に頼っている部分は、そうでないふりをせずにそう明記しています。

なぜ重要か

1 ファイルは書けてもプロジェクトを構成できない言語に、コードベースを賭ける人はいません。問題になる穴は特殊なものではありません。ヘルパーを隠せるか、ジェネリクスにある能力を要求できるか、どの終了経路でもファイルハンドルを解放できるか、2 つの処理を同時に走らせて両方を待てるか。Glyph はこの 4 つに答えています。しかも、意図的に捨てたアノテーション中心の方向を蒸し返すことなく答えています。

実例

宣言は pub を付けるまでモジュール内で非公開です。そのため公開されている面は一度の検索（grep '^pub'）でわかり、ヘルパーがうっかり漏れることはありません。

可視性：デフォルトで非公開 
pub fn charge(cents: int) -> Result<Receipt, string> { validate(cents)? ... }

fn validate(cents: int) -> Result<int, string> { ... }  # module-private; importing it elsewhere is an error

interface は TypeScript と同じく構造的です。ジェネリクスが要求できるメンバーシグネチャの集合です。implements も名前的型付けの儀式もありません。そのメンバーを持つ値ならどれでも当てはまり、tsc がそれを強制します。

インターフェースでジェネリクスを制約する 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer は、ブロックを抜けるときにどの経路でも後始末を実行します。早期 return でも、エラーが投げられた場合でもです。複数の defer は後入れ先出しで実行され、owned ハンドルとも組み合わせられます。また std/task は、切り離された Promise を放置するのではなく、並行処理を 1 つのライフタイムにまとめて待ち合わせます。

defer と構造化並行性 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])

正直に言っておくと、Glyph は TypeScript にコンパイルされ JavaScript エンジンで動くので、評価順序、値渡しと参照渡し、等価性（== は === で、オーバーロードはありません）、シングルスレッドでガベージコレクションのあるモデルは、新たに作ったものではなく受け継いだものです。仕様書は今これらを、自分で調べて気づくものではなく保証として明記しています。手動のメモリ管理や GC のないモデルはロードマップにありません。それは TypeScript にトランスパイルする言語の範囲外です。

if がないので、match がすべてを担う

網羅性の話を聞いた TypeScript 開発者が最初に聞くのは、match が本当に汎用の条件分岐なのか、それともユニオンを分解する便利な書き方にすぎないのか、ということです。答えは前者で、それを示すのが代入です。let や mut の値全体になっている match は、文が受け取れるものなら何でも受け取れます。アームはブロックにでき、await でき、外側のループから break でき、代入先の束縛を読むこともできます。最後のものを使えば、if なしでループを通して状態を畳み込めます。

リンクチェッカーより：コードブロックの追跡と、await するアーム 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}

どちらもアームごとに束縛へ代入する素朴な switch にコンパイルされるので、await は外側の async 関数の中に置かれ、累積値は TypeScript が推論できる普通の変数になります。大きな式の中、たとえば引数やオペランドとして使われた match は今もクロージャになるので、そのアームは単一の式でなければなりません。それ自身の let に持ち上げれば、この制限はなくなります。どちらのスニペットも examples/apps/linkcheck/main.glyph からのもので、これはまさにこの種の問題を見つけるために書かれた Markdown のリンクチェッカーです。

パターンで 2 段以上深い形を指定できる

複数のフィールドを持つバリアントはレコードを運ぶので、形を認識したいアームはレコードのフィールドの中まで入り込む必要があります。0.1.90 までは、フィールドの位置には名前しか書けませんでした。名前を変えることはできても、それだけでした。そこでタグをマッチさせるとコンパイルエラーになり、入れ子のコンストラクタはパーサーが扱えませんでした。回避策はすべてのフィールドを束縛して、階層ごとに入れ子の match を書くことで、赤黒木のリバランスのようなものでは別のプログラムになってしまいます。アームがケースと対応しなくなり、各階層で上の束縛を引き回すことになります。

赤黒木のリバランスの回転ケース 1 つを、1 つのアームで 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}

今はフィールドにどんなパターンでも書けます。バリアントのタグ、入れ子のコンストラクタ、入れ子の分解、リテラル、配列パターンです。書く前に知っておくべき帰結が 1 つあります。値を検査するフィールドは失敗しうるので、そのアームはもうバリアントを網羅したとは数えられません。Node のアームが Node({ color: Red, ... }) だけの match は、兄弟のアームか else が残りを引き受けるまで、網羅的でないと報告されます。チェッカーが網羅性を証明するのはタグの集合についてであって、フィールドの直積についてではないので、Red のアームと Black のアームを合わせれば Node を網羅する、とは判断しません。catch-all を求めるのは、実行時に match が末尾から抜け落ちることを許さない解釈です。数えるバリアントがまったくない場合も同じです。どのアームもフィールドを検査する、素のレコードに対する match には、後ろに else が必要です。

意外かもしれない影響が 1 つ、配列の位置に及びます。以前はアーム全体としての [Black] が任意の 1 要素配列にマッチするとみなされていたので、それに頼った match は網羅的と認定され、[Red] でもそのアームに入っていました。ここでも PascalCase の要素はバリアントの参照なので、そうした match は今、長さ 1 の配列に対して E0208 になります。要素を束縛して、それ自体を match してください。下の変換処理はまだ古いままで、検査の側が先に提供されたのはそのためです。

そしてコンパイラは match が何を生んだかを知っている

次の質問が、これが本当に役に立つかどうかを決めます。分岐から値を束縛したとき、Glyph はその型を知っているのか、それとも肩をすくめて後で tsc に任せるのか。0.1.45 までは任せていました。match 式はすべて unknown と型付けされていたので、言語で唯一の分岐構文から出てきた値は、そこから先は型がありませんでした。今は match はアームの型が一致すればその型を取り、T.parse は Result<T, Array<Issue>> を返すと分かっています。これは実際のコードの多くが分岐する形です。

割り勘アプリより：アノテーションなしで、i は number 
let wire = match WireLedger.parse(decoded) {
  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },
}

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...
}

どちらの半分も、以前は気づかれずにおかしくなっていたものです。このループは wire.expenses.entries() を出力します。反復対象の型が unknown のときは代わりに Object.entries(...) を出力し、i は文字列 "0" になります。これは正しい TypeScript なのでビルドはきれいに通り、プログラムは 1:a のつもりで 01:a と出力していました。また wire.expensez は今、生成された TypeScript 上の TS2339 ではなく、.glyph の行で Glyph から [E0210] type WireLedger has no field expensez として報告されます。型の合流は先頭での等価性です。return で終わるアームは投票せず、型が食い違うアームがあれば結果は以前と同じく unknown のままです。1 段深く見るのは型引数だけなので、None => [] は match 全体を台無しにせず Array<string> のアームと一致し、その後のループも number を束縛します。record.get に対する同じ連鎖も同じ理由で動きます。std/record の 6 つの関数はすべて、渡したレコードから値の型を引き継ぎます。このスニペットは examples/apps/settle/main.glyph からのもので、この変更で不要になったアノテーションが付いていました。

依存関係リゾルバより：検索、空のフォールバック、インデックス付きの走査 
let path = match record.get(res.reached, name) {
  Some(p) => p,
  None => [],
}

for i, hop in path {               # i is a number, so the indent nests
  let indent = string.repeat(STEP, i + 1)
  mut out = array.push(out, "${indent}${hop}")
}

これが最もコストの大きかった形です。Record<string, Array<string>> に対する record.get は Option<Array<string>> で、[] は要素の型が特に決まっていない配列です。そのため 2 つのアームは Array で一致し、要素の型は型を持っている方のアームから取られます。0.1.55 までは等価性で比較されていて、[] は不一致とみなされ、下のループは診断が 1 つもなく tsc --strict も通るビルドで 01:x と出力していました。コードは examples/apps/depsolve/main.glyph で、以前は冒頭に let path: Array<string> があり、このアノテーションが外せない理由を説明する 3 行のコメントが付いていました。

pad_start は自分で書く必要があるか

実際のプログラムで最初にぶつかる穴は、型システムの機能ではありません。string.slice を使おうとしたら何もない、というものです。ドッグフーディングを 5 回続けて同じ一覧が報告され、0.1.47 までは、このリポジトリの 6 つのアプリが自前の repeat を、5 つが自前の pad_start を持ち、どれも fold を使うべき場所にループを書いていました。この 11 個の名前は今は提供されていて、それを持っていた 7 つのアプリすべてからコピーが削除されています。

追加されたもの 
string.repeat(s, n)           string.slice(s, start, end?)       array.fold(xs, init, f)
string.pad_start(s, w, pad?)   string.index_of(s, needle, from?)  array.index_of(xs, x)
string.pad_end(s, w, pad?)     string.replace_all(s, from, to)     array.flat_map(xs, f)
string.trim_start(s) / trim_end(s)

# the 25-line block six apps each carried, and what replaced it:
let total = array.fold(expenses, 0, fn(sum, e) { sum + e.cents })
io.println("${string.pad_end(name, width)}  ${string.pad_start(amount, 9)}")

そのうち 3 つは、意図的に TypeScript の同名の関数と違う動きをします。repeat は負の回数に対して、TS のように例外を投げるのではなく "" を返します。そのおかげで、すでに長すぎる文字列に対しても repeat(pad, width - len(s)) が安全です。2 つの index_of はどちらも -1 ではなく Option<number> を返します。-1 は本物のインデックスが通る場所ならどこでも型チェックを通ってしまい、呼び出し位置から遠く離れた場所で失敗する数値だからです。置換は replace_all としてのみ提供されるので、1 か所だけをこっそり置き換える String.prototype.replace と混同する、最初の 1 つだけの形はありません。

fold は、タイプ量を減らすのではなく柱の 1 つを支えるものです。mut は状態が変わるすべての場所を grep できる形で記録したものですが、fold がないと、grep mut はレビュアーが気にするものを何も変更しない数え上げのループだらけになります。手書きの実装を削除したことで、examples/apps/ の変更箇所は 192 から 161 になりました。この書き換えはレビューではなく出力で確認しました。7 つのアプリすべてを固定の入力で書き換えの前後に実行し、標準出力、終了コード、HTTP レスポンスの 26 ファイルがすべてバイト単位で一致しました。

ディレクトリを走査して、何が壊れたかを判別できるか

std/fs は 6 つの関数を提供していましたが、ディレクトリを一覧するものはありませんでした。このリポジトリのリンクチェッカーは stdlib を飛び越えて node の readdirSync を使い、どのパスがディレクトリかは、読もうとして返ってきた errno を調べて判断していました。どちらも修正済みです。fs.read_dir は 1 階層下のエントリ名を返し、fs.is_dir は fs.exists と同じく bool で答えます。fs.stat は is_dir、is_file、バイト単位の size、エポックミリ秒の modified からなる FileInfo を返し、この時刻は time.format_iso でそのまま表示できます。再帰的な walk や glob はありません。走査はこの 3 つと path.join で 10 行ほどで書けます。

失敗の側はもっと大きく変わりました。FsError.kind は { tag: string } で、分類は NotFound だけでした。そのため「そのパスはディレクトリだ」と「そのパスが存在しない」を区別するには errno の文字列を比較する必要がありました。今は、プログラムが実際に回復処理を行う 5 種類に名前があり、名前のない errno は Other の末尾にそのまま入ります。

チェッカーはこの分類が閉じていることを知っているので、err.kind に対する match は、自分で宣言したユニオンと同じ基準で検査されます。6 つすべてを扱えば else は要らず、1 つ漏らせば fs.ErrorKind を名指しした E0200 でビルドが失敗します。fs.FsError と fs.FileInfo のフィールドも検査されるので、err.mesage は生成された TypeScript に対する tsc のエラーではなく、Glyph のソースに対する E0210 になります。

ツリーを走査し、何がおかしかったかを名前で示す 
let names = fs.read_dir(dir)?
for name in names {
  let child = path.join([dir, name])
  match fs.is_dir(child) {
    true  => visit(child),
    false => {
      let info = fs.stat(child)?
      report_size(child, info.size)
    },
  }
}

match err.kind {                        # no else arm: E0200 if you miss one
  fs.ErrorKind.NotFound         => io.eprintln("no such path"),
  fs.ErrorKind.NotADirectory    => io.eprintln("that is a file"),
  fs.ErrorKind.IsADirectory     => io.eprintln("that is a directory"),
  fs.ErrorKind.AlreadyExists    => io.eprintln("already there"),
  fs.ErrorKind.PermissionDenied => io.eprintln("cannot read it"),
  fs.ErrorKind.Other({ code })   => io.eprintln("errno ${code}"),
}

同じアプリから出た小さなものが 2 つ、一緒に入りました。regex.captures_all は、マッチしたテキストだけでなく、すべてのマッチのキャプチャグループを返します。これでフラットな key=value の走査が手書きのループでなくなります。また task.pool_settled は、all_settled の失敗時の振る舞いを持った task.pool です。並行数に上限があり、タスクごとに 1 つの結果が返り、ホストが 1 つ落ちても失うのはそのホストの結果だけで、プールがそれまでに集めた結果をすべて失うことはありません。

この検査は実際に動いています。上の match から PermissionDenied のアームを消すと、glyph check --no-tsc は E0200 で止まります。fs.ErrorKind に対する網羅的でない match で、欠けているバリアントは PermissionDenied です。stdlib のモデルを最初に書いたときは戻り値の型しか扱っていなかったので、このような match はきれいにコンパイルされ、実行時に例外を投げていました。今は fs.FsError、fs.FileInfo、fs.ErrorKind のフィールドとバリアントの形もモデル化されています。

それが正しい関数だと、どうしてわかるのか

それを求めたアプリが回避策をやめるまで、リリースを完了とみなさなかったからです。ライブラリ関数を提供することと、回避策がそれより長生きすることは別の話です。そこで、この 4 つを追加した変更で、リンクチェッカーにあったコピーも削除しました。readdirSync の import、2 つの errno 文字列の比較、97 行の手書きスキャナ、そして最初の失敗で止まるプールです。合計 122 行が消えました。

そのうち 2 つの削除はプログラムの動作を変えたので、その違いは議論ではなく測定で確かめました。読み取れないディレクトリを含むツリーに旧版と新版を向けると、新版は permission denied と出力してそのパスを読めないものとして数えます。旧版は errno が EISDIR かどうかしか聞けなかったので、そのパスをレポートからまるごと落としていました。3 つの URL のうち 1 つで例外を投げさせると、pool_settled は 3 行すべてを出力して失敗を名指ししましたが、pool は何も出力せずに未処理の reject で終了し、成功した 2 つの結果も道連れにしました。

スキャナの書き換えは設計上の懸念も解消しました。参加しなかったキャプチャグループは、空文字列にマッチしたグループと同じく "" として読まれるので、captures_all では選択肢のどの分岐がマッチしたのかわからないように見えました。実際にはわかります。各分岐のグループを、欲しい部分ではなく構文全体を囲むように書けばよいのです。マッチしたグループは `、[、!、< のいずれかで始まり、空にはなりません。空になりうる部分、つまりリンク先はその内側に入れ子になり、判定に使うことはありません。これで 180 行の文字単位の走査が、2 つのパターンと 12 行の振り分けになりました。リポジトリ自身のドキュメントと、壊すために作った fixture の両方で、出力はバイト単位で一致しました。

お金の計算に浮動小数点数は使わない

フィンテックの評価をその場で打ち切らせる穴は、IEEE-754 の number でお金を扱うことです。そこでは 0.1 + 0.2 は 0.3 にならず、253 を超える値は気づかないうちに精度を失います。std/decimal は BigInt の上に作った正確な 10 進固定小数点です。任意精度の整数に固定桁数の小数部を持たせたもので、加算、減算、乗算は正確で、除算にはスケールと丸め方を明示します。不正な金額はパースすると Err になり、黙って NaN になることはありません。

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

大きな整数を正確に扱う必要がある場合、たとえばアカウント ID やカウンタには bigint 型があります。リテラルは 123n で、TypeScript の本物の bigint として出力されます。bigint 型のレコードフィールドは境界で typeof === "bigint" を検証するので、JSON の number として送られてきた ID は、253 を超えて黙って丸められるのではなく拒否されます。

非同期コールバックにようやく型ができた

関数型は fn(A) -> T しかなく、これは (a: A) => T として出力されます。非同期の本体はこれに合わないので、遅延タスクを返す関数や非同期ハンドラのレコードはアノテーションなしにするしかなく、チェッカーはそこで検査をやめていました。async fn(A) -> T がその欠けていた型です。(a0: A) => Promise<T> として出力され、戻り値のない async fn() は () => Promise<void> になります。

Glyph は tsc に任せず、自分で両者を区別します。非同期関数が期待される場所に普通の関数を渡すと、return では E0204、呼び出しの引数では E0211 になり、メッセージには両方の側が示されます。判定しないのは戻り値が void の場合だけで、TypeScript ではそこにどんな関数でも置けます。

遅延タスクと、ハンドラのマップ 
fn task_for(url: string) -> async fn() -> Fetched {
  return async fn() -> Fetched { return { url: url, body: await fetch_one(url) } }
}

type Handler = async fn(string) -> string

async fn dispatch(routes: Record<string, Handler>, name: string, arg: string) -> string {
  return match record.get(routes, name) {
    Some(h) => await h(arg),
    None    => "no route",
  }
}

再帰的な型を、最後までマッチする
