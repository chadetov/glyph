27 · パースの失敗

パースが失敗したとき、その理由はわかるのか

わかります。どの問題もフィールドを名指しし、値がどのルールに違反したかを示し、分岐に使える code を持っています。where 述語で制約されたフィールドは述語そのものを報告するので、拒否の内容から grep で、その制約を課した行までたどれます。

なぜ重要か

「このペイロードは不正です」と言うだけのバリデータは、仕事の半分しかしていません。ハンドラはまだ判断しなければなりません。フィールドを入れ忘れたクライアントなのか、4 文字のパスワードを送ってきたクライアントなのか。一方は 400 で、もう一方は 422 です。バリデータが教えてくれなければ、バリデータがすでに持っていた情報を取り戻すために、同じボディを 2 つの異なる型で 2 回パースすることになります。

Glyph で認証 API を作ったときに、まさにそれが起きました。password キーがまったくないサインアップが weak_password として返ってきたのです。キーがない場合と短すぎる場合とで、同じ文字列が生成されていたからです。

実例

1 つの型に、1 つの制約：

signup.glyph 
pub type Password = string where value.length >= 8

pub type Signup = {
  email: string,
  password: Password,
}

4 つの不正なペイロードに、4 つの異なる答え。それぞれが 1 つの Issue で、code | path | message の形で示しています：

Signup.parse(...) 
// { "email": "user@example.com" }
missing     ["password"]  field `password` is required

// { "email": "user@example.com", "password": "short" }
refinement  ["password"]  expected Password (string where value.length >= 8)

// { "email": 42, "password": "longenough" }
type        ["email"]     field `email` must be string

// [1, 2, 3]
type        []            expected Signup (an object), got an array

肝心なのは 2 つ目です。value.length >= 8 は型のところに一度だけ書かれ、拒否はそれをそのまま引用します。HTTP 422 のボディからその文字列を grep に貼り付ければ、それを生んだ宣言にたどり着きます。エラーメッセージの層にルールのコピーを持つ必要は誰にもありません。そのコピーこそが、両者がずれていく原因です。

4 つ目は、以前はメッセージが悪いどころではありませんでした。typeof にとって配列はオブジェクトなので、必須フィールドのないレコードは配列をそのまま受け入れていました。また、[1, 2, 3] を送ると、宣言されたフィールドごとに 1 つずつわかりにくい問題が返ってきて、リストを送ったことに触れるものは 1 つもありませんでした。

ネストした型は自分で答える

型が独自のディスクリプタを持つフィールドは、その型の parse で検証され、問題はパスの先頭にフィールド名が付いて返ってきます。そのため 2 段下にネストした Password は ["body", "password"] を報告し、しかも自分のメッセージも持っています。何も再実行せずに、同じ問題から場所と理由の両方がわかります。

文字列ではなくコードで

Issue は省略可能な code を持ちます："missing"、"type"、"refinement"、"unexpected" のいずれかです。分岐にはこれを使ってください。メッセージのテキストでマッチするのは、Glyph が取り除こうとしている脆さそのものです。メッセージはレスポンスボディを読む人間のためのものです。

メッセージを読まずに 400 と 422 を分ける 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code は省略可能なので、手で組み立てた Issue も、これが導入される前に書かれた利用側のコードも、変更なしでコンパイルできます。

現状

提供中

レコードと where 型は、失敗したフィールドだけでなく、失敗したルールも報告します。必須フィールドがない場合は "missing"、形が違う場合（オブジェクトでない、または配列の場合を含む）は "type"、基底の型は通ったが述語で失敗した値は "refinement"、型が宣言していないキーは "unexpected" です。refinement は述語を引用します。型がディスクリプタを持つフィールドはそれに処理を委ねるので、ネストした問題は完全なパス付きで届きます。省略可能なフィールド（f?: T）が missing として報告されることはありません。

改善中

限界が 2 つあります。独自のディスクリプタを持たないもの、つまり制約のない型パラメータや、手書きの .d.ts から import した型で型付けされたフィールドは、今も平坦な検査と "type" の問題になります。コンパイラはそれらのディスクリプタを合成しないので、その宣言に glyph gen dts を実行するとディスクリプタが得られます。また、Issue という名前の型を独自に宣言したモジュールは、以前は出力されたファイルの中で prelude の型を覆い隠し、そのモジュールのディスクリプタをすべて壊していました。0.1.60 以降、その宣言は型名を書いた行で E0110 になるので、生成されたコードについての tsc エラーを読む代わりに、問題の場所がわかります。
