23 · 赤いビルドを直す

ビルドが失敗したとき、コンパイラはエージェントに直し方を教えてくれるか？

何が間違っているかを、パースが必要な文章ではなくデータとして伝えます。2 つの型、module::name の形の問題のシンボル、そして誤ったものの代わりに正しく置けるものの有限のリストです。glyph check --agent は、修正の編集が壊してはならないものも加えます。答えが完全に決まる場合は、glyph fix がそれを書き込みます。

なぜ重要か

コンパイラを相手にしたエージェントのループは、エラーを読み、編集を推測し、ビルドし直す、の繰り返しです。被害が生じるのは推測の段階で、それはエラーが文字列だから起きます。

  1. エラーを読む
  2. 編集を推測する
  3. ビルドし直す

コンパイラはそのすべてを知っていました。ユニオンのバリアントとそのペイロードを知っていて、else を足せば網羅性の保証を失うことも知っていて、返答の 1 行手前でその両方を捨てていたのです。

詳細 文字列が招く 2 つの間違った編集

「OrderStatus に対する網羅的でない match」と読んだエージェントは、match にアームが足りないことはわかります。しかし欠けているバリアントが何を持つかはわからないので、Paid("tx_1") と書いて、次の診断で間違いを知ります。あるいは「網羅的」という言葉を読んで else のアームを追加し、診断が守るために存在していた保証を捨てたままビルドを通してしまいます。

答えの読み方

取り上げるべき点が 3 つあります。

  • causecause は問題のシンボルで、診断が置かれている宣言である entity とは別のものです。ここでは編集は main::describe で行われ、合わせるべき形は orders::OrderStatus から来ています。
  • constraintsconstraints は修正ではありません。それぞれはコンパイラがすでに強制していることで、診断を満たす編集がその背後にある保証を壊さないように書き出されています。
  • symbolssymbols は、診断が名前を挙げたすべてのシンボルに対する glyph_symbol の答えなので、エージェントの次の編集に 2 回目の呼び出しは要りません。

キーは常にすべてそろっています。コンパイラが持っていない情報は、キーの欠落ではなく明示的な null として届くので、「ない」ことの表し方はどのコードでも、CLI と MCP のどちらでも 1 つだけです。

詳細 つながるアドレス、else の制約、symbols_absent

どちらも他のツールが受け取るアドレスなので、何も導き直さずに答えをつなげられます。

2 つ目の制約こそ、このキーが存在する理由です。else のアームは正当で、ビルドを通すことはできますが、制約はそれを選んだときに何を失うかを述べています。

ツールが拒否したシンボルは理由とともに symbols_absent に入るので、「調べなかった」と「調べたが存在しない」が区別されます。

答えが決まる場合は、コンパイラが書き込む

glyph fix が適用するのは、コンパイラが自力で決められる修正だけです。使われていない import、型検査器がちょうど 1 つの候補を算出した、バリアントでないアームの先頭、そしてちょうど 1 つの宣言済みフィールドと 1 文字違いの、レコードが宣言していないフィールドです。上の match はこれに当たりません。

上の match に対する glyph fix src 
glyph fix: removed 0 unused import(s) across 0 file(s).
glyph fix: declined E0200 in src/main.glyph: the compiler does not
           determine what a missing arm should do, so `glyph fix`
           writes none: add an arm for each of `Paid`, `Cancelled`.
           `glyph check --agent` gives the pattern each case takes.

// src/main.glyph is unchanged, and glyph check still fails with E0200.

コンパイラは、どのケースが欠けていて、それぞれがどんなパターンになるかを知っています。しかし注文が Paid のときにプログラムが何をすべきかは知りません。コンパイラが書く本体は、どれもコンパイルが通るだけの推測になります。

経緯 0.1.128 までの glyph fix が書いていたもの

0.1.128 までの glyph fix はその推測を書いていました。ケースごとに 1 つのアームを追加し、その本体はケースを出力して process.exit(1) を呼ぶものでした。するとプログラムは check、tsc、build を通り、glyph query variants は match を網羅的と報告したので、欠けたケースはコンパイルエラーから実行時のクラッシュに変わり、それを指摘するものは何も残りませんでした。

詳細 アームの出どころと、見送りの報告のしかた

そこでこのルールは修正を見送り、ケースの名前を挙げます。アームを書くのに必要なものは、すべて上の --agent の答えにあります。missing_variants と、symbols の下にある各バリアントの construct の書き方です。アームを書くのはあなたかエージェントです。コンパイラが振る舞いを推論できない他のコードと同じです。

glyph fix が書くものは、推測なしで書かれます。答えを決められないルールはすべて、見送ったことと理由を、適用した内容と同じ出力に表示します。タイポから 1 文字違いのフィールドが 2 つあれば、それは 1 つではなく 2 つであり、どちらかを選ぶのではなくそう伝えます。

コード自身の説明を、データとして

glyph --explain <CODE> --json は、詳しい説明、1 行の help、ドキュメントの URL、そしてコンパイラのネガティブコーパスにある誤ったプログラムと、それに対してこのコンパイラが出す診断の組を返します。

診断は保存されたものではなく問い合わせのたびにコンパイルされるので、コンパイラが実際に言う内容からずれることはありません。

glyph --explain E0200 --json 
{
  "code": "E0200",
  "title": "non-exhaustive match",
  "explanation": "A `match` over a tagged union must handle every variant.
    Unions are sealed (D9): adding a variant later forces every match to be
    updated, so a missing variant cannot silently fall through at runtime ...",
  "help": "Add an arm for each missing variant.",
  "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200",
  "counter_example": {
    "name": "alias_of_local_union_not_exhaustive",
    "expected_error": "E0200",
    "files": [ { "path": "alias_of_local_union_not_exhaustive.glyph",
                 "source": "module main\n\ntype Shape =\n  | Circle\n ..." } ],
    "diagnostic": { "code": "E0200",
                    "message": "non-exhaustive match on `Shape`: missing variants `Tri`",
                    "cause": "alias_of_local_union_not_exhaustive::Shape",
                    "related": ["Circle", "Square", "Tri"],
                    "missing_variants": ["Tri"] },
    "corrected": null,
    "corrected_absent": "`tests/negative/` pairs no repaired program with a case:
      an entry is a wrong program and the code it draws. A fix invented here would
      compile nowhere and be checked by nothing."
  }
}

コーパスが扱っていないコードには、作り話の例ではなく、counter_example: null と、コーパスにそのケースがないことを述べる文が返ります。コーパスは扱っている範囲を主張し、それ以外については何も主張しません。

詳細 glyph llms --negative で得られるコーパス全体

glyph --explain が渡すのはコードごとに 1 ケースです。コーパス全体も読めます。glyph llms --negative E0200 はそのコードを出す誤ったプログラムをすべて、問い合わせのたびにコンパイルして表示します。tsc --strict が受け入れるプログラムと、それを拒否する Glyph を組にした 2 つ目のコーパスがあれば、それも並べて返します。コードを指定しなければ、70 個のコードのうち 46 個にわたる 102 ケースを一覧し、ケースのない 24 個の名前を挙げます。カバー率は返ってきたものから推測するのではなく、明記されます。これを含め、コンパイラが自分自身について公開する内容は専用のページにあります。

現状

提供中

  • すべての診断は expected、actual、cause、alternatives、related、module、file、explain を持ち、コンパイラがその情報を持たない場合はそれぞれ明示的な null になる
    詳細

    すべての診断は expected、actual、cause、alternatives（alternatives_kind が、それが fields、members、variants、literals、exports のどれを並べたものかを示し、エラーが発生した場所で設定されます）、related、module、file、explain を持ちます。これらは導き直したものではなく、コンパイラが発生させたエラーから埋められ、コンパイラがその情報を持たない場合はそれぞれ明示的な null になります。

  • file は解決ルートからの相対パスで、レポートはそのルートを project_root に記すので、そのまま開けます。
  • glyph check --agent は診断ごとに constraints と symbols を加えます。
  • glyph fix は 3 つのルール（E0106、E0210、E0220）を適用し、見送ったものはすべて理由とともに示します。E0200 もすべてそうで、報告はしますが書き込みはしません。E0106E0210E0220
  • glyph --explain <CODE> --json はコンパイル済みの反例付きで説明を返し、glyph llms --negative <CODE> はそのコードを出す誤ったプログラムのコーパス全体を返します。

限界

  • E0211 の cause は null です。呼び出しの引数で問題となるシンボルはパラメータで、module::fn.param は識別子の語彙で表せないため、この null は抜け漏れではなく意図的なものです。E0211
  • 反例の corrected は常に null です。ネガティブコーパスはケースに修正済みのプログラムを組み合わせておらず、70 個のコードのうち 24 個にはケースがまったくないからです。
  • glyph fix が書くのは 3 つのルールだけで、網羅的でない match のアームは書きません。それはケースとそのパターンを診断に載せたうえで、あなたかエージェントに任されます。
  • 見送るものは、すべてはっきりと見送ったと伝えます。
