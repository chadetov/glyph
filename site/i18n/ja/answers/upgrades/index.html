08 · アップグレード

Glyph の新しいリリースでビルドが壊れることはないか？

自分で求めない限り、壊れません。Glyph のプロジェクトはコンパイラを厳密なバージョンに固定するので、今朝公開されたリリースが今日の午後のビルドに入り込むことはありません。1.0 より前のリリースは、昨日コンパイルできたコードを拒否する診断を追加してもよいことになっていて、たいていはそれがリリースの目的です。だから取り込むかどうかはあなたが決めることで、それはコマンド 1 つで済みます。

なぜ重要か

ほとんどのツールはキャレットで固定します。パッチリリースはバグ修正だからです。1.0 より前のコンパイラはそうではありません。Glyph の仕事はプログラムを拒否することであり、それが上達するとは新しいエラーが増えることです。import に対するより厳しい検査、以前はすり抜けていた網羅性の穴、型検査器がモデル化していなかった引数の数。こうしたリリースは良いリリースです。そして同時に、日付ライブラリを追加するために実行した npm install 経由で入ってきてほしくないものでもあります。

そのため glyph init は ^ を書きません。0.x のバージョンでもキャレットはパッチを変動させるので、そこが落とし穴です。^0.1.9 は、それ以降のすべての 0.1.x を黙って受け入れます。

生成直後の package.json 
"devDependencies": {
  // exact. no caret, no tilde.
  "@glyphlang/glyph": "0.1.72",
  "typescript": "^6.0.0",
  "tsx": "^4.19.0"
}

隣にある package-lock.json もコミットすれば、新しくクローンしたリポジトリは、その後に出たものではなく、テストしたツールチェーンでビルドされます。

もう半分

固定にはわかりやすい失敗の形が 1 つあります。古いコンパイラのまま 1 年過ごし、それに気づかないことです。手元のマシンには知らせてくれるものが何もなく、覚えて見に行かなければならない Web サイトは連絡手段とは言えません。そこで、セットアップについて何かを尋ねたときに、コンパイラが知らせます：

glyph doctor 
glyph — 0.1.72
  [update]   0.1.73 is published — `glyph --update` moves this compiler, `glyph upgrade` moves a project's pin
             what changed: https://glyphlang.io/versions/

glyph doctor — JavaScript toolchain
  [ok]       node: v22.1.0
  [ok]       tsx: tsx v4.19.0
  [ok]       tsc: Version 6.0.2
All good. `glyph run` and `glyph build --check` are ready.

新しいリリースが見つかっても、終了コードは決して変わらないので、CI で実行しても安全です。公開されたリリースはツールチェーンの故障ではありませんし、誰かが 10 分前にリリースしたからといって、成功していたパイプラインが失敗に変わるべきではありません。マシンがオフラインなら、確認はそう伝えて先に進みます。--offline を付ければ確認自体を飛ばし、ネットワークにはまったくアクセスしません。

レジストリにアクセスするものは他にありません。build、run、check は決してアクセスしません。ビルドのたびに外部と通信するコンパイラは、別の製品です。

アップグレードを取り込む

変わるのは 1 行で、いつ変えるかはあなたが決める 
$ glyph upgrade --dry-run
glyph upgrade: would move /app/package.json from 0.1.72 to 0.1.73 (nothing written).

$ glyph upgrade
glyph upgrade: /app/package.json now pins 0.1.73 (was 0.1.72).
glyph upgrade: what changed: https://glyphlang.io/versions/
glyph upgrade: build before you commit; a new release may report diagnostics
               this project did not have.

1 行を書き換えて npm install を実行します。ソースコードには触れませんし、アップグレードが完了したふりもしません。その後にビルドすることが肝心です。取り込んだばかりのリリースは、あなたのコードがまだ出会っていない判断を下してよいことになっているからです。--to <version> で特定のバージョンを指定でき、戻したいときは古いバージョンも指定できます。--no-install を付ければ、インストールはあなたに任されます。

プロジェクトではなくツールを更新する

upgrade が動かすのは package.json の中の固定バージョンです。古くなっているのが PATH 上のコンパイラである場合、それは誤ったコマンドですが、しばらくの間 doctor はそれでもこのコマンドを表示し、グローバルインストールに対して、ないかもしれないマニフェストを指し示していました。もう半分を担うのが glyph --update です。この分担は今では偶然ではなくルールです。--version、--help、--explain と同じく、フラグはツールに作用し、サブコマンドはあなたのコードに作用します。--update-dry-run は、実行するはずだった npm のコマンドを表示したところで止まります。

glyph --update 
$ glyph --update
glyph 0.1.72 is installed; 0.1.73 is published.
Release notes: https://glyphlang.io/versions/
A 0.1.x release may reject code that compiled before, so read the notes for anything between these two.

Running: npm install -g @glyphlang/glyph@0.1.73
   ... npm output ...

npm finished. Confirm with:
    glyph --version

更新するのは、識別できるインストールだけです。npx 経由で使っているコンパイラ、Glyph のソースツリーからビルドしたコンパイラ、見覚えのないパスにあるコンパイラについては、コマンドを表示するだけで何も上書きしません。推測で Homebrew のバイナリや誰かの cargo build の成果物を置き換えると、PATH が誰も選んでいないものを指すことになるからです。また、更新が成功したとまでは主張しません。npm は取得できなかった optionalDependency を飛ばしたまま 0 で終了することがあり、実際に Glyph のリリースがプラットフォーム用のバイナリなしで出荷されたことがありました。そのため最後の行では成功を断言せず、確認方法として glyph --version を示します。

現状

提供中

生成されたプロジェクトはバージョンを厳密に固定するので、リリースが勝手にビルドに入り込むことはありません。glyph doctor は使っているコンパイラをレジストリと比較して報告し、リリースノートへのリンクを示します。終了コードに影響することはなく、build/run/check から呼ばれることもありません。glyph upgrade は固定バージョンを動かしてインストールし、古いプロジェクトのキャレット指定も読み取るので、既存のプロジェクトも厳密な固定に移行できます。glyph --update はグローバルな npm インストールのコンパイラそのものを更新し、それ以外の方法で入ったコンパイラについては、推測せずに報告します。

改善中

リリースノートは 0.1 系全体で 1 ページなので、glyph upgrade は移行先のバージョンのエントリではなく、そのページにリンクします。新しいリリースのどの診断にあなたのコードが引っかかりそうかを教えてくれるものは、まだありません。それを知るにはビルドするしかなく、だからコマンドがそう促しています。また、複数のリリースをまたいでアップグレードしても、1 つ分と同じ 1 ステップで、その間に積み重なった変更の要約はありません。glyph --update は npm を呼び出してその終了コードを読むので、npm が終了したことはわかっても、PATH 上のバイナリが求めたバージョンであることまではわかりません。そのため、成功したと言う代わりに glyph --version を示します。
