エージェントがコードを気づかれずに壊すのを、何が防ぐのか

TypeScript ではそのままコンパイルが通ってしまう種類の変更（ケースの抜け、処理されないエラー、フィールド名の変更）が、出荷前にエージェントが直さなければならないコンパイルエラーになります。

なぜ重要か

エージェントがコードを壊すとき、たいていは派手には壊しません。自信満々に壊します。状態を追加し、分岐を落とし、フィールド名を変え、それでも型チェックはすべて通り、バグは本番で表に出ます。

高くつく失敗は、コンパイルが通って、しかも間違っていたものです。Glyph はこの穴を、“たぶん処理したはず”を“処理したことをコンパイラが証明した”に変えることで塞ぎます。

  • 封印されたユニオンタグ付きユニオンは封印されているので、match はすべてのケースを網羅しなければなりません。
  • 値としてのエラーエラーは消えてしまう例外ではなく、取り出して扱わなければならない値です。
  • 検査される境界さらに、どの型も実行時のデスクリプタを持つので、境界を越えるデータはその形に照らして検査されます。

捨てたエラーは警告になる

エラーも同じです。Result<T, E> を返す関数は、match で処理するか ? で伝播させるものです（そしてコンパイラはエラー型が一致するかを検査します）。Result を捨てると（文として呼び出して戻り値を無視すると）、Glyph は警告します（E0217）。捨てられたエラーは握りつぶされた失敗だからです。

glyph check --no-tsc、0.1.149（抜粋） 
13 │   save("a")
[E0217] Warning: typecheck: this `Result` is discarded; its `Err` case is silently ignored
    │ Help: Handle it with `match`, propagate it with `?`, or bind it (`let _ = ...`) to say the discard is intentional.

黙らせるには let _ = ... と意図して書きます。うっかり黙ることはありません。

標準ライブラリのユニオンも封印されている

標準ライブラリが持つユニオンでも基準は同じです。fs.ErrorKind は 6 種類の閉じた集合で、チェッカーはその形を知っています。そのため、ファイルシステムのエラーに対する match e.kind には else アームが要らず、種類を 1 つ書き漏らすと E0200 で失敗します。

E0200 種類の抜けE0210 不明なフィールドE0218 else が必要
詳細 フィールドのタイプミス、戻り値の型、数値と文字列の match

e.mesage は E0210 になり、後段で tsc が拾うものではありません。戻り値の型も伝わります。string.split(text, ",") は Array<string> なので、for i, part in string.split(text, ",") では i が数値として束縛されます。型のない反復対象から得られる文字列のキーにはなりません。

網羅性はユニオンだけのものではありません。number や string に対する match がリテラルのアームしか持たない場合、上限のない値域を網羅できないので、Glyph は else を要求します（E0218）。網羅されない値が実行時の throw まで素通りすることはありません。

規則はどこでも同じです。ケースを扱っていない match はコンパイルできません。

綴りを間違えたアームは catch-all ではなく抜けになる

タイプミスで抜けがこっそり覆い隠されることもありません。大文字で始まるアームの先頭はバリアントへの参照であって、新しい束縛ではありません。

status.glyph：綴りを間違えたアームは catch-all ではなく抜けになる 
fn label(s: Status) -> string {
  return match s {
    Loadign => "…",        // typo for Loading, read as a variant, not a binding
    Ready => "done",
    Failed(msg) => msg,
  }
}

経緯 以前の Glyph がタイプミスをどう扱ったか

大文字で始まるアームの先頭はバリアントへの参照であって、新しい束縛ではありません。以前の Glyph では、Loading を Loadign と綴り間違えると、その誤記をすべての値を束縛する catch-all として読み、match が網羅的に見えていました。今は、先頭は match 対象のユニオンに実在するバリアントを指していなければなりません。そうでなければビルドは E0220 で止まり、最も近い実在の名前を示します。実際に飛ばしたバリアントも、そのすぐ隣に E0200 として表示されます。

ペイロードの中のバリアント

この読み方は、バリアントが別のバリアントのペイロードになっている 1 段下でも同じです。外側のバリアントが何であっても、アームはペイロード自身のタグで分岐します。

repl.glyph：内側のアームはペイロードを束縛せず、検査する 
fn step(z: Zipper, line: string) -> Zipper {
  return match parse_command(line) {
    Err(Blank) => z,                          // a comment or an empty line
    Err(e) => { io.println(explain(e)) z },   // every other parse error
    Ok(command) => execute(z, command),
  }
}
E0305 case ラベルの重複
経緯 0.1.93 より前の死んだアームと、E0305 のガード

Err(e) の隣にある Err(Blank) は「空行は無視し、それ以外のパースエラーはすべて表示する」と読めます。しかし 0.1.93 までは、外側のタグに対する 2 つの case "Err": ラベルにコンパイルされ、最初のラベルがペイロード全体を Blank という名前で束縛していました。すべてのエラーが最初のアームに入り、2 つ目は死んだコードでしたが、何も指摘されませんでした。Glyph は診断を 1 つも出さず、tsc --strict は重複した case ラベルを受け入れます。今は、外側のバリアントが何であってもアームはペイロード自身のタグで分岐し、コンパイラは型チェッカーと同じように名前を読みます。ペイロードのユニオン自身のバリアント一覧で決め、その一覧が手の届かないときだけ名前の形で決めます。同じファイルで宣言したユニオンなら、大文字かどうかはもう関係ありません。別のモジュールからインポートしたユニオンでは、今のところバリアント一覧が手の届かないところにあるので、大文字のバリアントは分岐し、小文字のものはビルドを止めます。

止まるのは、switch にガードが入ったからです。同じ case ラベルを書くことになる 2 つのアームは E0305 になり、2 つ目のラベルが決して実行されない switch にはなりません。これでこの種の問題は、黙っていたものが声を上げるようになります。同じタグを 2 回使う変換は、実行時に間違ったアームを選ぶのではなく、ビルドを失敗させます。

インポートの書き方で検査が外れることはない

ユニオンをどうやってスコープに入れたかは、これに一切影響しません。Glyph ではバリアントのアームを 2 通りに書けて、どちらも同じように検査されます。import model { Cond, Yes, No } と書いて素のアームを使うか、import model（または import model as m）と書いて model.Yes(_) を使うかです。

interp.glyph：インポートの一覧を消しても、match は検査される 
import model { Action, All, Any, AtLeast, Clear, Condition, Context, Counter,
               Equals, Flag, FlagSet, Increment, Not, Set, Slot, Text }
import model
import std/result

pub fn evaluate(ctx: model.Context, c: model.Condition) -> result.Result<bool, SlotError> {
  return match c {
    model.Equals({ key, value }) => result.Ok(read_text(ctx, key, "equals")? == value),
    model.AtLeast({ key, least }) => result.Ok(read_count(ctx, key, "at-least")? >= least),
    model.FlagSet({ key }) => result.Ok(read_flag(ctx, key, "flag-set")?),
    model.All({ of }) => all_of(ctx, of),
    model.Any({ of }) => any_of(ctx, of),
    model.Not({ of }) => result.Ok(!(evaluate(ctx, of)?)),
  }
}
glyph build、最後のアームを削除した後 
[E0200] non-exhaustive match on `Condition`: missing variants Not
詳細 標準ライブラリのユニオン、文字列の列挙、一覧があった理由

これは標準ライブラリのユニオンにも当てはまります。option.Option<string> に対する match o { option.Some(s) => … } は、素の Some/None で書いた場合とまったく同じく、None の抜けで E0200 になります。0.1.56 までは修飾付きの書き方だと検査が丸ごと飛ばされ、実行時に throw する match に対してビルドは診断を 1 つも出しませんでした。

文字列の列挙も境界を越えます。catalog.glyph で宣言され、別のモジュールにインポートされた type ColType = "text" | "int" | "real" | "bool" は 4 つの値を保つので、4 つすべてを網羅する match は else なしでコンパイルでき、1 つを落とすと落とした値を示す E0200 になります。0.1.57 までは E0218 で、ヘルプには else アームを追加するよう書かれていました。そのヘルプは目の前のコードについて間違っており、従うとコンパイルエラーが実行時の素通りに変わっていました。3 つのインポートの書き方はすべて動きます。import catalog { ColType }、catalog.ColType を使う import catalog、c.ColType を使う import catalog as c です。

このインポート一覧が、この話の出どころです。ステートチャートエンジンのすべてのモジュールに手書きされ、その上には「ユニオンのコンストラクタは型と一緒には入ってこない」というコメントが付いていました。そのコメントは構文については正しく、理由については間違っていました。一覧があったのは、短い書き方だと検査が外れてしまうからで、それに誰も気づいていませんでした。検査が外れても何も言われないからです。今は、どちらの形を選ぶかは罠ではなく、本当の選択です。名前付きの形では、扱うバリアントがすべてインポート一覧に並ぶので、Equals を grep すれば見つかります。修飾付きの形では、各アームでそのバリアントがどのモジュールから来たかがわかります。どちらを選んでも検査は失われません。

インポートしたレコードはフィールドを保つ

今はレコードも境界を越えますが、0.1.58 まではそうではありませんでした。そのためレコードはフィールドの集合を保ち、間違ったフィールドは匿名の形についての tsc のエラーではなく、レコード名を示す E0210 になります。

詳細 line 11 のバグ、tsc が見逃すもの、同一性の伝わり方

あるファイルで宣言され、別のファイルで使われる型は、何もわからない状態で届いていました。そのせいで 2 つの検査が失われていました。その型のフィールドの綴りを間違えても Glyph のエラーはまったく出ず、sheet.rowz は tsc まで素通りして、自分では書いていない形についての TypeScript のメッセージとして返ってきました。また for i, r in sheet.rows は rows が配列だとわからず、sheet.rows.entries() ではなく Object.entries(sheet.rows) を出力していました。これでは i が文字列 "0" に束縛されます。すると i + 1 は加算ではなく連結になり、line 2 と報告されるべき行が line 11 と報告されます。

知っておく価値があるのは、tsc がどちらの半分を捕まえるかです。そのインデックスに対する算術は捕まえますが、エラーは Glyph が代わりに束縛した変数について、生成された TypeScript に対して報告されます。捕まえられないのは、数値のつもりの場所で文字列が受け入れられるすべての箇所です。文字列補間、連結、record.get のキーなどです。これらはどちらのチェッカーでも問題なくコンパイルされ、間違った数値を出力します。これはまさにこのプロジェクトがなくそうとしている種類のバグなので、それを再び持ち込むモジュール境界を Glyph は放っておけません。

インポートした型は今、宣言しているモジュールと宣言された名前をキーとする同一性を持って境界を越えるので、3 つのインポートの書き方はすべて同じ型に解決されます。宣言そのものは必要なときに取得され、宣言側のモジュールで変換されます。これは利用側にはできない部分です。名前解決はスパンに対して行われ、インポートした宣言のスパンは別のファイルに属しているからです。

これが表に出たのは examples/apps/csvql のクエリエンジンでした。そこには、インポートしたフィールドの型をエミッタのために書き直すだけの let の巻き上げが 3 つあり、その上の 4 行のコメントには、これがないとエラーメッセージの行番号と列番号が間違って出ると書かれていました。3 つとも削除し、アプリは 12 個のクエリすべてでバイト単位で同一の出力を返します。

境界で止まるものがまだ 1 つあります。table.Row が期待される場所に catalog.Sheet を渡すと両方の型を示す E0211 になりますが、interface のメンバー一覧は境界を越えないので、インポートした interface が期待される場所に渡したレコードは何とも比較されません。レコードのフィールド集合と同じ扱いをすると、構造的な適合の意味が黙って変わってしまいます。これは修正ではなく、言語の設計判断です。

PII のマスキングは型に置く

「慣習ではなく型のレベルにする」という同じ考え方が PII にも及びます。型に @redact fields: [ssn, dob] を付けると、コンパイラはそのデスクリプタにそれらのフィールドをマスクする redact() を生成するので、json.stringify(User.redact(u)) がそれらを漏らすことはありません。

E0219 @redact に不明なフィールド

型にないフィールドを指定するとコンパイルエラー（E0219）になり、黙って何もしないマスキングにはなりません。

リファインメントは最後まで検査される

デスクリプタに価値があるのは、それが型の宣言する検査を最後まで行う場合だけです。where リファインメントは、直接の Instant.parse だけでなく、その型が現れるすべての場所で述語を実行します。レコードのフィールドとして、Array の要素として、Option のペイロードとして、ユニオンのバリアントの中で、そして json.parse<T> を通してです。

schedule.glyph：述語は型を追ってフィールドの中まで入る 
fn is_instant(value: string) -> bool {
  return match time.parse_iso(value) {
    Some(_) => true,
    None => false,
  }
}

type Instant = string where is_instant(value)

type WireBlock = { start: Instant, end: Instant }
type WireParticipant = { name: string, busy: Array<WireBlock> }
type Calendar = { participants: Array<WireParticipant> }

// json.parse<Calendar>(text) on a file holding "start": "no"
//   => Err. It returned Ok before 0.1.41.
経緯 0.1.41 より前の、自信満々の間違ったスケジュール

別のモジュールからインポートしたレコードも同じです。0.1.41 までは、どちらもキーが存在するかどうかの検査に退化していて、それは何の検査にもなっていませんでした。

これが表に出たのは、下のスケジューリングアプリでした。このアプリは JSON ファイルからカレンダーを読み込み、すべてのタイムスタンプが正しい ISO-8601 の時刻であることを必要とします。以前はリファインメントが最上位で止まっていたので、手で編集されて "start": "no" になったファイルも問題なくパースされ、時刻は 0 として読まれ、アプリは自信満々にスケジュールを出力して終了コード 0 で終わっていました。

テストはビルドの一部として実行される

テストはコードの隣に置かれ、コンパイルの一部として実行されます。関数の上の @example や、@doc の中の ```glyph @run``` ブロックは、覚えておくべきフラグなしで glyph build が実行します。

詳細 黙って飛ばせない理由と、JSON のチャネル

偽になったものは、型エラーと同じようにビルドを失敗させます。それが狙いです。関数の本体を書き直すエージェントは、アサーションを置き去りにしてビルドを通すことはできません。--no-test で除外できますが、飛ばしたテストの数が表示されるので、迂回したことはログに残ります。

エージェントが読む JSON 出力も同じ判定を報告します。glyph build --json は診断の隣に examples オブジェクトを持ち、失敗した例があると ok が false になり、終了コードは 0 以外になります。0.1.43 までは、例は --test のときだけ実行され、JSON の経路は例を実行する前に返っていました。そのため、エージェントが読める唯一のチャネルが、自分自身のアサーションが偽であるプロジェクトに対して "ok": true を出力していました。tsx が PATH にない場合、検査していない合格を報告するのではなく、ビルドが失敗します。

下のトーナメント表アプリにはこれが 23 個あります。seed_order は倍々にしていく方法で標準的なトーナメントの順序を作ります。微妙に間違えやすく、それでいて正確に説明しやすい種類の関数です。倍にする規則を変えるとビルドが止まります。テストファイルもランナーもフラグも要りません。

作って見つけたもの

作って見つけた、さらに 4 つ

これらはどれも問題なくコンパイルされ、tsc --strict も通過しました。そして、どれもコンパイラを読んでではなく、アプリケーションを書いていて見つかりました。3 か所に現れた同じ失敗です。型はあることを言い、プログラムは別のことをしていました。

存在しないかもしれないキーを読む

存在しないかもしれないキーを読む：今は E0224 
fn name_of(row: Record<string, string>) -> string {
  return row.naem          // a typo. compiled, and returned undefined
}

今は record.get を指すコンパイルエラーになります。これは Option<V> を返すので、キーがない場合の行き先があります。

詳細 map の読み取りが配列のインデックスと違う理由

map のキーは任意なので、コンパイラはキーが存在するかを知ることができません。読み取りを string と型付けするのは、検査していないことを述べることであり、値は "undefined" という文字列として出力されていました。キーへの書き込みは変わりませんし、配列のインデックスも変わりません。範囲はプログラムが検査できる値ですが、map のキーはそうではありません。

undefined を返すメソッド

何も見つからないかもしれない検索: 現在は E0242 
let name = users.find(fn(u: User) -> bool { return u.id == id }).name
let last = xs.at(-1) ?? 0  // passed tsc --strict too

[E0242] the call to `users.find` returns `User | undefined`; Glyph writes a value that may be missing as an `Option`
Help: pass `users` and the same callback to `array.find`, which returns `Option<User>`, and `match` it

JavaScript のいくつかのメソッドは「何もない」を undefined で表します。Glyph 自身のチェッカーにはそれが見えなかったため、エディタとエージェントのツールは .name の読み取りを通していました。今はそれぞれが Option を返す標準ライブラリの関数を示し、配列のものは glyph fix が書き換えます。

詳細 どのメソッドが対象で、何に置き換えるか

一覧は TypeScript の宣言から読み取っています。配列の find、findLast、at と、文字列の at、codePointAt、match です。置き換え先は array.find、array.find_last、array.get、string.char_at、string.code_point_at、regex.matches です。?? のデフォルト値は match の None アームになります。array.get は負のインデックスに None を返すので、xs.at(-1) のヘルプは array.get(xs, array.len(xs) - 1) と書きます。npm の値に対するメソッド呼び出しは、Glyph がその型を知らないため判定しません。

== はどこでも値の等価性

コードは失敗しているのにテストは通った 
@example wrap("a") == wrap("a")   // passed: deep equality
fn same() -> bool {
  return wrap("a") == wrap("a")   // false. no diagnostic
}

== は今、どこでも値の等価性です。プリミティブは引き続き === にコンパイルされるので、普通の比較は変わりません。

経緯 壊れたコードでテストが通ってしまった仕組み

== は値の等価性だと文書化されていましたが、=== に変換されていました。これは、どちらかの辺がレコード、タグ付きユニオン、配列になった時点で参照の等価性です。同じ式が、テストでは構造で比較され、隣のプログラムでは同一性で比較されていたので、動かないコードに対してテストが成功を報告することがありました。

ループの束縛は要素の型を保つ

ループの中で消えていた網羅性 
for t in tiers {
  match t {
    "free" => ...          // "pro" unhandled: once merely a warning to add `else`
  }
}

今は扱っていないバリアントの名前を示します。検査を外すのではなく満たすための助言です。

経緯 以前出していた catch-all の助言

ループの束縛は要素の型を持っていなかったので、文字列リテラルのユニオンに対する match が string に対する match に格下げされ、コンパイラは catch-all を追加するよう助言していました。

インデックスでの読み取りは要素の型を持つ

xs[0] からのタイプミス: 今は E0210 
fn first_len(xs: Array<string>) -> number {
  let s = xs[0]
  return s.lenght
}

[E0210] type `string` has no field `lenght`; did you mean `length`?

Array<E> に対する xs[i] は E です。そのため、エディター、glyph check --no-tsc、エージェント向けツールが、それをどう使うかを検査します。フィールドの読み取り、メソッド呼び出し、return、引数、型注釈付きの let です。

経緯 以前は何が検査されていたか

0.1.183 までは、インデックスで読んだ要素は Glyph 側で型を持っていませんでした。-> number の下での return xs[0]、rows[0] のフィールド名の綴り間違い、number の引数に渡した xs[0] はどれも通り、完全なビルドの tsc の段階でしか見つかりませんでした。型は、tsc が生成されたコードに与えるものと同じです。生成される設定は noUncheckedIndexedAccess をオフにしているので、E | undefined ではなく E です。Glyph のインデックスは末尾を越えると undefined を返す代わりに RangeError を投げます。Option が欲しいときは array.get を使ってください。Record のキー読み取りは、値の型が unknown でない限り今も E0224 で、string や npm の値に対するインデックスは判定しません。

インポートしたジェネリックなユニオンも検査される

インポートしたジェネリックなユニオンに対する match で、バリアントが 1 つ抜けている 
import tree { Tree, Node }

fn label(t: Tree<string>) -> string {
  return match t {
    Node({ key: k }) => k    // Leaf unhandled: built clean, threw at run time
  }
}

今はどちらの場合も E0200 になります。2 つのインポートの書き方のどちらでも、型パラメータが開いたままでも具体的な型で具体化されていても同じです。

経緯 検査が始まらなかった理由

自分のモジュールで宣言したユニオンは、型パラメータを取るかどうかにかかわらず検査されます。兄弟モジュールからインポートしたものは、型パラメータを取らない場合にだけ検査されていました。Tree<string> は、インポートしたユニオンそのものではなく、その適用としてモジュール横断の網羅性チェックの経路に届きます。そして検査を開始する入口は後者ではなく前者を探していたので、match はまったく数えられていませんでした。tsc --strict は通過し、Leaf で throw していました。両方のファイルから <K> を削除すると、同じプログラムが E0200 になりました。

parse はしていない検査をしたとは言えない

検査せずに成功を報告していた parse：今は E0304 
type Conn = { id: number, sock: Socket }

Conn.parse(body)   // Ok. `sock` was never checked, and the message said it was

レコードにソケットを持たせるのは普通のことで、今もコンパイルできます。そのレコードを検証することは、書いた場所でも、そのレコードをインポートするすべてのモジュールでも拒否されるようになり、フィールド名とその型が示されます。拒否は形をたどって伝わります。入れ子のレコード、Array、Option を通してです。

詳細 存在することが検査にならない理由と、求められる修正

どのレコード型も実行時のデスクリプタを持ちます。ソケットや、extern_ts を通して届くものなど、コンパイラが中を見られない型のフィールドについては、生成される検査は「存在するか」だけで、報告されるメッセージは field `sock` must be Socket でした。常に真になる真偽値は役に立ちません。何も検査していない型を名指しするメッセージの下で常に真になるのは、もっと悪いことです。parse こそ、境界が信頼するよう言われているものだからです。

求められる修正は、どのみち書いていたはずの分割です。すべてのフィールドが検査可能なワイヤ型を作り、そこからドメインのレコードを組み立てます。unknown はこれに引っかかりません。何も主張しておらず、存在することがまさに検査のすべてだからです。

呼び出し側から見えないシグネチャの変更：0.1.116 で解消

関数を、生の文字列ではなくペイロードを受け取るように変更しても、古い形のまま渡している呼び出しはすべて問題なくビルドされていました。

billing.glyph：ユニオンが `string` パラメータを気づかれずに通過する 
type PaymentResult = Settled(string) | Declined(string)

fn takes_string(s: string) -> number { return s.length }

fn charge(r: PaymentResult) -> number {
  return takes_string(r)   // compiled clean before 0.1.116
}
glyph build、現在 
[E0211] argument type mismatch: expected `string`, found `PaymentResult`
   ╰─ Pass a value of the expected type, or change the parameter's type.
詳細 検査が働く場所と、黙っている場所

string、number、bool と型付けされたパラメータは、宣言されたユニオンやレコードの値を何の文句もなく受け入れていました。同じ呼び出しで bool の引数が合わない場合は、すでに E0211 だったにもかかわらずです。

このチェックは宣言を読むので、答えが確実な場所でだけ発動します。type Id = string のようなプリミティブの別名は、それが指す string として読まれるので、同じように判定されます。文字列リテラルのユニオン (D30) はそのリテラルで比較され、interface の値は、その値がオブジェクトなので、string が宣言された場所では拒否されます。extern_ts や typeof の本体については引き続き何も言わず、void も対象外です。引数、return、let の注釈のどれにも同じように届きます。三つとも一つの関係を共有しているからです。

逆方向は TypeScript と同じく値のメンバーを通ります。interface HasName { name: string } が宣言された場所では 5 は拒否され、interface HasLen { length: number } が宣言された場所では、文字列には length があるので "abc" は受け入れられます。bigint はそれ自身のメンバーを通して読まれるので、そこでは拒否されます。length を持たないからです。まだ判定されず tsc に任せている組み合わせが二つあります。メンバーがすべて省略可能で値と一つも共有しないインターフェース (G526) と、インターフェースに対する Option、Result、Record (G527) です。

型注釈付きの const は型を持つ

const には、受け取る側に対応する穴がありました。

catalog.glyph：型注釈付きの const と、それが持たないフィールド 
type Sheet = { rows: number, cols: number }
const ORIGIN: Sheet = { rows: 0, cols: 0 }

fn f() -> number {
  return ORIGIN.rowz   // compiled clean before 0.1.116
}
glyph build、現在 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
詳細 型注釈のない const と、どちらの修正も破壊的な理由

型注釈の付いたモジュールレベルの const は、注釈の内容にかかわらず Ty::Unknown に変換されていました。そのため、関数の中の同じ注釈付き let ならすでに報告されていたフィールドのタイプミスが、ちょうどそこで見えなくなっていました。

0.1.166 以降、注釈のない const は初期化子の型を持ちます。エミッタが書く TypeScript の const を tsc が読むのと同じ読み方です。const MODE = "read" はリテラル型を保ち、オブジェクトや配列の中のリテラルは広げられるので、const ITEMS = [1, 2] は Array<number> になり、mut の外での ITEMS.push(3) は E0240 です。チェッカーが型を付けられない初期化子では、その const は型なしのままです。どちらの修正も glyph check --no-tsc、言語サーバー、プレイグラウンドでは破壊的変更です。それぞれ前のリリースが受け入れていたプログラムを捕まえ始めるからです。完全な glyph build はどちらの場合もすでに tsc によって赤でした。

レコードが宣言していないフィールド

綴りを間違えた省略可能フィールド: 現在は E0210 
module profile

pub type Profile = {
  name: string,
  nick?: string,
}

pub fn guest() -> Profile {
  return { name: "guest", nik: "g" }   // [E0210] type `Profile` has no field `nik`; did you mean `nick`?
}

宣言されたレコードにないキーは、以前は Glyph のチェッカーを通っていました。そのため省略可能なフィールドのタイプミスはその値を捨ててしまい、気づくのは tsc だけでした。今はエディタ、エージェントのツール、glyph check --no-tsc がこれを拒否し、同じフィールドを読んだときと同じエラーを出します。glyph fix は nik を nick に書き換えます。

詳細 どこで判定され、何が対象外か

書かれたリテラルが宣言された型と出会う場所ではどこでも判定します。let、return、呼び出しの引数、バリアントのペイロード、mut による代入、入れ子のフィールド、配列の要素、match のアーム、そして tsc が見逃す Some、Ok、Err の引数です。より広いレコードを保持する束縛は、tsc と同じく引き続き受け入れられます。スプレッドから来るフィールドと、Record<K, V> に向けて書かれたキーも同様です。

    詳細

    string、number、bool、Array<T> に対するメンバーアクセスと呼び出しは、穴ではなく設計として tsc に任せています。Glyph はそこで JS の生のメンバーを許すので、s.length や xs.length はコンパイルでき、tsc --strict も通過します。欠けているのは、tsc を一切実行しない 4 つの場所での診断です。glyph check --no-tsc、言語サーバー、MCP サーバー、Playground です。

  • 例を含むオフラインのビルドには tsx か --no-test が必要
    詳細

    例のランナーは tsx を呼び出すので、例があって PATH に tsx がないプロジェクトは、黙って飛ばすのではなくビルドが失敗します。これは意図したものですが、オフラインでビルドするには tsx をインストールするか --no-test を付ける必要があります。

  • 普通の fn の中の await は、自分のソースに対して検出されるE0222
    詳細

    async の文脈は、Glyph が tsc に任せていた唯一の規則でした。今は普通の fn の中の await は自分のソースに対する E0222 になり、トップレベルの const の初期化式だけが今も許される例外です。これと、1 段前に移ったほかの 2 つの規則は 早い段階で検出にあります。

これが Glyph の 4 つの柱の 1 つ目である理由と、その保証がどこで止まるかは、検証可能性の柱のページにあります。
