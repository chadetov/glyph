Web ページを配信できるのか、それとも JSON API だけなのか

Web ページを配信できます。std/http はレスポンスヘッダを設定できるので、text/html のページ、302 リダイレクト、キャッシュのヘッダ、HTML フォームの POST は、どれも普通の Glyph で書けます。Express も手書きの TypeScript の補助コードも要りません。

なぜ重要か

0.1.46 まで、レスポンスは { status, body } で、サーバーはボディの形からコンテンツタイプを決めていました。文字列なら text/plain、それ以外は JSON です。API ならそれで十分ですが、ブラウザが描画するものには役に立ちません。

抜け出す方法は、手書きの .ts ファイルで node:http の上に自前のサーバーを書くことで、そうするとリクエストの経路全体が型検査の外に出てしまいます。コンストラクタが 2 つ足りないだけで、アプリケーションの境界がまるごと失われていました。

ハンドラは Result を返す

ハンドラは Result<Response, string> を返すので、404 は普通の Ok で、Err はアプリが答えられないもののために取っておかれ、サーバーがそれを 500 に変えます。

serve は listen している間は待機中のままなので、手でプロセスを生かしておく必要はなく、バインドの失敗は値として返ってきます。

どのレスポンスもヘッダを持つ

Response は必須の headers: Record<string, string> を持ちます。省略可能ではなく必須です。どのコンストラクタもこれを埋めるので、resp.headers を読むときに存在チェックは要らず、このチャネルを忘れることもありません。

  • 変更ではなく新しいレスポンスwith_header(resp, "cache-control", "no-store") はレスポンスを変更するのではなく新しいレスポンスを返します。Glyph にはレコードのフィールドを変更する手段がないからです。
  • Glyph の中で検査される型検査は 3 つのコンストラクタがどれも Response を返すことを知っているので、宣言した戻り値の型が Result<Response, string> のハンドラは、生成された出力に対する tsc ではなく Glyph の中で検査されます。

手で書くと間違えがちな 2 つの細部

  • ヘッダの値Node がヘッダに書き込むのを拒否する文字は、出力時に値から取り除かれます。そのためクエリパラメータから組み立てた location が 2 つ目のヘッダや 2 つ目のレスポンスを注入することはできず、短縮 URL に含まれる絵文字でサーバーが落ちることもありません。
  • フォームのボディform(req) は、パーセントエスケープと一緒に + を空白としてデコードします。手作りのフォームのパースがよく見落とす組み合わせです。生のボディを読むので、自分でパースするハンドラのための req.body はそのまま残ります。

現状

提供中

  • html、redirect、with_header、json、text、form
  • レスポンスヘッダは実際に送信され、コンテンツタイプは自分で設定しなかったときだけ推論される
  • 受信側では、リクエストヘッダ、クエリパラメータ、パスのセグメント、生のボディを扱える
  • クライアントは受け取ったレスポンスヘッダを報告します。

予定

    詳細

    上のコードが示している穴はパーセントエンコーディングです。form はフォームのボディをデコードしますが、URL を組み立てるための encode_component がないので、短縮サービスは自前で書いています。

  • クライアント側には、タイムアウト、リダイレクトのポリシー、head、リダイレクト後の最終的な URL もありません。
  • 静的ファイルのサーバーやテンプレートエンジンはなく、どちらも予定はありません。
