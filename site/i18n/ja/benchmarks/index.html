ベンチマーク

2 種類の根拠。

測る価値のある問いは 2 つあり、私たちはこれを分けて扱います。構造面：TypeScript が受け入れるもののうち、Glyph が構造上拒否するものは何か。これは現時点で証明でき、下に示しています。信頼性：エージェントが Glyph で書いたコードは、きちんと設定した strict な TypeScript の構成よりも、実際に出荷される欠陥が少ないのか。導入を決めるのはこの数値ですが、まだありません。構築中の調査で、代わりの指標をその答えであるかのように見せることはしません。（本当の比較は Glyph と素の TS ではなく、Glyph と strict な TS + zod + eslint + ts-pattern です。）

構造面：構造上証明できること

統計ではなく、対になった実証です。どれも Glyph が拒否し tsc --strict が受け入れるケースで、benchmarks ディレクトリから再現できます。

検証可能性：高くつくバグ
どちらもコンパイル時に検出

エージェントがいつも犯す 2 つのミス（match のバリアントの漏れと、as unknown as を通したキャスト）は、Glyph では拒否され、tsc --strict では受け入れられます。どちらも catches/ にある検証済みのケース（non-exhaustive-match、E0200。as-unknown-as、E0013）で、ビルドのゲートが再実行します。コンパイルが通る誤ったコードは高くつく失敗です。Glyph はそれを許しません。

grep しやすさ：1 つの名前、1 つの場所
いつでもマッチは 1 件

すべてのシンボルは宣言の形をちょうど 1 つだけ持ちます。それを散らばらせるオーバーロード、デコレータ、マージされた namespace はありません。

$ grep -n "fn welcome" main.glyph

差分の安定性：最初からレビューしやすい
1 行 → 1 行

Glyph での 1 行の編集は、トランスパイラを通しても 1 行の TypeScript の差分になり、glyph fmt は余計な書き換えを加えません。差分は変更そのもので、周りのノイズではありません。

安全性はふつうコードの長さで払うものです。静的型と明示的なエラー処理を持つほかの行、Go と Rust が最も長くなっています。Glyph はその両方を持ちながら長くなりません。glyph check と tsc を通るプログラムを実際に cl100k_base で数えると、TypeScript の 478 に対して 436 トークンで、約 9% 少なく、Python と同程度、Go より約 23%、Rust より 30% 少なくなります。差がつくのは本当の制御フローを持つ関数（parse_user、132 対 174）で、1 行の slugify では Glyph のほうが長くなります（67 対 47）。正規表現リテラルがないからです。関数 3 つの小さなサンプルです。以前の 341 という数値は、コンパイラが受け入れない fixture で測ったものだったので撤回しました。方法と注意点を見る →

信頼性：構築中の調査

上の構造面の結果は、Glyph が役立つと期待する理由であって、役立つことの証明ではありません。証明となるのは差分比較の調査です。同じエージェントが同じ現実的なタスクを、Glyph で 1 回、ツールを完全に揃えた strict な TypeScript の構成（tsconfig strict + typescript-eslint + ts-pattern + zod）で 1 回書き、すり抜けた意味上の欠陥と、一発でビルドがグリーンになる割合で評価します。5 人の異なるレビュアーが、自分たちを動かすのはこの数値だと言ったので、私たちはこれを構築しています。それができるまで、これらの棒グラフは主張ではなくプレースホルダです。
