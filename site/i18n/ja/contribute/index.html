コントリビュート

コンパイラの作りと、貢献の方法

コンパイラは、1 つの公開リポジトリにある 12 個のクレートからなる Rust のワークスペースで、ライセンスは MIT または Apache-2.0 です。今いちばん役に立つのは、小さな再現コード付きのバグ報告です。言語への変更は Issue から始めます。どのルールも番号付きの設計判断にさかのぼれるからです。

パイプライン

glyph build は字句解析、構文解析、名前解決、型検査を行って TypeScript を出力し、書き出したものに対して tsc --strict を実行します。中間の段階は salsa 上のインクリメンタルなクエリとして動くので、再検査では編集で無効にならなかった結果が再利用されます。

1 つの .glyph ファイルがクレートを通る流れ 
glyph-lexer → glyph-parser → glyph-resolver → glyph-typechecker → glyph-emit → tsc --strict
                (glyph-ast)        └──────── glyph-db (salsa) ────────┘
クレート役割
glyph-lexerトークン、キーワード、意味を持つ改行、テンプレートリテラル
glyph-ast構文木の型。すべてのノードにソース上の範囲を持つ
glyph-parser仕様のすべての設計判断に対応する Pratt パーサー。JSX も含む
glyph-resolver名前解決、モジュールグラフ、モジュール間の import の検査、prelude
glyph-dbsalsa のクエリパイプラインと、ファイルをまたいだ無効化
glyph-typechecker網羅性、?、ジェネリクス、owned、実行時ディスクリプタ、標準ライブラリのモデル
glyph-emitTypeScript の出力、ディスクリプタの生成、式単位のソースマップ
glyph-formatterglyph fmt：レイアウトは 1 通りだけ、コメントを保持し、冪等
glyph-lsp言語サーバーと MCP サーバー。1 つの解析層を共有する
glyph-cliglyph バイナリとすべてのサブコマンド
glyph-wasmWebAssembly 版のコンパイラ。Playground を動かしている
glyph-runtimeスタブ。テストは代わりに出力器と tsx を通して実行する

クレートの詳しい説明と現在のテスト数は glyph-compiler/README.md にあります。

ビルドとテスト

Rust 1.95 が rust-toolchain.toml で固定されています。一部のテストは tsc と tsx を呼び出すので、これらもインストールしてください。CI は警告をエラーとして clippy を実行しますが、cargo build も cargo test も clippy を実行しないので、push する前にスクリプトを実行してください。

clone してから 
npm install -g tsx typescript
cd glyph-compiler
cargo build --release -p glyph-cli      # target/release/glyph
cargo test --workspace
cd .. && python3 scripts/check_clippy.py  # the exact clippy command CI runs

# after an intentional syntax-tree change
INSTA_UPDATE=always cargo test -p glyph-parser --test snapshots

新しい診断を追加するときは、そのコードで失敗しなければならないプログラムを tests/negative/ に加えます。TypeScript が見逃すものを Glyph が検出するという主張は catches/ に置き、そこでゲートが両方のプログラムを実行します。

予定されていること、壊れていること

docs/roadmap/releases.md はリリースのロードマップで、リリース済みの各バージョンで何をしたか、次のリリースが何のためのものかが書かれています。docs/dogfooding-gaps.md は穴の台帳で、実際のアプリを作る中で見つかった制約がすべて、番号（G と数字）と状態の印付きで並んでいます。再現コードのある未解決の穴は、始めるのにちょうどよい場所です。

Issue とプルリクエスト

ツールチェーンの修正、診断、ドキュメント、サンプルは、直接プルリクエストにして構いません。構文や意味論の変更は Issue から始め、大きなものは docs/rfcs/ の RFC プロセスを通します。「便利だから」とルールを緩めるプルリクエストは、おそらく採用されません。その制約こそが要点だからです。プルリクエストは 1 つの穴に絞り、通常はコミット 1 から 3 個にして、各コミットに署名してください（git commit -s）。main は保護されていて、マージは rebase のみです。詳しいルールは CONTRIBUTING.md にあり、good first issue ラベルの付いた Issue は、最初の変更に向くように範囲を絞ってあります。
