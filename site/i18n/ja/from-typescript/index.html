TypeScript から来た人へ

すでに TypeScript を書いている人にとって何が変わるか

思ったより少しです。Glyph は tsc --strict を通る TypeScript にコンパイルされ、npm もデプロイもそのまま使え、見た目もほとんど同じです。違いはいくつかの差分だけで、どれも間違える余地を、コンパイラが行う検査に置き換えるものです。

TypeScript を知っていれば、ほとんどはもうわかっている

新しい言語を覚えるのではなく、この 4 つだけです。このサイトのどのサンプルにも出てくるものです。

match
網羅的な switch：ユニオンに対しては、コンパイラがすべてのケースを扱うように求めます。文と式の中では唯一の条件分岐でもあります。if/else も三項演算子もありません（理由は下で説明します）。JSX には <if> 要素と <match> 要素があります。
Result<T, E>
エラーは throw される例外ではなく戻り値です。match で処理するか、? 演算子で伝播させます。
fn f() -> T
関数です。-> の後が戻り値の型です。type X = {...} はレコードで、type X = A | B はタグ付きユニオンです。
mut x = e
再代入は明示的で、grep できます。普通の let 束縛が知らないうちに変わることはありません。変えるときは mut と書きます。

同じ React コンポーネントを両方で

同じコンポーネントを 2 回書いています。招待のリストで、空のときの表示、返事待ちの数を数える行、各行のラベルがあります。TSX が && と ? : を使うところで、Glyph は JSX の要素を使います。値を 1 つ受け取りパターンごとに <case> を 1 つ書く <match> と、省略できる <else> を伴う <if> で、後者は単純な真偽値向けの軽い書き方です。リストは <for> で書き、属性は class で、className にコンパイルされます。

InviteList.tsx 
export type Invite = { email: string; accepted: boolean };

export function InviteList(props: { invites: Invite[] }) {
  const waiting = props.invites.filter((i) => !i.accepted).length;
  return (
    <section>
      {waiting > 0 && <p className="note">{waiting} waiting for a reply</p>}
      {props.invites.length === 0 ? (
        <p className="empty">No invites sent yet.</p>
      ) : (
        <ul>
          {props.invites.map((invite) => (
            <li key={invite.email}>
              {invite.email}
              {invite.accepted ? (
                <span className="ok">joined</span>
              ) : (
                <span className="wait">pending</span>
              )}
            </li>
          ))}
        </ul>
      )}
    </section>
  );
}
invites.glyph 
module invites

import std/array

pub type Invite = { email: string, accepted: bool }

pub component InviteList(props: { invites: Array<Invite> }) {
  let waiting = array.filter(props.invites, fn(i: Invite) { return !i.accepted }).length
  return <section>
    <if cond={waiting > 0}>
      <p class="note">{waiting} waiting for a reply</p>
    </if>
    <match value={props.invites.length}>
      <case 0>
        <p class="empty">No invites sent yet.</p>
      </case>
      <case else>
        <ul>
          <for invite in={props.invites} key={invite.email}>
            <li>
              {invite.email}
              <if cond={invite.accepted}>
                <span class="ok">joined</span>
              </if>
              <else>
                <span class="wait">pending</span>
              </else>
            </li>
          </for>
        </ul>
      </case>
    </match>
  </section>
}

Glyph 側のほうが長くなります。主に、分岐ごとに要素が 1 つずつ必要だからです。<match> はすべての値を扱う必要があり、ここで <case else> を外すとビルドは E0218 で止まります。union に対してはすべてのバリアントを扱う必要があり (E0200)、増えた行数が役に立つのはそこです。React で使えますか? に、フックと Context を使った例があります。

エディタ対応とデバッグにはそれぞれ回答があります。ツールの回答 は言語サーバーと VS Code 拡張を、デバッグの回答 は .glyph ファイルに戻るソースマップを扱っています。開発中は、glyph build --watch が .glyph ファイルを保存するたびに TypeScript を再ビルドします。その出力を import する Vite の開発サーバーは、再ビルドのたびにコンポーネントを差し替えるのではなくページ全体を再読み込みするので、コンポーネントの state はリセットされます。自分で書いた .tsx ファイルには Vite のホットリロードがそのまま効きます。出力先は Vite のビルドディレクトリ (デフォルトは dist/) の外にしてください。開発サーバーはそのディレクトリを監視しません。

このサイトでいう「エージェント」は、Claude、Copilot、Cursor のような AI コーディングアシスタントのことです。Glyph が最も役立つのはこうしたエージェントですが、検査は人が書いたコードでもモデルが書いたコードでも同じです。すでに strict な TypeScript を zod や eslint と一緒に使っているなら、それに対して言語が何を加えるのかを読んでください。

if 文は存在しない

真偽値での分岐は、true と false に対する match です。片方の場合にだけ処理をするときは、もう一方のアームを空のブロックにします。JSX は例外で、上のコンポーネントの <if> 要素は、条件が成り立つときに子要素を描画し、そうでなければ何も描画しません。

TypeScript 
function label(admin: boolean): string {
  return admin ? "admin" : "member";
}

if (verbose) {
  console.log("starting");
}
Glyph 
fn label(admin: bool) -> string {
  return match admin {
    true => "admin",
    false => "member",
  }
}

match verbose {
  true => io.println("starting"),
  false => {},
}

理由は仕様の決定 D3 です。値で分岐する構文を 1 つにすれば、読むのも書くのも検索するのも 1 つの形で済みます。分岐から出てくる値は必ず match から出てきて、その結果の型は tsc に任せずに Glyph 自身の型検査器が求めます。ユニオンに対しては、同じ構文がすべてのケースを扱わなければならないものになります（E0200）。真偽値の場合、得られるものはあまりありません。false => {} は else を省くのと同じことしか言っていないからです。

代償はあります。1 行の三項演算子は 4 行の match になり、条件による早期 return は空のアームを持つ match になります。そして TypeScript に慣れた人が最初に違和感を覚えるのがここです。仕様では、この冗長さを受け入れたコストとして記録しています。それでも if と書くとエラー E0006 になり、そのヘルプが match の形を示します。三項演算子は同じヘルプ付きの E0013 です。

すでに払っているコスト

TypeScript のコードベースで AI エージェントと一緒に開発しているなら、これらは毎日のコストです。どれにも Glyph での具体的な答えがあり、リストからリンクしています。

  • エージェントは存在しない API をでっち上げます。TypeScript は型を消去するので、実行時がコンパイル時と一致しなくなるからです。Glyph の型は実行時の検査（T.parse、T.is）を持っています。型付き API を見てください。
  • エージェントは不確かさを any や as unknown as T でごまかし、コンパイラはそれを許します。Glyph にはどちらもありません。下の表を見てください。
  • 1 行の変更を頼んだのにファイル全体が書き直されます。編集のたびにフォーマッタの変更が連鎖するからです。glyph fmt にはオプションのない 1 つのレイアウトしかありません。きれいな差分を見てください。
  • 型ごとに手書きのバリデータ（zod とシリアライザ）を並べて保守していて、エージェントが片方のフィールド名だけを変え、もう片方を変えなくても、すべてコンパイルが通ります。Glyph では型がバリデータです。
  • シンボルを grep すると、関係のないマッチが 10 件見つかります。オーバーロード、デコレータ、マージされた namespace です。Glyph にはそのどれもありません。コードを探すを見てください。

TypeScript が用意している検査のオフスイッチと、Glyph での代わりのもの

下の TypeScript の構文は、どれも型検査器に検査をやめるよう伝えるものです。どれも Glyph の構文にはありません。中央の列は、0.1.149 の glyph check --no-tsc がそれぞれに対して出力したものです。

TypeScriptGlyph では代わりに書くもの
x!構文ではない：E0013match で処理するか、? で上に渡す Option<T>
x as T, as unknown as Tキャストは存在しない：E0013。ヘルプは検証するよう案内するResult を返す T.parse(x)

glyph check には、検査の段階を丸ごと飛ばすフラグはあります（--no-tsc は tsc --strict の実行を、--no-test は @example のテストを飛ばします）が、1 つの検査だけを黙らせるフラグはありません。TypeScript のプロジェクトが受け入れて Glyph が拒否するものの全リストは、それぞれを両方のコンパイラで実行した結果とともに、検出できるもののページにあります。

抜け道は 1 つだけで、grep で探せる

Glyph では書けない TypeScript が必要なときは、extern_ts("...") がインラインで 1 つの型か式を受け取り、それも tsc が検査します。モジュール全体なら、.ts を src/extern/ の下に置いて import extern/name と書きます。それ以外の相対インポートは認められていないので、このパスが唯一の入口です。どちらの形にも extern という単語が含まれるので、grep -rn extern src/ で型検査器が TypeScript に処理を渡すすべての場所を一覧できます。

src/clock.glyph 
module clock

pub fn now_ms() -> number {
  return extern_ts("Date.now()")
}

出力される TypeScript の見た目

モジュールごとに 1 ファイルの普通の TypeScript で、読むこともコミットすることもできます。ユニオンは判別可能なユニオンと、その実行時の検査を持つ値になり、match はタグに対する switch になります。これは左のモジュールに対する glyph build の出力で、インポートの行は省略しています。

plan.glyph 
module plan

pub type Plan = Free | Pro | Team

pub fn seats(p: Plan) -> number {
  return match p {
    Free => 1,
    Pro => 5,
    Team => 50,
  }
}

export type Plan =

  | { tag: "Pro" }
  | { tag: "Team" };

export const Free: Plan = { tag: "Free" };
export const Pro: Plan = { tag: "Pro" };
export const Team: Plan = { tag: "Team" };
export const Plan = {
  is(value: unknown): value is Plan { ... },
  parse(value: unknown) { ... },
  schema: ...,
};

export function seats(p: Plan): number {
  const __m0 = p;
  switch (__m0.tag) {
    case "Free": { return 1; }
    case "Pro": { return 5; }
    case "Team": { return 50; }
    default: throw new Error("non-exhaustive match");
  }
}

npm と、すでにある TypeScript

.glyph モジュールは npm パッケージを名前でインポートし（import kafkajs { Kafka }）、型はパッケージ自身の宣言から付きます。既存の .ts は、出力された Glyph のモジュールを普通のローカルファイルと同じようにインポートします。そのため、TypeScript のままのアプリの中で 1 つのモジュールから始められます。詳しくは 3 つの Q&A にあります。
