Glyph を堅牢にする方法

エージェントが壊そうとし、見つかったものは残しておきます。

エージェントが気づかれずに壊すことはできないと言う言語は、その主張に対してテストされなければなりません。私たちは、懐疑的なエンジニア（不満を抱えた React 開発者、へそ曲がりのバックエンド開発者、安全性を突く攻撃者）を演じる AI エージェントを動かし、アプリを作らせて保証を壊そうとさせます。そして見つかったものを修正するか、未解決の穴として記録します。そのループと、そこで見つかったものを紹介します。

tsc --strict を通過し、Glyph ではコンパイルできないケース

各ケースは 2 つのファイルです。tsc --strict で問題なく型検査を通る .ts と、コンパイルできない同じ内容の Glyph のプログラムです。ビルドのゲートである scripts/check_catches.py がすべてを再実行し、どちらかが期待どおりに動かなくなると失敗するので、保証が気づかないうちに消えればビルドも止まります。表には、検出できるもののページにある TypeScript のケース {{catches:count}} 件のうち、このように拒否される {{catches:refused}} 件を載せています。残りは、Glyph がデータの到着時に検査するもの、警告するもの、実行時に止めるもので、そのページに載っています。{{catches:breakdown}}

{{catches:refused-table}}

TypeScript でも検出できると判明したケースや、2 つのファイルが同じプログラムになっていなかったケースは、手加減して残すのではなく削除しました。catches/README.md にそれぞれとその理由を載せています。

マップの読み取りは、キーの綴りが正しくても拒否されます。Record<string, string> は、どのキーが存在するかについて何も言っていないからです。TypeScript では noUncheckedIndexedAccess で検出できますが、--strict はこれを有効にしません。欠けたユニオンのケースも、プロジェクトが採用すれば、typescript-eslint の switch-exhaustiveness-check か assertNever を使った default で TypeScript でも検出できます。Glyph ではどちらの検査も任意ではありません。

パースしたボディのケースでは、Glyph の json.parse は User ではなく Result を返すので、ボディを検査するまでは代入が型の不一致になります。TypeScript の JSON.parse は any を返し、user の注釈がそれを素通りさせます。

攻撃的なループ

どの発見も、コンパイラに対して再現し、根本から修正し、独立に再検証してはじめて数に入れます。

1

探索

ペルソナを演じるエージェントがプログラム（フォーム、バックエンド、状態を持つ UI）を作り、言語に邪魔された箇所をすべて記録します。

2

再現

各発見を、失敗する最小のプログラムにまで縮め、コンパイラに対して再実行します。再現できないものは捨てます。

3

修正

Rust のコンパイラで根本原因を修正し、修正前に失敗して修正後に通る回帰テストを付けます。テストスイート全体がグリーンのままでなければ、変更は取り消されます。

4

検証

独立した確認作業で、ビルドしたばかりのコンパイラに対してすべての再現コードを再実行し、何かを出荷する前に「エージェントは直したつもりだった」という抜けを見つけます。

最も重要だったもの：気づかれない正しさの穴

これらはどれも問題なくコンパイルが通り、型検査を通る誤ったコードを出荷しえました。まさに Glyph が防ぐために存在する種類のバグです。現在はどれもコンパイル時に検出されます。

重大、修正済み

Result の match での引数なしのエラーバリアント

Result<T, Empty | BadQty(...)> に対する match が、重複する 2 つの case "Err" 分岐に変換されていました。1 つ目がすべてのエラーを飲み込み、黙って誤ったアームに振り分けていました。

現在：正しい内側の switch を持つ 1 つにまとめた case になり、各バリアントが正しく振り分けられます。

重大、修正済み

綴りを間違えたコンストラクタが黙って catch-all になる

match のアームでバリアント名を打ち間違えると（Loaded のつもりで Loded）、何の診断もなく、必ずマッチする catch-all の束縛として扱われ、網羅性の不足を隠して実行時に誤った振り分けをしていました。

現在：未知のコンストラクタは、本物の名前と同じように、打ち間違えた箇所で拒否されます。

高、修正済み

bool の不完全な match が網羅性の検査をすり抜けた

match n > 0 { true => ... }（false のアームがない）がコンパイルを通り、tsc も通過し、実行時に例外を投げていました。

現在：コンパイル時の網羅性エラーになります。

高、修正済み

複数パラメータのコンポーネントが props を誤って束縛した

component C(a, b) は位置引数として出力されていましたが、React はコンポーネントを props を第 1 引数として呼び出すので、a が黙って props オブジェクト全体に束縛されていました。tsc も通過していました。

現在：単一の props レコードの形を案内する、明確なコンパイルエラーになります。

高、修正済み

JSX の <match> が網羅性の検査を飛ばしていた

<case> が欠けた JSX の <match> はグリーンでコンパイルが通り、実行時に例外を投げていました。検査されていた値レベルの match とは違っていました。

現在：同じ網羅性の検査が適用され、欠けたケースはコンパイルエラーになります。

高、修正済み

レコードのペイロードが誤ったフィールドに束縛された

レコードのペイロードを持つバリアントを名前に束縛すると（BadQty(b)）、平坦化されたペイロードから存在しない .value を読んでいました。

現在：ペイロードは正しく束縛されるので、b.sku が機能します。

型検査器が新たに強制するようになったルール

以前はコンパイラが tsc に任せていた健全性を、今は Glyph 自身が検出します。

修正済み

呼び出しの引数の数

引数が少なすぎても多すぎても受け入れられていました（そして NaN になるまで実行されていました）。現在は E0213 が誤った引数の数を拒否します。

修正済み

標準ライブラリの境界をまたぐ ? のエラー型

エラーが標準ライブラリのラッパーから来た場合、エラー型が厳密に一致するというルールが飛ばされていました。現在はそこでも強制されます。

修正済み

owned ハンドルの別名

リソースハンドルに対する let g = f は 2 つ目の束縛を作り、二重に閉じる可能性がありました。現在は拒否されます（E0215）。

修正済み

到達不能なアームとより深い検証

catch-all の後にあるアームを指摘するようになりました。json.parse<T> は、Record のフィールドを存在の確認だけでなく構造的に検証するようになりました。

最初に触れたときの引っかかりを解消

第一印象を悪くしていた小さなことで、どれも何の役にも立っていなかったものです。

修正済み

アクセシビリティ属性と data 属性

aria-label と data-* が引き算としてパースされていました。現在は機能し、正しい React の props として出力されます。

修正済み

npm のパッケージ名

ハイフンを含む指定子やスコープ付きの指定子（react-hook-form、@hookform/resolvers/zod）が拒否されていました。現在はそのままインポートできます。

修正済み

ブラウザ向けバンドルの初回実行

ブラウザ向けのビルドでランタイムの初期化コードが読み込まれず、初回実行でクラッシュしていました。現在は出力されるすべてのモジュールがそれを読み込みます。

修正済み

誤った方向に導くエラーメッセージ

if と書くと match を案内するようになりました。範囲パターンについてはそのことを直接伝えます。JSX の空白とテキスト中の単独の $ も扱えるようになりました。

未解決のもの：記録として

堅牢化とは、終わっていないものを明らかにすることでもあります。これらは隠さずに把握し、追跡しています。

意図して先送りしているもの、または設計判断を待っているもの：

暗黙の any になるクロージャを Glyph 自身の型検査器で拒否するには、正しく型付けされたコールバックでの誤検知を避けるために文脈からの推論が必要です。使いやすい FFI、つまり複雑な型を持つ TS ライブラリをライブラリごとのアダプタなしで使うことは、相互運用で最大の未解決の問題で、未解決の問題で追跡しています。別のモジュールや標準ライブラリから来たマップはまだ検査なしで読まれるので、E0224 はまだ sqlite.Row に届きません。また、2 つの束縛を持つ for i, x in xs は、まだ要素の型を失います。
