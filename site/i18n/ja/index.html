AI エージェントが書く。 コンパイラが検査する。

Glyph は TypeScript のように読めて、抜け道だけがありません。any もキャストも、検証されないデータもなく、すべてのケースを扱います。読みやすい TypeScript にコンパイルされるので、node も npm も既存のコードもそのまま使えます。

$ npx -y @glyphlang/glyph init hello && cd hello && npm install && npx glyph run

グローバルインストールは不要です。glyph を PATH に置く場合は npm install -g @glyphlang/glyph tsx typescript

エージェントは先にコンパイラに聞ける

examples/apps/csvql はこのリポジトリにある CSV クエリエンジンで、中心に Value ユニオンがあります。そこに Date ケースを追加する前に、エージェントはコンパイラの MCP サーバーに、その編集で何が壊れるかを聞きます。回答 (ここでは判定、場所、関数だけに絞っています) は、4 ファイルにまたがる 10 か所の match を挙げます。

WILL_FAIL の各エントリには、そこで出るエラーが付いています。実際にケースだけを追加すると、ちょうどその 8 つの E0200 エラーが出ました。 ABSORBS の 2 か所は何も出しません。 render::literal_text は日付リテラルを引用符なしで出力し、 exec::total はすべての日付を 0 として数えていたはずです。コンパイラのエラーだけを頼りに作業するエージェントは、8 か所を直して通ったビルドのまま止まります。修正後にもう一度聞くと、コンパイラは 10 か所すべてで WILL_FAIL と答えるので、次のケースもすり抜けられません。

Glyph はまだすべてを検出できるわけではありません。既知の穴 {{catches:gap-count}} 件には再現コードと gap 番号が付いています。また、ロジックの誤りは TypeScript と同じく Glyph でも通ってしまいます。 gap ログには、Glyph でアプリを作る中で見つかった制約がすべて番号と状態つきで記録されています。 まだ検出できないもの →
