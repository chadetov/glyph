柱 03 · 仕上げ

抽象化

小さく直交したコアで、意図をそのまま書きます。switch の連なりの代わりにパターンマッチ、throw される例外の代わりに Result、タプルの代わりに名前付きレコード。TypeScript のように積み重なった層ではなく、1 つの概念に 1 つの良いやり方です。

同じことを言う方法が多すぎる

TypeScript は積み重ねで成長し、どの層も残してきました。

  • 決まったケース決まったケースの集合は、enum、文字列リテラルのユニオン、const オブジェクトのどれでも表現できます。
  • 形形は interface、type、class のどれでも記述できます。
  • そのほかすべてnamespace とモジュール、デコレータと高階関数があり、ほぼすべてに 5 通りのイディオムがあって、それぞれに独自の落とし穴があります。

人間にとってそれは柔軟性です。エージェントにとっては地雷原です。表現方法が多いほど、落とし穴のある方法を選ぶ可能性が増え、その間に覚えておくべきイディオムも増えます。

Glyph の抽象化の柱は意図した引き算です。仕事ごとに 1 つの鋭い道具を、わかりやすいやり方がそのまま安全なやり方になるように選んでいます。

01 条件分岐は match だけ

if/else 文はありません。分岐はどこでも match で、match は値を生む式です。

1 つの構文で真偽の判定、ユニオンの振り分け、値の表のすべてを扱うので、どの分岐の形を使うかを決める必要がありません。

02 タグ付きユニオンとパターンマッチ

「これらの形のどれか 1 つ」を表すにはタグ付きユニオンを使い、それを分解するには match を使います。ケースを選ぶのと同じステップでペイロードを分解します。

feed.glyph 
type Feed =
  | Loading
  | Loaded(Array<Post>)
  | Failed(string)

fn view(feed: Feed) -> string {
  return match feed {
    Loading => "...",
    Loaded(posts) => render(posts),   // posts is Array<Post> here
    Failed(msg) => msg,               // msg is string here
  }
}
詳細 もう手で書かなくてよいもの

手で管理する判別用フィールドも、文字列タグに対する switch の連なりも、形を取り戻すために各分岐の中で書くキャストもありません。

03 例外より Result

失敗は隠れた制御フローのジャンプではなく値です。失敗しうる関数はそのことを戻り値の型（Result<T, E>）で示し、呼び出し箇所を try/catch で囲んで正しいものが正しいクラスを throw することを祈る代わりに、? 演算子で失敗を合成します。

エラーの経路は正常な経路と同じくらいよく見えます。

04 位置で決まるタプルより名前付きレコード

データは常に名前付きのフィールドで記述します。形は定義でも、構築でも、利用でも同じように読めます。

TypeScript：[0] と [1] は何か point.ts 
function origin(): [number, number] {
  return [0, 0];
}
const p = origin();
p[0]; p[1];  // x? y? row? col?
Glyph：名前が値と一緒に運ばれる point.glyph 
type Point = { x: number, y: number }

fn origin() -> Point {
  return { x: 0, y: 0 }
}
詳細 省略記法なし、無名のタプルなし

オブジェクトリテラルの省略記法はなく、[0] と [1] が何だったかを覚えておかなければならない無名のタプルに頼ることもありません。

05 仕事ごとに 1 つのプリミティブ

ある概念に専用の道具が必要なとき、Glyph はちょうど 1 つだけ用意します。

  • 共有状態共有される変更可能な状態は std/store に置きます。
  • ハンドル一度だけ閉じなければならないファイルやソケットのハンドルは owned リソースです。
  • 反復反復は for x in xs です。

どれも名前の付いた専用のプリミティブで、汎用部品の寄せ集めから毎回組み立て直して微妙に間違えるパターンではありません。

ここでの抽象化とは、道具を増やすことではなく少なく鋭くすることです。どの概念にもわかりやすい形があり、そのわかりやすい形こそが使うべきものです。

ベンチマーク：準備中

これを測る方法は表面積です。プログラムを理解するために読む人が頭に置いておくべき概念がいくつあるか、よくあるタスクをきれいに表現するのにどれだけのコードが必要か、です。

Glyph はまだ実運用で使われていないので、下のグラフはプレースホルダで、比較できる実際のプログラムがそろったら実測値で埋まります。
