柱 01 · 突破口

検証可能性

Glyph はエージェントが落ちる穴を塞ぎます。書ける any も as もなく、match は網羅的であることが証明され、宣言した型には厳格な実行時バリデータが付きます。これらはすべて tsc の上に重ねた厳格なレイヤーとして強制されます。Glyph 自身がすべてを検証するわけではなく、保証がどこで止まるかは下で具体的に説明します。

型がつく嘘

TypeScript では、型はコンパイル時の約束にすぎず、コードが動く前に消えてしまいます。User という注釈は消去されて何も残りません。ネットワーク呼び出し、JSON のパース、フォームの入力から実際に得られるオブジェクトは、どんな形でもありえます。さらに悪いことに、言語は型検査器に嘘をつく合法的な方法を 3 つも用意しています。any、as によるキャスト、非 null の ! です。急いで作業するエージェントは 3 つとも使い、tsc --strict がグリーンのままバグが出荷されます。

Glyph の最初の仕事は、これらの穴を塞ぐことです。注釈を増やすのではなく、抜け道を取り除き、すべての型がその証明を実行時まで持ち運ぶようにします。それが何を意味するのか、保証を 1 つずつ見ていきます。

01 any は存在しない

any は TypeScript で最も高くつくキーワードです。ある値と、その値が触れるすべてのものについて型システムを無効にします。境界にある 1 つの any が、下流の呼び出しグラフを気づかないうちに汚染します。Glyph にはそれがありません。トップ型は unknown で、unknown は何もできません。それが何であるかを証明するまで、呼び出すことも、インデックスでアクセスすることも、型付きの場所に渡すこともできません。

TypeScript：コンパイルは通り、クラッシュする handler.ts 
function handle(body: any) {
  // tsc --strict: fine.
  // runtime: throws on {}.
  return body.user.name.toUpperCase();
}
Glyph：絞り込みが証明になる handler.glyph 
fn handle(body: unknown) -> string {
  return match User.parse(body) {
    Ok(u) => string.upper(u.name),
    Err(_) => "unknown",
  }
}

コンパイラから見える検査なしに、unknown から型付きの値を取り出すことはできません。Glyph では、絞り込みそのものが実行時の証明です。それを飛ばす構文はありません。

02 型は実行時にも実在する

User.parse はなぜ存在するのでしょうか。すべてのレコード型と、ジェネリックでないすべてのタグ付きユニオンは、実行時ディスクリプタを一緒に生成するからです。is ガード、unknown を検証して Result にする parse、組み合わせ可能な schema です。レコードの形は想定されるのではなく実行時に実際に調べられるので、is User の検査は消去される空の処理ではなく、本物の検査です。

書いた型と、そこから生成されるディスクリプタ 
type User = {
  id: number,
  name: string,
  email: string,
}

// generated: User.is(v), User.parse(v) -> Result<User, ...>, User.schema

fn create(req: Request) -> Result<Response, string> {
  return match User.parse(req.body) {   // untrusted input, validated
    Ok(user) => Ok(json(201, user)),
    Err(issues) => Ok(json(400, issues)),
  }
}

これが「API ごとに手書きのバリデータが必要」という問題への答えです。型がバリデータです。境界（リクエストボディ、設定ファイル、サードパーティのレスポンス）は、不正なデータを実際に拒否できる検査を通ったときにだけ型付きになります。

これが止まる場所：レコードのディスクリプタはデフォルトで厳格です。宣言されたフィールドを確認し、宣言されていないキーを持つ値は拒否します（余分なキーを許すには型に @open を付けます）。ジェネリックなものも含めてレコード型にはディスクリプタが付くので、Paginated<User> は各要素を User として検査し、タグ付きユニオンのディスクリプタはタグを検査したうえで、そのバリアントのペイロードのフィールドを検査します。まだディスクリプタが付かないのは、ジェネリックなタグ付きユニオン（Box<T> = Empty | Full({ value: T }) には Box.parse がありません）と、参照するだけの .d.ts からインポートした型です。検査で形の一部しか証明できない場合、コンパイラはそう伝え、できない保証をほのめかすことはしません。

03 すべてのケースを扱わなければコンパイルできない

封じられたユニオンに対する match は、すべてのバリアントを扱わなければなりません。後でバリアントを追加すると、それを考慮していないすべての match がコンパイルできなくなります（E0200）。忘れられた switch の分岐のように、新しいケースが黙って undefined に落ちることはありません。ユニオンだけではありません。number や string をリテラル値で match するときは else が必要です（E0218）。これらの値域は無限で、リテラルの集合が完全になることはないからです。

status.glyph 
type Status = Active | Paused | Cancelled

fn label(s: Status) -> string {
  return match s {
    Active => "on",
    Paused => "hold",
    // forgot Cancelled...
  }
}
実行時の undefined ではなく、コンパイルエラー $ glyph build 
[E0200] non-exhaustive match on
`Status`: missing variant `Cancelled`

# the equivalent TS switch returns
# undefined at runtime and compiles
# clean. here it does not build.

04 エラーは不意打ちではなく値

失敗しうる関数は Result<T, E> を返します。match で処理するか、? 演算子で伝播させます。エラーの型は一致していなければなりません（不一致を隠す暗黙の変換はありません）。Result をまったく無視すると（副作用のために呼び出して戻り値を捨てると）、Glyph は警告します（E0217）。捨てられたエラーは握りつぶされた失敗だからです。黙らせるには let _ = ... と意図して書く必要があり、うっかり黙ることはありません。

pipeline.glyph 
fn load(id: string) -> Result<User, AppError> {
  let raw = fetch_user(id)?           // Err short-circuits to the caller
  let user = User.parse(raw.body)?    // validation Err propagates too
  return Ok(user)
}

fn main() -> number {
  save(user)   // E0217: this returns a Result whose Err is dropped
  return 0
}

05 個人情報も型のレベルで扱う

「慣習ではなくコンパイラの仕事にする」という同じ考え方は、機密データにまで及びます。型に @redact を付けると、そのディスクリプタにはそれらのフィールドをマスクする redact() が加わり、うっかり書いた json.stringify(User.redact(u)) からも漏れません。型にないフィールドを指定するとコンパイルエラー（E0219）になり、何も守らない伏せ字処理が黙って残ることはありません。

patient.glyph 
@redact fields: [diagnosis, notes]
type Patient = {
  name: string,
  diagnosis: string,
  notes: string,
}

// json.stringify(Patient.redact(p)) ->
// {"name":"Ada","diagnosis":"[REDACTED]","notes":"[REDACTED]"}

5 つの異なる失敗のしかた（検査されない入力、見落としたケース、捨てられたエラー、漏れた秘密情報、検証されないキー）のどれでも、対処の形は同じです。コンパイラは取り繕うことを拒否します。

どう強制されるか、保証がどこで止まるか

違いが重要なので正確に書きます。Glyph は tsc の上に重ねた、強制される厳格な方言であり、独立した検証器ではありません。自分で証明するものもあります。網羅性、? のエラー型、ソースに any/as がないこと、厳格なキーの検証です。それ以外の型の互換性は、TypeScript を出力して tsc --strict を実行することで強制し、失敗すればビルドが失敗します。肝心なのは、これらの検査が言語そのものであり、エージェントが無効にできる任意の lint ではないという点です。Glyph が型検査器を作り直しているという点ではありません。

ここにあった 2 つの限界は 0.1.10 で解消しました。以前のエミッタは、すべてのジェネリック関数に、tsc ではなく Glyph が検査した前提の戻り値キャストを挿入していました。現在それが入るのは、バリデータのコンビネータが形から導いた型（infer_output<Shape>）の値を組み立てる場所だけで、正直なジェネリックはすべてキャストなしで出力されます。また、バリデータの出力型を信用することもなくなりました。infer_output が渡された形から出力型を導き、tsc が注釈をそれと照合します。主張する型のフィールドが欠けた形は、今ではコンパイルに失敗します。

ジェネリック型も深く検証されるようになりました。Paginated<User> のディスクリプタは、各要素を存在するかどうかだけでなく User として検査します。限界が 1 つ残っているので、はっきり書きます。参照するだけの外部の .d.ts からインポートした型は、glyph gen dts で具体化するまでディスクリプタを持たないので、その型のフィールドは形ではなく存在だけが検査されます。この境界は意図したものです（Glyph が出力していない型に実行時の検証を約束することはできません）。具体化すればこの限界はなくなります。

「strict な TypeScript と lint の設定で同じことができる」

プログラムの内部ならかなり近づけます。strict、noUncheckedIndexedAccess、明示的な any を禁じるルールで、エージェントがすり抜けさせるものの大半は検出できます。ただし端で止まります。JSON.parse(body) as User はどの設定でもコンパイルが通り、よくある対策の zod スキーマは User の 2 つ目の記述で、1 つ目と手作業で同期させ続けなければなりません。Glyph では型がバリデータです。json.parse<User>(body) は User そのものと照合され、Glyph が実行時に検査できない型は信用されずに拒否されます。

もう 1 つの違いは、誰がそれを当てにできるかです。lint の設定は 1 つのリポジトリが選んだものです。見知らぬ TypeScript のコードベースを開いたエージェントは、そこで any が禁止されているとは想定できません。Glyph ではどこにも書けません。

同じ保証を、エージェントが犯すミスとそれを止めるエラーの観点から説明したのが エージェントが気づかないうちにコードを壊すのを、何が防ぐのか です。
