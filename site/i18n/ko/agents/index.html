에이전트와 도구 개발자를 위한 안내

에이전트를 위한 컴파일러 인터페이스

에이전트는 Glyph 컴파일러에게 심볼이 무엇인지, 편집이 무엇을 깨뜨릴지, 빌드가 왜 실패했는지 묻고 JSON으로 답을 받을 수 있습니다. glyph mcp는 stdio로 도구 열한 개를 제공하며, 각 도구는 glyph query 동사로도 쓸 수 있습니다. glyph llms는 오프라인에서 언어 레퍼런스를 출력합니다.

설정하기

glyph init은 새 프로젝트에 이 .mcp.json을 쓰고, glyph agents는 기존 프로젝트에 이 파일을 (glyph llms를 가리키는 AGENTS.md와 함께) 씁니다. 이 파일을 읽는 MCP 클라이언트라면 어느 것이든 서버를 실행합니다. 포트도 데몬도 없습니다.

glyph init이 쓰는 .mcp.json 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp"]
    }
  }
}

호출 하나와 실제 응답

어떤 파일이 레코드에 선언되지 않은 필드(u.naem)를 읽습니다. 에이전트가 glyph_diagnostics를 호출하면, 레코드가 실제로 선언한 필드와 그 필드를 가진 레코드를 담은 컴파일러 자체의 진단을 받습니다. 0.1.149에서 이 도구가 출력한 내용이며, 표시한 곳만 줄였습니다.

요청 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": {
      "path": "src/user.glyph"
    }
  }
}
결과 
{
  "diagnostics": [ {
    "code": "E0210",
    "severity": "error",
    "stage": "typecheck",
    "message": "type `U` has no field
      `naem`; did you mean `name`?",
    "alternatives": ["name", "email"],
    "alternatives_kind": "fields",
    "cause": "user::U",
    "entity": "user::greet",
    "file": "user.glyph",
    "range": {
      "start": { "line": 9, "col": 10 },
      "end": { "line": 9, "col": 16 } },
    ...
  } ],
  "member": true,
  "module": "user",
  "not_run": [
    { "what": "tsc", ... },
    { "what": "E0104, ...", ... },
    { "what": "E0400, ...", ... } ],
  "path": "src/user.glyph",
  "project_root": "src",
  "unindexed": []
}

not_run은 이 검사가 다루지 않은 것을 알려 주므로, 비어 있는 diagnostics 목록을 전체 빌드 결과로 오해할 일이 없습니다. MCP 클라이언트가 없으면 glyph query diagnostics --path src/user.glyph가 같은 JSON을 출력합니다. 모든 동사를 포함한 전체 도구 목록은 MCP 페이지에 있습니다.

편집하기 전에: 무엇이 깨질까?

examples/apps/csvql은 case 네 개짜리 유니언 Value를 가진, 파일 열한 개로 된 CSV 쿼리 엔진입니다. 다섯 번째 case를 추가하면 어떻게 되는지 물으면 glyph_impact는 파일 4개에 걸친 match 위치 10곳을 나열합니다. WILL_FAIL 8곳과, catch-all arm이 새 case를 삼키고 계속 컴파일되는 ABSORBS 2곳입니다. 실제로 case를 추가하면 정확히 그 8곳에서 E0200 오류 8개가 납니다. 흡수하는 2곳은 아무 말도 하지 않으므로, 답에서 그 위치를 짚어 줍니다.

명령줄에서 같은 질문하기 
glyph query impact --path value.glyph --entity value::Value \
  --change add_variant --variant Blob

빌드가 실패한 뒤에: 수정이 지켜야 할 것은?

glyph check --agent는 check --json의 진단에 키 두 개를 더해 출력합니다. constraints는 수정하는 편집이 깨뜨리면 안 되는 것을 나열합니다. 위의 오타라면 "the record's fields are closed: user::U declares name, email and no others"라고 나옵니다. symbols는 진단이 언급한 모든 심볼에 대한 glyph_symbol 응답을 담고 있으므로, 다음 편집에 두 번째 호출이 필요 없습니다. 수정 방법이 완전히 정해지는 경우에는 glyph fix가 직접 수정합니다.

오프라인에서 언어 읽기

glyph llms는 언어 레퍼런스를 출력하며, 이 사이트의 /llms.txt도 같은 문서입니다. glyph llms --json은 같은 지식을 컴파일러 자체 테이블에서 읽은 데이터로 제공합니다. 진단 코드 77개, prelude 이름 24개, export 340개를 가진 stdlib 모듈 40개, 언어 결정 49개, 그리고 도구 열한 개입니다. glyph llms --negative는 0.1.149에서 잘못된 프로그램 117개(다음 릴리스부터는 139개)를 각 프로그램이 일으키는 코드와 함께 반환하며, 요청할 때 컴파일합니다. 레퍼런스의 진단 테이블과 예약어 테이블이 컴파일러 자체 테이블과 어긋나면 scripts/check_llms_sync.py가 실패합니다.

오프라인 진입점 
glyph llms                  # the reference, as prose
glyph llms --json           # the same, as data from the compiler's tables
glyph llms --negative E0200 # wrong programs that draw E0200
glyph --explain E0200       # the long explanation of one code
