21 · 바이너리 데이터

바이너리 데이터를 다룰 수 있나요, 아니면 모든 것이 문자열인가요?

std/bytes는 옥텟의 불변 시퀀스를 제공하며, std/fs와 std/crypto 모두 이를 다룹니다. 0.1.78까지는 그렇지 않았습니다. 표준 라이브러리의 모든 경계가 문자열을 받고 문자열을 내보냈으므로, PNG를 읽을 수 없었고 HMAC에 실제 키를 줄 수도 없었습니다.

왜 중요한가

따로 작성된 두 애플리케이션, 하나는 PNG 리더이고 하나는 인증기였는데, 같은 주에 바로 이 문장에서 멈췄습니다. 둘 다 언어 안에서는 우회할 방법이 없었습니다.

  • 텍스트로 읽은 파일PNG의 첫 바이트는 0x89인데, 이것만으로는 올바른 UTF-8이 아닙니다. 이 파일을 텍스트로 읽으면 디코더가 해석하지 못하는 모든 바이트가 U+FFFD가 되므로, 프로그램이 보기도 전에 파일이 손상되고 아무것도 오류를 보고하지 않습니다.
  • 문자열을 거친 키키도 마찬가지입니다. HMAC 비밀 값은 임의의 옥텟이고, 이를 문자열로 거치면 값이 바뀌므로 명세와 다른 MAC을 계산하게 되며, 자기 코드에 대해 작성한 테스트는 모두 통과합니다.

Bytes 값이란

Bytes는 런타임에 Uint8Array이므로, 이를 받는 호스트 API에 꺼내지 않고 그대로 넘길 수 있습니다.

시퀀스 연산의 이름은 std/array와 std/string의 대응하는 함수를 따릅니다: len, get, slice, concat, index_of, starts_with. 어느 것도 인자를 변경하지 않습니다.

모든 디코딩은 거부할 수 있고, 어디서인지 알려 줍니다

만드는 데 가장 많은 비용이 든 부분이고, 이것을 쓰는 이유입니다. Node의 Buffer는 잘못된 입력을 받아들이고 성공을 보고합니다.

플랫폼이 조용히 하는 일 
Buffer.from("zz", "hex")        // an empty buffer, no error
Buffer.from("a-b_", "base64")   // skips - and _, decodes the rest, no error
buf.toString("utf8")            // U+FFFD for anything malformed, no error
Glyph가 하는 일 
match bytes.from_hex(input) {
  Ok(b) => use(b),
  Err(e) => io.eprintln("${e.message} at ${number.to_string(e.index)}"),
}

// "z" is not a hex digit at 0
// a trailing base64 group cannot be 1 character(s) long at 3
// not valid UTF-8 at 2
자세히 각 코덱이 거부하는 것

모든 코덱을 Buffer에 맡기지 않고 직접 구현했으므로, hex, base64, base64url, base32 모두 알파벳 밖의 문자, 바이트 하나를 온전히 인코딩하기에 너무 짧은 마지막 그룹, 데이터 끝을 넘는 비트를 담은 마지막 문자를 거부합니다. to_text는 올바른 UTF-8 시퀀스의 일부가 될 수 없는 첫 바이트를 찾아 훑으므로, 판정만이 아니라 위치를 알려 줍니다. from_array는 같은 이유로 0..255 밖의 값을 거부합니다. 조용한 & 0xff는 256을 0으로, 오타를 데이터로 바꿉니다.

코덱을 직접 구현한 덕분에 원래 목적이 아니었던 것도 얻었습니다. 이 모듈은 호스트 API를 전혀 쓰지 않고 Uint8Array, TextEncoder, TextDecoder만 쓰므로, std/bytes만 쓰는 번들은 Web Worker에서도 실행됩니다.

어떤 HMAC을 고르느냐에 따라 답이 달라집니다

std/crypto에는 이제 모든 알고리즘에 두 가지 형태가 있습니다.

  • 일반 이름일반 이름은 문자열을 받아 hex를 반환하며, 비밀번호 해싱에 맞습니다.
  • _bytes 형태_bytes 형태는 Bytes를 받고 반환하며, 전송 프로토콜에 맞습니다.

키가 bytes.from_base64나 crypto.random_bytes에서 왔다면 문자열이 담을 수 없는 바이트가 있으므로, 텍스트 형태는 조용히 다른 값을 계산합니다.

공격자가 제공한 값을 비밀 값과 비교할 때는 bytes.equals가 아니라 crypto.timing_safe_equal을 씁니다. equals는 불일치를 찾는 즉시 반환하므로, 걸린 시간이 앞쪽 몇 바이트가 맞았는지 알려 줍니다.

현재 상태

지금 제공되는 것

  • 함수 21개를 갖춘 std/bytes: 시퀀스 연산, UTF-8 연결, 그리고 문제가 된 위치를 짚는 Result를 반환하는 hex, base64, base64url, base32 코덱.
  • fs.read_bytes, write_bytes, append_bytes는 파일을 디코딩하지 않고 읽고 씁니다.
  • std/crypto에는 모든 다이제스트와 HMAC의 _bytes 형태, 이를 명시한 프로토콜을 위한 SHA-1, random_bytes, timing_safe_equal이 있습니다.
  • 코덱은 RFC 4648 테스트 벡터에, HMAC은 RFC 6238에 맞춰 컴파일러 자체 테스트에서 고정되어 있습니다.

개선 중

  • 아직 정수 코덱이 없으므로 헤더에서 빅엔디언 u32를 읽으려면 산술 연산을 직접 써야 합니다. 32비트를 넘으면 어차피 시프트는 맞는 도구가 아니므로 나눗셈을 씁니다.
  • 16진수 리터럴은 아직 파싱되지 않으므로, 10진수로 쓴 256개 항목짜리 CRC32 테이블은 읽기 어렵습니다.
  • std/websocket은 여전히 바이너리 프레임을 UTF-8 텍스트로 디코딩합니다. 필요했던 타입이 이제 생겼으니 프레임이 다음 차례입니다.
  • 그리고 std/encoding의 오래된 문자열 대 문자열 함수 여섯 개는 여전히 잘못된 입력에 아무 말도 하지 않으므로, 정확해야 하는 것에는 std/bytes 코덱을 쓰세요.
  • 코덱은 node의 Buffer에 맡기지 않고 TypeScript로 작성되었는데, 그래서 Web Worker에서 실행될 수 있으며, 1메가바이트 기준으로 플랫폼 구현보다 1배에서 35배 느립니다.
  • 키나 토큰 인코딩에서는 어느 쪽이든 측정할 만한 비용이 없습니다. 수십 메가바이트를 다룬다면 성능 가이드에 표가 있습니다.
