12 · 명세에서 시작하기

API 명세에서 타입이 있는 클라이언트와 서버를 생성할 수 있나요?

네. glyph gen openapi에 OpenAPI 명세를 주면 됩니다. --client는 작업마다 함수 하나씩, 타입이 있는 HTTP 클라이언트를 생성하고, --handlers는 서버 스텁과 동작하는 route 디스패처를 생성합니다. 기준이 zod 스키마라면 glyph gen zod가 같은 일을 합니다. 모든 결과는 숨겨진 코드 생성 단계가 아니라, 직접 소유하고 편집하는 커밋되고 grep할 수 있는 Glyph로 나옵니다.

왜 중요한가

직접 작성한 API 클라이언트와 DTO는 명세와 어긋나며, 그 어긋남은 아무도 반기지 않는 종류의 버그입니다. Glyph는 실제 코드(타입이 있는 함수, 런타임 디스크립터를 가진 실제 type 선언)를 생성하므로 명세가 기준으로 남고, 다시 생성하는 것은 블랙박스가 아니라 멱등이고 리뷰할 수 있는 diff입니다.

직접 보기: 클라이언트

각 작업은 타입이 있는 경로 매개변수와 요청 본문을 받고 HTTP Response를 반환하는 async fn이 됩니다.

$ glyph gen openapi tasks.yaml --out src/ --client 
async fn createTask(
  base: string,
  body: NewTask,
) -> Result<Response, HttpError> {
  return await post(
    "${base}/tasks",
    body,
  )
}

async fn getTask(base: string, id: number)
  -> Result<Response, HttpError> {
  return await get("${base}/tasks/${id}")
}
$ glyph gen openapi tasks.yaml --out src/ --handlers 
fn route(req: Request)
  -> Result<Response, string> {
  return match req.method {
    "GET" => match segments(req) {
      ["tasks"] => listTasks(req),
      // id captured from the path:
      ["tasks", id] => getTask(req, id),
      else => Ok(json(404, {
        error: "not found",
      })),
    },
    else => Ok(json(405, {
      error: "method not allowed",
    })),
  }
}

--handlers 라우터는 배열 패턴으로 경로를 매칭하므로, /tasks/{id}는 ["tasks", id]가 되고 매개변수를 대신 바인딩해 줍니다. 각 스텁은 본문 파싱 방법을 보여 주는 주석과 함께 501로 시작합니다. 내용을 채우고 await serve(PORT, route)로 연결하면 됩니다.

zod 스키마에서 생성하기

팀이 이미 zod로 모양을 정의하고 있다면 그것에서 바로 생성하세요. 스키마는 자체 디스크립터를 가진 일급 Glyph 타입이 됩니다.

schemas.ts 
export const Task = z.object({
  id: z.number(),
  title: z.string(),
  done: z.boolean(),
})
$ glyph gen zod schemas.ts --out src/ 
type Task = {
  id: number,
  title: string,
  done: bool,
}
// + a runtime descriptor, so
// Task.parse(value) validates.

다형적인 판별 유니언(OpenAPI discriminator)은 실제 Glyph 태그 유니언과, 판별 속성을 읽어 올바른 variant로 검증하는 생성된 parse_<Name>으로 나옵니다. Glyph는 임의의 속성이 아니라 생성자 이름으로 태그를 붙이므로, 생성된 디스패처가 전송 객체와 유니언 사이를 대신 이어 줍니다.

부족한 점: 생성은 전송 형식에 충실하므로 흔한 80%를 매핑합니다. 객체, 원시 타입, 배열, 참조, 선택 및 nullable 필드, 판별 유니언입니다. 정확히 표현할 수 없는 것(문자열 enum, 판별자가 없는 유니언)은 실제 데이터를 거부할 검증기를 만드는 대신 출력되는 안내와 함께 좁혀서 표현합니다. 더 풍부한 enum이 다음 차례입니다. 그리고 도구에는 실제 의존성이 있습니다. gen dts/gen zod에는 Node와 typescript/zod가 필요합니다. gen dts는 프로젝트에서 먼저 찾은 어떤 TypeScript(5, 6, 7.x 네이티브 포트)와도 동작하며, 빠져 있으면 무엇을 설치해야 하는지 정확히 알려 줍니다.

동기화 유지하기

생성된 모든 파일은 그것을 만든 정확한 명령을 헤더에 기록합니다. 명세가 바뀌면 어떤 명령을 다시 실행해야 하는지 찾을 필요가 없습니다. glyph regen이 헤더를 찾아 각 명령을 다시 실행하고 출력을 다시 씁니다. 멱등이므로 명세가 바뀌지 않았으면 아무것도 건드리지 않고, 커밋된 코드가 명세와 어긋나면 실패하는 pre-commit hook이나 CI 검사에 깔끔하게 넣을 수 있습니다.

현재 상태

지금 제공되는 것

glyph gen openapi(타입, --client, 실제 라우터를 갖춘 --handlers), glyph gen dts, glyph gen zod, 그리고 소스에서 전부 새로 고치는 glyph regen: 모든 명령이 커밋되고, 디스크립터를 가지며, 멱등하게 다시 생성되는 Glyph를 출력합니다.

하나의 Glyph 이름으로 작성될 두 타입이 있으면 생성기는 컴파일할 수 없는 파일을 만드는 대신 멈춥니다. 충돌하는 모든 원본을 짚고, 아무것도 쓰지 않으며, --rename Source=GlyphName으로 해결합니다. 이 선택은 생성된 헤더에 기록되므로 glyph regen이 이를 재현합니다.

앞으로 할 것

더 풍부한 enum 매핑과 더 넓은 OpenAPI 지원이며, 각각 전송 형식에 충실하고 좁힐 때는 안내한다는 같은 규칙을 따릅니다. 패키지 자체의 .d.ts에서 생성하면 그 interface와 type 선언을 읽으므로, API가 클래스로 되어 있거나 필드가 Omit 같은 계산된 타입을 쓰는 라이브러리는 생성기가 안내에서 짚고 glyph build가 해석되지 않았다고 보고하는 참조를 남깁니다. 그런 클래스를 import해서 new로 생성하는 것은 생성이 필요 없고 tsc가 검사하므로, 그 경로는 영향을 받지 않습니다.
