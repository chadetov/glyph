Glyph는 왜 tsc가 잡는 것을 더 일찍 잡나요?

생성된 TypeScript에 대한 오류는 작성하지도 않은 코드에 대한 오류이기 때문입니다. Glyph는 이런 오류를 어긴 규칙과 고치는 편집과 함께 여러분의 소스 기준으로 보고합니다.

왜 중요한가

Glyph는 TypeScript로 컴파일한 뒤 출력을 tsc --strict로 타입 검사하므로, Glyph가 모델링하지 않는 실수도 사라지지 않습니다. 한 단계 뒤에 생성된 파일의 언어로 돌아옵니다. 작성한 적 없는 함수 안의 await를 가리키는 TS1308, 또는 쓴 적 없는 switch에 대한 TS2366 같은 식입니다. 줄은 .glyph로 다시 매핑되지만, 설명은 그렇지 않습니다.

컴파일러가 가르치기를 멈추는 곳이 바로 그 틈입니다. 그래서 Glyph가 스스로 판정할 수 있는 규칙은 하나씩 앞으로 옮겨집니다. async fn 밖의 await(E0222), match를 값으로 쓰는데 값을 만들지 않는 match arm(E0223), 그리고 mut 없이 쓴 대입(E0008)입니다. 각각 규칙을 짚고, 그 뒤의 결정을 인용하며, 수정 전후를 보여 줍니다.

직접 보기

arm의 경우는 예전에 완전히 빠져나가던 것입니다. arm 위치의 {}는 빈 레코드가 아니라 빈 블록이므로, arm이 실행되고 아무것도 만들지 않았습니다.

status.glyph: 값이 필요한 위치에서 아무것도 내지 않는 arm 
fn label(s: Status) -> string {
  let text = match s {
    Loading => {},          // an empty block: the arm produces no value
    Ready => "done",
    Failed(msg) => msg,
  }
  return text
}
glyph build 
[E0223] this `match` arm produces no value, but the `match` is used as a value
   ╰─ End the arm with an expression, or `return` from it. `X => {}` is a no-op
      only where the `match` is a statement.
   note: A value-position arm lowers to `case X: { break; }` when it yields
         nothing, so the value would be `undefined` at run time.

이전에는 생성된 switch가 자신의 case를 빠져나갔고, text는 타입이 string이라고 하면서 undefined를 담고 있었습니다. tsc는 그런 모양의 일부는 잡고 일부는 놓칩니다. Glyph는 이제 위치를 판정할 수 있는 모든 곳에서 이를 판정합니다. let, mut, return, 그리고 반환 타입을 선언한 함수의 끝입니다. 문장으로 쓴 match에서는 X => {}를 의도한 무동작으로 그대로 둡니다.

await도 같은 방식입니다. Glyph에는 사용자에게 보이는 Promise가 없습니다. async fn -> T는 await하면 T가 되므로, 그 밖의 곳에서 await는 중단할 것이 없습니다. 예전에는 생성된 파일에 대한 tsc의 TS1308이었습니다. 이제는 E0222이며, 가장 안쪽의 둘러싼 호출 가능한 것이 판정하므로, async fn 안의 동기 람다는 별도의 문맥입니다. TypeScript와 같은 규칙입니다.

glyph build, `fn total() -> number { return await fetch_count() }`에 대해 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

// before: no Glyph diagnostic, then
dist/main.ts:14:18 - error TS1308: 'await' expressions are only allowed
within async functions and at the top levels of modules.

세 번째는 사람들이 첫날 어기는 규칙에 관한 것입니다. Glyph는 모든 변경을 표시하므로, 바인딩을 다시 대입하는 것은 mut x = e이고 새로 만드는 것은 let x = e입니다. 그냥 x = e라고 쓰면 예전에는 규칙이 아니라 문자를 짚는 "unexpected token: Equals"를 보고했습니다. 이제는 E0008이며, glyph --explain E0008이 표시가 있는 이유를 설명합니다. 값이 바뀌는 모든 곳은 mut로 시작하므로 grep "mut total"로 모두 찾을 수 있습니다.

? 연산자도 반대 방향에서 같은 처리를 받습니다. ?는 바인딩과, 그것이 있는 문장 앞에 놓이는 조기 return으로 펼쳐지므로, 펼쳐질 문장이 필요합니다. let, return, 인자, 그리고 이제 match arm 본문에서 동작합니다. 동작할 수 없는 곳에서는 연산자가 구현되지 않았다고 말하는 대신, 어떤 위치인지와 그 밖으로 바인딩하는 방법을 메시지가 알려 줍니다(E0302, E0303).

더 나쁜 경우: tsc도 만족할 때

엉뚱한 곳의 tsc 오류는 성가십니다. 다른 의미가 된 프로그램의 깔끔한 빌드가 진짜 문제이며, Glyph에는 그런 것이 하나 있었습니다. 선언한 모든 최상위 이름은 태그 유니언의 variant 생성자를 포함해 생성된 모듈에 그대로 들어가므로, Error라는 variant는 모듈 최상위에 export function Error(...)를 생성합니다. 그러면 컴파일러가 그 아래에 쓰는 new Error(...)가 여러분의 variant를 호출합니다.

type Key = string | number는 같은 결함이 더 친근한 얼굴을 한 것입니다. Glyph에서 A | B는 멤버가 variant 생성자인 태그 유니언을 선언하므로, 이 줄은 string과 number라는 variant를 선언합니다. 이는 컴파일되고 tsc --strict를 통과했으며, prelude의 number 네임스페이스를 가리는 export const number를 생성했습니다. 나중에 number.to_string 호출이 실패할 때까지는 아무것도 실패하지 않았습니다.

glyph build, `Error` variant가 있는 유니언에 대해 
[E0110] `Error` cannot name a type, variant, or function: the emitted module
        references the JavaScript global `Error`, and this declaration would
        shadow it
 5 │   | Error(string)
   │     ──────┬─────
   ╰─ Rename it (e.g. `Error` -> `Failure`). The name is legal TypeScript, so
      nothing downstream catches the rebinding.

// before: no Glyph diagnostic, then, twenty lines later
dist/main.ts:31:12 - error TS2345: Argument of type 'string' is not
assignable to parameter of type ...

범위는 선언이며, 이름을 바꿀 곳이 바로 거기입니다. 보호 목록은 JavaScript 전역 이름의 일반 목록이 아니라 emitter에서 끌어낸 것이고, 테스트가 emitter를 grep해서 대응하는 항목 없이 새 전역 참조가 나타나면 실패합니다. 핵심은 그 테스트입니다. Number는 int가 배포되어 Number.isInteger를 생성하기 시작하기 전까지 무해했고, 이 문제가 애초에 릴리스까지 간 경로가 그것입니다. Date, Math, JSON은 Glyph가 생성하는 어떤 것도 언급하지 않으므로 여전히 쓸 수 있습니다.

원시 타입 유니언의 경우는 별도의 코드 E0111을 받습니다. 설명 없이 거부하면 아무것도 가르치지 못하기 때문입니다. 그 줄이 실제로 어떻게 파싱되었는지 말하고, 이름 붙은 variant를 안내하며, 원시 TypeScript 유니언이 필요한 경계에는 extern_ts("string | number")를 알려 줍니다. Glyph가 쓰지 못하게 하는 모든 이름은 docs/reference/reserved-words.md에 표로 정리되어 있습니다. 키워드 32개, E0109의 바탕이 되는 TypeScript 예약어 33개, 그리고 가림 목록이며, 각각 그 이름이 쓰이는 이유가 함께 있습니다.

이것이 하지 않는 일도 분명히 해 두겠습니다. 여전히 타입이나 variant 이름을 Error로 지을 수 없으며, 이 문제를 찾아낸 스프레드시트 앱은 그 때문에 Cellerr라는 variant를 씁니다. 원래 쓰고 싶었던 프로그램은 여전히 쓸 수 없습니다. 바뀐 것은 빌드가 통과하면서 다른 의미가 되게 두는 대신, 컴파일러가 이제 선언에서 그렇다고 말한다는 점입니다. 그 이름을 쓸 수 있게 하려면 TypeScript로 갈 때 Glyph 이름을 변형해야 하는데, 그러면 스택 트레이스, dist/에 대한 grep, 직접 작성한 extern/ shim이 보는 것이 바뀌므로, 조용히 할 수 있는 패치가 아닙니다.

틀린 메시지는 메시지가 없는 것보다 나쁩니다

가림 목록은 emitter가 값으로 쓰는 이름에서 시작했습니다. 타입으로 쓰는 이름이 빠져 있었고, 그것이 이 문제 전체의 가장 날카로운 형태를 만들었습니다. 모든 디스크립터의 parse는 Result<T, Issue[]>를 반환하므로, 생성된 모듈은 여러분이 쓰든 안 쓰든 Issue를 씁니다. 자기 모듈에서 type Issue = { path: Array<string>, message: string }을 선언하면 여러분의 것이 이기고, 생성된 Issue 객체에는 여러분의 타입이 모르는 code 필드가 있으며, 빌드는 다른 곳을 가리키는 범위에서 생성된 코드에 대한 tsc 오류로 실패합니다.

Record도 같은 때 목록에 들어갔는데, TypeScript 내장 타입이고 다르게 주장하면 이름이 어디서 왔는지에 대해 메시지가 틀리게 되므로 prelude 이름이 아니라 JavaScript 전역 이름과 함께 분류했습니다. emitter를 grep하는 어긋남 테스트는 이제 앰비언트 타입도 다루며, 타입 위치의 Issue[]를 알아보는 법을 배워야 했는데, 이것이 릴리스까지 간 이유였습니다. Schema, Component, Option은 Date를 자유롭게 두는 것과 같은 규칙으로 계속 허용됩니다. emitter는 여러분이 타입 표기에 썼을 때만 이를 쓰므로, 하나를 선언해도 아무것도 가리지 않습니다.

이 종류의 다른 하나는 import였습니다. 로컬 import 경로는 import하는 파일의 디렉터리가 아니라 빌드 루트, 즉 glyph build에 넘긴 디렉터리에서 해석됩니다. 둘러싼 트리를 빌드하면 import catalog는 아무것도 찾지 못하고, 지금까지는 아무것도 그렇다고 말하지 않았습니다. 타입은 unknown으로 격하되었고, 그에 대한 match는 매칭하던 variant를 잃었으며, 결과적으로 모든 case를 다룬 match에 대해 비망라적 match라는 E0218을 받았습니다. 그 메시지가 요구한 대로 하면 올바른 코드에 죽은 else arm을 추가하게 됐을 것입니다.

glyph build examples/apps, csvql/ 안의 `import catalog`에 대해 
[E0104] unresolved import `catalog`: no module `catalog` under the build
        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from
        the importing file's directory (D15)
   ╰─ Build that module's own directory as the root, or spell the import path
      as it reads from the root.

// before: no import diagnostic, then
[E0218] non-exhaustive match on string   // on a match over all four values

이런 검사의 위험은 문제없는 것에 대해 발생하는 것이고, npm 패키지마다 헛경보를 울리는 import 검사기는 그것이 대신한 침묵보다 나쁩니다. 그래서 빌드는 먼저 .glyph 파일 없이 해석할 수 있는 모듈 이름을 모읍니다. <root>/.types/와 함께 제공되는 Node shim의 모든 declare module "X", 그리고 프로젝트 node_modules의 모든 패키지입니다. 그 목록에 있는 이름은 로컬 파일이 우연히 같은 기본 이름을 갖더라도 절대 보고하지 않습니다. 프로젝트에 node_modules가 아예 없으면 컴파일러는 설치하지 않은 의존성과 오타를 구분할 수 없으므로, 증명할 수 있는 것, 즉 루트 아래의 어떤 .glyph 파일이 답하는 import만 보고합니다.

해석 방식 자체는 바뀌지 않았습니다. 같은 프로그램이 빌드되고 같은 프로그램이 실패합니다. 바뀐 것은 실패가 이제 파일 두 개 떨어진 match를 탓하는 대신 import를 짚는다는 것이며, 그것이 전부입니다. 엉뚱한 원인을 보고하는 컴파일러는 그것을 쫓는 데 쓴 한 시간을 잃게 하고, 그 뒤의 모든 메시지에 대한 신뢰까지 잃게 합니다.

토큰이 아니라 규칙을 짚기

같은 문제의 조용한 형태는 맞지만 아무것도 알려 주지 않는 오류입니다. 레드-블랙 트리를 작성하던 에이전트가 모든 ML 계열 언어에 있는 위치 기반 생성자를 썼는데, 파서는 첫 쉼표에서 “expected )”와 “add the expected token”이라는 조언과 함께 멈췄습니다. 거기에 )를 넣으면 동작하는 프로그램이 아니라 다른 프로그램이 됩니다. Glyph variant는 payload 하나를 담고, 필드가 여러 개인 payload는 레코드입니다. 출력 어디에도 그 두 문장은 없었습니다.

glyph check, 이전과 현재 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.

그렇게 말하려면 파서가 거부하기 전에 목록 전체를 읽어야 했고, 그 덕분에 개수도 셀 수 있습니다. 범위는 우연히 멈춘 구분자가 아니라 필드 여섯 개 전체에 밑줄을 긋고, 제안하는 레코드는 파일에 있는 variant 이름과 타입 여섯 개로 만들어지므로, 수정 방법이 다른 사람의 예제가 아니라 여러분의 프로그램을 짚습니다. 필드 이름은 컴파일러가 제공할 수 없는 유일한 것이므로 빈칸으로 남깁니다.

메시지 뒤의 규칙은 빈틈이 아니라 선택입니다. Node(Black, l, x, b, h, r)은 인자를 바꿔 써도 타입 검사를 통과하는 형태이고, 네 번째 위치는 읽는 사람에게 아무것도 알려 주지 않습니다. 레코드 표기는 모든 필드에 이름을 붙이고, match arm은 쓰는 필드만 짚으며, 둘 다 grep으로 찾을 수 있습니다.

0.1.121에서 검사기가 넘겨받은 두 가지

Order { id: "a", total: 1 }은 TypeScript에서 온 사람이 레코드를 만들 때 쓰는 형태인데, Glyph에는 이런 형태가 없습니다. 값은 단독으로 쓰고 타입은 타입 표기에 둡니다. 예전에 컴파일러는 그 줄에 대해 0으로 종료한 빌드에서 도달할 수 없는 코드라는 E0108을 보고했습니다. 이름이 타입으로 해석되고 중괄호가 return 뒤의 블록으로 파싱되었기 때문입니다. 값 자리에 쓴 타입 이름은 E0228이고, 메시지는 선언에서 읽어 오므로 레코드는 필드를, 태그 유니언은 variant와 payload 모양을, 문자열 리터럴 유니언은 리터럴을 나열합니다. Order.parse(raw)와 Order.is(v)는 계속 허용됩니다. 타입 자신의 디스크립터의 수신자는 타입 이름이 들어갈 수 있는 유일한 표현식 위치이기 때문입니다.

그 수정은 이름이 타입인 경우를 고쳤고 파싱은 그대로 두었으므로, return h() { k: 2 }는 여전히 h()를 반환하고 경고와 함께 중괄호를 버렸습니다. 0.1.146부터는 문장이 끝난 줄의 {는 앞의 이름이 무엇이든 파싱 단계에서 E0013이고, 그 도움말이 같은 다시 쓰기를 알려 줍니다. 0.1.149부터 이 규칙은 중괄호로 시작하는 문장만이 아니라 모든 문장에 적용됩니다. let s = "a" "b"는 예전에 "a"를 바인딩하고 "b"를 버렸고, Glyph에는 캐스트가 없으므로 return x as User는 문장 세 개였습니다. 블록 안의 각 문장은 자기 줄에서 시작합니다.

glyph check, TypeScript 방식으로 만든 레코드에 대해 
[E0013] a statement cannot begin on the line where
        `return Order` ends
   ╰─ Glyph has no `TypeName { ... }` construction form. Write the literal
      alone and put the type on the annotation: `let o: Order = { id: "a" }`.

// 0.1.121 to 0.1.145: [E0228] on `Order`, then [E0108] on the braces
// before that: [E0108] Warning: lint: unreachable code, and exit 0

다른 하나는 원시 타입에 대입한 prelude 컨테이너입니다. o: Option<int>일 때 let x: string = o는 Glyph 검사기에서 아무것도 나오지 않았고, int로 선언된 매개변수에 Nullable<int>를 넘기는 것도 마찬가지였습니다. 이제 컨테이너 다섯 개가 양방향으로 다뤄집니다. Option, Result, Array, Record, Nullable은 인자가 무엇이든 string, number, bool이 결코 아니며, 스칼라에 대한 Nullable<T>는 한 단계 안의 T에 대해 판정하므로, let v: Nullable<int> = 3은 올바르고 let v: Nullable<int> = "three"는 E0204입니다. Nullable의 경우가 다른 것들보다 이 페이지에 더 어울리는데, tsc가 할 수 없는 판정이기 때문입니다. 생성된 const v: number | null = 3은 호출을 검사하기 전에 다시 number로 좁혀지므로, null을 드러내려고 존재하는 경계 타입이 int가 선언된 곳을 조용히 통과했고, 이를 잡을 수 있는 곳은 Glyph 검사기뿐이었습니다.

다음은 선언된 레코드나 유니언에 대한 같은 컨테이너였습니다. 0.1.130부터 let user: User = json.parse(body)는 expected User, found Result<unknown, Array<Issue>>인 E0204입니다. 예전에는 tsc만 이를 말했으므로, glyph check --no-tsc, 에디터, 플레이그라운드는 경계가 올바르게 처리해야 할 바로 그 한 줄에서 깨끗한 파일을 보여 줬습니다.

배열이나 문자열의 철자가 틀린 멤버도 예전에는 tsc를 기다리던 경우입니다. xs.lenght는 이제 "did you mean length"와 함께 E0210이며, 레코드의 필드 읽기를 필드에 대해 검사하듯 TypeScript 라이브러리가 배열과 문자열에 선언한 멤버에 대해 검사합니다. tsc도 둘 다 거부했을 것이므로 그것을 실행한 빌드는 이미 실패했습니다. 바뀐 것은 검사기와 그 위에 만든 모든 것이 먼저 이를 본다는 점입니다.

그리고 0.1.133부터 세 가지 더

let up = s.toUpperCase는 TypeScript에서 타입 검사를 통과하고 up()을 실행하면 예외를 던집니다. 읽는 순간 그것이 속한 문자열을 잃기 때문입니다. Glyph는 이를 E0234로 거부하고, 여기에 .bind(s)를 쓰는 것도 거부합니다. 대신 호출을 람다로 감싸세요. 검사기는 이제 TypeScript 자체의 선언에서 생성한 테이블로 각 배열 및 문자열 메서드가 무엇을 반환하는지 압니다.

Result에 대한 r?.label은 "오류를 전달한 다음 필드를 읽는다"처럼 읽힙니다. 하지만 이는 optional chaining이고 Result는 절대 null이 아니므로, Result 객체에서 필드를 읽고 아무것도 전달하지 않습니다. CSV 쿼리 도구를 만들던 에이전트가 정확히 이렇게 썼습니다. 이제 Option에서도 E0236이며, 도움말은 먼저 ?로 바인딩하라고 안내합니다.

타입 인자 없는 json.parse(body)는 검사하지 않은 읽기이며 Result<unknown, ...>입니다. Result<User, ...>가 선언된 곳에 쓰면, 예전에는 tsc가 선언에서 User를 추론했고 프로그램은 첫 필드를 읽을 때 충돌했습니다. 이제 emitter가 unknown을 명시적으로 쓰므로 glyph check가 tsc를 통해 이를 거부합니다. Glyph 자체 검사기는 선언된 타입 안에 unknown이 들어가는 것을 아직 잡지 못하므로, --no-tsc와 에디터는 Result<User, ...>가 선언된 곳에 쓴 Result<unknown, ...>를 여전히 놓칩니다. (그냥 let user: User = json.parse(body)는 바깥 타입이 이미 틀렸으므로 Glyph 자체 검사기의 E0204입니다.) 모든 깊이에서 unknown을 거부하는 것은 G325이며, 0.1.158에 계획되어 있습니다.

그리고 0.1.122에서 두 가지 더

type Mode = "read" | "write"는 유한한 문자열 집합을 선언하는데, Glyph 검사기는 값을 이와 아무것으로도 비교하지 않았습니다. 숫자, bool, 레코드, 집합 밖의 문자열이 모두 사용하지 않는 변수 경고만 남기고 glyph check --no-tsc를 통과했고, tsc는 생성된 TypeScript에서 그 모두를 거부했습니다. 그래서 전체 glyph build는 이에 대해 틀린 적이 없지만, 루프에 tsc가 없는 네 곳, 즉 --no-tsc, 언어 서버, MCP 도구, 플레이그라운드는 틀렸습니다.

let b: Mode = "rw"

// before: four unused-variable warnings, exit 0

tsc를 실행하지 않고, tsc가 보고한 네 개를 같은 네 문장에서 보고합니다. 이 규칙은 유니언을 런타임의 실제 모습인 string으로 읽고, 양방향에서 검사기에게 대응하는 string 질문을 하므로, 레코드나 컨테이너를 string에 대해 이미 거부하는 규칙을 모양마다 다시 쓰지 않고 그대로 물려받습니다. 두 리터럴 집합은 집합으로 비교하므로 더 좁은 유니언은 더 넓은 것이 선언된 곳에 들어갑니다. 별칭 연쇄는 양쪽에서 따라가고, import한 유니언은 로컬 유니언처럼 판정하며, Nullable<Mode>는 유니언을 유지한 채 안으로 들어갑니다.

레코드 필드나 제네릭 인자 안에 중첩된 유니언은 0.1.122에서는 tsc에 맡겼고, 0.1.123에서 판정합니다. 아래를 보세요.

두 번째는 tsc와는 전혀 관계없는 이야기입니다. 파서는 깊이 제한 없는 재귀 하강 파서이므로, 2천 단계 깊이로 중첩된 표현식은 프로세스의 스택을 다 써서 종료 코드 134로 중단되었습니다. glyph check에서도 나쁘지만, 루트 아래의 모든 파일을 읽는 glyph lsp와 glyph mcp에서는 더 나쁩니다. 병적인 파일 하나가 워크스페이스 전체의 서버를 멈추게 했습니다. 이제는 65번째 단계를 열려는 토큰에서 E0011을 냅니다.

0.1.123: 생성되는 string이 아니라 값이 실제로 가진 리터럴

type Mode = "read" | "write"는 선언에 집합을 두고 값에는 아무것도 두지 않았으므로, "read"는 string이고 ["read", "write"]는 Array<string>이었습니다. 그래서 두 프로그램을 구별할 수 없었습니다. Array<Mode>가 선언된 곳의 return ["read", "write"]는 tsc가 컴파일하고, xs: Array<string>에 대한 return xs는 거부합니다. 0.1.122는 틀리게 판정하는 대신 그 짝의 판정을 거절했는데, 이는 틀린 프로그램을 포기하는 대가로 올바른 프로그램을 얻은 것이었습니다. { mode: Mode }에 대한 { mode: "nope" }는 아무것도 내지 않았습니다.

이제 작성한 문자열 리터럴은 그것이 나타내는 리터럴 하나짜리 타입을 가지고, 배열 리터럴의 요소 타입은 요소들의 타입을 합친 것이며, 작성한 배열이나 객체 리터럴은 선언된 타입에 대해 요소 하나하나, 필드 하나하나 검사되므로, 진단이 리터럴을 짚고 밑줄을 긋습니다.

glyph check --no-tsc, 컨테이너 하나 안의 리터럴에 대해 
type Mode = "read" | "write"
type Cfg = { mode: Mode }

fn ok() -> Array<Mode> { return ["read", "write"] }
fn bad() -> Array<Mode> { return ["read", "nope"] }
fn wrong() -> Cfg { return { mode: "nope" } }
// 0.1.122: nothing, on all three
[E0204] type mismatch: expected `Mode`, found `"nope"`   (twice)

리터럴은 TypeScript가 넓히는 곳에서 다시 string으로 넓어집니다. 타입 표기가 없는 let(생성된 TypeScript let도 같은 방식으로 넓어집니다)과, 작성한 배열에 대한 for의 요소 바인딩입니다. 그래서 let l = "read" 다음의 takes_mode(l)은 여기서 거부되고 거기서는 TS2345입니다. const는 TypeScript const로 생성되어 리터럴을 유지하므로 takes_mode(CM)은 둘 다에서 컴파일됩니다. 이름을 통해 도착한 리터럴 타입은 넓어지지 않으며, 이는 TypeScript 자체의 freshness 규칙입니다. 이 모든 경우는 추론이 아니라 같은 TypeScript에 tsc --strict를 실행해서 확정했습니다.

판정을 거절하는 짝이 하나 남아 있습니다. Record의 키 인자와 다른 Record의 키 인자입니다. TypeScript는 Record<string, V>를 Record<Mode, V>가 선언하는 모든 키를 덮는 인덱스 시그니처로 쓰고 양방향 모두 받아들이므로, 이를 거부하면 컴파일되는 프로그램을 거부하게 됩니다. 검사기가 아직 아무 말도 하지 않는 모양이 두 가지 더 있습니다. Some(...) 안의 리터럴(prelude 생성자에 아직 타입이 없기 때문)과, 타입 표기 없는 let에 바인딩한 레코드 리터럴(객체 리터럴에 대해 레코드 타입을 합성하지 않기 때문)입니다.

std/ 아래의 모듈이 진단 없이 죽은 코드였습니다

std/와 extern/은 컴파일러가 가진 모듈을 가리키며, resolver는 이를 import용으로 예약해 두었습니다. 그런데 프로젝트 파일이 그런 모듈을 선언하는 것은 막지 않았습니다. 자기 src/io.glyph의 module std/io는 깔끔하게 컴파일되었고, 그다음 import std/io { shout }는 스텁으로 해석되어 shout가 export되지 않았다고 보고했습니다. 여러분의 파일은 읽히지도 않았습니다. 진단도 없고 코드도 실행되지 않는 파일은 컴파일러가 남길 수 있는 최악의 상태입니다. 겉보기에 잘못된 것이 하나도 없기 때문입니다.

한도는 64이며, 고른 것이 아니라 측정한 값입니다. 가장 비싼 구문인 중첩 배열 리터럴 한 단계는 릴리스 빌드에서 스택 7,792바이트, 디버그 빌드에서 8,810바이트를 쓰며, 주어진 깊이를 파싱할 수 있는 가장 작은 스레드 스택을 이진 탐색해서 찾았습니다. 파서가 실행되는 가장 얇은 스택은 생성된 스레드의 2 MiB이고, 언어 서버의 워커가 받는 것이 이것이며, 64단계는 더 비싼 빌드에서도 그 3분의 1 미만을 씁니다. 이 저장소의 .glyph 파일 343개 중 가장 깊은 중첩은 16입니다. 한도는 표현식, 타입, 패턴, 블록, JSX 자식에 똑같이 적용되며, 깊이는 파일 전체에 쓰는 예산이 아니라 구문별 중첩이므로 형제 배열 천 개는 여전히 파싱됩니다.

어느 컴파일러도 틀리지 않았을 때

세 번째 모양이 있고, 가장 나쁘게 읽히는 것이 이것입니다. Glyph는 아무것도 보고하지 않고, tsc는 맞는 것을 보고하며, 작성한 프로그램은 문제가 없었습니다. 실패한 것은 둘 사이의 번역입니다.

Glyph에서 바인딩은 평생 하나의 타입을 가집니다. TypeScript는 바인딩을 마지막으로 대입된 것으로 좁히고, 그 boolean은 true | false 유니언이므로, let done = false는 false 타입으로 tsc에 도달했고 생성된 switch의 true arm은 매칭할 것이 없었습니다.

poll.glyph, 그리고 0.1.89 이전에 tsc가 이에 대해 한 말 
fn classify() -> int {
  let done = false
  match done {
    true => { return 1 },
    false => { return 0 },
  }
}

// no Glyph diagnostic, then
[TS2678] Type 'true' is not comparable to type 'false'.

문자열 리터럴 집합으로 선언한 타입도 같은 방식으로 실패했고, ==도 마찬가지였는데 대신 TS2367로 돌아왔습니다. 메시지 두 개, 코드 두 개, 원인 하나입니다. 이 문제에 부딪힌 앱은 타이머 콜백이 설정하는 플래그를 폴링하고 있었는데, Glyph에 직접 생성할 수 있는 Promise가 없는 동안 이벤트 기반 API를 값으로 바꾸는 방법이 그것입니다. 콜백은 핵심이 아니었습니다. 콜백 없는 네 줄로도 재현됩니다.

진단할 것이 없으므로 새 진단으로 고치지 않습니다. emitter가 이제 값으로 분기하는 두 곳, 즉 match 검사 대상과 ==나 !=의 양쪽에서 검사기가 이미 결정한 타입을 다시 적습니다. 각 쪽은 자기 타입으로 결정되고 옆에 있는 것은 무시하므로, 두 바인딩 사이의 비교도 리터럴과의 비교와 똑같이 다뤄집니다.

원하는 검사는 여전히 발생합니다. m이 Mode일 때 m == "nope"는 여전히 거부되며, 이제 메시지는 m이 우연히 담고 있던 멤버 하나가 아니라 Mode를 짚습니다. 이를 대입에서 했다면 코드는 적었겠지만 이것을 버렸을 것입니다. 타입 표기가 있는 대입은 받아들여지지 않는 곳에서도 Mode로의 캐스트는 받아들여지고, 멤버십 검사는 Glyph가 의도적으로 tsc에 맡기는 부분입니다.

비용은 작고, 밝혀 둘 만합니다. 캐스트는 확인하는 것만이 아니라 좁힐 수도 있으므로, Glyph가 bool로 타입을 매긴 값의 TypeScript 타입이 unknown으로 나왔다면, 예전에 switch가 불평하던 곳을 이제 통과합니다. 두 타입은 여전히 비교 가능해야 하므로, 의미 있을 만큼 멀리 어긋난 모델, 즉 string 대 bool은 아무것도 아닌 대신 TS2352를 보고합니다.

같은 오타, 두 가지 답

철자가 틀린 표준 라이브러리 함수는 예전에 import를 어떻게 썼느냐에 따라 다른 답을 받았는데, 이는 어느 답도 믿지 말라고 가르치는 종류의 불일치입니다.

이름 import, 언제나 E0105 
import std/string { repeeat }
[E0105] import: `repeeat` is not exported by `std/string`
네임스페이스 읽기, 0.1.72 이전 
import std/string
string.repeeat(s, 2)
[TS2551] Property 'repeeat' does not exist on type ... Did you mean 'repeat'?

첫 번째 표기는 해석 단계에서 모듈의 export 목록에 대해 검사되었습니다. 두 번째는 아예 검사되지 않았으므로 tsc까지 넘어갔고, 그것은 객체에 대한 속성 접근으로 보고 그 관점에서 답했습니다. 이제 두 표기 모두 export 목록을 거치며, 둘 다 멤버와 그것이 빠진 모듈을 짚는 E0105를 보고합니다.

이를 켜자마자 아무도 찾고 있지 않던 것이 나왔습니다. 테스트 fixture 하나가 함수 이름이 write_text인데 fs.write를 호출하고 있었습니다. 그 fixture는 타입 검사를 끄고 실행되고 컴파일러의 다른 어떤 부분도 네임스페이스 멤버를 보지 않았기 때문에 몇 달 동안 통과했습니다. 이제 export 목록이 두 표기 모두의 기준이므로, 별도의 검사가 이를 런타임이 실제로 export하는 것과 맞춰 둡니다. 그 검사는 작성한 뒤 실패하는지 확인하려고 일부러 망가뜨려 봤는데, 그렇게 해서 첫 번째 버전이 아무것도 검사하지 않고 있었다는 것을 알게 되었습니다.

현재 상태

지금 제공되는 것

async fn 밖의 await에 대한 E0222, 값을 만들지 않는 값 위치 match arm에 대한 E0223, mut가 빠진 대입에 대한 E0008, 레코드 형태만 존재하는데 위치 기반 payload 필드를 여러 개 준 variant에 대한 E0010, 전달할 수 없는 위치의 ?에 대한 E0302/E0303, 생성된 모듈이 이미 의존하는 이름을 가리게 될 선언에 대한 E0110/E0111, 빌드 루트 아래의 어떤 모듈도 가리키지 않는 로컬 import에 대한 E0104, 이름 import로 닿았든 네임스페이스로 닿았든 모듈이 export하지 않는 이름에 대한 E0105, 값 자리에 쓴 타입 이름에 대한 E0228, 다른 문장이 끝난 줄에서 시작하는 문장(예전에는 그 뒤의 값을 버렸습니다)에 대한 E0013, tsc가 좁혀서 없애는 Nullable<T>의 경우를 포함해 원시 타입이나 선언된 레코드 또는 유니언에 대입하거나 넘긴 prelude 컨테이너에 대한 E0204/E0211, 배열이나 문자열에 없는 멤버에 대한 E0210, 문자열 리터럴 유니언의 선언된 집합에 없는 값에 대한 같은 두 코드, 64단계를 넘어 중첩된 구문에 대한 E0011, 예전에는 파서에서 일반적인 "expected module path segment"로 멈추던 상대 경로 import에 대한 E0101, 그리고 예전에는 깔끔하게 컴파일되고 닿을 수 없었던 std/나 extern/ 아래에 선언한 프로젝트 모듈에 대한 E0113. 가림 목록은 emitter가 스스로 쓰는 타입도 다루므로, Issue와 Record는 선언에서 잡힙니다. 모든 코드에는 한 줄짜리 수정 방법, 규칙을 설명하는 참고 사항, 그리고 자세한 glyph --explain 설명이 있습니다. docs/error-codes.md에 목록이 있고, 테스트가 둘을 맞춰 둡니다.

개선 중

array.map, flat_map, zip은 여전히 async 콜백을 아무 불평 없이 받아 pending 값의 배열을 돌려주며, 이는 [object Promise]로 출력됩니다. 조건 함수를 받는 배열 함수 다섯 개는 콜백 위치에서 E0211로 이를 막습니다. 나머지 세 개를 같은 방식으로 모델링하면 Glyph가 작업을 동시에 실행하는 방법인 par.all(array.map(items, async fn ...))도 거부하게 됩니다. pending 값의 배열을 언어에서 표현할 방법이 없기 때문입니다. 이는 빠진 항목이 아니라 타입 시스템 차원의 결정이므로 열려 있습니다. 모듈 수준 const 초기값에는 둘러싼 호출 가능한 것이 없으므로 최상위 await가 허용되고 생성된 ESM이 이를 실행합니다. Glyph가 암묵적인 비동기 모듈 초기화를 원하는지는 아직 열린 명세 질문입니다. E0223은 함수가 반환 타입을 선언할 때만 끝의 match를 판정할 수 있으므로, 타입 표기 없는 람다 안의 arm은 여전히 tsc까지 갑니다. 가림 쪽에서는 두 가지가 절반만 되어 있습니다. E0110은 이름을 유지하게 해 주지 않고 바꾸라고 하므로, Error, Number, Object, Array, Promise는 여전히 타입이나 variant 이름으로 쓸 수 없습니다. 그리고 E0111은 type Key = string | number가 엉뚱한 의미가 되는 것을 막지만 그것을 표현할 방법은 주지 않습니다. 원시 타입 두 개의 유니언은 Glyph에서 extern_ts 말고는 표현할 방법이 없고, 그 내용은 Glyph 자체 검사기가 불투명하게 다룹니다. 태그 없는 유니언은 망라성, 런타임 디스크립터, is에 영향을 주므로 타입 시스템 차원의 결정이며, 일정이 잡혀 있지 않습니다. E0104는 glyph build와 glyph check에는 닿지만 에디터에는 닿지 않습니다. LSP는 빌드 루트 없이 문서의 텍스트를 분석하고, 워크스페이스 폴더도 빌드 루트가 아니므로, 추측하면 이 검사가 피하려고 설계된 오탐이 생길 것입니다. 그리고 예약어 매개변수는 같은 파일의 관계없는 오류 뒤에 여전히 숨습니다. 수집 단계의 실패가 그것을 찾았을 해석 단계를 건너뛰게 하기 때문입니다. 이와 별도로, bool이나 문자열 리터럴 유니언 바인딩을 매칭 가능하게 유지하는 읽기 위치 고정은 생성 중인 모듈 안에서만 타입 별칭을 따라가므로, 한 모듈의 pub type Ready = bool과 다른 모듈의 let r: catalog.Ready = false는 여전히 TS2678로 tsc에 도달합니다. 문자열 리터럴 유니언은 세 가지 import 표기 모두에서 모듈 간에 다뤄지며, 0.1.123부터 진단은 표기 중 하나에서만 리터럴 집합을 출력하는 대신 모든 표기에서 선언(expected Mode)을 짚습니다.
