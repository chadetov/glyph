10 · 기존 앱 안에서

기존 앱 안에서 Glyph를 도입할 수 있나요, 아니면 전부 아니면 전무인가요?

다시 작성할 필요가 없습니다. 앱은 TypeScript로 두고, 틀리면 안 되는 부분(모델, 권한, 상태 전이, 돈 계산)을 Glyph로 작성합니다. glyph build는 앱이 여느 로컬 파일처럼 import하는 모듈을 생성하며, 번들러 설정도 경로 별칭도 필요 없습니다.

왜 중요한가

대부분의 팀은 애플리케이션을 다시 작성할 수 없고, 애플리케이션 대부분은 Glyph가 필요하지 않습니다. 필요한 부분은 도메인 핵심입니다. 다음 달에 AI 에이전트가 편집할 규칙이고, 아무도 조용히 틀리기를 원하지 않는 부분입니다.

이 핵심을 Glyph로 두면 망라적인 match, 캐스트 없음, 검증되는 경계를 정확히 효과가 있는 곳에서 얻고, React 컴포넌트, 스타일, 인프라는 평범한 TypeScript로 남습니다.

호스트에 추가할 것이 없습니다

생성된 코드에 필요한 것은 모두 코드와 함께 이동합니다.

  • 상대 경로 import번들된 표준 라이브러리를 포함해 import는 상대 경로이므로, 프로젝트의 tsconfig.json과 번들러에 아무것도 추가할 필요가 없습니다. 기본 Vite 프로젝트가 출력을 그대로 컴파일하고 번들하며, 같은 파일이 호스트의 tsc --strict도 통과합니다.
  • pub 내보내기앱이 import하는 것에는 pub를 붙이세요. 붙이지 않은 선언은 그 모듈 안에서만 보입니다.

가정이 아닙니다. 외부 엔지니어가 이 방식으로 React 칸반 보드를 만들었고, RBAC 매트릭스, 분석 공식, 상태 전이를 직접 작성한 React UI 아래의 Glyph 모듈 네 개에 담았습니다.

현재 상태

지금 제공되는 것

  • 생성된 출력은 호스트 프로젝트에 그대로 들어갑니다. 전체가 상대 경로 지정자이고, prelude 타입은 코드 자체가 가지고 있습니다.
  • 기본 Vite 프로젝트, 호스트 tsc --strict, esbuild, tsx로 검증했습니다.
  • 배포 가이드에 혼합 구조가 설명되어 있습니다.

앞으로 할 것

  • 아직 watch 모드는 없습니다. .glyph 소스를 편집한 뒤에는 glyph build를 다시 실행하세요(dev 스크립트에 연결해 두면 됩니다).
  • std/fs나 std/net을 쓰는 모듈은 Node를 다루는 여느 TypeScript처럼 호스트에 @types/node가 필요합니다.
