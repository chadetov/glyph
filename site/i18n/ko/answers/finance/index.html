16 · 돈과 안전

돈을 다루거나, 내가 통제하지 못하는 입력을 맡겨도 되나요?

네. 돈은 정확하게 다루고, 음수가 아님 같은 불변식은 경계에서 강제되는 타입이며, 신뢰할 수 없는 입력은 정제되지 않으면 SQL이나 셸 싱크에 닿을 수 없습니다. 각각 틀리면 컴파일 오류나 파싱 오류이며, 누군가 함수 세 개 떨어진 곳에서 기억해야 하는 관례가 아닙니다.

이 페이지의 내용

  1. 돈은 float가 아닙니다
  2. id와 카운터
  3. 타입으로서의 불변식
  4. 인젝션
  5. 현재 상태

돈은 float가 아닙니다

std/decimal은 BigInt 위의 정확한 10진 고정소수점입니다.

  • 정확한 산술덧셈, 뺄셈, 곱셈은 정확합니다.
  • 나눗셈나눗셈은 명시적인 자릿수를 받아 0에서 먼 쪽으로 반올림합니다.
  • 잘못된 입력형식이 잘못된 금액은 조용한 NaN이 아니라 Err로 파싱됩니다.

id와 카운터는 253을 넘어도 정확합니다

float 범위를 넘어 반올림되는 계정 id나 원장 카운터는 또 다른 종류의 재앙입니다.

bigint는 123n 리터럴을 쓰는 정확한 임의 정밀도 정수이고, bigint 타입의 레코드 필드는 경계에서 typeof === "bigint"를 검증하므로, JSON number로 도착한 id는 조용히 잘리지 않고 거부됩니다.

불변식은 주석이 아니라 타입입니다

"금액은 음수가 아니다", "평점은 1에서 5 사이다" 같은 검사는 한 번 작성되고 나중에 잊히는 종류입니다. where 정제는 불변식을 타입에 넣고, 디스크립터가 경계에서 이를 강제합니다.

refinements.glyph 
type Amount = int where value >= 0
type Rating = int where value >= 1 && value <= 5

Amount.parse(-1)   # Err  (not just "is a number")
Rating.parse(6)    # Err
Amount.parse(3.5)  # Err  (int check too)

조건식을 통과하지 못한 값은 애초에 Amount가 되지 않습니다.

인젝션은 컴파일 오류입니다

전형적인 원격 코드 실행 경로는 신뢰할 수 없는 입력이 SQL 쿼리, 셸 명령, HTML 템플릿에 닿는 것입니다. std/taint는 이를 타입 오류로 만듭니다.

  • 두 타입외부에서 온 값은 Tainted이고, 보호하려는 싱크는 Trusted를 받습니다.
  • 건너가는 길은 하나둘은 구조적으로 다르므로 한쪽에서 다른 쪽으로 가는 유일한 방법은 명시적인 sanitize입니다.
안전한 경로는 컴파일됩니다 
fn run_query(sql: Trusted<string>) -> void { ... }

let input: Tainted<string> = taint(req.body)
run_query(sanitize(input, escape))   # ok
인젝션 경로는 컴파일되지 않습니다 
module query

import std/taint { Tainted, Trusted, taint, expose }

fn run_query(sql: Trusted<string>) -> string {
  return expose(sql)
}

pub fn handle(body: string) -> string {
  let input: Tainted<string> = taint(body)
  return run_query(input)
}

// [E0211] argument type mismatch: expected
//   `taint.Trusted<string>`, found
//   `taint.Tainted<string>` (query.glyph:11)

오염된 값을 싱크에 바로 넘기면 tsc가 컴파일을 거부합니다.

현재 상태

지금 제공되는 것

  • 정확한 금액을 위한 std/decimal
  • 정확한 큰 정수를 위한 bigint
  • 불변식을 경계에서 검증하는 where 정제
  • 명시적인 sanitize 없이 신뢰할 수 없는 입력이 보호된 싱크에 닿지 못하게 하는 std/taint
  • 모두 검사됩니다. 잘못된 금액이나 id는 parse에서 실패하고, 잘못된 불변식도 parse에서 실패하며, 정제되지 않은 값은 tsc에서 실패합니다.

한계

  • 현재 where 정제는 원시 기본 타입을 다룹니다. 레코드와 필드 간 불변식(where value.paid <= value.total)은 계획된 확장입니다.
  • taint는 자동 흐름 분석이 아니라 싱크의 타입을 Trusted로 지정해서 선택하는 규율입니다
    자세히

    taint는 자동 흐름 분석이 아니라 싱크의 타입을 Trusted로 지정해서 선택하는 규율입니다. 컴파일러는 여러분이 선언한 경계를 강제할 뿐, 프로그램 전체에 걸쳐 오염을 대신 추론하지 않습니다.
