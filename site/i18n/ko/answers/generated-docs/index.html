25 · 어긋나지 않는 문서

에이전트가 읽는 문서는 생성된 것인가요, 사람이 써서 낡은 것인가요?

생성된 것입니다. glyph llms --json은 진단 목록, prelude, stdlib 시그니처, 언어 결정, 도구 설명서를 컴파일러 자체 테이블에서 출력하고, 사람이 쓴 사본이 이와 다르면 게이트가 빌드를 실패시킵니다. 에이전트가 처음 읽는 문서의 모든 Glyph 예제는 잘못된 예제까지 포함해 컴파일됩니다.

왜 중요한가

그냥 하는 질문이 아닙니다. 솔직한 답이 예전에는 "사람이 썼고, 낡았다"였기 때문입니다.

  • 도구 목록에이전트 안내 문서는 MCP 서버가 "도구 다섯 개를 제공한다"며 다섯 개를 나열했습니다. 서버는 일곱 개를 제공했습니다. 서버 자체의 지침이 에이전트에게 가장 먼저 쓰라고 하는 두 개는 문서에 한 번도 나오지 않았습니다.
  • 오류 코드오류 코드 58개는 사람이 관리하는 사본 세 곳에 있었고, 코드 문자열이 있는지만 검사했습니다.
  • 예제그 문서의 Glyph 예제 19개 중 2개만 컴파일되었고 17개는 단편으로 건너뛰었습니다.

모두 같은 결함입니다. 컴파일러에 대한 문서를, 선의를 가진 사람들이 컴파일러 옆에서 관리한 것입니다. 그것을 읽는 에이전트는 어느 문장이 여전히 참인지 알 수 없었고, 우리도 마찬가지였습니다.

진단을 위한 테이블 하나

진단 항목에는 목록의 설명 문장, 한 줄짜리 수정 방법, 자세한 설명, 그리고 컴파일러가 실제로 낸 진단에서 가져온 도움말과 참고 사항이 담깁니다.

코드 77개 중 51개에는 그 코드를 일으키는 잘못된 프로그램도 있으며, 요청하는 순간 컴파일됩니다. 나머지 26개에는 코퍼스에 사례가 없다고 적혀 있습니다.

자세히 사본 세 개를 하나로 합친 과정

코드 77개는 컴파일러의 테이블 하나에서 나오고, docs/error-codes.md와 에이전트 안내 문서의 목록 테이블은 어긋나면 실패하는 스크립트가 그 테이블에서 씁니다. 예전에 있던 사본 세 개를 합치다 보니, 설명은 있지만 목록에 자리가 없는 코드 하나와, 이스케이프된 파이프 때문에 들어 있던 표를 조용히 망가뜨린 행 하나가 나왔습니다.

prelude, stdlib, 그리고 결정들

prelude는 resolver가 해석에 쓰는 이름 24개와 각각이 무엇인지입니다. stdlib는 모듈 40개와 export 340개이며, 각 시그니처는 검사기 자체 테이블에서 읽어 진단과 같은 타입 출력기로 출력하므로, 문서의 시그니처가 곧 검사기가 여러분에게 요구할 시그니처입니다.

자세히 export가 나뉘는 방식

export는 세 가지로 나뉘고 절대 두 가지로 뭉치지 않습니다. 129개는 모든 위치가 모델링된 시그니처이고, 46개는 매개변수 타입 자리에 ?가 있어 몇 자리가 남았는지 알려 주는 줄과 함께 partially_modeled로 세며, 165개는 시그니처가 아예 없습니다. ?는 unknown을 출력한 것이므로, 완전한 시그니처로 공개되는 일은 없습니다.

이력 duplicate_numbers가 있는 이유

duplicate_numbers가 있는 이유는 생성기가 명세 자체의 목록을 읽기 때문인데, 처음 실행했을 때 둘 다 D43번인 서로 다른 결정 두 개를 찾아 "duplicate_numbers": [43]을 출력했습니다. 중복을 지우지 않고 충돌을 보고하며, 그 덕분에 누군가 알아챘습니다. 컴파일러에서 D 번호를 키로 쓰는 곳은 없으므로 영향을 받은 프로그램은 없었고, 인용을 따라가던 독자가 영향을 받았습니다. 이 문제는 고쳐졌습니다. D43은 await를 넘는 mut 규칙이고 never는 D47이므로 목록은 비어서 돌아옵니다. 현재 결정은 D1부터 D49까지 49개입니다.

잘못된 프로그램도 읽을 수 있습니다

컴파일러의 negative 코퍼스는 반드시 실패해야 하는 프로그램과 각각이 일으켜야 하는 코드의 모음입니다. 예전에는 cargo test에만 보였습니다.

규칙이 무엇을 거부하는지 배우는 에이전트가 바로 그 코퍼스가 염두에 둔 독자이므로, 이제 이를 답으로 제공하며, 각 사례는 요청할 때 컴파일되므로 옆의 진단은 이 컴파일러가 낸 것입니다.

자세히 커버리지, 그리고 catches/ 코퍼스

코드를 지정하지 않으면 0.1.149에서 코드 77개 중 53개에 걸친 사례 117개를 나열하고, 돌아온 결과에서 커버리지를 추론하게 두는 대신 사례가 없는 24개를 짚어 줍니다. 두 번째 코퍼스인 catches/는 tsc --strict가 받아들이는 프로그램과 이를 거부하는 Glyph를 짝짓고, 있으면 같은 답에 함께 돌아옵니다. 둘 다 디렉터리 자체에서 포함되므로, 어느 쪽에 사례를 추가하든 따로 기억해서 고칠 것 없이 답에 들어갑니다.

잘못된 예제까지 포함해 모든 예제가 컴파일됩니다

레퍼런스를 생성하는 것은 절반입니다. 나머지 절반은 에이전트가 처음 읽는 설명 글이며, 거기서 에이전트가 복사하는 것은 예제입니다.

그 문서의 모든 Glyph 코드 블록은 컴파일되는 완전한 프로그램이거나, 이름이 붙은 완전한 예제의 단편으로 표시되어 그 줄들이 해당 예제에 실제로 나와야 합니다.

  • 안내 문서예전에는 코드 블록 19개 중 2개가 컴파일되었고, 지금은 24개 중 20개가 컴파일되고 4개가 표시되어 있으며, 건너뛴 것은 없습니다.
  • stdlib 레퍼런스stdlib 레퍼런스는 8개 중 4개에서 8개 중 8개가 되었습니다.
  • 잘못된 형태코드 블록은 일으키는 코드를 명시해서 반드시 실패해야 하는 프로그램으로 표시할 수도 있으며, 문서가 경고하는 잘못된 형태 다섯 개를 이렇게 담고 있습니다. E0228을 일으키는 것, E0008을 일으키는 것, 그리고 세 개 더입니다. 진단과 짝지은 경고는 검사할 수 있습니다. 글로만 쓴 경고는 약속일 뿐입니다.
자세히 문서를 컴파일하면서 찾은 두 가지

문서를 컴파일하면서 읽기만 해서는 결코 찾지 못했을 두 가지를 찾았습니다. 인라인 백틱 세 개가 코드 블록 시작으로 읽혀서 250줄이 코드 조각 하나로 세어졌고 그 안의 어느 것도 검사되지 않았습니다. 그리고 stdlib 레퍼런스의 서버 예제는 std/http가 export하지 않는 http.serve를 호출했습니다. 함수 이름은 listen입니다.

넘겨주는 비용, 그리고 더 이상 들지 않게 된 비용

MCP 도구 열한 개는 예전에 모든 세션이 연결할 때 비용을 치르는 tools/list 응답에 설명서 전체를 담고 있었습니다. 45,509바이트 응답 중 31,446바이트가 설명이었습니다. 같은 도구 열한 개가 지금은 20,386바이트 응답 중 8,627바이트를 담습니다.

삭제한 것은 없습니다. 이전 텍스트는 도구 이름을 키로 그대로 보관되어 glyph llms --json 안에 공개되므로, 호출하는 순간 필요한 계약은 설명에 있고 나머지는 모든 세션의 첫 응답이 아니라 명령 하나 거리에 있습니다.

자세히 개수를 지키는 테스트

테스트가 도구 목록과 문서를 함께 읽으므로, 서버가 제공하지 않는 도구를 언급하거나 목록과 다른 개수를 적은 문서는 빌드를 실패시킵니다. "도구 다섯 개를 제공한다"에 필요했던 검사가 바로 이것입니다.

오프라인, 로컬

이 모두는 오프라인이고 로컬입니다. glyph llms는 설명 글을, glyph llms --json은 데이터를, glyph llms --negative는 잘못된 프로그램을 출력합니다.

네트워크는 있지만 바이너리가 없는 에이전트를 위해 같은 설명 글을 llms.txt로 제공합니다. 에이전트가 언어가 아니라 여러분의 코드에 대해 묻는 것은 쿼리 도구가 답합니다.

현재 상태

지금 제공되는 것

  • glyph llms --json은 컴파일러에서 일곱 개 섹션을 출력합니다
    자세히

    glyph llms --json은 컴파일러에서 일곱 개 섹션을 출력합니다. 진단 코드 77개(그중 51개에 컴파일된 반례 포함), 예약어 32개, prelude 이름 24개, export 340개를 가진 stdlib 모듈 40개, 명세에서 파싱한 언어 결정 49개, 그리고 glyph query 동사와 전체 설명서를 갖춘 도구 열한 개입니다.

  • docs/error-codes.md와 안내 문서의 진단 테이블은 컴파일러 자체 코드 테이블에서 씁니다
    자세히

    docs/error-codes.md와 안내 문서의 진단 테이블은 어긋나면 실패하는 스크립트가 컴파일러 자체 코드 테이블에서 쓰고, 그와 함께 llms.txt도 다시 맞춥니다.

  • 테스트가 도구 목록을 서버가 실제로 제공하는 것에 맞춰 둡니다.
  • 안내 문서와 stdlib 레퍼런스의 모든 Glyph 코드 블록은 컴파일되거나 컴파일되는 예제의 표시된 단편입니다
    자세히

    안내 문서와 stdlib 레퍼런스의 모든 Glyph 코드 블록은 컴파일되거나 컴파일되는 예제의 표시된 단편이며, 잘못된 형태 다섯 개는 각각 일으키는 코드와 짝지은 프로그램입니다.

  • glyph llms --negative는 cargo test가 실행하는 것과 같은 코퍼스에서 답합니다.

한계

  • 이 문서에는 잘못된 프로그램의 개수가 두 가지 나오며, 서로 다른 것을 셉니다
    자세히

    이 문서에는 잘못된 프로그램의 개수가 두 가지 나오며, 서로 다른 것을 셉니다. 코드 77개 중 51개는 tests/negative/에서 온 반례를 가지고, glyph llms --negative는 catches/의 거부 사례도 읽기 때문에 0.1.149에서 코드 53개에 걸친 사례 117개를 나열합니다. 다음 릴리스에는 그 뒤 catches/에 추가된 거부 사례 22개가 더해져 코드 55개에 걸친 사례 139개가 됩니다.

  • 0.1.149에서 코드 24개는 어느 코퍼스에도 잘못된 프로그램이 없으며, 답은 하나를 지어내는 대신 그 코드들을 짚어 줍니다.
  • stdlib export 340개 중 165개는 시그니처 없이 돌아옵니다
    자세히

    stdlib export 340개 중 165개는 시그니처 없이 돌아옵니다. 구현이 tsc가 검사하는 TypeScript이고 컴파일러 자체 테이블은 이에 대해 아무것도 모델링하지 않으므로, std/result::all이나 std/io::println에 대한 glyph_symbol은 그 이유와 함께 kind: null을 보고합니다.

  • 시그니처가 있는 175개 중 46개는 여전히 매개변수 타입 자리에 ?가 있습니다.
  • 그리고 문서는 서비스가 아니라 받아 가는 스냅숏입니다. 검색 계층도, 임베딩도, 그 위의 채팅 인터페이스도 없습니다.
