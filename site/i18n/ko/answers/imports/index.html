기존 TypeScript, JavaScript, npm 라이브러리를 쓸 수 있나요?

네. Glyph는 평범한 TypeScript로 컴파일되고 npm 위에서 동작합니다. .glyph 모듈은 어떤 패키지에서든 import하고, 그 자체도 기존 .ts에서 import할 수 있습니다. 파일 하나씩 도입하면 됩니다.

왜 중요한가

언어를 시험하려고 코드베이스를 다시 쓰는 사람은 없습니다. Glyph의 출력이 곧 TypeScript이므로, .glyph 파일은 기존 TS/React/Node 프로젝트의 한구석에 들어가서 같은 패키지를 import하고, 주변의 .ts로 export합니다. 새 런타임을 만드는 대신 TypeScript를 대상으로 삼은 이유가 바로 이 점진적인 경로입니다.

직접 보기

패키지는 이름으로 import하며(하이픈이 들어간 이름과 npm scope가 있는 이름 포함), Glyph는 예상한 그대로의 import를 생성합니다.

form.glyph 
import react { useState }
import react-hook-form { useForm }
import @hookform/resolvers/zod {
  zodResolver,
}
form.ts: 생성됨 
import { useState } from "react";
import { useForm } from "react-hook-form";
import { zodResolver }
  from "@hookform/resolvers/zod";

패키지가 설치되어 있고 자체 타입을 제공하면(또는 @types/...가 있으면) 할 일은 그것뿐입니다. 스텁도 어댑터 파일도 없습니다. glyph build는 프로젝트의 node_modules를 찾아 타입 검사기가 이를 보게 하므로, 패키지의 실제 타입이 코드를 검사하고 잘못된 호출은 실제 오류가 됩니다. 하위 경로 import(pkg/sub)도 패키지의 exports 맵을 통해 해석되므로 하위 경로 자체의 타입이 검사됩니다. 다음은 직접 작성한 것 없이 zod를 그대로 쓴 예입니다.

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
zod가 정의하지 않은 호출 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

glyph run은 같은 프로그램을 설치된 zod로 실행하므로 타입 검사만 하는 것이 아닙니다. 타입 검사기를 위해 패키지를 해석하는 설정 항목 하나가 런타임을 위해서도 패키지를 해석합니다. 타입을 제공하지 않고 @types/...도 없는 패키지에는 여전히 직접 작성한 선언이 필요하며, 그것이 .types/ 폴더의 용도입니다(TypeScript가 이미 쓰는 것과 같은 .d.ts 방식입니다). 그리고 타입 전용 import가 아니라 라이브러리의 모양을 일급이고 검증되는 Glyph 타입으로 쓰고 싶다면, glyph gen dts가 .d.ts를 디스크립터를 가진 실제 타입으로 실체화합니다. API마다 검증기를 직접 작성해야 하나요?를 보세요.

값 기반 타입은 일급입니다. type User = z.infer<typeof user_schema>가 바로 동작합니다. typeof user_schema는 실제 값 참조에 대한 타입 쿼리이고(오타는 해석되지 않는 이름 오류입니다), z.infer<...>는 평범한 멤버 제네릭 타입입니다. 그대로 생성되고 tsc가 이를 풀어내므로 u.name은 string이며, 검증은 zod가 원래 동작하는 방식대로 스키마 자체의 parse가 합니다. JSX prop spread(<input {...register()} />)도 일급입니다. Glyph로 아직 표현할 수 없는 드문 TypeScript 관용구에는 범위가 한정되고 grep할 수 있는 탈출구 extern_ts("...")가 있습니다. tsc가 이를 검사하지만, 정확히 말하면 런타임에 검증되는 경계가 아니라 신뢰 경계입니다(Glyph에게는 불투명하며, 값은 좁혀서 써야 하는 unknown으로 돌아옵니다). 따라서 어떤 라이브러리도 직접 작성한 어댑터 파일을 강요하지 않습니다.

TypeScript를 통째로 직접 작성해야 할 때

탈출구가 타입이나 표현식이 아니라 실제 런타임 코드여야 할 때도 있습니다. node 스트림 루프, new Promise, 워커 스레드 같은 것입니다. .ts를 <src>/extern/ 아래에 두고 import extern/<name>으로 가져오세요. 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

빌드는 <src>/extern/**를 출력에 배치하고 상대 경로 지정자를 생성하므로, tsc가 extern을 Glyph 코드와 함께 타입 검사하고 다시 빌드해도 지워지지 않습니다. Glyph 소스에서 상대 경로 import는 여전히 허용되지 않으므로(검색 용이성 규칙), extern/*가 유일하게 예약된 경로이며, grep -rn 'import extern/'로 언어를 벗어난 모든 곳을 찾을 수 있습니다. 쉬운 방향, 즉 .ts 파일이 컴파일된 Glyph를 import하는 것의 반대이며, 그쪽은 아무것도 필요 없습니다. 흔한 extern(http 서버, fs)은 아무것도 설치하지 않아도 함께 제공되는 node shim으로 타입 검사됩니다.

아무것도 설치하지 않고 하위 프로세스 지켜보기

함께 제공되는 node 선언에는 블로킹 쪽만이 아니라 child_process의 비동기 쪽도 있으므로, 오래 걸리는 명령의 출력을 실행 중에 보고하는 도구는 extern이 아니라 Glyph로 작성됩니다. 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

io.println이 아니라 io.print입니다. 청크는 줄이 아니라 스트림의 조각이고, 한 줄이 두 청크에 걸쳐 도착할 수 있습니다. 오버로드는 @types/node를 따르므로, 평범한 spawn(command, args)에서는 파이프가 null이 아닌 값으로 돌아오고 stdio를 넘기면 null일 수 있게 됩니다. stdio: "inherit" 뒤에 child.stdout을 읽으면 여기서도 TS18047이고 실제 타입 정의에서도 TS18047이므로, 같은 값에 대해 두 가지 다른 이야기가 나오지 않습니다. 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

shim을 편집하면 다음 실행은 편집한 shim으로

shim은 반복해서 고치는 파일이므로 소스로 쳐야 합니다. glyph run은 소스의 지문을 기준으로 빌드를 캐시하는데, 그 지문은 extern/ 아래의 모든 .ts와 .tsx를 내용뿐 아니라 경로로도 포함합니다. 하나를 편집하거나, 이름을 바꾸거나, 추가하거나, 지우면 다음 실행은 다시 빌드하고 tsc를 다시 실행합니다. 심볼릭 링크로 연결된 shim도 따라가므로, 소스 트리 밖에 둔 .ts는 실제 내용으로 해시됩니다.

덕분에 두 파일이 각자 사본을 선언하는 대신 shim이 타입을 소유할 수 있습니다. shim에서 모양을 export하고 Glyph 모듈에서 import하면, 컴파일러가 실행할 때마다 둘을 맞춰 둡니다.

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
shim이 필드 이름을 바꾸면 빌드가 알려 줌 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3

0.1.44까지 지문은 extern/을 통째로 건너뛰었으므로, 그런 이름 바꾸기는 이전 shim 사본으로 실행되는, 깔끔하게 타입 검사된 빌드를 만들었습니다. extern/ 아래의 .ts나 .tsx가 아닌 파일은 여전히 캐시에 영향을 주지 않으며, 이는 의도한 것입니다. shim 옆의 README.md는 함께 출력으로 복사되지만 아무것도 이를 타입 검사하거나 실행하지 않으므로 다시 빌드할 것이 없습니다.

클래스 기반 클라이언트: 데이터베이스와 메시징

대부분의 데이터베이스와 메시징 클라이언트는 클래스 기반입니다. new Kafka(...), new MongoClient(url), new Redis(), new Pool(cfg)처럼 씁니다. Glyph에는 정확히 이를 위한 new가 있습니다. TypeScript new를 그대로 생성하고 tsc가 패키지의 실제 생성자에 대해 검사하므로, 잘못된 인자는 실제 오류이고 정의되지 않은 대상은 이름으로 잡힙니다. 상호 운용 전용입니다. Glyph에는 자체 class가 없고, new는 패키지, .types 선언, extern_ts에서 온 타입만 생성합니다.

클래스 기반 클라이언트 (kafkajs) 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
팩토리 클라이언트에는 new가 필요 없음 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

지금 제공되는 것

어떤 npm 패키지든 import합니다(하이픈이 들어간 이름과 scope가 있는 이름 포함). 자체 타입을 제공하는(또는 @types/...가 있는) 설치된 패키지는 스텁 없이 타입 검사되고 실행됩니다. 클래스 기반 클라이언트는 new로 생성하며 tsc가 실제 생성자에 대해 검사하고, 팩토리 클라이언트는 import해서 바로 호출합니다. Node 내장 모듈(fs, path, http, 스트리밍 spawn을 포함한 child_process 등)은 별도 설정 없이 타입 검사되고, @types/node를 설치하면 자동으로 로드되며, CI가 컴파일러 자체 런타임을 그 패키지의 latest에 대해 빌드하므로 stdlib가 의존하는 선언이 node의 실제 선언과 어긋날 수 없습니다. 여러분의 코드만 닿는 선언은 아직 이 검사에 포함되지 않으며, 몇 개는 여전히 node보다 넓습니다. 그 밖의 것에는 .types/ 앰비언트 선언, .d.ts를 검증되는 Glyph 타입으로 실체화하는 glyph gen dts, 그리고 기존 TypeScript가 다시 import하는 깔끔한 .ts 출력이 있습니다. TypeScript를 통째로 직접 작성해야 할 때는 import extern/<name>이 <src>/extern/ 아래의 .ts에 닿으며, 이는 코드와 함께 배치되고 타입 검사되며 glyph run 캐시가 추적하므로 편집하면 다시 빌드됩니다.

앞으로 할 것

실체화는 이제 실제 SDK가 제공하는 모양(네임스페이스, 파일 간 및 별칭/네임스페이스 재export, 하위 경로 exports, 일급 제네릭)을 처리하고, 값 기반 타입(z.infer<typeof s>)은 일급입니다. 남은 주요 빈틈은 실체화하지 않은 패키지의 출력이 .d.ts에 대해 타입 검사는 되지만 실체화하지 않으면 런타임에 검증되지 않는다는 점입니다. extern/ 쪽에서는 두 명령의 소스 루트가 다릅니다. glyph run app.glyph는 파일 자체의 디렉터리를 루트로 삼고, glyph build src/는 지정한 디렉터리를 루트로 삼습니다. 그래서 하위 디렉터리의 프로그램은 shim을 서로 다른 두 곳에서 찾으며, 루트를 하나로 정하기 전까지 그런 구조의 프로젝트는 양쪽 모두에서 shim에 닿을 수 있어야 합니다. 닿지 않으면 요란하게 실패합니다.
