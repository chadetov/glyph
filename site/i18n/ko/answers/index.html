답변

엔지니어들이 Glyph에 대해 묻는 것.

각 답변은 예제를 보여 주고, 아직 동작하지 않는 것으로 끝납니다. 의문이 드는 곳에서 시작하세요. Glyph가 처음이라면 10분 만에 시작하기가 가장 빠른 첫걸음입니다.

해결하는 문제

에이전트의 편집이 아무도 모르게 깨뜨릴 수 있는 것과, 각각에 대해 Glyph가 하는 일.

01에이전트가 내 코드를 조용히 깨뜨리는 것을 무엇이 막아 주나요?

any도 캐스트도 없고, 망라적인 match, 런타임에 검사되는 타입, 빌드할 때마다 실행되는 코드 옆의 테스트가 있습니다.

 02에이전트의 편집이 깔끔하게 유지되나요, 아니면 파일 전체를 다시 포맷하나요?

한 줄을 바꾸면 diff도 한 줄입니다. 정해진 레이아웃은 하나이고, 다시 묶이는 것은 없습니다.

 03에이전트가(또는 내가) 무엇이 어디에 정의되어 있는지 찾을 수 있나요?

이름 하나에 선언 형태 하나. grep은 언제나 정의에 닿습니다.

도입할지 결정하기

도구를 더하는 대신 언어를 택한 이유와, 도입하는 데 드는 비용.

04왜 Go나 새 언어가 아니라 TypeScript인가요?

여러분의 생태계가 거기 있기 때문이고, 그래서 파일 단위로 도입할 수 있습니다.

 05그냥 strict TypeScript + zod + eslint + ts-pattern을 쓰면 안 되나요?

선택 사항이 아니라는 점: 에이전트가 설정으로 끌 수 없는 언어입니다.

 06AI를 쓰지 않아도 Glyph가 쓸 만한가요?

네. 보장은 사람이 직접 누리는 평범한 엔지니어링상의 이점입니다.

 07AI가 거의 본 적 없는 언어를 안정적으로 쓸 수 있나요?

모델이 TypeScript에 대해 아는 것은 대부분 그대로 통하고, 통하지 않는 곳은 컴파일러가 알려 줍니다.

 08새 Glyph 릴리스가 내 빌드를 깨뜨리나요?

프로젝트는 컴파일러 버전을 정확히 고정하므로 어떤 릴리스도 실수로 들어오지 않습니다. 새 릴리스가 있으면 glyph doctor가 알려 주고, glyph upgrade로 받습니다.

기존 스택과 함께 쓰기

npm 패키지, 기존 앱, API 경계, React.

09기존 TypeScript, JavaScript, npm 라이브러리를 쓸 수 있나요?

네. 어떤 npm 패키지든 import하고, 필요한 곳에는 직접 작성한 .ts shim을 두고, Glyph를 다시 .ts로 import할 수 있습니다.

 10기존 앱 안에서 Glyph를 도입할 수 있나요, 아니면 전부 아니면 전무인가요?

다시 작성할 필요가 없습니다. 도메인 핵심은 Glyph로, 나머지는 TypeScript로 둡니다. 생성된 TypeScript는 기본 Vite 앱이 여느 모듈처럼 import합니다.

 11API마다 검증기를 직접 작성해야 하나요?

아니요. 타입을 선언하면 검증기가 생성됩니다.

 12API 명세에서 타입이 있는 클라이언트와 서버를 생성할 수 있나요?

glyph gen openapi/zod/dts: 커밋하고 grep할 수 있는 코드.

 13React의 컴포넌트, hook, Context와 함께 쓸 수 있나요?

일급 JSX, hook, 망라적인 reducer 액션.

 14Glyph가 React에서 아직 못 하는 것은?

gap 번호마다 한 항목, 그동안 쓸 수 있는 방법과 함께.

 15함수 사이에서 변경 가능한 상태를 어떻게 공유하나요?

store입니다. .set/.update가 쓰기 창구인 const입니다.

만들 수 있는 것

프로그램 종류별로 본 언어와 표준 라이브러리.

16이것은 진짜 언어인가요, 구멍 많은 장난감인가요?

모듈 가시성, 인터페이스 제약, defer, 어떤 값으로든 쓸 수 있고 타입을 유지하는 match, 그리고 slice, pad_start, fold를 갖춘 표준 라이브러리.

 17돈을 다루거나, 내가 통제하지 못하는 입력을 맡겨도 되나요?

정확한 십진수와 id, 타입으로 표현한 불변식, 컴파일 오류가 되는 인젝션.

 18웹 페이지를 서빙할 수 있나요, 아니면 JSON API만 되나요?

직접 작성한 서버 없이 HTML, 리다이렉트, 응답 헤더, 폼 전송.

 19사용자가 입력하는 프로그램을 작성할 수 있나요?

io.read_line은 stdin이 닫힐 때까지 기다리지 않고 줄이 도착하는 대로 응답하므로, REPL이나 게임 루프가 동작합니다.

 20서버를 작성할 수 있나요, 아니면 프로세스가 그냥 종료되나요?

main은 준비를 마치고 반환하며, 소켓과 타이머가 대기 중인 동안 프로세스는 살아 있습니다. Node와 같은 규칙입니다.

 21바이너리 데이터를 다룰 수 있나요, 아니면 모든 것이 문자열인가요?

std/bytes는 옥텟의 나열이며, 잘못된 입력을 건너뛰지 않고 거부하는 코덱과 실제 키를 받는 HMAC이 있습니다.

에이전트와 함께 작업하기

편집 전후에 에이전트가 컴파일러에게 묻는 질문.

22변경하기 전에 그 변경이 무엇을 깨뜨릴지 컴파일러가 알려 줄 수 있나요?

glyph_impact: 파일을 건드리기 전에, 정해진 목록에서 고른 판정을 위치마다 이유와 함께 하나씩.

 23에이전트가 코드를 쓰기 전에 컴파일러에게 심볼이 무엇인지 물어볼 수 있나요?

glyph_symbol: 유니언의 variant와 각각을 생성하는 문법을 한 번의 호출로. 도구 열한 개, 각각 glyph query 동사가 있습니다.

 24빌드가 실패하면 컴파일러가 에이전트에게 고치는 방법을 알려 주나요?

진단에는 문제가 된 심볼, 가능한 대안, 수정하는 편집이 깨뜨리면 안 되는 것이 담깁니다. 컴파일러가 스스로 결정할 수 있는 수정은 glyph fix가 직접 씁니다.

 25에이전트가 읽는 문서는 생성된 것인가요, 사람이 써서 낡은 것인가요?

glyph llms --json은 진단, prelude, stdlib 시그니처, 도구 설명서를 컴파일러 자체 테이블에서 출력하고, 사람이 쓴 사본이 이와 다르면 게이트가 실패합니다.

 26래퍼가 있는데도 에이전트가 원래 라이브러리를 직접 가져오지 못하게 막을 수 있나요?

package.json에서 import 경로를 금지하고 대체할 모듈을 지정합니다. 그 경로를 가져오면 E0115이고, 도움말이 래퍼를 가리킵니다.

오류, 에디터, 프로덕션

무언가 잘못되었을 때 에디터에서 온콜까지 보게 되는 것.

27에디터, 디버깅, 오류 경험은 어떤가요?

모든 LSP 에디터를 위한 언어 서버와, 수정 방법을 알려 주는 고정된 코드를 가진 오류.

 28Glyph는 왜 tsc가 잡는 것을 더 일찍 잡나요?

await 문맥, 값이 없는 match arm, 빠진 mut을 생성된 TypeScript가 아니라 여러분의 소스 기준으로 보고합니다.

 29파싱이 실패하면 이유를 알 수 있나요?

어떤 필드인지, 어떤 규칙을 어겼는지, 위반한 where 조건, 그리고 분기에 쓸 code.

 30새벽 3시에 프로덕션에서 장애가 나면 온콜 담당자는 무엇을 보나요?

직접 소유한 읽을 수 있는 TS, .glyph로 연결되는 소스 맵, 그리고 build가 보고하는 것을 똑같이 보고하는 run.
