이것은 진짜 언어인가요, 구멍 많은 장난감인가요?

왜 중요한가

파일 하나는 쓸 수 있지만 프로젝트를 구조화할 수 없는 언어에 코드베이스를 걸 사람은 없습니다. 중요한 빈틈은 특이한 것이 아닙니다.

  • 가시성헬퍼를 숨길 수 있는가?
  • 제네릭 제약제네릭이 어떤 능력을 요구할 수 있는가?
  • 정리모든 종료 경로에서 파일 핸들을 해제할 수 있는가?
  • 동시성두 가지를 동시에 실행하고 둘 다 기다릴 수 있는가?

Glyph는 이 네 가지에 답하며, 의도적으로 버린 표기가 많은 방향을 다시 열지 않고 그렇게 합니다.

인터페이스로 제네릭 제약하기

interface는 TypeScript처럼 구조적입니다. 제네릭이 요구할 수 있는 멤버 시그니처의 집합입니다. implements도, 명목적 형식도 없습니다. 그 멤버를 가진 값이면 무엇이든 해당되며, tsc가 이를 강제합니다.

인터페이스로 제네릭 제약하기 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer와 구조적 동시성

defer는 블록이 끝날 때 조기 반환이나 던진 오류를 포함한 모든 경로에서 정리 코드를 실행합니다. 그리고 std/task는 떨어져 나간 promise를 남기는 대신 하나의 수명으로 동시 작업을 합칩니다.

defer + 구조적 동시성 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])
자세히 실행 순서, 그리고 owned 핸들

여러 defer는 나중에 등록한 것부터 실행되고, owned 핸들과 함께 쓸 수 있습니다.

JavaScript에서 물려받은 것

Glyph는 TypeScript로 컴파일되어 JavaScript 엔진에서 실행되므로, 평가 순서, 변경에 대한 참조 의미론, 가비지 컬렉션이 있는 단일 스레드 모델을 그대로 물려받습니다. 사양은 이것들을 나중에 알아내도록 두지 않고 보장으로 명시합니다.

다른 점은 동등성입니다. ==는 값을 비교하며 레코드는 필드 단위로 비교하지만, JavaScript의 ===는 참조를 비교합니다.

수동 메모리 관리와 GC가 없는 모델은 로드맵에 없습니다. TypeScript로 트랜스파일하는 언어의 범위를 벗어나기 때문입니다.

if가 없으므로 match가 모든 것을 감당해야 합니다

망라성 이야기를 들은 TypeScript 개발자가 가장 먼저 묻는 것은 match가 정말 범용 조건문인지, 아니면 유니언을 구조 분해하는 멋진 방법일 뿐인지입니다. 전자이며, 이를 증명하는 곳은 대입입니다.

let이나 mut의 값 전체인 match는 문장이 받는 것은 무엇이든 받습니다. arm은 블록일 수 있고, await할 수 있고, 둘러싼 반복문을 break로 빠져나갈 수 있으며, 대입 중인 바인딩을 읽을 수도 있습니다. if 없이 반복문에서 상태를 누적하는 방법이 바로 이것입니다.

링크 검사기에서: 코드 블록 추적, 그리고 await하는 arm 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}
자세히 무엇으로 컴파일되는가, 그리고 코드 조각의 출처

둘 다 arm마다 바인딩에 대입하는 평범한 switch로 컴파일되므로, await는 둘러싼 async 함수 안에 있고 누적 변수는 TypeScript가 추론할 수 있는 일반 변수입니다. 두 코드 조각 모두 바로 이런 것을 찾으려고 만든 Markdown 링크 검사기 examples/apps/linkcheck/main.glyph에서 가져왔습니다.

더 큰 표현식 안에서 인자나 피연산자로 쓴 match는 여전히 클로저가 되므로, arm은 단일 표현식이어야 합니다. 별도의 let으로 끌어올리면 이 제약이 사라집니다.

패턴은 한 단계 이상 아래의 모양을 지정할 수 있습니다

필드가 여러 개인 variant는 레코드를 담으므로, 모양을 알아보려는 arm은 레코드의 필드 속으로 들어가야 합니다. 이제 필드에는 어떤 패턴이든 올 수 있습니다. variant 태그, 중첩된 생성자, 중첩된 구조 분해, 리터럴, 배열 패턴입니다.

레드-블랙 재균형의 회전 case 하나를 arm 하나로 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}
이력 0.1.90 이전의 우회 방법

0.1.90까지 필드 위치에는 이름만 올 수 있었습니다. 이름을 바꿀 수는 있었지만 그게 전부였습니다. 거기서 태그를 매칭하면 컴파일 오류였고, 중첩된 생성자는 파서가 처리하지 못했습니다. 우회 방법은 모든 필드를 바인딩하고 단계마다 중첩된 match를 쓰는 것이었는데, 레드-블랙 트리 재균형 같은 것에서는 아예 다른 프로그램이 됩니다. arm이 case와 나란히 맞지 않게 되고, 각 단계가 위의 바인딩을 다시 이어 받아야 합니다.

작성하기 전에 알아 둘 결과가 하나 있습니다. 값을 검사하는 필드는 실패할 수 있으므로 그 arm은 더 이상 variant를 다룬 것으로 치지 않으며, Node arm이 Node({ color: Red, ... }) 하나뿐인 match는 형제 arm이나 else가 나머지를 받을 때까지 비망라적이라고 보고됩니다.

자세히 catch-all을 요구하는 이유, 그리고 배열 위치

검사기는 필드의 곱이 아니라 태그 집합에 대해 커버리지를 증명하므로, Red arm과 Black arm이 함께 Node를 다 다룬다는 것을 알아내지 못합니다. catch-all을 요구하는 것이 match가 런타임에 끝까지 빠져나가는 일을 막을 수 있는 해석입니다. 셀 variant가 아예 없는 곳에서도 마찬가지입니다. 모든 arm이 필드를 검사하는 평범한 레코드에 대한 match에는 뒤에 else가 필요합니다.

예상하지 못했을 수도 있는 곳이 배열 위치입니다. arm 전체로 쓴 [Black]은 예전에 요소 하나짜리 배열이면 무엇이든 매칭하는 것으로 쳤으므로, 그에 기댄 match는 망라적이라고 인정받은 뒤 [Red]에도 그 arm을 택했습니다. 여기서도 PascalCase 요소는 variant 참조이므로, 그런 match는 이제 길이 1인 배열에 대해 E0208입니다. 요소를 바인딩하고 따로 match하세요. 그 아래의 변환은 여전히 예전 것이며, 그래서 검사가 먼저 배포된 절반입니다.

E0208

그리고 컴파일러는 match가 무엇을 만들었는지 압니다

이 모든 것이 실제로 쓸모 있는지를 가르는 다음 질문은 이것입니다. 분기에서 값을 바인딩하면 Glyph가 그 타입을 아는가, 아니면 어깨를 으쓱하고 나중에 tsc가 정리하게 두는가? 이제 match는 arm들이 일치하면 그 타입을 가지고, T.parse는 실제 코드 대부분이 분기하는 모양인 Result<T, Array<Issue>>를 반환한다고 알려져 있습니다.

비용 정산 앱에서: 타입 표기 없이도 i는 숫자 
let wire = match WireLedger.parse(decoded) {
  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },
}

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...
}
이력 0.1.45 이전

0.1.45까지는 후자였습니다. 모든 match 표현식의 타입이 unknown이었으므로, 언어의 유일한 분기 구문에서 나온 값은 그때부터 타입이 없었습니다.

자세히 조용히 잘못되던 것, 그리고 합치는 방식

두 쪽 모두 예전에는 조용히 잘못되던 것입니다. 반복문은 wire.expenses.entries()를 생성합니다. 반복 대상의 타입이 unknown이면 대신 Object.entries(...)를 생성하고 i는 문자열 "0"이 되는데, 이는 올바른 TypeScript이므로 빌드는 깔끔했고 프로그램은 1:a를 의도한 곳에서 01:a를 출력했습니다. 그리고 wire.expensez는 이제 생성된 TypeScript의 TS2339가 아니라 .glyph 줄에서 Glyph가 내는 [E0210] type WireLedger has no field expensez입니다.

합치는 규칙은 머리에서의 동등성입니다. return으로 끝나는 arm은 투표하지 않고, 타입이 다른 arm들은 결과를 예전처럼 unknown으로 둡니다. 한 단계 더 깊이 보는 곳은 타입 인자뿐이므로, None => []는 match 전체를 망치지 않고 Array<string> arm과 일치하며, 그 뒤의 반복문도 여전히 숫자를 바인딩합니다. record.get에 대한 같은 연쇄도 같은 이유로 동작합니다. std/record 함수 여섯 개 모두 넘긴 레코드에서 값 타입을 가져옵니다. 코드 조각은 이 변경으로 지워진 타입 표기를 갖고 있던 examples/apps/settle/main.glyph에서 가져왔습니다.

빈 기본값을 둔 조회

가장 비용이 컸던 모양이 이것입니다. Record<string, Array<string>>에 대한 record.get은 Option<Array<string>>이고, []는 특정한 무엇도 아닌 것의 배열이므로, 두 arm은 Array에서 일치하고 요소 타입은 그것을 가진 arm에서 옵니다.

의존성 해석기에서: 조회, 빈 기본값, 인덱스를 쓰는 순회 
let path = match record.get(res.reached, name) {
  Some(p) => p,
  None => [],
}

for i, hop in path {               # i is a number, so the indent nests
  let indent = string.repeat(STEP, i + 1)
  mut out = array.push(out, "${indent}${hop}")
}
이력 0.1.55 이전

0.1.55까지는 동등성으로 비교했으므로 []는 불일치로 쳤고, 아래 반복문은 진단도 없고 tsc --strict도 통과한 빌드에서 01:x를 출력했습니다. 코드는 examples/apps/depsolve/main.glyph이며, 예전에는 이 타입 표기가 꼭 필요하다는 세 줄짜리 주석 아래에 let path: Array<string>으로 시작했습니다.

pad_start를 직접 작성해야 하나요?

실제 프로그램에서 처음 부딪히는 빈틈은 타입 시스템 기능이 아닙니다. string.slice를 찾았는데 아무것도 없는 것입니다.

추가된 것

연속된 도그푸딩 다섯 번이 같은 목록을 제출했고, 0.1.47까지 이 저장소의 앱 여섯 개가 자체 repeat를, 다섯 개가 자체 pad_start를 갖고 있었으며, 모두 fold가 있어야 할 곳에 반복문이 있었습니다.

TypeScript와 다른 점

그중 세 개는 의도적으로 TypeScript의 같은 이름 함수와 다르게 동작합니다.

  • repeatrepeat는 TS가 예외를 던지는 음수 횟수에서 ""를 반환하며, 덕분에 이미 너무 긴 문자열에 대해서도 repeat(pad, width - len(s))가 안전합니다.
  • index_of두 index_of 함수는 -1 대신 Option<number>를 반환합니다. -1은 실제 인덱스가 쓰이는 모든 곳에서 타입 검사를 통과하고, 호출 지점에서 한참 떨어진 곳에서 실패하는 숫자이기 때문입니다.
  • replace_all치환은 replace_all로만 제공되므로, 조용히 한 번만 바꾸는 String.prototype.replace와 헷갈릴 첫 번째만 바꾸는 형태가 없습니다.

fold가 중요한 이유

fold는 타이핑을 줄이는 것이 아니라 기둥 하나를 지켜 주는 함수입니다. mut는 상태가 바뀌는 모든 곳의 grep할 수 있는 기록인데, fold가 없으면 grep mut 결과가 리뷰어가 신경 쓸 것은 아무것도 바꾸지 않는 카운팅 반복문으로 가득 찹니다.

직접 만든 버전을 지우자 examples/apps/의 변경 위치가 192곳에서 161곳으로 줄었습니다.

자세히 다시 쓴 코드를 확인한 방법

다시 쓴 코드는 리뷰가 아니라 출력으로 확인했습니다. 앱 일곱 개를 모두 고정된 입력으로 전후에 실행했고, stdout, 종료 코드, HTTP 응답 파일 26개가 바이트 단위로 같았습니다.

디렉터리를 순회하고 무엇이 잘못됐는지 알 수 있나요?

std/fs에는 함수 여섯 개가 있었는데 어느 것도 디렉터리를 나열하지 않았습니다.

  • fs.read_dirfs.read_dir는 한 단계 아래의 항목 이름을 반환합니다.
  • fs.is_dirfs.is_dir는 fs.exists처럼 bool로 답합니다.
  • fs.statfs.stat은 is_dir, is_file, 바이트 단위의 size, epoch 밀리초 단위의 modified로 된 FileInfo를 반환하고, time.format_iso로 바로 출력할 수 있습니다.

재귀적인 walk와 glob은 없습니다. 순회는 이 세 가지와 path.join으로 열 줄 정도면 됩니다.

이력 이것들이 대신한 우회 방법

이 저장소의 링크 검사기는 stdlib를 넘어 node의 readdirSync에 손을 뻗었고, 어떤 경로가 디렉터리인지는 읽어 보고 돌아온 errno를 살펴서 알아냈습니다. 두 쪽 모두 고쳐졌습니다.

실패에는 이름이 있습니다

실패 쪽은 더 많이 바뀌었습니다. 이제 프로그램이 실제로 복구하는 다섯 가지 종류에는 이름이 있고, 이름이 없는 errno는 Other 꼬리에 그대로 담겨 도착합니다.

돈은 float로 계산하지 않습니다

핀테크 평가를 그 자리에서 끝낼 빈틈은 0.1 + 0.2가 0.3이 아니고 253을 넘는 값이 조용히 정밀도를 잃는 IEEE-754 number로 돈을 계산하는 것입니다.

std/decimal은 BigInt 위의 정확한 10진 고정소수점입니다. 소수 자릿수가 고정된 임의 정밀도 정수이므로 덧셈, 뺄셈, 곱셈은 정확하고, 나눗셈은 명시적인 자릿수와 반올림 방식을 받습니다. 형식이 잘못된 금액은 조용한 NaN이 아니라 Err로 파싱됩니다.

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

큰 정수

계정 id나 카운터처럼 정확해야 하는 큰 정수에는 bigint 타입이 있습니다. 리터럴은 123n이고, 실제 TypeScript bigint로 생성되며, bigint 타입의 레코드 필드는 경계에서 typeof === "bigint"를 검증하므로, JSON number로 보낸 id는 253을 넘어 조용히 반올림되지 않고 거부됩니다.

비동기 콜백에 드디어 타입이 생겼습니다

함수 타입은 fn(A) -> T뿐이었고, 이는 (a: A) => T로 생성됩니다. 비동기 본문은 여기에 맞지 않으므로, 지연된 작업을 반환하는 함수나 비동기 핸들러를 담은 레코드는 타입 표기 없이 둬야 했고 검사기는 더 이상 보지 않았습니다.

async fn(A) -> T가 그 빠진 타입입니다. (a0: A) => Promise<T>로 생성되고, 반환이 없는 async fn()은 () => Promise<void>로 생성됩니다.

끝까지 매칭되는 재귀 타입

유니언은 자신의 payload 안에서 타입 매개변수와 함께 자기 자신을 가리킬 수 있고, match arm은 생성자 패턴의 필드 안에 다른 생성자 패턴을 중첩할 수 있습니다. 둘을 합치면 레드-블랙 트리의 균형 규칙이 arm 네 개가 됩니다. 각각은 다시 쓰는 정확한 모양을 지정하고, 그 모양을 위의 주석이 주장하는 것이 아니라 컴파일러가 검사합니다.

  • 타입의 머리가 다른 arm들은 결과를 Glyph에게 unknown으로 둡니다
    자세히

    arm 합치기는 여전히 arm들이 타입의 머리에서 일치해야 합니다. 서로 다른 타입을 만들면 결과는 Glyph에게 unknown이고, 그것으로 무엇을 하든 tsc만 검사합니다.

  • stdlib 함수 아홉 개도 같은 처지입니다
    자세히

    stdlib 함수 아홉 개도 같은 처지입니다. 여섯 개는 선택적인 마지막 인자를 받는데(array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify), 인자 개수 검사는 숫자 하나와 숫자 하나를 비교하므로 이를 모델링하면 마지막 인자를 생략하는 모든 호출에서 거짓 오류를 보고하게 됩니다. array.map, flat_map, zip은 검사기가 들어가지 않는 콜백에서 요소 타입을 가져옵니다.

    이 아홉 개에서 바로 나온 값을 인덱스와 함께 반복하려면 먼저 타입 표기가 필요하고, None arm이 없는 string.index_of에 대한 match는 여전히 깔끔하게 빌드되고 런타임에 예외를 던집니다. array.index_of는 모델링되어 있어 E0200을 보고합니다.

  • 검사기가 타입을 매길 수 없었던 값에 대한 멤버와 호출 인자 개수는 검사되지 않습니다
    자세히

    자세히

    자세히

    다른 한계는 사라졌습니다. 자신의 매개변수에 대해 제네릭인 유니언(type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> }))은 매개변수가 없는 같은 유니언이 받아들이는 중첩 arm을 예전에는 거부했는데, 이제는 열린 타입 매개변수에서든 구체적인 인스턴스화에서든 받아들입니다. 같은 조회가 match에서 빠진 variant를 검사할지 자체를 결정하고 있었으므로, 이 릴리스 전까지는 Tree<K>에 대한 match가 Leaf를 빠뜨려도 깔끔하게 빌드되고 tsc --strict를 통과한 뒤 런타임에 예외를 던질 수 있었고, 제네릭이 아닌 표기는 E0200이었습니다.

    이제 두 표기 모두 보고하며, 유니언을 import 한 단계 떨어진 곳으로 옮겨도 답이 바뀌지 않습니다. Leaf를 빠뜨린 import한 Tree<string>에 대한 match는 import한 제네릭이 아닌 Tree와 똑같이 Leaf를 짚는 E0200입니다. 이는 별도로 검사되는 다른 코드 경로였고, 이 릴리스 전까지는 반대로 깔끔하게 빌드되고 런타임에 예외를 던졌습니다.

  • import한 유니언의 커버리지는 variant payload를 검사하지 않습니다
    자세히

    import한 유니언의 커버리지에 기대기 전에 알아 둘 것이 하나 더 있습니다. variant payload도 검사되지 않으므로, X가 payload 자신의 유니언의 variant인 B(X)는 빠진 Y를 보고하지 않고 모든 B에 매칭되며, 이는 제네릭과 아무 관계가 없습니다.

    필드를 바인딩하거나, payload가 없는 태그를 필드에서 매칭하는 것은 모든 경우에 동작합니다.
