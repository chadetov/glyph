27 · 파싱 실패

파싱이 실패하면 이유를 알 수 있나요?

네. 모든 문제는 필드를 짚고, 값이 어떤 규칙을 어겼는지 말하며, 분기에 쓸 수 있는 code를 담고 있습니다. where 조건식으로 제약된 필드는 조건식 자체를 보고하므로, 거부 메시지를 grep하면 그 제약을 건 줄로 돌아갈 수 있습니다.

이 페이지의 내용

  1. 왜 중요한가
  2. 중첩된 타입
  3. 문자열이 아니라 코드
  4. 현재 상태

왜 중요한가

"이 페이로드는 잘못되었다"고만 말하는 검증기는 일을 절반만 한 것입니다.

핸들러는 여전히 판단해야 합니다. 필드를 빠뜨린 클라이언트인가, 네 글자짜리 비밀번호를 보낸 클라이언트인가? 하나는 400이고 다른 하나는 422인데, 검증기가 말해 주지 않으면 검증기가 이미 갖고 있던 정보 한 조각을 되찾으려고 같은 본문을 서로 다른 타입으로 두 번 파싱하게 됩니다.

이력 이 문제가 나온 곳

Glyph로 인증 API를 만들 때 정확히 그런 일이 있었습니다. password 키가 아예 없는 가입 요청이 weak_password로 돌아왔습니다. 없는 경우와 너무 짧은 경우가 같은 문자열을 냈기 때문입니다.

중첩된 타입은 스스로 답합니다

자체 디스크립터가 있는 타입의 필드는 그 타입의 parse로 검증되고, 그 문제는 경로 앞에 필드 이름을 붙여 돌아옵니다. 그래서 두 단계 아래 중첩된 Password는 ["body", "password"]를 보고하면서도 자신의 메시지를 그대로 담고 있습니다.

문자열이 아니라 코드로

Issue에는 선택적인 code가 있습니다: "missing", "type", "refinement", "unexpected", "depth". 이것으로 분기하세요. 메시지 텍스트로 매칭하는 것은 Glyph가 없애려는 취약함이며, 메시지는 응답 본문을 읽는 사람을 위한 것입니다.

메시지를 읽지 않고 400/422 나누기 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code는 선택 필드이므로, 직접 만든 Issue와 이 필드가 생기기 전에 작성된 모든 사용 코드가 바뀌지 않고 그대로 컴파일됩니다.

자세히 "depth" 코드

"depth"는 객체와 배열이 1000단계보다 깊게 중첩된 본문에 대한 답입니다(std/schema의 MAX_DEPTH). 그런 일이 일어난 필드에서 문제 하나를 보고합니다. 0.1.150 이전에는 검사가 RangeError: Maximum call stack size exceeded를 던지며 핸들러까지 함께 쓰러뜨렸습니다.

현재 상태

지금 제공되는 것

  • 레코드와 where 타입은 실패한 필드뿐 아니라 실패한 규칙을 보고합니다missingtyperefinementunexpecteddepth
    자세히

    레코드와 where 타입은 실패한 필드뿐 아니라 실패한 규칙을 보고합니다. 필수 필드가 없으면 "missing", 모양이 틀리면(객체가 아니거나 배열인 경우 포함) "type", 기본 타입은 통과했지만 조건식에서 실패하면 "refinement", 타입이 선언하지 않은 키가 있으면 "unexpected", 값이 1000단계보다 깊게 중첩되어 있으면 "depth"입니다.

  • 정제 타입은 조건식을 인용합니다.
  • 디스크립터가 있는 타입의 필드는 검증을 그 디스크립터에 맡기므로, 중첩된 문제는 전체 경로와 함께 도착합니다.
  • 선택 필드(f?: T)는 없다고 보고되지 않습니다.

개선 중 2

  • 자체 디스크립터가 없는 것으로 타입이 지정된 필드는 여전히 단순한 검사와 "type" 문제를 받습니다
    자세히

    한계가 두 가지 있습니다. 자체 디스크립터가 없는 것, 즉 제약 없는 타입 매개변수나 직접 작성한 .d.ts에서 import한 타입으로 타입이 지정된 필드는 여전히 단순한 검사와 "type" 문제를 받습니다. 컴파일러가 이런 타입에는 디스크립터를 합성하지 않으며, 선언에 glyph gen dts를 실행해야 디스크립터가 생깁니다.

  • 모듈이 직접 선언한 Issue 타입은 그 이름을 쓴 줄에서 거부됩니다E01100.1.60부터
    자세히

    Issue라는 타입을 직접 선언한 모듈은 예전에는 생성된 파일 안에서 prelude의 것을 가려서 그 모듈의 모든 디스크립터를 망가뜨렸습니다. 0.1.60부터는 그 선언이 타입 이름을 쓴 줄에서 E0110이므로, 생성된 코드에 대한 tsc 오류를 읽는 대신 문제가 어디 있는지 바로 알 수 있습니다.
