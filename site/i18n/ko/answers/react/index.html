React의 컴포넌트, hook, Context와 함께 쓸 수 있나요?

네. component는 React 함수 컴포넌트로 컴파일되고, JSX는 createElement로 변환되며, React 자체의 hook은 이름으로 import하고 그 쌍은 구조 분해하며, reducer 상태는 평범한 TypeScript에 없는 망라성 검사를 받습니다. 페이지 자체(제목, 마운트 지점, 저장된 상태)는 std/dom과 std/storage로 다룹니다. 먼저 알아 둘 빈틈은 Glyph 자체 검사기가 hook이 반환하는 값에 타입을 매기지 않는다는 점이며, 그 값들은 tsc가 검사합니다.

왜 중요한가

에이전트가 작성하는 코드의 상당 부분이 React입니다. Glyph는 React를 덧붙인 것이 아니라 일급 대상으로 다룹니다. component는 별도의 키워드이므로 grep "^component "로 UI 전체를 감사할 수 있습니다.

React의 hook은 react에서 import하고 실제 이름과 타입으로 호출하며, tsc가 React 자체의 선언에 대해 검사합니다.

reducer와 hook

Double 액션을 추가하면 reducer는 그것을 짚는 E0200으로 컴파일을 멈춥니다. 평범한 TypeScript switch라면 그대로 배포되었을 것입니다.

E0200

Glyph 자체 검사기는 React에서 온 값에 타입을 매기지 않으므로, dispatch나 상태 setter에 넘긴 잘못된 인자는 에디터나 --no-tsc가 아니라 빌드의 tsc가 보고합니다.

자세히 hook이 반환한 쌍을 구조 분해하는 방식

쌍은 let [count, dispatch]로 구조 분해하고, 생성된 TypeScript는 satisfies readonly [unknown, unknown]을 덧붙이므로, tsc가 hook이 쌍을 반환했다는 것을 증명하면서 각 요소의 타입도 추론합니다.

Context와 라이브러리

React Context는 지금 createContext / useContext로 동작하고, 멤버 표현식 요소 이름(<ThemeContext.Provider>)도 우회 없이 바로 동작합니다.

  • prop spreadJSX prop spread도 동작합니다. <input {...register("email")} />는 props 안의 객체 spread로 변환되므로 react-hook-form 관용구에 어댑터가 필요 없습니다.
  • Zod 타입Zod의 값 기반 타입도 일급입니다. type FormData = z.infer<typeof schema>가 탈출구 없이 바로 동작합니다.

다른 점은 하나입니다. 컴포넌트는 위치 매개변수 여러 개가 아니라 props 레코드 하나를 받습니다. 그 경계가 정확히 어디인지는 라이브러리 사용하기와 하드닝 페이지를 보세요.

props는 tsc 전에 검사되나요?

네. Glyph가 각 요소를 컴포넌트의 props 레코드와 직접 비교하므로, 잘못된 값, 철자가 틀린 prop, 빠진 필수 prop은 그 prop을 짚는 Glyph 오류입니다. 컴포넌트를 이름으로 import했든 모듈을 통해 썼든 똑같이 동작합니다.

main.glyph, ui.glyph에 선언된 Card와 함께 
import ui

pub component App() {
  return <div>
    <ui.Card title="Q3" />
    <ui.Card title="Q4" cout={2} />
  </div>
}

// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`
// E0210 type `CardProps` has no field `cout`; did you mean `count`?
// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`

전체 빌드뿐 아니라 에디터와 MCP에서도 보입니다.

자세히 --json의 missing_fields, 그리고 props 레코드 하나(E0229)

--json은 빠진 이름을 missing_fields 목록으로 담으므로, 에이전트는 메시지를 파싱하지 않고 props를 추가할 수 있습니다. 컴포넌트는 props를 레코드 하나로 받아야 합니다. component Greeting(name: string)은 매개변수 위치에서 E0229입니다. React는 언제나 props 객체만 넘기므로 그런 요소는 타입 검사를 통과할 수 없기 때문입니다. 렌더링하지 않고 함수로 호출한다면 fn으로 선언하세요.

JSX 안의 <match>도 match처럼 검사되나요?

같은 것입니다. 각 <case>는 match arm과 같은 패턴을 받고, 컴파일러는 arm에 쓰는 코드로 이를 처리합니다.

  • payload 타입case가 바인딩하는 이름은 payload의 타입을 가지고, payload 레코드에 없는 필드는 E0210이며, 빠진 variant는 E0200입니다.
  • 부분적인 case값을 검사하는 case는 variant의 일부만 다루므로, 나머지를 받을 형제 case나 <case else>가 필요합니다.
results.glyph 
type Page =
  | Loading
  | Loaded({ users: Array<User>, total: number })
  | Failed(string)

component Results(props: { page: Page }) {
  return <match value={props.page}>
    <case Loading><p>Loading...</p></case>
    <case Loaded({ users, totl })><p>{users.length} of {totl}</p></case>
    <case Failed(message)><p>{message}</p></case>
  </match>
}

// E0210 type `{ users: Array<User>, total: number }` has no field `totl`; did you mean `total`?

페이지는 이것을 어떻게 시작하나요?

Glyph에는 최상위 문장이 없으므로, 페이지가 export된 main을 직접 호출합니다. 앱은 모듈 두 개입니다. 하나는 컴포넌트를 담고, 다른 하나는 std/dom과 react-dom의 createRoot로 이를 #root에 마운트합니다.

이벤트 속성은 snake case이고(on_change는 React의 onChange로 생성됩니다), 핸들러는 람다이며, input의 텍스트는 e.currentTarget.value입니다.

app.glyph 
module app

import react { useState }

pub component App() {
  let [name, set_name] = useState("")
  return <main>
    <input value={name} on_change={fn(e) { set_name(e.currentTarget.value) }} />
    <p>Hello, {name}</p>
  </main>
}
main.glyph 
module main

import react-dom/client { createRoot }
import std/dom
import std/console
import std/option { Some, None }
import app { App }

pub fn main() -> void {
  match dom.element_by_id("root") {
    Some(root) => createRoot(root).render(<App />),
    None => console.error("the page has no #root element"),
  }
}

자세히 빌드, 이 main이 아무것도 받지 않는 이유, 단계별 설명

npx glyph build . --out dist/gen은 모듈을 검사하고, React의 선언에 대해 tsc --strict를 실행하고, TypeScript를 dist/gen에 씁니다. 그다음 npx vite build --outDir dist/web이 index.html을 읽고 import를 따라가 React와 함께 번들합니다. 스크립트가 인자 없이 호출하므로 이 main은 아무것도 받지 않고 아무것도 반환하지 않습니다. glyph init이 쓰는 main(argv) -> number는 node에서 glyph run이 호출하는 것입니다. package.json과 설치 명령을 포함한 전체 안내는 glyph llms가 출력하는 레퍼런스의 브라우저 페이지에서 Glyph 실행하기에 있습니다. CI는 examples/apps/todo를 같은 방식으로 빌드하고 headless Chromium에서 렌더링합니다.

현재 상태

지금 제공되는 것

  • 컴포넌트, JSX, fragment(<>...</>)
  • 멤버 표현식 요소 이름(<Ctx.Provider>)
  • JSX prop spread({...register()})
  • 모든 import 표기에서 tsc 전에 컴포넌트에 대해 검사되는 props
  • 이름으로 import하는 React 자체 hook(useState, useReducer, useEffect)과 tsc의 타입 검사 및 쌍 구조 분해(let [count, set_count] = useState(0))
  • 망라적인 태그 유니언 액션을 쓰는 useReducer
  • arm의 패턴으로 match처럼 검사되고 변환되는 <match>/<case>
  • createContext/useContext를 통한 Context
  • std/dom(제목, 마운트 지점, 주소), std/storage, std/console로 다루는 페이지
  • JSX 텍스트는 TSX와 같은 방식으로 읽으므로 <p>Don't stop</p>는 평범한 텍스트입니다. 텍스트 안의 }, >, //, 그리고 &amp; 같은 HTML 엔티티는 대신 쓸 표기와 함께 거부됩니다(E0012).E0012
  • 배열에 대한 멤버 읽기는 검사되므로 Array<string>에 대한 {items.foo}는 E0210입니다.E0210
  • examples/apps/todo는 Vite로 번들하고 브라우저에서 렌더링되는 React 18 기반 앱 전체입니다.

앞으로 할 것

  • Glyph가 아직 다루지 못하는 React 패턴은 gap 번호와 그동안 쓸 수 있는 방법과 함께 Glyph가 React에서 아직 못 하는 것은?에 정리되어 있습니다.
  • Glyph 검사기는 hook의 결과에 타입을 매기지 않으므로, 숫자 상태에 대한 set_count("x")는 에디터의 Glyph 오류가 아니라 빌드의 tsc 오류입니다.
  • std/dom은 페이지를 읽고 제목을 설정하는 데서 멈춥니다. React가 자신이 렌더링하는 DOM을 소유하므로 요소 setter나 이벤트 리스너는 없습니다.
  • effect는 fn() -> void { ... }로 써야 합니다. 람다는 마지막 표현식을 반환하고, React는 이를 정리 함수로 호출할 것이기 때문입니다.
  • 인라인으로 쓴 props 타입은 이 메시지들에서 여전히 record로 표시되고, 이름 붙은 타입은 이름이 표시됩니다.
  • UI는 TypeScript로 두고 기존 Vite 앱에 Glyph 출력을 넣는 방법은 배포 가이드에 있습니다.
