14 · 공유 상태

함수 사이에서 변경 가능한 상태를 어떻게 공유하나요?

store를 씁니다. Glyph에는 변경 가능한 전역 변수가 없습니다. 모듈 바인딩은 const입니다. 공유 상태는 std/store에 둡니다. get()으로 읽고 set()/update()로 바꾸는 값을 담은 모듈 수준 const입니다. 바인딩은 절대 바뀌지 않고, 그 안의 값만 메서드 호출을 통해 바뀌므로, 모든 쓰기는 grep할 수 있는 .set(이나 .update( 그대로입니다.

직접 보기

store는 모듈 스코프에서 한 번 선언합니다. 모듈의 모든 함수가 이를 공유합니다. main을 거쳐 넘기는 let도, 값을 캡처하는 클로저도 필요 없습니다.

tasks.glyph 
import std/store { create }
import std/array

type Task = {
  id: number,
  title: string,
}

const tasks = create<Array<Task>>([])
const next_id = create(0)

fn add(title: string) -> Task {
  next_id.update(fn(n: number) -> number {
    return n + 1
  })
  let task = { id: next_id.get(), title: title }
  tasks.update(fn(cur: Array<Task>) -> Array<Task> {
    return array.push(cur, task)
  })
  return task
}

fn all() -> Array<Task> {
  return tasks.get()
}

왜 변경 가능한 전역 변수가 아니라 store인가

의도한 설계 선택입니다. Glyph는 mut를 로컬 대입으로 제한하고 모듈 바인딩을 const로 두는데, 쓰기 가능한 전역 변수가 흩어져 있으면 상태를 추론하기도, 찾기도 어려워지기 때문입니다. store는 두 규칙 중 어느 것도 느슨하게 할 필요가 없습니다. const s 바인딩은 불변이고, 그 안의 값은 set/update를 통해서만 바뀝니다. 그래서 공유 상태는 새 문법이 아니라 라이브러리로 제공되고(선형 타입도, 약해진 변경 규칙도 없습니다), 변경은 프로그램 전체에 퍼지지 않고 감사된 한 곳에만 있습니다.

TypeScript와 같은 날카로운 부분이 하나 있습니다. 빈 컬렉션은 요소 타입을 추론할 수 없으므로 명시적인 타입 인자로 시작하세요: create<Array<Task>>([]). 스칼라 store(create(0))는 잘 추론됩니다.

현재 상태

지금 제공되는 것

create, get, set, update를 갖춘 std/store: 공유되는 변경 가능 상태를 위한, grep할 수 있는 단 하나의 자리.

앞으로 할 것

같은 기본 요소 위의 편의 기능(파생 및 계산 store, 구독)을 언어를 바꾸지 않고 그 위에 더합니다.
