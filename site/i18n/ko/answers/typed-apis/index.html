API마다 검증기를 직접 작성해야 하나요?

아니요. Glyph에서는 타입이 곧 검증기입니다. type을 선언하면 컴파일러가 그 옆에 런타임 디스크립터를 생성하므로, 신뢰할 수 없는 요청이나 응답 본문을 호출 한 번으로 검증하며, 따로 작성하고 맞춰 둘 zod 스키마가 없습니다.

왜 중요한가

대부분의 TypeScript 스택에서 모든 페이로드는 두 번 기술됩니다. 한 번은 컴파일러를 위한 type으로, 또 한 번은 값이 런타임에 실제로 그 모양이 되도록 직접 작성한 검증기로.

둘은 어긋나고, 잘못된 데이터가 들어오는 곳이 바로 그 어긋남입니다. Glyph는 둘을 선언 하나로 합칩니다. 타입이 검증기를 만들어 내므로 서로 다를 수 없습니다.

직접 보기

DTO를 한 번 선언합니다. 그 디스크립터가 .parse(신뢰할 수 없는 값을 그 타입으로 검증)와 .is(타입 가드)를 주고, 그 밖에 작성할 것은 없습니다.

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}

// No drift between the type and

자세히 타입이 전달되는 방식과 제네릭의 예외

T.parse의 타입은 Result<T, Array<Issue>>이고 arm이 일치하는 match는 그 타입을 가지므로, let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, }는 함수의 나머지에서 NewTask를 주며, 필드 이름은 생성된 TypeScript에 대한 tsc가 아니라 Glyph가 검사합니다. 0.1.45에 들어왔고, 그 전에는 값이 match를 나오면 타입을 잃었습니다. 아직 그렇지 않은 것은 제네릭 타입의 parse입니다. 그 디스크립터는 타입 매개변수마다 런타임 검사기를 받기 때문입니다.

파싱 결과는 평범한 Result입니다

Glyph에서 T.parse는 언어의 실패할 수 있는 모든 함수가 반환하는 것과 같은 Result를 반환하므로, 그대로 돌려주거나, map_err로 검증 문제를 자신의 오류 타입으로 바꾸거나, ?로 전달할 수 있습니다.

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}

자세히 여기서 Result를 쓰는 런타임 비용

자기만의 모양으로 값을 돌려주는 검증기는 절반만 쓸모 있습니다. 나머지 오류 처리가 그 값을 다룰 수 없기 때문입니다. 파싱 결과에는 특별한 것이 하나도 없습니다.

예전에 그렇지 않았던 이유는 이렇습니다. 디스크립터는 type 옆에 생성되는데, 순수 객체를 생성하면 타입을 선언한 모듈이 런타임에 std/result에 의존하지 않아도 되었습니다. 이제는 그 거래를 반대로 합니다. pub type이 있는 모듈은 Result를 쓰든 안 쓰든 std/result import를 가지고, parse 호출은 어떤 Ok(...)든 할당하는 조합자 클로저를 할당합니다. 그 대가로 검증된 경계와 나머지 오류 처리가 같은 API가 됩니다.

직접 조합하기: 출력 타입은 믿는 것이 아니라 끌어냅니다

Glyph의 infer_output<Shape>는 모양에서 출력 타입을 끌어내고, tsc가 여러분의 타입 표기를 그에 대해 검사합니다. 주장하는 타입의 필드를 빠뜨린 모양은 컴파일되지 않습니다.

schema.glyph 
fn object_schema<Shape: Record<string, Schema<unknown>>>(
  shape: Shape,
) -> Schema<infer_output<Shape>> { ... }

type User = { name: string, age: number }

// The shape must produce a User, or this
// line does not compile:
const user_schema: Schema<User> =
  object_schema({
    name: string_schema(),
    age: number_schema(),
  })
Glyph가 없애는 어긋남 
// TS/zod: shape and output type are two
// separate things you keep in sync by hand.
const s = z.object({ name: z.string() });
type User = { name: string; age: number };
// `s` is inferred { name }, but nothing
// checks it against User. The `age` you
// forgot is caught at runtime, if ever.

// Glyph: drop `age` from the shape and
// `Schema<User>` fails to compile. The
// shape is the single source of truth.
자세히 TypeScript의 함정, 그리고 0.1.92부터 return을 따라가는 캐스트

zod 스타일의 조합자가 필요할 때가 있습니다. 작은 검증기를 조합해 검증기를 만드는 것입니다. TypeScript의 함정은 조합자의 출력 타입과 넘긴 모양이 서로 어긋난다는 것입니다. 모양을 쓰고, 두 번째 타입 매개변수에 같은 것을 반복하며, 둘이 일치하는지 검사하는 것은 없습니다.

끌어낸 타입은 조합자가 어떻게 반환하든 성립합니다. infer_output은 함수 경계에서 캐스트 하나가 필요합니다. 본문이 만드는 값이 모양에서 끌어낸 타입을 가진다는 것을 타입 시스템이 증명할 수 없기 때문이며, 컴파일러가 그 캐스트를 대신 씁니다. 0.1.91까지는 평범한 return <value>에 붙었습니다. return과 값 사이에 match를 두거나 본문을 r?로 끝내면 같은 함수가 컴파일되지 않았습니다. 컴파일러가 이미 받아들인 Glyph에 대해, 생성된 TypeScript 기준의 TS2322였습니다. 0.1.92부터 캐스트는 표기가 아니라 return을 따라가므로, return match strict { ... }는 같은 본문을 단일 return으로 쓴 것과 똑같이 타입 검사를 통과합니다.

신뢰할 수 없는 경계의 나머지

디스크립터는 json.parse<T>를 안전하게 만드는 것과 같은 것입니다. JSON 문자열을 주면 한 단계에서 파싱하고 검증합니다.

입력호출반환
JSON 문자열json.parse<T>(text)Result<T, Array<Issue>>
디코딩된 본문T.parse(value)Result<T, Array<Issue>>
헤더header(req, name)Option<string>
쿼리 매개변수query_param(req, name)Option<string>
자세히 요청 본문, 헤더, 쿼리 매개변수

요청 본문은 이미 unknown으로 디코딩되어 도착하므로, 거기서는 대신 T.parse(value)를 씁니다. 같은 보장이고 캐스트는 없습니다.

신뢰할 수 없는 경계의 나머지도 같은 방식으로 타입이 지정됩니다. header(req, name)와 query_param(req, name)은 Option<string>을 반환하므로, 헤더나 쿼리 매개변수가 없으면 None이고 match가 이를 처리하도록 강제합니다. None arm을 빠뜨리면 컴파일되지 않습니다. 없는 입력을 있는 것처럼 읽을 수 없습니다. 본문 필드도 같은 규칙을 따릅니다. timeout_ms?: number는 키가 없거나 숫자이므로, {"timeout_ms": null}은 T.parse, is T, json.parse<T> 모두에서 ["timeout_ms"] 위치의 Err입니다. 보내는 쪽이 null을 쓴다면 timeout_ms?: Nullable<number>로 선언하세요. 0.1.152 전까지는 그 null이 Ok 안에 담겨 돌아왔습니다.

enum을 키로 하는 맵은 키를 검사하나요?

네, 0.1.148부터입니다. type Tier = "free" | "pro"일 때 Record<Tier, int>는 키가 정확히 free와 pro인 객체만 파싱합니다. 엉뚱한 키와 빠진 키는 둘 다 Err이며, 같은 객체를 리터럴로 썼을 때 tsc가 하는 말도 그렇습니다.

키 타입parse가 각 키에 대해 검사하는 것
문자열 리터럴 유니언나열된 키 정확히, 빠진 것도 남는 것도 없이
where로 정제한 string이나 숫자조건식
int정수의 평범한 표기. "01"과 "1.5"는 실패
string새로운 것 없음
자세히 정제된 키와 int 키, 그리고 검사기가 지키는 것

where로 정제한 키 타입은 모든 키에 조건식을 실행하고, int 키는 정수의 평범한 표기여야 하므로 "01"과 "1.5"는 거부됩니다. Record<string, V>는 이전과 똑같이 검사됩니다. where로 문자열 리터럴 유니언을 정제할 수는 없습니다(0.1.152부터 type T2 = Tier where value != "pro"는 E0300입니다). 원하는 멤버를 별도의 유니언 type T2 = "free"로 작성하면, 같은 정확한 키 검사로 Record의 키가 됩니다. 0.1.153부터는 Glyph 자체 검사기가 코드에 작성한 값의 키도 지킵니다. Record<string, int>는 Record<Tier, int>로 선언된 자리에 올 수 없고 그 반대도 마찬가지이므로, 둘 사이를 건너는 길은 json.parse나 is Record<Tier, int> arm이며, record.set은 받은 키를 유지합니다. 자신의 타입 매개변수를 키로 하는 제네릭 레코드는 그 매개변수가 string이 아니면 거부됩니다.

날짜를 파싱하면 진짜 날짜를 얻나요?

네, 그리고 흥미로운 부분은 날짜가 아닌 입력에 대해 무엇을 돌려받느냐입니다. time.parse_iso는 Option<number>를 반환하며, ISO-8601이 아닌 모든 것에 대해 None입니다.

받아들임 
"2026-01-03"              // UTC midnight
"2026-07-25T18:33:08.000Z"
"2026-03-15T09:30:00-05:00"
"2028-02-29"              // a real leap day
모두 None 
"January 5 2026"   // not ISO
"2026-1-3"         // not padded
"2026-13-01"       // no month 13
"2026-02-31"       // no such day
"2026-02-29"       // not a leap year
"2026-01-03T10:00" // no offset

마지막 것이 사람들을 놀라게 하는데, 그것이 핵심입니다. Z도 +HH:MM 오프셋도 없는 날짜시간은 ECMAScript 문법상 로컬 시간이므로, 이를 받아들이면 같은 문자열이 프로그램을 실행한 컴퓨터에 따라 다른 날짜를 가리키게 됩니다.

자세히 Date.parse는 대신 무엇을 하는가, 그리고 왜 UTC인가

이는 JavaScript의 Date.parse보다 강한 주장입니다. 그 함수는 자유 형식 텍스트("January 5 2026")를 받고, "2026-1-3"처럼 자릿수를 채우지 않은 날짜는 프로세스가 마침 실행되는 시간대로 읽으며, 불가능한 날짜는 앞으로 넘겨서 성공으로 보고합니다. "2026-02-31"은 3월 3일이 되고, 무슨 일이 있었는지 아무 표시 없이 숫자를 돌려받습니다.

Glyph의 달력 접근자(time.year, time.month, time.day)는 UTC이며 그렇다고 밝힙니다. 호스트의 시간대를 조용히 가져오는 검증기는 이들이 거짓말하게 만들 것입니다. 그래서 문자열을 거부하고, 그것이 무엇을 뜻했는지는 여러분이 정합니다.

방어 코드가 기본 요소 안으로 옮겨졌습니다

애플리케이션이 표준 라이브러리 기본 요소 주위에 정확성 방어 코드를 쓴다면, 그 방어 코드는 기본 요소 안에 있어야 합니다. 앱에서 지운 것은 다음과 같습니다.

이전: 앱이 stdlib를 방어함 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
이후: 기본 요소가 선을 지킴 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

import std/regex도 함께 사라졌습니다. 같은 원장, 같은 거부된 행, 바이트 단위로 같은 보고서입니다.

이력 이것이 나온 경비 보고서 앱

이는 Glyph로 경비 보고서 CLI를 작성하면서 나왔습니다. 원장의 모든 행에는 날짜가 있고, 행을 엉뚱한 달에 넣는 것이 중요한 버그이므로, 앱은 예전 parse_iso를 믿지 않았습니다. 먼저 정규식으로 모양을 검사하고, 그다음 타임스탬프를 텍스트로 되돌려 넘어간 날짜를 잡아냈습니다.

타입조차 작성할 필요가 없습니다

모양이 이미 OpenAPI 명세나 TypeScript 선언 파일에 있다면 거기서 Glyph 타입을 생성하세요. 추론된 유령이 아니라, 각각 디스크립터를 가진 실제로 커밋되고 grep할 수 있는 type 선언입니다.

OpenAPI / JSON Schema 명세에서 
glyph gen openapi petstore.yaml \
  --out src/
설치된 패키지에서, 이름으로 
glyph gen dts api-types \
  --out src/types

전송 타입이 직접 작성한 것 없이 검증되는 경계가 됩니다.

webhook.glyph 
import types/api_types { Customer }

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),
  Err(issues) => reject(issues),
}

생성은 전송 형식에 충실합니다. 명세가 값에 대해 말하는 것이 parse가 검사하는 것입니다.

닿을 수 있는 두 파일에 있는 이름바인딩하지 않고 안내와 함께 표시
자세히 현재 실체화되는 것, 다시 생성하기, 제네릭 타입

glyph gen dts에 .d.ts 파일을 주거나, 위처럼 설치된 npm 패키지 이름을 주면 됩니다. node_modules에서 패키지 자체의 선언 진입점을 찾아, import해서 쓰는 커밋된 타입을 씁니다.

현재 실체화되는 것: gen dts는 패키지가 export하는 interface와 type 선언을 읽으며, declare namespace 트리 안의 것(단순 상호 참조는 스코프를 통해 해석됩니다)과 index barrel이 재export하는 형제 파일의 것(진입 .d.ts와 상대 경로로 import된 모든 .d.ts를 순회합니다)도 포함합니다. 제네릭은 일급으로 유지됩니다. interface Page<T>는 type Page<T>로 실체화되고, 각 항목이 있는지만이 아니라 타입 인자로서 검증하는 디스크립터를 받습니다. 별칭과 export * as 재export는 파일별 바인딩 맵으로 해석됩니다. 안전하게 만들 수 없는 경우 하나, 즉 닿을 수 있는 두 파일에서 충돌하는 타입 이름은 잘못된 모양을 조용히 바인딩하는 대신 안내와 함께 표시합니다. 실체화기가 닿지 못하는 것은 경계에서 쓰는 모양을 직접 작성하거나 extern_ts 탈출구를 쓰세요.

다시 생성하는 것은 멱등이므로 명세 변경은 깔끔하고 리뷰할 수 있는 diff입니다. 생성은 전송 형식에 충실합니다. 문자열 enum은 문자열 리터럴 유니언("free" | "pro")으로 실체화되므로 parse는 값이 문자열인지만이 아니라 멤버십을 검사하고, 그에 대한 match는 else 없이 망라적입니다. integer 필드는 int가 되므로, 평범한 숫자라면 통과했을 전송된 3.5가 parse에서 실패합니다. 정확한 Glyph 형태가 없는 구문(판별자 없는 유니언)은 실제 데이터를 거부할 검증기를 생성하는 대신 좁히고 안내를 출력합니다. 생성된 레코드에는 @open도 붙으므로, parse는 선언한 모든 필드를 검증하면서도 API가 나중에 추가하는 필드를 허용합니다. additionalProperties: false를 설정한 스키마는 엄격하게 유지됩니다. Glyph에서 레코드는 기본적으로 엄격하고, 이는 직접 작성한 레코드가 쓰는 것과 같은 grep할 수 있는 선언 위치의 표시이므로, 레코드의 의미는 바뀌지 않습니다.

제네릭 타입도 검증됩니다. Paginated<T>는 parse가 타입 인자를 받는 디스크립터를 가집니다. Paginated.parse<User>(body)는 모든 items 항목이 있는지만이 아니라 User로서 검사하고, match v { is Paginated<User> => ... }도 같은 방식으로 좁힙니다. 이는 모듈 경계를 넘어서도 성립합니다. 한 파일에서 Paginated<T>를 정의하고 다른 파일로 import해도, 거기서 Paginated.parse<User>(body)와 is Paginated<User> 모두 각 요소를 User로 검사합니다. 컴파일러는 호출 위치의 타입 인자로 요소별 검사를 만들므로, 제네릭 타입이 어느 파일에 있는지는 무엇이 검증되는지와 상관없습니다.

한계: 디스크립터는 대부분의 페이로드를 이루는 모양을 다룹니다. 객체, 원시 타입, 배열, 참조, 선택 및 nullable 필드, 그리고 이제 주어진 인스턴스화에서의 제네릭 타입입니다. Glyph가 생성하지 않은 타입(import만 하는 외부 패키지나 .d.ts)은 타입 검사는 되지만 실체화하기 전까지 디스크립터가 없으며, 실체화는 이제 설치된 패키지에 대한 명령 하나입니다(glyph gen dts <package>, 패키지가 export하는 최상위 인터페이스와 타입 별칭 대상). 이 경계는 의도한 것입니다. Glyph가 생성하지 않은 타입은 런타임 검증을 약속할 수 없으므로, 패키지마다 직접 선택하고, 결과는 빌드할 때마다 만들어지는 것이 아니라 커밋되고 grep할 수 있습니다.

데이터베이스도 경계입니다

데이터베이스에서 읽은 행은 요청 본문과 똑같이 신뢰할 수 없습니다. 요청 본문에 쓰는 것과 같은 .parse로 행을 검증합니다.

tasks.glyph 
type Task    = { id: int, title: string, done: bool }
type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.
match TaskRow.parse(row) {
  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}
없애는 버그 
// TS, better-sqlite3 / node:sqlite:
const row = stmt.get(id) as Task;
// `row.done` is really 0 or 1, a number.
// Nothing complains. Then:
if (row.done === true) { ... }   // never runs

// The row was `unknown`; the cast invented
// a type. Glyph makes you validate the row
// into TaskRow, and the int-to-bool step is
// a line of code, not a silent lie.
자세히 std/sqlite, 그리고 0 또는 1인 불리언

데이터베이스에서 읽은 행은 요청 본문과 똑같이 신뢰할 수 없습니다. 데이터베이스 스키마와 코드가 생각하는 행이 다를 수 있고, 캐스트(row as Task)가 이를 덮습니다. Node 내장 SQLite 위의 DB 모듈인 std/sqlite는 이 점을 적극 활용합니다. 쿼리는 Array<Record<string, unknown>>를 반환하므로, 검증하지 않고는 행을 Task로 다룰 방법이 없습니다.

이는 사람들이 끊임없이 배포하는 버그를 잡습니다. SQLite에는 불리언 타입이 없으므로 done 열은 정수 0이나 1로 돌아옵니다. 행을 bool 필드가 있는 레코드로 캐스트하면 task.done === true는 조용히 절대 참이 되지 않습니다. Glyph에서는 저장 모양과 도메인 모양이 별개의 타입이고, 둘 사이의 매핑은 실제로 보이는 한 줄입니다.

전체가 동작하는 예제입니다. examples/apps/tasks/main.glyph는 저장에 std/sqlite, 라우트에 std/http를 쓰는 영속 작업 API로, 데이터는 재시작해도 남고 전송 쪽과 데이터베이스 쪽 모두에서 검증합니다. 직접 작성한 검증기는 어디에도 없습니다.

서명된 웹훅도 경계입니다

웹훅 서명을 검증하려면 다시 직렬화한 사본이 아니라 보낸 쪽이 서명한 정확한 바이트가 필요합니다(파싱한 본문을 다시 문자열로 만들면 공백과 키 순서가 바뀌어 HMAC이 절대 맞지 않습니다). http.raw(req)가 그 바이트를 주므로 검사는 Glyph 안에 머뭅니다. 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
자세히 서명에는 원본 바이트, 모양에는 파싱된 본문

req.body는 여전히 모양 검사를 위한 파싱된 값이고, raw는 서명을 계산하는 변조되지 않은 페이로드입니다. 서명을 검증하고 본문을 검증하는 수신기에 직접 작성한 TypeScript는 필요 없습니다.

타입은 모양만이 아니라 불변식도 검증할 수 있습니다

모양 검사는 필드가 숫자라는 것을 알려 줍니다. 금액이 음수가 아니라거나 평점이 1에서 5 사이라는 것은 알려 주지 않습니다. where 정제는 그 불변식을 타입에 넣고, 디스크립터가 경계에서 이를 강제합니다.

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
작성하지 않는 것 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.

현재 상태

지금 제공되는 것 10

디스크립터

  • 선언된 모든 레코드와 태그 유니언은 제네릭 레코드를 포함해 런타임 디스크립터(.parse, .is, .schema)를 가집니다제네릭 태그 유니언은 제외
  • .parse는 언어의 나머지가 쓰는 것과 같은 Result를 반환하므로, map_err, ?, 그리고 그것을 반환하는 어떤 함수와도 조합됩니다
  • where 정제(int where value >= 0)는 경계에서 모양만이 아니라 불변식을 검증합니다
  • json.parse<T>가 JSON을 검증합니다
  • infer_output<Shape>는 조합자의 출력 타입을 모양에서 끌어내므로 둘이 어긋날 수 없습니다

생성

  • glyph gen openapi / glyph gen dts는 명세, .d.ts, 또는 이름으로 지정한 설치된 패키지에서 디스크립터를 가진 커밋되는 타입을 생성합니다

경계

  • std/sqlite는 행을 unknown으로 돌려주므로 데이터베이스도 다른 경계처럼 검증됩니다
  • 서명된 웹훅 수신기가 완전히 Glyph 안에 머뭅니다
    자세히

    http.raw(req)가 파싱하지 않은 요청 본문을 제공하므로, 웹훅 서명을 정확한 바이트에 대해 검증하고 서명된 웹훅 수신기가 완전히 Glyph 안에 머뭅니다.

  • 신뢰할 수 없는 입력은 sanitize 없이 SQL이나 셸 싱크에 닿을 수 없습니다
    자세히

    std/taint의 Tainted/Trusted 타입은 명시적인 sanitize 없이 신뢰할 수 없는 입력이 SQL이나 셸 싱크에 닿지 못하게 하므로, tsc가 컴파일 시점에 인젝션 경로를 거부합니다.

  • time.parse_iso는 ISO-8601만 받습니다
    자세히

    더 작은 경계 기본 요소도 같은 선을 지킵니다. time.parse_iso는 ISO-8601을 받고, 자유 형식 텍스트, 불가능한 날짜, 그리고 오프셋이 없어서 그렇지 않으면 호스트의 로컬 시간대로 읽힐 날짜시간에 대해서는 None을 반환합니다.

앞으로 할 것 3

  • 판별 유니언은 명세와 .d.ts에서 생성됩니다. 다음은 enum과 매핑된 타입 지원
    자세히

    판별 유니언은 이제 OpenAPI discriminator와 TypeScript .d.ts 유니언 모두에서 생성됩니다(parse_<Name> 디스패처가 태그를 읽고 올바른 variant로 검증합니다). 다음은 더 풍부한 enum과 매핑된 타입 지원입니다.

  • 명세에서 타입이 있는 클라이언트와 서버 코드를 만드는 것은 이미 제공됩니다 클라이언트와 서버 보기
  • 타임스탬프와 기간이 둘 다 number입니다
    자세히

    날짜에서는 엄격함이 기능의 전부이고, 파싱에서 멈춥니다. parse_iso는 epoch 밀리초를 돌려주므로 타임스탬프와 기간이 둘 다 number이고, 하나를 다른 것에 더하는 것을 막는 것은 없습니다. 별도의 날짜 타입은 나중에 내릴 결정이며, 작은 결정이 아닙니다.
