08 · 업그레이드

새 Glyph 릴리스가 내 빌드를 깨뜨리나요?

요청하지 않는 한 그렇지 않습니다. Glyph 프로젝트는 컴파일러를 정확한 버전으로 고정하므로, 오늘 아침 배포된 릴리스가 오늘 오후 여러분의 빌드에 들어오지 않습니다. 1.0 전에는 릴리스가 어제 컴파일되던 코드를 거부하는 진단을 추가할 수 있고, 보통 그것이 릴리스의 목적이므로, 받을지는 여러분이 결정하며 명령 하나면 됩니다.

왜 중요한가

대부분의 도구는 캐럿으로 고정합니다. 패치 릴리스는 버그 수정이기 때문입니다. 1.0 이전의 컴파일러는 그렇지 않습니다. Glyph의 일은 프로그램을 거부하는 것이고, 그 일을 더 잘하게 된다는 것은 새 오류를 뜻합니다. import에 대한 더 엄격한 검사, 예전에 빠져나가던 망라성의 구멍, 검사기가 모델링하지 않았던 인자 개수 같은 것들입니다. 이런 릴리스가 좋은 릴리스입니다. 동시에 날짜 라이브러리를 추가하려고 실행한 npm install로 들어오기를 원하지 않는 바로 그 릴리스이기도 합니다.

그래서 glyph init은 ^를 쓰지 않습니다. 0.x 버전에서 캐럿은 여전히 패치를 유동적으로 두는데, 그것이 함정입니다. ^0.1.9는 이후의 모든 0.1.x를 조용히 받아들입니다.

package.json, 생성된 그대로 
"devDependencies": {
  // exact. no caret, no tilde.
  "@glyphlang/glyph": "0.1.72",
  "typescript": "^6.0.0",
  "tsx": "^4.19.0"
}

옆에 있는 package-lock.json을 커밋하면, 새로 클론한 저장소는 그 사이 배포된 무언가가 아니라 테스트한 툴체인으로 빌드됩니다.

나머지 절반

고정에는 분명한 실패 방식이 하나 있습니다. 1년 동안 오래된 컴파일러에 머무르면서 그 사실을 모르는 것입니다. 여러분의 컴퓨터에서는 아무것도 알려 주지 않을 것이고, 기억해서 방문해야 하는 웹사이트는 알림 채널이 아닙니다. 그래서 설정에 대해 무엇이든 물으면 컴파일러가 알려 줍니다.

glyph doctor 
glyph — 0.1.72
  [update]   0.1.73 is published — `glyph --update` moves this compiler, `glyph upgrade` moves a project's pin
             what changed: https://glyphlang.io/versions/

glyph doctor — JavaScript toolchain
  [ok]       node: v22.1.0
  [ok]       tsx: tsx v4.19.0
  [ok]       tsc: Version 6.0.2
All good. `glyph run` and `glyph build --check` are ready.

더 새 릴리스를 발견해도 종료 코드는 절대 바뀌지 않으므로 CI에서 실행해도 안전합니다. 배포된 릴리스가 있다고 툴체인이 망가진 것은 아니며, 누군가 10분 전에 배포했다고 통과하던 파이프라인이 실패해서는 안 됩니다. 오프라인이면 검사가 그렇다고 말하고 넘어갑니다. --offline은 검사를 완전히 건너뛰고 네트워크 호출을 전혀 하지 않습니다.

그 밖에는 아무것도 레지스트리에 접속하지 않습니다. build, run, check는 절대 접속하지 않습니다. 빌드할 때마다 외부로 연락하는 컴파일러는 다른 제품입니다.

업그레이드 받기

한 줄이 바뀌고, 언제 할지는 여러분이 정합니다 
$ glyph upgrade --dry-run
glyph upgrade: would move /app/package.json from 0.1.72 to 0.1.73 (nothing written).

$ glyph upgrade
glyph upgrade: /app/package.json now pins 0.1.73 (was 0.1.72).
glyph upgrade: what changed: https://glyphlang.io/versions/
glyph upgrade: build before you commit; a new release may report diagnostics
               this project did not have.

한 줄을 다시 쓰고 npm install을 실행합니다. 소스는 건드리지 않으며, 업그레이드가 끝났다고 가정하지도 않습니다. 방금 받은 릴리스는 코드가 아직 겪어 보지 못한 판단을 내릴 수 있으므로, 그 뒤에 빌드하는 것이 핵심입니다. --to <version>은 특정 버전을 지정하며, 되돌아가고 싶을 때는 이전 버전도 됩니다. --no-install은 설치를 여러분에게 맡깁니다.

프로젝트가 아니라 도구 옮기기

upgrade는 package.json의 고정 버전을 옮깁니다. 뒤처진 것이 PATH에 있는 컴파일러라면 맞지 않는 명령인데, 한동안 doctor는 그래도 이 명령을 출력해서, 전역 설치를 있을지도 모르는 매니페스트로 안내했습니다. 나머지 절반은 glyph --update입니다. 이 구분은 이제 우연이 아니라 규칙입니다. 플래그는 --version, --help, --explain처럼 도구에 작용하고, 하위 명령은 여러분의 코드에 작용합니다. --update-dry-run은 실행했을 npm 명령을 출력하고 멈춥니다.

glyph --update 
$ glyph --update
glyph 0.1.72 is installed; 0.1.73 is published.
Release notes: https://glyphlang.io/versions/
A 0.1.x release may reject code that compiled before, so read the notes for anything between these two.

Running: npm install -g @glyphlang/glyph@0.1.73
   ... npm output ...

npm finished. Confirm with:
    glyph --version

식별할 수 있는 설치만 옮깁니다. npx로 실행한 컴파일러, Glyph 소스 트리에서 빌드한 컴파일러, 알아볼 수 없는 경로에 있는 컴파일러에 대해서는 명령만 출력하고 아무것도 덮어쓰지 않습니다. 추측으로 Homebrew 바이너리나 누군가의 cargo build를 바꾸면 아무도 선택하지 않은 것을 PATH가 가리키게 되기 때문입니다. 업데이트가 적용되었다고 단언하지도 않습니다. npm은 가져오지 못한 optionalDependency를 건너뛰고도 0으로 종료할 수 있고, 실제로 Glyph 릴리스 하나가 플랫폼 바이너리 없이 배포된 적이 있습니다. 그래서 마지막 줄은 성공을 단언하는 대신 확인 방법으로 glyph --version을 안내합니다.

현재 상태

지금 제공되는 것

생성된 프로젝트는 정확한 버전으로 고정하므로 어떤 릴리스도 실수로 빌드에 들어오지 않습니다. glyph doctor는 컴파일러를 레지스트리와 비교해 보고하고 릴리스 노트를 링크하며, 종료 코드에 영향을 주지 않고 build/run/check에서 접근하지도 않습니다. glyph upgrade는 고정 버전을 옮기고 설치하며, 오래된 프로젝트의 캐럿도 읽으므로 기존 프로젝트도 정확한 고정으로 옮길 수 있습니다. glyph --update는 전역 npm 설치의 경우 컴파일러 자체를 옮기고, 그 밖의 설치 방식에 대해서는 추측하지 않고 보고합니다.

개선 중

릴리스 노트는 전체 라인에 대해 페이지 하나이므로, glyph upgrade는 옮겨 가는 버전의 항목이 아니라 페이지를 링크합니다. 새 릴리스의 진단 중 어떤 것에 여러분의 코드가 걸릴지 알려 주는 것은 아직 없습니다. 알려면 빌드해야 하며, 그래서 명령이 빌드하라고 안내합니다. 여러 릴리스를 한 번에 건너뛰는 업그레이드도 하나를 건너뛸 때와 같은 한 단계이며, 그 사이에 쌓인 것을 요약해 주지 않습니다. glyph --update는 npm을 셸로 호출하고 종료 코드를 읽으므로, npm이 끝났다는 것은 알려 줄 수 있지만 PATH에 있는 바이너리가 요청한 버전이라는 것은 알려 줄 수 없습니다. 그래서 성공했다고 말하는 대신 glyph --version을 안내합니다.
