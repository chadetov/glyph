18 · 웹 서빙

웹 페이지를 서빙할 수 있나요, 아니면 JSON API만 되나요?

웹 페이지도 됩니다. std/http는 응답 헤더를 설정할 수 있으므로 text/html 페이지, 302 리다이렉트, 캐시 헤더, HTML 폼 전송이 모두 평범한 Glyph 코드입니다. Express도, 직접 작성한 TypeScript shim도 필요 없습니다.

이 페이지의 내용

  1. 왜 중요한가
  2. 핸들러는 Result를 반환합니다
  3. 모든 응답에는 헤더가 있습니다
  4. 두 가지 세부 사항
  5. 현재 상태

왜 중요한가

0.1.46까지 응답은 { status, body }였고, 서버가 본문의 모양으로 content type을 골랐습니다. 문자열이면 text/plain, 그 밖에는 JSON이었습니다. API에는 괜찮지만 브라우저가 렌더링하는 것에는 쓸모가 없습니다.

빠져나갈 방법은 직접 작성한 .ts 파일에서 node:http로 서버를 만드는 것이었고, 그러면 요청 경로 전체가 타입 검사기 밖에 놓였습니다. 생성자 두 개가 없어서 애플리케이션 경계 하나를 통째로 잃고 있었습니다.

핸들러는 Result를 반환합니다

핸들러는 Result<Response, string>를 반환하므로 404는 평범한 Ok이고, Err는 앱이 답할 수 없는 경우를 위한 것이며 서버가 이를 500으로 바꿉니다.

serve는 수신 대기하는 동안 pending 상태로 남으므로 프로세스를 직접 살려 둘 필요가 없고, 바인딩에 실패하면 값으로 돌아옵니다.

모든 응답에는 헤더가 있습니다

Response에는 필수 필드 headers: Record<string, string>가 있습니다. 선택이 아니라 필수입니다. 모든 생성자가 이를 채우므로 resp.headers를 읽을 때 없는지 확인할 필요가 없고, 이 채널을 잊을 수도 없습니다.

  • 변경이 아니라 새 응답Glyph에는 레코드 필드 변경이 없으므로 with_header(resp, "cache-control", "no-store")는 응답을 바꾸지 않고 새 응답을 반환합니다.
  • Glyph에서 검사됨타입 검사기는 세 생성자가 모두 Response를 반환한다는 것을 알기 때문에, 선언된 반환 타입이 Result<Response, string>인 핸들러는 생성된 출력에 대한 tsc가 아니라 Glyph에서 검사됩니다.

직접 하면 틀리기 쉬운 두 가지

  • 헤더 값Node가 헤더에 쓰기를 거부하는 문자는 내보낼 때 값에서 제거되므로, 쿼리 매개변수로 만든 location이 두 번째 헤더나 두 번째 응답을 끼워 넣을 수 없고, 단축 URL의 이모지가 서버를 멈추게 할 수도 없습니다.
  • 폼 본문form(req)는 퍼센트 이스케이프와 함께 +를 공백으로 디코딩합니다. 직접 만든 폼 파싱이 보통 놓치는 조합입니다. 원본 본문을 읽으므로 직접 파싱하는 핸들러를 위해 req.body는 그대로 둡니다.

현재 상태

지금 제공되는 것

  • html, redirect, with_header, json, text, form
  • 응답 헤더는 그대로 전송되고 content type은 직접 설정하지 않았을 때만 추론
  • 들어오는 쪽의 요청 헤더, 쿼리 매개변수, 경로 세그먼트, 원본 본문
  • 클라이언트는 받은 응답 헤더를 알려 줍니다.

앞으로 할 것

  • 위 코드에서 보이는 빈틈은 퍼센트 인코딩입니다
    자세히

    위 코드에서 보이는 빈틈은 퍼센트 인코딩입니다. form은 폼 본문을 디코딩하지만 URL을 만들기 위한 encode_component는 없어서 단축기가 직접 구현합니다.

  • 클라이언트 쪽에서도 타임아웃, 리다이렉트 정책, head, 리다이렉트가 도착한 최종 URL이 빠져 있습니다.
  • 정적 파일 서버와 템플릿 엔진은 없으며, 둘 다 만들 계획도 없습니다.
