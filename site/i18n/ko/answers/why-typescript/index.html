왜 Go나 새 언어가 아니라 TypeScript인가요?

TypeScript는 에이전트가 이미 가장 많은 코드를 쓰는 곳이고, 여러분의 생태계(npm, React, Node)가 있는 곳이기 때문입니다. Glyph를 파일 하나씩 도입할 수 있는 것은 오직 대상이 TS이기 때문입니다.

왜 중요한가

새 언어의 성패는 처음부터 배포까지 어떻게 가느냐에 달려 있습니다. TypeScript로 컴파일한다는 것은 코드베이스, 번들러, 테스트 러너, 배포 방식을 떠나지 않는다는 뜻입니다. Glyph는 이미 있는 .ts 파일 옆에 들어가고, 양방향 import가 모두 깔끔하게 동작합니다.

같은 프로젝트: .glyph와 .ts를 나란히 
// cart.glyph: new, written in Glyph
import { formatPrice } from "./format.ts"

// checkout.ts: existing, untouched
import { total } from "./cart.glyph"

TypeScript 코드베이스에 Go를 파일 단위로 넣을 수는 없습니다. 런타임도, 모듈 시스템도, 생태계도 다릅니다. 대상이 TS인 이유는 이 한 가지 사실 때문입니다.

Go에 대한 타당한 지적: 작고 안정적인 키워드 표면 덕분에 에이전트가 틀릴 수 있는 방법이 적습니다. 우리도 동의하며, Glyph가 각각을 하는 방법이 하나뿐인 작은 핵심을 의도적으로 유지하는 이유가 바로 그것입니다. 직접 비교할 수 있도록 Go를 밀도 벤치마크에 포함했습니다.

현재 상태

지금 제공되는 것

깔끔한 TypeScript 출력, 기존 .ts와의 양방향 import, 그리고 Node나 브라우저 번들이 실행되는 곳이면 어디서나 실행되는 작은 핵심.

측정 중

언어 간 벤치마크(Glyph, TS, Go, Python, Rust)는 코퍼스와 함께 커지므로, “작은 표면”이라는 주장은 단언이 아니라 숫자로 남습니다.
