기여하기

컴파일러의 구조와 기여하는 방법

컴파일러는 공개 저장소 하나에 있는 크레이트 열두 개짜리 Rust 워크스페이스이며, 라이선스는 MIT 또는 Apache-2.0입니다. 지금 가장 도움이 되는 것은 작은 재현 코드가 있는 버그 리포트입니다. 모든 규칙은 번호가 붙은 설계 결정으로 거슬러 올라가므로, 언어를 바꾸는 변경은 이슈에서 시작합니다.

파이프라인

glyph build는 렉싱, 파싱, 이름 해석, 타입 검사를 거쳐 TypeScript를 생성한 다음, 생성한 코드에 tsc --strict를 실행합니다. 중간 단계는 salsa 위에서 증분 쿼리로 실행되므로, 다시 검사할 때 편집으로 무효화되지 않은 결과를 재사용합니다.

.glyph 파일 하나가 크레이트를 거치는 과정 
glyph-lexer → glyph-parser → glyph-resolver → glyph-typechecker → glyph-emit → tsc --strict
                (glyph-ast)        └──────── glyph-db (salsa) ────────┘
크레이트하는 일
glyph-lexer토큰, 키워드, 의미 있는 줄바꿈, 템플릿 리터럴
glyph-ast모든 노드에 소스 범위가 있는 구문 트리 타입
glyph-parserJSX를 포함해 명세의 모든 결정을 다루는 Pratt 파서
glyph-resolver이름 해석, 모듈 그래프, 모듈 간 import 검사, prelude
glyph-dbsalsa 쿼리 파이프라인과 파일 간 무효화
glyph-typechecker망라성, ?, 제네릭, owned, 런타임 디스크립터, stdlib 모델
glyph-emitTypeScript 출력기, 디스크립터 생성, 표현식 수준의 소스 맵
glyph-formatterglyph fmt: 레이아웃 하나, 주석 보존, 멱등
glyph-lsp하나의 분석 계층을 공유하는 언어 서버와 MCP 서버
glyph-cliglyph 바이너리와 모든 하위 명령
glyph-wasm플레이그라운드를 실행하는 WebAssembly 컴파일러
glyph-runtime스텁입니다. 테스트는 대신 emitter와 tsx를 통해 실행

전체 크레이트 설명과 현재 테스트 수는 glyph-compiler/README.md에 있습니다.

빌드와 테스트

Rust 1.95가 rust-toolchain.toml에 고정되어 있습니다. 일부 테스트는 tsc와 tsx를 셸로 호출하므로 이것들도 설치하세요. CI는 경고를 오류로 취급하는 clippy를 실행하는데, cargo build도 cargo test도 clippy를 실행하지 않으므로 push하기 전에 스크립트를 실행하세요.

클론한 저장소에서 
npm install -g tsx typescript
cd glyph-compiler
cargo build --release -p glyph-cli      # target/release/glyph
cargo test --workspace
cd .. && python3 scripts/check_clippy.py  # the exact clippy command CI runs

# after an intentional syntax-tree change
INSTA_UPDATE=always cargo test -p glyph-parser --test snapshots

새 진단에는 그 코드로 실패해야 하는 tests/negative/ 아래의 프로그램이 함께 있어야 합니다. Glyph가 TypeScript가 놓치는 것을 잡는다는 주장은 catches/에 넣으며, 거기서 게이트가 양쪽을 모두 실행합니다.

계획된 것과 고장 난 것

docs/roadmap/releases.md는 릴리스 로드맵입니다. 배포된 각 릴리스가 한 일과 다음 릴리스들의 목적이 적혀 있습니다. docs/dogfooding-gaps.md는 gap 목록으로, 실제 앱을 만들면서 발견한 모든 한계가 번호(G와 숫자)와 상태 표시와 함께 기록되어 있습니다. 재현 코드가 있는 열린 gap은 시작하기 좋은 곳입니다.

이슈와 풀 리퀘스트

툴체인 수정, 진단, 문서, 예제는 바로 풀 리퀘스트로 보내도 됩니다. 문법이나 의미를 바꾸는 변경은 이슈에서 시작하고, 큰 변경은 docs/rfcs/의 RFC 절차를 거칩니다. 규칙을 "편의를 위해" 느슨하게 하는 PR은 거절될 가능성이 높습니다. 제약 자체가 핵심이기 때문입니다. 풀 리퀘스트 하나에는 gap 하나만 담고, 보통 커밋은 한 개에서 세 개로 하며, 각 커밋에 서명하세요(git commit -s). main은 보호되어 있고 병합은 rebase만 허용됩니다. 전체 규칙은 CONTRIBUTING.md에 있고, good first issue 레이블이 붙은 이슈는 첫 기여에 맞게 범위를 잡아 두었습니다.
