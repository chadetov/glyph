설계 · 비교

Glyph와 Effect

둘 다 사람과 에이전트가 믿고 쓸 수 있는 TypeScript를 목표로 합니다. Effect는 라이브러리입니다. TypeScript를 계속 쓰면서 타입이 있는 오류, 추적되는 의존성, 큰 도구 상자를 얻습니다. Glyph는 TypeScript로 컴파일되는 언어이므로, 라이브러리의 보장을 무너뜨리는 캐스트를 포함해 TypeScript가 허용하는 것을 거부할 수 있습니다. Effect가 훨씬 성숙합니다.

Effect가 스스로를 소개하는 방식

Effect 홈페이지는 "Reliable TypeScript for the AI era"를 첫 문구로 내세우고, "declarative patterns and strong type system make it easier for LLMs to generate correct, production-ready code"라고 말합니다(effect.website). 문서에서는 스스로를 "an ecosystem of tools that help you build better applications and libraries"라고 부르며, 계산이 무엇을 반환하고, 어떻게 실패할 수 있고, 무엇이 필요한지를 기록하는 Effect<Success, Error, Requirements> 타입을 중심으로 만들어졌습니다(Why Effect). strict를 켠 TypeScript 5.4 이상이 필요합니다(Installation). 이 인용문은 2026-11-19에 확인했습니다.

라이브러리와 언어라는 차이에서 오는 결과

Effect의 타입은 tsc가 검사하므로, tsc가 허용하는 것은 그 옆에서도 여전히 허용됩니다. 다음 코드는 effect 4.1.4와 TypeScript 6에서 tsc --strict로 컴파일됩니다. 캐스트가 오류 채널에서 NotFound를 없애고, 프로그램은 실패할 수 없다고 타입이 지정된 effect에서 실패를 보고합니다.

eff.ts: tsc --strict는 0으로 종료하고, 실행하면 "Failure undefined"를 출력 
import { Effect } from "effect"

class NotFound {
  readonly _tag = "NotFound"
}

const find = (id: string): Effect.Effect<number, NotFound> =>
  id === "1" ? Effect.succeed(1) : Effect.fail(new NotFound())

// The error channel says NotFound can happen. A cast erases it.
const quiet = find("2") as unknown as Effect.Effect<number, never>

// And a parsed body still takes any type you name.
type User = { email: string }
const user = JSON.parse("{}") as User

console.log(Effect.runSyncExit(quiet)._tag, user.email)

Glyph로 쓴 같은 함수는 Result를 반환하고, 작성할 캐스트가 없습니다. 두 번째 모듈은 TypeScript가 생성되기 전에 거부됩니다.

find.glyph: 빌드되고 tsc --strict를 통과 
module find

pub type NotFound = { id: string }

pub fn find(id: string) -> Result<number, NotFound> {
  return match id == "1" {
    true => Ok(1),
    false => Err({ id: id }),
  }
}
캐스트 추가: 거부됨 
module find

pub type NotFound = { id: string }

pub fn find(id: string) -> Result<number, NotFound> {
  return match id == "1" {
    true => Ok(1),
    false => Err({ id: id }),
  }
}

pub fn quiet() -> number {
  let n = find("2") as number
  return n
}

E0013의 도움말은 이렇습니다: "Glyph has no as cast ... to turn an unknown into a type, validate it with T.parse(v) or narrow it with match and is." Effect 코드베이스에서도 lint 규칙으로 이에 가깝게 만들 수 있으며, 누군가 끌 수 있는 규칙이 왜 다른 종류의 보장인지는 이 비교에서 다룹니다.

라이브러리는 할 수 없고 Glyph는 하는 것

무엇을 작성할 수 있는지는 언어가 정합니다. Glyph에는 any, 캐스트, non-null 단언, 오류를 덮는 주석이 없고, 유니언에 대한 모든 match는 모든 case를 다뤄야 합니다. 레코드와 유니언은 선언에서 생성된 런타임 검사를 가지므로 json.parse<User>(body)가 검증을 합니다. Effect의 Schema도 하나의 기술에서 타입을 만들어 내므로(소개 문서의 Schema.Schema.Type<typeof Person>), 거기서도 타입과 검증기가 어긋나지 않습니다. 다른 점은 TypeScript에서는 코드베이스가 그것을 쓰도록 강제하는 것이 없다는 것입니다. 컴파일러는 또한 변경이 무엇을 깨뜨릴지 같은, 프로그램에 대한 에이전트의 질문에 MCP나 명령줄로 답합니다.

이 페이지에서는 Glyph 모듈 안에서 Effect를 쓰는 것을 테스트하지 않았으므로, 둘을 함께 쓰는 것에 대해서는 아무 주장도 하지 않습니다.
