설계 · 비교

왜 ReScript, Gleam, Elm이 아닌가요?

셋 다 JavaScript로 컴파일되는 타입 언어이고, 셋 다 Glyph보다 오래되었고, 더 널리 쓰이며, 더 안정되어 있습니다. 새 코드베이스에 쓸 언어를 고르는 중이고 TypeScript에 가까이 있을 필요가 없다면 이 언어들을 먼저 살펴볼 만합니다. Glyph의 차이는 더 좁습니다. JavaScript가 아니라 TypeScript 소스를 생성하고, npm 패키지를 그 패키지 자체의 .d.ts로 타입을 붙여 import하며, 타입에서 런타임 검증기를 생성하고, 컴파일러가 에이전트를 위해 영향 범위 쿼리에 답합니다.

각 언어가 스스로를 소개하는 방식

ReScript 홈페이지는 "JavaScript Made Simple for Humans and AI"와 "Types > Vibes"를 첫 문구로 내세우고, "compiles to clean, efficient JavaScript"이며 "No any, no magic types, no surprise undefined."라고 말합니다. "automatically generate TypeScript types" 기능도 제공합니다(rescript-lang.org).

Gleam 홈페이지는 스스로를 "a friendly language for building type-safe systems that scale"이라 부르며 "No null values, no exceptions, clear error messages"를 내세웁니다. Erlang VM에서 실행되며 "can additionally compile to JavaScript", 그리고 "also generates TypeScript definitions"라고 합니다(gleam.run).

Elm 홈페이지는 "reliable web applications"를 위한 "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions"라고 소개하며, Elm이 "detects all API changes automatically"하여 "guarantee that every single Elm package follows semantic versioning"한다고 말합니다(elm-lang.org).

이 인용문은 2026-11-19에 확인했습니다.

Glyph가 다르게 하는 것

아래 내용은 모두 이 페이지를 위해 Glyph 0.1.149에서 실행했습니다.

TypeScript 소스를 생성합니다

glyph build는 모듈마다 .ts 파일 하나를 쓰고, tsc --strict가 이를 검사하며, Glyph를 그만 쓰더라도 그 파일은 남습니다. ReScript와 Gleam은 JavaScript를 생성하고 그 옆에 타입 정의를 만듭니다. 생성된 TypeScript는 TypeScript 페이지에서 볼 수 있습니다.

npm 패키지를 그 패키지 자체의 선언으로 타입을 붙여 import합니다

모듈은 패키지를 이름으로 import하고, 패키지의 .d.ts가 모든 사용처에 타입을 붙입니다. 먼저 작성해야 할 바인딩이 없습니다. ReScript에서는 "external is the primary ReScript feature for bringing in and using JavaScript values"이며(external), 타입은 ReScript 쪽에서 선언합니다. Gleam의 external에는 타입 표기가 필요하고, 컴파일러는 "cannot verify that the function implemented in the other language returns the specified types"라고 합니다(externals). Elm은 flag, port, 커스텀 엘리먼트를 통해 JavaScript와 통신합니다(interop). pg와 @types/pg를 설치하면 다음 코드는 거부됩니다.

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

코드가 TS2322인 것은 라이브러리의 값을 검사하는 것이 tsc이고, 그 결과를 Glyph 줄에 다시 매핑하기 때문입니다. Glyph 자체 검사기는 이를 보지 못하므로 glyph check --no-tsc, 에디터, MCP 도구는 이 오류를 놓칩니다(G257). .d.ts에서 가져온 타입에는 런타임 검사도 없습니다.

타입에서 검증기를 생성합니다

모든 레코드와 유니언은 선언에서 생성된 런타임 검사를 가지므로, 데이터가 맞지 않으면 json.parse<User>가 Err를 반환합니다. Elm에서는 모양마다 디코더를 작성하며, 가이드에도 "the decoders people write end up working as a validation phase"라고 적혀 있습니다(JSON).

main.glyph: JSON에 email이 없으므로 "refused"를 출력 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

컴파일러가 변경이 무엇을 깨뜨릴지 답합니다

편집하기 전에 에이전트는 변경이 어느 곳에 영향을 미치는지 MCP(glyph_impact)나 glyph query impact로 물어볼 수 있습니다. 망라적인 match 하나와 else로 끝나는 것 하나가 있는 유니언 Plan = Free | Pro | Team에 대해 새 variant를 물으면, 위치마다 답이 나옵니다.

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

두 번째 위치는 변경 후 컴파일에 실패하며, 이는 변경을 하고 나면 이 컴파일러들 모두가 알려 줄 것입니다. 첫 번째 위치는 계속 컴파일되면서 새 case를 else로 보내고, 그것을 짚어 주는 것이 이 쿼리입니다. 다른 도구는 에이전트 개발자를 위한 안내에 나와 있습니다.

이 페이지가 주장하지 않는 것

오류 메시지, 컴파일 속도, 런타임 성능은 비교하지 않았고, 세 언어 중 어느 것도 Glyph에서 호출하거나 반대로 호출해 보지 않았습니다. 인용문은 각 프로젝트를 그 프로젝트 자신의 말로 설명한 것입니다. 각자 그 말에 얼마나 부합하는지는 여러분이 확인할 몫이며, 근거 페이지에 있는 Glyph 자신의 주장도 마찬가지입니다.
