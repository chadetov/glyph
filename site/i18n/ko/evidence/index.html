근거

이 사이트의 각 주장을 검증하는 방법

Glyph가 무언가를 잡아낸다는 주장은 저장소에 있는 프로그램 한 쌍입니다. 하나는 TypeScript, 하나는 Glyph이고, CI 게이트가 변경이 있을 때마다 둘 다 실행합니다. TypeScript가 컴파일되지 않거나 Glyph가 거부하지 않게 되면 빌드가 실패합니다. 어떤 사례든 명령 두 개로 직접 실행해 볼 수 있습니다.

fixture

catches/ 아래의 각 디렉터리에는 ts.ts, glyph.glyph, 그리고 각각이 무엇을 하는지 적은 case.toml이 있습니다. scripts/check_catches.py는 CI에서 실행됩니다. 컴파일되지 않는 TypeScript 프로그램은 아무것도 증명하지 못하므로 모든 ts.ts가 tsc --strict를 통과해야 하고, Glyph 쪽은 사례의 종류에 따라 검사합니다. {{catches:breakdown}} 게이트가 검사하는 종류별로 보면 다음과 같습니다.

종류사례게이트가 Glyph 쪽에 요구하는 것
refused{{catches:refused-all}}case.toml에 적힌 코드로 빌드가 실패함
warned{{catches:warned-all}}빌드는 통과하고 그 코드를 경고로 보고함
boundary{{catches:boundary-all}}프로그램이 실행되고, 경계의 검사가 잘못된 데이터를 Err로 바꿈
runtime{{catches:runtime-all}}프로그램이 빌드된 뒤, 실행 중에 명시된 출력과 함께 멈춤
gap{{catches:gap-cases}}Glyph가 프로그램을 받아들이고 잘못 동작함. 구멍이 막히면 게이트가 실패하고 사례를 옮기라고 알려 줌

더 이상 시연할 수 없게 된 사례는 완화하지 않고 삭제하며, catches README에 삭제된 여섯 개와 그 이유가 나와 있습니다. 그중 하나는 tsc도 잡아내는 것으로 밝혀졌고, 다른 하나는 TypeScript 쪽이 값을 any로 받았기 때문에 성립했던 것입니다.

비교 대상인 TypeScript

각 사례에는 최대한 설정한 TypeScript 프로젝트라면 그 실수를 잡았을지도 적혀 있고, "TypeScript가 잡을까" 태그는 여기서 나옵니다. "최대한 설정"이란 tsc --strict에 더 엄격하게 만드는 모든 옵션을 더하고, typescript-eslint를 실행하는 것입니다. 게이트는 실행할 때마다 패키지(TypeScript 6, eslint 9, typescript-eslint 8, tsx 4, 최신 @types/node)를 새로 설치하며, 네트워크가 없으면 건너뛰지 않고 실패합니다.

strict 위에 더한 tsconfig 옵션 
noUncheckedIndexedAccess: true
noFallthroughCasesInSwitch: true
noUnusedLocals: true
noUnusedParameters: true
noImplicitReturns: true
noImplicitOverride: true
allowUnreachableCode: false
allowUnusedLabels: false
exactOptionalPropertyTypes: true
noPropertyAccessFromIndexSignature: true
eslint.config.mjs 
export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.strictTypeChecked,
  { rules: {
    "@typescript-eslint/switch-exhaustiveness-check": "error",
    "@typescript-eslint/strict-boolean-expressions": "error",
    "@typescript-eslint/require-array-sort-compare": "error",
    "require-atomic-updates": "error",
  } },
);

사례의 태그는 none, 또는 flag:와 그 실수를 보고하는 옵션 하나, 또는 lint:와 규칙입니다. 수정된 프로그램도 관련 없는 이유로 규칙에 걸리면 그 사례에는 ts_ok.ts가 있고, 태그는 실수에 대해 발생하는 것만 셉니다. 예를 들어 non-exhaustive-match는 lint:switch-exhaustiveness-check입니다. 그 규칙을 켜면 typescript-eslint가 잡아내고, 페이지에도 그렇게 적혀 있습니다.

이 사이트의 코드 조각은 컴파일됩니다

scripts/check_docs_compile.py는 CI에서 실행되며, 사이트에서 독립적으로 완결된(module로 시작하고 무언가를 선언하는) 모든 Glyph 코드 조각과 문서 및 llms.txt의 코드 조각을 컴파일합니다. 실패하도록 의도한 코드 조각은 자신이 일으키는 오류를 명시해야 하고, 정확히 그 오류만 일으켜야 합니다. React나 npm 패키지가 필요한 코드 조각은 그 패키지의 실제 타입으로 컴파일합니다. 단편 코드는 세어서 건너뛰고, 건너뛴 비율이 보이도록 그 수를 출력합니다.

아직 잡아내지 못하는 것

gap 사례 {{catches:gap-cases}}건은 각각의 gap 번호와 함께 잡아내는 것 페이지에 있습니다. Glyph로 앱을 만들면서 발견한 모든 gap은 목록인 docs/dogfooding-gaps.md에 있습니다. 여기서는 대괄호 표시만이 현재 상태를 나타내며([FIXED], [HALF FIXED], 열린 항목은 표시 없음), 열린 항목이 마지막으로 재현된 지 릴리스 다섯 개가 넘으면 scripts/check_gaps.py가 CI를 실패시킵니다.

릴리스에 Breaking 표시를 붙이는 방법

이전 버전이 받아들이던 프로그램을 거부하는 릴리스에는 Breaking 표시를 붙입니다. 이는 영향받는 가장 작은 프로그램을 작성해 이전에 배포된 릴리스와 새 바이너리에서 실행하고 종료 코드를 비교해서 결정합니다. 릴리스 노트의 문구에서 추론하지 않습니다. 0.1.99 이전 릴리스는 이렇게 검사한 적이 없으므로, 표시가 없는 릴리스는 안전하다는 뜻이 아니라 검사하지 않았다는 뜻입니다. 기록은 버전 페이지에 있습니다.
