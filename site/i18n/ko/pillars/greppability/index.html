기둥 02 · 핵심

검색 용이성

이름 하나에 위치 하나. 모든 심볼은 선언된 자리에서 문법 형태가 정확히 하나이므로, 평범한 grep이 언제나 정의를 찾습니다. 인덱스도, 언어 서버도, 운도 필요 없습니다.

"이건 어디에 정의되어 있지?"가 어려운 이유

성숙한 TypeScript 코드베이스에서는 가장 단순한 질문인 이 이름은 어디서 왔는가?가 가장 어려운 경우가 많습니다. 언어가 심볼 하나를 여러 곳에 흩어 놓는 방법을 여섯 가지쯤 제공합니다. 오버로드는 함수를 여러 시그니처로 나누고, 데코레이터는 함수를 다른 것으로 감싸고, namespace와 interface 병합은 타입을 여러 파일에 흩어 놓고, declare module은 소유하지 않은 코드를 확장하고, barrel index.ts 파일은 모든 것을 재export해서 import하는 경로가 실제로 무언가가 있는 곳이 아니게 만듭니다.

사람은 LSP와 손에 익은 습관으로 버팁니다. 에이전트는 grep합니다. 저장소를 텍스트로 읽는데, 이런 구문 하나하나가 코드가 어디 있는지에 대해 텍스트가 거짓말하는 곳입니다. Glyph는 이것들을 없앱니다. 그 결과 검색이 휴리스틱이 아니라 믿을 수 있는 기본 도구인 언어가 됩니다.

01 선언 하나, 형태 하나

함수, 타입, 컴포넌트는 한 가지 문법으로 정확히 한 번 선언합니다. 시그니처를 나누는 오버로드도, 이름을 다시 선언하는 방법도 없습니다. 이름이 같은 최상위 항목 두 개는 강한 오류(E0100)입니다. 그래서 정의를 찾는 검색에는 답이 정확히 하나입니다.

TypeScript: 결과 네 개, 그중 하나가 본문 $ grep -n "parseUser" src/ 
users.ts:4:  export function parseUser(
users.ts:9:  export function parseUser(
index.ts:2: export { parseUser } from
api.ts:7:   import { parseUser } from
Glyph: 첫 번째 결과가 정의 $ grep -n "fn parseUser" src/ 
users.glyph:12:fn parseUser(
  raw: unknown,
) -> Result<User, string> {

선언 키워드가 검색하는 이름의 일부입니다. grep "fn parseUser"는 호출, import, 재export에는 매칭될 수 없고, 오직 정의된 한 곳에만 매칭됩니다.

02 barrel 파일 없음: import 경로가 곧 위치

Glyph의 import는 절대 재export하지 않으며, import만 담은 모듈은 거부됩니다(E0102). index.ts로 출처를 세탁하는 계층이 없습니다. 그래서 import는 심볼이 실제로 있는 모듈을 가리킵니다. 경로가 곧 주소입니다.

import가 어디를 봐야 하는지 정확히 알려 줍니다 
import myapp/users { parseUser }
//     ^^^^^^^^^^^ the file is src/myapp/users.glyph.
//     not a re-export of a re-export of a barrel.

03 동작을 숨겨서 붙이는 방법 없음

함수를 보이지 않는 계층으로 감싸는 데코레이터도, 트리 곳곳의 멤버를 모으는 namespace 병합도, 열어 볼 생각도 못 할 파일에서 서드파티 타입을 확장하는 declare module도, 메서드가 가리키는 대상을 바꾸는 암묵적인 this도 없습니다. 이름은 선언 하나로 해석되고, 그것을 형성하는 모든 것은 그 선언에서 보입니다.

04 변경도 grep할 수 있습니다

검색 용이성은 정의를 찾는 것만이 아니라 효과를 찾는 것이기도 합니다. 공유 상태는 std/store에 있고, 그에 대한 모든 변경은 .set(이나 .update( 호출 그대로입니다. 그래서 파일 곳곳에 흩어진 대입을 찾아다니는 대신 검색 한 번으로 상태 하나의 쓰기 창구 전체를 나열할 수 있습니다.

$ grep -rn 'tasks\.\(set\|update\)' src/ 
src/tasks.glyph:16:  tasks.update(fn(cur) { ... })
src/tasks.glyph:24:  tasks.set([])
# every place the task list can change, enumerated.
# nothing hides in an ordinary `x = ...` elsewhere.

코드베이스의 텍스트가 구조에 대해 사실을 말할 때 grep할 수 있습니다. 여기 있는 모든 제약(이름마다 형태 하나, 재export 없음, 병합 없음)은 검색이 단서가 아니라 답을 돌려주게 하려고 있습니다.

벤치마크: 준비 중

이 주장을 측정할 수 있는 형태는 정밀도입니다. 어떤 심볼에 대해 평범한 grep 결과 중 실제로 찾던 것의 비율은 얼마이고, 에이전트가 정의에 닿기까지 몇 단계가 걸리는가. Glyph는 아직 실제 환경에서 쓰이지 않으므로 아래 차트는 자리 표시이며, 측정할 실제 코드베이스가 생기면 실제 숫자로 채워집니다.

효과는 규모와 자율성에 따라 커집니다. 사람은 코드베이스의 숨은 곳을 배우지만, 처음 보는 에이전트는 그렇지 않습니다. 검색 용이성 덕분에 도구(또는 새 팀원)가 저장소를 실제 모습 그대로 읽으며 탐색할 수 있습니다.

"lint 규칙으로 오버로드와 데코레이터를 금지할 수 있다"

자기 저장소에서는 그렇습니다. ESLint로 네임스페이스를 금지할 수 있고, 팀이 오버로드를 쓰지 않기로 합의할 수 있습니다. 그래도 언어는 여전히 이 모든 것을 허용하므로, 보장은 설정이 유지되는 동안만 유효하고 설정이 실행되는 코드에만 적용됩니다. 의존성, 생성된 파일, 다른 사람의 저장소에 대한 grep은 이에 기댈 수 없습니다. Glyph에는 이런 구문이 존재하지 않으므로, 팀의 누구도 설정하지 않은 파일을 포함해 모든 Glyph 파일에서 grep이 똑같이 동작합니다.

에이전트 입장에서 이것이 어떻게 보이는지, 즉 검색 한 번으로 정의나 값에 대한 모든 쓰기를 찾는 것은 에이전트가(또는 내가) 무엇이 어디에 정의되어 있는지 찾을 수 있나요?에서 답합니다.
