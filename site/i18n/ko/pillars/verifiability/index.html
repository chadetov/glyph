기둥 01 · 핵심

검증 가능성

Glyph는 에이전트가 빠지는 구멍을 막습니다. 작성할 수 있는 any도 as도 없고, match는 망라적임이 증명되며, 선언한 타입에는 엄격한 런타임 검증기가 붙고, 이 모두가 tsc 위의 엄격한 계층으로 강제됩니다. 모든 것을 직접 검증하지는 않으며, 보장이 정확히 어디서 멈추는지 아래에 솔직하게 적어 두었습니다.

타입이 할 수 있는 거짓말

TypeScript에서 타입은 코드가 실행되기 전에 사라지는 컴파일 시점의 약속입니다. User 표기는 지워져 아무것도 남지 않고, 네트워크 호출, JSON 파싱, 폼 필드에서 실제로 받는 객체는 어떤 모양이든 될 수 있습니다.

더 나쁜 것은 언어가 이에 대해 검사기에게 거짓말할 합법적인 방법 세 가지를 준다는 점입니다. any, as 캐스트, non-null !입니다. 빠르게 일하는 에이전트는 셋 다 꺼내 쓰고, 버그가 배포되는 동안 tsc --strict는 통과 상태를 유지합니다.

Glyph의 첫 번째 일은 이 구멍들을 막는 것입니다. 표기를 더하는 것이 아니라, 탈출구를 없애고 모든 타입이 증명을 런타임까지 가지고 가게 해서입니다. 보장을 하나씩 보면 다음과 같습니다.

01 any가 없습니다

Glyph에는 이것이 없습니다. 최상위 타입은 unknown이고, unknown은 무력합니다. 그것이 무엇인지 증명하기 전까지는 호출하거나, 인덱싱하거나, 타입이 있는 곳에 넘길 수 없습니다.

자세히 any 하나가 그렇게 비싼 이유

any는 TypeScript에서 가장 비싼 키워드입니다. 값 하나와 그 값이 닿는 모든 것에 대해 타입 시스템을 꺼 버립니다. 경계에 있는 any 하나가 그 아래의 호출 그래프를 조용히 오염시킵니다.

컴파일러가 볼 수 있는 검사 없이는 unknown에서 타입이 있는 값을 꺼낼 수 없습니다. Glyph에서는 좁히기가 곧 런타임 증명입니다. 이를 건너뛰는 문법은 없습니다.

02 타입은 런타임에도 실재합니다

User.parse는 어떻게 존재할까요? 모든 레코드 타입과 제네릭이 아닌 모든 태그 유니언이 런타임 디스크립터를 함께 생성하기 때문입니다. is 가드, unknown을 Result로 검증하는 parse, 조합할 수 있는 schema입니다.

작성하는 타입과, 그로부터 생성되는 디스크립터 
type User = {
  id: number,
  name: string,
  email: string,
}

// generated: User.is(v), User.parse(v) -> Result<User, ...>, User.schema

fn create(req: Request) -> Result<Response, string> {
  return match User.parse(req.body) {   // untrusted input, validated
    Ok(user) => Ok(json(201, user)),
    Err(issues) => Ok(json(400, issues)),
  }
}

"API마다 직접 작성한 검증기가 필요하다"에 대한 답이 이것입니다. 타입이 곧 검증기입니다.

자세히 디스크립터가 검사하는 것

레코드의 모양은 가정되는 것이 아니라 런타임에 실제로 검사되므로, is User 검사는 지워지는 무동작이 아니라 실제 검사입니다.

경계(요청 본문, 설정 파일, 서드파티 응답)는 잘못된 데이터를 실제로 거부할 수 있는 검사를 통과해야만 타입을 얻습니다.

한계: 레코드의 디스크립터는 기본적으로 엄격합니다. 선언된 필드를 확인하고, 선언되지 않은 키를 가진 값은 거부합니다(추가 키를 허용하려면 타입에 @open을 붙입니다). 레코드 타입은 제네릭을 포함해 디스크립터를 가지므로, Paginated<User>는 각 요소를 User로 검사하고, 태그 유니언의 디스크립터는 태그를 검사한 다음 그 variant의 payload 필드를 검사합니다.

아직 디스크립터가 없는 것은 제네릭 태그 유니언(Box<T> = Empty | Full({ value: T })에는 Box.parse가 없습니다)과, 참조만 하는 .d.ts에서 import한 타입입니다. 검사가 모양의 일부만 증명할 수 있는 곳에서는, 컴파일러가 할 수 없는 보장을 암시하는 대신 그렇다고 말합니다.

03 모든 case를 다루거나, 컴파일되지 않거나

봉인된 유니언에 대한 match는 모든 variant를 처리해야 합니다. 나중에 variant를 추가하면 그것을 고려하지 않은 모든 match가 컴파일되지 않습니다(E0200).

status.glyph 
type Status = Active | Paused | Cancelled

fn label(s: Status) -> string {
  return match s {
    Active => "on",
    Paused => "hold",
    // forgot Cancelled...
  }
}
런타임 undefined가 아니라 컴파일 오류 $ glyph build 
[E0200] non-exhaustive match on
`Status`: missing variant `Cancelled`

# the equivalent TS switch returns
# undefined at runtime and compiles
# clean. here it does not build.
E0200E0218
자세히 숫자와 문자열 match

잊힌 switch 분기처럼 새 case가 조용히 undefined로 빠질 수 없습니다. 유니언만이 아닙니다. number나 string을 리터럴 값으로 매칭하면 else가 필요합니다(E0218). 그 정의역은 끝이 없어서 리터럴 집합으로는 결코 완전해질 수 없기 때문입니다.

04 오류는 놀랄 일이 아니라 값입니다

실패할 수 있는 함수는 Result<T, E>를 반환합니다. match로 처리하거나 ? 연산자로 전달하며, 오류 타입이 맞아야 합니다(불일치를 숨기는 암묵적 변환은 없습니다).

pipeline.glyph 
fn load(id: string) -> Result<User, AppError> {
  let raw = fetch_user(id)?           // Err short-circuits to the caller
  let user = User.parse(raw.body)?    // validation Err propagates too
  return Ok(user)
}

fn main() -> number {
  save(user)   // E0217: this returns a Result whose Err is dropped
  return 0
}

Result를 완전히 무시하면(효과를 위해 호출하고 반환값을 버리면) Glyph가 경고합니다(E0217). 버려진 오류는 삼켜진 실패이기 때문입니다. 경고는 let _ = ...로 의도적으로만 끌 수 있고, 실수로 꺼지는 일은 없습니다.

05 개인정보도 타입 수준입니다

"관례가 아니라 컴파일러의 일로 만든다"는 같은 원칙이 민감한 데이터까지 이어집니다. 타입에 @redact를 붙이면 디스크립터에 그 필드를 가리는 redact()가 생기므로, 무심코 쓴 json.stringify(User.redact(u))가 그 필드를 유출할 수 없습니다.

patient.glyph 
@redact fields: [diagnosis, notes]
type Patient = {
  name: string,
  diagnosis: string,
  notes: string,
}

// json.stringify(Patient.redact(p)) ->
// {"name":"Ada","diagnosis":"[REDACTED]","notes":"[REDACTED]"}

타입에 없는 필드를 지정하면 아무것도 보호하지 않는 마스킹이 아니라 컴파일 오류(E0219)입니다.

다섯 가지 실패 방식(검사하지 않은 입력, 놓친 case, 버려진 오류, 유출된 비밀 값, 검증하지 않은 키)이 있고, 모두 고치는 방식의 모양이 같습니다. 컴파일러는 그런 척하기를 거부합니다.

강제하는 방식, 그리고 보장이 멈추는 곳

차이가 중요하므로 정확히 말하겠습니다. Glyph는 독립적인 검증기가 아니라 tsc 위의 엄격하고 강제되는 방언입니다.

  • Glyph가 증명일부는 직접 증명합니다. 망라성, ? 오류 타입, 소스에 any/as가 없다는 것, 엄격한 키 검증입니다.
  • tsc를 통해 강제나머지 타입 호환성은 TypeScript를 생성하고 빌드를 실패시키는 tsc --strict를 실행해서 강제합니다.

핵심은 Glyph가 타입 검사기를 다시 구현한다는 것이 아니라, 이 검사들이 에이전트가 끌 수 있는 선택적 lint가 아니라 언어라는 것입니다.

이력 0.1.10에서 막힌 한계, 깊은 제네릭 검증

여기 있던 이전의 한계 두 가지는 0.1.10에서 막혔습니다. emitter는 예전에 모든 제네릭 함수에 tsc가 아니라 Glyph가 검사하는 반환 캐스트를 넣었습니다. 이제는 검증기 조합자가 모양에서 파생된 타입(infer_output<Shape>)의 값을 만드는 곳에서만 넣으며, 정직한 제네릭은 모두 캐스트 없이 생성됩니다. 그리고 검증기의 출력 타입을 더 이상 그냥 믿지 않습니다. infer_output이 넘긴 모양에서 그 타입을 끌어내고 tsc가 여러분의 타입 표기를 그에 대해 검사하므로, 주장하는 타입의 필드가 빠진 모양은 이제 컴파일에 실패합니다.

제네릭 타입도 이제 깊게 검증됩니다. Paginated<User> 디스크립터는 모든 요소가 있는지만이 아니라 User로서 검사합니다.

한계가 하나 남아 있으며, 분명히 밝혀 둡니다. 참조만 하는 외부 .d.ts에서 import한 타입은 glyph gen dts로 실체화하기 전까지 디스크립터가 없으므로, 그 타입의 필드는 모양이 아니라 존재 여부만 검사됩니다. 이 경계는 의도한 것이며(Glyph가 생성하지 않은 타입은 런타임 검증을 약속할 수 없습니다), 실체화하면 막힙니다.

벤치마크: 준비 중

이 주장은 경험적인 것이므로 측정할 계획입니다. 에이전트가 작성한 실제 변경 모음을 각각 tsc --strict와 Glyph로 실행하고, 각각이 실제로 무엇을 잡는지 세는 것입니다.

Glyph는 아직 실제 환경에서 쓰이지 않으므로 보고할 숫자가 없습니다. 아래 차트는 자리 표시이며, 실제 사용이 생기는 순간 실제 데이터로 채워집니다.

아직 측정하지 않음 방법론은 정해졌고, 코퍼스는 실제 Glyph 사용에서 가져와야 합니다. 숫자가 나오는 대로 (그것이 무엇이든) 여기에 공개하겠습니다.

이 중 어느 것도 번거로운 의식을 대가로 얻는 것이 아닙니다. 증명 표기도, 계약도, 만족시켜야 할 검증기도 없습니다. 위의 코드는 평범한 Glyph일 뿐입니다. 검증 가능성은 켜는 기능이 아니라, 거짓말할 방법이 사라지고 나면 남는 것입니다.

"strict TypeScript와 lint 설정이면 된다"

프로그램 안에서는 거의 그렇습니다. strict, noUncheckedIndexedAccess, 그리고 명시적 any를 금지하는 규칙이 에이전트가 빠져나갈 것의 대부분을 잡습니다. 하지만 가장자리에서 멈춥니다.

  • 경계에서JSON.parse(body) as User는 어떤 설정에서든 컴파일되며, 흔한 해결책인 zod 스키마는 첫 번째와 직접 맞춰 둬야 하는 User의 두 번째 기술입니다. Glyph에서는 타입이 곧 검증기입니다. json.parse<User>(body)는 User 자체에 대해 검사되고, Glyph가 런타임에 검사할 수 없는 타입은 믿는 대신 거부됩니다.
  • 저장소를 넘어서다른 차이는 누가 이에 기댈 수 있느냐입니다. lint 설정은 저장소 하나가 내린 선택입니다. 낯선 TypeScript 코드베이스를 연 에이전트는 거기서 any가 금지되어 있다고 가정할 수 없습니다. Glyph에서는 어디서도 쓸 수 없습니다.

같은 보장을 에이전트가 저지르는 실수와 그것을 막는 오류의 관점에서 본 답은 에이전트가 내 코드를 조용히 깨뜨리는 것을 무엇이 막아 주나요?에 있습니다.
