여기서 시작하기 · 약 10분

첫 번째 Glyph 프로그램

프로젝트를 만들고 실행한 다음, 일부러 깨뜨리고 컴파일러가 내는 오류를 읽어 봅니다. Glyph에 대한 사전 지식은 필요 없습니다. TypeScript를 조금이라도 써 봤다면 모든 줄을 따라갈 수 있습니다.

1 · 프로젝트 만들기

Glyph는 macOS와 Linux(x64, ARM), Windows(x64)용으로 미리 빌드된 바이너리로 npm에 배포되며, Node 18 이상이 필요합니다. 이 방법은 전역으로 아무것도 설치하지 않습니다. npx가 프로젝트를 만들기 위해 컴파일러를 받아 오고, 프로젝트는 Glyph가 실행과 타입 검사에 쓰는 tsx, typescript와 함께 자체 컴파일러 버전을 고정합니다.

터미널 
npx -y @glyphlang/glyph init hello
cd hello
npm install

glyph를 PATH에 두고 싶다면, Glyph가 함께 쓰는 두 도구와 함께 전역으로 설치하고 이 페이지의 명령에서 npx를 빼세요.

터미널, 전역 설치를 쓰는 방법 
npm install -g @glyphlang/glyph tsx typescript
glyph doctor                    # confirms your toolchain is ready
glyph init hello
cd hello

2 · 생성된 파일 살펴보기

glyph init은 바로 실행할 수 있는 시작 프로젝트를 만듭니다. src/main.glyph, 타입이 있는 npm 패키지는 여기에 아무것도 필요 없고 이 디렉터리는 타입을 제공하지 않는 패키지를 위한 곳이라고 설명하는 src/.types/README.md, package.json, .gitignore, 그리고 코딩 에이전트가 스스로 읽는 파일 두 개입니다. 전체 언어 레퍼런스를 위해 glyph llms를 가리키는 AGENTS.md와, 에이전트가 타입과 참조를 검색하는 대신 컴파일러에 물어볼 수 있도록 glyph mcp를 등록하는 .mcp.json입니다. 이미 있는 프로젝트에서는 glyph agents가 이 두 파일을 작성합니다. package.json은 컴파일러, typescript, tsx를 devDependencies에 고정하므로, 프로젝트를 클론한 사람은 누구나 전역 설치 없이 npm install만으로 빌드할 수 있습니다.

src/main.glyph를 열어 보세요. hello-world 프로그램입니다.

src/main.glyph 
module main

import std/io

fn main(argv: Array<string>) -> number {
  io.println("hello from glyph")
  return 0
}

눈여겨볼 점이 두 가지 있습니다. 프로그램은 main(argv)를 실행하고, main은 프로세스 종료 코드인 number를 반환합니다. 반환하면 프로세스를 강제로 멈추지 않고 종료 코드만 설정하므로, 서버를 시작하는 프로그램은 계속 요청을 처리합니다.

3 · 실행하기

터미널 
npx glyph run
hello from glyph

glyph run은 코드를 타입 검사하고, TypeScript로 컴파일하고, 실행했습니다. 이 페이지의 나머지 부분에서 반복할 루프가 바로 이것입니다.

4 · 실제 코드 추가하기

이제 본문을 중요한 결정으로 바꿔 봅니다. 결제 상태에 따라 주문을 발송할지 정하는 것입니다. 여기서 계속 쓰게 될 두 가지가 등장합니다. 태그 유니언(type Payment = ...)과, Glyph의 유일한 조건문인 match입니다.

src/main.glyph 
module main

type Payment = Pending | Paid | Failed

fn ship(p: Payment) -> string {
  return match p {
    Pending => "hold: waiting for the money",
    Paid => "ship it",
    Failed => "hold: payment failed",
  }
}

fn main(argv: Array<string>) -> number {
  print(ship(Paid))
  return 0
}
터미널 
npx glyph run
ship it

5 · 일부러 깨뜨리기

이 부분이 Glyph가 무엇을 위해 있는지 보여 줍니다. 티켓에 "환불 지원"이라고 적혀 있으니 Payment에 Refunded를 추가하고 ship은 그대로 둡니다. 에이전트가 한 파일에서 타입을 바꾸고, 그 타입으로 판단하는 코드는 열어 보지도 않을 때 하는 일이 바로 이것입니다. 다시 실행해 봅니다.

src/main.glyph (단어 하나 추가) 
type Payment = Pending | Paid | Failed | Refunded
$ npx glyph run 
[E0200] Error: typecheck: non-exhaustive match on `Payment`: missing variants `Refunded`
    ╭─[ main:6:10 ]
    │
  6 │ ╭─▶   return match p {
    ┆ ┆
 10 │ ├─▶   }
    │ ╰───────── non-exhaustive match on `Payment`: missing variants `Refunded`
    │
    │     Help: Add an arm for each missing variant.
────╯

실행되지 않았습니다. 대부분의 코드가 작성되는 TypeScript에서는 반대입니다. 두 가지 "hold" 경우를 처리하고 default: return "ship it"으로 끝나는 switch는 새 경우가 추가된 뒤에도 tsc --strict를 통과하고, 환불된 주문을 전부 발송합니다. 여기서는 경우를 빠뜨린 match가 모두 컴파일 오류가 되며, 안정적인 코드(E0200), 정확한 위치, 빠진 경우의 이름을 알려 줍니다. 자세한 설명이 필요하면 언제든 glyph --explain E0200을 실행하세요.

6 · 고치기

환불이 발송에 어떤 의미인지는 컴파일러가 정할 수 없습니다. 그건 여러분이 정할 일입니다. 암을 추가하면 다시 실행됩니다.

src/main.glyph 
fn ship(p: Payment) -> string {
  return match p {
    Pending => "hold: waiting for the money",
    Paid => "ship it",
    Failed => "hold: payment failed",
    Refunded => "hold: refunded, nothing to ship",
  }
}
터미널 (print(ship(Refunded))로 바꾼 경우) 
npx glyph run
hold: refunded, nothing to ship

이것이 핵심 루프입니다. 작성하고, 실행하고, 무언가 잘못되면 코드가 배포되기 전에 컴파일러가 무엇이 잘못됐고 어떻게 고치는지 정확히 알려 줍니다.
