22 · Pergunte ao compilador

Meu agente pode perguntar ao compilador o que é um símbolo antes de escrever código?

Em uma chamada. O glyph_symbol recebe o module::name que um diagnóstico já imprimiu, ou uma posição em um arquivo, e responde com os campos de um record e seus tipos, as variantes de uma union com seus payloads e a sintaxe que constrói cada uma, os parâmetros e o retorno de algo chamável, os membros de uma interface, e se um match sobre ele precisa ser exaustivo.

Por que isso importa

Um agente que precisa tratar um caso novo em uma union que ele não declarou tem que saber o que as variantes carregam. Ler a declaração significa achar o arquivo primeiro. A busca de símbolos dava a ele um nome e um intervalo de bytes, e a listagem de variantes dava ["Pending", "Paid", "Cancelled"]. A partir disso o agente escreve Paid("tx_1"), que não é a forma certa, e descobre por um diagnóstico. O compilador tinha o payload o tempo todo. A ferramenta o descartava uma linha antes da resposta.

É esse o padrão que a interface para agentes foi feita para eliminar: fatos que o compilador já calcula e memoiza, e que nenhuma ferramenta repassa. Uma auditoria de um projeto com três módulos encontrou o hover respondendo em duas de quatorze posições, e toda union chegando sem seus payloads.

Veja na prática

Um projeto com três arquivos, com OrderStatus declarado em orders.glyph. Consultado a partir de main.glyph, que não o importa:

glyph query symbol --path src/main.glyph --entity orders::OrderStatus 
{
  "entity": "orders::OrderStatus",
  "kind": "union",
  "pub": true,
  "type": "Pending | Paid({ transaction_id: string }) | Cancelled",
  "exhaustive_match": true,
  "variants": [
    { "name": "Pending",   "payload": null, "construct": "Pending",
      "payload_absent": "`Pending` is declared with no payload." },
    { "name": "Paid",      "payload": "{ transaction_id: string }",
      "construct": "Paid({ transaction_id: string })" },
    { "name": "Cancelled", "payload": null, "construct": "Cancelled",
      "payload_absent": "`Cancelled` is declared with no payload." }
  ],
  "fields": null,
  "fields_absent": "`orders::OrderStatus` is a union and declares no record fields.",
  "path": "src/orders.glyph",
  "range": { "start": { "line": 2, "character": 4 },
             "end":   { "line": 5, "character": 13 } },
  "origin": "glyph",
  "origin_detail": "`orders::OrderStatus` is declared in src/orders.glyph, a Glyph
    module this project holds, and the compiler parsed and resolved that declaration"
}

Resumido: a resposta também traz generics, parameters, returns, members, literals, owner, async e examples. Cada um deles é um par. Uma chave só é null junto com uma frase <key>_absent dizendo por quê, então um agente nunca precisa adivinhar se uma resposta ausente significa que o símbolo não tem aquilo ou que a ferramenta não olhou. Um const sem anotação não informa tipo nenhum por essa regra: o verificador de propósito não infere o tipo de uma declaração a partir do seu inicializador, então imprimir o tipo do inicializador diria a quem chama que os usos do nome são verificados contra algo que não verifica nada.

A segunda pergunta que um agente faz

Com a forma em mãos, a próxima coisa que ele quer saber é se o valor que tem pode ir onde ele está prestes a colocá-lo. O glyph_assignable consulta a própria comparação do verificador. Cada lado é um module::name ou um tipo escrito em Glyph, lido no escopo do arquivo que você indicar, e o veredito diz qual de três coisas aconteceu.

--from 'Nullable<int>' --to int 
{
  "verdict": "WILL_FAIL",
  "because": "the checker's own comparison
    refuses a `Nullable<number>` value where a
    `number` is declared, so every site that
    writes this pairing is a diagnostic",
  "diagnostics": [
    { "code": "E0204",
      "at": "an annotated `let` or `const`,
             and a `return`" },
    { "code": "E0211", "at": "a call argument" }
  ],
  "from": { "asked": "Nullable<int>",
            "form": "spelling",
            "read_as": "Nullable<number>" },
  "to":   { "asked": "int", "form": "spelling",
            "read_as": "number" }
}
--from 'Option<int>' --to 'Option<int>' 
{
  "verdict": "COMPATIBLE",
  "because": "two generic applications are
    compared by arity, by base and by argument,
    and every one of those pairings is itself
    accepted, so the checker accepts a
    `Option<number>` value where a
    `Option<number>` is declared. This is a rule
    accepting rather than a rule staying silent",
  "diagnostics": null,
  "diagnostics_absent": "the checker refuses
    nothing for this pairing, so no code is
    raised for it anywhere"
}

A palavra é COMPATIBLE, não SAFE, e a diferença vale uma frase. SAFE é a palavra do glyph_impact, e significa que um local específico continua correto depois de uma edição específica. Esta resposta é sobre dois tipos, sem local nem edição na pergunta. O terceiro veredito é UNDETERMINED, dado sempre que nenhuma regra cobre o par: dois tipos de função voltam assim, porque a relação por baixo compara os retornos e não diz nada sobre os parâmetros. O silêncio dela ali não é uma aceitação, e a ferramenta não vai relatá-lo como uma.

A outra direção: do que isto depende, e o que aquele módulo me oferece

O glyph_references responde quem usa um símbolo. O glyph_dependencies são as mesmas tabelas lidas pela outra ponta: do que uma declaração depende, todas as declarações que o código dela cita, divididas em CALLS, REFERENCES e FIELD_ACCESS, cada aresta trazendo as duas pontas e onde está. O glyph_exports responde o que um módulo deixa visível para quem o importa, a partir da própria consulta de exports do compilador e não de uma varredura: toda declaração pub e toda variante que uma union pub expõe, cada uma como uma entrada com sua identidade, tipo de declaração e assinatura. Um agente prestes a escrever um import pode perguntar o que há do outro lado em vez de abrir o arquivo.

Construir o espelho de uma relação foi o que pegou um bug na original. Toda aresta traz uma procedência, e PROVED deveria dizer que o compilador leu as duas pontas. Ela respondia PROVED para uma aresta que apontava para um módulo cujo parse falha, onde nada tinha sido lido. Agora responde UNDETERMINED com o motivo, e como glyph_references e glyph_impact chamam a mesma função, os dois estavam errados do mesmo jeito e os dois foram corrigidos.

Onze ferramentas, e nenhum cliente necessário

O glyph mcp oferece onze: glyph_symbol, glyph_impact, glyph_assignable, glyph_diagnostics, glyph_hover, glyph_definition, glyph_references, glyph_variants, glyph_symbols, glyph_dependencies e glyph_exports. Cada uma tem um verbo glyph query que recebe os mesmos argumentos como flags e imprime o mesmo JSON, passando pelo mesmo ponto de entrada que um cliente alcança, então um agente que só roda comandos de shell faz as mesmas perguntas. O glyph_diagnostics verifica um arquivo dentro do seu projeto e retorna o diagnóstico que o glyph check --json imprime, a partir do mesmo tipo Rust, com um teste que roda as duas interfaces em seis projetos e compara o JSON chave por chave. Todos os detalhes estão na página do MCP.

Tudo isso é perguntado antes de uma edição. Depois dela, o compilador responde na outra direção: o glyph check --agent imprime cada diagnóstico com os invariantes que uma edição de reparo precisa manter e a descrição glyph_symbol de cada símbolo citado, então a forma de que o agente precisa chega junto com o erro que a pediu. Isso tem uma página própria.

Situação atual

Disponível hoje

Onze ferramentas de leitura via MCP, cada uma com um verbo glyph query. O glyph_symbol responde por identidade ou por posição, e todo fato que ele não tem é null ao lado da frase dizendo por quê. A identidade chega à stdlib: o Result do prelude é std/result::Result, que é o módulo em que o resolver o registra e o módulo de onde o emissor escreve o import, então glyph query symbol --entity std/result::Result responde com Ok(T) e Err(E), glyph query exports --module std/result lista a interface, e um E0200 sobre ele traz essa identidade em cause. Não há código Glyph por trás, então path e range são null com esse motivo, em vez de ausentes. O hover responde em todas as quatorze posições que uma auditoria testou em um projeto com três módulos, contra duas antes de este trabalho começar: um nome declarado em outro módulo responde a partir da declaração desse módulo, então o binding do import, uma função importada em uma chamada, uma variante importada usada como valor e um campo lido de um record importado têm todos um tipo. glyph_dependencies e glyph_exports completam o conjunto que o G221 pedia. O glyph_variants traz cada payload e sua sintaxe de construção; glyph_definition e glyph_symbols trazem o module::name, então uma resposta se encadeia no glyph_impact sem recalcular nada. A tabela de tipos de assinatura do glyph_impact decide um contêiner contra um contêiner, um record estrutural contra um record estrutural ou declarado (local, importado, genérico ou um segundo nome), um elemento JSX como a chamada em que ele se transforma, e uma union de literais de string em qualquer lado com a mesma comparação que o glyph_assignable faz, então as duas ferramentas não podem discordar sobre um mesmo par. Um argumento cujo par a relação lê por inteiro é WILL_FAIL seja qual for o resultado da comparação, porque change_signature_type não nomeia um tipo substituto e um par aceito é um em que um substituto pode ser recusado; só um par que a relação recusa é UNDETERMINED.

Onde para

Nenhuma ferramenta aqui escreve: sem rename, sem edição aplicada. O lado da escrita é o glyph fix na linha de comando, e ele repara três coisas, não qualquer coisa que você peça: imports não usados, a cabeça de um braço para a qual o verificador tem exatamente uma sugestão, e um nome de campo a um caractere de exatamente um campo declarado. Um export da stdlib para o qual o compilador não modela nem declaração nem assinatura responde kind: null com o motivo: std/result::all e std/io::println são tipados em TypeScript que o compilador prepara e que nenhuma etapa do Glyph lê. O glyph_diagnostics pula três verificações que o glyph check faz: o tsc, a verificação E0104 de um import que não aponta para nenhum módulo, que precisa da visão que o build tem de node_modules, e o E0400 para um @example que falha, que precisa rodar o projeto gerado. Ele nomeia as três em not_run em vez de responder como se as tivesse feito.
