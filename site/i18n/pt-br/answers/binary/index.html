Consigo lidar com dados binários, ou tudo é string?

O std/bytes dá a você uma sequência imutável de octetos, e o std/fs e o std/crypto falam essa língua. Até a 0.1.78 não falavam: toda fronteira da biblioteca padrão recebia string e devolvia string, então não dava para ler um PNG nem passar uma chave de verdade para um HMAC.

Por que isso importa

Duas aplicações escritas de forma independente, um leitor de PNG e um autenticador, pararam nessa mesma frase na mesma semana. Nenhuma das duas conseguia contornar o problema dentro da linguagem.

  • Um arquivo lido como textoO primeiro byte de um PNG é 0x89, que sozinho não é UTF-8 válido. Leia esse arquivo como texto e todo byte que o decodificador não consegue interpretar vira U+FFFD, então o arquivo está corrompido antes de o seu programa vê-lo, e nada relata erro.
  • Uma chave passada por uma stringO mesmo acontece com uma chave: um segredo de HMAC é uma sequência arbitrária de octetos, e passá-lo por uma string o altera, então você calcula um MAC diferente do que a especificação manda, e todo teste que você escreveu contra o seu próprio código passa.

O que é um valor Bytes

Bytes é um Uint8Array em tempo de execução, então pode ser passado para qualquer API do host que receba um, sem desembrulhar.

As operações de sequência têm os nomes das equivalentes em std/array e std/string: len, get, slice, concat, index_of, starts_with. Nenhuma altera o argumento.

Toda decodificação pode recusar, e diz onde

Esta é a parte que mais custou construir e é o motivo para usar o módulo. O Buffer do Node aceita entrada malformada e relata sucesso:

O que a plataforma faz em silêncio 
Buffer.from("zz", "hex")        // an empty buffer, no error
Buffer.from("a-b_", "base64")   // skips - and _, decodes the rest, no error
buf.toString("utf8")            // U+FFFD for anything malformed, no error
O que o Glyph faz 
match bytes.from_hex(input) {
  Ok(b) => use(b),
  Err(e) => io.eprintln("${e.message} at ${number.to_string(e.index)}"),
}

// "z" is not a hex digit at 0
// a trailing base64 group cannot be 1 character(s) long at 3
// not valid UTF-8 at 2
Detalhes o que cada codec recusa

Cada codec é escrito por extenso em vez de delegado ao Buffer, então hex, base64, base64url e base32 recusam um caractere fora do alfabeto, um grupo final curto demais para codificar um byte inteiro e um caractere final que carrega bits além do fim dos dados. O to_text percorre os bytes para achar o primeiro que não pode fazer parte de uma sequência UTF-8 válida, então você recebe uma posição em vez de um veredito. O from_array rejeita qualquer coisa fora de 0..255 pelo mesmo motivo: um & 0xff silencioso transforma 256 em 0 e um erro de digitação em dado.

Escrever os codecs por extenso trouxe algo que não era o objetivo. O módulo não usa nenhuma API do host, só Uint8Array, TextEncoder e TextDecoder, então um bundle que só usa std/bytes continua rodando num Web Worker.

O HMAC que você escolhe muda a resposta

O std/crypto agora tem as duas formas de cada algoritmo.

  • O nome simplesO nome simples recebe uma string e devolve hex, que é o que o hash de uma senha pede.
  • A forma _bytesA forma _bytes recebe e devolve Bytes, que é o que um protocolo de rede pede.

Se a chave veio de bytes.from_base64 ou de crypto.random_bytes, ela tem bytes que uma string não consegue guardar, e a forma de texto vai calcular outra coisa em silêncio.

Para verificar um valor enviado por um atacante contra um segredo, use crypto.timing_safe_equal, não bytes.equals. O equals retorna assim que encontra uma diferença, então o tempo que ele leva revela quantos bytes iniciais estavam certos.

Situação atual

Disponível hoje

  • O std/bytes com 21 funções: as operações de sequência, a ponte com UTF-8 e codecs hex, base64, base64url e base32 que retornam um Result com a posição problemática.
  • fs.read_bytes, write_bytes e append_bytes leem e escrevem um arquivo sem decodificar.
  • O std/crypto tem uma forma _bytes de cada digest e HMAC, além de SHA-1 para os protocolos que o especificam, random_bytes e timing_safe_equal.
  • Os codecs são fixados contra os vetores da RFC 4648 e o HMAC contra a RFC 6238, na própria suíte de testes do compilador.

Ficando mais preciso

  • Ainda não há codec de inteiros, então ler um u32 big-endian de um cabeçalho é uma conta que você escreve: acima de 32 bits, shift é a ferramenta errada de qualquer jeito, então se usa divisão.
  • Literais hexadecimais ainda não passam no parse, o que deixa difícil de ler uma tabela de CRC32 com 256 entradas escrita em decimal.
  • O std/websocket ainda decodifica um frame binário como texto UTF-8; o tipo de que ele precisava agora existe, e os frames são o próximo passo.
  • E as seis funções mais antigas de string para string do std/encoding continuam silenciosas diante de entrada malformada, então use os codecs do std/bytes para tudo o que precisa estar certo.
  • Os codecs são escritos em TypeScript em vez de delegar ao Buffer do Node, e é isso que permite rodá-los num Web Worker; eles são entre 1x e 35x mais lentos que os da plataforma num megabyte.
  • Codificar uma chave ou um token não custa nada mensurável em nenhum dos dois casos; o guia de desempenho tem a tabela se você estiver movendo dezenas de megabytes.
