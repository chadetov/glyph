Consigo gerar um cliente e um servidor tipados a partir da spec da minha API?

Sim. Aponte o glyph gen openapi para uma spec OpenAPI: --client emite um client HTTP tipado, uma função por operação; --handlers emite stubs de servidor e um dispatcher route funcional. Se a sua fonte da verdade é um schema zod, o glyph gen zod faz o mesmo. Tudo sai como Glyph comitado e buscável por grep, que é seu e que você edita, nunca uma etapa de codegen escondida.

Por que isso importa

Clients de API escritos à mão e seus DTOs se afastam da spec, e esse desvio é uma classe de bug de que ninguém gosta.

Como o Glyph gera código de verdade (funções tipadas, declarações type reais com descritores em tempo de execução), a spec continua sendo a fonte da verdade, e regenerar produz um diff idempotente e revisável, não uma caixa-preta.

O router do --handlers

O router do --handlers casa o path com padrões de array, então /tasks/{id} vira ["tasks", id] e faz o bind do parâmetro para você.

  1. /tasks/{id}
  2. ["tasks", id]
  3. getTask(req, id)

Cada stub começa como um 501 com um comentário mostrando o parse do body; você os preenche e liga tudo com await serve(PORT, route).

A partir de um schema zod

Se o seu time já define formatos com zod, gere direto a partir deles. O schema vira um tipo Glyph de primeira classe com seu próprio descritor:

schemas.ts 
export const Task = z.object({
  id: z.number(),
  title: z.string(),
  done: z.boolean(),
})
$ glyph gen zod schemas.ts --out src/ 
type Task = {
  id: number,
  title: string,
  done: bool,
}
// + a runtime descriptor, so
// Task.parse(value) validates.

O que ele mapeia

Uma discriminated union polimórfica (um discriminator do OpenAPI) sai como uma union etiquetada real do Glyph mais um parse_<Name> gerado, que lê a propriedade discriminadora e valida para a variante certa.

Detalhes por que um dispatcher é gerado

Como o Glyph etiqueta pelo nome do construtor e não por uma propriedade arbitrária, o dispatcher gerado faz a ponte entre o objeto que vem da rede e a union para você.

Onde fica aquém

A geração é fiel ao formato da rede, então mapeia os 80% comuns: objetos, primitivos, arrays, referências, campos opcionais e nullable (mantidos separados: um campo nullable vira Nullable<T>, e um campo que o schema não exige ganha ?, que não aceita null), e discriminated unions. O que não consegue representar com exatidão (um enum de strings, uma union não discriminada) ela estreita com uma nota impressa, em vez de um validador que rejeitaria dados reais. Enums mais ricos vêm a seguir.

Detalhes o que os geradores precisam ter instalado

E as ferramentas têm dependências reais: gen dts/gen zod precisam de Node mais typescript/zod. O gen dts funciona com qualquer TypeScript (5, 6 ou o port nativo 7.x), resolvido primeiro a partir do seu projeto, e os comandos dizem exatamente o que instalar se faltar algo.

Mantendo tudo em sincronia

Todo arquivo gerado registra no cabeçalho o comando exato que o criou. Quando uma spec muda, você não precisa caçar quais comandos rodar de novo: glyph regen procura esses cabeçalhos e roda cada um de novo, reescrevendo a saída.

É idempotente, então um regen sem mudança na spec não toca em nada; encaixa direto num hook de pre-commit ou numa verificação de CI que falha se o código comitado tiver se afastado da spec.

Situação atual

Disponível hoje

  • glyph gen openapi (tipos, --client, --handlers com um router real), glyph gen dts, glyph gen zod e glyph regen para atualizar tudo a partir da fonte: todos os comandos emitem Glyph comitado, com descritores e regenerado de forma idempotente.
  • Dois tipos que seriam escritos sob um mesmo nome Glyph param o gerador, em vez de produzir um arquivo que não compila: ele nomeia cada fonte em colisão, não grava nada, e --rename Source=GlyphName resolve.
  • Essa escolha fica registrada no cabeçalho gerado, então o glyph regen a repete.

A caminho

  • Mapeamento de enums mais rico e cobertura maior do OpenAPI, cada um chegando sob a mesma regra: fiel ao formato da rede, com nota quando estreitar.
  • Gerar a partir do próprio .d.ts de um pacote lê as declarações interface e type dele, então uma biblioteca cuja API é feita de classes, ou cujos campos usam tipos computados como Omit, deixa referências que o gerador cita numa nota e que o glyph build informa como não resolvidas.
  • Importar uma classe dessas e construí-la com new não precisa de geração e é verificado pelo tsc, então esse caminho não é afetado.
