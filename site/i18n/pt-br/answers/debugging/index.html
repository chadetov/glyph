Quando quebra em produção às 3 da manhã, o que o plantão vê?

TypeScript legível que é seu, com um source map de volta para o seu .glyph ao lado de cada arquivo emitido. Um debugger, um bundler ou um rastreador de erros liga o código em execução ao seu fonte, e até quem nunca viu Glyph consegue ler o TS gerado. Antes de tudo isso, glyph build e glyph run informam os mesmos diagnósticos sobre a mesma árvore, então o ciclo rápido não esconde algo que o build teria pegado. Duas limitações, ambas no caminho do glyph run, estão descritas abaixo.

1 · O TypeScript gerado é seu para ler

O Glyph não traz um runtime opaco. Ele emite TypeScript comum e formatado, que você comita e faz deploy como qualquer outro TS.

Então o pior caso (alguém de plantão que não conhece Glyph, às 3 da manhã) ainda está lendo TypeScript puro, não um dialeto. Não há caixa-preta entre o seu fonte e a produção.

2 · Source maps de volta para .glyph

Todo .ts emitido vem com um source map v3 padrão (.ts.map) ao lado, com um comentário sourceMappingURL e o seu fonte Glyph embutido (sourcesContent).

dist/main.ts (final) 
// ...emitted TypeScript...
//# sourceMappingURL=main.ts.map    // v3 map, .glyph embedded

Qualquer coisa que consome source maps (Chrome DevTools, um debugger do Node, um rastreador de erros como o Sentry, o seu bundler) consegue encadear por ele e mostrar a linha do .glyph, não a gerada.

3 · Erros de build e de tipo já apontam para o Glyph

Raramente você chega à produção com um erro de tipo, porque glyph build roda tsc --strict e mapeia cada erro do tsc de volta para o seu fonte .glyph (mesmo cursor, com o código de erro do TypeScript preservado).

E glyph build --json emite cada diagnóstico como JSON estruturado (código, severidade, arquivo, linha/coluna a partir de 1, ajuda) para o seu CI ou suas ferramentas agirem.

Detalhes onde o cursor cai

O cursor fica na menor expressão Glyph cujo código o tsc rejeitou: um argumento errado sublinha esse argumento, um campo com erro de digitação dentro de um handler de evento JSX sublinha esse acesso a membro, não o return inteiro em volta.

4 · glyph run diz as mesmas coisas

O comando que você digita o dia todo é glyph run, e até a 0.1.40 ele era mais calado que o build. Agora ele informa o mesmo conjunto: avisos incluídos, no arquivo que você indicou e nos vizinhos, depois da saída do programa, com uma linha de contagem.

um import não usado, adicionado um passo antes do código que o usaria 
$ printf 'look\nquit\n' | glyph run adventure.glyph
...the game plays and exits 0...

[E0106] Warning: lint: unused import `math`
    ╭─[adventure:21:1]
    │
 21 │ import std/math
    │         ╰─────── unused import `math`
    │ Help: Remove the import. Nothing in this module references it.

glyph run: 0 error(s), 1 warning(s) in the source tree
Detalhes o cache de execução

O cache de execução guarda os diagnósticos, então uma segunda execução de fontes inalterados diz o que a primeira disse em vez de ficar em silêncio, e uma entrada de cache sem diagnósticos conta como miss e é reconstruída.

Histórico antes da 0.1.40

Ele compilava o diretório inteiro, pegava a lista de arquivos emitidos do relatório e jogava os diagnósticos fora. Uma árvore que o glyph build apontava rodava limpa e saía com 0.

Duas limitações atuais

  • O stack de crash do próprio glyph run ainda mostra números de linha do .ts.O glyph run executa via tsx, e o tsx não encadeia o source map pela sua própria transformação .ts→.js, então um throw não capturado durante o glyph run informa a linha gerada. Remapear esse stack é um trabalho futuro.
  • Um erro num módulo vizinho não muda o exit code do glyph run.Um módulo que falhou ao compilar fica indisponível para import, e um programa que nunca o importou roda mesmo assim. Agora você vê o erro, mas o processo ainda sai com o que o main retornou.
Detalhes stacks de produção, e por que o exit code continua igual

Isso afeta o ciclo local do run; num deploy de verdade você faz glyph build para .ts, empacota com o seu toolchain normal e o .ts.map encadeia como sempre, então o stack de produção que dispara o alerta é mapeado de volta para .glyph.

Fazer ele sair com código diferente de zero quebraria árvores que hoje rodam bem, então isso é uma decisão em aberto, não um descuido. Se você quer que a saúde da árvore decida o exit code, use glyph build.

Situação atual

Disponível hoje

  • TS legível e comitado.
  • Um .ts.map v3 por arquivo.
  • Erros do tsc remapeados para .glyph.
  • Diagnósticos em --json.
  • glyph run informa o que glyph build informa, com cache quente inclusive.
  • A cadeia de source maps do seu toolchain de deploy chega ao .glyph.

A caminho

  • Remapear o próprio stack de crash do glyph run (para que o ciclo local também mostre frames do .glyph).
  • Uma decisão sobre se o erro de um módulo vizinho deve fazer o glyph run sair com código diferente de zero.
  • Um debugging mais rico no editor via LSP.
