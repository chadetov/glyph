Por que o Glyph detecta o que o tsc detecta, só que antes?

Porque um erro no TypeScript gerado é um erro sobre código que você não escreveu. O Glyph informa esses erros no seu fonte, com a regra que você violou e a edição que conserta.

Por que isso importa

O Glyph compila para TypeScript e depois verifica os tipos da saída com tsc --strict, então um erro que o Glyph não modela não se perde. Ele volta uma etapa depois, descrito em termos do arquivo emitido: um TS1308 apontando para um await numa função que você nunca escreveu daquele jeito, ou um TS2366 sobre um switch que não é seu. A linha é mapeada de volta para o seu .glyph, mas a explicação não.

Essa distância é onde o compilador para de ensinar. Por isso cada regra que o Glyph consegue decidir sozinho sobe de etapa: await fora de uma async fn (E0222), um braço de match que não produz valor quando o match é usado como valor (E0223) e uma atribuição escrita sem mut (E0008). Cada um nomeia a regra, cita a decisão por trás dela e mostra o antes e o depois.

Veja na prática

O caso do braço é o que antes escapava por completo. {} na posição de braço é um bloco vazio, não um record vazio, então o braço rodava e não produzia nada:

status.glyph: um braço que não produz nada, numa posição que precisa de valor 
fn label(s: Status) -> string {
  let text = match s {
    Loading => {},          // an empty block: the arm produces no value
    Ready => "done",
    Failed(msg) => msg,
  }
  return text
}
glyph build 
[E0223] this `match` arm produces no value, but the `match` is used as a value
   ╰─ End the arm with an expression, or `return` from it. `X => {}` is a no-op
      only where the `match` is a statement.
   note: A value-position arm lowers to `case X: { break; }` when it yields
         nothing, so the value would be `undefined` at run time.

Antes disso, o switch emitido saía dos próprios casos e text ficava com undefined enquanto o tipo dizia string. O tsc pega algumas formas disso e deixa passar outras. Agora o Glyph decide sempre que a posição é decidível: um let, um mut, um return ou o final de uma função que declara tipo de retorno. Um match usado como statement mantém X => {} como o no-op deliberado que é.

await segue a mesma lógica. O Glyph não tem Promise visível para o usuário: uma async fn -> T é aguardada até um T, então await em qualquer outro lugar não tem o que suspender. Antes isso era o TS1308 do tsc no arquivo gerado. Agora é E0222, e quem decide é o callable mais interno que o envolve, então uma lambda síncrona dentro de uma async fn é um contexto à parte, a mesma regra que o TypeScript usa.

glyph build, em `fn total() -> number { return await fetch_count() }` 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

// before: no Glyph diagnostic, then
dist/main.ts:14:18 - error TS1308: 'await' expressions are only allowed
within async functions and at the top levels of modules.

O terceiro é sobre uma regra que as pessoas quebram no primeiro dia. O Glyph marca toda mutação, então reatribuir um binding é mut x = e e criar um é let x = e. Um x = e sozinho informava "unexpected token: Equals", que nomeia um caractere em vez da regra. Agora é E0008, e glyph --explain E0008 explica por que a marca existe: todo lugar onde um valor muda começa com mut, então grep "mut total" encontra todos.

O operador ? recebe o mesmo tratamento pelo outro lado. ? se expande num binding mais um return antecipado, colocado antes do statement em que ele está, então precisa de um statement onde se expandir. Funciona num let, num return, num argumento e agora no corpo de um braço de match. Onde não pode funcionar, a mensagem diz qual é a posição e como extrair o valor para um binding (E0302 e E0303), em vez de afirmar que o operador não está implementado.

O caso pior: quando o tsc também fica satisfeito

Um erro do tsc no lugar errado incomoda. Um build limpo num programa que significa outra coisa é o problema de verdade, e o Glyph tinha um. Todo nome de nível superior que você declara vai literalmente para o módulo emitido, inclusive os construtores das variantes de uma union etiquetada, então uma variante chamada Error emite export function Error(...) no nível superior do módulo. O new Error(...) que o compilador escreve abaixo dela então chama a sua variante.

type Key = string | number é o mesmo defeito com uma cara mais simpática. Em Glyph, A | B declara uma union etiquetada cujos membros são construtores de variantes, então essa linha declara variantes chamadas string e number. Compilava, passava no tsc --strict e emitia um export const number que sombreava o namespace number do prelude. Nada falhava até uma chamada number.to_string mais adiante falhar.

glyph build, numa union com uma variante `Error` 
[E0110] `Error` cannot name a type, variant, or function: the emitted module
        references the JavaScript global `Error`, and this declaration would
        shadow it
 5 │   | Error(string)
   │     ──────┬─────
   ╰─ Rename it (e.g. `Error` -> `Failure`). The name is legal TypeScript, so
      nothing downstream catches the rebinding.

// before: no Glyph diagnostic, then, twenty lines later
dist/main.ts:31:12 - error TS2345: Argument of type 'string' is not
assignable to parameter of type ...

O trecho marcado é a declaração, que é onde a renomeação acontece. A lista protegida é derivada do emissor, e não de uma lista genérica de globais do JavaScript, e um teste faz grep no emissor e falha quando aparece uma nova referência global sem a entrada correspondente. Esse teste é o ponto: Number era inofensivo até o int sair e começar a emitir Number.isInteger, e foi assim que isso chegou a uma release. Date, Math e JSON continuam livres, porque nada que o Glyph emite os menciona.

O caso da union de primitivos ganha um código próprio, E0111, porque rejeitar sem explicar não ensina nada. Ele diz como a linha foi de fato interpretada, aponta para variantes nomeadas e indica extern_ts("string | number") para a fronteira em que você quer a union crua do TypeScript. Todo nome que o Glyph não deixa você usar está tabelado em docs/reference/reserved-words.md: as 32 palavras-chave, as 33 palavras reservadas do TypeScript por trás do E0109 e a lista de sombreamento, cada uma com o motivo de o nome estar ocupado.

Vale deixar claro o que isso não faz. Você ainda não pode chamar um tipo ou uma variante de Error, e a planilha que revelou isso tem uma variante chamada Cellerr por causa disso. O programa que ela queria ser ainda não pode ser escrito; o que mudou é que o compilador agora diz isso na declaração, em vez de deixar o build ficar verde e significar outra coisa. Tornar o nome utilizável exige alterar os nomes do Glyph na passagem para TypeScript, o que muda o que um stack trace, um grep em dist/ e um shim extern/ escrito à mão enxergam, então não é um patch que dá para fazer em silêncio.

Uma mensagem errada é pior do que nenhuma mensagem

A lista de sombreamento começou com os nomes que o emissor escreve como valores. Faltavam os que ele escreve como tipos, e isso produziu a versão mais aguda de todo esse problema. O parse de todo descritor retorna Result<T, Issue[]>, então o módulo emitido escreve Issue quer você tenha escrito ou não. Declare type Issue = { path: Array<string>, message: string } no seu módulo e o seu vence, os objetos Issue emitidos carregam um campo code que o seu nunca viu, e o build falha com um erro do tsc sobre código gerado, num trecho que aponta para outro lugar.

glyph build, antes: quinze destes, nenhum perto da causa 
dist/corpus/infer_output.ts:52:9 - error TS2353: Object literal may only
specify known properties, and 'code' does not exist in type 'Issue'.
glyph build, agora 
[E0110] `Issue` cannot name a type, variant, or function: the emitted module
        references the Glyph prelude global `Issue`, and this declaration
        would shadow it
   ╰─ Rename it. The name is legal TypeScript, so nothing downstream catches
      the rebinding.

Record entrou na lista ao mesmo tempo, registrado junto com os globais do JavaScript e não com os nomes do prelude, porque é um built-in do TypeScript e dizer o contrário deixaria a mensagem errada sobre a origem do nome. O teste de divergência que faz grep no emissor agora cobre também os tipos ambientes, e precisou aprender a ver Issue[] numa posição de tipo, que é o motivo de isso ter chegado a uma release. Schema, Component e Option continuam permitidos pela mesma regra que mantém Date livre: o emissor só os escreve porque você os escreveu numa anotação, então declarar um deles não sombreia nada.

O outro caso dessa classe era um import. Um caminho de import local é resolvido a partir da raiz do build, o diretório que você passa para o glyph build, e não do diretório do arquivo que faz o import. Faça o build de uma árvore que o contém e import catalog não encontra nada, e até agora nada dizia isso. O tipo se degradava para desconhecido, um match sobre ele perdia as variantes que estava casando, e o que você recebia era E0218, match não exaustivo, num match que cobria todos os casos. Fazer o que essa mensagem pedia teria adicionado um braço else morto a um código correto.

glyph build examples/apps, em `import catalog` dentro de csvql/ 
[E0104] unresolved import `catalog`: no module `catalog` under the build
        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from
        the importing file's directory (D15)
   ╰─ Build that module's own directory as the root, or spell the import path
      as it reads from the root.

// before: no import diagnostic, then
[E0218] non-exhaustive match on string   // on a match over all four values

O risco numa verificação dessas é ela disparar em coisas que estão certas, e um verificador de imports que dá alarme falso em todo pacote do npm é pior do que o silêncio que substituiu. Por isso o build primeiro reúne os nomes de módulo que consegue resolver sem um arquivo .glyph: todo declare module "X" em <root>/.types/ e no shim de Node incluído, mais todo pacote no node_modules do projeto. Um nome dessa lista nunca é informado, mesmo quando um arquivo local tem o mesmo nome base. Quando o projeto não tem node_modules, o compilador não consegue distinguir uma dependência não instalada de um erro de digitação, então informa só o que consegue provar: um import ao qual algum arquivo .glyph sob a raiz corresponde.

A resolução em si não mudou. Os mesmos programas fazem build e os mesmos programas falham. O que mudou é que a falha agora nomeia o import, em vez de acusar um match a dois arquivos de distância, e é só isso: um compilador que informa a causa errada custa a hora gasta correndo atrás dela, e depois o benefício da dúvida em toda mensagem seguinte.

Nomear a regra, não o token

A versão mais discreta do mesmo problema é um erro que está correto e mesmo assim não diz nada. Um agente escrevendo uma árvore rubro-negra usou o construtor posicional que toda linguagem da família ML tem, e o parser parou na primeira vírgula com “expected )” e o conselho “add the expected token”. Colocar um ) ali produz outro programa, não um que funcione. Uma variante do Glyph carrega um payload, e um payload com vários campos é um record. Nenhuma dessas duas frases aparecia em lugar nenhum da saída.

glyph check, antes e agora 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.

Para dizer isso, o parser precisou ler a lista inteira antes de recusá-la, e é isso que também permite contar. O trecho sublinha os seis campos, em vez do separador em que ele por acaso parou, e o record sugerido é montado a partir do nome da variante e dos seis tipos do arquivo, então o conserto nomeia o seu programa, e não um exemplo de outra pessoa. Os nomes dos campos são a única coisa que o compilador não consegue fornecer, então ele os deixa como lacunas.

A regra por trás da mensagem é uma escolha, não uma falha. Node(Black, l, x, b, h, r) é a troca de argumentos que passa na verificação de tipos, e a posição quatro não diz nada a quem lê. A grafia com record nomeia todos os campos, um braço de match nomeia só os campos que usa, e as duas coisas são encontráveis com grep.

Mais dois que o verificador assumiu na 0.1.121

Order { id: "a", total: 1 } é o que quem vem do TypeScript escreve para montar um record, e o Glyph não tem essa forma: um valor é escrito sozinho e o tipo vai na anotação. O que o compilador dizia sobre essa linha era E0108, código inalcançável, num build que saía com 0, porque o nome era resolvido para o tipo e as chaves eram lidas como um bloco depois do return. O nome de um tipo escrito como valor é E0228, e a mensagem é tirada da declaração, então um record lista seus campos, uma union etiquetada lista suas variantes com o formato dos payloads e uma union de string literals lista seus literais. Order.parse(raw) e Order.is(v) continuam válidos, já que o receptor do próprio descritor de um tipo é a única posição de expressão onde cabe um nome de tipo.

Isso consertou o caso em que o nome era um tipo e deixou o parse como estava, então return h() { k: 2 } ainda retornava h() e descartava as chaves com um aviso. Desde a 0.1.146, um { na linha em que um statement terminou é E0013 no parse, seja qual for o nome antes dele, e a ajuda dá a mesma reescrita. Desde a 0.1.149 a regra cobre todo statement, não só um que abre com chave: let s = "a" "b" fazia bind de "a" e descartava "b", e return x as User eram três statements, já que o Glyph não tem cast. Cada statement de um bloco começa na sua própria linha.

glyph check, num record montado do jeito do TypeScript 
[E0013] a statement cannot begin on the line where
        `return Order` ends
   ╰─ Glyph has no `TypeName { ... }` construction form. Write the literal
      alone and put the type on the annotation: `let o: Order = { id: "a" }`.

// 0.1.121 to 0.1.145: [E0228] on `Order`, then [E0108] on the braces
// before that: [E0108] Warning: lint: unreachable code, and exit 0

O outro é um contêiner do prelude atribuído a um primitivo. let x: string = o com o: Option<int> não gerava nada no verificador do Glyph, e passar um Nullable<int> para um parâmetro declarado int também não. Cinco contêineres agora são cobertos nas duas direções: Option, Result, Array, Record e Nullable nunca são string, number ou bool, sejam quais forem seus argumentos, e Nullable<T> contra um escalar é decidido um nível abaixo, contra T, então let v: Nullable<int> = 3 continua correto e let v: Nullable<int> = "three" é E0204. O caso do Nullable pertence a esta página mais do que os outros, porque é um que o tsc não consegue pegar: o const v: number | null = 3 emitido é estreitado de volta para number antes de a chamada ser verificada, então um tipo de fronteira que existe para tornar o null visível passava em silêncio onde um int estava declarado, e o verificador do Glyph era o único lugar onde isso poderia ser pego.

Os mesmos contêineres contra um record ou uma union declarados vieram em seguida. Desde a 0.1.130, let user: User = json.parse(body) é E0204, esperado User, encontrado Result<unknown, Array<Issue>>. Antes, só o tsc dizia isso, o que significava que glyph check --no-tsc, o editor e o playground mostravam um arquivo limpo justamente na linha que uma fronteira existe para acertar.

Um membro com erro de digitação num array ou numa string é o outro caso que antes esperava o tsc. xs.lenght é E0210 com "did you mean length", verificado contra os membros que a biblioteca do TypeScript declara para arrays e strings, do mesmo jeito que a leitura de um campo de record é verificada contra os campos dele. O tsc teria recusado os dois, então um build que o rodava já ficava vermelho; a mudança é que o verificador, e tudo o que é construído sobre ele, os vê primeiro.

E mais três, desde a 0.1.133

let up = s.toUpperCase passa na verificação de tipos do TypeScript e lança erro quando up() roda, porque a leitura perde a string a que o método pertence. O Glyph recusa isso como E0234, e recusa também .bind(s) nele: envolva a chamada numa lambda. O verificador agora sabe o que cada método de array e de string retorna, a partir de uma tabela gerada das próprias declarações do TypeScript.

r?.label num Result parece dizer "propague o erro e depois leia o campo". É optional chaining, e um Result nunca é null, então lê o campo do objeto Result e não propaga nada. Um agente escreveu exatamente isso ao construir uma ferramenta de consulta em CSV. Agora é E0236, num Option também, e a ajuda diz para fazer bind com ? primeiro.

json.parse(body) sem argumento de tipo é a leitura não verificada, um Result<unknown, ...>. Escrito onde um Result<User, ...> estava declarado, o tsc inferia User a partir da declaração e o programa quebrava na primeira leitura de campo. Agora o emissor escreve o unknown explicitamente, então glyph check o recusa via tsc. O próprio verificador do Glyph ainda não pega um unknown que cai dentro de um tipo declarado, então --no-tsc e o editor ainda deixam passar Result<unknown, ...> escrito onde Result<User, ...> está declarado. (Um let user: User = json.parse(body) simples é E0204 pelo próprio verificador do Glyph, porque o tipo externo já está errado.) Recusar unknown em qualquer profundidade é o G325, planejado para a 0.1.158.

E mais dois na 0.1.122

type Mode = "read" | "write" declara um conjunto finito de strings, e o verificador do Glyph não comparava um valor com ele por critério nenhum. Um número, um bool, um record e uma string fora do conjunto passavam todos no glyph check --no-tsc só com avisos de variável não usada, enquanto o tsc recusava cada um deles no TypeScript emitido. Então um glyph build completo nunca errou nisso, mas as quatro superfícies que não têm tsc no ciclo erravam: --no-tsc, o language server, as ferramentas MCP e o playground.

glyph check --no-tsc, num tipo que lista suas strings válidas 
type Mode = "read" | "write"

let a: Mode = 3
let b: Mode = "rw"
let c: Mode = takes_mode(true)
let d: Mode = { x: 1 }
// before: four unused-variable warnings, exit 0
[E0204] type mismatch: expected `Mode`, found `number`
[E0204] type mismatch: expected `Mode`, found `"rw"`
[E0211] argument type mismatch: expected `Mode`, found `bool`
[E0204] type mismatch: expected `Mode`, found `record`

São os quatro que o tsc informava, nos mesmos quatro statements, sem rodar o tsc. A regra lê a union como o que ela é em tempo de execução, uma string, e faz ao verificador a pergunta correspondente sobre string em cada direção, então herda as regras que já recusam um record ou um contêiner contra uma string, em vez de reescrevê-las formato por formato. Dois conjuntos de literais são comparados como conjuntos, então uma union mais estreita cabe onde uma mais ampla está declarada; uma cadeia de aliases é seguida dos dois lados; uma union importada é decidida como uma local; e Nullable<Mode> é percorrido com a union intacta.

Uma union aninhada num campo de record ou num argumento genérico ficava a cargo do tsc na 0.1.122 e é decidida na 0.1.123. Veja abaixo.

O segundo não é uma história de tsc. O parser é descendente recursivo sem limite de profundidade, então uma expressão aninhada em dois mil níveis estourava a pilha do processo e abortava com exit 134. Isso é ruim no glyph check e pior no glyph lsp e no glyph mcp, que leem todo arquivo sob a raiz: um único arquivo patológico derrubava o servidor para o workspace inteiro. Agora é E0011, levantado no token que abriria o nível 65.

0.1.123: o literal que um valor é, não a string para a qual ele é emitido

type Mode = "read" | "write" colocava o conjunto na declaração e nada no valor, então "read" era uma string e ["read", "write"] um Array<string>. Isso tornava dois programas indistinguíveis: return ["read", "write"] onde um Array<Mode> está declarado, que o tsc compila, e return xs para um xs: Array<string>, que ele recusa. A 0.1.122 preferiu não decidir esse par a decidir errado, e isso garantiu o programa certo abrindo mão de pegar o errado: { mode: "nope" } contra um { mode: Mode } não gerava nada.

Um string literal escrito agora tem o tipo de um único literal que ele soletra, o tipo dos elementos de um array literal é a junção dos tipos dos elementos, e um array ou objeto literal escrito é verificado elemento por elemento e campo por campo contra o tipo declarado, então o diagnóstico nomeia o literal e o sublinha.

glyph check --no-tsc, num literal um nível dentro de um contêiner 
type Mode = "read" | "write"
type Cfg = { mode: Mode }

fn ok() -> Array<Mode> { return ["read", "write"] }
fn bad() -> Array<Mode> { return ["read", "nope"] }
fn wrong() -> Cfg { return { mode: "nope" } }
// 0.1.122: nothing, on all three
[E0204] type mismatch: expected `Mode`, found `"nope"`   (twice)

O literal volta a ser string onde o TypeScript o alarga: num let sem anotação, cujo let emitido em TypeScript alarga do mesmo jeito, e no binding de elemento de um for sobre um array escrito. Então let l = "read" seguido de takes_mode(l) é recusado aqui e é TS2345 lá. Um const emite um const do TypeScript e mantém o literal, então takes_mode(CM) compila nos dois. Um tipo literal que chegou por meio de um nome não é alargado, que é a própria regra de freshness do TypeScript. Cada linha disso foi decidida rodando tsc --strict no TypeScript equivalente, não por dedução.

Um par ainda fica sem decisão: o argumento de chave de um Record contra o de outro Record. O TypeScript escreve Record<string, V> como uma index signature que cobre toda chave que um Record<Mode, V> declara e o aceita nas duas direções, então recusá-lo recusaria um programa que compila. Mais dois formatos sobre os quais o verificador ainda não diz nada: um literal dentro de Some(...), porque um construtor do prelude ainda não tem tipo aqui, e um record literal ligado a um let sem anotação, porque nenhum tipo record é sintetizado para um objeto literal.

Um módulo sob std/ era código morto sem diagnóstico

std/ e extern/ nomeiam módulos que o compilador traz consigo, e o resolvedor os reservava para imports. Nada impedia um arquivo do projeto de declarar um deles. module std/io no seu próprio src/io.glyph compilava limpo, e então import std/io { shout } era resolvido para o stub e informava que shout não é exportado: o seu arquivo nunca era lido. Um arquivo que não gera diagnóstico nenhum e não roda código nenhum é a pior situação em que um compilador pode deixar você, porque nada nele parece errado.

glyph check --no-tsc, em src/io.glyph declarando `module std/io` 
// before: glyph check: 2 module(s) checked, no diagnostics.  (exit 0)

[E0113] `std/io` declares a module under `std/`, a prefix reserved for the
        modules the compiler carries (D15)
 1 │ module std/io
   │ ──────┬──────
   ╰─ Rename the module to a path of your own (`io`, `app/io`).

O prefixo é comparado como um primeiro segmento inteiro, então standard, externals/io, app/std e app/extern/helper não são afetados, e importar com qualquer um dos prefixos continua funcionando como sempre.

glyph check, em `const x = ` seguido de 2.000 colchetes aninhados 
// before: thread 'main' has overflowed its stack
//         fatal runtime error: stack overflow, aborting   (exit 134)

[E0011] this array literal nests deeper than the parser's limit of 64 levels
   ╰─ Name the inner levels: pull them out into `let` bindings, or into a
      `fn` that returns one of them, so no single expression, type or
      pattern is more than 64 levels deep.

O limite é 64, e foi medido, não escolhido. Um nível da construção mais cara, um array literal aninhado, custa 7.792 bytes de pilha no build de release e 8.810 no de debug, valores encontrados por busca binária da menor pilha de thread em que uma dada profundidade consegue passar pelo parse. A pilha mais fina em que o parser roda é a de 2 MiB de uma thread criada, que é o que os workers do language server recebem, e 64 níveis gastam menos de um terço dela no build mais caro. O aninhamento mais profundo entre os 343 arquivos .glyph deste repositório é 16. O limite cobre igualmente expressões, tipos, padrões, blocos e filhos JSX, e mil arrays irmãos continuam passando pelo parse, porque a profundidade é o aninhamento por construção, não um orçamento gasto ao longo do arquivo.

Quando nenhum dos compiladores está errado

Existe um terceiro formato, e é o que pior se lê. O Glyph não informa nada, o tsc informa algo verdadeiro, e o programa que você escreveu estava certo. O que falhou foi a tradução entre os dois.

Um binding em Glyph tem um único tipo durante toda a vida. O TypeScript estreita um binding para o que viu atribuído por último, e o boolean dele é a union true | false, então let done = false chegava ao tsc com tipo false, e o braço true do switch emitido não tinha o que casar.

poll.glyph, e o que o tsc dizia sobre ele antes da 0.1.89 
fn classify() -> int {
  let done = false
  match done {
    true => { return 1 },
    false => { return 0 },
  }
}

// no Glyph diagnostic, then
[TS2678] Type 'true' is not comparable to type 'false'.

Um tipo declarado como um conjunto de string literals falhava do mesmo jeito, e o == também, que voltava como TS2367: duas mensagens, dois códigos, uma causa. O app que esbarrou nisso fazia polling de uma flag que um callback de timer define, que é como se transforma uma API baseada em eventos num valor enquanto o Glyph não tem uma Promise que você possa construir à mão. O callback acabou sendo irrelevante: quatro linhas sem callback já reproduzem.

O conserto não é um diagnóstico novo, porque não há nada a diagnosticar. Agora o emissor reafirma o tipo que o verificador já decidiu, nos dois lugares que discriminam sobre um valor: o scrutinee do match e cada lado de um == ou !=. Cada lado é decidido pelo seu próprio tipo e ignora o que está ao lado, então uma comparação entre dois bindings é coberta do mesmo jeito que uma comparação com um literal.

As verificações que você quer continuam disparando. m == "nope", com m sendo um Mode, continua rejeitado, e agora a mensagem nomeia Mode em vez do único membro que m por acaso guardava. Fazer isso na atribuição teria dado menos código e jogado isso fora: um cast para Mode é aceito onde a atribuição anotada não é, e a verificação de pertencimento é a parte que o Glyph deixa para o tsc de propósito.

O custo é pequeno e vale nomear. Um cast pode estreitar além de confirmar, então um valor que o Glyph tipa como bool e cujo tipo TypeScript saiu unknown agora passa onde o switch antes reclamava. Os dois tipos ainda precisam ser comparáveis, então um modelo que se desviou o bastante para importar, string contra bool, informa TS2352 em vez de nada.

O mesmo erro de digitação, duas respostas

Uma função da biblioteca padrão com erro de digitação recebia uma resposta diferente dependendo de como você tinha escrito o import, e esse é o tipo de inconsistência que ensina a não confiar em nenhuma das duas respostas.

o import nomeado, sempre um E0105 
import std/string { repeeat }
[E0105] import: `repeeat` is not exported by `std/string`
a leitura pelo namespace, antes da 0.1.72 
import std/string
string.repeeat(s, 2)
[TS2551] Property 'repeeat' does not exist on type ... Did you mean 'repeat'?

A primeira grafia era verificada contra a lista de exports do módulo durante a resolução. A segunda não era verificada em nada, então caía para o tsc, que via um acesso a propriedade num objeto e respondia nesses termos. As duas grafias agora passam pela lista de exports, e as duas dizem E0105, nomeando o membro e o módulo em que ele falta.

Ligar isso encontrou na hora algo que ninguém estava procurando: uma fixture de teste vinha chamando fs.write, sendo que a função é write_text. Passava havia meses porque essa fixture roda com a verificação de tipos desligada, e nada mais no compilador olhava para membros de namespace. A lista de exports agora é a autoridade para as duas grafias, então uma verificação separada a mantém alinhada com o que o runtime de fato exporta. Essa verificação foi escrita e depois quebrada de propósito para confirmar que falhava, e foi assim que descobrimos que a primeira versão dela não verificava nada, em silêncio.

Disponível hoje

E0222 para await fora de uma async fn, E0223 para um braço de match em posição de valor que não produz valor, E0008 para uma atribuição sem mut, E0010 para uma variante com vários campos posicionais no payload quando a forma que existe é a de record, E0302/E0303 para um ? numa posição de onde ele não pode propagar, E0110/E0111 para uma declaração que sombrearia um nome do qual o módulo emitido já depende, E0104 para um import local que não nomeia nenhum módulo sob a raiz do build, E0105 para um nome que um módulo não exporta, tanto por import nomeado quanto por namespace, E0228 para o nome de um tipo escrito onde se espera um valor, E0013 para um statement que começa na linha em que outro terminou, o que antes descartava o valor depois dele, E0204/E0211 para um contêiner do prelude atribuído ou passado como primitivo ou como record ou union declarados, incluindo o caso do Nullable<T> que o tsc elimina ao estreitar, E0210 para um membro que um array ou uma string não tem, os mesmos dois códigos para um valor que não está no conjunto declarado de uma union de string literals, E0011 para uma construção aninhada além de 64 níveis, E0101 para um caminho de import relativo, que antes parava no parser como um genérico "expected module path segment", e E0113 para um módulo do projeto declarado sob std/ ou extern/, que antes compilava limpo e ficava inalcançável. A lista de sombreamento cobre os tipos que o emissor escreve por conta própria, então Issue e Record são pegos na declaração. Todo código tem um conserto de uma linha, uma nota explicando a regra e um texto longo no glyph --explain; docs/error-codes.md lista o catálogo e um teste mantém os dois alinhados.

Ficando mais preciso

array.map, flat_map e zip ainda aceitam um callback async sem reclamar e devolvem um array de valores pendentes, que é impresso como [object Promise]; as cinco funções de array que recebem predicado barram isso, com E0211 no callback. Modelar as outras três do mesmo jeito também rejeitaria par.all(array.map(items, async fn ...)), que é como o Glyph executa trabalho concorrente, porque um array de valores pendentes não tem como ser escrito na linguagem. Isso é uma decisão de sistema de tipos, não uma entrada faltando, então está em aberto. O inicializador de um const no nível do módulo não tem callable que o envolva, então um await no nível superior é permitido e o ESM emitido o executa; se o Glyph quer inicialização assíncrona implícita de módulos ainda é uma questão em aberto na especificação. E0223 só consegue julgar um match final quando a função declara tipo de retorno, então um braço dentro de uma lambda sem anotação ainda chega ao tsc. No lado do sombreamento, duas coisas estão só pela metade. E0110 manda renomear em vez de deixar você manter o nome, então Error, Number, Object, Array e Promise continuam proibidos para um tipo ou uma variante. E E0111 impede que type Key = string | number signifique a coisa errada sem dar a você um jeito de dizê-la: uma union de dois tipos primitivos não tem como ser escrita em Glyph a não ser com extern_ts, cujo conteúdo o próprio verificador trata como opaco. Unions sem etiqueta mexem com exaustividade, descritores em tempo de execução e is, então isso é uma decisão de sistema de tipos e não está agendado. E0104 chega ao glyph build e ao glyph check, mas não ao editor: o LSP analisa o texto de um documento sem raiz de build, e a pasta do workspace também não é uma, então adivinhar produziria os falsos positivos que a verificação foi feita para evitar. E um parâmetro com palavra reservada ainda fica escondido atrás de um erro não relacionado no mesmo arquivo, porque uma falha na etapa de coleta pula a etapa de resolução que o teria encontrado. À parte disso, a fixação no local de leitura que mantém casável um binding bool ou de union de string literals só segue um alias de tipo dentro do módulo que está sendo emitido, então pub type Ready = bool num módulo e let r: catalog.Ready = false em outro ainda chegam ao tsc como TS2678. Unions de string literals são cobertas entre módulos nas três grafias de import, e desde a 0.1.123 o diagnóstico nomeia a declaração (esperado Mode) em todas as grafias, em vez de imprimir o conjunto de literais em uma delas.
