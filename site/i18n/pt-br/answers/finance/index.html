16 · Dinheiro e segurança

Posso confiar nele com dinheiro, e com entrada que eu não controlo?

Pode. Dinheiro é exato, um invariante como não negativo é um tipo que a fronteira garante, e entrada não confiável não chega a um sink de SQL ou de shell sem ser sanitizada. Se você errar em qualquer um desses pontos, o resultado é um erro de compilação ou de parse, e não uma convenção que alguém precisa lembrar três funções depois.

Dinheiro não é float

std/decimal é ponto fixo decimal exato sobre BigInt.

  • Aritmética exataSoma, subtração e multiplicação são exatas.
  • DivisãoA divisão recebe uma escala explícita e arredonda metade para longe do zero.
  • Entrada inválidaUm valor malformado vira um Err no parse, nunca um NaN silencioso.

Ids e contadores continuam exatos além de 253

Um id de conta ou um contador de razão contábil que estoura a faixa do float e é arredondado é outro tipo de catástrofe.

bigint é um inteiro exato de precisão arbitrária com literais 123n, e um campo de record do tipo bigint valida typeof === "bigint" na fronteira, então um id que chega como number no JSON é rejeitado em vez de truncado sem aviso.

Um invariante é um tipo, não um comentário

"O valor não é negativo" e "a nota vai de 1 a 5" são as verificações que se escrevem uma vez e se esquecem depois. Um refinamento where coloca o invariante no tipo, e o descritor o garante na fronteira.

refinements.glyph 
type Amount = int where value >= 0
type Rating = int where value >= 1 && value <= 5

Amount.parse(-1)   # Err  (not just "is a number")
Rating.parse(6)    # Err
Amount.parse(3.5)  # Err  (int check too)

Um valor que não satisfaz o predicado nunca chega a virar um Amount.

Injeção é erro de compilação

O caminho clássico para execução remota de código é entrada não confiável chegando a uma query SQL, a um comando de shell ou a um template HTML. std/taint transforma isso em erro de tipo.

  • Dois tiposUm valor vindo de fora é Tainted; um sink que você quer proteger recebe Trusted.
  • Um só caminhoOs dois são estruturalmente distintos, então o único caminho de um para o outro é um sanitize explícito.
o caminho seguro compila 
fn run_query(sql: Trusted<string>) -> void { ... }

let input: Tainted<string> = taint(req.body)
run_query(sanitize(input, escape))   # ok
o caminho da injeção não compila 
module query

import std/taint { Tainted, Trusted, taint, expose }

fn run_query(sql: Trusted<string>) -> string {
  return expose(sql)
}

pub fn handle(body: string) -> string {
  let input: Tainted<string> = taint(body)
  return run_query(input)
}

// [TS2345] Argument of type 'Tainted<string>'
//   is not assignable to parameter of type
//   'Trusted<string>'. (query.glyph:11)

Passe o valor tainted direto para um sink e o tsc se recusa a compilar.

Situação atual

Disponível hoje

  • std/decimal para dinheiro exato
  • bigint para inteiros grandes exatos
  • Refinamentos where para que um invariante seja validado na fronteira
  • std/taint para que entrada não confiável não chegue a um sink protegido sem um sanitize explícito
  • Tudo isso é verificado: um valor ou id inválido falha no parse, um invariante violado falha no parse, e um valor não sanitizado falha no tsc.

Onde para

  • Hoje um refinamento where cobre tipos base primitivos; invariantes de record e entre campos (where value.paid <= value.total) são uma extensão planejada.
  • Taint é uma disciplina que você adota ao tipar um sink como Trusted, não uma análise de fluxo automática
    Detalhes

    Taint é uma disciplina que você adota ao tipar um sink como Trusted, não uma análise de fluxo automática: o compilador garante a fronteira que você declara, ele não infere taint pelo programa inteiro para você.
