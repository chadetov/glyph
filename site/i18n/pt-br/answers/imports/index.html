Posso usar minhas bibliotecas de TypeScript, JavaScript e npm?

Sim. Glyph compila para TypeScript comum e usa o npm: um módulo .glyph importa de qualquer pacote e pode ser importado pelo seu .ts existente. Você adota um arquivo de cada vez.

Por que isso importa

Ninguém reescreve uma base de código para experimentar uma linguagem. Como a saída do Glyph é TypeScript, um arquivo .glyph entra num canto de um projeto TS/React/Node existente, importa os mesmos pacotes e exporta de volta para o .ts ao redor. Esse caminho gradual é o motivo de ter TypeScript como alvo em vez de lançar um runtime novo.

Veja na prática

Você importa pacotes pelo nome (inclusive os com hífen e os com escopo npm) e o Glyph emite o import que você esperaria:

form.glyph 
import react { useState }
import react-hook-form { useForm }
import @hookform/resolvers/zod {
  zodResolver,
}
form.ts: gerado 
import { useState } from "react";
import { useForm } from "react-hook-form";
import { zodResolver }
  from "@hookform/resolvers/zod";

Se o pacote está instalado e traz seus próprios tipos (ou tem um @types/...), é só isso. Sem stub, sem arquivo adaptador. O glyph build encontra o node_modules do seu projeto e aponta o verificador de tipos para ele, então os tipos reais do pacote verificam seu código e uma chamada errada é um erro de verdade. Imports de subcaminho (pkg/sub) também são resolvidos pelo mapa exports do pacote, então os tipos próprios de um subcaminho são verificados. Aqui está o zod usado diretamente, sem nada escrito à mão:

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
uma chamada que o zod não define 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

O glyph run executa o mesmo programa com o zod instalado, então não é só verificação de tipos: a mesma entrada de configuração que resolve o pacote para o verificador de tipos o resolve também para o runtime. Um pacote que não traz nenhum tipo e não tem @types/... ainda precisa de uma declaração escrita por você, e é para isso que serve a pasta .types/ (o mesmo mecanismo de .d.ts que o TypeScript já usa). E quando você quer a forma de uma biblioteca como um tipo Glyph de primeira classe e validado, em vez de um import só de tipos, o glyph gen dts materializa um .d.ts em tipos reais com descritores: veja preciso escrever à mão um validador para cada API?

Tipos derivados de valores são de primeira classe. type User = z.infer<typeof user_schema> funciona direto: typeof user_schema é uma consulta de tipo sobre uma referência real a um valor (um erro de digitação é um erro de nome não resolvido), e z.infer<...> é um tipo genérico membro comum. Ele é emitido literalmente e o tsc o reduz, então u.name é um string; a validação vem do próprio parse do schema, que é como o zod já funciona. Spread de props em JSX (<input {...register()} />) também é de primeira classe. Para o raro idioma de TypeScript que o Glyph ainda não consegue expressar, extern_ts("...") é a válvula de escape delimitada e fácil de achar com grep: o tsc o verifica, mas sendo preciso, é uma fronteira de confiança, não uma validada em runtime (opaca para o Glyph, um valor volta como unknown para ser estreitado). Então uma biblioteca nunca obriga você a escrever um arquivo adaptador à mão.

Quando você precisa de TypeScript escrito à mão por inteiro

Às vezes a válvula de escape não é um tipo nem uma expressão, e sim código de runtime de verdade: um loop sobre um stream do node, um new Promise, uma worker thread. Coloque o .ts em <src>/extern/ e acesse-o com import extern/<name>. 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

O build copia <src>/extern/** para a saída e emite um especificador relativo, então o tsc verifica os tipos do extern junto com seu código Glyph e um rebuild nunca o remove. Imports relativos continuam proibidos no código Glyph (uma regra de buscabilidade), então extern/* é o único caminho reservado, e grep -rn 'import extern/' encontra todos os lugares onde você saiu da linguagem. É o inverso da direção fácil, um arquivo .ts importando seu Glyph compilado, que não precisa de nada. Um extern comum (um servidor http, fs) é verificado contra o shim de node embutido, sem nada instalado.

Acompanhando um subprocesso, sem nada instalado

As declarações de node embutidas trazem a metade assíncrona de child_process, não só a bloqueante, então uma ferramenta que mostra a saída de um comando longo enquanto ele roda é Glyph, não um extern: 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

io.print e não io.println: um chunk é um pedaço do stream, não uma linha, e uma linha pode chegar dividida entre dois deles. Os overloads seguem o @types/node, então os pipes voltam não nulos de um spawn(command, args) simples e anuláveis quando você passa stdio. Ler child.stdout depois de stdio: "inherit" dá TS18047 aqui e TS18047 com as tipagens reais, em vez de duas versões diferentes sobre o mesmo valor: 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

Edite o shim, e a próxima execução usa o shim que você editou

Um shim é um arquivo em que você itera, então ele tem que contar como código-fonte. O glyph run guarda um build em cache sob uma impressão digital das suas fontes, e essa impressão cobre todo .ts e .tsx em extern/, pelo caminho e pelo conteúdo. Edite um, renomeie um, adicione um, apague um, e a próxima execução refaz o build e roda o tsc de novo. Um shim que é link simbólico é seguido, então um .ts mantido fora da árvore de código é hasheado pelo que realmente contém.

É isso que permite que o shim seja dono de um tipo, em vez de os dois arquivos declararem cada um sua cópia. Exporte a forma a partir do shim, importe-a no módulo Glyph, e o compilador mantém os dois em sincronia a cada execução:

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
o shim renomeou um campo, e o build avisa 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3

Até a 0.1.44 a impressão digital ignorava extern/ por completo, então esse rename produzia um build limpo e com tipos verificados rodando a cópia anterior do shim. Arquivos em extern/ que não são .ts nem .tsx continuam sem afetar o cache, e isso é proposital: um README.md ao lado do seu shim é copiado para a saída junto com ele, mas nada o verifica nem o executa, então não há nada para refazer.

Clientes baseados em classes: os de banco de dados e mensageria

A maioria dos clientes de banco de dados e mensageria é baseada em classes: você escreve new Kafka(...), new MongoClient(url), new Redis(), new Pool(cfg). O Glyph tem new exatamente para isso. Ele emite um new de TypeScript literal e o tsc o verifica contra o construtor real do pacote, então um argumento errado é um erro de verdade e um callee indefinido é detectado pelo nome. Continua sendo só para interop: o Glyph não tem class própria, e new só constrói um tipo que vem de um pacote, de uma declaração em .types ou de extern_ts.

um cliente baseado em classe (kafkajs) 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
um cliente de factory não precisa de new 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

Situação atual

Disponível hoje

Importe qualquer pacote npm (inclusive nomes com hífen e com escopo). Um pacote instalado que traz seus próprios tipos (ou tem @types/...) é verificado e roda sem stub. Clientes baseados em classes são construídos com new, verificados pelo tsc contra o construtor real; clientes de factory são importados e chamados diretamente. Os builtins do node (fs, path, http, child_process incluindo o spawn com streaming, e o resto) são verificados sem configuração, com o @types/node carregado automaticamente quando você o instala, e a CI compila o runtime do próprio compilador contra esse pacote na versão latest, então uma declaração da qual a stdlib depende não pode divergir da real do node. Uma declaração que só o seu código usa ainda não é coberta por essa verificação, e algumas ainda são mais amplas que as do node. Declarações ambientes em .types/ para todo o resto, glyph gen dts para materializar um .d.ts em tipos Glyph validados, e uma saída .ts limpa que o seu TypeScript existente importa de volta. Quando você precisa de TypeScript escrito à mão por inteiro, import extern/<name> acessa um .ts em <src>/extern/, copiado e verificado junto com seu código, e acompanhado pelo cache do glyph run, então editá-lo refaz o build.

A caminho

A materialização agora lida com as formas que SDKs reais trazem (namespaces, re-exports entre arquivos, com alias e de namespace, exports de subcaminho, e genéricos de primeira classe), e tipos derivados de valores (z.infer<typeof s>) são de primeira classe. O principal gap que resta é que as saídas de um pacote não materializado são verificadas contra o seu .d.ts, mas não validadas em runtime, a menos que você as materialize. Do lado do extern/, a raiz das fontes difere entre os dois comandos: glyph run app.glyph usa como raiz o diretório do próprio arquivo, glyph build src/ usa o diretório que você indica. Um programa em um subdiretório, portanto, procura seu shim em dois lugares diferentes, e até escolhermos uma raiz, um projeto organizado assim precisa que o shim seja acessível a partir dos dois. Quando não é, a falha é explícita.
