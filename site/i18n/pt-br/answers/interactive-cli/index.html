18 · Programas em que você digita

Posso escrever um programa em que alguém digita?

Pode. io.read_line retorna assim que uma linha inteira chega e não espera o stdin fechar, então um REPL, um game loop ou um cliente de chat responde a cada linha antes de ler a próxima. Até a 0.1.62 ele esperava, e vale dizer isso com todas as letras, porque tornava impossível qualquer programa interativo.

Por que isso importa

Um leitor de linhas que só retorna no fim da entrada é um leitor de arquivos com nome de leitor de linhas. Passar um arquivo por pipe funciona perfeitamente, e é por isso que nada pegou o problema: todos os apps do repositório que liam stdin liam um pipe. Aí alguém escreveu um cliente de chat, e ele ficou em silêncio enquanto a pessoa digitava e imprimiu todas as respostas de uma vez depois do Ctrl-D.

Esse app saiu como um reprodutor de sessões sobre um arquivo JSON gravado, com um comentário no código explicando o porquê. Outros três apps tinham sido moldados em torno da mesma coisa sem que ninguém desse nome a ela: o campo minado não conseguia redesenhar entre jogadas, a aventura de texto não conseguia responder a look, e um REPL não avaliava nada até você desligar.

Veja na prática

O loop inteiro da sessão ao vivo do app de chat. Ler, aplicar, imprimir, repetir:

examples/apps/chat/main.glyph 
fn converse(limit: Option<int>) -> Server {
  let state = server.empty()
  io.println(LIVE_BANNER)
  loop {
    let text = match io.read_line() {
      Some(l) => l,
      None => { break },
    }
    match client_line(text) {
      None => { io.println(LIVE_HINT) },
      Some(sent) => {
        let done = turn(state, sent.from, sent.line)
        report(done.lines)
        mut state = done.state
      },
    }
  }
  return state
}

Rodando num terminal de verdade, com cada linha digitada a cerca de 0,6 segundo uma da outra e o stdin aberto. A coluna da esquerda são milissegundos desde o início do processo:

Um a dois milissegundos da linha digitada até a resposta. Antes da correção, nada era impresso até 6460ms, que é quando o stdin fechava. A primeira resposta numa execução completa chega por volta de 1,6 segundo, e isso é o tsx inicializando, não latência de leitura.

O que pega na prática

Um \r no final é removido, então um arquivo CRLF e um arquivo LF dão as mesmas linhas e você não fica depurando um caractere invisível numa entrada vinda do Windows. Uma entrada que termina sem quebra de linha final ainda devolve essa última linha uma vez antes do None, então a última linha de um arquivo sem quebra no final não some sem aviso. Um caractere UTF-8 multibyte dividido entre duas leituras fica guardado e é completado, em vez de virar caractere de substituição.

read_to_string esvazia o mesmo buffer, então os dois se combinam: read_line para um cabeçalho e depois read_to_string para o corpo devolve o resto, nem uma segunda cópia nem uma string vazia. Chamado primeiro, ele continua retornando todo o stdin. 200.000 linhas via pipe são contadas em uns 20ms, então ler uma linha por vez não custa throughput.

Uma linha de cabeçalho, depois o corpo 
let header = io.read_line()
let body = io.read_to_string()

Situação atual

Disponível hoje

io.read_line retorna quando uma linha chega, não quando o stream fecha, então loops de prompt/leitura/resposta funcionam tanto num terminal quanto num pipe. CRLF é normalizado, uma última linha sem terminador é entregue uma vez, caracteres multibyte sobrevivem às fronteiras entre chunks, e read_to_string pega o resto do mesmo buffer. Um teste de regressão mantém o stdin aberto e exige o eco de volta, porque um teste que passa um arquivo por pipe também passa com a implementação quebrada. io.print e io.eprint escrevem sem quebra de linha, então o prompt > de um REPL fica na mesma linha em que a resposta é digitada, e io.is_terminal / io.stdin_is_terminal dizem ao programa se ele está falando com uma pessoa ou com um pipe, então uma flag como o --stdin do app de chat deixou de ser o único jeito de perguntar.

Ainda incompleto

Um programa que quer redesenhar a tela não tem controle de cursor: std/io não tem funções de cursor ou de tela e nenhum outro módulo da stdlib as adiciona, então uma UI de terminal em tela cheia ainda significa escrever os códigos de escape você mesmo.
