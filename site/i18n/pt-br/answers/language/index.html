É uma linguagem de verdade, ou um brinquedo cheio de buracos?

Ela tem o que você procura numa base de código real: visibilidade de módulos, interfaces para restringir genéricos, defer para limpeza e helpers de concorrência. Onde ela se apoia em JavaScript, ela diz isso em vez de fingir o contrário.

Por que isso importa

Uma linguagem em que dá para escrever um arquivo mas não estruturar um projeto não é uma em que você vai apostar uma base de código. Os buracos que importam não são exóticos:

  • VisibilidadeDá para esconder um helper?
  • Restrições de genéricosUm genérico pode exigir uma capacidade?
  • LimpezaDá para liberar um handle de arquivo em todo caminho de saída?
  • ConcorrênciaDá para rodar duas coisas ao mesmo tempo e esperar as duas?

O Glyph responde a essas quatro, e faz isso sem reabrir a direção cheia de anotações que abandonou de propósito.

Interfaces restringem genéricos

Uma interface é estrutural, como uma do TypeScript: é um conjunto de assinaturas de membros que um genérico pode exigir. Sem implements, sem cerimônia nominal. Qualquer valor com os membros se qualifica, e o tsc garante isso.

interfaces restringem genéricos 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer e concorrência estruturada

O defer executa a limpeza quando o bloco termina, em todo caminho, inclusive num return antecipado ou num erro lançado. E o std/task junta trabalho concorrente sob um só tempo de vida, em vez de deixar promises soltas.

defer + concorrência estruturada 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])
Detalhes ordem de execução, e handles owned

Vários defers rodam na ordem último a entrar, primeiro a sair, e ele se combina com handles owned.

O que ele herda do JavaScript

O Glyph compila para TypeScript e roda em um motor JavaScript, então herda a ordem de avaliação, a semântica de referência para mutação e o modelo de thread única com coleta de lixo. A especificação afirma isso como garantias em vez de deixar você descobrir sozinho.

A igualdade é onde ele difere: == compara valores, records campo a campo, enquanto o === do JavaScript compara referências.

Memória manual e um modelo sem coleta de lixo não estão no roadmap; ficam fora do que uma linguagem que transpila para TypeScript é.

Não existe if, então o match tem de carregar tudo

A primeira coisa que alguém que vem do TypeScript pergunta depois de ouvir sobre exaustividade é se o match é mesmo uma condicional de uso geral ou só um jeito bonito de desestruturar uma union. É a primeira opção, e o lugar que prova isso é a atribuição.

Um match que é o valor inteiro de um let ou de um mut aceita tudo o que uma instrução aceita: um braço pode ser um bloco, um braço pode fazer await, um braço pode dar break no loop em volta, e um braço pode ler a variável que está atribuindo, que é como você acumula estado num loop sem if.

do verificador de links: rastreamento de blocos de código, e um braço com await 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}
Detalhes para o que ele compila, e de onde vêm os trechos

Os dois compilam para um switch simples que atribui a variável em cada braço, então o await fica na função async que o envolve e o acumulador é uma variável normal que o TypeScript consegue inferir. Os dois trechos são de examples/apps/linkcheck/main.glyph, um verificador de links em Markdown escrito justamente para encontrar esse tipo de coisa.

Um match usado dentro de uma expressão maior, como argumento ou operando, ainda vira uma closure, o que significa que os braços precisam ser expressões únicas. Levá-lo para um let próprio elimina essa limitação.

Um padrão pode nomear um formato mais de um nível abaixo

Uma variante com vários campos carrega um record, então um braço que quer reconhecer um formato precisa entrar nos campos desse record. Um campo agora aceita qualquer padrão: uma tag de variante, um construtor aninhado, uma desestruturação aninhada, um literal, um padrão de array.

um caso de rotação do rebalanceamento rubro-negro, num braço só 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}
Histórico o contorno antes da 0.1.90

Até a 0.1.90, a posição de campo aceitava um nome e mais nada: dava para renomeá-lo, e só. Casar uma tag ali era erro de compilação, e um construtor aninhado derrubava o parser. O contorno era vincular cada campo e escrever um match aninhado por nível, o que, para algo como o rebalanceamento de uma árvore rubro-negra, é outro programa: os braços deixam de se alinhar com os casos e cada nível repassa as variáveis do nível de cima.

Há uma consequência que vale conhecer antes de escrever um. Um campo que testa um valor pode falhar, então o braço deixa de contar como cobertura da sua variante, e um match cujo único braço Node é Node({ color: Red, ... }) é reportado como não exaustivo até que um braço irmão ou um else cuide do resto.

Detalhes por que ele exige o catch-all, e a posição de array

O verificador prova cobertura sobre um conjunto de tags, não sobre um produto de campos, então ele não vai deduzir que um braço Red e um braço Black juntos esgotam Node. Exigir o catch-all é a leitura que não deixa um match passar do fim em tempo de execução. O mesmo vale onde não há variantes para contar: um match sobre um record simples em que todo braço testa um campo precisa de um else no final.

Um lugar onde isso chega e que talvez você não espere é a posição de array. [Black] como braço inteiro contava como casar com qualquer array de um elemento, então um match que dependia dele era certificado como exaustivo e depois pegava esse braço também para [Red]. Um elemento em PascalCase é uma referência a variante aqui também, então um match assim agora dá E0208 em arrays de tamanho 1. Vincule o elemento e faça o match nele separadamente. A tradução por baixo ainda é a antiga, e é por isso que a checagem foi a metade publicada primeiro.

E0208

E o compilador sabe o que o match produziu

A pergunta seguinte é a que decide se algo disso sustenta peso: depois que você extrai um valor de um ramo, o Glyph sabe o tipo dele, ou dá de ombros e deixa o tsc resolver depois? Um match agora assume o tipo dos braços quando eles concordam, e o compilador sabe que T.parse retorna Result<T, Array<Issue>>, que é o formato sobre o qual a maior parte do código real ramifica.

do divisor de despesas: sem anotação, e i é um number 
let wire = match WireLedger.parse(decoded) {
  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },
}

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...
}
Histórico antes da 0.1.45

Até a 0.1.45 dava de ombros. Toda expressão match era tipada como desconhecida, então um valor que saía da única construção de ramificação da linguagem ficava sem tipo dali em diante.

Detalhes o que dava errado em silêncio, e como a junção funciona

As duas metades disso são coisas que davam errado em silêncio. O loop emite wire.expenses.entries(); quando o tipo do que é iterado é desconhecido, ele emite Object.entries(...) no lugar e i é a string "0", o que é TypeScript válido, então o build saía limpo e o programa imprimia 01:a quando queria dizer 1:a. E wire.expensez agora é [E0210] type WireLedger has no field expensez vindo do Glyph, na linha do .glyph, em vez de um TS2339 no TypeScript gerado.

A junção é igualdade no topo: um braço que termina em return não vota, e braços cujos tipos discordam deixam o resultado desconhecido, como antes. Ela olha um nível mais fundo só num argumento de tipo, então None => [] concorda com um braço Array<string> em vez de derrubar o match inteiro, e o loop logo depois continua vinculando um number. A mesma cadeia sobre record.get funciona pelo mesmo motivo: as seis funções do std/record levam o tipo do valor do record que você passa. O trecho é de examples/apps/settle/main.glyph, que carregava a anotação que isso eliminou.

Uma busca com fallback vazio

Esse é o formato em que isso mais custava. record.get sobre um Record<string, Array<string>> é um Option<Array<string>>, e [] é um array de nada em particular, então os dois braços concordam em Array e o tipo do elemento vem do braço que tem um.

do resolvedor de dependências: uma busca, um fallback vazio, um percurso por índice 
let path = match record.get(res.reached, name) {
  Some(p) => p,
  None => [],
}

for i, hop in path {               # i is a number, so the indent nests
  let indent = string.repeat(STEP, i + 1)
  mut out = array.push(out, "${indent}${hop}")
}
Histórico antes da 0.1.55

Até a 0.1.55 eles eram comparados por igualdade, [] contava como discordância, e o loop abaixo imprimia 01:x num build sem diagnósticos em que o tsc --strict passava. O código é examples/apps/depsolve/main.glyph, que antes abria com let path: Array<string> sob um comentário de três linhas explicando que a anotação era essencial.

Preciso escrever pad_start eu mesmo?

O primeiro buraco que você encontra num programa real não é um recurso do sistema de tipos. É procurar string.slice e não encontrar nada.

Esses onze nomes vêm na biblioteca agora, e as cópias foram apagadas de todos os sete apps que as tinham.

Histórico as cópias que os apps carregavam antes da 0.1.47

Cinco rodadas seguidas de dogfooding registraram a mesma lista, e até a 0.1.47 seis apps neste repositório tinham o seu próprio repeat, cinco o seu próprio pad_start, e todos tinham um loop onde cabia um fold.

Onde eles diferem do TypeScript

Três deles se afastam de propósito dos homônimos do TypeScript.

  • repeatrepeat retorna "" com uma contagem negativa, onde o TS lança erro, e é isso que torna repeat(pad, width - len(s)) seguro numa string que já é longa demais.
  • index_ofAs duas funções index_of retornam Option<number> em vez de -1, porque -1 é um number que passa na checagem de tipos em todo lugar onde um índice real passa e falha bem longe da chamada.
  • replace_allA substituição existe só como replace_all, então não há uma forma que troca só a primeira ocorrência para confundir com String.prototype.replace, que troca uma ocorrência só, sem avisar.

Por que o fold importa

O fold é o que compra um pilar em vez de só economizar digitação. mut é o registro buscável de todo lugar onde o estado muda, e sem fold, grep mut volta cheio de loops de contagem que não alteram nada que interesse a quem revisa.

Apagar as versões feitas à mão levou examples/apps/ de 192 pontos de mutação para 161.

Detalhes como a reescrita foi conferida

A reescrita foi conferida pela saída, não por revisão: os sete apps rodaram com entradas fixas antes e depois, 26 arquivos de stdout, códigos de saída e respostas HTTP, todos idênticos byte a byte.

Dá para percorrer um diretório e saber o que quebrou?

O std/fs veio com seis funções e nenhuma listava um diretório.

  • fs.read_dirfs.read_dir retorna os nomes das entradas um nível abaixo.
  • fs.is_dirfs.is_dir responde com um bool como o fs.exists faz.
  • fs.statfs.stat retorna um FileInfo com is_dir, is_file, size em bytes e modified em milissegundos desde a epoch, que o time.format_iso formata diretamente.

Não há walk recursivo nem glob; um percurso são essas três mais path.join em umas dez linhas.

Histórico o contorno que elas substituíram

O verificador de links deste repositório passava por cima da stdlib e ia direto no readdirSync do Node, e descobria quais caminhos eram diretórios tentando lê-los e inspecionando o errno que voltava. As duas metades disso foram corrigidas.

As falhas têm nome

O lado das falhas mudou mais. Agora os cinco tipos de que um programa de fato se recupera têm nome, e um errno sem nome chega intacto na cauda Other.

O verificador sabe que essa taxonomia é fechada, então um match sobre err.kind é cobrado no mesmo nível de uma union que você mesmo declarou: cubra os seis e você não precisa de else, deixe um de fora e o build falha com E0200 citando fs.ErrorKind.

E0200E0210
percorrer uma árvore, e dizer o que deu errado 
let names = fs.read_dir(dir)?
for name in names {
  let child = path.join([dir, name])
  match fs.is_dir(child) {
    true  => visit(child),
    false => {
      let info = fs.stat(child)?
      report_size(child, info.size)
    },
  }
}

match err.kind {                        # no else arm: E0200 if you miss one
  fs.ErrorKind.NotFound         => io.eprintln("no such path"),
  fs.ErrorKind.NotADirectory    => io.eprintln("that is a file"),
  fs.ErrorKind.IsADirectory     => io.eprintln("that is a directory"),
  fs.ErrorKind.AlreadyExists    => io.eprintln("already there"),
  fs.ErrorKind.PermissionDenied => io.eprintln("cannot read it"),
  fs.ErrorKind.Other({ code })   => io.eprintln("errno ${code}"),
}
Detalhes a taxonomia antiga, campos verificados, e como testar a verificação você mesmo

FsError.kind era { tag: string }, com NotFound como toda a taxonomia, então distinguir “esse caminho é um diretório” de “esse caminho não existe” significava comparar uma string de errno.

fs.FsError e fs.FileInfo também têm campos verificados, então err.mesage dá E0210 no seu código Glyph em vez de um erro do tsc no TypeScript gerado.

Essa checagem está ativa. Apague o braço PermissionDenied do match acima e o glyph check --no-tsc para com E0200: match não exaustivo sobre fs.ErrorKind, faltando as variantes PermissionDenied. Quando o modelo da stdlib foi escrito, ele cobria só tipos de retorno, e um match como este compilava sem erro e lançava exceção em tempo de execução; os formatos de campos e variantes de fs.FsError, fs.FileInfo e fs.ErrorKind agora estão modelados.

Duas adições menores

Duas mudanças menores entraram junto, ambas vindas do mesmo app.

  • regex.captures_allregex.captures_all dá os grupos de captura de cada correspondência, em vez de só o texto casado, então uma varredura simples de key=value deixa de ser um loop feito à mão.
  • task.pool_settledtask.pool_settled é o task.pool com o comportamento de falha do all_settled: concorrência limitada, um resultado por tarefa, e um host fora do ar custa só o resultado daquele host, e não todos os resultados que o pool tinha juntado.

Como saber se as funções são as certas?

Porque o app que as pediu teve de parar de contorná-las antes de a release contar como concluída.

Uma função de biblioteca publicada e um contorno que sobrevive a ela são afirmações diferentes, então a mesma mudança que adicionou essas quatro apagou as cópias do verificador de links: o import de readdirSync, as duas comparações de string de errno, 97 linhas de scanner feito à mão e o pool que falhava no primeiro erro. Saíram 122 linhas.

Duas mudanças de comportamento, medidas

Duas dessas remoções mudaram o que o programa faz, e a diferença foi medida em vez de discutida.

  • Um diretório ilegívelAponte a versão antiga e a nova para uma árvore com um diretório que você não consegue ler: a nova imprime permission denied e conta o caminho como ilegível, e a antiga, que só conseguia perguntar se o errno era EISDIR, deixava o caminho de fora do relatório.
  • Uma URL que falhaFaça uma de três URLs lançar erro: o pool_settled imprimiu as três linhas e apontou a falha, e o pool não imprimiu nada e morreu numa rejeição não tratada, levando junto os dois resultados bons.
Detalhes a reescrita do scanner e a preocupação com a alternância

A reescrita do scanner também resolveu uma dúvida de design. Como um grupo de captura que não participou aparece como "", igual a um que casou vazio, parecia que o captures_all não conseguia dizer qual ramo de uma alternância disparou. Consegue, se você escrever o grupo de cada ramo em volta da construção inteira, e não em volta da parte que você quer: um grupo que disparou começa então com `, [, ! ou <, e não pode estar vazio. A parte que pode ser vazia, o destino do link, fica aninhada dentro e nunca é o que você pergunta. Isso transformou um percurso de 180 linhas, caractere por caractere, em dois padrões e um despacho de 12 linhas, com saída idêntica byte a byte na própria documentação do repositório e numa fixture feita para quebrá-lo.

Dinheiro não roda em float

O buraco que encerraria na hora a avaliação de uma fintech é fazer contas de dinheiro com number IEEE-754, onde 0.1 + 0.2 não é 0.3 e valores acima de 253 perdem precisão em silêncio.

O std/decimal é ponto fixo decimal exato sobre BigInt: um inteiro de precisão arbitrária com um número fixo de casas decimais, então adição, subtração e multiplicação são exatas e a divisão recebe uma escala e um arredondamento explícitos. Um valor malformado vira um Err no parse, nunca um NaN silencioso.

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

Inteiros grandes

Para números inteiros grandes e exatos, ids de conta e contadores, existe o tipo bigint: os literais são 123n, ele vira um bigint de verdade no TypeScript, e um campo de record tipado como bigint valida typeof === "bigint" na fronteira, então um id enviado como number no JSON é rejeitado em vez de ser arredondado em silêncio acima de 253.

Um callback async finalmente tem um tipo

Um tipo de função era fn(A) -> T e mais nada, o que emite (a: A) => T. Um corpo async não cabe nisso, então uma função que retornava uma tarefa adiada, ou um record de handlers async, tinha de ficar sem anotação e o verificador deixava de olhar.

async fn(A) -> T é esse tipo que faltava. Ele emite (a0: A) => Promise<T>, e async fn() sem retorno emite () => Promise<void>.

uma tarefa adiada, e um mapa de handlers 
fn task_for(url: string) -> async fn() -> Fetched {
  return async fn() -> Fetched { return { url: url, body: await fetch_one(url) } }
}

type Handler = async fn(string) -> string

async fn dispatch(routes: Record<string, Handler>, name: string, arg: string) -> string {
  return match record.get(routes, name) {
    Some(h) => await h(arg),
    None    => "no route",
  }
}
Detalhes como o Glyph distingue funções comuns de funções async

O próprio Glyph separa os dois, em vez de deixar isso para o tsc: uma função comum onde se espera uma async é E0204 num return e E0211 num argumento de chamada, e a mensagem cita os dois lados.

O único caso que ele não julga é um retorno void, em que o TypeScript aceita qualquer função.

Um tipo recursivo, casado até o fundo

Uma union pode citar a si mesma dentro do próprio conteúdo, com seus parâmetros de tipo, e um braço de match pode aninhar um padrão de construtor dentro do campo de outro padrão de construtor. Junte as duas coisas e as regras de balanceamento de uma árvore rubro-negra viram quatro braços: cada um nomeia o formato exato que reescreve, e quem verifica o formato é o compilador, não um comentário acima dele afirmando isso.

um dos quatro casos de rotação 
type Tree<K, V> =
  | Leaf
  | Node({ color: Color, left: Tree<K, V>, key: K, value: V, size: int, right: Tree<K, V> })

fn balance<K, V>(t: Tree<K, V>) -> Tree<K, V> {
  return match t {
    Node({ color: Black, left: Node({ color: Red, left: Node({ color: Red, left: a, key: xk, value: xv, right: b }), key: yk, value: yv, right: c }), key: zk, value: zv, right: d }) => node(
      Red,
      node(Black, a, xk, xv, b),
      yk,
      yv,
      node(Black, c, zk, zv, d),
    ),
    // the other three cases, then:
    other => other,
  }
}

    A visibilidade é checada em anotações de tipo, não em valores lidos por um namespace: lib.helper() com helper privado ainda é um erro do tsc, não do Glyph.

Async

  • Um await no topo, no inicializador de um const no nível do módulo, é permitidoE0222
    Detalhes

    O contexto async agora é checado (E0222) exceto num ponto: o inicializador de um const no nível do módulo não tem função em volta, então um await no topo ali é permitido e o ESM emitido o executa.

Tipos inferidos

  • Braços que discordam no topo do tipo deixam o resultado desconhecido para o Glyph
    Detalhes

    A junção dos braços ainda exige que eles concordem no topo do tipo: quando produzem tipos diferentes, o resultado é desconhecido para o Glyph e só o tsc verifica o que você faz com ele.

  • Nove funções da stdlib estão na mesma situação
    Detalhes

    Nove funções da stdlib estão na mesma situação. Seis recebem um argumento final opcional (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify) e a checagem de aridade compara um número com um número, então modelá-las daria um erro falso em toda chamada que omite o último argumento; array.map, flat_map e zip tiram o tipo do elemento de um callback em que o verificador não entra.

    Um valor que sai direto dessas nove precisa de uma anotação antes de você iterá-lo com índice, e um match sobre string.index_of sem braço None ainda faz o build sem erro e lança exceção em tempo de execução. array.index_of está modelada e relata E0200.

  • Membros e aridade de chamada sobre um valor que o verificador não conseguiu tipar não são checados
    Detalhes

    Membros e aridade de chamada sobre um valor que o verificador não conseguiu tipar continuam sem checagem nessa fronteira, em vez de virar erro.

Biblioteca

  • string indexa unidades de código UTF-16, e nenhum chars ou char_at está planejado
    Detalhes

    Do lado da biblioteca, string indexa unidades de código UTF-16, como len e split sempre fizeram, e isso está decidido: não existe chars nem char_at e nenhum está planejado, porque uma metade de par substituto devolvida parece um caractere até o momento em que é escrita. Codifique com encoding.hex_encode e leia dois dígitos hex por vez.

  • captures_all não dá offsets; fs.read_dir mantém a ordem do sistema operacional
    Detalhes

    O captures_all devolve grupos e nenhum offset, então um scanner que precisa saber em que ponto da linha uma correspondência começou ainda escreve o próprio loop, e o fs.read_dir devolve as entradas na ordem do sistema operacional, então ordene-as quando a saída precisar ser reproduzível.

Padrões

  • Um construtor com conteúdo num campo falha numa union acessada por um import de namespaceE0300
    Detalhes

    Um padrão de campo aninhado ainda tem uma limitação: um construtor que carrega conteúdo, num campo, numa union acessada por um import de namespace. import tree { Node } seguido de Node({ left: Node({ key: k }) }) compila, e import tree seguido de tree.Node({ left: tree.Node({ key: k }) }) dá E0300 na mesma union.

  • Uma union genérica sobre o próprio parâmetro aceita o braço aninhado e é checada quanto a variantes faltandoE0200
    Detalhes

    A outra limitação acabou: uma union genérica sobre o próprio parâmetro (type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> })) recusava o braço aninhado que a mesma union sem o parâmetro aceita, e agora o aceita, tanto com um parâmetro de tipo aberto quanto numa instanciação concreta. A mesma busca decidia se o match era checado quanto a variantes faltando, então até esta release um match sobre Tree<K> podia omitir Leaf, fazer o build sem erro, passar no tsc --strict e lançar exceção em tempo de execução, enquanto a forma não genérica dava E0200.

    As duas formas relatam o erro, e mover a union para trás de um import não muda mais a resposta: um match sobre um Tree<string> importado que omite Leaf dá E0200 citando Leaf, igual ao Tree não genérico importado. Esse era outro caminho de código, checado separadamente, e até esta release ia no sentido contrário, fazendo o build sem erro e lançando exceção em tempo de execução.

  • A cobertura de uma union importada nunca checa o conteúdo das variantes
    Detalhes

    Uma coisa sobre a cobertura de uma union importada ainda vale saber antes de confiar nela: o conteúdo das variantes também nunca é checado, então B(X), onde X é uma variante da própria union do conteúdo, casa com todo B em vez de relatar o Y que falta, e isso não tem nada a ver com genéricos.

    Vincular um campo, ou casar nele uma tag sem conteúdo, funciona em todos os casos.
