Posso escrever um servidor, ou o processo simplesmente termina?

Pode escrever um servidor. main faz o setup e retorna, e o processo continua vivo enquanto houver sockets e timers pendentes, a mesma regra que o Node usa. Até a 0.1.63 não era assim: o runner derrubava o processo no momento em que main retornava, então um servidor fazia bind na porta e morria no mesmo tick.

Por que isso importa

Essa é a diferença entre uma linguagem que roda um script e uma que roda um serviço. Um servidor, um file watcher, um bot segurando uma conexão com um gateway, um executor de jobs: nenhum deles termina dentro de main. Eles registram handlers e entregam o processo aos eventos.

Histórico como falhava antes da 0.1.63

O comportamento antigo falhava do pior jeito possível, que é em silêncio. glyph run app.glyph --serve 4100 não imprimia nada, nem a linha dentro do callback de listen, e saía com 0. Nada no código parecia errado e a checagem de tipos passava. Um agente que esbarra nisso não tem erro para reportar nem motivo para achar que algo falhou.

Depois que main retorna

Duas coisas que vale saber. O return 0 roda antes de o primeiro cliente se conectar: é o código com que o processo vai sair um dia, não uma afirmação sobre quando ele sai.

E qualquer coisa que falhe depois que main retornou precisa definir o próprio código de saída, porque o valor de retorno de main já foi usado. É para isso que serve o handler de error. Sem ele, um servidor que não consegue fazer bind na porta esvazia o event loop e sai com 0, reportando sucesso.

Detalhes tipos para o import de net

net é um builtin do Node, então é um import comum, mas não está entre os seis para os quais o compilador já traz tipos ambientes (fs, http, path, os, crypto, url). Ou você instala @types/node e o build passa a preferi-lo, ou coloca uma declaração em .types/net.d.ts ao lado do seu código, que é o que o app de chat faz para não precisar de nenhuma dependência.

Um de verdade

examples/apps/chat é um servidor de chat que mantém vários clientes TCP ao mesmo tempo. As partes que não tocam a rede ficam separadas e testáveis: remontagem de linhas, roteamento e o motor das salas são funções puras verificadas por @example, e um arquivo conversa com os sockets.

Três clientes conectados ao mesmo tempo 
alice> /join #general

carol> /join #random
alice> hello everyone

alice sees:  1  #general <alice> hello everyone
bob sees:    1  #general <alice> hello everyone
carol sees:  (nothing: she is in #random)

Remontagem de linhas

O TCP não entrega mensagens, entrega bytes, então o final de um chunk normalmente é meia linha. Essa remontagem é uma função pura com os casos chatos escritos como exemplos em vez de provocados num socket:

Na outra direção: um cliente de longa duração

Um bot tem o mesmo formato, apontado para fora. examples/apps/discord é um cliente do gateway do Discord: conecta via WebSocket, se identifica, manda heartbeats no intervalo que o servidor define, acompanha um número de sequência para que uma conexão derrubada seja retomada em vez de começar do zero, percebe quando a conexão está aberta mas morta e espera um tempo crescente entre reconexões.

A parte que vale copiar é onde a lógica fica. Decidir o que fazer com um RECONNECT, um heartbeat perdido ou um token recusado é uma função pura que recebe uma sessão e um evento e devolve uma sessão nova e uma lista de ações. Um módulo executa essas ações num socket real.

É por isso que a lógica de reconexão, que é a parte difícil de acertar, é verificada por @example em vez de desconectando um cabo de rede:

Histórico três bugs, dois mocks

Cada um desses três exemplos é um bug que estava no código antes. Escrever um gateway mock e apontar o bot para ele pegou um deles. Os outros dois foram pegos por um segundo mock escrito a partir da documentação do Discord, e não a partir do cliente, que manda as coisas que um mock cooperativo nunca manda: um pedido de heartbeat sem aviso e um código de fechamento que significa "seu token está errado, pare de tentar". Um mock escrito pelo autor do cliente só testa as partes do protocolo que o autor leu.

Situação atual

Disponível hoje

  • Retornar de main define o código de saída sem parar o processo, então servidores, watchers e event loops rodam.
  • Um programa que só calcula ainda sai no momento em que main retorna, com o mesmo código, então nada mudou para programas curtos.
  • Builtins do Node como net são imports comuns, e uma exceção no setup ainda encerra o programa
    Detalhes

    Builtins do Node como net são imports comuns, e um programa que lança uma exceção durante o setup ainda termina, agora depois que o diagnóstico chegou a um stderr redirecionado em vez de possivelmente ser cortado pela saída.

  • std/timers agenda trabalho (after, every, cancel, unref) e std/websocket abre uma conexão, então nenhum dos dois precisa de uma declaração escrita à mão.

Ficando mais preciso

  • Um listener que não consegue fazer bind depois que main retornou sai com 0, a menos que o programa diga o contrário
    Detalhes

    Um listener que não consegue fazer bind depois que main retornou sai com 0, a menos que o programa diga o contrário: process.set_exit_code(1) registra a falha sem derrubar o trabalho ainda em andamento, e process.exit(1) para na hora.

  • O compilador ainda não consegue avisar que você esqueceu.
  • E ainda não há como declarar que uma função não retorna, então o main de um servidor carrega um return 0 que nunca é alcançado.
