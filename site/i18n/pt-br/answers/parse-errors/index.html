27 · Falhas de parse

Quando um parse falha, eu descubro o motivo?

Sim. Cada issue aponta o campo, diz qual regra o valor violou e carrega um code que você pode usar para ramificar. Um campo restrito por um predicado where informa o próprio predicado, então a rejeição leva por grep à linha que impôs a regra.

Por que isso importa

Um validador que diz "este payload está errado" fez metade do trabalho. O handler ainda precisa decidir: é um cliente que esqueceu um campo ou um cliente que mandou uma senha de quatro caracteres? Um caso é 400, o outro é 422, e se o validador não diz, você acaba fazendo o parse do mesmo body duas vezes, com dois tipos diferentes, para recuperar uma informação que o validador já tinha.

Foi exatamente isso que aconteceu ao construir uma API de autenticação em Glyph. Um cadastro sem a chave password voltava como weak_password, porque ausente e curta demais produziam a mesma string.

Veja na prática

Um tipo, uma restrição:

signup.glyph 
pub type Password = string where value.length >= 8

pub type Signup = {
  email: string,
  password: Password,
}

Quatro payloads ruins, quatro respostas diferentes. Cada um é um Issue, mostrado como code | path | message:

Signup.parse(...) 
// { "email": "user@example.com" }
missing     ["password"]  field `password` is required

// { "email": "user@example.com", "password": "short" }
refinement  ["password"]  expected Password (string where value.length >= 8)

// { "email": 42, "password": "longenough" }
type        ["email"]     field `email` must be string

// [1, 2, 3]
type        []            expected Signup (an object), got an array

O segundo é o ponto. value.length >= 8 é escrito uma vez, no tipo, e a rejeição o cita literalmente. Cole essa string, tirada do body de um HTTP 422, no grep e você cai na declaração que a produziu. Ninguém precisa manter uma cópia da regra na camada de mensagens de erro, que é como as duas acabam divergindo.

O quarto já foi pior do que uma mensagem ruim. Para o typeof, um array é um objeto, então um record sem campos obrigatórios aceitava um array direto, e um [1, 2, 3] enviado voltava como um issue confuso por campo declarado, sem nenhum mencionar que você tinha mandado uma lista.

Tipos aninhados respondem por si mesmos

Um campo cujo tipo tem seu próprio descritor é validado pelo parse desse tipo, e os issues voltam com o nome do campo na frente do path. Assim, um Password aninhado dois níveis abaixo informa ["body", "password"] e ainda carrega a própria mensagem. Você recebe o local e o motivo no mesmo issue, sem rodar nada de novo.

O código, não a string

Issue carrega um code opcional: "missing", "type", "refinement" ou "unexpected". Ramifique por ele. Comparar texto de mensagem é a fragilidade que o Glyph existe para eliminar, e a mensagem é para a pessoa que lê o body da resposta.

Uma separação entre 400 e 422 que não lê a mensagem 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code é opcional, então um Issue que você monta à mão, e todo consumidor escrito antes de ele existir, continuam compilando sem mudança.

Situação atual

Disponível hoje

Records e tipos where informam a regra que falhou, não só o campo: "missing" para um campo obrigatório ausente, "type" para o formato errado (incluindo um não objeto ou um array), "refinement" para um valor que passou no tipo base e falhou no predicado, e "unexpected" para uma chave que o tipo não declara. Um refinement cita seu predicado. Um campo cujo tipo tem descritor delega a ele, então os issues aninhados chegam com o path completo. Campos opcionais (f?: T) nunca são informados como ausentes.

Ficando mais preciso

Dois limites. Um campo tipado por algo sem descritor próprio, um parâmetro de tipo sem restrição ou um tipo importado de um .d.ts escrito à mão, ainda recebe a verificação rasa e um issue "type"; o compilador não sintetiza um descritor para esses casos, e rodar glyph gen dts sobre a declaração é o que dá um descritor a eles. Um módulo que declarava seu próprio tipo chamado Issue sombreava o do prelude dentro do arquivo emitido e quebrava todos os descritores daquele módulo; desde a 0.1.60 essa declaração é E0110 na linha que nomeia o tipo, então você descobre onde está o problema em vez de ler um erro do tsc sobre código gerado.
