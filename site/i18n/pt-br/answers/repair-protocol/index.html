23 · Consertar um build quebrado

Quando o build falha, o compilador diz ao meu agente como consertar?

Ele diz o que está errado como dados, não como uma frase para interpretar: os dois tipos, o símbolo culpado como module::name, e a lista finita do que poderia estar legalmente no lugar da coisa errada. O glyph check --agent acrescenta o que a edição de reparo não pode quebrar. Quando a resposta está totalmente determinada, o glyph fix a escreve.

Por que isso importa

O ciclo de um agente em volta de um compilador é: ler o erro, chutar a edição, rebuildar. O chute é onde o estrago acontece, e acontece porque o erro é uma string. Um agente que lê "non-exhaustive match on OrderStatus" sabe que faltam braços no match. Não sabe o que as variantes ausentes carregam, então escreve Paid("tx_1") e descobre pelo próximo diagnóstico. Ou lê a palavra "exhaustive", acrescenta um braço else, e o build fica verde depois de jogar fora justamente a garantia que o diagnóstico existia para proteger.

O compilador sabia de tudo isso. Sabia as variantes da union e seus payloads, sabia que um else abriria mão do selo, e descartou as duas coisas uma linha antes da resposta.

Veja na prática

Um projeto com dois módulos. orders declara a union; main escreve um match sobre ela e trata um caso. O glyph check --agent, resumido às chaves que importam aqui:

glyph check --agent --no-tsc src 
{
  "code": "E0200",
  "severity": "error",
  "stage": "typecheck",
  "message": "non-exhaustive match on `OrderStatus`: missing variants
              `Paid`, `Cancelled`",
  "help": "Add an arm for each missing variant.",
  "file":   "main.glyph",
  "module": "main",
  "entity": "main::describe",
  "cause":  "orders::OrderStatus",
  "related": ["Pending", "Paid", "Cancelled"],
  "missing_variants": ["Paid", "Cancelled"],
  "expected": null, "actual": null, "alternatives": null,

  "constraints": [
    "preserve exhaustiveness: this match must name every case of
     `OrderStatus`, so add one arm for each of `Paid`, `Cancelled`.",
    "do not add an `else` arm: `OrderStatus` is declared in this project,
     and a catch-all forfeits the guarantee that adding a variant to it
     later forces this match to be updated (D9)."
  ],

  "symbols": [
    { "entity": "orders::OrderStatus", "kind": "union", "pub": true,
      "type": "Pending | Paid({ transaction_id: string }) | Cancelled",
      "exhaustive_match": true,
      "variants": [
        { "name": "Pending", "payload": null, "construct": "Pending" },
        { "name": "Paid",    "payload": "{ transaction_id: string }",
          "construct": "Paid({ transaction_id: string })" },
        { "name": "Cancelled", "payload": null, "construct": "Cancelled" }
      ] }
  ],
  "symbols_absent": [],

  "explain": { "command": "glyph --explain E0200",
               "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200" }
}

Três coisas merecem destaque. cause é o símbolo culpado, e é diferente de entity, que é a declaração onde o diagnóstico está: aqui a edição acontece em main::describe e a forma que ela precisa seguir vem de orders::OrderStatus. Os dois são endereços que as outras ferramentas aceitam, então uma resposta se encadeia na próxima sem recalcular nada.

constraints não são o reparo. Cada uma é algo que o compilador já impõe, escrito por extenso para que a edição que resolve o diagnóstico não quebre a garantia por trás dele. A segunda restrição é o motivo de a chave existir: um braço else é válido, deixaria o build verde, e a restrição diz quanto custa escolhê-lo.

symbols é a resposta de glyph_symbol para cada símbolo que o diagnóstico cita, então a próxima edição do agente não precisa de uma segunda chamada. Um símbolo que a ferramenta recusa aparece em symbols_absent com o motivo, o que separa "não olhamos" de "olhamos e não está lá".

Toda chave está sempre presente. Um fato que o compilador não tem chega como um null explícito, nunca como uma chave ausente, então a ausência tem uma única forma em todos os códigos, tanto na CLI quanto no MCP.

Quando a resposta está determinada, o compilador a escreve

O glyph fix aplica só os reparos que o compilador decide sozinho: imports não usados, a cabeça de um braço que não é uma variante quando o verificador calculou exatamente uma sugestão, e um campo que o record não declara quando exatamente um campo declarado está a um caractere de distância. O match acima não é um desses casos.

glyph fix src, no match acima 
glyph fix: removed 0 unused import(s) across 0 file(s).
glyph fix: declined E0200 in src/main.glyph: the compiler does not
           determine what a missing arm should do, so `glyph fix`
           writes none: add an arm for each of `Paid`, `Cancelled`.
           `glyph check --agent` gives the pattern each case takes.

// src/main.glyph is unchanged, and glyph check still fails with E0200.

O compilador sabe quais casos faltam e o padrão de cada um. Ele não sabe o que o programa deve fazer quando um pedido está Paid, e qualquer corpo que escrevesse seria um chute que compila. Até a 0.1.128, o glyph fix escrevia esse chute: um braço por caso, com um corpo que imprimia o caso e chamava process.exit(1). O programa então passava no check, no tsc e no build, e o glyph query variants relatava o match como exaustivo, ou seja, o caso ausente tinha passado de erro de compilação para crash em tempo de execução, sem nada que o apontasse.

Por isso a regra recusa, e nomeia os casos. Tudo o que é preciso para escrever os braços já está na resposta do --agent acima: missing_variants, e a forma construct de cada variante em symbols. Escrever os braços cabe a você ou ao seu agente, como qualquer outro código cujo comportamento o compilador não consegue inferir.

O que o glyph fix escreve, ele escreve sem chutar, e cada regra que não consegue decidir uma resposta imprime a recusa e o motivo na mesma saída do que foi aplicado. Dois campos a um caractere de um erro de digitação são dois, não um, e ele diz isso em vez de escolher.

A explicação do próprio código, como dados

O glyph --explain <CODE> --json responde com a explicação completa, o help de uma linha, a URL da documentação e um programa errado do corpus negativo do compilador, junto com o diagnóstico que este compilador gera para ele. O diagnóstico é compilado na hora em que você pede, não armazenado, então não pode divergir do que o compilador realmente diz.

glyph --explain E0200 --json 
{
  "code": "E0200",
  "title": "non-exhaustive match",
  "explanation": "A `match` over a tagged union must handle every variant.
    Unions are sealed (D9): adding a variant later forces every match to be
    updated, so a missing variant cannot silently fall through at runtime ...",
  "help": "Add an arm for each missing variant.",
  "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200",
  "counter_example": {
    "name": "alias_of_local_union_not_exhaustive",
    "expected_error": "E0200",
    "files": [ { "path": "alias_of_local_union_not_exhaustive.glyph",
                 "source": "module main\n\ntype Shape =\n  | Circle\n ..." } ],
    "diagnostic": { "code": "E0200",
                    "message": "non-exhaustive match on `Shape`: missing variants `Tri`",
                    "cause": "alias_of_local_union_not_exhaustive::Shape",
                    "related": ["Circle", "Square", "Tri"],
                    "missing_variants": ["Tri"] },
    "corrected": null,
    "corrected_absent": "`tests/negative/` pairs no repaired program with a case:
      an entry is a wrong program and the code it draws. A fix invented here would
      compile nowhere and be checked by nothing."
  }
}

Um código que o corpus não cobre volta com counter_example: null e uma frase dizendo que o corpus não tem caso para ele, em vez de um exemplo inventado. O corpus afirma o que cobre e nada sobre o resto.

O glyph --explain entrega um caso por código. O corpus inteiro também pode ser lido: glyph llms --negative E0200 imprime todos os programas errados que geram o código, cada um compilado na hora, e quando um segundo corpus pareia um programa que o tsc --strict aceita com o Glyph que o recusa, ele vem junto. Sem código, lista 102 casos em 46 dos 70 códigos e nomeia os 24 que não têm nenhum, então a cobertura é declarada, não deduzida do que voltou. Isso e o resto do que o compilador publica sobre si mesmo estão em uma página própria.

Situação atual

Disponível hoje

Todo diagnóstico traz expected, actual, cause, alternatives (com alternatives_kind dizendo se lista fields, members, variants, literals ou exports, definido onde o erro é gerado), related, module, file e explain, preenchidos a partir do erro que o compilador gerou em vez de recalculados, e cada um é um null explícito quando o compilador não tem esse fato. file é um caminho relativo à raiz de resolução, e o relatório nomeia essa raiz em project_root, então o caminho abre. O glyph check --agent acrescenta constraints e symbols por diagnóstico. O glyph fix aplica três regras (E0106, E0210, E0220) e declara cada recusa com o motivo, incluindo todo E0200, que ele relata e nunca escreve. O glyph --explain <CODE> --json retorna a explicação com um contraexemplo compilado, e o glyph llms --negative <CODE> retorna o corpus inteiro de programas errados que o geram.

Onde para

cause no E0211 é null: o símbolo culpado em um argumento de chamada é um parâmetro, e module::fn.param não é algo que o vocabulário de identidade consiga expressar, então o null é proposital, não um esquecimento. corrected em um contraexemplo é sempre null, porque o corpus negativo não pareia nenhum programa reparado com um caso, e 24 dos 70 códigos não têm caso algum. O glyph fix escreve três regras e nada mais, e não escreve braço nenhum para um match não exaustivo: esses ficam para você ou seu agente, com os casos e seus padrões no diagnóstico. Tudo o que ele recusa, recusa em voz alta.
