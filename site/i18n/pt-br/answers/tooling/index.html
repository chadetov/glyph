Como é a experiência de editor, depuração e erros?

glyph lsp fala o Language Server Protocol via stdio, então qualquer editor com cliente LSP ganha diagnósticos, tipos no hover, go-to-definition, autocomplete e format-on-save. Há uma extensão para VS Code no repositório; ela ainda não está no Marketplace, então você faz o build a partir do código-fonte. Todo erro traz um código estável, a correção e o motivo.

Por que isso importa

Editar uma linguagem que o seu editor não entende parece um retrocesso, e no começo essa reclamação era justa. Não é mais: o editor oferece as comodidades modernas, e os erros são escritos para ensinar, não só para rejeitar.

É um LSP de verdade, ou só um plugin de VS Code?

De verdade. O compilador vem com um language server que você inicia com glyph lsp, que fala o Language Server Protocol via stdio (o transporte JSON-RPC padrão que todo cliente LSP entende).

A extensão de VS Code incluída é um cliente fino em volta dele, mas nada é específico do VS Code: aponte qualquer editor com suporte a LSP, Neovim, Helix, Zed, Emacs (eglot), para glyph lsp e ele se comporta igual.

É o mesmo binário que você já instalou (npx @glyphlang/glyph lsp), então não há servidor separado para baixar.

O que o servidor implementa

O servidor implementa o que um editor precisa: diagnósticos ao vivo com os códigos estáveis abaixo, tipos no hover, go-to-definition (entre módulos por meio de um import nomeado; por um namespace, ui.Button ainda não responde nada), autocomplete, símbolos do documento e do workspace para o outline e a busca de símbolos, find-references em todo o workspace, rename e formatação no layout canônico do glyph fmt para format-on-save.

O rename é completo: renomear uma declaração de nível de módulo edita a definição, todas as referências e o binding de import de cada módulo que a importa em todo o workspace, e confere o nome novo (um identificador válido, não uma palavra-chave) antes de mexer em qualquer coisa.

Dois limites que vale conhecer: o índice entre arquivos é reconstruído a cada requisição em vez de ficar em cache (tudo bem para um projeto normal, vale acelerar depois), e um arquivo que no momento não passa no parse é pulado, então um rename não alcança referências dentro de um arquivo que está quebrado.

Mensagens de erro

Deixamos as mensagens mais precisas exatamente onde agentes e iniciantes mais tropeçam: escrever if agora aponta para match em vez de um “token inesperado” genérico, e um número errado de argumentos, um match não exaustivo ou uma variante digitada errado ganham cada um seu próprio erro com código e correção.

Erros de tipo que só o back-end TypeScript consegue detectar apontavam para o .ts gerado. Agora eles são mapeados de volta para o seu .glyph (o mesmo caret do ariadne, o mesmo código estável), então um erro do tsc se lê como um erro nativo do Glyph.

Depuração

Você depura o TypeScript emitido com as ferramentas que já usa, como o inspector do Node, as devtools do navegador ou o debugger JS/TS da sua IDE.

Todo build gera um source map v3 padrão ao lado de cada .ts (com o código Glyph embutido), então um debugger ou um bundler que encadeia maps volta para os números de linha do seu .glyph.

Uma coisa que ainda não cobre: a stack de crash do próprio glyph run ainda imprime linhas do .ts, porque o tsx não encadeia o map pela transformação dele. Remapear essa stack é o próximo passo.

Perguntar “isso compila?” sem rodar

glyph check path.glyph faz a checagem de tipos de um arquivo, ou de um diretório inteiro, e sai. Ele não escreve nada na sua árvore, o que o glyph run não podia prometer e o glyph build nem fazia (ele recusava qualquer coisa que não fosse um diretório).

--no-tsc--json--no-test
Detalhes o que ele roda, e as flags

Roda o mesmo pipeline de um build, incluindo o tsc --strict sobre o TypeScript emitido, num diretório temporário que ele apaga ao sair. --no-tsc para depois das etapas do Glyph quando você quer a resposta rápida; --json dá a um agente o mesmo formato de diagnóstico que o glyph build --json. Um arquivo é verificado no contexto do seu próprio diretório, então um arquivo vizinho quebrado ainda faz o check falhar. Seus testes @example e @doc @run também rodam aqui, o mesmo gate que o glyph build usa, então um check não pode dizer que está tudo limpo numa árvore em que o build falharia; --no-test os pula quando você quer uma resposta que não executa nada.

A saída também não mente para você

Agora o resumo é impresso depois de todas as etapas que podem deixar o build vermelho, então um build vermelho nunca mostra uma linha verde.

Histórico o resumo que vinha cedo demais

Um build que falhava começava com “no diagnostics” e depois imprimia erros do tsc embaixo, porque o resumo da etapa Glyph era escrito antes de a etapa TypeScript rodar.

Na mesma leva, glyph run app.glyph --min -12.50 passou a funcionar: um hífen no começo fazia o clap rejeitar o argumento antes de o seu main chegar a vê-lo.

Flags que são do glyph continuam indo para o glyph, então ponha -- antes de uma flag do programa que colida com uma delas.

E para o agente no loop

glyph build --json emite cada diagnóstico como JSON estruturado: código estável, severidade, mensagem, arquivo e intervalo de linha/coluna a partir de 1, mais o help e a note, incluindo erros do tsc mapeados para o seu código Glyph. Um agente lê e age sobre eles diretamente, em vez de raspar texto do terminal.

glyph mcp para agentes interativos

Para agentes interativos há mais do que diagnósticos em lote: glyph mcp roda um servidor Model Context Protocol via stdio (o mesmo binário, a mesma análise que o editor usa), expondo as consultas do language server como ferramentas MCP. Um agente pode pedir os diagnósticos de um arquivo, o tipo numa posição, onde um nome está definido (seguindo imports), toda referência a um símbolo no projeto inteiro, ou uma busca de símbolos, sem rodar um build completo nem ler todos os arquivos.

É um adaptador fino sobre a mesma camada de análise pura, não uma segunda implementação, então não tem como divergir do que o compilador e o editor veem.

Nem tudo é erro fatal

O Glyph tem um nível de warning que aponta peso morto sem falhar o build: um import não usado (E0106), um let não usado (E0107, exceto nomes que começam com _) e código inalcançável depois de um return/break/continue (E0108).

E0106E0107E0108

Isso mantém um módulo honesto: um import morto é justamente o tipo de ruído de buscabilidade que faz o leitor caçar uma dependência que o código não tem de fato. Os warnings aparecem na mesma saída renderizada e em --json, marcados pela severidade, e o TypeScript continua sendo emitido.

Situação atual

Disponível hoje

  • Um language server para qualquer editor, respondendo através de fronteiras de módulodesde a 0.1.124
    Detalhes

    Um language server (glyph lsp via stdio, qualquer editor; extensão de VS Code incluída) com highlighting, diagnósticos, hover, go-to-def, autocomplete, símbolos, find-references e rename em todo o workspace e format-on-save, respondendo através de fronteiras de módulo desde a 0.1.124: o servidor mantém um banco por projeto com os buffers abertos sobrepostos aos arquivos em disco, então o hover numa função importada ou num campo de um record importado dá a mesma resposta que glyph query hover, uma edição não salva num arquivo é vista de outro, e cada tecla custa de um a nove por cento a mais do que custava com um só arquivo;

  • Um servidor Model Context Protocol glyph mcp com onze ferramentas
    Detalhes

    um servidor Model Context Protocol glyph mcp com onze ferramentas, as consultas do editor mais glyph_symbol, glyph_impact, glyph_assignable, glyph_dependencies e glyph_exports, cada uma com um verbo de glyph query que imprime o mesmo JSON para um agente sem cliente MCP;

  • Códigos de erro estáveis, glyph --explain, erros do back-end tsc mapeados para o código .glyph, um nível de warning (import/binding não usado, código inalcançável) e diagnósticos estruturados em --json.
  • glyph check [path] faz a checagem de tipos de um arquivo ou de uma árvore sem rodá-los nem escrever saída.
  • glyph fmt --check serve de gate de formatação no CI: não escreve nada e sai com código diferente de zero quando um arquivo ainda não está no layout canônico.

A caminho

  • Guardar em cache o índice entre arquivos em vez de reconstruí-lo a cada requisição (ganho de velocidade em árvores grandes).
  • Remapear a stack de crash do próprio glyph run, já que o tsx não encadeia o map emitido pela transformação dele, então essa stack ainda aponta para o .ts emitido e não para o seu .glyph.
