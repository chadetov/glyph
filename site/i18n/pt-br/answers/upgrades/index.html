Uma release nova do Glyph vai quebrar meu build?

Não sem você pedir. Um projeto Glyph fixa o compilador em uma versão exata, então uma release publicada hoje de manhã não chega ao seu build hoje à tarde. Antes da 1.0, uma release pode adicionar um diagnóstico que recusa código que compilava ontem, e geralmente esse é o objetivo da release. Por isso a decisão de adotá-la é sua, e é um comando só.

Por que isso importa

A maioria das ferramentas você fixa com um caret, porque uma release de patch é correção de bug. Um compilador antes da 1.0 não é assim.

Detalhes por que erros novos são as releases boas

O trabalho do Glyph é recusar programas, e melhorar nisso significa erros novos: uma checagem mais rígida em um import, uma brecha de exaustividade que antes passava, uma aridade que o checker não modelava. Essas são as releases boas. E são exatamente as que você não quer que cheguem por um npm install que você rodou para adicionar uma biblioteca de datas.

Por isso o glyph init não escreve ^. Em uma versão 0.x, um caret ainda deixa o patch flutuar, e essa é a armadilha: ^0.1.9 aceita em silêncio toda 0.1.x posterior.

Faça commit do package-lock.json ao lado dele e um clone novo builda com o toolchain que você testou, não com o que saiu depois.

A outra metade

Fixar a versão tem um modo de falha óbvio: você fica um ano num compilador velho e nunca fica sabendo. Então o compilador avisa, quando você pergunta qualquer coisa sobre o seu setup:

Detalhes por que o compilador é o canal

Nada na sua máquina avisaria, e um site que você precisa lembrar de visitar não é um canal.

glyph doctor 
glyph — 0.1.72
  [update]   0.1.73 is published — `glyph --update` moves this compiler, `glyph upgrade` moves a project's pin
             what changed: https://glyphlang.io/versions/

glyph doctor — JavaScript toolchain
  [ok]       node: v22.1.0
  [ok]       tsx: tsx v4.19.0
  [ok]       tsc: Version 6.0.2
All good. `glyph run` and `glyph build --check` are ready.

Encontrar uma release mais nova nunca muda o código de saída, então é seguro rodar isso na CI.

Detalhes CI, offline, e o que nunca usa a rede

Uma release publicada não é um toolchain quebrado, e um pipeline verde não deveria ficar vermelho porque alguém publicou algo dez minutos atrás. Se a máquina estiver offline, a checagem diz isso e segue em frente; --offline pula a checagem e não faz nenhuma chamada de rede.

Nada mais acessa o registry. build, run e check nunca acessam. Um compilador que liga para casa a cada build é outro produto.

Fazendo o upgrade

Ele reescreve uma linha e roda npm install. Não mexe no seu código-fonte e não finge que o upgrade terminou: buildar depois é o ponto, porque a release que você acabou de adotar pode ter opiniões que o seu código ainda não conheceu.

Uma linha muda, e você decide quando 
$ glyph upgrade --dry-run
glyph upgrade: would move /app/package.json from 0.1.72 to 0.1.73 (nothing written).

$ glyph upgrade
glyph upgrade: /app/package.json now pins 0.1.73 (was 0.1.72).
glyph upgrade: what changed: https://glyphlang.io/versions/
glyph upgrade: build before you commit; a new release may report diagnostics
               this project did not have.
Detalhes escolher uma versão, pular a instalação

--to <version> escolhe uma versão específica, inclusive uma mais antiga quando você quer voltar, e --no-install deixa a instalação com você.

Atualizando a ferramenta, não o projeto

upgrade move uma versão fixada em um package.json. glyph --update é a outra metade.

A divisão agora é uma regra, não uma coincidência: flags agem sobre a ferramenta, como --version, --help e --explain, e subcomandos agem sobre o seu código.

Histórico o que o doctor sugeria antes

Esse é o comando errado quando o que está desatualizado é o compilador no seu PATH, e por um tempo o doctor sugeria ele mesmo assim, apontando uma instalação global para um manifest que ela talvez nem tenha.

glyph --update 
$ glyph --update
glyph 0.1.72 is installed; 0.1.73 is published.
Release notes: https://glyphlang.io/versions/
A 0.1.x release may reject code that compiled before, so read the notes for anything between these two.

Running: npm install -g @glyphlang/glyph@0.1.73
   ... npm output ...

npm finished. Confirm with:
    glyph --version

--update-dry-run para depois de imprimir o comando npm que teria rodado.

  • Só uma instalação que ele consegue identificarEle só atualiza uma instalação que consegue identificar. Um compilador acessado via npx, buildado a partir de uma árvore de código do Glyph ou num caminho que ele não reconhece recebe o comando impresso e nada sobrescrito, porque substituir um binário do Homebrew ou o cargo build de alguém no chute deixa o PATH apontando para algo que ninguém escolheu.
  • Sem afirmar que deu certoEle também não afirma que a atualização deu certo: o npm pode sair com zero tendo pulado uma optionalDependency que não conseguiu baixar, e foi assim que uma release do Glyph saiu uma vez sem binário de plataforma. Por isso a última linha indica glyph --version como a checagem em vez de declarar sucesso.

Situação atual

Disponível hoje

  • Projetos criados pelo scaffold fixam a versão exata, então nenhuma release chega a um build por acidente.
  • glyph doctor compara seu compilador com o registry e linka as notas de versão, sem nunca afetar o código de saída e sem ser acionado por build/run/check.
  • glyph upgrade move a versão fixada, instala e lê o caret de um projeto mais antigo, para que projetos existentes também possam passar para uma versão exata.
  • glyph --update atualiza o próprio compilador, numa instalação global via npm, e para todas as outras formas de instalação ele informa em vez de chutar.

Ficando mais preciso

  • As notas de versão são uma página só para a linha inteira, então glyph upgrade linka a página, não a entrada da versão para a qual você está indo.
  • Ainda nada diz quais diagnósticos da release nova o seu código vai disparar: para saber, é preciso buildar, e é por isso que o comando manda fazer isso.
  • E fazer upgrade passando por várias releases de uma vez é o mesmo passo único de uma só, sem resumo do que se acumulou no meio.
  • glyph --update chama o npm e lê o código de saída dele, então consegue dizer que o npm terminou, mas não que o binário no PATH é a versão que você pediu; é por isso que ele aponta para glyph --version em vez de dizer que funcionou.
