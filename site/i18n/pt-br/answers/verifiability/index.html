O que impede um agente de quebrar meu código sem ninguém perceber?

Uma categoria inteira de mudança que compila sem alarde em TypeScript (um caso esquecido, um erro não tratado, um campo renomeado) vira um erro de compilação que o agente precisa corrigir antes de ir para produção.

Por que isso importa

Agentes normalmente não quebram o código de forma barulhenta. Eles quebram com confiança: adicionam um estado, deixam um branch de fora ou renomeiam um campo, tudo continua passando na verificação de tipos, e o bug aparece em produção.

As falhas caras são as que compilaram e estavam erradas. O Glyph fecha essa brecha transformando “você provavelmente tratou isso” em “o compilador provou que você tratou”.

  • Unions seladasAs unions etiquetadas são seladas, então o match precisa cobrir todos os casos.
  • Erros como valoresErros são valores que você precisa desembrulhar, não exceções que somem.
  • Fronteiras verificadasE todo tipo carrega um descritor de runtime, então os dados que cruzam uma fronteira são verificados contra o formato deles.

Um erro descartado gera um aviso

O mesmo vale para erros: uma função que retorna Result<T, E> deve ser tratada com match ou propagada com ? (e o compilador confere se o tipo de erro bate). E se você larga um Result no chão (chama como uma instrução e ignora o que ela retornou), o Glyph avisa (E0217), porque um erro descartado é uma falha engolida.

glyph check --no-tsc, 0.1.149 (trecho) 
13 │   save("a")
[E0217] Warning: typecheck: this `Result` is discarded; its `Err` case is silently ignored
    │ Help: Handle it with `match`, propagate it with `?`, or bind it (`let _ = ...`) to say the discard is intentional.

Você silencia o aviso de propósito com let _ = ..., nunca por acidente.

As unions da biblioteca padrão também são seladas

A exigência é a mesma para uma union que pertence à biblioteca padrão. fs.ErrorKind é um conjunto fechado de seis tipos, e o verificador conhece o formato dele, então match e.kind sobre um erro do sistema de arquivos não precisa de braço else e falha com E0200 quando você deixa um tipo de fora.

E0200 tipo faltandoE0210 campo desconhecidoE0218 precisa de else
Detalhes erros de digitação em campos, tipos de retorno, match em números e strings

e.mesage é E0210, e não algo que o tsc pega mais adiante. Os tipos de retorno também acompanham: string.split(text, ",") é um Array<string>, então for i, part in string.split(text, ",") liga i como um número, e não como a chave string que você teria com um iterando sem tipo.

A exaustividade não vale só para unions. Um match sobre um number ou string só com braços literais não tem como cobrir um domínio ilimitado, então o Glyph exige um else (E0218) em vez de deixar o valor não coberto cair num throw em runtime.

A regra é a mesma em todo lugar: um match que não dá conta de um caso não compila.

Um braço com erro de digitação é uma brecha, não um catch-all

Um erro de digitação também não consegue esconder uma brecha sem ninguém ver. A cabeça de um braço com letra maiúscula é uma referência a uma variante, não uma ligação nova.

status.glyph: um braço com erro de digitação é uma brecha, não um catch-all 
fn label(s: Status) -> string {
  return match s {
    Loadign => "…",        // typo for Loading, read as a variant, not a binding
    Ready => "done",
    Failed(msg) => msg,
  }
}
glyph build 
[E0220] `Loadign` is not a variant of `Status`; did you mean `Loading`?
   ╰─ a lowercase name would be a binding; a PascalCase name is read as a variant
[E0200] non-exhaustive match on `Status`: missing variant `Loading`
Histórico o que versões antigas do Glyph faziam com o erro de digitação

A cabeça de um braço com letra maiúscula é uma referência a uma variante, não uma ligação nova, então se você escrevia Loading errado como Loadign, versões antigas do Glyph liam o erro como um catch-all que ligava qualquer valor e fazia o match parecer completo. Agora a cabeça precisa nomear uma variante real da union sobre a qual você faz o match. Quando não nomeia, o build para com E0220 e aponta o nome real mais próximo, e a variante que você de fato pulou continua aparecendo como E0200 logo ao lado.

Variantes dentro de um payload

Essa leitura vale um nível abaixo, onde a variante é o payload de outra. O braço agora despacha pela tag do próprio payload, seja qual for a variante externa.

repl.glyph: o braço interno testa o payload, não o liga 
fn step(z: Zipper, line: string) -> Zipper {
  return match parse_command(line) {
    Err(Blank) => z,                          // a comment or an empty line
    Err(e) => { io.println(explain(e)) z },   // every other parse error
    Ok(command) => execute(z, command),
  }
}
E0305 rótulo de case duplicado
Histórico o braço morto antes da 0.1.93, e a proteção do E0305

Err(Blank) ao lado de Err(e) se lê como "ignore uma linha em branco, imprima todos os outros erros de parse", e até a 0.1.93 isso compilava para dois rótulos case "Err": na tag externa, e o primeiro ligava o payload inteiro com o nome Blank. Todo erro caía no primeiro braço, o segundo era código morto, e nada avisava: o Glyph não reportava nenhum diagnóstico e o tsc --strict aceita um rótulo de case duplicado. O braço agora despacha pela tag do próprio payload, seja qual for a variante externa, e o compilador lê o nome do mesmo jeito que o verificador de tipos: quem decide é a lista de variantes da própria union do payload, e só quando essa lista está fora de alcance é que o formato do nome decide. Para uma union declarada no mesmo arquivo, a capitalização não importa mais. Para uma importada de outro módulo, a lista de variantes hoje está fora de alcance, então uma variante com maiúscula despacha e uma com minúscula para o build.

Ele para porque agora o switch tem uma proteção. Dois braços que escreveriam o mesmo rótulo case são E0305, e não um switch cujo segundo rótulo nunca roda. É isso que torna essa categoria barulhenta em vez de silenciosa: uma tradução para TypeScript que usa a mesma tag duas vezes falha o build, em vez de escolher o braço errado em tempo de execução.

A forma do import nunca desliga a verificação

O jeito como a union entrou no escopo não muda nada disso. O Glyph deixa você escrever um braço de variante de duas formas, e as duas são verificadas igual: import model { Cond, Yes, No } com braços sem prefixo, ou import model (ou import model as m) com model.Yes(_).

interp.glyph: a lista de import saiu, o match continua verificado 
import model { Action, All, Any, AtLeast, Clear, Condition, Context, Counter,
               Equals, Flag, FlagSet, Increment, Not, Set, Slot, Text }
import model
import std/result

pub fn evaluate(ctx: model.Context, c: model.Condition) -> result.Result<bool, SlotError> {
  return match c {
    model.Equals({ key, value }) => result.Ok(read_text(ctx, key, "equals")? == value),
    model.AtLeast({ key, least }) => result.Ok(read_count(ctx, key, "at-least")? >= least),
    model.FlagSet({ key }) => result.Ok(read_flag(ctx, key, "flag-set")?),
    model.All({ of }) => all_of(ctx, of),
    model.Any({ of }) => any_of(ctx, of),
    model.Not({ of }) => result.Ok(!(evaluate(ctx, of)?)),
  }
}
glyph build, depois de apagar o último braço 
[E0200] non-exhaustive match on `Condition`: missing variants Not
Detalhes unions da biblioteca padrão, enums de string e por que a lista existia

Isso vale também para as unions da biblioteca padrão, então match o { option.Some(s) => … } sobre um option.Option<string> é E0200 pelo None que falta, exatamente como na forma sem prefixo Some/None. Até a 0.1.56, a forma qualificada pulava a verificação por completo e o build não reportava nenhum diagnóstico num match que lançava erro em tempo de execução.

Um enum de string também cruza a fronteira. type ColType = "text" | "int" | "real" | "bool" declarado em catalog.glyph e importado em outro módulo mantém os seus quatro valores, então um match que cobre os quatro compila sem else, e deixar um de fora é E0200 nomeando o valor que faltou. Até a 0.1.57 isso era E0218, com um texto de ajuda dizendo para adicionar um braço else. Essa ajuda estava errada sobre o código em questão, e segui-la transformava um erro de compilação numa queda silenciosa em runtime. As três formas de import funcionam: import catalog { ColType }, import catalog com catalog.ColType e import catalog as c com c.ColType.

Foi dessa lista de import que tudo isso surgiu. Ela era escrita à mão em cada módulo de um motor de statecharts, com um comentário acima dizendo que os construtores de uma union não chegam junto com o tipo dela. O comentário estava certo sobre a sintaxe e errado sobre o motivo: a lista estava lá porque a forma mais curta desligava a verificação, e ninguém tinha percebido, porque desligar é silencioso. Qual forma você escolhe agora é uma escolha de verdade, e não uma armadilha. A forma nomeada coloca na lista de import cada variante que você trata, que é o que um grep por Equals encontra. A forma qualificada diz, em cada braço, de qual módulo a variante veio. Nenhuma das duas custa a verificação.

Records importados mantêm seus campos

Records também cruzam agora, e até a 0.1.58 não cruzavam. Por isso um record mantém o seu conjunto de campos, e um campo errado é E0210 nomeando o record, e não um erro do tsc sobre um formato anônimo.

glyph build, num campo digitado errado de um record importado 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
// Before 0.1.58: no Glyph diagnostic at all, only a tsc error downstream.

Detalhes o bug da linha 11, o que o tsc deixa passar, como a identidade cruza

Um tipo declarado num arquivo e usado em outro chegava sem nada conhecido sobre ele, e isso custava duas verificações diferentes. Um campo digitado errado nele não gerava nenhum erro do Glyph, então sheet.rowz caía no tsc e voltava como uma mensagem de TypeScript sobre um formato que você nunca escreveu. E for i, r in sheet.rows não conseguia saber que rows era um array, então emitia Object.entries(sheet.rows) em vez de sheet.rows.entries(). Isso liga i à string "0". i + 1 então concatena em vez de somar, e uma linha que deveria ser reportada como line 2 aparece como line 11.

O que vale saber é qual metade o tsc pega. A aritmética sobre esse índice ele pega, embora reporte o erro contra o TypeScript gerado, numa variável que o Glyph ligou por você. O que ele não consegue pegar é cada lugar onde uma string é aceita onde se queria um número: interpolação de string, concatenação, uma chave de record.get. Esses compilam sem erros nos dois verificadores e imprimem o número errado. É exatamente o tipo de bug que este projeto existe para eliminar, então uma fronteira de módulo que o traz de volta não é uma fronteira que o Glyph possa deixar como está.

Um tipo importado agora carrega uma identidade através da fronteira, indexada pelo módulo que o declara e pelo nome declarado, então as três formas de import resolvem para o mesmo tipo. A própria declaração é buscada sob demanda e processada do lado do módulo que a declara, que é a metade que um consumidor não consegue fazer: a resolução trabalha sobre spans, e os spans de uma declaração importada pertencem a outro arquivo.

Foi no motor de consultas em examples/apps/csvql que isso apareceu. Ele tinha três hoists de let cuja única função era repetir o tipo de um campo importado para o emissor, sob um comentário de quatro linhas explicando que, sem eles, os números de linha e coluna numa mensagem de erro saem errados. Os três foram apagados e o app imprime uma saída idêntica byte a byte nas doze consultas.

Uma coisa ainda para na fronteira. Passar um catalog.Sheet onde se espera um table.Row é E0211 nomeando os dois tipos, mas a lista de membros de uma interface não cruza, então um record passado onde se espera uma interface importada é comparado com nada. Dar a ela o mesmo tratamento que o conjunto de campos de um record recebe mudaria sem alarde o que satisfação estrutural significa, e isso é uma decisão de linguagem, não uma correção.

O mascaramento de dados pessoais fica no tipo

O mesmo instinto de "colocar no tipo, não em convenção" cobre dados pessoais (PII). Coloque @redact fields: [ssn, dob] num tipo e o compilador gera um redact() no descritor dele que mascara esses campos, então json.stringify(User.redact(u)) não tem como vazá-los.

E0219 campo desconhecido em @redact

Nomeie um campo que o tipo não tem e é um erro de compilação (E0219), e não uma redação que em silêncio não faz nada.

Refinamentos são verificados até o fundo

Um descritor só vale alguma coisa se for a verificação que o tipo declara, até o fundo. Um refinamento where roda o seu predicado em qualquer lugar onde o tipo aparece, e não só num Instant.parse direto: como campo de um record, como elemento de um Array, como payload de um Option, dentro de uma variante de union e através de json.parse<T>.

schedule.glyph: o predicado acompanha o tipo até dentro do campo 
fn is_instant(value: string) -> bool {
  return match time.parse_iso(value) {
    Some(_) => true,
    None => false,
  }
}

type Instant = string where is_instant(value)

type WireBlock = { start: Instant, end: Instant }
type WireParticipant = { name: string, busy: Array<WireBlock> }
type Calendar = { participants: Array<WireParticipant> }

// json.parse<Calendar>(text) on a file holding "start": "no"
//   => Err. It returned Ok before 0.1.41.
Histórico a agenda errada e cheia de confiança antes da 0.1.41

O mesmo vale para um record importado de outro módulo. Até a 0.1.41, os dois casos voltavam a só verificar se a chave estava presente, o que não verifica coisa nenhuma.

Foi no app de agendamento abaixo que isso apareceu. Ele lê calendários de um arquivo JSON e precisa que cada timestamp seja um instante ISO-8601 de verdade. Antes, o refinamento parava no nível de cima, então um arquivo editado à mão com "start": "no" passava no parse sem problema, o instante era lido como 0, e o app imprimia uma agenda cheia de confiança e saía com código 0.

Os testes rodam como parte do build

Os testes ficam ao lado do código e rodam como parte da compilação. Um @example acima de uma função, ou um bloco ```glyph @run``` dentro de um @doc, é executado pelo glyph build sem nenhuma flag para lembrar.

Detalhes por que não dá para pular em silêncio, e o canal JSON

Um exemplo falso falha o build do mesmo jeito que um erro de tipo, e é essa a ideia: um agente que reescreve o corpo de uma função não consegue passar no build deixando a asserção para trás. --no-test desliga e imprime quantos testes pulou, então o desvio fica visível no log.

A saída JSON que os agentes leem reporta o mesmo veredito. glyph build --json traz um objeto examples ao lado dos diagnósticos, e um exemplo que falha deixa ok falso e o código de saída diferente de zero. Até a 0.1.43, os exemplos só rodavam com --test, e o caminho JSON retornava antes de eles rodarem, então o único canal que um agente consegue ler imprimia "ok": true num projeto cuja própria asserção era falsa. Se o tsx não estiver no PATH, o build falha em vez de reportar uma aprovação que nunca verificou.

O app de chaveamento abaixo tem 23 desses. seed_order monta a ordem padrão do chaveamento por duplicação, que é o tipo de função fácil de errar de um jeito sutil e fácil de descrever com exatidão. Mude a regra de duplicação e o build para, sem arquivo de teste, sem runner, sem flag.

Encontrados construindo com ele

Mais quatro, encontrados construindo com ele

Cada um destes compilava sem erros e passava no tsc --strict, e cada um foi encontrado escrevendo uma aplicação, e não lendo o compilador. São a mesma falha em três lugares: os tipos diziam uma coisa e o programa fazia outra.

Ler uma chave que pode não existir

ler uma chave que pode não existir: agora E0224 
fn name_of(row: Record<string, string>) -> string {
  return row.naem          // a typo. compiled, and returned undefined
}

Agora é um erro de compilação que aponta para record.get, que retorna Option<V> para que o caso ausente tenha para onde ir.

Detalhes por que ler um mapa é diferente de indexar um array

As chaves de um mapa são arbitrárias, então o compilador não tem como saber que a chave está lá. Tipar a leitura como string afirmava algo que ele não tinha verificado, e o valor era impresso como o texto "undefined". Escrever uma chave não mudou, e indexar um array também não: um limite é um valor que o programa pode verificar, uma chave de mapa não.

Um método que responde undefined

uma busca que pode não encontrar nada: agora E0242 
let name = users.find(fn(u: User) -> bool { return u.id == id }).name
let last = xs.at(-1) ?? 0  // passed tsc --strict too

[E0242] the call to `users.find` returns `User | undefined`; Glyph writes a value that may be missing as an `Option`
Help: pass `users` and the same callback to `array.find`, which returns `Option<User>`, and `match` it

Alguns métodos de JavaScript dizem "não há nada" com undefined, que o checker do próprio Glyph não enxergava, então o editor e as ferramentas do agente deixavam passar a leitura de .name. Agora cada um aponta para a função da biblioteca padrão que devolve um Option, e o glyph fix escreve as de array.

Detalhes quais métodos, e o que os substitui

A lista vem das declarações do TypeScript: find, findLast e at em um array, e at, codePointAt e match em uma string. As substituições são array.find, array.find_last, array.get, string.char_at, string.code_point_at e regex.matches. Um padrão com ?? vira o braço None de um match. array.get responde None para um índice negativo, então o help para xs.at(-1) escreve array.get(xs, array.len(xs) - 1). Um método chamado em um valor de npm não é julgado, porque o Glyph não conhece o tipo dele.

== é igualdade de valor em todo lugar

um teste que passava enquanto o código falhava 
@example wrap("a") == wrap("a")   // passed: deep equality
fn same() -> bool {
  return wrap("a") == wrap("a")   // false. no diagnostic
}

== agora é igualdade de valor em todo lugar; primitivos continuam compilando para ===, então as comparações comuns não mudam.

Histórico como um teste podia passar com código quebrado

== estava documentado como igualdade de valor e virava ===, que é igualdade de referência assim que um dos lados é um record, uma union etiquetada ou um array. A mesma expressão comparava estruturalmente num teste e por identidade no programa ao lado, então um teste podia reportar sucesso num código que não funcionava.

A variável de um loop mantém o tipo do elemento

exaustividade que evaporava dentro de um loop 
for t in tiers {
  match t {
    "free" => ...          // "pro" unhandled: once merely a warning to add `else`
  }
}

Agora ele nomeia a variante que você não tratou, que é um conselho para satisfazer a verificação, e não para desligá-la.

Histórico o conselho de catch-all que ele dava

A variável do loop não carregava o tipo do elemento, então um match sobre uma union de literais de string virava um match sobre string e o compilador sugeria adicionar um catch-all.

Uma leitura por índice tem o tipo do elemento

um erro de digitação depois de xs[0]: agora E0210 
fn first_len(xs: Array<string>) -> number {
  let s = xs[0]
  return s.lenght
}

[E0210] type `string` has no field `lenght`; did you mean `length`?

xs[i] em um Array<E> é um E, então o editor, o glyph check --no-tsc e as ferramentas do agente verificam o que você faz com ele: ler um campo, chamar um método, um return, um argumento, um let anotado.

Histórico o que era verificado antes

Até a 0.1.183 um elemento lido por índice não tinha tipo do lado do Glyph. return xs[0] sob -> number, um campo com erro de digitação em rows[0] e xs[0] passado para um parâmetro number passavam, e só a etapa do tsc de um build completo pegava. O tipo é o que o tsc dá ao código gerado, que deixa noUncheckedIndexedAccess desligado: E, não E | undefined. O índice do Glyph lança um RangeError depois do fim em vez de devolver undefined; use array.get quando quiser um Option. Ler uma chave de um Record continua sendo E0224, a menos que o tipo do valor seja unknown, e um índice em uma string ou em um valor do npm não é julgado.

Unions genéricas importadas são verificadas

uma variante deixada de fora num match sobre uma union genérica importada 
import tree { Tree, Node }

fn label(t: Tree<string>) -> string {
  return match t {
    Node({ key: k }) => k    // Leaf unhandled: built clean, threw at run time
  }
}

Agora é E0200 em qualquer caso, nas duas formas de import, tanto com um parâmetro aberto quanto com uma instanciação concreta.

Histórico por que a verificação nunca começava

Uma union que o seu próprio módulo declara é verificada, receba ela parâmetros de tipo ou não. Uma importada de um módulo vizinho só era verificada quando não recebia nenhum. Tree<string> chega ao caminho de cobertura entre módulos como uma aplicação de uma union importada, e não como a union em si, e o gate que inicia a verificação procurava a segunda forma, então o match nunca era contado: o tsc --strict passava e um Leaf lançava erro. Apague <K> dos dois arquivos e o mesmo programa era E0200.

Um parse não pode afirmar uma verificação que não fez

um parse que reportava sucesso sem verificar: agora E0304 
type Conn = { id: number, sock: Socket }

Conn.parse(body)   // Ok. `sock` was never checked, and the message said it was

Guardar um socket num record é algo comum e continua compilando. Validar um agora é recusado onde está escrito e em cada módulo que importa o record, nomeando o campo e o tipo dele, e a recusa acompanha o formato: através de um record aninhado, de um Array, de um Option.

Detalhes por que presença não é verificação, e a correção que ele pede

Todo tipo record carrega um descritor de runtime. Para um campo cujo tipo o compilador não consegue enxergar por dentro, um socket ou qualquer coisa vinda de extern_ts, a verificação gerada era "está presente", enquanto a mensagem reportada dizia field `sock` must be Socket. Um booleano que é sempre verdadeiro é inútil. Um que é sempre verdadeiro sob uma mensagem que nomeia um tipo que nada verificou é pior, porque o parse é justamente aquilo em que uma fronteira é orientada a confiar.

A correção que ele pede é a separação que você escreveria de qualquer jeito: um tipo de transporte com todos os campos verificáveis, e depois um record de domínio que você monta a partir dele. unknown não é pego por isso, porque não afirma nada, e a presença é de fato a verificação inteira.

Uma mudança de assinatura invisível no ponto de chamada: resolvido na 0.1.116

Mude uma função para receber um payload em vez de uma string crua, e todas as chamadas que ainda passavam o formato antigo compilavam sem erros.

billing.glyph: uma union passa por um parâmetro `string` sem ninguém notar 
type PaymentResult = Settled(string) | Declined(string)

fn takes_string(s: string) -> number { return s.length }

fn charge(r: PaymentResult) -> number {
  return takes_string(r)   // compiled clean before 0.1.116
}
glyph build, agora 
[E0211] argument type mismatch: expected `string`, found `PaymentResult`
   ╰─ Pass a value of the expected type, or change the parameter's type.
Detalhes onde a verificação dispara, e onde fica quieta

Um parâmetro tipado como string, number ou bool aceitava um valor de uma union ou record declarado sem reclamar de nada, embora a mesma chamada com um argumento bool incompatível já fosse E0211.

A verificação lê a declaração, então só dispara onde a resposta é certa. Um alias primitivo como type Id = string é lido como o string que ele nomeia, então é decidido do mesmo jeito. Uma união de literais de string (D30) é comparada pelos seus literais, e um valor de um interface é recusado onde um string é declarado, porque o valor dele é um objeto. Um corpo extern_ts ou typeof continua sem dizer nada, e void também fica de fora. Ela alcança um argumento, um return e uma anotação de let da mesma forma, já que os três compartilham uma relação.

A outra direção passa pelos membros do valor, como no TypeScript: 5 é recusado onde interface HasName { name: string } é declarada, e "abc" é aceito onde interface HasLen { length: number } é declarada, porque uma string tem length. Um bigint é lido pelos próprios membros, então é recusado ali: ele não tem length. Dois pares ainda não são decididos e ficam para o tsc: uma interface cujos membros são todos opcionais e não compartilha nenhum com o valor (G526), e Option, Result e Record contra uma interface (G527).

Um const anotado tem tipo

Um const tinha a brecha correspondente do lado de quem recebe.

catalog.glyph: um const anotado, e o campo que ele não tem 
type Sheet = { rows: number, cols: number }
const ORIGIN: Sheet = { rows: 0, cols: 0 }

fn f() -> number {
  return ORIGIN.rowz   // compiled clean before 0.1.116
}
glyph build, agora 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
Detalhes consts sem anotação, e por que as duas correções quebram compatibilidade

Um const no nível do módulo com uma anotação de tipo virava Ty::Unknown independentemente do que a anotação dizia, então um erro de digitação num campo dele ficava invisível justo onde o mesmo let anotado dentro de uma função já reportava o erro.

Desde a 0.1.166 uma const sem anotação tem o tipo do seu inicializador, lido do jeito que o tsc lê a const TypeScript que o emissor escreve: const MODE = "read" mantém seu tipo literal, e um literal dentro de um objeto ou array é alargado, então const ITEMS = [1, 2] é um Array<number> e ITEMS.push(3) fora de mut é E0240. Um inicializador que o checker não consegue tipar deixa a const sem tipo. As duas correções quebram compatibilidade em glyph check --no-tsc, no servidor de linguagem e no playground, já que cada uma passa a pegar um programa que a versão anterior aceitava; um glyph build completo já ficava vermelho pelo tsc nos dois casos.

Um campo que o record não declara

um campo opcional com erro de digitação: agora E0210 
module profile

pub type Profile = {
  name: string,
  nick?: string,
}

pub fn guest() -> Profile {
  return { name: "guest", nik: "g" }   // [E0210] type `Profile` has no field `nik`; did you mean `nick`?
}

Uma chave que o record declarado não tem passava antes pelo checker do Glyph, então um erro de digitação em um campo opcional jogava fora o valor e só o tsc percebia. O editor, as ferramentas para agentes e o glyph check --no-tsc a recusam agora, com o mesmo erro que a leitura desse campo dá, e o glyph fix renomeia nik para nick.

Detalhes onde é verificado e o que fica de fora

É verificado onde quer que um literal escrito encontre um tipo declarado: um let, um return, um argumento de chamada, o payload de uma variante, uma atribuição com mut, um campo aninhado, um elemento de array, um braço de match e o argumento de Some, Ok ou Err, que o tsc deixa passar. Um binding que guarda um record mais amplo continua aceito, como o tsc aceita, assim como campos que vêm de um spread e chaves escritas para um Record<K, V>.

Match

  • A cobertura de uma union importada ainda não olha dentro do payload de uma varianteo próximo a aprofundar
    Detalhes

    Um parâmetro de tipo costumava desligar a verificação: até a 0.1.90, um match sobre Tree<K> podia omitir uma variante, compilar sem erros, passar no tsc --strict e lançar erro em tempo de execução, enquanto o mesmo match sobre Tree era E0200. Isso está resolvido para uma union que o seu próprio módulo declara e, desde a 0.1.95, para uma que está a um import de distância. O que ainda é mais raso no caminho importado é a profundidade, e não o gate: a verificação que roda para uma union importada nunca olha dentro do payload de uma variante, então B(X) sobre uma union importada cujo payload também é uma union casa com todo B, em vez de reportar o Y que falta, e nenhum parâmetro de tipo está envolvido. É a próxima coisa a aprofundar.

  • Uma variante de payload com minúscula de uma union importada para o buildE0305
    Detalhes

    Uma variante na posição de payload agora é lida da lista de variantes da union do payload, então a capitalização do nome deixa de importar para uma union que o seu módulo declara. Para uma importada de outro módulo não há lista para ler e o formato do nome ainda decide, o que significa que Err(Blank) despacha e Err(blank) para o build com E0305: uma falha barulhenta num programa válido, e a correção precisa do mesmo registro de unions importadas de que a verificação de cobertura rasa acima precisa.

  • Um padrão de construtor sobre um payload record (Ok(Point)) falha no tsc, não no Glyph
    Detalhes

    Um padrão de construtor sobre um payload que é um record, e não uma union (Ok(Point)), falha pelo tsc nomeando um .tag que você nunca escreveu, quando deveria ser um diagnóstico do Glyph nomeando o tipo e o padrão.

  • Um braço sem prefixo digitado errado reporta duas linhas para o mesmo nomeE0220E0103
    Detalhes

    A verificação de erros de digitação (E0220) agora cobre do mesmo jeito uma union declarada no módulo e uma alcançada por um import de namespace (model.Nooo(_)), com formato de construtor ou sem prefixo: até a 0.1.115, uma cabeça sem prefixo digitada errado sobre uma union importada (Loadign, sem argumentos) era contada como cobrindo uma variante e não dizia nada, enquanto o mesmo erro numa union local já reportava E0220; as duas formas reportam agora. Um braço sem prefixo digitado errado também dispara E0103, uma etapa antes, então você recebe as duas linhas para o mesmo nome.

Tipos, records e literais

  • Um literal com spread não tem tipo
    Detalhes

    Um literal com spread não tem tipo, então um campo que falta ou que tem o tipo errado fica a cargo do tsc. Uma chave escrita ao lado do spread continua sendo verificada contra o record declarado.

  • Os membros de uma interface importada e o tipo de um const importado ainda não cruzam
    Detalhes

    Os tipos agora cruzam uma fronteira de módulo intactos: unions mantêm a exaustividade, etiquetadas ou de literais de string, e um record mantém o seu conjunto de campos, então um campo digitado errado num record importado é E0210 nomeando o próprio tipo desse record, e for i, x sobre um dos campos array dele liga um número sem anotação. O que ainda não cruza é a lista de membros de uma interface, então um record passado onde se espera uma interface importada é comparado com nada; um const importado tem o mesmo formato, um nível ao lado: ele ainda é Ty::Unknown, então um erro de digitação num campo através de um import nomeado ou de namespace continua silencioso, tenha o módulo de origem anotado o tipo ou não.

  • Um estreitamento de fluxo mais profundo está no roadmap

Ferramentas e a biblioteca padrão

  • Acesso a membros em primitivos e arrays não tem diagnóstico onde o tsc não roda
    Detalhes

    Acesso a membros e chamadas em string, number, bool e Array<T> ficam por conta do tsc por design, e não por uma brecha; o Glyph permite membros JS crus ali, então s.length e xs.length compilam e passam no tsc --strict, e o que continua faltando é um diagnóstico nas quatro superfícies que nunca rodam o tsc: glyph check --no-tsc, o language server, o servidor MCP e o playground.

  • Um build offline com exemplos precisa do tsx ou de --no-test
    Detalhes

    O executor de exemplos chama o tsx, então um projeto que tem exemplos e não tem tsx no PATH falha o build em vez de pular em silêncio; isso é proposital, mas significa que um build offline precisa do tsx instalado ou de --no-test.

  • Um await num fn comum é pego no seu próprio código-fonteE0222
    Detalhes

    O contexto assíncrono era a única regra que o Glyph deixava para o tsc; um await num fn comum agora é E0222 no seu próprio código-fonte, e o inicializador de um const de nível superior é o único caso ainda permitido. Essa e outras duas regras que subiram uma etapa estão em detectado antes.
