Por que não só TypeScript strict + zod + eslint + ts-pattern?

Porque cada uma dessas garantias é opcional, e um agente pode contornar cada uma delas com uma linha. O rigor do Glyph não é um arquivo de configuração que o agente pode editar. É a linguagem. O ponto de controle deixa de ser "lembramos de rodar o lint neste arquivo?" e passa a ser "compila?".

Uma configuração de TypeScript bem feita leva você longe, e se o seu time roda tudo isso na CI, você já fechou a maioria das brechas que o Glyph mira. É a alternativa que vale levar a sério, então aqui está o mapeamento:

01 Obrigatório ganha de opcional

Cada uma dessas válvulas de escape é uma config que o agente pode editar. O Glyph não tem nenhuma válvula dessas: não existe as, nem pragma de ignore, nem como tirar um valor tipado de um unknown sem uma checagem que o compilador consiga ver.

TypeScript: as válvulas existem handler.ts 
const user = body as unknown as User;
// @ts-ignore
doThing(user.mispelled);
// eslint-disable-next-line
return anything as any;
Glyph: nada para desligar handler.glyph 
return match User.parse(body) {
  Ok(user) => use(user),
  Err(_) => fallback(),
}
// no `as`, no ignore pragma,
// no lint to switch off.

Um rigor que o agente não consegue desligar na config fica num ponto de controle diferente de um rigor que ele consegue. O Glyph é construído sobre essa diferença.

Detalhes o que um agente consegue escrever passando por cima do eslint

Sua config do eslint só protege o código que o agente faz passar por ela, e o agente pode escrever as unknown as User, @ts-ignore, // eslint-disable-next-line, ou simplesmente esquecer o .exhaustive(), e ainda assim compila e é mergeado.

02 O tipo é o validador: sem segundo artefato

No Glyph o tipo é o validador: declarar type User = {...} gera User.parse junto. Um artefato, nada para sincronizar, nada para esquecer.

  • zod: schema primeiroO zod inverte a sua fonte da verdade: você escreve o schema, deriva o tipo dele e depois mantém o tipo, o schema e qualquer serializador sincronizados à mão.
  • Onde entra a divergênciaManter isso alinhado é justamente onde um agente introduz divergência: ele renomeia um campo no tipo e não no schema, e os dois continuam compilando.

03 Mutação buscável

No Glyph, estado compartilhado vive num store e toda mudança é um .set(/.update( literal; grep 'mut ' encontra toda mutação local. O TypeScript padrão não tem equivalente.

Detalhes onde uma escrita em TypeScript pode se esconder

No TypeScript, uma mudança de estado pode se esconder atrás de =, .push(), Object.assign, um setter ou um spread. Não existe um token único para buscar, e nenhuma regra de lint resolve isso por completo.

O diff do modo de falha

Mesma tarefa: um agente adiciona uma variante a uma union e esquece de tratá-la em um de três lugares:

TS com ferramentas 
// ts-pattern .exhaustive() catches it,
// IF every site used ts-pattern and
// nobody wrote a default: case or a
// switch that only logs. Those
// compile green and skip the new case.
Glyph 
[E0200] non-exhaustive match on
`Feed`: missing variant `Archived`
// every unhandled match, everywhere,
// fails the build. No opt-in, no
// escape, no forgotten default.

Onde o TypeScript com ferramentas ainda está na frente

Quatro pontos em que ele está à frente do Glyph hoje:

  • Validação mais rica.Os descritores do Glyph são strict por padrão (recusam chaves não declaradas), e um refinamento where coloca um predicado sobre um primitivo (type Email = string where value.includes("@")), que o descritor roda em toda fronteira que o tipo alcança. O zod ainda está na frente de dois jeitos: traz checagens prontas como .email() e .url(), que no Glyph você escreve por conta própria, e refina objetos inteiros, enquanto um where num record (lo <= hi entre dois campos) é E0300 hoje.
  • Matching mais profundo.Os guards e os padrões estruturais profundos do ts-pattern vão além do que o match do Glyph expressa.
  • A "ausência comprovável" para na fronteira do .ts.As garantias do Glyph valem para código escrito em Glyph; uma exceção lançada por uma dependência do npm ainda passa por fora do Result, e um tipo importado de um .d.ts não tem descritor em runtime.
  • Ecossistema e contratação.O ferramental, a comunidade e o mercado de profissionais de TypeScript são muito maiores, com anos de uso em produção. O Glyph é uma versão preliminar.

Se você ligou por completo o TypeScript com ferramentas e seus agentes ficam dentro dele, você já tem a maior parte disso. O argumento do Glyph é que "ficam dentro dele" é a parte que sustenta tudo, e é justamente a parte que um agente quebra. Obrigatoriedade, validação com um artefato só e mutação buscável são o que você não consegue acrescentando mais ferramentas opcionais.
