Posso servir uma página web, ou só uma API JSON?

Uma página web. O std/http define headers de resposta, então uma página text/html, um redirect 302, um header de cache e o envio de um formulário HTML são Glyph comum. Sem Express, sem shim de TypeScript escrito à mão.

Por que isso importa

Até a 0.1.46 uma resposta era { status, body } e o servidor escolhia o content type pelo formato do body: uma string virava text/plain, qualquer outra coisa virava JSON. Isso serve para uma API e não serve para nada que um navegador renderiza.

A saída era escrever seu próprio servidor sobre node:http num arquivo .ts escrito à mão, o que deixa todo o caminho da requisição fora do type checker. Dois construtores faltando custavam uma fronteira inteira da aplicação.

Um handler retorna um Result

Um handler retorna Result<Response, string>, então um 404 é um Ok comum e um Err fica reservado para o que o app não consegue responder, que o servidor transforma em 500.

O serve fica pendente enquanto escuta, então nada precisa manter o processo vivo na mão, e uma falha no bind volta como valor.

Toda resposta leva headers

Response tem um campo obrigatório headers: Record<string, string>. Obrigatório, não opcional: todo construtor o preenche, então ler resp.headers nunca exige checar ausência, e não há como esquecer o canal.

  • Uma resposta nova, não uma mutaçãowith_header(resp, "cache-control", "no-store") retorna uma resposta nova em vez de alterar a existente, porque o Glyph não tem mutação de campo de record.
  • Verificado em GlyphO type checker sabe que os três construtores retornam um Response, então um handler cujo tipo de retorno declarado diz Result<Response, string> é verificado em Glyph, e não pelo tsc sobre a saída gerada.

Dois detalhes que você erraria fazendo à mão

  • Valores de headerQualquer caractere que o Node se recusa a escrever num header é removido do valor na saída, então um location montado a partir de um parâmetro de query não consegue injetar um segundo header nem uma segunda resposta, e um emoji numa URL encurtada não derruba o servidor.
  • Bodies de formulárioform(req) decodifica + como espaço junto com os escapes de porcentagem, a dupla que o parse de formulário feito à mão costuma esquecer; ele lê o body bruto, então req.body fica intacto para handlers que fazem o parse por conta própria.

Situação atual

Disponível hoje

  • html, redirect, with_header, json, text e form
  • Headers de resposta enviados de fato, com o content type inferido só quando você não definiu um
  • Headers da requisição, parâmetros de query, segmentos do path e o body bruto na entrada
  • O cliente informa os headers de resposta que recebeu.

A caminho

  • Percent encoding é a lacuna que o trecho acima mostra
    Detalhes

    Percent encoding é a lacuna que o trecho acima mostra: form decodifica um body de formulário, mas não existe encode_component para montar uma URL, então o encurtador escreve o seu.

  • Também faltam no lado do cliente: timeout, política de redirect, head e a URL final em que um redirect terminou.
  • Não há servidor de arquivos estáticos nem engine de templates, e não há plano para nenhum dos dois.
