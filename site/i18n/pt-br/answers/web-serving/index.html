17 · Servindo a web

Posso servir uma página web, ou só uma API JSON?

Uma página web. O std/http define headers de resposta, então uma página text/html, um redirect 302, um header de cache e o envio de um formulário HTML são Glyph comum. Sem Express, sem shim de TypeScript escrito à mão.

Por que isso importa

Até a 0.1.46 uma resposta era { status, body } e o servidor escolhia o content type pelo formato do body: uma string virava text/plain, qualquer outra coisa virava JSON. Isso serve para uma API e não serve para nada que um navegador renderiza. A saída era escrever seu próprio servidor sobre node:http num arquivo .ts escrito à mão, o que deixa todo o caminho da requisição fora do type checker. Dois construtores faltando custavam uma fronteira inteira da aplicação.

Veja na prática

Este é o roteador de examples/apps/shortlink/main.glyph, um encurtador de URLs que vem no repositório. Um formulário HTML cria um código, um POST responde com um redirect para que recarregar a página no navegador nunca reenvie o formulário, e seguir um código é um 302 para o destino:

shortlink.glyph: uma página HTML, um envio de formulário e o 302 
fn handle_home(req: Request) -> Response {
  return match req.method {
    "GET" => html(200, home_page(links.get(), query_param(req, "error"))),
    "POST" => {
      let fields = form(req)
      match create_link(form_field(fields, "url"), form_field(fields, "alias")) {
        Ok(link) => redirect(303, "/${link.code}+"),
        Err(message) => redirect(303, "/?error=${url_encode(message)}"),
      }
    },
    else => html(405, page("405", "<h1>405</h1>")),
  }
}

fn route(req: Request) -> Result<Response, string> {
  return match segments(req) {
    [] => Ok(handle_home(req)),
    [one] => match stats_code(percent_decode(one)) {
      Some(code) => Ok(handle_stats(code)),
      None => Ok(handle_code(percent_decode(one))),
    },
    else => Ok(html(404, not_found_page(path(req)))),
  }
}

async fn main(argv: Array<string>) -> number {
  let outcome = await serve(8138, route)
  return match outcome { Ok(_) => 0, Err(_) => 1, }
}

Uma release atrás, o mesmo app estava no repositório com 615 linhas, 121 delas num servidor node:http escrito à mão num arquivo .ts ao lado, porque um Location e um body text/html não tinham como ser escritos. Hoje ele tem 494 linhas e não importa nada fora do std. Um handler retorna Result<Response, string>, então um 404 é um Ok comum e um Err fica reservado para o que o app não consegue responder, que o servidor transforma em 500. O serve fica pendente enquanto escuta, então nada precisa manter o processo vivo na mão, e uma falha no bind volta como valor.

Response tem um campo obrigatório headers: Record<string, string>. Obrigatório, não opcional: todo construtor o preenche, então ler resp.headers nunca exige checar ausência, e não há como esquecer o canal. with_header(resp, "cache-control", "no-store") retorna uma resposta nova em vez de alterar a existente, porque o Glyph não tem mutação de campo de record. O type checker sabe que os três construtores retornam um Response, então um handler cujo tipo de retorno declarado diz Result<Response, string> é verificado em Glyph, e não pelo tsc sobre a saída gerada.

Dois detalhes que você erraria fazendo à mão. Qualquer caractere que o Node se recusa a escrever num header é removido do valor na saída, então um location montado a partir de um parâmetro de query não consegue injetar um segundo header nem uma segunda resposta, e um emoji numa URL encurtada não derruba o servidor. E form(req) decodifica + como espaço junto com os escapes de porcentagem, a dupla que o parse de formulário feito à mão costuma esquecer; ele lê o body bruto, então req.body fica intacto para handlers que fazem o parse por conta própria.

Situação atual

Disponível hoje

html, redirect, with_header, json, text e form; headers de resposta enviados de fato, com o content type inferido só quando você não definiu um; headers da requisição, parâmetros de query, segmentos do path e o body bruto na entrada; o cliente informa os headers de resposta que recebeu.

A caminho

Percent encoding é a lacuna que o trecho acima mostra: form decodifica um body de formulário, mas não existe encode_component para montar uma URL, então o encurtador escreve o seu. Também faltam no lado do cliente: timeout, política de redirect, head e a URL final em que um redirect terminou. Não há servidor de arquivos estáticos nem engine de templates, e não há plano para nenhum dos dois.
