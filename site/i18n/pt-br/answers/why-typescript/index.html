Por que TypeScript, e não Go ou uma linguagem nova?

Porque TypeScript é onde os agentes já escrevem mais código e onde vive o seu ecossistema (npm, React, Node). O Glyph pode ser adotado um arquivo por vez só porque o alvo dele é TS.

Por que isso importa

Uma linguagem nova vive ou morre pelo caminho entre o zero e a produção. Compilar para TypeScript significa que você nunca sai do seu codebase, do seu bundler, do seu test runner nem do seu deploy. O Glyph se encaixa ao lado dos arquivos .ts que você já tem, e o import funciona sem atrito nas duas direções:

o mesmo projeto: .glyph e .ts, lado a lado 
// cart.glyph: new, written in Glyph
import { formatPrice } from "./format.ts"

// checkout.ts: existing, untouched
import { total } from "./cart.glyph"

Não dá para colocar Go num codebase TypeScript arquivo por arquivo: é outro runtime, outro sistema de módulos, outro ecossistema. Esse fato sozinho é o motivo de o alvo ser TS.

O argumento justo a favor do Go: o conjunto pequeno e estável de palavras-chave dá ao agente menos jeitos de errar. Concordamos: é exatamente por isso que o Glyph mantém um núcleo pequeno de propósito, com um único jeito de fazer cada coisa. O Go está no nosso benchmark de densidade para uma comparação direta.

Situação atual

Disponível hoje

Saída TypeScript limpa, imports nas duas direções com o seu .ts existente e um núcleo pequeno que roda em qualquer lugar onde roda Node ou um bundle de navegador.

Em medição

O benchmark entre linguagens (Glyph, TS, Go, Python, Rust) cresce junto com o corpus, então a afirmação de “superfície pequena” continua sendo um número, e não uma alegação.
