Design · Comparação

Glyph e Effect

Os dois buscam um TypeScript em que pessoas e agentes possam confiar. Effect é uma biblioteca: você continua escrevendo TypeScript e ganha erros tipados, dependências rastreadas e uma caixa de ferramentas grande. Glyph é uma linguagem que compila para TypeScript, então pode recusar o que o TypeScript permite, inclusive os casts que desfazem as garantias de uma biblioteca. Effect é bem mais maduro.

Como o Effect se descreve

A página inicial do Effect abre com "Reliable TypeScript for the AI era" e diz que seus "declarative patterns and strong type system make it easier for LLMs to generate correct, production-ready code" (effect.website). A documentação o chama de "an ecosystem of tools that help you build better applications and libraries", construído em torno de um tipo Effect<Success, Error, Requirements> que registra o que uma computação retorna, como ela pode falhar e do que ela precisa (Why Effect). Ele exige TypeScript 5.4 ou mais recente com strict ativado (Installation). Essas citações foram lidas em 2026-11-19.

A diferença que vem de ser biblioteca ou linguagem

Os tipos do Effect são checados pelo tsc, então tudo o que o tsc permite continua permitido ao lado deles. Isto compila com tsc --strict usando effect 4.1.4 e TypeScript 6. O cast tira NotFound do canal de erro, e o programa relata uma falha vinda de um effect tipado como incapaz de falhar.

eff.ts: tsc --strict sai com 0; ao rodar, imprime "Failure undefined" 
import { Effect } from "effect"

class NotFound {
  readonly _tag = "NotFound"
}

const find = (id: string): Effect.Effect<number, NotFound> =>
  id === "1" ? Effect.succeed(1) : Effect.fail(new NotFound())

// The error channel says NotFound can happen. A cast erases it.
const quiet = find("2") as unknown as Effect.Effect<number, never>

// And a parsed body still takes any type you name.
type User = { email: string }
const user = JSON.parse("{}") as User

console.log(Effect.runSyncExit(quiet)._tag, user.email)

A mesma função em Glyph retorna um Result, e não há cast para escrever. O segundo módulo é recusado antes de qualquer TypeScript ser emitido.

find.glyph: faz o build, passa no tsc --strict 
module find

pub type NotFound = { id: string }

pub fn find(id: string) -> Result<number, NotFound> {
  return match id == "1" {
    true => Ok(1),
    false => Err({ id: id }),
  }
}
adicionando um cast: recusado 
module find

pub type NotFound = { id: string }

pub fn find(id: string) -> Result<number, NotFound> {
  return match id == "1" {
    true => Ok(1),
    false => Err({ id: id }),
  }
}

pub fn quiet() -> number {
  let n = find("2") as number
  return n
}

A ajuda do E0013 diz: "Glyph has no as cast ... to turn an unknown into a type, validate it with T.parse(v) or narrow it with match and is." Um time consegue chegar perto disso numa base de código com Effect usando regras de lint, e essa comparação explica por que uma regra que alguém pode desligar é uma garantia diferente.

O que o Glyph faz e uma biblioteca não consegue

Uma linguagem decide o que pode ser escrito. O Glyph não tem any, nem cast, nem asserção de não nulo, nem comentário que silencia um erro, e todo match sobre uma union precisa cobrir todos os casos. Records e unions carregam uma checagem de runtime gerada a partir da declaração, então json.parse<User>(body) valida. O Schema do Effect também deriva um tipo de uma única descrição (Schema.Schema.Type<typeof Person> na introdução dele), então ali o tipo e o validador também não se desencontram; a diferença é que nada no TypeScript obriga uma base de código a usá-lo. O compilador também responde perguntas sobre um programa para um agente, como o que uma mudança vai quebrar, via MCP ou pela linha de comando.

Esta página não testou o uso do Effect dentro de um módulo Glyph, então não afirma nada sobre combinar os dois.
