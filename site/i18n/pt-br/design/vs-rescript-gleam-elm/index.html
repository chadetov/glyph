Design · Comparação

Por que não ReScript, Gleam ou Elm?

As três são linguagens tipadas que compilam para JavaScript, e as três são mais antigas, mais usadas e mais estáveis que o Glyph. Se você está escolhendo uma linguagem para um codebase novo e não precisa ficar perto do TypeScript, vale olhar para elas primeiro. As diferenças do Glyph são mais estreitas: ele gera código-fonte TypeScript em vez de JavaScript, importa pacotes npm tipados pelo próprio .d.ts, gera validadores de runtime a partir dos seus tipos, e o compilador responde a consultas de impacto para um agente.

Como cada uma se descreve

A página inicial do ReScript abre com "JavaScript Made Simple for Humans and AI" e "Types > Vibes", e diz que ele "compiles to clean, efficient JavaScript" com "No any, no magic types, no surprise undefined." Ela oferece "automatically generate TypeScript types" (rescript-lang.org).

A página inicial do Gleam o chama de "a friendly language for building type-safe systems that scale", com "No null values, no exceptions, clear error messages". Ele roda na VM do Erlang e "can additionally compile to JavaScript", e "also generates TypeScript definitions" (gleam.run).

A página inicial do Elm descreve "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions", para "reliable web applications", e diz que o Elm "detects all API changes automatically" para "guarantee that every single Elm package follows semantic versioning" (elm-lang.org).

Essas citações foram lidas em 2026-11-19.

O que o Glyph faz diferente

Cada um destes foi rodado no Glyph 0.1.149 para esta página.

Ele gera código-fonte TypeScript

glyph build escreve um arquivo .ts por módulo, que o tsc --strict depois verifica e que você mantém se parar de usar o Glyph. ReScript e Gleam geram JavaScript e definições de tipo ao lado. O TypeScript gerado aparece na página sobre TypeScript.

Ele importa pacotes npm tipados pelas próprias declarações

Um módulo importa um pacote pelo nome, e o .d.ts do pacote tipa cada uso. Não há binding para escrever antes. No ReScript, "external is the primary ReScript feature for bringing in and using JavaScript values" (external), com os tipos declarados do lado do ReScript. Os externals do Gleam precisam de anotações de tipo, e o compilador "cannot verify that the function implemented in the other language returns the specified types" (externals). O Elm conversa com JavaScript por flags, ports e custom elements (interop). Com pg e @types/pg instalados, isto é recusado:

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

O código é TS2322 porque é o tsc que verifica os valores de uma biblioteca, mapeado de volta para a linha do Glyph. O checker do próprio Glyph não os vê, então glyph check --no-tsc, o editor e as ferramentas MCP não pegam esse erro (G257). Um tipo importado de um .d.ts também não tem checagem em runtime.

Ele gera o validador a partir do tipo

Todo record e toda union carregam uma checagem de runtime gerada a partir da declaração, então json.parse<User> retorna Err quando os dados não batem. No Elm você escreve um decoder para cada formato, e o guia observa que "the decoders people write end up working as a validation phase" (JSON).

main.glyph: imprime "refused", porque o JSON não tem email 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

O compilador responde o que uma mudança vai quebrar

Antes de uma edição, um agente pode perguntar até onde uma mudança chega, via MCP (glyph_impact) ou com glyph query impact. Numa union Plan = Free | Pro | Team com um match exaustivo e um que termina em else, perguntar sobre uma variante nova dá uma resposta por ponto de uso:

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

O segundo ponto deixaria de compilar depois da mudança, o que qualquer um desses compiladores também diria quando a mudança fosse feita. O primeiro continuaria compilando e mandaria o caso novo para o seu else, e é a consulta que o aponta. Para quem constrói agentes lista as outras ferramentas.

O que esta página não afirma

Ela não comparou mensagens de erro, velocidade de compilação nem desempenho em runtime, e não tentou chamar nenhuma das três a partir do Glyph nem o contrário. As citações descrevem cada projeto com as próprias palavras dele; até que ponto cada um cumpre o que diz é algo para você verificar, assim como as afirmações do próprio Glyph na página de evidências.
