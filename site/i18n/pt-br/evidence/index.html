Evidências

Como cada afirmação deste site é verificada

Uma afirmação de que o Glyph detecta algo é um par de programas no repositório, um em TypeScript e um em Glyph, e um gate de CI roda os dois a cada mudança. Se o TypeScript para de compilar ou o Glyph deixa de ser recusado, o build falha. Você pode rodar qualquer caso por conta própria com dois comandos.

As fixtures

Cada diretório em catches/ contém ts.ts, glyph.glyph e um case.toml dizendo o que cada um faz. scripts/check_catches.py roda na CI. Ele exige que todo ts.ts passe no tsc --strict, já que um programa TypeScript que não compila não prova nada, e verifica a metade Glyph de acordo com o tipo do caso. {{catches:breakdown}} Pelo tipo que o gate verifica:

TipoCasosO que o gate exige do Glyph
refused{{catches:refused-all}}O build falha com o código que está em case.toml
warned{{catches:warned-all}}O build passa e reporta esse código como aviso
boundary{{catches:boundary-all}}O programa roda, e a checagem na fronteira transforma o dado ruim em um Err
runtime{{catches:runtime-all}}O programa builda e depois para quando roda, com a saída indicada
gap{{catches:gap-cases}}O Glyph aceita o programa e ele faz a coisa errada. Quando a brecha fecha, o gate falha e diz para mover o caso

Um caso que deixa de ser demonstrável é apagado, não amenizado, e o README dos casos lista os seis que foram apagados e por quê. Descobriu-se que um deles também era detectado pelo tsc; outro só funcionava porque o TypeScript dele recebia um valor como any.

O TypeScript com que é comparado

Cada caso também diz se um projeto TypeScript configurado por completo teria detectado o erro, e é daí que vem a etiqueta "o TypeScript detectaria?". "Configurado por completo" é tsc --strict mais todas as opções que o deixam mais rígido, e uma execução do typescript-eslint. O gate instala os pacotes do zero a cada execução (TypeScript 6, eslint 9, typescript-eslint 8, tsx 4 e o @types/node mais recente) e, sem rede, falha em vez de pular.

A etiqueta de um caso é none, flag: mais a única opção que o reporta, ou lint: mais a regra. Quando o programa corrigido também dispara uma regra por um motivo não relacionado, o caso traz um ts_ok.ts e a etiqueta só conta o que dispara no erro. Por exemplo, non-exhaustive-match é lint:switch-exhaustiveness-check: o typescript-eslint detecta se você ativar essa regra, e a página diz isso.

Os trechos de código deste site compilam

scripts/check_docs_compile.py roda na CI e compila todo trecho Glyph do site que se sustenta sozinho (começa com module e declara algo), mais os da documentação e do llms.txt. Um trecho que deve falhar precisa nomear o erro que provoca, e precisa provocar exatamente esse. Trechos que precisam de React ou de um pacote npm são compilados contra os tipos reais desses pacotes. Fragmentos são contados e pulados, e a contagem é impressa para que a parcela pulada continue visível.

O que ele ainda não detecta

Os {{catches:gap-cases}} casos gap estão na página de casos, cada um com seu número de gap. Todo gap encontrado construindo apps em Glyph está no registro, docs/dogfooding-gaps.md, onde um marcador entre colchetes é o único status vivo ([FIXED], [HALF FIXED], ou nenhum para os abertos) e scripts/check_gaps.py falha a CI quando uma entrada aberta foi reproduzida pela última vez há mais de cinco releases.

Como uma release é marcada como Breaking

Uma release é marcada como Breaking quando recusa um programa que a versão anterior aceitava. Isso é decidido escrevendo o menor programa afetado e rodando-o com a release anterior publicada e com o binário novo, e depois comparando os códigos de saída. Não é deduzido do texto das notas. As releases anteriores à 0.1.99 nunca foram testadas assim, então uma sem marca não foi testada, o que não quer dizer que seja segura. O registro está na página de versões.
