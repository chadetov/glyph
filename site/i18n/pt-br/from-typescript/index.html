Para quem vem do TypeScript

O que muda quando você já escreve TypeScript

Menos do que você imagina. Glyph compila para TypeScript que passa no tsc --strict, mantém o npm e o seu deploy, e se lê quase igual. As diferenças são poucas, e cada uma troca uma forma de errar por uma verificação que o compilador faz.

Se você conhece TypeScript, já conhece quase tudo isto

Você não aprende uma linguagem nova, só estas quatro coisas. São as que aparecem em todos os exemplos deste site.

match
Um switch exaustivo: sobre uma union, o compilador obriga você a tratar todos os casos. Também é a única condicional: não existe if/else nem ternário, como explicado abaixo.
Result<T, E>
Erros como valores de retorno, não como exceções lançadas. Você trata um com match ou o propaga com o operador ?.
fn f() -> T
Uma função; o -> indica o tipo de retorno. Um type X = {...} é um record, e um type X = A | B é uma union etiquetada.
mut x = e
Reatribuição é explícita e fácil de buscar. Um let comum nunca muda por baixo de você; para mudar um, você escreve mut.

Um componente React nas duas linguagens

O mesmo componente duas vezes: uma lista de convites com estado vazio, uma linha que conta os que ainda aguardam resposta e um rótulo em cada linha. Onde o TSX usa && e ? :, o Glyph usa <match>, que recebe um valor e um <case> por padrão. Listas usam <for>, e o atributo é class, que compila para className.

InviteList.tsx 
export type Invite = { email: string; accepted: boolean };

export function InviteList(props: { invites: Invite[] }) {
  const waiting = props.invites.filter((i) => !i.accepted).length;
  return (
    <section>
      {waiting > 0 && <p className="note">{waiting} waiting for a reply</p>}
      {props.invites.length === 0 ? (
        <p className="empty">No invites sent yet.</p>
      ) : (
        <ul>
          {props.invites.map((invite) => (
            <li key={invite.email}>
              {invite.email}
              {invite.accepted ? (
                <span className="ok">joined</span>
              ) : (
                <span className="wait">pending</span>
              )}
            </li>
          ))}
        </ul>
      )}
    </section>
  );
}
invites.glyph 
module invites

import std/array

pub type Invite = { email: string, accepted: bool }

pub component InviteList(props: { invites: Array<Invite> }) {
  let waiting = array.filter(props.invites, fn(i: Invite) { return !i.accepted }).length
  return <section>
    <match value={waiting > 0}>
      <case true>
        <p class="note">{waiting} waiting for a reply</p>
      </case>
      <case false></case>
    </match>
    <match value={props.invites.length}>
      <case 0>
        <p class="empty">No invites sent yet.</p>
      </case>
      <case else>
        <ul>
          <for invite in={props.invites} key={invite.email}>
            <li>
              {invite.email}
              <match value={invite.accepted}>
                <case true>
                  <span class="ok">joined</span>
                </case>
                <case false>
                  <span class="wait">pending</span>
                </case>
              </match>
            </li>
          </for>
        </ul>
      </case>
    </match>
  </section>
}

A metade em Glyph é mais longa. O && vira um <match> com um caso false vazio, e omitir esse caso é E0209, porque um match sobre um bool precisa cobrir os dois valores. Sobre uma union, o mesmo elemento precisa cobrir todas as variantes (E0200), e é aí que as linhas a mais se pagam: Funciona com React? mostra um caso, com hooks e Context.

Suporte a editor e depuração têm respostas próprias: a resposta sobre ferramentas trata do language server e da extensão para VS Code, e a resposta sobre depuração trata dos source maps de volta ao arquivo .glyph. No ciclo de desenvolvimento, glyph build --watch recompila o TypeScript sempre que você salva um arquivo .glyph. Um dev server do Vite que importa essa saída recarrega a página inteira depois de cada recompilação em vez de trocar o componente a quente, então o estado do componente se perde; seus próprios arquivos .tsx continuam com o hot reload do Vite. Grave a saída fora do diretório de build do Vite (dist/ por padrão), porque o dev server não observa esse diretório.

"Agentes", neste site, são assistentes de código com IA como Claude, Copilot e Cursor. Glyph ajuda mais a eles, mas as verificações são as mesmas seja o código escrito por uma pessoa ou por um modelo. Se você já usa TypeScript estrito com zod e eslint, veja o que uma linguagem acrescenta a isso.

Não existe if

Um desvio sobre um booleano é um match em true e false. Quando você só age em um dos lados, o outro braço é um bloco vazio.

TypeScript 
function label(admin: boolean): string {
  return admin ? "admin" : "member";
}

if (verbose) {
  console.log("starting");
}
Glyph 
fn label(admin: bool) -> string {
  return match admin {
    true => "admin",
    false => "member",
  }
}

match verbose {
  true => io.println("starting"),
  false => {},
}

O motivo é a decisão D3 da especificação: uma única construção para desviar com base em um valor, então há uma só forma para ler, escrever e buscar. Um valor que sai de um desvio sempre sai de um match, cujo tipo de resultado o próprio verificador do Glyph calcula, em vez de deixar isso para o tsc. Para uma union, é essa mesma construção que precisa cobrir todos os casos (E0200). Para um booleano isso rende pouco, já que false => {} não diz nada além de omitir um else.

Isso tem um custo. Um ternário de uma linha vira um match de quatro linhas, um retorno antecipado sob uma condição é um match com um braço vazio, e é a primeira coisa que parece errada para quem lê TypeScript. A especificação registra a verbosidade como um custo aceito. Escrever if mesmo assim dá o erro E0006, cuja ajuda mostra a forma com match; um ternário dá E0013, com a mesma ajuda.

O imposto que você já paga

Se você desenvolve com agentes de IA em uma base de código TypeScript, estes são os custos do dia a dia. Cada um tem uma resposta específica no Glyph, com link na lista.

  • Agentes inventam APIs, porque o TypeScript apaga seus tipos e o runtime deixa de concordar com o tempo de compilação. Os tipos do Glyph trazem uma verificação em runtime (T.parse, T.is), veja APIs tipadas.
  • Agentes disfarçam a incerteza com any e as unknown as T, e o compilador deixa. Nenhum dos dois existe no Glyph, veja a tabela abaixo.
  • Você pede uma mudança de uma linha e recebe o arquivo inteiro reescrito, porque o formatador se propaga a cada edição. O glyph fmt tem um único layout, sem opções, veja diffs limpos.
  • Você mantém um validador escrito à mão ao lado de cada tipo (zod, e um serializador), e um agente renomeia um campo em um deles mas não nos outros; tudo continua compilando. No Glyph, o tipo é o validador.
  • Você faz grep por um símbolo e encontra dez resultados sem relação: overloads, decorators, namespaces mesclados. Glyph não tem nada disso, veja encontrar as coisas.

Uma válvula de escape, e dá para achá-la com grep

Quando você precisa de TypeScript que o Glyph não consegue expressar, extern_ts("...") recebe um tipo ou expressão inline, e o tsc continua verificando. Para um módulo inteiro, coloque o .ts em src/extern/ e escreva import extern/name; imports relativos são proibidos fora isso, então esse caminho é a única entrada. As duas formas contêm a palavra extern, então grep -rn extern src/ lista todos os lugares onde o verificador passa o controle para o TypeScript.

src/clock.glyph 
module clock

pub fn now_ms() -> number {
  return extern_ts("Date.now()")
}

Como é o TypeScript gerado

TypeScript comum, um arquivo por módulo, que você pode ler e commitar. Uma union vira uma union discriminada mais um valor que carrega sua verificação em runtime, e um match vira um switch na tag. Esta é a saída do glyph build para o módulo da esquerda, sem as linhas de import.

plan.glyph 
module plan

pub type Plan = Free | Pro | Team

pub fn seats(p: Plan) -> number {
  return match p {
    Free => 1,
    Pro => 5,
    Team => 50,
  }
}
plan.ts (gerado, resumido) 
export type Plan =
  | { tag: "Free" }
  | { tag: "Pro" }
  | { tag: "Team" };

export const Free: Plan = { tag: "Free" };
export const Pro: Plan = { tag: "Pro" };
export const Team: Plan = { tag: "Team" };
export const Plan = {
  is(value: unknown): value is Plan { ... },
  parse(value: unknown) { ... },
  schema: ...,
};

export function seats(p: Plan): number {
  const __m0 = p;
  switch (__m0.tag) {
    case "Free": { return 1; }
    case "Pro": { return 5; }
    case "Team": { return 50; }
    default: throw new Error("non-exhaustive match");
  }
}

Se você parar de usar Glyph, o .ts gerado é o que fica com você. Ele não tem dependência de runtime além de um pequeno diretório de suporte que o build grava ao lado.

npm, e o TypeScript que você já tem

Um módulo .glyph importa um pacote npm pelo nome (import kafkajs { Kafka }), tipado pelas declarações do próprio pacote, e o seu .ts existente importa os módulos Glyph gerados como qualquer arquivo local.
