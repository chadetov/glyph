Para agentes · Model Context Protocol

Ligue seu agente ao compilador do Glyph

O glyph mcp roda um servidor Model Context Protocol com onze ferramentas sobre o seu projeto: o que é um símbolo, o que quebra se você mudá-lo, se um valor de um tipo pode ir onde outro está declarado, do que uma declaração depende, o que um módulo exporta, diagnósticos verificados dentro do projeto, o tipo sob o cursor, onde um nome é definido, todas as referências a ele, todo local de match sobre uma union, e busca de símbolos. Cada uma também é um verbo do glyph query, então um agente sem cliente MCP faz as mesmas perguntas e recebe os mesmos bytes.

Por que um agente quer isso

Um agente editando uma base de código costuma trabalhar às cegas. Lê arquivos, chuta tipos e só descobre se quebrou algo depois de um build. O Glyph já responde essas perguntas para um editor. O glyph mcp dá ao agente as mesmas respostas direto do compilador, sem raspar a saída do build nem ler todos os arquivos para descobrir quem chama o quê. Duas das ferramentas respondem perguntas que um editor nunca faz: glyph_symbol retorna as variantes de uma union com a sintaxe que constrói cada uma, que é o que um agente precisa antes de escrever o match, e glyph_impact responde o que uma edição quebra antes de a edição existir.

Configuração

Qualquer cliente MCP pode iniciá-lo. Aponte o cliente para o binário glyph com o subcomando mcp, e passe a raiz do projeto como argumento ou rode-o a partir do diretório do projeto. Ele fala MCP via stdio, então não há porta nem daemon.

configuração do cliente mcp (genérica) 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp", "/path/to/your/project"]
    }
  }
}

Na primeira conexão o cliente chama initialize e tools/list; o servidor informa as onze ferramentas abaixo. As posições que você envia seguem a convenção do LSP: uma line a partir de 0 e um character a partir de 0, em unidades de código UTF-16. Os intervalos dos diagnósticos voltam do jeito que o glyph check --json os imprime, com line e col a partir de 1, mais o offset em bytes.

A descrição de cada ferramenta traz o contrato de que você precisa no momento da chamada, e o manual completo fica no glyph llms --json em tools, indexado pelo nome da ferramenta, com o verbo glyph query de cada uma ao lado. Essa resposta trazia todos os manuais: onze ferramentas, 31.446 bytes de descrição em uma resposta de 45.509 bytes. Agora são 8.627 em uma resposta de 20.386 bytes, e nada foi apagado. Toda sessão paga pelo tools/list ao conectar e só paga pelo manual quando o pede. Esse documento é gerado a partir das tabelas do próprio compilador, e um teste quebra o build se ele citar uma ferramenta que este servidor não oferece.

As onze ferramentas

ferramentas expostas pelo glyph mcp 
// everything the compiler holds about one symbol: kind, identity,
// visibility, a record's fields, a union's variants with payloads and
// construction syntax, parameters and return, interface members,
// whether a `match` over it must be exhaustive, its `@example`.
// The identity reaches the stdlib: std/result::Result answers with
// Ok(T) and Err(E), and `path` is null beside the reason why
glyph_symbol(entity)                       // or (path, line, character)

// what breaks if you make one named change to one declaration:
// add_variant, remove_variant, rename, change_arity,
// change_signature_type, remove. One verdict per site
glyph_impact(entity, change)

// can a value of `from` go where a `to` is declared? Asked of the
// checker's own comparison. Each side is a `module::name` or a
// Glyph type spelling read in the scope of `path`
glyph_assignable(path, from, to)

// every diagnostic for one file, checked inside its project, in the
// shape `glyph check --json` prints, plus what was not checked
glyph_diagnostics(path)

// the type at a position: an expression, a declaration name, a
// parameter, an annotation, a variant, or a binding
glyph_hover(path, line, character)

// where the name is defined, following imports across modules,
// with the `module::name` so the answer chains into glyph_impact
glyph_definition(path, line, character)

// every edge into a symbol across the project, split by relation
// (CALLS, REFERENCES, GENERATED_FROM), each with its provenance
glyph_references(path, name)               // or by position

// every `match` site over one tagged union and which variants each
// site's arms name, with the union's own variants
glyph_variants(path, name)

// search top-level declarations and union variants by name, each
// entry with its identity, `pub`, kind and one-line signature
glyph_symbols(query)

// what one declaration depends on: every declaration its own source
// names, split by relation (CALLS, REFERENCES, FIELD_ACCESS), each
// edge with both ends and its provenance. The mirror of references
glyph_dependencies(entity)

// what one module makes visible to an importer: every `pub`
// declaration and every variant a `pub` union hoists, each with
// its identity, kind and signature
glyph_exports(module)

Veja na prática

Um tools/call para glyph_diagnostics em um arquivo com um erro de digitação em um campo retorna o diagnóstico do próprio compilador, o mesmo tipo Rust que o glyph check --json serializa, dentro de um envelope que também diz o que a verificação não cobriu.

requisição 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": { "path": "src/user.glyph" }
  }
}
resultado (o conteúdo JSON da ferramenta) 
{
  "path": "src/user.glyph",
  "module": "user",
  "project_root": "src",
  "member": true,
  "diagnostics": [
    {
      "code": "E0210",
      "severity": "error",
      "stage": "typecheck",
      "message": "type `U` has no field `naem`; did you mean `name`?",
      "help": "Check the field name for a typo,
        or add the field to the type.",
      "entity": "user::greet",
      "file": "user",
      "range": {
        "start": { "line": 9, "col": 10, "offset": 99 },
        "end":   { "line": 9, "col": 16, "offset": 105 }
      },
      "union": null,
      "missing_variants": null
    }
  ],
  "unindexed": [],
  "not_run": [ ... ]
}

O arquivo é verificado dentro do seu projeto, então um campo errado em um record importado e um match sem braços sobre uma union importada são relatados aqui do jeito que o glyph check os relata. O que a ferramenta não conseguiu cobrir está na resposta, em vez de ficar para você supor: member diz se a varredura do projeto alcança o arquivo, unindexed nomeia arquivos do projeto cujo parse falha, e not_run nomeia as três verificações que o glyph check faz e esta não: tsc, E0104 para um import que não aponta para nenhum módulo, que precisa da visão que o build tem de node_modules, e E0400 para um @example que falha, que é decidido rodando o projeto gerado. Um teste roda as duas interfaces em seis projetos e compara o JSON chave por chave, então as duas não podem divergir.

O glyph_references cobre o workspace inteiro: pergunte sobre um símbolo e você recebe a declaração, todos os usos, e o binding de import de cada módulo que o importa, em todos os arquivos. Ele usa a mesma identidade entre arquivos que o rename do editor usa, então a resposta cobre o projeto inteiro, não só o arquivo de onde você perguntou.

Sem cliente MCP? As mesmas perguntas na linha de comando

Toda ferramenta tem um verbo glyph query que recebe os argumentos da própria ferramenta como flags e imprime o JSON da ferramenta no stdout. Uma pergunta respondida sai com 0; uma recusada escreve o motivo no stderr e sai com 2. Os verbos passam pelo mesmo ponto de entrada que um cliente MCP alcança, e um teste de integração faz a mesma pergunta às duas interfaces e compara as respostas como texto, então um verbo que reformatasse ou resumisse falharia.

as mesmas onze perguntas, sem cliente 
glyph query symbol       --path src/main.glyph --entity orders::OrderStatus
glyph query impact       --entity orders::OrderStatus --change add_variant --variant Refunded
glyph query assignable   --path src/main.glyph --from 'Nullable<int>' --to int
glyph query diagnostics  --path src/main.glyph
glyph query hover        --path src/main.glyph --line 9 --character 6
glyph query definition   --path src/main.glyph --line 9 --character 6
glyph query references   --path src/orders.glyph --name create
glyph query variants     --path src/orders.glyph --name OrderStatus
glyph query symbols      --query order
glyph query dependencies --path src/main.glyph --entity main::build
glyph query exports      --path src/main.glyph --module orders

// the same two, asked about a module the compiler carries
glyph query symbol       --path src/main.glyph --entity std/result::Result
glyph query exports      --path src/main.glyph --module std/result

Quando o build já está vermelho

As ferramentas respondem perguntas feitas antes de uma edição. Depois dela, o que ler é o glyph check --agent, que imprime os diagnósticos do check --json com mais duas chaves em cada um: constraints, os invariantes que uma edição de reparo precisa manter, e symbols, a resposta de glyph_symbol para cada símbolo que o diagnóstico cita, então a próxima edição não precisa de uma segunda chamada. Em um match com braços faltando, isso significa que as variantes da union, com seus payloads, chegam junto com o erro que as pediu, além da frase dizendo que um braço else abriria mão da garantia que o diagnóstico existe para proteger. Quando o reparo está totalmente determinado, o glyph fix o escreve e diz o que recusou. Há um passo a passo do ciclo inteiro com saída real.

Situação atual

Disponível hoje

Um servidor glyph mcp [root] via stdio com onze ferramentas: glyph_symbol, glyph_impact, glyph_assignable, glyph_diagnostics, glyph_hover, glyph_definition, glyph_references (no workspace inteiro), glyph_variants, glyph_symbols, glyph_dependencies e glyph_exports. Cada uma tem um verbo glyph query que imprime o mesmo JSON. As respostas vêm das consultas do próprio compilador, e todo fato que uma ferramenta não tem é null ao lado de uma frase <key>_absent dizendo por quê. O hover responde em um nome declarado em outro módulo, então uma função importada no local da chamada e um campo lido de um record importado têm, ambos, um tipo. A identidade de uma entidade chega à stdlib: o Result do prelude é std/result::Result, que é o módulo em que o resolver o registra e o módulo de onde o emissor escreve o import, então o glyph_symbol sobre ele responde com Ok(T) e Err(E), e o glyph_exports sobre std/result lista a interface. Não há código Glyph por trás, então path e range são null com esse motivo, em vez de ausentes.

A caminho

As ferramentas só leem: você não consegue renomear nem aplicar uma edição via MCP. O lado da escrita fica na linha de comando, como glyph fix. O servidor varre o projeto de novo a cada chamada em vez de manter um índice em cache, e pula qualquer arquivo cujo parse falha. A resposta de tools/list tem 20.386 bytes, contra 45.509 antes, e isso ainda é contexto que toda sessão paga ao conectar.

Além das ferramentas, um agente pode ler a linguagem e os diagnósticos offline: llms.txt é o texto, glyph llms --json é o mesmo conhecimento como dados vindos das tabelas do próprio compilador, e glyph build --json é o caminho em lote para diagnósticos com código em uma árvore inteira.
