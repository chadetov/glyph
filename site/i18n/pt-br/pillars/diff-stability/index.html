Estabilidade dos diffs

Uma mudança de uma linha é um diff de uma linha. Um formato canônico, vírgulas finais e listas que ficam inteiras em uma linha ou com um elemento por linha, nunca reempacotadas. Assim o review mostra a mudança que foi feita, não o ruído em volta dela.

Review é ler diffs

Quase tudo em que confiamos numa mudança (o review, o blame, o revert, o bisect) se apoia no diff. Então a relação sinal/ruído do diff é o que vale.

Detalhes de onde vem o ruído

Na maioria dos codebases ela é péssima: um formatter refaz a quebra de uma linha, um ordenador de imports embaralha um bloco, um rename mexe no espaçamento de cada chamada, e a única linha que importa fica enterrada entre cinquenta que não importam.

Agentes pioram muito isso. Diante de uma tarefa pequena, um modelo reescreve sem cerimônia uma função inteira, ou um arquivo inteiro, para mudar uma coisa, porque regenerar é mais fácil para ele do que editar com precisão. Quem revisa fica comparando uma reescrita com o original e torcendo para que a única mudança de verdade seja a pretendida.

O Glyph é feito para que o layout não dê ao modelo nada para remexer.

01 Um layout canônico, sem escolhas

glyph fmt reimprime cada arquivo num único layout fixo: indentação de dois espaços, vírgula final em toda lista de várias linhas, e uma lista que fica numa linha enquanto couber em 100 colunas e passa a um elemento por linha quando não cabe. É tudo ou nada.

Detalhes sem reempacotar, uma única forma válida

O formatter nunca reempacota seus elementos para preencher uma linha, então uma lista nunca fica metade numa linha e metade na seguinte, e adicionar um campo é uma única linha adicionada. Como existe exatamente uma forma válida, não há o que discutir nem nada para uma ferramenta "consertar" por fora.

O custo disso é o limite de largura. Renomeie um binding de modo que uma chamada passe de 100 colunas e a chamada se expande para um argumento por linha: uma edição de um token, um diff de quatro linhas. A contrapartida é que o layout depende só do código e da coluna em que ele começa, então dois agentes editando o mesmo arquivo chegam aos mesmos bytes.

A vírgula final faz um trabalho discreto: como o último elemento já termina em vírgula, adicionar um irmão nunca edita a linha de cima. Uma inserção, uma linha.

02 A ordem é estável, então o histórico é legível

Um elemento por linha significa que reordenar, inserir ou remover um item toca só as linhas desse item, nunca as vizinhas.

O git blame continua útil: o último commit que tocou cada linha é o commit que de fato mudou aquele elemento, não a passada de formatação que reempacotou a linha que ele dividia com outros.

03 Sem barrel files: sem ruído nos imports

Como imports nunca reexportam e não existem camadas de agregação index.ts (E0102), adicionar ou mover um símbolo não se propaga por um barrel que todo consumidor importa. As dependências que você edita são as que você quis editar; o resto do grafo de imports não se mexe.

04 A geração é idempotente, não um bloco opaco

A mesma disciplina vale para código gerado. glyph gen e glyph regen reimprimem a saída pelo formatter canônico, então regenerar depois de uma mudança na spec produz um diff mínimo que dá para revisar, umas poucas linhas alteradas, e não a substituição inteira de um arquivo escrito por máquina.

um campo adicionado à spec → o diff regenerado 
  type Task = {
    id: number,
    title: string,
+   done: bool,
  }
// glyph regen re-ran the recorded command; this is the whole diff.

E todo .ts emitido vem com source map, então até a saída compilada aponta direto para a linha que você mudou.

05 "TypeScript faz isso com Prettier"

Em boa parte da formatação, faz. Prettier com trailingComma: "all" põe vírgula no último elemento e imprime listas longas com um item por linha, e isso cobre a maior parte da seção 01. As diferenças estão em três pontos.

  • O layout depende só do código.O Prettier mantém um objeto literal expandido se o autor pôs uma quebra de linha depois do {, e o recolhe se não pôs, então o mesmo objeto pode sair de dois jeitos dependendo de como foi digitado da primeira vez. Dois agentes escrevendo a mesma coisa produzem dois layouts, e a próxima edição em um deles aparece como reflow. glyph fmt imprime { a: 1, b: 2 } do mesmo jeito, não importa como a entrada estava quebrada.
  • Não há nada para configurar.A saída do Prettier é o que o arquivo de config do repositório disser, e alguns repositórios nem têm um. Um agente que passa de um projeto TypeScript para outro encontra um layout diferente em cada um. Um arquivo Glyph tem o mesmo layout em todo projeto, porque o formatter não tem opções.
  • O formatter não muda o que um arquivo diz.glyph fmt é testado fazendo o parse da própria saída e comparando a árvore sintática com a da entrada, em todos os exemplos do repositório e sob um fuzzer. Quando um comentário fica num lugar onde o layout não tem linha para ele, o formatter recusa o arquivo (E0500) em vez de mover o comentário para perto de código que ele não descreve.

Uma coisa da lista ainda não está pronta: glyph fmt não ordena imports, então dois agentes adicionando um import em lugares diferentes ainda produzem blocos de import diferentes (G358).

A estabilidade dos diffs é o que transforma "o agente mudou alguma coisa" em "o agente mudou exatamente isto". Quando o ruído de fundo é zero, o review é rápido e a confiança sai barata.
