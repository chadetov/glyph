Pilar 01 · A cunha

Verificabilidade

O Glyph fecha as brechas por onde um agente escorrega: não existe any nem as que você possa escrever, o match é comprovadamente exaustivo, e os tipos que você declara ganham validadores estritos em runtime, tudo imposto como uma camada estrita sobre o tsc. Ele não verifica tudo sozinho, e abaixo está dito exatamente onde a garantia termina.

A mentira que um tipo pode contar

No TypeScript, um tipo é uma promessa de tempo de compilação que evapora antes de o código rodar. Uma anotação User é apagada por completo; o objeto que você realmente recebe de uma chamada de rede, de um parse de JSON ou de um campo de formulário pode ter qualquer forma. Pior, a linguagem oferece três formas válidas de mentir para o verificador sobre isso: any, um cast as e um ! de não nulo. Um agente trabalhando rápido usa as três, e o tsc --strict continua verde enquanto o bug vai para produção.

A primeira tarefa do Glyph é fechar essas brechas. Não com mais anotações, mas removendo as válvulas de escape e fazendo cada tipo levar sua prova até o runtime. Veja o que isso significa, uma garantia de cada vez.

01 Não existe any

any é a palavra-chave mais cara do TypeScript: ela desliga o sistema de tipos para um valor e para tudo em que esse valor encosta. Um único any numa fronteira contamina silenciosamente o grafo de chamadas dali para frente. O Glyph não tem isso. O tipo do topo é unknown, e unknown é inerte: você não pode chamá-lo, indexá-lo nem passá-lo para nada tipado até ter provado o que ele é.

TypeScript: compila, depois quebra handler.ts 
function handle(body: any) {
  // tsc --strict: fine.
  // runtime: throws on {}.
  return body.user.name.toUpperCase();
}
Glyph: o estreitamento é a prova handler.glyph 
fn handle(body: unknown) -> string {
  return match User.parse(body) {
    Ok(u) => string.upper(u.name),
    Err(_) => "unknown",
  }
}

Você não consegue tirar um valor tipado de unknown sem uma verificação que o compilador enxergue. No Glyph, o estreitamento é a prova em runtime. Não existe sintaxe para pulá-lo.

02 Os tipos existem em runtime

Como User.parse existe? Porque todo tipo record, e toda union etiquetada não genérica, gera um descritor de runtime junto: um guard is, um parse que valida um unknown e devolve um Result, e um schema componível. A forma do record é de fato inspecionada em runtime, não presumida, então uma verificação is User é uma verificação real, não um no-op apagado.

o tipo que você escreve, e o descritor gerado a partir dele 
type User = {
  id: number,
  name: string,
  email: string,
}

// generated: User.is(v), User.parse(v) -> Result<User, ...>, User.schema

fn create(req: Request) -> Result<Response, string> {
  return match User.parse(req.body) {   // untrusted input, validated
    Ok(user) => Ok(json(201, user)),
    Err(issues) => Ok(json(400, issues)),
  }
}

Esta é a resposta para "toda API precisa de um validador escrito à mão". O tipo é o validador. Uma fronteira (o corpo de uma requisição, um arquivo de configuração, uma resposta de terceiros) só se torna tipada passando por uma verificação que consegue de fato rejeitar dados ruins.

Onde isso termina: o descritor de um record é estrito por padrão. Ele confirma os campos declarados e rejeita um valor que traga chaves não declaradas (coloque @open no tipo para permitir extras). Tipos record ganham descritor, inclusive os genéricos, então Paginated<User> verifica cada elemento como um User, e o descritor de uma union etiquetada verifica a tag e depois os campos do payload daquela variante. O que ainda não ganha descritor é uma union etiquetada genérica (Box<T> = Empty | Full({ value: T }) não tem Box.parse), ou um tipo importado de um .d.ts que você só referencia. Quando uma verificação consegue provar só parte de uma forma, o compilador diz isso em vez de sugerir uma garantia que não pode dar.

03 Todos os casos, ou não compila

Um match sobre uma union selada precisa tratar todas as variantes. Adicione uma variante depois e todo match que não a considerava para de compilar (E0200). O caso novo não consegue cair silenciosamente em undefined como acontece com um ramo de switch esquecido. E não são só unions: fazer match de um number ou string em valores literais exige um else (E0218), porque esses domínios são ilimitados e um conjunto de literais nunca fica completo.

status.glyph 
type Status = Active | Paused | Cancelled

fn label(s: Status) -> string {
  return match s {
    Active => "on",
    Paused => "hold",
    // forgot Cancelled...
  }
}
erro de compilação, não um undefined em runtime $ glyph build

04 Erros são valores, não surpresas

Uma função que pode falhar retorna Result<T, E>. Você o trata com match, ou o propaga com o operador ?, e o tipo do erro precisa bater (não há conversão implícita escondendo uma incompatibilidade). Ignore um Result por completo (chame pela ação e descarte o que voltou) e o Glyph avisa (E0217), porque um erro descartado é uma falha engolida. Você o silencia de propósito com let _ = ..., nunca por acidente.

pipeline.glyph 
fn load(id: string) -> Result<User, AppError> {
  let raw = fetch_user(id)?           // Err short-circuits to the caller
  let user = User.parse(raw.body)?    // validation Err propagates too
  return Ok(user)
}

fn main() -> number {
  save(user)   // E0217: this returns a Result whose Err is dropped
  return 0
}

05 Até dados pessoais ficam no nível dos tipos

O mesmo instinto de "isso é trabalho do compilador, não uma convenção" chega até os dados sensíveis. Coloque @redact em um tipo e o descritor dele ganha um redact() que mascara esses campos, então um json.stringify(User.redact(u)) perdido não consegue vazá-los. Cite um campo que o tipo não tem e é um erro de compilação (E0219), não um mascaramento que silenciosamente não protege nada.

patient.glyph 
@redact fields: [diagnosis, notes]
type Patient = {
  name: string,
  diagnosis: string,
  notes: string,
}

// json.stringify(Patient.redact(p)) ->
// {"name":"Ada","diagnosis":"[REDACTED]","notes":"[REDACTED]"}

Cinco modos de falha diferentes (entrada não verificada, um caso esquecido, um erro descartado, um segredo vazado, uma chave não validada) e em todos a correção tem a mesma forma: o compilador se recusa a fingir.

Como é imposto, e onde a garantia termina

Sendo preciso, porque a diferença importa: o Glyph é um dialeto estrito e imposto sobre o tsc, não um verificador independente. Algumas coisas ele prova sozinho: exaustividade, o tipo de erro do ?, a ausência de any/as no seu código, validação estrita de chaves. O resto da compatibilidade de tipos ele impõe emitindo TypeScript e rodando o tsc --strict, que quebra o build. A cunha é que essas verificações são a linguagem, não um lint opcional que o agente pode desligar, e não que o Glyph reimplemente um verificador de tipos.

Duas limitações anteriores daqui foram resolvidas na 0.1.10. O emissor inseria um cast de retorno verificado pelo Glyph e não pelo tsc em toda função genérica; agora isso só acontece onde um combinador de validação monta um valor de um tipo derivado de uma forma (infer_output<Shape>), e todo genérico correto é emitido sem cast nenhum. E o tipo de saída de um validador não é mais aceito na confiança: o infer_output o deriva da forma que você passa, e o tsc verifica sua anotação contra ele: uma forma sem um campo do tipo que você declara agora não compila.

Tipos genéricos agora também validam em profundidade: um descritor Paginated<User> verifica cada elemento como um User, não só sua presença. Resta uma limitação, dita com todas as letras: um tipo importado de um .d.ts externo que você só referencia não tem descritor até você materializá-lo com glyph gen dts, então um campo desse tipo é verificado quanto à presença, não à forma. Essa fronteira é proposital (um tipo que o Glyph não emitiu não pode prometer validação em runtime), e materializá-lo resolve.

Nada disso custa cerimônia. Não há anotações de prova, nem contratos, nem verificador a satisfazer. O código acima é Glyph comum. Verificabilidade não é um recurso que você liga; é o que sobra quando as formas de mentir deixam de existir.

"TypeScript estrito e uma config de lint já fazem isso"

Dentro de um programa, chegam perto. strict, noUncheckedIndexedAccess e uma regra contra any explícito pegam a maior parte do que um agente deixaria passar. Eles param nas bordas. JSON.parse(body) as User compila com qualquer configuração que exista, e a correção de costume, um schema zod, é uma segunda descrição de User que precisa ser mantida em sincronia com a primeira à mão. No Glyph o tipo é o validador: json.parse<User>(body) é verificado contra o próprio User, e um tipo que o Glyph não consegue verificar em runtime é recusado em vez de aceito na confiança.

A outra diferença é quem pode contar com isso. Uma config de lint é uma escolha que um repositório fez. Um agente que abre uma base TypeScript desconhecida não pode presumir que any é proibido ali; no Glyph, ele não pode ser escrito em lugar nenhum.

A mesma garantia, vista pelos erros que um agente comete e pelos erros de compilação que o impedem, é respondida em O que impede um agente de quebrar meu código sem ninguém perceber?
