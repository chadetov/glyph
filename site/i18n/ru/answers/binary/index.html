20 · Бинарные данные

Можно ли работать с бинарными данными, или всё строка?

std/bytes даёт неизменяемую последовательность октетов, и с ней работают и std/fs, и std/crypto. До 0.1.78 так не было: каждая граница стандартной библиотеки принимала и возвращала строки, поэтому PNG нельзя было прочитать, а HMAC нельзя было передать настоящий ключ.

Почему это важно

Первый байт PNG равен 0x89, и сам по себе это некорректный UTF-8. Прочитайте такой файл как текст, и каждый байт, который декодер не может понять, станет U+FFFD, так что файл испорчен ещё до того, как его увидит ваша программа, и никто не сообщает об ошибке. То же самое происходит с ключом: секрет HMAC это произвольные октеты, и если провести его через строку, он изменится, так что вы вычислите другой MAC, чем требует спецификация, а все тесты, написанные против вашего же кода, пройдут.

Два независимо написанных приложения, одно читает PNG, другое аутентификатор, упёрлись в одну и ту же проблему на одной неделе. Ни одно не могло обойти её средствами языка.

Посмотрите сами

Аутентификатор по RFC 6238, которому нужны байты с обеих сторон HMAC. Секрет приходит в base32, сообщение это восьмибайтовый счётчик, почти целиком из нулей, а дайджест индексируется собственным последним байтом:

Одноразовый пароль от начала до конца 
module totp

import std/bytes
import std/crypto
import std/math
import std/array
import std/option { Some, None }
import std/result { Result, Ok }

fn at(b: bytes.Bytes, i: int) -> int {
  return match bytes.get(b, i) {
    Some(v) => v,
    None => 0,
  }
}

pub fn code(secret: string, counter: number) -> Result<number, bytes.BytesError> {
  let key = bytes.from_base32(secret)?
  let message = bytes.from_array(array.map(array.range(8), fn(i: int) -> int {
    return math.floor(counter / math.pow(256, 7 - i)) % 256
  }))?

  let mac = crypto.hmac_sha1_bytes(key, message)
  let offset = at(mac, bytes.len(mac) - 1) % 16
  return Ok((((at(mac, offset) % 128) * 16777216)
    + (at(mac, offset + 1) * 65536)
    + (at(mac, offset + 2) * 256)
    + at(mac, offset + 3)) % 100000000)
}

Во время выполнения Bytes это Uint8Array, поэтому его можно передать любому API хоста, который такой принимает, без распаковки. Операции над последовательностью названы так же, как их аналоги в std/array и std/string: len, get, slice, concat, index_of, starts_with. Ничто не изменяет свой аргумент.

Любое декодирование может отказать и говорит где

Эту часть было дороже всего сделать, и именно ради неё стоит этим пользоваться. Buffer в Node принимает некорректный ввод и сообщает об успехе:

Что платформа делает молча 
Buffer.from("zz", "hex")        // an empty buffer, no error
Buffer.from("a-b_", "base64")   // skips - and _, decodes the rest, no error
buf.toString("utf8")            // U+FFFD for anything malformed, no error
Что делает Glyph 
match bytes.from_hex(input) {
  Ok(b) => use(b),
  Err(e) => io.eprintln("${e.message} at ${number.to_string(e.index)}"),
}

// "z" is not a hex digit at 0
// a trailing base64 group cannot be 1 character(s) long at 3
// not valid UTF-8 at 2

Каждый кодек написан самостоятельно, а не делегирует работу Buffer, поэтому hex, base64, base64url и base32 отклоняют символ вне своего алфавита, последнюю группу, слишком короткую, чтобы закодировать целый байт, и последний символ, несущий биты за концом данных. to_text ищет первый байт, который не может быть частью корректной последовательности UTF-8, так что вы получаете позицию, а не просто вердикт. from_array отклоняет всё вне 0..255 по той же причине: тихое & 0xff превращает 256 в 0, а опечатку в данные.

Самостоятельная реализация кодеков дала то, ради чего её не делали. Модуль вообще не обращается к API хоста, только к Uint8Array, TextEncoder и TextDecoder, так что бандл, который использует только std/bytes, работает и в Web Worker.

От выбора HMAC зависит ответ

В std/crypto теперь есть обе формы каждого алгоритма. Обычное имя принимает строку и возвращает hex, что и нужно для хеширования пароля. Форма _bytes принимает и возвращает Bytes, что нужно сетевому протоколу. Если ключ получен из bytes.from_base64 или crypto.random_bytes, в нём есть байты, которые строка не может хранить, и текстовая форма молча вычислит что-то другое.

Для сверки значения, присланного атакующим, с секретом используйте crypto.timing_safe_equal, а не bytes.equals. equals возвращается, как только находит несовпадение, поэтому время его работы выдаёт, сколько начальных байтов были верными.

Текущее состояние

Уже работает

std/bytes с 21 функцией: операции над последовательностью, мост к UTF-8 и кодеки hex, base64, base64url и base32, которые возвращают Result с позицией ошибки. fs.read_bytes, write_bytes и append_bytes читают и пишут файл без декодирования. В std/crypto есть форма _bytes для каждого дайджеста и HMAC, а также SHA-1 для протоколов, которые его требуют, random_bytes и timing_safe_equal. Кодеки закреплены тестовыми векторами RFC 4648, а HMAC векторами RFC 6238 в собственном наборе тестов компилятора.

Становится точнее

Кодека для целых чисел пока нет, так что чтение big-endian u32 из заголовка это арифметика, которую вы пишете сами: за пределами 32 бит сдвиг всё равно неподходящий инструмент, поэтому используется деление. Шестнадцатеричные литералы пока не разбираются, из-за чего таблицу CRC32 на 256 элементов, записанную в десятичном виде, трудно читать. std/websocket всё ещё декодирует бинарный фрейм как текст UTF-8; нужный для этого тип теперь есть, и фреймы следующие на очереди. А шесть старых функций std/encoding вида «строка в строку» по-прежнему молчат при некорректном вводе, так что для всего, что должно быть правильным, используйте кодеки std/bytes. Кодеки написаны на TypeScript, а не делегируют работу Buffer из node, и именно поэтому работают в Web Worker; на мегабайте данных они медленнее платформенных, от 1x до 35x. Кодирование ключа или токена в любом случае обходится в неизмеримо малое время; если вы перегоняете десятки мегабайт, таблица есть в руководстве по производительности.
