12 · Из вашей спецификации

Можно ли сгенерировать типизированный клиент и сервер из спецификации API?

Да. Направьте glyph gen openapi на спецификацию OpenAPI: --client генерирует типизированный HTTP-клиент, по одной функции на операцию; --handlers генерирует серверные заготовки и работающий диспетчер route. Если источник истины у вас это схема zod, то же самое делает glyph gen zod. Всё получается в виде закоммиченного Glyph, который можно искать grep, который принадлежит вам и который вы правите, а не скрытого шага кодогенерации.

Почему это важно

Рукописные API-клиенты и их DTO расходятся со спецификацией, и такое расхождение это класс багов, который никто не любит. Поскольку Glyph генерирует настоящий код (типизированные функции, настоящие объявления type с дескрипторами для проверки во время выполнения), спецификация остаётся источником истины, а повторная генерация даёт идемпотентный дифф, который можно ревьюить, а не чёрный ящик.

Посмотрите сами: клиент

Каждая операция становится async fn с типизированными параметрами пути и типизированным телом запроса и возвращает HTTP Response:

$ glyph gen openapi tasks.yaml --out src/ --client 
async fn createTask(
  base: string,
  body: NewTask,
) -> Result<Response, HttpError> {
  return await post(
    "${base}/tasks",
    body,
  )
}

async fn getTask(base: string, id: number)
  -> Result<Response, HttpError> {
  return await get("${base}/tasks/${id}")
}
$ glyph gen openapi tasks.yaml --out src/ --handlers 
fn route(req: Request)
  -> Result<Response, string> {
  return match req.method {
    "GET" => match segments(req) {
      ["tasks"] => listTasks(req),
      // id captured from the path:
      ["tasks", id] => getTask(req, id),
      else => Ok(json(404, {
        error: "not found",
      })),
    },
    else => Ok(json(405, {
      error: "method not allowed",
    })),
  }
}

Роутер из --handlers сопоставляет путь с паттернами массивов, так что /tasks/{id} становится ["tasks", id] и параметр связывается за вас. Каждая заготовка начинается как 501 с комментарием, показывающим разбор тела; вы их заполняете и подключаете через await serve(PORT, route).

Или из схемы zod

Если ваша команда уже описывает структуры через zod, генерируйте прямо из них. Схема становится полноценным типом Glyph с собственным дескриптором:

schemas.ts 
export const Task = z.object({
  id: z.number(),
  title: z.string(),
  done: z.boolean(),
})
$ glyph gen zod schemas.ts --out src/ 
type Task = {
  id: number,
  title: string,
  done: bool,
}
// + a runtime descriptor, so
// Task.parse(value) validates.

Полиморфное размеченное объединение (discriminator в OpenAPI) превращается в настоящее размеченное объединение Glyph и сгенерированную функцию parse_<Name>, которая читает свойство-дискриминатор и проверяет значение как нужный вариант. Поскольку Glyph помечает варианты по имени конструктора, а не по произвольному свойству, сгенерированный диспетчер связывает объект из сети с union за вас.

Где он не дотягивает: генерация следует формату данных в сети, поэтому покрывает частые 80%: объекты, примитивы, массивы, ссылки, необязательные и nullable-поля и размеченные объединения. То, что нельзя представить точно (строковый enum, неразмеченный union), сужается с выведенным примечанием, а не превращается в валидатор, который отклонял бы настоящие данные. Следующими будут более богатые enum. И у инструментов есть реальные зависимости: gen dts/gen zod нужны Node и typescript/zod. gen dts работает с любым TypeScript (5, 6 или нативным портом 7.x), который сначала ищется в вашем проекте, и если чего-то не хватает, они точно говорят, что установить.

Синхронизация

Каждый сгенерированный файл записывает в заголовок точную команду, которая его создала. Когда спецификация меняется, не нужно выяснять, какие команды перезапускать: glyph regen находит эти заголовки, перезапускает каждую команду и перезаписывает результат. Это идемпотентно, так что regen без изменений в спецификации ничего не трогает; его легко встроить в pre-commit хук или в проверку в CI, которая падает, если закоммиченный код разошёлся со спецификацией.

Текущее состояние

Уже работает

glyph gen openapi (типы, --client, --handlers с настоящим роутером), glyph gen dts, glyph gen zod и glyph regen, чтобы обновить всё из исходников: каждая команда выдаёт закоммиченный Glyph с дескрипторами, который идемпотентно перегенерируется.

Два типа, которые получили бы одно и то же имя в Glyph, останавливают генератор, а не порождают файл, который не скомпилируется: он называет каждый конфликтующий источник, ничего не пишет, а --rename Source=GlyphName разрешает конфликт. Этот выбор записывается в сгенерированный заголовок, так что glyph regen его повторяет.

В работе

Более богатое отображение enum и более широкое покрытие OpenAPI, всё по тому же правилу: следовать формату данных и выводить примечание при сужении. Генерация из собственного .d.ts пакета читает его объявления interface и type, поэтому библиотека, API которой состоит из классов или поля которой используют вычисляемые типы вроде Omit, оставляет ссылки, которые генератор называет в примечании, а glyph build сообщает как неразрешённые. Импорт такого класса и создание его через new генерации не требуют и проверяются tsc, так что этот путь не затронут.
