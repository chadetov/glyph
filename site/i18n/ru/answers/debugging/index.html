28 · Эксплуатация

Когда в три часа ночи всё ломается в продакшене, что видит дежурный?

Читаемый TypeScript, который принадлежит вам, и рядом с каждым сгенерированным файлом source map обратно в ваш .glyph. Отладчик, бандлер или трекер ошибок прослеживает работающий код до вашего исходника, а сгенерированный TS может прочитать даже тот, кто никогда не видел Glyph. А ещё раньше glyph build и glyph run сообщают одни и те же диагностики на одном и том же дереве, так что быстрый цикл не может скрыть то, что поймала бы сборка. Два ограничения, оба на пути glyph run, описаны ниже.

1 · Сгенерированный TypeScript можно читать, он ваш

Glyph не поставляет непрозрачный рантайм. Он генерирует обычный отформатированный TypeScript, который вы коммитите и деплоите как любой другой TS. Поэтому даже в худшем случае (дежурный инженер, который не знает Glyph, в три часа ночи) он читает обычный TypeScript, а не диалект. Между вашим исходником и продакшеном нет чёрного ящика.

2 · Source maps обратно в .glyph

Рядом с каждым сгенерированным .ts лежит стандартный source map версии 3 (.ts.map) с комментарием sourceMappingURL и встроенным исходником на Glyph (sourcesContent). Всё, что понимает source maps (Chrome DevTools, отладчик Node, трекер ошибок вроде Sentry, ваш бандлер), может пройти по цепочке и показать строку .glyph, а не сгенерированную.

dist/main.ts (конец) 
// ...emitted TypeScript...
//# sourceMappingURL=main.ts.map    // v3 map, .glyph embedded

3 · Ошибки сборки и типов уже указывают на Glyph

До продакшена с ошибкой типов вы доберётесь редко, потому что glyph build запускает tsc --strict и отображает каждую ошибку tsc обратно на ваш исходник .glyph (та же каретка, код ошибки TypeScript сохраняется). Каретка ставится под наименьшее выражение Glyph, код которого отклонил tsc: неверный аргумент подчёркивает этот аргумент, опечатка в имени поля внутри обработчика событий JSX подчёркивает это обращение к члену, а не весь return вокруг него. А glyph build --json выдаёт каждую диагностику в виде структурированного JSON (код, серьёзность, файл, строка и столбец с отсчётом от 1, подсказка), с которым может работать ваш CI или инструменты.

4 · glyph run говорит вам то же самое

Команда, которую вы набираете весь день, это glyph run, и до 0.1.40 она была тише сборки. Она компилировала весь каталог, брала из отчёта список сгенерированных файлов и выбрасывала диагностики. Дерево, о котором glyph build сообщал проблемы, запускалось чисто и завершалось с кодом 0. Теперь она сообщает тот же набор: с предупреждениями, по названному вами файлу и по соседним, после вывода программы, со строкой-итогом. Кэш запусков хранит их, так что повторный запуск неизменённых исходников говорит то же, что первый, а не молчит, а запись кэша без диагностик считается промахом и пересобирается.

Два текущих ограничения

Стек падения самого glyph run всё ещё показывает номера строк .ts. glyph run выполняет код через tsx, а tsx не проводит source map через собственное преобразование .ts→.js, поэтому непойманное исключение во время glyph run показывает сгенерированную строку. Переотображение этого стека запланировано отдельно. Это важно для локального цикла run; в настоящем деплое вы делаете glyph build в .ts, собираете его своим обычным тулчейном, и .ts.map работает по цепочке как обычно, так что продакшен-стек, по которому вас будят, отображается обратно в .glyph.

Ошибка в соседнем модуле не меняет код выхода glyph run. Модуль, который не скомпилировался, нельзя импортировать, а программа, которая его не импортировала, всё равно запускается. Ошибку вы теперь видите, но процесс по-прежнему завершается с тем, что вернул main. Ненулевой код выхода сломал бы деревья, которые сегодня нормально работают, поэтому это открытое решение, а не недосмотр. Если вы хотите, чтобы код выхода зависел от состояния всего дерева, используйте glyph build.

Текущее состояние

Уже работает

Читаемый закоммиченный TS, .ts.map версии 3 на каждый файл, ошибки tsc, отображённые на .glyph, и диагностики в --json. glyph run сообщает то же, что glyph build, в том числе с тёплым кэшем. Цепочка source maps вашего тулчейна для деплоя доходит до .glyph.

В работе

Переотображение стека падения самого glyph run (чтобы локальный цикл тоже показывал кадры .glyph), решение о том, должна ли ошибка соседнего модуля давать ненулевой код выхода glyph run, и более богатая отладка в редакторе через LSP.
