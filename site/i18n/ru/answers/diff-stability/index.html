02 · Изменения, которые можно проверить

Останутся ли правки агента чистыми, или он переформатирует весь файл?

Изменение в одну строку всегда даёт дифф в одну строку. В Glyph одна каноническая раскладка, поэтому агент не может похоронить настоящее изменение под стеной переформатирования.

Почему это важно

Когда агент открывает pull request, дифф и есть ревью. Если настоящее исправление в одну строку приходит как переформатирование на 200 строк, никто не видит, что на самом деле изменилось, и именно в этом шуме проскакивает баг. Стабильность диффов значит, что дифф показывает изменение и ничего, кроме изменения.

Основную работу делают два правила. Вот каждое из них в виде диффа, который вы бы проверяли.

Пример 1: завершающие запятые, один элемент на строку

Добавим маршрут. В распространённом стиле TypeScript прежняя последняя строка меняется только ради того, чтобы получить запятую. Для изменения в один элемент двигаются две строки:

TypeScript: добавить "/billing" 
 const routes = [
   "/home",
-  "/about"
+  "/about",
+  "/billing"
 ]
3 строки затронуты ради 1 изменения
Glyph: добавить "/billing" 
 let routes = [
   "/home",
   "/about",
+  "/billing",
 ]
добавлена 1 строка, ровно изменение

Завершающие запятые обязательны, а список, который не помещается в одну строку, раскладывается по одному элементу на строку, а не переупаковывается, поэтому вставка, удаление или перестановка элемента никогда не задевают соседей. То же верно для полей записей, параметров, веток match и импортов. У порога есть цена: переименование, из-за которого вызов вылезает за 100 столбцов, разворачивает весь список аргументов по одному на строку.

Пример 2: одна каноническая раскладка

Правильное форматирование ровно одно, и его выдаёт glyph fmt. Пробелы, переносы и выравнивание это не выбор, который агент может «подчистить», поэтому смысловая правка не может потащить за собой переразбивку строк. Поменяйте тип одного поля, и это весь дифф:

user.glyph: меняете одно поле, проверяете одну строку 
 type User = {
   id: string,
-  age: string,
+  age: number,
   email: string,
 }

Поскольку раскладка фиксирована, два разных агента, правящих один файл, дают побайтно одинаковое форматирование: никакой переразбивки, никакого шума «мой форматтер против твоего» и чистый git blame, который указывает на коммит, действительно изменивший строку, а не на тот, что её переформатировал.

Раскладка одна, но не двигает ли форматтер мои комментарии?

Раньше двигал, и это был баг, который стоит назвать. В Glyph нет блочных комментариев и синтаксиса doc-комментариев, поэтому строка // это единственный способ пояснить поле записи, вариант union или ветку match. Форматтер выводил накопленные комментарии только на границах объявлений и операторов, а значит, комментарий, написанный внутри конструкции, сползал вниз к следующему объявлению и читался как документация к тому, на что попал. Выяснилось это, когда на Glyph писали «Сапёра». Эти два объявления взяты из настоящего приложения (комментарии сокращены) и пропущены через старый форматтер и через новый.

0.1.37: один проход fmt 
type Visibility =
  | Hidden
  | Flagged
  | Revealed

// Face down. Prints as `.`.
// Face down and marked by the player.
// Face up. `Cell.adjacent` is what gets printed.
type Cell = { mine: bool, adjacent: int, visibility: Visibility }
// Number of mined neighbours. Only meaningful
// once mines are placed.
три комментария к вариантам теперь документируют запись
0.1.38: тот же файл 
type Visibility =
  // Face down. Prints as `.`.
  | Hidden
  // Face down and marked by the player.
  | Flagged
  // Face up. `Cell.adjacent` is what gets printed.
  | Revealed

type Cell = {
  mine: bool,
  // Number of mined neighbours. Only meaningful
  // once mines are placed.
  adjacent: int,
  visibility: Visibility,
}
каждый комментарий над тем, что он описывает

Теперь правило такое: комментарий выводится над тем элементом, над которым был написан, внутри тела записи, списка вариантов union, литерала массива или объекта, списка аргументов или параметров и match. А конструкция с комментарием внутри всегда принимает форму «один элемент на строку» при любом размере, чтобы комментарию было над чем стоять. Так что type Shape = { w: int, h: int } по-прежнему сворачивается в одну строку, но как только вы документируете h, запись остаётся развёрнутой.

Почему это считается ошибкой корректности, а не косметикой: ничего не падало. Сборка завершалась с кодом 0, tsc проходил, а испорченный вывод сам был неподвижной точкой, так что glyph fmt --check в CI был зелёным на файле, комментарии которого теперь утверждали неправду. Это тот же класс сбоев, ради устранения которого существует Glyph, только в форматтере, а не в системе типов.

Может ли glyph fmt сломать программу, которая собирается?

Мог, и один случай всё ещё открыт. Сначала исправленный. Ветка, означающая «пустая запись», пишется как true => ({}). Позиция тела ветки это единственное место в грамматике, где открывающая { неоднозначна, и парсер решает это, требуя сразу после скобки key: или .... У пустого объекта нет ни того, ни другого, поэтому когда форматтер убирал скобки и печатал true => {}, ветка возвращалась пустым блоком, и файл переставал собираться: E0223, ветка не даёт значения. Вы запускали форматтер на рабочем коде и получали код, который больше не компилируется.

Теперь принтер берёт в скобки тело ветки, чей самый левый токен это {, который при повторном разборе стал бы блоком, то есть пустой объект и всё, что на нём построено (({}).size возвращается как ({}.size)). Тело ветки, которое и так читается однозначно, вроде false => { a: "x" }, остаётся без скобок, так что больше нигде новой пунктуации не появляется. fmt на результате даёт неподвижную точку, а сгенерированный TypeScript не меняется. Форматтер, который вашей программе приходится переживать, хуже отсутствующей возможности, потому что он портит код, который уже работал.

Ещё два случая исправлены в 0.1.138. Внутри блока строка, начинающаяся с (, продолжает строку выше, а до 0.1.137 форматтер печатал load()? с последующим .run() как (load()?).run(), так что после let a = 1 отформатированный файл означал let a = 1(…).run(). Теперь он оставляет load()?, а .run() с отступом на следующей строке, и пишет e?(x), e?[0] и e? ? без скобок. Второй случай касался уточнения where у union: форматтер его выбрасывал, и программа, которую check отклонял, превращалась в принимаемую. Теперь фаззер разбирает отформатированный файл и сравнивает дерево с исходным, так что раскладка, меняющая смысл файла, падает на первом же проходе, а не ждёт, пока кто-то заметит.

Правила форматирования, на которых это держится, и компромисс, на который они идут, описаны на странице принципа стабильности диффов.

Текущее состояние

Уже работает

Обязательные завершающие запятые, списки по одному элементу на строку и единственная каноническая раскладка glyph fmt, без потерь при круговом преобразовании и идемпотентная, с форматированием при сохранении в редакторе. glyph fmt никогда не переносит комментарий туда, где ему не место. Комментарии остаются над тем элементом, над которым были написаны, в том числе внутри записи, литерала, списка аргументов, match, между операндами оператора и между шагами цепочки методов, которая тогда раскладывается по одному шагу на строку с точкой в начале.

Ограничения и что дальше

Комментарий всегда выводится на отдельной строке, поэтому написанный в конце строки кода (w: int, // width in cells) переезжает на строку над следующим элементом. Границу объявления он больше не пересекает, но всё-таки двигается; чтобы оставить его в конце строки, принтер должен отслеживать, какую строку делит комментарий. Комментарий там, где раскладке некуда его поставить, например внутри индекса, после аргументов вызова посреди цепочки или перед операндом ! или await, больше не переносится: glyph fmt отказывается форматировать файл, оставляет его как был и называет строку и место, куда поставить комментарий, а glyph check сообщает то же самое как предупреждение E0500. Комментарий между атрибутами JSX или между полями паттерна объекта тоже отклоняется, хотя раскладка по одному на строку могла бы его разместить; эти раскладки в списке задач. Кроме того, у принтера пока нет правила для разбивки длинной цепочки методов или +, поэтому слишком длинная цепочка вместо этого разбивает самый внутренний список аргументов, а это неправильное место. Ещё мы строим бенчмарк размера диффов на тех же правках в TypeScript, чтобы этот принцип стал числом, которое можно проверить.
