16 · Деньги и безопасность

Можно ли доверить ему деньги и ввод, который я не контролирую?

Да. Деньги считаются точно, инвариант вроде неотрицательности это тип, который проверяется на границе, а недоверенный ввод не может попасть в SQL или shell без очистки. Ошибка в любом из этих мест это ошибка компиляции или разбора, а не соглашение, о котором кто-то должен помнить через три функции.

Деньги это не float

Финансовая система на IEEE-754 number это баг, который ждёт своего отчёта: 0.1 + 0.2 не равно 0.3, а значения больше 253 молча теряют точность. std/decimal это точная десятичная арифметика с фиксированной точкой поверх BigInt. Сложение, вычитание и умножение точные; деление принимает явный масштаб и округляет половину от нуля; некорректная сумма разбирается в Err, а не в молчаливый NaN.

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()      # "11.34", exact

decimal("2")?.div(decimal("3")?, 2)   # "0.67", half away from zero
ошибка, которую это убирает 
// JS number, the default everywhere:
0.1 + 0.2            // 0.30000000000000004
1_000_000_000_000.10 * 1.07   // rounding drift
9007199254740993     // === 9007199254740992

// None of these are your money anymore.

Идентификаторы и счётчики остаются точными после 253

Идентификатор счёта или счётчик в реестре, который выходит за диапазон float и округляется, это катастрофа другого рода. bigint это точное целое произвольной точности с литералами вида 123n, а поле записи типа bigint проверяет typeof === "bigint" на границе, поэтому идентификатор, пришедший как JSON number, отклоняется, а не тихо обрезается.

Инвариант это тип, а не комментарий

«Сумма неотрицательна» и «оценка от 1 до 5» это проверки, которые пишут один раз и потом забывают. Уточнение where переносит инвариант в тип, и дескриптор обеспечивает его на границе. Значение, не прошедшее предикат, вообще не становится Amount.

refinements.glyph 
type Amount = int where value >= 0
type Rating = int where value >= 1 && value <= 5

Amount.parse(-1)   # Err  (not just "is a number")
Rating.parse(6)    # Err
Amount.parse(3.5)  # Err  (int check too)

Инъекция это ошибка компиляции

Классический путь к удалённому выполнению кода это недоверенный ввод, который попадает в SQL-запрос, shell-команду или HTML-шаблон. std/taint делает это ошибкой типов. Значение извне имеет тип Tainted; приёмник, который вы хотите защитить, принимает Trusted. Эти типы структурно различны, поэтому перейти от одного к другому можно только через явный sanitize. Передайте приёмнику tainted-значение напрямую, и tsc откажется это компилировать.

безопасный путь компилируется 
fn run_query(sql: Trusted<string>) -> void { ... }

let input: Tainted<string> = taint(req.body)
run_query(sanitize(input, escape))   # ok
путь для инъекции нет 
module query

import std/taint { Tainted, Trusted, taint, expose }

fn run_query(sql: Trusted<string>) -> string {
  return expose(sql)
}

pub fn handle(body: string) -> string {
  let input: Tainted<string> = taint(body)
  return run_query(input)
}

// [TS2345] Argument of type 'Tainted<string>'
//   is not assignable to parameter of type
//   'Trusted<string>'. (query.glyph:11)

Текущее состояние

Уже работает

std/decimal для точных денег, bigint для точных больших целых, уточнения where, чтобы инвариант проверялся на границе, и std/taint, чтобы недоверенный ввод не мог попасть в защищённый приёмник без явного sanitize. Всё это проверяется: некорректная сумма или идентификатор не проходят parse, нарушенный инвариант не проходит parse, а неочищенное значение не проходит tsc.

Где это заканчивается

Уточнение where сегодня работает для примитивных базовых типов; инварианты записей и связи между полями (where value.paid <= value.total) это запланированное расширение. Taint это дисциплина, которую вы включаете сами, объявляя тип приёмника Trusted, а не автоматический анализ потоков: компилятор обеспечивает объявленную вами границу и не выводит taint по всей программе за вас.
