16 · Деньги и безопасность

Можно ли доверить ему деньги и ввод, который я не контролирую?

Да. Деньги считаются точно, инвариант вроде неотрицательности это тип, который проверяется на границе, а недоверенный ввод не может попасть в SQL или shell без очистки. Ошибка в любом из этих мест это ошибка компиляции или разбора, а не соглашение, о котором кто-то должен помнить через три функции.

Деньги это не float

std/decimal это точная десятичная арифметика с фиксированной точкой поверх BigInt.

  • Точная арифметикаСложение, вычитание и умножение точные.
  • ДелениеДеление принимает явный масштаб и округляет половину от нуля.
  • Некорректный вводНекорректная сумма разбирается в Err, а не в молчаливый NaN.

Идентификаторы и счётчики остаются точными после 253

Идентификатор счёта или счётчик в реестре, который выходит за диапазон float и округляется, это катастрофа другого рода.

bigint это точное целое произвольной точности с литералами вида 123n, а поле записи типа bigint проверяет typeof === "bigint" на границе, поэтому идентификатор, пришедший как JSON number, отклоняется, а не тихо обрезается.

Инвариант это тип, а не комментарий

«Сумма неотрицательна» и «оценка от 1 до 5» это проверки, которые пишут один раз и потом забывают. Уточнение where переносит инвариант в тип, и дескриптор обеспечивает его на границе.

refinements.glyph 
type Amount = int where value >= 0
type Rating = int where value >= 1 && value <= 5

Amount.parse(-1)   # Err  (not just "is a number")
Rating.parse(6)    # Err
Amount.parse(3.5)  # Err  (int check too)

Значение, не прошедшее предикат, вообще не становится Amount.

Инъекция это ошибка компиляции

Классический путь к удалённому выполнению кода это недоверенный ввод, который попадает в SQL-запрос, shell-команду или HTML-шаблон. std/taint делает это ошибкой типов.

  • Два типаЗначение извне имеет тип Tainted; приёмник, который вы хотите защитить, принимает Trusted.
  • Один путь между нимиЭти типы структурно различны, поэтому перейти от одного к другому можно только через явный sanitize.
безопасный путь компилируется 
fn run_query(sql: Trusted<string>) -> void { ... }

let input: Tainted<string> = taint(req.body)
run_query(sanitize(input, escape))   # ok
путь для инъекции нет 
module query

import std/taint { Tainted, Trusted, taint, expose }

fn run_query(sql: Trusted<string>) -> string {
  return expose(sql)
}

pub fn handle(body: string) -> string {
  let input: Tainted<string> = taint(body)
  return run_query(input)
}

// [E0211] argument type mismatch: expected
//   `taint.Trusted<string>`, found
//   `taint.Tainted<string>` (query.glyph:11)

Передайте приёмнику tainted-значение напрямую, и tsc откажется это компилировать.

Текущее состояние

Уже работает

  • std/decimal для точных денег
  • bigint для точных больших целых
  • Уточнения where, чтобы инвариант проверялся на границе
  • std/taint, чтобы недоверенный ввод не мог попасть в защищённый приёмник без явного sanitize
  • Всё это проверяется: некорректная сумма или идентификатор не проходят parse, нарушенный инвариант не проходит parse, а неочищенное значение не проходит tsc.

Где это заканчивается

  • Уточнение where сегодня работает для примитивных базовых типов; инварианты записей и связи между полями (where value.paid <= value.total) это запланированное расширение.
  • Taint это дисциплина, которую вы включаете сами, объявляя тип приёмника Trusted, а не автоматический анализ потоков
    Подробнее

    Taint это дисциплина, которую вы включаете сами, объявляя тип приёмника Trusted, а не автоматический анализ потоков: компилятор обеспечивает объявленную вами границу и не выводит taint по всей программе за вас.
