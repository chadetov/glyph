21 · До правки

Может ли компилятор сказать, что сломает изменение, до того как я его сделаю?

Для шести видов правок да. glyph_impact принимает объявление, которое вы собираетесь изменить, и само изменение (переименовать, удалить вариант, сменить тип параметра, сменить арность, удалить объявление) и отвечает одним вердиктом на каждое место из закрытого списка, у каждого есть причина, почему вердикт именно такой, а не другой.

Почему это важно

Когда вы переименовываете функцию, расширяете union или меняете то, что принимает параметр, вы либо ищете старое имя через grep и надеетесь, что нашли все вызовы, либо делаете правку и читаете, что потом скажет компилятор. Ни один из способов не говорит, какие места продолжат компилироваться, но тихо станут неправильными: match с веткой catch-all не падает, когда вы добавляете вариант, он просто начинает отправлять новый случай туда, куда никто не решал его отправлять. Такое место никогда не проявится при сборке. glyph_impact отвечает до правки, на основе того же анализа, который выполняет компилятор.

Что приходит в ответ

Запрос называет сущность по её идентичности module::name и изменение из закрытого списка: add_variant, remove_variant, rename, change_arity, change_signature_type, remove. Изменение обязательно, потому что вердикт это факт о правке; без названной правки каждое место вернулось бы просто ссылкой, а не последствием. Ответ называет сущность, изменение и список impact: одна запись на место, в каждой объявление, внутри которого оно находится, relation, verdict, because и код диагностики, который выдаст компилятор, если он ровно один. Вердикты образуют закрытый список, и каждый значит одно: WILL_FAIL (компилятор может доказать, что место перестанет компилироваться), ABSORBS (может доказать, что изменение будет здесь молча поглощено), SAFE (может доказать, что место останется корректным), UNDETERMINED (он посмотрел на это место и не может установить последствие) и NOT_INDEXED (для места такой формы вопрос вообще нельзя задать).

Посмотрите сами

Модуль объявляет label(s: string) -> number. До неё доходят три вызывающих места: одно передаёт строковый литерал, другое передаёт значение, тип которого это псевдоним для string, импортированный из другого модуля, а третье читает label как значение и никогда его не вызывает. Если спросить, что change_signature_type сделает с каждым из них, получится три разных вердикта, потому что это три разных утверждения:

запрос 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_impact",
    "arguments": {
      "entity": "lib::label",
      "change": { "kind": "change_signature_type" }
    }
  }
}
результат, сокращённый до трёх мест 
{
  "entity": "lib::label",
  "impact": [
    {
      "entity": "literal::probe",
      "verdict": "WILL_FAIL",
      "diagnostic": "E0211",
      "because": "every argument at this site is paired with
        a parameter the relation reads in full, so a
        replacement parameter type any of those pairings does
        not accept is E0211 here. The pairings: argument 1
        (`\"x\"`, `\"x\"`) against parameter `s: string`: ..."
    },
    {
      "entity": "imported::probe",
      "verdict": "UNDETERMINED",
      "diagnostic": null,
      "because": "argument 1 (`c`, `Cell`) against parameter
        `s: string`: `Cell` is declared in another module as
        an alias for a primitive, and the checker compares an
        imported declaration only when the declaration at the
        end of its chain of names is a tagged union or a
        record (G215, G226), so a replacement is compared
        against nothing here and only `tsc` on a full `glyph
        build` would see a mismatch"
    },
    {
      "entity": "reader::sizer",
      "verdict": "NOT_INDEXED",
      "diagnostic": null,
      "because": "this site reads the name rather than
        applying it, so no argument is paired with a
        parameter here, and Glyph does not compare a
        function value's parameter types against the type
        its use context expects"
    }
  ]
}

Одна правка, три места, три вердикта, и because у каждого это настоящая фраза, которую выдаёт компилятор, а не метка категории. Это повторяет собственный тест компилятора для этого изменения (a_signature_type_change_gets_one_verdict_per_kind_of_site в glyph-cli/tests/agent_loop.rs): тест затем делает правку и проверяет, что E0211 появляется ровно там, где предсказал WILL_FAIL, а в двух других местах компилятор молчит.

На реальном приложении

В examples/apps/csvql, движке запросов к CSV из одиннадцати файлов в этом репозитории, есть одно размеченное объединение Value, сейчас с четырьмя вариантами. Если спросить glyph_impact, что сделает добавление пятого (Blob), он находит 10 мест match в 4 файлах: в 8 компиляция упадёт, а в 2 есть ветка catch-all, которая молча поглотит новый вариант. Если действительно добавить вариант, компилятор сообщает ровно 8 ошибок E0200 ровно в 8 предсказанных местах и ничего не говорит о 2 местах ABSORBS ни до, ни после. Текстовый поиск веток catch-all по тому же приложению, то, что вы делали бы без инструмента, находит те же 2 настоящих места среди 20 совпадений (точность 0.10) и ничего не говорит о 8 падающих, потому что не знает, какой тип разбирает match.

Текущее состояние

Уже работает

Шесть видов изменений из закрытого списка (add_variant, remove_variant, rename, change_arity, change_signature_type, remove) и пять вердиктов из закрытого списка, одна запись на каждое затронутое место с причиной и кодом диагностики. change_signature_type решается для каждого аргумента вызова по собственным правилам сравнения проверки типов, и место получает самый слабый вердикт из своих аргументов. JSX-элемент оценивается как вызов, в который он понижается: <Card title="x" /> это одна запись props, переданная в Card, и каждый атрибут указывается напротив поля, с которым он сверяется, с тем вердиктом, который получил бы аргумент вызова того же типа. Покрытие (что поиск смог и не смог прочитать) указывается для каждого поиска, а не один раз на весь ответ, и каждый узел сообщает, пришёл ли он из исходника на Glyph, из лазейки extern_ts или из непрозрачного .d.ts.

Где это заканчивается

Глубина точна на одном шаге и пуста дальше: Glyph никогда не выводит тип объявления из его тела, поэтому тип вызываемой функции не может дойти до сигнатуры вызывающей, и изменение X может сделать некорректными только выражения, которые называют X. Если запросить глубину 2, ответ вернётся с next_query, где назван точный вопрос, потому что второму шагу нужно исправление, которое кто-то внесёт в первое место, а этого исправления ещё нет. UNDETERMINED и NOT_INDEXED это разные утверждения: аргумент, для которого у проверки типов нет типа, или сопоставление записи с полем, которое не читает ни одно правило, это UNDETERMINED (посмотрел и не смог решить); функция, прочитанная как значение, а не вызванная, это NOT_INDEXED (там вопрос вообще нельзя было задать). Следить стоит за ABSORBS: место продолжает компилироваться и при этом доказуемо неправильно, а зелёная сборка этого никогда не покажет.
