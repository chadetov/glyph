Можно ли использовать мой существующий TypeScript, JavaScript и библиотеки из npm?

Да. Glyph компилируется в обычный TypeScript и работает поверх npm: модуль .glyph импортирует из любого пакета и сам импортируется из ваших существующих .ts. Внедрять его можно по одному файлу.

Почему это важно

Никто не переписывает кодовую базу, чтобы попробовать язык. Поскольку результат работы Glyph и есть TypeScript, файл .glyph встаёт в уголок существующего проекта на TS/React/Node, импортирует те же пакеты и экспортирует обратно в окружающие его .ts.

Этот постепенный путь и есть причина целиться в TypeScript, а не выпускать новую среду выполнения.

Установленные пакеты приносят свои типы

Если пакет установлен и поставляется со своими типами (или для него есть @types/...), больше ничего делать не нужно. Ни заглушки, ни файла-адаптера.

glyph build находит node_modules вашего проекта и направляет на него проверку типов, так что настоящие типы пакета проверяют ваш код, а неправильный вызов становится настоящей ошибкой.

Вот zod, используемый напрямую, без единой рукописной строки:

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
вызов, которого нет в zod 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

glyph run выполняет ту же программу с установленным zod, так что это не только проверка типов: одна запись в конфигурации, которая разрешает пакет для проверки типов, разрешает его и для среды выполнения.

Пакету, у которого нет типов и нет @types/..., по-прежнему нужно объявление, которое пишете вы, и для этого есть папка .types/ (тот же механизм .d.ts, который уже использует TypeScript).

Подробнее импорты подпутей и типы с валидацией из .d.ts

Импорты подпутей (pkg/sub) тоже разрешаются через карту exports пакета, поэтому собственные типы подпути проверяются.

А если форма библиотеки нужна вам как полноценный тип Glyph с валидацией, а не как импорт только типов, glyph gen dts превращает .d.ts в настоящие типы с дескрипторами: см. нужно ли писать валидатор для каждого API вручную?

Типы из значений, spread в JSX и лазейка

Типы, выведенные из значений, поддерживаются полноценно. Spread пропсов в JSX (<input {...register()} />) тоже поддерживается полноценно.

Так что библиотека никогда не вынуждает писать файл-адаптер вручную.

Для редкой идиомы TypeScript, которую Glyph пока не может записать, есть extern_ts("..."), ограниченная лазейка, которую легко найти поиском: tsc её проверяет, но тут важно быть точным, это граница доверия, а не граница с проверкой во время выполнения (для Glyph она непрозрачна, значение возвращается как unknown, которое надо сузить).

Подробнее как разрешается z.infer<typeof s>

type User = z.infer<typeof user_schema> работает напрямую: typeof user_schema это запрос типа по ссылке на настоящее значение (опечатка даёт ошибку неразрешённого имени), а z.infer<...> это обычный обобщённый тип-член. Он генерируется дословно, а tsc его сводит, так что u.name имеет тип string; валидацию обеспечивает собственный parse схемы, как zod и так работает.

Когда нужен целый рукописный TypeScript

Иногда лазейка нужна не для типа или выражения, а для настоящего кода времени выполнения: цикла по потоку node, new Promise, рабочего потока. Положите .ts в <src>/extern/ и обращайтесь к нему через import extern/<name>. 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

Относительные импорты в исходниках Glyph по-прежнему запрещены (это правило удобства поиска), поэтому extern/* единственный зарезервированный путь, и grep -rn 'import extern/' находит каждое место, где вы вышли за пределы языка.

Подробнее копирование в сборку, обратное направление и прослойка для node

Сборка копирует <src>/extern/** в выходной каталог и генерирует относительный спецификатор, так что tsc проверяет extern вместе с вашим кодом на Glyph, а пересборка никогда его не удаляет.

Это обратная сторона простого направления, когда файл .ts импортирует ваш скомпилированный Glyph, для чего не нужно вообще ничего. Типичный extern (HTTP-сервер, fs) проходит проверку типов против встроенной прослойки для node, ничего не устанавливая.

Наблюдение за подпроцессом без установки чего-либо

Встроенные объявления node включают асинхронную половину child_process, а не только блокирующую, так что инструмент, который показывает вывод долгой команды во время её работы, пишется на Glyph, а не через extern: 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

io.print, а не io.println: фрагмент это кусок потока, а не строка, и одна строка может прийти в двух фрагментах.

Перегрузки следуют @types/node, так что каналы возвращаются ненулевыми при простом spawn(command, args) и допускающими null, как только вы передаёте stdio. Чтение child.stdout после stdio: "inherit" даёт TS18047 здесь и TS18047 с настоящими типами, а не две разные истории об одном и том же значении: 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

Отредактируйте прослойку, и следующий запуск использует отредактированную

Прослойка это файл, над которым вы работаете итеративно, поэтому он должен считаться исходником.

glyph run кэширует сборку под отпечатком ваших исходников, и этот отпечаток охватывает каждый .ts и .tsx в extern/, и по пути, и по содержимому.

Подробнее что вызывает пересборку

Отредактируйте один, переименуйте, добавьте или удалите, и следующий запуск пересоберёт проект и заново запустит tsc. Прослойка-симлинк разыменовывается, так что .ts, лежащий вне дерева исходников, хэшируется по тому, что он на самом деле содержит.

Именно это позволяет прослойке владеть типом, вместо того чтобы оба файла объявляли свою копию. Экспортируйте форму из прослойки, импортируйте её в модуле Glyph, и компилятор держит их согласованными при каждом запуске:

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
прослойка переименовала поле, и сборка об этом сообщает 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3
История до 0.1.44 и файлы, которые не учитываются

До 0.1.44 отпечаток полностью пропускал extern/, так что такое переименование давало чистую, прошедшую проверку типов сборку, которая запускала предыдущую копию прослойки. Файлы в extern/, не являющиеся .ts или .tsx, по-прежнему не влияют на кэш, и это намеренно: README.md рядом с прослойкой копируется в выходной каталог вместе с ней, но его никто не проверяет и не запускает, так что пересобирать нечего.

Клиенты на классах: базы данных и очереди сообщений

Большинство клиентов баз данных и систем сообщений построены на классах: вы пишете new Kafka(...), new MongoClient(url), new Redis(), new Pool(cfg). Именно для этого в Glyph есть new.

клиент на классе (kafkajs) 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
клиенту-фабрике new не нужен 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

Он генерирует дословный new на TypeScript, а tsc проверяет его против настоящего конструктора пакета, так что неправильный аргумент становится настоящей ошибкой, а неопределённый вызываемый объект ловится по имени.

Это остаётся только для взаимодействия: своего class в Glyph нет, а new создаёт только тип, который пришёл из пакета, из объявления в .types или из extern_ts.

Текущее состояние

Уже работает

  • Импорт любого пакета из npm (включая имена с дефисом и со scope).
  • Установленный пакет, который поставляется со своими типами (или имеет @types/...), проходит проверку типов и запускается без заглушки.
  • Клиенты на классах создаются через new, который tsc проверяет против настоящего конструктора; клиенты-фабрики импортируются и вызываются напрямую.
  • Встроенные модули node проходят проверку типов сразу
    Подробнее

    Встроенные модули node (fs, path, http, child_process, включая потоковый spawn, и остальные) проходят проверку типов сразу, причём @types/node подгружается автоматически, если вы его установите, а CI собирает собственную среду выполнения компилятора против этого пакета в версии latest, так что объявление, от которого зависит стандартная библиотека, не может разойтись с настоящим объявлением node.

  • Объявления, до которых доходит только ваш код, эта проверка пока не покрывает, и некоторые из них всё ещё шире, чем в node.
  • Окружающие объявления в .types/ для всего остального.
  • glyph gen dts, чтобы превратить .d.ts в типы Glyph с валидацией.
  • Чистый вывод в .ts, который ваш существующий TypeScript импортирует обратно.
  • import extern/<name> обращается к рукописному TypeScript в <src>/extern/
    Подробнее

    Когда нужен целый рукописный TypeScript, import extern/<name> обращается к .ts в <src>/extern/, который копируется в сборку и проверяется вместе с вашим кодом, а кэш glyph run его отслеживает, так что правка вызывает пересборку.

В работе

  • Материализация справляется с формами, которые реально встречаются в SDK, а типы, выведенные из значений, поддерживаются полноценно
    Подробнее

    Материализация теперь справляется с формами, которые реально встречаются в SDK (пространства имён, реэкспорты между файлами, через псевдонимы и пространства имён, exports подпутей и полноценные обобщённые типы), а типы, выведенные из значений (z.infer<typeof s>), поддерживаются полноценно.

  • Главный оставшийся пробел: результаты нематериализованного пакета проверяются по типам против его .d.ts, но не валидируются во время выполнения, пока вы их не материализуете.
  • Со стороны extern/ корень исходников у glyph run и glyph build разный
    Подробнее

    Со стороны extern/ корень исходников у двух команд разный: glyph run app.glyph берёт за корень каталог самого файла, а glyph build src/ каталог, который вы указали. Поэтому программа в подкаталоге ищет свою прослойку в двух разных местах, и пока мы не выберем один корень, в проекте с такой структурой прослойка должна быть доступна из обоих. Если это не так, сборка падает с явной ошибкой.
