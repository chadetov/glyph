Это настоящий язык или игрушка с дырами?

В нём есть то, что нужно в настоящей кодовой базе: видимость модулей, интерфейсы для ограничения дженериков, defer для очистки ресурсов и хелперы для конкурентности. Там, где он опирается на JavaScript, он так и говорит, а не делает вид, что это не так.

Почему это важно

На языке, в котором можно написать один файл, но нельзя выстроить структуру проекта, кодовую базу не построишь. Важные пробелы вполне обыденные:

  • ВидимостьМожно ли спрятать хелпер?
  • Ограничения дженериковМожет ли дженерик требовать возможность?
  • ОчисткаМожно ли освободить файловый дескриптор на каждом пути выхода?
  • КонкурентностьМожно ли запустить две вещи одновременно и дождаться обеих?

Glyph отвечает на все четыре вопроса и не возвращается при этом к перегруженному аннотациями направлению, от которого сознательно отказался.

Интерфейсы ограничивают дженерики

interface структурный, как в TypeScript: это набор сигнатур членов, которые может требовать дженерик. Никакого implements и номинальных церемоний. Подходит любое значение с этими членами, а следит за этим tsc.

интерфейсы ограничивают дженерики 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer и структурированная конкурентность

defer выполняет очистку при выходе из блока на любом пути, включая ранний return и выброшенную ошибку. А std/task объединяет конкурентную работу с одним временем жизни, вместо того чтобы оставлять висящие промисы.

defer + структурированная конкурентность 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])
Подробнее порядок выполнения и дескрипторы owned

Несколько defer выполняются в обратном порядке (последний первым), и всё это сочетается с дескрипторами owned.

Что унаследовано от JavaScript

Glyph компилируется в TypeScript и работает на движке JavaScript, поэтому наследует порядок вычислений, ссылочную семантику при изменении данных и однопоточную модель со сборкой мусора. Спецификация описывает это как гарантии, а не оставляет вам выяснять самим.

Отличается он в сравнении: == сравнивает значения, записи поле за полем, а === в JavaScript сравнивает ссылки.

Ручного управления памятью и модели без сборки мусора в планах нет: это за пределами того, чем является язык, транспилируемый в TypeScript.

if нет, поэтому match должен нести всё

Первое, что спрашивает разработчик на TypeScript после рассказа про исчерпывающую проверку: match это настоящая условная конструкция общего назначения или просто удобный способ разобрать union? Первое, и лучше всего это видно на присваивании.

match, который целиком является значением let или mut, принимает всё, что принимает оператор: ветка может быть блоком, ветка может делать await, ветка может выполнить break из окружающего цикла, и ветка может читать привязку, которой присваивает значение. Так состояние протаскивается через цикл без if.

из проверки ссылок: отслеживание блоков кода и ветка с await 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}
Подробнее во что это компилируется и откуда взяты фрагменты

Оба примера компилируются в обычный switch, который присваивает привязку в каждой ветке, поэтому await оказывается в объемлющей async-функции, а аккумулятор становится обычной переменной, тип которой TypeScript может вывести. Оба фрагмента взяты из examples/apps/linkcheck/main.glyph, проверки ссылок в Markdown, написанной как раз для того, чтобы находить такие вещи.

match, использованный внутри более крупного выражения, как аргумент или операнд, по-прежнему превращается в замыкание, а значит, его ветки должны быть одиночными выражениями. Если вынести его в отдельный let, это ограничение снимается.

Паттерн может описывать форму глубже одного уровня

Вариант с несколькими полями несёт запись, поэтому ветка, которая хочет распознать форму, должна добираться до полей этой записи. Теперь поле принимает любой паттерн: тег варианта, вложенный конструктор, вложенную деструктуризацию, литерал, паттерн массива.

один случай поворота при балансировке красно-чёрного дерева, одной веткой 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}
История обходной путь до 0.1.90

До 0.1.90 на месте поля можно было написать только имя: его можно было переименовать, и всё. Сопоставление с тегом там было ошибкой компиляции, а вложенный конструктор парсер не понимал. Обходной путь состоял в том, чтобы привязать каждое поле и написать вложенный match на каждый уровень, а для чего-то вроде балансировки красно-чёрного дерева это уже другая программа: ветки перестают совпадать со случаями, и каждый уровень заново протаскивает привязки верхних.

У этого есть следствие, о котором стоит знать заранее. Поле, которое проверяет значение, может не совпасть, поэтому такая ветка больше не считается покрывающей свой вариант, и match, где единственная ветка Node это Node({ color: Red, ... }), считается неполным, пока остальное не заберёт соседняя ветка или else.

Подробнее почему требуется catch-all, и позиция массива

Проверка доказывает покрытие по множеству тегов, а не по произведению полей, поэтому она не выяснит, что ветки Red и Black вместе исчерпывают Node. Требовать ветку catch-all значит выбрать прочтение, при котором match не может проскочить свой конец во время выполнения. То же самое там, где вариантов для подсчёта нет вообще: match по обычной записи, в котором каждая ветка проверяет поле, требует else в конце.

Одно место, куда это доходит и где вы этого можете не ждать, это позиция массива. [Black] как целая ветка раньше считался совпадающим с любым одноэлементным массивом, так что match, полагавшийся на это, признавался исчерпывающим, а потом уходил в эту же ветку и для [Red]. Элемент в PascalCase здесь тоже ссылка на вариант, поэтому такой match теперь даёт E0208 на массивах длины 1. Привяжите элемент и сопоставляйте его отдельно. Понижение под этим всё ещё старое, поэтому проверка и стала той половиной, которая вышла первой.

E0208

И компилятор знает, что вернул match

Следующий вопрос решает, есть ли во всём этом реальный смысл: когда вы получаете значение из ветки, знает ли Glyph его тип, или пожимает плечами и оставляет это tsc на потом? Теперь match получает тип своих веток, когда они согласны, а про T.parse известно, что он возвращает Result<T, Array<Issue>>, и именно по такой форме ветвится большая часть реального кода.

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...

История до 0.1.45

До 0.1.45 пожимал. Каждое выражение match имело неизвестный тип, так что значение, полученное из единственной ветвящейся конструкции языка, с этого места оставалось нетипизированным.

Подробнее что ломалось тихо и как работает объединение

Обе половины этого раньше ломались тихо. Цикл генерирует wire.expenses.entries(); когда тип итерируемого значения неизвестен, вместо этого генерируется Object.entries(...), и i оказывается строкой "0". Это корректный TypeScript, поэтому сборка проходила чисто, а программа печатала 01:a там, где имелось в виду 1:a. А wire.expensez теперь даёт [E0210] type WireLedger has no field expensez от Glyph, на строке .glyph, а не TS2339 в сгенерированном TypeScript.

Объединение работает как равенство по голове типа: ветка, которая заканчивается return, не голосует, а ветки, чьи типы расходятся, оставляют результат неизвестным, как было раньше. На уровень глубже оно смотрит только в аргументе типа, поэтому None => [] согласуется с веткой Array<string>, а не топит весь match, и цикл после него по-прежнему привязывает число. Та же цепочка поверх record.get работает по той же причине: все шесть функций std/record берут тип значения из записи, которую вы передаёте. Фрагмент взят из examples/apps/settle/main.glyph, где была аннотация, которую это изменение удалило.

Поиск с пустым запасным вариантом

Именно эта форма обходилась дороже всего. record.get на Record<string, Array<string>> даёт Option<Array<string>>, а [] это массив неизвестно чего, поэтому две ветки согласны на Array, а тип элемента берётся из той ветки, где он есть.

из резолвера зависимостей: поиск, пустой запасной вариант, обход по индексу 
let path = match record.get(res.reached, name) {
  Some(p) => p,
  None => [],
}

for i, hop in path {               # i is a number, so the indent nests
  let indent = string.repeat(STEP, i + 1)
  mut out = array.push(out, "${indent}${hop}")
}
История до 0.1.55

До 0.1.55 их сравнивали на равенство, [] считался расхождением, и цикл ниже печатал 01:x в сборке без диагностик, которую пропускал tsc --strict. Код лежит в examples/apps/depsolve/main.glyph, где раньше он начинался с let path: Array<string> под комментарием в три строки, объяснявшим, что без этой аннотации всё сломается.

Придётся ли писать pad_start самому?

Первый пробел, на который натыкаешься в реальной программе, это не возможность системы типов. Это когда тянешься за string.slice и ничего там не находишь.

История копии, которые приложения носили до 0.1.47

Пять раундов догфудинга подряд приносили один и тот же список, и до 0.1.47 шесть приложений в этом репозитории носили свой repeat, пять свой pad_start, и во всех был цикл там, где напрашивался fold.

Чем они отличаются от TypeScript

Три из них намеренно расходятся со своими тёзками из TypeScript.

  • repeatrepeat возвращает "" при отрицательном счётчике там, где TS бросает исключение, и именно поэтому repeat(pad, width - len(s)) безопасен на строке, которая уже слишком длинная.
  • index_ofОбе функции index_of возвращают Option<number> вместо -1, потому что -1 это число, которое проходит проверку типов везде, где проходит настоящий индекс, а падает далеко от места вызова.
  • replace_allЗамена есть только в виде replace_all, поэтому нет формы «только первое вхождение», которую можно перепутать с String.prototype.replace, тихо заменяющим одно вхождение.

Почему важен fold

fold единственный из них, который даёт выигрыш по принципу, а не просто экономит набор текста. mut это находимая grep запись каждого места, где меняется состояние, а без fold grep mut возвращает кучу циклов-счётчиков, которые не меняют ничего, что интересно ревьюеру.

Удаление самописных версий уменьшило число мест мутации в examples/apps/ со 192 до 161.

Подробнее как проверяли переписанное

Переписанное проверяли по выводу, а не на ревью: все семь приложений запускались на фиксированных входных данных до и после, 26 файлов stdout, кодов выхода и HTTP-ответов, все совпали побайтно.

Можно ли обойти каталог и понять, что сломалось?

В std/fs было шесть функций, и ни одна не выводила содержимое каталога.

  • fs.read_dirfs.read_dir возвращает имена записей на один уровень вниз.
  • fs.is_dirfs.is_dir отвечает значением bool, как fs.exists.
  • fs.statfs.stat возвращает FileInfo из is_dir, is_file, size в байтах и modified в миллисекундах от эпохи, которое time.format_iso выводит напрямую.

Рекурсивного walk и glob нет; обход это эти три функции плюс path.join, примерно десять строк.

История обходной путь, который они заменили

Проверка ссылок в этом репозитории лезла мимо стандартной библиотеки в readdirSync из node и определяла, какие пути являются каталогами, пытаясь их прочитать и разбирая вернувшийся errno. Обе половины исправлены.

У ошибок есть имена

Сторона ошибок изменилась сильнее. Теперь у пяти видов ошибок, после которых программа реально восстанавливается, есть имена, а errno без имени приходит без потерь в хвосте Other.

Проверка типов знает, что эта таксономия закрыта, поэтому к match по err.kind предъявляются те же требования, что и к union, который вы объявили сами: покройте все шесть, и else не нужен, пропустите один, и сборка падает с E0200, называющей fs.ErrorKind.

Подробнее старая таксономия, проверяемые поля и как проверить самому

FsError.kind был { tag: string }, и вся таксономия состояла из NotFound, так что отличить «этот путь каталог» от «этого пути нет» можно было только сравнением строки errno.

У fs.FsError и fs.FileInfo поля тоже проверяются, так что err.mesage это E0210 по вашему исходнику на Glyph, а не ошибка tsc по сгенерированному TypeScript.

Эта проверка работает. Удалите ветку PermissionDenied из match выше, и glyph check --no-tsc остановится с E0200: неполный match по fs.ErrorKind, не хватает вариантов PermissionDenied. Когда модель стандартной библиотеки только писалась, она покрывала одни возвращаемые типы, и такой match компилировался чисто и падал во время выполнения; формы полей и вариантов fs.FsError, fs.FileInfo и fs.ErrorKind теперь смоделированы.

Два небольших дополнения

Вместе с этим появились две функции поменьше, обе из того же приложения.

  • regex.captures_allregex.captures_all даёт группы захвата для каждого совпадения, а не только совпавший текст, так что плоский поиск key=value перестаёт быть самописным циклом.
  • task.pool_settledtask.pool_settled это task.pool с поведением при ошибках как у all_settled: ограниченная конкурентность, один результат на задачу, и один упавший хост стоит вам только результата этого хоста, а не всех результатов, которые пул успел собрать.

Откуда известно, что это правильные функции?

Оттуда, что приложение, которое их просило, должно было перестать обходить их отсутствие, прежде чем выпуск засчитали как готовый.

Библиотечная функция, которая вышла, и обходной путь, который её пережил, это разные утверждения, поэтому то же изменение, что добавило эти четыре функции, удалило их копии из проверки ссылок: импорт readdirSync, оба сравнения строк errno, 97 строк самописного сканера и пул, падающий при первой ошибке. Ушло 122 строки.

Два изменения поведения, измеренные

Два из этих удалений изменили поведение программы, и разницу измерили, а не обсуждали.

  • Нечитаемый каталогЗапустите старую и новую версии на дереве, где есть каталог, который нельзя прочитать: новая печатает permission denied и считает путь нечитаемым, а старая, которая могла только спросить, равен ли errno EISDIR, вообще не включала его в отчёт.
  • Падающий URLСделайте так, чтобы один из трёх URL бросал исключение: pool_settled напечатал все три строки и назвал сбой, а pool не напечатал ничего и упал на необработанном rejection, утащив за собой два хороших результата.
Подробнее переписанный сканер и опасения насчёт альтернации

Переписывание сканера закрыло и одно сомнение в дизайне. Поскольку группа захвата, которая не участвовала в совпадении, читается как "", так же как группа, совпавшая с пустой строкой, казалось, что captures_all не может сказать, какая ветка альтернативы сработала. Может, если оборачивать группой каждой ветки всю конструкцию, а не только нужную часть: тогда сработавшая группа начинается с `, [, ! или < и не может быть пустой. Часть, которая может быть пустой (цель ссылки), вложена внутрь, и про неё никогда не спрашивают. Так обход по символам на 180 строк превратился в два паттерна и диспетчеризацию на 12 строк с побайтно одинаковым выводом на документации самого репозитория и на тестовых данных, собранных специально, чтобы это сломать.

Деньги не считают на float

Пробел, который сразу закончил бы оценку в финтехе, это деньги на IEEE-754 number, где 0.1 + 0.2 не равно 0.3, а значения больше 253 тихо теряют точность.

std/decimal это точная десятичная арифметика с фиксированной точкой поверх BigInt: целое число произвольной точности с фиксированным количеством знаков после запятой, поэтому сложение, вычитание и умножение точны, а деление принимает явный масштаб и режим округления. Некорректная сумма разбирается в Err, а не в тихий NaN.

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

Большие целые числа

Для точных больших целых чисел, идентификаторов счетов и счётчиков, есть тип bigint: литералы пишутся как 123n, он генерируется в настоящий bigint TypeScript, а поле записи с типом bigint проверяет typeof === "bigint" на границе, так что идентификатор, пришедший как JSON number, отклоняется, а не тихо округляется после 253.

У async-колбэка наконец есть тип

Тип функции был только fn(A) -> T, который генерируется в (a: A) => T. Async-тело в это не вписывается, поэтому функцию, возвращающую отложенную задачу, или запись из async-обработчиков приходилось оставлять без аннотации, и проверка типов переставала туда смотреть.

async fn(A) -> T это недостающий тип. Он генерируется в (a0: A) => Promise<T>, а async fn() без возвращаемого типа генерируется в () => Promise<void>.

отложенная задача и словарь обработчиков 
fn task_for(url: string) -> async fn() -> Fetched {
  return async fn() -> Fetched { return { url: url, body: await fetch_one(url) } }
}

type Handler = async fn(string) -> string

async fn dispatch(routes: Record<string, Handler>, name: string, arg: string) -> string {
  return match record.get(routes, name) {
    Some(h) => await h(arg),
    None    => "no route",
  }
}
Подробнее как Glyph различает обычные и async-функции

Glyph сам различает эти два типа, а не оставляет это tsc: обычная функция там, где ожидается async, это E0204 в return и E0211 в аргументе вызова, и сообщение называет обе стороны.

Единственный случай, который он не оценивает, это возвращаемый тип void, где TypeScript принимает любую функцию.

Рекурсивный тип, сопоставленный до самого низа

Union может называть сам себя внутри своей полезной нагрузки, со своими параметрами типа, а ветка match может вкладывать паттерн конструктора в поле другого паттерна конструктора. Вместе это даёт правила балансировки красно-чёрного дерева в четыре ветки: каждая называет ровно ту форму, которую переписывает, и форму проверяет компилятор, а не комментарий над ней, который это утверждает.

type Tree<K, V> =
  | Leaf
  | Node({ color: Color, left: Tree<K, V>, key: K, value: V, size: int, right: Tree<K, V> })

fn balance<K, V>(t: Tree<K, V>) -> Tree<K, V> {
  return match t {
    Node({ color: Black, left: Node({ color: Red, left: Node({ color: Red, left: a, key: xk, value: xv, right: b }), key: yk, value: yv, right: c }), key: zk, value: zv, right: d }) => node(
      Red,
      node(Black, a, xk, xv, b),
      yk,
      yv,
      node(Black, c, zk, zv, d),
    ),
    // the other three cases, then:
    other => other,
  }
}

Видимость

  • Приватный импорт даёт то же сообщение, что и отсутствующее имя
    Подробнее

    Приватный импорт сообщает «not exported by M», то же сообщение, что и для отсутствующего имени; различать «приватное, пометьте pub» и «такого имени нет» научат в одном из следующих уточнений, оно в очереди.

  • Приватное значение, прочитанное через пространство имён, это ошибка tsc, а не Glyph
    Подробнее

    Видимость проверяется в аннотациях типов, но не для значений, прочитанных через пространство имён: lib.helper(), где helper приватный, по-прежнему ошибка tsc, а не Glyph.

Async

  • await верхнего уровня в инициализаторе const на уровне модуля разрешёнE0222
    Подробнее

    Async-контекст теперь проверяется (E0222), кроме одного места: у инициализатора const на уровне модуля нет объемлющей вызываемой сущности, поэтому await верхнего уровня там разрешён, и сгенерированный ESM его выполняет.

Выводимые типы

  • Если ветки расходятся по голове типа, результат для Glyph неизвестен
    Подробнее

    Объединению веток всё ещё нужно, чтобы ветки совпадали по голове типа: когда они дают разные типы, результат для Glyph неизвестен, и что вы с ним делаете, проверяет только tsc.

  • В таком же положении девять функций стандартной библиотеки
    Подробнее

    В таком же положении девять функций стандартной библиотеки. Шесть принимают необязательный последний аргумент (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify), а проверка арности сравнивает одно число с одним числом, так что их моделирование давало бы ложную ошибку на каждом вызове без последнего аргумента; array.map, flat_map и zip берут тип элемента из колбэка, в который проверка типов не заходит.

    Значению, взятому прямо из этих девяти функций, нужна аннотация, прежде чем обходить его по индексу, а match по string.index_of без ветки None по-прежнему собирается чисто и падает во время выполнения. array.index_of смоделирован и сообщает E0200.

Библиотека

  • string индексирует единицы кода UTF-16, и chars или char_at не планируется
    Подробнее

    Со стороны библиотеки string индексирует единицы кода UTF-16, как всегда делали len и split, и это решено окончательно: chars или char_at нет и не планируется, потому что возвращённая половинка суррогатной пары выглядит как символ ровно до того момента, когда её выводят.   • captures_all не даёт смещений; fs.read_dir сохраняет порядок ОС
    Подробнее

    captures_all возвращает группы без смещений, так что сканер, которому нужно знать, где в строке началось совпадение, по-прежнему пишет свой цикл, а fs.read_dir отдаёт записи в порядке ОС, так что сортируйте их, когда вывод должен быть воспроизводимым.

Паттерны

  • Конструктор с полезной нагрузкой в поле не работает на union, доступном через импорт пространства имёнE0300
    Подробнее

    У вложенного паттерна поля осталось одно ограничение: конструктор с полезной нагрузкой в поле, на union, доступном через импорт пространства имён. import tree { Node }, а затем Node({ left: Node({ key: k }) }) компилируется, а import tree, а затем tree.Node({ left: tree.Node({ key: k }) }) даёт E0300 на том же union.

  • Union, обобщённый по собственному параметру, принимает вложенную ветку и проверяется на пропущенные вариантыE0200
    Подробнее

    Второго ограничения больше нет: union, обобщённый по собственному параметру (type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> })), раньше отвергал вложенную ветку, которую принимал тот же union без параметра, а теперь принимает её, и с открытым параметром типа, и с конкретной подстановкой. Тот же поиск решал, проверяется ли match на пропущенные варианты вообще, поэтому до этого выпуска match по Tree<K> мог пропустить Leaf, собраться чисто, пройти tsc --strict и упасть во время выполнения там, где необобщённое написание давало E0200.

    Теперь об этом сообщают оба написания, и перенос union на один импорт дальше больше не меняет ответ: match по импортированному Tree<string> без Leaf даёт E0200 с названием Leaf, так же как импортированный необобщённый Tree. Это был другой путь в коде, проверялся он отдельно и до этого выпуска вёл себя наоборот: собирался чисто и падал во время выполнения.

  • Покрытие импортированного union никогда не проверяет полезные нагрузки его вариантов
    Подробнее

    Об одном свойстве покрытия импортированного union стоит знать, прежде чем на него полагаться: полезные нагрузки его вариантов тоже никогда не проверяются, поэтому B(X), где X вариант собственного union полезной нагрузки, совпадает с каждым B, вместо того чтобы сообщить о пропущенном Y, и к дженерикам это отношения не имеет.

    Привязка поля или сопоставление с тегом без полезной нагрузки в поле работают во всех случаях.
