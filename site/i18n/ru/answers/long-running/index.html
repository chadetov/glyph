19 · Серверы и демоны

Можно ли написать сервер, или процесс просто завершится?

Сервер написать можно. main выполняет настройку и возвращается, а процесс живёт, пока есть ожидающие сокеты и таймеры, по тому же правилу, что и в Node. До 0.1.63 так не было: раннер завершал процесс в момент возврата из main, так что сервер занимал порт и умирал в том же тике.

Почему это важно

В этом разница между языком, который может выполнить скрипт, и языком, который может запустить сервис. Сервер, наблюдатель за файлами, бот, держащий соединение с gateway, исполнитель задач: ни один из них не заканчивает работу внутри main. Они настраивают обработчики и отдают процесс событиям.

Старое поведение ломалось худшим из возможных способов, то есть молча. glyph run app.glyph --serve 4100 ничего не печатал, даже строку внутри колбэка listen, и завершался с кодом 0. В исходнике ничего не выглядело неправильным, и проверка типов проходила. У агента, который на это наткнётся, нет ни ошибки, о которой можно сообщить, ни причины думать, что что-то сломалось.

Посмотрите сами

TCP-сервер целиком. main возвращается сразу; колбэки выполняются, пока живёт процесс:

Сервер от начала до конца 
module main

import std/io
import std/process
import net { createServer }

fn main(argv: Array<string>) -> number {
  let server = createServer(fn(socket) {
    mut socket.write("hello\n")
    mut socket.end()
  })

  mut server.on("error", fn(err) {
    io.eprintln("cannot listen: ${err.message}")
    process.exit(1)
  })

  mut server.listen(4000, fn() {
    io.println("listening on 4000")
  })
  return 0
}

net это встроенный модуль Node, поэтому импортируется обычным образом, но он не входит в шесть модулей, для которых компилятор поставляет встроенные типы (fs, http, path, os, crypto, url). Либо установите @types/node, и сборка будет использовать его, либо положите объявление в .types/net.d.ts рядом с исходниками, как делает чат-приложение, чтобы вообще обойтись без зависимостей.

Две вещи, которые стоит знать. return 0 выполняется ещё до того, как подключится первый клиент: это код, с которым процесс в итоге завершится, а не указание, когда он завершится. И всё, что падает после возврата из main, должно само выставить код выхода, потому что возвращаемое значение main уже использовано. Для этого и нужен обработчик error. Без него сервер, который не может занять порт, опустошает цикл событий и завершается с кодом 0, сообщая об успехе.

Настоящий пример

examples/apps/chat это чат-сервер, который держит несколько TCP-клиентов одновременно. Части, которые не касаются сети, остаются отдельными и тестируемыми: сборка строк, маршрутизация и движок комнат это чистые функции, проверяемые @example, и только один файл работает с сокетами.

Три клиента подключены одновременно

Обратное направление: долгоживущий клиент

Бот устроен так же, только направлен наружу. examples/apps/discord это клиент gateway Discord: он подключается по WebSocket, представляется, шлёт heartbeat с интервалом, который задаёт сервер, отслеживает номер последовательности, чтобы оборванное соединение возобновлялось, а не начиналось заново, замечает, когда соединение открыто, но мертво, и делает паузы между переподключениями.

Перенимать стоит то, где живёт логика. Решение, что делать с RECONNECT, пропущенным heartbeat или отклонённым токеном, это чистая функция от сессии и одного события к новой сессии и списку действий. Один модуль выполняет эти действия на настоящем сокете. Поэтому логика переподключения, которую труднее всего сделать правильно, проверяется @example, а не выдёргиванием сетевого кабеля:

Каждый из этих трёх примеров сначала был багом в коде. Один из них поймал mock gateway, на который направили бота. Два других поймал второй mock, написанный по документации Discord, а не по клиенту; он присылает то, чего покладистый mock никогда не делает: запрос heartbeat без повода и код закрытия, означающий «ваш токен неверен, хватит спрашивать». Mock, написанный автором клиента, проверяет только те части протокола, которые автор прочитал.

Текущее состояние

Уже работает

Возврат из main выставляет код выхода, не останавливая процесс, так что серверы, наблюдатели и циклы событий работают. Программа, которая только вычисляет, по-прежнему завершается в момент возврата из main с тем же кодом, так что для коротких программ ничего не изменилось. Встроенные модули Node вроде net импортируются обычным образом, а программа, которая бросает исключение во время настройки, по-прежнему завершается, теперь уже после того, как её диагностика дошла до stderr в пайпе, а не, возможно, обрезалась при выходе. std/timers планирует работу (after, every, cancel, unref), а std/websocket открывает соединение, так что ни тому, ни другому не нужно рукописное объявление.

Становится точнее

Слушатель, который не смог занять порт после возврата из main, завершается с кодом 0, если программа не скажет иного: process.set_exit_code(1) фиксирует ошибку, не прерывая работу, которая ещё идёт, а process.exit(1) останавливает процесс сразу. Компилятор пока не умеет предупреждать, что вы об этом забыли. И по-прежнему нельзя записать, что функция не возвращается, поэтому main сервера содержит return 0, до которого выполнение никогда не доходит.
