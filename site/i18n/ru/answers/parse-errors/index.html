27 · Ошибки разбора

Когда разбор не удаётся, узнаю ли я почему?

Да. Каждая проблема называет поле, говорит, какое правило нарушило значение, и несёт code, по которому можно ветвиться. Поле, ограниченное предикатом where, сообщает сам предикат, так что по отказу grep приводит к строке, где это ограничение задано.

Почему это важно

Валидатор, который говорит «этот payload плохой», сделал половину работы. Обработчику всё равно нужно решить: это клиент, который забыл поле, или клиент, который прислал пароль из четырёх символов? Первое это 400, второе 422, и если валидатор этого не говорит, в итоге вы разбираете одно и то же тело дважды с двумя разными типами, чтобы восстановить информацию, которая у валидатора уже была.

Именно это и случилось при написании API авторизации на Glyph. Регистрация вообще без ключа password возвращалась как weak_password, потому что отсутствующее и слишком короткое значение давали одну и ту же строку.

Посмотрите сами

Один тип, одно ограничение:

signup.glyph 
pub type Password = string where value.length >= 8

pub type Signup = {
  email: string,
  password: Password,
}

Четыре плохих payload, четыре разных ответа. Каждый из них это один Issue, показанный как code | path | message:

Signup.parse(...) 
// { "email": "user@example.com" }
missing     ["password"]  field `password` is required

// { "email": "user@example.com", "password": "short" }
refinement  ["password"]  expected Password (string where value.length >= 8)

// { "email": 42, "password": "longenough" }
type        ["email"]     field `email` must be string

// [1, 2, 3]
type        []            expected Signup (an object), got an array

Главное здесь второй. value.length >= 8 написано один раз, в типе, и отказ цитирует его дословно. Вставьте эту строку из тела ответа HTTP 422 в grep, и вы попадёте на объявление, которое её породило. Никому не нужно держать копию правила в слое сообщений об ошибках, а именно так эти две копии и расходятся.

Четвёртый раньше был хуже, чем просто плохое сообщение. Для typeof массив это объект, поэтому запись без обязательных полей принимала его без вопросов, а присланный [1, 2, 3] возвращался как по одной непонятной проблеме на каждое объявленное поле, и ни одна не упоминала, что вы прислали список.

Вложенные типы отвечают сами за себя

Поле, у типа которого есть собственный дескриптор, проверяется parse этого типа, и его проблемы возвращаются с именем поля в начале пути. Так что Password, вложенный на два уровня, сообщает ["body", "password"] и сохраняет своё сообщение. Место и причину вы получаете из одной и той же проблемы, ничего не перезапуская.

Код, а не строка

Issue несёт необязательный code: "missing", "type", "refinement" или "unexpected". Ветвитесь по нему. Сопоставление по тексту сообщения это та хрупкость, которую Glyph и призван убрать, а сообщение предназначено для человека, читающего тело ответа.

Разделение на 400/422 без чтения сообщения 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code необязателен, поэтому Issue, собранный вручную, и любой потребитель, написанный до его появления, по-прежнему компилируются без изменений.

Текущее состояние

Уже работает

Записи и типы where сообщают нарушенное правило, а не только поле: "missing" для отсутствующего обязательного поля, "type" для неверной формы (включая не-объект или массив), "refinement" для значения, которое прошло базовый тип, но не прошло предикат, и "unexpected" для ключа, которого тип не объявляет. Уточнение цитирует свой предикат. Поле, у типа которого есть дескриптор, передаёт проверку ему, поэтому вложенные проблемы приходят с полным путём. Необязательные поля (f?: T) никогда не сообщаются как отсутствующие.

Становится точнее

Два ограничения. Поле, типизированное чем-то без собственного дескриптора (неограниченным параметром типа или типом, импортированным из рукописного .d.ts), по-прежнему получает плоскую проверку и проблему "type"; компилятор не синтезирует для них дескриптор, а дать его может запуск glyph gen dts на объявлении. Модуль, объявляющий собственный тип с именем Issue, раньше перекрывал тип из прелюдии внутри сгенерированного файла и ломал все дескрипторы в этом модуле; начиная с 0.1.60 такое объявление даёт E0110 на строке, где назван тип, так что вы узнаёте, где проблема, вместо того чтобы читать ошибку tsc о сгенерированном коде.
