Когда разбор не удаётся, узнаю ли я почему?

Да. Каждая проблема называет поле, говорит, какое правило нарушило значение, и несёт code, по которому можно ветвиться. Поле, ограниченное предикатом where, сообщает сам предикат, так что по отказу grep приводит к строке, где это ограничение задано.

Почему это важно

Валидатор, который говорит «этот payload плохой», сделал половину работы.

Обработчику всё равно нужно решить: это клиент, который забыл поле, или клиент, который прислал пароль из четырёх символов? Первое это 400, второе 422, и если валидатор этого не говорит, в итоге вы разбираете одно и то же тело дважды с двумя разными типами, чтобы восстановить информацию, которая у валидатора уже была.

История где это всплыло

Именно это и случилось при написании API авторизации на Glyph. Регистрация вообще без ключа password возвращалась как weak_password, потому что отсутствующее и слишком короткое значение давали одну и ту же строку.

Вложенные типы отвечают сами за себя

Поле, у типа которого есть собственный дескриптор, проверяется parse этого типа, и его проблемы возвращаются с именем поля в начале пути. Так что Password, вложенный на два уровня, сообщает ["body", "password"] и сохраняет своё сообщение.

Код, а не строка

Issue несёт необязательный code: "missing", "type", "refinement", "unexpected" или "depth". Ветвитесь по нему. Сопоставление по тексту сообщения это та хрупкость, которую Glyph и призван убрать, а сообщение предназначено для человека, читающего тело ответа.

Разделение на 400/422 без чтения сообщения 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code необязателен, поэтому Issue, собранный вручную, и любой потребитель, написанный до его появления, по-прежнему компилируются без изменений.

Подробнее код "depth"

"depth" это ответ для тела, вложенного глубже 1000 объектов и массивов (MAX_DEPTH в std/schema): одна проблема на том поле, где это случилось, тогда как до 0.1.150 проверка бросала RangeError: Maximum call stack size exceeded и роняла вместе с собой обработчик.

Текущее состояние

Уже работает

  • Записи и типы where сообщают нарушенное правило, а не только полеmissingtyperefinementunexpecteddepth
    Подробнее

    Записи и типы where сообщают нарушенное правило, а не только поле: "missing" для отсутствующего обязательного поля, "type" для неверной формы (включая не-объект или массив), "refinement" для значения, которое прошло базовый тип, но не прошло предикат, "unexpected" для ключа, которого тип не объявляет, и "depth" для значения, вложенного глубже 1000 уровней.

  • Уточнение цитирует свой предикат.
  • Поле, у типа которого есть дескриптор, передаёт проверку ему, поэтому вложенные проблемы приходят с полным путём.
  • Необязательные поля (f?: T) никогда не сообщаются как отсутствующие.

Становится точнее 2

  • Поле, типизированное чем-то без собственного дескриптора, по-прежнему получает плоскую проверку и проблему "type"
    Подробнее

    Два ограничения. Поле, типизированное чем-то без собственного дескриптора (неограниченным параметром типа или типом, импортированным из рукописного .d.ts), по-прежнему получает плоскую проверку и проблему "type"; компилятор не синтезирует для них дескриптор, а дать его может запуск glyph gen dts на объявлении.

  • Собственный тип модуля с именем Issue отклоняется на строке, где он названE0110с 0.1.60
    Подробнее

    Модуль, объявляющий собственный тип с именем Issue, раньше перекрывал тип из прелюдии внутри сгенерированного файла и ломал все дескрипторы в этом модуле; начиная с 0.1.60 такое объявление даёт E0110 на строке, где назван тип, так что вы узнаёте, где проблема, вместо того чтобы читать ошибку tsc о сгенерированном коде.
