Работает ли он с React: компоненты, хуки и Context?

Да. component компилируется в функциональный компонент React, JSX понижается в createElement, собственные хуки React импортируются по имени, а их пары деструктурируются, и состояние редьюсера получает исчерпывающую проверку, которой нет в обычном TypeScript. К самой странице (её заголовку, точке монтирования, сохранённому состоянию) обращаются через std/dom и std/storage. Ограничение, о котором стоит знать сразу: собственная проверка Glyph не типизирует то, что возвращает хук, поэтому эти значения проверяет tsc.

Почему это важно

Большая часть кода, который пишут агенты, это React. Glyph считает его полноценной целью, а не надстройкой: component это отдельное ключевое слово (так что grep "^component " проверяет весь ваш UI). Хуки React импортируются из react и вызываются под своими настоящими именами и с настоящими типами, а tsc проверяет их по собственным объявлениям React.

Посмотрите сами

Настоящий useReducer из React с редьюсером над размеченным объединением. Каждое действие должно быть обработано, и компилятор это проверяет:

counter.glyph, с react@18 и его типами 
import react { useReducer }

type Action = Inc | Dec | Reset

fn reducer(n: number, a: Action) -> number {
  return match a {
    Inc => n + 1,
    Dec => n - 1,
    Reset => 0,
    // add an Action variant and this match is E0200
  }
}

pub component Counter() {
  let [count, dispatch] = useReducer(reducer, 0)
  return <button on_click={fn() { dispatch(Inc) }}>{count}</button>
}

Добавьте действие Double, и редьюсер перестанет компилироваться с E0200, где оно названо, тогда как обычный switch в TypeScript пропустил бы это в релиз. Пара деструктурируется через let [count, dispatch], а сгенерированный TypeScript добавляет satisfies readonly [unknown, unknown], так что tsc доказывает, что хук вернул пару, и всё равно выводит тип каждого элемента. Собственная проверка Glyph не типизирует значения, пришедшие из React, поэтому о неверном аргументе dispatch или сеттера состояния сообщает tsc при сборке, а не редактор или --no-tsc. Context React уже работает через createContext / useContext, а имена элементов в виде обращения к члену (<ThemeContext.Provider>) работают напрямую, без обходных путей.

Spread пропсов в JSX тоже работает: <input {...register("email")} /> понижается в spread объекта в props, так что идиоме react-hook-form адаптер не нужен. Типы zod, выведенные из значений, поддерживаются полноценно: type FormData = z.infer<typeof schema> работает напрямую, без лазейки. Одно отличие: компонент принимает одну запись props, а не несколько позиционных параметров. Где именно проходит эта граница, смотрите в использовании ваших библиотек и на странице про укрепление.

Проверяются ли пропсы до tsc?

Да. Glyph сам сравнивает каждый элемент с записью props его компонента, поэтому неверное значение, опечатка в имени пропса и отсутствующий обязательный пропс это ошибки Glyph, в которых пропс назван. Вы видите их в редакторе и через MCP, а не только в полной сборке. Это работает одинаково, импортирован ли компонент по имени или через свой модуль:

main.glyph, где Card объявлен в ui.glyph 
import ui

pub component App() {
  return <div>
    <ui.Card title="Q3" />
    <ui.Card title="Q4" cout={2} />
  </div>
}

// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`
// E0210 type `CardProps` has no field `cout`; did you mean `count`?
// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`

--json передаёт отсутствующие имена списком missing_fields, так что агент может добавить пропсы, не разбирая сообщение. Кроме того, компонент должен принимать свои props одной записью: component Greeting(name: string) даёт E0229 на параметре, потому что React всегда передаёт только объект props, и такой элемент никогда не прошёл бы проверку типов. Если вы вызываете его как функцию, а не рендерите, объявите его через fn.

Проверяется ли <match> в JSX как match?

Это одно и то же. Каждый <case> принимает тот же паттерн, что и ветка match, и компилятор прогоняет его через тот же код, что и ветку. Имена, которые привязывает case, получают типы полезной нагрузки, поле, которого нет в записи полезной нагрузки, даёт E0210, а пропущенный вариант даёт E0200. Case, который проверяет значение, покрывает только часть своего варианта, поэтому ему нужен соседний case или <case else>, который заберёт остальное:

results.glyph 
type Page =
  | Loading
  | Loaded({ users: Array<User>, total: number })
  | Failed(string)

component Results(props: { page: Page }) {
  return <match value={props.page}>
    <case Loading><p>Loading...</p></case>
    <case Loaded({ users, totl })><p>{users.length} of {totl}</p></case>
    <case Failed(message)><p>{message}</p></case>
  </match>
}

// E0210 type `{ users: Array<User>, total: number }` has no field `totl`; did you mean `total`?

Как страница его запускает?

В Glyph нет операторов верхнего уровня, поэтому страница сама вызывает экспортированный main. Приложение состоит из двух модулей: в одном компоненты, а другой монтирует их на #root через std/dom и createRoot из react-dom. Атрибуты событий пишутся в snake case (on_change генерирует onChange React), обработчик это лямбда, а текст поля ввода это e.currentTarget.value.

app.glyph 
module app

import react { useState }

pub component App() {
  let [name, set_name] = useState("")
  return <main>
    <input value={name} on_change={fn(e) { set_name(e.currentTarget.value) }} />
    <p>Hello, {name}</p>
  </main>
}
main.glyph 
module main

import react-dom/client { createRoot }
import std/dom
import std/console
import std/option { Some, None }
import app { App }

pub fn main() -> void {
  match dom.element_by_id("root") {
    Some(root) => createRoot(root).render(<App />),
    None => console.error("the page has no #root element"),
  }
}
index.html рядом с двумя модулями 
<div id="root"></div>
<script type="module">
  import { main } from "./dist/gen/main.ts";
  main();
</script>

npx glyph build . --out dist/gen проверяет модули, запускает tsc --strict по объявлениям React и пишет TypeScript в dist/gen. Затем npx vite build --outDir dist/web читает index.html, идёт по импорту и собирает бандл вместе с React. Этот main ничего не принимает и ничего не возвращает, потому что скрипт вызывает его без аргументов; main(argv) -> number, который пишет glyph init, это тот, что вызывает glyph run под node. Полный разбор с package.json и строкой установки находится в разделе запуск Glyph на странице в браузере справочника, который печатает glyph llms. CI собирает examples/apps/todo так же и отрисовывает его в headless Chromium.

Текущее состояние

Уже работает

Компоненты, JSX, фрагменты (<>...</>), имена элементов в виде обращения к члену (<Ctx.Provider>), spread пропсов в JSX ({...register()}), пропсы, проверяемые по компоненту до tsc при любом написании импорта, собственные хуки React, импортируемые по имени (useState, useReducer, useEffect), с проверкой их типов в tsc и деструктуризацией пар (let [count, set_count] = useState(0)), useReducer с исчерпывающими действиями на размеченном объединении, <match>/<case>, которые проверяются и понижаются как match с паттернами веток, Context через createContext/useContext и страница через std/dom (заголовок, точка монтирования, адрес), std/storage и std/console. Текст в JSX читается так же, как его читает TSX, поэтому <p>Don't stop</p> это обычный текст; }, >, // и HTML-сущность вроде &amp; в тексте отклоняются (E0012) с подсказкой, как написать вместо этого. Обращение к члену массива проверяется, поэтому {items.foo} на Array<string> даёт E0210. examples/apps/todo это целое приложение на React 18, которое собирается Vite и отрисовывается в браузере.

В работе

Проверка Glyph не типизирует результат хука, поэтому set_count("x") на числовом состоянии это ошибка tsc при сборке, а не ошибка Glyph в редакторе. std/dom ограничивается чтением страницы и установкой её заголовка: DOM, который рендерит React, принадлежит React, поэтому сеттеров элементов и обработчиков событий там нет. Эффект нужно писать как fn() -> void { ... }, потому что лямбда возвращает своё последнее выражение, и React вызвал бы его как функцию очистки. Тип props, записанный inline, в этих сообщениях по-прежнему показывается как record; именованный показывает своё имя. Как встроить вывод Glyph в существующее приложение на Vite с UI на TypeScript, описано в руководстве по развёртыванию.
