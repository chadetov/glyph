Как обстоят дела с редактором, отладкой и ошибками?

glyph lsp работает по Language Server Protocol через stdio, поэтому любой редактор с LSP-клиентом получает диагностики, типы при наведении, переход к определению, автодополнение и форматирование при сохранении. Расширение для VS Code лежит в репозитории; в Marketplace его пока нет, так что его собирают из исходников. Каждая ошибка содержит стабильный код, исправление и причину.

Почему это важно

Править код на языке, которого ваш редактор не понимает, ощущается как шаг назад, и поначалу это была справедливая претензия. Теперь уже нет: редактор даёт вам привычные современные удобства, а ошибки написаны так, чтобы учить, а не просто отклонять.

Это настоящий LSP или просто плагин для VS Code?

Настоящий. Компилятор поставляется с языковым сервером, который запускается как glyph lsp и работает по Language Server Protocol через stdio (стандартный транспорт JSON-RPC, который понимает любой LSP-клиент). Встроенное расширение для VS Code это тонкий клиент вокруг него, но ничего специфичного для VS Code там нет: направьте любой редактор с поддержкой LSP, Neovim, Helix, Zed, Emacs (eglot), на glyph lsp, и он будет вести себя так же. Это тот же бинарный файл, который вы уже установили (npx @glyphlang/glyph lsp), так что отдельный сервер скачивать не нужно.

Сервер реализует то, что нужно редактору: диагностики на лету со стабильными кодами (о них ниже), типы при наведении, переход к определению (между модулями через именованный импорт; через пространство имён ui.Button по-прежнему ничего не возвращает), автодополнение, символы документа и рабочего пространства для структуры и поиска символов, поиск ссылок по всему рабочему пространству, переименование и форматирование в канонической раскладке glyph fmt для форматирования при сохранении. Переименование полное: переименование объявления уровня модуля правит его определение, каждую ссылку и привязку import в каждом импортирующем модуле по всему рабочему пространству, а перед любыми изменениями проверяет новое имя (настоящий идентификатор, а не ключевое слово). Два ограничения, о которых стоит знать: межфайловый индекс перестраивается на каждый запрос, а не кэшируется (для обычного проекта нормально, позже стоит ускорить), и файл, который сейчас не разбирается, пропускается, так что переименование не дойдёт до ссылок внутри файла, который сам сломан.

Посмотрите сами

Каждая диагностика содержит стабильный код, исправление в одну строку и часто причину в дизайне языка. glyph --explain печатает полную версию для любой из них:

glyph build 
[E0203] the `?` operator propagates error type `HttpError`,
        but this function returns `Result<_, string>`
   ╰─ Help: map the error first, e.g. `.map_err(...)`,
      so its `E` matches the function's.

Мы доработали сообщения именно там, где чаще всего спотыкаются агенты и новички: если написать if, вас теперь направят к match, а не выдадут общее «unexpected token», а неверное число аргументов, неполный match или опечатка в варианте получают каждый свою ошибку с кодом, которую можно исправить.

Ошибки типов, которые может поймать только бэкенд TypeScript, раньше указывали на сгенерированный .ts. Теперь они переносятся обратно на ваш .glyph (та же каретка ariadne, тот же стабильный код), так что ошибка tsc читается как родная ошибка Glyph.

Отладка: вы отлаживаете сгенерированный TypeScript инструментами, которыми уже пользуетесь, например инспектором Node, devtools браузера или отладчиком JS/TS в вашей IDE. Каждая сборка кладёт рядом с каждым .ts стандартную source map v3 (с встроенным исходником на Glyph), так что отладчик или бандлер, который сцепляет карты, возвращается к номерам строк вашего .glyph. Одно это пока не покрывает: собственный стек падения glyph run всё ещё печатает строки .ts, потому что tsx не протягивает карту через своё преобразование. Перенос этого стека следующий на очереди.

Узнать «компилируется ли это?», не запуская: glyph check path.glyph проверяет типы одного файла или целого каталога и завершается. Он ничего не пишет в ваше дерево, чего не мог обещать glyph run и чего вообще не делал glyph build (он отказывался работать со всем, что не каталог). Он выполняет тот же конвейер, что и сборка, включая tsc --strict по сгенерированному TypeScript, во временный каталог, который удаляет на выходе. --no-tsc останавливается после стадий Glyph, когда нужен быстрый ответ; --json даёт агенту ту же форму диагностик, что и glyph build --json. Файл проверяется в контексте своего каталога, так что сломанный соседний файл всё равно валит проверку. Ваши тесты @example и @doc @run тоже запускаются здесь, тот же гейт, что использует glyph build, так что проверка не может сообщить о чистом дереве, на котором упала бы сборка; --no-test их пропускает, когда нужен ответ, при котором ничего не выполняется.

Вывод тоже вам не врёт. Упавшая сборка раньше начиналась со строки «no diagnostics», а под ней печатала ошибки tsc, потому что сводка стадий Glyph писалась до того, как запускалась стадия TypeScript. Теперь сводка печатается после каждой стадии, которая может сделать сборку красной, так что в красной сборке никогда не бывает зелёной строки. Заодно заработал glyph run app.glyph --min -12.50: раньше из-за дефиса в начале clap отклонял аргумент ещё до того, как его видел ваш main. Флаги, которые принадлежат glyph, по-прежнему привязываются к glyph, поэтому ставьте -- перед флагом программы, который совпадает с одним из них.

А для агента в цикле: glyph build --json выдаёт каждую диагностику как структурированный JSON: стабильный код, серьёзность, сообщение, файл и диапазон строк и столбцов с единицы, плюс подсказку и примечание, включая ошибки tsc, перенесённые на ваш исходник Glyph. Агент читает их и действует по ним напрямую, а не выковыривает из текста терминала.

Для интерактивных агентов есть не только пакетные диагностики: glyph mcp запускает сервер Model Context Protocol через stdio (тот же бинарный файл, тот же анализ, что использует редактор) и предоставляет запросы языкового сервера как инструменты MCP. Агент может запросить диагностики файла, тип в позиции, где определено имя (с переходом по импортам), каждую ссылку на символ во всём проекте или поиск символов, не запуская полную сборку и не читая каждый файл. Это тонкий адаптер над тем же чистым слоем анализа, а не вторая реализация, так что он не может разойтись с тем, что видят компилятор и редактор.

Не всё является жёсткой ошибкой. В Glyph есть уровень предупреждений, который отмечает мёртвый груз, не валя сборку: неиспользуемый импорт (E0106), неиспользуемый let (E0107, кроме имён, начинающихся с _) и недостижимый код после return/break/continue (E0108). Они держат модуль в чистоте: мёртвый импорт это как раз тот шум, который мешает поиску и заставляет читателя искать зависимость, которой у кода на самом деле нет. Предупреждения появляются в том же отрисованном выводе и в выводе --json, помечены уровнем серьёзности, и TypeScript при этом всё равно генерируется.

Текущее состояние

Уже работает

Языковой сервер (glyph lsp через stdio, любой редактор; расширение для VS Code в комплекте) с подсветкой, диагностиками, наведением, переходом к определению, автодополнением, символами, поиском ссылок и переименованием по всему рабочему пространству и форматированием при сохранении, который с 0.1.124 отвечает через границу модуля: сервер держит одну базу данных на проект, где ваши открытые буферы наложены поверх файлов на диске, так что наведение на импортированную функцию или поле импортированной записи даёт тот же ответ, что и glyph query hover, несохранённая правка в одном файле видна из другого, а нажатие клавиши стоит на один-девять процентов больше, чем в однофайловом режиме; MCP-сервер glyph mcp с одиннадцатью инструментами, запросами редактора плюс glyph_symbol, glyph_impact, glyph_assignable, glyph_dependencies и glyph_exports, у каждого есть команда glyph query, печатающая тот же JSON для агента без MCP-клиента; стабильные коды ошибок, glyph --explain, ошибки бэкенда tsc, перенесённые на исходник .glyph, уровень предупреждений (неиспользуемый импорт или привязка, недостижимый код) и структурированные диагностики --json. glyph check [path] проверяет типы одного файла или дерева, не запуская его и не записывая вывод. glyph fmt --check проверяет форматирование в CI: ничего не пишет и завершается с ненулевым кодом, если файл ещё не в единственной канонической раскладке.

В работе

Кэширование межфайлового индекса вместо перестройки на каждый запрос (выигрыш в скорости на больших деревьях) и перенос собственного стека падения glyph run: tsx не протягивает сгенерированную карту через своё преобразование, поэтому этот стек всё ещё называет сгенерированный .ts, а не ваш .glyph.
