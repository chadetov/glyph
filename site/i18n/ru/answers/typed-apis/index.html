Нужно ли писать валидатор для каждого API вручную?

Нет. В Glyph тип сам является своим валидатором. Объявите type, и компилятор сгенерирует рядом с ним дескриптор для проверки во время выполнения, так что недоверенное тело запроса или ответа проверяется одним вызовом, без отдельной схемы zod, которую нужно писать и поддерживать в согласии с типом.

Почему это важно

В большинстве стеков на TypeScript каждый payload описан дважды: один раз как type для компилятора и ещё раз как рукописный валидатор, чтобы значение во время выполнения действительно имело эту форму.

Эти два описания расходятся, и именно через это расхождение проходят плохие данные. Glyph сводит их в одно объявление: тип порождает валидатор, поэтому они не могут разойтись.

Посмотрите сами

Объявите DTO один раз. Его дескриптор даёт .parse (проверить недоверенное значение и получить значение этого типа) и .is (type guard), и больше ничего писать не нужно:

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}
что вы не писали 
// No zod schema:
const NewTask = z.object({
  title: z.string(),
  done: z.boolean(),
});
// No drift between the type and
// the validator, because there is
// only one declaration.

// A bad body, {"title": 123},
// takes the Err arm. Only a
// well-formed body reaches Ok.

Типизированное значение после match

Значение можно и вынести наружу, а не делать всю работу внутри ветки.

api.glyph: значение выходит из match типизированным 
let task = match NewTask.parse(req.body) {
  Ok(t) => t,
  Err(issues) => { return bad_request(issues) },
}
task.titel   // E0210: type `NewTask` has no field `titel`; did you mean `title`?
с 0.1.45обобщённые типы: пока нет
Подробности как переносится тип и исключение для обобщённых типов

T.parse имеет тип Result<T, Array<Issue>>, а match, ветки которого согласованы, несёт их тип, поэтому let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, } даёт вам NewTask до конца функции, а имена полей проверяет Glyph, а не tsc на сгенерированном TypeScript. Это появилось в 0.1.45; до этого значение теряло тип, как только покидало match. Единственный parse, который всё ещё этого не делает, у обобщённого типа, потому что его дескриптор принимает проверку во время выполнения для каждого параметра типа.

Результат разбора это обычный Result

В Glyph T.parse возвращает тот же Result, что и любая функция языка, которая может завершиться ошибкой, поэтому его можно сразу вернуть, пропустить через map_err, чтобы превратить ошибки валидации в собственный тип ошибки, или пробросить через ?.

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}

Подробности цена Result во время выполнения

Валидатор, который возвращает значение в собственной закрытой форме, полезен только наполовину, потому что остальная обработка ошибок не может с ним работать. В результате разбора нет ничего особенного.

Раньше было иначе по одной причине: дескриптор генерируется рядом с вашим type, и голый объект в выводе избавлял модуль, объявляющий тип, от зависимости от std/result во время выполнения. Теперь этот компромисс решён в другую сторону. Модуль с pub type несёт импорт std/result, даже если нигде не пишет Result, а вызов parse выделяет те же замыкания комбинаторов, что и любой Ok(...). Взамен проверенная граница и остальная обработка ошибок пользуются одним API.

Свои комбинаторы: тип результата выводится, а не принимается на веру

infer_output<Shape> в Glyph выводит тип результата из формы, а tsc сверяет с ним вашу аннотацию. Форма, в которой нет поля заявленного типа, не компилируется:

schema.glyph 
fn object_schema<Shape: Record<string, Schema<unknown>>>(
  shape: Shape,
) -> Schema<infer_output<Shape>> { ... }

type User = { name: string, age: number }

// The shape must produce a User, or this
// line does not compile:
const user_schema: Schema<User> =
  object_schema({
    name: string_schema(),
    age: number_schema(),
  })
расхождение, которое убирает Glyph 
// TS/zod: shape and output type are two
// separate things you keep in sync by hand.
const s = z.object({ name: z.string() });
type User = { name: string; age: number };
// `s` is inferred { name }, but nothing
// checks it against User. The `age` you
// forgot is caught at runtime, if ever.

// Glyph: drop `age` from the shape and
// `Schema<User>` fails to compile. The
// shape is the single source of truth.
Подробности ловушка TypeScript и приведение, которое с 0.1.92 следует за return

Иногда нужен комбинатор в стиле zod: валидатор, собранный из меньших. Ловушка в TypeScript в том, что тип результата комбинатора и переданная ему форма расходятся. Вы пишете форму, потом повторяете её во втором параметре типа, и никто не проверяет, что они совпадают.

Выведенный тип сохраняется, как бы комбинатор ни возвращал значение. infer_output требует одного приведения на границе функции, потому что тело строит значение, про которое система типов не может доказать, что у него тип, выведенный из формы, и компилятор пишет это приведение за вас. До 0.1.91 включительно оно прикреплялось к простому return <value>. Стоило поставить match между return и значением или закончить тело на r?, и та же функция переставала компилироваться: TS2322 на сгенерированном TypeScript для кода на Glyph, который компилятор уже принял. Начиная с 0.1.92 приведение следует за самим возвратом, а не за его записью, поэтому return match strict { ... } проходит проверку типов так же, как запись того же тела с одним return.

Остальная недоверенная граница

Тот же дескриптор делает безопасным json.parse<T>: дайте ему строку JSON, и он за один шаг разберёт и проверит её.

ВводВызовВозвращает

Декодированное телоT.parse(value)Result<T, Array<Issue>>
Заголовокheader(req, name)Option<string>
Параметр запросаquery_param(req, name)Option<string>
Подробности тела запросов, заголовки и параметры запроса

Тело запроса приходит уже декодированным как unknown, поэтому там используется T.parse(value): та же гарантия, без приведения.

Остальная недоверенная граница типизирована так же: header(req, name) и query_param(req, name) возвращают Option<string>, поэтому отсутствующий заголовок или параметр запроса это None, и match заставляет его обработать. Уберите ветку None, и код не скомпилируется. Отсутствующий ввод нельзя прочитать так, будто он есть.

Проверяет ли словарь с ключами-перечислением свои ключи?

Да, с 0.1.148. Record<Tier, int> при type Tier = "free" | "pro" разбирает только объект, ключи которого ровно free и pro: и лишний ключ, и отсутствующий дают Err, и то же самое tsc говорит об этом объекте, записанном литералом.

Тип ключаЧто parse проверяет для каждого ключа
Union строковых литераловровно перечисленные ключи, без пропущенных и без лишних
Тип, уточнённый через whereпредикат

Подробности уточнённые и int-ключи и что пока остаётся за tsc

Для типа ключа, уточнённого через where, предикат выполняется на каждом ключе, а ключ int должен быть обычной записью целого числа, поэтому "01" и "1.5" отклоняются. Record<string, V> проверяется точно так же, как раньше. Собственная проверка Glyph по-прежнему оставляет ключи значения, написанного в коде, на tsc, а обобщённая запись с ключом по собственному параметру типа отклоняется, если этот параметр не string.

Если я разбираю дату, получу ли я настоящую дату?

Да, и интереснее всего, что вы получаете на вводе, который датой не является. time.parse_iso возвращает Option<number>, и это None для всего, что не ISO-8601.

принимается 
"2026-01-03"              // UTC midnight
"2026-07-25T18:33:08.000Z"
"2026-03-15T09:30:00-05:00"
"2028-02-29"              // a real leap day
None, для каждого из них 
"January 5 2026"   // not ISO
"2026-1-3"         // not padded
"2026-13-01"       // no month 13
"2026-02-31"       // no such day
"2026-02-29"       // not a leap year
"2026-01-03T10:00" // no offset

Последний случай удивляет людей больше всего, и в нём весь смысл. Дата со временем без Z и без смещения +HH:MM по грамматике ECMAScript считается локальным временем, поэтому если её принять, одна и та же строка будет означать разные календарные дни в зависимости от того, на какой машине запущена программа.

Подробности что вместо этого делает Date.parse и почему UTC

Это более сильное обещание, чем у Date.parse в JavaScript, который принимает произвольный текст ("January 5 2026"), читает дату без ведущих нулей вроде "2026-1-3" в том часовом поясе, в котором случайно работает процесс, и сообщает о несуществующем дне как об успехе, перенося его вперёд: "2026-02-31" становится 3 марта, и вы получаете число без всякого указания на то, что что-то произошло.

Календарные функции Glyph (time.year, time.month, time.day) работают в UTC и прямо это говорят, а валидатор, который незаметно подтягивает часовой пояс машины, заставил бы их врать. Поэтому строка отклоняется, и вы сами решаете, что она означала.

Проверка переехала в примитив

Когда приложение пишет проверку корректности вокруг примитива стандартной библиотеки, этой проверке место в самом примитиве. Вот что приложение удалило:

до: приложение охраняет стандартную библиотеку 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
после: примитив сам держит границу 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

Вместе с ней ушёл import std/regex. Тот же реестр, те же отклонённые строки, тот же отчёт байт в байт.

История приложение для отчётов о расходах, откуда это взялось

Это появилось при написании CLI для отчётов о расходах на Glyph. В каждой строке реестра есть дата, и записать строку не в тот месяц это та ошибка, которая имеет значение, поэтому приложение не доверяло старому parse_iso: сначала проверяло форму регулярным выражением, а потом переводило метку времени обратно в текст, чтобы поймать перенесённый день.

Типы можно даже не писать

Если форма уже описана в спецификации OpenAPI или в файле объявлений TypeScript, сгенерируйте из неё типы Glyph: настоящие закоммиченные объявления type, которые можно найти grep, у каждого свой дескриптор, а не выведенный фантом:

из спецификации OpenAPI / JSON Schema 
glyph gen openapi petstore.yaml \
  --out src/
из установленного пакета, по имени 
glyph gen dts api-types \
  --out src/types

Тип с провода становится проверенной границей, без единой рукописной строки:

webhook.glyph 
import types/api_types { Customer }

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),
  Err(issues) => reject(issues),
}

Генерация верна проводу: что спецификация говорит о значении, то parse и проверяет.

В спецификации или .d.tsСгенерированный Glyph

Поле integerint; 3.5 с провода не проходит

Подробности что материализуется сегодня, повторная генерация, обобщённые типы

Направьте glyph gen dts на файл .d.ts или, как выше, на установленный пакет из npm по имени: он находит собственную точку входа объявлений пакета в node_modules и записывает закоммиченные типы, которые вы импортируете.

Что материализуется сегодня: gen dts читает объявления interface и type, которые экспортирует пакет, включая те, что внутри дерева declare namespace (голые перекрёстные ссылки разрешаются через область видимости), и те, что лежат в соседних файлах, которые реэкспортирует barrel-файл index (обходится входной .d.ts и каждый .d.ts, импортированный по относительному пути). Обобщённый тип остаётся полноценным: interface Page<T> материализуется как type Page<T> и получает дескриптор, который проверяет каждый элемент как его аргумент типа, а не просто на наличие. Реэкспорты с псевдонимом и export * as разрешаются через карту привязок для каждого файла. Единственный случай, который нельзя сделать безопасным, имя типа, совпадающее в двух достижимых файлах, он помечает примечанием, а не молча привязывает не ту форму. Для всего, до чего материализатор не дотягивается, напишите вручную формы, с которыми пересекаете границу, или воспользуйтесь лазейкой extern_ts.

Повторная генерация идемпотентна, поэтому изменение спецификации даёт чистый дифф, который удобно ревьюить. Генерация верна проводу: строковый enum материализуется как union строковых литералов ("free" | "pro"), поэтому parse проверяет принадлежность, а не только то, что значение строка, и match по нему исчерпывающий без else. Поле integer становится int, поэтому 3.5 с провода не проходит parse, хотя обычное число прошло бы. Если у конструкции нет точной формы в Glyph (неразмеченный union), она сужается, и генератор выводит примечание, а не создаёт валидатор, который отклонял бы настоящие данные. Сгенерированные записи также несут @open, поэтому parse допускает поле, которое API добавит позже, и при этом проверяет каждое объявленное поле; схема с additionalProperties: false остаётся строгой. Записи в Glyph по умолчанию строгие, и это та же пометка в месте объявления, которую можно найти grep и которую использовала бы рукописная запись, так что смысл записи никак не меняется.

Обобщённые типы тоже проверяются. Paginated<T> получает дескриптор, чей parse принимает аргумент типа: Paginated.parse<User>(body) проверяет каждый элемент items как User, а не только на наличие, и match v { is Paginated<User> => ... } сужает так же. Это работает и через границы модулей: определите Paginated<T> в одном файле, import его в другой, и там Paginated.parse<User>(body) и is Paginated<User> по-прежнему проверяют каждый элемент как User. Компилятор строит проверку элемента из аргумента типа в месте вызова, поэтому в каком файле живёт обобщённый тип, на проверку не влияет.

Где это заканчивается: дескрипторы покрывают формы, из которых состоит большинство payload: объекты, примитивы, массивы, ссылки, необязательные и nullable-поля, а теперь и обобщённые типы с конкретными аргументами. Тип, который сгенерировал не Glyph (внешний пакет или .d.ts, который вы только импортируете), проходит проверку типов, но не несёт дескриптора, пока вы его не материализуете, а это теперь одна команда для установленного пакета (glyph gen dts <package>, для экспортируемых им интерфейсов и псевдонимов типов верхнего уровня). Эта граница намеренная: тип, который Glyph не сгенерировал, не может обещать проверку во время выполнения, поэтому вы включаете её для каждого пакета отдельно, а результат закоммичен и находится grep, а не возникает из ниоткуда при каждой сборке.

База данных тоже граница

Строка, прочитанная из базы данных, так же недоверенна, как тело запроса. Тот же .parse, что и для тела запроса, проверяет строку.

tasks.glyph 
type Task    = { id: int, title: string, done: bool }
type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.
match TaskRow.parse(row) {
  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}
ошибка, которую это убирает 
// TS, better-sqlite3 / node:sqlite:
const row = stmt.get(id) as Task;
// `row.done` is really 0 or 1, a number.
// Nothing complains. Then:
if (row.done === true) { ... }   // never runs

// The row was `unknown`; the cast invented
// a type. Glyph makes you validate the row
// into TaskRow, and the int-to-bool step is
// a line of code, not a silent lie.
Подробности std/sqlite и булево значение 0 или 1

Строка, прочитанная из базы данных, так же недоверенна, как тело запроса: схема базы и представление о строке в вашем коде могут расходиться, а приведение (row as Task) это скрывает. std/sqlite, модуль для работы с базой поверх встроенного SQLite в Node, на этом и построен. Запрос возвращает Array<Record<string, unknown>>, поэтому обращаться со строкой как с Task, не проверив её, нельзя.

Это ловит ошибку, которую постоянно выпускают в продакшен. В SQLite нет булева типа, поэтому столбец done возвращается как целое 0 или 1. Приведите строку к записи с полем bool, и task.done === true молча никогда не будет истинным. В Glyph форма хранения и форма предметной области это разные типы, а соответствие между ними занимает одну строку, которую видно:

Всё это есть в рабочем примере: examples/apps/tasks/main.glyph это API задач с сохранением, std/sqlite для хранения и std/http для маршрутов, с данными, которые переживают перезапуск, и проверкой и на стороне сети, и на стороне базы. Рукописных валидаторов в нём нет нигде.

Подписанный вебхук тоже граница

Для проверки подписи вебхука нужны ровно те байты, которые подписал отправитель, а не повторно сериализованная копия (если снова превратить разобранное тело в строку, изменятся пробелы и порядок ключей, и HMAC никогда не совпадёт). http.raw(req) отдаёт эти байты, поэтому проверка остаётся в Glyph: 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
Подробности сырые байты для подписи, разобранное тело для формы

req.body по-прежнему разобранное значение для проверки формы; raw это нетронутый payload, по которому вычисляется подпись. Получателю, который проверяет подпись и валидирует тело, рукописный TypeScript не нужен.

Тип может проверять свои инварианты, а не только форму

Проверка формы говорит, что поле это число. Она не говорит, что сумма неотрицательна или что оценка от 1 до 5. Уточнение where переносит этот инвариант в тип, и дескриптор обеспечивает его на границе:

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
что вы не пишете 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.

Дескрипторы

  • Каждая объявленная запись и размеченное объединение несут дескриптор для проверки во время выполнения (.parse, .is, .schema), включая обобщённые записиобобщённое размеченное объединение нет
  • .parse возвращает тот же Result, что и весь остальной язык, поэтому сочетается с map_err, с ? и с любой функцией, которая его возвращает
  • Уточнение where (int where value >= 0) проверяет на границе инвариант, а не только форму
  • json.parse<T> проверяет JSON
  • infer_output<Shape> выводит тип результата комбинатора из его формы, поэтому они не могут разойтись

Генерация

  • glyph gen openapi / glyph gen dts генерируют закоммиченные типы с дескрипторами из спецификации, из .d.ts или из установленного пакета по имени

Границы

  • std/sqlite возвращает строки как unknown, поэтому база данных становится такой же проверенной границей, как любая другая
  • Получатель подписанных вебхуков целиком остаётся в Glyph
    Подробности

    http.raw(req) даёт доступ к неразобранному телу запроса, поэтому подпись вебхука проверяется по точным байтам, и получатель подписанных вебхуков целиком остаётся в Glyph.

  • Недоверенный ввод не попадёт в SQL или shell без sanitize
    Подробности

    Типы Tainted/Trusted из std/taint не дают недоверенному вводу попасть в SQL или shell без явного sanitize, поэтому tsc отклоняет путь для инъекции при компиляции.

  • time.parse_iso принимает ISO-8601 и ничего больше
    Подробности

    Мелкие примитивы на границе держат ту же линию: time.parse_iso принимает ISO-8601 и возвращает None для произвольного текста, несуществующего дня и даты со временем без смещения, которую иначе прочитали бы в локальном часовом поясе машины.
