05 · Сравнение

Почему не просто строгий TypeScript + zod + eslint + ts-pattern?

Потому что каждая из этих гарантий включается по желанию, и агент может обойти любую из них одной строкой. Строгость Glyph это не конфигурационный файл, который агент может поправить. Это сам язык. Точка контроля смещается с «не забыли ли мы прогнать линтер по этому файлу» на «компилируется ли это».

Что уже даёт TypeScript с инструментами

Хорошо настроенный TypeScript заводит очень далеко, и если ваша команда гоняет всё это в CI, большинство пробелов, на которые нацелен Glyph, у вас уже закрыто. Это альтернатива, к которой стоит отнестись серьёзно, поэтому вот соответствие:

что уже даёт TypeScript с инструментами 
no `any`            → noImplicitAny + @typescript-eslint/no-explicit-any
exhaustive match    → ts-pattern .exhaustive() (compile-time, today)
errors as values    → neverthrow / Effect
runtime validation  → zod at every boundary
must-handle errors  → an eslint rule
deterministic diffs → Biome / Prettier

Если всё это у вас подключено и соблюдается, вы прошли большую часть пути. В TypeScript эти идеи есть. Язык, делая их обязательными, добавляет к ним три вещи.

01 Обязательное лучше необязательного

Конфигурация eslint защищает только тот код, который агент пропускает через неё, а агент может написать as unknown as User, @ts-ignore, // eslint-disable-next-line или просто забыть .exhaustive(), и это всё равно скомпилируется и будет смёржено. Каждая из этих лазеек это настройка, которую агент может поменять. В Glyph такой лазейки нет: нет as, нет прагмы игнорирования, нет способа получить типизированное значение из unknown без проверки, которую видит компилятор.

TypeScript: лазейки есть handler.ts 
const user = body as unknown as User;
// @ts-ignore
doThing(user.mispelled);
// eslint-disable-next-line
return anything as any;
Glyph: отключать нечего handler.glyph 
return match User.parse(body) {
  Ok(user) => use(user),
  Err(_) => fallback(),
}
// no `as`, no ignore pragma,
// no lint to switch off.

Строгость, которую агент не может отключить конфигурацией, находится в другой точке контроля, чем строгость, которую может. На этой разнице и построен Glyph.

02 Тип и есть валидатор: второго артефакта нет

zod переворачивает источник истины: вы пишете схему, выводите из неё тип, а потом вручную синхронизируете тип, схему и любой сериализатор. Именно при поддержании этого соответствия агент и вносит расхождение: переименовывает поле в типе, но не в схеме, и оба продолжают компилироваться. В Glyph тип и есть валидатор: объявление type User = {...} генерирует рядом User.parse. Один артефакт, нечего синхронизировать, нечего забыть.

03 Мутации, которые находит grep

В TypeScript изменение состояния может прятаться за =, .push(), Object.assign, сеттером или spread. Нет одного токена, который можно искать, и ни одно правило линтера это полностью не исправляет. В Glyph общее состояние живёт в store, и каждое изменение это буквальный .set(/.update(; grep 'mut ' находит каждую локальную мутацию. В обычном TypeScript аналога нет.

Разница в том, как всё ломается

Та же задача: агент добавляет вариант в union и забывает обработать его в одном из трёх мест:

TS с инструментами 
// ts-pattern .exhaustive() catches it,
// IF every site used ts-pattern and
// nobody wrote a default: case or a
// switch that only logs. Those
// compile green and skip the new case.
Glyph 
[E0200] non-exhaustive match on
`Feed`: missing variant `Archived`
// every unhandled match, everywhere,
// fails the build. No opt-in, no
// escape, no forgotten default.

В чём TypeScript с инструментами пока впереди

Четыре места, где сегодня он опережает Glyph:

  • Более богатая валидация. Дескрипторы Glyph по умолчанию строгие (они отклоняют необъявленные ключи), а уточнение where накладывает предикат на примитив (type Email = string where value.includes("@")), и дескриптор выполняет его на каждой границе, до которой доходит тип. zod всё ещё впереди в двух отношениях: в нём есть готовые проверки вроде .email() и .url(), которые в Glyph вы пишете сами, и он уточняет целые объекты, тогда как where на записи (lo <= hi по двум полям) сегодня даёт E0300.
  • Более глубокое сопоставление. Гарды и глубокие структурные паттерны ts-pattern выходят за пределы того, что выражает match в Glyph.
  • «Доказуемое отсутствие» заканчивается на границе .ts. Гарантии Glyph действуют для кода, написанного на Glyph; исключение, выброшенное зависимостью из npm, всё равно обходит Result, а у импортированного типа из .d.ts нет дескриптора для проверки во время выполнения.
  • Экосистема и найм. Инструменты, сообщество и рынок разработчиков TypeScript намного больше, и за ними годы использования в продакшене. Glyph это ранняя предварительная версия.

Если TypeScript с инструментами у вас подключён полностью и ваши агенты остаются внутри него, большая часть этого у вас уже есть. Довод Glyph в том, что вся нагрузка лежит на словах «остаются внутри», и именно их агент нарушает. Обязательность, валидация одним артефактом и мутации, которые находит grep, это то, чего не получить, добавляя новые необязательные инструменты.

Если вы готовы уйти с TypeScript на более старый типизированный язык, компилирующийся в JavaScript, страница Почему не ReScript, Gleam или Elm? сравнивает Glyph с ними.

Текущее состояние

Уже работает

Нет any/as, исчерпывающий match (E0200/E0218), предупреждение об отброшенном Result (E0217), валидаторы, сгенерированные из типов, и мутации, которые находит grep: всё обязательное, и ничто из этого не правило eslint, которое можно отключить.

Измеряется

Утверждение, что агенты допускают меньше ускользнувших дефектов в Glyph, чем в хорошо настроенном строгом TS, это бенчмарк, который мы строим, и сравнение идёт с TypeScript с инструментами, а не с наивным TS. Смотрите бенчмарки.
