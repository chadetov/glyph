Можно ли отдавать веб-страницу, или только JSON API?

Веб-страницу. std/http выставляет заголовки ответа, поэтому страница text/html, редирект 302, заголовок кэширования и отправка HTML-формы пишутся на обычном Glyph. Без Express и без рукописной прослойки на TypeScript.

Почему это важно

До 0.1.46 ответ был { status, body }, и сервер выбирал content type по форме тела: строка становилась text/plain, всё остальное JSON. Для API этого достаточно, а для всего, что отображает браузер, бесполезно.

Выход был один: написать свой сервер на node:http в рукописном файле .ts, и тогда весь путь запроса оказывался вне проверки типов. Из-за двух недостающих конструкторов приходилось отдавать целую границу приложения.

Обработчик возвращает Result

Обработчик возвращает Result<Response, string>, поэтому 404 это обычный Ok, а Err остаётся для того, на что приложение ответить не может, и сервер превращает его в 500.

serve остаётся в ожидании, пока слушает порт, поэтому ничего не нужно делать вручную, чтобы процесс не завершился, а неудачная привязка к порту возвращается как значение.

У каждого ответа есть заголовки

Response несёт обязательное поле headers: Record<string, string>. Именно обязательное, а не необязательное: его заполняет каждый конструктор, поэтому чтение resp.headers никогда не требует проверки на отсутствие, и про этот канал нельзя забыть.

  • Новый ответ, а не изменениеwith_header(resp, "cache-control", "no-store") возвращает новый ответ, а не изменяет существующий, потому что в Glyph нельзя изменять поля записи.
  • Проверяется в GlyphПроверка типов знает, что все три конструктора возвращают Response, поэтому обработчик с объявленным типом возврата Result<Response, string> проверяется в Glyph, а не tsc на сгенерированном выводе.

Две детали, которые вручную легко сделать неправильно

  • Значения заголовковЛюбой символ, который Node отказывается записать в заголовок, удаляется из значения на выходе, поэтому location, собранный из параметра запроса, не может внедрить второй заголовок или второй ответ, а эмодзи в сокращаемом URL не уронит сервер.
  • Тела формform(req) декодирует + как пробел вместе с процентным кодированием, а именно эту пару обычно упускает самописный разбор форм; он читает сырое тело, поэтому req.body остаётся нетронутым для обработчиков, которые разбирают его сами.

Текущее состояние

Уже работает

  • html, redirect, with_header, json, text и form
  • Заголовки ответа уходят в сеть, а content type выводится, только если вы его не задали
  • На входе доступны заголовки запроса, параметры запроса, сегменты пути и сырое тело
  • Клиент сообщает полученные заголовки ответа.

В работе

  • Процентное кодирование это пробел, который виден во фрагменте выше
    Подробнее

    Процентное кодирование это пробел, который виден во фрагменте выше: form декодирует тело формы, но encode_component для сборки URL нет, поэтому сокращатель пишет свою функцию.

  • На стороне клиента тоже не хватает таймаута, политики редиректов, head и итогового URL, на который привёл редирект.
  • Сервера статических файлов и шаблонизатора нет, и их не планируется.
