Доказательства

Как проверяется каждое утверждение на этом сайте

Утверждение, что Glyph что-то ловит, это пара программ в репозитории, одна на TypeScript и одна на Glyph, и проверка в CI запускает обе при каждом изменении. Если TypeScript перестаёт компилироваться или Glyph перестаёт отклонять программу, сборка падает. Любой случай можно запустить самому двумя командами.

Фикстуры

В каждом каталоге внутри catches/ лежат ts.ts, glyph.glyph и case.toml, где сказано, что делает каждый из них. scripts/check_catches.py работает в CI. Он требует, чтобы каждый ts.ts проходил tsc --strict, потому что программа на TypeScript, которая не компилируется, ничего не доказывает, а половину на Glyph проверяет в соответствии с видом случая. {{catches:breakdown}} По видам, которые проверяет гейт:

ВидСлучаиЧто гейт требует от Glyph
refused{{catches:refused-all}}Сборка падает с кодом из case.toml
warned{{catches:warned-all}}Сборка проходит и сообщает этот код как предупреждение
boundary{{catches:boundary-all}}Программа работает, а проверка на границе превращает плохие данные в Err
runtime{{catches:runtime-all}}Программа собирается, а затем останавливается при выполнении с указанным выводом
gap{{catches:gap-cases}}Glyph принимает программу, и она делает не то. Когда дыра закрывается, гейт падает и просит перенести случай

Случай, который перестаёт быть доказуемым, удаляется, а не смягчается, и README случаев перечисляет шесть удалённых и причины. Один из них, как оказалось, ловит и tsc; другой работал только потому, что его TypeScript принимал значение как any.

TypeScript, с которым идёт сравнение

Для каждого случая также указано, поймал бы ошибку полностью настроенный проект на TypeScript или нет; отсюда метка «поймал бы это TypeScript». «Полностью настроенный» означает tsc --strict плюс все опции, которые делают его строже, и прогон typescript-eslint. Гейт при каждом запуске заново устанавливает пакеты (TypeScript 6, eslint 9, typescript-eslint 8, tsx 4 и последний @types/node) и без сети падает, а не пропускает проверку.

опции tsconfig поверх strict 
noUncheckedIndexedAccess: true
noFallthroughCasesInSwitch: true
noUnusedLocals: true
noUnusedParameters: true
noImplicitReturns: true
noImplicitOverride: true
allowUnreachableCode: false
allowUnusedLabels: false
exactOptionalPropertyTypes: true
noPropertyAccessFromIndexSignature: true
eslint.config.mjs 
export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.strictTypeChecked,
  { rules: {
    "@typescript-eslint/switch-exhaustiveness-check": "error",
    "@typescript-eslint/strict-boolean-expressions": "error",
    "@typescript-eslint/require-array-sort-compare": "error",
    "require-atomic-updates": "error",
  } },
);

Метка случая это none, flag: плюс единственная опция, которая о нём сообщает, или lint: плюс правило. Если исправленная программа тоже задевает какое-то правило по посторонней причине, у случая есть ts_ok.ts, и метка учитывает только то, что срабатывает на ошибке. Например, non-exhaustive-match имеет метку lint:switch-exhaustiveness-check: typescript-eslint поймает его, если включить это правило, и страница так и говорит.

Воспроизведите один случай

Запустите гейт на одном случае из клона репозитория или сделайте это вручную. Обе половины non-exhaustive-match в том виде, в каком их запускали для этой страницы:

гейт, один случай 
$ python3 scripts/check_catches.py non-exhaustive-match
catches: 1/1 cases hold every claim they make.
TypeScript checked with tsc --strict and the full flag set (typescript 6.0.3),
typescript-eslint 8.73.0 strictTypeChecked on eslint 9.39.5, run with
tsx 4.23.15, and @types/node 26.6.6.
половина на TypeScript, вручную 
$ npm i -D typescript@6 tsx@4
$ npx tsc --strict --noEmit ts.ts
$ echo $?
0
$ npx tsx ts.ts
finished
archived logged nothing
половина на Glyph, вручную 
$ glyph check --no-tsc catches/non-exhaustive-match
[E0200] Error: typecheck: non-exhaustive match
  on `"todo" | "doing" | "done" | "archived"`:
  missing variants "archived"
glyph check: 1 error(s) across 1 module(s)

Фрагменты кода на этом сайте компилируются

scripts/check_docs_compile.py работает в CI и компилирует каждый самостоятельный фрагмент Glyph на сайте (он начинается с module и что-то объявляет), а также фрагменты в документации и в llms.txt. Фрагмент, который должен падать, обязан назвать ошибку, которую вызывает, и вызывать ровно её. Фрагменты, которым нужен React или пакет из npm, компилируются с настоящими типами этих пакетов. Неполные фрагменты подсчитываются и пропускаются, а их число печатается, чтобы доля пропущенных оставалась на виду.

Что он пока не ловит

Случаи вида gap ({{catches:gap-cases}}) есть на странице случаев, у каждого свой номер gap. Каждая дыра, найденная при написании приложений на Glyph, есть в реестре docs/dogfooding-gaps.md, где единственный живой статус это пометка в квадратных скобках ([FIXED], [HALF FIXED] или никакой для открытых), а scripts/check_gaps.py валит CI, если открытая запись последний раз воспроизводилась больше пяти выпусков назад.

Как выпуск получает пометку Breaking

Выпуск помечается как Breaking, если он отклоняет программу, которую принимала предыдущая версия. Это решается так: пишется самая маленькая затронутая программа, она запускается под опубликованным предыдущим выпуском и под новым бинарным файлом, и сравниваются коды завершения. Из формулировок заметок это не выводится. Выпуски до 0.1.99 так никогда не проверялись, поэтому выпуск без пометки не проверен, а не безопасен. Записи есть на странице версий.
