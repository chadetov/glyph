Если вы пишете на TypeScript

Что меняется, если вы уже пишете на TypeScript

Меньше, чем можно ожидать. Glyph компилируется в TypeScript, который проходит tsc --strict, сохраняет npm и ваш деплой и читается почти так же. Отличий немного, и каждое заменяет способ ошибиться проверкой, которую делает компилятор.

Если вы знаете TypeScript, большую часть вы уже знаете

Новый язык учить не нужно, только эти четыре вещи. Они встречаются в каждом примере на этом сайте.

match
Исчерпывающий switch: для union компилятор заставляет обработать каждый вариант. Это ещё и единственная условная конструкция: нет ни if/else, ни тернарного оператора, объяснение ниже.
Result<T, E>
Ошибки как возвращаемые значения, а не брошенные исключения. Ошибку обрабатывают через match или передают выше оператором ?.
fn f() -> T
Функция; -> обозначает её возвращаемый тип. type X = {...} это запись, а type X = A | B размеченное объединение.
mut x = e
Переприсваивание явное, и его легко найти поиском. Обычная привязка let никогда не меняется у вас за спиной; чтобы изменить её, пишут mut.

«Агенты» на этом сайте означают ИИ-ассистентов для программирования, таких как Claude, Copilot и Cursor. Им Glyph помогает больше всего, но проверки одинаковы, кто бы ни написал код: человек или модель. Если вы уже используете строгий TypeScript с zod и eslint, вот что добавляет к этому язык.

Здесь нет if

Ветвление по булеву значению это match по true и false. Если действие нужно только в одном случае, другая ветка это пустой блок.

TypeScript 
function label(admin: boolean): string {
  return admin ? "admin" : "member";
}

if (verbose) {
  console.log("starting");
}
Glyph 
fn label(admin: bool) -> string {
  return match admin {
    true => "admin",
    false => "member",
  }
}

match verbose {
  true => io.println("starting"),
  false => {},
}

Причина в решении D3 из спецификации: одна конструкция для ветвления по значению, поэтому есть одна форма, которую нужно читать, писать и искать. Значение, полученное из ветвления, всегда получается из match, тип результата которого вычисляет собственная проверка Glyph, а не tsc. Для union та же конструкция обязана покрыть все варианты (E0200). Для булева значения выигрыш небольшой, ведь false => {} говорит не больше, чем отсутствие else.

У этого есть цена. Тернарный оператор в одну строку превращается в match на четыре строки, ранний возврат по условию становится match с пустой веткой, и это первое, что кажется странным читателю с опытом TypeScript. Спецификация записывает многословность как принятую цену. Если всё же написать if, будет ошибка E0006, подсказка к которой показывает форму с match; тернарный оператор даёт E0013 с той же подсказкой.

Налог, который вы уже платите

Если вы разрабатываете с ИИ-агентами на кодовой базе TypeScript, вот ваши ежедневные издержки. На каждую в Glyph есть конкретный ответ, ссылки в списке.

  • Агенты выдумывают API, потому что TypeScript стирает типы и среда выполнения перестаёт совпадать с тем, что было при компиляции. Типы Glyph несут проверку во время выполнения (T.parse, T.is), см. типизированные API.
  • Агенты замазывают неуверенность через any и as unknown as T, и компилятор им это позволяет. В Glyph нет ни того, ни другого, см. таблицу ниже.
  • Вы просите изменить одну строку и получаете переписанный файл, потому что форматтер каскадно меняет всё при каждой правке. У glyph fmt одна раскладка без опций, см. чистые диффы.
  • Рядом с каждым типом вы держите рукописный валидатор (zod и сериализатор), а агент переименовывает поле в одном месте, но не в остальных; и всё это по-прежнему компилируется. В Glyph тип и есть валидатор.
  • Вы ищете символ через grep и находите десяток посторонних совпадений: перегрузки, декораторы, слитые namespace. В Glyph ничего этого нет, см. поиск по коду.

Выключатели проверок в TypeScript и что вместо них в Glyph

Каждая конструкция TypeScript ниже велит проверке типов перестать проверять. Ни одна из них не является синтаксисом Glyph. В средней колонке то, что glyph check --no-tsc напечатал для каждой на 0.1.149.

У glyph check есть флаги, которые пропускают целый проход (--no-tsc пропускает запуск tsc --strict, --no-test пропускает тесты @example), но нет флагов, глушащих отдельную проверку. Одна лазейка, и её можно найти grep

Когда нужен TypeScript, который Glyph не может выразить, extern_ts("...") принимает один встроенный тип или выражение, и tsc всё равно его проверяет. Для целого модуля положите .ts в src/extern/ и напишите import extern/name; относительные импорты в остальном запрещены, так что это единственный путь. Обе формы содержат слово extern, поэтому grep -rn extern src/ показывает все места, где проверка передаёт управление TypeScript.

src/clock.glyph 
module clock

pub fn now_ms() -> number {
  return extern_ts("Date.now()")
}

Как выглядит сгенерированный TypeScript

Обычный TypeScript, по файлу на модуль, который можно читать и коммитить. Union превращается в размеченное объединение плюс значение с проверкой во время выполнения, а match становится switch по тегу. Это вывод glyph build для модуля слева, без строк импорта.

plan.glyph 
module plan

pub type Plan = Free | Pro | Team

pub fn seats(p: Plan) -> number {
  return match p {
    Free => 1,
    Pro => 5,
    Team => 50,
  }
}
plan.ts (сгенерирован, сокращён) 
export type Plan =
  | { tag: "Free" }
  | { tag: "Pro" }
  | { tag: "Team" };

export const Free: Plan = { tag: "Free" };
export const Pro: Plan = { tag: "Pro" };
export const Team: Plan = { tag: "Team" };
export const Plan = {
  is(value: unknown): value is Plan { ... },
  parse(value: unknown) { ... },
  schema: ...,
};

export function seats(p: Plan): number {
  const __m0 = p;
  switch (__m0.tag) {
    case "Free": { return 1; }
    case "Pro": { return 5; }
    case "Team": { return 50; }
    default: throw new Error("non-exhaustive match");
  }
}

Удалите ветку Team, и сборка остановится до того, как будет записан хоть какой-то TypeScript:

Если вы перестанете использовать Glyph, у вас останется сгенерированный .ts. У него нет зависимостей во время выполнения, кроме небольшого каталога поддержки, который сборка кладёт рядом.

npm и TypeScript, который у вас уже есть

Модуль .glyph импортирует пакет из npm по имени (import kafkajs { Kafka }) с типами из деклараций самого пакета, а ваш существующий .ts импортирует сгенерированные модули Glyph как любой локальный файл.
