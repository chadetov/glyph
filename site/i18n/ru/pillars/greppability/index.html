Принцип 02 · Основа

Удобство поиска

Одно имя, одно место. У каждого символа ровно одна синтаксическая форма в месте объявления, поэтому обычный grep всегда находит определение, без индекса, без языкового сервера и без везения.

Почему на вопрос «где это определено?» трудно ответить

В зрелой кодовой базе на TypeScript самый простой вопрос, откуда взялось это имя?, часто оказывается самым трудным.

Подробнее перегрузки, декораторы, слияние, дополнение модулей, barrel-файлы

Язык предлагает полдюжины способов размазать один символ по многим местам: перегрузки делят функцию на несколько сигнатур, декораторы оборачивают её во что-то другое, слияние namespace и interface разбрасывает тип по файлам, declare module дополняет чужой код, а barrel-файлы index.ts реэкспортируют всё подряд, так что путь импорта не совпадает с местом, где что-то на самом деле лежит.

Человек справляется с помощью LSP и мышечной памяти. Агент ищет grep: он читает репозиторий как текст, и каждая из этих конструкций это место, где текст врёт о том, где находится код.

Glyph их убирает. В результате поиск становится надёжным примитивом, а не эвристикой.

01 Одно объявление, одна форма

Функция, тип или компонент объявляются ровно один раз, одним синтаксисом. Нет перегрузок, которые делят сигнатуру, и нет способа объявить имя повторно: две сущности верхнего уровня с одним именем дают жёсткую ошибку (E0100).

E0100

Ключевое слово объявления входит в искомое имя. grep "fn parseUser" не может совпасть с вызовом, импортом или реэкспортом, только с единственным местом, где имя определено.

Так что у поиска определения ровно один ответ.

02 Нет barrel-файлов: путь импорта и есть расположение

Импорты в Glyph никогда не реэкспортируются, а модуль, который состоит только из импортов, отклоняется (E0102). Слоя index.ts, который отмывает происхождение, нет.

импорт точно говорит, куда смотреть 
import myapp/users { parseUser }
//     ^^^^^^^^^^^ the file is src/myapp/users.glyph.
//     not a re-export of a re-export of a barrel.
E0102

Поэтому импорт называет модуль, где символ действительно лежит: путь и есть адрес.

03 Нет скрытых способов прицепить поведение

Нет декораторов, оборачивающих функцию в невидимый слой, нет слияния namespace, собирающего члены со всего дерева, нет declare module, дополняющего сторонний тип из файла, который вы бы никогда не открыли, и нет неявного this, меняющего то, на что ссылается метод.

Имя разрешается в одно объявление, и всё, что его формирует, видно в этом объявлении.

04 Даже изменения можно найти grep

Удобство поиска касается не только поиска определений, но и поиска эффектов. Общее состояние живёт в std/store, и каждое его изменение это буквальный вызов .set( или .update(.

$ grep -rn 'tasks\.\(set\|update\)' src/ 
src/tasks.glyph:16:  tasks.update(fn(cur) { ... })
src/tasks.glyph:24:  tasks.set([])
# every place the task list can change, enumerated.
# nothing hides in an ordinary `x = ...` elsewhere.

Поэтому один поиск перечисляет всю поверхность записи для этого состояния, и не нужно выискивать присваивания, разбросанные по файлу.

Кодовая база удобна для поиска, когда её текст говорит правду о её структуре. Каждое ограничение здесь (одна форма на имя, никаких реэкспортов, никакого слияния) нужно для того, чтобы поиск возвращал ответ, а не зацепку.

Бенчмарк: скоро

Измеримая версия этого утверждения это точность: какая доля совпадений обычного grep для данного символа оказывается тем, что вы искали, и за сколько шагов агент добирается до определения?

Пока не измерено Мы сообщим точность grep и число шагов до определения на реальной кодовой базе на Glyph, как только такая появится, и опубликуем числа здесь, какими бы они ни оказались.

Выигрыш растёт с масштабом и с автономностью. Человек узнаёт, где в кодовой базе что спрятано; агент, начинающий с нуля, этого не знает. Удобство поиска позволяет инструменту (или новому коллеге) ориентироваться, просто читая репозиторий таким, какой он есть.

«Правило линтера может запретить перегрузки и декораторы»

В вашем собственном репозитории да. ESLint может запретить namespace, а команда может договориться не использовать перегрузки.

Язык всё равно всё это позволяет, так что гарантия живёт, пока живёт конфигурация, и покрывает только код, на котором она запускается. grep по зависимости, сгенерированному файлу или чужому репозиторию не может на неё рассчитывать.

В Glyph этих конструкций нет, поэтому grep работает одинаково на любом файле Glyph, включая те, которые никто из вашей команды не настраивал.

Как это выглядит со стороны агента, когда определение или каждая запись в значение находится одним поиском, разобрано в ответе Может ли агент (или я) найти, где что определено?
