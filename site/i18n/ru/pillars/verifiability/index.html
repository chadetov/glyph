Принцип 01 · Основа

Проверяемость

Glyph закрывает дыры, в которые проваливается агент: нет any и нет as, которые можно написать, match доказуемо исчерпывающий, а объявленные типы получают строгие валидаторы для времени выполнения, и всё это обеспечивается строгим слоем поверх tsc. Сам он проверяет не всё, и ниже прямо сказано, где именно кончается гарантия.

Ложь, которую может сказать тип

В TypeScript тип это обещание времени компиляции, которое испаряется до запуска кода. Аннотация User стирается в ничто; объект, который вы на самом деле получаете из сетевого вызова, разбора JSON или поля формы, может иметь любую форму. Хуже того, язык даёт три законных способа соврать проверке типов: any, приведение as и non-null !. Агент, работающий быстро, хватается за все три, а tsc --strict остаётся зелёным, пока ошибка уходит в продакшен.

Первая задача Glyph закрыть эти дыры. Не большим числом аннотаций, а удалением лазеек и тем, что каждый тип несёт своё доказательство до времени выполнения. Вот что это значит, по одной гарантии за раз.

01 any нет

any самое дорогое ключевое слово в TypeScript: оно выключает систему типов для значения и для всего, чего это значение касается. Один any на границе незаметно отравляет весь граф вызовов ниже. В Glyph его нет. Верхний тип это unknown, а unknown инертен: его нельзя вызвать, индексировать или передать куда-либо типизированное, пока вы не доказали, что это такое.

TypeScript: компилируется, а потом падает handler.ts 
function handle(body: any) {
  // tsc --strict: fine.
  // runtime: throws on {}.
  return body.user.name.toUpperCase();
}
Glyph: сужение типа и есть доказательство handler.glyph 
fn handle(body: unknown) -> string {
  return match User.parse(body) {
    Ok(u) => string.upper(u.name),
    Err(_) => "unknown",
  }
}

Получить типизированное значение из unknown без проверки, которую видит компилятор, нельзя. В Glyph сужение типа и есть доказательство во время выполнения. Синтаксиса, чтобы его пропустить, нет.

02 Типы существуют во время выполнения

Откуда берётся User.parse? Каждый тип записи и каждое необобщённое размеченное объединение генерирует рядом с собой дескриптор для времени выполнения: guard is, функцию parse, которая валидирует unknown в Result, и составную schema. Форма записи действительно проверяется во время выполнения, а не предполагается, так что проверка is User настоящая, а не стёртая пустышка.

тип, который вы пишете, и дескриптор, сгенерированный из него 
type User = {
  id: number,
  name: string,
  email: string,
}

// generated: User.is(v), User.parse(v) -> Result<User, ...>, User.schema

fn create(req: Request) -> Result<Response, string> {
  return match User.parse(req.body) {   // untrusted input, validated
    Ok(user) => Ok(json(201, user)),
    Err(issues) => Ok(json(400, issues)),
  }
}

Это ответ на «для каждого API нужен рукописный валидатор». Тип и есть валидатор. Граница (тело запроса, файл конфигурации, ответ стороннего сервиса) становится типизированной только после проверки, которая действительно может отклонить плохие данные.

Где это заканчивается: дескриптор записи по умолчанию строгий. Он подтверждает объявленные поля и отклоняет значение с необъявленными ключами (поставьте на тип @open, чтобы разрешить лишние). Дескриптор получают типы записей, включая обобщённые, так что Paginated<User> проверяет каждый элемент как User, а дескриптор размеченного объединения проверяет тег, а затем поля данных этого варианта. Дескриптора всё ещё нет у обобщённого размеченного объединения (у Box<T> = Empty | Full({ value: T }) нет Box.parse) и у типа, импортированного из .d.ts, на который вы только ссылаетесь. Где проверка может доказать только часть формы, компилятор так и говорит, а не намекает на гарантию, которую не может дать.

03 Все варианты, иначе не компилируется

match по закрытому union обязан обработать каждый вариант. Добавьте вариант позже, и каждый match, который его не учёл, перестанет компилироваться (E0200). Новый вариант не может молча провалиться в undefined, как это бывает с забытой веткой switch. И это касается не только union: сопоставление number или string с литералами требует else (E0218), потому что эти множества не ограничены и набор литералов никогда не будет полным.

status.glyph 
type Status = Active | Paused | Cancelled

fn label(s: Status) -> string {
  return match s {
    Active => "on",
    Paused => "hold",
    // forgot Cancelled...
  }
}
ошибка компиляции, а не undefined во время выполнения $ glyph build 
[E0200] non-exhaustive match on
`Status`: missing variant `Cancelled`

# the equivalent TS switch returns
# undefined at runtime and compiles
# clean. here it does not build.

04 Ошибки это значения, а не сюрпризы

Функция, которая может завершиться ошибкой, возвращает Result<T, E>. Его обрабатывают через match или передают выше оператором ?, и тип ошибки должен совпадать (неявного преобразования, скрывающего несовпадение, нет). Если полностью проигнорировать Result (вызвать ради эффекта и выбросить результат), Glyph предупредит (E0217), потому что отброшенная ошибка это проглоченный сбой. Заглушить предупреждение можно только намеренно, через let _ = ..., но никогда случайно.

pipeline.glyph 
fn load(id: string) -> Result<User, AppError> {
  let raw = fetch_user(id)?           // Err short-circuits to the caller
  let user = User.parse(raw.body)?    // validation Err propagates too
  return Ok(user)
}

fn main() -> number {
  save(user)   // E0217: this returns a Result whose Err is dropped
  return 0
}

05 Даже персональные данные на уровне типов

Тот же подход «пусть это будет работой компилятора, а не соглашением» доходит до чувствительных данных. Поставьте @redact на тип, и его дескриптор получит redact(), который маскирует эти поля, так что случайный json.stringify(User.redact(u)) не сможет их слить. Если назвать поле, которого у типа нет, будет ошибка компиляции (E0219), а не маскировка, которая молча ничего не защищает.

patient.glyph 
@redact fields: [diagnosis, notes]
type Patient = {
  name: string,
  diagnosis: string,
  notes: string,
}

// json.stringify(Patient.redact(p)) ->
// {"name":"Ada","diagnosis":"[REDACTED]","notes":"[REDACTED]"}

Пять разных видов сбоев (непроверенный ввод, пропущенный вариант, отброшенная ошибка, утёкший секрет, невалидированный ключ), и в каждом исправление одинаковое: компилятор отказывается притворяться.

Как это обеспечивается и где кончается гарантия

Скажем точно, потому что разница важна: Glyph это строгий, принудительный диалект поверх tsc, а не независимый верификатор. Некоторые вещи он доказывает сам: исчерпываемость, тип ошибки для ?, отсутствие any/as в вашем исходном коде, валидацию строгих ключей. Остальную совместимость типов он обеспечивает, генерируя TypeScript и запуская tsc --strict, который валит сборку. Суть в том, что эти проверки это язык, а не опциональный линтер, который агент может отключить, и вовсе не в том, что Glyph заново реализует проверку типов.

Два прежних ограничения здесь закрыты в 0.1.10. Раньше эмиттер вставлял приведение возвращаемого значения, проверенное Glyph, а не tsc, в каждую обобщённую функцию; теперь оно появляется только там, где комбинатор валидатора собирает значение типа, выведенного из формы (infer_output<Shape>), а каждая честная обобщённая функция генерируется вообще без приведения. И выходному типу валидатора больше не доверяют на слово: infer_output выводит его из переданной формы, а tsc сверяет с ним вашу аннотацию: форма, в которой нет поля заявленного типа, теперь не компилируется.

Обобщённые типы теперь тоже валидируются глубоко: дескриптор Paginated<User> проверяет каждый элемент как User, а не только его наличие. Остаётся одно ограничение, назовём его прямо: импортированный тип из внешнего .d.ts, на который вы только ссылаетесь, не имеет дескриптора, пока вы не материализуете его через glyph gen dts, поэтому у поля такого типа проверяется наличие, а не форма. Эта граница намеренная (тип, который сгенерировал не Glyph, не может обещать проверку во время выполнения), и материализация её закрывает.

Это утверждение эмпирическое, поэтому мы собираемся его измерить: взять корпус реальных изменений, написанных агентами, прогнать каждое через tsc --strict и через Glyph и посчитать, что на самом деле ловит каждый. Ничего из этого не покупается церемониями. Нет аннотаций доказательств, нет контрактов, нет верификатора, которого нужно удовлетворить. Код выше это обычный Glyph. Проверяемость не функция, которую включают; это то, что остаётся, когда способов соврать больше нет.

«Строгий TypeScript и конфиг линтера это и так делают»

Внутри программы они подходят близко. strict, noUncheckedIndexedAccess и правило против явного any ловят большую часть того, что агент иначе пропустил бы. Останавливаются они на границах. JSON.parse(body) as User компилируется при любых настройках, а обычное исправление, схема zod, это второе описание User, которое приходится вручную держать в согласии с первым. В Glyph тип и есть валидатор: json.parse<User>(body) проверяется по самому User, а тип, который Glyph не может проверить во время выполнения, отклоняется, а не принимается на веру.

Другая разница в том, кто может на это полагаться. Конфиг линтера это выбор одного репозитория. Агент, открывший незнакомую кодовую базу на TypeScript, не может считать, что any там запрещён; в Glyph его нельзя написать нигде.

Та же гарантия в виде ошибок, которые делает агент, и сообщений, которые их останавливают, разобрана в ответе Что мешает агенту незаметно сломать мой код?
