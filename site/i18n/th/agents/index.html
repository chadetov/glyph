สำหรับเอเจนต์และคนสร้างเครื่องมือ

อินเทอร์เฟซของคอมไพเลอร์สำหรับเอเจนต์

เอเจนต์ถามคอมไพเลอร์ของ Glyph ได้ว่าสัญลักษณ์คืออะไร การแก้จะทำอะไรพัง และทำไม build ล้มเหลว แล้วได้คำตอบเป็น JSON glyph mcp ให้บริการสิบเอ็ดเครื่องมือผ่าน stdio แต่ละตัวเป็นคำสั่งย่อยของ glyph query ด้วย และ glyph llms พิมพ์เอกสารอ้างอิงภาษาแบบออฟไลน์

ตั้งค่า

glyph init เขียน .mcp.json นี้ลงในโปรเจกต์ใหม่ และ glyph agents เขียนมัน (พร้อม AGENTS.md ที่ชี้ไปที่ glyph llms) ลงในโปรเจกต์ที่มีอยู่แล้ว MCP client ไหนที่อ่านไฟล์นี้ก็จะเปิดเซิร์ฟเวอร์เอง ไม่มี port และไม่มี daemon

.mcp.json ตามที่ glyph init เขียน 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp"]
    }
  }
}

การเรียกหนึ่งครั้ง พร้อมคำตอบจริง

ไฟล์หนึ่งอ่าน field ที่ record ของมันไม่ได้ประกาศไว้ (u.naem) เอเจนต์เรียก glyph_diagnostics และได้ diagnostic ของคอมไพเลอร์เอง พร้อม field ที่ record ประกาศไว้จริงและ record ที่เป็นเจ้าของ นี่คือ output ของเครื่องมือบน 0.1.149 ตัดเฉพาะจุดที่ทำเครื่องหมายไว้

request 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": {
      "path": "src/user.glyph"
    }
  }
}
ผลลัพธ์ 
{
  "diagnostics": [ {
    "code": "E0210",
    "severity": "error",
    "stage": "typecheck",
    "message": "type `U` has no field
      `naem`; did you mean `name`?",
    "alternatives": ["name", "email"],
    "alternatives_kind": "fields",
    "cause": "user::U",
    "entity": "user::greet",
    "file": "user.glyph",
    "range": {
      "start": { "line": 9, "col": 10 },
      "end": { "line": 9, "col": 16 } },
    ...
  } ],
  "member": true,
  "module": "user",
  "not_run": [
    { "what": "tsc", ... },
    { "what": "E0104, ...", ... },
    { "what": "E0400, ...", ... } ],
  "path": "src/user.glyph",
  "project_root": "src",
  "unindexed": []
}

not_run บอกว่าการตรวจครั้งนี้ไม่ได้ครอบคลุมอะไร list diagnostics ที่ว่างจึงไม่ถูกเข้าใจผิดว่าเป็น build เต็ม ถ้าไม่มี MCP client glyph query diagnostics --path src/user.glyph ก็พิมพ์ JSON เดียวกัน รายการเครื่องมือทั้งหมดพร้อมทุกคำสั่งย่อยอยู่ในหน้า MCP

ก่อนแก้: จะทำอะไรพัง?

examples/apps/csvql เป็น query engine สำหรับ CSV สิบเอ็ดไฟล์ ที่มี union สี่ case ชื่อ Value เมื่อถามว่าการเพิ่ม case ที่ห้าจะมีผลอย่างไร glyph_impact แสดง match 10 จุดใน 4 ไฟล์: WILL_FAIL 8 จุด และ ABSORBS 2 จุด ซึ่ง arm แบบ catch-all จะกลืน case ใหม่ไปและยังคอมไพล์ผ่าน เมื่อเพิ่ม case จริงๆ ได้ error E0200 8 ตัวพอดี ที่ 8 จุดนั้น 2 จุดที่กลืนไปจะเงียบ ซึ่งเป็นเหตุผลที่คำตอบต้องระบุชื่อมัน

คำถามเดียวกันบน command line 
glyph query impact --path value.glyph --entity value::Value \
  --change add_variant --variant Blob

หลัง build แดง: การแก้ต้องรักษาอะไรไว้?

glyph check --agent พิมพ์ diagnostic ของ check --json โดยเพิ่ม key อีกสองตัวในแต่ละข้อ constraints แสดงสิ่งที่การแก้ต้องไม่ทำพัง สำหรับคำผิดข้างบนจะอ่านได้ว่า "the record's fields are closed: user::U declares name, email and no others" symbols ถือคำตอบของ glyph_symbol สำหรับทุกสัญลักษณ์ที่ diagnostic อ้างถึง การแก้ครั้งถัดไปจึงไม่ต้องเรียกซ้ำ ในกรณีที่วิธีแก้ถูกกำหนดไว้ชัดเจน glyph fix จะเขียนให้

อ่านภาษาแบบออฟไลน์

glyph llms พิมพ์เอกสารอ้างอิงภาษา และ /llms.txt บนเว็บนี้คือเอกสารเดียวกัน glyph llms --json คือความรู้ชุดนั้นในรูปข้อมูล อ่านจากตารางของคอมไพเลอร์เอง: รหัส diagnostic 77 ตัว ชื่อใน prelude 24 ชื่อ stdlib 40 module ที่มี export 340 ตัว decision ของภาษา 49 ข้อ และเครื่องมือสิบเอ็ดตัว glyph llms --negative คืนโปรแกรมที่ผิด 117 ตัวใน 0.1.149 (139 ตัวตั้งแต่รุ่นถัดไป) พร้อมรหัสที่แต่ละตัวได้ คอมไพล์เมื่อคุณขอ scripts/check_llms_sync.py จะ fail เมื่อตาราง diagnostic และคำสงวนในเอกสารอ้างอิงไม่ตรงกับของคอมไพเลอร์

จุดเริ่มต้นแบบออฟไลน์ 
glyph llms                  # the reference, as prose
glyph llms --json           # the same, as data from the compiler's tables
glyph llms --negative E0200 # wrong programs that draw E0200
glyph --explain E0200       # the long explanation of one code
