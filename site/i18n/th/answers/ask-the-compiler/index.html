22 · ถามคอมไพเลอร์

เอเจนต์ของฉันถามคอมไพเลอร์ได้ไหมว่าสัญลักษณ์คืออะไร ก่อนเขียนโค้ด?

ในการเรียกครั้งเดียว glyph_symbol รับ module::name ที่ diagnostic พิมพ์ไว้แล้ว หรือตำแหน่งในไฟล์ แล้วตอบด้วย field ของ record พร้อม type, variant ของ union พร้อม payload และ syntax ที่ใช้สร้างแต่ละตัว, parameter และ return ของสิ่งที่เรียกได้, member ของ interface และ match บนมันต้องครบทุกกรณีหรือไม่

ในหน้านี้

  1. ทำไมเรื่องนี้สำคัญ
  2. ทุก null บอกเหตุผล
  3. Assignable
  4. dependency และ export
  5. สิบเอ็ดเครื่องมือ
  6. สถานะตอนนี้

ทำไมเรื่องนี้สำคัญ

เอเจนต์ที่ถูกขอให้จัดการ case ใหม่ใน union ที่มันไม่ได้ประกาศเองต้องรู้ว่า variant ถืออะไรไว้ การอ่าน declaration หมายถึงต้องหาไฟล์ก่อน

คอมไพเลอร์มี payload อยู่ตลอด เครื่องมือทิ้งมันไปหนึ่งบรรทัดก่อนตอบ

ที่มา สิ่งที่การค้นหาสัญลักษณ์เคยคืนให้

การค้นหาสัญลักษณ์เคยให้แค่ชื่อและช่วงไบต์ และรายการ variant เคยให้แค่ ["Pending", "Paid", "Cancelled"] จากตรงนั้นเอเจนต์เขียน Paid("tx_1") ซึ่งไม่ใช่รูปร่างที่ถูก แล้วไปรู้จาก diagnostic

นั่นคือรูปแบบที่ช่องทางสำหรับเอเจนต์สร้างขึ้นมาเพื่อกำจัด: ข้อเท็จจริงที่คอมไพเลอร์คำนวณและ memoize ไว้แล้ว แต่ไม่มีเครื่องมือไหนส่งให้ การตรวจโปรเจกต์สาม module พบว่า hover ตอบได้สองจากสิบสี่ตำแหน่ง และทุก union มาโดยไม่มี payload

ทุก null บอกเหตุผล

ตัดบางส่วน: คำตอบยังมี generics, parameters, returns, members, literals, owner, async และ examples ทุกตัวมาเป็นคู่

key จะเป็น null ก็ต่อเมื่อมีประโยค <key>_absent อยู่ข้างๆ บอกเหตุผล เอเจนต์จึงไม่ต้องเดาว่าคำตอบที่หายไปหมายถึงสัญลักษณ์ไม่มีสิ่งนั้น หรือเครื่องมือไม่ได้ดู

รายละเอียด const ที่ไม่มี annotation

const ที่ไม่มี annotation จะไม่รายงาน type ตามกฎนี้: ตัวตรวจตั้งใจไม่อนุมาน type ของ declaration จาก initializer การพิมพ์ type ของ initializer จะบอกผู้เรียกว่าการใช้ชื่อนั้นถูกตรวจกับบางอย่าง ทั้งที่ไม่ได้ตรวจอะไรเลย

คำถามที่สองที่เอเจนต์ถาม

เมื่อได้รูปร่างแล้ว สิ่งถัดไปที่มันอยากรู้คือค่าที่ถืออยู่ใส่ในที่ที่กำลังจะใส่ได้ไหม glyph_assignable ใช้การเปรียบเทียบของตัวตรวจเอง

รายละเอียด คำตัดสินสามแบบ และทำไมไม่มี SAFE

แต่ละฝั่งเป็น module::name หรือการเขียน type ของ Glyph อ่านในขอบเขตของไฟล์ที่คุณระบุ และคำตัดสินบอกว่าเกิดอะไรขึ้นในสามแบบ

คำที่ใช้คือ COMPATIBLE ไม่ใช่ SAFE และความต่างควรได้หนึ่งประโยค SAFE เป็นคำของ glyph_impact และหมายถึงจุดหนึ่งยังถูกต้องหลังการแก้หนึ่งครั้ง คำตอบนี้เกี่ยวกับ type สองตัวโดยไม่มีจุดและไม่มีการแก้ในคำถาม คำตัดสินที่สามคือ UNDETERMINED ซึ่งใช้เมื่อไม่มีกฎไหนครอบคลุมการจับคู่นั้น type ของฟังก์ชันสองตัวกลับมาแบบนั้น เพราะความสัมพันธ์ข้างใต้เปรียบเทียบ return และไม่บอกอะไรเกี่ยวกับ parameter ความเงียบของมันตรงนั้นไม่ใช่การยอมรับ และเครื่องมือจะไม่รายงานว่าเป็นการยอมรับ

อีกทิศทาง: สิ่งนี้พึ่งพาอะไร และ module นั้นให้อะไรฉันบ้าง

เอเจนต์ที่กำลังจะเขียน import ถามได้ว่ามีอะไรอยู่อีกฝั่งแทนที่จะเปิดไฟล์

  • glyph_referencesglyph_references ตอบว่าใครใช้สัญลักษณ์หนึ่ง
  • glyph_dependenciesglyph_dependencies คือตารางเดียวกันอ่านจากอีกฝั่ง: declaration หนึ่งพึ่งพาอะไร ทุก declaration ที่ซอร์สของมันอ้างถึง แยกเป็น CALLS, REFERENCES และ FIELD_ACCESS แต่ละเส้นมีทั้งสองปลายและตำแหน่งที่อยู่
  • glyph_exportsglyph_exports ตอบว่า module หนึ่งเปิดอะไรให้ผู้ import เห็น จากคิวรี export ของคอมไพเลอร์เอง ไม่ใช่จากการสแกน: ทุก declaration ที่เป็น pub และทุก variant ที่ union แบบ pub ยกขึ้นมา แต่ละตัวเป็นรายการพร้อมตัวตน ชนิด และ signature
ที่มา บั๊ก PROVED ที่ภาพสะท้อนจับได้

การสร้างภาพสะท้อนของความสัมพันธ์คือสิ่งที่จับบั๊กในตัวเดิมได้ ทุกเส้นมีที่มากำกับ และ PROVED ควรหมายความว่าคอมไพเลอร์อ่านทั้งสองปลายแล้ว มันเคยตอบ PROVED สำหรับเส้นที่เข้าไปใน module ที่ parse ไม่ผ่าน ซึ่งไม่มีอะไรถูกอ่านเลย ตอนนี้มันตอบ UNDETERMINED พร้อมเหตุผล และเพราะ glyph_references กับ glyph_impact เรียกฟังก์ชันเดียวกัน ทั้งคู่จึงผิดแบบเดียวกันและถูกแก้ทั้งคู่

สิบเอ็ดเครื่องมือ และไม่ต้องมี client

glyph mcp ให้บริการสิบเอ็ดตัว: glyph_symbol, glyph_impact, glyph_assignable, glyph_diagnostics, glyph_hover, glyph_definition, glyph_references, glyph_variants, glyph_symbols, glyph_dependencies และ glyph_exports

แต่ละตัวมีคำสั่งย่อยของ glyph query ที่รับ argument เดียวกันเป็น flag และพิมพ์ JSON เดียวกัน วิ่งผ่าน entry point เดียวกับที่ client ใช้ เอเจนต์ที่รันได้แค่คำสั่ง shell จึงถามคำถามเดียวกันได้

รายละเอียด diagnostic และสิ่งที่ตามมาหลังการแก้

glyph_diagnostics ตรวจไฟล์ภายในโปรเจกต์และคืน diagnostic ที่ glyph check --json พิมพ์ จาก type ของ Rust ตัวเดียวกัน พร้อมเทสต์ที่รันทั้งสองช่องทางบนหกโปรเจกต์และเทียบ JSON ทีละ key รายละเอียดเต็มอยู่ในหน้า MCP

ทั้งหมดนั้นถามก่อนแก้ หลังแก้ คอมไพเลอร์ตอบในอีกทิศทาง: glyph check --agent พิมพ์แต่ละ diagnostic พร้อม invariant ที่การแก้ต้องรักษาไว้ และคำอธิบาย glyph_symbol ของทุกสัญลักษณ์ที่มันอ้างถึง รูปร่างที่เอเจนต์ต้องใช้จึงมาพร้อมกับ error ที่ต้องการมัน เรื่องนั้นมีหน้าของตัวเอง

สถานะตอนนี้

ใช้ได้วันนี้

  • เครื่องมืออ่านสิบเอ็ดตัวผ่าน MCP แต่ละตัวมีคำสั่งย่อยของ glyph query
  • glyph_symbol ตอบตามตัวตนหรือตามตำแหน่ง และทุกข้อเท็จจริงที่มันไม่มีเป็น null พร้อมประโยคบอกเหตุผล
  • ตัวตนไปถึง stdlib: std/result::Result
    รายละเอียด

    ตัวตนไปถึง stdlib: Result ใน prelude คือ std/result::Result ซึ่งเป็น module ที่ resolver ลงทะเบียนมันไว้ และเป็น module ที่ emitter เขียน import มาจาก glyph query symbol --entity std/result::Result จึงตอบด้วย Ok(T) และ Err(E), glyph query exports --module std/result แสดงรายการ API และ E0200 บนมันมีตัวตนนั้นใน cause ไม่มีซอร์ส Glyph อยู่เบื้องหลัง path และ range จึงเป็น null พร้อมเหตุผลนั้น แทนที่จะหายไป

  • hover ตอบได้สิบสี่จากสิบสี่ตำแหน่งที่ทดสอบ
    รายละเอียด

    hover ตอบได้ครบทั้งสิบสี่ตำแหน่งที่การตรวจทดสอบบนโปรเจกต์สาม module เทียบกับสองตำแหน่งก่อนเริ่มงานนี้: ชื่อที่ประกาศใน module อื่นตอบจาก declaration ของ module นั้นเอง binding ของ import ฟังก์ชันที่ import มา ณ จุดที่เรียก variant ที่ import มาและใช้เป็นค่า และ field ที่อ่านจาก record ที่ import มา จึงมี type ทั้งหมด

  • glyph_dependencies และ glyph_exports ปิดชุดที่ G221 ขอไว้G221
  • glyph_variants มี payload และ syntax การสร้างของแต่ละตัว glyph_definition และ glyph_symbols มี module::name คำตอบจึงต่อเข้า glyph_impact ได้โดยไม่ต้องหาใหม่
  • glyph_impact และ glyph_assignable ใช้การเปรียบเทียบเดียวกัน
    รายละเอียด

    ตาราง signature-type ของ glyph_impact ตัดสิน container เทียบ container, record เชิงโครงสร้างเทียบ record เชิงโครงสร้างหรือที่ประกาศไว้ (ในเครื่อง ที่ import มา generic หรือชื่อที่สอง), element ของ JSX ในฐานะการเรียกที่มันถูกแปลงไป และ union ของ string literal ทั้งสองฝั่งด้วยการเปรียบเทียบเดียวกับที่ glyph_assignable ทำ เครื่องมือทั้งสองจึงขัดแย้งกันเรื่องการจับคู่หนึ่งไม่ได้ argument ที่ความสัมพันธ์อ่านการจับคู่ได้ครบเป็น WILL_FAIL ไม่ว่าการเปรียบเทียบจะออกมาทางไหน เพราะ change_signature_type ไม่ได้ระบุ type ที่ใช้แทน และการจับคู่ที่ยอมรับคือการจับคู่ที่ type ที่ใช้แทนอาจถูกปฏิเสธได้ มีเพียงการจับคู่ที่ความสัมพันธ์ปฏิเสธที่จะตัดสินเท่านั้นที่เป็น UNDETERMINED

หยุดตรงไหน

  • ไม่มีเครื่องมือไหนที่นี่เขียน: ไม่มี rename ไม่มีการแก้ที่นำไปใช้
  • ฝั่งเขียนคือ glyph fix และมันซ่อมสามอย่าง
    รายละเอียด

    ฝั่งเขียนคือ glyph fix บน command line และมันซ่อมสามอย่าง ไม่ใช่อะไรก็ได้ที่คุณขอ: import ที่ไม่ได้ใช้, หัวของ arm ที่ตัวตรวจมีคำแนะนำเดียวพอดี และชื่อ field ที่ห่างหนึ่งตัวอักษรจาก field ที่ประกาศไว้ตัวเดียวพอดี

  • export บางตัวของ stdlib ตอบ kind: null
    รายละเอียด

    export ของ stdlib ที่คอมไพเลอร์ไม่ได้ model ทั้ง declaration และ signature จะตอบ kind: null พร้อมเหตุผล: std/result::all และ std/io::println มี type อยู่ใน TypeScript ที่คอมไพเลอร์นำเข้าไป และไม่มี pass ของ Glyph ไหนอ่าน

  • glyph_diagnostics ข้ามสามการตรวจที่ glyph check ทำ และระบุไว้ใน not_run
    รายละเอียด

    glyph_diagnostics ข้ามสามการตรวจที่ glyph check ทำ: tsc, การตรวจ E0104 สำหรับ import ที่อ้างถึง module ที่ไม่มี ซึ่งต้องใช้มุมมอง node_modules ของ build และ E0400 สำหรับ @example ที่ fail ซึ่งต้องรันโปรเจกต์ที่ emit ออกมา มันระบุทั้งสามไว้ใน not_run แทนที่จะตอบราวกับว่าได้ทำแล้ว
