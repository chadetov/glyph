21 · ข้อมูลไบนารี

จัดการข้อมูลไบนารีได้ไหม หรือทุกอย่างเป็น string?

std/bytes ให้ลำดับของ octet ที่เปลี่ยนค่าไม่ได้ และทั้ง std/fs และ std/crypto ก็ใช้มัน จนถึง 0.1.78 ยังไม่ใช่แบบนี้: ทุกขอบเขตใน standard library รับ string และคืน string ไฟล์ PNG จึงอ่านไม่ได้ และ HMAC ก็ใส่ key จริงไม่ได้

ในหน้านี้

  1. ทำไม string ทำไบต์พัง
  2. ค่า Bytes คืออะไร
  3. การ decode ที่ปฏิเสธได้
  4. การเลือก HMAC
  5. สถานะตอนนี้

ทำไมเรื่องนี้สำคัญ

สองแอปที่เขียนแยกกัน ตัวหนึ่งอ่าน PNG อีกตัวเป็น authenticator หยุดที่ประโยคเดียวกันนี้ในสัปดาห์เดียวกัน ทั้งคู่หาทางเลี่ยงภายในภาษาไม่ได้

  • ไฟล์ที่ถูกอ่านเป็นข้อความไบต์แรกของ PNG คือ 0x89 ซึ่งไม่ใช่ UTF-8 ที่ถูกต้องเมื่ออยู่เดี่ยวๆ อ่านไฟล์นั้นเป็นข้อความแล้วทุกไบต์ที่ decoder ตีความไม่ได้จะกลายเป็น U+FFFD ไฟล์จึงเสียหายก่อนโปรแกรมของคุณจะเห็น และไม่มีอะไรรายงาน error
  • key ที่ถูกส่งผ่าน stringเรื่องเดียวกันเกิดกับ key: secret ของ HMAC เป็น octet อะไรก็ได้ และการส่งมันผ่าน string จะเปลี่ยนมัน คุณจึงคำนวณ MAC ได้ไม่ตรงกับที่สเปกบอก และทุกเทสต์ที่คุณเขียนกับโค้ดของตัวเองก็ผ่าน

ค่า Bytes คืออะไร

Bytes เป็น Uint8Array ตอนรัน จึงส่งให้ API ของ host ที่รับมันได้โดยไม่ต้องแกะ

operation ของลำดับตั้งชื่อตามตัวที่คล้ายกันใน std/array และ std/string: len, get, slice, concat, index_of, starts_with ไม่มีตัวไหนแก้ argument ของมัน

ทุกการ decode ปฏิเสธได้ และบอกว่าตรงไหน

นี่คือส่วนที่สร้างยากที่สุด และเป็นเหตุผลที่ควรใช้มัน Buffer ของ Node รับ input ที่ผิดรูปและรายงานว่าสำเร็จ:

สิ่งที่แพลตฟอร์มทำแบบเงียบๆ 
Buffer.from("zz", "hex")        // an empty buffer, no error
Buffer.from("a-b_", "base64")   // skips - and _, decodes the rest, no error
buf.toString("utf8")            // U+FFFD for anything malformed, no error
สิ่งที่ Glyph ทำ 
match bytes.from_hex(input) {
  Ok(b) => use(b),
  Err(e) => io.eprintln("${e.message} at ${number.to_string(e.index)}"),
}

// "z" is not a hex digit at 0
// a trailing base64 group cannot be 1 character(s) long at 3
// not valid UTF-8 at 2
รายละเอียด แต่ละ codec ปฏิเสธอะไร

ทุก codec เขียนขึ้นเองแทนที่จะส่งต่อให้ Buffer hex, base64, base64url และ base32 จึงปฏิเสธอักขระที่อยู่นอก alphabet ของมัน กลุ่มท้ายที่สั้นเกินจะเข้ารหัสไบต์เต็ม และอักขระสุดท้ายที่มีบิตเกินท้ายข้อมูล to_text สแกนหาไบต์แรกที่เป็นส่วนของลำดับ UTF-8 ที่ถูกต้องไม่ได้ คุณจึงได้ตำแหน่ง ไม่ใช่แค่คำตัดสิน from_array ปฏิเสธทุกอย่างที่อยู่นอก 0..255 ด้วยเหตุผลเดียวกัน: & 0xff แบบเงียบๆ เปลี่ยน 256 เป็น 0 และเปลี่ยนคำผิดเป็นข้อมูล

การเขียน codec เองให้ผลพลอยได้ที่ไม่ได้ตั้งใจ module นี้ไม่ใช้ API ของ host เลย มีแค่ Uint8Array, TextEncoder และ TextDecoder bundle ที่แตะแค่ std/bytes จึงยังรันใน Web Worker ได้

HMAC แบบไหนที่คุณเลือกเปลี่ยนคำตอบ

ตอนนี้ std/crypto มีทั้งสองรูปแบบของทุก algorithm

  • ชื่อธรรมดาชื่อธรรมดารับ string และคืน hex ซึ่งเหมาะกับการ hash รหัสผ่าน
  • รูปแบบ _bytesรูปแบบ _bytes รับและคืน Bytes ซึ่งเหมาะกับ wire protocol

ถ้า key มาจาก bytes.from_base64 หรือ crypto.random_bytes มันมีไบต์ที่ string เก็บไม่ได้ และรูปแบบข้อความจะคำนวณอย่างอื่นออกมาแบบเงียบๆ

การตรวจค่าที่ผู้โจมตีส่งมาเทียบกับ secret ใช้ crypto.timing_safe_equal ไม่ใช่ bytes.equals equals คืนค่าทันทีที่เจอจุดที่ไม่ตรงกัน เวลาที่ใช้จึงบอกได้ว่าไบต์นำหน้ากี่ตัวที่ถูก

สถานะตอนนี้

ใช้ได้วันนี้

  • std/bytes ที่มี 21 ฟังก์ชัน: operation ของลำดับ สะพาน UTF-8 และ codec แบบ hex, base64, base64url และ base32 ที่คืน Result ซึ่งระบุตำแหน่งที่ผิด
  • fs.read_bytes, write_bytes และ append_bytes อ่านและเขียนไฟล์โดยไม่ decode
  • std/crypto มีรูปแบบ _bytes ของทุก digest และ HMAC รวมถึง SHA-1 สำหรับ protocol ที่กำหนดให้ใช้ random_bytes และ timing_safe_equal
  • codec ถูกตรึงกับ vector ของ RFC 4648 และ HMAC กับ RFC 6238 ในชุดเทสต์ของคอมไพเลอร์เอง

กำลังคมขึ้น

  • ยังไม่มี codec สำหรับจำนวนเต็ม การอ่าน u32 แบบ big-endian จาก header จึงเป็นการคำนวณที่คุณเขียนเอง: เกิน 32 บิต shift ก็เป็นเครื่องมือที่ผิดอยู่แล้ว จึงใช้การหาร
  • hex literal ยัง parse ไม่ได้ ตาราง CRC32 256 ช่องที่เขียนเป็นเลขฐานสิบจึงอ่านยาก
  • std/websocket ยัง decode frame ไบนารีเป็นข้อความ UTF-8 type ที่มันต้องการมีแล้ว และ frame คือสิ่งถัดไป
  • และฟังก์ชัน string-to-string รุ่นเก่าหกตัวของ std/encoding ยังเงียบเมื่อเจอ input ที่ผิดรูป จึงควรใช้ codec ของ std/bytes กับทุกอย่างที่ต้องถูกต้อง
  • codec เขียนด้วย TypeScript แทนที่จะส่งต่อให้ Buffer ของ node ซึ่งเป็นสิ่งที่ทำให้มันรันใน Web Worker ได้ และช้ากว่าของแพลตฟอร์ม 1 ถึง 35 เท่าบนข้อมูลหนึ่งเมกะไบต์
  • การเข้ารหัส key หรือ token ไม่มีต้นทุนที่วัดได้ไม่ว่าทางไหน คู่มือเรื่องประสิทธิภาพมีตารางถ้าคุณย้ายข้อมูลหลายสิบเมกะไบต์
