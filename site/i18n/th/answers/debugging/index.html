28 · การดูแลระบบ

เมื่อพังบน production ตอนตีสาม คนที่ on-call เห็นอะไร?

TypeScript ที่อ่านได้และเป็นของคุณ พร้อมsource map ที่ชี้กลับไปยัง .glyphข้างทุกไฟล์ที่ emit debugger, bundler หรือ error tracker ไล่โค้ดที่กำลังรันกลับไปยังซอร์สของคุณได้ และแม้แต่คนที่ไม่เคยเห็น Glyph ก็อ่าน TS ที่ generate ได้ ก่อนหน้านั้น glyph build และ glyph run รายงาน diagnostic ชุดเดียวกันบน tree เดียวกัน loop ที่เร็วจึงซ่อนสิ่งที่ build จะจับได้ไม่ได้ ข้อจำกัดสองข้อ ซึ่งอยู่บนเส้นทาง glyph run ทั้งคู่ ระบุไว้ด้านล่าง

1 · TypeScript ที่ generate เป็นของคุณ อ่านได้

Glyph ไม่ได้ส่ง runtime ที่ทึบแสงมาด้วย มัน emit TypeScript ธรรมดาที่จัดรูปแบบแล้ว ซึ่งคุณ commit และ deploy เหมือน TS ทั่วไป กรณีที่แย่ที่สุด (วิศวกร on-call ที่ไม่รู้จัก Glyph ตอนตีสาม) ก็ยังอ่าน TypeScript ธรรมดา ไม่ใช่ภาษาถิ่น ไม่มีกล่องดำระหว่างซอร์สของคุณกับ production

2 · source map ที่ชี้กลับไปยัง .glyph

ทุกไฟล์ .ts ที่ emit มี source map มาตรฐาน v3 (.ts.map) อยู่ข้างๆ พร้อม comment sourceMappingURL และซอร์ส Glyph ของคุณฝังอยู่ (sourcesContent) อะไรก็ตามที่ใช้ source map (Chrome DevTools, Node debugger, error tracker อย่าง Sentry, bundler ของคุณ) ไล่ต่อผ่านมันได้และแสดงบรรทัดใน .glyph ไม่ใช่บรรทัดที่ generate

dist/main.ts (ส่วนท้าย) 
// ...emitted TypeScript...
//# sourceMappingURL=main.ts.map    // v3 map, .glyph embedded

3 · error ตอน build และ type error ชี้ไปที่ Glyph อยู่แล้ว

คุณแทบไม่มีทางไปถึง production พร้อม type error เพราะ glyph build รัน tsc --strict และmap ทุก error ของ tsc กลับไปยังซอร์ส .glyph ของคุณ (เครื่องหมายชี้ตำแหน่งแบบเดียวกัน และรักษารหัส error ของ TypeScript ไว้) เครื่องหมายชี้อยู่ที่ expression ของ Glyph ที่เล็กที่สุดซึ่งโค้ดของมันถูก tsc ปฏิเสธ: argument ที่ผิดจะขีดเส้นใต้ argument นั้น field ที่สะกดผิดใน event handler ของ JSX จะขีดเส้นใต้การเข้าถึง member นั้น ไม่ใช่ return ทั้งก้อนรอบๆ และ glyph build --json emit ทุก diagnostic เป็น JSON ที่มีโครงสร้าง (code, severity, file, line/col เริ่มจาก 1, help) ให้ CI หรือเครื่องมือของคุณนำไปใช้

4 · glyph run บอกสิ่งเดียวกัน

คำสั่งที่คุณพิมพ์ทั้งวันคือ glyph run และจนถึง 0.1.40 มันเงียบกว่า build มันคอมไพล์ทั้งไดเรกทอรี เอารายการไฟล์ที่ emit ออกจากรายงาน แล้วทิ้ง diagnostic ไป tree ที่ glyph build เตือนจะรันผ่านสะอาดและ exit 0 ตอนนี้มันรายงานชุดเดียวกัน: รวมคำเตือน ทั้งในไฟล์ที่คุณระบุและไฟล์ข้างเคียง หลัง output ของโปรแกรม พร้อมจำนวนหนึ่งบรรทัด cache ของการรันเก็บมันไว้ การรันครั้งที่สองของซอร์สที่ไม่เปลี่ยนจึงบอกสิ่งที่ครั้งแรกบอก แทนที่จะเงียบไป และรายการใน cache ที่ไม่มี diagnostic ถือว่า miss และ build ใหม่

import ที่ไม่ได้ใช้ เพิ่มเข้ามาก่อนโค้ดที่จะใช้มันหนึ่งขั้น 
$ printf 'look\nquit\n' | glyph run adventure.glyph
...the game plays and exits 0...

ข้อจำกัดสองข้อในตอนนี้

stack ตอน crash ของ glyph run เองยังแสดงเลขบรรทัดของ .ts glyph run รันผ่าน tsx และ tsx ไม่ได้ไล่ source map ต่อผ่านการแปลง .ts→.js ของตัวเอง throw ที่ไม่ถูกจับระหว่าง glyph run จึงรายงานบรรทัดที่ generate การ remap stack นั้นเป็นงานที่จะตามมา มันมีผลกับ loop run ในเครื่อง ส่วนการ deploy จริง คุณ glyph build เป็น .ts แล้ว bundle ด้วย toolchain ปกติ และ .ts.map ก็ไล่ต่อตามปกติ stack บน production ที่ปลุกคุณขึ้นมาจึง map กลับไปยัง .glyph

error ใน module ข้างเคียงไม่เปลี่ยน exit code ของ glyph run module ที่คอมไพล์ไม่ผ่านจะ import ไม่ได้ และโปรแกรมที่ไม่เคย import มันก็ยังรันไป ตอนนี้คุณเห็น error แล้ว แต่ process ยัง exit ด้วยค่าที่ main คืนมา การทำให้มัน exit ไม่เป็นศูนย์จะทำให้ tree ที่รันได้ดีวันนี้ fail จึงเป็นการตัดสินใจที่ยังเปิดอยู่ ไม่ใช่การมองข้าม ถ้าคุณต้องการให้สุขภาพของ tree เป็นตัวตัดสิน exit code ให้ใช้ glyph build

สถานะตอนนี้

ใช้ได้วันนี้

TS ที่อ่านได้และ commit ไว้ .ts.map v3 ต่อไฟล์ error ของ tsc ที่ remap ไปยัง .glyph และ diagnostic แบบ --json glyph run รายงานแบบเดียวกับ glyph build รวมถึงตอน cache อุ่นอยู่ สาย source map ของ toolchain สำหรับ deploy ไปถึง .glyph

กำลังมา

remap stack ตอน crash ของ glyph run เอง (เพื่อให้ loop run ในเครื่องแสดง frame ของ .glyph ด้วย) การตัดสินใจว่า error ใน module ข้างเคียงควรทำให้ glyph run exit ไม่เป็นศูนย์หรือไม่ และการดีบักใน editor ที่ดีขึ้นผ่าน LSP
