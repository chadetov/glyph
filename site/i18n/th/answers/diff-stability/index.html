02 · การเปลี่ยนแปลงที่รีวิวได้

การแก้ของเอเจนต์จะสะอาด หรือจัดรูปแบบไฟล์ใหม่ทั้งไฟล์?

การแก้หนึ่งบรรทัดคือdiff หนึ่งบรรทัดทุกครั้ง Glyph มี layout มาตรฐานแบบเดียว เอเจนต์จึงฝังการเปลี่ยนแปลงจริงไว้ใต้กำแพงของการจัดรูปแบบใหม่ไม่ได้

ทำไมเรื่องนี้สำคัญ

เมื่อเอเจนต์เปิด pull request diff คือการรีวิว ถ้าการแก้หนึ่งบรรทัดจริงๆ มาในรูปการจัดรูปแบบใหม่ 200 บรรทัด ก็ไม่มีใครเห็นว่าอะไรเปลี่ยนจริง และความรกนั้นคือที่ที่บั๊กหลุดผ่านไป diff ที่คงที่หมายความว่า diff แสดงการเปลี่ยนแปลง และไม่มีอะไรนอกจากการเปลี่ยนแปลง

กฎสองข้อทำงานส่วนใหญ่ นี่คือแต่ละข้อ แสดงเป็น diff ที่คุณจะรีวิว

ตัวอย่างที่ 1: trailing comma และหนึ่งรายการต่อบรรทัด

เพิ่ม route หนึ่งตัว ในสไตล์ที่พบบ่อยของ TypeScript บรรทัดสุดท้ายเดิมต้องเปลี่ยนเพื่อเพิ่ม comma สองบรรทัดขยับสำหรับการเปลี่ยนรายการเดียว:

TypeScript: เพิ่ม "/billing" 
 const routes = [
   "/home",
-  "/about"
+  "/about",
+  "/billing"
 ]
3 บรรทัดขยับสำหรับ 1 การเปลี่ยนแปลง
Glyph: เพิ่ม "/billing" 
 let routes = [
   "/home",
   "/about",
+  "/billing",
 ]
เพิ่ม 1 บรรทัด ตรงกับการเปลี่ยนแปลงพอดี

trailing comma เป็นสิ่งบังคับ และ list ที่ไม่พอดีในบรรทัดเดียวจะเป็นหนึ่ง element ต่อบรรทัดแทนที่จะถูกจัดกลุ่มใหม่ การแทรก ลบ หรือสลับลำดับรายการจึงไม่กระทบรายการข้างเคียง เช่นเดียวกับ field ของ record, parameter, arm ของ match และ import เกณฑ์นี้มีต้นทุน: การเปลี่ยนชื่อที่ดันการเรียกให้เกิน 100 คอลัมน์จะขยาย argument list ทั้งหมดเป็นหนึ่งตัวต่อบรรทัด

ตัวอย่างที่ 2: layout มาตรฐานแบบเดียว

มีการจัดรูปแบบที่ถูกต้องเพียงแบบเดียว ซึ่ง glyph fmt สร้างขึ้น whitespace การตัดบรรทัด และการจัดแนว ไม่ใช่ตัวเลือกที่เอเจนต์จะ “จัดให้เรียบร้อย” ได้ การแก้เชิงความหมายจึงลากการจัดวางใหม่ไปด้วยไม่ได้ เปลี่ยน type ของ field หนึ่งตัว นั่นคือ diff ทั้งหมด:

user.glyph: เปลี่ยน field เดียว รีวิวบรรทัดเดียว 
 type User = {
   id: string,
-  age: string,
+  age: number,
   email: string,
 }

เพราะ layout ตายตัว เอเจนต์สองตัวที่แก้ไฟล์เดียวกันจึงได้การจัดรูปแบบที่เหมือนกันทุกไบต์ ไม่มีการจัดวางใหม่ที่วุ่นวาย ไม่มีความรกแบบ “formatter ของฉันกับของคุณ” และ git blame ที่สะอาดชี้ไปที่ commit ที่เปลี่ยนบรรทัดนั้นจริง ไม่ใช่ commit ที่จัดรูปแบบใหม่

layout มาตรฐานแบบเดียว แล้ว formatter จะย้าย comment ของฉันไหม?

เคย และนั่นเป็นบั๊กที่ควรพูดถึง Glyph ไม่มี block comment และไม่มี syntax สำหรับ doc comment บรรทัด // จึงเป็นวิธีเดียวที่จะอธิบาย field ของ record, variant ของ union หรือ arm ของ match formatter ปล่อย comment ที่ค้างอยู่เฉพาะที่ขอบของ declaration และ statement ซึ่งหมายความว่า comment ที่เขียนภายใน construct จะไหลลงไปที่ declaration ถัดไป และอ่านแล้วเหมือนเป็นเอกสารของสิ่งที่มันไปตกอยู่ การเขียน Minesweeper ด้วย Glyph คือสิ่งที่ทำให้มันโผล่ขึ้นมา declaration สองตัวนี้มาจากแอปจริง (ตัด comment ให้พอดี) รันผ่าน formatter ตัวเก่าและตัวใหม่

0.1.37: fmt หนึ่งรอบ 
type Visibility =
  | Hidden
  | Flagged
  | Revealed

// Face down. Prints as `.`.
// Face down and marked by the player.
// Face up. `Cell.adjacent` is what gets printed.
type Cell = { mine: bool, adjacent: int, visibility: Visibility }
// Number of mined neighbours. Only meaningful
// once mines are placed.
comment ของ variant สามตัวตอนนี้กลายเป็นเอกสารของ record
0.1.38: ไฟล์เดียวกัน 
type Visibility =
  // Face down. Prints as `.`.
  | Hidden
  // Face down and marked by the player.
  | Flagged
  // Face up. `Cell.adjacent` is what gets printed.
  | Revealed

type Cell = {
  mine: bool,
  // Number of mined neighbours. Only meaningful
  // once mines are placed.
  adjacent: int,
  visibility: Visibility,
}
ทุก comment อยู่บนสิ่งที่มันอธิบาย

กฎตอนนี้: comment ถูก emit ซ้ำไว้เหนือรายการที่มันเขียนไว้เหนือ ทั้งภายใน body ของ record, list ของ variant ใน union, literal แบบ array หรือ object, list ของ argument หรือ parameter และ match และ construct ที่มี comment อยู่ข้างในจะใช้รูปแบบหนึ่ง element ต่อบรรทัดเสมอ ไม่ว่าขนาดเท่าไร comment จึงมีรายการให้วางอยู่เหนือ type Shape = { w: int, h: int } จึงยังยุบเหลือบรรทัดเดียว และทันทีที่คุณเขียนเอกสารให้ h record ก็จะคงสภาพขยายไว้

ทำไมเรื่องนี้นับเป็นบั๊กเรื่องความถูกต้องไม่ใช่เรื่องหน้าตา: ไม่มีอะไร fail build exit 0 tsc ผ่าน และ output ที่เพี้ยนก็เป็น fixed point ในตัวเอง glyph fmt --check ใน CI จึงเขียวบนไฟล์ที่ comment บอกสิ่งที่ไม่จริงไปแล้ว นั่นคือความล้มเหลวประเภทเดียวกับที่ Glyph มีไว้กำจัด แค่อยู่ใน formatter แทนที่จะอยู่ใน type system

glyph fmt ทำให้โปรแกรมที่ build ผ่านพังได้ไหม?

เคยได้ และยังมีกรณีหนึ่งที่เปิดอยู่ เริ่มจากที่แก้แล้ว arm ที่หมายถึง “record ว่าง” เขียนว่า true => ({}) ตำแหน่ง body ของ arm คือที่เดียวใน grammar ที่ { นำหน้ากำกวม และ parser ตัดสินโดยกำหนดให้ต้องมี key: หรือ ... ต่อจากวงเล็บปีกกาทันที object ว่างไม่มีทั้งสองอย่าง เมื่อ formatter ตัดวงเล็บออกแล้วพิมพ์ใหม่เป็น true => {} arm จึงกลับมาเป็นblock ว่าง และไฟล์ก็ build ไม่ผ่าน: E0223 arm ไม่ได้ให้ค่า คุณรัน formatter บนโค้ดที่ใช้งานได้แล้วได้โค้ดที่คอมไพล์ไม่ผ่านอีกต่อไป

ตอนนี้ printer ใส่วงเล็บให้ body ของ arm ที่ token ซ้ายสุดเป็น { ซึ่งจะถูก parse ใหม่เป็น block ได้ ซึ่งก็คือ object ว่างและอะไรก็ตามที่สร้างบนมัน (({}).size กลับมาเป็น ({}.size)) body ของ arm ที่อ่านได้ไม่กำกวมอยู่แล้ว อย่าง false => { a: "x" } ยังไม่มีวงเล็บ จึงไม่มีเครื่องหมายใหม่ให้อ่านที่อื่น fmt เป็น fixed point บนผลลัพธ์ และ TypeScript ที่ emit ออกมาไม่เปลี่ยน formatter ที่โปรแกรมของคุณต้องเอาตัวรอดจากมันแย่กว่าฟีเจอร์ที่ขาดไป เพราะมันทำลายโค้ดที่เคยใช้ได้แล้ว

อีกสองกรณีถูกแก้ใน 0.1.138 ภายใน block บรรทัดที่ขึ้นต้นด้วย ( จะต่อจากบรรทัดข้างบน และจนถึง 0.1.137 formatter พิมพ์ load()? ตามด้วย .run() เป็น (load()?).run() หลัง let a = 1 ไฟล์ที่จัดรูปแบบแล้วจึงหมายถึง let a = 1(…).run() ตอนนี้มันเก็บ load()? ไว้โดยมี .run() ย่อหน้าอยู่บรรทัดถัดไป และเขียน e?(x), e?[0] และ e? ? โดยไม่มีวงเล็บ อีกกรณีคือ refinement where ของ union ซึ่ง formatter ทิ้งไป ทำให้โปรแกรมที่ check ปฏิเสธกลายเป็นโปรแกรมที่มันยอมรับ ตอนนี้ fuzzer parse ไฟล์ที่จัดรูปแบบแล้วและเทียบ tree กับของต้นฉบับ layout ที่เปลี่ยนความหมายของไฟล์จึง fail ตั้งแต่รอบแรก แทนที่จะรอให้ใครมาสังเกต

กฎการจัดรูปแบบเบื้องหลังเรื่องนี้ และสิ่งที่มันแลก อยู่ในหน้าเสาหลักเรื่อง diff ที่คงที่

สถานะตอนนี้

ใช้ได้วันนี้

trailing comma ที่บังคับ, list แบบหนึ่งรายการต่อบรรทัด และ layout มาตรฐานแบบเดียวของ glyph fmt ซึ่ง round-trip ได้และรันซ้ำได้ผลเท่าเดิม พร้อม format-on-save ใน editor glyph fmt ไม่เคยย้าย comment ไปที่ที่มันไม่ควรอยู่ comment อยู่เหนือรายการที่มันเขียนไว้เหนือ รวมถึงภายใน record, literal, argument list, match, ระหว่าง operand ของ operator และระหว่างขั้นของ method chain ซึ่งจะเป็นหนึ่งขั้นต่อบรรทัดโดยมีจุดนำหน้า

ขอบเขต และสิ่งที่จะตามมา

comment จะถูก emit ในบรรทัดของตัวเองเสมอ comment ที่เขียนไว้ท้ายบรรทัดโค้ด (w: int, // width in cells) จึงย้ายไปอยู่บรรทัดเหนือรายการถัดไป มันไม่ข้ามขอบ declaration แล้ว แต่ก็ยังย้าย การเก็บไว้ท้ายบรรทัดต้องให้ printer ติดตามว่า comment อยู่บรรทัดเดียวกับอะไร comment ในตำแหน่งที่ layout ไม่มีที่วาง เช่นภายใน index หลัง argument ของการเรียกกลาง chain หรือก่อน operand ของ ! หรือ await จะไม่ถูกย้ายอีกต่อไป: glyph fmt ปฏิเสธไฟล์ ปล่อยไว้ตามเดิม และระบุบรรทัดพร้อมบอกว่าควรย้าย comment ไปไว้ไหน และ glyph check รายงานสิ่งเดียวกันเป็นคำเตือน E0500 comment ระหว่าง attribute ของ JSX หรือระหว่าง field ของ object pattern ก็ถูกปฏิเสธด้วย ทั้งที่ layout แบบหนึ่งต่อบรรทัดวางได้ layout เหล่านั้นอยู่ในรายการแล้ว printer ยังไม่มีกฎสำหรับตัด method chain หรือ chain ของ + ที่ยาว chain ที่ยาวเกินจึงไปตัดที่ argument list ด้านในสุดแทน ซึ่งเป็นที่ที่ผิด เรากำลังสร้าง benchmark ขนาดของ diff เทียบกับการแก้แบบเดียวกันใน TypeScript ด้วย เพื่อให้เสาหลักข้อนี้เป็นตัวเลขที่คุณตรวจได้
