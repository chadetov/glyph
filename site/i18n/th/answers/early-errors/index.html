ทำไม Glyph จับสิ่งที่ tsc จับได้ แต่เร็วกว่า?

เพราะ error บน TypeScript ที่ generate คือ error เกี่ยวกับโค้ดที่คุณไม่ได้เขียน Glyph รายงานสิ่งเหล่านี้เทียบกับซอร์สของคุณ พร้อมกฎที่คุณละเมิดและการแก้ที่ทำให้ถูก

ในหน้านี้

  1. ทำไมเรื่องนี้สำคัญ
  2. arm ที่ไม่ให้ค่า
  3. await นอก async
  4. mut ที่ขาดไป
  5. เมื่อ tsc ก็พอใจด้วย
  6. ข้อความที่ผิด
  7. ระบุกฎ ไม่ใช่ token
  8. รับมาทำใน 0.1.121
  9. ตั้งแต่ 0.1.133
  10. ใน 0.1.122
  11. literal type, 0.1.123
  12. module ใต้ std/
  13. ขีดจำกัดการซ้อน
  14. เมื่อไม่มีใครผิด
  15. คำผิดเดียวกัน
  16. สถานะตอนนี้

ทำไมเรื่องนี้สำคัญ

Glyph คอมไพล์เป็น TypeScript แล้วตรวจ type ของ output ด้วย tsc --strict ความผิดพลาดที่ Glyph ไม่ได้ model จึงไม่หายไป มันกลับมาในขั้นถัดไป โดยพูดในแง่ของไฟล์ที่ emit: TS1308 ที่ชี้ไปที่ await ในฟังก์ชันที่คุณไม่เคยเขียน หรือ TS2366 เกี่ยวกับ switch ที่คุณไม่ได้เขียน

บรรทัดถูก map กลับไปยัง .glyph ของคุณ แต่คำอธิบายไม่ได้ถูก map ช่องว่างนั้นคือที่ที่คอมไพเลอร์เลิกสอน

กฎแต่ละข้อที่ Glyph ตัดสินเองได้จึงย้ายขึ้นมา:

  • E0222await นอก async fn
  • E0223arm ของ match ที่ไม่ให้ค่าในขณะที่ match ถูกใช้เป็นค่า
  • E0008การ assign ที่เขียนโดยไม่มี mut

แต่ละข้อระบุกฎ อ้าง decision ที่อยู่เบื้องหลัง และแสดงก่อนและหลัง

arm ที่ไม่ให้ค่า

ก่อนหน้านี้ switch ที่ emit หลุดออกจาก case ของตัวเอง และ text ถือ undefined ขณะที่ type บอกว่า string tsc จับบางรูปแบบได้และพลาดบางรูปแบบ

ตอนนี้ Glyph ตัดสินทุกที่ที่ตำแหน่งตัดสินได้: let, mut, return หรือส่วนท้ายของฟังก์ชันที่ประกาศ return type match แบบ statement ยังเก็บ X => {} ไว้เป็นการไม่ทำอะไรโดยตั้งใจตามที่มันเป็น

await นอก async fn

await ก็ย้ายแบบเดียวกัน Glyph ไม่มี Promise ที่ผู้ใช้มองเห็น: async fn -> T ถูก await ได้เป็น T await ที่อื่นจึงไม่มีอะไรให้พักรอ

glyph build บน `fn total() -> number { return await fetch_count() }` 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

// before: no Glyph diagnostic, then
dist/main.ts:14:18 - error TS1308: 'await' expressions are only allowed
within async functions and at the top levels of modules.
รายละเอียด สิ่งที่เรียกได้ตัวไหนเป็นตัวตัดสิน

สิ่งนั้นเคยเป็น TS1308 ของ tsc บนไฟล์ที่ generate ตอนนี้เป็น E0222 และสิ่งที่เรียกได้ซึ่งครอบอยู่ชั้นในสุดเป็นตัวตัดสิน lambda แบบ synchronous ภายใน async fn จึงเป็นบริบทของตัวเอง ซึ่งเป็นกฎเดียวกับที่ TypeScript ใช้ ความผิดพลาดในทางกลับกัน คือการเรียกที่ไม่มีใคร await เป็น E0238: save(1) ที่อยู่บรรทัดเดียว let _ = save(1) และ let n: number = load() จะถูกปฏิเสธ เพราะการเรียกเริ่มทำงานแล้วโปรแกรมก็ไปต่อโดยไม่รอ callback แบบ sync ที่ตั้งใจสั่งงานแล้วไม่รอให้เขียน task.detach(async fn() -> void { await save(1) }) ซึ่งจะรายงานความล้มเหลวทาง stderr

การ assign ที่ไม่มี mut

ตัวที่สามเกี่ยวกับกฎที่คนละเมิดตั้งแต่วันแรก Glyph ทำเครื่องหมายทุกการแก้ค่า การ assign binding ใหม่คือ mut x = e และการสร้างใหม่คือ let x = e

E0008E0302E0303

x = e เปล่าๆ เคยรายงาน "unexpected token: Equals" ซึ่งระบุอักขระแทนที่จะระบุกฎ ตอนนี้เป็น E0008 และ glyph --explain E0008 อธิบายว่าทำไมเครื่องหมายนี้มีอยู่: ทุกที่ที่ค่าเปลี่ยนขึ้นต้นด้วย mut grep "mut total" จึงเจอทุกจุด

รายละเอียด operator ?, E0302 และ E0303

operator ? ได้การดูแลแบบเดียวกันจากอีกทาง ? ขยายเป็น binding บวก return ก่อนเวลาที่วางไว้ก่อน statement ที่มันอยู่ มันจึงต้องมี statement ให้ขยายเข้าไป มันใช้ได้ใน let, return, argument และตอนนี้ใน body ของ arm ของ match ด้วย ตรงไหนที่ใช้ไม่ได้ ข้อความจะบอกว่าเป็นตำแหน่งไหนและจะ bind ออกมาอย่างไร (E0302 และ E0303) แทนที่จะอ้างว่า operator ยังไม่ได้ implement

กรณีที่แย่กว่า: เมื่อ tsc ก็พอใจด้วย

error ของ tsc ในที่ผิดเป็นเรื่องน่ารำคาญ build ที่สะอาดบนโปรแกรมที่มีความหมายอีกอย่างคือปัญหาจริง และ Glyph เคยมี

ทุกชื่อระดับบนสุดที่คุณประกาศเข้าไปใน module ที่ emit ตรงตัว รวมถึง constructor ของ variant ใน tagged union variant ชื่อ Error จึง emit export function Error(...) ที่ระดับบนสุดของ module แล้ว new Error(...) ที่คอมไพเลอร์เขียนไว้ข้างล่างก็เรียก variant ของคุณ

glyph build บน union ที่มี variant `Error` 
[E0110] `Error` cannot name a type, variant, or function: the emitted module
        references the JavaScript global `Error`, and this declaration would
        shadow it
 5 │   | Error(string)
   │     ──────┬─────
   ╰─ Rename it (e.g. `Error` -> `Failure`). The name is legal TypeScript, so
      nothing downstream catches the rebinding.

// before: no Glyph diagnostic, then, twenty lines later
dist/main.ts:31:12 - error TS2345: Argument of type 'string' is not
assignable to parameter of type ...
E0110E0111E0109
รายละเอียด type Key = string | number, รายการที่ป้องกันไว้, E0111

type Key = string | number คือข้อบกพร่องเดียวกันในหน้าตาที่เป็นมิตรกว่า ใน Glyph A | B ประกาศ tagged union ที่สมาชิกเป็นconstructorของ variant บรรทัดนั้นจึงประกาศ variant ชื่อ string และ number มันคอมไพล์ผ่าน ผ่าน tsc --strict และ emit export const number ที่บัง namespace number ของ prelude ไม่มีอะไร fail จนกระทั่งการเรียก number.to_string ทีหลัง fail

span คือ declaration ซึ่งเป็นที่ที่ต้องเปลี่ยนชื่อ รายการที่ป้องกันไว้ derive มาจาก emitter ไม่ใช่จากรายการ global ของ JavaScript ทั่วไป และมีเทสต์ที่ grep emitter แล้ว fail เมื่อมีการอ้างถึง global ใหม่โดยไม่มีรายการที่ตรงกัน เทสต์นั้นคือประเด็น: Number ไม่มีพิษภัยจนกระทั่ง int ออกมาและเริ่ม emit Number.isInteger ซึ่งเป็นวิธีที่เรื่องนี้หลุดไปถึงรุ่นที่ออกตั้งแต่แรก Date, Math และ JSON ยังใช้ได้ เพราะไม่มีอะไรที่ Glyph emit อ้างถึงมัน

กรณี union ของ primitive ได้รหัสของตัวเองคือ E0111 เพราะการปฏิเสธโดยไม่อธิบายไม่ได้สอนอะไร มันบอกว่าบรรทัดนั้นถูก parse เป็นอะไรจริงๆ ชี้ไปที่ variant ที่มีชื่อ และระบุ extern_ts("string | number") สำหรับขอบเขตที่คุณต้องการ union ของ TypeScript ดิบ ทุกชื่อที่ Glyph ไม่ให้ใช้อยู่ในตารางใน docs/reference/reserved-words.md: keyword 32 คำ คำสงวนของ TypeScript 33 คำที่อยู่เบื้องหลัง E0109 และรายการชื่อที่บังกัน แต่ละคำมีเหตุผลว่าทำไมชื่อนั้นถูกจองไว้

ควรพูดให้ชัดว่าสิ่งนี้ไม่ได้ทำอะไร คุณยังตั้งชื่อ type หรือ variant ว่า Error ไม่ได้ และ spreadsheet ที่ทำให้เรื่องนี้โผล่ขึ้นมาก็มี variant ชื่อ Cellerr เพราะเหตุนี้ โปรแกรมที่มันอยากเป็นยังเขียนไม่ได้ สิ่งที่เปลี่ยนคือตอนนี้คอมไพเลอร์บอกที่ declaration แทนที่จะปล่อยให้ build เขียวแล้วมีความหมายอีกอย่าง

รายละเอียด ทำไมไม่ทำให้ชื่อนั้นใช้ได้ไปเลย

การทำให้ชื่อนั้นใช้ได้หมายถึงต้องแปลงชื่อของ Glyph ตอนเข้าสู่ TypeScript ซึ่งเปลี่ยนสิ่งที่ stack trace, grep บน dist/ และ shim extern/ ที่เขียนเองมองเห็น จึงไม่ใช่ patch ที่เราทำแบบเงียบๆ ได้

ข้อความที่ผิดแย่กว่าไม่มีข้อความ

รายการชื่อที่บังกันเริ่มจากชื่อที่ emitter เขียนเป็นค่า มันขาดชื่อที่ emitter เขียนเป็นtype และนั่นทำให้เกิดปัญหานี้ในแบบที่แหลมคมที่สุด

glyph build ก่อน: แบบนี้สิบห้าตัว ไม่มีตัวไหนอยู่ใกล้ต้นเหตุ 
dist/corpus/infer_output.ts:52:9 - error TS2353: Object literal may only
specify known properties, and 'code' does not exist in type 'Issue'.
glyph build ตอนนี้ 
[E0110] `Issue` cannot name a type, variant, or function: the emitted module
        references the Glyph prelude global `Issue`, and this declaration
        would shadow it
   ╰─ Rename it. The name is legal TypeScript, so nothing downstream catches
      the rebinding.
รายละเอียด ทำไม Issue ถึงชนกัน และ Record

parse ของทุก descriptor คืน Result<T, Issue[]> module ที่ emit จึงเขียน Issue ไม่ว่าคุณจะเขียนหรือไม่ ประกาศ type Issue = { path: Array<string>, message: string } ใน module ของคุณเอง แล้วของคุณจะชนะ object Issue ที่ emit มี field code ที่ของคุณไม่รู้จัก และ build fail ด้วย error ของ tsc เกี่ยวกับโค้ดที่ generate ที่ span ซึ่งชี้ไปที่อื่น

Record เข้ารายการในเวลาเดียวกัน โดยจัดไว้กับ global ของ JavaScript แทนที่จะเป็นชื่อใน prelude เพราะมันเป็น built-in ของ TypeScript และการอ้างเป็นอย่างอื่นจะทำให้ข้อความผิดเรื่องที่มาของชื่อ เทสต์ตรวจความเพี้ยนที่ grep emitter ตอนนี้ครอบคลุม type แบบ ambient ด้วย และต้องเรียนรู้ที่จะเห็น Issue[] ในตำแหน่ง type ซึ่งเป็นเหตุผลที่เรื่องนี้หลุดไปถึงรุ่นที่ออก Schema, Component และ Option ยังใช้ได้ตามกฎเดียวกับที่ทำให้ Date ใช้ได้: emitter เขียนมันก็เพราะคุณเขียนไว้ใน annotation การประกาศมันจึงไม่บังอะไร

import ที่โยนความผิดให้ match

อีกตัวในกลุ่มนี้คือ import path ของ import ในเครื่อง resolve จาก build root คือไดเรกทอรีที่คุณส่งให้ glyph build ไม่ใช่จากไดเรกทอรีของไฟล์ที่ import

glyph build examples/apps บน `import catalog` ภายใน csvql/ 
[E0104] unresolved import `catalog`: no module `catalog` under the build
        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from
        the importing file's directory (D15)
   ╰─ Build that module's own directory as the root, or spell the import path
      as it reads from the root.

// before: no import diagnostic, then
[E0218] non-exhaustive match on string   // on a match over all four values
รายละเอียด สิ่งที่มันเคยรายงาน และวิธีเลี่ยง false positive

build tree ที่ครอบอยู่แล้ว import catalog หาอะไรไม่เจอ และจนถึงตอนนี้ไม่มีอะไรบอก type ลดลงเป็น unknown match บนมันเสีย variant ที่มันกำลัง match และสิ่งที่คุณได้คือ E0218 match ไม่ครบ บน match ที่ครอบคลุมทุก case ถ้าทำตามที่ข้อความนั้นขอ ก็จะเพิ่ม arm else ที่ไม่มีวันรันให้โค้ดที่ถูกต้อง

ความเสี่ยงของการตรวจแบบนี้คือมันเตือนสิ่งที่ไม่ได้ผิด และตัวตรวจ import ที่ร้องเตือนทุกแพ็กเกจ npm แย่กว่าความเงียบที่มันมาแทน build จึงรวบรวมชื่อ module ที่ resolve ได้โดยไม่ต้องมีไฟล์ .glyph ก่อน: ทุก declare module "X" ใต้ <root>/.types/ และใน Node shim ที่มาด้วย บวกทุกแพ็กเกจใน node_modules ของโปรเจกต์ ชื่อที่อยู่ในรายการนั้นไม่เคยถูกรายงาน แม้ไฟล์ในเครื่องจะบังเอิญชื่อเดียวกัน เมื่อโปรเจกต์ไม่มี node_modules เลย คอมไพเลอร์แยก dependency ที่ยังไม่ได้ติดตั้งออกจากคำผิดไม่ได้ มันจึงรายงานเฉพาะสิ่งที่พิสูจน์ได้: import ที่มีไฟล์ .glyph ใต้ root ตอบรับอยู่

การ resolve เองไม่ได้เปลี่ยน โปรแกรมเดิม build ผ่าน และโปรแกรมเดิม fail สิ่งที่เปลี่ยนคือความล้มเหลวตอนนี้ระบุ import แทนที่จะกล่าวหา match ที่อยู่ห่างไปสองไฟล์ ซึ่งคือทั้งหมดของเรื่อง: คอมไพเลอร์ที่รายงานต้นเหตุผิดทำให้คุณเสียเวลาหนึ่งชั่วโมงไปไล่มัน และเสียความเชื่อใจในทุกข้อความหลังจากนั้น

ระบุกฎ ไม่ใช่ token

ปัญหาเดียวกันในแบบที่เงียบกว่าคือ error ที่ถูกต้องแต่ไม่บอกอะไรเลย

glyph check ก่อนและตอนนี้ 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.
รายละเอียด red-black tree และการแก้ที่ระบุโปรแกรมของคุณ

เอเจนต์ที่เขียน red-black tree หยิบ constructor ตามตำแหน่งที่ทุกภาษาตระกูล ML มี แล้ว parser หยุดที่ comma ตัวแรกพร้อม “expected )” และคำแนะนำ “add the expected token” การเพิ่ม ) ตรงนั้นได้โปรแกรมอีกตัว ไม่ใช่โปรแกรมที่ใช้งานได้ variant ของ Glyph มี payload เดียว และ payload ที่มีหลาย field คือ record ไม่มีประโยคไหนในสองประโยคนั้นอยู่ใน output เลย

นั่นแย่กับ glyph check และแย่กว่ากับ glyph lsp และ glyph mcp ซึ่งอ่านทุกไฟล์ใต้ root: ไฟล์ผิดปกติไฟล์เดียวทำให้ server ล่มทั้ง workspace ตอนนี้เป็น E0011 แจ้งที่ token ที่จะเปิดชั้นที่ 65

ขีดจำกัดคือ 64 และมาจากการวัด ไม่ใช่การเลือกเอา

รายละเอียด วัด 64 มาอย่างไร

construct ที่แพงที่สุดหนึ่งชั้น คือ array literal ที่ซ้อนกัน ใช้ stack 7,792 ไบต์ใน release build และ 8,810 ใน debug ซึ่งหาได้จากการ binary search หา thread stack ที่เล็กที่สุดที่ความลึกหนึ่งๆ จะ parse ได้ stack ที่บางที่สุดที่ parser รันคือ 2 MiB ของ thread ที่ spawn ขึ้นมา ซึ่งเป็นสิ่งที่ worker ของ language server ได้ และ 64 ชั้นใช้ไม่ถึงหนึ่งในสามของมันใน build ที่แพงกว่า การซ้อนที่ลึกที่สุดในไฟล์ .glyph 343 ไฟล์ของ repository นี้คือ 16 ขีดจำกัดครอบคลุม expression, type, pattern, block และ children ของ JSX เหมือนกัน และ array ข้างเคียงกันพันตัวยัง parse ได้ เพราะความลึกคือการซ้อนต่อ construct ไม่ใช่งบที่ใช้ไปทั้งไฟล์

เมื่อไม่มีคอมไพเลอร์ตัวไหนผิด

มีรูปแบบที่สาม และเป็นตัวที่อ่านแล้วแย่ที่สุด Glyph ไม่รายงานอะไร tsc รายงานบางอย่างที่จริง และโปรแกรมที่คุณเขียนก็ไม่ได้ผิด

สิ่งที่ล้มเหลวคือการแปลระหว่างสองตัวนั้น

poll.glyph และสิ่งที่ tsc บอกเกี่ยวกับมันก่อน 0.1.89 
fn classify() -> int {
  let done = false
  match done {
    true => { return 1 },
    false => { return 0 },
  }
}

// no Glyph diagnostic, then
[TS2678] Type 'true' is not comparable to type 'false'.
รายละเอียด ทำไม tsc เห็น false และแอปที่เจอปัญหานี้

binding ใน Glyph มี type เดียวตลอดอายุของมัน TypeScript narrow binding ให้เป็นสิ่งที่เห็นถูก assign ล่าสุด และ boolean ของมันคือ union true | false let done = false จึงไปถึง tsc ด้วย type false และ arm true ของ switch ที่ emit ก็ไม่มีอะไรให้ match

type ที่ประกาศเป็นชุดของ string literal ล้มเหลวแบบเดียวกัน และ == ก็เช่นกัน ซึ่งกลับมาเป็น TS2367 แทน: สองข้อความ สองรหัส ต้นเหตุเดียว แอปที่เจอมันกำลัง poll flag ที่ callback ของ timer ตั้ง ซึ่งเป็นวิธีเปลี่ยน API แบบ event ให้เป็นค่า ในขณะที่ Glyph ไม่มี Promise ที่คุณสร้างเองได้ callback กลายเป็นว่าไม่ใช่ประเด็น: สี่บรรทัดที่ไม่มี callback ก็ทำให้เกิดได้

การแก้ไม่ใช่ diagnostic ใหม่ เพราะไม่มีอะไรให้วินิจฉัย ตอนนี้ emitter ระบุ type ที่ตัวตรวจตัดสินไว้แล้วซ้ำอีกครั้ง ในสองที่ที่แยกแยะตามค่า: scrutinee ของ match และทั้งสองฝั่งของ == หรือ !=

รายละเอียด การตรวจที่ยังทำงานอยู่ และต้นทุนของมัน

แต่ละฝั่งตัดสินด้วย type ของตัวเองและไม่สนสิ่งที่อยู่ข้างๆ การเปรียบเทียบระหว่างสอง binding จึงถูกครอบคลุมแบบเดียวกับการเปรียบเทียบกับ literal

การตรวจที่คุณต้องการยังทำงาน m == "nope" ที่ m เป็น Mode ยังถูกปฏิเสธ และตอนนี้ข้อความระบุ Mode แทนที่จะเป็นสมาชิกตัวเดียวที่ m บังเอิญถืออยู่ การทำที่การ assign แทนจะใช้โค้ดน้อยกว่าและจะทิ้งสิ่งนั้นไป: cast เป็น Mode ถูกยอมรับในที่ที่การ assign แบบมี annotation ไม่ถูกยอมรับ และการตรวจความเป็นสมาชิกคือส่วนที่ Glyph ตั้งใจปล่อยให้ tsc

ต้นทุนมีน้อยและควรระบุ cast narrow ได้เช่นเดียวกับยืนยัน ค่าที่ Glyph ให้ type เป็น bool ซึ่ง type ใน TypeScript ออกมาเป็น unknown จึงผ่านในที่ที่ switch เคยบ่น type ทั้งสองยังต้องเทียบกันได้ model ที่เพี้ยนไปไกลพอจะมีผล อย่าง string เทียบกับ bool จึงรายงาน TS2352 แทนที่จะไม่บอกอะไร

คำผิดเดียวกัน สองคำตอบ

ฟังก์ชันของ standard library ที่สะกดผิดเคยได้คำตอบต่างกันขึ้นกับว่าคุณเขียน import แบบไหน ซึ่งเป็นความไม่สม่ำเสมอแบบที่สอนให้คุณไม่เชื่อคำตอบทั้งสอง

import ด้วยชื่อ เป็น E0105 เสมอ 
import std/string { repeeat }
[E0105] import: `repeeat` is not exported by `std/string`
การอ่านผ่าน namespace ก่อน 0.1.72 
import std/string
string.repeeat(s, 2)
[TS2551] Property 'repeeat' does not exist on type ... Did you mean 'repeat'?

ตอนนี้ทั้งสองแบบผ่านรายการ export และทั้งคู่บอก E0105 โดยระบุ member และ module ที่มันขาดไป

รายละเอียด ทำไมการเขียนสองแบบถึงต่างกัน และเปิดใช้แล้วเจออะไร

การเขียนแบบแรกถูกตรวจกับรายการ export ของ module ตอน resolve แบบที่สองไม่ถูกตรวจเลย มันจึงตกไปถึง tsc ซึ่งเห็นการเข้าถึง property บน object และตอบในแง่นั้น

การเปิดใช้มันเจอสิ่งที่ไม่มีใครมองหาทันที: test fixture ตัวหนึ่งเรียก fs.write ทั้งที่ฟังก์ชันชื่อ write_text มันผ่านมาหลายเดือนเพราะ fixture นั้นรันโดยปิดการตรวจ type และไม่มีอะไรอื่นในคอมไพเลอร์ดู member ของ namespace ตอนนี้รายการ export เป็นแหล่งอ้างอิงของทั้งสองแบบ การตรวจแยกต่างหากจึงรักษามันให้ตรงกับสิ่งที่ runtime export จริง การตรวจนั้นถูกเขียนขึ้น แล้วตั้งใจทำให้พังเพื่อยืนยันว่ามัน fail ซึ่งเป็นวิธีที่เราพบว่าเวอร์ชันแรกของมันไม่ได้ตรวจอะไรเลยแบบเงียบๆ

กำลังคมขึ้น

  • E0238 รู้ว่าการเรียกเป็น async ก็ต่อเมื่อตัวตรวจของ Glyph มี signature ของมัน

    E0238 รู้ว่าการเรียกเป็น async ก็ต่อเมื่อตัวตรวจของ Glyph มี signature ของมัน ดังนั้น promise จากแพ็กเกจ npm หรือ builtin ของ node ยังอาจถูกทิ้งไปเงียบๆ ได้ callback แบบ async ที่ส่งให้ forEach หรือ timer ก็ยังไม่ถูกปฏิเสธเช่นกัน: กฎนี้ต้องจำลองตำแหน่งของ callback ก่อน และอยู่ในแผนแล้ว

  • array.map, flat_map และ zip ยังรับ callback แบบ async โดยไม่บ่น
    รายละเอียด

    array.map, flat_map และ zip ยังรับ callback แบบ async โดยไม่บ่น และคืน array ของค่าที่ยังค้างอยู่ ซึ่งพิมพ์ออกมาเป็น [object Promise] ฟังก์ชัน array ห้าตัวที่รับ predicate หยุดมันได้ ด้วย E0211 ที่ callback การ model อีกสามตัวแบบเดียวกันจะปฏิเสธ par.all(array.map(items, async fn ...)) ด้วย ซึ่งเป็นวิธีที่ Glyph รันงานพร้อมกัน เพราะ array ของค่าที่ยังค้างไม่มีวิธีเขียนในภาษา นั่นเป็นการตัดสินใจเรื่อง type system ไม่ใช่รายการที่ขาด จึงยังเปิดอยู่

  • await ระดับบนสุดได้รับอนุญาต
    รายละเอียด

    initializer ของ const ระดับ module ไม่มีสิ่งที่เรียกได้ครอบอยู่ await ระดับบนสุดจึงได้รับอนุญาต และ ESM ที่ emit ก็รันมัน Glyph ต้องการการเริ่ม module แบบ async โดยนัยหรือไม่ยังเป็นคำถามในสเปกที่เปิดอยู่

  • E0223 ตัดสิน match ท้ายฟังก์ชันได้ก็ต่อเมื่อฟังก์ชันประกาศ return type arm ภายใน lambda ที่ไม่มี annotation จึงยังไปถึง tsc
  • E0110 บอกให้คุณเปลี่ยนชื่อแทนที่จะให้เก็บชื่อไว้
    รายละเอียด

    ฝั่งชื่อที่บังกัน มีสองอย่างที่ทำไปได้แค่ครึ่ง E0110 บอกให้คุณเปลี่ยนชื่อแทนที่จะให้เก็บชื่อไว้ Error, Number, Object, Array และ Promise จึงยังใช้เป็นชื่อ type หรือ variant ไม่ได้

  • E0111 หยุด type Key = string | number ไม่ให้มีความหมายผิด โดยไม่ได้ให้วิธีเขียนสิ่งที่ตั้งใจ
    รายละเอียด

    และ E0111 หยุด type Key = string | number ไม่ให้มีความหมายผิด โดยไม่ได้ให้วิธีเขียนสิ่งที่ตั้งใจ: union ของ primitive สอง type ไม่มีวิธีเขียนใน Glyph นอกจาก extern_ts ซึ่งตัวตรวจของมันเองมองเนื้อหาเป็นของทึบ union ที่ไม่มี tag แตะเรื่องความครบถ้วน runtime descriptor และ is ข้อนั้นจึงเป็นการตัดสินใจเรื่อง type system และยังไม่ได้กำหนดเวลา

  • E0104 ไปถึง glyph build และ glyph check แต่ไม่ถึง editor
    รายละเอียด

    E0104 ไปถึง glyph build และ glyph check แต่ไม่ถึง editor: LSP วิเคราะห์ข้อความของเอกสารโดยไม่มี build root และโฟลเดอร์ของ workspace ก็ไม่ใช่ build root การเดาจะทำให้เกิดการเตือนผิดที่การตรวจนี้ออกแบบมาให้หลีกเลี่ยง

  • parameter ที่เป็นคำสงวนยังซ่อนอยู่หลัง error ที่ไม่เกี่ยวข้องในไฟล์เดียวกัน เพราะความล้มเหลวใน pass รวบรวมจะข้าม pass resolve ที่จะเจอมัน
  • การตรึงที่จุดอ่านตาม type alias เฉพาะภายใน module ที่กำลัง emit
    รายละเอียด

    อีกเรื่องหนึ่ง การตรึงที่จุดอ่านซึ่งทำให้ binding แบบ bool หรือ union ของ string literal ยัง match ได้ ตาม type alias เฉพาะภายใน module ที่กำลัง emit pub type Ready = bool ใน module หนึ่ง และ let r: catalog.Ready = false ในอีก module จึงยังไปถึง tsc เป็น TS2678 union ของ string literal ถูกครอบคลุมข้าม module ในการ import ทั้งสามแบบ และตั้งแต่ 0.1.123 diagnostic ระบุ declaration (expected Mode) ในทุกแบบ แทนที่จะพิมพ์ชุด literal ในแบบใดแบบหนึ่ง
