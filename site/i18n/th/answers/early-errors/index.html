26 · จับได้เร็วกว่า

ทำไม Glyph จับสิ่งที่ tsc จับได้ แต่เร็วกว่า?

เพราะ error บน TypeScript ที่ generate คือ error เกี่ยวกับโค้ดที่คุณไม่ได้เขียน Glyph รายงานสิ่งเหล่านี้เทียบกับซอร์สของคุณ พร้อมกฎที่คุณละเมิดและการแก้ที่ทำให้ถูก

ทำไมเรื่องนี้สำคัญ

Glyph คอมไพล์เป็น TypeScript แล้วตรวจ type ของ output ด้วย tsc --strict ความผิดพลาดที่ Glyph ไม่ได้ model จึงไม่หายไป มันกลับมาในขั้นถัดไป โดยพูดในแง่ของไฟล์ที่ emit: TS1308 ที่ชี้ไปที่ await ในฟังก์ชันที่คุณไม่เคยเขียน หรือ TS2366 เกี่ยวกับ switch ที่คุณไม่ได้เขียน บรรทัดถูก map กลับไปยัง .glyph ของคุณ แต่คำอธิบายไม่ได้ถูก map

ช่องว่างนั้นคือที่ที่คอมไพเลอร์เลิกสอน กฎแต่ละข้อที่ Glyph ตัดสินเองได้จึงย้ายขึ้นมา: await นอก async fn (E0222), arm ของ match ที่ไม่ให้ค่าในขณะที่ match ถูกใช้เป็นค่า (E0223) และการ assign ที่เขียนโดยไม่มี mut (E0008) แต่ละข้อระบุกฎ อ้าง decision ที่อยู่เบื้องหลัง และแสดงก่อนและหลัง

ดูของจริง

กรณีของ arm คือตัวที่เคยหลุดไปทั้งหมด {} ในตำแหน่ง arm คือ block ว่าง ไม่ใช่ record ว่าง arm จึงรันและไม่ให้อะไรออกมา:

status.glyph: arm ที่ไม่ให้อะไรเลย ในตำแหน่งที่ต้องการค่า 
fn label(s: Status) -> string {
  let text = match s {
    Loading => {},          // an empty block: the arm produces no value
    Ready => "done",
    Failed(msg) => msg,
  }
  return text
}
glyph build 
[E0223] this `match` arm produces no value, but the `match` is used as a value
   ╰─ End the arm with an expression, or `return` from it. `X => {}` is a no-op
      only where the `match` is a statement.
   note: A value-position arm lowers to `case X: { break; }` when it yields
         nothing, so the value would be `undefined` at run time.

ก่อนหน้านี้ switch ที่ emit หลุดออกจาก case ของตัวเอง และ text ถือ undefined ขณะที่ type บอกว่า string tsc จับบางรูปแบบได้และพลาดบางรูปแบบ ตอนนี้ Glyph ตัดสินทุกที่ที่ตำแหน่งตัดสินได้: let, mut, return หรือส่วนท้ายของฟังก์ชันที่ประกาศ return type match แบบ statement ยังเก็บ X => {} ไว้เป็นการไม่ทำอะไรโดยตั้งใจตามที่มันเป็น

await ก็ย้ายแบบเดียวกัน Glyph ไม่มี Promise ที่ผู้ใช้มองเห็น: async fn -> T ถูก await ได้เป็น T await ที่อื่นจึงไม่มีอะไรให้พักรอ สิ่งนั้นเคยเป็น TS1308 ของ tsc บนไฟล์ที่ generate ตอนนี้เป็น E0222 และสิ่งที่เรียกได้ซึ่งครอบอยู่ชั้นในสุดเป็นตัวตัดสิน lambda แบบ synchronous ภายใน async fn จึงเป็นบริบทของตัวเอง ซึ่งเป็นกฎเดียวกับที่ TypeScript ใช้

glyph build บน `fn total() -> number { return await fetch_count() }` 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

ตัวที่สามเกี่ยวกับกฎที่คนละเมิดตั้งแต่วันแรก Glyph ทำเครื่องหมายทุกการแก้ค่า การ assign binding ใหม่คือ mut x = e และการสร้างใหม่คือ let x = e x = e เปล่าๆ เคยรายงาน "unexpected token: Equals" ซึ่งระบุอักขระแทนที่จะระบุกฎ ตอนนี้เป็น E0008 และ glyph --explain E0008 อธิบายว่าทำไมเครื่องหมายนี้มีอยู่: ทุกที่ที่ค่าเปลี่ยนขึ้นต้นด้วย mut grep "mut total" จึงเจอทุกจุด

operator ? ได้การดูแลแบบเดียวกันจากอีกทาง ? ขยายเป็น binding บวก return ก่อนเวลาที่วางไว้ก่อน statement ที่มันอยู่ มันจึงต้องมี statement ให้ขยายเข้าไป มันใช้ได้ใน let, return, argument และตอนนี้ใน body ของ arm ของ match ด้วย ตรงไหนที่ใช้ไม่ได้ ข้อความจะบอกว่าเป็นตำแหน่งไหนและจะ bind ออกมาอย่างไร (E0302 และ E0303) แทนที่จะอ้างว่า operator ยังไม่ได้ implement

กรณีที่แย่กว่า: เมื่อ tsc ก็พอใจด้วย

error ของ tsc ในที่ผิดเป็นเรื่องน่ารำคาญ build ที่สะอาดบนโปรแกรมที่มีความหมายอีกอย่างคือปัญหาจริง และ Glyph เคยมี ทุกชื่อระดับบนสุดที่คุณประกาศเข้าไปใน module ที่ emit ตรงตัว รวมถึง constructor ของ variant ใน tagged union variant ชื่อ Error จึง emit export function Error(...) ที่ระดับบนสุดของ module แล้ว new Error(...) ที่คอมไพเลอร์เขียนไว้ข้างล่างก็เรียก variant ของคุณ

type Key = string | number คือข้อบกพร่องเดียวกันในหน้าตาที่เป็นมิตรกว่า ใน Glyph A | B ประกาศ tagged union ที่สมาชิกเป็นconstructorของ variant บรรทัดนั้นจึงประกาศ variant ชื่อ string และ number มันคอมไพล์ผ่าน ผ่าน tsc --strict และ emit export const number ที่บัง namespace number ของ prelude ไม่มีอะไร fail จนกระทั่งการเรียก number.to_string ทีหลัง fail

span คือ declaration ซึ่งเป็นที่ที่ต้องเปลี่ยนชื่อ รายการที่ป้องกันไว้ derive มาจาก emitter ไม่ใช่จากรายการ global ของ JavaScript ทั่วไป และมีเทสต์ที่ grep emitter แล้ว fail เมื่อมีการอ้างถึง global ใหม่โดยไม่มีรายการที่ตรงกัน เทสต์นั้นคือประเด็น: Number ไม่มีพิษภัยจนกระทั่ง int ออกมาและเริ่ม emit Number.isInteger ซึ่งเป็นวิธีที่เรื่องนี้หลุดไปถึงรุ่นที่ออกตั้งแต่แรก Date, Math และ JSON ยังใช้ได้ เพราะไม่มีอะไรที่ Glyph emit อ้างถึงมัน

กรณี union ของ primitive ได้รหัสของตัวเองคือ E0111 เพราะการปฏิเสธโดยไม่อธิบายไม่ได้สอนอะไร มันบอกว่าบรรทัดนั้นถูก parse เป็นอะไรจริงๆ ชี้ไปที่ variant ที่มีชื่อ และระบุ extern_ts("string | number") สำหรับขอบเขตที่คุณต้องการ union ของ TypeScript ดิบ ทุกชื่อที่ Glyph ไม่ให้ใช้อยู่ในตารางใน docs/reference/reserved-words.md: keyword 32 คำ คำสงวนของ TypeScript 33 คำที่อยู่เบื้องหลัง E0109 และรายการชื่อที่บังกัน แต่ละคำมีเหตุผลว่าทำไมชื่อนั้นถูกจองไว้

ควรพูดให้ชัดว่าสิ่งนี้ไม่ได้ทำอะไร คุณยังตั้งชื่อ type หรือ variant ว่า Error ไม่ได้ และ spreadsheet ที่ทำให้เรื่องนี้โผล่ขึ้นมาก็มี variant ชื่อ Cellerr เพราะเหตุนี้ โปรแกรมที่มันอยากเป็นยังเขียนไม่ได้ สิ่งที่เปลี่ยนคือตอนนี้คอมไพเลอร์บอกที่ declaration แทนที่จะปล่อยให้ build เขียวแล้วมีความหมายอีกอย่าง การทำให้ชื่อนั้นใช้ได้หมายถึงต้องแปลงชื่อของ Glyph ตอนเข้าสู่ TypeScript ซึ่งเปลี่ยนสิ่งที่ stack trace, grep บน dist/ และ shim extern/ ที่เขียนเองมองเห็น จึงไม่ใช่ patch ที่เราทำแบบเงียบๆ ได้

ข้อความที่ผิดแย่กว่าไม่มีข้อความ

รายการชื่อที่บังกันเริ่มจากชื่อที่ emitter เขียนเป็นค่า มันขาดชื่อที่ emitter เขียนเป็นtype และนั่นทำให้เกิดปัญหานี้ในแบบที่แหลมคมที่สุด parse ของทุก descriptor คืน Result<T, Issue[]> module ที่ emit จึงเขียน Issue ไม่ว่าคุณจะเขียนหรือไม่ ประกาศ type Issue = { path: Array<string>, message: string } ใน module ของคุณเอง แล้วของคุณจะชนะ object Issue ที่ emit มี field code ที่ของคุณไม่รู้จัก และ build fail ด้วย error ของ tsc เกี่ยวกับโค้ดที่ generate ที่ span ซึ่งชี้ไปที่อื่น

specify known properties, and 'code' does not exist in type 'Issue'.

Record เข้ารายการในเวลาเดียวกัน โดยจัดไว้กับ global ของ JavaScript แทนที่จะเป็นชื่อใน prelude เพราะมันเป็น built-in ของ TypeScript และการอ้างเป็นอย่างอื่นจะทำให้ข้อความผิดเรื่องที่มาของชื่อ เทสต์ตรวจความเพี้ยนที่ grep emitter ตอนนี้ครอบคลุม type แบบ ambient ด้วย และต้องเรียนรู้ที่จะเห็น Issue[] ในตำแหน่ง type ซึ่งเป็นเหตุผลที่เรื่องนี้หลุดไปถึงรุ่นที่ออก Schema, Component และ Option ยังใช้ได้ตามกฎเดียวกับที่ทำให้ Date ใช้ได้: emitter เขียนมันก็เพราะคุณเขียนไว้ใน annotation การประกาศมันจึงไม่บังอะไร

อีกตัวในกลุ่มนี้คือ import path ของ import ในเครื่อง resolve จาก build root คือไดเรกทอรีที่คุณส่งให้ glyph build ไม่ใช่จากไดเรกทอรีของไฟล์ที่ import build tree ที่ครอบอยู่แล้ว import catalog หาอะไรไม่เจอ และจนถึงตอนนี้ไม่มีอะไรบอก type ลดลงเป็น unknown match บนมันเสีย variant ที่มันกำลัง match และสิ่งที่คุณได้คือ E0218 match ไม่ครบ บน match ที่ครอบคลุมทุก case ถ้าทำตามที่ข้อความนั้นขอ ก็จะเพิ่ม arm else ที่ไม่มีวันรันให้โค้ดที่ถูกต้อง

        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from

ความเสี่ยงของการตรวจแบบนี้คือมันเตือนสิ่งที่ไม่ได้ผิด และตัวตรวจ import ที่ร้องเตือนทุกแพ็กเกจ npm แย่กว่าความเงียบที่มันมาแทน build จึงรวบรวมชื่อ module ที่ resolve ได้โดยไม่ต้องมีไฟล์ .glyph ก่อน: ทุก declare module "X" ใต้ <root>/.types/ และใน Node shim ที่มาด้วย บวกทุกแพ็กเกจใน node_modules ของโปรเจกต์ ชื่อที่อยู่ในรายการนั้นไม่เคยถูกรายงาน แม้ไฟล์ในเครื่องจะบังเอิญชื่อเดียวกัน เมื่อโปรเจกต์ไม่มี node_modules เลย คอมไพเลอร์แยก dependency ที่ยังไม่ได้ติดตั้งออกจากคำผิดไม่ได้ มันจึงรายงานเฉพาะสิ่งที่พิสูจน์ได้: import ที่มีไฟล์ .glyph ใต้ root ตอบรับอยู่

การ resolve เองไม่ได้เปลี่ยน โปรแกรมเดิม build ผ่าน และโปรแกรมเดิม fail สิ่งที่เปลี่ยนคือความล้มเหลวตอนนี้ระบุ import แทนที่จะกล่าวหา match ที่อยู่ห่างไปสองไฟล์ ซึ่งคือทั้งหมดของเรื่อง: คอมไพเลอร์ที่รายงานต้นเหตุผิดทำให้คุณเสียเวลาหนึ่งชั่วโมงไปไล่มัน และเสียความเชื่อใจในทุกข้อความหลังจากนั้น

ระบุกฎ ไม่ใช่ token

ปัญหาเดียวกันในแบบที่เงียบกว่าคือ error ที่ถูกต้องแต่ไม่บอกอะไรเลย เอเจนต์ที่เขียน red-black tree หยิบ constructor ตามตำแหน่งที่ทุกภาษาตระกูล ML มี แล้ว parser หยุดที่ comma ตัวแรกพร้อม “expected )” และคำแนะนำ “add the expected token” การเพิ่ม ) ตรงนั้นได้โปรแกรมอีกตัว ไม่ใช่โปรแกรมที่ใช้งานได้ variant ของ Glyph มี payload เดียว และ payload ที่มีหลาย field คือ record ไม่มีประโยคไหนในสองประโยคนั้นอยู่ใน output เลย

glyph check ก่อนและตอนนี้ 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.

การจะพูดแบบนั้นได้ parser ต้องอ่านทั้ง list ก่อนปฏิเสธ ซึ่งก็ทำให้มันนับได้ด้วย span ขีดเส้นใต้ทั้งหก field แทนที่จะเป็นตัวคั่นที่มันบังเอิญไปตาย และ record ที่แนะนำสร้างจากชื่อ variant และหก type ในไฟล์ วิธีแก้จึงระบุโปรแกรมของคุณ ไม่ใช่ตัวอย่างของคนอื่น ชื่อ field เป็นสิ่งเดียวที่คอมไพเลอร์ใส่ให้ไม่ได้ มันจึงเว้นไว้เป็นช่องว่าง

กฎเบื้องหลังข้อความเป็นการเลือก ไม่ใช่ช่องว่าง Node(Black, l, x, b, h, r) คือการสลับ argument ที่ตรวจ type ผ่าน และตำแหน่งที่สี่ไม่บอกอะไรคนอ่าน การเขียนแบบ record ระบุทุก field arm ของ match ระบุแค่ field ที่ใช้ และทั้งสองอย่างเป็นสิ่งที่ grep หาเจอ

[TS2678] Type 'true' is not comparable to type 'false'.

type ที่ประกาศเป็นชุดของ string literal ล้มเหลวแบบเดียวกัน และ == ก็เช่นกัน ซึ่งกลับมาเป็น TS2367 แทน: สองข้อความ สองรหัส ต้นเหตุเดียว แอปที่เจอมันกำลัง poll flag ที่ callback ของ timer ตั้ง ซึ่งเป็นวิธีเปลี่ยน API แบบ event ให้เป็นค่า ในขณะที่ Glyph ไม่มี Promise ที่คุณสร้างเองได้ callback กลายเป็นว่าไม่ใช่ประเด็น: สี่บรรทัดที่ไม่มี callback ก็ทำให้เกิดได้

การแก้ไม่ใช่ diagnostic ใหม่ เพราะไม่มีอะไรให้วินิจฉัย ตอนนี้ emitter ระบุ type ที่ตัวตรวจตัดสินไว้แล้วซ้ำอีกครั้ง ในสองที่ที่แยกแยะตามค่า: scrutinee ของ match และทั้งสองฝั่งของ == หรือ != แต่ละฝั่งตัดสินด้วย type ของตัวเองและไม่สนสิ่งที่อยู่ข้างๆ การเปรียบเทียบระหว่างสอง binding จึงถูกครอบคลุมแบบเดียวกับการเปรียบเทียบกับ literal

การตรวจที่คุณต้องการยังทำงาน m == "nope" ที่ m เป็น Mode ยังถูกปฏิเสธ และตอนนี้ข้อความระบุ Mode แทนที่จะเป็นสมาชิกตัวเดียวที่ m บังเอิญถืออยู่ การทำที่การ assign แทนจะใช้โค้ดน้อยกว่าและจะทิ้งสิ่งนั้นไป: cast เป็น Mode ถูกยอมรับในที่ที่การ assign แบบมี annotation ไม่ถูกยอมรับ และการตรวจความเป็นสมาชิกคือส่วนที่ Glyph ตั้งใจปล่อยให้ tsc

ต้นทุนมีน้อยและควรระบุ cast narrow ได้เช่นเดียวกับยืนยัน ค่าที่ Glyph ให้ type เป็น bool ซึ่ง type ใน TypeScript ออกมาเป็น unknown จึงผ่านในที่ที่ switch เคยบ่น type ทั้งสองยังต้องเทียบกันได้ model ที่เพี้ยนไปไกลพอจะมีผล อย่าง string เทียบกับ bool จึงรายงาน TS2352 แทนที่จะไม่บอกอะไร

คำผิดเดียวกัน สองคำตอบ

ฟังก์ชันของ standard library ที่สะกดผิดเคยได้คำตอบต่างกันขึ้นกับว่าคุณเขียน import แบบไหน ซึ่งเป็นความไม่สม่ำเสมอแบบที่สอนให้คุณไม่เชื่อคำตอบทั้งสอง

import ด้วยชื่อ เป็น E0105 เสมอ 
import std/string { repeeat }
[E0105] import: `repeeat` is not exported by `std/string`
การอ่านผ่าน namespace ก่อน 0.1.72 
import std/string
string.repeeat(s, 2)
[TS2551] Property 'repeeat' does not exist on type ... Did you mean 'repeat'?

การเขียนแบบแรกถูกตรวจกับรายการ export ของ module ตอน resolve แบบที่สองไม่ถูกตรวจเลย มันจึงตกไปถึง tsc ซึ่งเห็นการเข้าถึง property บน object และตอบในแง่นั้น ตอนนี้ทั้งสองแบบผ่านรายการ export และทั้งคู่บอก E0105 โดยระบุ member และ module ที่มันขาดไป

การเปิดใช้มันเจอสิ่งที่ไม่มีใครมองหาทันที: test fixture ตัวหนึ่งเรียก fs.write ทั้งที่ฟังก์ชันชื่อ write_text มันผ่านมาหลายเดือนเพราะ fixture นั้นรันโดยปิดการตรวจ type และไม่มีอะไรอื่นในคอมไพเลอร์ดู member ของ namespace ตอนนี้รายการ export เป็นแหล่งอ้างอิงของทั้งสองแบบ การตรวจแยกต่างหากจึงรักษามันให้ตรงกับสิ่งที่ runtime export จริง การตรวจนั้นถูกเขียนขึ้น แล้วตั้งใจทำให้พังเพื่อยืนยันว่ามัน fail ซึ่งเป็นวิธีที่เราพบว่าเวอร์ชันแรกของมันไม่ได้ตรวจอะไรเลยแบบเงียบๆ

สถานะตอนนี้

ใช้ได้วันนี้

E0222 สำหรับ await นอก async fn, E0223 สำหรับ arm ของ match ในตำแหน่งค่าที่ไม่ให้ค่า, E0008 สำหรับการ assign ที่ขาด mut, E0010 สำหรับ variant ที่ได้ payload ตามตำแหน่งหลาย field ในขณะที่รูปแบบ record คือรูปแบบที่มีอยู่, E0302/E0303 สำหรับ ? ในตำแหน่งที่ส่งต่อไม่ได้, E0110/E0111 สำหรับ declaration ที่จะบังชื่อที่ module ที่ emit พึ่งพาอยู่, E0104 สำหรับ import ในเครื่องที่ไม่ได้ระบุ module ใต้ build root, E0105 สำหรับชื่อที่ module ไม่ได้ export ไม่ว่าคุณจะเข้าถึงผ่าน import ด้วยชื่อหรือผ่าน namespace, E0228 สำหรับชื่อของ type ที่เขียนในที่ที่ต้องการค่า, E0013 สำหรับ statement ที่เริ่มบนบรรทัดที่อีกตัวจบ ซึ่งเคยทิ้งค่าที่ตามมา, E0204/E0211 สำหรับ container ของ prelude ที่ถูก assign หรือส่งเป็น primitive หรือ record หรือ union ที่ประกาศไว้ รวมถึงกรณี Nullable<T> ที่ tsc narrow ทิ้งไป, E0210 สำหรับ member ที่ array หรือ string ไม่มี, สองรหัสเดียวกันสำหรับค่าที่ไม่อยู่ในชุดที่ union ของ string literal ประกาศไว้, E0011 สำหรับ construct ที่ซ้อนเกิน 64 ชั้น, E0101 สำหรับ path ของ import แบบ relative ซึ่งเคยหยุดใน parser ด้วย "expected module path segment" ทั่วไป และ E0113 สำหรับ module ในโปรเจกต์ที่ประกาศใต้ std/ หรือ extern/ ซึ่งเคยคอมไพล์ผ่านสะอาดแต่เข้าถึงไม่ได้ รายการชื่อที่บังกันครอบคลุม type ที่ emitter เขียนเอง Issue และ Record จึงถูกจับที่ declaration ทุกรหัสมีวิธีแก้หนึ่งบรรทัด note ที่อธิบายกฎ และคำอธิบายแบบยาวใน glyph --explain docs/error-codes.md แสดงแคตตาล็อก และมีเทสต์รักษาทั้งสองให้ตรงกัน

กำลังคมขึ้น

array.map, flat_map และ zip ยังรับ callback แบบ async โดยไม่บ่น และคืน array ของค่าที่ยังค้างอยู่ ซึ่งพิมพ์ออกมาเป็น [object Promise] ฟังก์ชัน array ห้าตัวที่รับ predicate หยุดมันได้ ด้วย E0211 ที่ callback การ model อีกสามตัวแบบเดียวกันจะปฏิเสธ par.all(array.map(items, async fn ...)) ด้วย ซึ่งเป็นวิธีที่ Glyph รันงานพร้อมกัน เพราะ array ของค่าที่ยังค้างไม่มีวิธีเขียนในภาษา นั่นเป็นการตัดสินใจเรื่อง type system ไม่ใช่รายการที่ขาด จึงยังเปิดอยู่ initializer ของ const ระดับ module ไม่มีสิ่งที่เรียกได้ครอบอยู่ await ระดับบนสุดจึงได้รับอนุญาต และ ESM ที่ emit ก็รันมัน Glyph ต้องการการเริ่ม module แบบ async โดยนัยหรือไม่ยังเป็นคำถามในสเปกที่เปิดอยู่ E0223 ตัดสิน match ท้ายฟังก์ชันได้ก็ต่อเมื่อฟังก์ชันประกาศ return type arm ภายใน lambda ที่ไม่มี annotation จึงยังไปถึง tsc ฝั่งชื่อที่บังกัน มีสองอย่างที่ทำไปได้แค่ครึ่ง E0110 บอกให้คุณเปลี่ยนชื่อแทนที่จะให้เก็บชื่อไว้ Error, Number, Object, Array และ Promise จึงยังใช้เป็นชื่อ type หรือ variant ไม่ได้ และ E0111 หยุด type Key = string | number ไม่ให้มีความหมายผิด โดยไม่ได้ให้วิธีเขียนสิ่งที่ตั้งใจ: union ของ primitive สอง type ไม่มีวิธีเขียนใน Glyph นอกจาก extern_ts ซึ่งตัวตรวจของมันเองมองเนื้อหาเป็นของทึบ union ที่ไม่มี tag แตะเรื่องความครบถ้วน runtime descriptor และ is ข้อนั้นจึงเป็นการตัดสินใจเรื่อง type system และยังไม่ได้กำหนดเวลา E0104 ไปถึง glyph build และ glyph check แต่ไม่ถึง editor: LSP วิเคราะห์ข้อความของเอกสารโดยไม่มี build root และโฟลเดอร์ของ workspace ก็ไม่ใช่ build root การเดาจะทำให้เกิดการเตือนผิดที่การตรวจนี้ออกแบบมาให้หลีกเลี่ยง และ parameter ที่เป็นคำสงวนยังซ่อนอยู่หลัง error ที่ไม่เกี่ยวข้องในไฟล์เดียวกัน เพราะความล้มเหลวใน pass รวบรวมจะข้าม pass resolve ที่จะเจอมัน อีกเรื่องหนึ่ง การตรึงที่จุดอ่านซึ่งทำให้ binding แบบ bool หรือ union ของ string literal ยัง match ได้ ตาม type alias เฉพาะภายใน module ที่กำลัง emit pub type Ready = bool ใน module หนึ่ง และ let r: catalog.Ready = false ในอีก module จึงยังไปถึง tsc เป็น TS2678 union ของ string literal ถูกครอบคลุมข้าม module ในการ import ทั้งสามแบบ และตั้งแต่ 0.1.123 diagnostic ระบุ declaration (expected Mode) ในทุกแบบ แทนที่จะพิมพ์ชุด literal ในแบบใดแบบหนึ่ง
