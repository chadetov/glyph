17 · เงินและความปลอดภัย

ไว้ใจมันกับเรื่องเงิน และกับ input ที่ควบคุมไม่ได้ได้ไหม?

ได้ เงินแม่นยำ invariant อย่างไม่ติดลบเป็นtype ที่ขอบเขตบังคับใช้ และ input ที่ไม่น่าไว้ใจไปถึง sink ของ SQL หรือ shell ไม่ได้ถ้าไม่ผ่านการ sanitize แต่ละข้อเป็น error ตอนคอมไพล์หรือตอน parse ถ้าคุณทำผิด ไม่ใช่ธรรมเนียมที่ใครสักคนต้องจำไว้ห่างออกไปสามฟังก์ชัน

ในหน้านี้

  1. เงินไม่ใช่ float
  2. id และตัวนับ
  3. invariant เป็น type
  4. Injection
  5. สถานะตอนนี้

เงินไม่ใช่ float

std/decimal เป็น fixed-point ฐานสิบที่แม่นยำบน BigInt

  • เลขคณิตที่แม่นยำการบวก ลบ และคูณแม่นยำ
  • การหารการหารต้องระบุ scale และปัดครึ่งออกจากศูนย์
  • input ที่ผิดจำนวนเงินที่ผิดรูป parse ได้เป็น Err ไม่มีวันเป็น NaN แบบเงียบๆ

id และตัวนับยังแม่นยำเมื่อเกิน 253

id บัญชีหรือตัวนับในบัญชีแยกประเภทที่ล้นช่วงของ float แล้วถูกปัด เป็นหายนะอีกแบบหนึ่ง

bigint คือจำนวนเต็มความแม่นยำไม่จำกัดที่แม่นยำ มี literal แบบ 123n และ field ของ record ที่มี type เป็น bigint จะ validate typeof === "bigint" ที่ขอบเขต id ที่มาเป็น number ใน JSON จึงถูกปฏิเสธแทนที่จะถูกตัดทอนไปเงียบๆ

invariant เป็น type ไม่ใช่ comment

"จำนวนเงินไม่ติดลบ" และ "คะแนนอยู่ระหว่าง 1 ถึง 5" คือการตรวจที่เขียนครั้งเดียวแล้วถูกลืมทีหลัง refinement แบบ where ใส่ invariant ไว้ใน type และ descriptor บังคับใช้มันที่ขอบเขต

refinements.glyph 
type Amount = int where value >= 0
type Rating = int where value >= 1 && value <= 5

Amount.parse(-1)   # Err  (not just "is a number")
Rating.parse(6)    # Err
Amount.parse(3.5)  # Err  (int check too)

ค่าที่ไม่ผ่าน predicate จะไม่มีวันกลายเป็น Amount ตั้งแต่แรก

injection เป็น compile error

เส้นทางคลาสสิกสู่การรันโค้ดจากระยะไกลคือ input ที่ไม่น่าไว้ใจไปถึง SQL query, คำสั่ง shell หรือ template HTML std/taint ทำให้สิ่งนั้นเป็น type error

  • สอง typeค่าจากภายนอกเป็น Tainted sink ที่คุณต้องการป้องกันรับ Trusted
  • ทางข้ามทางเดียวทั้งสองต่างกันในเชิงโครงสร้าง ทางเดียวที่จะไปจากตัวหนึ่งสู่อีกตัวคือ sanitize ที่เขียนชัดแจ้ง
เส้นทางที่ปลอดภัยคอมไพล์ผ่าน 
fn run_query(sql: Trusted<string>) -> void { ... }

let input: Tainted<string> = taint(req.body)
run_query(sanitize(input, escape))   # ok
เส้นทางที่มี injection คอมไพล์ไม่ผ่าน 
module query

import std/taint { Tainted, Trusted, taint, expose }

fn run_query(sql: Trusted<string>) -> string {
  return expose(sql)
}

pub fn handle(body: string) -> string {
  let input: Tainted<string> = taint(body)
  return run_query(input)
}

// [E0211] argument type mismatch: expected
//   `taint.Trusted<string>`, found
//   `taint.Tainted<string>` (query.glyph:11)

ส่งค่าที่ tainted ให้ sink ตรงๆ แล้ว tsc จะไม่ยอมคอมไพล์

สถานะตอนนี้

ใช้ได้วันนี้

  • std/decimal สำหรับเงินที่แม่นยำ
  • bigint สำหรับจำนวนเต็มขนาดใหญ่ที่แม่นยำ
  • refinement แบบ where เพื่อให้ invariant ถูก validate ที่ขอบเขต
  • std/taint เพื่อให้ input ที่ไม่น่าไว้ใจไปถึง sink ที่ป้องกันไว้ไม่ได้ถ้าไม่มี sanitize ที่ชัดแจ้ง
  • แต่ละข้อถูกตรวจ: จำนวนเงินหรือ id ที่ผิด fail ที่ parse, invariant ที่ผิด fail ที่ parse และค่าที่ไม่ผ่านการ sanitize fail ที่ tsc

หยุดตรงไหน

  • ตอนนี้ refinement แบบ where ครอบคลุม type พื้นฐานที่เป็น primitive ส่วน invariant ของ record และข้าม field (where value.paid <= value.total) เป็นส่วนขยายที่วางแผนไว้
  • taint เป็นวินัยที่คุณเลือกใช้โดยให้ type ของ sink เป็น Trusted ไม่ใช่การวิเคราะห์ flow อัตโนมัติ
    รายละเอียด

    taint เป็นวินัยที่คุณเลือกใช้โดยให้ type ของ sink เป็น Trusted ไม่ใช่การวิเคราะห์ flow อัตโนมัติ: คอมไพเลอร์บังคับใช้ขอบเขตที่คุณประกาศ มันไม่ได้อนุมาน taint ทั่วทั้งโปรแกรมให้คุณ
