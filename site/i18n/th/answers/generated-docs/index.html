24 · เอกสารที่เพี้ยนไม่ได้

เอกสารที่เอเจนต์อ่านถูก generate ขึ้นมา หรือเขียนด้วยมือและล้าสมัย?

generate ขึ้นมา glyph llms --json emit แคตตาล็อก diagnostic, prelude, signature ของ stdlib, decision ของภาษา และคู่มือเครื่องมือ ออกมาจากตารางของคอมไพเลอร์เอง และมี gate ที่ทำให้ build fail เมื่อสำเนาที่เขียนด้วยมือไม่ตรงกัน ทุกตัวอย่าง Glyph ในเอกสารที่เอเจนต์ใช้เริ่มต้นถูกคอมไพล์ รวมถึงตัวที่ผิดด้วย

ทำไมเรื่องนี้สำคัญ

คำถามนี้ไม่ใช่วาทศิลป์ เพราะคำตอบตรงๆ เคยเป็น "เขียนด้วยมือ และใช่" เอกสารเริ่มต้นสำหรับเอเจนต์บอกว่าเซิร์ฟเวอร์ MCP "exposes five tools" และแสดงห้าตัว เซิร์ฟเวอร์ให้บริการเจ็ดตัว สองตัวที่คำแนะนำของเซิร์ฟเวอร์เองบอกให้เอเจนต์ใช้ก่อนไม่ปรากฏในนั้นเลย รหัส error 58 ตัวอยู่ในสำเนาที่ดูแลด้วยมือสามชุด ตรวจแค่ว่ามี string ของรหัสอยู่หรือไม่ จากตัวอย่าง Glyph 19 ตัวในเอกสารนั้น คอมไพล์ 2 ตัว และ 17 ตัวถูกข้ามไปในฐานะชิ้นส่วน

ทุกข้อเหล่านั้นคือข้อบกพร่องเดียวกัน เอกสารเกี่ยวกับคอมไพเลอร์ ดูแลอยู่ข้างคอมไพเลอร์ โดยคนที่มีเจตนาดี เอเจนต์ที่อ่านมันบอกไม่ได้ว่าประโยคไหนยังจริงอยู่ และเราก็บอกไม่ได้เช่นกัน

ดูของจริง

เจ็ดส่วน แต่ละส่วนอ่านจากตารางที่คอมไพเลอร์มีอยู่แล้ว รายการ diagnostic มีประโยคจากแคตตาล็อก วิธีแก้หนึ่งบรรทัด คำอธิบายแบบยาว และ help กับ note ที่เอามาจาก diagnostic ที่คอมไพเลอร์สร้าง 51 จาก 77 รหัสมีโปรแกรมที่ผิดซึ่งได้รหัสนั้นด้วย คอมไพล์ตอนที่คุณถาม อีก 26 ตัวบอกว่าชุดตัวอย่างไม่มีกรณีสำหรับมัน

รหัส 77 ตัวมาจากตารางเดียวในคอมไพเลอร์ และ docs/error-codes.md กับตารางแคตตาล็อกในเอกสารเริ่มต้นสำหรับเอเจนต์ถูกเขียนจากมันโดยสคริปต์ที่ fail เมื่อเพี้ยน การรวมสามสำเนาที่เคยมีเจอรหัสหนึ่งที่มีคำอธิบายแต่ไม่มีที่ในรายการ และแถวหนึ่งที่ pipe ที่ escape ไว้ทำให้ตารางที่มันอยู่พังไปเงียบๆ

prelude, stdlib และ decision

prelude คือ 24 ชื่อที่ resolver ใช้ resolve พร้อมบอกว่าแต่ละตัวคืออะไร stdlib คือ 40 module กับ 340 export และแต่ละ signature อ่านออกมาจากตารางของตัวตรวจเอง และพิมพ์ด้วย type printer ตัวเดียวกับที่ diagnostic ใช้ signature ในเอกสารจึงเป็น signature ที่ตัวตรวจจะบังคับคุณ export แบ่งเป็นสามกลุ่มเสมอ ไม่ใช่สอง: 129 signature ถูก model ครบทุกตำแหน่ง 46 ตัวมี ? ในตำแหน่งที่ควรเป็น type ของ parameter และนับเป็น partially_modeled พร้อมบรรทัดที่บอกว่ายังเหลืออีกกี่ตำแหน่ง และ 165 ตัวไม่มี signature เลย ? คือ unknown ที่ถูก render จึงไม่เคยถูกเผยแพร่เป็น signature ที่สมบูรณ์

duplicate_numbers มีอยู่เพราะ generator อ่านรายการของสเปกเอง และครั้งแรกที่รัน มันเจอ decision สองข้อที่ต่างกันแต่มีหมายเลข D43 ทั้งคู่ แล้วพิมพ์ "duplicate_numbers": [43] มันรายงานการชนแทนที่จะตัดตัวซ้ำทิ้ง ซึ่งเป็นวิธีที่ทำให้มีคนรู้ ไม่มีอะไรในคอมไพเลอร์ใช้หมายเลข D เป็น key จึงไม่มีโปรแกรมไหนได้รับผลกระทบ แต่คนอ่านที่ตามการอ้างอิงได้รับผลกระทบ ข้อนั้นแก้แล้ว: D43 คือกฎ mut ข้าม await และ never คือ D47 รายการจึงกลับมาว่าง ตอนนี้มี 49 decision ตั้งแต่ D1 ถึง D49

โปรแกรมที่ผิดก็อ่านได้เช่นกัน

ชุดตัวอย่างเชิงลบของคอมไพเลอร์คือชุดโปรแกรมที่ต้อง fail พร้อมรหัสที่แต่ละตัวต้องได้ มันเคยมองเห็นได้แค่จาก cargo test เอเจนต์ที่กำลังเรียนรู้ว่ากฎปฏิเสธอะไรคือผู้อ่านที่มันถูกเขียนมาให้ ตอนนี้มันจึงตอบได้ และแต่ละกรณีถูกคอมไพล์เมื่อคุณถาม diagnostic ข้างๆ จึงเป็นของคอมไพเลอร์ตัวนี้

ถ้าไม่ระบุรหัส มันแสดง 117 กรณีบน 53 จาก 77 รหัสใน 0.1.149 และระบุชื่อ 24 รหัสที่ไม่มี แทนที่จะปล่อยให้คุณอนุมานความครอบคลุมจากสิ่งที่กลับมา ชุดที่สองคือ catches/ จับคู่โปรแกรมที่ tsc --strict ยอมรับกับ Glyph ที่ปฏิเสธมัน และกลับมาในคำตอบเดียวกันเมื่อมี ทั้งสองชุดฝังมาจากไดเรกทอรีเอง กรณีที่เพิ่มในชุดไหนก็อยู่ในคำตอบโดยไม่ต้องจำไปแก้ที่ที่สอง

ทุกตัวอย่างคอมไพล์ได้ รวมถึงตัวที่ผิด

การ generate เอกสารอ้างอิงเป็นแค่ครึ่งเดียว อีกครึ่งคือร้อยแก้วที่เอเจนต์ใช้เริ่มต้น ซึ่งตัวอย่างคือส่วนที่มันลอกไป ทุก fence ของ Glyph ในเอกสารนั้นเป็นโปรแกรมสมบูรณ์ที่คอมไพล์ได้ หรือถูกทำเครื่องหมายว่าเป็นชิ้นส่วนของตัวอย่างสมบูรณ์ที่มีชื่อ ซึ่งบรรทัดของมันต้องปรากฏอยู่ในนั้น เคยมี 19 fence คอมไพล์ 2 ตอนนี้มี 24 คอมไพล์ 20 ทำเครื่องหมาย 4 และไม่มีตัวไหนถูกข้าม เอกสารอ้างอิง stdlib เพิ่มจาก 4 ใน 8 เป็น 8 ใน 8

fence ยังถูกทำเครื่องหมายเป็นโปรแกรมที่ต้อง fail ได้ด้วย โดยระบุรหัสที่มันได้ ซึ่งเป็นวิธีที่เอกสารถือรูปแบบที่ผิดห้าแบบที่มันเตือนไว้: ตัวที่ได้ E0228 ตัวที่ได้ E0008 และอีกสามตัว คำเตือนที่คู่กับ diagnostic ตรวจได้ คำเตือนที่เขียนเป็นร้อยแก้วเป็นแค่คำสัญญา

การคอมไพล์เอกสารเจอสองอย่างที่การอ่านไม่มีวันเจอ triple backtick แบบ inline ถูกอ่านเป็นตัวเปิด fence 250 บรรทัดจึงนับเป็นชิ้นเดียวและไม่มีอะไรข้างในถูกตรวจ และ server ตัวอย่างในเอกสารอ้างอิง stdlib เรียก http.serve ซึ่ง std/http ไม่ได้ export ฟังก์ชันที่ถูกคือ listen

ต้นทุนของการส่งมอบ และสิ่งที่ไม่ต้องจ่ายอีกแล้ว

เครื่องมือ MCP สิบเอ็ดตัวเคยแบกคู่มือทั้งหมดไว้ใน reply ของ tools/list ซึ่งทุก session จ่ายตอนเชื่อมต่อ: คำอธิบาย 31,446 ไบต์ ใน reply ขนาด 45,509 ไบต์ ตอนนี้เครื่องมือสิบเอ็ดตัวเดิมแบก 8,627 ใน reply ขนาด 20,386 ไบต์ ไม่มีอะไรถูกลบ ข้อความเดิมถูกเก็บไว้ตรงตัว ใช้ชื่อเครื่องมือเป็น key และเผยแพร่ภายใน glyph llms --json ข้อตกลงที่คุณต้องใช้ตอนเรียกจึงอยู่ในคำอธิบาย และส่วนที่เหลืออยู่ห่างไปหนึ่งคำสั่ง แทนที่จะอยู่ใน reply แรกของทุก session มีเทสต์ที่อ่านรายการเครื่องมือและเอกสารไปพร้อมกัน เอกสารที่อ้างถึงเครื่องมือที่เซิร์ฟเวอร์ไม่ได้ให้บริการ หรือจำนวนที่ไม่ตรงกับรายการ จะทำให้ build fail นั่นคือการตรวจที่ "exposes five tools" ต้องการ

ทั้งหมดนี้ทำงานแบบออฟไลน์และในเครื่อง glyph llms พิมพ์ร้อยแก้ว glyph llms --json พิมพ์ข้อมูล glyph llms --negative พิมพ์โปรแกรมที่ผิด ร้อยแก้วเดียวกันให้บริการที่ llms.txt สำหรับเอเจนต์ที่มี network แต่ไม่มี binary สิ่งที่เอเจนต์ถามเกี่ยวกับโค้ดของคุณ แทนที่จะเกี่ยวกับภาษา คือเครื่องมือคิวรี

สถานะตอนนี้

ใช้ได้วันนี้

glyph llms --json emit เจ็ดส่วนออกมาจากคอมไพเลอร์: รหัส diagnostic 77 ตัว 51 ตัวมีตัวอย่างค้านที่คอมไพล์แล้ว คำสงวน 32 คำ ชื่อใน prelude 24 ชื่อ stdlib 40 module ที่มี export 340 ตัว decision ของภาษา 49 ข้อที่ parse จากสเปก และเครื่องมือสิบเอ็ดตัวพร้อมคำสั่งย่อย glyph query และคู่มือเต็ม docs/error-codes.md และตาราง diagnostic ของเอกสารเริ่มต้นถูกเขียนจากตารางรหัสของคอมไพเลอร์เองโดยสคริปต์ที่ fail เมื่อเพี้ยน และสะท้อน llms.txt ใหม่ไปพร้อมกัน มีเทสต์ที่ยึดแคตตาล็อกเครื่องมือให้ตรงกับสิ่งที่เซิร์ฟเวอร์ให้บริการ ทุก fence ของ Glyph ในเอกสารเริ่มต้นและเอกสารอ้างอิง stdlib คอมไพล์ได้หรือเป็นชิ้นส่วนที่ทำเครื่องหมายไว้ของตัวที่คอมไพล์ได้ และรูปแบบที่ผิดห้าแบบเป็นโปรแกรมที่คู่กับรหัสที่แต่ละตัวได้ glyph llms --negative ตอบจากชุดตัวอย่างเดียวกับที่ cargo test รัน

หยุดตรงไหน

จำนวนโปรแกรมที่ผิดปรากฏสองครั้งในเอกสารนี้และนับคนละอย่าง: 51 จาก 77 รหัสมีตัวอย่างค้านจาก tests/negative/ และ glyph llms --negative แสดง 117 กรณีบน 53 รหัสใน 0.1.149 เพราะมันอ่านการปฏิเสธใน catches/ ด้วย รุ่นถัดไปเพิ่มการปฏิเสธ 22 ตัวที่เพิ่มใน catches/ ตั้งแต่นั้น รวมเป็น 139 กรณีบน 55 รหัส ใน 0.1.149 มี 24 รหัสที่ไม่มีโปรแกรมที่ผิดในชุดไหนเลย และคำตอบระบุชื่อมันแทนที่จะแต่งขึ้นมา 165 จาก 340 export ของ stdlib กลับมาโดยไม่มี signature: implementation เป็น TypeScript ที่ tsc ตรวจ และตารางของคอมไพเลอร์เองไม่ได้ model อะไรให้มัน glyph_symbol บน std/result::all หรือ std/io::println จึงรายงาน kind: null พร้อมเหตุผลนั้น ใน 175 ตัวที่มี มี 46 ตัวที่ยังมี ? ในตำแหน่งที่ควรเป็น type ของ parameter และเอกสารเป็น snapshot ที่คุณดึงมา ไม่ใช่ service: ไม่มีชั้น retrieval ไม่มี embedding และไม่มีช่องทางแชทครอบมัน
