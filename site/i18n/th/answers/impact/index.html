21 · ก่อนแก้

คอมไพเลอร์บอกได้ไหมว่าการเปลี่ยนแปลงจะทำอะไรพัง ก่อนที่ฉันจะแก้?

สำหรับการแก้หกแบบ ได้ glyph_impact รับ declaration ที่คุณกำลังจะเปลี่ยนและตัวการเปลี่ยนแปลง (เปลี่ยนชื่อ ลบ variant เปลี่ยน type ของ parameter เปลี่ยนจำนวน argument ลบทิ้ง) แล้วตอบด้วยคำตัดสินหนึ่งข้อต่อจุดจากรายการที่ปิดไว้ แต่ละข้อพร้อมเหตุผลว่าทำไมเป็นคำตัดสินนั้นและไม่ใช่ข้ออื่น

ทำไมเรื่องนี้สำคัญ

เมื่อเปลี่ยนชื่อฟังก์ชัน ขยาย union หรือเปลี่ยนสิ่งที่ parameter รับ คุณจะ grep หาชื่อเก่าแล้วหวังว่าเจอทุกจุดที่เรียก หรือไม่ก็แก้ไปแล้วอ่านว่าคอมไพเลอร์บอกอะไรหลังจากนั้น ไม่มีวิธีไหนบอกคุณได้ว่าจุดไหนจะยังคอมไพล์ผ่านแต่ผิดแบบเงียบๆ: match ที่มี arm แบบ catch-all ไม่ fail เมื่อคุณเพิ่ม variant มันแค่เริ่มส่ง case ใหม่ไปที่ที่ไม่มีใครเลือก จุดนั้นไม่เคยโผล่ใน build glyph_impact ตอบก่อนแก้ บนการวิเคราะห์เดียวกับที่คอมไพเลอร์รัน

สิ่งที่ได้กลับมา

request ระบุ entity ด้วยตัวตน module::name และการเปลี่ยนแปลงจากรายการที่ปิดไว้: add_variant, remove_variant, rename, change_arity, change_signature_type, remove การเปลี่ยนแปลงเป็นสิ่งบังคับ เพราะคำตัดสินคือข้อเท็จจริงเกี่ยวกับการแก้ ถ้าไม่ระบุการแก้ ทุกจุดจะกลับมาเป็นแค่ reference แทนที่จะเป็นผลที่ตามมา คำตอบระบุ entity การเปลี่ยนแปลง และรายการ impact: หนึ่งรายการต่อจุด แต่ละรายการมี declaration ที่มันอยู่ relation, verdict, because และรหัส diagnostic ที่คอมไพเลอร์จะแจ้งเมื่อมีอยู่ตัวเดียว คำตัดสินเป็นชุดปิดและแต่ละตัวมีความหมายเดียว: WILL_FAIL (คอมไพเลอร์พิสูจน์ได้ว่าจุดนั้นจะคอมไพล์ไม่ผ่าน), ABSORBS (พิสูจน์ได้ว่าการเปลี่ยนแปลงถูกรับไว้ตรงนี้แบบเงียบๆ), SAFE (พิสูจน์ได้ว่าจุดนั้นยังถูกต้อง), UNDETERMINED (ดูจุดนี้แล้วแต่ยืนยันผลไม่ได้) และ NOT_INDEXED (คำถามนี้ถามไม่ได้เลยสำหรับจุดที่มีรูปแบบนี้)

ดูของจริง

module หนึ่งประกาศ label(s: string) -> number มีผู้เรียกสามจุด: จุดหนึ่งส่ง string literal อีกจุดส่งค่าที่ type เป็น alias ของ string ที่ import มาจาก module อื่น และอีกจุดอ่าน label เป็นค่าและไม่เคยเรียกมัน การถามว่า change_signature_type ทำอะไรกับแต่ละจุดได้คำตัดสินสามแบบ เพราะเป็นข้อกล่าวอ้างสามแบบ:

การแก้เดียวกัน สามจุด สามคำตัดสิน และ because ในแต่ละข้อคือประโยคจริงที่คอมไพเลอร์สร้าง ไม่ใช่ป้ายหมวดหมู่ นี่สะท้อนเทสต์ของคอมไพเลอร์เองสำหรับการเปลี่ยนแปลงนี้ (a_signature_type_change_gets_one_verdict_per_kind_of_site ใน glyph-cli/tests/agent_loop.rs): เทสต์ทำการแก้หลังจากนั้น และตรวจว่า E0211 เกิดตรงจุดที่ WILL_FAIL บอกไว้พอดี และคอมไพเลอร์เงียบในอีกสองจุด

บนแอปพลิเคชันจริง

examples/apps/csvql query engine สำหรับ CSV สิบเอ็ดไฟล์ใน repository นี้ มี tagged union หนึ่งตัวคือ Value ซึ่งวันนี้มีสี่ variant การถาม glyph_impact ว่าการเพิ่มตัวที่ห้า (Blob) ทำอะไร เจอจุดที่ match 10 จุดใน 4 ไฟล์: 8 จุดจะคอมไพล์ไม่ผ่าน และ 2 จุดมี arm แบบ catch-all ที่จะกลืน variant ใหม่ไปเงียบๆ เมื่อเพิ่ม variant จริงๆ คอมไพเลอร์รายงาน E0200 8 ตัวพอดี ที่ 8 จุดที่คาดไว้พอดี และไม่บอกอะไรเลยที่ 2 จุด ABSORBS ทั้งก่อนและหลัง การค้นหาข้อความหา arm แบบ catch-all ทั่วแอปเดียวกัน ซึ่งเป็นสิ่งที่คุณจะทำถ้าไม่มีเครื่องมือ เจอ 2 จุดจริงนั้นฝังอยู่ใน 20 ผลลัพธ์ (precision 0.10) และไม่บอกอะไรเลยเกี่ยวกับ 8 จุดที่ fail เพราะมันไม่รู้ว่า match ตรวจค่าที่เป็น type อะไร

สถานะตอนนี้

ใช้ได้วันนี้

การเปลี่ยนแปลงหกแบบที่เป็นชุดปิด (add_variant, remove_variant, rename, change_arity, change_signature_type, remove) และคำตัดสินห้าแบบที่เป็นชุดปิด หนึ่งรายการต่อจุดที่ได้รับผลกระทบพร้อมเหตุผลและรหัส diagnostic change_signature_type ตัดสินทีละ argument ของการเรียกตามกฎการเปรียบเทียบของตัวตรวจเอง และแต่ละจุดได้คำตัดสินที่อ่อนที่สุดของ argument ทั้งหมด element ของ JSX ตัดสินเหมือนการเรียกที่มันถูกแปลงไป: <Card title="x" /> คือ props record หนึ่งตัวที่ส่งให้ Card และแต่ละ attribute แสดงคู่กับ field ที่มันถูกตรวจ พร้อมคำตัดสินที่ argument ของการเรียกที่มี type เดียวกันจะได้ ความครอบคลุม (การค้นหาอ่านอะไรได้และอะไรไม่ได้) ระบุทีละการค้นหา แทนที่จะระบุครั้งเดียวทั้งคำตอบ และทุก node บอกว่ามาจากซอร์ส Glyph, ทางออก extern_ts หรือ .d.ts ที่มองไม่เห็นข้างใน

หยุดตรงไหน

ความลึกแม่นยำที่หนึ่งขั้นและว่างเปล่าเลยจากนั้น: Glyph ไม่เคยอนุมาน type ของ declaration จาก body ของมัน type ของฟังก์ชันที่ถูกเรียกจึงไปไม่ถึง signature ของผู้เรียก และการเปลี่ยน X ทำให้เป็นโมฆะได้เฉพาะ expression ที่ระบุชื่อ X ถ้าขอความลึก 2 คำตอบจะกลับมาพร้อม next_query ที่ระบุคำถามที่ถูกต้องแทน เพราะสิ่งที่ขั้นที่สองต้องใช้คือการแก้ที่ใครสักคนทำให้จุดแรก และการแก้นั้นยังไม่มี UNDETERMINED และ NOT_INDEXED เป็นข้อกล่าวอ้างคนละแบบ: argument ที่ตัวตรวจไม่มี type ให้ หรือ record ที่จับคู่กับ field ที่ไม่มีกฎไหนอ่าน คือ UNDETERMINED (ดูแล้วแต่ตัดสินไม่ได้) ฟังก์ชันที่ถูกอ่านเป็นค่าแทนที่จะถูกเรียกคือ NOT_INDEXED (คำถามถามไม่ได้ตรงนั้นตั้งแต่แรก) ABSORBS คือตัวที่ต้องจับตา: จุดนั้นยังคอมไพล์ผ่านและถูกพิสูจน์แล้วว่าผิด ซึ่ง build ที่เขียวจะไม่มีวันแสดงให้คุณเห็น
