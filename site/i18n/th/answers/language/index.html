15 · ความครบถ้วนของภาษา

นี่เป็นภาษาจริง หรือของเล่นที่มีช่องโหว่?

มันมีสิ่งที่คุณต้องใช้ใน codebase จริง: การมองเห็นของ module, interface สำหรับจำกัด generic, defer สำหรับ cleanup และ helper สำหรับconcurrency ตรงไหนที่มันพึ่ง JavaScript มันก็บอกไว้ แทนที่จะแกล้งทำเป็นไม่ใช่

ทำไมเรื่องนี้สำคัญ

ภาษาที่เขียนไฟล์เดียวได้แต่จัดโครงสร้างโปรเจกต์ไม่ได้ ไม่ใช่ภาษาที่คุณจะเดิมพัน codebase ด้วย ช่องว่างที่สำคัญไม่ได้แปลกประหลาด: ซ่อน helper ได้ไหม generic กำหนดความสามารถได้ไหม ปล่อย file handle ในทุกทางออกได้ไหม รันสองอย่างพร้อมกันแล้วรอทั้งคู่ได้ไหม Glyph ตอบทั้งสี่ข้อ โดยไม่ย้อนกลับไปทางที่เต็มไปด้วย annotation ซึ่งตั้งใจทิ้งไปแล้ว

ดูของจริง

declaration เป็น private ของ module จนกว่าคุณจะทำเครื่องหมาย pub API สาธารณะจึงหาได้ด้วยการค้นหาครั้งเดียว (grep '^pub') และ helper ไม่มีวันรั่วออกไปโดยบังเอิญ:

การมองเห็น: private โดยค่าเริ่มต้น 
pub fn charge(cents: int) -> Result<Receipt, string> { validate(cents)? ... }

fn validate(cents: int) -> Result<int, string> { ... }  # module-private; importing it elsewhere is an error

interface เป็นเชิงโครงสร้างเหมือนของ TypeScript: เป็นชุดของ signature ของ member ที่ generic กำหนดได้ ไม่มี implements ไม่มีพิธีแบบ nominal ค่าใดที่มี member ครบก็ผ่าน และ tsc บังคับใช้

interface จำกัด generic 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer รัน cleanup เมื่อออกจาก block ในทุกเส้นทาง รวมถึงการ return ก่อนเวลาหรือ error ที่ถูก throw defer หลายตัวรันแบบเข้าหลังออกก่อน และใช้ร่วมกับ handle แบบ owned ได้ และ std/task รวมงานที่ทำพร้อมกันให้มีอายุเดียว แทนที่จะปล่อย promise ที่หลุดลอยไว้

defer + structured concurrency 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])

Glyph คอมไพล์เป็น TypeScript และรันบนเอนจิน JavaScript จึงรับลำดับการประเมินผล ความหมายแบบ reference เมื่อมีการแก้ไขค่า และโมเดลเธรดเดียวที่มี garbage collection มาด้วย จุดที่ต่างคือการเปรียบเทียบความเท่ากัน: == เปรียบเทียบค่า โดย record จะเทียบทีละฟิลด์ ส่วน === ของ JavaScript เปรียบเทียบ reference สเปกระบุเรื่องเหล่านี้เป็นการรับประกัน แทนที่จะปล่อยให้คุณค้นพบเอง การจัดการหน่วยความจำเองและโมเดลที่ไม่มี GC ไม่อยู่ในโรดแมป เพราะอยู่นอกขอบเขตของภาษาที่ทรานสไพล์เป็น TypeScript

ไม่มี if match จึงต้องแบกทุกอย่าง

สิ่งแรกที่นักพัฒนา TypeScript ถามหลังจากได้ฟังเรื่องความครบถ้วนคือ match เป็นเงื่อนไขทั่วไปจริงหรือแค่วิธีสวยๆ ในการ destructure union คำตอบคืออย่างแรก และที่ที่พิสูจน์ได้คือการ assign match ที่เป็นค่าทั้งหมดของ let หรือ mut รับทุกอย่างที่ statement รับได้: arm เป็น block ได้ arm await ได้ arm break ออกจาก loop รอบนอกได้ และ arm อ่าน binding ที่มันกำลัง assign ได้ ซึ่งเป็นวิธีพับ state ผ่าน loop โดยไม่มี if

จากตัวตรวจลิงก์: การติดตาม fence และ arm ที่ await 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}

ทั้งคู่คอมไพล์เป็น switch ธรรมดาที่ assign binding ในแต่ละ arm await จึงอยู่ในฟังก์ชัน async ที่ครอบอยู่ และตัวสะสมเป็นตัวแปรปกติที่ TypeScript อนุมานได้ match ที่ใช้ภายใน expression ที่ใหญ่กว่า เป็น argument หรือ operand ยังกลายเป็น closure ซึ่งหมายความว่า arm ต้องเป็น expression เดียว การยกมันออกมาเป็น let ของตัวเองปลดข้อจำกัดนั้น โค้ดทั้งสองชิ้นมาจาก examples/apps/linkcheck/main.glyph ตัวตรวจลิงก์ใน Markdown ที่เขียนขึ้นเพื่อหาเรื่องแบบนี้โดยเฉพาะ

pattern ระบุรูปร่างที่ลึกกว่าหนึ่งชั้นได้

variant ที่มีหลาย field ถือ record ไว้ arm ที่ต้องการจำรูปร่างหนึ่งจึงต้องเอื้อมผ่าน field ของ record จนถึง 0.1.90 ตำแหน่ง field รับแค่ชื่อและไม่มีอย่างอื่น: คุณเปลี่ยนชื่อได้ และแค่นั้น การ match tag ตรงนั้นเป็น compile error และ constructor ที่ซ้อนกันทำให้ parser ล้ม วิธีเลี่ยงคือ bind ทุก field แล้วเขียน match ซ้อนกันทีละชั้น ซึ่งสำหรับอะไรอย่างการปรับสมดุล red-black tree ก็กลายเป็นอีกโปรแกรมหนึ่ง: arm ไม่ตรงกับ case อีกต่อไป และแต่ละชั้นต้องร้อย binding ข้างบนใหม่

case การหมุนหนึ่งแบบของการปรับสมดุล red-black เป็น arm เดียว 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}

ตอนนี้ field รับ pattern ใดก็ได้: tag ของ variant, constructor ที่ซ้อนกัน, destructure ที่ซ้อนกัน, literal, array pattern มีผลที่ตามมาที่ควรรู้ก่อนเขียน field ที่ทดสอบค่าอาจไม่ match arm จึงไม่นับว่าครอบคลุม variant ของมันอีกต่อไป และ match ที่มี arm Node แค่ Node({ color: Red, ... }) จะถูกรายงานว่าไม่ครบจนกว่าจะมี arm ข้างเคียงหรือ else รับส่วนที่เหลือ ตัวตรวจพิสูจน์ความครอบคลุมบนชุดของ tag ไม่ใช่บนผลคูณของ field มันจึงไม่คำนวณว่า arm Red กับ arm Black รวมกันครบ Node การขอ catch-all คือการตีความที่ไม่มีทางปล่อยให้ match หลุดท้ายตอนรัน เช่นเดียวกับที่ที่ไม่มี variant ให้นับเลย: match บน record ธรรมดาที่ทุก arm ทดสอบ field ต้องมี else ตามหลัง

ที่หนึ่งที่สิ่งนี้ไปถึงซึ่งคุณอาจไม่คาดคิดคือตำแหน่งใน array [Black] ทั้ง arm เคยนับว่า match กับ array หนึ่ง element ใดก็ได้ match ที่พึ่งมันจึงถูกรับรองว่าครบ แล้วก็ใช้ arm นั้นกับ [Red] ด้วย element ที่เป็น PascalCase เป็นการอ้างถึง variant ที่นี่เช่นกัน match แบบนั้นตอนนี้จึงเป็น E0208 บน array ความยาว 1 ให้ bind element แล้ว match มันแยกต่างหาก การแปลงข้างใต้ยังเป็นแบบเก่า ซึ่งเป็นเหตุผลที่การตรวจเป็นครึ่งที่ออกมาก่อน

และคอมไพเลอร์รู้ว่า match ให้อะไรออกมา

คำถามต่อมาคือตัวที่ตัดสินว่าทั้งหมดนี้รับน้ำหนักได้จริงหรือไม่: เมื่อคุณ bind ค่าออกมาจาก branch แล้ว Glyph รู้ type ของมันไหม หรือยักไหล่แล้วปล่อยให้ tsc จัดการทีหลัง? จนถึง 0.1.45 มันยักไหล่ match expression ทุกตัวมี type เป็น unknown ค่าที่ออกมาจาก construct แตก branch เพียงตัวเดียวในภาษาจึงไม่มี type ตั้งแต่ตรงนั้น ตอนนี้ match ได้ type ของ arm เมื่อมันตรงกัน และรู้ว่า T.parse คืน Result<T, Array<Issue>> ซึ่งเป็นรูปร่างที่โค้ดจริงส่วนใหญ่แตก branch

จากตัวแบ่งค่าใช้จ่าย: ไม่มี annotation และ i เป็นตัวเลข 
let wire = match WireLedger.parse(decoded) {
  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },
}

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...
}

ทั้งสองส่วนนั้นเป็นเรื่องที่เคยผิดแบบเงียบๆ loop emit wire.expenses.entries() เมื่อ type ของสิ่งที่วนเป็น unknown มันจะ emit Object.entries(...) แทน และ i เป็นstring "0" ซึ่งเป็น TypeScript ที่ถูกต้อง build จึงสะอาด และโปรแกรมพิมพ์ 01:a ทั้งที่หมายถึง 1:a และ wire.expensez ตอนนี้เป็น [E0210] type WireLedger has no field expensez จาก Glyph บนบรรทัดของ .glyph แทนที่จะเป็น TS2339 บน TypeScript ที่ generate การรวม type คือความเท่ากันที่ส่วนหัว: arm ที่ลงท้ายด้วย return ไม่ได้ร่วมโหวต และ arm ที่ type ไม่ตรงกันทำให้ผลเป็น unknown เหมือนเดิม มันมองลึกลงไปอีกชั้นเฉพาะที่ type argument None => [] จึงตรงกับ arm ที่เป็น Array<string> แทนที่จะทำให้ทั้ง match จม และ loop ที่ตามมายัง bind ตัวเลขได้ chain เดียวกันบน record.get ใช้ได้ด้วยเหตุผลเดียวกัน: ฟังก์ชันทั้งหกตัวของ std/record พา type ของค่าออกมาจาก record ที่คุณส่ง โค้ดนี้มาจาก examples/apps/settle/main.glyph ซึ่งเคยมี annotation ที่สิ่งนี้ลบออกไป

จากตัว resolve dependency: การค้นหา ค่าว่างสำรอง และการเดินตาม index 
let path = match record.get(res.reached, name) {
  Some(p) => p,
  None => [],
}

for i, hop in path {               # i is a number, so the indent nests
  let indent = string.repeat(STEP, i + 1)
  mut out = array.push(out, "${indent}${hop}")
}

นั่นคือรูปร่างที่เสียหายมากที่สุด record.get บน Record<string, Array<string>> เป็น Option<Array<string>> และ [] เป็น array ของอะไรก็ได้ arm ทั้งสองจึงตรงกันที่ Array และ type ของ element มาจาก arm ที่มี จนถึง 0.1.55 พวกมันถูกเทียบด้วยความเท่ากัน [] นับเป็นความไม่ตรงกัน และ loop ด้านล่างพิมพ์ 01:x บน build ที่ไม่มี diagnostic และ tsc --strict ผ่าน โค้ดอยู่ที่ examples/apps/depsolve/main.glyph ซึ่งเคยเปิดด้วย let path: Array<string> ใต้ comment สามบรรทัดที่อธิบายว่า annotation นั้นรับน้ำหนักอยู่

ต้องเขียน pad_start เองไหม?

ช่องว่างแรกที่คุณเจอในโปรแกรมจริงไม่ใช่ฟีเจอร์ของ type system แต่คือการเอื้อมหา string.slice แล้วไม่เจออะไร รอบ dogfooding ห้ารอบติดกันบันทึกรายการเดียวกัน และจนถึง 0.1.47 แอปหกตัวใน repo นี้มี repeat ของตัวเอง ห้าตัวมี pad_start ของตัวเอง และทุกตัวมี loop ในที่ที่ควรเป็น fold ตอนนี้ชื่อทั้งสิบเอ็ดนั้นมาพร้อมแล้ว และสำเนาถูกลบออกจากแอปทั้งเจ็ดที่มี

สิ่งที่เพิ่มเข้ามา 
string.repeat(s, n)           string.slice(s, start, end?)       array.fold(xs, init, f)
string.pad_start(s, w, pad?)   string.index_of(s, needle, from?)  array.index_of(xs, x)
string.pad_end(s, w, pad?)     string.replace_all(s, from, to)     array.flat_map(xs, f)
string.trim_start(s) / trim_end(s)

# the 25-line block six apps each carried, and what replaced it:
let total = array.fold(expenses, 0, fn(sum, e) { sum + e.cents })
io.println("${string.pad_end(name, width)}  ${string.pad_start(amount, 9)}")

สามตัวในนั้นตั้งใจทำต่างจากชื่อเดียวกันใน TypeScript repeat คืน "" เมื่อจำนวนติดลบ ในขณะที่ TS throw ซึ่งทำให้ repeat(pad, width - len(s)) ปลอดภัยกับ string ที่ยาวเกินอยู่แล้ว ฟังก์ชัน index_of ทั้งสองคืน Option<number> แทน -1 เพราะ -1 เป็นตัวเลขที่ตรวจ type ผ่านทุกที่ที่ index จริงผ่าน และ fail ห่างจากจุดเรียกมาก การแทนที่มีแค่ replace_all จึงไม่มีรูปแบบที่แทนแค่ตัวแรกให้สับสนกับ String.prototype.replace ซึ่งแทนแค่ครั้งเดียวแบบเงียบๆ

fold คือตัวที่ได้ประโยชน์ต่อเสาหลัก ไม่ใช่แค่ประหยัดการพิมพ์ mut คือบันทึกที่ grep หาได้ของทุกจุดที่ state เปลี่ยน และถ้าไม่มี fold grep mut จะกลับมาเต็มไปด้วย loop นับเลขที่ไม่ได้แก้อะไรที่คนรีวิวสนใจ การลบตัวที่เขียนเองทำให้ examples/apps/ ลดจาก 192 จุดแก้ค่าเหลือ 161 การเขียนใหม่ตรวจด้วย output ไม่ใช่ด้วยการรีวิว: แอปทั้งเจ็ดรันกับ input ตายตัวก่อนและหลัง stdout, exit code และ HTTP response 26 ไฟล์ เหมือนกันทุกไบต์

เดินไดเรกทอรีแล้วบอกได้ไหมว่าอะไรพัง?

std/fs มีหกฟังก์ชันและไม่มีตัวไหนแสดงรายการในไดเรกทอรี ตัวตรวจลิงก์ใน repo นี้เอื้อมข้าม stdlib ไปใช้ readdirSync ของ node และหาว่า path ไหนเป็นไดเรกทอรีโดยลองอ่านแล้วดู errno ที่กลับมา ทั้งสองส่วนแก้แล้ว fs.read_dir คืนชื่อรายการลึกลงไปหนึ่งชั้น fs.is_dir ตอบเป็น bool แบบเดียวกับ fs.exists และ fs.stat คืน FileInfo ที่มี is_dir, is_file, size เป็นไบต์ และ modified เป็นมิลลิวินาทีนับจาก epoch ซึ่ง time.format_iso render ได้โดยตรง ไม่มี walk แบบ recursive และไม่มี glob การเดินคือสามตัวนั้นบวก path.join ประมาณสิบบรรทัด

ฝั่งความล้มเหลวเปลี่ยนมากกว่า FsError.kind เคยเป็น { tag: string } โดยมี NotFound เป็นการจำแนกทั้งหมด การแยก “path นั้นเป็นไดเรกทอรี” ออกจาก “path นั้นไม่มีอยู่” จึงต้องเทียบ string ของ errno ตอนนี้ห้าชนิดที่โปรแกรมกู้คืนได้จริงมีชื่อ และ errno ที่ไม่มีชื่อมาถึงครบถ้วนในส่วนท้าย Other

ตัวตรวจรู้ว่าการจำแนกนั้นเป็นชุดปิด match บน err.kind จึงถูกถือมาตรฐานเดียวกับ union ที่คุณประกาศเอง: ครอบคลุมทั้งหกแล้วไม่ต้องมี else ขาดไปหนึ่งแล้ว build จะ fail ด้วย E0200 ที่ระบุ fs.ErrorKind fs.FsError และ fs.FileInfo ก็มี field ที่ถูกตรวจ err.mesage จึงเป็น E0210 เทียบกับซอร์ส Glyph ของคุณ แทนที่จะเป็น error ของ tsc เทียบกับ TypeScript ที่ generate

การตรวจนั้นใช้งานจริง ลบ arm PermissionDenied ออกจาก match ข้างบน แล้ว glyph check --no-tsc จะหยุดด้วย E0200: match ไม่ครบบน fs.ErrorKind ขาด variant PermissionDenied ตอนที่ model ของ stdlib ถูกเขียนครั้งแรก มันครอบคลุมแค่ return type และ match แบบนี้คอมไพล์ผ่านสะอาดแล้ว throw ตอนรัน ตอนนี้รูปร่างของ field และ variant ของ fs.FsError, fs.FileInfo และ fs.ErrorKind ถูก model แล้ว

รู้ได้อย่างไรว่าฟังก์ชันเหล่านี้ถูกตัว?

เพราะแอปที่ขอมันต้องเลิกใช้ทางเลี่ยงเสียก่อน รุ่นนั้นจึงจะนับว่าเสร็จ ฟังก์ชันในไลบรารีที่ออกมาแล้วกับทางเลี่ยงที่ยังอยู่ต่อเป็นข้อกล่าวอ้างคนละแบบ การเปลี่ยนแปลงเดียวกันที่เพิ่มสี่ตัวนี้จึงลบสำเนาของตัวตรวจลิงก์ไปด้วย: import readdirSync, การเทียบ string ของ errno ทั้งสองจุด, scanner ที่เขียนเอง 97 บรรทัด และ pool แบบ fail-fast รวมแล้วลบออกไป 122 บรรทัด

การลบสองอย่างในนั้นเปลี่ยนสิ่งที่โปรแกรมทำ และความต่างถูกวัด ไม่ใช่ถูกเถียง ชี้ทั้งรุ่นเก่าและรุ่นใหม่ไปที่ tree ที่มีไดเรกทอรีที่คุณอ่านไม่ได้: รุ่นใหม่พิมพ์ permission denied และนับ path นั้นว่าอ่านไม่ได้ ส่วนรุ่นเก่าซึ่งถามได้แค่ว่า errno เป็น EISDIR หรือไม่ ไม่ใส่มันในรายงานเลย ทำให้หนึ่งในสาม URL throw: pool_settled พิมพ์ครบสามแถวและระบุความล้มเหลว ส่วน pool ไม่พิมพ์อะไรเลยและตายไปด้วย rejection ที่ไม่ถูกจัดการ พาผลที่ดีสองตัวไปด้วย

การเขียน scanner ใหม่ยังคลายความกังวลด้านการออกแบบด้วย เพราะ capture group ที่ไม่ได้มีส่วนร่วมอ่านได้เป็น "" เหมือนกับตัวที่ match ค่าว่าง captures_all จึงดูเหมือนบอกไม่ได้ว่า branch ไหนของ alternation ทำงาน แต่บอกได้ ถ้าคุณเขียน group ของแต่ละ branch ครอบทั้ง construct แทนที่จะครอบแค่ส่วนที่ต้องการ: group ที่ทำงานจะเริ่มด้วย `, [, ! หรือ < และว่างไม่ได้ ชิ้นที่อาจว่าง คือปลายทางของลิงก์ ซ้อนอยู่ข้างในและไม่เคยเป็นสิ่งที่คุณถามถึง นั่นเปลี่ยนการเดินทีละอักขระ 180 บรรทัดให้เหลือสอง pattern และการ dispatch 12 บรรทัด โดย output เหมือนกันทุกไบต์ทั้งบนเอกสารของ repo เองและบน fixture ที่สร้างมาเพื่อทำให้มันพัง

เงินไม่ได้คำนวณด้วย float

ช่องว่างที่จะจบการประเมินด้าน fintech ทันทีคือการคำนวณเงินด้วย number แบบ IEEE-754 ซึ่ง 0.1 + 0.2 ไม่ใช่ 0.3 และค่าที่เกิน 253 เสียความแม่นยำไปเงียบๆ std/decimal เป็น fixed-point ฐานสิบที่แม่นยำบน BigInt: จำนวนเต็มความแม่นยำไม่จำกัดที่มีจำนวนหลักทศนิยมตายตัว การบวก ลบ และคูณจึงแม่นยำ และการหารต้องระบุ scale และการปัดเศษ จำนวนเงินที่ผิดรูป parse ได้เป็น Err ไม่มีวันเป็น NaN แบบเงียบๆ

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

สำหรับจำนวนเต็มขนาดใหญ่ที่แม่นยำ อย่าง id บัญชีและตัวนับ มี type bigint: literal เป็น 123n มัน emit เป็น bigint จริงของ TypeScript และ field ของ record ที่มี type เป็น bigint จะ validate typeof === "bigint" ที่ขอบเขต id ที่ส่งมาเป็น number ใน JSON จึงถูกปฏิเสธแทนที่จะถูกปัดเงียบๆ เมื่อเกิน 253

callback แบบ async มี type ในที่สุด

type ของฟังก์ชันเคยเป็น fn(A) -> T และไม่มีอย่างอื่น ซึ่ง emit เป็น (a: A) => T body แบบ async ไม่เข้ากับสิ่งนั้น ฟังก์ชันที่คืนงานที่เลื่อนไว้ หรือ record ของ handler แบบ async จึงต้องปล่อยไว้โดยไม่มี annotation และตัวตรวจก็เลิกดู async fn(A) -> T คือ type ที่ขาดไปนั้น มัน emit เป็น (a0: A) => Promise<T> และ async fn() ที่ไม่มี return emit เป็น () => Promise<void>

Glyph แยกสองอย่างนี้ออกจากกันเอง แทนที่จะปล่อยให้ tsc: ฟังก์ชันธรรมดาในที่ที่ต้องการฟังก์ชัน async เป็น E0204 ที่ return และ E0211 ที่ argument ของการเรียก และข้อความระบุทั้งสองฝั่ง กรณีเดียวที่มันไม่ตัดสินคือ return แบบ void ซึ่ง TypeScript ยอมให้ฟังก์ชันใดก็ได้

งานที่เลื่อนไว้ และ map ของ handler 
fn task_for(url: string) -> async fn() -> Fetched {
  return async fn() -> Fetched { return { url: url, body: await fetch_one(url) } }
}

type Handler = async fn(string) -> string

async fn dispatch(routes: Record<string, Handler>, name: string, arg: string) -> string {
  return match record.get(routes, name) {
    Some(h) => await h(arg),
    None    => "no route",
  }

type แบบ recursive ที่ match ได้ลึกจนสุด

union อ้างถึงตัวเองภายใน payload ของมันได้ พร้อม type parameter และ arm ของ match ซ้อน constructor pattern ไว้ใน field ของ constructor pattern อีกตัวได้ เอาสองอย่างนี้มารวมกัน กฎการปรับสมดุลของ red-black tree ก็เหลือสี่ arm: แต่ละ arm ระบุรูปร่างที่มันเขียนใหม่พอดี และคอมไพเลอร์คือผู้ตรวจรูปร่าง แทนที่จะเป็น comment ข้างบนที่อ้างไว้ examples/apps/leaderboard/main.glyph คือโปรแกรมทั้งหมด เป็น leaderboard ที่เก็บทุกคะแนนไว้ใน tree และตอบคิวรี rank, top-N และช่วง ด้วยการเดิน tree แทนการเรียง log ใหม่

type Tree<K, V> =
  | Leaf
  | Node({ color: Color, left: Tree<K, V>, key: K, value: V, size: int, right: Tree<K, V> })

fn balance<K, V>(t: Tree<K, V>) -> Tree<K, V> {
  return match t {
    Node({ color: Black, left: Node({ color: Red, left: Node({ color: Red, left: a, key: xk, value: xv, right: b }), key: yk, value: yv, right: c }), key: zk, value: zv, right: d }) => node(
      Red,
      node(Black, a, xk, xv, b),
      yk,
      yv,
      node(Black, c, zk, zv, d),
    ),
    // the other three cases, then:
    other => other,
  }
}

ใช้ได้วันนี้

การมองเห็นแบบ pub ที่บังคับใช้กับทั้งสองวิธีในการอ้างถึง type ของ module ข้างเคียง (import ด้วยชื่อ และ annotation lib.Secret), ข้อจำกัดแบบ interface เชิงโครงสร้าง, defer, std/task (all/race/all_settled/pool/pool_settled), async fn(A) -> T เป็น type ที่เขียนได้, union ที่อ้างถึงตัวเองใน payload ซึ่ง match ได้ด้วย arm ที่ซ้อน constructor pattern ไว้ใน field ของอีกตัว, match เป็นค่าของ let หรือ mut โดยมี block, await และการควบคุม loop ใน arm, match ที่ arm ตรงกันพา type ไปใช้ในส่วนที่เหลือของโปรแกรม, T.parse ที่มี type, std/decimal สำหรับคำนวณเงินอย่างแม่นยำ, bigint สำหรับจำนวนเต็มขนาดใหญ่ที่แม่นยำ, ตัวคั่นหลัก, ส่วนของสเปกที่รับผิดชอบ semantics ที่สืบทอดจาก JS และ standard library ที่มี string.slice, index_of, repeat, pad_start, pad_end, replace_all, trim_start, trim_end และ array.fold, index_of, flat_map บวก fs.read_dir, fs.is_dir, fs.stat, การจำแนก FsError.kind ที่ตัวตรวจบังคับคุณ และ regex.captures_all ส่วนใหญ่ของ std/string และ std/array พา return type เข้ามาในโปรแกรมของคุณแล้ว string.split จึงเป็น Array<string> และ loop บนมันก็ bind index เป็นตัวเลข std/record ก็ถูก model ด้วย โดยอ่าน type ของค่าจาก record ที่คุณส่ง: record.get(t, k) บน Record<string, Array<string>> เป็น Option<Array<string>> และ record.keys(t) เป็น Array<string> array.sort(record.keys(t), cmp) จึงรักษา type ของ element ไว้

หยุดตรงไหน

import ที่เป็น private รายงานว่า “not exported by M” ซึ่งเป็นข้อความเดียวกับชื่อที่ไม่มีอยู่ การแยก “เป็น private ให้ทำเครื่องหมาย pub” ออกจาก “ไม่มีชื่อนี้” เป็นการปรับปรุงที่อยู่ในคิว การมองเห็นถูกตรวจบน type annotation ไม่ใช่บนค่าที่อ่านผ่าน namespace: lib.helper() ที่ helper เป็น private ยังเป็น error ของ tsc ไม่ใช่ของ Glyph บริบทของ async ถูกตรวจแล้ว (E0222) ยกเว้นจุดเดียว: initializer ของ const ระดับ module ไม่มีสิ่งที่เรียกได้ครอบอยู่ await ระดับบนสุดตรงนั้นจึงได้รับอนุญาต และ ESM ที่ emit ออกมาก็รันมัน การรวม type ของ arm ยังต้องให้ arm ตรงกันที่ส่วนหัวของ type: เมื่อได้ type ต่างกัน ผลจะเป็น unknown สำหรับ Glyph และมีแค่ tsc ที่ตรวจสิ่งที่คุณทำกับมัน ฟังก์ชันใน stdlib เก้าตัวอยู่ในสถานะเดียวกัน หกตัวรับ argument ท้ายที่ไม่บังคับ (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify) และการตรวจจำนวน argument เทียบตัวเลขหนึ่งตัวกับตัวเลขหนึ่งตัว การ model มันจึงจะรายงาน error ผิดๆ ทุกครั้งที่เรียกโดยไม่ใส่ argument ตัวสุดท้าย ส่วน array.map, flat_map และ zip ได้ type ของ element จาก callback ที่ตัวตรวจไม่ได้เดินเข้าไป ค่าที่ออกมาจากเก้าตัวนี้โดยตรงต้องมี annotation ก่อนวนด้วย index และ match บน string.index_of เป็น E0300 บน union เดียวกัน ขออีกจุดหายไปแล้ว: union ที่เป็น generic บน parameter ของตัวเอง (type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> })) เคยปฏิเสธ arm ที่ซ้อนกัน ซึ่ง union เดียวกันที่ไม่มี parameter ยอมรับ ตอนนี้รับได้แล้ว ทั้งที่ type parameter ที่ยังเปิดอยู่และที่ instantiation ที่ระบุจริง การค้นหาเดียวกันนี้เป็นตัวตัดสินด้วยว่า match ถูกตรวจหา variant ที่ขาดหรือไม่ จนถึงรุ่นนี้ match บน Tree<K> จึงละ Leaf ได้ build ผ่านสะอาด ผ่าน tsc --strict และ throw ตอนรัน ขณะที่การเขียนแบบไม่ generic เป็น E0200 ตอนนี้ทั้งสองแบบรายงาน และการย้าย union ไปอยู่ห่างออกไปหนึ่ง import ก็ไม่เปลี่ยนคำตอบอีกต่อไป: match บน Tree<string> ที่ import มาซึ่งละ Leaf เป็น E0200 ที่ระบุ Leaf เหมือนกับ Tree ที่ไม่ generic ที่ import มา นั่นเป็นอีกเส้นทางโค้ดที่ตรวจแยกกัน และมันเป็นไปในทางตรงข้ามจนถึงรุ่นนี้ คือ build ผ่านสะอาดแล้ว throw ตอนรัน มีอย่างหนึ่งเกี่ยวกับความครอบคลุมของ union ที่ import มาที่ควรรู้ก่อนพึ่งพามัน: payload ของ variant ไม่เคยถูกตรวจเช่นกัน B(X) ที่ X เป็น variant ของ union ใน payload เองจึง match กับ B ทุกตัวแทนที่จะรายงาน Y ที่ขาดไป และเรื่องนั้นไม่เกี่ยวกับ generic การ bind field หรือการ match tag ที่ไม่มี payload ในนั้นใช้ได้ทุกกรณี
