28 · parse ไม่ผ่าน

เมื่อ parse ไม่ผ่าน ฉันจะรู้ไหมว่าเพราะอะไร?

รู้ ทุกปัญหาบอกชื่อ field บอกว่าค่าผิดกฎข้อไหน และมี code ที่ใช้แตก branch ได้ field ที่ถูกจำกัดด้วย predicate where จะรายงานตัว predicate เอง การปฏิเสธจึง grep ย้อนกลับไปหาบรรทัดที่กำหนดกฎนั้นได้

ในหน้านี้

  1. ทำไมเรื่องนี้สำคัญ
  2. type ที่ซ้อนกัน
  3. ดูที่ code ไม่ใช่ข้อความ
  4. สถานะตอนนี้

ทำไมเรื่องนี้สำคัญ

validator ที่บอกว่า "payload นี้ผิด" ทำงานได้แค่ครึ่งเดียว

handler ยังต้องตัดสินว่า นี่คือ client ที่ลืม field หรือ client ที่ส่งรหัสผ่านยาวสี่ตัวอักษร? อันหนึ่งคือ 400 อีกอันคือ 422 และถ้า validator ไม่บอก คุณก็ต้อง parse body เดิมสองรอบด้วย type สองแบบเพื่อกู้ข้อมูลหนึ่งบิตที่ validator มีอยู่แล้ว

ที่มา เรื่องนี้เจอที่ไหน

นั่นคือสิ่งที่เกิดขึ้นจริงตอนสร้าง auth API ด้วย Glyph การสมัครที่ไม่มี key password เลยกลับมาเป็น weak_password เพราะกรณีไม่มีกับกรณีสั้นเกินไปให้ string เดียวกัน

type ที่ซ้อนกันตอบแทนตัวเองได้

field ที่ type ของมันมี descriptor ของตัวเองจะถูก validate ด้วย parse ของ type นั้น และปัญหาของมันกลับมาพร้อมชื่อ field นำหน้า path Password ที่ซ้อนลงไปสองชั้นจึงรายงาน ["body", "password"] และยังมีข้อความของตัวเอง

ใช้รหัส ไม่ใช่ string

Issue มี code ที่ไม่บังคับ: "missing", "type", "refinement", "unexpected" หรือ "depth" ให้แตก branch ด้วยสิ่งนั้น การ match ด้วยข้อความคือความเปราะบางที่ Glyph มีไว้กำจัด และข้อความมีไว้ให้คนที่อ่าน response body

การแยก 400/422 โดยไม่อ่านข้อความ 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code ไม่บังคับ Issue ที่คุณสร้างเอง และทุกโค้ดที่ใช้มันซึ่งเขียนก่อนที่มันจะมี จึงยังคอมไพล์ได้โดยไม่ต้องแก้

รายละเอียด code "depth"

"depth" คือคำตอบสำหรับ body ที่ซ้อน object และ array ลึกเกิน 1000 ชั้น (MAX_DEPTH ใน std/schema): ปัญหาเดียวที่ field ที่มันเกิด ซึ่งก่อน 0.1.150 การตรวจจะ throw RangeError: Maximum call stack size exceeded และพา handler ล่มไปด้วย

สถานะตอนนี้

ใช้ได้วันนี้

  • record และ type แบบ where รายงานกฎที่ล้มเหลว ไม่ใช่แค่ field ที่ล้มเหลวmissingtyperefinementunexpecteddepth
    รายละเอียด

    record และ type แบบ where รายงานกฎที่ล้มเหลว ไม่ใช่แค่ field ที่ล้มเหลว: "missing" สำหรับ field บังคับที่ไม่มี, "type" สำหรับรูปร่างที่ผิด (รวมถึงสิ่งที่ไม่ใช่ object หรือเป็น array), "refinement" สำหรับค่าที่ผ่าน type พื้นฐานแต่ไม่ผ่าน predicate, "unexpected" สำหรับ key ที่ type ไม่ได้ประกาศ และ "depth" สำหรับค่าที่ซ้อนลึกเกิน 1000 ชั้น

  • refinement ยก predicate ของมันมาให้
  • field ที่ type มี descriptor จะส่งต่อให้ descriptor นั้น ปัญหาที่ซ้อนกันจึงมาพร้อม path เต็ม
  • field ที่ไม่บังคับ (f?: T) ไม่เคยถูกรายงานว่าหายไป

กำลังคมขึ้น 2

  • field ที่ type ไม่มี descriptor ของตัวเองยังได้การตรวจแบบแบนและปัญหา "type"
    รายละเอียด

    มีสองขอบ field ที่ type ไม่มี descriptor ของตัวเอง เช่น type parameter ที่ไม่มีข้อจำกัด หรือ type ที่ import จาก .d.ts ที่เขียนเอง ยังได้การตรวจแบบแบนและปัญหา "type" คอมไพเลอร์ไม่สังเคราะห์ descriptor ให้สิ่งเหล่านั้น และการรัน glyph gen dts กับ declaration คือสิ่งที่ให้ descriptor แก่มัน

  • type ของ module เองที่ชื่อ Issue ถูกปฏิเสธที่บรรทัดที่ตั้งชื่อมันE0110ตั้งแต่ 0.1.60
    รายละเอียด

    module ที่ประกาศ type ของตัวเองชื่อ Issue เคยบังตัวใน prelude ภายในไฟล์ที่ emit และทำให้ทุก descriptor ใน module นั้นพัง ตั้งแต่ 0.1.60 declaration นั้นเป็น E0110 ที่บรรทัดที่ตั้งชื่อ type คุณจึงรู้ว่าปัญหาอยู่ตรงไหน แทนที่จะต้องอ่าน error ของ tsc เกี่ยวกับโค้ดที่ generate
