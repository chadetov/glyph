01 · คำสัญญาหลัก

อะไรกันเอเจนต์ไม่ให้ทำโค้ดของฉันพังแบบเงียบๆ?

การเปลี่ยนแปลงทั้งประเภทที่คอมไพล์ผ่านแบบเงียบๆใน TypeScript (case ที่ขาด error ที่ไม่ได้จัดการ field ที่เปลี่ยนชื่อ) กลายเป็นcompile error ที่เอเจนต์ต้องแก้ก่อนจะปล่อยออกไปได้

ในหน้านี้

  1. ทำไมเรื่องนี้สำคัญ
  2. Error
  3. คำผิดใน arm
  4. ข้าม module
  5. Refinement
  6. เทสต์ใน build
  7. เจอจากการสร้างของจริง
  8. สถานะตอนนี้

ทำไมเรื่องนี้สำคัญ

เอเจนต์มักไม่ได้ทำโค้ดพังแบบเสียงดัง มันทำพังแบบมั่นใจ: เพิ่มสถานะ ทิ้ง branch หรือเปลี่ยนชื่อ field ทุกอย่างยังตรวจ type ผ่าน แล้วบั๊กก็ไปโผล่บน production

ความล้มเหลวที่แพงคือตัวที่คอมไพล์ผ่านและผิด Glyph ปิดช่องว่างนั้นด้วยการเปลี่ยน “คุณน่าจะจัดการแล้ว” เป็น “คอมไพเลอร์พิสูจน์แล้วว่าคุณจัดการ”

  • union ที่ปิดผนึกtagged union ปิดผนึก match จึงต้องครอบคลุมทุก case
  • error เป็นค่าerror เป็นค่าที่คุณต้องแกะ ไม่ใช่ exception ที่หายไป
  • ขอบเขตที่ถูกตรวจและทุก type มี runtime descriptor ข้อมูลที่ข้ามขอบเขตจึงถูกตรวจเทียบกับรูปร่างของมัน

error ที่ถูกทิ้งได้คำเตือน

error ก็เช่นกัน: ฟังก์ชันที่คืน Result<T, E> มีไว้ให้จัดการด้วย match หรือส่งต่อด้วย ? (และคอมไพเลอร์ตรวจว่า error type ตรงกัน) และถ้าคุณทิ้ง Result ไปเฉยๆ (เรียกเป็น statement แล้วเพิกเฉยต่อสิ่งที่มันคืน) Glyph จะเตือน (E0217) เพราะ error ที่ถูกทิ้งคือความล้มเหลวที่ถูกกลืน

glyph check --no-tsc, 0.1.149 (ตัดตอน) 
13 │   save("a")
[E0217] Warning: typecheck: this `Result` is discarded; its `Err` case is silently ignored
    │ Help: Handle it with `match`, propagate it with `?`, or bind it (`let _ = ...`) to say the discard is intentional.

คุณปิดเสียงมันได้อย่างตั้งใจด้วย let _ = ... ไม่ใช่โดยบังเอิญ

union ของ standard library ก็ปิดผนึก

มาตรฐานเดียวกันใช้กับ union ที่ standard library เป็นเจ้าของ fs.ErrorKind เป็นชุดปิดของหกชนิด และตัวตรวจรู้รูปร่างของมัน match e.kind บน error ของ filesystem จึงไม่ต้องมี arm else และ fail ด้วย E0200 เมื่อคุณละชนิดใดไป

E0200 ขาดชนิดE0210 field ที่ไม่รู้จักE0218 ต้องมี else
รายละเอียด คำผิดใน field, return type, การ match ตัวเลขและ string

e.mesage เป็น E0210 แทนที่จะเป็นสิ่งที่ tsc จับได้ทีหลัง return type ก็เดินทางไปด้วย: string.split(text, ",") เป็น Array<string> for i, part in string.split(text, ",") จึง bind i เป็นตัวเลข แทนที่จะเป็น key แบบ string ที่ได้จากสิ่งที่วนซึ่งไม่มี type

ความครบถ้วนไม่ได้มีไว้แค่กับ union match บน number หรือ string ที่มีแต่ arm แบบ literal ครอบคลุมโดเมนที่ไม่มีขอบเขตไม่ได้ Glyph จึงกำหนดให้ต้องมี else (E0218) แทนที่จะปล่อยให้ค่าที่ไม่ถูกครอบคลุมตกไปเป็น throw ตอนรัน

กฎเหมือนกันทุกที่: match ที่ไม่ได้รองรับ case ใด คอมไพล์ไม่ผ่าน

arm ที่สะกดผิดคือช่องว่าง ไม่ใช่ catch-all

คำผิดก็กลบช่องว่างแบบเงียบๆ ไม่ได้ หัวของ arm ที่ขึ้นต้นด้วยตัวใหญ่คือการอ้างถึง variant ไม่ใช่ binding ใหม่

status.glyph: arm ที่สะกดผิดคือช่องว่าง ไม่ใช่ catch-all 
fn label(s: Status) -> string {
  return match s {
    Loadign => "…",        // typo for Loading, read as a variant, not a binding
    Ready => "done",
    Failed(msg) => msg,
  }
}
glyph build 
[E0220] `Loadign` is not a variant of `Status`; did you mean `Loading`?
   ╰─ a lowercase name would be a binding; a PascalCase name is read as a variant
[E0200] non-exhaustive match on `Status`: missing variant `Loading`
ที่มา Glyph รุ่นเก่าทำอะไรกับคำผิดนี้

หัวของ arm ที่ขึ้นต้นด้วยตัวใหญ่คือการอ้างถึง variant ไม่ใช่ binding ใหม่ ถ้าคุณสะกด Loading ผิดเป็น Loadign Glyph รุ่นเก่าอ่านคำผิดนั้นเป็น catch-all ที่ bind ทุกค่าและทำให้ match ดูครบ ตอนนี้หัวต้องระบุ variant จริงของ union ที่คุณกำลัง match ถ้าไม่ใช่ build จะหยุดด้วย E0220 และชี้ไปที่ชื่อจริงที่ใกล้ที่สุด และ variant ที่คุณข้ามไปจริงๆ ยังโผล่เป็น E0200 อยู่ข้างๆ

variant ภายใน payload

การอ่านแบบนั้นยังใช้ได้ลึกลงไปอีกชั้น ที่ variant เป็น payload ของอีกตัว ตอนนี้ arm dispatch ตาม tag ของ payload เอง ไม่ว่า variant ชั้นนอกจะเป็นอะไร

repl.glyph: arm ชั้นในทดสอบ payload ไม่ได้ bind มัน 
fn step(z: Zipper, line: string) -> Zipper {
  return match parse_command(line) {
    Err(Blank) => z,                          // a comment or an empty line
    Err(e) => { io.println(explain(e)) z },   // every other parse error
    Ok(command) => execute(z, command),
  }
}
E0305 label ของ case ซ้ำ
ที่มา arm ที่ไม่มีวันรันก่อน 0.1.93 และการป้องกัน E0305

Err(Blank) ข้าง Err(e) อ่านว่า "ข้ามบรรทัดว่าง พิมพ์ error จากการ parse ตัวอื่นทั้งหมด" และจนถึง 0.1.93 มันคอมไพล์เป็น label case "Err": สองตัวบน tag ชั้นนอก ตัวแรก bind ทั้ง payload ภายใต้ชื่อ Blank ทุก error ไปที่ arm แรก ตัวที่สองเป็นโค้ดที่ไม่มีวันรัน และไม่มีอะไรบอก: Glyph ไม่รายงาน diagnostic และ tsc --strict ยอมรับ label ของ case ที่ซ้ำ ตอนนี้ arm dispatch ตาม tag ของ payload เอง ไม่ว่า variant ชั้นนอกจะเป็นอะไร และคอมไพเลอร์อ่านชื่อแบบเดียวกับที่ typechecker อ่าน: รายการ variant ของ union ใน payload เป็นตัวตัดสิน และเฉพาะเมื่อรายการนั้นเข้าไม่ถึง รูปของชื่อจึงเป็นตัวตัดสิน สำหรับ union ที่ประกาศในไฟล์เดียวกัน ตัวใหญ่ตัวเล็กไม่สำคัญอีกต่อไป สำหรับตัวที่ import จาก module อื่น ตอนนี้รายการ variant ยังเข้าไม่ถึง variant ตัวใหญ่จึง dispatch และตัวเล็กหยุด build

มันหยุดเพราะตอนนี้ switch ถูกป้องกันไว้ arm สองตัวที่จะเขียน label case เดียวกันคือ E0305 ไม่ใช่ switch ที่ label ตัวที่สองไม่มีวันรัน นั่นคือสิ่งที่ทำให้ปัญหาประเภทนี้ดังแทนที่จะเงียบ: การแปลงที่หยิบ tag เดียวกันสองครั้งทำให้ build fail แทนที่จะเลือก arm ผิดตอนรัน

วิธีเขียน import ไม่เคยปิดการตรวจ

union เข้ามาใน scope อย่างไรไม่เปลี่ยนอะไรในเรื่องนี้ Glyph ให้คุณเขียน arm ของ variant ได้สองแบบ และทั้งคู่ถูกตรวจเหมือนกัน: import model { Cond, Yes, No } กับ arm เปล่าๆ หรือ import model (หรือ import model as m) กับ model.Yes(_)

interp.glyph: รายการ import ถูกเอาออก match ยังถูกตรวจ 
import model { Action, All, Any, AtLeast, Clear, Condition, Context, Counter,
               Equals, Flag, FlagSet, Increment, Not, Set, Slot, Text }
import model
import std/result

pub fn evaluate(ctx: model.Context, c: model.Condition) -> result.Result<bool, SlotError> {
  return match c {
    model.Equals({ key, value }) => result.Ok(read_text(ctx, key, "equals")? == value),
    model.AtLeast({ key, least }) => result.Ok(read_count(ctx, key, "at-least")? >= least),
    model.FlagSet({ key }) => result.Ok(read_flag(ctx, key, "flag-set")?),
    model.All({ of }) => all_of(ctx, of),
    model.Any({ of }) => any_of(ctx, of),
    model.Not({ of }) => result.Ok(!(evaluate(ctx, of)?)),
  }
}
glyph build หลังลบ arm สุดท้าย 
[E0200] non-exhaustive match on `Condition`: missing variants Not
รายละเอียด union ของ standard library, string enum และทำไมรายการนั้นถึงมีอยู่

สิ่งนี้ใช้กับ union ของ standard library ด้วย match o { option.Some(s) => … } บน option.Option<string> จึงเป็น E0200 สำหรับ None ที่ขาด เหมือนกับการเขียนแบบ Some/None เปล่าๆ ทุกประการ จนถึง 0.1.56 การเขียนแบบระบุ module ข้ามการตรวจไปทั้งหมด และ build ไม่รายงาน diagnostic บน match ที่ throw ตอนรัน

string enum ก็ข้ามขอบเขตได้ type ColType = "text" | "int" | "real" | "bool" ที่ประกาศใน catalog.glyph แล้ว import เข้าอีก module ยังรักษาค่าทั้งสี่ไว้ match ที่ครอบคลุมทั้งสี่จึงคอมไพล์ผ่านโดยไม่มี else และการทิ้งไปหนึ่งตัวเป็น E0200 ที่ระบุค่าที่คุณทิ้ง จนถึง 0.1.57 มันเป็น E0218 พร้อมข้อความช่วยเหลือที่บอกให้เพิ่ม arm else ข้อความนั้นผิดเกี่ยวกับโค้ดตรงหน้า และการทำตามเปลี่ยน compile error ให้เป็นการตกทะลุตอนรัน การ import ทั้งสามแบบใช้ได้: import catalog { ColType }, import catalog กับ catalog.ColType และ import catalog as c กับ c.ColType

รายการ import นั้นคือที่มาของเรื่องนี้ มันถูกเขียนด้วยมือในทุก module ของ statechart engine พร้อม comment ข้างบนที่บอกว่า constructor ของ union ไม่ได้มาพร้อมกับ type ของมัน comment ถูกเรื่อง syntax แต่ผิดเรื่องเหตุผล: รายการนั้นมีอยู่เพราะการเขียนแบบสั้นกว่าปิดการตรวจ และไม่มีใครสังเกต เพราะการปิดนั้นเงียบ ตอนนี้แบบที่คุณเลือกเป็นตัวเลือกจริง ไม่ใช่กับดัก แบบระบุชื่อใส่ทุก variant ที่คุณจัดการไว้ในรายการ import ซึ่งเป็นสิ่งที่ grep หา Equals จะเจอ แบบระบุ module บอกที่แต่ละ arm ว่า variant มาจาก module ไหน ไม่มีแบบไหนทำให้เสียการตรวจ

record ที่ import มารักษา field ไว้

ตอนนี้ record ก็ข้ามได้ และจนถึง 0.1.58 ยังข้ามไม่ได้ record จึงรักษาชุด field ไว้ และ field ที่ผิดเป็น E0210 ที่ระบุ record แทนที่จะเป็น error ของ tsc เกี่ยวกับรูปร่างนิรนาม

glyph build บน field ที่พิมพ์ผิดของ record ที่ import มา 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
// Before 0.1.58: no Glyph diagnostic at all, only a tsc error downstream.

// Both annotations are load-bearing. `for i, x in <record field>` picks its

// and the row/column numbers in a `BadCell` are wrong.
let raw_rows: Array<Array<string>> = sheet.rows
for i, raw_row in raw_rows {
for i, raw_row in sheet.rows {
  let typed: Array<Value> = []
  let cols: Array<ColumnSpec> = spec.columns
  for j, col in cols {
  for j, col in spec.columns {
    …
  }

รายละเอียด บั๊ก line 11, สิ่งที่ tsc พลาด, ตัวตนข้ามขอบเขตอย่างไร

type ที่ประกาศในไฟล์หนึ่งและใช้ในอีกไฟล์มาถึงโดยไม่มีใครรู้อะไรเกี่ยวกับมัน ซึ่งทำให้เสียการตรวจสองอย่าง field ที่สะกดผิดบนมันไม่ได้ error จาก Glyph เลย sheet.rowz จึงตกไปถึง tsc และกลับมาเป็นข้อความ TypeScript เกี่ยวกับรูปร่างที่คุณไม่เคยเขียน และ for i, r in sheet.rows บอกไม่ได้ว่า rows เป็น array มันจึง emit Object.entries(sheet.rows) แทน sheet.rows.entries() ซึ่ง bind i กับ string "0" จากนั้น i + 1 ก็ต่อ string แทนที่จะบวก และแถวที่ควรรายงานว่า line 2 ก็รายงานเป็น line 11

ส่วนที่ควรรู้คือ tsc จับครึ่งไหน การคำนวณบน index นั้นมันจับได้ แม้จะรายงาน error เทียบกับ TypeScript ที่ generate สำหรับตัวแปรที่ Glyph bind แทนคุณ สิ่งที่มันจับไม่ได้คือทุกที่ที่รับ string ในที่ที่ตั้งใจให้เป็นตัวเลข: string interpolation, การต่อ string, key ของ record.get สิ่งเหล่านั้นคอมไพล์ผ่านสะอาดภายใต้ตัวตรวจทั้งสอง และพิมพ์ตัวเลขผิด นั่นคือรูปแบบของบั๊กที่โปรเจกต์นี้มีไว้กำจัด ขอบเขตของ module ที่นำมันกลับมาจึงไม่ใช่ขอบเขตที่ Glyph จะปล่อยไว้ได้

ตอนนี้ type ที่ import มามีตัวตนข้ามขอบเขต โดยใช้ module ที่ประกาศและชื่อที่ประกาศเป็น key การ import ทั้งสามแบบจึง resolve ไปที่ type เดียวกัน ตัว declaration ถูกดึงมาเมื่อต้องการและถูกแปลงที่ฝั่ง module ที่ประกาศ ซึ่งเป็นครึ่งที่ผู้ใช้ทำเองไม่ได้: การ resolve ทำงานบน span และ span ของ declaration ที่ import มาเป็นของอีกไฟล์

query engine ใน examples/apps/csvql คือที่ที่เรื่องนี้โผล่ขึ้นมา มันมีการยก let สามจุดที่มีหน้าที่เดียวคือระบุ type ของ field ที่ import มาซ้ำให้ emitter ใต้ comment สี่บรรทัดที่อธิบายว่าถ้าไม่มีมัน เลขแถวและคอลัมน์ในข้อความ error จะออกมาผิด ทั้งสามจุดถูกลบแล้ว และแอปพิมพ์ output เหมือนเดิมทุกไบต์สำหรับคิวรีทั้งสิบสอง

ยังมีอย่างหนึ่งที่หยุดที่ขอบเขต การส่ง catalog.Sheet ในที่ที่ต้องการ table.Row เป็น E0211 ที่ระบุทั้งสอง type แต่รายการ member ของ interface ไม่ข้ามมา record ที่ส่งในที่ที่ต้องการ interface ที่ import มาจึงถูกเทียบกับความว่างเปล่า การให้มันได้การดูแลแบบที่ชุด field ของ record ได้จะเปลี่ยนความหมายของการเข้ากันได้เชิงโครงสร้างแบบเงียบๆ ซึ่งเป็นการตัดสินใจของภาษา ไม่ใช่การแก้บั๊ก

การปิดบัง PII อยู่ที่ type

สัญชาตญาณเดียวกันคือ "ทำให้อยู่ระดับ type ไม่ใช่ธรรมเนียม" ครอบคลุม PII ด้วย ใส่ @redact fields: [ssn, dob] บน type แล้วคอมไพเลอร์จะ generate redact() บน descriptor ของมันที่ปิดบัง field เหล่านั้น json.stringify(User.redact(u)) จึงทำข้อมูลรั่วไม่ได้

E0219 field ที่ไม่รู้จักใน @redact

ระบุ field ที่ type ไม่มีแล้วจะเป็น compile error (E0219) ไม่ใช่การปิดบังที่ไม่ได้ทำอะไรแบบเงียบๆ

refinement ถูกตรวจลึกจนสุด

descriptor มีค่าก็ต่อเมื่อมันเป็นการตรวจที่ type ประกาศไว้ ลึกจนสุด refinement แบบ where รัน predicate ทุกที่ที่ type ปรากฏ ไม่ใช่แค่ที่ Instant.parse โดยตรง: เป็น field ของ record, เป็น element ของ Array, เป็น payload ของ Option, ภายใน variant ของ union และผ่าน json.parse<T>

schedule.glyph: predicate ตาม type เข้าไปใน field 
fn is_instant(value: string) -> bool {
  return match time.parse_iso(value) {
    Some(_) => true,
    None => false,
  }
}

type Instant = string where is_instant(value)

type WireBlock = { start: Instant, end: Instant }
type WireParticipant = { name: string, busy: Array<WireBlock> }
type Calendar = { participants: Array<WireParticipant> }

// json.parse<Calendar>(text) on a file holding "start": "no"
//   => Err. It returned Ok before 0.1.41.
ที่มา ตารางนัดหมายที่ผิดอย่างมั่นใจก่อน 0.1.41

เช่นเดียวกับ record ที่ import จาก module อื่น จนถึง 0.1.41 ทั้งสองกรณีถอยไปตรวจแค่ว่ามี key อยู่ ซึ่งไม่ได้ตรวจอะไรเลย

แอปจัดตารางด้านล่างคือที่ที่เรื่องนี้โผล่ขึ้นมา มันอ่านปฏิทินจากไฟล์ JSON และต้องให้ทุก timestamp เป็นเวลาแบบ ISO-8601 จริง ก่อนหน้านี้ refinement หยุดที่ชั้นบนสุด ไฟล์ที่แก้ด้วยมือซึ่งมี "start": "no" จึง parse ผ่าน เวลาอ่านได้เป็น 0 และแอปพิมพ์ตารางอย่างมั่นใจแล้ว exit 0

เทสต์รันเป็นส่วนหนึ่งของ build

เทสต์อยู่ข้างโค้ดและรันเป็นส่วนหนึ่งของการคอมไพล์ @example เหนือฟังก์ชัน หรือ block ```glyph @run``` ภายใน @doc ถูกรันโดย glyph build โดยไม่มี flag ให้ต้องจำ

bracket.glyph: ทำให้การจัดลำดับพัง แล้ว build จะหยุด 
@example seed_order(2) == [1, 2]
@example seed_order(4) == [1, 4, 2, 3]
@example seed_order(8) == [1, 8, 4, 5, 2, 7, 3, 6]
fn seed_order(size: int) -> Array<int> { … }

รายละเอียด ทำไมข้ามแบบเงียบๆ ไม่ได้ และช่องทาง JSON

ตัวที่เป็นเท็จทำให้ build fail แบบเดียวกับ type error ซึ่งคือประเด็น: เอเจนต์ที่เขียน body ของฟังก์ชันใหม่ผ่าน build โดยทิ้ง assertion ไว้ข้างหลังไม่ได้ --no-test เลือกไม่รันและพิมพ์ว่าข้ามเทสต์ไปกี่ตัว การข้ามจึงมองเห็นได้ใน log

output แบบ JSON ที่เอเจนต์อ่านรายงานคำตัดสินเดียวกัน glyph build --json มี object examples ข้าง diagnostic และ example ที่ fail ทำให้ ok เป็น false และ exit code ไม่เป็นศูนย์ จนถึง 0.1.43 example รันเฉพาะภายใต้ --test และเส้นทาง JSON return ก่อนที่มันจะรันเลย ช่องทางเดียวที่เอเจนต์อ่านได้จึงพิมพ์ "ok": true บนโปรเจกต์ที่ assertion ของตัวเองเป็นเท็จ ถ้า tsx ไม่อยู่ใน PATH build จะ fail แทนที่จะรายงานว่าผ่านทั้งที่ไม่ได้ตรวจ

แอป bracket ด้านล่างมีแบบนี้ 23 ตัว seed_order สร้างลำดับ bracket มาตรฐานด้วยการเพิ่มเป็นสองเท่า ซึ่งเป็นฟังก์ชันแบบที่ทำผิดแบบแนบเนียนได้ง่าย และอธิบายให้แม่นยำได้ง่าย เปลี่ยนกฎการเพิ่มเป็นสองเท่าแล้ว build จะหยุด โดยไม่ต้องมีไฟล์เทสต์ runner หรือ flag

เจอจากการสร้างของจริง

อีกสี่อย่าง ที่เจอจากการสร้างของจริงด้วยมัน

แต่ละข้อคอมไพล์ผ่านสะอาดและผ่าน tsc --strict และแต่ละข้อถูกพบจากการเขียนแอปพลิเคชัน ไม่ใช่จากการอ่านคอมไพเลอร์ มันคือความล้มเหลวเดียวกันในสามที่: type บอกอย่างหนึ่ง และโปรแกรมทำอีกอย่าง

อ่าน key ที่อาจไม่มีอยู่

อ่าน key ที่อาจไม่มีอยู่: ตอนนี้เป็น E0224 
fn name_of(row: Record<string, string>) -> string {
  return row.naem          // a typo. compiled, and returned undefined
}

ตอนนี้เป็น compile error ที่ชี้ไปที่ record.get ซึ่งคืน Option<V> กรณีที่ไม่มีจึงมีที่ให้ไป

รายละเอียด ทำไมการอ่าน map ต่างจากการ index array

key ของ map เป็นอะไรก็ได้ คอมไพเลอร์จึงรู้ไม่ได้ว่า key มีอยู่ การให้ type ของการอ่านเป็น string คือการยืนยันสิ่งที่ไม่ได้ตรวจ และค่าถูกพิมพ์ออกมาเป็นข้อความ "undefined" การเขียน key ไม่ได้ถูกแตะ และการ index array ก็เช่นกัน: ขอบเขตเป็นค่าที่โปรแกรมตรวจได้ key ของ map ไม่ใช่

เมธอดที่ตอบกลับเป็น undefined

การค้นหาที่อาจไม่พบอะไรเลย: ตอนนี้เป็น E0242 
let name = users.find(fn(u: User) -> bool { return u.id == id }).name
let last = xs.at(-1) ?? 0  // passed tsc --strict too

[E0242] the call to `users.find` returns `User | undefined`; Glyph writes a value that may be missing as an `Option`
Help: pass `users` and the same callback to `array.find`, which returns `Option<User>`, and `match` it

เมธอดบางตัวของ JavaScript บอกว่า "ไม่มีอะไร" ด้วย undefined ซึ่ง checker ของ Glyph เองมองไม่เห็น editor และเครื่องมือของ agent จึงปล่อยการอ่าน .name ผ่านไป ตอนนี้แต่ละตัวชี้ไปที่ฟังก์ชันใน standard library ที่คืนค่าเป็น Option และ glyph fix เขียนแทนให้สำหรับเมธอดของ array

รายละเอียด เมธอดไหนบ้าง และใช้อะไรแทน

รายการนี้อ่านจาก declaration ของ TypeScript ได้แก่ find, findLast และ at บน array และ at, codePointAt และ match บน string ตัวแทนคือ array.find, array.find_last, array.get, string.char_at, string.code_point_at และ regex.matches ค่าเริ่มต้นที่ใช้ ?? จะกลายเป็น arm None ของ match และเพราะ array.get ตอบ None เมื่อ index ติดลบ help สำหรับ xs.at(-1) จึงเขียนเป็น array.get(xs, array.len(xs) - 1) เมธอดที่เรียกบนค่าจาก npm จะไม่ถูกตรวจ เพราะ Glyph ไม่รู้ type ของมัน

== คือความเท่ากันของค่าทุกที่

เทสต์ที่ผ่านขณะที่โค้ดล้มเหลว 
@example wrap("a") == wrap("a")   // passed: deep equality
fn same() -> bool {
  return wrap("a") == wrap("a")   // false. no diagnostic
}

ตอนนี้ == คือความเท่ากันของค่าทุกที่ primitive ยังคอมไพล์เป็น === การเปรียบเทียบทั่วไปจึงไม่เปลี่ยน

ที่มา เทสต์ผ่านบนโค้ดที่พังได้อย่างไร

== ถูกบันทึกในเอกสารว่าเป็นความเท่ากันของค่า แต่ถูกแปลงเป็น === ซึ่งเป็นความเท่ากันของreferenceทันทีที่ฝั่งใดฝั่งหนึ่งเป็น record, tagged union หรือ array expression เดียวกันเปรียบเทียบเชิงโครงสร้างในเทสต์ และเปรียบเทียบตัวตนในโปรแกรมข้างๆ เทสต์จึงรายงานว่าสำเร็จบนโค้ดที่ใช้งานไม่ได้

binding ของ loop รักษา type ของ element ไว้

ความครบถ้วนที่ระเหยหายไปภายใน loop 
for t in tiers {
  match t {
    "free" => ...          // "pro" unhandled: once merely a warning to add `else`
  }
}

ตอนนี้มันระบุ variant ที่คุณยังไม่ได้จัดการ ซึ่งเป็นคำแนะนำให้ทำตามการตรวจ ไม่ใช่ให้ปิดมัน

ที่มา คำแนะนำ catch-all ที่มันเคยให้

binding ของ loop ไม่มี type ของ element match บน union ของ string literal จึงลดลงเป็น match บน string และคอมไพเลอร์แนะนำให้เพิ่ม catch-all

union แบบ generic ที่ import มาถูกตรวจ

variant ที่ขาดไปใน match บน union แบบ generic ที่ import มา 
import tree { Tree, Node }

fn label(t: Tree<string>) -> string {
  return match t {
    Node({ key: k }) => k    // Leaf unhandled: built clean, threw at run time
  }
}

ตอนนี้เป็น E0200 ทั้งสองทาง ทั้งในการ import ทั้งสองแบบ และทั้งที่ parameter ที่ยังเปิดอยู่และที่ instantiation ที่ระบุจริง

ที่มา ทำไมการตรวจไม่เคยเริ่ม

union ที่ module ของคุณเองประกาศถูกตรวจไม่ว่าจะรับ type parameter หรือไม่ ส่วนตัวที่ import จาก module ข้างเคียงถูกตรวจเฉพาะเมื่อไม่รับ parameter Tree<string> ไปถึงเส้นทางตรวจความครอบคลุมข้าม module ในฐานะการใช้ union ที่ import มา แทนที่จะเป็นตัว union เอง และด่านที่เริ่มการตรวจมองหาแบบหลัง match จึงไม่เคยถูกนับเลย: tsc --strict ผ่าน และ Leaf ก็ throw ลบ <K> ออกจากทั้งสองไฟล์ แล้วโปรแกรมเดียวกันเป็น E0200

parse อ้างการตรวจที่มันไม่ได้ทำไม่ได้

parse ที่รายงานว่าสำเร็จโดยไม่ได้ตรวจ: ตอนนี้เป็น E0304 
type Conn = { id: number, sock: Socket }

Conn.parse(body)   // Ok. `sock` was never checked, and the message said it was

การถือ socket ไว้ใน record เป็นเรื่องปกติและยังคอมไพล์ได้ การ validate มันตอนนี้ถูกปฏิเสธตรงที่เขียนและในทุก module ที่ import record นั้น โดยระบุ field และ type ของมัน และการปฏิเสธตามรูปร่างไป: ผ่าน record ที่ซ้อนกัน, Array, Option

รายละเอียด ทำไมการมีอยู่ไม่ใช่การตรวจ และการแก้ที่มันขอ

ทุก record type มี runtime descriptor สำหรับ field ที่คอมไพเลอร์มองเข้าไปใน type ไม่ได้ เช่น socket หรืออะไรก็ตามที่เข้าถึงผ่าน extern_ts การตรวจที่ generate คือ "มีอยู่ไหม" ขณะที่ข้อความที่รายงานอ่านว่า field `sock` must be Socket boolean ที่เป็นจริงเสมอไม่มีประโยชน์ ตัวที่เป็นจริงเสมอภายใต้ข้อความที่ระบุ type ที่ไม่มีอะไรตรวจแย่กว่า เพราะ parse คือสิ่งที่ขอบเขตถูกบอกให้เชื่อ

การแก้ที่มันขอคือการแยกที่คุณจะเขียนอยู่แล้ว type สำหรับข้อมูลบน wire ที่ทุก field ตรวจได้ แล้วจึงสร้าง record ของโดเมนจากมัน unknown ไม่ถูกจับโดยสิ่งนี้ เพราะมันไม่ได้อ้างอะไร และการมีอยู่ก็คือการตรวจทั้งหมดจริงๆ

การเปลี่ยน signature ที่มองไม่เห็นที่จุดเรียก: ปิดใน 0.1.116

เปลี่ยนฟังก์ชันให้รับ payload แทน string ดิบ แล้วทุกจุดเรียกที่ยังส่งรูปร่างเดิมก็ build ผ่านสะอาด

billing.glyph: union ข้าม parameter แบบ `string` ไปโดยไม่มีใครสังเกต 
type PaymentResult = Settled(string) | Declined(string)

fn takes_string(s: string) -> number { return s.length }

fn charge(r: PaymentResult) -> number {
  return takes_string(r)   // compiled clean before 0.1.116
}
glyph build ตอนนี้ 
[E0211] argument type mismatch: expected `string`, found `PaymentResult`
   ╰─ Pass a value of the expected type, or change the parameter's type.
รายละเอียด การตรวจทำงานที่ไหน และเงียบที่ไหน

parameter ที่มี type เป็น string, number หรือ bool เคยรับค่าของ union หรือ record ที่ประกาศไว้โดยไม่บ่นเลย ทั้งที่การเรียกแบบเดียวกันที่ส่ง argument bool ที่ไม่ตรงเป็น E0211 อยู่แล้ว

การตรวจอ่าน declaration มันจึงทำงานเฉพาะที่คำตอบแน่นอน alias ของ primitive, union ของ string literal (D30), body ของ extern_ts หรือ typeof และ interface ยังไม่บอกอะไร เพราะไม่มีตัวไหนพิสูจน์ได้ว่าไม่ใช่ string แบบที่ tagged union หรือ record พิสูจน์ได้ void ก็ถูกยกเว้นด้วย มันไปถึง argument, return และ annotation ของ let เหมือนกัน เพราะทั้งสามใช้ความสัมพันธ์เดียวกัน

const ที่มี annotation มี type

const มีช่องว่างที่ตรงกันในฝั่งรับ

catalog.glyph: const ที่มี annotation และ field ที่มันไม่มี 
type Sheet = { rows: number, cols: number }
const ORIGIN: Sheet = { rows: 0, cols: 0 }

fn f() -> number {
  return ORIGIN.rowz   // compiled clean before 0.1.116
}
glyph build ตอนนี้ 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
รายละเอียด const ที่ไม่มี annotation และทำไมการแก้ทั้งสองเป็น Breaking

const ระดับ module ที่มี type annotation ถูกแปลงเป็น Ty::Unknown ไม่ว่า annotation จะบอกอะไร field ที่พิมพ์ผิดบนมันจึงมองไม่เห็น ตรงที่ let ที่มี annotation แบบเดียวกันภายในฟังก์ชันรายงานอยู่แล้ว

const ที่ไม่มี annotation ไม่ได้อ้างอะไรและตั้งใจให้เป็น Unknown: การอนุมานจาก initializer เป็นคำถามอีกข้อที่มีพื้นที่ของการเตือนผิดต่างออกไป การแก้ทั้งสองเป็น Breaking ภายใต้ glyph check --no-tsc, language server และ playground เพราะแต่ละอย่างเริ่มจับโปรแกรมที่รุ่นก่อนยอมรับ ส่วน glyph build เต็มแดงผ่าน tsc อยู่แล้วทั้งสองกรณี

field ที่เกินมายังเป็นหน้าที่ของ tsc

การตรวจ record literal อย่างหนึ่งยังเป็นของ tsc ไม่ใช่ของ Glyph glyph build หยุดที่มัน ส่วน glyph check --no-tsc, language server และ playground ไม่บอกอะไร (G273)

point.glyph: field ที่เกินมา ปล่อยให้ tsc

pub type Point = {
  x: number,

}

TS2353 จาก tscG273
รายละเอียด tsc รายงานอย่างไร

literal ที่มี field ที่ record ที่ประกาศไม่มี ผ่านตัวตรวจของ Glyph และ tsc ปฏิเสธมันบน TypeScript ที่ emit เป็น TS2353 ซึ่ง map กลับมาที่ literal

สถานะตอนนี้

ใช้ได้วันนี้ 19

Matching

  • match ที่ครบทุกกรณีบน union ที่ปิดผนึก: ของคุณหรือของ module ข้างเคียง generic หรือไม่ก็ตาม และของ standard library เช่น fs.ErrorKindE0200
  • match ที่ครบทุกกรณีบน number/stringE0218
  • arm ของ variant ที่พิมพ์ผิดถูกจับเป็น compile error พร้อมแนะนำ variant ที่ใกล้ที่สุด แทนที่จะเป็น catch-all แบบเงียบๆE0220
  • variant ในตำแหน่ง payload dispatch ตาม tag ของ payload เอง แทนที่จะ bind มัน
  • arm สองตัวที่จะตอบ tag เดียวกันถูกปฏิเสธเป็น E0305 แทนที่ตัวหนึ่งจะชนะไปเงียบๆ
  • binding ของ for ที่รักษา type ของ element ไว้

type, record และ literal

  • union หรือ record ที่ประกาศไว้ถูกส่งในที่ที่ต้องการ string/number/boolE0211
  • field ที่พิมพ์ผิดบน const ระดับ module ที่มี annotationE0210
  • == เป็นความเท่ากันของค่าบนทุก type
  • การอ่าน key จาก map ถูกปฏิเสธE0224
  • เมธอดในตัวที่ตอบ undefined เช่น find หรือ at ถูกปฏิเสธ พร้อมบอกรูปแบบที่ใช้ OptionE0242ตั้งแต่ 0.1.161
  • object literal และ attribute ของ JSX ถูกตรวจเทียบกับ type ที่ประกาศE0204E0211E0210ตั้งแต่ 0.1.124
    รายละเอียด

    ตั้งแต่ 0.1.124 object literal มี record type ตาม field ที่มันเขียน let g: string = { x: 1 }, literal ที่ขาด field ที่ record ที่ประกาศกำหนด และ literal ที่ส่งในที่ที่ไม่เข้ากัน จึงเป็น E0204 หรือ E0211 พร้อมระบุ type ที่ประกาศ ทั้งที่ let, const, return และ argument ของการเรียก และ attribute ของ JSX ถูกตรวจเทียบกับ props record ของ component <Button variant="nope" /> จึงได้ E0211 พร้อมค่าที่มันรับ และ attribute ที่ record ไม่ได้ประกาศได้ E0210 ซึ่ง glyph fix เปลี่ยนชื่อให้

  • field หรือ prop บังคับที่ขาดไปถูกระบุชื่อE0211E0229ตั้งแต่ 0.1.125
    รายละเอียด

    ตั้งแต่ 0.1.125 record literal หรือ element ของ component ที่ละ field บังคับไปจะระบุชื่อมัน ทั้งในข้อความและใน missing_fields บน --json และ element ที่ขาด prop บังคับเป็น E0211 แม้จะไม่ได้เขียน attribute เลย component ที่ parameter ตัวเดียวไม่ใช่ record เป็น E0229

  • ทุก field ของ record เปรียบเทียบด้วยกฎเดียวกับ recordตั้งแต่ 0.1.127
    รายละเอียด

    ตั้งแต่ 0.1.127 ทุก field ของ record เปรียบเทียบด้วยกฎเดียวกับ record record ที่ซ้อนกัน type ที่ประกาศไว้ หรือ union ของ string literal ภายในจึงถูกปฏิเสธในที่ที่ tsc ปฏิเสธ เช่นเดียวกับ field ที่ไม่บังคับในที่ที่ประกาศว่าบังคับ ฟังก์ชันที่ return ไม่เข้ากัน และ member ของ interface ในเครื่อง record ที่ทุก field ไม่บังคับปฏิเสธค่าที่ไม่มี field ร่วมเลย แบบเดียวกับ TS2559 parameter ของฟังก์ชันยังไม่ถูกเปรียบเทียบ

Matching

  • การตรวจความครอบคลุมของ union ที่ import มายังไม่มองเข้าไปใน payload ของ variantสิ่งถัดไปที่จะทำให้ลึกขึ้น
    รายละเอียด

    type parameter เคยปิดการตรวจ: จนถึง 0.1.90 match บน Tree<K> ละ variant ได้ build ผ่านสะอาด ผ่าน tsc --strict และ throw ตอนรัน ขณะที่ match เดียวกันบน Tree เป็น E0200 สิ่งนั้นปิดแล้วสำหรับ union ที่ module ของคุณประกาศ และตั้งแต่ 0.1.95 สำหรับตัวที่อยู่ห่างไปหนึ่ง import สิ่งที่ยังตื้นกว่าบนเส้นทางของ import คือความลึก ไม่ใช่ด่าน: การตรวจที่รันสำหรับ union ที่ import มาไม่เคยมองเข้าไปใน payload ของ variant B(X) บน union ที่ import มาซึ่ง payload เป็น union อีกตัวจึง match กับ B ทุกตัวแทนที่จะรายงาน Y ที่ขาด และไม่มี type parameter เกี่ยวข้องเลย นั่นคือสิ่งถัดไปที่จะทำให้ลึกขึ้น

  • variant ตัวเล็กใน payload ของ union ที่ import มาทำให้ build หยุดE0305
    รายละเอียด

    ตอนนี้ variant ในตำแหน่ง payload อ่านจากรายการ variant ของ union ใน payload ตัวใหญ่ตัวเล็กของชื่อจึงไม่สำคัญอีกต่อไปสำหรับ union ที่ module ของคุณประกาศ สำหรับตัวที่ import จาก module อื่นไม่มีรายการให้อ่าน และรูปของชื่อยังเป็นตัวตอบ ซึ่งหมายความว่า Err(Blank) dispatch และ Err(blank) หยุด build ที่ E0305: ความล้มเหลวเสียงดังบนโปรแกรมที่ถูกต้อง และต้องใช้ registry ของ union ที่ import มาแบบเดียวกับที่การตรวจความครอบคลุมแบบตื้นข้างบนต้องการ

  • constructor pattern บน payload ที่เป็น record (Ok(Point)) fail ใน tsc ไม่ใช่ใน Glyph
    รายละเอียด

    constructor pattern บน payload ที่เป็น record แทนที่จะเป็น union (Ok(Point)) fail ผ่าน tsc โดยระบุ .tag ที่คุณไม่เคยเขียน ในขณะที่ควรเป็น diagnostic ของ Glyph ที่ระบุ type และ pattern

  • arm เปล่าที่สะกดผิดรายงานสองบรรทัดสำหรับชื่อเดียวกันE0220E0103
    รายละเอียด

    ตอนนี้การตรวจคำผิด (E0220) ครอบคลุมทั้ง union ที่ประกาศใน module และตัวที่เข้าถึงผ่าน namespace import (model.Nooo(_)) ไม่ว่าจะเป็นรูป constructor หรือเปล่าๆ: จนถึง 0.1.115 หัวเปล่าที่สะกดผิดบน union ที่ import มา (Loadign ไม่มี argument) ถูกนับว่าครอบคลุม variant หนึ่งและไม่บอกอะไร ขณะที่คำผิดเดียวกันบน union ในเครื่องรายงาน E0220 อยู่แล้ว ตอนนี้ทั้งสองแบบรายงาน arm เปล่าที่สะกดผิดยังไปโดน E0103 ซึ่งอยู่ก่อนหนึ่งขั้นด้วย คุณจึงได้สองบรรทัดสำหรับชื่อเดียวกัน

type, record และ literal

  • literal ที่มี spread ไม่มี type และ field ที่เกินมายังถูกยอมรับG273
    รายละเอียด

    literal ที่มี spread ไม่มี type และ field ที่เกินมายังถูกยอมรับ ในขณะที่ tsc ปฏิเสธมันบน literal ที่สร้างใหม่เป็น TS2353 (G273)

  • member ของ interface ที่ import มาและ type ของ const ที่ import มายังไม่ข้ามมา
    รายละเอียด

    ตอนนี้ type ข้ามขอบเขต module ได้ครบ: union รักษาความครบถ้วนไว้ ทั้งแบบมี tag และแบบ string literal และ record รักษาชุด field ไว้ field ที่พิมพ์ผิดบน record ที่ import มาจึงเป็น E0210 ที่ระบุ type ของ record นั้นเอง และ for i, x บน field ที่เป็น array ของมันก็ bind ตัวเลขโดยไม่ต้องมี annotation สิ่งที่ยังไม่ข้ามมาคือรายการ member ของ interface record ที่ส่งในที่ที่ต้องการ interface ที่ import มาจึงถูกเทียบกับความว่างเปล่า const ที่ import มาเป็นรูปร่างเดียวกันอีกชั้นหนึ่ง: มันยังเป็น Ty::Unknown field ที่พิมพ์ผิดผ่าน import ด้วยชื่อหรือ namespace จึงยังเงียบ ไม่ว่า module ต้นทางจะใส่ annotation ไว้หรือไม่

  • การ narrow ตาม flow ที่ลึกขึ้นอยู่ใน roadmap

ขอบเขตของข้อมูล

  • find หรือ at บนค่าจาก npm จะไม่ถูกตรวจ ตรวจเฉพาะ array หรือ string ที่ Glyph รู้ typeE0242
  • map จาก module อื่นหรือจาก standard library ถูกอ่านโดยไม่ตรวจE0224
    รายละเอียด

    map ที่มาจาก module อื่นหรือจาก standard library ยังถูกอ่านโดยไม่ตรวจ E0224 จึงยังไม่ครอบคลุม sqlite.Row และ for i, x in xs ที่มีสอง binding ยังเสีย type ไป

  • type จาก .d.ts ธรรมดาไม่มี descriptor ให้ materialize ด้วย glyph gen dtsE0304
    รายละเอียด

    ตอนนี้ type ที่ import จาก module Glyph อื่น validate ผ่าน descriptor ของตัวเอง เช่นเดียวกับ refinement แบบ where ในตำแหน่ง field ส่วน type ที่ import จาก .d.ts ธรรมดาไม่มี descriptor ให้ validate ผ่าน และ parse บน record ที่ถือมันตอนนี้ถูกปฏิเสธ (E0304) แทนที่จะรายงานความสำเร็จที่ไม่ได้ตรวจ ให้ materialize ด้วย glyph gen dts เพื่อให้ได้ type ที่ validate ได้

เครื่องมือและ standard library

  • ฟังก์ชันเก้าตัวของ std/string และ std/array ยังคืนค่าที่ไม่มี type
    รายละเอียด

    return type ของ stdlib ที่ตัวตรวจ model ไว้ครอบคลุมครึ่งที่มีจำนวน argument ตายตัวของ std/string และ std/array ฟังก์ชันหกตัวที่มี argument ท้ายที่ไม่บังคับ (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify) และ array.map/flat_map/zip ยังไม่มี type ค่าที่ออกมาจากตัวใดตัวหนึ่งโดยตรงจึงต้องมี annotation ก่อนวนด้วย index

  • การเข้าถึง member บน primitive และ array ไม่มี diagnostic ในที่ที่ tsc ไม่ได้รัน
    รายละเอียด

    การเข้าถึง member และการเรียกบน string, number, bool และ Array<T> ถูกปล่อยให้ tsc โดยการออกแบบ ไม่ใช่เพราะเป็นช่องว่าง Glyph อนุญาต member ดิบของ JS ตรงนั้น s.length และ xs.length จึงคอมไพล์และผ่าน tsc --strict สิ่งที่ยังขาดคือ diagnostic สำหรับสี่ช่องทางที่ไม่เคยรัน tsc: glyph check --no-tsc, language server, เซิร์ฟเวอร์ MCP และ playground

  • build แบบออฟไลน์ที่มี example ต้องมี tsx หรือ --no-test
    รายละเอียด

    ตัวรัน example เรียก tsx โปรเจกต์ที่มี example แต่ไม่มี tsx ใน PATH จึงทำให้ build fail แทนที่จะข้ามไปเงียบๆ นั่นเป็นความตั้งใจ แต่หมายความว่า build แบบออฟไลน์ต้องติดตั้ง tsx หรือใช้ --no-test

  • await ใน fn ธรรมดาถูกจับเทียบกับซอร์สของคุณเองE0222
    รายละเอียด

    บริบทของ async เคยเป็นกฎข้อเดียวที่ Glyph ปล่อยให้ tsc ตอนนี้ await ใน fn ธรรมดาเป็น E0222 เทียบกับซอร์สของคุณเอง โดย initializer ของ const ระดับบนสุดเป็นกรณีเดียวที่ยังได้รับอนุญาต เรื่องนั้นและกฎอีกสองข้อที่ย้ายขึ้นมาหนึ่งขั้นอยู่ในจับได้เร็วกว่า

ทำไมนี่เป็นเสาหลักข้อแรกจากสี่ข้อของ Glyph และการรับประกันหยุดตรงไหน อยู่ในหน้าเสาหลักเรื่องตรวจสอบได้
