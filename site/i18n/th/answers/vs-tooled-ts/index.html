05 · การเปรียบเทียบ

ทำไมไม่ใช้แค่ TypeScript แบบ strict + zod + eslint + ts-pattern?

เพราะการรับประกันทุกข้อในนั้นต้องเลือกเปิดเอง และเอเจนต์หลบแต่ละข้อได้ในบรรทัดเดียว ความเข้มงวดของ Glyph ไม่ใช่ไฟล์ config ที่เอเจนต์แก้ได้ มันคือตัวภาษา จุดบังคับใช้ย้ายจาก "เราจำได้ไหมว่าต้อง lint ไฟล์นี้" มาเป็น "มันคอมไพล์ผ่านไหม"

สิ่งที่ TypeScript ที่ใส่เครื่องมือครบครอบคลุมอยู่แล้ว

การตั้งค่า TypeScript ที่ดีพาคุณไปได้ไกล และถ้าทีมของคุณรันทั้งหมดใน CI คุณก็ปิดช่องโหว่ส่วนใหญ่ที่ Glyph มุ่งเป้าไปแล้ว มันเป็นทางเลือกที่ควรพิจารณาอย่างจริงจัง นี่คือการเทียบกัน:

สิ่งที่ TypeScript ที่ใส่เครื่องมือครบให้คุณอยู่แล้ว 
no `any`            → noImplicitAny + @typescript-eslint/no-explicit-any
exhaustive match    → ts-pattern .exhaustive() (compile-time, today)
errors as values    → neverthrow / Effect
runtime validation  → zod at every boundary
must-handle errors  → an eslint rule
deterministic diffs → Biome / Prettier

ถ้าคุณผูกทั้งหมดนั้นไว้และบังคับใช้จริง คุณก็มาได้เกือบครบแล้ว TypeScript มีแนวคิดเหล่านี้ สิ่งที่ภาษาเพิ่มให้ด้วยการทำให้มันไม่ใช่ตัวเลือก สรุปได้สามข้อ

01 ไม่ใช่ตัวเลือก ชนะ ต้องเลือกเปิดเอง

config ของ eslint ป้องกันได้เฉพาะโค้ดที่เอเจนต์ส่งผ่านมัน และเอเจนต์เขียน as unknown as User, @ts-ignore, // eslint-disable-next-line หรือแค่ลืม .exhaustive() ได้ แล้วมันก็ยังคอมไพล์และ merge ได้ ทางหนีทีไล่ทุกทางเป็น config ที่เอเจนต์แก้ได้ Glyph ไม่มีทางหนีแบบนั้นให้หยิบ: ไม่มี as ไม่มี pragma สำหรับ ignore ไม่มีทางได้ค่าที่มี type ออกมาจาก unknown โดยไม่มีการตรวจที่คอมไพเลอร์มองเห็น

TypeScript: มีทางหนีอยู่ handler.ts 
const user = body as unknown as User;
// @ts-ignore
doThing(user.mispelled);
// eslint-disable-next-line
return anything as any;
Glyph: ไม่มีอะไรให้ปิด handler.glyph 
return match User.parse(body) {
  Ok(user) => use(user),
  Err(_) => fallback(),
}
// no `as`, no ignore pragma,
// no lint to switch off.

ความเข้มงวดที่เอเจนต์ปิดผ่าน config ไม่ได้อยู่ที่จุดบังคับใช้คนละจุดกับความเข้มงวดที่มันปิดได้ Glyph สร้างขึ้นบนความต่างนั้น

02 type คือ validator: ไม่มีสิ่งที่สองให้ดูแล

zod กลับด้านแหล่งความจริงของคุณ: คุณเขียน schema แล้ว derive type จากมัน จากนั้นต้องรักษา type, schema และ serializer ให้ตรงกันด้วยมือ การรักษาให้ตรงกันคือจุดที่เอเจนต์ทำให้เพี้ยน: มันเปลี่ยนชื่อ field ใน type แต่ไม่เปลี่ยนใน schema และทั้งคู่ยังคอมไพล์ผ่าน ใน Glyph type คือ validator: การประกาศ type User = {...} จะ generate User.parse มาด้วย สิ่งเดียว ไม่มีอะไรต้องรักษาให้ตรงกัน ไม่มีอะไรให้ลืม

03 การแก้ค่าที่ grep หาได้

ใน TypeScript การเปลี่ยน state ซ่อนอยู่หลัง =, .push(), Object.assign, setter หรือ spread ได้ ไม่มี token เดียวให้ค้นหา และไม่มีกฎ lint ไหนแก้ได้หมด ใน Glyph state ที่ใช้ร่วมกันอยู่ใน store และทุกการเปลี่ยนคือข้อความ .set(/.update( ส่วน grep 'mut ' เจอทุกการแก้ค่าระดับ local TypeScript ปกติไม่มีสิ่งที่เทียบเท่า

diff ของรูปแบบความล้มเหลว

งานเดียวกัน เอเจนต์เพิ่ม variant ให้ union แล้วลืมจัดการในหนึ่งจากสามจุด:

TS ที่ใส่เครื่องมือครบ 
// ts-pattern .exhaustive() catches it,
// IF every site used ts-pattern and
// nobody wrote a default: case or a
// switch that only logs. Those
// compile green and skip the new case.
Glyph 
[E0200] non-exhaustive match on
`Feed`: missing variant `Archived`
// every unhandled match, everywhere,
// fails the build. No opt-in, no
// escape, no forgotten default.

จุดที่ TypeScript ที่ใส่เครื่องมือครบยังทำได้ดีกว่า

สี่จุดที่มันเหนือกว่า Glyph ในวันนี้:

  • validation ที่ละเอียดกว่า descriptor ของ Glyph เข้มโดยค่าเริ่มต้น (ปฏิเสธ key ที่ไม่ได้ประกาศ) และ refinement แบบ where ใส่ predicate ให้ primitive ได้ (type Email = string where value.includes("@")) ซึ่ง descriptor รันที่ทุกขอบเขตที่ type ไปถึง zod ยังนำอยู่สองเรื่อง: มีการตรวจสำเร็จรูปอย่าง .email() และ .url() ที่ใน Glyph คุณต้องเขียนเอง และ refine ทั้ง object ได้ ขณะที่ where บน record (lo <= hi ข้ามสอง field) ตอนนี้เป็น E0300
  • matching ที่ลึกกว่า guard และ pattern เชิงโครงสร้างแบบลึกของ ts-pattern ไปได้ไกลกว่าที่ match ของ Glyph แสดงได้
  • "การพิสูจน์ว่าไม่มี" หยุดที่ขอบเขตของ .ts การรับประกันของ Glyph ใช้กับโค้ดที่เขียนด้วย Glyph exception ที่ throw จาก dependency ของ npm ยังข้าม Result ไปได้ และ type จาก .d.ts ที่ import มาไม่มี runtime descriptor
  • Ecosystem และการจ้างคน เครื่องมือ ชุมชน และกลุ่มคนที่จ้างได้ของ TypeScript ใหญ่กว่ามาก และมีการใช้งานจริงใน production มาหลายปี Glyph ยังเป็นพรีวิวช่วงแรก

ถ้าคุณผูก TypeScript ที่ใส่เครื่องมือครบไว้หมดแล้วและเอเจนต์อยู่ภายในนั้น คุณก็ได้ส่วนใหญ่ของสิ่งนี้แล้ว ข้อโต้แย้งของ Glyph คือ "อยู่ภายในนั้น" เป็นวลีที่รับน้ำหนักทั้งหมด และเป็นวลีที่เอเจนต์ทำพัง ความเป็นข้อบังคับ validation ที่มีสิ่งเดียว และการแก้ค่าที่ grep หาได้ คือส่วนที่คุณไม่ได้จากการเพิ่มเครื่องมือแบบเลือกเปิดเข้าไปอีก

ถ้าคุณพร้อมจะออกจาก TypeScript ไปใช้ภาษาที่มี type รุ่นเก่ากว่าที่คอมไพล์เป็น JavaScript ทำไมไม่ใช้ ReScript, Gleam หรือ Elm? เปรียบเทียบ Glyph กับภาษาเหล่านั้น

ใช้ได้วันนี้

ไม่มี any/as, match ที่ต้องครบทุกกรณี (E0200/E0218), คำเตือนเมื่อทิ้ง Result (E0217), validator ที่ generate จาก type และการแก้ค่าที่ grep หาได้: ทั้งหมดไม่ใช่ตัวเลือก ไม่มีข้อไหนเป็นกฎ eslint ที่คุณปิดได้

กำลังวัด

ข้อกล่าวอ้างว่าเอเจนต์สร้าง defect ที่หลุดออกไปใน Glyph น้อยกว่าใน TS แบบ strict ที่ตั้งค่ามาอย่างดี คือ benchmark ที่เรากำลังสร้าง โดยเทียบกับ TS ที่ใส่เครื่องมือครบ ไม่ใช่ TS แบบดิบ ดูbenchmark
