การออกแบบ

สี่เสาหลัก และบันทึก decision สำหรับทุกกฎ

ทุกกฎใน Glyph ถูกทดสอบกับคุณสมบัติสี่ข้อ และแต่ละกฎเป็น decision ที่มีหมายเลขในสเปกพร้อมเสาหลักที่มันรับใช้ เสาหลักเป็นคุณสมบัติของภาษา ไม่ใช่ของการตั้งค่าโปรเจกต์ เอเจนต์ที่เปิด codebase ของ Glyph ที่ไม่คุ้นเคยจึงพึ่งพามันได้โดยไม่ต้องไปหาก่อนว่าโปรเจกต์เลือกตั้งค่าอะไรไว้

เสาหลัก

เรียงตามความสำคัญ สองข้อแรกคือจุดหลัก เป็นปัญหาที่คุณเจอทุกวัน สองข้อหลังคือส่วนเสริมที่ทำให้ใช้แล้วสบาย เมื่อขัดกัน สองข้อแรกชนะ

เสาหลัก 01ตรวจสอบได้

ไม่มี any และไม่มี as ให้เขียน match ต้องครอบคลุมทุก case และ type ที่เป็น record และ union จะ generate validator แบบเข้มสำหรับตอนรัน ค่าที่ขอบเขตจึงถูกตรวจ ไม่ใช่ถูกสันนิษฐาน เป็นชั้นที่เข้มอยู่บน tsc ซึ่งปิดไม่ได้ ข้อผิดพลาดหลายอย่างที่ tsc --strict ยอมรับคอมไพล์ไม่ผ่านที่นี่ ส่วนที่ยังผ่านได้อยู่แสดงไว้ในสิ่งที่ยังจับไม่ได้

เสาหลัก 02ค้นหาได้ด้วย grep

หนึ่งชื่อ หนึ่งที่ ทุกสัญลักษณ์มีรูปแบบทาง syntax เพียงแบบเดียวที่ declaration ของมัน ไม่มี overload, decorator, this แบบแฝง หรือการ merge namespace grep "fn parseUser" เจอนิยามเลย

 เสาหลัก 03นามธรรม

เขียนตามที่ตั้งใจ: pattern matching แทนบันได switch, Result แทน exception ที่ throw, record ที่มีชื่อแทน tuple จาก core เล็กๆ ที่แต่ละส่วนตั้งฉากกัน ไม่ใช่ชั้นที่พอกพูนกันมาแบบ TypeScript

 เสาหลัก 04diff ที่คงที่

การแก้หนึ่งบรรทัดคือ diff หนึ่งบรรทัด มี layout มาตรฐานแบบเดียว: list อยู่ในบรรทัดเดียวเมื่อพอดี และหนึ่ง element ต่อบรรทัดเมื่อไม่พอดี ไม่มีการจัดกลุ่มใหม่ มี trailing comma ไม่มี barrel file และไม่มีตัวเลือก โค้ดเดียวกันจึงพิมพ์ออกมาเหมือนกันในทุกโปรเจกต์ คนรีวิวอ่านการเปลี่ยนแปลง ไม่ใช่ความวุ่นวายรอบๆ

สเปกคือรายการ decision

docs/language/spec.md มี decision ที่มีหมายเลข 49 ข้อ ตั้งแต่ D1 ถึง D49 แต่ละข้อปิดท้ายด้วยเสาหลักที่มันรับใช้ grammar ทำตามสเปก: ความกำกวมจะถูกแก้ในสเปกก่อน แล้วจึงเขียนลงใน parser glyph llms --json parse รายการนี้ออกมาจากสเปก เอเจนต์จึงอ่าน decision ชุดเดียวกับคุณ ตัวอย่างหนึ่ง แบบย่อ:

D9 จาก docs/language/spec.md (แบบย่อ) 
D9. `else` is a catch-all arm; `_` is a position-level wildcard;
a PascalCase arm head is a variant reference, not a binding.

... a PascalCase head that names no variant of that union is a
compile error (E0220, with a nearest-variant suggestion), never a
silent catch-all that would mask a missing variant (E0200) and
misroute values at runtime. ...

*[verifiability, abstraction]*

สิ่งที่ตั้งใจตัดออกไป

แถลงการณ์ ระบุจุดยืนไว้ ฉบับย่อคือข้อจำกัดแต่ละข้อต้องพิสูจน์ว่าคุ้มค่ากับเสาหลักข้อใดข้อหนึ่ง Glyph ไม่มี if/else (match เป็นเงื่อนไขแบบเดียว) ไม่มี class ไม่มี overload หรือ decorator ไม่มี cast ไม่มี any ไม่มี import แบบ relative และไม่มีตัวเลือกของ formatter และมันปรับแต่งไม่ได้ด้วย: formatter เดียว การ resolve module แบบเดียว ความเข้มระดับเดียว ข้อจำกัดที่น่ารำคาญจะได้เอกสาร ไม่ใช่กฎที่หลวมลง

การเปรียบเทียบ

Glyph ใกล้เคียงกับหลายสิ่งที่มีอยู่แล้ว และการเปรียบเทียบแต่ละข้อด้านล่างบอกว่าอีกทางเลือกทำอะไรได้ดีกว่า

ทำไมต้อง TypeScript ไม่ใช่ Go หรือภาษาใหม่?

ทำไมเป้าหมายคือ TypeScript และสิ่งนั้นทำให้อะไรเป็นไปได้: การนำมาใช้ทีละไฟล์

 ทำไมไม่ใช้ TypeScript แบบ strict + zod + eslint + ts-pattern?

การตรวจแบบเดียวกันในรูปการตั้งค่า เทียบกับในรูปภาษา และจุดที่ TypeScript ที่ใส่เครื่องมือครบยังทำได้ดีกว่า

 เทียบกับ Effect แล้วเป็นอย่างไร?

ไลบรารี TypeScript ที่มี error แบบมี type และ ecosystem ขนาดใหญ่ เทียบกับภาษาที่เอาทางหนีทีไล่ออกไป

 ทำไมไม่ใช้ ReScript, Gleam หรือ Elm?

สามภาษาที่มี type รุ่นเก่ากว่าที่คอมไพล์เป็น JavaScript แต่ละตัวเหนือกว่าตรงไหน และ Glyph ทำอะไรต่างออกไป

 นี่เป็นภาษาจริง หรือของเล่นที่มีช่องโหว่?

การมองเห็นของ module, interface, defer, standard library และขอบเขตที่ยังมีอยู่

สมมติฐานเบื้องหลังทั้งหมดนี้ ซึ่งยังไม่ใช่ผลลัพธ์: เอเจนต์ที่ได้งานเดียวกันจะเขียนโค้ดที่ถูกต้องได้สม่ำเสมอกว่าใน Glyph มากกว่าใน TypeScript และคนรีวิวใช้เวลายืนยันน้อยกว่า งานศึกษานั้นยังไม่ได้ทำ เว็บนี้จึงไม่ใส่ตัวเลขให้มัน Benchmark บอกว่าตอนนี้วัดอะไรไปแล้วบ้าง
