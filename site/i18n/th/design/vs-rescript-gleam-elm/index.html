ทำไมไม่ใช้ ReScript, Gleam หรือ Elm?

ทั้งสามเป็นภาษาที่มี type และคอมไพล์เป็น JavaScript และทั้งสามเก่ากว่า มีคนใช้มากกว่า และนิ่งกว่า Glyph ถ้าคุณกำลังเลือกภาษาสำหรับ codebase ใหม่และไม่จำเป็นต้องอยู่ใกล้ TypeScript ก็ควรดูพวกมันก่อน ความต่างของ Glyph แคบกว่านั้น: มัน emit ซอร์ส TypeScript แทน JavaScript import แพ็กเกจ npm โดยได้ type จาก .d.ts ของแพ็กเกจเอง generate validator สำหรับตอนรันจาก type ของคุณ และคอมไพเลอร์ของมันตอบคิวรีเรื่องผลกระทบให้เอเจนต์ได้

แต่ละตัวอธิบายตัวเองอย่างไร

หน้าแรกของ ReScript เปิดด้วย "JavaScript Made Simple for Humans and AI" และ "Types > Vibes" และบอกว่ามัน "compiles to clean, efficient JavaScript" โดย "No any, no magic types, no surprise undefined." และเสนอว่าจะ "automatically generate TypeScript types" (rescript-lang.org)

หน้าแรกของ Gleam เรียกตัวเองว่า "a friendly language for building type-safe systems that scale" พร้อม "No null values, no exceptions, clear error messages" มันรันบน Erlang VM และ "can additionally compile to JavaScript" และ "also generates TypeScript definitions" (gleam.run)

หน้าแรกของ Elm อธิบายว่าเป็น "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions" สำหรับ "reliable web applications" และบอกว่า Elm "detects all API changes automatically" เพื่อ "guarantee that every single Elm package follows semantic versioning" (elm-lang.org)

จุดที่พวกมันเหนือกว่า

ด้านReScript, Gleam, ElmGlyph
ความเติบโตเต็มที่ใช้งานจริงใน production มาหลายปี หน้าแรกของ ReScript แสดงโลโก้บริษัทเต็มหน้า ส่วน Elm อ้างถึง NoRedInk ที่มีโค้ดมากกว่า 300k บรรทัดและไม่มี runtime exception ที่สับสนใน productionพรีวิวช่วงแรก ยังไม่ถึง 1.0 ดูแลหลักๆ โดยคนคนเดียว และหลายรุ่นเป็น Breaking
การรับประกันElm อ้างว่าไม่มี runtime exception, Gleam ไม่มีค่า null และไม่มี exception, ReScript ไม่มี any และไม่มี undefined ที่ไม่คาดคิดไม่มี any และไม่มี cast แต่ช่องโหว่ที่รู้แล้ว {{catches:gap-cases}} ข้อแสดงไว้ และ exception ที่ throw จากภายในแพ็กเกจ npm ยังข้าม Result ไปได้
ข้อความ errorหน้าแรกของ Elm เปิดด้วย "friendly error messages" และ Gleam สัญญาว่ามี "clear error messages" ทั้งคู่มีผู้ใช้หลายปีอยู่เบื้องหลังทุก error มีรหัสที่คงที่และบรรทัดช่วยเหลือ แต่ถูกใช้งานมาน้อยกว่ามาก
เครื่องมือและ ecosystemGleam มาพร้อม "compiler, build tool, formatter, editor integrations, and package manager all built in" ส่วน Elm บังคับใช้ semantic versioning กับแพ็กเกจของมันใช้ npm สำหรับแพ็กเกจ extension ของ VS Code ต้อง build จากซอร์ส
เป้าหมายGleam รันบน Erlang VM ได้ด้วยTypeScript เท่านั้น สำหรับ Node และเบราว์เซอร์

สิ่งที่ Glyph ทำต่างออกไป

แต่ละข้อนี้รันบน Glyph 0.1.149 สำหรับหน้านี้

มัน emit ซอร์ส TypeScript

glyph build เขียนไฟล์ .ts หนึ่งไฟล์ต่อหนึ่ง module ซึ่ง tsc --strict ตรวจต่อ และคุณเก็บไว้ใช้ได้ถ้าเลิกใช้ Glyph ReScript และ Gleam emit JavaScript และ generate type definition ไว้ข้างๆ TypeScript ที่ emit ออกมาแสดงไว้ในหน้า TypeScript

มัน import แพ็กเกจ npm โดยได้ type จาก declaration ของแพ็กเกจเอง

module หนึ่ง import แพ็กเกจด้วยชื่อ และ .d.ts ของแพ็กเกจให้ type กับทุกจุดที่ใช้ ไม่มี binding ที่ต้องเขียนก่อน ใน ReScript "external is the primary ReScript feature for bringing in and using JavaScript values" (external) โดยประกาศ type ไว้ฝั่ง ReScript ส่วน external ของ Gleam ต้องมี type annotation และคอมไพเลอร์ "cannot verify that the function implemented in the other language returns the specified types" (externals) Elm คุยกับ JavaScript ผ่าน flag, port และ custom element (interop) เมื่อติดตั้ง pg และ @types/pg แล้ว โค้ดนี้จะถูกปฏิเสธ:

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

รหัสเป็น TS2322 เพราะ tsc คือตัวที่ตรวจค่าของไลบรารี แล้ว map กลับมาที่บรรทัดของ Glyph ตัวตรวจของ Glyph เองมองไม่เห็นค่าเหล่านี้ glyph check --no-tsc, editor และเครื่องมือ MCP จึงพลาด error นี้ (G257) type ที่ import จาก .d.ts ก็ไม่มีการตรวจตอนรันด้วย

มัน generate validator จาก type

ทุก record และ union มีการตรวจตอนรันที่ generate จาก declaration ของมัน json.parse<User> จึงคืน Err เมื่อข้อมูลไม่ตรง ใน Elm คุณเขียน decoder ให้แต่ละรูปร่าง และคู่มือของมันบอกว่า "the decoders people write end up working as a validation phase" (JSON)

main.glyph: พิมพ์ "refused" เพราะ JSON ไม่มี email 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

คอมไพเลอร์ของมันตอบได้ว่าการเปลี่ยนแปลงจะทำอะไรพัง

ก่อนแก้ เอเจนต์ถามได้ว่าการเปลี่ยนแปลงไปถึงจุดไหนบ้าง ผ่าน MCP (glyph_impact) หรือด้วย glyph query impact บน union Plan = Free | Pro | Team ที่มี match แบบครบทุกกรณีหนึ่งจุด และอีกจุดที่ลงท้ายด้วย else การถามถึง variant ใหม่จะได้คำตอบรายจุด:

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

จุดที่สองจะคอมไพล์ไม่ผ่านหลังการเปลี่ยนแปลง ซึ่งคอมไพเลอร์ของทั้งสามภาษาก็บอกได้เมื่อเปลี่ยนไปแล้ว จุดแรกจะยังคอมไพล์ผ่านและส่ง case ใหม่ไปที่ else ของมัน และคิวรีนี้คือสิ่งที่ระบุชื่อมัน สำหรับคนสร้างเอเจนต์แสดงเครื่องมืออื่นๆ

สิ่งที่หน้านี้ไม่ได้อ้าง

หน้านี้ไม่ได้เปรียบเทียบข้อความ error ความเร็วในการคอมไพล์ หรือประสิทธิภาพตอนรัน และไม่ได้ลองเรียกภาษาใดในสามภาษานี้จาก Glyph หรือในทางกลับกัน ข้อความที่ยกมาอธิบายแต่ละโปรเจกต์ด้วยถ้อยคำของมันเอง แต่ละตัวทำได้ตามนั้นแค่ไหนเป็นสิ่งที่คุณต้องตรวจเอง เช่นเดียวกับข้อกล่าวอ้างของ Glyph เองในหน้าหลักฐาน
