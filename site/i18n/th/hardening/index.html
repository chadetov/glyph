Glyph ถูกทำให้แข็งแรงอย่างไร

เอเจนต์พยายามทำให้พัง และเราเก็บสิ่งที่พวกมันเจอไว้

ภาษาที่บอกว่าเอเจนต์ของคุณทำพังแบบเงียบๆ ไม่ได้ ต้องถูกทดสอบตามนั้น เรารันเอเจนต์ AI ที่สวมบทวิศวกรขี้สงสัย (นักพัฒนา React ที่หงุดหงิด คนทำ backend ที่ชอบเถียง และคนที่จ้องหาช่องโหว่ด้านความปลอดภัย) ให้สร้างแอปและพยายามทำลายการรับประกัน แล้วแก้สิ่งที่พวกมันเจอ หรือบันทึกไว้เป็น gap ที่ยังเปิดอยู่ นี่คือ loop นั้น และสิ่งที่มันเจอ

กรณีที่ผ่าน tsc --strict แต่คอมไพล์ไม่ผ่านใน Glyph

แต่ละกรณีมีสองไฟล์: .ts ที่ตรวจ type ผ่านสะอาดภายใต้ tsc --strict และโปรแกรมเดียวกันใน Glyph ที่คอมไพล์ไม่ผ่าน build gate ชื่อ scripts/check_catches.py รันทุกกรณีซ้ำ และจะ fail ถ้าฝั่งใดฝั่งหนึ่งไม่ทำงานตามที่ควร การรับประกันที่หายไปเงียบๆ จึงทำให้ build พังไปด้วย ตารางแสดง {{catches:refused}} ข้อจากกรณีของ TypeScript {{catches:count}} ข้อในหน้าสิ่งที่จับได้ที่ถูกปฏิเสธด้วยวิธีนี้ หน้านั้นมีส่วนที่เหลือ ซึ่ง Glyph ตรวจเมื่อข้อมูลเข้ามา เตือน หรือหยุดตอนรัน {{catches:breakdown}}

{{catches:refused-table}}

กรณีที่กลายเป็นว่า TypeScript ก็จับได้ หรือที่สองฝั่งไม่ใช่โปรแกรมเดียวกัน ถูกลบทิ้งไม่ใช่ถูกทำให้อ่อนลง catches/README.md แสดงแต่ละกรณีพร้อมเหตุผล

การอ่านจาก map ถูกปฏิเสธแม้จะสะกด key ถูก เพราะ Record<string, string> ไม่ได้บอกอะไรเลยว่ามี key ไหนอยู่บ้าง TypeScript จับได้ด้วย noUncheckedIndexedAccess ซึ่ง --strict ไม่ได้เปิดให้ case ของ union ที่ขาดไปก็จับได้ใน TypeScript เช่นกัน ด้วย switch-exhaustiveness-check ของ typescript-eslint หรือ default แบบ assertNever ถ้าโปรเจกต์เลือกใช้ ใน Glyph การตรวจทั้งสองอย่างไม่ใช่ตัวเลือก

ในกรณี body ที่ parse แล้ว json.parse ของ Glyph คืนค่าเป็น Result ไม่ใช่ User การ assign จึงเป็น type ที่ไม่ตรงกันจนกว่า body จะถูกตรวจ JSON.parse ของ TypeScript คืนค่า any และ annotation บน user ก็ฟอกมันให้ดูสะอาด

loop แบบปรปักษ์

ทุกสิ่งที่เจอจะถูกทำซ้ำกับคอมไพเลอร์ แก้ที่ต้นเหตุ และยืนยันซ้ำโดยอิสระก่อนจะนับ

1

สำรวจ

เอเจนต์ที่สวมบทบาทสร้างโปรแกรม (ฟอร์ม backend UI ที่มี state) และบันทึกทุกจุดที่ภาษาขัดขวางพวกมัน

2

ทำซ้ำ

ทุกสิ่งที่เจอถูกย่อให้เหลือโปรแกรมที่ล้มเหลวที่เล็กที่สุด แล้วรันซ้ำกับคอมไพเลอร์ อะไรที่ทำซ้ำไม่ได้จะถูกทิ้ง

3

แก้

แก้ที่ต้นเหตุในคอมไพเลอร์ Rust พร้อม regression test ที่ fail ก่อนแก้และผ่านหลังแก้ เทสต์ทั้งชุดต้องยังเขียวอยู่ ไม่อย่างนั้นการเปลี่ยนแปลงจะถูก revert

4

ยืนยัน

รอบตรวจที่เป็นอิสระรันโค้ดทำซ้ำทุกตัวกับคอมไพเลอร์ที่เพิ่ง build ใหม่ เพื่อจับ gap แบบ “เอเจนต์คิดว่าแก้แล้ว” ก่อนที่อะไรจะถูกปล่อยออกไป

ที่สำคัญที่สุด: ช่องโหว่ที่ทำให้ผิดแบบเงียบๆ

แต่ละข้อนี้คอมไพล์ผ่านสะอาด และอาจปล่อยโค้ดผิดที่ผ่านการตรวจ typeออกไปได้ ซึ่งเป็นประเภทบั๊กที่ Glyph มีไว้ป้องกันพอดี ตอนนี้ทุกข้อถูกจับได้ตอนคอมไพล์

วิกฤต แก้แล้ว

error variant ที่ไม่มี payload ใน match ของ Result

match บน Result<T, Empty | BadQty(...)> ถูกแปลงเป็น branch case "Err" ซ้ำกันสองตัว ตัวแรกกลืน error ทุกตัวและส่งไปยัง arm ที่ผิดแบบเงียบๆ

ตอนนี้: case เดียวที่จัดกลุ่มแล้ว พร้อม switch ด้านในที่ถูกต้อง แต่ละ variant ไปถูกที่

วิกฤต แก้แล้ว

constructor ที่สะกดผิดกลายเป็น catch-all แบบเงียบๆ

variant ที่พิมพ์ผิดใน arm ของ match (Loded แทน Loaded) ถูก bind เงียบๆ เป็น catch-all ที่ match ได้ทุกอย่าง ทำให้มองไม่เห็นว่าไม่ครบทุกกรณี และส่งผิดที่ตอนรัน โดยไม่มี diagnostic เลย

ตอนนี้: constructor ที่ไม่รู้จักถูกปฏิเสธตรงจุดที่พิมพ์ผิด เหมือนชื่อทั่วไป

สูง แก้แล้ว

match บน bool ที่ไม่ครบหลุดการตรวจความครบถ้วนไปได้

match n > 0 { true => ... } (ขาด arm false) คอมไพล์ผ่านและผ่าน tsc แล้ว throw ตอนรัน

ตอนนี้: เป็น error แบบ match ไม่ครบทุกกรณีตอนคอมไพล์

สูง แก้แล้ว

component ที่มีหลาย parameter bind props ผิด

component C(a, b) emit parameter ตามตำแหน่ง แต่ React เรียก component โดยส่ง props เป็นตัวแรก a จึงถูก bind เงียบๆ กับ props object ทั้งก้อน และมันผ่าน tsc

ตอนนี้: compile error ที่ชัดเจน ชี้ไปที่รูปแบบ props record ตัวเดียว

สูง แก้แล้ว

<match> ใน JSX ข้ามการตรวจความครบถ้วน

<match> ใน JSX ที่ขาด <case> คอมไพล์ผ่านเขียวแล้ว throw ตอนรัน ต่างจาก match ระดับค่าที่ถูกตรวจ

ตอนนี้: ใช้การตรวจความครบถ้วนแบบเดียวกัน case ที่ขาดเป็น compile error

สูง แก้แล้ว

payload ที่เป็น record ถูก bind กับ field ผิด

การ bind variant ที่มี payload เป็น record เข้ากับชื่อ (BadQty(b)) ไปอ่าน .value ที่ไม่มีอยู่จาก payload ที่ถูกแผ่ออก

ตอนนี้: payload ถูก bind อย่างถูกต้อง b.sku จึงใช้ได้

กฎที่ตัวตรวจบังคับใช้แล้วตอนนี้

ความถูกต้องที่คอมไพเลอร์เคยปล่อยให้ tsc จัดการ ตอนนี้ Glyph จับได้เอง

แก้แล้ว

จำนวน argument ในการเรียก

argument ที่น้อยหรือมากเกินไปเคยถูกยอมรับ (และรันได้ NaN) ตอนนี้ E0213 ปฏิเสธจำนวน argument ที่ผิด

แก้แล้ว

error type ของ ? ข้ามขอบเขตของ stdlib

กฎเรื่อง error type ต้องตรงกันพอดีเคยถูกข้ามเมื่อ error มาจาก wrapper ของ stdlib ตอนนี้บังคับใช้ที่นั่นด้วย

แก้แล้ว

การสร้างชื่อแฝงให้ handle แบบ owned

let g = f บน resource handle สร้าง binding ตัวที่สองที่อาจปิดซ้ำสองครั้ง ตอนนี้ถูกปฏิเสธ (E0215)

แก้แล้ว

arm ที่ไปไม่ถึง และการ validate ที่ลึกขึ้น

arm ที่อยู่หลัง catch-all ถูกเตือนแล้ว json.parse<T> ตอนนี้ validate field ของ Record ตามโครงสร้าง แทนที่จะตรวจแค่ว่ามีอยู่

ความติดขัดตอนใช้ครั้งแรก เอาออกแล้ว

เรื่องเล็กๆ ที่ทำให้ความประทับใจแรกแย่ และไม่มีประโยชน์อะไรเลย

แก้แล้ว

Accessibility และ data attribute

aria-label และ data-* เคยถูก parse เป็นการลบ ตอนนี้ใช้ได้ และ emit เป็น React props ที่ถูกต้อง

แก้แล้ว

ชื่อแพ็กเกจ npm

ชื่อที่มีขีดและมี scope (react-hook-form, @hookform/resolvers/zod) เคยถูกปฏิเสธ ตอนนี้ import ได้โดยตรง

แก้แล้ว

การรันครั้งแรกใน browser bundle

runtime bootstrap ไม่ถูกโหลดใน build สำหรับเบราว์เซอร์ ทำให้ crash ตอนรันครั้งแรก ตอนนี้ทุก module ที่ emit ออกมาดึงมันเข้ามาด้วย

แก้แล้ว

ข้อความ error ที่ชี้ผิดทาง

การเขียน if ตอนนี้ชี้ไปที่ match range pattern บอกไว้ตรงๆ และจัดการ whitespace ใน JSX กับ $ เดี่ยวๆ ในข้อความได้แล้ว

ยังเปิดอยู่: บันทึกไว้

การทำให้แข็งแรงหมายถึงการระบุสิ่งที่ยังไม่เสร็จด้วย สิ่งเหล่านี้รู้แล้วและถูกติดตาม ไม่ได้ซ่อนไว้

ตั้งใจเลื่อนออกไป หรือรอ design decision:

การปฏิเสธ closure ที่เป็น any แบบแฝงในตัวตรวจของ Glyph เองต้องใช้การอนุมานตามบริบท เพื่อไม่ให้เตือนผิดกับ callback ที่มี type ถูกต้อง FFI ที่ใช้สะดวก คือการใช้ไลบรารี TS ที่มี type ซับซ้อนโดยไม่ต้องมี adapter แยกแต่ละไลบรารี เป็นคำถามเรื่อง interop ที่ใหญ่ที่สุดที่ยังเปิดอยู่ ติดตามไว้ใน open questions map ที่มาจาก module อื่นหรือจาก standard library ยังถูกอ่านโดยไม่ตรวจ E0224 จึงยังไปไม่ถึง sqlite.Row และ for i, x in xs ที่มีสอง binding ยังเสีย type ของ element ไป
