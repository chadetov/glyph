เสาหลัก 03 · ส่วนเสริม

นามธรรม

เขียนตามที่ตั้งใจด้วยcore เล็กๆ ที่แต่ละส่วนตั้งฉากกัน: pattern matching แทนบันได switch, Result แทน exception ที่ throw, record ที่มีชื่อแทน tuple หนึ่งวิธีที่ดีต่อหนึ่งแนวคิด ไม่ใช่ชั้นที่พอกพูนกันมาแบบ TypeScript

ในหน้านี้

  1. วิธีที่มากเกินไป
  2. match เป็นเงื่อนไข
  3. tagged union
  4. Result แทน exception
  5. record ที่มีชื่อ
  6. หนึ่ง primitive ต่องาน
  7. benchmark

วิธีพูดเรื่องเดียวกันมีมากเกินไป

TypeScript โตมาด้วยการพอกพูน และเก็บทุกชั้นไว้

  • ชุด case ที่ตายตัวคุณ model ชุด case ที่ตายตัวได้เป็น enum, union ของ string literal หรือ object แบบ const
  • รูปร่างคุณอธิบายรูปร่างได้ด้วย interface, type หรือ class
  • ที่เหลือทั้งหมดมี namespace และ module, decorator และ higher-order function มีห้า idiom สำหรับแทบทุกอย่าง แต่ละตัวมีกรณีขอบของตัวเอง

สำหรับคน นั่นคือความยืดหยุ่น สำหรับเอเจนต์มันคือทุ่นระเบิด: วิธีแสดงสิ่งหนึ่งที่มากขึ้นหมายถึงโอกาสเลือกตัวที่มีกับดักมากขึ้น และมี idiom ให้จำไม่ให้สับสนมากขึ้น

เสาหลักเรื่องนามธรรมของ Glyph คือการลบออกโดยตั้งใจ: เครื่องมือคมหนึ่งชิ้นต่องาน เลือกให้วิธีที่ชัดที่สุดเป็นวิธีที่ปลอดภัยด้วย

01 match เป็นเงื่อนไขแบบเดียว

ไม่มี statement if/else การแตก branch คือ match ทุกที่ และ match เป็น expression: มันให้ค่า

construct เดียวครอบคลุมการทดสอบ boolean การ dispatch ตาม union และตารางค่า จึงไม่ต้องตัดสินใจว่าจะใช้รูปแบบการแตก branch แบบไหน

02 tagged union และ pattern matching

วิธี model "หนึ่งในรูปร่างเหล่านี้" คือ tagged union และวิธีแยกมันออกคือ match ซึ่ง destructure payload ในขั้นเดียวกับที่เลือก case

feed.glyph 
type Feed =
  | Loading
  | Loaded(Array<Post>)
  | Failed(string)

fn view(feed: Feed) -> string {
  return match feed {
    Loading => "...",
    Loaded(posts) => render(posts),   // posts is Array<Post> here
    Failed(msg) => msg,               // msg is string here
  }
}
รายละเอียด สิ่งที่คุณไม่ต้องเขียนเองอีกต่อไป

ไม่มี field discriminant ให้ดูแลเอง ไม่มีบันได switch บน tag ที่เป็น string ไม่มี cast ในแต่ละ branch เพื่อกู้รูปร่างคืน

03 Result แทน exception

ความล้มเหลวเป็นค่า ไม่ใช่การกระโดดของ control flow ที่ซ่อนอยู่ ฟังก์ชันที่อาจล้มเหลวบอกไว้ใน return type (Result<T, E>) และคุณประกอบความล้มเหลวด้วย operator ? แทนที่จะครอบจุดเรียกด้วย try/catch แล้วหวังว่าสิ่งที่ถูกจะ throw class ที่ถูก

เส้นทาง error มองเห็นได้เท่ากับเส้นทางปกติ

04 record ที่มีชื่อแทน tuple ตามตำแหน่ง

ข้อมูลอธิบายด้วย field ที่มีชื่อเสมอ รูปร่างอ่านเหมือนกันทั้งที่นิยาม ที่สร้าง และที่ใช้

TypeScript: [0] กับ [1] คืออะไร? point.ts 
function origin(): [number, number] {
  return [0, 0];
}
const p = origin();
p[0]; p[1];  // x? y? row? col?
Glyph: ชื่อเดินทางไปพร้อมค่า point.glyph 
type Point = { x: number, y: number }

fn origin() -> Point {
  return { x: 0, y: 0 }
}
รายละเอียด ไม่มี shorthand ไม่มี tuple นิรนาม

ไม่มี object-literal shorthand และไม่มีการหยิบ tuple นิรนามที่คุณต้องจำว่า [0] และ [1] คืออะไร

05 primitive หนึ่งตัวต่องาน

เมื่อแนวคิดหนึ่งต้องมีเครื่องมือของตัวเอง Glyph ให้แค่หนึ่งตัวพอดี

  • state ที่ใช้ร่วมกันstate ที่ใช้ร่วมกันและเปลี่ยนค่าได้อยู่ใน std/store
  • handlehandle ของไฟล์หรือ socket ที่ต้องปิดครั้งเดียวคือ resource แบบ owned
  • การวนซ้ำการวนซ้ำคือ for x in xs

แต่ละตัวเป็น primitive เดียวที่มีชื่อและสร้างมาเพื่องานนั้น ไม่ใช่ pattern ที่คุณต้องประกอบใหม่จากชิ้นส่วนทั่วไปแล้วทำผิดแบบแนบเนียน

นามธรรมในที่นี้หมายถึงเครื่องมือที่น้อยลงและคมขึ้น ไม่ใช่มากขึ้น ทุกแนวคิดมีรูปแบบที่ชัดเจน และรูปแบบที่ชัดเจนคือรูปแบบที่ตั้งใจให้ใช้

benchmark: กำลังมา

วิธีวัดเรื่องนี้คือพื้นที่ผิว: คนอ่านต้องถือแนวคิดที่แตกต่างกันกี่อย่างเพื่อเข้าใจโปรแกรม และต้องใช้โค้ดเท่าไรในการแสดงงานทั่วไปอย่างสะอาด

Glyph ยังไม่ได้ใช้งานจริงในโลกภายนอก กราฟด้านล่างจึงเป็นที่ว่างรอไว้ ซึ่งจะเติมด้วยการวัดจริงเมื่อมีโปรแกรมจริงมากพอให้เปรียบเทียบ

จำนวนแนวคิดที่แตกต่างกันในการอ่าน module ทั่วไป · ยิ่งน้อยยิ่งดี

core ที่เล็กกว่าเรียนรู้ได้ง่ายกว่าสำหรับคน ซึ่งเรียนครั้งเดียว และทำให้ถูกได้ง่ายกว่าสำหรับโมเดลทุกครั้ง นั่นคือชั้นส่วนเสริมทั้งหมดในประโยคเดียว: เอาตัวเลือกที่เพิ่มแค่ความเสี่ยงออกไป แล้วสิ่งที่เหลือคือภาษาที่พูดตามที่หมายถึง
