เสาหลัก 03 · ส่วนเสริม

diff ที่คงที่

การแก้หนึ่งบรรทัดคือdiff หนึ่งบรรทัด รูปแบบมาตรฐานเดียว trailing comma และ list ที่อยู่ในบรรทัดเดียวทั้งหมด หรือหนึ่ง element ต่อบรรทัดทั้งหมด ไม่มีการจัดกลุ่มใหม่ การรีวิวจึงแสดงการเปลี่ยนแปลงที่เกิดขึ้น ไม่ใช่ความวุ่นวายรอบๆ

การรีวิวคือการอ่าน diff

แทบทุกอย่างที่เราเชื่อถือเกี่ยวกับการเปลี่ยนแปลง (การรีวิว blame การ revert การ bisect) สร้างบน diff อัตราส่วนสัญญาณต่อสิ่งรบกวนของ diff จึงเป็นสกุลเงินจริง ใน codebase ส่วนใหญ่มันแย่มาก: formatter จัดบรรทัดที่ตัดไว้ใหม่ ตัวเรียง import สลับทั้ง block การเปลี่ยนชื่อแตะ whitespace ของทุกจุดที่เรียก และบรรทัดเดียวที่สำคัญก็จมอยู่ในห้าสิบบรรทัดที่ไม่สำคัญ

เอเจนต์ทำให้เรื่องนี้แย่ลงมาก เมื่อได้งานเล็กๆ โมเดลยินดีเขียนทั้งฟังก์ชันหรือทั้งไฟล์ใหม่เพื่อเปลี่ยนสิ่งเดียว เพราะการสร้างใหม่ง่ายกว่าการแก้อย่างแม่นยำสำหรับมัน คนรีวิวต้องมาเทียบ diff ระหว่างของที่เขียนใหม่กับต้นฉบับ และหวังว่าการเปลี่ยนแปลงจริงมีแค่ที่ตั้งใจ Glyph สร้างมาให้ layout ไม่มีอะไรให้โมเดลปั่นป่วน

01 layout มาตรฐานเดียว ไม่มีตัวเลือก

glyph fmt พิมพ์ทุกไฟล์ใหม่ใน layout ตายตัวแบบเดียว: ย่อหน้าสองช่อง trailing comma ในทุก list ที่มีหลายบรรทัด และ list ที่อยู่ในบรรทัดเดียวขณะที่ยังพอดีใน 100 คอลัมน์ และเป็นหนึ่ง element ต่อบรรทัดเมื่อไม่พอดี เป็นแบบทั้งหมดหรือไม่มีเลย formatter ไม่เคยจัดกลุ่ม element ใหม่ให้เต็มบรรทัด list จึงไม่มีวันอยู่บรรทัดหนึ่งบางส่วนและบรรทัดถัดไปบางส่วน และการเพิ่ม field คือการเพิ่มหนึ่งบรรทัด เพราะมีรูปร่างที่ถูกต้องเพียงแบบเดียว จึงไม่มีอะไรให้เถียงกัน และไม่มีอะไรให้เครื่องมือแอบ "แก้" ไปด้วย

เกณฑ์ความกว้างคือต้นทุนของเรื่องนี้ เปลี่ยนชื่อ binding จนการเรียกเกิน 100 คอลัมน์ แล้วการเรียกจะขยายเป็นหนึ่ง argument ต่อบรรทัด: แก้หนึ่ง token ได้ diff สี่บรรทัด สิ่งที่แลกมาคือ layout ขึ้นกับโค้ดและคอลัมน์ที่มันเริ่มเท่านั้น เอเจนต์สองตัวที่แก้ไฟล์เดียวกันจึงได้ไบต์ที่ตรงกัน

สไตล์ที่จัดบรรทัดใหม่: การเปลี่ยนแปลงหนึ่งครั้ง แตะสามบรรทัด git diff (การจัดรูปแบบแบบอัดแน่น) 
- type User = { id: number, name:
-   string }
+ type User = { id: number, name:
+   string, email: string }
Glyph: การเปลี่ยนแปลงหนึ่งครั้ง เพิ่มหนึ่งบรรทัด git diff (แบบมาตรฐาน) 
  type User = {
    id: number,
    name: string,
+   email: string,
  }

trailing comma ทำงานอย่างเงียบๆ: เพราะ element สุดท้ายลงท้ายด้วย comma อยู่แล้ว การเพิ่มตัวข้างเคียงจึงไม่เคยแก้บรรทัดข้างบน แทรกหนึ่งครั้ง หนึ่งบรรทัด

02 ลำดับคงที่ ประวัติจึงอ่านได้

หนึ่ง element ต่อบรรทัดหมายความว่าการสลับลำดับ แทรก หรือลบรายการ แตะเฉพาะบรรทัดของรายการนั้น ไม่เคยแตะเพื่อนข้างเคียง git blame ยังมีความหมาย: commit ล่าสุดที่แตะแต่ละบรรทัดคือ commit ที่เปลี่ยน element นั้นจริง ไม่ใช่รอบจัดรูปแบบที่บังเอิญจัดแถวที่มันอยู่ร่วมใหม่

03 ไม่มีไฟล์ barrel: ไม่มีความวุ่นวายใน import

เพราะ import ไม่เคย re-export และไม่มีชั้นรวม index.ts (E0102) การเพิ่มหรือย้ายสัญลักษณ์จึงไม่กระเพื่อมผ่าน barrel ที่ผู้ใช้ทุกคน import เส้น dependency ที่คุณแก้คือเส้นที่คุณตั้งใจ ส่วนที่เหลือของกราฟ import ไม่ขยับ

04 การ generate ให้ผลเท่าเดิมเมื่อรันซ้ำ ไม่ใช่ก้อนทึบ

วินัยเดียวกันขยายไปถึงโค้ดที่ generate glyph gen และ glyph regen พิมพ์ output ใหม่ผ่าน formatter มาตรฐาน การ generate ใหม่หลังสเปกเปลี่ยนจึงได้ diff ที่เล็กที่สุดซึ่งรีวิวได้จริง เปลี่ยนไม่กี่บรรทัด ไม่ใช่แทนที่ไฟล์ที่เครื่องเขียนทั้งไฟล์ และทุก .ts ที่ emit มี source map มาด้วย แม้แต่ output ที่คอมไพล์แล้วก็ไล่กลับไปยังบรรทัดที่คุณแก้ได้สะอาด

เพิ่ม field ในสเปก → diff ที่ generate ใหม่ 
  type Task = {
    id: number,
    title: string,
+   done: bool,
  }
// glyph regen re-ran the recorded command; this is the whole diff.

05 "TypeScript ทำแบบนี้ได้ด้วย Prettier"

สำหรับการจัดรูปแบบส่วนใหญ่ ทำได้ Prettier ที่ตั้ง trailingComma: "all" ใส่ comma ให้ element สุดท้าย และพิมพ์ list ยาวเป็นหนึ่งตัวต่อบรรทัด ซึ่งได้ส่วนใหญ่ของหัวข้อ 01 แล้ว ความต่างอยู่สามที่

layout ขึ้นกับโค้ดเท่านั้น Prettier คง object literal ไว้แบบขยายถ้าคนเขียนขึ้นบรรทัดใหม่หลัง { และยุบมันถ้าไม่ได้ขึ้น object เดียวกันจึงพิมพ์ได้สองแบบขึ้นกับว่าพิมพ์มาแบบไหนตอนแรก เอเจนต์สองตัวที่เขียนสิ่งเดียวกันได้สอง layout และการแก้ครั้งถัดไปของตัวใดตัวหนึ่งจะโผล่เป็นการจัดบรรทัดใหม่ glyph fmt พิมพ์ { a: 1, b: 2 } แบบเดียวกันไม่ว่า input จะถูกตัดบรรทัดอย่างไร

ไม่มีอะไรให้ตั้งค่า output ของ Prettier เป็นไปตามไฟล์ config ของ repository และบาง repository ก็ไม่มี เอเจนต์ที่ย้ายไปมาระหว่างโปรเจกต์ TypeScript จะเจอ layout ต่างกันในแต่ละที่ ไฟล์ Glyph มี layout เดียวกันในทุกโปรเจกต์ เพราะ formatter ไม่มีตัวเลือก

formatter เปลี่ยนความหมายของไฟล์ไม่ได้ glyph fmt ถูกทดสอบโดย parse output ของตัวเองแล้วเทียบ syntax tree กับของ input บนทุกตัวอย่างใน repository และภายใต้ fuzzer เมื่อ comment อยู่ในที่ที่ layout ไม่มีบรรทัดให้ มันจะปฏิเสธไฟล์ (E0500) แทนที่จะย้าย comment ไปอยู่ข้างโค้ดที่มันไม่ได้อธิบาย

มีอย่างหนึ่งในรายการที่ยังไม่เสร็จ: glyph fmt ไม่เรียง import เอเจนต์สองตัวที่เพิ่ม import คนละตำแหน่งจึงยังได้ block ของ import ต่างกัน (G358)

diff ที่คงที่คือสิ่งที่เปลี่ยน "เอเจนต์เปลี่ยนอะไรบางอย่าง" ให้เป็น "เอเจนต์เปลี่ยนสิ่งนี้พอดี" เมื่อระดับสิ่งรบกวนเป็นศูนย์ การรีวิวก็เร็วและความไว้ใจก็ได้มาง่าย

benchmark: กำลังมา

ตัวเลขที่จับเรื่องนี้ได้คือขนาดของ diff ต่อการเปลี่ยนแปลงเชิงตรรกะหนึ่งครั้ง: มีกี่บรรทัดที่ขยับเมื่อคุณแก้ตามที่ตั้งใจหนึ่งครั้ง ใน Glyph เทียบกับการเปลี่ยนแปลง TypeScript ที่เทียบเท่าซึ่งผ่าน formatter ทั่วไป Glyph ยังไม่ได้ใช้งานจริงในโลกภายนอก กราฟด้านล่างจึงเป็นที่ว่างรอไว้ ซึ่งจะเติมด้วยการวัดจริงเมื่อมีประวัติจริงให้ดึงมา
