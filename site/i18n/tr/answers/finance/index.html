16 · Para ve güvenlik

Ona parayla ve kontrol etmediğim girdilerle güvenebilir miyim?

Evet. Para hesapları kesindir, negatif olmama gibi bir değişmez sınırda zorlanan bir tiptir ve güvenilmeyen girdi temizlenmeden bir SQL ya da shell hedefine ulaşamaz. Bunların her biri, yanlış yaparsanız bir derleme ya da parse hatasıdır; birinin üç fonksiyon ötede hatırlaması gereken bir gelenek değil.

Para bir float değildir

IEEE-754 number üzerine kurulmuş bir finans sistemi, bildirilmeyi bekleyen bir bug'dır: 0.1 + 0.2, 0.3 değildir ve 253'ü aşan değerler sessizce hassasiyet kaybeder. std/decimal, BigInt üzerinde kesin, 10 tabanlı sabit noktalı aritmetiktir. Toplama, çıkarma ve çarpma kesindir; bölme açık bir ölçek alır ve yarımı sıfırdan uzağa yuvarlar; hatalı bir tutar sessiz bir NaN'a değil, bir Err'e parse edilir.

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()      # "11.34", exact

decimal("2")?.div(decimal("3")?, 2)   # "0.67", half away from zero
ortadan kaldırdığı bug 
// JS number, the default everywhere:
0.1 + 0.2            // 0.30000000000000004
1_000_000_000_000.10 * 1.07   // rounding drift
9007199254740993     // === 9007199254740992

// None of these are your money anymore.

Id'ler ve sayaçlar 253'ü aştığında da kesin kalır

Float aralığını aşıp yuvarlanan bir hesap id'si ya da defter sayacı, başka türden bir felakettir. bigint, 123n literal'leri olan, kesin ve keyfi hassasiyetli bir tam sayıdır; bigint olarak tiplenmiş bir record alanı sınırda typeof === "bigint" doğrulaması yapar, böylece JSON number olarak gelen bir id sessizce kırpılmak yerine reddedilir.

Bir değişmez yorum değil, tiptir

"Tutar negatif değildir" ve "puan 1 ile 5 arasındadır", bir kez yazılıp sonra unutulan kontrollerdir. Bir where daraltması değişmezi tipin içine koyar ve tanımlayıcı onu sınırda zorlar. Koşulu sağlamayan bir değer hiçbir zaman bir Amount olmaz.

refinements.glyph 
type Amount = int where value >= 0
type Rating = int where value >= 1 && value <= 5

Amount.parse(-1)   # Err  (not just "is a number")
Rating.parse(6)    # Err
Amount.parse(3.5)  # Err  (int check too)

Injection bir derleme hatasıdır

Klasik uzaktan kod çalıştırma yolu, güvenilmeyen girdinin bir SQL sorgusuna, bir shell komutuna ya da bir HTML şablonuna ulaşmasıdır. std/taint bunu bir tip hatası yapar. Dışarıdan gelen bir değer Tainted'dır; korumak istediğiniz bir hedef Trusted alır. İkisi yapısal olarak farklıdır, bu yüzden birinden diğerine geçmenin tek yolu açık bir sanitize'dır. Bir hedefe tainted değeri doğrudan verirseniz tsc derlemeyi reddeder.

güvenli yol derlenir 
fn run_query(sql: Trusted<string>) -> void { ... }

let input: Tainted<string> = taint(req.body)
run_query(sanitize(input, escape))   # ok
injection yolu derlenmez 
module query

import std/taint { Tainted, Trusted, taint, expose }

fn run_query(sql: Trusted<string>) -> string {
  return expose(sql)
}

pub fn handle(body: string) -> string {
  let input: Tainted<string> = taint(body)
  return run_query(input)
}

// [TS2345] Argument of type 'Tainted<string>'
//   is not assignable to parameter of type
//   'Trusted<string>'. (query.glyph:11)

Şu anki durum

Bugün yayında

Kesin para hesapları için std/decimal, kesin büyük tam sayılar için bigint, bir değişmezin sınırda doğrulanması için where daraltmaları ve güvenilmeyen girdinin açık bir sanitize olmadan korunan bir hedefe ulaşamaması için std/taint. Her biri kontrol edilir: hatalı bir tutar ya da id parse'da başarısız olur, ihlal edilen bir değişmez parse'da başarısız olur, temizlenmemiş bir değer tsc'de başarısız olur.

Nerede duruyor

Bir where daraltması bugün temel ilkel tipleri kapsar; record ve alanlar arası değişmezler (where value.paid <= value.total) planlanan bir genişletmedir. Taint, bir hedefi Trusted olarak tipleyerek isteğe bağlı olarak benimsediğiniz bir disiplindir, otomatik bir akış analizi değil: derleyici sizin tanımladığınız sınırı zorlar, taint'i tüm program boyunca sizin için çıkarmaz.
