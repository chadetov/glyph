Her API için elle validator yazmam gerekiyor mu?

Hayır. Glyph'te bir tip kendi validator'ıdır. Bir type tanımlayın, derleyici yanına bir çalışma zamanı descriptor'ı üretir; böylece güvenilmeyen bir istek ya da yanıt gövdesi tek bir çağrıyla doğrulanır, yazılacak ve senkron tutulacak ayrı bir zod şeması yoktur.

Neden önemli

Çoğu TypeScript stack'inde her payload iki kez tanımlanır: bir kez derleyici için bir type olarak, bir kez de değerin çalışma zamanında gerçekten o şekilde olması için elle yazılmış bir validator olarak.

İkisi zamanla birbirinden ayrışır ve kötü veri tam da bu ayrışmadan içeri sızar. Glyph ikisini tek bir tanımda birleştirir: tip validator'ı üretir, bu yüzden birbirleriyle çelişemezler.

Görün

DTO'yu bir kez tanımlayın. Descriptor'ı size .parse (güvenilmeyen bir değeri tipe doğrulayarak dönüştürür) ve .is (bir type guard) verir, başka yazacak bir şey yoktur:

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}
yazmadığınız şey 
// No zod schema:
const NewTask = z.object({
  title: z.string(),
  done: z.boolean(),
});
// No drift between the type and
// the validator, because there is
// only one declaration.

// A bad body, {"title": 123},
// takes the Err arm. Only a
// well-formed body reaches Ok.

Tipli değeri match'ten sonra da tutun

İşi arm'ın içinde yapmak yerine değeri dışarı da çıkarabilirsiniz.

api.glyph: değer match'ten tipli olarak çıkar 
let task = match NewTask.parse(req.body) {
  Ok(t) => t,
  Err(issues) => { return bad_request(issues) },
}
task.titel   // E0210: type `NewTask` has no field `titel`; did you mean `title`?
0.1.45'ten berigeneric tipler: henüz değil
Ayrıntılar tipin nasıl taşındığı ve generic istisnası

T.parse'ın tipi Result<T, Array<Issue>>'dir ve arm'ları uyuşan bir match onların tipini taşır; böylece let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, } fonksiyonun geri kalanı için size bir NewTask verir ve alan adları üretilen TypeScript üzerinde tsc tarafından değil Glyph tarafından kontrol edilir. Bu 0.1.45'te geldi; öncesinde değer match'ten çıkınca tipsiz kalıyordu. Hâlâ bunu yapmayan tek şey generic bir tipin parse'ıdır, çünkü onun descriptor'ı her tip parametresi için bir çalışma zamanı denetleyicisi alır.

Parse sonucu sıradan bir Result

Glyph'te T.parse, dildeki başarısız olabilen her fonksiyonun döndürdüğü Result'ın aynısını döndürür; böylece onu doğrudan geri verebilir, doğrulama sorunlarını kendi hata tipinize çevirmek için map_err'den geçirebilir ya da ? ile yukarı iletebilirsiniz.

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}
bunun yerini aldığı şey 
// Until 0.1.52 the generated descriptor
// returned a bare { tag, value } object,
// so both of the first two shapes were
// tsc errors (TS2322 and TS2339) even
// though Glyph's own checker reported
// Result<T, Array<Issue>>. The workaround
// was an identity re-wrap:

match NewTask.parse(body) {
  Ok(t)  => Ok(t),          // does nothing
  Err(e) => Err(reword(e)),

Ayrıntılar burada Result kullanmanın çalışma zamanı maliyeti

Size değeri kendine özel bir şekilde geri veren bir validator ancak yarı yarıya işe yarar, çünkü hata yönetiminizin geri kalanı ona dokunamaz. Bir parse sonucunda özel hiçbir şey yok.

Eskiden farklı olmasının nedeni: descriptor type'ınızın yanında üretilir ve çıplak nesneyi üretmek, bir tip tanımlayan modülün çalışma zamanında std/result'a bağımlı olmasını önlüyordu. Bu takas artık tersine yapılıyor. İçinde pub type olan bir modül, hiç Result yazmasa bile bir std/result import'u taşır ve bir parse çağrısı, herhangi bir Ok(...)'nun ayırdığı combinator closure'larını ayırır. Karşılığında elde ettiğiniz şey, doğrulanan sınırın ve hata yönetiminizin geri kalanının aynı API olmasıdır.

Kendinizinkini oluşturmak: çıktı tipi güvenilmez, türetilir

Glyph'in infer_output<Shape>'i çıktı tipini şekilden türetir ve tsc annotation'ınızı ona karşı kontrol eder. İddia ettiğiniz tipin bir alanını atlayan bir şekil derlenmez:

schema.glyph 
fn object_schema<Shape: Record<string, Schema<unknown>>>(
  shape: Shape,
) -> Schema<infer_output<Shape>> { ... }

type User = { name: string, age: number }

// The shape must produce a User, or this
// line does not compile:
const user_schema: Schema<User> =
  object_schema({
    name: string_schema(),
    age: number_schema(),
  })
Glyph'in ortadan kaldırdığı ayrışma 
// TS/zod: shape and output type are two
// separate things you keep in sync by hand.
const s = z.object({ name: z.string() });
type User = { name: string; age: number };
// `s` is inferred { name }, but nothing
// checks it against User. The `age` you
// forgot is caught at runtime, if ever.

// Glyph: drop `age` from the shape and
// `Schema<User>` fails to compile. The
// shape is the single source of truth.
Ayrıntılar TypeScript tuzağı ve 0.1.92'den beri return'ü izleyen cast

Bazen zod tarzı bir combinator istersiniz: daha küçüklerini birleştirerek bir validator kurmak. TypeScript'teki tuzak, combinator'ın çıktı tipi ile ona verdiğiniz şekil'in birbirinden ayrışmasıdır. Şekli yazarsınız, sonra ikinci bir tip parametresinde kendinizi tekrar edersiniz ve ikisinin uyuştuğunu hiçbir şey kontrol etmez.

Türetilen tip, combinator nasıl dönerse dönsün geçerlidir. infer_output'un fonksiyonun sınırında bir cast'e ihtiyacı vardır, çünkü gövde tip sisteminin şekilden türetilen tipi taşıdığını kanıtlayamadığı bir değer kurar ve bu cast'i derleyici sizin için yazar. 0.1.91'e kadar bu cast düz bir return <value>'a bağlıydı. return ile değer arasına bir match koyun ya da gövdeyi r? ile bitirin, aynı fonksiyon derlenmeyi bırakıyordu: derleyicinin zaten kabul ettiği Glyph üzerinden, üretilen TypeScript'e karşı bir TS2322. 0.1.92 itibarıyla cast, return'ün yazımını değil return'ün kendisini izliyor; böylece return match strict { ... }, aynı gövdenin tek return'lü yazımıyla aynı şekilde tip kontrolünden geçer.

Güvenilmeyen sınırın geri kalanı

Descriptor, json.parse<T>'yi güvenli kılanla aynıdır: ona bir JSON string'i verin, tek adımda hem parse eder hem de doğrular.

Ayrıntılar istek gövdeleri, header'lar ve query parametreleri

Bir istek gövdesi zaten çözülmüş bir unknown olarak gelir; orada bunun yerine T.parse(value) kullanırsınız: aynı garanti, cast yok.

Güvenilmeyen sınırın geri kalanı da aynı şekilde tiplenir: header(req, name) ve query_param(req, name) Option<string> döndürür; böylece eksik bir header ya da query parametresi None olur ve match sizi onu ele almaya zorlar. None arm'ını atlarsanız derlenmez. Olmayan bir girdi varmış gibi okunamaz.

Bir enum ile anahtarlanmış bir map anahtarlarını kontrol ediyor mu?

Evet, 0.1.148'den beri. type Tier = "free" | "pro" ile bir Record<Tier, int>, yalnızca anahtarları tam olarak free ve pro olan bir nesneyi parse eder: fazladan bir anahtar da eksik bir anahtar da Err olur; tsc'nin aynı nesne literal olarak yazıldığında söylediği de budur.

where ile daraltılmış bir tipkoşul

Ayrıntılar daraltılmış ve int anahtarlar, hâlâ tsc'ye kalanlar

where ile daraltılmış bir anahtar tipi koşulunu her anahtarda çalıştırır ve bir int anahtarın bir tam sayının düz yazımı olması gerekir; bu yüzden "01" ve "1.5" reddedilir. Bir Record<string, V> tam olarak eskisi gibi kontrol edilir. Glyph'in kendi checker'ı, kodda yazdığınız bir değerin anahtarlarını hâlâ tsc'ye bırakır ve kendi tip parametresiyle anahtarlanmış generic bir record, o parametre string olmadığı sürece reddedilir.

Bir tarihi parse edersem gerçek bir tarih mi alırım?

Evet; ilginç olan kısım tarih olmayan bir girdi için ne geri aldığınız. time.parse_iso Option<number> döndürür ve ISO-8601 olmayan her şey için None'dır.

kabul edilir 
"2026-01-03"              // UTC midnight
"2026-07-25T18:33:08.000Z"
"2026-03-15T09:30:00-05:00"
"2028-02-29"              // a real leap day
None, hepsi 
"January 5 2026"   // not ISO
"2026-1-3"         // not padded
"2026-13-01"       // no month 13
"2026-02-31"       // no such day
"2026-02-29"       // not a leap year
"2026-01-03T10:00" // no offset

İnsanları şaşırtan sonuncusu ve asıl mesele de o. Z ve +HH:MM offset'i olmayan bir datetime, ECMAScript gramerine göre yerel saattir; dolayısıyla onu kabul etmek, aynı string'in programı hangi makinenin çalıştırdığına bağlı olarak farklı bir takvim gününü göstermesi demek olurdu.

Ayrıntılar Date.parse'ın bunun yerine ne yaptığı ve neden UTC

Bu, JavaScript'in Date.parse'ından daha güçlü bir iddia; o, serbest biçimli metin alır ("January 5 2026"), "2026-1-3" gibi sıfırla doldurulmamış bir tarihi süreç hangi saat diliminde çalışıyorsa onda okur ve imkânsız bir günü ileriye kaydırarak başarı olarak raporlar: "2026-02-31" 3 Mart olur ve bir şey olduğuna dair hiçbir işaret olmadan bir sayı geri alırsınız.

Glyph'in takvim erişimcileri (time.year, time.month, time.day) UTC'dir ve bunu açıkça söyler; host'un saat dilimini sessizce içeri alan bir validator onları yalan söyletirdi. Bu yüzden string reddedilir ve ne anlama geldiğine siz karar verirsiniz.

Koruma, primitive'in içine taşındı

Bir uygulama bir standart kütüphane primitive'inin etrafına bir doğruluk koruması yazıyorsa, o korumanın yeri primitive'in kendisidir. Uygulamanın sildiği şey şu:

önce: uygulama stdlib'i koruyor 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
sonra: çizgiyi primitive tutuyor 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

import std/regex de onunla birlikte gitti. Aynı defter, aynı reddedilen satırlar, byte byte aynı rapor.

Geçmiş bunun çıktığı masraf raporu uygulaması

Bu, Glyph'te bir masraf raporu CLI'ı yazarken ortaya çıktı. Her defter satırı bir tarih taşır ve bir satırı yanlış aya kaydetmek önemli olan hatadır; bu yüzden uygulama eski parse_iso'ya güvenmedi: önce şekli bir regex ile kontrol etti, sonra ileri kaymış bir günü yakalamak için timestamp'i tekrar metne çevirip karşılaştırdı.

Tipleri yazmanız bile gerekmiyor

Şekil zaten bir OpenAPI spesifikasyonunda ya da bir TypeScript tanım dosyasında varsa Glyph tiplerini ondan üretin: çıkarımla oluşmuş hayali bir şey değil, her biri descriptor'ıyla birlikte gelen, commit edilmiş, grep'lenebilir gerçek type tanımları:

bir OpenAPI / JSON Schema spesifikasyonundan 
glyph gen openapi petstore.yaml \
  --out src/
kurulu bir paketten, adıyla 
glyph gen dts api-types \
  --out src/types

Bir wire tipi, hiçbir şey elle yazılmadan doğrulanan bir sınıra dönüşür:

webhook.glyph 
import types/api_types { Customer }

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),
  Err(issues) => reject(issues),
}

Üretim wire'a sadıktır: spesifikasyonun bir değer hakkında söylediği, parse'ın kontrol ettiği şeydir.

Spesifikasyonda ya da .d.ts'teÜretilen Glyph
Bir string enumbir string-literal union; parse üyeliği kontrol eder
Bir integer alanıint; wire'dan gelen bir 3.5 başarısız olur
Bir nesne şeması@open ile işaretlenmiş bir record; additionalProperties: false ile strict
interface Page<T>type Page<T>, her öğe T olarak kontrol edilir

Ayrıntılar bugün neyin üretildiği, yeniden üretim, generic tipler

glyph gen dts'i bir .d.ts dosyasına ya da yukarıdaki gibi adıyla kurulu bir npm paketine yöneltin: paketin kendi tanım girişini node_modules'ten çözer ve import ettiğiniz, commit edilen tipler yazar.

Bugün üretilenler: gen dts, bir paketin export ettiği interface ve type tanımlarını okur; bir declare namespace ağacının içindekiler (çıplak çapraz referanslar kapsam üzerinden çözülür) ve bir index barrel'ının yeniden export ettiği kardeş dosyalardakiler de buna dahildir (giriş .d.ts'i artı göreli olarak import edilen her .d.ts dolaşılır). Bir generic birinci sınıf olarak korunur: interface Page<T>, type Page<T> olarak üretilir ve her öğeyi yalnızca varlığı için değil, tip argümanı olarak doğrulayan bir descriptor alır. Takma adlı ve export * as yeniden export'lar dosya başına bir binding map'i üzerinden çözülür. Güvenli kılamadığı tek durumda, erişilebilen iki dosya arasında çakışan bir tip adında, yanlış şekli sessizce bağlamak yerine onu bir notla işaretler. Üreticinin ulaşamadığı her şey için sınırı geçerken kullandığınız şekilleri elle yazın ya da extern_ts kaçış kapısını kullanın.

Yeniden üretim idempotent'tir; böylece bir spesifikasyon değişikliği temiz, review edilebilir bir diff olur. Üretim wire'a sadıktır: bir string enum bir string-literal union olarak üretilir ("free" | "pro"); böylece parse yalnızca değerin bir string olduğunu değil üyeliği kontrol eder ve onun üzerindeki bir match bir else olmadan kapsamı tamdır. Bir integer alanı int olur; böylece wire'dan gelen bir 3.5, düz bir number'ın geçeceği yerde parse'tan geçemez. Bir yapının tam bir Glyph karşılığı olmadığında (discriminator'ı olmayan bir union), gerçek veriyi reddedecek bir validator üretmek yerine daraltır ve bir not yazdırır. Üretilen record'lar ayrıca @open taşır; böylece parse, tanımladığı her alanı doğrulamaya devam ederken API'nin sonradan eklediği bir alana tolerans gösterir. additionalProperties: false ayarlayan bir şema strict kalır. Glyph'te record'lar varsayılan olarak strict'tir ve bu, elle yazılmış bir record'un da kullanacağı, tanım yerindeki aynı grep'lenebilir işarettir; dolayısıyla bir record'un ne anlama geldiğine dair hiçbir şey değişmez.

Generic tipler de doğrulanır. Bir Paginated<T>, parse'ı tip argümanını alan bir descriptor alır: Paginated.parse<User>(body) her items girdisini yalnızca varlığı için değil, bir User olarak kontrol eder ve match v { is Paginated<User> => ... } aynı şekilde daraltır. Bu modül sınırları boyunca da geçerlidir: Paginated<T>'yi bir dosyada tanımlayın, başka birine import edin; oradaki Paginated.parse<User>(body) da is Paginated<User> da her elemanı yine bir User olarak kontrol eder. Derleyici eleman başına kontrolü çağrı yerindeki tip argümanından kurar; bu yüzden generic tipin hangi dosyada durduğu neyin doğrulandığını değiştirmez.

Nerede duruyor: descriptor'lar çoğu payload'ın oluştuğu şekilleri kapsar: nesneler, primitive'ler, array'ler, referanslar, isteğe bağlı ve nullable alanlar ve artık belirli bir örneklemedeki generic tipler. Glyph'in üretmediği bir tip (yalnızca import ettiğiniz harici bir paket ya da .d.ts) tip kontrolünden geçer ama siz onu üretene kadar descriptor taşımaz; bu artık kurulu pakete karşı tek bir komut (glyph gen dts <package>, export ettiği üst seviye interface'ler ve tip takma adları için). Bu sınır bilinçli: Glyph'in üretmediği bir tip çalışma zamanı doğrulaması vaat edemez; bu yüzden paket paket siz katılırsınız ve sonuç her build'de yoktan var edilmez, commit edilir ve grep'lenebilir.

Veritabanı da bir sınırdır

Bir veritabanından okunan bir satır, bir istek gövdesiyle tam olarak aynı şekilde güvenilmezdir. Bir istek gövdesinde kullandığınız .parse'ın aynısı bir satırı doğrular.

tasks.glyph 
type Task    = { id: int, title: string, done: bool }
type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.
match TaskRow.parse(row) {
  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}
bunun ortadan kaldırdığı hata 
// TS, better-sqlite3 / node:sqlite:
const row = stmt.get(id) as Task;
// `row.done` is really 0 or 1, a number.
// Nothing complains. Then:
if (row.done === true) { ... }   // never runs

// The row was `unknown`; the cast invented
// a type. Glyph makes you validate the row
// into TaskRow, and the int-to-bool step is
// a line of code, not a silent lie.
Ayrıntılar std/sqlite ve 0 ya da 1 olan boolean

Bir veritabanından okunan bir satır, bir istek gövdesiyle tam olarak aynı şekilde güvenilmezdir: veritabanı şeması ile kodunuzun satır hakkındaki fikri uyuşmayabilir ve bir cast (row as Task) bunu örtbas eder. Node'un yerleşik SQLite'ı üzerindeki DB modülü std/sqlite bunu esas alır. Bir sorgu Array<Record<string, unknown>> döndürür; dolayısıyla bir satırı önce doğrulamadan bir Task olarak ele almanın yolu yoktur.

Bu, insanların sürekli production'a gönderdiği bir hatayı yakalar. SQLite'ın boolean tipi yoktur, bu yüzden bir done sütunu 0 ya da 1 tamsayısı olarak geri gelir. Satırı bool alanı olan bir record'a cast edin, task.done === true sessizce hiçbir zaman true olmaz. Glyph'te saklama şekli ile domain şekli ayrı tiplerdir ve aralarındaki eşleme gözünüzle gördüğünüz tek bir satırdır:

Hepsi çalışan bir örnek: examples/apps/tasks/main.glyph, saklama için std/sqlite ve route'lar için std/http kullanan, verisi yeniden başlatmadan sonra da kalan ve hem wire hem veritabanı tarafında doğrulama yapan, kalıcı bir görev API'si. İçinde hiçbir yerde elle yazılmış validator yok.

İmzalı bir webhook da bir sınırdır

Bir webhook imzasını doğrulamak, yeniden serileştirilmiş bir kopyayı değil, göndericinin imzaladığı tam byte'ları gerektirir (parse edilmiş bir gövdeyi yeniden string'e çevirmek boşlukları ve anahtar sırasını değiştirir, bu yüzden HMAC asla eşleşmez). http.raw(req) size o byte'ları verir, böylece kontrol Glyph'te kalır: 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
Ayrıntılar imza için ham byte'lar, şekil için parse edilmiş gövde

req.body, şekil kontrolü için hâlâ parse edilmiş değerdir; raw ise imzanın üzerinden hesaplandığı, kurcalanmamış payload'dır. Bir imzayı doğrulayan ve gövdeyi validate eden bir alıcının elle yazılmış TypeScript'e ihtiyacı yoktur.

Bir tip yalnızca şeklini değil değişmezlerini de doğrulayabilir

Bir şekil kontrolü size bir alanın number olduğunu söyler. Tutarın negatif olmadığını ya da puanın 1 ile 5 arasında olduğunu söylemez. Bir where daraltması bu değişmezi tipe koyar ve descriptor onu sınırda zorunlu kılar:

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
yazmadığınız şey 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.

Bugün kullanılabilir 10

Descriptor'lar

  • Tanımlanan her record ve tagged union bir çalışma zamanı descriptor'ı taşır (.parse, .is, .schema), generic record'lar dahilgeneric bir tagged union taşımaz
  • .parse, dilin geri kalanının kullandığı Result'ın aynısını döndürür; böylece map_err ile, ? ile ve onu döndüren her fonksiyonla birlikte kullanılabilir
  • Bir where daraltması (int where value >= 0), sınırda yalnızca bir şekli değil bir değişmezi doğrular
  • json.parse<T> JSON'u doğrular
  • infer_output<Shape>, bir combinator'ın çıktı tipini şeklinden türetir, böylece ikisi ayrışamaz

Üretim

  • glyph gen openapi / glyph gen dts, bir spesifikasyondan, bir .d.ts dosyasından ya da adıyla kurulu bir paketten descriptor taşıyan, commit edilen tipler üretir

Sınırlar

  • std/sqlite satırları unknown olarak verir, böylece veritabanı da diğerleri gibi doğrulanan bir sınırdır
  • İmzalı bir webhook alıcısı tamamen Glyph'te kalır
    Ayrıntılar

    http.raw(req) parse edilmemiş istek gövdesini sunar; böylece bir webhook imzası tam byte'lar üzerinden doğrulanır ve imzalı bir webhook alıcısı tamamen Glyph'te kalır.

  • Güvenilmeyen girdi sanitize olmadan bir SQL ya da shell hedefine ulaşamaz
    Ayrıntılar

    std/taint'in Tainted/Trusted tipleri, güvenilmeyen girdinin açık bir sanitize olmadan bir SQL ya da shell hedefine ulaşmasını engeller; böylece tsc bir injection yolunu derleme zamanında reddeder.

  • time.parse_iso ISO-8601 alır, başka hiçbir şey almaz
    Ayrıntılar

    Daha küçük sınır primitive'leri de aynı çizgiyi tutar: time.parse_iso ISO-8601 alır ve serbest biçimli metin, imkânsız bir gün ve aksi halde host'un yerel saat diliminde okunacak offset'siz bir datetime için None döndürür.

Yolda 3

  • Discriminated union'lar bir spesifikasyondan ve bir .d.ts'ten üretiliyor; sırada enum ve mapped type kapsamı var
    Ayrıntılar

    Discriminated union'lar artık hem bir OpenAPI discriminator'ından hem de bir TypeScript .d.ts union'ından üretiliyor (bir parse_<Name> dağıtıcısı tag'i okur ve doğru variant'a doğrular). Sırada: daha zengin enum ve mapped type kapsamı.

  • Bir spesifikasyondan tipli istemci ve sunucu kodu zaten hazır İstemci & sunucuya bakın
  • Bir timestamp ve bir süre ikisi de number
    Ayrıntılar

    Tarihlerde katılık özelliğin kendisidir ve parse'ta biter: parse_iso epoch milisaniyesi verir; dolayısıyla bir timestamp ve bir süre ikisi de number'dır ve birini diğerine eklemenizi hiçbir şey engellemez. Ayrı bir tarih tipi daha sonraki bir karar ve küçük bir karar değil.
