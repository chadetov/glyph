Neden ReScript, Gleam ya da Elm değil?

Üçü de JavaScript'e derlenen tipli diller ve üçü de Glyph'ten daha eski, daha yaygın kullanılan ve daha oturmuş. Yeni bir kod tabanı için dil seçiyorsanız ve TypeScript'e yakın kalmanız gerekmiyorsa, önce onlara bakmaya değer. Glyph'in farkları daha dar: JavaScript yerine TypeScript kaynak kodu üretir, npm paketlerini kendi .d.ts'lerinden gelen tiplerle import eder, tiplerinizden çalışma zamanı validator'ları üretir ve derleyicisi bir ajan için etki sorgularını yanıtlar.

Her biri kendini nasıl tanımlıyor

ReScript'in ana sayfası "JavaScript Made Simple for Humans and AI" ve "Types > Vibes" ile açılıyor ve dilin "compiles to clean, efficient JavaScript" olduğunu, "No any, no magic types, no surprise undefined." sunduğunu söylüyor. "automatically generate TypeScript types" seçeneği de sunuyor (rescript-lang.org).

Gleam'in ana sayfası onu "a friendly language for building type-safe systems that scale" olarak, "No null values, no exceptions, clear error messages" ile tanımlıyor. Erlang VM üzerinde çalışıyor, "can additionally compile to JavaScript" ve "also generates TypeScript definitions" (gleam.run).

Elm'in ana sayfası "reliable web applications" için "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions" tanımını yapıyor ve Elm'in "detects all API changes automatically" ederek "guarantee that every single Elm package follows semantic versioning" sağladığını söylüyor (elm-lang.org).

Bu alıntılar 2026-11-19'da okundu.

Glyph'in farklı yaptıkları

Bunların her biri bu sayfa için Glyph 0.1.149 üzerinde çalıştırıldı.

TypeScript kaynak kodu üretir

glyph build, modül başına bir .ts dosyası yazar; bu dosyayı ardından tsc --strict kontrol eder ve Glyph'i kullanmayı bırakırsanız elinizde kalır. ReScript ve Gleam JavaScript üretir ve yanına tip tanımları oluşturur. Üretilen TypeScript TypeScript sayfasında gösteriliyor.

npm paketlerini kendi tanımlarından gelen tiplerle import eder

Bir modül bir paketi adıyla import eder ve paketin .d.ts'i her kullanımı tipler. Önce yazılması gereken bir binding yoktur. ReScript'te "external is the primary ReScript feature for bringing in and using JavaScript values" (external) ve tipler ReScript tarafında tanımlanır. Gleam'in external'ları tip anotasyonu gerektirir ve derleyici "cannot verify that the function implemented in the other language returns the specified types" (externals). Elm, JavaScript ile flag'ler, port'lar ve custom element'ler üzerinden konuşur (interop). pg ve @types/pg kuruluyken şu reddedilir:

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

Kod TS2322'dir, çünkü bir kütüphanenin değerlerini kontrol eden tsc'dir ve sonuç Glyph satırına geri eşlenir. Glyph'in kendi checker'ı bunları görmez; bu yüzden glyph check --no-tsc, editör ve MCP araçları bu hatayı kaçırır (G257). Bir .d.ts'ten import edilen tipin çalışma zamanı kontrolü de yoktur.

Validator'ı tipten üretir

Her record ve union, tanımından üretilen bir çalışma zamanı kontrolü taşır; bu yüzden veri eşleşmediğinde json.parse<User> Err döndürür. Elm'de her yapı için bir decoder yazarsınız ve rehberi "the decoders people write end up working as a validation phase" diye not düşer (JSON).

main.glyph: JSON'da email olmadığı için "refused" yazdırır 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

Derleyicisi bir değişikliğin neyi bozacağını yanıtlar

Bir düzenlemeden önce bir ajan, bir değişikliğin hangi yerlere ulaştığını MCP üzerinden (glyph_impact) ya da glyph query impact ile sorabilir. Biri kapsamı tam bir match, diğeri else ile biten iki eşleşme içeren bir Plan = Free | Pro | Team union'ında, yeni bir variant hakkında sormak her yer için ayrı yanıt verir:

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

İkinci yer değişiklikten sonra derlenemez; değişiklik yapıldığında bu derleyicilerin herhangi biri de bunu söylerdi. Birincisi derlenmeye devam eder ve yeni durumu kendi else'ine gönderir; onu adıyla belirten şey sorgudur. Diğer araçlar Ajan geliştirenler için sayfasında listeleniyor.

Bu sayfanın iddia etmedikleri

Hata mesajlarını, derleme hızını ya da çalışma zamanı performansını karşılaştırmadı ve üçünden herhangi birini Glyph'ten ya da tersi yönde çağırmayı denemedi. Alıntılar her projeyi kendi sözleriyle anlatıyor; her birinin bunlara ne kadar uyduğunu kontrol etmek size kalıyor, tıpkı Glyph'in kanıtlar sayfasındaki kendi iddiaları için olduğu gibi.
