20 · 二进制数据

能处理二进制数据吗，还是一切都是字符串？

std/bytes 为你提供不可变的八位字节序列，std/fs 和 std/crypto 都支持它。在 0.1.78 之前并非如此：标准库的每个边界都是字符串进、字符串出，所以无法读取 PNG，也无法给 HMAC 一个真正的密钥。

为什么这很重要

PNG 的第一个字节是 0x89，它单独出现时不是合法的 UTF-8。把这个文件当文本读取，解码器无法理解的每个字节都会变成 U+FFFD，所以文件在你的程序看到之前就已经损坏了，而且没有任何报错。密钥也是一样：HMAC 的密钥是任意的八位字节，经过字符串中转就会改变，于是你算出的 MAC 和规范要求的不同，而你针对自己代码写的每个测试都能通过。

两个独立编写的应用，一个是 PNG 读取器，一个是身份验证器，在同一周卡在了同一个问题上。两者都无法在语言内部绕过。

看看实际效果

一个 RFC 6238 身份验证器，HMAC 的两侧都需要字节。密钥以 base32 编码传入，消息是一个大部分为零的八字节计数器，摘要则用它自己的最后一个字节做索引：

一次性密码，从头到尾 
module totp

import std/bytes
import std/crypto
import std/math
import std/array
import std/option { Some, None }
import std/result { Result, Ok }

fn at(b: bytes.Bytes, i: int) -> int {
  return match bytes.get(b, i) {
    Some(v) => v,
    None => 0,
  }
}

pub fn code(secret: string, counter: number) -> Result<number, bytes.BytesError> {
  let key = bytes.from_base32(secret)?
  let message = bytes.from_array(array.map(array.range(8), fn(i: int) -> int {
    return math.floor(counter / math.pow(256, 7 - i)) % 256
  }))?

  let mac = crypto.hmac_sha1_bytes(key, message)
  let offset = at(mac, bytes.len(mac) - 1) % 16
  return Ok((((at(mac, offset) % 128) * 16777216)
    + (at(mac, offset + 1) * 65536)
    + (at(mac, offset + 2) * 256)
    + at(mac, offset + 3)) % 100000000)
}

Bytes 在运行时是一个 Uint8Array，所以可以不经拆包直接交给任何接受它的宿主 API。序列操作的命名与 std/array 和 std/string 中的对应函数一致：len、get、slice、concat、index_of、starts_with。没有任何操作会修改它的参数。

每次解码都可能拒绝，并说明位置

这是构建成本最高的部分，也是使用它的理由。Node 的 Buffer 会接受格式错误的输入并报告成功：

平台悄悄做了什么 
Buffer.from("zz", "hex")        // an empty buffer, no error
Buffer.from("a-b_", "base64")   // skips - and _, decodes the rest, no error
buf.toString("utf8")            // U+FFFD for anything malformed, no error
Glyph 怎么做 
match bytes.from_hex(input) {
  Ok(b) => use(b),
  Err(e) => io.eprintln("${e.message} at ${number.to_string(e.index)}"),
}

// "z" is not a hex digit at 0
// a trailing base64 group cannot be 1 character(s) long at 3
// not valid UTF-8 at 2

每个编解码器都是自己实现的，而不是委托给 Buffer，所以 hex、base64、base64url 和 base32 都会拒绝字母表之外的字符、短到无法编码一个完整字节的末尾分组，以及携带了超出数据末尾的位的最后一个字符。to_text 会扫描找出第一个不可能属于合法 UTF-8 序列的字节，所以你得到的是一个位置，而不只是一个结论。from_array 出于同样的原因拒绝 0..255 之外的任何值：悄悄执行 & 0xff 会把 256 变成 0，把笔误变成数据。

自己实现编解码器还带来了一个原本没打算要的好处。这个模块完全不使用任何宿主 API，只用 Uint8Array、TextEncoder 和 TextDecoder，所以只用到 std/bytes 的打包产物也能在 Web Worker 中运行。

选哪种 HMAC 会改变结果

std/crypto 现在为每个算法提供两种形式。普通名字的版本接受字符串、返回 hex，适合哈希密码。_bytes 形式接受并返回 Bytes，适合线路协议。如果密钥来自 bytes.from_base64 或 crypto.random_bytes，它包含字符串无法容纳的字节，文本形式会悄悄算出另一个结果。

把攻击者提供的值与密钥比对时，用 crypto.timing_safe_equal，而不是 bytes.equals。equals 一发现不匹配就返回，所以它花的时间会泄露前面有多少个字节是对的。

当前状态

现已提供

包含 21 个函数的 std/bytes：序列操作、UTF-8 转换，以及 hex、base64、base64url 和 base32 编解码器，它们返回一个指出出错位置的 Result。fs.read_bytes、write_bytes 和 append_bytes 不经解码地读写文件。std/crypto 为每个摘要和 HMAC 提供 _bytes 形式，还有供规定使用它的协议使用的 SHA-1、random_bytes 和 timing_safe_equal。编解码器用 RFC 4648 的测试向量、HMAC 用 RFC 6238 的测试向量固定在编译器自己的测试套件中。

正在改进

目前还没有整数编解码器，所以从头部读取大端 u32 需要你自己写算术：超过 32 位时移位本来就不是合适的工具，所以用的是除法。十六进制字面量仍然无法解析，这让用十进制写的 256 项 CRC32 表很难读。std/websocket 仍然把二进制帧解码为 UTF-8 文本；它需要的类型现在已经有了，接下来就处理帧。std/encoding 中较早的六个字符串到字符串的函数遇到格式错误的输入仍然不报错，所以凡是必须正确的地方，都请使用 std/bytes 的编解码器。这些编解码器用 TypeScript 编写，而不是委托给 Node 的 Buffer，正因如此它们才能在 Web Worker 中运行；处理 1 MB 数据时，它们比平台实现慢 1 到 35 倍。编码一个密钥或令牌，两者的开销都小到无法测量；如果你要处理几十 MB 的数据，性能指南里有对比表。
