凌晨 3 点在生产环境出问题时，值班的人会看到什么？

你自己掌握的可读 TypeScript，每个生成的文件旁边都有指回你的 .glyph 的 source map。调试器、打包工具或错误追踪服务能把运行中的代码追溯到你的源码，即使从没见过 Glyph 的人也能读懂生成的 TS。在这一切之前，glyph build 和 glyph run 对同一棵目录树报告相同的诊断，所以快速迭代的循环不会藏住构建本来能发现的问题。下面列出了两个限制，都在 glyph run 这条路径上。

1 · 生成的 TypeScript 由你来读

Glyph 不附带不透明的运行时。它生成普通的、格式化好的 TypeScript，你像对待其他 TS 一样提交和部署它。

所以最坏的情况（凌晨 3 点，一个不懂 Glyph 的值班工程师）读的仍然是普通的 TypeScript，而不是某种方言。从你的源码到生产环境之间没有黑盒。

2 · 指回 .glyph 的 source map

每个生成的 .ts 旁边都有一个标准的 v3 source map（.ts.map），带有 sourceMappingURL 注释，并嵌入了你的 Glyph 源码（sourcesContent）。

dist/main.ts（末尾） 
// ...emitted TypeScript...
//# sourceMappingURL=main.ts.map    // v3 map, .glyph embedded

任何使用 source map 的工具（Chrome DevTools、Node 调试器、Sentry 这样的错误追踪服务、你的打包工具）都能沿着它串起来，显示 .glyph 的行，而不是生成代码的行。

3 · 构建和类型错误本来就指向 Glyph

带着类型错误进入生产环境的情况很少见，因为 glyph build 会运行 tsc --strict，并把每个 tsc 错误映射回你的 .glyph 源码（同样的插入符，保留 TypeScript 错误码）。

glyph build --json 则把每条诊断输出为结构化 JSON（错误码、严重程度、文件、从 1 开始的行/列、帮助），供你的 CI 或工具使用。

详情 插入符落在哪里

插入符落在 tsc 拒绝的代码所对应的最小 Glyph 表达式上：参数错误时标出那个参数，JSX 事件处理器里拼错的字段标出那次成员访问，而不是包住它的整个 return。

4 · glyph run 告诉你同样的东西

你每天都在敲的命令是 glyph run，而在 0.1.40 之前，它比构建安静。现在它报告同样的一组诊断：包括警告，覆盖你指定的文件及其同级文件，显示在程序输出之后，并附一行计数。

一个未使用的导入，在会用到它的代码之前一步加入 
$ printf 'look\nquit\n' | glyph run adventure.glyph
...the game plays and exits 0...

[E0106] Warning: lint: unused import `math`
    ╭─[adventure:21:1]
    │
 21 │ import std/math
    │         ╰─────── unused import `math`
    │ Help: Remove the import. Nothing in this module references it.

glyph run: 0 error(s), 1 warning(s) in the source tree
详情 运行缓存

运行缓存会保存这些诊断，所以对未改动的源码第二次运行时，说的和第一次一样，不会变得沉默；缺少诊断的缓存条目算作未命中，会重新构建。

历史 0.1.40 之前

它编译整个目录，从报告里取出生成的文件列表，然后把诊断丢掉。一棵被 glyph build 指出问题的目录树，用它运行却毫无提示，退出码为 0。

当前的两个限制

  • glyph run 自身的崩溃堆栈仍然显示 .ts 行号。glyph run 通过 tsx 执行，而 tsx 不会把 source map 串过它自己的 .ts→.js 转换，所以 glyph run 期间未捕获的异常报告的是生成代码的行。重新映射这个堆栈是后续工作。
  • 同级模块中的错误不会改变 glyph run 的退出码。编译失败的模块无法被导入，而从没导入它的程序照常运行。现在你能看到这个错误，但进程的退出码仍然是 main 返回的值。
详情 生产环境的堆栈，以及退出码为什么保持不变

它影响本地的 run 循环；在实际部署中，你用 glyph build 生成 .ts，用常规工具链打包，.ts.map 照常串起来，所以真正让你被呼叫的生产堆栈能映射回 .glyph。

让它以非零退出，会使今天运行正常的目录树失败，所以这是一个尚未做出的决定，而不是疏忽。如果你希望由目录树的健康状况决定退出码，那就用 glyph build。

当前状态

现已提供

  • 提交到仓库的可读 TS。
  • 每个文件一个 v3 .ts.map。
  • tsc 错误重新映射到 .glyph。
  • --json 诊断。
  • glyph run 报告的内容和 glyph build 一致，缓存命中时也一样。
  • 你的部署工具链的 source map 链能追溯到 .glyph。
