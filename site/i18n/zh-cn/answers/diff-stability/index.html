02 · 便于审查的改动

智能体的编辑会保持干净，还是会把整个文件重新格式化？

改一行就是一行 diff，每次都是。Glyph 只有一种标准排版，所以智能体无法把真正的改动埋在一大片重新格式化之下。

本页内容

  1. 为什么重要
  2. 尾随逗号
  3. 一种标准排版
  4. 注释留在原处
  5. fmt 会弄坏构建吗？
  6. 当前状态

为什么重要

智能体提交 pull request 时，diff 就是审查的对象。如果一个一行的修复变成了 200 行的重新格式化，没有人能看出到底改了什么，而 bug 恰恰会从这种噪声中溜过去。

稳定的 diff 意味着 diff 显示的是改动，并且只有改动。

大部分工作由两条规则完成。下面逐一展示，以你审查时会看到的 diff 的形式。

尾随逗号，每行一项

尾随逗号是必需的，一行放不下的列表会每行一个元素，而不是重新排布，所以插入、删除或调整某一项的顺序，永远不会影响相邻的项。

记录字段、参数、match 分支和导入也是如此。

这个阈值有代价：一次重命名如果让某个调用超过 100 列，整个参数列表都会展开成每行一个。

一种标准排版

正确的格式只有一种，由 glyph fmt 生成。空白、换行和对齐都不是智能体可以“整理”的选项，所以语义上的编辑不会顺带引起重新排版。改一个字段的类型，diff 就只有这一处：

user.glyph：改一个字段，审查一行 
 type User = {
   id: string,
-  age: string,
+  age: number,
   email: string,
 }

因为排版是固定的，两个不同的智能体编辑同一个文件，会产生逐字节相同的格式，没有重新排版带来的反复改动，没有“我的格式化工具和你的不一样”这种噪声，git blame 也干净，指向真正改了那一行的提交，而不是重新格式化它的提交。

只有一种标准排版，那格式化工具会挪动我的注释吗？

以前会，这是一个值得点名的 bug。现在的规则是：注释会重新输出在它原来所在的那一项上方，适用于记录体、联合类型的变体列表、数组或对象字面量、实参或形参列表，以及 match。

历史 注释是怎么漂移的，以及暴露它的应用

Glyph 没有块注释，也没有文档注释语法，所以 // 行是解释记录字段、联合类型变体或 match 分支的唯一方式。格式化工具只在声明和语句的边界处输出待处理的注释，这意味着写在某个结构内部的注释会往下漂到下一个声明，读起来就像是它落在的那个东西的文档。用 Glyph 写扫雷游戏时暴露了这个问题。下面这两个声明来自那个真实的应用（注释有删减），分别用旧的和新的格式化工具处理。

0.1.37：运行一次 fmt 
type Visibility =
  | Hidden
  | Flagged
  | Revealed

// Face down. Prints as `.`.
// Face down and marked by the player.
// Face up. `Cell.adjacent` is what gets printed.
type Cell = { mine: bool, adjacent: int, visibility: Visibility }
// Number of mined neighbours. Only meaningful
// once mines are placed.
三条变体注释现在成了一个记录的文档
0.1.38：同一个文件 
type Visibility =
  // Face down. Prints as `.`.
  | Hidden
  // Face down and marked by the player.
  | Flagged
  // Face up. `Cell.adjacent` is what gets printed.
  | Revealed

type Cell = {
  mine: bool,
  // Number of mined neighbours. Only meaningful
  // once mines are placed.
  adjacent: int,
  visibility: Visibility,
}
每条注释都在它描述的东西上面

而且一个内部带注释的结构无论大小，总是采用每行一个元素的形式，这样注释就有一项可以放在上方。所以 type Shape = { w: int, h: int } 仍然会收成一行，而一旦你给 h 写了注释，这个记录就会保持展开。

详情 为什么这算正确性 bug

为什么这算正确性 bug，而不是外观问题：什么都没有失败。构建以 0 退出，tsc 通过，被搞乱的输出本身也是不动点，所以 CI 中的 glyph fmt --check 对一个注释已经在说错话的文件给出了通过。这和 Glyph 要消除的是同一类失败，只不过发生在格式化工具里，而不是类型系统里。

glyph fmt 会把一个能构建的程序弄坏吗？

会过，而且还有一种情况没有解决。一个你的程序必须扛得住的格式化工具，比缺少一个功能更糟，因为它会破坏本来能用的代码。

  • 分支体现在，如果分支体最左边的记号是一个会被重新解析为代码块的 {，打印器就会给它加上括号，这包括空对象以及在它基础上构建的任何东西（({}).size 会变成 ({}.size)）。
  • 模糊测试模糊测试现在会解析格式化后的文件，并把语法树与原文件的比较，所以一种改变了文件含义的排版会在第一轮就失败，而不是等某个人注意到。
历史 无法再构建的空记录

先说已经修复的。表示“空记录”的分支写作 true => ({})。分支体位置是语法中唯一一个开头的 { 有歧义的地方，解析器的处理方式是要求大括号后面紧跟 key: 或 ...。空对象两者都没有，所以当格式化工具去掉括号、重新打印成 true => {} 时，这个分支被解析成了一个空代码块，文件无法再构建：E0223，分支不产生值。你对能运行的代码跑了一次格式化工具，得到的代码却不再能编译。

本来就没有歧义的分支体，比如 false => { a: "x" }，保持不加括号，所以其他地方不会多出需要阅读的标点。fmt 对结果是不动点，生成的 TypeScript 也没有变化。

历史 0.1.138 又修复的两个

0.1.138 又修复了两个。在代码块中，以 ( 开头的行会接续上一行，而在 0.1.137 及之前，格式化工具会把 load()? 后接 .run() 打印成 (load()?).run()，于是在 let a = 1 之后，格式化后的文件意思变成了 let a = 1(…).run()。现在它会保留 load()?，把 .run() 缩进放在下一行，并且把 e?(x)、e?[0] 和 e? ? 写成不带括号的形式。另一个是联合类型的 where 精化，格式化工具会把它丢掉，让一个 check 会拒绝的程序变成它会接受的程序。

这些格式化规则的背景，以及它们所做的取舍，见稳定的 diff 支柱页面。

当前状态

现已提供

  • 必需的尾随逗号、每行一项的列表，以及 glyph fmt 的单一标准排版，可往返转换且幂等，编辑器中支持保存时格式化。
  • glyph fmt 永远不会把注释挪到不属于它的地方。
  • 注释会保留在它原来所在的那一项上方
    详情

    注释会保留在它原来所在的那一项上方，包括在记录、字面量、实参列表、match 内部，在运算符的两个操作数之间，以及在方法链的各步之间，此时方法链会每行一步，点号放在行首。

边界，以及接下来的工作

  • 写在代码行末尾的注释会移到下一项的上方一行
    详情

    注释总是单独输出在一行上，所以写在代码行末尾的注释（w: int, // width in cells）会被移到下一项的上方一行。它不再跨越声明边界，但确实会移动；要让它保持在行尾，打印器需要记录注释和哪一行共享。

  • 排版中无处安放的注释会被拒绝，而不是被挪动E0500
    详情

    如果注释所在的位置在排版中无处安放，比如在索引内部、在方法链中间某个调用的实参之后，或者在 ! 或 await 的操作数之前，它不会再被挪动：glyph fmt 会拒绝这个文件，保持原样，并指出所在行以及注释应该放在哪里，glyph check 也会以警告 E0500 报告同样的问题。

  • JSX 属性之间、对象模式的字段之间的注释也会被拒绝，而这些地方本可以用每行一个的排版放下它；这些排版已经列入计划。
  • 打印器目前也还没有拆分长方法链或长 + 链的规则，所以过长的链会改为拆开最内层的实参列表，而那是错误的位置。
  • 我们还在构建一个 diff 大小的基准测试，对比在 TypeScript 中做同样编辑的结果，这样这根支柱就成了一个你可以核对的数字。
