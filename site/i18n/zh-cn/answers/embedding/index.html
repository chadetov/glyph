10 · 在你的应用中

能在现有应用里引入 Glyph 吗，还是必须全部改写？

不需要重写。应用继续用 TypeScript，把出不得错的部分（模型、权限、状态转换、金额计算）用 Glyph 编写。glyph build 生成的模块可以被你的应用像任何本地文件一样导入，不需要打包工具配置，也不需要路径别名。

为什么重要

大多数团队没法重写一个应用，而应用的大部分也不需要 Glyph。需要它的是领域核心：下个月 AI 智能体会去修改、谁都不希望它悄悄出错的那些规则。

把这个核心放在 Glyph 中，你就在最值得的地方得到穷尽的 match、没有类型断言、经过校验的边界，而 React 组件、样式和基础设施仍然是普通的 TypeScript。

宿主项目无需任何添加

生成的代码所需的一切都随它一起提供。

  • 相对路径导入导入使用相对路径，包括打包在内的标准库，所以你项目的 tsconfig.json 和打包工具不需要任何改动：标准的 Vite 脚手架可以原样编译和打包这些输出，同样的文件也能通过宿主项目的 tsc --strict。
  • pub 导出用 pub 标记应用要导入的内容；不带它的声明是模块私有的。

这不是假设：一位外部工程师用这种方式构建了一个 React 看板，RBAC 矩阵、分析公式和状态转换放在四个 Glyph 模块中，上面是手写的 React UI。

当前状态

现已提供

  • 生成的输出可以原样放进宿主项目：全部使用相对路径说明符，prelude 类型由代码自身携带。
  • 已在标准 Vite 脚手架、宿主 tsc --strict、esbuild 和 tsx 上验证。
  • 部署指南介绍了混合布局。

正在进行

  • glyph build --watch 会在每次保存 .glyph 文件时重新构建，但和 Vite 开发服务器一起用时，Glyph 的改动会让整页刷新，而不是热替换组件。请把输出放在 Vite 的构建目录（默认是 dist/）之外，它的开发服务器不监视那个目录。
  • 使用 std/fs 或 std/net 的模块需要宿主项目安装 @types/node，和任何涉及 Node 的 TypeScript 一样。
