问答

工程师关于 Glyph 的问题。

每个回答都有一个完整示例，并在结尾说明还有哪些做不到。从你最有疑问的地方开始读。第一次接触 Glyph？10 分钟上手是最快的入门方式。

它解决的问题

智能体的编辑会在不知不觉中破坏什么，以及 Glyph 对每一种如何应对。

01什么能防止智能体悄悄改坏我的代码？

没有 any，没有类型断言，match 必须穷尽，类型带运行时检查，以及每次构建都会运行的就近测试。

 02智能体的编辑会保持干净，还是会把整个文件重新格式化？

改一行就是一行 diff。只有一种标准排版，不会重新打包。

 03智能体（或者我）能找到任何东西的定义位置吗？

一个名字，一种声明形式。grep 总能找到它。

决定是否采用

为什么是一门语言而不是更多的工具，以及引入它的成本。

04为什么是 TypeScript，而不是 Go 或者一门全新的语言？

因为你的生态就在那里，这也是为什么可以按文件引入。

 05为什么不直接用严格模式的 TypeScript + zod + eslint + ts-pattern？

不可选：智能体无法通过配置关掉的语言。

 06如果我不用 AI，Glyph 还值得用吗？

值得：这些保证本身就是实实在在的工程收益，人也能直接受益。

 07AI 能可靠地写一门它几乎没见过的语言吗？

模型对 TypeScript 的了解大多能直接沿用，编译器会指出那些不能沿用的地方。

 08新的 Glyph 版本会破坏我的构建吗？

项目会精确固定编译器版本，所以不会有版本意外进来。glyph doctor 告诉你有新版本；glyph upgrade 负责升级。

配合你的技术栈使用

npm 包、现有应用、API 边界、React。

09我能使用现有的 TypeScript、JavaScript 和 npm 库吗？

能：导入任何 npm 包，需要时保留手写的 .ts 适配层，还能在 .ts 中反过来导入 Glyph。

 10能在现有应用里引入 Glyph 吗，还是必须全部改写？

不需要重写：领域核心用 Glyph，其余用 TypeScript。生成的 TypeScript 可以像其他模块一样被标准的 Vite 应用导入。

 11每个 API 都要手写校验器吗？

不用。声明类型就会生成它的校验器。

 12能根据 API 规范生成类型化的客户端和服务端吗？

glyph gen openapi/zod/dts：提交到仓库、可以 grep 的代码。

 13能和 React 一起用吗：组件、hooks 和 Context？

一等支持 JSX、hooks，以及必须穷尽的 reducer action。

 14Glyph 在 React 上还有哪些做不到？

每个 gap 编号一项，附有在此之前的写法。

 15怎样在函数之间共享可变状态？

用 store：一个 const，它的 .set/.update 就是写入接口。

能用它构建什么

按程序类型介绍语言和标准库。

16这是一门真正的语言，还是一个有很多缺口的玩具？

模块可见性、接口约束、defer、可以当作任意值使用并带有类型的 match，以及包含 slice、pad_start 和 fold 的标准库。

 17涉及金额、以及我无法控制的输入时，能信任它吗？

精确的小数和 id，不变式即类型，注入是编译错误。

 18能提供网页，还是只能做 JSON API？

HTML、重定向、响应头和表单提交，不需要手写服务器。

 19能写一个让人输入命令的程序吗？

io.read_line 在每行到达时就返回，而不是等 stdin 关闭，所以 REPL 或游戏循环都能工作。

 20能写服务器吗，还是进程直接就退出了？

main 做完初始化就返回；只要还有挂起的 socket 和定时器，进程就保持运行，和 Node 的规则一样。

 21能处理二进制数据吗，还是一切都是字符串？

std/bytes 是字节序列，编解码器会拒绝格式错误的输入而不是跳过，HMAC 使用真正的密钥。

与智能体协作

智能体在编辑前后向编译器提出的问题。

22编译器能在我改动之前告诉我改动会破坏什么吗？

glyph_impact：在你动文件之前，为每个位置给出一个来自固定列表的结论，并附上原因。

 23我的智能体能在写代码之前问编译器某个符号是什么吗？

glyph_symbol：一次调用就能拿到联合类型的各个变体，以及构造每个变体的语法。共十一个工具，每个都有对应的 glyph query 子命令。

 24构建失败时，编译器会告诉智能体怎么修吗？

诊断会带上出错的符号、合法的替代写法，以及修复性编辑不能破坏的东西。编译器能自行确定的修复，由 glyph fix 直接写入。

 25智能体读的文档是生成的，还是手写的、已经过时的？

glyph llms --json 从编译器自己的表中输出诊断、prelude、标准库签名和工具手册，手写的副本与之不一致时检查会失败。

 26我们已经有封装了，能阻止智能体直接导入原始库吗？

在 package.json 中禁止该导入路径并指明替代模块。导入它会得到 E0115，帮助信息会指向你的封装。

错误、编辑器与生产环境

出问题时你会看到什么，从编辑器到值班。

27编辑器、调试和报错的体验如何？

适用于任何 LSP 编辑器的语言服务器，以及带稳定错误码、会指出修复方法的报错。

 28为什么 Glyph 能发现 tsc 能发现的问题，而且更早？

await 上下文、没有值的 match 分支、缺少的 mut，都针对你的源码报告，而不是针对生成的 TypeScript。

 29解析失败时，我能知道原因吗？

哪个字段、违反了哪条规则、违反了哪个 where 谓词，以及一个可以用来分支处理的 code。

 30凌晨 3 点在生产环境出问题时，值班的人会看到什么？

你自己掌握的可读 TS，指回 .glyph 的 source map，以及报告内容与 build 一致的 run。
