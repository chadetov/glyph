20 · 服务器与守护进程

能写服务器吗，还是进程直接就退出了？

可以写服务器。main 完成初始化后返回，只要还有挂起的 socket 和定时器，进程就保持运行，和 Node 用的是同一条规则。在 0.1.63 之前并非如此：main 一返回，运行器就结束进程，所以服务器绑定端口后在同一个 tick 里就退出了。

为什么这很重要

这就是能运行脚本的语言和能运行服务的语言之间的区别。服务器、文件监视器、保持网关连接的机器人、任务运行器：它们都不会在 main 里结束。它们设置好处理函数，然后把进程交给事件。

历史 0.1.63 之前它是怎么失败的

旧的行为以最糟糕的方式失败，也就是悄无声息。glyph run app.glyph --serve 4100 什么都不打印，连 listen 回调里的那一行都没有，然后以 0 退出。源码看起来没有任何问题，类型检查也通过了。遇到这种情况的智能体没有错误可报告，也没有理由认为有什么失败了。

main 返回之后

有两点值得了解。return 0 在第一个客户端连接之前就执行了：它是进程最终退出时使用的退出码，而不是说明进程何时退出。

另外，任何在 main 返回之后才失败的东西都必须自己设置退出码，因为 main 的返回值已经用掉了。error 处理函数就是为此而设。没有它，一个无法绑定端口的服务器会在事件循环清空后以 0 退出，报告成功。

详情 net 导入的类型

net 是 Node 内置模块，所以它是普通的导入，但它不在编译器自带环境类型的六个模块（fs、http、path、os、crypto、url）之列。你可以安装 @types/node，构建会优先使用它；也可以在源码旁边放一个 .types/net.d.ts 声明，聊天应用就是这么做的，所以它完全不需要依赖。

反方向：长时间运行的客户端

机器人是同样的结构，只是方向朝外。examples/apps/discord 是一个 Discord 网关客户端：它通过 WebSocket 连接、发送身份信息、按服务器指定的间隔发送心跳、记录序列号以便断线后恢复而不是从头开始、发现连接虽然打开但已经失效的情况，并在重连之间退避。

值得借鉴的是逻辑放在哪里。如何应对 RECONNECT、错过的心跳或被拒绝的令牌，是一个纯函数：输入一个会话和一个事件，输出新的会话和一组动作。由一个模块在真实的 socket 上执行这些动作。

历史 三个 bug，两个 mock

这三个示例原本都是代码中的 bug。编写一个模拟网关并让机器人连接它，发现了其中一个。另外两个是由第二个模拟网关发现的，它依据 Discord 的文档编写，而不是依据客户端编写，因此会发送配合型的模拟网关从不发送的东西：一个未经请求的心跳请求，以及一个意思是“你的令牌不对，别再问了”的关闭码。由客户端作者编写的模拟网关，只能测试作者读过的那部分协议。

当前状态

现已提供

  • 从 main 返回会设置退出码，但不会停止进程，所以服务器、监视器和事件循环都能运行。
  • 只做计算的程序仍然在 main 返回时以同样的退出码立即退出，所以短程序的行为没有任何变化。
  • 像 net 这样的 Node 内置模块是普通导入，初始化时抛出异常仍会终止
    详情

    像 net 这样的 Node 内置模块是普通导入；在初始化期间抛出异常的程序仍然会终止，而且现在会在它的诊断写入管道连接的 stderr 之后才终止，而不是可能被退出截断。

  • std/timers 负责调度工作（after、every、cancel、unref），std/websocket 负责打开连接，所以两者都不需要手写声明。

正在改进

  • 在 main 返回后才绑定失败的监听器会以 0 退出，除非程序另行指定
    详情

    在 main 返回后才绑定失败的监听器会以 0 退出，除非程序另行指定：process.set_exit_code(1) 记录失败而不中断仍在进行的工作，process.exit(1) 则立即停止。

  • 编译器目前还不能提醒你忘了这一步。
  • 另外，现在仍然无法声明一个函数不会返回，所以服务器的 main 带着一个永远执行不到的 return 0。
