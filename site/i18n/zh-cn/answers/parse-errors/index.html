27 · 解析失败

解析失败时，我能知道原因吗？

能。每个问题都会指出字段，说明值违反了哪条规则，并带有一个可以用来分支处理的 code。受 where 谓词约束的字段会报告谓词本身，所以通过 grep 就能从拒绝信息找回施加这条约束的那一行。

本页内容

  1. 为什么重要
  2. 嵌套类型

为什么这很重要

一个只会说“这个负载有问题”的校验器只做了一半的工作。

处理函数仍然要判断：这是一个忘了某个字段的客户端，还是一个发来四个字符长密码的客户端？前者是 400，后者是 422，如果校验器不说，你最终只能用两个不同的类型把同一个请求体解析两遍，来找回校验器本来就知道的那一点信息。

历史 这个问题是在哪里出现的

用 Glyph 构建一个认证 API 时正好遇到了这种情况。一个完全没有 password 键的注册请求返回了 weak_password，因为缺失和过短产生的是同一个字符串。

嵌套类型自己给出答案

如果字段的类型有自己的描述符，就由那个类型的 parse 来校验，它的问题返回时路径前面会加上字段名。所以嵌套两层的 Password 会报告 ["body", "password"]，并仍然带着它自己的信息。

看错误码，而不是看字符串

Issue 带有一个可选的 code："missing"、"type"、"refinement"、"unexpected" 或 "depth"。根据它来分支。匹配信息文本正是 Glyph 要消除的脆弱之处，信息是给阅读响应体的人看的。

不读信息文本的 400/422 区分 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code 是可选的，所以你手动构造的 Issue，以及在它出现之前写好的所有使用方，都无需修改就能编译。

详情 "depth" 这个 code

当请求体中对象和数组的嵌套超过 1000 层（std/schema 中的 MAX_DEPTH）时，答案就是 "depth"：在发生嵌套过深的字段上报告一个问题。而在 0.1.150 之前，这个检查会抛出 RangeError: Maximum call stack size exceeded，连同处理函数一起崩掉。

当前状态

现已提供

  • 记录和 where 类型会报告失败的规则，而不只是失败的字段missingtyperefinementunexpecteddepth
    详情

    记录和 where 类型会报告失败的规则，而不只是失败的字段：缺少必填字段时为 "missing"，形状不对（包括非对象或数组）时为 "type"，值通过了基础类型但不满足谓词时为 "refinement"，类型没有声明的键为 "unexpected"，值的嵌套超过 1000 层时为 "depth"。

  • 细化类型会引用它的谓词。
  • 字段的类型有描述符时会委托给它，所以嵌套的问题带着完整路径返回。
  • 可选字段（f?: T）永远不会被报告为缺失。

正在加强 2

  • 如果字段的类型自身没有描述符，它仍然只做扁平检查并得到 "type" 问题
    详情

    有两个边缘情况。如果字段的类型自身没有描述符，比如不受约束的类型参数，或者从手写的 .d.ts 导入的类型，它仍然只做扁平检查并得到 "type" 问题；编译器不会为这些类型合成描述符，对声明运行 glyph gen dts 才能为它们生成一个。

  • 模块自己声明的名为 Issue 的类型，会在命名它的那一行被拒绝E0110自 0.1.60 起
    详情

    以前，一个模块如果自己声明了名为 Issue 的类型，会在生成的文件里遮蔽 prelude 中的那个，导致该模块的每个描述符都失效；从 0.1.60 开始，这样的声明会在命名该类型的那一行报 E0110，所以你能知道问题出在哪，而不是去读一条关于生成代码的 tsc 错误。
