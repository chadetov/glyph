11 · 数据边界

每个 API 都要手写校验器吗？

不用。在 Glyph 中，类型本身就是它的校验器。声明一个 type，编译器会在旁边生成一个运行时描述符，所以不可信的请求体或响应体一次调用就能校验，不需要另外编写并同步维护一份 zod schema。

为什么重要

在大多数 TypeScript 技术栈中，每个负载都要描述两次：一次是给编译器看的 type，另一次是手写的校验器，确保这个值在运行时真的是这个形状。

两者会逐渐偏离，而偏离之处正是坏数据溜进来的地方。Glyph 把它们合并成一个声明：类型产生校验器，所以两者不可能不一致。

看看实际效果

DTO 只需声明一次。它的描述符提供 .parse（把不可信的值校验为该类型）和 .is（类型守卫），不需要再写别的：

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}
你没有写的东西 
// No zod schema:
const NewTask = z.object({
  title: z.string(),
  done: z.boolean(),
});
// No drift between the type and
// the validator, because there is
// only one declaration.

// A bad body, {"title": 123},
// takes the Err arm. Only a
// well-formed body reaches Ok.

在 match 之后保留有类型的值

你也可以把值取出来，而不是在分支里完成所有工作。

api.glyph：值离开 match 时仍带着类型 
let task = match NewTask.parse(req.body) {
  Ok(t) => t,
  Err(issues) => { return bad_request(issues) },
}
task.titel   // E0210: type `NewTask` has no field `titel`; did you mean `title`?
自 0.1.45 起泛型类型：尚未支持
详情 类型如何传递，以及泛型的例外

T.parse 的类型是 Result<T, Array<Issue>>，而各分支类型一致的 match 会带着这个类型，所以 let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, } 在函数的剩余部分给你一个 NewTask，字段名由 Glyph 检查，而不是由 tsc 在生成的 TypeScript 上检查。这在 0.1.45 中落地；在此之前，值一离开 match 就没有类型了。泛型类型的 parse 仍然做不到，因为它的描述符需要为每个类型参数传入一个运行时检查器。

解析结果是普通的 Result

在 Glyph 中，T.parse 返回的 Result 和语言中每个可能失败的函数返回的一样，所以你可以直接把它返回，用 map_err 把校验问题转成你自己的错误类型，或者用 ? 向上传递。

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}

详情 在这里使用 Result 的运行时开销

一个以自己私有形状返回值的校验器只有一半用处，因为你其余的错误处理碰不到它。解析结果没有任何特殊之处。

它曾经不是这样的原因：描述符生成在你的 type 旁边，输出一个裸对象可以让声明类型的模块在运行时不依赖 std/result。现在这个取舍反了过来。含有 pub type 的模块无论是否写过 Result，都会带上对 std/result 的导入，而一次 parse 调用会分配任何 Ok(...) 都会分配的组合子闭包。换来的是：经过校验的边界和其余的错误处理使用同一套 API。

自己组合：输出类型是推导出来的，而不是被信任的

Glyph 的 infer_output<Shape> 从形状推导出输出类型，并由 tsc 检查你的标注是否与之相符。如果形状漏掉了你声称的类型中的某个字段，就无法编译：

schema.glyph 
fn object_schema<Shape: Record<string, Schema<unknown>>>(
  shape: Shape,
) -> Schema<infer_output<Shape>> { ... }

type User = { name: string, age: number }

// The shape must produce a User, or this
// line does not compile:
const user_schema: Schema<User> =
  object_schema({
    name: string_schema(),
    age: number_schema(),
  })
Glyph 消除的偏离 
// TS/zod: shape and output type are two
// separate things you keep in sync by hand.
const s = z.object({ name: z.string() });
type User = { name: string; age: number };
// `s` is inferred { name }, but nothing
// checks it against User. The `age` you
// forgot is caught at runtime, if ever.

// Glyph: drop `age` from the shape and
// `Schema<User>` fails to compile. The
// shape is the single source of truth.
详情 TypeScript 的陷阱，以及自 0.1.92 起跟随 return 的类型断言

有时你需要 zod 风格的组合子：把较小的校验器组合成一个校验器。TypeScript 中的陷阱是，组合子的输出类型和你传给它的形状会逐渐偏离。你写好形状，再在第二个类型参数里重复一遍，而没有任何东西检查两者是否一致。

无论组合子以什么方式返回，推导出的类型都成立。infer_output 需要在函数边界处做一次类型断言，因为函数体构造的值无法被类型系统证明带有由形状推导出的类型，这个类型断言由编译器替你写。在 0.1.91 及之前，它只附加在普通的 return <value> 上。如果在 return 和值之间放一个 match，或者让函数体以 r? 结尾，同一个函数就无法编译了：针对生成的 TypeScript 报出 TS2322，而对应的 Glyph 编译器早已接受。从 0.1.92 起，类型断言跟随的是 return 本身而不是它的写法，所以 return match strict { ... } 和同一函数体用单个 return 写出来的版本类型检查结果相同。

不可信边界的其余部分

让 json.parse<T> 变得安全的也是同一个描述符：给它一个 JSON 字符串，它会一步完成解析和校验。

输入调用返回
JSON 字符串json.parse<T>(text)Result<T, Array<Issue>>
已解码的请求体T.parse(value)Result<T, Array<Issue>>
请求头header(req, name)Option<string>
查询参数query_param(req, name)Option<string>
详情 请求体、请求头和查询参数

请求体到达时已经解码为 unknown，所以这时你要用 T.parse(value)：同样的保证，不需要类型断言。

不可信边界的其余部分也以同样方式定型：header(req, name) 和 query_param(req, name) 返回 Option<string>，所以缺失的请求头或查询参数是 None，而 match 强制你处理它。省略 None 分支就无法编译。不存在的输入不可能被当作存在来读取。请求体字段遵循同样的规则：timeout_ms?: number 要么是不存在的键，要么是数字，所以 {"timeout_ms": null} 在 ["timeout_ms"] 处得到 Err，无论来自 T.parse、is T 还是 json.parse<T>。如果发送方会写 null，就声明 timeout_ms?: Nullable<number>。在 0.1.152 之前，这个 null 会出现在 Ok 里返回。

以枚举为键的映射会检查它的键吗？

会，自 0.1.148 起。对于 type Tier = "free" | "pro"，Record<Tier, int> 只会解析键恰好为 free 和 pro 的对象：多出一个键或缺少一个键都是 Err，这和 tsc 对同一个对象写成字面量时的判断一致。

键类型parse 对每个键检查什么
字符串字面量联合类型恰好是列出的键，不缺也不多
用 where 细化的 string 或数字谓词
int整数的普通写法；"01" 和 "1.5" 不通过
string没有新变化
详情 细化类型和 int 类型的键，以及检查器把关的部分

用 where 细化的键类型会对每个键运行谓词，int 键必须是整数的普通写法，所以 "01" 和 "1.5" 被拒绝。Record<string, V> 的检查方式和以前完全一样。where 不能细化字符串字面量联合类型（自 0.1.152 起，type T2 = Tier where value != "pro" 是 E0300）；把你想要的成员写成单独的联合类型 type T2 = "free"，它作为 Record 的键时会得到同样的精确键检查。自 0.1.153 起，对于你在代码中写出的值，Glyph 自己的检查器也会检查它的键：Record<string, int> 不能用在声明为 Record<Tier, int> 的位置，反过来也一样，所以跨越这条界线要通过 json.parse 或一个 is Record<Tier, int> 分支，而 record.set 会保留传给它的键类型。以自身类型参数为键的泛型记录会被拒绝，除非该参数是 string。

解析一个日期，得到的是真正的日期吗？

是的，更值得一看的是，对于不是日期的输入你会得到什么。time.parse_iso 返回 Option<number>，对任何不是 ISO-8601 的内容都返回 None。

接受 
"2026-01-03"              // UTC midnight
"2026-07-25T18:33:08.000Z"
"2026-03-15T09:30:00-05:00"
"2028-02-29"              // a real leap day
全部返回 None 
"January 5 2026"   // not ISO
"2026-1-3"         // not padded
"2026-13-01"       // no month 13
"2026-02-31"       // no such day
"2026-02-29"       // not a leap year
"2026-01-03T10:00" // no offset

最后一个最让人意外，而它正是重点所在。按照 ECMAScript 语法，没有 Z 也没有 +HH:MM 偏移的日期时间是本地时间，所以接受它就意味着同一个字符串会因运行程序的机器不同而指向不同的日历日。

详情 Date.parse 会怎么做，以及为什么用 UTC

这比 JavaScript 的 Date.parse 要严格。后者接受自由格式的文本（"January 5 2026"），按进程碰巧所在的时区读取没有补零的日期，比如 "2026-1-3"，并且把不可能存在的日期向后滚动后当作成功："2026-02-31" 变成 3 月 3 日，你拿到一个数字，没有任何迹象表明发生了什么。

Glyph 的日历访问函数（time.year、time.month、time.day）使用 UTC，并且明确说明这一点，而一个悄悄引入宿主时区的校验器会让它们给出错误结果。所以这样的字符串会被拒绝，由你来决定它的含义。

守卫移进了基础函数

当应用在标准库的基础函数外面包一层正确性守卫时，这个守卫应该放进基础函数本身。下面是应用删掉的代码：

之前：应用为标准库加守卫 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
之后：由基础函数把关 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

import std/regex 也一起删掉了。同样的账本，同样被拒绝的行，报告逐字节相同。

历史 这个改动来自的报销应用

这个改动来自用 Glyph 编写的一个报销单命令行工具。每一行账目都带有日期，而把一行记到错误的月份是真正要紧的 bug，所以这个应用不信任旧的 parse_iso：它先用正则表达式检查格式，再把时间戳转回文本，以发现被滚动过的日期。

连类型都不用自己写

如果形状已经存在于 OpenAPI 规范或 TypeScript 声明文件中，就从中生成 Glyph 类型：真实的、提交到仓库的、可以 grep 的 type 声明，每个都带有描述符，而不是推断出来的虚影：

从 OpenAPI / JSON Schema 规范生成 
glyph gen openapi petstore.yaml \
  --out src/
按名字从已安装的包生成 
glyph gen dts api-types \
  --out src/types

线上传输的类型变成经过校验的边界，不需要任何手写代码：

webhook.glyph 
import types/api_types { Customer }

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),
  Err(issues) => reject(issues),
}

生成过程忠实于线上格式：规范对一个值的描述，就是 parse 检查的内容。

在规范或 .d.ts 中生成的 Glyph
字符串枚举字符串字面量联合类型；parse 检查取值是否在其中
integer 字段int；线上的 3.5 不通过
对象 schema标记为 @open 的记录；有 additionalProperties: false 时为严格模式
interface Page<T>type Page<T>，每一项都按 T 检查
无判别字段的联合类型收窄，并打印一条说明
同一个名字出现在两个可达文件中标记并附说明，不做绑定
详情 目前能生成什么、重新生成、泛型类型

把 glyph gen dts 指向一个 .d.ts 文件，或者像上面那样按名字指向一个已安装的 npm 包：它会从 node_modules 中解析出该包自己的声明入口，并写出供你导入的、提交到仓库的类型。

目前能生成的内容：gen dts 读取包导出的 interface 和 type 声明，包括 declare namespace 树中的声明（裸的交叉引用会通过作用域解析），以及 index 汇总文件重新导出的同级文件中的声明（会遍历入口 .d.ts 及其通过相对路径导入的每个 .d.ts）。泛型保持一等地位：interface Page<T> 生成为 type Page<T>，并得到一个按类型参数校验每一项的描述符，而不只是检查是否存在。带别名的重新导出和 export * as 重新导出通过每个文件的绑定映射解析。唯一无法保证安全的情况，即一个类型名在两个可达文件中冲突，它会标记并附上说明，而不是悄悄绑定到错误的形状。对于生成器处理不到的内容，就手写你在边界上用到的形状，或者使用 extern_ts 逃生口。

重新生成是幂等的，所以规范的改动会是一个干净、可审查的 diff。生成过程忠实于线上格式：字符串枚举生成为字符串字面量联合类型（"free" | "pro"），所以 parse 检查的是取值是否在其中，而不只是检查它是否为字符串，对它的 match 不需要 else 就是穷尽的。integer 字段变成 int，所以线上的 3.5 会让 parse 失败，而普通的 number 则会通过。如果某个结构没有完全对应的 Glyph 形式（比如无判别字段的联合类型），它会收窄并打印一条说明，而不是生成一个会拒绝真实数据的校验器。生成的记录还带有 @open，所以 parse 能容忍 API 以后新增的字段，同时仍然校验它声明的每个字段；设置了 additionalProperties: false 的 schema 保持严格。Glyph 中的记录默认是严格的，而这和手写记录使用的是同一个可以 grep 的声明处标记，所以记录的含义没有任何变化。

泛型类型同样会被校验。Paginated<T> 得到的描述符，其 parse 接受类型参数：Paginated.parse<User>(body) 会把 items 的每一项按 User 检查，而不只是检查是否存在，match v { is Paginated<User> => ... } 也以同样方式收窄。这一点跨模块边界同样成立：在一个文件中定义 Paginated<T>，在另一个文件中 import 它，那里的 Paginated.parse<User>(body) 和 is Paginated<User> 仍然会把每个元素按 User 检查。编译器在调用处根据类型参数构造逐元素检查，所以泛型类型位于哪个文件，不影响校验的内容。

它的边界：描述符覆盖了大多数负载所由构成的形状：对象、基本类型、数组、引用、可选和可空字段，以及现在在具体实例化下的泛型类型。不是由 Glyph 生成的类型（你只是导入的外部包或 .d.ts）会被类型检查，但在你把它生成出来之前没有描述符，而现在这只需要对已安装的包运行一条命令（glyph gen dts <package>，针对它导出的顶层 interface 和类型别名）。这个边界是有意的：一个不是 Glyph 生成的类型无法承诺运行时校验，所以你按包逐个选择加入，结果被提交到仓库且可以 grep，而不是每次构建时凭空变出来。

数据库也是边界

从数据库读出的一行，和请求体一样不可信。你在请求体上用的 .parse 同样可以校验一行数据。

tasks.glyph 
type Task    = { id: int, title: string, done: bool }
type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.
match TaskRow.parse(row) {
  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}
它消除的 bug 
// TS, better-sqlite3 / node:sqlite:
const row = stmt.get(id) as Task;
// `row.done` is really 0 or 1, a number.
// Nothing complains. Then:
if (row.done === true) { ... }   // never runs

// The row was `unknown`; the cast invented
// a type. Glyph makes you validate the row
// into TaskRow, and the int-to-bool step is
// a line of code, not a silent lie.
详情 std/sqlite，以及值为 0 或 1 的布尔

从数据库读出的一行，和请求体一样不可信：数据库 schema 和你的代码对这一行的理解可能不一致，而类型断言（row as Task）会把这种不一致掩盖掉。std/sqlite 是基于 Node 内置 SQLite 的数据库模块，它正是按这个思路设计的。查询返回 Array<Record<string, unknown>>，所以不先校验就没有办法把一行当作 Task 使用。

这能抓住一个人们经常上线的 bug。SQLite 没有布尔类型，所以 done 列返回的是整数 0 或 1。把这一行断言成带 bool 字段的记录，task.done === true 就悄无声息地永远不成立。在 Glyph 中，存储形状和领域形状是两个不同的类型，两者之间的映射是你能直接看到的一行代码：

带签名的 webhook 也是边界

校验 webhook 签名需要发送方签名时的原始字节，而不是重新序列化的副本（把解析后的请求体重新转成字符串会改变空白和键的顺序，HMAC 就永远对不上）。http.raw(req) 把这些字节交给你，所以校验可以留在 Glyph 中完成： 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
详情 签名用原始字节，形状用解析后的请求体

req.body 仍然是用于形状检查的解析值；raw 是计算签名所依据的未经改动的负载。一个既校验签名又校验请求体的接收端不需要任何手写的 TypeScript。

类型不仅能校验形状，还能校验不变式

形状检查告诉你某个字段是数字，但不会告诉你金额非负，或者评分在 1 到 5 之间。where 细化把这个不变式放进类型，由描述符在边界处强制执行：

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
你不用写的东西 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.
