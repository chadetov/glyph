新的 Glyph 版本会破坏我的构建吗？

除非你主动要求，否则不会。Glyph 项目把编译器固定到一个精确版本，所以今天早上发布的版本不会在下午进入你的构建。在 1.0 之前，一个版本可以新增诊断，拒绝昨天还能编译的代码，而这通常正是这个版本的意义所在，所以要不要升级由你决定，而且只需要一条命令。

为什么这很重要

大多数工具你会用 ^ 来固定，因为补丁版本是 bug 修复。1.0 之前的编译器不是这样。Glyph 的工作就是拒绝程序，而做得更好意味着新的错误：对导入更严格的检查、以前会漏过去的穷尽性漏洞、检查器之前没有建模的参数数量。这些是好的版本。但它们也正是你不希望在为了添加一个日期库而运行 npm install 时混进来的版本。

所以 glyph init 不写 ^。对 0.x 版本来说，^ 仍然会让补丁版本浮动，这正是陷阱所在：^0.1.9 会悄悄接受之后的每个 0.1.x。

package.json，脚手架生成的样子 
"devDependencies": {
  // exact. no caret, no tilde.
  "@glyphlang/glyph": "0.1.72",
  "typescript": "^6.0.0",
  "tsx": "^4.19.0"
}

把旁边的 package-lock.json 也提交，新克隆的仓库就会用你测试过的工具链构建，而不是用之后发布的随便哪个版本。

另一半

固定版本有一个明显的失效方式：你在一个旧编译器上待了一年却毫不知情。你机器上的任何东西都不会告诉你，而一个需要你记得去访问的网站也算不上通知渠道。所以，当你向编译器询问关于你的环境配置的任何问题时，它会告诉你：

glyph doctor 
glyph — 0.1.72
  [update]   0.1.73 is published — `glyph --update` moves this compiler, `glyph upgrade` moves a project's pin
             what changed: https://glyphlang.io/versions/

glyph doctor — JavaScript toolchain
  [ok]       node: v22.1.0
  [ok]       tsx: tsx v4.19.0
  [ok]       tsc: Version 6.0.2
All good. `glyph run` and `glyph build --check` are ready.

发现新版本永远不会改变退出码，所以在 CI 中运行它是安全的。一个已发布的版本并不意味着工具链坏了，绿色的流水线不应该因为有人十分钟前发了版本就变红。如果机器离线，检查会说明这一点然后继续；--offline 会完全跳过它，不发出任何网络请求。

其他命令都不会访问 registry。build、run 和 check 从不这样做。每次构建都要联网报告的编译器是另一种产品。

进行升级

只改一行，时机由你决定 
$ glyph upgrade --dry-run
glyph upgrade: would move /app/package.json from 0.1.72 to 0.1.73 (nothing written).

$ glyph upgrade
glyph upgrade: /app/package.json now pins 0.1.73 (was 0.1.72).
glyph upgrade: what changed: https://glyphlang.io/versions/
glyph upgrade: build before you commit; a new release may report diagnostics
               this project did not have.

它改写一行并运行 npm install。它不碰你的源码，也不假装升级已经完成：之后的构建才是关键，因为你刚升级的版本可能对你的代码有它还没遇到过的意见。--to <version> 指定一个具体版本，想回退时也可以指定更旧的版本；--no-install 则把安装留给你自己。

升级工具，而不是项目

upgrade 修改的是 package.json 中固定的版本。如果落后的是你 PATH 上的编译器，用它就不对了，而有一段时间 doctor 照样会打印它，让全局安装去修改一个可能并不存在的清单文件。glyph --update 是另一半。这种划分现在是一条规则而不是巧合：flag 作用于工具本身，就像 --version、--help 和 --explain 那样；子命令作用于你的代码。--update-dry-run 在打印它将要运行的 npm 命令后停止。

glyph --update 
$ glyph --update
glyph 0.1.72 is installed; 0.1.73 is published.
Release notes: https://glyphlang.io/versions/
A 0.1.x release may reject code that compiled before, so read the notes for anything between these two.

Running: npm install -g @glyphlang/glyph@0.1.73
   ... npm output ...

npm finished. Confirm with:
    glyph --version

它只会更新它能识别的安装。通过 npx 调用的编译器、从 Glyph 源码树构建的编译器，或者位于它不认识的路径上的编译器，只会打印出命令而不覆盖任何东西，因为凭猜测替换一个 Homebrew 二进制文件或某人的 cargo build 产物，会让 PATH 指向一个没有人选择过的东西。它也不会声称更新已经成功：npm 可能在跳过一个无法获取的 optionalDependency 后仍以 0 退出，Glyph 曾经就因此发布过一个没有平台二进制文件的版本，所以最后一行给出的是用 glyph --version 检查，而不是断言成功。

当前状态

现已提供

脚手架生成的项目会精确固定版本，所以没有版本会意外进入构建。glyph doctor 对照 registry 报告你的编译器版本并链接到版本说明，它永远不会影响自己的退出码，也不会被 build/run/check 触发。glyph upgrade 修改固定的版本并安装，还能读取旧项目中的 ^ 写法，所以已有的项目也能改成精确固定。glyph --update 升级编译器本身，适用于全局 npm 安装；对于其他所有安装方式，它只报告而不猜测。

正在改进

版本说明是整条版本线共用的一个页面，所以 glyph upgrade 链接的是这个页面，而不是你要升级到的那个版本的条目。目前还没有什么能告诉你，新版本的哪些诊断会被你的代码触发：要知道就得构建，所以命令会提示你这样做。一次跨越多个版本的升级，和升级一个版本是同样的一步，不会汇总中间累积的变化。glyph --update 调用 npm 并读取它的退出码，所以它能告诉你 npm 执行完了，却不能告诉你 PATH 上的二进制文件就是你要的版本；这就是为什么它指向 glyph --version，而不是说更新成功了。
