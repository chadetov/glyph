05 · 对比

为什么不直接用严格模式的 TypeScript + zod + eslint + ts-pattern？

因为这些保证每一项都是可选的，智能体用一行代码就能绕过其中任何一项。Glyph 的严格性不是一个智能体能修改的配置文件，而是语言本身。执行点从“我们有没有记得对这个文件跑 lint”变成了“它能不能编译通过”。

配齐工具的 TypeScript 已经覆盖了什么

配置良好的 TypeScript 能帮你走很远，如果你的团队在 CI 中把这些全部跑起来，Glyph 针对的大部分 gap 你已经补上了。这是值得认真对待的替代方案，下面是对照：

配齐工具的 TypeScript 已经提供的东西 
no `any`            → noImplicitAny + @typescript-eslint/no-explicit-any
exhaustive match    → ts-pattern .exhaustive() (compile-time, today)
errors as values    → neverthrow / Effect
runtime validation  → zod at every boundary
must-handle errors  → an eslint rule
deterministic diffs → Biome / Prettier

如果这些你都接好了并且强制执行，你已经完成了大半。TypeScript 有这些思路。一门语言把它们变成不可选的，额外带来的东西归结为三点。

01 不可选胜过可选

你的 eslint 配置只保护智能体经过它的代码，而智能体可以写 as unknown as User、@ts-ignore、// eslint-disable-next-line，或者干脆忘了 .exhaustive()，代码照样能编译、照样能合并。这些逃生口每一个都是智能体可以修改的配置。Glyph 没有这样的逃生口可用：没有 as，没有忽略检查的指令，不经过编译器能看到的检查，就没有办法从 unknown 中得到一个有类型的值。

TypeScript：逃生口就在那里 handler.ts 
const user = body as unknown as User;
// @ts-ignore
doThing(user.mispelled);
// eslint-disable-next-line
return anything as any;
Glyph：没有可以关掉的东西 handler.glyph 
return match User.parse(body) {
  Ok(user) => use(user),
  Err(_) => fallback(),
}
// no `as`, no ignore pragma,
// no lint to switch off.

智能体无法通过配置关掉的严格性，与它能关掉的严格性，处在不同的执行点上。Glyph 就建立在这个区别之上。

02 类型就是校验器：没有第二份产物

zod 颠倒了你的唯一事实来源：你写的是 schema，从中推导出类型，然后手动让类型、schema 以及任何序列化器保持同步。保持它们一致，恰恰是智能体引入偏差的地方：它在类型里改了字段名，却没改 schema，两者仍然都能编译。在 Glyph 中，类型就是校验器：声明 type User = {...} 时会同时生成 User.parse。只有一份产物，没有需要同步的东西，也没有可以忘掉的东西。

03 可检索的修改

在 TypeScript 中，状态变化可以藏在 =、.push()、Object.assign、setter 或展开语法后面。没有一个可以搜索的单一记号，也没有哪条 lint 规则能彻底解决。在 Glyph 中，共享状态放在 store 里，每次修改都是字面上的 .set(/.update(；grep 'mut ' 能找到每一处局部修改。原生 TypeScript 没有对应的东西。

出错方式的对比

同样的任务：智能体给联合类型加了一个变体，却在三处中的一处忘了处理它：

配齐工具的 TS 
// ts-pattern .exhaustive() catches it,
// IF every site used ts-pattern and
// nobody wrote a default: case or a
// switch that only logs. Those
// compile green and skip the new case.
Glyph 
[E0200] non-exhaustive match on
`Feed`: missing variant `Archived`
// every unhandled match, everywhere,
// fails the build. No opt-in, no
// escape, no forgotten default.

配齐工具的 TypeScript 仍然领先的地方

目前它在四个方面领先 Glyph：

  • 更丰富的校验。Glyph 的描述符默认是严格的（会拒绝未声明的键），where 精化可以给基本类型加上谓词（type Email = string where value.includes("@")），描述符会在这个类型到达的每个边界上运行它。zod 仍在两方面领先：它自带现成的检查，例如 .email() 和 .url()，而在 Glyph 中你要自己写；它还能对整个对象做精化，而记录上的 where（跨两个字段的 lo <= hi）目前是 E0300。
  • 更深入的匹配。ts-pattern 的守卫和深层结构模式，超出了 Glyph 的 match 能表达的范围。
  • “可证明不存在”止于 .ts 边界。Glyph 的保证只对 Glyph 写出的代码成立；npm 依赖抛出的异常仍然会绕过 Result，导入的 .d.ts 类型也不带运行时描述符。
  • 生态与招聘。TypeScript 的工具、社区和招聘人才池要大得多，背后还有多年的生产使用经验。Glyph 还是早期预览版。

如果你已经把配齐工具的 TypeScript 完全接好，而且你的智能体一直待在它的范围之内，你已经拥有了其中的大部分。Glyph 的论点是，“一直待在范围之内”才是关键所在，而这恰恰是智能体会打破的。不可选、单一产物的校验和可检索的修改，是你靠添加更多可选工具得不到的部分。

如果你愿意离开 TypeScript，改用一门编译到 JavaScript 的、更成熟的类型化语言，为什么不用 ReScript、Gleam 或 Elm？对比了 Glyph 与它们。

当前状态

现已提供

没有 any/as，穷尽的 match（E0200/E0218），丢弃 Result 时的警告（E0217），由类型生成的校验器，以及可检索的修改：全都不可选，没有一项是可以关掉的 eslint 规则。
