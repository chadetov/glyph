18 · 提供网页

能提供网页，还是只能做 JSON API？

能提供网页。std/http 可以设置响应头，所以 text/html 页面、302 重定向、缓存头和 HTML 表单提交都是普通的 Glyph 代码。不需要 Express，也不需要手写的 TypeScript 适配层。

为什么重要

在 0.1.46 之前，响应是 { status, body }，由服务器根据响应体的形状选择内容类型：字符串是 text/plain，其他一律是 JSON。这对 API 没问题，但对浏览器要渲染的东西毫无用处。

唯一的办法是在手写的 .ts 文件里基于 node:http 自己写服务器，这会让整个请求路径脱离类型检查器。缺两个构造函数，代价是整个应用的一条边界。

处理函数返回 Result

处理函数返回 Result<Response, string>，所以 404 是普通的 Ok，Err 留给应用无法回答的情况，由服务器转成 500。

serve 在监听期间保持挂起，所以不需要手动维持进程存活，绑定失败也会以值的形式返回。

每个响应都带响应头

Response 带有一个必填的 headers: Record<string, string>。是必填而不是可选：每个构造函数都会填上它，所以读取 resp.headers 永远不需要检查是否存在，这个通道也不会被遗忘。

  • 返回新响应，而不是修改with_header(resp, "cache-control", "no-store") 返回一个新的响应，而不是修改原有的，因为 Glyph 没有记录字段的修改操作。
  • 在 Glyph 中检查类型检查器知道这三个构造函数都返回 Response，所以声明返回类型为 Result<Response, string> 的处理函数在 Glyph 中就被检查，而不是由 tsc 在生成的输出上检查。

两个手写时很容易出错的细节

  • 响应头的值Node 拒绝写入响应头的任何字符都会在输出时从值中剔除，所以用查询参数构造的 location 无法注入第二个响应头或第二个响应，短链接中的 emoji 也无法让服务器崩溃。
  • 表单请求体form(req) 会把 + 解码为空格，同时处理百分号转义，手写的表单解析通常会漏掉这一对；它读取的是原始请求体，所以对于自己解析请求体的处理函数，req.body 保持不变。

当前状态

现已提供

  • html、redirect、with_header、json、text 和 form
  • 响应头会实际发送，只有在你没有设置内容类型时才会推断它
  • 入站方向可以读取请求头、查询参数、路径片段和原始请求体
  • 客户端会报告它收到的响应头。
