基准测试

两类证据。

有两个值得测量的问题，我们把它们分开。结构性的：哪些 TypeScript 接受的东西被 Glyph 从构造上拒绝了？这在今天就能证明，见下文。可靠性的：与一套配置良好的严格模式 TypeScript 相比，智能体用 Glyph 交付的缺陷真的更少吗？这个数字决定是否值得采用，而我们还没有它。这是一项我们正在搭建的研究，我们不会把某个替代指标包装成这个答案。（真正的比较不是 Glyph 对比随便写的 TS，而是 Glyph 对比严格模式 TS + zod + eslint + ts-pattern。）

结构性：从构造上就可证明

不是统计数据，而是成对的演示。每一个都是 Glyph 拒绝而 tsc --strict 接受的案例，可以在 benchmarks 目录中复现。

可验证性：真正让你付出代价的 bug
两者都在编译时被发现

智能体经常犯的两种错误（漏掉 match 的一个变体，以及通过 as unknown as 做类型断言）会被 Glyph 拒绝，而 tsc --strict 接受。两者都是 catches/ 中经过检验的案例（non-exhaustive-match，E0200；as-unknown-as，E0013），由构建检查重新运行。能编译的错误代码是代价最高的失败，Glyph 不允许它出现。

可检索性：一个名字，一个位置
每次都只有 1 个匹配

每个符号都只有一种声明形式：没有重载、装饰器或合并的命名空间把它分散开。

$ grep -n "fn welcome" main.glyph
15: fn welcome(user: User) -> Result<string, string> {
稳定的 diff：天然便于审查
1 行 → 1 行

一行 Glyph 编辑经过转译后产生一行 TypeScript diff，glyph fmt 也不会引入无关变动。diff 就是改动本身，而不是周围的噪音。

安全通常意味着更长：Go 和 Rust 这两行同样有静态类型和显式错误处理，也是最长的。Glyph 两者兼备，却没有因此变长：436 个 token，TypeScript 是 478 个，少了约 9%，与 Python 持平，比 Go 少约 23%，比 Rust 少 30%；这些都是用真实的 cl100k_base 对能通过 glyph check（含 tsc）的程序计数得到的。优势体现在有真实控制流的函数上（parse_user，132 对 174）；在一行的 slugify 上 Glyph 更长（67 对 47），因为它没有正则字面量。只有三个函数，样本很小。早先的 341 这个数字是在编译器不接受的测试用例上测得的，已撤回。查看方法和注意事项 →

可靠性：我们正在搭建的研究

上面的结构性结果是预期 Glyph 会有帮助的理由，并不是它确实有帮助的证明。证明需要一项对照研究：同一个智能体、同样贴近实际的任务，一次用 Glyph 写，一次用配齐工具的严格模式 TypeScript 写（tsconfig strict + typescript-eslint + ts-pattern + zod），按漏到线上的语义缺陷和一次构建通过率打分。五位不同的审阅者告诉我们，这个数字才能说服他们，所以我们正在搭建它；在它出来之前，这些柱状图只是占位，不是结论。
