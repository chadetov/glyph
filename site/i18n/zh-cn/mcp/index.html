面向智能体 · Model Context Protocol

把智能体接入 Glyph 的编译器

glyph mcp 运行一个 Model Context Protocol 服务器，针对你的项目提供十一个工具：某个符号是什么；改了它会破坏什么；某个类型的值能否放到声明为另一个类型的地方；一个声明依赖什么；一个模块导出什么；在项目范围内检查的诊断；光标处的类型；名字在哪里定义；它的每一处引用；对某个联合类型的每一处 match；以及符号搜索。每个工具同时也是一个 glyph query 子命令，所以没有 MCP 客户端的智能体也能问同样的问题，得到逐字节相同的结果。

智能体为什么需要它

在代码库里做编辑的智能体，通常是在摸黑工作。它读文件、猜类型，直到构建之后才知道有没有改坏东西。Glyph 本来就会为编辑器回答这些问题。glyph mcp 让智能体直接从编译器拿到同样的答案，不用去抓取构建输出，也不用为了搞清谁调用了谁而读遍每个文件。其中两个工具回答的是编辑器从不会问的问题：glyph_symbol 返回联合类型的各个变体以及构造每个变体的语法，这正是智能体写 match 之前需要的；glyph_impact 在编辑发生之前就回答它会破坏什么。

配置

任何 MCP 客户端都能启动它。把客户端指向 glyph 可执行文件和 mcp 子命令，并把项目根目录作为参数传入，或者在项目目录下运行。它通过 stdio 使用 MCP，所以没有端口，也没有守护进程。

MCP 客户端配置（通用） 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp", "/path/to/your/project"]
    }
  }
}

首次连接时，客户端会调用 initialize 和 tools/list；服务器报告下面的十一个工具。你发送的位置遵循 LSP 约定：从 0 开始的 line，以及从 0 开始、以 UTF-16 码元计的 character。诊断范围的返回格式和 glyph check --json 打印的一样：从 1 开始的 line 和 col，外加字节 offset。

每个工具的描述里写着调用时需要知道的约定，完整手册在 glyph llms --json 的 tools 下，按工具名索引，每个工具旁边还附有对应的 glyph query 子命令。这个回复以前会带上所有手册：十一个工具，45,509 字节的回复中有 31,446 字节是描述。现在是 20,386 字节的回复中占 8,627 字节，而且什么都没删。每个会话在连接时都要为 tools/list 付出代价，而手册只有在主动请求时才需要付出。那份文档由编译器自己的表生成，如果它提到了这个服务器不提供的工具，会有测试让构建失败。

十一个工具

glyph mcp 提供的工具 
// everything the compiler holds about one symbol: kind, identity,
// visibility, a record's fields, a union's variants with payloads and
// construction syntax, parameters and return, interface members,
// whether a `match` over it must be exhaustive, its `@example`.
// The identity reaches the stdlib: std/result::Result answers with
// Ok(T) and Err(E), and `path` is null beside the reason why
glyph_symbol(entity)                       // or (path, line, character)

// what breaks if you make one named change to one declaration:
// add_variant, remove_variant, rename, change_arity,
// change_signature_type, remove. One verdict per site
glyph_impact(entity, change)

// can a value of `from` go where a `to` is declared? Asked of the
// checker's own comparison. Each side is a `module::name` or a
// Glyph type spelling read in the scope of `path`
glyph_assignable(path, from, to)

// every diagnostic for one file, checked inside its project, in the
// shape `glyph check --json` prints, plus what was not checked
glyph_diagnostics(path)

// the type at a position: an expression, a declaration name, a
// parameter, an annotation, a variant, or a binding
glyph_hover(path, line, character)

// where the name is defined, following imports across modules,
// with the `module::name` so the answer chains into glyph_impact
glyph_definition(path, line, character)

// every edge into a symbol across the project, split by relation
// (CALLS, REFERENCES, GENERATED_FROM), each with its provenance
glyph_references(path, name)               // or by position

// every `match` site over one tagged union and which variants each
// site's arms name, with the union's own variants
glyph_variants(path, name)

// search top-level declarations and union variants by name, each
// entry with its identity, `pub`, kind and one-line signature
glyph_symbols(query)

// what one declaration depends on: every declaration its own source
// names, split by relation (CALLS, REFERENCES, FIELD_ACCESS), each
// edge with both ends and its provenance. The mirror of references
glyph_dependencies(entity)

// what one module makes visible to an importer: every `pub`
// declaration and every variant a `pub` union hoists, each with
// its identity, kind and signature
glyph_exports(module)

看看实际效果

对一个有字段拼写错误的文件，调用 glyph_diagnostics 的 tools/call 会返回编译器自己的诊断，与 glyph check --json 序列化的是同一个 Rust 类型，外面包了一层，还会说明这次检查没有覆盖什么。

请求 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": { "path": "src/user.glyph" }
  }
}
结果（工具的 JSON 内容） 
{
  "path": "src/user.glyph",
  "module": "user",
  "project_root": "src",
  "member": true,
  "diagnostics": [
    {
      "code": "E0210",
      "severity": "error",
      "stage": "typecheck",
      "message": "type `U` has no field `naem`; did you mean `name`?",
      "help": "Check the field name for a typo,
        or add the field to the type.",
      "entity": "user::greet",
      "file": "user",
      "range": {
        "start": { "line": 9, "col": 10, "offset": 99 },
        "end":   { "line": 9, "col": 16, "offset": 105 }
      },
      "union": null,
      "missing_variants": null
    }
  ],
  "unindexed": [],
  "not_run": [ ... ]
}

文件是在它所属的项目内检查的，所以导入的记录上的错误字段，以及对导入的联合类型缺少分支的 match，在这里的报告方式和 glyph check 一样。工具没能覆盖的部分会写在答案里，而不是留给你去猜：member 说明项目遍历是否覆盖到这个文件，unindexed 列出无法解析的项目文件，not_run 列出 glyph check 会做而这里不做的三项检查：tsc；E0104（导入了不存在的模块），它需要构建所看到的 node_modules；以及 E0400（@example 失败），它要运行生成的项目才能判定。有一个测试会在六个项目上同时运行这两种方式，并逐个键比较 JSON，所以两者不会出现偏差。

glyph_references 覆盖整个工作区：问一个符号，你会得到它的声明、每一处使用，以及每个导入它的模块的 import 绑定，跨越所有文件。它使用的跨文件标识和编辑器重命名用的是同一套，所以答案覆盖整个项目，而不只是你发起询问的那个文件。

没有 MCP 客户端？在命令行上问同样的问题

每个工具都有一个 glyph query 子命令，把工具自己的参数作为 flag，并在 stdout 上打印工具的 JSON。问题得到回答时退出码为 0；被拒绝时把原因写到 stderr，退出码为 2。这些子命令走的是 MCP 客户端调用的同一个入口，有一个集成测试会向两种方式问同一个问题并按文本比较答案，所以任何会重新格式化或做摘要的子命令都过不了这个测试。

同样的十一个问题，无需客户端 
glyph query symbol       --path src/main.glyph --entity orders::OrderStatus
glyph query impact       --entity orders::OrderStatus --change add_variant --variant Refunded
glyph query assignable   --path src/main.glyph --from 'Nullable<int>' --to int
glyph query diagnostics  --path src/main.glyph
glyph query hover        --path src/main.glyph --line 9 --character 6
glyph query definition   --path src/main.glyph --line 9 --character 6
glyph query references   --path src/orders.glyph --name create
glyph query variants     --path src/orders.glyph --name OrderStatus
glyph query symbols      --query order
glyph query dependencies --path src/main.glyph --entity main::build
glyph query exports      --path src/main.glyph --module orders

// the same two, asked about a module the compiler carries
glyph query symbol       --path src/main.glyph --entity std/result::Result
glyph query exports      --path src/main.glyph --module std/result

构建已经失败时

这些工具回答的是编辑之前的问题。编辑之后，要读的是 glyph check --agent，它打印 check --json 的诊断，并在每条诊断上多加两个键：constraints，修复性编辑必须保持的不变式；symbols，诊断中提到的每个符号的 glyph_symbol 结果，所以下一次编辑不需要再调用一次。对于缺少分支的 match，这意味着联合类型的各个变体及其负载会随着要求它们的错误一起到达，同时附上一句说明：使用 else 分支就会放弃这条诊断所要保护的保证。修复方式完全确定时，glyph fix 会直接写入，并说明它拒绝做了哪些修改。这里有一份带真实输出的完整流程演练。

当前状态

现已提供

一个通过 stdio 运行的 glyph mcp [root] 服务器，提供十一个工具：glyph_symbol、glyph_impact、glyph_assignable、glyph_diagnostics、glyph_hover、glyph_definition、glyph_references（覆盖整个工作区）、glyph_variants、glyph_symbols、glyph_dependencies 和 glyph_exports。每个工具都有一个打印相同 JSON 的 glyph query 子命令。答案来自编译器自己的查询，工具不掌握的每项信息都为 null，旁边附一句 <key>_absent 说明原因。悬停信息对其他模块中声明的名字也有效，所以调用处的导入函数和从导入记录上读取的字段都有类型。实体标识能追溯到标准库：prelude 中的 Result 是 std/result::Result，也就是解析器注册它所用的模块，以及生成代码时导入它的模块，所以对它调用 glyph_symbol 会得到 Ok(T) 和 Err(E)，对 std/result 调用 glyph_exports 会列出它的接口。它背后没有 Glyph 源码，所以 path 和 range 为 null 并附上原因，而不是直接缺失。

正在进行

这些工具只读：你不能通过 MCP 重命名或应用编辑。写入能力放在命令行上，即 glyph fix。服务器每次调用都会重新扫描项目，而不是保留缓存的索引，并且会跳过任何无法解析的文件。tools/list 的回复是 20,386 字节，比原来的 45,509 字节少了，但这仍然是每个会话在连接时都要付出的上下文。

除了这些工具，智能体还可以离线阅读语言和诊断信息：llms.txt 是文字版，glyph llms --json 是来自编译器自己的表的同一份知识的数据版，glyph build --json 则是对整个目录树批量获取带错误码诊断的方式。
