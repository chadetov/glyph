支柱 04 · 打磨

稳定的 diff

改一行就是一行 diff。唯一的标准格式、尾随逗号，列表要么全部写在一行，要么每个元素一行，从不重新打包，所以审查时看到的是真正做出的改动，而不是周围的无关变动。

审查就是读 diff

我们对一个改动所信任的几乎一切（审查、blame、回退、bisect）都建立在 diff 之上。所以 diff 的信噪比才是真正的硬通货。在大多数代码库中它都很糟糕：格式化工具把一行折行重新排版，import 排序工具把一块代码打乱，一次重命名改动了每个调用处的空白，而那一行真正重要的改动被埋在五十行无关的改动里。

智能体让情况严重恶化。给它一个小任务，模型会很乐意为了改一处而重写整个函数，甚至整个文件，因为对它来说重新生成比精确编辑容易。审查者只能拿重写后的版本和原版做 diff，然后祈祷唯一真正的改动就是预期的那一处。Glyph 的设计让排版没有任何可供模型折腾的余地。

01 唯一的标准排版，没有选择

glyph fmt 用一种固定排版重新打印每个文件：两个空格缩进，每个多行列表都有尾随逗号，列表放得进 100 列时保持一行，放不下时每个元素一行。这个选择是全有或全无的。格式化工具从不为了填满一行而重新打包元素，所以列表永远不会一部分在这一行、一部分在下一行，新增一个字段就是新增一行。因为合法的形式只有一种，所以没有什么可争论的，也没有什么能让工具顺手“修正”的。

宽度阈值就是这样做的代价。给一个绑定改名，导致一个调用超过 100 列，这个调用就会展开成每个参数一行：改了一个 token，diff 却是四行。换来的是排版只取决于代码本身和它起始的列，别无其他，所以两个智能体编辑同一个文件，最终会得到相同的字节。

重新折行的风格：一处改动，三行受影响 git diff（紧凑格式） 
- type User = { id: number, name:
-   string }
+ type User = { id: number, name:
+   string, email: string }
Glyph：一处改动，新增一行 git diff（标准格式） 
  type User = {
    id: number,
    name: string,
+   email: string,
  }

尾随逗号在默默发挥作用：因为最后一个元素已经以逗号结尾，新增一个同级元素永远不会修改它上面那一行。插入一处，就是一行。

02 顺序稳定，所以历史清晰可读

每个元素一行，意味着重新排序、插入或删除一项只影响这一项所在的行，不会碰到相邻的行。git blame 保持有意义：每一行最后一次被修改的提交，就是真正修改了那个元素的提交，而不是碰巧把它所在的行重新打包的那次格式化。

03 没有 barrel 文件：没有 import 变动

因为导入从不重新导出，也没有 index.ts 这样的汇总层（E0102），新增或移动一个符号不会波及每个使用者都导入的 barrel 文件。你编辑的依赖关系就是你想改的那些；导入图的其余部分不会动。

04 代码生成是幂等的，而不是一大坨

同样的规矩也适用于生成的代码。glyph gen 和 glyph regen 会通过标准格式化工具重新打印输出，所以规范变化后重新生成，得到的是一个最小的、真正能审查的 diff，只有几行改动，而不是把机器写的文件整个替换掉。每个生成的 .ts 都附带 source map，所以即使是编译后的输出，也能清楚地追溯到你修改的那一行。

规范中新增一个字段 → 重新生成后的 diff 
  type Task = {
    id: number,
    title: string,
+   done: bool,
  }
// glyph regen re-ran the recorded command; this is the whole diff.

05 “TypeScript 用 Prettier 也能做到”

就大部分格式化而言，确实可以。设置了 trailingComma: "all" 的 Prettier 会给最后一个元素加逗号，并把长列表每个元素打印一行，这就实现了第 01 节的大部分内容。区别在三个地方。

排版只取决于代码。如果作者在 { 后面换了行，Prettier 会让对象字面量保持展开，否则就折叠，所以同一个对象可能因为最初的输入方式不同而被打印成两种样子。两个智能体写同样的东西，会得到两种排版，下一次编辑其中一个时就会表现为重新排版。glyph fmt 无论输入怎样折行，打印出来的 { a: 1, b: 2 } 都一样。

没有任何东西可以配置。Prettier 的输出取决于仓库的配置文件，而有些仓库根本没有配置文件。在不同 TypeScript 项目之间切换的智能体，在每个项目里遇到的排版都不一样。一个 Glyph 文件在每个项目中的排版都相同，因为格式化工具没有选项。

格式化工具不能改变文件的含义。glyph fmt 的测试方法是解析它自己的输出，并把语法树与输入的语法树比较，覆盖仓库中的每个示例，还在模糊测试下进行。如果一条注释所在的位置在排版中没有对应的行，它会拒绝这个文件（E0500），而不是把注释移到与之无关的代码旁边。

清单上还有一项没有完成：glyph fmt 不会对 import 排序，所以两个智能体在不同位置新增 import，仍然会产生不同的 import 块（G358）。

稳定的 diff 能把“智能体改了点东西”变成“智能体恰好改了这些”。当噪音降到零，审查就快，信任的成本也低。

它让你失去一点自由（不能按自己喜欢的方式手动排一行），换来的是大量的可读性。这是每个打磨类支柱都在做的取舍：放弃一个无关紧要的选择，保住一个重要的信号。
