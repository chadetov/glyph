支柱 01 · 切入点

可验证性

Glyph 堵上了智能体会掉进去的漏洞：没有可以写的 any 和 as，match 可证明是穷尽的，你声明的类型会得到严格的运行时校验器，这些都作为 tsc 之上的一层严格检查来强制执行。它并不自己验证一切，下文会明确说明保证在哪里止步。

类型会说的谎

在 TypeScript 中，类型是一个编译时的承诺，代码运行之前就蒸发了。User 标注会被擦除得一干二净；你从网络调用、JSON 解析或表单字段实际拿到的对象，可能是任何结构。

更糟的是，语言还给了你三种合法的方式就此向检查器撒谎：any、as 类型断言，以及非空断言 !。赶进度的智能体三种都会用，而 tsc --strict 一直是绿的，bug 就这样上线了。

Glyph 的首要任务就是堵上这些漏洞。不是靠更多的标注，而是去掉逃生口，让每个类型把它的证明一直带到运行时。下面逐条说明这意味着什么。

01 没有 any

Glyph 没有它。顶层类型是 unknown，而 unknown 是惰性的：在你证明它是什么之前，不能调用它、不能索引它，也不能把它传给任何有类型的地方。

详情 为什么一个 any 的代价这么高

any 是 TypeScript 中代价最高的关键字：它会对一个值以及这个值碰到的一切关掉类型系统。边界上的一个 any 会悄悄污染下游的整个调用图。

不经过编译器看得见的检查，你就无法从 unknown 中得到有类型的值。在 Glyph 中，收窄就是运行时证明。没有任何语法可以跳过它。

02 类型在运行时是真实存在的

User.parse 是怎么来的？因为每个记录类型，以及每个非泛型的标签联合，都会同时生成一个运行时描述符：一个 is 守卫，一个把 unknown 校验成 Result 的 parse，以及一个可组合的 schema。

你写的类型，以及由它生成的描述符 
type User = {
  id: number,
  name: string,
  email: string,
}

// generated: User.is(v), User.parse(v) -> Result<User, ...>, User.schema

fn create(req: Request) -> Result<Response, string> {
  return match User.parse(req.body) {   // untrusted input, validated
    Ok(user) => Ok(json(201, user)),
    Err(issues) => Ok(json(400, issues)),
  }
}

这就是对“每个 API 都要手写校验器”的回答。类型本身就是校验器。

详情 描述符检查什么

记录的结构在运行时会被真正检查，而不是假定，所以 is User 检查是真正的检查，而不是被擦除的空操作。

边界（请求体、配置文件、第三方响应）只有通过一个真正能拒绝错误数据的检查，才会获得类型。

它在哪里止步：记录的描述符默认是严格的。它确认声明的字段，并拒绝带有未声明键的值（在类型上加 @open 可以允许额外的键）。记录类型都有描述符，包括泛型记录，所以 Paginated<User> 会把每个元素当作 User 来检查；标签联合的描述符先检查标签，再检查该变体的负载字段。

仍然没有描述符的是泛型标签联合（Box<T> = Empty | Full({ value: T }) 没有 Box.parse），以及只是引用的 .d.ts 中导入的类型。如果某个检查只能证明结构的一部分，编译器会直接说明，而不是暗示一个它做不到的保证。

03 覆盖每种情况，否则无法编译

对封闭联合类型的 match 必须处理每个变体。以后新增一个变体，每一个没有考虑它的 match 都会停止编译（E0200）。

status.glyph 
type Status = Active | Paused | Cancelled

fn label(s: Status) -> string {
  return match s {
    Active => "on",
    Paused => "hold",
    // forgot Cancelled...
  }
}

详情 对数字与字符串的 match

新情况不会像遗漏的 switch 分支那样悄悄落到 undefined。而且不只是联合类型：对 number 或 string 按字面值匹配时必须有 else（E0218），因为这些取值范围是无界的，一组字面值永远不可能完整。

04 错误是值，不是意外

可能失败的函数返回 Result<T, E>。你用 match 处理它，或者用 ? 运算符向上传递，而且错误类型必须对得上（没有隐式转换来掩盖不匹配）。

pipeline.glyph 
fn load(id: string) -> Result<User, AppError> {
  let raw = fetch_user(id)?           // Err short-circuits to the caller
  let user = User.parse(raw.body)?    // validation Err propagates too
  return Ok(user)
}

fn main() -> number {
  save(user)   // E0217: this returns a Result whose Err is dropped
  return 0
}

如果完全忽略一个 Result（只为了副作用调用它，丢掉返回值），Glyph 会给出警告（E0217），因为被丢弃的错误就是被吞掉的失败。你只能用 let _ = ... 有意地让它安静，绝不会是无意的。

05 连 PII 也在类型层面处理

同样是“交给编译器，而不是靠约定”的思路，一直延伸到敏感数据。在类型上加 @redact，它的描述符就会多一个屏蔽这些字段的 redact()，所以随手写的 json.stringify(User.redact(u)) 不会泄露它们。

patient.glyph 
@redact fields: [diagnosis, notes]
type Patient = {
  name: string,
  diagnosis: string,
  notes: string,
}

// json.stringify(Patient.redact(p)) ->
// {"name":"Ada","diagnosis":"[REDACTED]","notes":"[REDACTED]"}

如果写了类型中不存在的字段，就是编译错误（E0219），而不是一个悄悄什么都没保护的屏蔽。

五种不同的失败方式（未检查的输入、漏掉的情况、丢掉的错误、泄露的机密、未校验的键），每一种的修复都是同一个形状：编译器拒绝假装。

如何强制执行，以及保证在哪里止步

这里要说得准确，因为区别很重要：Glyph 是建立在 tsc 之上、强制执行的严格方言，而不是一个独立的验证器。

  • 由 Glyph 证明有些东西它自己证明：穷尽性、? 的错误类型、源码中不存在 any/as、严格的键校验。
  • 通过 tsc 强制执行其余的类型兼容性，它通过生成 TypeScript 并运行 tsc --strict 来强制执行，不通过就让构建失败。

切入点在于这些检查就是语言本身，而不是智能体可以关掉的可选 lint，并不在于 Glyph 重新实现了一个类型检查器。

历史 0.1.10 中堵上的边界，泛型的深度校验

这里早先的两个边界在 0.1.10 中已经堵上。代码生成器过去会在每个泛型函数中插入一个由 Glyph 而不是 tsc 检查的返回值类型断言；现在只有在校验器组合子组装一个由结构推导出的类型（infer_output<Shape>）的值时才会插入，所有正常的泛型生成的代码都完全没有类型断言。另外，校验器的输出类型不再被无条件信任：infer_output 根据你传入的结构推导它，tsc 会拿你的标注去对照：如果结构缺少你所声称类型中的某个字段，现在就无法编译。

泛型类型现在也会深度校验：Paginated<User> 的描述符会把每个元素当作 User 来检查，而不只是检查是否存在。

还剩一个边界，直接说明：从外部 .d.ts 导入、你只是引用的类型，在你用 glyph gen dts 把它具体化之前没有描述符，所以这种类型的字段只检查是否存在，不检查结构。这个边界是有意的（Glyph 没有生成的类型无法承诺运行时校验），把它具体化就能堵上。

“严格模式的 TypeScript 加一套 lint 配置也能做到”

在程序内部，它们很接近。strict、noUncheckedIndexedAccess 和一条禁止显式 any 的规则，能拦住智能体原本会溜过去的大部分问题。它们在边界处止步。

  • 在边界处JSON.parse(body) as User 在任何设置下都能编译，而通常的修补办法 zod schema，是 User 的第二份描述，必须手动与第一份保持同步。在 Glyph 中，类型本身就是校验器：json.parse<User>(body) 直接对照 User 检查，而 Glyph 无法在运行时检查的类型会被拒绝，而不是被信任。
  • 跨仓库另一个区别在于谁能依赖它。lint 配置是某个仓库自己做的选择。打开一个陌生 TypeScript 代码库的智能体，不能假定那里禁止了 any；而在 Glyph 中，任何地方都写不出它。
