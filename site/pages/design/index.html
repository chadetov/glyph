Design

Four pillars, and a decision record for every rule

Every rule in Glyph is tested against four properties, and each rule is a numbered decision in the spec with the pillar it serves. The pillars are properties of the language rather than of a project's configuration, so an agent opening an unfamiliar Glyph codebase can rely on them without first finding out which settings it chose.

The pillars

In order of what matters most. The first two are the wedge, the problems you feel every day. The last two are the polish that makes it pleasant. When they conflict, the wedge wins.

Pillar 01Verifiability

No any and no as you can write; match must cover every case; and your record and union types generate strict runtime validators, so a boundary value is checked, not assumed. A strict layer over tsc that can't be switched off: the mistakes an agent ships that tsc --strict waves through don't compile here.

 Pillar 02Greppability

One name, one place. Every symbol has exactly one syntactic form at its declaration, with no overloads, decorators, implicit this, or namespace merging. grep "fn parseUser" finds the definition.

 Pillar 03Diff stability

A one-line change is a one-line diff. One canonical layout: a list is inline while it fits and one element per line when it doesn't, never repacked, with trailing commas, no barrel files and no options, so the same code prints the same way in every project. Reviewers read the change, not the churn.

 Pillar 04Abstraction

Say what you mean: pattern matching over switch ladders, Result over thrown exceptions, named records over tuples, from a small orthogonal core rather than TypeScript's accreted layers.

The spec is a list of decisions

docs/language/spec.md holds 49 numbered decisions, D1 to D49, each ending with the pillar it serves. The grammar follows the spec: an ambiguity is resolved there first, then encoded in the parser. glyph llms --json parses the list out of the spec, so an agent reads the same decisions you do. One of them, shortened:

D9, from docs/language/spec.md (shortened) 
D9. `else` is a catch-all arm; `_` is a position-level wildcard;
a PascalCase arm head is a variant reference, not a binding.

... a PascalCase head that names no variant of that union is a
compile error (E0220, with a nearest-variant suggestion), never a
silent catch-all that would mask a missing variant (E0200) and
misroute values at runtime. ...

*[verifiability, abstraction]*

What it deliberately leaves out

The manifesto states the stance, and the short version is that each restriction earns its place against a pillar. Glyph has no if/else (match is the only conditional), no classes, no overloads or decorators, no casts, no any, no relative imports and no formatter options. It is also not configurable: one formatter, one module resolution, one strictness level. Annoying restrictions get documentation, not a looser rule.

Module visibility, interfaces, defer, the standard library, and the edges it still has.

The bet behind all of it, stated as a hypothesis rather than a result: an agent given the same task produces correct code more reliably in Glyph than in TypeScript, and the reviewer spends less time confirming it. That study has not been run, so this site puts no number on it. Benchmarks says what is measured so far.
