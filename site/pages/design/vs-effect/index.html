Design · Comparison

Glyph and Effect

Both aim at TypeScript that people and agents can rely on. Effect is a library: you keep writing TypeScript and get typed errors, tracked dependencies and a large toolbox. Glyph is a language that compiles to TypeScript, so it can refuse what TypeScript allows, including the casts that undo a library's guarantees. Effect is far more mature.

How Effect describes itself

Effect's home page leads with "Reliable TypeScript for the AI era" and says its "declarative patterns and strong type system make it easier for LLMs to generate correct, production-ready code" (effect.website). Its docs call it "an ecosystem of tools that help you build better applications and libraries", built around an Effect<Success, Error, Requirements> type that records what a computation returns, how it can fail, and what it needs (Why Effect). It asks for TypeScript 5.4 or newer with strict on (Installation). These quotes were read on 2026-11-19.

The difference that follows from library versus language

Effect's types are checked by tsc, so everything tsc allows is still allowed next to them. This compiles under tsc --strict with effect 4.1.4 and TypeScript 6. The cast removes NotFound from the error channel, and the program reports a failure from an effect typed as unable to fail.

eff.ts: tsc --strict exits 0; running it prints "Failure undefined" 
import { Effect } from "effect"

class NotFound {
  readonly _tag = "NotFound"
}

const find = (id: string): Effect.Effect<number, NotFound> =>
  id === "1" ? Effect.succeed(1) : Effect.fail(new NotFound())

// The error channel says NotFound can happen. A cast erases it.
const quiet = find("2") as unknown as Effect.Effect<number, never>

// And a parsed body still takes any type you name.
type User = { email: string }
const user = JSON.parse("{}") as User

console.log(Effect.runSyncExit(quiet)._tag, user.email)

The same function in Glyph returns a Result, and there is no cast to write. The second module is refused before any TypeScript is emitted.

find.glyph: builds, passes tsc --strict 
module find

pub type NotFound = { id: string }

pub fn find(id: string) -> Result<number, NotFound> {
  return match id == "1" {
    true => Ok(1),
    false => Err({ id: id }),
  }
}
adding a cast: refused 
module find

pub type NotFound = { id: string }

pub fn find(id: string) -> Result<number, NotFound> {
  return match id == "1" {
    true => Ok(1),
    false => Err({ id: id }),
  }
}

pub fn quiet() -> number {
  let n = find("2") as number
  return n
}

E0013's help reads: "Glyph has no as cast ... to turn an unknown into a type, validate it with T.parse(v) or narrow it with match and is." A team can get close to this in an Effect codebase with lint rules, and that comparison covers why a rule someone can turn off is a different guarantee.

What Glyph does that a library can't

A language decides what can be written. Glyph has no any, no cast, no non-null assertion and no comment that silences an error, and every match over a union has to cover every case. Records and unions carry a runtime check generated from the declaration, so json.parse<User>(body) validates. Effect's Schema also derives a type from one description (Schema.Schema.Type<typeof Person> in its introduction), so the type and the validator don't drift there either; what differs is that nothing in TypeScript makes a codebase use it. The compiler also answers questions about a program for an agent, such as what a change will break, over MCP or the command line.

This page has not tested using Effect from inside a Glyph module, so it makes no claim about combining the two.
