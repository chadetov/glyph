Design · Comparison

Why not ReScript, Gleam or Elm?

All three are typed languages that compile to JavaScript, and all three are older, more widely used and more settled than Glyph. If you are choosing a language for a new codebase and don't need to stay close to TypeScript, they deserve a look first. Glyph's differences are narrower: it emits TypeScript source rather than JavaScript, it imports npm packages typed from their own .d.ts, it generates runtime validators from your types, and its compiler answers impact queries for an agent.

How each describes itself

ReScript's home page leads with "JavaScript Made Simple for Humans and AI" and "Types > Vibes", and says it "compiles to clean, efficient JavaScript" with "No any, no magic types, no surprise undefined." It offers to "automatically generate TypeScript types" (rescript-lang.org).

Gleam's home page calls it "a friendly language for building type-safe systems that scale" with "No null values, no exceptions, clear error messages". It runs on the Erlang VM and "can additionally compile to JavaScript", and "also generates TypeScript definitions" (gleam.run).

Elm's home page describes "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions", for "reliable web applications", and says Elm "detects all API changes automatically" to "guarantee that every single Elm package follows semantic versioning" (elm-lang.org).

These quotes were read on 2026-11-19.

What Glyph does differently

Each of these was run on Glyph 0.1.149 for this page.

It emits TypeScript source

glyph build writes one .ts file per module, which tsc --strict then checks, and which you keep if you stop using Glyph. ReScript and Gleam emit JavaScript and generate type definitions next to it. The emitted TypeScript is shown on the TypeScript page.

It imports npm packages typed from their own declarations

A module imports a package by name, and the package's .d.ts types every use. There is no binding to write first. In ReScript, "external is the primary ReScript feature for bringing in and using JavaScript values" (external), with the types declared on the ReScript side. Gleam's externals need type annotations, and the compiler "cannot verify that the function implemented in the other language returns the specified types" (externals). Elm talks to JavaScript through flags, ports and custom elements (interop). With pg and @types/pg installed, this is refused:

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

The code is TS2322 because tsc is what checks a library's values, mapped back onto the Glyph line. Glyph's own checker does not see them, so glyph check --no-tsc, the editor and the MCP tools miss this error (G257). A type imported from a .d.ts also has no runtime check.

It generates the validator from the type

Every record and union carries a runtime check generated from its declaration, so json.parse<User> returns Err when the data does not match. In Elm you write a decoder for each shape, and its guide notes that "the decoders people write end up working as a validation phase" (JSON).

main.glyph: prints "refused", because the JSON has no email 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

Its compiler answers what a change will break

Before an edit, an agent can ask which places a change reaches, over MCP (glyph_impact) or with glyph query impact. On a union Plan = Free | Pro | Team with one exhaustive match and one that ends in else, asking about a new variant answers per site:

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

The second site would fail to compile after the change, which any of these compilers would also tell you once the change is made. The first would keep compiling and send the new case to its else, and the query is what names it. For agent builders lists the other tools.

What this page does not claim

It has not compared error messages, compile speed or runtime performance, and it has not tried calling any of the three from Glyph or the other way round. The quotes describe each project in its own words; how well each lives up to them is for you to check, as it is for Glyph's own claims on the evidence page.
