Who maintains it

Who maintains Glyph, and what happens if they stop

One person maintains Glyph today: the project lead, who handles the language design, the compiler and the releases. If the project stopped, the TypeScript your builds emitted would keep compiling with tsc and no Glyph dependency, and the MIT or Apache-2.0 licence lets anyone fork it.

That table is MAINTAINERS.md, and this page says what it and the other project documents commit to. Maintainers review and merge pull requests, triage issues, shepherd RFCs, cut releases and uphold the Code of Conduct.

The bus factor

The bus factor is one. Growing the maintainer list is a stated goal, but it has not happened yet. Three things limit what a stalled project would cost you:

  • The output is yours. glyph build writes plain TypeScript that passes tsc --strict, and you commit it. Without Glyph, your code keeps building with tsc.
  • The licence is MIT or Apache-2.0, at your option, so anyone can fork the compiler and continue it.
  • glyph init pins the compiler to an exact version, and published npm versions are never yanked, so a build you have today keeps the compiler it was tested with.

If the lead steps away

GOVERNANCE.md treats the repository, the glyphlang.io domain and the npm org as project assets rather than personal ones. Today one maintainer holds access to all three, and adding a second maintainer with access is the first step of the succession plan. Once there is more than one maintainer, the others choose a new lead by majority vote if the lead becomes unavailable. Until then, continuity rests on the emitted TypeScript, the licence, and the fact that published npm versions are never removed.

Maintainers are added by invitation from the existing ones, on a record of good contributions and reviews and agreement with the project's direction. There is no quota. If you have been contributing and want to help maintain it, open a thread in Discussions.

How decisions are made

The model is a project lead with the final say on language design and direction, and review, triage and merging shared among the maintainers. The stated intent is to move toward a steering council as the contributor base grows.

  • Bug fixes, docs, diagnostics, examples and tooling go through ordinary pull-request review. Three CI checks must pass before anything merges: version consistency, the test suite with the examples type-checked, and the site's links, HTML and sub-nav. GitHub does not let an author approve their own pull request, so on a one-maintainer repository a required review would mean either nothing merges or an admin bypasses it. Reviews are not required for that reason, and that is the first setting to revisit when a second maintainer arrives.
  • A change to the language's syntax or semantics goes through the RFC process: a written proposal, public discussion, and a maintainer decision recorded on the RFC. The four pillars are the criteria, and "the constraint is the point" is a valid reason to decline. A proposal that reopens the abandoned, annotation-heavy direction starts from a presumption of no.
  • When maintainers disagree, the proposal stays open for at least a week so every objection is answered in writing. If there is still no consensus, the lead decides and records the reasoning on the issue or RFC. A contested language change defaults to not shipping, because reversing a released syntax decision is expensive.
  • A change to the governance document is itself an RFC, and its history is in the repository.

Reporting a security issue

Report it privately, through a private security advisory on the repository, or by email to security@glyphlang.io with a description, the affected version and a reproducer if you have one. Please don't open a public issue until it has been triaged and a fix is available.

SECURITY.md promises an acknowledgement within a few days, an assessment of severity and affected versions, a fix released as promptly as the severity warrants and named in the release notes, and credit in the advisory unless you would rather stay anonymous.

In scope: the compiler and CLI (@glyphlang/glyph and its platform packages), the bundled standard-library runtime, glyph gen, and any way Glyph could emit unsafe TypeScript or run untrusted input during a build. Out of scope: vulnerabilities in npm packages you install yourself, which go upstream, and issues that need an already compromised developer machine. Published npm packages carry provenance attestations, and CI fails when the Cargo version and the npm package versions disagree.

Release cadence

Releases are cut when work lands, not on a calendar, and the 0.1.x line moves quickly. A minor bump (0.2.0, 0.3.0) marks a milestone reached, not a date. Every release is a v* git tag that triggers the publish workflow, so the npm version and the tagged source always match. A release is marked Breaking when it rejects a program the previous version accepted; the teams page says what that has meant in practice, and the release notes list every version.

Deprecation policy

When a construct or a standard-library name is going away:

  1. A release marks it deprecated with a warning that names the replacement, and the release notes say so.
  2. It keeps working for at least one more 0.1.x release after the warning first appears, so an upgrade never breaks and forces a fix in the same step.
  3. Where the migration is mechanical, glyph fmt or a codemod does the rewrite.

The policy covers names being removed. It does not cover new diagnostics: before 1.0 a release may reject code that compiled before, with no deprecation window, because catching a latent bug is usually the point of the change. After 1.0 the windows lengthen, and a breaking language change needs a major version. docs/stability.md has the full pre-1.0 policy.

Who uses it

No company or production deployment is documented, and there are no case studies yet. Two applications by authors with no connection to the project have been read and recorded in the repository: glyph-hello, a tic-tac-toe game whose engine, HTTP server and terminal client are Glyph, and glyph-kanban, a React Kanban board whose domain core is 292 lines of Glyph imported by hand-written TSX under Vite. What each one found is in the gap log.
