--- version: 0.1.139 month: 2026-11 tags: breaking ---

Reading a member off an Option or a Result is now checked. An Option has no members, and a Result has two, map and map_err. Anything else is E0210, and the message says which members exist:

type `Result<Note, string>` has no field `value`: a `Result`'s only members are `map` and `map_err`

Before, r.value, r.tag and o.tag passed glyph check and the full build, because they are how the emitted TypeScript stores the value and tsc could see them. They are not part of the language: reading r.value on an Err gives you the error where you expected the success value, and nothing warns you. Open the value with match, or bind a Result with ? first and read the field after:

note.glyph 
let note = load()?
return Ok(note.name)

A misspelled method gets a suggestion (r.mapp(f) points at map). .map_err(f)?, the most common way to use a Result, is unchanged.

The check needs to know the value is an Option or a Result. A value built with Ok(x) or Some(x) and never annotated is not typed that way yet, so let r = Ok(x) followed by r.value still passes, and so does r["value"]. Both are on the list.

Breaking

We ran the published 0.1.137 and this build on the same programs. o.tag, r.tag and r.value passed glyph check with tsc and now fail. Other reads, such as o.name or r.unwrap(), were already refused by tsc in a full check and are now also caught under --no-tsc, in the editor and over MCP. On every .glyph file in the repository except the two test files added to be refused, and on all 32 example apps, glyph check gives the same result as before, and the emitted TypeScript is identical.
