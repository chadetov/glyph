--- version: 0.1.152 month: 2026-11 date: 2026-11-20 tags: breaking headline: A null in an optional field is refused, and the error names the type that accepts it ---

An optional field f?: T now means an absent key or a T. A key holding null is refused unless T is Nullable, and so is a key holding undefined from host code.

Before this release a null there passed the check and stayed in the value, while the type said number. With type Opts = { timeout_ms?: number }, decoding {"timeout_ms": null} succeeded, { timeout_ms: 5000, ...opts } overwrote the default with null, and cfg.timeout_ms * 2 came out as 0. An Option field holding null decoded and then crashed in the first match. Now the decode fails at the field:

[{"path":["timeout_ms"],"message":"field `timeout_ms` is null; declare it `timeout_ms?: Nullable<number>` to accept null","code":"type"}]

The suggested type always compiles. It follows aliases, so a field typed MaybeInt with type MaybeInt = Option<int> is told Nullable<int>, not the Nullable<MaybeInt> that Glyph would refuse. Where no spelling would work, the message says so instead of guessing. A test compiles every suggestion the suite produces.

Every way of checking a value gives the same answer: json.parse<T>, T.parse, T.is, an is T pattern, T.schema and json.parse_with, at any depth, in arrays, maps, generics and union payloads. To accept null, declare the field f?: Nullable<T>.

This reverses the 0.1.68 rule that read a null in an optional field as absence. Both reasons for it are gone: no generator writes a ? field expecting null any more, and Nullable is the spelling for "absent, null or a value".

Breaking

At run time only. json.parse<Opts>("{\"timeout_ms\": null}") is Ok in 0.1.151 and an Err at ["timeout_ms"] here, and is answers false on the same input. glyph check gives the same exit code on every program. No file in the repository, none of the 32 example apps and neither outside app we test against decodes a null into an optional field.
