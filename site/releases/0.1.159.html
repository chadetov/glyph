--- version: 0.1.159 month: 2026-11 date: 2026-11-21 tags: breaking headline: An async callback passed where nothing will wait for it is an error ---

ids.forEach(async fn(id) { await save(id) }) used to compile. forEach does not wait for its callback, so every save ran on its own, the function returned before any of them finished, and a failure in one was lost. The same held for timers.every, a socket handler, or any parameter declared fn(...) -> void. Now an async function given where a sync void callback is declared is E0211:

[E0211] `forEach` calls its callback without waiting, so each call of this `async fn` runs on its own and its errors are lost
Help: Await each call in order, so the code after it runs once they are done and a failure reaches you: `for id in ids { await save(id) }`.

The help is worked out from the program. Inside an async function, a forEach becomes a for loop that awaits each call. Inside a sync function, the help says the function cannot wait, and offers to make it async or to start each call on purpose with task.detach. map, filter and find with an async callback get a help naming the call and the array to loop over. The array methods read the same callback slot that 0.1.158 uses to type a lambda's parameters, so the parameter in the suggested loop has the type you'd expect.

The other direction is covered too. A sync function given where an async one is declared, such as task.detach(tick) with a plain fn tick(), is E0211 before tsc runs, and the help writes the async wrapper for you. Each mistake gets one diagnostic. An async callback inside "${array.map(...)}" no longer also draws a text-conversion error for the array of promises it would have produced. An unrelated error on the same line is still reported.

The same pairing at a let, a return, a record field or a component prop is refused too, but with the general message rather than one that names the callee (G421).

Breaking

A program that passes an async function to a sync void callback, binds one to a fn(...) -> void, gives a sync function where an async one is declared, or gives array.map an async lambda now fails to compile (0.1.158 exits 0, 0.1.159 exits 1). No tracked example app is affected: across the corpus the only new diagnostic is on the catch case for this mistake.
