--- version: 0.1.165 month: 2026-11 date: 2026-11-22 tags: breaking headline: A literal can only name fields its type declares ---

With type Opt = { name: string, nick?: string, }, writing { name: "a", nik: "b", } where an Opt is expected passed Glyph's own checker. The misspelled optional field was silently dropped. Only tsc caught it, so the editor, the MCP tools and the applyEdit gate let it through. Now a key that the declared record does not have is E0210, underlined at the key:

[E0210] type `Opt` has no field `nik`; did you mean `nick`?

It is checked wherever a literal is written for a declared type: a let or const with an annotation, a return, a call argument, a variant payload, a mut assignment, nested fields, array elements, the arms of a match in one of those places, a lambda's return where its type is declared, a JSX component attribute, and inside Some(...), Ok(...) and Err(...). That last group goes beyond tsc, which lets an extra field through there. Values written in those last positions are compared too, so Some({ name: 4, }) under Option<Opt> is refused. Fields that come from a spread, a variable holding a wider record, and Record<K, V> are not judged.

glyph fix renames a key that is one letter away from a declared field, unless the literal already has that field.

A safer glyph fix inside templates

An escape inside a ${}, as in "a${f(\"x\") + b.nik}", still shifts positions after it. Review of this release showed a fix could land on the wrong copy of identical text there, so every fix rule now declines in that region, using the lexer's record of where the escapes are. 0.1.168 makes those escapes a parse error.

Breaking

Yes. A literal with an undeclared key now fails check --no-tsc, and under full check too inside Some, Ok and Err: let f: Option<Opt> = Some({ name: "x", extra: 6, }) exits 0 under 0.1.164 and 1 under 0.1.165. Across 383 tracked programs, nothing else changed.
