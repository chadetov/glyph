--- version: 0.1.166 month: 2026-11 date: 2026-11-22 tags: breaking headline: An unannotated const has the type of its value ---

Glyph's own checker gave a module const with no annotation no type at all. So const ITEMS = [1, 2] followed by ITEMS.push(3) slipped past the mut rule, let x: string = CFG.n on const CFG = { n: 1, } passed, and a store.create(0) held in a const was invisible to the checks 0.1.163 added. Only tsc caught any of it, so the editor, the MCP tools and the applyEdit gate let it through.

Now an unannotated const has the type tsc gives it. A string literal that is the whole value keeps its literal type, so const MODE = "read" still passes where a "read" | "write" is declared. Literals inside an object or array widen, so CFG is { n: number } and ITEMS is Array<number>. A value the checker cannot type stays untyped. An imported pub const gets the same type whether it is imported by name or through a namespace, and hover and the MCP tools report it.

That makes ITEMS.push(3) E0240, the field reads above E0204, and a Set, Store or Deque held in a const is judged the way it is in a let. A const holding a wider record is still accepted where a narrower one is declared, as with any value read by name; only a fresh literal gets 0.1.165's extra-field error.

Comparisons with == against such a const keep the same emitted code as before. Emitting === there would have exposed TypeScript's literal types and made tsc refuse comparisons Glyph accepts.

Breaking

Yes, under full check as well as --no-tsc. ITEMS.push(3) on an unannotated const exits 0 under 0.1.165 and 1 under 0.1.166, and so does FOUND ?? 0 with const FOUND = array.find(...), which 0.1.162's rule now reaches. The other new refusals are ones tsc already made. Across 285 tracked programs, no diagnostic changed; one comparison in an example app now emits === on a value typed number.
