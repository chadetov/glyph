--- version: 0.1.169 month: 2026-11 date: 2026-11-23 tags: breaking headline: An escape inside the ${} of a "..." string is a parse error ---

A nested string literal inside the ${} of a "..." string could only be written with escapes, as in "a${f(\"x\")}". That spelling existed to get around the rule that says to bind such a value with let first. It also left every position after the escape a few bytes early, so 0.1.165 had to stop glyph fix from touching anything there.

Now a backslash inside the ${} of a "..." string is E0002, pointing at the escape, and the help is written from your code:

[E0002] `\"` is an escape inside the `${}` of a `"..."` string, which Glyph does not allow
Help: ... Bind the value with `let` and interpolate the name: `let label = x + "é"`, then `"a${label}"`. Or write the whole string as `"""a${x + "é"}"""`, which reads a string literal inside `${}` as written.

Triple-quoted strings are unchanged, and so is an escape outside the ${}, such as "a\n${x}" or "\${x}". When the text around the ${} holds an escape, the help names the """ form only in words, since a """ string would not decode it.

Two related changes. glyph fmt no longer rewrites a one-line """ template into the "..." spelling; it used to turn valid code into the form this release refuses. And with that region gone, the guard that stopped glyph fix after an escape is removed, so a rename inside a """ interpolation that holds an escape now applies instead of being declined.

Breaking

Yes, under full check as well as --no-tsc: "a${f(\"x\")}" exits 0 under 0.1.168 and 1 under 0.1.169. No tracked program had such an escape, so nothing in the corpus changed.
