--- version: 0.1.176 month: 2026-11 date: 2026-11-24 tags: breaking headline: An unknown value is refused where another type is declared ---

Glyph's checker never refused a value of type unknown. With u: unknown, let s: string = u passed check --no-tsc and the agent gate, and only tsc caught it. That is the most common way unchecked data reaches typed code: a json.parse result handed on without being validated.

Now an unknown stands only where unknown is declared. Anywhere the checker knows the declared type, it is E0204 at a let, const, return or record field, and E0211 at an argument. The check reaches inside containers and function types, so [u] as an Array<string> and a fn(number) -> unknown where fn(number) -> string is declared are refused too. A generic wrapper that returns json.parse(s) as Result<T, ...> is caught by Glyph itself now. The help says how to check the value first: T.parse(value), json.parse<T>(text), or an is arm in a match.

Some things stay accepted: string.from(u), User.is(u) and User.parse(u), u inside a Record<string, unknown>, and anything whose declared type the checker does not decide, such as an extern_ts or package type. Some(u) where Option<string> is declared still passes; that is G436.

is T on a type parameter

A type parameter has no runtime check, so is Doc inside fn h<Doc> was always refused with E0304, but only once everything else typechecked. With this release that would have shown up as a misleading type mismatch first. The checker now reports E0304 itself, at the pattern, for every such pattern in the file in one run.

Breaking

Yes. let u: unknown = get() followed by let s: string = u exits 0 under 0.1.175's check --no-tsc and 1 under 0.1.176. Every new refusal is one tsc already makes. Across 376 tracked programs the output is byte-identical to 0.1.174.
