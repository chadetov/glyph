--- version: 0.1.177 month: 2026-11 date: 2026-11-24 tags: breaking headline: A sort of numbers needs a comparator ---

JavaScript's sort() with no comparator compares elements as strings, so [100, 9, 25].sort() gives [100, 25, 9]. tsc accepts it and so did Glyph. It is one of the easiest bugs for an agent to write and one of the hardest to spot in review, because the call looks right.

Now sort() and toSorted() with no comparator are E0243 unless the elements are text: a string, a string-literal union, a refined string, or an alias of one. Numbers, int, bigint, records, unions, Option and an unbounded type parameter are all refused. A generic T: string sorts as text; T: Named is refused. array.sort already required a comparator and is unchanged.

The help writes the comparator for you in the form you used: mut xs.sort(fn(a: number, b: number) -> number { return a - b }) for numbers, the same with int, and a named cmp with its type for anything else. For toSorted it suggests array.sort(xs, ...), because the TypeScript target Glyph emits (es2022) has no toSorted and tsc refuses it.

E0240, which asks for mut on a sort in place, now suggests the comparator form too, and glyph fix no longer adds the mut on its own there, since that would leave a sort E0243 refuses.

Glyph's checker still types a bigint as number. That is G500.

Breaking

Yes. mut scores.sort() on [100, 9, 25] exits 0 under 0.1.176 with check --no-tsc and with full check, and 1 under 0.1.177. Across 286 tracked programs the only change is the catch case written to show this bug, which is now refused.
