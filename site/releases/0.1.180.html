--- version: 0.1.180 month: 2026-11 date: 2026-11-24 tags: breaking headline: A lost update across an await is caught on elements and map entries too ---

E0225 catches a read of a parameter's field before an await and a write to it after: whatever another task wrote in between is lost. Until now it only looked at fields, so a.balance was caught and c[0] was not.

It now covers elements and map entries: c[0], m["k"], a[0].balance and c[i]. An index counts when its key cannot change between the read and the write, which means a literal, or a name no mut reassigns anywhere in the function. A read written array.get(c, 0) or record.get(m, "k") counts as a read of that element, and the message says so: (read through `array.get(c, 0)`). That matters for maps, where Glyph refuses the bare m[k] read.

A key that can change (c[i + 1], or a name some mut reassigns), a local array, a push, and a re-read after the await are all left alone. Async lambdas are still not checked (G517). The rule also fires when the value written was read again after the await, which cannot lose an update; that was already true for fields and is G516, scheduled next in the rolling lane.

Breaking

Yes. Reading c[0], awaiting, then writing mut c[0] = ... exits 0 under 0.1.179 and 1 under 0.1.180. tsc says nothing about any of these; this check is Glyph's own. Across the 375 programs the corpus script measures, the only change is the catch case written to show this bug, which is now a refused case.
