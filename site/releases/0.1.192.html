--- version: 0.1.192 month: 2026-11 date: 2026-11-26 tags: breaking headline: E0225 looks inside async lambdas ---

E0225 catches a lost update across an await: a place is read, the code waits, and the place is written with something computed from the old value. The check visited only top-level async fn declarations. The same pattern inside an async fn() { ... } lambda passed silently. That includes an event handler written in a JSX attribute, or a callback held in a const. That was the case the rule exists for, since a lambda's captured state is shared by every run of it.

Now every async lambda is checked, at any depth. Inside one, a place counts if it is rooted at the lambda's own parameters or at anything it captures from an enclosing scope, a parameter or a local. A captured local counts because the lambda can run several times at once and every run shares it. A binding the lambda declares for itself does not count. The rule is 0.1.191's: E0225 fires only when a value read before the await reaches the write.

Breaking

Yes. A lambda that reads c[0], awaits, then writes c[0] from that read exits 0 under 0.1.191's check --no-tsc and full check, and 1 under 0.1.192. tsc reports nothing on it. Across the 376 programs the corpus script measures, the output is identical to 0.1.191.
