--- version: 0.1.194 month: 2026-11 date: 2026-11-26 tags: breaking headline: array.concat takes one element type, in both spellings ---

array.concat was declared as fn(Array<T>, Array<U>) -> Array<T>, so its second argument could hold anything. return array.concat([1, 2], ["a"]) from a function declared -> Array<number> passed check --no-tsc, and only tsc refused it. The method form was not checked at all: xs.concat(["a"]), xs.concat("a") and xs.concat([[1]]) on an Array<number> all passed (G521).

Now both arrays share one element type, fn(Array<T>, Array<T>) -> Array<T>, and the cases above are E0211 at the argument that does not fit. The method form accepts an element or an array of elements, so xs.concat(4) and xs.concat([4]) still pass. glyph llms --json publishes the new signature.

Fixing this also removed an older false refusal. A generic function given two different literals, such as pair("a", "b") under fn pair<T>(a: T, b: T) -> T, was refused with "expected "a", found "b"". tsc reads T as "a" | "b", and Glyph now does too. One neighbour of that case is still refused: a declared union followed by a literal it does not hold, pair(m, "c") with m: Mode. tsc accepts that one, so it is filed as G648 and scheduled as the first fix after this batch.

Breaking

Yes. The array.concat([1, 2], ["a"]) program exits 0 under 0.1.193's check --no-tsc and 1 under 0.1.194, and tsc already refused it on a full check. Across the 376 programs the corpus script measures, no exit code changed. One error message got more specific, naming Array<"a" | "b"> where it printed Array<?>.
