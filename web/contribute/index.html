How the compiler is built, and how to help

The compiler is a Rust workspace of twelve crates in one public repository, licensed MIT or Apache-2.0. Bug reports with a small reproduction help most today. A change to the language starts as an issue, because every rule traces to a numbered design decision.

The pipeline#

glyph build lexes, parses, resolves names, type-checks and emits TypeScript, then runs tsc --strict on what it wrote. The middle stages run as incremental queries on salsa, so a re-check reuses the results an edit did not invalidate.

one .glyph file, through the crates 
glyph-lexer → glyph-parser → glyph-resolver → glyph-typechecker → glyph-emit → tsc --strict
                (glyph-ast)        └──────── glyph-db (salsa) ────────┘
CrateWhat it does
glyph-lexerTokens, keywords, significant newlines, template literals
glyph-astSyntax tree types, with a source span on every node
glyph-parserPratt parser for every decision in the spec, JSX included
glyph-resolverName resolution, the module graph, cross-module import checks, the prelude
glyph-dbThe salsa query pipeline and cross-file invalidation
glyph-typecheckerExhaustiveness, ?, generics, owned, runtime descriptors, the stdlib model
glyph-emitThe TypeScript writer, descriptor generation, expression-level source maps
glyph-formatterglyph fmt: one layout, comment-preserving, idempotent
glyph-lspThe language server and the MCP server, sharing one analysis layer
glyph-cliThe glyph binary and every subcommand
glyph-wasmThe compiler in WebAssembly, which runs the playground
glyph-runtimeA stub; tests run through the emitter and tsx instead

glyph-compiler/README.md has the full crate notes and the current test count.

Build and test#

Rust 1.95 is pinned in rust-toolchain.toml. Some tests shell out to tsc and tsx, so install those too. CI runs clippy with warnings as errors, and neither cargo build nor cargo test runs it, so run the script before you push.

from a clone 
npm install -g tsx typescript
cd glyph-compiler
cargo build --release -p glyph-cli      # target/release/glyph
cargo test --workspace
cd .. && python3 scripts/check_clippy.py  # the exact clippy command CI runs

# after an intentional syntax-tree change
INSTA_UPDATE=always cargo test -p glyph-parser --test snapshots

A new diagnostic comes with a program under tests/negative/ that must fail with that code. A claim that Glyph catches something TypeScript misses goes in catches/, where a gate runs both halves.

What is planned, and what is broken#

docs/roadmap/releases.md is the release roadmap: what each shipped release did and what the next ones are for. docs/dogfooding-gaps.md is the gap ledger, every limitation found by building real apps, each numbered (G plus a number) with a status marker. An open gap with a reproduction is a good place to start.

Issues and pull requests#

Toolchain fixes, diagnostics, docs and examples can go straight to a pull request. A change to syntax or semantics starts with an issue, and larger ones go through the RFC process in docs/rfcs/; a PR that relaxes a rule "to be helpful" will probably be declined, because the restriction is the point. Keep a pull request to one gap, usually one to three commits, and sign each commit (git commit -s). main is protected and merges are rebase-only. CONTRIBUTING.md has the full rules, and issues labelled good first issue are scoped for a first change.
