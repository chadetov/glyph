Warum das wichtig ist

Glyph kompiliert zu TypeScript und prüft die Ausgabe dann mit tsc --strict, also geht ein Fehler, den Glyph nicht modelliert, nicht verloren. Er kommt eine Stufe später zurück, formuliert in Bezug auf die erzeugte Datei: ein TS1308, das auf ein await in einer Funktion zeigt, die du nie geschrieben hast, oder ein TS2366 über einen switch, den du nicht geschrieben hast.

Die Zeile wird auf deine .glyph zurückgebildet, die Erklärung aber nicht. In dieser Lücke hört der Compiler auf zu erklären.

Also wandert jede Regel, die Glyph selbst entscheiden kann, nach vorn:

  • E0222await außerhalb einer async fn
  • E0223ein match-Arm, der keinen Wert erzeugt, während das match als Wert verwendet wird
  • E0008Eine Zuweisung ohne mut

Jede nennt die Regel, verweist auf die Entscheidung dahinter und zeigt das Vorher und Nachher.

Ein Arm, der keinen Wert erzeugt

Vorher fiel der erzeugte switch aus seinen eigenen Fällen heraus, und text enthielt undefined, während sein Typ string sagte. tsc findet manche Formen davon und übersieht andere.

Glyph entscheidet es jetzt überall, wo die Position entscheidbar ist: ein let, ein mut, ein return oder das Ende einer Funktion, die einen Rückgabetyp deklariert. Ein match als Anweisung behält X => {} als den bewussten No-op, der es ist.

await außerhalb einer async fn

Bei await ist es derselbe Schritt. Glyph hat kein für den Benutzer sichtbares Promise: Eine async fn -> T wird zu einem T ge-awaited, also hat await überall sonst nichts zu suspendieren.

glyph build, auf `fn total() -> number { return await fetch_count() }` 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

// before: no Glyph diagnostic, then
dist/main.ts:14:18 - error TS1308: 'await' expressions are only allowed
within async functions and at the top levels of modules.
Details welches Aufrufbare entscheidet

Das war früher TS1308 von tsc an der erzeugten Datei. Jetzt ist es E0222, und das innerste umgebende Aufrufbare entscheidet, also ist ein synchrones Lambda innerhalb einer async fn ein eigener Kontext, dieselbe Regel, die TypeScript verwendet. Der umgekehrte Fehler, ein Aufruf, auf den niemand wartet, ist E0238: save(1) allein in einer Zeile, let _ = save(1) und let n: number = load() werden abgelehnt, weil der Aufruf startet und das Programm ohne ihn weiterläuft. Ein synchroner Callback, der etwas anstoßen und vergessen will, schreibt task.detach(async fn() -> void { await save(1) }); das meldet einen Fehler auf stderr.

Eine Zuweisung ohne mut

Die dritte betrifft eine Regel, die man am ersten Tag bricht. Glyph markiert jede Mutation, also ist das Neuzuweisen eines Bindings mut x = e und das Einführen eines let x = e.

E0008E0302E0303

Ein bloßes x = e meldete früher "unexpected token: Equals", was ein Zeichen nennt statt der Regel. Jetzt ist es E0008, und glyph --explain E0008 erklärt, warum es die Markierung gibt: Jede Stelle, an der sich ein Wert ändert, beginnt mit mut, also findet grep "mut total" alle.

Details der Operator ?, E0302 und E0303

Der Operator ? bekommt dieselbe Behandlung aus der anderen Richtung. ? wird zu einem Binding plus einem vorzeitigen return erweitert, das vor die Anweisung gesetzt wird, in der es steht, also braucht es eine Anweisung, in die es sich erweitern kann. Es funktioniert in einem let, einem return, einem Argument und jetzt auch im Rumpf eines match-Arms. Wo es nicht funktionieren kann, sagt die Meldung, welche Position es ist und wie man daraus herausbindet (E0302 und E0303), statt zu behaupten, der Operator sei nicht implementiert.

Der schlimmere Fall: wenn auch tsc zufrieden ist

Ein tsc-Fehler an der falschen Stelle ist ärgerlich. Ein sauberer Build für ein Programm, das etwas anderes bedeutet, ist das eigentliche Problem, und Glyph hatte eins.

Jeder Name auf oberster Ebene, den du deklarierst, landet wörtlich im erzeugten Modul, auch die Varianten-Konstruktoren einer Tagged Union, also erzeugt eine Variante namens Error ein export function Error(...) auf oberster Modulebene. Das new Error(...), das der Compiler darunter schreibt, ruft dann deine Variante auf.

glyph build, auf einer Union mit einer Variante `Error` 
[E0110] `Error` cannot name a type, variant, or function: the emitted module
        references the JavaScript global `Error`, and this declaration would
        shadow it
 5 │   | Error(string)
   │     ──────┬─────
   ╰─ Rename it (e.g. `Error` -> `Failure`). The name is legal TypeScript, so
      nothing downstream catches the rebinding.

// before: no Glyph diagnostic, then, twenty lines later
dist/main.ts:31:12 - error TS2345: Argument of type 'string' is not
assignable to parameter of type ...
E0110E0111E0109
Details type Key = string | number, die geschützte Liste, E0111

type Key = string | number ist derselbe Mangel mit freundlicherem Gesicht. In Glyph deklariert A | B eine Tagged Union, deren Mitglieder Varianten-Konstruktoren sind, also deklariert diese Zeile Varianten namens string und number. Sie kompilierte, bestand tsc --strict und erzeugte ein export const number, das den Prelude-Namespace number überdeckte. Nichts schlug fehl, bis ein späterer Aufruf von number.to_string es tat.

Der Span ist die Deklaration, denn dort gehört die Umbenennung hin. Die geschützte Liste wird aus dem Emitter abgeleitet statt aus einer allgemeinen Liste von JavaScript-Globals, und ein Test greppt den Emitter und schlägt fehl, wenn eine neue globale Referenz ohne passenden Eintrag auftaucht. Dieser Test ist der Punkt: Number war harmlos, bis int ausgeliefert wurde und anfing, Number.isInteger zu erzeugen, und genau so ist das überhaupt in ein Release gelangt. Date, Math und JSON bleiben frei, weil nichts, was Glyph erzeugt, sie erwähnt.

Der Fall der primitiven Union bekommt einen eigenen Code, E0111, weil eine Ablehnung ohne Erklärung nichts lehrt. Er sagt, als was die Zeile tatsächlich geparst wurde, verweist auf benannte Varianten und nennt extern_ts("string | number") für die Grenze, an der du die rohe TypeScript-Union willst. Jeder Name, den Glyph dich nicht verwenden lässt, ist in docs/reference/reserved-words.md tabelliert: die 32 Schlüsselwörter, die 33 reservierten TypeScript-Wörter hinter E0109 und die Liste der überdeckten Namen, jeweils mit dem Grund, warum der Name vergeben ist.

Man sollte klar sagen, was das nicht leistet. Du kannst einen Typ oder eine Variante weiterhin nicht Error nennen, und die Tabellenkalkulation, bei der das aufgefallen ist, hat deshalb eine Variante namens Cellerr. Das Programm, das sie sein wollte, lässt sich weiterhin nicht schreiben; geändert hat sich, dass der Compiler das jetzt an der Deklaration sagt, statt den Build grün werden zu lassen und etwas anderes zu bedeuten.

Details warum der Name nicht einfach benutzbar gemacht wird

Den Namen benutzbar zu machen hieße, Glyph-Namen auf dem Weg nach TypeScript umzuschreiben, was ändert, was ein Stacktrace, ein grep über dist/ und ein handgeschriebener extern/-Shim sehen, also ist das kein Patch, den wir still machen können.

Eine falsche Meldung ist schlimmer als keine

Die Liste der überdeckten Namen begann mit Namen, die der Emitter als Werte schreibt. Es fehlten die, die er als Typen schreibt, und das ergab die schärfste Version dieses ganzen Problems.

glyph build, vorher: fünfzehn davon, keiner in der Nähe der Ursache 
dist/corpus/infer_output.ts:52:9 - error TS2353: Object literal may only
specify known properties, and 'code' does not exist in type 'Issue'.
glyph build, jetzt 
[E0110] `Issue` cannot name a type, variant, or function: the emitted module
        references the Glyph prelude global `Issue`, and this declaration
        would shadow it
   ╰─ Rename it. The name is legal TypeScript, so nothing downstream catches
      the rebinding.
Details warum Issue kollidiert, und Record

Das parse jedes Deskriptors gibt Result<T, Issue[]> zurück, also schreibt das erzeugte Modul Issue, ob du es geschrieben hast oder nicht. Deklarier type Issue = { path: Array<string>, message: string } in deinem eigenen Modul, und deins gewinnt, die erzeugten Issue-Objekte tragen ein Feld code, von dem deins nie gehört hat, und der Build schlägt mit einem tsc-Fehler über generierten Code fehl, an einem Span, der woandershin zeigt.

Record kam gleichzeitig auf die Liste, eingeordnet bei den JavaScript-Globals statt bei den Prelude-Namen, weil es ein TypeScript-Builtin ist und die Meldung sonst falsch darüber wäre, woher der Name kommt. Der Drift-Test, der den Emitter greppt, deckt jetzt auch ambiente Typen ab, und er musste lernen, Issue[] an einer Typposition zu sehen, und genau deshalb ist das in ein Release gelangt. Schema, Component und Option bleiben nach derselben Regel erlaubt, die Date frei hält: Der Emitter schreibt sie nur, weil du sie in einer Annotation geschrieben hast, also überdeckt eine Deklaration nichts.

Ein Import, der einem match die Schuld gab

Der andere Fall dieser Klasse war ein Import. Ein lokaler Importpfad wird vom Build-Root aus aufgelöst, dem Verzeichnis, das du glyph build übergibst, nicht vom Verzeichnis der importierenden Datei.

glyph build examples/apps, auf `import catalog` innerhalb von csvql/ 
[E0104] unresolved import `catalog`: no module `catalog` under the build
        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from
        the importing file's directory (D15)
   ╰─ Build that module's own directory as the root, or spell the import path
      as it reads from the root.

// before: no import diagnostic, then
[E0218] non-exhaustive match on string   // on a match over all four values
Details was früher gemeldet wurde, und wie Fehlalarme vermieden werden

Bau einen umgebenden Baum, und import catalog findet nichts, und bis jetzt sagte das nichts. Der Typ verfiel zu unbekannt, ein match darüber verlor die Varianten, die es matchte, und was du bekamst, war E0218, nicht erschöpfendes match, bei einem match, das jeden Fall abdeckte. Zu tun, was diese Meldung verlangte, hätte korrektem Code einen toten else-Arm hinzugefügt.

Das Risiko bei einer solchen Prüfung ist, dass sie bei Dingen anschlägt, die in Ordnung sind, und ein Import-Checker, der bei jedem npm-Paket falschen Alarm schlägt, ist schlimmer als die Stille, die er ersetzt hat. Also sammelt der Build zuerst die Modulnamen, die er ohne .glyph-Datei auflösen kann: jedes declare module "X" unter <root>/.types/ und im mitgelieferten Node-Shim, plus jedes Paket im node_modules des Projekts. Ein Name auf dieser Liste wird nie gemeldet, selbst wenn eine lokale Datei zufällig denselben Basisnamen hat. Wenn ein Projekt überhaupt kein node_modules hat, kann der Compiler eine nicht installierte Abhängigkeit nicht von einem Tippfehler unterscheiden, also meldet er nur, was er beweisen kann: einen Import, zu dem eine .glyph-Datei unter dem Root passt.

Die Auflösung selbst hat sich nicht geändert. Dieselben Programme bauen, und dieselben Programme scheitern. Geändert hat sich, dass der Fehlschlag jetzt den Import nennt, statt ein match zwei Dateien weiter zu beschuldigen, und das ist alles: Ein Compiler, der die falsche Ursache meldet, kostet dich die Stunde, die du ihr nachjagst, und danach den Vertrauensvorschuss bei jeder folgenden Meldung.

Die Regel nennen, nicht das Token

Die leisere Version desselben Problems ist ein Fehler, der korrekt ist und dir trotzdem nichts sagt.

glyph check, vorher und jetzt 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.
Details der Rot-Schwarz-Baum, und wie der Fix dein Programm nennt

Ein Agent, der einen Rot-Schwarz-Baum schrieb, griff zum positionalen Konstruktor, den jede Sprache der ML-Familie hat, und der Parser blieb beim ersten Komma stehen, mit “expected )” und dem Rat “add the expected token”. Dort ein ) hinzuzufügen ergibt ein anderes Programm, kein funktionierendes. Eine Glyph-Variante trägt einen Payload, und ein Payload mit mehreren Feldern ist ein Record. Keiner dieser beiden Sätze stand irgendwo in der Ausgabe.

Um das zu sagen, musste der Parser die ganze Liste lesen, bevor er sie ablehnt, und dadurch kann er auch zählen. Der Span unterstreicht alle sechs Felder statt des Trennzeichens, an dem er zufällig gescheitert ist, und der vorgeschlagene Record wird aus dem Variantennamen und den sechs Typen in der Datei gebaut, also nennt der Fix dein Programm und nicht ein Beispiel von jemand anderem. Feldnamen sind das Einzige, was der Compiler nicht liefern kann, also lässt er sie als Lücken.

Die Regel hinter der Meldung ist eine Entscheidung, keine Lücke. Node(Black, l, x, b, h, r) ist die Vertauschung von Argumenten, die durch die Typprüfung geht, und Position vier sagt einem Leser nichts. Die Record-Schreibweise nennt jedes Feld, ein match-Arm nennt nur die Felder, die er verwendet, und beides findet grep.

Zwei weitere, die der Checker in 0.1.121 übernommen hat

Order { id: "a", total: 1 } ist das, was jemand aus TypeScript schreibt, um einen Record zu bauen, und Glyph hat keine solche Form: Ein Wert wird für sich geschrieben, und der Typ steht in der Annotation.

glyph check, auf einem Record, der auf TypeScript-Art gebaut wird 
[E0013] a statement cannot begin on the line where
        `return Order` ends
   ╰─ Glyph has no `TypeName { ... }` construction form. Write the literal
      alone and put the type on the annotation: `let o: Order = { id: "a" }`.

// 0.1.121 to 0.1.145: [E0228] on `Order`, then [E0108] on the braces
// before that: [E0108] Warning: lint: unreachable code, and exit 0
E0228E0013seit 0.1.146
Geschichte von E0108 über E0228 zu E0013

Was der Compiler früher zu dieser Zeile sagte, war E0108, unerreichbarer Code, bei einem Build, der mit 0 endete, weil der Name zum Typ aufgelöst wurde und die geschweiften Klammern als Block nach dem return geparst wurden. Ein Typname, der als Wert geschrieben wird, ist E0228, und die Meldung wird aus der Deklaration gelesen, also listet ein Record seine Felder, eine Tagged Union ihre Varianten mit ihren Payload-Formen und eine Union aus String-Literalen ihre Literale. Order.parse(raw) und Order.is(v) bleiben erlaubt, da der Empfänger des eigenen Deskriptors eines Typs die eine Ausdrucksposition ist, an die ein Typname gehört.

Das behob den Fall, in dem der Name ein Typ war, und ließ das Parsen in Ruhe, also gab return h() { k: 2 } weiterhin h() zurück und ließ die Klammern mit einer Warnung fallen. Seit 0.1.146 ist eine { in der Zeile, in der eine Anweisung endete, beim Parsen E0013, egal welcher Name davor steht, und ihre Hilfe gibt dieselbe Umschreibung. Seit 0.1.149 gilt die Regel für jede Anweisung, nicht nur für eine, die mit einer Klammer beginnt: let s = "a" "b" band früher "a" und ließ "b" fallen, und return x as User waren drei Anweisungen, da Glyph keinen Cast hat.

Jede Anweisung in einem Block beginnt in einer eigenen Zeile.

Ein Container, wo ein Primitiv deklariert ist

Der andere ist ein Prelude-Container, der einem Primitiv zugewiesen wird. let x: string = o mit o: Option<int> löste beim Glyph-Checker nichts aus, und ebenso wenig die Übergabe eines Nullable<int> an einen als int deklarierten Parameter.

Fünf Container sind jetzt in beide Richtungen abgedeckt: Option, Result, Array, Record und Nullable sind nie ein string, eine number oder ein bool, egal mit welchen Argumenten, und Nullable<T> gegen einen Skalar wird eine Ebene tiefer gegen T entschieden, also bleibt let v: Nullable<int> = 3 korrekt, und let v: Nullable<int> = "three" ist E0204.

Details der Fall, den nur Glyph finden kann, und Records seit 0.1.130

Der Fall Nullable gehört mehr als die anderen auf diese Seite, weil tsc ihn nicht entscheiden kann: Das erzeugte const v: number | null = 3 wird vor der Prüfung des Aufrufs wieder zu number eingeengt, also ging ein Grenztyp, der null sichtbar machen soll, still durch, wo ein int deklariert war, und der Glyph-Checker war die einzige Stelle, an der es hätte auffallen können.

Dieselben Container gegen einen deklarierten Record oder eine Union kamen als Nächstes. Seit 0.1.130 ist let user: User = json.parse(body) E0204, erwartet User, gefunden Result<unknown, Array<Issue>>. Vorher sagte das nur tsc, was hieß, dass glyph check --no-tsc, der Editor und der Playground eine saubere Datei zeigten, genau bei der einen Zeile, die eine Systemgrenze richtig machen soll.

Ein falsch geschriebener Member auf einem Array oder einem String

Ein falsch geschriebener Member auf einem Array oder einem String ist der andere Fall, der früher auf tsc wartete. xs.lenght ist E0210 mit "did you mean length", geprüft gegen die Member, die die TypeScript-Bibliothek für Arrays und Strings deklariert, so wie ein Feldzugriff auf einen Record gegen seine Felder geprüft wird. Dasselbe gilt in einem Callback, dessen Parameter keinen geschriebenen Typ hat: Der Parameter bekommt den Typ, den seine Position erwartet, also ist in users.map(fn(u) -> string { return u.nmae }) u ein User und der Tippfehler E0210.

tsc hätte alle drei abgelehnt, also war ein Build, der es ausführte, schon rot; die Änderung ist, dass der Checker und alles, was darauf aufbaut, sie zuerst sieht.

Und drei weitere seit 0.1.133

Eine Methode, von ihrem String gelesen

let up = s.toUpperCase besteht in TypeScript die Typprüfung und wirft, wenn up() läuft, weil der Lesezugriff den String verliert, zu dem die Methode gehört. Glyph lehnt das als E0234 ab und lehnt auch .bind(s) darauf ab: Pack den Aufruf stattdessen in ein Lambda.

E0234
Details woher die Methodentypen kommen

Der Checker weiß jetzt, was jede Array- und String-Methode zurückgibt, aus einer Tabelle, die aus den eigenen Deklarationen von TypeScript generiert wird.

Optional Chaining auf einem Result

r?.label auf einem Result liest sich wie "den Fehler weiterreichen, dann das Feld lesen". Es ist Optional Chaining, und ein Result ist nie null, also liest es das Feld vom Result-Objekt und reicht nichts weiter.

E0236

Ein Agent hat genau das beim Bau eines CSV-Abfrage-Tools geschrieben. Jetzt ist es E0236, auch bei einem Option, und die Hilfe sagt, dass du zuerst mit ? binden sollst.

Ein ungeprüftes json.parse

json.parse(body) ohne Typargument ist das ungeprüfte Lesen, ein Result<unknown, ...>. Dort geschrieben, wo ein Result<User, ...> deklariert war, leitete tsc früher User aus der Deklaration ab, und das Programm stürzte beim ersten Feldzugriff ab.

Der Emitter schreibt das unknown jetzt aus, also lehnt glyph check es über tsc ab.

Glyphs eigener Checker erkennt noch kein unknown, das innerhalb eines deklarierten Typs landet, also übersehen --no-tsc und der Editor weiterhin Result<unknown, ...>, wo Result<User, ...> deklariert ist. (Ein bloßes let user: User = json.parse(body) ist E0204 von Glyphs eigenem Checker, weil schon der äußere Typ falsch ist.) unknown in jeder Tiefe abzulehnen ist als G325 auf der Release-Roadmap geplant.

G325

Und zwei weitere in 0.1.122

type Mode = "read" | "write" deklariert eine endliche Menge von Strings, und der Glyph-Checker verglich einen Wert mit überhaupt nichts dagegen. Eine Zahl, ein bool, ein Record und ein String außerhalb der Menge bestanden alle glyph check --no-tsc mit nichts als Warnungen über unbenutzte Variablen, während tsc jeden davon am erzeugten TypeScript ablehnte.

Ein vollständiger glyph build lag hier also nie falsch, aber die vier Schnittstellen ohne tsc in der Schleife schon: --no-tsc, der Language Server, die MCP-Tools und der Playground.

glyph check --no-tsc, auf einem Typ, der seine zulässigen Strings auflistet 
type Mode = "read" | "write"

let a: Mode = 3
let b: Mode = "rw"
let c: Mode = takes_mode(true)
let d: Mode = { x: 1 }
// before: four unused-variable warnings, exit 0
[E0204] type mismatch: expected `Mode`, found `number`
[E0204] type mismatch: expected `Mode`, found `"rw"`
[E0211] argument type mismatch: expected `Mode`, found `bool`
[E0204] type mismatch: expected `Mode`, found `record`
Details wie die Union verglichen wird

Das sind die vier, die tsc gemeldet hat, an denselben vier Anweisungen, ohne tsc auszuführen. Die Regel liest die Union als das, was sie zur Laufzeit ist, ein string, und stellt dem Checker in jeder Richtung die entsprechende string-Frage, also erbt sie die Regeln, die einen Record oder einen Container gegen einen string schon ablehnen, statt sie Form für Form neu zu formulieren. Zwei Literalmengen werden als Mengen verglichen, also passt eine engere Union dorthin, wo eine weitere deklariert ist; einer Alias-Kette wird auf beiden Seiten gefolgt; eine importierte Union wird wie eine lokale entschieden; und in Nullable<Mode> wird mit intakter Union hinabgestiegen.

Eine Union, die in einem Record-Feld oder einem generischen Argument steckt, wurde in 0.1.122 tsc überlassen und wird in 0.1.123 entschieden. Siehe unten.

0.1.123: das Literal, das ein Wert ist, nicht der string, zu dem er wird

type Mode = "read" | "write" legte die Menge auf die Deklaration und nichts auf den Wert, also war "read" ein string und ["read", "write"] ein Array<string>.

Geschichte was 0.1.122 aufgegeben hat

Das machte zwei Programme ununterscheidbar: return ["read", "write"], wo ein Array<Mode> deklariert ist, das tsc kompiliert, und return xs für ein xs: Array<string>, das es ablehnt. 0.1.122 lehnte die Entscheidung über diese Kombination ab, statt sie falsch zu treffen, und erkaufte das richtige Programm damit, das falsche aufzugeben: { mode: "nope" } gegen ein { mode: Mode } löste nichts aus.

Ein geschriebenes String-Literal hat jetzt den Typ des einen Literals, das es buchstabiert, der Elementtyp eines Array-Literals ist die Vereinigung der Typen seiner Elemente, und ein geschriebenes Array- oder Objektliteral wird Element für Element und Feld für Feld gegen den deklarierten Typ geprüft, also nennt die Diagnose das Literal und unterstreicht es.

glyph check --no-tsc, auf einem Literal eine Container-Ebene tief 
type Mode = "read" | "write"
type Cfg = { mode: Mode }

fn ok() -> Array<Mode> { return ["read", "write"] }
fn bad() -> Array<Mode> { return ["read", "nope"] }
fn wrong() -> Cfg { return { mode: "nope" } }
// 0.1.122: nothing, on all three
[E0204] type mismatch: expected `Mode`, found `"nope"`   (twice)
Details wo das Literal erweitert wird, und Record-Schlüssel seit 0.1.153

Das Literal wird dort wieder zu string erweitert, wo TypeScript es erweitert: bei einem let ohne Annotation, dessen erzeugtes TypeScript-let genauso erweitert, und beim Element-Binding eines for über ein geschriebenes Array. Also wird let l = "read" gefolgt von takes_mode(l) hier abgelehnt und dort mit TS2345. Eine const erzeugt eine TypeScript-const und behält ihr Literal, also kompiliert takes_mode(CM) unter beiden. Ein Literaltyp, der über einen Namen ankam, wird nicht erweitert, das ist TypeScripts eigene Freshness-Regel. Jede Zeile davon wurde entschieden, indem tsc --strict auf das gleichwertige TypeScript ausgeführt wurde, nicht durch Nachdenken.

Das Schlüsselargument eines Record wird seit 0.1.153 strenger gehalten, als tsc es hält. TypeScript schreibt Record<string, V> als Index-Signatur und akzeptiert es gegen ein Record<Mode, V> in beide Richtungen. Glyph lehnt beides ab: Die offene Map kann Schlüssel außerhalb von Mode enthalten oder einen vermissen lassen, und in ein Record<Mode, V>, das als die offene Map weitergegeben wird, lässt sich ein fremder Schlüssel schreiben. Der Weg von einem zum anderen führt über einen is-Arm oder ein json.parse.

Zu zwei Formen sagt der Checker noch nichts: ein Literal innerhalb von Some(...), weil ein Prelude-Konstruktor hier noch keinen Typ hat, und ein Record-Literal, das an ein let ohne Annotation gebunden wird, weil für ein Objektliteral kein Record-Typ synthetisiert wird.

Ein Modul unter std/ war toter Code ohne Diagnose

std/ und extern/ benennen Module, die der Compiler mitbringt, und der Resolver reservierte sie für Imports. Nichts hinderte eine Projektdatei daran, eins zu deklarieren.

glyph check --no-tsc, auf src/io.glyph, das `module std/io` deklariert 
// before: glyph check: 2 module(s) checked, no diagnostics.  (exit 0)

[E0113] `std/io` declares a module under `std/`, a prefix reserved for the
        modules the compiler carries (D15)
 1 │ module std/io
   │ ──────┬──────
   ╰─ Rename the module to a path of your own (`io`, `app/io`).
Details was früher passierte, und welche Pfade reserviert sind

module std/io in deinem eigenen src/io.glyph kompilierte sauber, und dann wurde import std/io { shout } zum Stub aufgelöst und meldete, dass shout nicht exportiert wird: Deine Datei wurde nie gelesen.

Das Präfix wird als ganzes erstes Segment gematcht, also bleiben standard, externals/io, app/std und app/extern/helper unberührt, und Importe unter einem der beiden Präfixe funktionieren weiterhin wie immer.

Eine Datei, die keine Diagnose auslöst und keinen Code ausführt, ist die schlimmste Form, in der ein Compiler dich zurücklassen kann, weil nichts daran falsch aussieht.

Der zweite in 0.1.122

Eine Tiefengrenze für den Parser

Der zweite ist überhaupt keine tsc-Geschichte. Der Parser ist rekursiver Abstieg ohne Tiefenschutz, also brachte ein Ausdruck, der zweitausend Ebenen tief verschachtelt war, den Prozess an das Ende seines Stacks und brach mit Exit-Code 134 ab.

glyph check, auf `const x = ` gefolgt von 2.000 verschachtelten Klammern 
// before: thread 'main' has overflowed its stack
//         fatal runtime error: stack overflow, aborting   (exit 134)

[E0011] this array literal nests deeper than the parser's limit of 64 levels
   ╰─ Name the inner levels: pull them out into `let` bindings, or into a
      `fn` that returns one of them, so no single expression, type or
      pattern is more than 64 levels deep.
Details warum es für den Language Server wichtig war

Das ist schlecht bei glyph check und schlimmer bei glyph lsp und glyph mcp, die jede Datei unter dem Root lesen: Eine einzige pathologische Datei legte den Server für den ganzen Workspace lahm. Jetzt ist es E0011, ausgelöst an dem Token, das Ebene 65 geöffnet hätte.

Die Grenze ist 64, und sie wurde gemessen statt gewählt.

Details wie die 64 gemessen wurde

Eine Ebene des teuersten Konstrukts, eines verschachtelten Array-Literals, kostet im Release-Build 7.792 Bytes Stack und im Debug-Build 8.810, ermittelt per binärer Suche nach dem kleinsten Thread-Stack, mit dem eine gegebene Tiefe noch geparst wird. Der dünnste Stack, auf dem der Parser läuft, sind die 2 MiB eines gestarteten Threads, die die Worker des Language Servers bekommen, und 64 Ebenen verbrauchen im teureren Build weniger als ein Drittel davon. Die tiefste Verschachtelung in den 343 .glyph-Dateien dieses Repositorys ist 16. Die Grenze gilt für Ausdrücke, Typen, Patterns, Blöcke und JSX-Kinder gleichermaßen, und tausend nebeneinanderliegende Arrays werden weiterhin geparst, weil die Tiefe die Verschachtelung pro Konstrukt ist und kein Budget, das über die Datei verbraucht wird.

Wenn keiner der beiden Compiler falsch liegt

Es gibt eine dritte Form, und sie liest sich am schlechtesten. Glyph meldet nichts, tsc meldet etwas Wahres, und das Programm, das du geschrieben hast, war in Ordnung.

Gescheitert ist die Übersetzung zwischen beiden.

poll.glyph und was tsc vor 0.1.89 dazu sagte 
fn classify() -> int {
  let done = false
  match done {
    true => { return 1 },
    false => { return 0 },
  }
}

// no Glyph diagnostic, then
[TS2678] Type 'true' is not comparable to type 'false'.
Details warum tsc false sah, und die App, die darauf stieß

Ein Binding hat in Glyph einen Typ für seine ganze Lebensdauer. TypeScript engt ein Binding auf das ein, was es zuletzt zugewiesen gesehen hat, und sein boolean ist die Union true | false, also kam let done = false bei tsc als false typisiert an, und der true-Arm des erzeugten switch hatte nichts zu matchen.

Ein Typ, der als Menge von String-Literalen deklariert war, scheiterte auf dieselbe Weise, und ebenso ==, das stattdessen als TS2367 zurückkam: zwei Meldungen, zwei Codes, eine Ursache. Die App, die darauf stieß, fragte ein Flag ab, das ein Timer-Callback setzt, so macht man aus einer eventbasierten API einen Wert, solange Glyph kein Promise hat, das man von Hand konstruieren kann. Der Callback stellte sich als nebensächlich heraus: Vier Zeilen ohne Callback reichen dafür.

Der Fix ist keine neue Diagnose, weil es nichts zu diagnostizieren gibt. Der Emitter wiederholt jetzt den Typ, den der Checker schon entschieden hat, an den beiden Stellen, die über einen Wert unterscheiden: am Untersuchungswert des match und auf beiden Seiten eines == oder !=.

Details die Prüfungen, die weiterhin anschlagen, und was es kostet

Jede Seite wird nach ihrem eigenen Typ entschieden und ignoriert, was neben ihr steht, also ist ein Vergleich zwischen zwei Bindings genauso abgedeckt wie ein Vergleich mit einem Literal.

Die Prüfungen, die du willst, schlagen weiterhin an. m == "nope", wo m ein Mode ist, wird weiterhin abgelehnt, und jetzt nennt die Meldung Mode statt des einzelnen Mitglieds, das m gerade hielt. Das bei der Zuweisung zu tun, wäre weniger Code gewesen und hätte genau das weggeworfen: Ein Cast zu Mode wird akzeptiert, wo die annotierte Zuweisung es nicht wird, und die Mitgliedschaftsprüfung ist der Teil, den Glyph absichtlich tsc überlässt.

Was es kostet, ist klein, aber erwähnenswert. Ein Cast kann einengen statt nur bestätigen, also besteht ein Wert, den Glyph als bool typisiert und dessen TypeScript-Typ unknown herauskam, jetzt dort, wo sich der switch früher beschwert hat. Die beiden Typen müssen weiterhin vergleichbar sein, also meldet ein Modell, das weit genug abgedriftet ist, um eine Rolle zu spielen, string gegen bool, TS2352 statt nichts.

Derselbe Tippfehler, zwei Antworten

Eine falsch geschriebene Funktion der Standardbibliothek bekam früher eine andere Antwort, je nachdem, wie du den Import geschrieben hattest, und genau so eine Inkonsistenz bringt dir bei, keiner der beiden Antworten zu trauen.

der benannte Import, immer ein E0105 
import std/string { repeeat }
[E0105] import: `repeeat` is not exported by `std/string`
der Zugriff über den Namespace, vor 0.1.72 
import std/string
string.repeeat(s, 2)
[TS2551] Property 'repeeat' does not exist on type ... Did you mean 'repeat'?

Beide Schreibweisen laufen jetzt über die Exportliste, und beide sagen E0105 und nennen den Member und das Modul, in dem er fehlt.

Details warum sich die beiden Schreibweisen unterschieden, und was das Einschalten fand

Die erste Schreibweise wurde bei der Auflösung gegen die Exportliste des Moduls geprüft. Die zweite wurde überhaupt nicht geprüft, also fiel sie zu tsc durch, das einen Eigenschaftszugriff auf ein Objekt sah und in diesen Begriffen antwortete.

Das Einschalten fand sofort etwas, nach dem niemand gesucht hatte: Ein Test-Fixture hatte fs.write aufgerufen, wo die Funktion write_text heißt. Es war monatelang durchgegangen, weil dieses Fixture mit abgeschalteter Typprüfung läuft und nichts anderes im Compiler sich Namespace-Member ansah. Die Exportliste ist jetzt für beide Schreibweisen maßgeblich, also hält eine separate Prüfung sie im Einklang mit dem, was die Laufzeit tatsächlich exportiert. Diese Prüfung wurde geschrieben und dann absichtlich kaputtgemacht, um zu bestätigen, dass sie fehlschlägt, und so haben wir herausgefunden, dass ihre erste Version still nichts geprüft hatte.

Wird schärfer

  • E0238 erkennt einen Aufruf nur dann als async, wenn Glyphs Checker seine Signatur kennt
    Details

    E0238 weiß nur dann, dass ein Aufruf async ist, wenn Glyphs Checker seine Signatur kennt, daher kann ein Promise aus einem npm-Paket oder einem node-Builtin weiterhin still verworfen werden. Ein async-Callback, der an forEach, einen Timer, einen Socket-Handler oder irgendeinen fn(...) -> void-Parameter übergeben wird, wird mit E0211 abgelehnt, weil nichts auf ihn wartet.

  • Wer außerhalb eines Aufrufs fn und async fn verwechselt, wird mit einer allgemeinen Meldung abgelehnt
    Details

    Bei einem Aufruf bekommt die falsche Art von Funktion eine Hilfe, die man einfügen kann: Einem synchronen tick, das an task.detach übergeben wird, wird gesagt, async fn() -> void { tick() } zu übergeben oder async fn tick() zu deklarieren. Eine async fn, die in einem let an ein fn(...) -> void gebunden, zurückgegeben oder in einem Feld gespeichert wird, wird ebenfalls abgelehnt, aber die Meldung sagt nur expected `function`, found `async function` und überlässt die Korrektur dir.

  • Ein await auf oberster Ebene ist erlaubt
    Details

    Ein const-Initialisierer auf Modulebene hat nichts Aufrufbares um sich, also ist ein await auf oberster Ebene erlaubt, und das erzeugte ESM führt es aus; ob Glyph eine implizite asynchrone Modulinitialisierung will, ist noch eine offene Frage der Spezifikation.

  • E0223 kann ein match am Ende nur beurteilen, wenn die Funktion einen Rückgabetyp deklariert, also erreicht ein Arm in einem nicht annotierten Lambda weiterhin tsc.
  • E0110 sagt dir, dass du umbenennen sollst, statt dich den Namen behalten zu lassen
    Details

    Auf der Seite der überdeckten Namen sind zwei Dinge nur halb erledigt. E0110 sagt dir, dass du umbenennen sollst, statt dich den Namen behalten zu lassen, also sind Error, Number, Object, Array und Promise für einen Typ oder eine Variante weiterhin tabu.

  • E0111 verhindert, dass type Key = string | number das Falsche bedeutet, ohne dir einen Weg zu geben, es auszudrücken
    Details

    Und E0111 verhindert, dass type Key = string | number das Falsche bedeutet, ohne dir einen Weg zu geben, es auszudrücken: Eine Union aus zwei primitiven Typen hat in Glyph keine Schreibweise außer extern_ts, dessen Inhalt der eigene Checker als undurchsichtig behandelt. Unions ohne Tag berühren Erschöpfendheit, Laufzeit-Deskriptoren und is, also ist das eine Entscheidung des Typsystems, und sie ist nicht eingeplant.

  • E0104 erreicht glyph build und glyph check, aber nicht den Editor
    Details

    E0104 erreicht glyph build und glyph check, aber nicht den Editor: Der LSP analysiert den Text eines Dokuments ohne Build-Root, und der Workspace-Ordner ist auch keins, also würde Raten genau die Fehlalarme erzeugen, die die Prüfung vermeiden soll.

  • Ein Parameter mit reserviertem Wort versteckt sich weiterhin hinter einem anderen Fehler in derselben Datei, weil ein Fehlschlag im Sammel-Durchlauf den Auflösungs-Durchlauf überspringt, der ihn gefunden hätte.
  • Die Typfixierung an der Lesestelle folgt einem Typ-Alias nur innerhalb des Moduls, das gerade erzeugt wird
    Details

    Unabhängig davon folgt die Typfixierung an der Lesestelle, die ein bool- oder String-Literal-Union-Binding matchbar hält, einem Typ-Alias nur innerhalb des Moduls, das gerade erzeugt wird, also erreicht pub type Ready = bool in einem Modul und let r: catalog.Ready = false in einem anderen weiterhin tsc als TS2678. Unions aus String-Literalen sind modulübergreifend in allen drei Import-Schreibweisen abgedeckt, und seit 0.1.123 nennt die Diagnose bei jeder Schreibweise die Deklaration (erwartet Mode), statt bei einer davon ihre Literalmenge auszugeben.

Die Codebeispiele auf dieser Seite werden bei jedem Build mit Glyph 0.1.158 geprüft. Zuletzt geändert: 21. Nov. 2026.
