Ja. Glyph kompiliert zu gewöhnlichem TypeScript und läuft über npm: Ein .glyph-Modul importiert aus jedem Paket und lässt sich selbst aus deinem bestehenden .ts importieren. Du führst es Datei für Datei ein.

Warum das wichtig ist

Niemand schreibt eine Codebasis neu, um eine Sprache auszuprobieren. Weil Glyphs Ausgabe TypeScript ist, passt eine .glyph-Datei in eine Ecke eines bestehenden TS/React/Node-Projekts, importiert dieselben Pakete und exportiert zurück an das .ts drumherum.

Dieser schrittweise Weg ist der ganze Grund, TypeScript als Ziel zu nehmen, statt eine neue Laufzeit auszuliefern.

Installierte Pakete bringen ihre eigenen Typen mit

Wenn das Paket installiert ist und eigene Typen mitbringt (oder ein @types/... hat), ist das alles, was du tun musst. Kein Stub, keine Adapter-Datei.

glyph build findet das node_modules deines Projekts und richtet den Typchecker darauf aus, also prüfen die echten Typen des Pakets deinen Code, und ein falscher Aufruf ist ein echter Fehler.

Hier wird zod inline verwendet, ohne etwas Handgeschriebenes:

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
ein Aufruf, den zod nicht definiert 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

glyph run führt dasselbe Programm gegen das installierte zod aus, es ist also nicht nur eine Typprüfung: Der eine Konfigurationseintrag, der das Paket für den Typchecker auflöst, löst es auch für die Laufzeit auf.

Ein Paket, das keine Typen mitbringt und kein @types/... hat, braucht weiterhin eine Deklaration, die du schreibst, und dafür ist der Ordner .types/ da (derselbe .d.ts-Mechanismus, den TypeScript schon verwendet).

Details Subpath-Imports und validierte Typen aus einer .d.ts

Subpath-Imports (pkg/sub) werden ebenfalls über die exports-Map des Pakets aufgelöst, also werden die eigenen Typen eines Subpaths geprüft.

Und wenn du die Form einer Bibliothek als vollwertigen, validierten Glyph-Typ statt als reinen Typ-Import willst, macht glyph gen dts aus einer .d.ts echte Typen mit Deskriptoren: siehe Muss ich für jede API einen Validator von Hand schreiben?

Aus Werten abgeleitete Typen, JSX-Spread und die Hintertür

Aus Werten abgeleitete Typen sind vollwertig. Prop-Spread in JSX (<input {...register()} />) ist ebenfalls vollwertig.

Eine Bibliothek zwingt dich also nie zu einer handgeschriebenen Adapter-Datei.

Für das seltene TypeScript-Idiom, das Glyph noch nicht ausdrücken kann, ist extern_ts("...") die abgegrenzte, durchsuchbare Hintertür: tsc prüft es, aber genau genommen ist es eine Vertrauensgrenze, keine zur Laufzeit validierte (undurchsichtig für Glyph, ein Wert kommt als unknown zurück, das du einengen musst).

Details wie z.infer<typeof s> aufgelöst wird

type User = z.infer<typeof user_schema> funktioniert direkt: typeof user_schema ist eine Typabfrage über eine echte Wertreferenz (ein Tippfehler ist ein Fehler wegen eines nicht aufgelösten Namens), und z.infer<...> ist ein gewöhnlicher generischer Member-Typ. Er wird wörtlich ausgegeben, und tsc löst ihn auf, also ist u.name ein string; die Validierung kommt aus dem eigenen parse des Schemas, so wie zod ohnehin funktioniert.

Wenn du ganzes handgeschriebenes TypeScript brauchst

Manchmal ist die Hintertür kein Typ oder Ausdruck, sondern echter Laufzeitcode: eine Schleife über einen Node-Stream, ein new Promise, ein Worker-Thread. Leg die .ts unter <src>/extern/ ab und erreiche sie mit import extern/<name>. 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

Relative Imports bleiben im Glyph-Quellcode verboten (eine Regel der Durchsuchbarkeit), also ist extern/* der einzige reservierte Pfad, und grep -rn 'import extern/' findet jede Stelle, an der du die Sprache verlassen hast.

Details Bereitstellung, die andere Richtung und der Node-Shim

Der Build kopiert <src>/extern/** in die Ausgabe und erzeugt einen relativen Specifier, also prüft tsc das Extern zusammen mit deinem Glyph-Code, und ein Neubau entfernt es nie.

Es ist das Gegenstück zur einfachen Richtung, einer .ts-Datei, die dein kompiliertes Glyph importiert, was überhaupt nichts braucht. Ein übliches Extern (ein HTTP-Server, fs) wird ohne Installation gegen den mitgelieferten Node-Shim typgeprüft.

Einen Unterprozess beobachten, ohne etwas zu installieren

Die mitgelieferten Node-Deklarationen enthalten die asynchrone Hälfte von child_process, nicht nur die blockierende, also ist ein Tool, das die Ausgabe eines langen Befehls meldet, während er läuft, Glyph und kein Extern: 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

io.print und nicht io.println: Ein Chunk ist ein Ausschnitt aus dem Stream, keine Zeile, und eine Zeile kann über zwei davon verteilt ankommen.

Die Overloads folgen @types/node, also kommen die Pipes bei einem einfachen spawn(command, args) als nicht-null zurück und als nullbar, sobald du stdio übergibst. child.stdout nach stdio: "inherit" zu lesen ist hier TS18047 und mit den echten Typings TS18047, statt zwei verschiedener Geschichten über denselben Wert: 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

Bearbeite den Shim, und der nächste Lauf verwendet den bearbeiteten

Ein Shim ist eine Datei, an der du iterierst, also muss sie als Quelle zählen.

glyph run cacht einen Build unter einem Fingerprint deiner Quellen, und dieser Fingerprint umfasst jede .ts und .tsx unter extern/, nach Pfad und nach Inhalt.

Details was einen Neubau auslöst

Bearbeite eine, benenne eine um, füge eine hinzu, lösche eine, und der nächste Lauf baut neu und führt tsc erneut aus. Einem verlinkten Shim wird gefolgt, also wird eine .ts, die außerhalb des Quellbaums liegt, nach ihrem tatsächlichen Inhalt gehasht.

Deshalb kann der Shim einen Typ besitzen, statt dass beide Dateien ihre eigene Kopie davon deklarieren. Exportiere die Form aus dem Shim, importiere sie im Glyph-Modul, und der Compiler hält die beiden bei jedem Lauf zusammen:

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
der Shim hat ein Feld umbenannt, der Build sagt es 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3
Geschichte vor 0.1.44, und die Dateien, die nicht zählen

Bis 0.1.44 übersprang der Fingerprint extern/ vollständig, also erzeugte diese Umbenennung einen sauberen, typgeprüften Build, der die vorherige Kopie des Shims ausführte. Dateien unter extern/, die keine .ts oder .tsx sind, beeinflussen den Cache weiterhin nicht, und das ist Absicht: Eine README.md neben deinem Shim wird mit ihm in die Ausgabe kopiert, aber nichts prüft oder führt sie aus, also gibt es nichts neu zu bauen.

Klassenbasierte Clients: die für Datenbanken und Messaging

Die meisten Clients für Datenbanken und Messaging sind klassenbasiert: Du schreibst new Kafka(...), new MongoClient(url), new Redis(), new Pool(cfg). Genau dafür hat Glyph new.

ein klassenbasierter Client (kafkajs) 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
ein Factory-Client braucht kein new 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

Es erzeugt ein wörtliches TypeScript-new, und tsc prüft es gegen den echten Konstruktor des Pakets, also ist ein falsches Argument ein echter Fehler, und ein undefinierter Aufgerufener wird mit Namen erkannt.

Es bleibt auf Interop beschränkt: Glyph hat keine eigene class, und new konstruiert nur einen Typ, der aus einem Paket, einer .types-Deklaration oder extern_ts kommt.

Wo es steht

Heute verfügbar

  • Importiere jedes npm-Paket (auch Namen mit Bindestrich und Scope).
  • Ein installiertes Paket, das eigene Typen mitbringt (oder @types/... hat), wird ohne Stub typgeprüft und ausgeführt.
  • Klassenbasierte Clients werden mit new konstruiert, von tsc gegen den echten Konstruktor geprüft; Factory-Clients werden importiert und direkt aufgerufen.
  • Node-Builtins werden ohne Weiteres typgeprüft
    Details

    Node-Builtins (fs, path, http, child_process einschließlich des streamenden spawn und der Rest) werden ohne Weiteres typgeprüft, wobei @types/node automatisch geladen wird, wenn du es installierst, und CI baut die eigene Laufzeit des Compilers gegen dieses Paket in der Version latest, sodass eine Deklaration, von der die Stdlib abhängt, nicht von der echten von Node abweichen kann.

  • Eine Deklaration, die nur dein Code erreicht, deckt diese Prüfung noch nicht ab, und einige sind noch weiter gefasst als bei Node.
  • Ambiente .types/-Deklarationen für alles andere.
  • glyph gen dts, um aus einer .d.ts validierte Glyph-Typen zu machen.
  • Saubere .ts-Ausgabe, die dein bestehendes TypeScript zurückimportiert.
  • import extern/<name> erreicht handgeschriebenes TypeScript unter <src>/extern/
    Details

    Wenn du ganzes handgeschriebenes TypeScript brauchst, erreicht import extern/<name> eine .ts unter <src>/extern/, mit deinem Code bereitgestellt und typgeprüft und vom Cache von glyph run verfolgt, sodass eine Änderung daran einen Neubau auslöst.

In Arbeit

  • Die Materialisierung kommt mit den Formen echter SDKs zurecht, und aus Werten abgeleitete Typen sind vollwertig
    Details

    Die Materialisierung kommt jetzt mit den Formen zurecht, die echte SDKs mitbringen (Namespaces, dateiübergreifende und per Alias oder Namespace laufende Re-Exports, Subpath-exports und vollwertige Generics), und aus Werten abgeleitete Typen (z.infer<typeof s>) sind vollwertig.

  • Die größte verbleibende Lücke ist, dass die Ausgaben eines nicht materialisierten Pakets gegen seine .d.ts typgeprüft, aber nicht zur Laufzeit validiert werden, solange du sie nicht materialisierst.
  • Auf der Seite von extern/ unterscheidet sich das Quell-Root zwischen glyph run und glyph build
    Details

    Auf der Seite von extern/ unterscheidet sich das Quell-Root zwischen den beiden Befehlen: glyph run app.glyph nimmt das eigene Verzeichnis der Datei als Root, glyph build src/ das Verzeichnis, das du nennst. Ein Programm in einem Unterverzeichnis sucht seinen Shim deshalb an zwei verschiedenen Stellen, und bis wir uns auf ein Root festlegen, braucht ein so aufgebautes Projekt den Shim von beiden aus erreichbar. Wenn er es nicht ist, schlägt es laut fehl.

Die Codebeispiele auf dieser Seite werden bei jedem Build mit Glyph 0.1.183 geprüft. Zuletzt geändert: 21. Nov. 2026.
