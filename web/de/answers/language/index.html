Warum das wichtig ist

Eine Sprache, in der du eine Datei schreiben, aber kein Projekt strukturieren kannst, ist keine, auf die du eine Codebasis setzt. Die Lücken, auf die es ankommt, sind nicht exotisch:

  • SichtbarkeitKann ich einen Helper verstecken?
  • Generische BoundsKann ein Generic eine Fähigkeit verlangen?
  • AufräumenKann ich ein Datei-Handle auf jedem Ausgangspfad freigeben?
  • NebenläufigkeitKann ich zwei Dinge gleichzeitig laufen lassen und auf beide warten?

Glyph beantwortet diese vier, und zwar ohne die annotationslastige Richtung wieder zu öffnen, die es bewusst aufgegeben hat.

Interfaces schränken Generics ein

Ein interface ist strukturell, wie in TypeScript: eine Menge von Member-Signaturen, die ein Generic verlangen kann. Kein implements, keine nominale Zeremonie. Jeder Wert mit den Membern erfüllt es, und tsc setzt es durch.

Interfaces schränken Generics ein 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer und strukturierte Nebenläufigkeit

defer führt Aufräumarbeiten aus, wenn der Block verlassen wird, auf jedem Pfad, auch bei einem vorzeitigen Return oder einem geworfenen Fehler. Und std/task führt nebenläufige Arbeit mit einer gemeinsamen Lebensdauer zusammen, statt losgelöste Promises zurückzulassen.

defer + strukturierte Nebenläufigkeit 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])
Details Reihenfolge und owned-Handles

Mehrere defers laufen last-in-first-out, und es lässt sich mit owned-Handles kombinieren.

Was es von JavaScript erbt

Glyph kompiliert zu TypeScript und läuft auf einer JavaScript-Engine, übernimmt also die Auswertungsreihenfolge, die Referenzsemantik bei Mutation und das Single-Thread-Modell mit Garbage Collection. Die Spezifikation nennt das als Garantien, statt dich es selbst herausfinden zu lassen.

Bei der Gleichheit weicht es ab: == vergleicht Werte, Records Feld für Feld, während das === von JavaScript Referenzen vergleicht.

Manuelle Speicherverwaltung und ein Modell ohne GC stehen auf keiner Roadmap; sie liegen außerhalb dessen, was eine Sprache ist, die nach TypeScript transpiliert.

Es gibt kein if, also muss match alles tragen

Das Erste, was ein TypeScript-Entwickler nach dem Pitch zur Erschöpfendheit fragt, ist, ob match wirklich eine allgemeine Bedingung ist oder nur eine nette Art, eine Union zu destrukturieren. Es ist Ersteres, und der Beweis dafür ist die Zuweisung.

Ein match, das der ganze Wert eines let oder eines mut ist, nimmt alles, was eine Anweisung nimmt: Ein Arm kann ein Block sein, ein Arm kann awaiten, ein Arm kann mit break die umgebende Schleife verlassen, und ein Arm kann das Binding lesen, dem er zuweist, und so faltest du Zustand durch eine Schleife ohne if.

aus dem Link-Checker: Codeblöcke verfolgen und ein Arm mit await 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}
Details wozu es kompiliert, und woher die Schnipsel stammen

Beides kompiliert zu einem einfachen switch, der das Binding pro Arm zuweist, also sitzt das await in der umgebenden async-Funktion, und der Akkumulator ist eine normale Variable, die TypeScript ableiten kann. Beide Schnipsel stammen aus examples/apps/linkcheck/main.glyph, einem Markdown-Link-Checker, der geschrieben wurde, um genau so etwas zu finden.

Ein match, das innerhalb eines größeren Ausdrucks verwendet wird, als Argument oder Operand, wird weiterhin zu einer Closure, und damit müssen seine Arme einzelne Ausdrücke sein. Es in ein eigenes let herauszuziehen hebt das auf.

Ein Pattern kann eine Form mehr als eine Ebene tief benennen

Eine Variante mit mehreren Feldern trägt einen Record, also muss ein Arm, der eine Form erkennen will, durch die Felder des Records greifen. Ein Feld nimmt jetzt jedes Pattern: einen Varianten-Tag, einen verschachtelten Konstruktor, ein verschachteltes Destructuring, ein Literal, ein Array-Pattern.

ein Rotationsfall beim Rebalancing eines Rot-Schwarz-Baums, als ein Arm 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}
Geschichte der Workaround vor 0.1.90

Bis 0.1.90 nahm die Feldposition einen Namen und sonst nichts: Du konntest ihn umbenennen, das war alles. Dort einen Tag zu matchen war ein Compile-Fehler, und ein verschachtelter Konstruktor fiel aus dem Parser. Der Workaround war, jedes Feld zu binden und pro Ebene ein verschachteltes match zu schreiben, was bei so etwas wie dem Rebalancing eines Rot-Schwarz-Baums ein anderes Programm ist: Die Arme passen nicht mehr zu den Fällen, und jede Ebene fädelt die Bindings darüber neu ein.

Eine Folge solltest du kennen, bevor du eins schreibst. Ein Feld, das einen Wert testet, kann fehlschlagen, also zählt der Arm nicht mehr als Abdeckung seiner Variante, und ein match, dessen einziger Node-Arm Node({ color: Red, ... }) ist, wird als nicht erschöpfend gemeldet, bis ein Geschwister-Arm oder ein else den Rest nimmt.

Details warum es den Catch-all verlangt, und die Array-Position

Der Checker beweist Abdeckung über einer Menge von Tags, nicht über einem Produkt von Feldern, also wird er nicht herausfinden, dass ein Red-Arm und ein Black-Arm zusammen Node erschöpfen. Den Catch-all zu verlangen ist die Lesart, bei der ein match zur Laufzeit nie über sein Ende hinausfallen kann. Dasselbe gilt, wo es gar keine Varianten zu zählen gibt: Ein match über einem einfachen Record, dessen Arme alle ein Feld testen, braucht ein else dahinter.

Eine Stelle, an der das hinreicht, ohne dass du es erwartest, ist die Array-Position. [Black] als ganzer Arm zählte früher als Treffer für jedes Array mit einem Element, also wurde ein match, das sich darauf stützte, als erschöpfend bestätigt und nahm diesen Arm dann auch für [Red]. Ein Element in PascalCase ist auch hier eine Variantenreferenz, also ist ein solches match jetzt E0208 bei Arrays der Länge 1. Binde das Element und matche es separat. Die Übersetzung darunter ist noch die alte, deshalb wurde die Prüfung als erste Hälfte ausgeliefert.

E0208

Und der Compiler weiß, was das match erzeugt hat

Die Folgefrage entscheidet, ob irgendetwas davon trägt: Wenn du einen Wert aus einer Verzweigung bindest, kennt Glyph seinen Typ, oder zuckt es mit den Schultern und lässt tsc das später klären? Ein match nimmt jetzt den Typ seiner Arme, wenn sie übereinstimmen, und von T.parse ist bekannt, dass es Result<T, Array<Issue>> zurückgibt, die Form, über die der meiste echte Code verzweigt.

aus dem Ausgabenteiler: keine Annotation, und i ist eine Zahl 
let wire = match WireLedger.parse(decoded) {
  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },
}

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...
}
Geschichte vor 0.1.45

Bis 0.1.45 zuckte es mit den Schultern. Jeder match-Ausdruck war als unbekannt typisiert, also war ein Wert, der aus dem einzigen Verzweigungskonstrukt der Sprache kam, ab da untypisiert.

Details was still schiefging, und wie die Zusammenführung funktioniert

Beide Hälften davon sind Dinge, die früher still schiefgingen. Die Schleife erzeugt wire.expenses.entries(); wenn der Typ des Iterierten unbekannt ist, erzeugt sie stattdessen Object.entries(...), und i ist der String "0", was gültiges TypeScript ist, also war der Build sauber, und das Programm gab 01:a aus, wo 1:a gemeint war. Und wire.expensez ist jetzt [E0210] type WireLedger has no field expensez von Glyph, an der .glyph-Zeile, statt eines TS2339 im erzeugten TypeScript.

Die Zusammenführung ist Gleichheit am Kopf des Typs: Ein Arm, der mit return endet, stimmt nicht mit ab, und Arme, deren Typen sich unterscheiden, lassen das Ergebnis unbekannt wie zuvor. Eine Ebene tiefer schaut sie nur bei einem Typargument, also stimmt None => [] mit einem Array<string>-Arm überein, statt das ganze match zu versenken, und die Schleife danach bindet weiterhin eine Zahl. Dieselbe Kette über record.get funktioniert aus demselben Grund: Alle sechs Funktionen von std/record übernehmen den Werttyp aus dem Record, den du übergibst. Der Schnipsel stammt aus examples/apps/settle/main.glyph, wo die Annotation stand, die dadurch wegfiel.

Ein Lookup mit leerem Fallback

Diese Form hat am meisten gekostet. record.get auf einem Record<string, Array<string>> ist ein Option<Array<string>>, und [] ist ein Array von nichts Bestimmtem, also stimmen die beiden Arme bei Array überein, und der Elementtyp kommt aus dem Arm, der einen hat.

aus dem Abhängigkeitsauflöser: ein Lookup, ein leerer Fallback, ein indizierter Durchlauf 
let path = match record.get(res.reached, name) {
  Some(p) => p,
  None => [],
}

for i, hop in path {               # i is a number, so the indent nests
  let indent = string.repeat(STEP, i + 1)
  mut out = array.push(out, "${indent}${hop}")
}
Geschichte vor 0.1.55

Bis 0.1.55 wurden sie auf Gleichheit verglichen, [] zählte als Abweichung, und die Schleife darunter gab 01:x aus, in einem Build ohne Diagnosen, den tsc --strict bestand. Der Code ist examples/apps/depsolve/main.glyph, wo er früher mit let path: Array<string> begann, unter einem dreizeiligen Kommentar, der erklärte, dass die Annotation tragend war.

Muss ich pad_start selbst schreiben?

Die Lücke, auf die du in einem echten Programm zuerst triffst, ist kein Feature des Typsystems. Es ist der Griff nach string.slice, und da ist nichts.

was dazugekommen ist 
string.repeat(s, n)           string.slice(s, start, end?)       array.fold(xs, init, f)
string.pad_start(s, w, pad?)   string.index_of(s, needle, from?)  array.index_of(xs, x)
string.pad_end(s, w, pad?)     string.replace_all(s, from, to)     array.flat_map(xs, f)
string.trim_start(s) / trim_end(s)

# the 25-line block six apps each carried, and what replaced it:
let total = array.fold(expenses, 0, fn(sum, e) { sum + e.cents })
io.println("${string.pad_end(name, width)}  ${string.pad_start(amount, 9)}")

Diese elf Namen werden jetzt mitgeliefert, und die Kopien sind aus allen sieben Apps gelöscht, die sie hatten.

Geschichte die Kopien, die die Apps vor 0.1.47 mitschleppten

Fünf Dogfooding-Runden hintereinander meldeten dieselbe Liste, und bis 0.1.47 hatten sechs Apps in diesem Repo ihr eigenes repeat, fünf ihr eigenes pad_start, und alle eine Schleife, wo ein Fold hingehörte.

Wo sie von TypeScript abweichen

Drei davon weichen bewusst von ihren TypeScript-Namensvettern ab.

  • repeatrepeat gibt bei einer negativen Anzahl "" zurück, wo TS wirft, und genau das macht repeat(pad, width - len(s)) sicher bei einem String, der schon zu lang ist.
  • index_ofBeide index_of-Funktionen geben Option<number> zurück statt -1, weil -1 eine Zahl ist, die überall durch die Typprüfung geht, wo ein echter Index es tut, und weit vom Aufruf entfernt fehlschlägt.
  • replace_allErsetzen gibt es nur als replace_all, also gibt es keine Variante, die nur das erste Vorkommen ersetzt und mit String.prototype.replace verwechselt werden könnte, das still nur ein Vorkommen ersetzt.

Warum fold wichtig ist

fold ist dasjenige, das einer Säule dient, statt nur Tipparbeit zu sparen. mut ist die durchsuchbare Aufzeichnung jeder Stelle, an der sich Zustand ändert, und ohne Fold liefert grep mut lauter Zählschleifen, die nichts verändern, was einen Reviewer interessiert.

Das Löschen der selbstgebauten Versionen brachte examples/apps/ von 192 Mutationsstellen auf 161.

Details wie der Rewrite geprüft wurde

Der Rewrite wurde anhand der Ausgabe geprüft, nicht per Review: Alle sieben Apps liefen vorher und nachher mit festen Eingaben, 26 Dateien mit stdout, Exit-Codes und HTTP-Antworten, alle byteidentisch.

Kann ich ein Verzeichnis durchlaufen und erkennen, was kaputtging?

std/fs lieferte sechs Funktionen, und keine davon listete ein Verzeichnis.

  • fs.read_dirfs.read_dir gibt die Namen der Einträge eine Ebene tiefer zurück.
  • fs.is_dirfs.is_dir antwortet mit einem bool, wie es fs.exists tut.
  • fs.statfs.stat gibt eine FileInfo aus is_dir, is_file, size in Bytes und modified in Epoch-Millisekunden zurück, die time.format_iso direkt darstellt.

Es gibt kein rekursives walk und kein Glob; ein Durchlauf ist diese drei plus path.join in etwa zehn Zeilen.

Geschichte der Workaround, den sie ersetzt haben

Der Link-Checker in diesem Repo griff an der Stdlib vorbei auf Nodes readdirSync zu und fand heraus, welche Pfade Verzeichnisse waren, indem er versuchte, sie zu lesen, und das zurückkommende errno untersuchte. Beide Hälften davon sind behoben.

Fehlschläge haben Namen

Die Fehlerseite hat sich stärker verändert. Jetzt haben die fünf Arten, von denen sich ein Programm tatsächlich erholt, Namen, und ein errno ohne Namen kommt unverändert am Other-Ende an.

Der Checker weiß, dass diese Taxonomie abgeschlossen ist, also wird ein match auf err.kind am selben Maßstab gemessen wie eine Union, die du selbst deklariert hast: Deck die sechs ab, und du brauchst kein else, lass eine weg, und der Build schlägt mit E0200 fehl und nennt fs.ErrorKind.

E0200E0210
einen Baum durchlaufen und benennen, was schiefging 
let names = fs.read_dir(dir)?
for name in names {
  let child = path.join([dir, name])
  match fs.is_dir(child) {
    true  => visit(child),
    false => {
      let info = fs.stat(child)?
      report_size(child, info.size)
    },
  }
}

match err.kind {                        # no else arm: E0200 if you miss one
  fs.ErrorKind.NotFound         => io.eprintln("no such path"),
  fs.ErrorKind.NotADirectory    => io.eprintln("that is a file"),
  fs.ErrorKind.IsADirectory     => io.eprintln("that is a directory"),
  fs.ErrorKind.AlreadyExists    => io.eprintln("already there"),
  fs.ErrorKind.PermissionDenied => io.eprintln("cannot read it"),
  fs.ErrorKind.Other({ code })   => io.eprintln("errno ${code}"),
}
Details die alte Taxonomie, geprüfte Felder, und die Prüfung selbst ausprobieren

FsError.kind war { tag: string } mit NotFound als ganzer Taxonomie, also hieß “dieser Pfad ist ein Verzeichnis” von “dieser Pfad fehlt” zu unterscheiden, einen errno-String zu vergleichen.

fs.FsError und fs.FileInfo haben ebenfalls geprüfte Felder, also ist err.mesage E0210 an deinem Glyph-Quellcode statt eines tsc-Fehlers am erzeugten TypeScript.

Diese Prüfung ist aktiv. Lösch den Arm PermissionDenied aus dem match oben, und glyph check --no-tsc bricht mit E0200 ab: non-exhaustive match on fs.ErrorKind, missing variants PermissionDenied. Als das Stdlib-Modell zuerst geschrieben wurde, deckte es nur Rückgabetypen ab, und ein match wie dieses kompilierte sauber und warf zur Laufzeit; die Feld- und Variantenformen von fs.FsError, fs.FileInfo und fs.ErrorKind sind jetzt modelliert.

Zwei kleinere Ergänzungen

Zwei kleinere kamen mit, beide aus derselben App.

  • regex.captures_allregex.captures_all gibt dir die Capture-Gruppen jedes Treffers statt nur des getroffenen Texts, also hört ein flacher key=value-Scan auf, eine selbstgebaute Schleife zu sein.
  • task.pool_settledtask.pool_settled ist task.pool mit dem Fehlerverhalten von all_settled: begrenzte Nebenläufigkeit, ein Ergebnis pro Task, und ein toter Host kostet dich das Ergebnis dieses Hosts statt aller Ergebnisse, die der Pool gesammelt hatte.

Woher weißt du, dass es die richtigen Funktionen sind?

Weil die App, die nach ihnen gefragt hat, aufhören musste, sie zu umgehen, bevor das Release als fertig galt.

Eine Bibliotheksfunktion, die ausgeliefert wird, und ein Workaround, der sie überlebt, sind verschiedene Aussagen, also hat dieselbe Änderung, die diese vier hinzufügte, die Kopien des Link-Checkers gelöscht: den Import von readdirSync, beide errno-String-Vergleiche, 97 Zeilen selbstgebauten Scanner und den Pool, der beim ersten Fehler abbricht. 122 Zeilen fielen weg.

Zwei Verhaltensänderungen, gemessen

Zwei dieser Löschungen haben verändert, was das Programm tut, und der Unterschied wurde gemessen statt diskutiert.

  • Ein unlesbares VerzeichnisRichte die alte und die neue Version auf einen Baum mit einem Verzeichnis, das du nicht lesen kannst: Die neue gibt permission denied aus und zählt den Pfad als unlesbar, und die alte, die nur fragen konnte, ob das errno EISDIR war, ließ ihn ganz aus dem Bericht weg.
  • Eine fehlschlagende URLLass eine von drei URLs werfen: pool_settled gab alle drei Zeilen aus und nannte den Fehlschlag, und pool gab nichts aus und starb an einer unbehandelten Rejection, mitsamt den beiden guten Ergebnissen.
Details der Rewrite des Scanners und die Sorge um die Alternation

Der Rewrite des Scanners hat auch eine Design-Sorge ausgeräumt. Da eine Capture-Gruppe, die nicht beteiligt war, als "" gelesen wird, genau wie eine, die leer getroffen hat, sah es so aus, als könnte captures_all dir nicht sagen, welcher Zweig einer Alternation gegriffen hat. Es kann, wenn du die Gruppe jedes Zweigs um das ganze Konstrukt schreibst statt um den Teil, den du willst: Eine Gruppe, die gegriffen hat, beginnt dann mit `, [, ! oder < und kann nicht leer sein. Das möglicherweise leere Stück, das Link-Ziel, steckt darin und ist nie das, wonach du fragst. Das machte aus einem zeichenweisen Durchlauf über 180 Zeilen zwei Patterns und eine Verteilung über 12 Zeilen, mit byteidentischer Ausgabe auf der eigenen Dokumentation des Repos und auf einem Fixture, das gebaut wurde, um es zu brechen.

Geld läuft nicht auf Floats

Die Lücke, die eine Fintech-Evaluierung sofort beenden würde, ist Geld auf IEEE-754-number, wo 0.1 + 0.2 nicht 0.3 ist und Werte jenseits von 253 still an Genauigkeit verlieren.

std/decimal ist exakter Festkomma-Wert zur Basis 10 über BigInt: eine Ganzzahl beliebiger Genauigkeit mit einer festen Zahl von Nachkommastellen, also sind Addition, Subtraktion und Multiplikation exakt, und Division nimmt eine explizite Skala und Rundung. Ein fehlerhafter Betrag wird zu einem Err geparst, nie zu einem stillen NaN.

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

Große ganze Zahlen

Für exakte große ganze Zahlen, Konto-IDs und Zähler, gibt es den Typ bigint: Literale sind 123n, er wird zu einem echten TypeScript-bigint, und ein Record-Feld vom Typ bigint validiert typeof === "bigint" an der Systemgrenze, also wird eine ID, die als JSON-number geschickt wird, abgelehnt statt jenseits von 253 still gerundet.

Ein async-Callback hat endlich einen Typ

Ein Funktionstyp war fn(A) -> T und sonst nichts, was zu (a: A) => T wird. Ein async-Rumpf passt da nicht hinein, also musste eine Funktion, die einen verzögerten Task zurückgibt, oder ein Record aus async-Handlern ohne Annotation bleiben, und der Checker schaute nicht mehr hin.

async fn(A) -> T ist dieser fehlende Typ. Er wird zu (a0: A) => Promise<T>, und async fn() ohne Rückgabe wird zu () => Promise<void>.

ein verzögerter Task und eine Map von Handlern 
fn task_for(url: string) -> async fn() -> Fetched {
  return async fn() -> Fetched { return { url: url, body: await fetch_one(url) } }
}

type Handler = async fn(string) -> string

async fn dispatch(routes: Record<string, Handler>, name: string, arg: string) -> string {
  return match record.get(routes, name) {
    Some(h) => await h(arg),
    None    => "no route",
  }
}
Details wie Glyph einfache und async-Funktionen auseinanderhält

Glyph hält die beiden selbst auseinander, statt es tsc zu überlassen: Eine einfache Funktion, wo eine async-Funktion erwartet wird, ist E0204 bei einem Return und E0211 bei einem Aufrufargument, und die Meldung nennt beide Seiten.

Der eine Fall, den es nicht beurteilt, ist eine Rückgabe vom Typ void, bei der TypeScript jede Funktion zulässt.

Ein rekursiver Typ, bis ganz unten gematcht

Eine Union kann sich selbst in ihrem eigenen Payload nennen, mit ihren Typparametern, und ein match-Arm kann ein Konstruktor-Pattern im Feld eines anderen Konstruktor-Patterns verschachteln. Zusammen sind die Balancierungsregeln eines Rot-Schwarz-Baums vier Arme: Jeder nennt genau die Form, die er umschreibt, und der Compiler prüft die Form, statt eines Kommentars darüber, der sie behauptet.

einer der vier Rotationsfälle 
type Tree<K, V> =
  | Leaf
  | Node({ color: Color, left: Tree<K, V>, key: K, value: V, size: int, right: Tree<K, V> })

fn balance<K, V>(t: Tree<K, V>) -> Tree<K, V> {
  return match t {
    Node({ color: Black, left: Node({ color: Red, left: Node({ color: Red, left: a, key: xk, value: xv, right: b }), key: yk, value: yv, right: c }), key: zk, value: zv, right: d }) => node(
      Red,
      node(Black, a, xk, xv, b),
      yk,
      yv,
      node(Black, c, zk, zv, d),
    ),
    // the other three cases, then:
    other => other,
  }
}

Wo es aufhört 11

Sichtbarkeit

  • Ein privater Import meldet dieselbe Meldung wie ein fehlender Name
    Details

    Ein privater Import meldet “not exported by M”, dieselbe Meldung wie ein fehlender Name; “privat, markier es mit pub” von “kein solcher Name” zu unterscheiden, ist eine eingeplante Verfeinerung.

  • Ein privater Wert, über einen Namespace gelesen, ist ein tsc-Fehler, kein Glyph-Fehler
    Details

    Sichtbarkeit wird bei Typannotationen geprüft, nicht bei Werten, die über einen Namespace gelesen werden: lib.helper(), wo helper privat ist, ist weiterhin ein tsc-Fehler statt eines Glyph-Fehlers.

Async

  • Ein await auf oberster Ebene in einem const-Initialisierer auf Modulebene ist erlaubtE0222
    Details

    Der async-Kontext wird jetzt geprüft (E0222), außer an einer Stelle: Ein const-Initialisierer auf Modulebene hat nichts Aufrufbares um sich, also ist ein await auf oberster Ebene dort erlaubt, und das erzeugte ESM führt es aus.

Abgeleitete Typen

  • Arme, die beim Kopf des Typs nicht übereinstimmen, lassen das Ergebnis für Glyph unbekannt
    Details

    Die Zusammenführung der Arme verlangt weiterhin, dass die Arme beim Kopf des Typs übereinstimmen: Wenn sie verschiedene Typen erzeugen, ist das Ergebnis für Glyph unbekannt, und nur tsc prüft, was du damit machst.

  • Neun Stdlib-Funktionen sind in derselben Lage
    Details

    Neun Stdlib-Funktionen sind in derselben Lage. Sechs nehmen ein optionales letztes Argument (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify), und die Prüfung der Argumentanzahl vergleicht eine Zahl mit einer Zahl, also würde ihre Modellierung bei jedem Aufruf, der das letzte Argument weglässt, einen falschen Fehler melden; array.map, flat_map und zip nehmen ihren Elementtyp aus einem Callback, in den der Checker nicht hineinschaut.

    Ein Wert direkt aus diesen neun braucht eine Annotation, bevor du ihn mit einem Index durchläufst, und ein match auf string.index_of ohne None-Arm baut weiterhin sauber und wirft zur Laufzeit. array.index_of ist modelliert und meldet E0200.

  • Member und Argumentanzahl gegen einen Wert, den der Checker nicht typisieren konnte, bleiben ungeprüft
    Details

    Member und Argumentanzahl gegen einen Wert, den der Checker nicht typisieren konnte, bleiben an dieser Grenze ungeprüft, statt ein Fehler zu sein.

Bibliothek

  • string indiziert UTF-16-Codeeinheiten, und kein chars oder char_at ist geplant
    Details

    Auf der Bibliotheksseite indiziert string UTF-16-Codeeinheiten, wie es len und split immer getan haben, und das ist entschieden: Es gibt kein chars oder char_at, und keins ist geplant, weil eine zurückgegebene Surrogat-Hälfte bis zu dem Moment wie ein Zeichen aussieht, in dem sie ausgegeben wird. Kodier mit encoding.hex_encode und lies jeweils zwei Hex-Ziffern.

  • captures_all liefert keine Offsets; fs.read_dir behält die Reihenfolge des Betriebssystems
    Details

    captures_all liefert Gruppen und keine Offsets, also schreibt ein Scanner, der wissen muss, wo in der Zeile ein Treffer begann, weiterhin seine eigene Schleife, und fs.read_dir liefert Einträge in der Reihenfolge des Betriebssystems, also sortiere sie, wenn die Ausgabe reproduzierbar sein muss.

Patterns

  • Ein Payload-Konstruktor in einem Feld scheitert auf einer Union, die über einen Namespace-Import erreicht wirdE0300
    Details

    Ein verschachteltes Feld-Pattern hat noch eine Grenze: ein Konstruktor mit Payload, in einem Feld, auf einer Union, die über einen Namespace-Import erreicht wird. import tree { Node } und dann Node({ left: Node({ key: k }) }) kompiliert, und import tree und dann tree.Node({ left: tree.Node({ key: k }) }) ist E0300 auf derselben Union.

  • Eine Union, die über ihren eigenen Parameter generisch ist, nimmt den verschachtelten Arm und wird auf fehlende Varianten geprüftE0200
    Details

    Die andere Grenze ist weg: Eine Union, die über ihren eigenen Parameter generisch ist (type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> })), lehnte früher den verschachtelten Arm ab, den dieselbe Union ohne den Parameter akzeptiert, und nimmt ihn jetzt, bei einem offenen Typparameter und bei einer konkreten Instanziierung gleichermaßen. Derselbe Lookup entschied, ob das match überhaupt auf fehlende Varianten geprüft wurde, also konnte bis zu diesem Release ein match auf Tree<K> Leaf weglassen, sauber bauen, tsc --strict bestehen und zur Laufzeit werfen, wo die nicht generische Schreibweise E0200 war.

    Beide Schreibweisen melden es, und die Union einen Import weiter zu verschieben ändert die Antwort nicht mehr: Ein match auf einem importierten Tree<string>, das Leaf weglässt, ist E0200 und nennt Leaf, genau wie beim importierten nicht generischen Tree. Das war ein anderer Codepfad, separat geprüft, und er lief bis zu diesem Release andersherum: sauberer Build und Wurf zur Laufzeit.

  • Die Abdeckung einer importierten Union prüft nie ihre Varianten-Payloads
    Details

    Eine Sache an der Abdeckung einer importierten Union solltest du noch kennen, bevor du dich darauf stützt: Ihre Varianten-Payloads werden ebenfalls nie geprüft, also matcht B(X), wo X eine Variante der eigenen Union des Payloads ist, jedes B, statt das fehlende Y zu melden, und das hat nichts mit Generics zu tun.

    Ein Feld zu binden oder darin einen Tag ohne Payload zu matchen funktioniert in jedem Fall.
