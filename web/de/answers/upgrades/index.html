Nicht, ohne dass du danach fragst. Ein Glyph-Projekt pinnt seinen Compiler auf eine exakte Version, also erreicht ein Release, das heute Morgen veröffentlicht wurde, deinen Build nicht heute Nachmittag. Vor 1.0 darf ein Release eine Diagnose hinzufügen, die Code ablehnt, der gestern kompiliert hat, und meistens ist genau das der Sinn des Releases, also ist die Entscheidung, eins zu übernehmen, deine, und es ist ein einziger Befehl.

  1. Warum der Pin exakt ist
  2. Erfahren, dass es ein Release gibt

Warum das wichtig ist

Die meisten Tools pinnst du mit einem Caret, weil ein Patch-Release ein Bugfix ist. Ein Compiler vor 1.0 ist das nicht.

Details warum neue Fehler die guten Releases sind

Glyphs ganze Aufgabe ist es, Programme abzulehnen, und darin besser zu werden heißt neue Fehler: eine strengere Prüfung bei einem Import, ein Loch in der Erschöpfendheit, durch das früher etwas rutschte, eine Argumentanzahl, die der Checker nicht modelliert hatte. Diese Releases sind die guten. Sie sind auch genau die, die du nicht über ein npm install bekommen willst, das du ausgeführt hast, um eine Datumsbibliothek hinzuzufügen.

Deshalb schreibt glyph init kein ^. Bei einer 0.x-Version lässt ein Caret den Patch weiterhin schwimmen, und genau das ist die Falle: ^0.1.9 akzeptiert stillschweigend jedes spätere 0.1.x.

Committe die package-lock.json daneben, und ein frischer Klon baut mit der Toolchain, die du getestet hast, nicht mit dem, was seitdem erschienen ist.

Die andere Hälfte

Ein Pin hat einen offensichtlichen Fehlermodus: Du sitzt ein Jahr auf einem alten Compiler und erfährst es nie. Also sagt es dir der Compiler, wenn du ihn irgendetwas über dein Setup fragst:

Details warum der Compiler der Kanal ist

Nichts auf deinem Rechner würde es dir sagen, und eine Website, an deren Besuch du denken musst, ist kein Kanal.

glyph doctor 
glyph — 0.1.72
  [update]   0.1.73 is published — `glyph --update` moves this compiler, `glyph upgrade` moves a project's pin
             what changed: https://glyphlang.io/versions/

glyph doctor — JavaScript toolchain
  [ok]       node: v22.1.0
  [ok]       tsx: tsx v4.19.0
  [ok]       tsc: Version 6.0.2
All good. `glyph run` and `glyph build --check` are ready.

Ein neueres Release zu finden ändert nie den Exit-Code, also kannst du das bedenkenlos in CI ausführen.

Details CI, offline, und was nie das Netzwerk berührt

Ein veröffentlichtes Release ist keine kaputte Toolchain, und eine grüne Pipeline sollte nicht rot werden, weil jemand vor zehn Minuten etwas veröffentlicht hat. Wenn der Rechner offline ist, sagt die Prüfung das und macht weiter; --offline überspringt sie ganz und macht überhaupt keinen Netzwerkaufruf.

Nichts anderes kontaktiert die Registry. build, run und check tun es nie. Ein Compiler, der bei jedem Build nach Hause telefoniert, ist ein anderes Produkt.

Das Upgrade übernehmen

Es schreibt eine Zeile neu und führt npm install aus. Es fasst deinen Quellcode nicht an, und es tut nicht so, als wäre das Upgrade fertig: Danach zu bauen ist der Sinn der Sache, weil das Release, das du gerade übernommen hast, Meinungen haben darf, denen dein Code noch nicht begegnet ist.

Eine Zeile ändert sich, und du entscheidest wann 
$ glyph upgrade --dry-run
glyph upgrade: would move /app/package.json from 0.1.72 to 0.1.73 (nothing written).

$ glyph upgrade
glyph upgrade: /app/package.json now pins 0.1.73 (was 0.1.72).
glyph upgrade: what changed: https://glyphlang.io/versions/
glyph upgrade: build before you commit; a new release may report diagnostics
               this project did not have.
Details eine Version wählen, die Installation überspringen

--to <version> nennt eine bestimmte Version, auch eine ältere, wenn du zurück willst, und --no-install überlässt die Installation dir.

Das Tool bewegen, nicht das Projekt

upgrade verschiebt einen Pin in einer package.json. glyph --update ist die andere Hälfte.

Die Aufteilung ist jetzt eine Regel und kein Zufall: Flags wirken auf das Tool, so wie --version, --help und --explain, und Unterbefehle wirken auf deinen Code.

Geschichte was doctor früher ausgegeben hat

upgrade ist der falsche Befehl, wenn der Compiler in deinem PATH veraltet ist, und eine Zeit lang hat doctor ihn trotzdem ausgegeben und eine globale Installation auf ein Manifest verwiesen, das sie vielleicht gar nicht hat.

glyph --update 
$ glyph --update
glyph 0.1.72 is installed; 0.1.73 is published.
Release notes: https://glyphlang.io/versions/
A 0.1.x release may reject code that compiled before, so read the notes for anything between these two.

Running: npm install -g @glyphlang/glyph@0.1.73
   ... npm output ...

npm finished. Confirm with:
    glyph --version

--update-dry-run hört auf, nachdem es den npm-Befehl ausgegeben hat, den es ausgeführt hätte.

  • Nur eine Installation, die es identifizieren kannEs aktualisiert nur eine Installation, die es identifizieren kann. Ein Compiler, der über npx erreicht wird, aus einem Glyph-Quellbaum gebaut wurde oder unter einem Pfad liegt, den es nicht erkennt, bekommt den Befehl ausgegeben, und nichts wird überschrieben, weil das Ersetzen eines Homebrew-Binarys oder eines cargo build von jemandem auf Verdacht einen PATH hinterlässt, der auf etwas zeigt, das niemand gewählt hat.
  • Keine Behauptung, dass es angekommen istEs behauptet auch nicht, dass das Update angekommen ist: npm kann mit null enden, nachdem es eine optionalDependency übersprungen hat, die es nicht holen konnte, und so wurde einmal ein Glyph-Release ohne Plattform-Binary ausgeliefert, also nennt die letzte Zeile glyph --version als Prüfung, statt Erfolg zu behaupten.

Wo es steht

Heute verfügbar

  • Angelegte Projekte pinnen exakt, also erreicht kein Release versehentlich einen Build.
  • glyph doctor vergleicht deinen Compiler mit der Registry und verlinkt die Release Notes, ohne je seinen Exit-Code zu beeinflussen oder von build/run/check aus erreichbar zu sein.
  • glyph upgrade verschiebt den Pin, installiert ihn und liest ein Caret aus einem älteren Projekt, damit auch bestehende Projekte auf einen exakten Pin umgestellt werden können.
  • glyph --update aktualisiert den Compiler selbst, für eine globale npm-Installation, und meldet für jeden anderen Weg, auf dem er dorthin gekommen sein könnte, statt zu raten.

Wird schärfer

  • Die Release Notes sind eine Seite für die ganze Versionslinie, also verlinkt glyph upgrade die Seite statt den Eintrag für die Version, auf die du wechselst.
  • Noch sagt dir nichts, welche der Diagnosen des neuen Releases dein Code gleich auslösen wird: Um das herauszufinden, musst du bauen, und deshalb sagt der Befehl das.
  • Und ein Upgrade über mehrere Releases auf einmal ist derselbe einzelne Schritt wie über eins, ohne Zusammenfassung dessen, was sich dazwischen angesammelt hat.
  • glyph --update ruft npm auf und liest seinen Exit-Code, also kann es dir sagen, dass npm fertig ist, aber nicht, dass das Binary im PATH die Version ist, die du wolltest; deshalb verweist es auf glyph --version, statt zu sagen, dass es geklappt hat.
