Weil jede dieser Garantien Opt-in ist und ein Agent jede davon mit einer Zeile umgehen kann. Glyphs Strenge ist keine Konfigurationsdatei, die der Agent bearbeiten kann. Sie ist die Sprache. Der Punkt der Durchsetzung wandert von "haben wir daran gedacht, diese Datei zu linten" zu "kompiliert es".

Ein gut konfiguriertes TypeScript-Setup bringt dich weit, und wenn dein Team all das in CI ausführt, hast du die meisten Lücken, auf die Glyph zielt, schon geschlossen. Es ist die Alternative, die man ernst nehmen sollte, also hier die Gegenüberstellung:

01 Nicht optional schlägt Opt-in

Jede dieser Hintertüren ist eine Konfiguration, die der Agent bearbeiten kann. Glyph hat keine solche Hintertür: Es gibt kein as, kein Ignore-Pragma und keinen Weg, einen typisierten Wert aus unknown zu bekommen, ohne eine Prüfung, die der Compiler sehen kann.

TypeScript: Die Hintertüren gibt es handler.ts 
const user = body as unknown as User;
// @ts-ignore
doThing(user.mispelled);
// eslint-disable-next-line
return anything as any;
Glyph: nichts zum Abschalten handler.glyph 
return match User.parse(body) {
  Ok(user) => use(user),
  Err(_) => fallback(),
}
// no `as`, no ignore pragma,
// no lint to switch off.

Strenge, die der Agent nicht per Konfiguration abschalten kann, sitzt an einem anderen Punkt der Durchsetzung als Strenge, bei der er es kann. Auf diesem Unterschied ist Glyph gebaut.

Details was ein Agent an eslint vorbei schreiben kann

Deine eslint-Konfiguration schützt nur Code, den der Agent durch sie leitet, und der Agent kann as unknown as User, @ts-ignore oder // eslint-disable-next-line schreiben oder einfach das .exhaustive() vergessen, und es kompiliert trotzdem und wird gemergt.

02 Der Typ ist der Validator: kein zweites Artefakt

In Glyph ist der Typ der Validator: Die Deklaration type User = {...} erzeugt User.parse gleich mit. Ein Artefakt, nichts synchron zu halten, nichts zu vergessen.

  • zod: zuerst das Schemazod kehrt deine maßgebliche Quelle um: Du schreibst das Schema, leitest den Typ daraus ab und hältst dann Typ, Schema und jeden Serializer von Hand synchron.
  • Wo Abweichungen entstehenGenau beim Synchronhalten führt ein Agent Abweichungen ein: Er benennt ein Feld im Typ um, aber nicht im Schema, und beides kompiliert trotzdem.

03 Durchsuchbare Mutation

In Glyph lebt gemeinsamer Zustand in einem Store, und jede Änderung ist ein wörtliches .set(/.update(; grep 'mut ' findet jede lokale Mutation. Normales TypeScript hat keine Entsprechung.

Details wo sich ein Schreibzugriff in TypeScript verstecken kann

In TypeScript kann sich eine Zustandsänderung hinter =, .push(), Object.assign, einem Setter oder einem Spread verstecken. Es gibt kein einzelnes Token, nach dem man suchen kann, und keine Lint-Regel behebt das ganz.

Der Unterschied im Fehlerfall

Dieselbe Aufgabe, ein Agent fügt einer Union eine Variante hinzu und vergisst, sie an einer von drei Stellen zu behandeln:

TS mit Tooling 
// ts-pattern .exhaustive() catches it,
// IF every site used ts-pattern and
// nobody wrote a default: case or a
// switch that only logs. Those
// compile green and skip the new case.
Glyph 
[E0200] non-exhaustive match on
`Feed`: missing variant `Archived`
// every unhandled match, everywhere,
// fails the build. No opt-in, no
// escape, no forgotten default.

Wo TypeScript mit Tooling noch vorn liegt

Vier Stellen, an denen es heute vor Glyph liegt:

  • Reichhaltigere Validierung.Glyph-Deskriptoren sind standardmäßig strikt (sie lehnen nicht deklarierte Schlüssel ab), und eine where-Verfeinerung legt ein Prädikat auf ein Primitiv (type Email = string where value.includes("@")), das der Deskriptor an jeder Grenze ausführt, die der Typ erreicht. zod liegt in zwei Punkten noch vorn: Es liefert fertige Prüfungen wie .email() und .url(), die du in Glyph selbst schreibst, und es verfeinert ganze Objekte, während ein where auf einem Record (lo <= hi über zwei Felder) heute E0300 ist.
  • Tieferes Matching.Die Guards und tiefen strukturellen Patterns von ts-pattern gehen über das hinaus, was Glyphs match ausdrückt.
  • "Nachweisbares Fehlen" endet an der .ts-Grenze.Glyphs Garantien gelten für Code, den Glyph erzeugt hat; eine Exception aus einer npm-Abhängigkeit umgeht Result weiterhin, und ein importierter .d.ts-Typ hat keinen Laufzeit-Deskriptor.
  • Ökosystem und Recruiting.Das TypeScript-Tooling, die Community und der Pool an Entwicklern sind viel größer, mit Jahren im Produktionseinsatz dahinter. Glyph ist eine frühe Vorschau.

Wenn du TypeScript mit Tooling vollständig verdrahtet hast und deine Agenten darin bleiben, hast du das meiste davon. Glyphs Argument ist, dass "darin bleiben" der tragende Teil des Satzes ist, und genau den bricht ein Agent. Nicht optionale Prüfungen, Validierung mit einem einzigen Artefakt und durchsuchbare Mutation sind die Teile, die du nicht bekommst, indem du mehr Opt-in-Tools hinzufügst.

Wenn du bereit bist, TypeScript für eine ältere typisierte Sprache zu verlassen, die zu JavaScript kompiliert, vergleicht Warum nicht ReScript, Gleam oder Elm? Glyph mit diesen.

Wo es steht

Heute verfügbar

  • Kein any/as.
  • Erschöpfendes match.E0200E0218
  • Warnung bei verworfenem Result.E0217
  • Aus Typen erzeugte Validatoren.
  • Durchsuchbare Mutation.
  • Alles nicht optional, nichts davon eine eslint-Regel, die du abschalten kannst.
    Details

    Kein any/as, erschöpfendes match (E0200/E0218), Warnung bei verworfenem Result (E0217), aus Typen erzeugte Validatoren und durchsuchbare Mutation: alles nicht optional, nichts davon eine eslint-Regel, die du abschalten kannst.

Wird gemessen

  • Die Aussage, dass Agenten in Glyph weniger durchgerutschte Fehler produzieren als in gut konfiguriertem striktem TS, ist der Benchmark, den wir aufbauen, gegen TS mit Tooling, nicht gegen naives TS. Siehe die Benchmarks.
