Fälle, die TypeScript durchlässt

Gefunden, bevor es ausgeliefert wird

Insgesamt gibt es 46 geprüfte Fälle: 37 TypeScript-Fälle, 5 JavaScript-Fallen, die es in Glyph nicht gibt, und 4 Lücken, die Glyph noch nicht schließt. Glyph lehnt 28 davon beim Build ab (23 TypeScript-Fälle und 5 Fallen).

Jedes TypeScript-Beispiel in der Liste besteht tsc --strict ohne Fehler. Jedes wird außerdem gegen ein maximal konfiguriertes Projekt geprüft: alle Compiler-Flags, die strenger als --strict sind, dazu typescript-eslint strictTypeChecked. Von den 37 Fällen erkennt dieses Setup 21 überhaupt nicht. Ein standardmäßig deaktiviertes Compiler-Flag findet 5, eine Lint-Regel 11. Ein Projekt muss jedes davon einschalten, und ein Agent kann es wieder ausschalten. In Glyph ist keins davon eine Konfigurationsoption.

Jeder Eintrag besteht aus zwei Programmen in catches/, und die Ausgabe unter jedem ist das, was die Tools ausgegeben haben. Ein Build-Gate, scripts/check_catches.py, führt jeden Fall erneut aus und schlägt fehl, wenn eine der beiden Hälften nicht mehr tut, was die Seite sagt. Die vollständige TypeScript-Konfiguration, gegen die es prüft, steht in diesem Skript.

2

Ein Fall, den niemand behandelt hat

Wahrscheinlichkeit 5 von 5Schwere 4 von 5

Ein Agent fügt einen Status "archived" hinzu. Der Handler, der jeden Status meldet, wurde geschrieben, bevor es ihn gab.

TypeScriptkompiliert ohne Warnung
ts.ts
switch (s) {
  case "todo":
    console.log("not started");
    break;
  case "doing":
    console.log("in progress");
    break;
  case "done":
    console.log("finished");
    break;
}
$ tsx ts.ts
finished
archived logged nothing

Das Archivieren eines Eintrags loggt nichts. Nichts sagt, dass der switch veraltet ist.

Nur Lintgefunden durch die Lint-Regel switch-exhaustiveness-check

Glyphbeim Build abgelehnt
glyph.glyph
match s {
  "todo" => print("not started"),
  "doing" => print("in progress"),
  "done" => print("finished"),
}
$ glyph build
[E0200] Error: typecheck: non-exhaustive match on `"todo" | "doing" | "done" | "archived"`: missing variants "archived"
Help: Add an arm for each missing variant.

Der Build bricht ab und nennt den Fall.

TypeScript prüft nur dann, ob ein switch jeden Fall abdeckt, wenn die Funktion aus jedem Zweig einen Wert zurückgibt, oder mit dem Idiom assertNever. Ein Handler, der nichts zurückgibt, bekommt keins von beidem. In Glyph muss jedes match jeden Fall abdecken, also listet eine neue Variante jede Stelle, die sich ändern muss.

3

find mit ! vertrauen

Wahrscheinlichkeit 5 von 5Schwere 4 von 5

Einen Record per ID nachschlagen.

TypeScriptkompiliert, stürzt dann zur Laufzeit ab
ts.ts
return users.find((u) => u.id === id)!.name;
$ tsx ts.ts
TypeError: Cannot read properties of undefined (reading 'name')

Nur Lintgefunden durch die Lint-Regel no-non-null-assertion

find gibt ein Option zurück, also muss der leere Fall behandelt werden.

Ohne das ! lehnt tsc --strict diese Zeile ab. Das ! ist genau das, was diese Prüfung abschaltet, und zur Laufzeit tut es nichts. Glyph hat kein !.

Ein Schlüssel, der vielleicht nicht existiert

Wahrscheinlichkeit 4 von 5Schwere 3 von 5

Ein Feld aus einer Zeile von Strings lesen, mit falsch geschriebenem Namen.

TypeScriptkompiliert, gibt dann undefined aus
ts.ts
export function nameOf(row: Record<string, string>): string {
  return row.naem;
}
$ tsx ts.ts
undefined

Jeder Schlüssel liest sich als string, auch einer, den es nicht gibt, also gibt das falsch geschriebene Feld undefined aus.

Standardmäßig ausgefunden durch das Compiler-Flag noUncheckedIndexedAccess

Glyphbeim Build abgelehnt
glyph.glyph
pub fn name_of(row: Record<string, string>) -> string {
  return row.naem
}

Help: Use `record.get(map, "key")`, which returns `Option<V>` so the absent case has somewhere to go. `record.has` tests for the key alone.

Ein Lesezugriff auf eine Map sagt, dass er leer sein kann, also muss der Code sagen, was dann passiert.

TypeScripts Record<string, string> behauptet, dass jeder mögliche Schlüssel einen String hat. Glyph behandelt es als Map, in der ein Lookup nichts finden kann, und lehnt deshalb auch das korrekt geschriebene row.name ab.

5 JavaScript-Fallen, die es in Glyph nicht gibt

Ältere Fallen, in die Agenten immer noch ab und zu tappen. Glyph lehnt jedes dieser Programme ab, aber nicht, weil es den Fehler erkennt: Das Feature dahinter gibt es in der Sprache nicht, und der Ersatz wird genannt.

  • "10,20,30".split(",").map(parseInt) ergibt [10, NaN, NaN], weil map den Index als Zahlenbasis übergibt. Glyph hat number.parse, das ein Result zurückgibt. Im Playground öffnen
  • Eine /g-Regex, die mit .test wiederverwendet wird, schlägt bei jedem zweiten Treffer fehl, weil sie sich lastIndex merkt. Glyph hat keine Regex-Objekte; regex.matches(pattern, text) hat keinen Zustand. Im Playground öffnen
  • [1, 2, 3].forEach(counter.increment) führt die Methode ohne ihr Objekt aus. Glyph hat keine Klassen und kein this. Im Playground öffnen
  • Math.max(...[]) ist -Infinity. Glyphs array.max gibt ein Option zurück, leer bei einer leeren Liste. Im Playground öffnen
  • Array(3).map(...) gibt drei Löcher zurück, weil map sie überspringt. Glyph hat kein Array(n); Arrays werden als Literale geschrieben. Im Playground öffnen

Was Glyph noch nicht findet

4 Lücken, die Glyph noch nicht schließt. Jede davon kompiliert heute in Glyph und macht dasselbe Falsche wie in TypeScript. Jede hat eine Reproduktion in catches/ und eine offene Gap-Nummer, und das Gate schlägt fehl, sobald ein Fix landet, damit der Eintrag die Lücke nicht überlebt.

  • requested || 3 macht aus einer echten 0 eine 3. G386
  • Ein verlorenes Update über ein await hinweg auf c[0], wo derselbe Schreibzugriff auf ein Feld abgelehnt wird. G390
  • input + 1 auf einem String, users.find(...).name und ein Feldzugriff auf unknown werden nur vom tsc-Schritt gefunden, nicht von Glyphs eigenem Checker, also übersehen sie der Editor und die Agenten-Tools. G381, G382

Logikfehler sind in jeder Studie zu Code von Agenten die größte Klasse, und kein Typchecker sieht sie: Eine falsche Formel oder eine falsch verstandene Aufgabe kompiliert in Glyph genauso wie in TypeScript.

Glyph hat eine einzige Hintertür, extern_ts, für TypeScript, das es nicht ausdrücken kann. Es ist ein festes Schlüsselwort, also listet grep extern_ts jede Stelle, an der die Regeln ausgesetzt sind.
