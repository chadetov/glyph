Umstieg von TypeScript

Was sich ändert, wenn du schon TypeScript schreibst

Weniger, als du denkst. Glyph kompiliert zu TypeScript, das tsc --strict besteht, behält npm und dein Deployment bei und liest sich fast gleich. Die Unterschiede sind eine Handvoll, und jeder tauscht eine Möglichkeit, falsch zu liegen, gegen eine Prüfung des Compilers.

Wenn du TypeScript kannst, kennst du das meiste schon#

Du lernst keine neue Sprache, nur diese vier Dinge. Sie kommen in jedem Beispiel auf dieser Website vor.

match
Ein erschöpfender switch: Über einer Union zwingt dich der Compiler, jeden Fall zu behandeln. In Anweisungen und Ausdrücken ist es auch die einzige Bedingung: Es gibt kein if/else und keinen ternären Operator, unten erklärt. JSX hat die Elemente <if> und <match>.
Result<T, E>
Fehler als Rückgabewerte statt geworfener Exceptions. Du behandelst einen mit match oder reichst ihn mit dem Operator ? weiter.
fn f() -> T
Eine Funktion; der -> ist ihr Rückgabetyp. Ein type X = {...} ist ein Record, und ein type X = A | B ist eine Tagged Union.
mut x = e
Neuzuweisung ist explizit und durchsuchbar. Ein einfaches let-Binding ändert sich nie unter dir; um eines zu ändern, schreibst du mut.

Eine React-Komponente in beiden#

Dieselbe Komponente zweimal: eine Liste von Einladungen mit leerem Zustand, eine Zeile, die die noch offenen zählt, und ein Label in jeder Zeile. Wo das TSX && und ? : verwendet, verwendet Glyph JSX-Elemente: <match>, das einen Wert und ein <case> pro Muster nimmt, und <if> mit einem optionalen <else>, die leichtere Form für einen einfachen Boolean. Listen schreibst du mit <for>, und das Attribut heißt class, das zu className kompiliert.

InviteList.tsx 
export type Invite = { email: string; accepted: boolean };

export function InviteList(props: { invites: Invite[] }) {
  const waiting = props.invites.filter((i) => !i.accepted).length;
  return (
    <section>
      {waiting > 0 && <p className="note">{waiting} waiting for a reply</p>}
      {props.invites.length === 0 ? (
        <p className="empty">No invites sent yet.</p>
      ) : (
        <ul>
          {props.invites.map((invite) => (
            <li key={invite.email}>
              {invite.email}
              {invite.accepted ? (
                <span className="ok">joined</span>
              ) : (
                <span className="wait">pending</span>
              )}
            </li>
          ))}
        </ul>
      )}
    </section>
  );
}
invites.glyph 
module invites

import std/array

pub type Invite = { email: string, accepted: bool }

pub component InviteList(props: { invites: Array<Invite> }) {
  let waiting = array.filter(props.invites, fn(i: Invite) { return !i.accepted }).length
  return <section>
    <if cond={waiting > 0}>
      <p class="note">{waiting} waiting for a reply</p>
    </if>
    <match value={props.invites.length}>
      <case 0>
        <p class="empty">No invites sent yet.</p>
      </case>
      <case else>
        <ul>
          <for invite in={props.invites} key={invite.email}>
            <li>
              {invite.email}
              <if cond={invite.accepted}>
                <span class="ok">joined</span>
              </if>
              <else>
                <span class="wait">pending</span>
              </else>
            </li>
          </for>
        </ul>
      </case>
    </match>
  </section>
}

Die Glyph-Hälfte ist länger, vor allem weil jeder Zweig ein eigenes Element ist. Ein <match> muss jeden Wert abdecken: Nimm hier <case else> weg, und der Build bricht mit E0218 ab. Über einer Union muss es jede Variante abdecken (E0200), und dort zahlen sich die zusätzlichen Zeilen aus: Funktioniert es mit React? zeigt ein Beispiel mit Hooks und Context.

Editor-Unterstützung und Debugging haben eigene Antworten: die Antwort zu den Werkzeugen behandelt den Language Server und die VS-Code-Erweiterung, die Antwort zum Debugging die Source Maps zurück zur .glyph-Datei. In der Entwicklung baut glyph build --watch das TypeScript bei jedem Speichern einer .glyph-Datei neu. Ein Vite-Dev-Server, der diese Ausgabe importiert, lädt nach jedem Neubau die ganze Seite neu, statt die Komponente im laufenden Betrieb auszutauschen, also geht der State der Komponente verloren; deine eigenen .tsx-Dateien behalten Vites Hot Reload. Schreib die Ausgabe außerhalb von Vites Build-Verzeichnis (dist/ standardmäßig), weil der Dev-Server dieses Verzeichnis nicht beobachtet.

"Agenten" meint auf dieser Website KI-Coding-Assistenten wie Claude, Copilot und Cursor. Glyph hilft ihnen am meisten, aber die Prüfungen sind dieselben, egal ob ein Mensch oder ein Modell den Code geschrieben hat. Wenn du schon striktes TypeScript mit zod und eslint einsetzt, steht hier, was eine Sprache darüber hinaus bringt.

Es gibt keine if-Anweisung#

Eine Verzweigung über einem Boolean ist ein match auf true und false. Wenn du nur auf einer Seite etwas tust, ist der andere Arm ein leerer Block. JSX ist die Ausnahme: Das <if>-Element in der Komponente oben rendert seine Kinder, wenn die Bedingung gilt, und sonst nichts.

TypeScript 
function label(admin: boolean): string {
  return admin ? "admin" : "member";
}

if (verbose) {
  console.log("starting");
}
Glyph 
fn label(admin: bool) -> string {
  return match admin {
    true => "admin",
    false => "member",
  }
}

match verbose {
  true => io.println("starting"),
  false => {},
}

Der Grund ist Entscheidung D3 in der Spezifikation: ein Konstrukt zum Verzweigen über einen Wert, also eine Form, die man liest, schreibt und sucht. Ein Wert, der aus einer Verzweigung kommt, kommt immer aus einem match, dessen Ergebnistyp Glyphs eigener Checker bestimmt, statt ihn tsc zu überlassen. Bei einer Union ist dasselbe Konstrukt dasjenige, das jeden Fall abdecken muss (E0200). Bei einem Boolean bringt das wenig, denn false => {} sagt nicht mehr als ein weggelassenes else.

Es kostet dich etwas. Ein einzeiliger ternärer Ausdruck wird zu einem vierzeiligen match, ein vorzeitiges Return unter einer Bedingung ist ein match mit einem leeren Arm, und es ist das Erste, was einem TypeScript-Leser falsch vorkommt. Die Spezifikation hält die Ausführlichkeit als akzeptierte Kosten fest. Trotzdem if zu schreiben ist der Fehler E0006, dessen Hilfe die match-Form zeigt; ein ternärer Ausdruck ist E0013 mit derselben Hilfe.

Der Preis, den du schon zahlst#

Wenn du mit KI-Agenten an einer TypeScript-Codebasis arbeitest, sind das die täglichen Kosten. Jede hat in Glyph eine konkrete Antwort, verlinkt in der Liste.

  • Agenten halluzinieren APIs, weil TypeScript seine Typen löscht und die Laufzeit nicht mehr mit der Compile-Zeit übereinstimmt. Glyph-Typen bringen eine Laufzeitprüfung mit (T.parse, T.is), siehe typisierte APIs.
  • Agenten überkleistern Unsicherheit mit any und as unknown as T, und der Compiler lässt sie. Beides gibt es in Glyph nicht, siehe die Tabelle unten.
  • Du bittest um eine einzeilige Änderung und bekommst eine komplett neu geschriebene Datei, weil der Formatter bei jeder Änderung kaskadiert. glyph fmt hat ein einziges Layout ohne Optionen, siehe saubere Diffs.
  • Du pflegst neben jedem Typ einen handgeschriebenen Validator (zod und einen Serializer), und ein Agent benennt ein Feld in einem davon um, aber nicht in den anderen; alles kompiliert trotzdem. In Glyph ist der Typ der Validator.
  • Du grepst nach einem Symbol und findest zehn Treffer, die nichts damit zu tun haben: Overloads, Decorators, zusammengeführte Namespaces. Nichts davon gibt es in Glyph, siehe Dinge finden.

Eine Hintertür, und du kannst danach greppen#

Wenn du TypeScript brauchst, das Glyph nicht ausdrücken kann, nimmt extern_ts("...") einen einzelnen Inline-Typ oder -Ausdruck, und tsc prüft ihn trotzdem. Für ein ganzes Modul legst du die .ts unter src/extern/ ab und schreibst import extern/name; relative Imports sind sonst nicht erlaubt, also ist dieser Pfad der einzige Weg hinein. Beide Formen enthalten das Wort extern, also listet grep -rn extern src/ jede Stelle, an der der Checker an TypeScript übergibt.

src/clock.glyph 
module clock

pub fn now_ms() -> number {
  return extern_ts("Date.now()")
}

Wie das erzeugte TypeScript aussieht#

Einfaches TypeScript, eine Datei pro Modul, die du lesen und committen kannst. Eine Union wird zu einer Discriminated Union plus einem Wert, der ihre Laufzeitprüfung trägt, und ein match wird zu einem switch über den Tag. Das ist die Ausgabe von glyph build für das Modul links, mit gekürzten Import-Zeilen.

plan.glyph 
module plan

pub type Plan = Free | Pro | Team

pub fn seats(p: Plan) -> number {
  return match p {
    Free => 1,
    Pro => 5,
    Team => 50,
  }
}
plan.ts (erzeugt, gekürzt) 
export type Plan =
  | { tag: "Free" }
  | { tag: "Pro" }
  | { tag: "Team" };

export const Free: Plan = { tag: "Free" };
export const Pro: Plan = { tag: "Pro" };
export const Team: Plan = { tag: "Team" };
export const Plan = {
  is(value: unknown): value is Plan { ... },
  parse(value: unknown) { ... },
  schema: ...,
};

export function seats(p: Plan): number {
  const __m0 = p;
  switch (__m0.tag) {
    case "Free": { return 1; }
    case "Pro": { return 5; }
    case "Team": { return 50; }
    default: throw new Error("non-exhaustive match");
  }
}

Lösch den Arm Team, und der Build bricht ab, bevor irgendein TypeScript geschrieben wird:

Wenn du Glyph nicht mehr verwendest, behältst du das erzeugte .ts. Es hat keine Laufzeitabhängigkeit außer einem kleinen mitgelieferten Support-Verzeichnis, das der Build daneben schreibt.

npm und das TypeScript, das du schon hast#

Ein .glyph-Modul importiert ein npm-Paket über seinen Namen (import kafkajs { Kafka }), typisiert aus den eigenen Deklarationen des Pakets, und dein bestehendes .ts importiert die erzeugten Glyph-Module wie jede lokale Datei. Du kannst also mit einem einzigen Modul in einer App anfangen, die TypeScript bleibt. Die Details stehen in drei Antworten.
