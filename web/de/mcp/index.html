Für Agenten · Model Context Protocol

Verbinde deinen Agenten mit Glyphs Compiler

glyph mcp startet einen Model-Context-Protocol-Server mit elf Tools für dein Projekt: was ein Symbol ist, was kaputtgeht, wenn du es änderst, ob ein Wert eines Typs dort stehen darf, wo ein anderer deklariert ist, wovon eine Deklaration abhängt, was ein Modul exportiert, Diagnosen innerhalb des Projekts, der Typ an einer Cursorposition, wo ein Name definiert ist, jede Referenz darauf, jede match-Stelle über einer Union und die Symbolsuche. Jedes davon ist auch ein Verb von glyph query, sodass ein Agent ohne MCP-Client dieselben Fragen stellt und dieselben Bytes bekommt.

Warum ein Agent das will#

Ein Agent, der eine Codebasis bearbeitet, arbeitet normalerweise blind. Er liest Dateien, rät Typen und merkt erst nach einem Build, ob er etwas kaputtgemacht hat. Glyph beantwortet diese Fragen schon für einen Editor. glyph mcp gibt einem Agenten dieselben Antworten direkt vom Compiler, ohne Build-Ausgaben auszuwerten oder jede Datei zu lesen, um herauszufinden, wer was aufruft. Zwei der Tools beantworten Fragen, die ein Editor nie stellt: glyph_symbol liefert die Varianten einer Union mit der Syntax, die jede erzeugt, und genau das braucht ein Agent, bevor er das match schreibt, und glyph_impact beantwortet, was eine Änderung kaputtmacht, bevor es die Änderung gibt.

Einrichten#

Jeder MCP-Client kann ihn starten. Richte den Client auf das glyph-Binary mit dem Unterbefehl mcp aus und übergib dein Projekt-Root als Argument oder starte ihn aus dem Projektverzeichnis. Er spricht MCP über stdio, es gibt also keinen Port und keinen Daemon.

MCP-Client-Konfiguration (allgemein) 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp", "/path/to/your/project"]
    }
  }
}

Beim ersten Verbinden ruft der Client initialize und tools/list auf; der Server meldet die elf Tools unten. Positionen, die du sendest, folgen der LSP-Konvention: eine 0-basierte line und ein 0-basierter character in UTF-16-Codeeinheiten. Diagnosebereiche kommen so zurück, wie glyph check --json sie ausgibt, mit 1-basierter line und col plus dem Byte-offset.

Die Beschreibung jedes Tools enthält den Vertrag, den du im Moment des Aufrufs brauchst, und das vollständige Handbuch steht in glyph llms --json unter tools, nach Toolnamen geordnet, mit dem jeweiligen Verb von glyph query daneben. Früher enthielt diese Antwort jedes Handbuch: elf Tools, 31.446 Bytes Beschreibung in einer Antwort von 45.509 Bytes. Jetzt sind es 8.627 in einer Antwort von 20.386 Bytes, und nichts wurde gelöscht. Jede Session bezahlt beim Verbinden für tools/list und für das Handbuch nur, wenn sie danach fragt. Dieses Dokument wird aus den eigenen Tabellen des Compilers generiert, und ein Test lässt den Build fehlschlagen, wenn es ein Tool nennt, das dieser Server nicht anbietet.

Die elf Tools#

Tools, die glyph mcp bereitstellt 
// everything the compiler holds about one symbol: kind, identity,
// visibility, a record's fields, a union's variants with payloads and
// construction syntax, parameters and return, interface members,
// whether a `match` over it must be exhaustive, its `@example`.
// The identity reaches the stdlib: std/result::Result answers with
// Ok(T) and Err(E), and `path` is null beside the reason why
glyph_symbol(entity)                       // or (path, line, character)

// what breaks if you make one named change to one declaration:
// add_variant, remove_variant, rename, change_arity,
// change_signature_type, remove. One verdict per site
glyph_impact(entity, change)

// can a value of `from` go where a `to` is declared? Asked of the
// checker's own comparison. Each side is a `module::name` or a
// Glyph type spelling read in the scope of `path`
glyph_assignable(path, from, to)

// every diagnostic for one file, checked inside its project, in the
// shape `glyph check --json` prints, plus what was not checked
glyph_diagnostics(path)

// the type at a position: an expression, a declaration name, a
// parameter, an annotation, a variant, or a binding
glyph_hover(path, line, character)

// where the name is defined, following imports across modules,
// with the `module::name` so the answer chains into glyph_impact
glyph_definition(path, line, character)

// every edge into a symbol across the project, split by relation
// (CALLS, REFERENCES, GENERATED_FROM), each with its provenance
glyph_references(path, name)               // or by position

// every `match` site over one tagged union and which variants each
// site's arms name, with the union's own variants
glyph_variants(path, name)

// search top-level declarations and union variants by name, each
// entry with its identity, `pub`, kind and one-line signature
glyph_symbols(query)

// what one declaration depends on: every declaration its own source
// names, split by relation (CALLS, REFERENCES, FIELD_ACCESS), each
// edge with both ends and its provenance. The mirror of references
glyph_dependencies(entity)

// what one module makes visible to an importer: every `pub`
// declaration and every variant a `pub` union hoists, each with
// its identity, kind and signature
glyph_exports(module)

So sieht es aus#

Ein tools/call für glyph_diagnostics auf einer Datei mit einem Tippfehler in einem Feld liefert die Diagnose des Compilers selbst, denselben Rust-Typ, den glyph check --json serialisiert, in einer Hülle, die außerdem sagt, was die Prüfung nicht abgedeckt hat.

Request 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": { "path": "src/user.glyph" }
  }
}
Ergebnis (der JSON-Inhalt des Tools) 
{
  "path": "src/user.glyph",
  "module": "user",
  "project_root": "src",
  "member": true,
  "diagnostics": [
    {
      "code": "E0210",
      "severity": "error",
      "stage": "typecheck",
      "message": "type `U` has no field `naem`; did you mean `name`?",
      "help": "Check the field name for a typo,
        or add the field to the type.",
      "entity": "user::greet",
      "file": "user",
      "range": {
        "start": { "line": 9, "col": 10, "offset": 99 },
        "end":   { "line": 9, "col": 16, "offset": 105 }
      },
      "union": null,
      "missing_variants": null
    }
  ],
  "unindexed": [],
  "not_run": [ ... ]
}

Die Datei wird innerhalb ihres Projekts geprüft, also werden ein falsches Feld auf einem importierten Record und ein match mit fehlenden Armen über einer importierten Union hier so gemeldet, wie glyph check sie meldet. Was das Tool nicht abdecken konnte, steht in der Antwort, statt dass du es annehmen musst: member sagt, ob der Durchlauf durch das Projekt die Datei erreicht, unindexed nennt Projektdateien, die sich nicht parsen lassen, und not_run nennt die drei Prüfungen, die glyph check macht und diese nicht: tsc, E0104 für einen Import, der kein Modul nennt, wofür die Sicht des Builds auf node_modules nötig ist, und E0400 für ein fehlschlagendes @example, was durch Ausführen des erzeugten Projekts entschieden wird. Ein Test lässt beide Schnittstellen auf sechs Projekten laufen und vergleicht das JSON Schlüssel für Schlüssel, damit die beiden nicht auseinanderlaufen.

glyph_references gilt für den ganzen Workspace: Frag nach einem Symbol, und du bekommst seine Deklaration, jede Verwendung und das import-Binding jedes importierenden Moduls, über alle Dateien hinweg. Es verwendet dieselbe dateiübergreifende Identität wie das Umbenennen im Editor, also deckt die Antwort das ganze Projekt ab und nicht nur die Datei, aus der du gefragt hast.

Kein MCP-Client? Dieselben Fragen auf der Kommandozeile#

Jedes Tool hat ein Verb von glyph query, das die Argumente des Tools als Flags nimmt und das JSON des Tools auf stdout ausgibt. Eine beantwortete Frage endet mit Exit-Code 0; eine abgelehnte schreibt den Grund nach stderr und endet mit 2. Die Verben laufen über denselben Einstiegspunkt, den ein MCP-Client erreicht, und ein Integrationstest stellt beiden Schnittstellen dieselbe Frage und vergleicht die Antworten als Text, sodass ein Verb, das umformatiert oder zusammenfasst, daran scheitern würde.

dieselben elf Fragen, ohne Client 
glyph query symbol       --path src/main.glyph --entity orders::OrderStatus
glyph query impact       --entity orders::OrderStatus --change add_variant --variant Refunded
glyph query assignable   --path src/main.glyph --from 'Nullable<int>' --to int
glyph query diagnostics  --path src/main.glyph
glyph query hover        --path src/main.glyph --line 9 --character 6
glyph query definition   --path src/main.glyph --line 9 --character 6
glyph query references   --path src/orders.glyph --name create
glyph query variants     --path src/orders.glyph --name OrderStatus
glyph query symbols      --query order
glyph query dependencies --path src/main.glyph --entity main::build
glyph query exports      --path src/main.glyph --module orders

// the same two, asked about a module the compiler carries
glyph query symbol       --path src/main.glyph --entity std/result::Result
glyph query exports      --path src/main.glyph --module std/result

Wenn der Build schon rot ist#

Die Tools beantworten Fragen, die vor einer Änderung gestellt werden. Danach ist glyph check --agent das, was du liest: Es gibt die Diagnosen von check --json mit zwei zusätzlichen Schlüsseln pro Eintrag aus: constraints, die Invarianten, die eine reparierende Änderung erhalten muss, und symbols, die Antwort von glyph_symbol für jedes Symbol, das die Diagnose nennt, sodass die nächste Änderung keinen zweiten Aufruf braucht. Bei einem match mit fehlenden Armen heißt das, dass die Varianten der Union mit ihren Payloads zusammen mit dem Fehler ankommen, der nach ihnen verlangt hat, dazu der Satz, dass ein else-Arm genau die Garantie aufgeben würde, die die Diagnose schützen soll. Wo die Reparatur vollständig feststeht, schreibt glyph fix sie und sagt, was es abgelehnt hat. Es gibt einen Durchgang durch die ganze Schleife mit echter Ausgabe.

Wo es steht#

Heute verfügbar

Ein Server glyph mcp [root] über stdio mit elf Tools: glyph_symbol, glyph_impact, glyph_assignable, glyph_diagnostics, glyph_hover, glyph_definition, glyph_references (für den ganzen Workspace), glyph_variants, glyph_symbols, glyph_dependencies und glyph_exports. Jedes hat ein Verb von glyph query, das dasselbe JSON ausgibt. Die Antworten kommen aus den eigenen Abfragen des Compilers, und jede Information, die ein Tool nicht hat, ist null, mit einem Satz in <key>_absent daneben, der sagt, warum. Hover antwortet auch bei einem Namen, der in einem anderen Modul deklariert ist, sodass eine importierte Funktion an ihrer Aufrufstelle und ein Feld, das aus einem importierten Record gelesen wird, beide einen Typ haben. Eine Entitätsidentität reicht bis in die Stdlib: Das Result aus dem Prelude ist std/result::Result, das Modul, unter dem der Resolver es registriert und aus dem der Emitter den Import schreibt, also antwortet glyph_symbol darauf mit Ok(T) und Err(E), und glyph_exports auf std/result listet die Schnittstelle. Dahinter steht kein Glyph-Quellcode, also sind path und range null, mit diesem Grund, statt zu fehlen.

In Arbeit

Die Tools lesen nur: Du kannst über MCP nichts umbenennen und keine Änderung anwenden. Die schreibende Seite gibt es stattdessen auf der Kommandozeile, als glyph fix. Der Server scannt das Projekt bei jedem Aufruf neu, statt einen gecachten Index zu halten, und überspringt jede Datei, die sich nicht parsen lässt. Die Antwort auf tools/list ist 20.386 Bytes groß, nach 45.509, und das ist immer noch Kontext, den jede Session beim Verbinden bezahlt.

Neben den Tools kann ein Agent die Sprache und die Diagnosen offline lesen: llms.txt ist der Fließtext, glyph llms --json dasselbe Wissen als Daten aus den eigenen Tabellen des Compilers, und glyph build --json der Batch-Weg für codierte Diagnosen über einen ganzen Verzeichnisbaum.
