Für Teams

Was es garantiert, was die Einführung kostet und wie du wieder rauskommst

Glyph lehnt eine konkrete, geprüfte Liste von Fällen ab, die ein striktes TypeScript-Projekt akzeptiert, und es kompiliert zu TypeScript, das du behalten kannst, wenn du es nicht mehr verwendest. Es ist eine frühe Vorschau: vor 1.0, hauptsächlich von einer Person gepflegt, mit mehreren Releases pro Woche.

Was es garantiert#

Jede Aussage darüber, was Glyph findet, ist ein Fall im Verzeichnis catches/ des Repositorys: dasselbe Programm in TypeScript und in Glyph, beide von einem CI-Gate ausgeführt. Insgesamt gibt es 47 geprüfte Fälle: 37 TypeScript-Fälle, 5 JavaScript-Fallen, die es in Glyph nicht gibt, und 5 Lücken, die Glyph noch nicht schließt. Glyph lehnt 28 davon beim Build ab (23 TypeScript-Fälle und 5 Fallen). Von den Fehlern, die es nicht ablehnt, lösen 3 eine Warnung aus, 9 sind fehlerhafte Daten, die an einer Laufzeitprüfung an der Systemgrenze gestoppt werden, und 2 stoppen zur Laufzeit. Die, auf die sich jemand beim Review von Agenten-Code am meisten stützt:

CodeWas abgelehnt wird
E0200Ein match, das einen Fall einer Union auslässt, sodass ein neuer Fall jede Stelle auflistet, die sich ändern muss
E0013Ein Cast (as, as unknown as); es gibt keinen Cast und kein any
E0204Geparstes JSON, das ungeprüft einem typisierten Namen zugewiesen wird
E0224Ein Lesezugriff auf eine Map, die so typisiert ist, als wäre der Schlüssel immer da
E0217Ein Result, das einfach fallen gelassen wird (eine Warnung; let _ = sagt, dass es Absicht war)

Die Seite mit den Fällen listet jeden Fall mit seinem TypeScript, seinem Glyph und dem Fehler und sagt, welche ein maximal konfiguriertes typescript-eslint-Setup ebenfalls gefunden hätte.

Wo es aufhört#

Die Garantien gelten für Code, der in Glyph geschrieben ist. Eine Exception, die in einer npm-Abhängigkeit geworfen wird, umgeht Result weiterhin, und ein Typ, der aus der .d.ts eines Pakets importiert wird, hat keine Laufzeitprüfung. Innerhalb von Glyph stehen die 5 offenen Lücken mit ihren Gap-Nummern unter was es noch nicht findet, und die vollständige Liste ist docs/dogfooding-gaps.md. Einen Vergleich mit striktem TypeScript plus zod, eslint und ts-pattern, einschließlich der Stellen, an denen dieses Setup noch vorn liegt, findest du unter warum nicht TypeScript mit Tooling.

Einführung in einer bestehenden App#

Es gibt keinen Rewrite. Du schreibst den Teil, bei dem du dir keinen Fehler leisten kannst (Modelle, Berechtigungen, Zustandsübergänge, Geld), in Glyph, und der Rest der App bleibt TypeScript und importiert die erzeugten Module wie jede lokale Datei. Die Anleitung verwendet ein normales Vite-Grundgerüst: Kann ich Glyph in meiner bestehenden App einführen?

Der Ausstiegsweg#

glyph build schreibt einfaches TypeScript, eine Datei pro Modul, das tsc --strict besteht. Wenn du Glyph nicht mehr verwendest, committest du diese Ausgabe und machst mit tsc weiter. Die Lizenz ist MIT oder Apache-2.0, ein Fork ist also immer möglich. Umstieg von TypeScript zeigt ein Modul neben seiner erzeugten Datei.

Pinning und Upgrades#

glyph init pinnt den Compiler in der package.json auf eine exakte Version, ohne ^, sodass kein Release versehentlich in deinem Build landet. Drei Befehle erledigen den Rest:

gezielt upgraden 
glyph doctor     # your version against the latest release; never fails CI for that
glyph upgrade    # moves the project's pin, runs npm install, links the notes
glyph --update   # moves the installed compiler itself

Release-Takt und die Breaking-Markierung#

Die Versionsseite hat einen Eintrag für jedes Release von 0.1.0 bis 0.1.162, insgesamt 161, und 35 davon erschienen zwischen dem 1. Nov. 2026 und dem 22. Nov. 2026. Ein Release wird als Breaking markiert, wenn es ein Programm ablehnt, das die vorherige Version akzeptiert hat, und so landen die meisten Korrektheits-Fixes. 45 Einträge tragen die Markierung. Sie wird gesetzt, indem das kleinste betroffene Programm unter beiden Versionen ausgeführt wird, nicht durch Lesen des Diffs, und Releases vor 0.1.99 wurden nicht so getestet, ein unmarkiertes altes Release ist also ungetestet und nicht sicher.

Was ein Breaking-Release in der Praxis gekostet hat: Jede neuere Release Note sagt, was passiert ist, als die alte und die neue Version über die Beispiel-Apps des Repositorys liefen. Das sind die neuesten Breaking-Releases, zitiert aus ihren Release Notes:

  • 0.1.162: “Across the 285 example apps, standalone files, catch cases and test programs, the only new diagnostic is on the catch case for this mistake.”
  • 0.1.161: “Across the 97 example apps and standalone files, nothing changes except the catch case for this mistake.”
  • 0.1.160: “Across the 394 example apps and standalone files, the only new diagnostic is on the catch case for this mistake.”
  • 0.1.159: Die Release Notes sagen dazu nichts.
  • 0.1.158: Die Release Notes sagen dazu nichts.
  • 0.1.157: “Writing this rule turned up a real bug in one of the example apps.”

Die Beispiel-Apps sind der eigene Code des Projekts, der von Release zu Release kompilierbar gehalten wird, also taucht eine neu abgelehnte Form dort seltener auf als in deinem Code. Jede Release Note nennt die Formen, die sie ablehnt, also lies sie vor dem Upgrade.

Status#

Glyph ist vor 1.0. Vor 1.0 können sich Syntax, Standardbibliothek und die Form des erzeugten TypeScript ändern, und ein Release kann Code ablehnen, der vorher kompiliert hat. docs/stability.md sagt, was sich ändern kann und was stabil gehalten wird. MAINTAINERS.md sagt klar, dass das Projekt heute hauptsächlich von einer Person gepflegt wird.

Einwände, beantwortet#

Wir nutzen kaum KI. Lohnt es sich trotzdem?

Die Prüfungen sind dieselben, egal wer den Code schreibt: weniger Überraschungen zur Laufzeit, kleinere Diffs, Code, den du greppen kannst.

 Wir setzen schon striktes TypeScript und Lint ein.

Jede dieser Prüfungen ist Opt-in und lässt sich mit einer Zeile abschalten. Die von Glyph nicht.

 Können unsere Agenten eine Sprache schreiben, die sie kaum gesehen haben?

Das meiste, was ein Modell über TypeScript weiß, lässt sich übertragen, und den Rest benennt der Compiler.

 Warum überhaupt zu TypeScript kompilieren?

Dort sind npm, React und Node, und deshalb kann die Einführung Datei für Datei passieren.

 Was sieht die Rufbereitschaft, wenn es kaputtgeht?

Lesbares TypeScript, Source Maps zurück zur .glyph-Datei und stabile Fehlercodes.

 Woher wissen wir, dass das alles stimmt?

Wie jede Aussage auf dieser Website geprüft wird und wie du eine selbst reproduzierst.
