Un cambio de una línea es un diff de una línea, siempre. Glyph tiene un único formato canónico, así que un agente no puede enterrar un cambio real bajo un muro de reformateo.

Por qué importa#

Cuando un agente abre un pull request, el diff es la revisión. Si un arreglo de una línea llega como un reformateo de 200 líneas, nadie puede ver qué ha cambiado, y ese ruido es justo por donde se cuela un bug. Estabilidad de los diffs significa que el diff muestra el cambio y nada más que el cambio.

Dos reglas hacen casi todo el trabajo. Aquí está cada una, mostrada como el diff que revisarías.

Ejemplo 1: comas finales, un elemento por línea#

Añade una ruta. En el estilo habitual de TypeScript, la que antes era la última línea tiene que cambiar solo para ganar una coma. Se mueven dos líneas para un cambio de un elemento:

TypeScript: añadir "/billing" 
 const routes = [
   "/home",
-  "/about"
+  "/about",
+  "/billing"
 ]
3 líneas movidas para 1 cambio
Glyph: añadir "/billing" 
 let routes = [
   "/home",
   "/about",
+  "/billing",
 ]
1 línea añadida, exactamente el cambio

Las comas finales son obligatorias, y una lista que no cabe en una línea va con un elemento por línea en lugar de reempaquetarse, así que insertar, quitar o reordenar una entrada nunca toca a sus vecinas. Lo mismo vale para campos de records, parámetros, brazos de match e imports. El umbral tiene un coste: un renombrado que lleva una llamada más allá de las 100 columnas expande toda la lista de argumentos a uno por línea.

Ejemplo 2: un único formato canónico#

Hay exactamente un formato correcto, el que produce glyph fmt. Los espacios, los saltos de línea y la alineación no son decisiones que un agente pueda “ordenar”, así que una edición semántica no puede arrastrar un reflujo con ella. Cambia el tipo de un campo, y ese es todo el diff:

user.glyph: cambias un campo, revisas una línea 
 type User = {
   id: string,
-  age: string,
+  age: number,
   email: string,
 }

Como el formato es fijo, dos agentes distintos que editan el mismo archivo producen un formato idéntico byte a byte, sin reflujos, sin el ruido de “mi formateador frente al tuyo”, y con un git blame limpio que apunta al commit que cambió de verdad una línea, no al que la reformateó.

Un único formato canónico, entonces, ¿el formateador mueve mis comentarios?#

Lo hacía, y fue un bug que merece la pena nombrar. Glyph no tiene comentarios de bloque ni sintaxis de comentarios de documentación, así que una línea // es la única forma de explicar un campo de un record, una variante de una unión o un brazo de match. El formateador solo volcaba los comentarios pendientes en los límites de declaraciones y sentencias, lo que significaba que un comentario escrito dentro de una construcción bajaba hasta la siguiente declaración y se leía como documentación de aquello donde caía. Escribir un buscaminas en Glyph es lo que lo destapó. Estas dos declaraciones vienen de la app real (con los comentarios recortados para que quepan), pasadas por el formateador antiguo y por el nuevo.

0.1.37: una pasada de fmt 
type Visibility =
  | Hidden
  | Flagged
  | Revealed

// Face down. Prints as `.`.
// Face down and marked by the player.
// Face up. `Cell.adjacent` is what gets printed.
type Cell = { mine: bool, adjacent: int, visibility: Visibility }
// Number of mined neighbours. Only meaningful
// once mines are placed.
tres comentarios de variantes documentan ahora un record
0.1.38: el mismo archivo 
type Visibility =
  // Face down. Prints as `.`.
  | Hidden
  // Face down and marked by the player.
  | Flagged
  // Face up. `Cell.adjacent` is what gets printed.
  | Revealed

type Cell = {
  mine: bool,
  // Number of mined neighbours. Only meaningful
  // once mines are placed.
  adjacent: int,
  visibility: Visibility,
}
cada comentario sobre lo que describe

La regla ahora: un comentario se vuelve a emitir encima del elemento sobre el que se escribió, dentro del cuerpo de un record, de la lista de variantes de una unión, de un literal de array u objeto, de una lista de argumentos o parámetros, y de un match. Y una construcción que contiene un comentario interior siempre usa la forma de un elemento por línea, sea cual sea su tamaño, para que el comentario tenga un elemento sobre el que colocarse. Así, type Shape = { w: int, h: int } sigue quedando en una línea, y en cuanto documentas h el record se queda expandido.

Por qué esto cuenta como un bug de corrección y no como uno estético: nada falló. El build salió con 0, tsc pasó y la salida destrozada era a su vez un punto fijo, así que glyph fmt --check en CI salía en verde sobre un archivo cuyos comentarios ahora decían algo falso. Es la misma clase de fallo que Glyph existe para eliminar, solo que en el formateador y no en el sistema de tipos.

¿Puede glyph fmt romper un programa que compila?#

Podía, y un caso sigue abierto. Primero el que está corregido. Un brazo que significa “el record vacío” se escribe true => ({}). La posición del cuerpo de un brazo es el único sitio de la gramática donde una { inicial es ambigua, y el parser lo resuelve exigiendo key: o ... justo después de la llave. Un objeto vacío no tiene ninguna de las dos cosas, así que cuando el formateador quitaba los paréntesis y volvía a imprimir true => {}, el brazo volvía como un bloque vacío y el archivo dejaba de compilar: E0223, el brazo no produce ningún valor. Pasabas un formateador sobre código que funcionaba y obtenías código que ya no compilaba.

Ahora el printer pone entre paréntesis el cuerpo de un brazo cuyo primer token es una { que se volvería a parsear como bloque, es decir, el objeto vacío y todo lo que se construye sobre él (({}).size vuelve como ({}.size)). El cuerpo de un brazo que ya se lee sin ambigüedad, como false => { a: "x" }, se queda sin paréntesis, así que no aparece puntuación nueva en ningún otro sitio. fmt es un punto fijo sobre el resultado y el TypeScript generado no cambia. Un formateador al que tu programa tiene que sobrevivir es peor que una funcionalidad que falta, porque daña código que ya funcionaba.

Se corrigieron dos más en la 0.1.138. Dentro de un bloque, una línea que empieza con ( continúa la línea anterior, y hasta la 0.1.137 el formateador imprimía load()? seguido de .run() como (load()?).run(), así que después de let a = 1 el archivo formateado significaba let a = 1(…).run(). Ahora mantiene load()? con .run() indentado en la línea siguiente, y escribe e?(x), e?[0] y e? ? sin paréntesis. El otro era el refinamiento where de una unión, que el formateador eliminaba, convirtiendo un programa que check rechazaba en uno que aceptaba. El fuzzer ahora parsea el archivo formateado y compara el árbol con el del original, así que un formato que cambia lo que significa un archivo falla en la primera pasada en lugar de esperar a que alguien se dé cuenta.

Las reglas de formato que hay detrás, y el intercambio que suponen, están en la página del pilar de estabilidad de los diffs.

Dónde está#

Disponible hoy

Comas finales obligatorias, listas con un elemento por línea y el formato canónico único de glyph fmt, que hace round-trip y es idempotente, con formateo al guardar en el editor. glyph fmt nunca mueve un comentario a un sitio donde no corresponde. Los comentarios se mantienen encima del elemento sobre el que se escribieron, también dentro de un record, un literal, una lista de argumentos, un match, entre los operandos de un operador y entre los pasos de una cadena de métodos, que entonces va con un paso por línea y el punto delante.

El límite, y lo que viene

Un comentario siempre se emite en su propia línea, así que uno escrito al final de una línea de código (w: int, // width in cells) se mueve a la línea de encima del siguiente elemento. Ya no cruza el límite de una declaración, pero sí se mueve; mantenerlo al final de la línea requiere que el printer sepa con qué línea comparte un comentario. Un comentario donde el formato no tiene dónde ponerlo, como dentro de un índice, después de los argumentos de una llamada en medio de una cadena, o antes de un operando de ! o await, ya no se mueve: glyph fmt rechaza el archivo, lo deja como estaba y nombra la línea y dónde poner el comentario, y glyph check informa de lo mismo como el aviso E0500. Un comentario entre atributos de JSX o entre los campos de un patrón de objeto también se rechaza, aunque un formato de uno por línea podría colocarlo; esos formatos están en la lista. El printer tampoco tiene todavía una regla para partir una cadena larga de métodos o de +, así que una cadena demasiado larga parte la lista de argumentos más interna, que es el sitio equivocado. También estamos construyendo un benchmark de tamaño de diffs frente a las mismas ediciones en TypeScript, para que este pilar sea una cifra que puedas comprobar.
