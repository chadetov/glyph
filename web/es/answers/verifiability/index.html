Por qué importa

Los agentes no suelen romper el código de forma ruidosa. Lo rompen con seguridad: añaden un estado, quitan una rama o renombran un campo, todo sigue pasando la comprobación de tipos y el bug aparece en producción.

Los fallos caros son los que compilaron y estaban mal. Glyph cierra ese hueco convirtiendo “probablemente lo manejaste” en “el compilador demostró que lo hiciste.”

  • Uniones selladasLas uniones etiquetadas están selladas, así que match tiene que cubrir todos los casos.
  • Errores como valoresLos errores son valores que tienes que desenvolver, no excepciones que desaparecen.
  • Fronteras comprobadasY cada tipo lleva un descriptor de runtime, así que los datos que cruzan una frontera se comprueban contra su forma.

Un error descartado es un aviso

Lo mismo con los errores: una función que devuelve Result<T, E> está pensada para manejarse con match o propagarse con ? (y el compilador comprueba que el tipo de error encaja). Y si descartas un Result (lo llamas como sentencia e ignoras lo que devolvió), Glyph te avisa (E0217), porque un error descartado es un fallo que se ha tragado.

glyph check --no-tsc, 0.1.149 (extracto) 
13 │   save("a")
[E0217] Warning: typecheck: this `Result` is discarded; its `Err` case is silently ignored
    │ Help: Handle it with `match`, propagate it with `?`, or bind it (`let _ = ...`) to say the discard is intentional.

Lo silencias a propósito con let _ = ..., nunca por accidente.

Las uniones de la librería estándar también están selladas

El listón es el mismo para una unión que pertenece a la librería estándar. fs.ErrorKind es un conjunto cerrado de seis tipos, y el checker conoce su forma, así que match e.kind sobre un error del sistema de archivos no necesita brazo else y falla con E0200 cuando dejas fuera un tipo.

E0200 falta un tipoE0210 campo desconocidoE0218 necesita else
Detalles erratas en campos, tipos de retorno, match sobre números y strings

e.mesage es E0210 y no algo que tsc detecte más adelante. Los tipos de retorno también viajan: string.split(text, ",") es un Array<string>, así que for i, part in string.split(text, ",") enlaza i como número en lugar de la clave de tipo string que obtendrías de un iterable sin tipo.

La exhaustividad no es solo para uniones. Un match sobre un number o un string con solo brazos literales no puede cubrir un dominio sin límites, así que Glyph exige un else (E0218) en lugar de dejar que el valor no cubierto acabe en una excepción en tiempo de ejecución.

La regla es la misma en todas partes: un match que no tiene en cuenta un caso no compila.

Un brazo mal escrito es un hueco, no un comodín

Una errata tampoco puede tapar un hueco sin avisar. La cabeza de un brazo en mayúscula es una referencia a una variante, no un binding nuevo.

status.glyph: un brazo mal escrito es un hueco, no un comodín 
fn label(s: Status) -> string {
  return match s {
    Loadign => "…",        // typo for Loading, read as a variant, not a binding
    Ready => "done",
    Failed(msg) => msg,
  }
}
glyph build 
[E0220] `Loadign` is not a variant of `Status`; did you mean `Loading`?
   ╰─ a lowercase name would be a binding; a PascalCase name is read as a variant
[E0200] non-exhaustive match on `Status`: missing variant `Loading`
Historia qué hacían las versiones antiguas de Glyph con la errata

La cabeza de un brazo en mayúscula es una referencia a una variante, no un binding nuevo, así que si escribías Loading como Loadign, las versiones antiguas de Glyph leían la errata como un comodín que enlazaba cualquier valor y hacía que el match pareciera completo. Ahora la cabeza tiene que nombrar una variante real de la unión sobre la que haces match. Cuando no lo hace, el build se detiene con E0220 y señala el nombre real más cercano, y la variante que de verdad te saltaste sigue apareciendo como E0200 justo al lado.

Variantes dentro de un payload

Esa lectura se mantiene un nivel más abajo, donde la variante es el payload de otra. El brazo ahora discrimina por la etiqueta del propio payload, sea cual sea la variante exterior.

repl.glyph: el brazo interior comprueba el payload, no lo enlaza 
fn step(z: Zipper, line: string) -> Zipper {
  return match parse_command(line) {
    Err(Blank) => z,                          // a comment or an empty line
    Err(e) => { io.println(explain(e)) z },   // every other parse error
    Ok(command) => execute(z, command),
  }
}
E0305 etiqueta de case duplicada
Historia el brazo muerto antes de la 0.1.93, y la protección E0305

Err(Blank) junto a Err(e) se lee como "ignora una línea en blanco, imprime cualquier otro error de parseo", y hasta la 0.1.93 compilaba a dos etiquetas case "Err": sobre la etiqueta exterior, la primera de las cuales enlazaba todo el payload con el nombre Blank. Todos los errores iban al primer brazo, el segundo era código muerto y nada lo decía: Glyph no informaba de ningún diagnóstico y tsc --strict acepta una etiqueta de case duplicada. El brazo ahora discrimina por la etiqueta del propio payload, sea cual sea la variante exterior, y el compilador lee el nombre igual que el typechecker: decide la propia lista de variantes de la unión del payload, y solo cuando esa lista no está al alcance decide la forma del nombre. Para una unión declarada en el mismo archivo, las mayúsculas ya no importan. Para una importada de otro módulo, la lista de variantes hoy no está al alcance, así que una variante en mayúscula discrimina y una en minúscula detiene el build.

Lo detiene porque ahora el switch está protegido. Dos brazos que escribirían la misma etiqueta case son E0305, no un switch cuya segunda etiqueta nunca se puede ejecutar. Eso es lo que hace que esta categoría sea ruidosa en lugar de silenciosa: una traducción que recurre dos veces a la misma etiqueta hace fallar el build en lugar de elegir el brazo equivocado en tiempo de ejecución.

La forma de escribir el import nunca desactiva la comprobación

Cómo llegó la unión al ámbito no cambia nada de esto. Glyph te deja escribir un brazo de variante de dos formas, y las dos se comprueban igual: import model { Cond, Yes, No } con brazos sin prefijo, o import model (o import model as m) con model.Yes(_).

interp.glyph: la lista del import se fue, el match se sigue comprobando 
import model { Action, All, Any, AtLeast, Clear, Condition, Context, Counter,
               Equals, Flag, FlagSet, Increment, Not, Set, Slot, Text }
import model
import std/result

pub fn evaluate(ctx: model.Context, c: model.Condition) -> result.Result<bool, SlotError> {
  return match c {
    model.Equals({ key, value }) => result.Ok(read_text(ctx, key, "equals")? == value),
    model.AtLeast({ key, least }) => result.Ok(read_count(ctx, key, "at-least")? >= least),
    model.FlagSet({ key }) => result.Ok(read_flag(ctx, key, "flag-set")?),
    model.All({ of }) => all_of(ctx, of),
    model.Any({ of }) => any_of(ctx, of),
    model.Not({ of }) => result.Ok(!(evaluate(ctx, of)?)),
  }
}
glyph build, después de borrar el último brazo 
[E0200] non-exhaustive match on `Condition`: missing variants Not
Detalles uniones de la librería estándar, enums de strings y por qué existía la lista

Eso vale también para las uniones de la librería estándar, así que match o { option.Some(s) => … } sobre un option.Option<string> es E0200 por el None que falta, exactamente igual que con la forma Some/None sin prefijo. Hasta la 0.1.56 la forma cualificada se saltaba la comprobación por completo y el build no informaba de ningún diagnóstico en un match que lanzaba una excepción en tiempo de ejecución.

Un enum de strings también cruza la frontera. type ColType = "text" | "int" | "real" | "bool" declarado en catalog.glyph e importado en otro módulo mantiene sus cuatro valores, así que un match que cubre los cuatro compila sin else, y quitar uno es E0200 nombrando el valor que quitaste. Hasta la 0.1.57 era E0218, con un texto de ayuda que te decía que añadieras un brazo else. Esa ayuda se equivocaba sobre el código que tenía delante, y seguirla convertía un error de compilación en un fallthrough en tiempo de ejecución. Funcionan las tres formas de import: import catalog { ColType }, import catalog con catalog.ColType e import catalog as c con c.ColType.

De esa lista de imports es de donde salió esto. Estaba escrita a mano en cada módulo de un motor de statecharts, con un comentario encima que decía que los constructores de una unión no llegan con su tipo. El comentario acertaba en la sintaxis y se equivocaba en el motivo: la lista estaba ahí porque la forma más corta desactivaba la comprobación, y nadie lo había notado, porque desactivarla no hace ruido. Qué forma elijas es ahora una elección real y no una trampa. La forma con nombres pone cada variante que manejas en la lista del import, que es lo que encuentra un grep de Equals. La forma cualificada dice en cada brazo de qué módulo viene la variante. Ninguna te cuesta la comprobación.

Los records importados mantienen sus campos

Los records ahora también cruzan, y hasta la 0.1.58 no lo hacían. Así que un record mantiene su conjunto de campos, y un campo incorrecto es E0210 nombrando el record en lugar de un error de tsc sobre una forma anónima.

glyph build, sobre una errata en un campo de un record importado 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
// Before 0.1.58: no Glyph diagnostic at all, only a tsc error downstream.
table.glyph: los hoists y el comentario que los explicaba han desaparecido 
// Both annotations are load-bearing. `for i, x in <record field>` picks its
// lowering from the iterand's type as the checker knows it, and a field
// access is not enough: without the `let`, `i` and `j` come out as strings
// and the row/column numbers in a `BadCell` are wrong.
let raw_rows: Array<Array<string>> = sheet.rows
for i, raw_row in raw_rows {
for i, raw_row in sheet.rows {
  let typed: Array<Value> = []
  let cols: Array<ColumnSpec> = spec.columns
  for j, col in cols {
  for j, col in spec.columns {
    …
  }
}

// sheet: Sheet, declared in catalog.glyph and imported here.
// Emitted TypeScript: sheet.rows.entries(), not Object.entries(sheet.rows).
Detalles el bug de la línea 11, lo que tsc no ve, cómo cruza la identidad

Un tipo declarado en un archivo y usado en otro llegaba sin que se supiera nada de él, lo que costaba dos comprobaciones distintas. Un campo mal escrito no provocaba ningún error de Glyph, así que sheet.rowz acababa en tsc y volvía como un mensaje de TypeScript sobre una forma que nunca escribiste. Y for i, r in sheet.rows no podía saber que rows era un array, así que generaba Object.entries(sheet.rows) en lugar de sheet.rows.entries(). Eso enlaza i al string "0". i + 1 entonces concatena en lugar de sumar, y una fila que debería informarse como line 2 se informa como line 11.

Lo que vale la pena saber es qué mitad detecta tsc. La aritmética sobre ese índice sí la detecta, aunque informa del error sobre el TypeScript generado, en una variable que Glyph enlazó por ti. Lo que no puede detectar es cada sitio donde se acepta un string cuando se quería un número: interpolación de strings, concatenación, la clave de un record.get. Eso compila sin errores con los dos checkers e imprime el número equivocado. Esa es la forma de bug que este proyecto existe para eliminar, así que una frontera entre módulos que la reintroduce no es una frontera que Glyph pueda dejar estar.

Un tipo importado lleva ahora una identidad a través de la frontera, basada en el módulo que lo declara y el nombre que declara, así que las tres formas de import se resuelven al mismo tipo. La declaración en sí se obtiene bajo demanda y se procesa en el lado del módulo que la declara, que es la mitad que un consumidor no puede hacer: la resolución trabaja sobre spans, y los spans de una declaración importada pertenecen a otro archivo.

El motor de consultas de examples/apps/csvql es donde salió a la luz. Tenía tres hoists con let cuyo único trabajo era repetirle al emisor el tipo de un campo importado, bajo un comentario de cuatro líneas que explicaba que sin ellos los números de fila y columna de un mensaje de error salían mal. Los tres están borrados y la app imprime una salida idéntica byte a byte para las doce consultas.

Hay una cosa que todavía se detiene en la frontera. Pasar un catalog.Sheet donde se espera un table.Row es E0211 nombrando los dos tipos, pero la lista de miembros de una interface no cruza, así que un record pasado donde se espera una interface importada se compara con nada. Darle el mismo trato que recibe el conjunto de campos de un record cambiaría sin avisar lo que significa la satisfacción estructural, y eso es una decisión del lenguaje, no un arreglo.

El enmascarado de datos personales vive en el tipo

El mismo instinto de "llevarlo al nivel del tipo, no dejarlo en una convención" cubre los datos personales. Pon @redact fields: [ssn, dob] en un tipo y el compilador genera un redact() en su descriptor que enmascara esos campos, así que json.stringify(User.redact(u)) no puede filtrarlos.

E0219 campo desconocido en @redact

Si nombras un campo que el tipo no tiene, es un error de compilación (E0219), no un enmascarado que no hace nada sin avisar.

Los refinamientos se comprueban hasta el fondo

Un descriptor solo vale algo si es la comprobación que declara el tipo, hasta el fondo. Un refinamiento where ejecuta su predicado en cualquier sitio donde aparezca el tipo, no solo en un Instant.parse directo: como campo de un record, como elemento de un Array, como payload de un Option, dentro de una variante de una unión y a través de json.parse<T>.

schedule.glyph: el predicado sigue al tipo hasta dentro del campo 
fn is_instant(value: string) -> bool {
  return match time.parse_iso(value) {
    Some(_) => true,
    None => false,
  }
}

type Instant = string where is_instant(value)

type WireBlock = { start: Instant, end: Instant }
type WireParticipant = { name: string, busy: Array<WireBlock> }
type Calendar = { participants: Array<WireParticipant> }

// json.parse<Calendar>(text) on a file holding "start": "no"
//   => Err. It returned Ok before 0.1.41.
Historia la planificación equivocada con total seguridad antes de la 0.1.41

Lo mismo vale para un record importado de otro módulo. Hasta la 0.1.41, los dos casos se limitaban a comprobar que la clave estaba presente, lo que no comprueba nada.

La app de planificación de abajo es donde salió a la luz. Lee calendarios de un archivo JSON y necesita que cada timestamp sea un instante ISO-8601 real. Antes, el refinamiento se detenía en el nivel superior, así que un archivo editado a mano con "start": "no" se parseaba sin problemas, el instante se leía como 0 y la app imprimía con total seguridad una planificación y salía con 0.

Los tests se ejecutan como parte del build

Los tests viven junto al código y se ejecutan como parte de su compilación. Un @example encima de una función, o un bloque ```glyph @run``` dentro de un @doc, lo ejecuta glyph build sin ningún flag que haya que recordar.

bracket.glyph: rompe la asignación de cabezas de serie y el build se detiene 
@example seed_order(2) == [1, 2]
@example seed_order(4) == [1, 4, 2, 3]
@example seed_order(8) == [1, 8, 4, 5, 2, 7, 3, 6]
fn seed_order(size: int) -> Array<int> { … }

// glyph build src --out dist

// glyph build src --out dist --json
{ "ok": false, "errors": 1, "tsc": "passed",
  "examples": { "total": 23, "ran": true, "skipped": false,
    "failures": ["bracket example #16: …"] } }
Detalles por qué no se puede saltar sin que se note, y el canal JSON

Uno falso hace fallar el build igual que un error de tipos, y de eso se trata: un agente que reescribe el cuerpo de una función no puede pasar el build dejando atrás la aserción. --no-test los desactiva e imprime cuántos tests se ha saltado, así que el atajo queda visible en el log.

La salida JSON que leen los agentes informa del mismo veredicto. glyph build --json lleva un objeto examples junto a los diagnósticos, y un ejemplo que falla pone ok a false y el código de salida distinto de cero. Hasta la 0.1.43 los ejemplos solo se ejecutaban con --test, y la ruta JSON retornaba antes de que llegaran a ejecutarse, así que el único canal que un agente puede leer imprimía "ok": true en un proyecto cuya propia aserción era falsa. Si tsx no está en el PATH, el build falla en lugar de informar de un éxito que nunca comprobó.

La app de cuadros de torneo de abajo tiene 23 de estos. seed_order construye el orden estándar del cuadro duplicando, que es el tipo de función fácil de equivocar sutilmente y fácil de describir con exactitud. Cambia la regla de duplicado y el build se detiene, sin archivo de tests, sin runner y sin flags.

Encontrado construyendo con él

Cuatro más, encontrados construyendo con él

Cada uno compilaba sin errores y pasaba tsc --strict, y cada uno se encontró escribiendo una aplicación y no leyendo el compilador. Son el mismo fallo en tres sitios: los tipos decían una cosa y el programa hacía otra.

Leer una clave que quizá no exista

leer una clave que quizá no exista: ahora E0224 
fn name_of(row: Record<string, string>) -> string {
  return row.naem          // a typo. compiled, and returned undefined
}

Ahora es un error de compilación que señala record.get, que devuelve Option<V> para que el caso en que falta tenga adónde ir.

Detalles por qué leer de un mapa es distinto de indexar un array

Las claves de un mapa son arbitrarias, así que el compilador no puede saber si la clave está. Tipar la lectura como string afirmaba algo que no había comprobado, y el valor se imprimía como el texto "undefined". Escribir una clave no cambia, y tampoco indexar un array: un límite es un valor que un programa puede comprobar, una clave de mapa no.

Un método que responde undefined

una búsqueda que puede no encontrar nada: ahora E0242 
let name = users.find(fn(u: User) -> bool { return u.id == id }).name
let last = xs.at(-1) ?? 0  // passed tsc --strict too

[E0242] the call to `users.find` returns `User | undefined`; Glyph writes a value that may be missing as an `Option`
Help: pass `users` and the same callback to `array.find`, which returns `Option<User>`, and `match` it

Algunos métodos de JavaScript dicen "no hay nada" con undefined, que el checker del propio Glyph no veía, así que el editor y las herramientas del agente dejaban pasar la lectura de .name. Ahora cada uno apunta a la función de la biblioteca estándar que devuelve un Option, y glyph fix escribe las de arrays.

Detalles qué métodos, y qué los sustituye

La lista se lee de las declaraciones de TypeScript: find, findLast y at en un array, y at, codePointAt y match en un string. Los reemplazos son array.find, array.find_last, array.get, string.char_at, string.code_point_at y regex.matches. Un valor por defecto con ?? pasa a ser el brazo None de un match. array.get responde None con un índice negativo, así que la ayuda para xs.at(-1) escribe array.get(xs, array.len(xs) - 1). Un método llamado sobre un valor de npm no se juzga, porque Glyph no conoce su tipo.

== es igualdad de valor en todas partes

un test que pasaba mientras el código fallaba 
@example wrap("a") == wrap("a")   // passed: deep equality
fn same() -> bool {
  return wrap("a") == wrap("a")   // false. no diagnostic
}

== es ahora igualdad de valor en todas partes; los primitivos siguen compilando a ===, así que las comparaciones normales no cambian.

Historia cómo podía pasar un test sobre código roto

== estaba documentado como igualdad de valor y se traducía a ===, que es igualdad de referencia en cuanto cualquiera de los dos lados es un record, una unión etiquetada o un array. La misma expresión comparaba la estructura en un test y la identidad en el programa de al lado, así que un test podía informar de éxito sobre código que no funcionaba.

Un binding de bucle mantiene el tipo de sus elementos

exhaustividad que se evaporaba dentro de un bucle 
for t in tiers {
  match t {
    "free" => ...          // "pro" unhandled: once merely a warning to add `else`
  }
}

Ahora nombra la variante que no has manejado, que es un consejo para cumplir la comprobación y no para desactivarla.

Historia el consejo de añadir un comodín que daba antes

El binding del bucle no llevaba tipo de elemento, así que un match sobre una unión de literales de string se degradaba a un match sobre string y el compilador aconsejaba añadir un comodín.

Una lectura por índice tiene el tipo de su elemento

una errata tras xs[0]: ahora E0210 
fn first_len(xs: Array<string>) -> number {
  let s = xs[0]
  return s.lenght
}

[E0210] type `string` has no field `lenght`; did you mean `length`?

xs[i] sobre un Array<E> es un E, así que el editor, glyph check --no-tsc y las herramientas del agente comprueban lo que haces con él: leer un campo, llamar a un método, un return, un argumento, un let anotado.

Historia qué se comprobaba antes

Hasta 0.1.183 un elemento leído por índice no tenía tipo para Glyph. return xs[0] bajo -> number, un campo mal escrito sobre rows[0] y xs[0] pasado a un parámetro number pasaban, y solo el paso de tsc de un build completo los detectaba. El tipo es el que tsc da al código generado, que deja noUncheckedIndexedAccess desactivado: E, no E | undefined. El índice de Glyph lanza un RangeError más allá del final en lugar de devolver undefined; usa array.get cuando quieras un Option. Leer una clave de un Record sigue siendo E0224 salvo que su tipo de valor sea unknown, y un índice sobre un string o sobre un valor de npm no se juzga.

Las uniones genéricas importadas se comprueban

una variante que falta en un match sobre una unión genérica importada 
import tree { Tree, Node }

fn label(t: Tree<string>) -> string {
  return match t {
    Node({ key: k }) => k    // Leaf unhandled: built clean, threw at run time
  }
}

Ahora es E0200 en cualquier caso, con las dos formas de import y tanto con un parámetro abierto como con una instanciación concreta.

Historia por qué la comprobación nunca arrancaba

Una unión que declara tu propio módulo se comprueba tenga o no parámetros de tipo. Una importada de un módulo hermano solo se comprobaba cuando no tenía ninguno. Tree<string> llega a la ruta de cobertura entre módulos como una aplicación de una unión importada y no como una unión importada, y la condición que arranca la comprobación buscaba lo segundo, así que el match ni siquiera se contaba: tsc --strict pasaba y un Leaf lanzaba una excepción. Borra <K> de los dos archivos y el mismo programa era E0200.

Un parse no puede afirmar una comprobación que no hizo

un parse que informaba de éxito sin comprobar: ahora E0304 
type Conn = { id: number, sock: Socket }

Conn.parse(body)   // Ok. `sock` was never checked, and the message said it was

Tener un socket en un record es normal y sigue compilando. Validarlo se rechaza ahora donde se escribe y en cada módulo que importa el record, nombrando el campo y su tipo, y el rechazo sigue la forma: a través de un record anidado, un Array, un Option.

Detalles por qué la presencia no es una comprobación, y el arreglo que pide

Cada tipo record lleva un descriptor de runtime. Para un campo cuyo tipo el compilador no puede ver por dentro, un socket o cualquier cosa a la que se llega a través de extern_ts, la comprobación generada era "¿está presente?" mientras el mensaje decía field `sock` must be Socket. Un booleano que siempre es verdadero no sirve para nada. Uno que siempre es verdadero bajo un mensaje que nombra un tipo que nada comprobó es peor, porque parse es aquello en lo que se le dice a una frontera que confíe.

El arreglo que pide es la separación que habrías escrito de todos modos: un tipo de transporte cuyos campos se pueden comprobar todos, y luego un record de dominio que construyes a partir de él. unknown no se ve afectado, porque no afirma nada y la presencia es de verdad toda la comprobación.

Un cambio de firma, invisible en la llamada: cerrado en la 0.1.116

Cambia una función para que reciba un payload en lugar de un string sin más, y todas las llamadas que seguían pasando la forma antigua compilaban sin errores.

billing.glyph: una unión pasa por un parámetro `string` sin que nadie lo note 
type PaymentResult = Settled(string) | Declined(string)

fn takes_string(s: string) -> number { return s.length }

fn charge(r: PaymentResult) -> number {
  return takes_string(r)   // compiled clean before 0.1.116
}
glyph build, ahora 
[E0211] argument type mismatch: expected `string`, found `PaymentResult`
   ╰─ Pass a value of the expected type, or change the parameter's type.
Detalles dónde salta la comprobación y dónde se calla

Un parámetro de tipo string, number o bool aceptaba antes un valor de una unión o un record declarados sin ninguna queja, aunque la llamada idéntica con un argumento bool que no encajaba ya era E0211.

La comprobación lee la declaración, así que solo salta donde la respuesta es segura. Un alias primitivo como type Id = string se lee como el string que nombra, así que se decide igual. Una unión de literales de cadena (D30) se compara por sus literales, y un valor de un interface se rechaza donde se declara un string, porque su valor es un objeto. Un cuerpo extern_ts o typeof sigue sin decir nada, y void también queda excluido. Llega igual a un argumento, a un return y a una anotación de let, porque los tres comparten una relación.

La otra dirección pasa por los miembros del valor, como en TypeScript: 5 se rechaza donde se declara interface HasName { name: string }, y "abc" se acepta donde se declara interface HasLen { length: number }, porque una cadena tiene length. Un bigint se lee por sus propios miembros, así que ahí se rechaza: no tiene length. Dos emparejamientos aún no se deciden y quedan para tsc: una interfaz cuyos miembros son todos opcionales y no comparte ninguno con el valor (G526), y Option, Result y Record frente a una interfaz (G527).

Un const anotado tiene tipo

Un const tenía el hueco equivalente en el lado receptor.

catalog.glyph: un const anotado, y el campo que no tiene 
type Sheet = { rows: number, cols: number }
const ORIGIN: Sheet = { rows: 0, cols: 0 }

fn f() -> number {
  return ORIGIN.rowz   // compiled clean before 0.1.116
}
glyph build, ahora 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
Detalles consts sin anotar, y por qué los dos arreglos son breaking

Un const de nivel de módulo con una anotación de tipo se traducía a Ty::Unknown dijera lo que dijera la anotación, así que una errata en un campo era invisible justo donde el let anotado idéntico dentro de una función ya la informaba.

Desde 0.1.166 una const sin anotar tiene el tipo de su inicializador, leído como tsc lee la const de TypeScript que escribe el emisor: const MODE = "read" conserva su tipo literal, y un literal dentro de un objeto o un array se ensancha, así que const ITEMS = [1, 2] es un Array<number> y ITEMS.push(3) fuera de mut es E0240. Un inicializador que el checker no puede tipar deja la const sin tipo. Ambos arreglos rompen compatibilidad en glyph check --no-tsc, el servidor de lenguaje y el playground, porque cada uno empieza a detectar un programa que la versión anterior aceptaba; un glyph build completo ya estaba en rojo por tsc en ambos casos.

Un campo que el record no declara

un campo opcional mal escrito: ahora E0210 
module profile

pub type Profile = {
  name: string,
  nick?: string,
}

pub fn guest() -> Profile {
  return { name: "guest", nik: "g" }   // [E0210] type `Profile` has no field `nik`; did you mean `nick`?
}

Una clave que el record declarado no tiene pasaba antes el checker de Glyph, así que una errata en un campo opcional tiraba su valor y solo tsc lo notaba. El editor, las herramientas para agentes y glyph check --no-tsc la rechazan ahora, con el mismo error que da leer ese campo, y glyph fix renombra nik a nick.

Detalles dónde se comprueba y qué queda fuera

Se comprueba dondequiera que un literal escrito se encuentra con un tipo declarado: un let, un return, un argumento de llamada, la carga de una variante, una asignación mut, un campo anidado, un elemento de array, un brazo de match y el argumento de Some, Ok o Err, que tsc deja pasar. Un binding que guarda un record más amplio se sigue aceptando, como lo acepta tsc, y también los campos que vienen de un spread y las claves escritas para un Record<K, V>.

Match

  • La cobertura de una unión importada todavía no mira dentro del payload de una variantelo siguiente que se profundiza
    Detalles

    Un parámetro de tipo desactivaba antes la comprobación: hasta la 0.1.90 un match sobre Tree<K> podía omitir una variante, compilar sin errores, pasar tsc --strict y lanzar una excepción en tiempo de ejecución, mientras que el mismo match sobre Tree era E0200. Eso está cerrado para una unión que declara tu propio módulo y, desde la 0.1.95, para una que está a un import de distancia. Lo que sigue siendo menos profundo en la ruta importada es la profundidad y no la condición de arranque: la comprobación que se ejecuta para una unión importada nunca mira dentro del payload de una variante, así que B(X) sobre una unión importada cuyo payload es a su vez una unión cubre cualquier B en lugar de informar del Y que falta, y no hay ningún parámetro de tipo de por medio. Eso es lo siguiente que se va a profundizar.

  • Una variante de payload en minúscula de una unión importada detiene el buildE0305
    Detalles

    Una variante en posición de payload se lee ahora de la lista de variantes de la unión del payload, así que las mayúsculas del nombre dejan de importar para una unión que declara tu módulo. Para una importada de otro módulo no hay lista que leer y sigue respondiendo la forma del nombre, lo que significa que Err(Blank) discrimina y Err(blank) detiene el build en E0305: un fallo ruidoso sobre un programa válido, que necesita el mismo registro de uniones importadas que necesita la comprobación de cobertura superficial de arriba.

  • Un patrón constructor sobre un payload record (Ok(Point)) falla en tsc, no en Glyph
    Detalles

    Un patrón constructor sobre un payload que es un record y no una unión (Ok(Point)) falla a través de tsc nombrando un .tag que nunca escribiste, cuando debería ser un diagnóstico de Glyph que nombre el tipo y el patrón.

  • Un brazo sin argumentos mal escrito informa de dos líneas para el mismo nombreE0220E0103
    Detalles

    La comprobación de erratas (E0220) cubre ahora por igual una unión declarada en el módulo y una a la que se llega a través de un import de namespace (model.Nooo(_)), con forma de constructor o sin argumentos: hasta la 0.1.115, una cabeza sin argumentos mal escrita sobre una unión importada (Loadign, sin argumentos) contaba como si cubriera una variante y no decía nada, mientras que la misma errata sobre una unión local ya informaba E0220; ahora las dos formas lo informan. Un brazo sin argumentos mal escrito también dispara E0103, una etapa antes, así que recibes las dos líneas para el mismo nombre.

Herramientas y librería estándar

  • El acceso a miembros de primitivos y arrays no tiene diagnóstico donde no se ejecuta tsc
    Detalles

    El acceso a miembros y las llamadas sobre string, number, bool y Array<T> se dejan a tsc por diseño, no por un hueco; Glyph permite ahí los miembros de JS tal cual, así que s.length y xs.length compilan y pasan tsc --strict, y lo que sigue faltando es un diagnóstico para las cuatro superficies que nunca ejecutan tsc: glyph check --no-tsc, el servidor de lenguaje, el servidor MCP y el playground.

  • Un build sin conexión con ejemplos necesita tsx o --no-test
    Detalles

    El ejecutor de ejemplos llama a tsx, así que un proyecto que tiene ejemplos y no tiene tsx en el PATH hace fallar el build en lugar de saltárselos sin avisar; es deliberado, pero significa que un build sin conexión necesita tsx instalado o --no-test.

  • Un await en un fn normal se detecta sobre tu propio código fuenteE0222
    Detalles

    El contexto asíncrono era la única regla que Glyph dejaba a tsc; un await en un fn normal es ahora E0222 sobre tu propio código fuente, con el inicializador de un const de nivel superior como el único caso que sigue permitido. Esa y otras dos reglas que subieron de etapa están en detectado antes.
