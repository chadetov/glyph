Si vienes de TypeScript

Qué cambia cuando ya escribes TypeScript

Menos de lo que esperas. Glyph compila a TypeScript que pasa tsc --strict, mantiene npm y tu despliegue, y se lee casi igual. Las diferencias son un puñado, y cada una cambia una forma de equivocarse por una comprobación que hace el compilador.

Si sabes TypeScript, ya sabes casi todo esto#

No aprendes un lenguaje nuevo, solo estas cuatro cosas. Son las que aparecen en todos los ejemplos de este sitio.

match
Un switch exhaustivo: sobre una unión, el compilador te obliga a manejar cada caso. En sentencias y expresiones también es el único condicional: no hay if/else ni operador ternario, se explica más abajo. JSX tiene los elementos <if> y <match>.
Result<T, E>
Los errores como valores de retorno, no como excepciones lanzadas. Los manejas con match, o los propagas con el operador ?.
fn f() -> T
Una función; el -> es su tipo de retorno. Un type X = {...} es un record, y un type X = A | B es una unión etiquetada.
mut x = e
La reasignación es explícita y se puede buscar con grep. Un binding let normal nunca cambia a tus espaldas; escribes mut para cambiar uno.

Un componente de React en los dos#

El mismo componente dos veces: una lista de invitaciones con estado vacío, una línea que cuenta las que siguen esperando respuesta y una etiqueta en cada fila. Donde el TSX usa && y ? :, el Glyph usa elementos JSX: <match>, que recibe un valor y un <case> por patrón, y <if> con un <else> opcional, la forma más ligera para un booleano simple. Las listas usan <for>, y el atributo es class, que compila a className.

InviteList.tsx 
export type Invite = { email: string; accepted: boolean };

export function InviteList(props: { invites: Invite[] }) {
  const waiting = props.invites.filter((i) => !i.accepted).length;
  return (
    <section>
      {waiting > 0 && <p className="note">{waiting} waiting for a reply</p>}
      {props.invites.length === 0 ? (
        <p className="empty">No invites sent yet.</p>
      ) : (
        <ul>
          {props.invites.map((invite) => (
            <li key={invite.email}>
              {invite.email}
              {invite.accepted ? (
                <span className="ok">joined</span>
              ) : (
                <span className="wait">pending</span>
              )}
            </li>
          ))}
        </ul>
      )}
    </section>
  );
}
invites.glyph 
module invites

import std/array

pub type Invite = { email: string, accepted: bool }

pub component InviteList(props: { invites: Array<Invite> }) {
  let waiting = array.filter(props.invites, fn(i: Invite) { return !i.accepted }).length
  return <section>
    <if cond={waiting > 0}>
      <p class="note">{waiting} waiting for a reply</p>
    </if>
    <match value={props.invites.length}>
      <case 0>
        <p class="empty">No invites sent yet.</p>
      </case>
      <case else>
        <ul>
          <for invite in={props.invites} key={invite.email}>
            <li>
              {invite.email}
              <if cond={invite.accepted}>
                <span class="ok">joined</span>
              </if>
              <else>
                <span class="wait">pending</span>
              </else>
            </li>
          </for>
        </ul>
      </case>
    </match>
  </section>
}

La mitad en Glyph es más larga, sobre todo porque cada rama es su propio elemento. Un <match> tiene que cubrir todos los valores: quita aquí el <case else> y el build se detiene con E0218. Sobre una unión tiene que cubrir todas las variantes (E0200), y ahí es donde las líneas de más se pagan: ¿Funciona con React? muestra uno, con hooks y Context.

El soporte de editor y la depuración tienen sus propias respuestas: la respuesta sobre herramientas cubre el language server y la extensión de VS Code, y la respuesta sobre depuración cubre los source maps que vuelven al archivo .glyph. Para el ciclo de desarrollo, glyph build --watch recompila el TypeScript cada vez que guardas un archivo .glyph. Un servidor de desarrollo de Vite que importa esa salida recarga la página entera después de cada recompilación en lugar de reemplazar el componente en caliente, así que el estado del componente se pierde; tus propios archivos .tsx conservan el hot reload de Vite. Escribe la salida fuera del directorio de build de Vite (dist/ por defecto), porque su servidor de desarrollo no vigila ese directorio.

En este sitio, "agentes" son asistentes de programación con IA como Claude, Copilot y Cursor. Glyph es a ellos a quienes más ayuda, pero las comprobaciones son las mismas tanto si el código lo escribió una persona como un modelo. Si ya usas TypeScript estricto con zod y eslint, esto es lo que añade un lenguaje a eso.

No hay sentencia if#

Una bifurcación sobre un booleano es un match sobre true y false. Cuando solo actúas en un lado, el otro brazo es un bloque vacío. JSX es la excepción: el elemento <if> del componente de arriba renderiza sus hijos cuando la condición se cumple y nada en caso contrario.

TypeScript 
function label(admin: boolean): string {
  return admin ? "admin" : "member";
}

if (verbose) {
  console.log("starting");
}
Glyph 
fn label(admin: bool) -> string {
  return match admin {
    true => "admin",
    false => "member",
  }
}

match verbose {
  true => io.println("starting"),
  false => {},
}

El motivo es la decisión D3 de la especificación: una sola construcción para bifurcar según un valor, así que hay una sola forma que leer, escribir y buscar. Un valor que sale de una bifurcación siempre sale de un match, cuyo tipo de resultado calcula el checker propio de Glyph en lugar de dejárselo a tsc. Para una unión, esa misma construcción es la que tiene que cubrir todos los casos (E0200). Para un booleano aporta poco, ya que false => {} no dice más que omitir un else.

Tiene un coste. Un ternario de una línea se convierte en un match de cuatro, un return anticipado según una condición es un match con un brazo vacío, y es lo primero que le parece raro a quien lee TypeScript. La especificación recoge la verbosidad como un coste aceptado. Escribir if de todos modos da el error E0006, cuya ayuda muestra la forma con match; un ternario da E0013 con la misma ayuda.

El peaje que ya pagas#

Si desarrollas con agentes de IA sobre un código TypeScript, estos son los costes del día a día. Cada uno tiene una respuesta concreta en Glyph, enlazada desde la lista.

  • Los agentes se inventan APIs, porque TypeScript borra sus tipos y el runtime deja de coincidir con lo que había al compilar. Los tipos de Glyph llevan una comprobación en tiempo de ejecución (T.parse, T.is), consulta APIs tipadas.
  • Los agentes tapan la incertidumbre con any y as unknown as T, y el compilador se lo permite. Ninguno de los dos existe en Glyph, consulta la tabla de abajo.
  • Pides un cambio de una línea y te reescriben el archivo entero, porque el formateador encadena cambios en cada edición. glyph fmt tiene un solo formato sin opciones, consulta diffs limpios.
  • Mantienes un validador escrito a mano junto a cada tipo (zod, y un serializador), y un agente renombra un campo en uno pero no en los demás; todo sigue compilando. En Glyph el tipo es el validador.
  • Haces grep de un símbolo y encuentras diez coincidencias que no tienen nada que ver: sobrecargas, decoradores, namespaces fusionados. Glyph no tiene nada de eso, consulta encontrar cosas.

Los interruptores de apagado que te da TypeScript, y lo que Glyph tiene en su lugar#

Cada construcción de TypeScript de abajo le dice al checker que deje de comprobar. Ninguna es sintaxis de Glyph. La columna del medio es lo que imprimió glyph check --no-tsc para cada una en la 0.1.149.

glyph check tiene flags que se saltan una fase entera (--no-tsc se salta la ejecución de tsc --strict, --no-test se salta los tests @example), y ninguno que silencie una comprobación concreta. La lista completa de lo que acepta un proyecto TypeScript y Glyph rechaza, con cada caso ejecutado en los dos compiladores, está en la página de casos.

Una vía de escape, y la puedes buscar con grep#

Cuando necesitas TypeScript que Glyph no sabe escribir, extern_ts("...") acepta un tipo o una expresión en línea, y tsc lo sigue comprobando. Para un módulo entero, pon el .ts en src/extern/ y escribe import extern/name; los imports relativos no están permitidos en ningún otro caso, así que esa ruta es la única entrada. Las dos formas contienen la palabra extern, así que grep -rn extern src/ lista cada sitio donde el checker cede el control a TypeScript.

src/clock.glyph 
module clock

pub fn now_ms() -> number {
  return extern_ts("Date.now()")
}

Cómo es el TypeScript generado#

TypeScript normal, un archivo por módulo, que puedes leer y commitear. Una unión se convierte en una unión discriminada más un valor que lleva su comprobación en tiempo de ejecución, y un match se convierte en un switch sobre la etiqueta. Esta es la salida de glyph build para el módulo de la izquierda, sin las líneas de import.

plan.glyph 
module plan

pub type Plan = Free | Pro | Team

pub fn seats(p: Plan) -> number {
  return match p {
    Free => 1,
    Pro => 5,
    Team => 50,
  }
}
plan.ts (generado, recortado) 
export type Plan =
  | { tag: "Free" }
  | { tag: "Pro" }
  | { tag: "Team" };

export const Free: Plan = { tag: "Free" };
export const Pro: Plan = { tag: "Pro" };
export const Team: Plan = { tag: "Team" };
export const Plan = {
  is(value: unknown): value is Plan { ... },
  parse(value: unknown) { ... },
  schema: ...,
};

export function seats(p: Plan): number {
  const __m0 = p;
  switch (__m0.tag) {
    case "Free": { return 1; }
    case "Pro": { return 5; }
    case "Team": { return 50; }
    default: throw new Error("non-exhaustive match");
  }
}

Borra el brazo Team y el build se detiene antes de escribir nada de TypeScript:

Si dejas de usar Glyph, lo que te quedas es el .ts generado. No tiene dependencias en tiempo de ejecución aparte de un pequeño directorio de soporte que el build escribe a su lado.

npm, y el TypeScript que ya tienes#

Un módulo .glyph importa un paquete de npm por su nombre (import kafkajs { Kafka }), tipado con las declaraciones del propio paquete, y tu .ts existente importa los módulos de Glyph generados como cualquier archivo local. Así que puedes empezar con un solo módulo dentro de una app que sigue siendo TypeScript. Los detalles están en tres respuestas.

¿Puedo usar mis librerías de TypeScript, JavaScript y npm?

Importar paquetes, mantener un shim en .ts e importar Glyph de vuelta en .ts.

 ¿Puedo adoptar Glyph dentro de mi app actual?

El núcleo del dominio en Glyph y el resto en TypeScript, en un proyecto Vite estándar.
