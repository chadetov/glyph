Para agentes · Model Context Protocol

Conecta tu agente al compilador de Glyph

glyph mcp ejecuta un servidor de Model Context Protocol con once herramientas sobre tu proyecto: qué es un símbolo, qué se rompe si lo cambias, si un valor de un tipo puede ir donde se declara otro, de qué depende una declaración, qué exporta un módulo, diagnósticos comprobados dentro del proyecto, el tipo en la posición del cursor, dónde se define un nombre, cada referencia a él, cada sitio con match sobre una unión y búsqueda de símbolos. Cada una es también un verbo de glyph query, así que un agente sin cliente MCP hace las mismas preguntas y recibe los mismos bytes.

Por qué lo quiere un agente#

Un agente que edita un código suele trabajar a ciegas. Lee archivos, adivina tipos y solo se entera de si ha roto algo después de un build. Glyph ya responde a esas preguntas para un editor. glyph mcp le da a un agente las mismas respuestas directamente desde el compilador, sin rascar la salida del build ni leer todos los archivos para saber quién llama a qué. Dos de las herramientas responden preguntas que un editor nunca hace: glyph_symbol devuelve las variantes de una unión con la sintaxis que construye cada una, que es lo que un agente necesita antes de escribir el match, y glyph_impact responde qué rompe una edición antes de que la edición exista.

Configúralo#

Cualquier cliente MCP puede lanzarlo. Apunta el cliente al binario glyph con el subcomando mcp, y pasa la raíz del proyecto como argumento o ejecútalo desde el directorio del proyecto. Habla MCP por stdio, así que no hay puerto ni daemon.

configuración del cliente MCP (genérica) 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp", "/path/to/your/project"]
    }
  }
}

Al conectarse por primera vez, el cliente llama a initialize y tools/list; el servidor anuncia las once herramientas de abajo. Las posiciones que envías siguen la convención de LSP: una line empezando en 0 y un character empezando en 0, en unidades de código UTF-16. Los rangos de los diagnósticos vuelven como los imprime glyph check --json, con line y col empezando en 1 más el offset en bytes.

La descripción de cada herramienta lleva el contrato que necesitas en el momento de la llamada, y el manual completo está en glyph llms --json bajo tools, indexado por nombre de herramienta, con el verbo de glyph query de cada una al lado. Esa respuesta antes llevaba todos los manuales: once herramientas, 31,446 bytes de descripción en una respuesta de 45,509 bytes. Ahora son 8,627 en una respuesta de 20,386 bytes, y no se borró nada. Cada sesión paga tools/list al conectarse y paga el manual solo cuando lo pide. Ese documento se genera a partir de las propias tablas del compilador, y un test hace fallar el build si nombra una herramienta que este servidor no sirve.

Las once herramientas#

herramientas que expone glyph mcp 
// everything the compiler holds about one symbol: kind, identity,
// visibility, a record's fields, a union's variants with payloads and
// construction syntax, parameters and return, interface members,
// whether a `match` over it must be exhaustive, its `@example`.
// The identity reaches the stdlib: std/result::Result answers with
// Ok(T) and Err(E), and `path` is null beside the reason why
glyph_symbol(entity)                       // or (path, line, character)

// what breaks if you make one named change to one declaration:
// add_variant, remove_variant, rename, change_arity,
// change_signature_type, remove. One verdict per site
glyph_impact(entity, change)

// can a value of `from` go where a `to` is declared? Asked of the
// checker's own comparison. Each side is a `module::name` or a
// Glyph type spelling read in the scope of `path`
glyph_assignable(path, from, to)

// every diagnostic for one file, checked inside its project, in the
// shape `glyph check --json` prints, plus what was not checked
glyph_diagnostics(path)

// the type at a position: an expression, a declaration name, a
// parameter, an annotation, a variant, or a binding
glyph_hover(path, line, character)

// where the name is defined, following imports across modules,
// with the `module::name` so the answer chains into glyph_impact
glyph_definition(path, line, character)

// every edge into a symbol across the project, split by relation
// (CALLS, REFERENCES, GENERATED_FROM), each with its provenance
glyph_references(path, name)               // or by position

// every `match` site over one tagged union and which variants each
// site's arms name, with the union's own variants
glyph_variants(path, name)

// search top-level declarations and union variants by name, each
// entry with its identity, `pub`, kind and one-line signature
glyph_symbols(query)

// what one declaration depends on: every declaration its own source
// names, split by relation (CALLS, REFERENCES, FIELD_ACCESS), each
// edge with both ends and its provenance. The mirror of references
glyph_dependencies(entity)

// what one module makes visible to an importer: every `pub`
// declaration and every variant a `pub` union hoists, each with
// its identity, kind and signature
glyph_exports(module)

Míralo#

Un tools/call a glyph_diagnostics sobre un archivo con una errata en un campo devuelve el diagnóstico del propio compilador, el mismo tipo de Rust que serializa glyph check --json, dentro de un envoltorio que además dice qué no cubrió la comprobación.

petición 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": { "path": "src/user.glyph" }
  }
}
resultado (el contenido JSON de la herramienta) 
{
  "path": "src/user.glyph",
  "module": "user",
  "project_root": "src",
  "member": true,
  "diagnostics": [
    {
      "code": "E0210",
      "severity": "error",
      "stage": "typecheck",
      "message": "type `U` has no field `naem`; did you mean `name`?",
      "help": "Check the field name for a typo,
        or add the field to the type.",
      "entity": "user::greet",
      "file": "user",
      "range": {
        "start": { "line": 9, "col": 10, "offset": 99 },
        "end":   { "line": 9, "col": 16, "offset": 105 }
      },
      "union": null,
      "missing_variants": null
    }
  ],
  "unindexed": [],
  "not_run": [ ... ]
}

El archivo se comprueba dentro de su proyecto, así que un campo incorrecto en un record importado y un match al que le faltan brazos sobre una unión importada se informan aquí igual que los informa glyph check. Lo que la herramienta no pudo cubrir aparece en la respuesta en lugar de dejar que lo supongas: member dice si el recorrido del proyecto llega al archivo, unindexed nombra los archivos del proyecto que no se pueden parsear y not_run nombra las tres comprobaciones que hace glyph check y esta no: tsc, E0104 para un import que no nombra ningún módulo, que necesita la vista del build sobre node_modules, y E0400 para un @example que falla, que se decide ejecutando el proyecto generado. Un test ejecuta las dos superficies sobre seis proyectos y compara el JSON clave por clave, así que no pueden divergir.

glyph_references abarca todo el workspace: preguntas por un símbolo y obtienes su declaración, cada uso y el binding de import de cada módulo que lo importa, en todos los archivos. Usa la misma identidad entre archivos que el renombrado del editor, así que la respuesta cubre todo el proyecto, no solo el archivo desde el que preguntaste.

¿Sin cliente MCP? Las mismas preguntas en la línea de comandos#

Cada herramienta tiene un verbo de glyph query que recibe los argumentos de la herramienta como flags e imprime su JSON por stdout. Una pregunta respondida sale con 0; una rechazada escribe el motivo en stderr y sale con 2. Los verbos pasan por el mismo punto de entrada al que llega un cliente MCP, y un test de integración hace la misma pregunta a las dos superficies y compara las respuestas como texto, así que un verbo que reformateara o resumiera haría fallar el test.

las mismas once preguntas, sin cliente 
glyph query symbol       --path src/main.glyph --entity orders::OrderStatus
glyph query impact       --entity orders::OrderStatus --change add_variant --variant Refunded
glyph query assignable   --path src/main.glyph --from 'Nullable<int>' --to int
glyph query diagnostics  --path src/main.glyph
glyph query hover        --path src/main.glyph --line 9 --character 6
glyph query definition   --path src/main.glyph --line 9 --character 6
glyph query references   --path src/orders.glyph --name create
glyph query variants     --path src/orders.glyph --name OrderStatus
glyph query symbols      --query order
glyph query dependencies --path src/main.glyph --entity main::build
glyph query exports      --path src/main.glyph --module orders

// the same two, asked about a module the compiler carries
glyph query symbol       --path src/main.glyph --entity std/result::Result
glyph query exports      --path src/main.glyph --module std/result

Cuando el build ya está en rojo#

Las herramientas responden preguntas hechas antes de una edición. Después de una, lo que hay que leer es glyph check --agent, que imprime los diagnósticos de check --json con dos claves más en cada uno: constraints, los invariantes que una edición de reparación tiene que mantener, y symbols, la respuesta de glyph_symbol para cada símbolo que nombra el diagnóstico, así que la siguiente edición no necesita una segunda llamada. En un match al que le faltan brazos, eso significa que las variantes de la unión con sus payloads llegan junto con el error que las pidió, junto con la frase que dice que un brazo else renunciaría a la garantía que el diagnóstico existe para proteger. Cuando la reparación está totalmente determinada, glyph fix la escribe y dice lo que ha descartado. Hay un recorrido por todo el ciclo con salida real.

Dónde está#

Disponible hoy

Un servidor glyph mcp [root] por stdio con once herramientas: glyph_symbol, glyph_impact, glyph_assignable, glyph_diagnostics, glyph_hover, glyph_definition, glyph_references (en todo el workspace), glyph_variants, glyph_symbols, glyph_dependencies y glyph_exports. Cada una tiene un verbo de glyph query que imprime el mismo JSON. Las respuestas salen de las propias consultas del compilador, y cada dato que una herramienta no tiene es null, junto a una frase <key>_absent que explica por qué. El hover responde sobre un nombre declarado en otro módulo, así que tanto una función importada en el sitio de la llamada como un campo leído de un record importado tienen tipo. La identidad de una entidad llega hasta la librería estándar: el Result del preludio es std/result::Result, que es el módulo bajo el que lo registra el resolver y el módulo desde el que el emisor escribe el import, así que glyph_symbol sobre él responde con Ok(T) y Err(E) y glyph_exports sobre std/result lista su superficie. No hay código fuente de Glyph detrás, así que path y range son null con ese motivo en lugar de faltar.

En camino

Las herramientas solo leen: no puedes renombrar ni aplicar una edición a través de MCP. La parte de escritura está en la línea de comandos, como glyph fix. El servidor vuelve a recorrer el proyecto en cada llamada en lugar de mantener un índice en caché, y se salta cualquier archivo que no se pueda parsear. La respuesta de tools/list ocupa 20,386 bytes, frente a 45,509, y sigue siendo contexto que cada sesión paga al conectarse.

Además de las herramientas, un agente puede leer el lenguaje y la superficie de diagnósticos sin conexión: llms.txt es la prosa, glyph llms --json el mismo conocimiento en forma de datos sacado de las propias tablas del compilador, y glyph build --json la vía por lotes para diagnósticos con código en todo un árbol.
