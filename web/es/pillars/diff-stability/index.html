Pilar 03 · El pulido

Estabilidad de los diffs

Un cambio de una línea es un diff de una línea. Un formato canónico, comas finales y una lista que va o entera en línea o entera con un elemento por línea, sin reempaquetarse nunca, así que una revisión muestra el cambio que se hizo, no el ruido a su alrededor.

Revisar es leer diffs#

Casi todo lo que nos da confianza en un cambio (la revisión, el blame, el revert, el bisect) se basa en el diff. Así que la relación señal/ruido del diff es lo que cuenta de verdad. En la mayoría de los códigos es terrible: un formateador recoloca una línea partida, un ordenador de imports baraja un bloque, un renombrado toca los espacios de cada llamada, y la única línea que importa queda enterrada entre cincuenta que no.

Los agentes lo empeoran mucho. Ante una tarea pequeña, un modelo reescribe sin problema una función entera, o un archivo entero, para cambiar una cosa, porque regenerar le resulta más fácil que editar con precisión. A quien revisa le toca comparar una reescritura con el original y esperar que el único cambio real sea el que se pidió. Glyph está hecho para que el formato no le dé al modelo nada que remover.

01 Un formato canónico, sin opciones#

glyph fmt reimprime cada archivo con un único formato fijo: sangría de dos espacios, coma final en cada lista de varias líneas, y una lista que se queda en una línea mientras quepa en 100 columnas y pasa a un elemento por línea cuando no. Es todo o nada. El formateador nunca reempaqueta tus elementos para llenar una línea, así que una lista nunca está en parte en una fila y en parte en la siguiente, y añadir un campo es una sola línea añadida. Como hay exactamente una forma legal, no hay nada que discutir ni nada que una herramienta pueda "arreglar" por su cuenta.

El límite de ancho es lo que cuesta esto. Renombra un binding de forma que una llamada pase de 100 columnas y la llamada se expande a un argumento por línea: una edición de un token, un diff de cuatro líneas. A cambio, el formato depende del código y de la columna en la que empieza y de nada más, así que dos agentes que editan el mismo archivo llegan a los mismos bytes.

Estilo recolocado: un cambio, tres líneas tocadas git diff (formato empaquetado) 
- type User = { id: number, name:
-   string }
+ type User = { id: number, name:
+   string, email: string }
Glyph: un cambio, una línea añadida git diff (canónico) 
  type User = {
    id: number,
    name: string,
+   email: string,
  }

La coma final hace un trabajo discreto: como el último elemento ya termina en coma, añadir un hermano nunca edita la línea de arriba. Una inserción, una línea.

02 El orden es estable, así que el historial se entiende#

Un elemento por línea significa que reordenar, insertar o quitar un elemento solo toca las líneas de ese elemento, nunca las de sus vecinos. git blame sigue teniendo sentido: el último commit que tocó cada línea es el commit que de verdad cambió ese elemento, no la pasada de formato que reempaquetó la fila que compartía.

03 Sin barrel files: sin ruido en los imports#

Como los imports nunca reexportan y no hay capas de agregación index.ts (E0102), añadir o mover un símbolo no se propaga por un barrel que importan todos los consumidores. Las aristas de dependencia que editas son las que querías editar; el resto del grafo de imports no se mueve.

04 La generación es idempotente, no un bloque opaco#

La misma disciplina se extiende al código generado. glyph gen y glyph regen reimprimen su salida con el formateador canónico, así que regenerar tras un cambio en la especificación produce un diff mínimo que de verdad puedes revisar, un par de líneas cambiadas, no la sustitución completa de un archivo escrito por una máquina. Y cada .ts generado incluye un source map, así que hasta la salida compilada se puede seguir limpiamente hasta la línea que cambiaste.

un campo añadido a la especificación → el diff regenerado 
  type Task = {
    id: number,
    title: string,
+   done: bool,
  }
// glyph regen re-ran the recorded command; this is the whole diff.

05 "TypeScript puede hacer esto con Prettier"#

Con buena parte del formato, sí. Prettier con trailingComma: "all" pone una coma en el último elemento e imprime las listas largas con un elemento por línea, y eso te da casi toda la sección 01. Las diferencias están en tres sitios.

El formato depende solo del código. Prettier mantiene expandido un objeto literal si su autor puso un salto de línea después de la {, y lo colapsa si no lo puso, así que el mismo objeto se puede imprimir de dos formas según cómo se escribiera la primera vez. Dos agentes que escriben lo mismo producen dos formatos, y la siguiente edición de uno de ellos aparece como una recolocación. glyph fmt imprime { a: 1, b: 2 } igual, venga como venga partida la entrada.

No hay nada que configurar. La salida de Prettier es lo que diga el archivo de configuración del repositorio, y algunos repositorios no tienen. Un agente que pasa de un proyecto TypeScript a otro se encuentra un formato distinto en cada uno. Un archivo Glyph tiene el mismo formato en todos los proyectos, porque el formateador no tiene opciones.

El formateador no puede cambiar lo que dice un archivo. glyph fmt se prueba parseando su propia salida y comparando el árbol sintáctico con el de la entrada, en cada ejemplo del repositorio y con un fuzzer. Cuando un comentario está en un sitio para el que el formato no tiene línea, rechaza el archivo (E0500) en lugar de mover el comentario junto a código que no describe.

Hay una cosa de la lista que todavía no está hecha: glyph fmt no ordena los imports, así que dos agentes que añaden un import en sitios distintos siguen produciendo bloques de imports distintos (G358).

La estabilidad de los diffs es lo que convierte "el agente cambió algo" en "el agente cambió exactamente esto". Cuando el ruido de fondo es cero, revisar es rápido y la confianza sale barata.

El benchmark: en camino#

La cifra que lo recoge es el tamaño del diff por cambio lógico: cuántas líneas se mueven al hacer una edición intencionada, en Glyph frente a un cambio equivalente en TypeScript pasado por un formateador típico. Glyph todavía no se usa en el mundo real, así que el gráfico de abajo es un marcador de posición que se rellenará con mediciones reales cuando haya un historial real del que sacarlas.
