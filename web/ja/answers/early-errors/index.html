なぜ重要か

Glyph は TypeScript にコンパイルし、その出力を tsc --strict で型検査します。そのため Glyph がモデル化していないミスも失われはしません。ただし 1 段階遅れて、出力されたファイルの言葉で戻ってきます。自分で書いた覚えのない関数の中の await を指す TS1308 や、書いていない switch についての TS2366 です。

行番号はあなたの .glyph に対応付けられますが、説明はそうなりません。この隔たりこそ、コンパイラが教えるのをやめてしまう場所です。

そこで Glyph が自分で判定できるルールは、1 つずつ前の段階に移しています。

  • E0222async fn の外での await
  • E0223値として使われている match の中で、値を生まない match アーム
  • E0008mut なしで書かれた代入

どれもルールを名指しし、その背後にある設計判断を示し、修正前と修正後を見せます。

値を生まないアーム

以前は、出力された switch が自分のケースを抜けてしまい、型は string なのに text には undefined が入っていました。tsc はこの形のいくつかは検出しますが、見逃すものもあります。

今の Glyph は、位置から判定できるところではどこでもこれを判定します。let、mut、return、そして戻り値の型を宣言した関数の末尾です。文としての match では、X => {} は意図的な何もしない処理としてそのまま使えます。

async fn の外の await

await も同じ考え方です。Glyph にはユーザーから見える Promise がありません。async fn -> T は await されて T になるので、それ以外の場所の await には中断すべきものがありません。

glyph build、対象は `fn total() -> number { return await fetch_count() }` 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

// before: no Glyph diagnostic, then
dist/main.ts:14:18 - error TS1308: 'await' expressions are only allowed
within async functions and at the top levels of modules.
詳細 どの呼び出し可能なものが判定するか

以前は生成されたファイルに対する tsc の TS1308 でしたが、今は E0222 です。判定するのは最も内側の呼び出し可能なものなので、async fn の中にある同期ラムダはそれ自体が独立した文脈になります。TypeScript と同じルールです。 逆の間違い、つまり誰も await しない呼び出しは E0238 です。単独の行の save(1)、let _ = save(1)、let n: number = load() は拒否されます。呼び出しは始まるのに、プログラムはそれを待たずに先へ進むからです。発火して忘れるつもりの同期コールバックは task.detach(async fn() -> void { await save(1) }) と書きます。これは失敗を stderr に報告します。

mut のない代入

3 つ目は、初日から破られるルールについてです。Glyph はすべての変更に印を付けるので、束縛への再代入は mut x = e、束縛の導入は let x = e と書きます。

E0008E0302E0303

素の x = e は以前「unexpected token: Equals」と報告されていましたが、これはルールではなく文字を名指ししています。今は E0008 になり、glyph --explain E0008 がこの印がある理由を説明します。値が変わる場所はすべて mut で始まるので、grep "mut total" でそのすべてが見つかる、というものです。

詳細 ? 演算子、E0302 と E0303

? 演算子も、逆の方向から同じ扱いを受けています。? は、束縛と、それが置かれた文の前に配置される早期 return に展開されるので、展開先となる文が必要です。let、return、引数の中で使え、今では match アームの本体でも使えます。使えない場所では、演算子が未実装だと言うのではなく、それがどの位置なのか、どう束縛して外に出せばよいかをメッセージが示します（E0302 と E0303）。

もっと悪いケース：tsc も満足しているとき

間違った場所に出る tsc のエラーは厄介です。しかし本当の問題は、別の意味になったプログラムがきれいにビルドできてしまうことで、Glyph にはそれが 1 つありました。

宣言したトップレベルの名前は、タグ付きユニオンのバリアントのコンストラクタも含め、すべてそのまま出力モジュールに入ります。そのため Error という名前のバリアントは、モジュールのトップレベルに export function Error(...) を出力します。するとその下でコンパイラが書く new Error(...) が、あなたのバリアントを呼び出してしまいます。

glyph build、対象は `Error` バリアントを持つユニオン 
[E0110] `Error` cannot name a type, variant, or function: the emitted module
        references the JavaScript global `Error`, and this declaration would
        shadow it
 5 │   | Error(string)
   │     ──────┬─────
   ╰─ Rename it (e.g. `Error` -> `Failure`). The name is legal TypeScript, so
      nothing downstream catches the rebinding.

// before: no Glyph diagnostic, then, twenty lines later
dist/main.ts:31:12 - error TS2345: Argument of type 'string' is not
assignable to parameter of type ...
E0110E0111E0109
詳細 type Key = string | number、保護される名前の一覧、E0111

type Key = string | number は、見た目がもう少し穏やかな同じ欠陥です。Glyph では A | B はタグ付きユニオンを宣言し、そのメンバーはバリアントのコンストラクタです。つまりこの行は string と number という名前のバリアントを宣言します。これはコンパイルが通り、tsc --strict も通り、prelude の number 名前空間を隠す export const number を出力しました。後で number.to_string を呼び出して失敗するまで、何も失敗しませんでした。

スパンは宣言を指しています。名前を変える場所はそこだからです。保護される名前のリストは JavaScript のグローバル全般のリストからではなく、エミッタから導出されます。テストがエミッタを grep し、対応するエントリのない新しいグローバル参照が現れると失敗します。重要なのはこのテストです。Number は、int が出荷されて Number.isInteger を出力し始めるまでは無害でした。そもそもこの問題がリリースに入ってしまったのはそのためです。Date、Math、JSON は使えるままです。Glyph が出力するものの中にそれらは出てこないからです。

プリミティブのユニオンのケースには専用のコード E0111 があります。説明なしに拒否しても何も伝わらないからです。メッセージは、その行が実際にどうパースされたかを示し、名前付きのバリアントを案内し、生の TypeScript のユニオンが欲しい境界では extern_ts("string | number") を使うよう示します。Glyph が使わせない名前はすべて docs/reference/reserved-words.md に表としてまとめてあります。32 個のキーワード、E0109 の対象となる 33 個の TypeScript の予約語、そして隠蔽リストで、それぞれその名前が使えない理由が付いています。

これで何ができないのかも、はっきりさせておく価値があります。型やバリアントに Error という名前を付けることは、今もできません。この問題を見つけたスプレッドシートのアプリは、そのために Cellerr というバリアントを持っています。本来書きたかったプログラムは今も書けません。変わったのは、ビルドをグリーンにして別の意味にしてしまうのではなく、コンパイラが宣言の場所でそう言うようになったことです。

詳細 なぜ単にその名前を使えるようにしないのか

この名前を使えるようにするには、TypeScript に渡すときに Glyph の名前を変換（マングリング）する必要があります。そうするとスタックトレース、dist/ に対する grep、手書きの extern/ シムから見えるものが変わるので、黙って入れられる修正ではありません。

間違ったメッセージは、メッセージがないより悪い

隠蔽リストは、エミッタが値として書く名前から始まりました。型として書く名前が抜けていて、それがこの問題全体の中で最も鋭い形を生みました。

glyph build、以前：これが 15 個、どれも原因の近くにない 
dist/corpus/infer_output.ts:52:9 - error TS2353: Object literal may only
specify known properties, and 'code' does not exist in type 'Issue'.
glyph build、現在 
[E0110] `Issue` cannot name a type, variant, or function: the emitted module
        references the Glyph prelude global `Issue`, and this declaration
        would shadow it
   ╰─ Rename it. The name is legal TypeScript, so nothing downstream catches
      the rebinding.
詳細 なぜ Issue が衝突するのか、そして Record

すべてのディスクリプタの parse は Result<T, Issue[]> を返すので、出力モジュールはあなたが書いたかどうかにかかわらず Issue を書きます。自分のモジュールで type Issue = { path: Array<string>, message: string } を宣言するとそちらが優先され、出力された Issue オブジェクトにはあなたの型が知らない code フィールドがあるので、ビルドは生成コードについての tsc のエラーで、別の場所を指すスパンとともに失敗します。

Record も同時にリストに加わりました。TypeScript の組み込みなので、prelude の名前ではなく JavaScript のグローバルと一緒に登録しています。そうしないと、その名前がどこから来たかについてメッセージが間違ったことを言ってしまうからです。エミッタを grep するずれ検出のテストは今では ambient な型もカバーしていて、型の位置にある Issue[] を認識できるようにする必要がありました。これがリリースに入ってしまった理由はそこにあります。Schema、Component、Option は、Date を使えるままにしているのと同じルールで使えます。エミッタがそれらを書くのはあなたが注釈に書いたときだけなので、宣言しても何も隠しません。

match のせいにした import

この種類のもう 1 つは import でした。ローカルの import パスは、import しているファイルのディレクトリではなく、ビルドルート（glyph build に渡したディレクトリ）から解決されます。

glyph build examples/apps、対象は csvql/ 内の `import catalog` 
[E0104] unresolved import `catalog`: no module `catalog` under the build
        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from
        the importing file's directory (D15)
   ╰─ Build that module's own directory as the root, or spell the import path
      as it reads from the root.

// before: no import diagnostic, then
[E0218] non-exhaustive match on string   // on a match over all four values
詳細 以前の報告内容と、誤検出を避ける仕組み

外側のツリーをビルドすると import catalog は何も見つけられず、これまでそれを伝えるものはありませんでした。型は unknown に劣化し、それに対する match はマッチしていたバリアントを見失い、得られるのは、すべてのケースを網羅した match に対する E0218（網羅的でない match）でした。そのメッセージの言うとおりにすると、正しいコードに死んだ else アームを足すことになっていました。

この種のチェックの危険は、問題のないものにまで反応することです。npm パッケージのたびに誤報を出す import チェッカーは、それが置き換えた沈黙より悪いものです。そこでビルドはまず、.glyph ファイルなしで解決できるモジュール名を集めます。<root>/.types/ の下と同梱の Node シムにあるすべての declare module "X"、そしてプロジェクトの node_modules にあるすべてのパッケージです。このリストにある名前は、たとえローカルファイルとベース名が同じでも報告されません。プロジェクトに node_modules がまったくない場合、コンパイラは未インストールの依存とタイプミスを区別できないので、証明できるものだけを報告します。つまり、ルート配下のどれかの .glyph ファイルが該当する import です。

解決の仕組み自体は変わっていません。同じプログラムがビルドでき、同じプログラムが失敗します。変わったのは、失敗が 2 ファイル先の match を責めるのではなく、import を名指しするようになったことで、それがすべてです。間違った原因を報告するコンパイラは、それを追いかけて費やす 1 時間を奪い、その後のすべてのメッセージに対する信頼も失います。

トークンではなくルールを名指しする

同じ問題のもっと目立たない形は、正しいのに何も伝えないエラーです。

glyph check、以前と現在 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.
詳細 赤黒木と、修正後のメッセージがあなたのプログラムを名指しする仕組み

赤黒木を書いていたエージェントが、ML 系のどの言語にもある位置引数のコンストラクタを使おうとしたところ、パーサは最初のカンマで止まり、「) が必要」と「必要なトークンを追加してください」という助言を出しました。そこに ) を足すと、動くプログラムではなく別のプログラムになります。Glyph のバリアントはペイロードを 1 つだけ持ち、複数のフィールドを持つペイロードはレコードです。出力のどこにも、そのどちらの文もありませんでした。

それを伝えるために、パーサは拒否する前にリスト全体を読む必要がありました。そのおかげで数えることもできます。スパンはたまたま止まった区切り文字ではなく 6 つのフィールド全体に下線を引き、提案されるレコードはバリアント名とファイル中の 6 つの型から組み立てられます。そのため修正案は、誰かの例ではなくあなたのプログラムを名指しします。フィールド名だけはコンパイラが用意できないので、穴として残します。

このメッセージの背後にあるルールは、穴ではなく選択です。Node(Black, l, x, b, h, r) は引数を入れ替えても型検査が通る形で、4 番目の位置は読み手に何も伝えません。レコードの書き方ならすべてのフィールドに名前が付き、match アームは使うフィールドだけを名指しします。どちらも grep で見つけられます。

0.1.121 でチェッカーが引き受けたもう 2 つ

Order { id: "a", total: 1 } は、TypeScript から来た人がレコードを作るときに書くものですが、Glyph にはこの形がありません。値は値だけで書き、型は注釈に書きます。

glyph check、対象は TypeScript 流に作ったレコード 
[E0013] a statement cannot begin on the line where
        `return Order` ends
   ╰─ Glyph has no `TypeName { ... }` construction form. Write the literal
      alone and put the type on the annotation: `let o: Order = { id: "a" }`.

// 0.1.121 to 0.1.145: [E0228] on `Order`, then [E0108] on the braces
// before that: [E0108] Warning: lint: unreachable code, and exit 0
E0228E00130.1.146 から
経緯 E0108 から E0228、そして E0013 へ

以前この行についてコンパイラが言っていたのは、終了コード 0 のビルドでの E0108（到達不能なコード）でした。名前が型に解決され、波括弧が return の後のブロックとしてパースされたからです。型の名前を値として書くと今は E0228 になり、メッセージは宣言から読み取られます。レコードならフィールドを、タグ付きユニオンならバリアントとそのペイロードの形を、文字列リテラルのユニオンならそのリテラルを列挙します。Order.parse(raw) と Order.is(v) は使えるままです。型自身のディスクリプタのレシーバは、型名が置かれるべき唯一の式の位置だからです。

これで名前が型だったケースは直りましたが、パースはそのままだったので、return h() { k: 2 } は相変わらず h() を返し、警告を出して波括弧を捨てていました。0.1.146 からは、文が終わった行にある { は、その前の名前が何であれ、パース時に E0013 になり、その help が同じ書き換えを示します。0.1.149 からは、このルールが波括弧で始まるものだけでなくすべての文に適用されます。let s = "a" "b" は以前 "a" を束縛して "b" を捨てていましたし、Glyph にはキャストがないので return x as User は 3 つの文になっていました。

ブロック内の各文は、それぞれ新しい行で始まります。

プリミティブと宣言された場所に置かれたコンテナ

もう 1 つは、prelude のコンテナをプリミティブに代入するケースです。o: Option<int> のときの let x: string = o に対して Glyph のチェッカーは何も言わず、int と宣言された引数に Nullable<int> を渡しても同じでした。

今は 5 つのコンテナが両方向でカバーされています。Option、Result、Array、Record、Nullable は、型引数が何であれ string、number、bool にはなりません。スカラーに対する Nullable<T> は 1 段内側の T で判定するので、let v: Nullable<int> = 3 は正しいままで、let v: Nullable<int> = "three" は E0204 です。

詳細 Glyph だけが検出できるケースと、0.1.130 からのレコード

Nullable のケースは他よりもこのページにふさわしいものです。tsc には判定できないからです。出力される const v: number | null = 3 は呼び出しが検査される前に number に絞り込まれるので、null を見えるようにするために存在する境界の型が、int と宣言された場所を黙って通過していました。検出できる場所は Glyph のチェッカーだけでした。

次に、同じコンテナを宣言済みのレコードやユニオンと比べるケースに取り組みました。0.1.130 からは、let user: User = json.parse(body) は E0204 になり、User を期待したのに Result<unknown, Array<Issue>> が見つかったと報告します。以前は tsc しかそれを言わなかったので、glyph check --no-tsc、エディタ、Playground では、境界が正しく扱うべきまさにその 1 行で、ファイルがきれいに見えていました。

配列や文字列のメンバーのつづり間違い

配列や文字列のメンバーのつづり間違いも、以前は tsc を待っていたケースです。xs.lenght は「length ではありませんか」付きの E0210 になります。レコードのフィールド読み取りをそのフィールドと照合するのと同じように、TypeScript のライブラリが配列と文字列に宣言しているメンバーと照合します。型を書いていないパラメーターを持つコールバックの中でも同じです。パラメーターはその位置が期待する型を受け取るので、users.map(fn(u) -> string { return u.nmae }) では u は User であり、タイポは E0210 になります。

tsc は三つとも拒否していたので、それを実行するビルドはすでに赤くなっていました。変わったのは、チェッカーと、その上に作られたすべてのものが、先にそれを検出するようになったことです。

詳細 ユニオンをどう比較するか

tsc が報告していた 4 つを、同じ 4 つの文で、tsc を実行せずに報告しています。このルールはユニオンを実行時の姿、つまり string として読み、それぞれの方向で対応する string の問いをチェッカーに投げます。そのため、レコードやコンテナを string と比べて拒否する既存のルールを、形ごとに書き直すのではなくそのまま引き継ぎます。2 つのリテラル集合は集合として比較されるので、狭いユニオンは広いユニオンが宣言された場所に入れられます。エイリアスの連鎖は両側でたどられ、import したユニオンもローカルのものと同じように判定され、Nullable<Mode> はユニオンを保ったまま内側に降りて判定されます。

レコードのフィールドやジェネリック引数の中に入れ子になったユニオンは、0.1.122 では tsc に任せ、0.1.123 で判定するようにしました。下を見てください。

0.1.123：値が出力される string ではなく、値そのもののリテラル

type Mode = "read" | "write" は集合を宣言の側に置き、値の側には何も置いていなかったので、"read" は string、["read", "write"] は Array<string> でした。

経緯 0.1.122 が諦めたもの

そのため 2 つのプログラムが区別できませんでした。Array<Mode> と宣言された場所での return ["read", "write"]（tsc はコンパイルします）と、xs: Array<string> に対する return xs（こちらは拒否します）です。0.1.122 は間違えるよりはと、この組み合わせを判定しないことにし、その結果、誤ったプログラムを諦める代わりに正しいプログラムを通していました。{ mode: Mode } に対する { mode: "nope" } には何も報告されませんでした。

今では、書かれた文字列リテラルはそれが表す 1 つのリテラルの型を持ち、配列リテラルの要素型はその要素の型を合わせたものになります。書かれた配列リテラルやオブジェクトリテラルは、宣言された型と要素ごと、フィールドごとに照合されるので、診断はそのリテラルを名指しして下線を引きます。

glyph check --no-tsc、対象はコンテナ 1 段内側のリテラル 
type Mode = "read" | "write"
type Cfg = { mode: Mode }

fn ok() -> Array<Mode> { return ["read", "write"] }
fn bad() -> Array<Mode> { return ["read", "nope"] }
fn wrong() -> Cfg { return { mode: "nope" } }
// 0.1.122: nothing, on all three
[E0204] type mismatch: expected `Mode`, found `"nope"`   (twice)
詳細 リテラルが広がる場所と、0.1.153 からの Record のキー

リテラルは、TypeScript が広げるのと同じ場所で string に広がります。注釈のない let（出力される TypeScript の let も同じように広がります）と、書かれた配列に対する for の要素の束縛です。そのため let l = "read" の後の takes_mode(l) は、こちらでは拒否され、向こうでは TS2345 になります。const は TypeScript の const を出力してリテラルを保つので、takes_mode(CM) はどちらでもコンパイルが通ります。名前を経由して届いたリテラル型は広げません。これは TypeScript 自身の freshness ルールです。これらはどの行も、推論で決めたのではなく、同等の TypeScript に tsc --strict を実行して確かめています。

0.1.153 から、Record のキー引数は tsc よりも厳しく扱われます。TypeScript は Record<string, V> をインデックスシグネチャとして書き、Record<Mode, V> に対して両方向で受け入れます。Glyph はどちらも拒否します。開いたマップは Mode の外のキーを持っているかもしれないし、どれかが欠けているかもしれません。また開いたマップとして渡された Record<Mode, V> には、余計なキーが書き込まれるおそれがあります。一方から他方へ移るには、is のアームか json.parse を通ります。

チェッカーがまだ何も言わない形が 2 つあります。Some(...) の中のリテラル（prelude のコンストラクタにはまだここで型がないため）と、注釈のない let に束縛されたレコードリテラル（オブジェクトリテラルに対してレコード型を合成しないため）です。

std/ の下のモジュールが、診断なしの死んだコードになっていた

std/ と extern/ はコンパイラが持ち運ぶモジュールの名前で、リゾルバはそれを import 用に予約していました。しかしプロジェクトのファイルがそれを宣言することを止めるものはありませんでした。

glyph check --no-tsc、対象は `module std/io` を宣言する src/io.glyph

        modules the compiler carries (D15)

   ╰─ Rename the module to a path of your own (`io`, `app/io`).
詳細 以前起きていたことと、予約されているパス

自分の src/io.glyph に module std/io と書くときれいにコンパイルが通り、その後 import std/io { shout } はスタブに解決されて、shout はエクスポートされていないと報告しました。あなたのファイルは一度も読まれていなかったのです。

このプレフィックスは最初のセグメント全体として照合されるので、standard、externals/io、app/std、app/extern/helper は影響を受けず、どちらのプレフィックスの下からの import もこれまでどおり動きます。

何の診断も出さず、何のコードも実行しないファイルは、コンパイラが残しうる最悪の状態です。見た目にはどこもおかしくないからです。

詳細 言語サーバーにとってなぜ重要だったか

glyph check でもまずいですが、ルート配下のすべてのファイルを読む glyph lsp と glyph mcp ではもっとまずく、1 つの異常なファイルがワークスペース全体のサーバーを落としていました。今は E0011 になり、65 段目を開くはずだったトークンで報告されます。

上限は 64 で、適当に選んだのではなく測定して決めました。

詳細 64 をどう測定したか

最もコストの高い構文である入れ子の配列リテラルは、1 段あたりリリースビルドで 7,792 バイト、デバッグビルドで 8,810 バイトのスタックを使います。ある深さをパースできる最小のスレッドスタックを二分探索して求めた値です。パーサが動く最も薄いスタックは生成されたスレッドの 2 MiB で、これは言語サーバーのワーカーが使うものです。64 段なら、コストの高いほうのビルドでもその 3 分の 1 未満しか使いません。このリポジトリにある 343 個の .glyph ファイルの中で最も深い入れ子は 16 です。上限は式、型、パターン、ブロック、JSX の子要素のすべてに適用され、兄弟関係にある 1000 個の配列は今もパースできます。深さは構文ごとの入れ子の深さであって、ファイル全体で消費される予算ではないからです。

どちらのコンパイラも間違っていないとき

3 つ目の形があり、これが一番たちの悪いものです。Glyph は何も報告せず、tsc は正しいことを報告し、あなたが書いたプログラムには問題がない。

失敗しているのは、その間の変換です。

poll.glyph と、0.1.89 より前に tsc がそれについて言っていたこと 
fn classify() -> int {
  let done = false
  match done {
    true => { return 1 },
    false => { return 0 },
  }
}

// no Glyph diagnostic, then
[TS2678] Type 'true' is not comparable to type 'false'.
詳細 なぜ tsc には false が見えたのか、そしてそれに当たったアプリ

Glyph の束縛は、その生存期間を通じて 1 つの型を持ちます。TypeScript は束縛を最後に代入されたものに絞り込み、その boolean は true | false というユニオンです。そのため let done = false は false 型として tsc に届き、出力された switch の true アームにはマッチするものがありませんでした。

文字列リテラルの集合として宣言した型も同じように失敗し、== も同様で、こちらは TS2367 として返ってきました。メッセージが 2 つ、コードが 2 つ、原因は 1 つです。これに当たったアプリは、タイマーのコールバックが設定するフラグをポーリングしていました。Glyph に手で作れる Promise がない間、イベントベースの API を値に変えるにはそうするしかないからです。結局コールバックは本質ではなく、コールバックのない 4 行でも再現します。

修正は新しい診断ではありません。診断すべきものがないからです。今はエミッタが、チェッカーがすでに決めた型を、値を判別する 2 つの場所で改めて書き出します。match の対象と、== や != の両辺です。

詳細 今も働く検査と、そのコスト

各辺は隣にあるものを無視してそれ自身の型で決まるので、2 つの束縛どうしの比較も、リテラルとの比較と同じようにカバーされます。

必要なチェックは今も働きます。m が Mode のときの m == "nope" は引き続き拒否され、今ではメッセージが、m がたまたま保持していた単一のメンバーではなく Mode を名指しします。これを代入の場所で行えばコードは少なく済みましたが、このチェックを捨てることになっていました。注釈付きの代入が受け入れられない場所でも Mode へのキャストは受け入れられますし、メンバーシップのチェックは Glyph が意図的に tsc に任せている部分だからです。

代償は小さいですが、明記しておく価値があります。キャストは確認だけでなく絞り込みもできるので、Glyph が bool と型付けした値の TypeScript の型が unknown になっていた場合、以前は switch がエラーを出していたところを今は通過します。それでも 2 つの型は比較可能でなければならないので、問題になるほどずれたモデル（string と bool）では、何も言わないのではなく TS2352 が報告されます。

同じタイプミスに、2 つの答え

標準ライブラリの関数名のつづりを間違えると、以前は import の書き方によって違う答えが返ってきました。こういう不一致があると、どちらの答えも信用しないようになってしまいます。

名前空間からの読み取り、0.1.72 より前

詳細 2 つの書き方の違いの理由と、検査を有効にして見つかったもの

1 つ目の書き方は、解決の段階でモジュールのエクスポート一覧と照合されていました。2 つ目はまったく照合されていなかったので tsc まで流れ、そこではそれをオブジェクトのプロパティアクセスとみなして、その言葉で答えていました。

これを有効にしたとたん、誰も探していなかったものが見つかりました。あるテストの fixture が、関数名は write_text なのに fs.write を呼び出していたのです。その fixture は型検査をオフにして実行されていて、コンパイラの他のどこも名前空間のメンバーを見ていなかったので、何か月も通過していました。今はエクスポート一覧が両方の書き方の基準なので、それをランタイムが実際にエクスポートしているものと一致させる別のチェックがあります。そのチェックは書いた後にわざと壊して失敗することを確かめました。そうして、最初の版が実は何もチェックしていなかったことがわかりました。

改善中

  • E0238 が呼び出しを非同期だと分かるのは、Glyph のチェッカーがそのシグネチャを持っている場合だけ
    詳細

    E0238 が呼び出しを async だと知るのは、Glyph のチェッカーがそのシグネチャを持っているときだけなので、npm パッケージや node のビルトインからの promise は今も黙って捨てられることがあります。forEach、タイマー、ソケットのハンドラー、あるいは任意の fn(...) -> void パラメーターに渡した async コールバックは、何もそれを待たないので E0211 で拒否されます。

  • 呼び出しの外で fn と async fn を取り違えると、汎用のメッセージで拒否されます
    詳細

    呼び出しでは、種類の違う関数には貼り付けて使えるヘルプが付きます。task.detach に渡した同期の tick には、async fn() -> void { tick() } を渡すか async fn tick() と宣言するよう示されます。let で fn(...) -> void に束縛した、返した、あるいはフィールドに入れた async fn も拒否されますが、メッセージは expected `function`, found `async function` と言うだけで、修正はあなたに任されます。

  • トップレベルの await は許可されている
    詳細

    モジュールレベルの const の初期化式には外側の呼び出し可能なものがないので、トップレベルの await は許可され、出力される ESM がそれを実行します。Glyph が暗黙の非同期モジュール初期化を望むかどうかは、まだ仕様上の未解決の問いです。

  • E0223 が末尾の match を判定できるのは、関数が戻り値の型を宣言している場合だけなので、注釈のないラムダの中のアームは今も tsc まで届きます。
  • E0110 は名前を残させるのではなく、変更するよう伝える
    詳細

    隠蔽の側では、2 つのことが半分しか終わっていません。E0110 は名前を残させるのではなく変更するよう伝えるので、Error、Number、Object、Array、Promise は今も型やバリアントの名前に使えません。

  • E0111 は type Key = string | number が間違った意味になるのを止めるが、それを表す方法は与えない
    詳細

    また E0111 は、type Key = string | number が間違った意味になるのを止めますが、それを表す方法を与えるわけではありません。2 つのプリミティブ型のユニオンは、Glyph では extern_ts 以外に書き方がなく、その中身は Glyph のチェッカーからは不透明として扱われます。タグなしユニオンは網羅性、実行時のディスクリプタ、is に関わるので、これは型システムの判断であり、予定は立っていません。

  • E0104 は glyph build と glyph check には届くが、エディタには届かない
    詳細

    E0104 は glyph build と glyph check には届きますが、エディタには届きません。LSP はビルドルートなしでドキュメントのテキストを解析し、ワークスペースのフォルダもビルドルートではないので、推測するとこのチェックが避けるように設計された誤検出が出てしまうからです。

  • 予約語のパラメータは、同じファイル内の無関係なエラーの陰に今も隠れます。collect パスで失敗すると、それを見つけたはずの resolve パスがスキップされるからです。
  • 読み取り箇所での型の固定は、出力中のモジュール内でしか型エイリアスをたどらない
    詳細

    それとは別に、bool や文字列リテラルのユニオンの束縛をマッチ可能に保つための読み取り箇所での型の固定は、型エイリアスを出力中のモジュール内でしかたどりません。そのため、あるモジュールの pub type Ready = bool と、別のモジュールの let r: catalog.Ready = false は、今も TS2678 として tsc まで届きます。文字列リテラルのユニオンは、3 つの import の書き方のすべてでモジュールをまたいでカバーされており、0.1.123 からは、どの書き方でも診断がリテラルの集合を表示するのではなく宣言（Mode を期待）を名指しします。
