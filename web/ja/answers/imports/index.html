なぜ重要か

言語を試すためにコードベースを書き直す人はいません。Glyph の出力は TypeScript そのものなので、.glyph ファイルは既存の TS/React/Node プロジェクトの片隅に置けて、同じパッケージを import し、周りの .ts に向けて export できます。

新しいランタイムを出すのではなく TypeScript をターゲットにする理由は、この段階的な導入経路にあります。

インストール済みのパッケージは自前の型を持ち込む

パッケージがインストール済みで、自前の型を同梱している（または @types/... がある）なら、やることはそれだけです。スタブもアダプタファイルも要りません。

glyph build がプロジェクトの node_modules を見つけて型チェッカーに渡すので、パッケージの本物の型があなたのコードを検査し、誤った呼び出しはちゃんとエラーになります。

次の例では zod をそのまま使っていて、手書きのものは何もありません。

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
zod に存在しない呼び出し 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

glyph run は同じプログラムをインストール済みの zod に対して実行するので、型チェックだけで終わりません。型チェッカーのためにパッケージを解決する設定項目 1 つが、ランタイムのための解決も兼ねています。

型を同梱せず @types/... もないパッケージには、やはり自分で書く宣言が必要で、そのための場所が .types/ フォルダです（TypeScript がすでに使っている .d.ts と同じ仕組みです）。

詳細 サブパスの import と、.d.ts から作る検証される型

サブパスの import（pkg/sub）もパッケージの exports マップを通して解決されるので、サブパス自身の型も検査されます。

また、型だけの import ではなく、ライブラリの形を Glyph のファーストクラスの検証される型として扱いたい場合は、glyph gen dts が .d.ts から記述子付きの本物の型を生成します。API ごとにバリデータを手書きする必要があるかを参照してください。

値から導かれる型、JSX のスプレッド、そして抜け道

値から導かれる型もファーストクラスです。JSX の props スプレッド（<input {...register()} />）もファーストクラスです。

そのため、ライブラリのせいでアダプタファイルを手書きさせられることはありません。

Glyph がまだ書けないまれな TypeScript のイディオムには、範囲が限定され grep で見つけられる抜け道として extern_ts("...") があります。tsc は検査しますが、正確に言えば、これは信頼の境界であって実行時に検証される境界ではありません（Glyph からは中身が見えず、値は unknown で返るので絞り込みが必要です）。

詳細 z.infer<typeof s> の解決のされ方

type User = z.infer<typeof user_schema> はそのまま動きます。typeof user_schema は実在する値の参照に対する型クエリで（タイプミスは未解決の名前のエラーになります）、z.infer<...> は普通のメンバージェネリック型です。そのまま出力されて tsc が簡約するので、u.name は string になります。検証はスキーマ自身の parse が行い、これは zod 本来の動き方です。

TypeScript を丸ごと手書きしたいとき

抜け道として必要なのが型や式ではなく、実際のランタイムコードのこともあります。node のストリームのループ、new Promise、ワーカースレッドなどです。その .ts を <src>/extern/ の下に置き、import extern/<name> で参照します。 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

Glyph のソースでは相対 import は今も禁止なので（grep しやすさのための規則）、extern/* だけが予約されたパスです。grep -rn 'import extern/' で、言語の外に出たすべての箇所が見つかります。

詳細 配置、逆方向、node シム

ビルドは <src>/extern/** を出力に配置して相対指定子を出力するので、tsc は extern を Glyph のコードと一緒に型チェックし、再ビルドで消されることもありません。

これは簡単な方向、つまりコンパイル済みの Glyph を .ts ファイルから import する場合の逆で、そちらは何も要りません。よくある extern（http サーバー、fs）は、何もインストールしなくても同梱の node シムに対して型チェックされます。

何もインストールせずにサブプロセスを監視する

同梱の node 宣言には、ブロッキングな方だけでなく child_process の非同期な方も含まれています。そのため、長いコマンドの出力を実行中に表示するツールは、extern ではなく Glyph で書けます。 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

io.println ではなく io.print を使います。チャンクはストリームの一部であって行ではなく、1 行が 2 つのチャンクにまたがって届くこともあるからです。

オーバーロードは @types/node に従うので、単純な spawn(command, args) ではパイプが非 null で返り、stdio を渡すと null になりうる型になります。stdio: "inherit" の後で child.stdout を読むと、ここでは TS18047、本物の型定義でも TS18047 になります。同じ値について 2 つの異なる説明が出ることはありません。 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

シムを編集すれば、次の実行は編集後のシムになる

シムは繰り返し手を入れるファイルなので、ソースとして扱われる必要があります。

glyph run はビルドをソースのフィンガープリントでキャッシュしますが、このフィンガープリントは extern/ の下にあるすべての .ts と .tsx を、内容だけでなくパスも含めて対象にします。

詳細 再ビルドのきっかけになるもの

1 つ編集しても、名前を変えても、追加しても、削除しても、次の実行で再ビルドされ tsc が再実行されます。シンボリックリンクのシムはたどられるので、ソースツリーの外に置いた .ts も実際の内容でハッシュされます。

これがあるので、両方のファイルがそれぞれ型のコピーを宣言するのではなく、シムが型を持てます。シムから形を export し、Glyph モジュールでそれを import すれば、コンパイラが実行のたびに両者を一致させます。

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
シムでフィールド名を変えると、ビルドがそれを指摘する 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3
経緯 0.1.44 より前と、対象にならないファイル

0.1.44 までフィンガープリントは extern/ を完全に無視していたので、この名前変更をしても、型チェックの通ったきれいなビルドが前のシムのまま動いていました。extern/ の下にある .ts や .tsx 以外のファイルは今もキャッシュに影響しませんが、これは意図的です。シムの隣の README.md は一緒に出力へコピーされますが、型チェックも実行もされないので、再ビルドするものがありません。

クラスベースのクライアント：データベースやメッセージング

データベースやメッセージングのクライアントの多くはクラスベースです。new Kafka(...)、new MongoClient(url)、new Redis()、new Pool(cfg) のように書きます。Glyph の new はまさにこのためにあります。

クラスベースのクライアント（kafkajs） 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
ファクトリ型のクライアントには new は不要 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

TypeScript の new をそのまま出力し、tsc がパッケージの本物のコンストラクタに対して検査するので、誤った引数はちゃんとエラーになり、未定義の呼び出し先は名前で検出されます。

用途は相互運用に限られます。Glyph 自体には class がなく、new で生成できるのは、パッケージ、.types の宣言、extern_ts のいずれかから来た型だけです。

現状

提供中

  • どの npm パッケージでも import できます（ハイフンを含む名前やスコープ付きの名前も含む）。
  • 自前の型を同梱している（または @types/... がある）インストール済みのパッケージは、スタブなしで型チェックされ実行されます。
  • クラスベースのクライアントは new で生成し、tsc が本物のコンストラクタに対して検査します。ファクトリ型のクライアントはそのまま import して呼び出せます。
  • Node の組み込みモジュールは最初から型チェックされる
    詳細

    Node の組み込みモジュール（fs、path、http、ストリーミングの spawn を含む child_process など）は最初から型チェックされ、@types/node をインストールすれば自動的に読み込まれます。CI はコンパイラ自身のランタイムをそのパッケージの latest に対してビルドするので、stdlib が依存する宣言が node の本物の宣言からずれることはありません。

  • あなたのコードだけが使う宣言はまだこの検査の対象外で、node より型が広いものもいくつか残っています。
  • その他すべてに使える .types/ のアンビエント宣言。
  • .d.ts を検証される Glyph の型にする glyph gen dts。
  • 既存の TypeScript から import できるきれいな .ts 出力。
  • import extern/<name> で <src>/extern/ の下の手書きの TypeScript を参照できる
    詳細

    TypeScript を丸ごと手書きしたいときは、import extern/<name> で <src>/extern/ の下の .ts を参照できます。それはコードと一緒に配置・型チェックされ、glyph run のキャッシュに追跡されるので、編集すれば再ビルドされます。

予定

  • 型の生成は実際の SDK が提供する形を扱え、値から導かれる型もファーストクラス
    詳細

    型の生成は、実際の SDK が提供する形（名前空間、ファイルをまたぐ再エクスポートや別名・名前空間の再エクスポート、サブパスの exports、ファーストクラスのジェネリクス）を扱えるようになり、値から導かれる型（z.infer<typeof s>）もファーストクラスになりました。

  • 残る主な穴は、型を生成していないパッケージの出力は .d.ts に対して型チェックされるものの、生成しない限り実行時には検証されないことです。
  • extern/ については、glyph run と glyph build でソースルートが異なる
    詳細

    extern/ については、2 つのコマンドでソースルートが異なります。glyph run app.glyph はファイル自身のディレクトリを、glyph build src/ は指定したディレクトリをルートにします。そのためサブディレクトリにあるプログラムは 2 か所でシムを探すことになり、ルートを 1 つに決めるまでは、そうした構成のプロジェクトでは両方からシムに届くようにしておく必要があります。届かない場合ははっきりと失敗します。
