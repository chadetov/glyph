書けます。io.read_line は 1 行が届いた時点で return し、stdin が閉じるのを待ちません。そのため REPL、ゲームループ、チャットクライアントは、次の行を読む前に各行に応答します。0.1.62 までは待っていました。これははっきり書いておく価値があります。それが原因で、対話型のプログラムはどれも書けなかったからです。

なぜ重要か

入力の終わりでしか return しない行リーダーは、行リーダーの名前を付けたファイルリーダーです。

ファイルをパイプで通すと完璧に動くので、誰も気づきませんでした。リポジトリで stdin を読むアプリはどれもパイプから読んでいたのです。そこへ誰かがチャットクライアントを書いたところ、入力している間は黙ったままで、Ctrl-D を押した後にすべての応答を一度に出力しました。

経緯 この問題に合わせて形を変えたアプリ

そのアプリは、記録した JSON ファイルを再生するセッションリプレイヤーとしてリリースされ、ソースにはその理由を説明するコメントが付いていました。ほかに 3 つのアプリが、誰もそれと名指ししないまま、同じ問題に合わせた形になっていました。マインスイーパーは手番の間に再描画できず、テキストアドベンチャーは look に応答できず、REPL は入力を終えるまで何も評価しませんでした。

実際につまずきやすい点

  • CRLF末尾の \r は取り除かれるので、CRLF のファイルでも LF のファイルでも同じ行が得られ、Windows からの入力で見えない文字をデバッグする羽目にはなりません。
  • 最後の改行なし最後の改行なしで終わる入力も、None の前にその最後の行を一度返すので、末尾に改行のないファイルの最終行が黙って捨てられることはありません。
  • 分割された UTF-8読み取りの境界をまたいで分割されたマルチバイトの UTF-8 は、置換文字にならずに保持されて完成させられます。

read_line のあとに read_to_string

read_to_string は同じバッファから読み出すので、2 つは組み合わせられます。ヘッダを read_line で読んでからボディを read_to_string で読むと、2 つ目のコピーでも空文字列でもなく、残りの部分が得られます。最初に呼べば、従来どおり stdin 全体を返します。

ヘッダ行を読み、続いてボディを読む 
let header = io.read_line()
let body = io.read_to_string()

パイプで渡した 200,000 行を数えるのに約 20ms しかかからないので、1 行ずつ読んでもスループットが犠牲になることはありません。

現状

提供中

  • io.read_line はストリームが閉じたときではなく行が届いたときに return するので、プロンプト、読み取り、応答のループはターミナルでもパイプでも同じように動きます。
  • CRLF は正規化され、終端のない最後の行は一度だけ渡され、マルチバイト文字はチャンクの境界をまたいでも壊れず、read_to_string は同じバッファの残りを受け取ります。
  • リグレッションテストは stdin を開いたままにしてエコーが返ってくることを要求する
    詳細

    リグレッションテストは stdin を開いたままにしてエコーが返ってくることを要求します。ファイルをパイプで渡すテストは、壊れた実装に対しても通ってしまうからです。

  • io.print と io.eprint は改行なしで書き込む
  • io.is_terminal / io.stdin_is_terminal は、相手が人かパイプかをプログラムに教える
    詳細

    io.print と io.eprint は改行なしで書き込むので、REPL の > プロンプトは答えを入力する行に表示されます。io.is_terminal / io.stdin_is_terminal は、相手が人かパイプかをプログラムに教えるので、チャットアプリの --stdin のようなフラグだけが判断の手段ではなくなりました。

まだ粗い点

  • 画面を再描画したいプログラムには、カーソル制御の手段がない
    詳細

    画面を再描画したいプログラムには、カーソル制御の手段がありません。std/io にはカーソルや画面の関数がなく、ほかの標準ライブラリのモジュールにもないので、全画面のターミナル UI を作るには、今もエスケープコードを自分で書く必要があります。
