なぜ重要か

1 ファイルは書けてもプロジェクトを構成できない言語に、コードベースを賭ける人はいません。問題になる穴は特殊なものではありません。

  • 可視性ヘルパーを隠せるか。
  • ジェネリクスの境界ジェネリクスにある能力を要求できるか。
  • 後始末どの終了経路でもファイルハンドルを解放できるか。
  • 並行性2 つの処理を同時に走らせて両方を待てるか。

Glyph はこの 4 つに答えています。しかも、意図的に捨てたアノテーション中心の方向を蒸し返すことなく答えています。

インターフェースでジェネリクスを制約する

interface は TypeScript と同じく構造的です。ジェネリクスが要求できるメンバーシグネチャの集合です。implements も名前的型付けの儀式もありません。そのメンバーを持つ値ならどれでも当てはまり、tsc がそれを強制します。

インターフェースでジェネリクスを制約する 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer と構造化並行性

defer は、ブロックを抜けるときにどの経路でも後始末を実行します。早期 return でも、エラーが投げられた場合でもです。また std/task は、切り離された Promise を放置するのではなく、並行処理を 1 つのライフタイムにまとめて待ち合わせます。

defer と構造化並行性 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])
詳細 実行順序と owned ハンドル

複数の defer は後入れ先出しで実行され、owned ハンドルとも組み合わせられます。

JavaScript から受け継ぐもの

Glyph は TypeScript にコンパイルされ JavaScript エンジンで動くため、評価順序、ミューテーションにおける参照のセマンティクス、シングルスレッドでガベージコレクションのあるモデルを引き継ぎます。仕様はこれらを、あとで気づくものではなく保証として明記しています。

違うのは等価性です。== は値を比較し、レコードはフィールドごとに比べます。一方 JavaScript の === は参照を比較します。

手動メモリ管理や GC のないモデルはロードマップにありません。TypeScript にトランスパイルする言語の範囲外です。

if がないので、match がすべてを担う

網羅性の話を聞いた TypeScript 開発者が最初に聞くのは、match が本当に汎用の条件分岐なのか、それともユニオンを分解する便利な書き方にすぎないのか、ということです。答えは前者で、それを示すのが代入です。

let や mut の値全体になっている match は、文が受け取れるものなら何でも受け取れます。アームはブロックにでき、await でき、外側のループから break でき、代入先の束縛を読むこともできます。最後のものを使えば、if なしでループを通して状態を畳み込めます。

リンクチェッカーより：コードブロックの追跡と、await するアーム 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}
詳細 何にコンパイルされるか、スニペットの出どころ

どちらもアームごとに束縛へ代入する素朴な switch にコンパイルされるので、await は外側の async 関数の中に置かれ、累積値は TypeScript が推論できる普通の変数になります。どちらのスニペットも examples/apps/linkcheck/main.glyph からのもので、これはまさにこの種の問題を見つけるために書かれた Markdown のリンクチェッカーです。

大きな式の中、たとえば引数やオペランドとして使われた match は今もクロージャになるので、そのアームは単一の式でなければなりません。それ自身の let に持ち上げれば、この制限はなくなります。

パターンで 2 段以上深い形を指定できる

複数のフィールドを持つバリアントはレコードを運ぶので、形を認識したいアームはレコードのフィールドの中まで入り込む必要があります。今はフィールドにどんなパターンでも書けます。バリアントのタグ、入れ子のコンストラクタ、入れ子の分解、リテラル、配列パターンです。

赤黒木のリバランスの回転ケース 1 つを、1 つのアームで 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}
経緯 0.1.90 より前の回避策

0.1.90 までは、フィールドの位置には名前しか書けませんでした。名前を変えることはできても、それだけでした。そこでタグをマッチさせるとコンパイルエラーになり、入れ子のコンストラクタはパーサーが扱えませんでした。回避策はすべてのフィールドを束縛して、階層ごとに入れ子の match を書くことで、赤黒木のリバランスのようなものでは別のプログラムになってしまいます。アームがケースと対応しなくなり、各階層で上の束縛を引き回すことになります。

書く前に知っておくべき帰結が 1 つあります。値を検査するフィールドは失敗しうるので、そのアームはもうバリアントを網羅したとは数えられません。Node のアームが Node({ color: Red, ... }) だけの match は、兄弟のアームか else が残りを引き受けるまで、網羅的でないと報告されます。

詳細 なぜ catch-all を求めるのか、そして配列の位置

チェッカーが網羅性を証明するのはタグの集合についてであって、フィールドの直積についてではないので、Red のアームと Black のアームを合わせれば Node を網羅する、とは判断しません。catch-all を求めるのは、実行時に match が末尾から抜け落ちることを許さない解釈です。数えるバリアントがまったくない場合も同じです。どのアームもフィールドを検査する、素のレコードに対する match には、後ろに else が必要です。

意外かもしれない影響が 1 つ、配列の位置に及びます。以前はアーム全体としての [Black] が任意の 1 要素配列にマッチするとみなされていたので、それに頼った match は網羅的と認定され、[Red] でもそのアームに入っていました。ここでも PascalCase の要素はバリアントの参照なので、そうした match は今、長さ 1 の配列に対して E0208 になります。要素を束縛して、それ自体を match してください。下の変換処理はまだ古いままで、検査の側が先に提供されたのはそのためです。

E0208

そしてコンパイラは match が何を生んだかを知っている

次の質問が、これが本当に役に立つかどうかを決めます。分岐から値を束縛したとき、Glyph はその型を知っているのか、それとも肩をすくめて後で tsc に任せるのか。今は match はアームの型が一致すればその型を取り、T.parse は Result<T, Array<Issue>> を返すと分かっています。これは実際のコードの多くが分岐する形です。

割り勘アプリより：アノテーションなしで、i は number 
let wire = match WireLedger.parse(decoded) {
  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...

経緯 0.1.45 より前

0.1.45 までは任せていました。match 式はすべて unknown と型付けされていたので、言語で唯一の分岐構文から出てきた値は、そこから先は型がありませんでした。

詳細 気づかれずにおかしくなっていたことと、型の合流の仕組み

どちらの半分も、以前は気づかれずにおかしくなっていたものです。このループは wire.expenses.entries() を出力します。反復対象の型が unknown のときは代わりに Object.entries(...) を出力し、i は文字列 "0" になります。これは正しい TypeScript なのでビルドはきれいに通り、プログラムは 1:a のつもりで 01:a と出力していました。また wire.expensez は今、生成された TypeScript 上の TS2339 ではなく、.glyph の行で Glyph から [E0210] type WireLedger has no field expensez として報告されます。

型の合流は先頭での等価性です。return で終わるアームは投票せず、型が食い違うアームがあれば結果は以前と同じく unknown のままです。1 段深く見るのは型引数だけなので、None => [] は match 全体を台無しにせず Array<string> のアームと一致し、その後のループも number を束縛します。record.get に対する同じ連鎖も同じ理由で動きます。std/record の 6 つの関数はすべて、渡したレコードから値の型を引き継ぎます。このスニペットは examples/apps/settle/main.glyph からのもので、この変更で不要になったアノテーションが付いていました。

空のフォールバック付きの検索

これが最もコストの大きかった形です。Record<string, Array<string>> に対する record.get は Option<Array<string>> で、[] は要素の型が特に決まっていない配列です。そのため 2 つのアームは Array で一致し、要素の型は型を持っている方のアームから取られます。

依存関係リゾルバより：検索、空のフォールバック、インデックス付きの走査 
let path = match record.get(res.reached, name) {
  Some(p) => p,
  None => [],
}

for i, hop in path {               # i is a number, so the indent nests
  let indent = string.repeat(STEP, i + 1)
  mut out = array.push(out, "${indent}${hop}")
}
経緯 0.1.55 より前

0.1.55 までは等価性で比較されていて、[] は不一致とみなされ、下のループは診断が 1 つもなく tsc --strict も通るビルドで 01:x と出力していました。コードは examples/apps/depsolve/main.glyph で、以前は冒頭に let path: Array<string> があり、このアノテーションが外せない理由を説明する 3 行のコメントが付いていました。

pad_start は自分で書く必要があるか

実際のプログラムで最初にぶつかる穴は、型システムの機能ではありません。string.slice を使おうとしたら何もない、というものです。

経緯 0.1.47 より前にアプリが持っていたコピー

ドッグフーディングを 5 回続けて同じ一覧が報告され、0.1.47 までは、このリポジトリの 6 つのアプリが自前の repeat を、5 つが自前の pad_start を持ち、どれも fold を使うべき場所にループを書いていました。

TypeScript と違うところ

そのうち 3 つは、意図的に TypeScript の同名の関数と違う動きをします。

  • repeatrepeat は負の回数に対して、TS のように例外を投げるのではなく "" を返します。そのおかげで、すでに長すぎる文字列に対しても repeat(pad, width - len(s)) が安全です。
  • index_of2 つの index_of はどちらも -1 ではなく Option<number> を返します。-1 は本物のインデックスが通る場所ならどこでも型チェックを通ってしまい、呼び出し位置から遠く離れた場所で失敗する数値だからです。
  • replace_all置換は replace_all としてのみ提供されるので、1 か所だけをこっそり置き換える String.prototype.replace と混同する、最初の 1 つだけの形はありません。

fold が重要な理由

fold は、タイプ量を減らすのではなく柱の 1 つを支えるものです。mut は状態が変わるすべての場所を grep できる形で記録したものですが、fold がないと、grep mut はレビュアーが気にするものを何も変更しない数え上げのループだらけになります。

手書きの実装を削除したことで、examples/apps/ の変更箇所は 192 から 161 になりました。

詳細 書き換えをどう確認したか

この書き換えはレビューではなく出力で確認しました。7 つのアプリすべてを固定の入力で書き換えの前後に実行し、標準出力、終了コード、HTTP レスポンスの 26 ファイルがすべてバイト単位で一致しました。

ディレクトリを走査して、何が壊れたかを判別できるか

std/fs は 6 つの関数を提供していましたが、ディレクトリを一覧するものはありませんでした。

  • fs.read_dirfs.read_dir は 1 階層下のエントリ名を返します。
  • fs.is_dirfs.is_dir は fs.exists と同じく bool で答えます。
  • fs.statfs.stat は is_dir、is_file、バイト単位の size、エポックミリ秒の modified からなる FileInfo を返し、この時刻は time.format_iso でそのまま表示できます。

再帰的な walk や glob はありません。走査はこの 3 つと path.join で 10 行ほどで書けます。

経緯 これらが置き換えた回避策

このリポジトリのリンクチェッカーは stdlib を飛び越えて node の readdirSync を使い、どのパスがディレクトリかは、読もうとして返ってきた errno を調べて判断していました。どちらも修正済みです。

失敗には名前がある

失敗の側はもっと大きく変わりました。今は、プログラムが実際に回復処理を行う 5 種類に名前があり、名前のない errno は Other の末尾にそのまま入ります。

チェッカーはこの分類が閉じていることを知っているので、err.kind に対する match は、自分で宣言したユニオンと同じ基準で検査されます。6 つすべてを扱えば else は要らず、1 つ漏らせば fs.ErrorKind を名指しした E0200 でビルドが失敗します。

E0200E0210
ツリーを走査し、何がおかしかったかを名前で示す 
let names = fs.read_dir(dir)?
for name in names {
  let child = path.join([dir, name])
  match fs.is_dir(child) {
    true  => visit(child),
    false => {
      let info = fs.stat(child)?
      report_size(child, info.size)
    },
  }
}

match err.kind {                        # no else arm: E0200 if you miss one
  fs.ErrorKind.NotFound         => io.eprintln("no such path"),
  fs.ErrorKind.NotADirectory    => io.eprintln("that is a file"),
  fs.ErrorKind.IsADirectory     => io.eprintln("that is a directory"),
  fs.ErrorKind.AlreadyExists    => io.eprintln("already there"),
  fs.ErrorKind.PermissionDenied => io.eprintln("cannot read it"),
  fs.ErrorKind.Other({ code })   => io.eprintln("errno ${code}"),
}
詳細 以前の分類、検査されるフィールド、検査を自分で試す方法

FsError.kind は { tag: string } で、分類は NotFound だけでした。そのため「そのパスはディレクトリだ」と「そのパスが存在しない」を区別するには errno の文字列を比較する必要がありました。

fs.FsError と fs.FileInfo のフィールドも検査されるので、err.mesage は生成された TypeScript に対する tsc のエラーではなく、Glyph のソースに対する E0210 になります。

この検査は実際に動いています。上の match から PermissionDenied のアームを消すと、glyph check --no-tsc は E0200 で止まります。fs.ErrorKind に対する網羅的でない match で、欠けているバリアントは PermissionDenied です。stdlib のモデルを最初に書いたときは戻り値の型しか扱っていなかったので、このような match はきれいにコンパイルされ、実行時に例外を投げていました。今は fs.FsError、fs.FileInfo、fs.ErrorKind のフィールドとバリアントの形もモデル化されています。

小さな追加が 2 つ

同じアプリから出た小さなものが 2 つ、一緒に入りました。

  • regex.captures_allregex.captures_all は、マッチしたテキストだけでなく、すべてのマッチのキャプチャグループを返します。これでフラットな key=value の走査が手書きのループでなくなります。
  • task.pool_settledtask.pool_settled は、all_settled の失敗時の振る舞いを持った task.pool です。並行数に上限があり、タスクごとに 1 つの結果が返り、ホストが 1 つ落ちても失うのはそのホストの結果だけで、プールがそれまでに集めた結果をすべて失うことはありません。

それが正しい関数だと、どうしてわかるのか

それを求めたアプリが回避策をやめるまで、リリースを完了とみなさなかったからです。

ライブラリ関数を提供することと、回避策がそれより長生きすることは別の話です。そこで、この 4 つを追加した変更で、リンクチェッカーにあったコピーも削除しました。readdirSync の import、2 つの errno 文字列の比較、97 行の手書きスキャナ、そして最初の失敗で止まるプールです。合計 122 行が消えました。

測定した 2 つの動作の変化

そのうち 2 つの削除はプログラムの動作を変えたので、その違いは議論ではなく測定で確かめました。

  • 読み取れないディレクトリ読み取れないディレクトリを含むツリーに旧版と新版を向けると、新版は permission denied と出力してそのパスを読めないものとして数えます。旧版は errno が EISDIR かどうかしか聞けなかったので、そのパスをレポートからまるごと落としていました。
  • 失敗する URL3 つの URL のうち 1 つで例外を投げさせると、pool_settled は 3 行すべてを出力して失敗を名指ししましたが、pool は何も出力せずに未処理の reject で終了し、成功した 2 つの結果も道連れにしました。
詳細 スキャナの書き換えと、選択（alternation）の懸念

スキャナの書き換えは設計上の懸念も解消しました。参加しなかったキャプチャグループは、空文字列にマッチしたグループと同じく "" として読まれるので、captures_all では選択肢のどの分岐がマッチしたのかわからないように見えました。実際にはわかります。各分岐のグループを、欲しい部分ではなく構文全体を囲むように書けばよいのです。マッチしたグループは `、[、!、< のいずれかで始まり、空にはなりません。空になりうる部分、つまりリンク先はその内側に入れ子になり、判定に使うことはありません。これで 180 行の文字単位の走査が、2 つのパターンと 12 行の振り分けになりました。リポジトリ自身のドキュメントと、壊すために作った fixture の両方で、出力はバイト単位で一致しました。

お金の計算に浮動小数点数は使わない

フィンテックの評価をその場で打ち切らせる穴は、IEEE-754 の number でお金を扱うことです。そこでは 0.1 + 0.2 は 0.3 にならず、253 を超える値は気づかないうちに精度を失います。

std/decimal は BigInt の上に作った正確な 10 進固定小数点です。任意精度の整数に固定桁数の小数部を持たせたもので、加算、減算、乗算は正確で、除算にはスケールと丸め方を明示します。不正な金額はパースすると Err になり、黙って NaN になることはありません。

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

大きな整数

大きな整数を正確に扱う必要がある場合、たとえばアカウント ID やカウンタには bigint 型があります。リテラルは 123n で、TypeScript の本物の bigint として出力されます。bigint 型のレコードフィールドは境界で typeof === "bigint" を検証するので、JSON の number として送られてきた ID は、253 を超えて黙って丸められるのではなく拒否されます。

非同期コールバックにようやく型ができた

関数型は fn(A) -> T しかなく、これは (a: A) => T として出力されます。非同期の本体はこれに合わないので、遅延タスクを返す関数や非同期ハンドラのレコードはアノテーションなしにするしかなく、チェッカーはそこで検査をやめていました。

async fn(A) -> T がその欠けていた型です。(a0: A) => Promise<T> として出力され、戻り値のない async fn() は () => Promise<void> になります。

遅延タスクと、ハンドラのマップ 
fn task_for(url: string) -> async fn() -> Fetched {
  return async fn() -> Fetched { return { url: url, body: await fetch_one(url) } }
}

type Handler = async fn(string) -> string

async fn dispatch(routes: Record<string, Handler>, name: string, arg: string) -> string {
  return match record.get(routes, name) {
    Some(h) => await h(arg),
    None    => "no route",
  }
}
詳細 Glyph が普通の関数と非同期関数をどう区別するか

Glyph は tsc に任せず、自分で両者を区別します。非同期関数が期待される場所に普通の関数を渡すと、return では E0204、呼び出しの引数では E0211 になり、メッセージには両方の側が示されます。

判定しないのは戻り値が void の場合だけで、TypeScript ではそこにどんな関数でも置けます。

再帰的な型を、最後までマッチする

ユニオンは自身のペイロードの中で、型パラメータ付きで自分自身を指定でき、match のアームはコンストラクタパターンのフィールドの中に別のコンストラクタパターンを入れ子にできます。この 2 つを組み合わせると、赤黒木のバランス規則は 4 つのアームになります。各アームが書き換える形を正確に示し、その形を検査するのは、上に書かれたコメントではなくコンパイラです。

4 つの回転ケースのうちの 1 つ 
type Tree<K, V> =
  | Leaf
  | Node({ color: Color, left: Tree<K, V>, key: K, value: V, size: int, right: Tree<K, V> })

fn balance<K, V>(t: Tree<K, V>) -> Tree<K, V> {
  return match t {
    Node({ color: Black, left: Node({ color: Red, left: Node({ color: Red, left: a, key: xk, value: xv, right: b }), key: yk, value: yv, right: c }), key: zk, value: zv, right: d }) => node(
      Red,
      node(Black, a, xk, xv, b),
      yk,
      yv,
      node(Black, c, zk, zv, d),
    ),
    // the other three cases, then:
    other => other,
  }
}

examples/apps/leaderboard/main.glyph がプログラム全体で、すべてのスコアを木に保持し、ログを並べ直すのではなく木を走査して順位、上位 N 件、範囲のクエリに答えるリーダーボードです。

パターン

  • 名前空間 import を通して参照するユニオンでは、フィールドに置いたペイロード付きのコンストラクタが失敗するE0300
    詳細

    入れ子のフィールドパターンには 1 つだけ限界が残っています。名前空間 import を通して参照するユニオンの、フィールドに置いたペイロード付きのコンストラクタです。import tree { Node } の後の Node({ left: Node({ key: k }) }) はコンパイルされますが、import tree の後の tree.Node({ left: tree.Node({ key: k }) }) は、同じユニオンなのに E0300 になります。

  • 自身のパラメータについてジェネリックなユニオンも、入れ子のアームを受け入れ、欠けたバリアントが検査されるE0200
    詳細

    もう 1 つの限界は解消しました。自身のパラメータについてジェネリックなユニオン（type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> })）は、パラメータのない同じユニオンなら受け入れる入れ子のアームを以前は拒否していましたが、今は開いた型パラメータでも具体的なインスタンス化でも受け入れます。同じ検索処理が、そもそも match の欠けたバリアントを検査するかどうかも決めていたので、このリリースまでは Tree<K> への match は Leaf を省いてもきれいにビルドされ、tsc --strict も通り、実行時に例外を投げていました。非ジェネリックな書き方なら E0200 になっていたのにです。

    今はどちらの書き方でも報告され、ユニオンを別のモジュールから import しても答えは変わりません。import した Tree<string> への Leaf を省いた match は、import した非ジェネリックな Tree と同じく、Leaf を名指しした E0200 になります。これは別々に検査される別のコードパスで、このリリースまでは逆の結果、つまりきれいにビルドされて実行時に例外を投げていました。

  • import したユニオンの網羅性検査は、バリアントのペイロードを検査しない
    詳細

    import したユニオンの網羅性について、頼る前に知っておくべきことがもう 1 つあります。そのバリアントのペイロードも検査されないので、X がペイロード自身のユニオンのバリアントであるとき、B(X) は欠けている Y を報告せずにすべての B にマッチします。これはジェネリクスとは関係ありません。

    フィールドを束縛すること、あるいはペイロードのないタグをフィールドでマッチすることは、どの場合でも動きます。
