サーバーは書けます。main が準備をして return し、ソケットやタイマーが待機中の間はプロセスが生き続けます。Node と同じルールです。0.1.63 より前はそうではありませんでした。main が return した瞬間にランナーがプロセスを終了させていたので、サーバーはポートをバインドしたその tick のうちに終了していました。

なぜ重要か

これは、スクリプトを実行できる言語とサービスを実行できる言語の違いです。サーバー、ファイルウォッチャー、ゲートウェイ接続を保持するボット、ジョブランナー。どれも main の中では終わりません。ハンドラを用意し、プロセスをイベントに引き渡します。

経緯 0.1.63 より前の失敗の仕方

以前の挙動は最悪の形で失敗していました。黙って失敗するのです。glyph run app.glyph --serve 4100 は何も出力せず、listen コールバック内の行すら出さずに、終了コード 0 で終わりました。ソースにはおかしなところがなく、型検査も通りました。これに当たったエージェントには、報告すべきエラーも、何かが失敗したと考える理由もありません。

main が return した後

知っておくべきことが 2 つあります。return 0 は最初のクライアントが接続するより前に実行されます。これはプロセスが最終的に終了するときのコードであって、いつ終了するかを表すものではありません。

また、main が return した後に失敗した処理は、自分で終了コードを設定しなければなりません。main の戻り値はもう使われてしまっているからです。error ハンドラはそのためにあります。これがないと、ポートをバインドできなかったサーバーはイベントループを空にして終了コード 0 で終わり、成功を報告してしまいます。

詳細 net の import の型

net は Node の組み込みモジュールなので普通に import できますが、コンパイラがアンビエント型を同梱している 6 つ（fs、http、path、os、crypto、url）には含まれません。@types/node をインストールすればビルドはそちらを優先します。あるいはソースの隣の .types/net.d.ts に宣言を置きます。チャットアプリは後者の方法で、依存関係を一切持たずに済ませています。

実際のアプリ

examples/apps/chat は、複数の TCP クライアントを同時に保持するチャットサーバーです。ネットワークに触れない部分は分離され、テスト可能になっています。行の再組み立て、ルーティング、ルームエンジンは @example で検査される純粋関数で、ソケットとやり取りするのは 1 つのファイルだけです。

3 つのクライアントが同時に接続した状態 
alice> /join #general
bob>   /join #general
carol> /join #random
alice> hello everyone

alice sees:  1  #general <alice> hello everyone
bob sees:    1  #general <alice> hello everyone
carol sees:  (nothing: she is in #random)

逆方向：長時間動くクライアント

ボットは同じ形を外向きにしたものです。examples/apps/discord は Discord のゲートウェイクライアントです。WebSocket で接続して identify し、サーバーが指定する間隔でハートビートを送り、シーケンス番号を追跡して接続が切れても最初からではなく resume で再開し、接続が開いているのに死んでいる状態を検知し、再接続の間にバックオフします。

真似する価値があるのは、ロジックの置き場所です。RECONNECT、ハートビートの欠落、拒否されたトークンにどう対処するかの判断は、セッションと 1 つのイベントから、新しいセッションとアクションのリストを返す純粋関数です。それらのアクションを実際のソケットで実行するのは 1 つのモジュールです。

経緯 3 つのバグと 2 つのモック

この 3 つの例は、どれも最初はコードに存在したバグです。モックのゲートウェイを書いてボットを向けたところ、そのうち 1 つが見つかりました。残りの 2 つは、クライアントからではなく Discord のドキュメントから書いた 2 つ目のモックで見つかりました。このモックは、協力的なモックなら決して送らないものを送ります。求めていないハートビート要求や、「トークンが間違っているので、もう要求しないでください」という意味のクローズコードです。クライアントの作者が書いたモックは、作者が読んだ部分のプロトコルしかテストしません。

現状

提供中

  • main から return すると、プロセスを止めずに終了コードが設定されるので、サーバー、ウォッチャー、イベントループが動き続けます。
  • 計算するだけのプログラムは従来どおり main が return した瞬間に同じコードで終了するので、短いプログラムの挙動は何も変わっていません。
  • net のような Node の組み込みモジュールは普通に import でき、セットアップ中の throw は引き続き終了させる
    詳細

    net のような Node の組み込みモジュールは普通に import でき、セットアップ中に throw したプログラムは引き続き終了します。ただし今は、診断がパイプされた stderr に届いてから終了するので、終了によって途中で切れることはありません。

  • std/timers は処理をスケジュールし（after、every、cancel、unref）、std/websocket は接続を開くので、どちらも手書きの宣言は不要です。

改善中

  • main が return した後にバインドに失敗したリスナーは、プログラムが何も指定しなければ終了コード 0 で終わる
    詳細

    main が return した後にバインドに失敗したリスナーは、プログラムが何も指定しなければ終了コード 0 で終わります。process.set_exit_code(1) は実行中の処理を止めずに失敗を記録し、process.exit(1) は即座に終了します。

  • 指定し忘れたことをコンパイラが警告することはまだできません。
  • また、関数が return しないことを書き表す方法もまだないので、サーバーの main には決して到達しない return 0 が残ります。
