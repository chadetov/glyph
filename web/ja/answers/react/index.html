なぜ重要か

エージェントが書くコードの多くは React です。Glyph は React を後付けではなく正式なターゲットとして扱います。component は独立したキーワードです（なので grep "^component " で UI 全体を確認できます）。

React のフックは react から import して本来の名前と型で呼び出し、tsc が React 自身の型宣言に対して検査します。

reducer とフック

Double アクションを追加すると、reducer はそれを名指しする E0200 でコンパイルできなくなります。素の TypeScript の switch なら、そのままリリースされてしまうところです。

E0200

Glyph 自身の型検査は React から来る値を型付けしないので、dispatch や state のセッターへの誤った引数は、エディタや --no-tsc ではなく、ビルド中の tsc が報告します。

詳細 フックが返すペアの分割代入

ペアは let [count, dispatch] で分割代入され、出力される TypeScript には satisfies readonly [unknown, unknown] が付くので、tsc はフックがペアを返したことを証明しつつ、各要素の型を推論します。

Context とライブラリ

React の Context は現在 createContext / useContext で使え、メンバー式の要素名（<ThemeContext.Provider>）もそのまま使えます。回避策は要りません。

  • props スプレッドJSX の props スプレッドも使えます。<input {...register("email")} /> は props の中のオブジェクトスプレッドに変換されるので、react-hook-form のイディオムにアダプタは要りません。
  • Zod の型Zod の値から導出される型も正式にサポートされています。type FormData = z.infer<typeof schema> がそのまま使え、抜け道は要りません。

1 つだけ違う点があります。コンポーネントは複数の位置引数ではなく、1 つの props レコードを受け取ります。その境界がどこにあるかは、既存のライブラリを使うと堅牢化のページを参照してください。

props は tsc より前に検査されるか？

されます。Glyph は各要素をそのコンポーネントの props レコードと自分で照合するので、誤った値、綴りを間違えた prop、必須の prop の欠落は、その prop の名前を挙げる Glyph のエラーになります。コンポーネントを名前で import しても、モジュール経由で import しても同じように動きます：

main.glyph。Card は ui.glyph で宣言 
import ui

pub component App() {
  return <div>
    <ui.Card title="Q3" />
    <ui.Card title="Q4" cout={2} />
  </div>
}

// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`
// E0210 type `CardProps` has no field `cout`; did you mean `count`?
// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`

フルビルドだけでなく、エディタや MCP でも見えます。

詳細 --json の missing_fields と、1 つの props レコード（E0229）

--json は欠けている名前を missing_fields のリストとして返すので、エージェントはメッセージをパースせずに props を追加できます。また、コンポーネントは props を 1 つのレコードとして受け取る必要があります。component Greeting(name: string) はパラメータの位置で E0229 になります。React は props オブジェクトしか渡さないので、その要素は決して型検査を通らないからです。レンダリングせずに関数として呼び出すなら、fn で宣言してください。

JSX の中の <match> は match と同じように検査されるか？

同じものです。各 <case> は match のアームと同じパターンを受け取り、コンパイラはアームに使うのと同じコードでそれを処理します。

  • ペイロードの型case が束縛する名前はペイロードの型を持ち、ペイロードのレコードにないフィールドは E0210、欠けているバリアントは E0200 になります。
  • 部分的な case値を判定する case はそのバリアントの一部しか扱わないので、残りを受け持つ兄弟の case か <case else> が必要です。
results.glyph 
type Page =
  | Loading
  | Loaded({ users: Array<User>, total: number })
  | Failed(string)

component Results(props: { page: Page }) {
  return <match value={props.page}>
    <case Loading><p>Loading...</p></case>
    <case Loaded({ users, totl })><p>{users.length} of {totl}</p></case>
    <case Failed(message)><p>{message}</p></case>
  </match>
}

// E0210 type `{ users: Array<User>, total: number }` has no field `totl`; did you mean `total`?

ページからはどう起動するのか？

Glyph にはトップレベルの文がないので、ページがエクスポートされた main を自分で呼び出します。アプリは 2 つのモジュールからなります。コンポーネントを持つモジュールと、std/dom と react-dom の createRoot を使ってそれらを #root にマウントするモジュールです。

イベント属性はスネークケースで（on_change は React の onChange として出力されます）、ハンドラはラムダで、入力のテキストは e.currentTarget.value です。

app.glyph 
module app

import react { useState }

pub component App() {
  let [name, set_name] = useState("")
  return <main>
    <input value={name} on_change={fn(e) { set_name(e.currentTarget.value) }} />
    <p>Hello, {name}</p>
  </main>
}
main.glyph 
module main

import react-dom/client { createRoot }
import std/dom
import std/console
import std/option { Some, None }
import app { App }

pub fn main() -> void {
  match dom.element_by_id("root") {
    Some(root) => createRoot(root).render(<App />),
    None => console.error("the page has no #root element"),
  }
}
index.html。2 つのモジュールと同じ場所に置く 
<div id="root"></div>
<script type="module">
  import { main } from "./dist/gen/main.ts";
  main();
</script>

  2. tsc --strict

詳細 ビルド、この main が何も受け取らない理由、手順の解説

npx glyph build . --out dist/gen はモジュールを検査し、React の型宣言に対して tsc --strict を実行し、TypeScript を dist/gen に書き出します。続いて npx vite build --outDir dist/web が index.html を読み、import をたどって React とともにバンドルします。この main は何も受け取らず何も返しません。スクリプトが引数なしで呼び出すからです。glyph init が書く main(argv) -> number は、node 上で glyph run が呼び出すものです。package.json とインストールのコマンドを含む手順の全体は、glyph llms が出力するリファレンスのブラウザのページで Glyph を動かすにあります。CI は examples/apps/todo を同じ方法でビルドし、ヘッドレス Chromium でレンダリングしています。

現状

提供中

  • コンポーネント、JSX、フラグメント（<>...</>）
  • メンバー式の要素名（<Ctx.Provider>）
  • JSX の props スプレッド（{...register()}）
  • どの import の書き方でも tsc より前にコンポーネントに対して検査される props
  • 名前で import する React 自身のフック（useState、useReducer、useEffect。型は tsc が検査し、ペアは分割代入できます：let [count, set_count] = useState(0)）
  • 網羅的なタグ付きユニオンのアクションを持つ useReducer
  • アームのパターンを使う match として検査・変換される <match>/<case>
  • createContext/useContext による Context
  • std/dom（タイトル、マウント先、アドレス）、std/storage、std/console を通したページの操作
  • JSX のテキストは TSX と同じように読まれるので、<p>Don't stop</p> は普通のテキストです。}、>、//、&amp; のような HTML エンティティはテキスト中では拒否され（E0012）、代わりの書き方が示されます。E0012
  • 配列に対するメンバーの読み取りは検査されるので、Array<string> に対する {items.foo} は E0210 です。E0210
  • examples/apps/todo は、Vite でバンドルされブラウザでレンダリングされる React 18 のアプリ一式です。

予定

  • Glyph の型検査はフックの戻り値を型付けしないので、数値の state に対する set_count("x") は、エディタでの Glyph のエラーではなく、ビルド中の tsc のエラーになります。
  • std/dom にできるのはページの読み取りとタイトルの設定までです。React がレンダリングする DOM は React のものなので、要素のセッターやイベントリスナーはありません。
  • エフェクトは fn() -> void { ... } と書く必要があります。ラムダは最後の式を返すので、React がそれをクリーンアップとして呼んでしまうからです。
  • インラインで書いた props の型は、これらのメッセージでは今も record と表示されます。名前付きの型ならその名前が表示されます。
  • UI を TypeScript で書いた既存の Vite アプリに Glyph の出力を組み込む方法は、デプロイのガイドにあります。
