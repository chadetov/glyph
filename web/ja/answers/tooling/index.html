なぜ重要か

エディタが理解しない言語を編集するのは後退に感じられますし、初期のころはそれはもっともな不満でした。今はそうではありません。エディタでは今どきの便利な機能が使え、エラーは拒否するだけでなく、教えるように書かれています。

本物の LSP ですか、それとも VS Code のプラグインにすぎないのですか？

本物です。コンパイラには glyph lsp で起動する言語サーバーが含まれており、stdio 上で Language Server Protocol を話します（どの LSP クライアントも理解する標準の JSON-RPC トランスポートです）。

同梱の VS Code 拡張はその薄いクライアントですが、VS Code 固有の部分はありません。Neovim、Helix、Zed、Emacs（eglot）など、LSP に対応したどのエディタでも glyph lsp を指定すれば同じように動きます。

すでにインストールしたのと同じバイナリ（npx @glyphlang/glyph lsp）なので、別途サーバーを取得する必要はありません。

サーバーが実装しているもの

サーバーはエディタに必要な機能を実装しています。後述の安定したコード付きのリアルタイム診断、hover による型表示、定義へのジャンプ（名前付き import 経由ならモジュールをまたいで動きます。namespace 経由の ui.Button にはまだ何も答えません）、補完、アウトラインとシンボル検索のためのドキュメントシンボルとワークスペースシンボル、ワークスペース全体の参照検索、リネーム、そして保存時の整形のための正規の glyph fmt レイアウトによるフォーマットです。

リネームは完全に動きます。モジュールレベルの宣言をリネームすると、その定義、すべての参照、そしてワークスペース全体で import している各モジュールの import 束縛が書き換わります。何かを変更する前に、新しい名前（キーワードではない正しい識別子か）も検査します。

知っておくべき制限が 2 つあります。ファイルをまたぐインデックスはキャッシュされず、リクエストごとに再構築されます（通常のプロジェクトなら問題なく、将来高速化する価値があります）。また、現時点でパースできないファイルはスキップされるので、それ自体が壊れているファイル内の参照にはリネームが届きません。

エラーメッセージ

エラーメッセージは、エージェントや初心者が最もつまずくところを重点的に改善しました。if と書くと、汎用的な “unexpected token” ではなく match を使うよう案内します。引数の数の誤り、網羅的でない match、バリアントの書き間違いには、それぞれ専用のコード付きの、直せるエラーがあります。

TypeScript のバックエンドでしか検出できない型エラーは、以前は生成された .ts を指していました。今は元の .glyph に対応付けて表示されます（同じ ariadne のキャレット、同じ安定したコード）。そのため tsc のエラーも Glyph 本来のエラーと同じように読めます。

デバッグ

出力された TypeScript を、Node のインスペクタ、ブラウザの開発者ツール、IDE の JS/TS デバッガなど、すでに使っているツールでデバッグします。

どのビルドでも、各 .ts の横に標準の v3 ソースマップ（Glyph のソースを埋め込んだもの）を出力するので、マップを連鎖させるデバッガやバンドラなら .glyph の行番号に戻れます。

まだ対応していないことが 1 つあります。glyph run 自身のクラッシュ時のスタックは、まだ .ts の行を表示します。tsx が変換の際にマップを連鎖させないためです。このスタックの対応付けは次の作業です。

実行せずに「これはコンパイルできるか」を聞く

glyph check path.glyph は 1 つのファイル、またはディレクトリ全体を型検査して終了します。ツリーには何も書き込みません。これは glyph run には約束できないことで、glyph build はそもそも行いませんでした（ディレクトリ以外は拒否していました）。

--no-tsc--json--no-test
詳細 何を実行するか、そしてフラグ

ビルドと同じパイプラインを、出力した TypeScript に対する tsc --strict も含めて実行し、終了時に削除する一時ディレクトリで行います。速く答えがほしいときは --no-tsc で Glyph の段階のあとに止められます。--json は、glyph build --json と同じ形の診断をエージェントに渡します。ファイルはそのディレクトリの文脈で検査されるので、隣のファイルが壊れていれば検査も失敗します。@example と @doc @run のテストもここで、glyph build と同じゲートとして実行されます。そのため、ビルドなら失敗するツリーを check がクリーンと報告することはありません。何も実行しない答えがほしいときは --no-test でテストを省けます。

出力も嘘をつかない

今はビルドを赤にしうるすべての段階のあとにサマリーを出力するので、赤いビルドで緑の行が出ることはありません。

経緯 早すぎたサマリー

以前は、失敗するビルドが “no diagnostics” で始まり、その下に tsc のエラーを表示していました。Glyph の段階のサマリーが、TypeScript の段階の実行前に書かれていたためです。

同じ作業で、glyph run app.glyph --min -12.50 も動くようになりました。以前は先頭のハイフンのせいで、main に届く前に clap が引数を拒否していました。

glyph 自身のフラグは引き続き glyph に結び付くので、それと衝突するプログラムのフラグの前には -- を置いてください。

ループの中にいるエージェントのために

glyph build --json はすべての診断を構造化された JSON で出力します。安定したコード、重大度、メッセージ、ファイル、1 始まりの行と列の範囲、さらに help と note です。Glyph のソースに対応付けた tsc のエラーも含みます。エージェントはターミナルのテキストを切り出すのではなく、これを直接読んで対応できます。

対話的なエージェント向けの glyph mcp

対話的なエージェント向けには、バッチの診断以外にもあります。glyph mcp は stdio 上で Model Context Protocol サーバーを実行し（同じバイナリで、エディタと同じ解析を使います）、言語サーバーのクエリを MCP ツールとして公開します。エージェントは、フルビルドを実行したりすべてのファイルを読んだりせずに、ファイルの診断、ある位置の型、名前が定義されている場所（import をたどります）、プロジェクト全体でのシンボルへのすべての参照、シンボル検索を問い合わせられます。

同じ純粋な解析レイヤーの上の薄いアダプターで、別の実装ではないので、コンパイラやエディタが見ているものからずれることはありません。

すべてがハードエラーというわけではない

Glyph には、ビルドを失敗させずに無駄を指摘する警告のレベルがあります。未使用の import（E0106）、未使用の let（E0107。_ で始まる名前は除外）、そして return/break/continue のあとの到達不能なコード（E0108）です。

E0106E0107E0108

これらはモジュールを正直に保ちます。使われていない import は、コードが実際には持っていない依存関係を読み手に探させる、まさに grep しやすさを損なうノイズです。警告は同じ表示と --json の出力に重大度付きで現れ、TypeScript も出力されます。

現状

提供中

  • どのエディタでも使え、モジュールの境界をまたいで答える言語サーバー0.1.124 から
    詳細

    言語サーバー（stdio 上の glyph lsp。どのエディタでも使え、VS Code 拡張を同梱）。ハイライト、診断、hover、定義へのジャンプ、補完、シンボル、ワークスペース全体の参照検索とリネーム、保存時の整形を備え、0.1.124 からはモジュールの境界をまたいで答えます。サーバーはプロジェクトごとに 1 つのデータベースを持ち、開いているバッファをディスク上のファイルに重ねているので、import した関数や import したレコードのフィールドを hover すると glyph query hover と同じ答えが返り、あるファイルの未保存の編集が別のファイルから見え、1 回のキー入力のコストは単一ファイルのときより 1 から 9 パーセント増えるだけです。

  • 11 のツールを持つ glyph mcp の Model Context Protocol サーバー
    詳細

    glyph mcp の Model Context Protocol サーバーは 11 のツールを持ちます。エディタのクエリに加えて glyph_symbol、glyph_impact、glyph_assignable、glyph_dependencies、glyph_exports で、それぞれに MCP クライアントを持たないエージェントのために同じ JSON を出力する glyph query のサブコマンドがあります。

  • 安定したエラーコード、glyph --explain、.glyph のソースに対応付けた tsc バックエンドのエラー、警告のレベル（未使用の import や束縛、到達不能なコード）、--json による構造化された診断。
  • glyph check [path] は 1 つのファイルやツリーを、実行も出力の書き込みもせずに型検査します。
  • glyph fmt --check は CI で整形のゲートになります。何も書き込まず、ファイルが唯一の正規のレイアウトになっていなければ 0 以外で終了します。

予定

  • ファイルをまたぐインデックスをリクエストごとに再構築せずキャッシュすること（大きなツリーで速くなります）。
  • glyph run 自身のクラッシュ時のスタックの対応付け。tsx は出力されたマップを変換の際に連鎖させないので、そのスタックはまだ .glyph ではなく出力された .ts を示します。
