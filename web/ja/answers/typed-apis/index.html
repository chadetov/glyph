なぜ重要か

ほとんどの TypeScript のスタックでは、すべてのペイロードを2 回記述します。1 回はコンパイラのための type として、もう 1 回は、実行時に値が本当にその形であるようにするための手書きのバリデータとしてです。

この 2 つはずれていき、そのずれこそが不正なデータが入り込む場所です。Glyph はこれを 1 つの宣言にまとめます。型がバリデータを生み出すので、両者が食い違うことはありません。

実例

DTO を 1 回宣言します。そのディスクリプタが .parse（信頼できない値をその型に検証する）と .is（型ガード）を提供し、ほかに書くものはありません。

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}
書かずに済んだもの 
// No zod schema:
const NewTask = z.object({
  title: z.string(),
  done: z.boolean(),
});
// No drift between the type and
// the validator, because there is
// only one declaration.

// A bad body, {"title": 123},
// takes the Err arm. Only a
// well-formed body reaches Ok.

match のあとも型付きの値を保つ

アームの中で処理する代わりに、値を取り出すこともできます。

api.glyph：値は型付きのまま match を出る 
let task = match NewTask.parse(req.body) {
  Ok(t) => t,
  Err(issues) => { return bad_request(issues) },
}
task.titel   // E0210: type `NewTask` has no field `titel`; did you mean `title`?
0.1.45 からジェネリック型：未対応
詳細 型がどう引き継がれるか、そしてジェネリックの例外

T.parse の型は Result<T, Array<Issue>> で、アームの型が一致する match はその型を持ちます。そのため let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, } と書けば、関数の残りの部分で NewTask が得られ、フィールド名は生成された TypeScript に対する tsc ではなく Glyph が検査します。これは 0.1.45 で入りました。それ以前は、値は match を出ると型を失っていました。今もそうならないのはジェネリック型の parse だけです。そのディスクリプタは型パラメータごとに実行時のチェッカーを受け取るからです。

parse の結果は普通の Result

Glyph の T.parse は、言語の中で失敗しうるすべての関数が返すのと同じ Result を返します。そのまま返すことも、map_err で検証の問題を自分のエラー型に変えることも、? で伝播させることもできます。

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}
これが置き換えたもの 
// Until 0.1.52 the generated descriptor
// returned a bare { tag, value } object,
// so both of the first two shapes were
// tsc errors (TS2322 and TS2339) even
// though Glyph's own checker reported
// Result<T, Array<Issue>>. The workaround
// was an identity re-wrap:

match NewTask.parse(body) {
  Ok(t)  => Ok(t),          // does nothing
  Err(e) => Err(reword(e)),
}

// Four lines to say map_err. bracket.glyph
// carried this twice until the fix landed.
詳細 ここで Result を使う実行時のコスト

独自の形で値を返すバリデータは半分しか役に立ちません。残りのエラー処理がそれを扱えないからです。parse の結果に特別なところは何もありません。

以前そうでなかった理由は、ディスクリプタが type の横に生成されるため、裸のオブジェクトを出力すれば、型を宣言するモジュールが実行時に std/result に依存せずに済んだからです。今はそのトレードオフを逆にしています。pub type を含むモジュールは、Result と書くかどうかにかかわらず std/result の import を持ち、parse の呼び出しは Ok(...) と同じくコンビネータのクロージャを確保します。その代わりに、検証された境界と残りのエラー処理が同じ API になります。

自分で組み合わせる：出力の型は信頼するのではなく導出する

Glyph の infer_output<Shape> は形から出力の型を導出し、tsc があなたの型注釈をそれに対して検査します。主張する型のフィールドを省いた形はコンパイルできません。

schema.glyph 
fn object_schema<Shape: Record<string, Schema<unknown>>>(
  shape: Shape,
) -> Schema<infer_output<Shape>> { ... }

type User = { name: string, age: number }

// The shape must produce a User, or this
// line does not compile:
const user_schema: Schema<User> =
  object_schema({
    name: string_schema(),
    age: number_schema(),
  })
Glyph がなくすずれ 
// TS/zod: shape and output type are two
// separate things you keep in sync by hand.
const s = z.object({ name: z.string() });
type User = { name: string; age: number };
// `s` is inferred { name }, but nothing
// checks it against User. The `age` you
// forgot is caught at runtime, if ever.

// Glyph: drop `age` from the shape and
// `Schema<User>` fails to compile. The
// shape is the single source of truth.
詳細 TypeScript の落とし穴と、0.1.92 から return に追従するキャスト

zod 風のコンビネータ、つまり小さなバリデータを組み合わせてバリデータを作りたいこともあります。TypeScript での落とし穴は、コンビネータの出力の型と、渡した形がずれていくことです。形を書いたあと、2 つ目の型パラメータで同じことを繰り返し書きますが、両者が一致しているかを検査するものはありません。

導出された型は、コンビネータがどう返しても成り立ちます。infer_output には関数の境界で 1 つのキャストが必要です。本体が作る値が、形から導出された型を持つことを型システムが証明できないためで、そのキャストはコンパイラが書きます。0.1.91 までは、それは単純な return <value> に付けられていました。return と値の間に match を挟んだり、本体を r? で終えたりすると、同じ関数がコンパイルできなくなりました。コンパイラがすでに受け入れた Glyph に対して、生成された TypeScript で TS2322 が出たのです。0.1.92 からは、キャストは書き方ではなく return そのものに追従するので、return match strict { ... } も、同じ本体を単一の return で書いたものと同じように型検査を通ります。

信頼できない境界の残り

このディスクリプタは、json.parse<T> を安全にしているのと同じものです。JSON 文字列を渡すと、パースと検証を 1 ステップで行います。

入力呼び出し戻り値
JSON 文字列json.parse<T>(text)Result<T, Array<Issue>>
デコード済みのボディT.parse(value)Result<T, Array<Issue>>
ヘッダーheader(req, name)Option<string>
クエリパラメータquery_param(req, name)Option<string>
詳細 リクエストボディ、ヘッダー、クエリパラメータ

リクエストボディはデコード済みの unknown として届くので、そこでは代わりに T.parse(value) を使います。保証は同じで、キャストは不要です。

信頼できない境界の残りも同じように型付けされています。header(req, name) と query_param(req, name) は Option<string> を返すので、ヘッダーやクエリパラメータがなければ None になり、match がその処理を強制します。None のアームを省くとコンパイルできません。存在しない入力を、あるかのように読むことはできません。ボディのフィールドも同じ規則に従います。timeout_ms?: number は「キーがない」か「数値」のどちらかなので、{"timeout_ms": null} は T.parse、is T、json.parse<T> のどれでも ["timeout_ms"] での Err になります。送り手が null を書く場合は timeout_ms?: Nullable<number> と宣言してください。0.1.152 までは、その null が Ok の中に入って返っていました。

enum をキーにしたマップは、キーを検査しますか？

はい、0.1.148 から検査します。type Tier = "free" | "pro" のときの Record<Tier, int> は、キーがちょうど free と pro であるオブジェクトだけをパースします。余分なキーも欠けているキーも Err になり、これは同じオブジェクトをリテラルで書いたときに tsc が言うことと同じです。

キーの型parse が各キーで検査すること
文字列リテラルユニオン列挙されたキーとちょうど一致すること。欠けも余分もなし
where で絞り込んだ string または数値述語
int整数の素直な表記であること。"01" や "1.5" は失敗
string新しい検査はなし
詳細 絞り込んだ型と int のキー、そしてチェッカーが保証すること

where で絞り込んだキーの型は、すべてのキーで述語を実行します。int のキーは整数の素直な表記でなければならないので、"01" や "1.5" は拒否されます。Record<string, V> は以前とまったく同じように検査されます。where で文字列リテラルユニオンを絞り込むことはできません（type T2 = Tier where value != "pro" は 0.1.152 から E0300 です）。意図するメンバーをそれ自体のユニオンとして type T2 = "free" のように書けば、同じ厳密なキーの検査付きで Record のキーにできます。0.1.153 からは、コード中に書いた値のキーも Glyph 自身のチェッカーが保証します。Record<Tier, int> と宣言された場所に Record<string, int> は置けず、その逆も同じです。そのため境界を越えるには json.parse か is Record<Tier, int> のアームを通ることになり、record.set は渡されたキーをそのまま保ちます。また、自身の型パラメータをキーにしたジェネリックなレコードは、そのパラメータが string でない限り拒否されます。

日付をパースしたら、正しい日付が得られますか？

はい。面白いのは、日付でない入力に対して何が返るかです。time.parse_iso は Option<number> を返し、ISO-8601 でないものすべてに対して None になります。

受け入れる 
"2026-01-03"              // UTC midnight
"2026-07-25T18:33:08.000Z"
"2026-03-15T09:30:00-05:00"
"2028-02-29"              // a real leap day
どれも None 
"January 5 2026"   // not ISO
"2026-1-3"         // not padded
"2026-13-01"       // no month 13
"2026-02-31"       // no such day
"2026-02-29"       // not a leap year
"2026-01-03T10:00" // no offset

最後のものは意外に思われがちですが、これこそが要点です。Z も +HH:MM のオフセットもない日時は、ECMAScript の文法ではローカル時刻です。それを受け入れると、同じ文字列が、プログラムを実行したマシンによって違う日付を指すことになります。

詳細 Date.parse の挙動と、UTC である理由

これは JavaScript の Date.parse より強い主張です。こちらは自由形式のテキスト（"January 5 2026"）を受け付け、"2026-1-3" のようなゼロ埋めのない日付をプロセスがたまたま動いているタイムゾーンで読み、存在しない日を繰り上げて成功として扱います。"2026-02-31" は 3 月 3 日になり、何かが起きたことを示すものは何もないまま数値が返ってきます。

Glyph のカレンダーのアクセサ（time.year、time.month、time.day）は UTC で、そのことを明示しています。ホストのタイムゾーンを黙って持ち込むバリデータがあれば、これらは嘘をつくことになります。そこで文字列は拒否され、それが何を意味していたかはあなたが決めます。

ガードはプリミティブの中に移った

アプリケーションが標準ライブラリのプリミティブの周りに正しさのためのガードを書いているなら、そのガードはプリミティブに属します。アプリが削除したのは次のコードです。

変更前：アプリが stdlib をガードしている 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
変更後：プリミティブが守っている 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

import std/regex も一緒になくなりました。台帳も、拒否される行も、レポートもバイト単位で同じです。

経緯 この変更のきっかけになった経費報告アプリ

これは Glyph で書いた経費報告の CLI から生まれました。台帳のどの行にも日付があり、行を間違った月に記録してしまうのが重大なバグです。そこでアプリは以前の parse_iso を信頼せず、まず正規表現で形を検査し、次にタイムスタンプをテキストに戻して、繰り上がった日を検出していました。

型を書く必要すらない

形がすでに OpenAPI の仕様や TypeScript の宣言ファイルにあるなら、そこから Glyph の型を生成します。推論された実体のないものではなく、コミットされ、grep できる実際の type 宣言で、それぞれにディスクリプタが付きます。

OpenAPI / JSON Schema の仕様から 
glyph gen openapi petstore.yaml \
  --out src/
インストール済みのパッケージから、名前で 
glyph gen dts api-types \
  --out src/types

ワイヤ型が、何も手書きせずに検証された境界になります。

webhook.glyph 
import types/api_types { Customer }

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),
  Err(issues) => reject(issues),
}

生成はワイヤに忠実です。仕様が値について述べていることが、そのまま parse の検査内容になります。

仕様または .d.ts での表現生成される Glyph
文字列の enum文字列リテラルユニオン。parse がメンバーかどうかを検査
integer のフィールドint。ワイヤ上の 3.5 は失敗
オブジェクトのスキーマ@open を付けたレコード。additionalProperties: false なら厳格
interface Page<T>type Page<T>。各要素を T として検査
判別子のないユニオン注記を出力したうえで絞り込む
到達可能な 2 つのファイルにある同じ名前束縛せず、注記で警告
詳細 現在生成されるもの、再生成、ジェネリック型

glyph gen dts には .d.ts ファイルを指定するか、上の例のようにインストール済みの npm パッケージを名前で指定します。node_modules からパッケージ自身の宣言のエントリを解決し、import して使うコミット用の型を書き出します。

現在生成されるもの：gen dts は、パッケージが export する interface と type の宣言を読みます。declare namespace の木の中にあるもの（修飾なしの相互参照はスコープを通じて解決されます）や、index のバレルが再 export している隣のファイルにあるもの（エントリの .d.ts と、相対パスで import されるすべての .d.ts をたどります）も含みます。ジェネリックはそのまま第一級として保たれます。interface Page<T> は type Page<T> として生成され、各要素を存在だけでなく型引数の型として検証するディスクリプタが付きます。別名付きの再 export や export * as による再 export は、ファイルごとの束縛マップを通じて解決されます。安全にできない唯一のケース、つまり到達可能な 2 つのファイルで型名が衝突する場合は、間違った形を黙って束縛するのではなく注記で警告します。生成器が届かないものについては、境界をまたぐ形を手書きするか、extern_ts の抜け道を使ってください。

再生成は冪等なので、仕様の変更はきれいでレビューしやすい差分になります。生成はワイヤに忠実です。文字列の enum は文字列リテラルユニオン（"free" | "pro"）として生成されるので、parse は値が文字列であることだけでなくメンバーかどうかを検査し、それに対する match は else なしで網羅的になります。integer のフィールドは int になるので、普通の number なら通るワイヤ上の 3.5 は parse で失敗します。Glyph に正確な対応形がない構文（判別子のないユニオン）は、実際のデータを拒否してしまうバリデータを出力するのではなく、絞り込んで注記を出力します。生成されたレコードには @open も付くので、parse は宣言されたすべてのフィールドを検証しつつ、API があとから追加したフィールドを許容します。additionalProperties: false を指定したスキーマは厳格なままです。Glyph のレコードはデフォルトで厳格で、これは手書きのレコードでも使う、grep できる宣言側のマーカーと同じものです。レコードの意味は何も変わりません。

ジェネリック型も検証されます。Paginated<T> には、型引数を受け取る parse を持つディスクリプタが付きます。Paginated.parse<User>(body) は items の各エントリを、存在だけでなくUser として検査し、match v { is Paginated<User> => ... } も同じように絞り込みます。これはモジュールの境界をまたいでも成り立ちます。Paginated<T> をあるファイルで定義し、別のファイルに import しても、そこでの Paginated.parse<User>(body) と is Paginated<User> は各要素を User として検査します。コンパイラは呼び出し箇所の型引数から要素ごとの検査を組み立てるので、ジェネリック型がどのファイルにあっても検証内容は変わりません。

できないこと：ディスクリプタが対応するのは、ほとんどのペイロードを構成する形です。オブジェクト、プリミティブ、配列、参照、省略可能なフィールドと null 許容のフィールド、そして特定のインスタンス化をしたジェネリック型です。Glyph が生成していない型（import するだけの外部パッケージや .d.ts）は型検査されますが、生成するまではディスクリプタを持ちません。生成は今ではインストール済みのパッケージに対する 1 つのコマンド（glyph gen dts <package>。パッケージが export するトップレベルのインターフェースと型エイリアスが対象）で済みます。この境界は意図的なものです。Glyph が出力していない型は実行時の検証を約束できないので、パッケージごとにオプトインし、その結果はビルドのたびに作り出されるのではなく、コミットされて grep できます。

データベースも境界

データベースから読んだ行は、リクエストボディとまったく同じ意味で信頼できません。リクエストボディに使うのと同じ .parse で行を検証します。

tasks.glyph 
type Task    = { id: int, title: string, done: bool }
type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.
match TaskRow.parse(row) {
  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}
これでなくなるバグ 
// TS, better-sqlite3 / node:sqlite:
const row = stmt.get(id) as Task;
// `row.done` is really 0 or 1, a number.
// Nothing complains. Then:
if (row.done === true) { ... }   // never runs

// The row was `unknown`; the cast invented
// a type. Glyph makes you validate the row
// into TaskRow, and the int-to-bool step is
// a line of code, not a silent lie.
詳細 std/sqlite と、0 か 1 の真偽値

データベースから読んだ行は、リクエストボディとまったく同じ意味で信頼できません。データベースのスキーマとコードが想定する行の形は食い違うことがあり、キャスト（row as Task）はそれを覆い隠します。Node 組み込みの SQLite の上に作られた DB モジュール std/sqlite は、この点を徹底しています。クエリは Array<Record<string, unknown>> を返すので、まず検証しない限り行を Task として扱う方法はありません。

これは本番に出がちなバグを検出します。SQLite には真偽値の型がないので、done 列は整数の 0 か 1 として返ってきます。行を bool のフィールドを持つレコードにキャストすると、task.done === true は黙って決して true になりません。Glyph では保存用の形とドメインの形は別の型で、その間の対応付けは目に見える 1 行です。

全体は動く例として用意しています。examples/apps/tasks/main.glyph は永続化されたタスク API で、保存に std/sqlite、ルーティングに std/http を使い、データは再起動しても残り、ワイヤ側とデータベース側の両方で検証します。手書きのバリデータはどこにもありません。

署名付き Webhook も境界

Webhook の署名を検証するには、再シリアライズしたコピーではなく、送信側が署名したバイト列そのものが必要です（パースしたボディを文字列化し直すと空白やキーの順序が変わり、HMAC が一致しなくなります）。http.raw(req) はそのバイト列を渡すので、検査を Glyph の中に保てます。 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
詳細 署名には生のバイト列、形にはパースしたボディ

req.body は引き続き形の検査に使うパース済みの値で、raw は署名の計算対象となる改ざんされていないペイロードです。署名を検証し、ボディを検証する受信側に、手書きの TypeScript は要りません。

型は形だけでなく不変条件も検証できる

形の検査でわかるのは、フィールドが number だということです。金額が負でないことや、評価が 1 から 5 の間であることはわかりません。where による絞り込みはその不変条件を型に入れ、ディスクリプタが境界でそれを強制します。

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
書かずに済むもの 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.

現在提供しているもの 10

ディスクリプタ

  • 宣言されたすべてのレコードとタグ付きユニオンは、ジェネリックなレコードも含め、実行時のディスクリプタ（.parse、.is、.schema）を持つジェネリックなタグ付きユニオンは持たない
  • .parse は言語のほかの部分と同じ Result を返すので、map_err、?、そして Result を返すどの関数とも組み合わせられる
  • where による絞り込み（int where value >= 0）は、形だけでなく不変条件を境界で検証する
  • json.parse<T> は JSON を検証する
  • infer_output<Shape> はコンビネータの出力の型を形から導出するので、両者がずれることはない

生成

  • glyph gen openapi / glyph gen dts は、仕様、.d.ts、またはインストール済みのパッケージ名から、ディスクリプタ付きのコミット用の型を生成する

境界

  • std/sqlite は行を unknown として返すので、データベースもほかと同じく検証された境界になる
  • 署名付き Webhook の受信側を完全に Glyph で書ける
    詳細

    http.raw(req) はパース前のリクエストボディを公開するので、Webhook の署名を正確なバイト列に対して検証でき、署名付き Webhook の受信側を完全に Glyph で書けます。

  • 信頼できない入力は sanitize なしに SQL やシェルの出力先に届かない
    詳細

    std/taint の Tainted/Trusted 型は、明示的な sanitize なしに信頼できない入力が SQL やシェルの出力先に届くのを防ぐので、tsc がインジェクションの経路をコンパイル時に拒否します。

  • time.parse_iso は ISO-8601 だけを受け付ける
    詳細

    より小さな境界のプリミティブも同じ線を守っています。time.parse_iso は ISO-8601 を受け付け、自由形式のテキスト、存在しない日、そしてそのままではホストのローカルタイムゾーンで読まれてしまうオフセットのない日時に対しては None を返します。

今後の予定 3

  • 判別子付きユニオンは仕様と .d.ts から生成される。次は enum と mapped type への対応
    詳細

    判別子付きユニオンは、OpenAPI の discriminator と TypeScript の .d.ts のユニオンの両方から生成されるようになりました（parse_<Name> のディスパッチャがタグを読み、正しいバリアントに検証します）。次は enum と mapped type への対応を広げます。

  • 仕様から型付きのクライアントとサーバーのコードを生成する機能はすでに提供済み クライアントとサーバーを見る
  • タイムスタンプと期間はどちらも number
    詳細

    日付については、厳格さこそが機能のすべてで、それはパースの段階で終わります。parse_iso はエポックからのミリ秒を返すので、タイムスタンプと期間はどちらも number で、一方をもう一方に足すのを止めるものはありません。専用の日付型を入れるかどうかは今後の判断で、小さな判断ではありません。
