それらの保証はどれもオプトインで、エージェントは 1 行でそれぞれを迂回できるからです。Glyph の厳格さは、エージェントが編集できる設定ファイルではありません。言語そのものです。強制のポイントが「このファイルに lint をかけるのを忘れなかったか」から「コンパイルが通るか」に移ります。

きちんと設定した TypeScript の環境でもかなりのところまで行けますし、チームがそのすべてを CI で実行しているなら、Glyph が狙う穴の大半はすでに塞がっています。真剣に検討する価値のある選択肢なので、対応関係を示します：

01 オプトインより必須

こうした抜け道はどれも、エージェントが編集できる設定です。Glyph には手を伸ばせる抜け道がありません。as も、無視用のプラグマもなく、コンパイラに見える検査なしに unknown から型付きの値を取り出す方法もありません。

TypeScript：抜け道が存在する handler.ts 
const user = body as unknown as User;
// @ts-ignore
doThing(user.mispelled);
// eslint-disable-next-line
return anything as any;
Glyph：無効にするものがない handler.glyph 
return match User.parse(body) {
  Ok(user) => use(user),
  Err(_) => fallback(),
}
// no `as`, no ignore pragma,
// no lint to switch off.

エージェントが設定で無効にできない厳格さは、無効にできる厳格さとは別の強制ポイントにあります。Glyph はその違いの上に作られています。

詳細 エージェントが eslint をすり抜けて書けるもの

eslint の設定が守れるのは、エージェントがそれを通すコードだけです。エージェントは as unknown as User、@ts-ignore、// eslint-disable-next-line を書くことも、単に .exhaustive() を忘れることもでき、それでもコンパイルは通ってマージされます。

02 型がバリデータになる：2 つ目の成果物はない

Glyph では型がバリデータです。type User = {...} を宣言すると、それと一緒に User.parse が生成されます。成果物は 1 つで、同期させるものも忘れるものもありません。

  • zod：スキーマが先zod は信頼できる情報源を逆転させます。スキーマを書き、そこから型を導き出し、型、スキーマ、シリアライザを手で同期させ続けます。
  • ずれが入り込む場所それらを揃えておくところこそ、エージェントがずれを持ち込む場所です。型のフィールド名を変えてスキーマは変えず、どちらもコンパイルは通ります。

03 grep できる変更

Glyph では共有状態はストアに置かれ、すべての変更は文字どおりの .set(/.update( です。grep 'mut ' でローカルな変更もすべて見つかります。素の TypeScript にはこれに相当するものがありません。

詳細 TypeScript で書き込みが隠れられる場所

TypeScript では、状態の変更は =、.push()、Object.assign、セッター、スプレッドの陰に隠れられます。検索できる単一のトークンはなく、これを完全に解決する lint ルールもありません。

失敗の仕方の差分

同じタスクで、エージェントがユニオンにバリアントを追加し、3 か所のうち 1 か所で扱うのを忘れた場合：

ツールを揃えた TS 
// ts-pattern .exhaustive() catches it,
// IF every site used ts-pattern and
// nobody wrote a default: case or a
// switch that only logs. Those
// compile green and skip the new case.
Glyph 
[E0200] non-exhaustive match on
`Feed`: missing variant `Archived`
// every unhandled match, everywhere,
// fails the build. No opt-in, no
// escape, no forgotten default.

ツールを揃えた TypeScript がまだ勝っているところ

現時点で Glyph より勝っている点が 4 つあります：

  • より豊かな検証。Glyph のディスクリプタはデフォルトで厳格（宣言していないキーを拒否）で、where による refinement はプリミティブに述語を付けられます（type Email = string where value.includes("@")）。ディスクリプタは型が届くすべての境界でそれを実行します。それでも zod が勝っている点が 2 つあります。.email() や .url() のような既製の検査を備えていること（Glyph では自分で書きます）と、オブジェクト全体に refinement をかけられることです。レコードに対する where（2 つのフィールドにまたがる lo <= hi）は、現時点では E0300 になります。
  • より深いマッチング。ts-pattern のガードや深い構造パターンは、Glyph の match で表せる範囲を超えています。
  • 「存在しないことの証明」は .ts の境界で止まります。Glyph の保証は Glyph が書いたコードに対して成り立ちます。npm の依存パッケージから throw された例外は今も Result を迂回しますし、import した .d.ts の型には実行時ディスクリプタがありません。
  • エコシステムと採用。TypeScript のツール、コミュニティ、採用できる人材ははるかに大きく、何年もの本番での利用実績があります。Glyph はアーリープレビューです。

ツールを揃えた TypeScript を完全に組み込み、エージェントがその中にとどまるなら、これらの大半は手に入っています。Glyph の主張は、「その中にとどまる」こそが要となる言葉であり、エージェントが破るのはまさにその部分だということです。必須であること、1 つの成果物での検証、grep できる変更は、オプトインのツールをいくら追加しても得られない部分です。

詳細 ReScript、Gleam、Elm

TypeScript を離れて、JavaScript にコンパイルされる歴史のある型付き言語に移ることも考えているなら、ReScript、Gleam、Elm ではなぜ駄目なのかで Glyph とそれらを比較しています。
