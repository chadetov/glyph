TypeScript が通してしまうケース

出荷する前に検出する

チェック済みのケースは全部で 47 件です。TypeScript のケースが 37 件、Glyph には存在しない JavaScript の落とし穴が 5 件、Glyph がまだ塞いでいない穴が 5 件です。そのうち 28 件はビルド時に Glyph が拒否します（TypeScript のケース 23 件と落とし穴 5 件）。

リストにある TypeScript の例は、どれも tsc --strict をエラーなしで通過します。さらに各例を、最も厳しく設定したプロジェクトでも検証しています。--strict より厳しいコンパイラフラグをすべて有効にし、typescript-eslint の strictTypeChecked も加えた設定です。37 件のケースのうち 21 件は、この設定のどれにも検出されません。デフォルトでは無効のコンパイラフラグで検出できるのが 5 件、lint ルールで検出できるのが 11 件です。これらはプロジェクトごとに 1 つずつ有効にする必要があり、エージェントが無効に戻すこともできます。Glyph では、どれも設定項目ではありません。

各項目は catches/ にある 2 つのプログラムで、その下の出力はツールが実際に表示したものです。ビルドのゲートである scripts/check_catches.py がすべてのケースを再実行し、どちらかがこのページの記述どおりに動かなくなると失敗します。検証に使う TypeScript の設定の全体は、このスクリプトにあります。

TypeScript のケース 37 件

起こりやすさ AI エージェントがそれを書く頻度 深刻度 本番に出たときの被害の大きさ

評価は 1 から 5 の 5 段階で、エージェントが書いたコードに関する公開研究と、私たち自身がエージェントを動かした結果をもとにした判断です。これらの頻度を直接測定した人はいません。リストは起こりやすさと深刻度の積の順に並んでいます。

プログラムの外から来るデータ

起こりやすさ 5 段階中 5深刻度 5 段階中 5

リクエストボディ、ファイル、API のレスポンス。

TypeScriptコンパイルは通り、不正なデータのまま動く
ts.ts
const user = JSON.parse(body) as User;
console.log(sendInvoice(user.plan));
$ tsx ts.ts
invoice for the undefined plan

データを検査するものが何もありません。undefined がプランとしてそのまま流れていきます。

Glyphデータの到着時に検査
glyph.glyph
let out = match json.parse<User>(body) {
  Ok(user) => send_invoice(user.plan),
  Err(issues) => "rejected: ${json.stringify(issues)}",
}
$ glyph run
rejected: [{"path":["plan"],"message":"field `plan` is required","code":"missing"}]

本物の User ではないボディは Err になります。プログラムが偽物を持つことはありません。

as User は何も検査しません。自分を信じるようにコンパイラに伝えるだけです。Glyph には as がありません。

2

誰も扱わなかったケース

起こりやすさ 5 段階中 5深刻度 5 段階中 4

エージェントが "archived" というステータスを追加する。各ステータスを通知するハンドラは、それが存在する前に書かれていた。

TypeScript警告なしでコンパイルが通る
ts.ts
switch (s) {
  case "todo":
    console.log("not started");
    break;
  case "doing":
    console.log("in progress");
    break;
  case "done":
    console.log("finished");
    break;
}
$ tsx ts.ts
finished
archived logged nothing

アイテムをアーカイブしても何もログに出ません。switch が古くなっていることを示すものは何もありません。

lint のみlint ルール switch-exhaustiveness-check で検出されます

Glyphビルド時に拒否
glyph.glyph
match s {
  "todo" => print("not started"),
  "doing" => print("in progress"),
  "done" => print("finished"),
}
$ glyph build
[E0200] Error: typecheck: non-exhaustive match on `"todo" | "doing" | "done" | "archived"`: missing variants "archived"
Help: Add an arm for each missing variant.

ビルドが止まり、そのケースの名前が示されます。

TypeScript が switch ですべてのケースが扱われているかを検査するのは、関数がすべての分岐から値を返す場合か、assertNever のイディオムを使った場合だけです。何も返さないハンドラはどちらにも当てはまりません。Glyph ではすべての match がすべてのケースを扱わなければならないので、バリアントを追加すると、変更が必要な箇所がすべて一覧されます。

起こりやすさ 5 段階中 5深刻度 5 段階中 4

ID でレコードを探す。

TypeScriptコンパイルは通り、実行時にクラッシュする
ts.ts
return users.find((u) => u.id === id)!.name;

! はコンパイラに「信じてくれ」と伝えるものです。実行時には何もしません。

lint のみlint ルール no-non-null-assertion で検出されます

Glyphビルド時に拒否

find は Option を返すので、空の場合を扱わなければなりません。

シグネチャに表れないエラー

起こりやすさ 5 段階中 4深刻度 5 段階中 4

失敗しうる関数を、それを知らないコードが呼び出す。

TypeScriptコンパイルは通り、実行時にクラッシュする
ts.ts
function loadConfig(): Config {
  throw new Error("missing file");
}

const cfg = loadConfig(); // no try
$ tsx ts.ts

型は Config と言っています。throw しうることはどこにも書かれていません。

失敗は戻り値の型の一部なので、呼び出し側はそれを扱わなければなりません。

TypeScript の関数の型には、何を返すかは書かれますが、何を throw するかは書かれません。Glyph では失敗が戻り値の型の一部なので、どの呼び出し側からも見えます。

自分のオブジェクトを忘れるメソッド

起こりやすさ 5 段階中 2深刻度 5 段階中 3

メソッドを値として受け渡す。

TypeScriptコンパイルは通り、実行時にクラッシュする
ts.ts
const up = name.toUpperCase;
console.log(up());
$ tsx ts.ts
TypeError: String.prototype.toUpperCase called on null or undefined

メソッドが文字列から切り離され、その文字列を見失います。

lint のみlint ルール unbound-method で検出されます

Glyphビルド時に拒否
glyph.glyph
let up = name.toUpperCase
$ glyph build
[E0234] Error: typecheck: method `toUpperCase` of `string` is read without being called

メソッドは読み取ったその場で呼び出す必要があります。代わりに関数を渡してください。

TypeScript のメソッドは、呼び出されたオブジェクト（this）に依存します。name.toUpperCase() から値として取り出すと、どの文字列を使えばよいかがわからなくなります。

数量 1.5

起こりやすさ 5 段階中 2深刻度 5 段階中 3

整数しかありえない注文明細。

TypeScriptコンパイルは通り、不正なデータのまま動く
ts.ts
type Order = { qty: number };

const text = '{"qty": 1.5}';
console.log((JSON.parse(text) as Order).qty);
$ tsx ts.ts
1.5

TypeScript には number が 1 つしかありません。商品が半分だけ出荷されます。

何も検出しないコンパイラフラグをすべて有効にし、typescript-eslint を strict 設定にしても検出されません

Glyphデータの到着時に検査
glyph.glyph
type Order = { qty: int }

let out = match json.parse<Order>(text) {
  Ok(o) => "qty ${o.qty}",
  Err(issues) => "rejected: ${json.stringify(issues)}",
}
$ glyph run
rejected: [{"path":["qty"],"message":"field `qty` must be int","code":"type"}]

int は独立した型で、検査されます。

TypeScript では、整数にも小数にも同じ number 型を使います。Glyph には int があり、データの到着時に検査します。

Glyph には存在しない JavaScript の落とし穴 5 件

昔からある落とし穴ですが、エージェントは今でもときどきはまります。Glyph はどのプログラムも拒否しますが、ミスを見つけるからではありません。その原因となる機能が言語になく、代わりに使うものが示されるからです。

  • "10,20,30".split(",").map(parseInt) は [10, NaN, NaN] になります。map がインデックスを基数として渡すからです。Glyph には Result を返す number.parse があります。 Playground で開く
  • /g 付きの正規表現を .test で使い回すと、lastIndex を覚えているせいで 1 回おきにマッチに失敗します。Glyph には正規表現オブジェクトがなく、regex.matches(pattern, text) は状態を持ちません。 Playground で開く
  • [1, 2, 3].forEach(counter.increment) は、メソッドをそのオブジェクトなしで実行します。Glyph にはクラスも this もありません。 Playground で開く
  • Math.max(...[]) は -Infinity です。Glyph の array.max は Option を返し、空のリストでは空になります。 Playground で開く
  • Array(3).map(...) は穴が 3 つの配列を返します。map が穴を飛ばすからです。Glyph には Array(n) がなく、配列はリテラルで書きます。 Playground で開く

Glyph がまだ検出できないもの

Glyph がまだ塞いでいない穴 5 件。どれも現在の Glyph でコンパイルが通り、TypeScript と同じ誤った動作をします。それぞれに catches/ の再現コードと未解決の gap 番号があり、修正が入るとゲートが失敗するので、穴が塞がった後に項目が残ることはありません。

  • requested || 3 は、正当な 0 を 3 に変えてしまいます。 G386
  • 数値に対する .sort() は数値を文字列として並べ替えます：100,25,9。 G388
  • c[0] に対する await をまたいだ更新の消失。フィールドへの同じ書き込みなら拒否されます。 G390
  • 文字列に対する input + 1、users.find(...).name、unknown に対するフィールドの読み取りは、tsc のステップでしか検出されず、Glyph 自身の型検査では検出されません。そのためエディタやエージェント向けツールでは見逃されます。 G381, G382

エージェントが書いたコードに関するどの研究でも、最大の分類はロジックの誤りで、型検査器にはそれが見えません。式の誤りやタスクの読み違いは、TypeScript と同じく Glyph でもコンパイルが通ります。

Glyph には、TypeScript で書くしかないもののための抜け道が 1 つだけあります。extern_ts です。固定のキーワードなので、grep extern_ts でルールが停止している場所をすべて一覧できます。
