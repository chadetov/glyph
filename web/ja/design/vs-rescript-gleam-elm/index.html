ReScript、Gleam、Elm ではなぜ駄目なのか

3 つとも JavaScript にコンパイルされる型付き言語で、どれも Glyph より歴史が長く、広く使われ、安定しています。新しいコードベースのために言語を選んでいて、TypeScript に近い位置にとどまる必要がないなら、まずこれらを検討する価値があります。Glyph の違いはもっと限られたものです。JavaScript ではなく TypeScript のソースを出力すること、npm パッケージをそれ自身の .d.ts の型付きで import すること、型から実行時バリデータを生成すること、そしてコンパイラがエージェントのために影響範囲のクエリに答えることです。

それぞれが自身をどう説明しているか#

ReScript のホームページは "JavaScript Made Simple for Humans and AI" と "Types > Vibes" を掲げ、"compiles to clean, efficient JavaScript" で "No any, no magic types, no surprise undefined." だと述べています。また "automatically generate TypeScript types" できるとしています（rescript-lang.org）。

Gleam のホームページは自身を "a friendly language for building type-safe systems that scale" と呼び、"No null values, no exceptions, clear error messages" を挙げています。Erlang VM 上で動き、"can additionally compile to JavaScript"、さらに "also generates TypeScript definitions" とあります（gleam.run）。

Elm のホームページは "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions" を "reliable web applications" のための言語として紹介し、Elm は "detects all API changes automatically" ことで "guarantee that every single Elm package follows semantic versioning" と述べています（elm-lang.org）。

これらの引用は 2026-11-19 に確認したものです。

相手のほうが優れている点#

分野ReScript、Gleam、ElmGlyph
成熟度何年もの本番運用の実績。ReScript のホームページには企業ロゴが並び、Elm のホームページは 30 万行以上のコードを持ちながら本番で不可解な実行時例外が出ていない NoRedInk を挙げているアーリープレビューで 1.0 前。主に 1 人でメンテナンスしており、多くのリリースが Breaking
保証Elm は実行時例外なし、Gleam は null 値も例外もなし、ReScript は any も予期しない undefined もなしと主張しているany もキャストもないが、既知の穴 11 件を公開しており、npm パッケージの中で throw された例外は今も Result をすり抜ける
エラーメッセージElm のホームページは "friendly error messages" を掲げ、Gleam は "clear error messages" を約束している。どちらも長年の利用者に支えられているすべてのエラーに固定のコードとヘルプ行があるが、使われてきた量ははるかに少ない

Glyph が違うやり方をしている点#

以下はどれも、このページのために Glyph 0.1.149 で実行したものです。

TypeScript のソースを出力する

glyph build はモジュールごとに 1 つの .ts ファイルを書き出し、それを tsc --strict が検査します。Glyph をやめても、このファイルは手元に残ります。ReScript と Gleam は JavaScript を出力し、その隣に型定義を生成します。出力される TypeScript は TypeScript のページで紹介しています。

npm パッケージをそれ自身の型宣言の型付きで import する

モジュールはパッケージを名前で import し、パッケージの .d.ts がすべての使用箇所に型を付けます。先に書いておくバインディングはありません。ReScript では "external is the primary ReScript feature for bringing in and using JavaScript values"（external）で、型は ReScript 側で宣言します。Gleam の external には型注釈が必要で、コンパイラは "cannot verify that the function implemented in the other language returns the specified types"（externals）とされています。Elm は flags、ports、カスタム要素を通じて JavaScript とやり取りします（interop）。pg と @types/pg をインストールした状態で、次のコードは拒否されます。

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

コードが TS2322 なのは、ライブラリの値を検査するのが tsc で、その結果が Glyph の行に対応付けられているからです。Glyph 自身の型検査はそれらを見ないので、glyph check --no-tsc、エディタ、MCP のツールはこのエラーを見逃します（G257）。また、.d.ts から import した型には実行時の検査がありません。

型からバリデータを生成する

すべてのレコードとユニオンは宣言から生成された実行時の検査を持つので、データが合わないとき json.parse<User> は Err を返します。Elm では形ごとにデコーダを書き、ガイドには "the decoders people write end up working as a validation phase" とあります（JSON）。

main.glyph：JSON に email がないので "refused" と出力する 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

変更が何を壊すかにコンパイラが答える

編集の前に、エージェントは変更がどの箇所に及ぶかを、MCP（glyph_impact）や glyph query impact で問い合わせられます。網羅的な match が 1 つと else で終わる match が 1 つあるユニオン Plan = Free | Pro | Team で新しいバリアントについて聞くと、箇所ごとに答えが返ります。

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

2 つ目の箇所は変更後にコンパイルが通らなくなります。これは変更を加えれば、どのコンパイラでも教えてくれることです。1 つ目の箇所はコンパイルが通り続け、新しいケースを else に送ります。それを名指しするのがこのクエリです。その他のツールはエージェント開発者向けのページにあります。

このページが主張しないこと#

エラーメッセージ、コンパイル速度、実行時の性能は比較していません。また、3 つのどれかを Glyph から呼び出すことも、その逆も試していません。引用は各プロジェクトが自分の言葉で述べたもので、それがどれだけ実態に合っているかは、Glyph 自身の主張と同じく、根拠のページを見てご自身で確かめてください。
