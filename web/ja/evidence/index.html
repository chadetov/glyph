根拠

このサイトの各主張をどう検証しているか

Glyph が何かを検出するという主張は、リポジトリにある 1 組のプログラムです。1 つは TypeScript、1 つは Glyph で書かれており、CI のゲートが変更のたびに両方を実行します。TypeScript のほうがコンパイルできなくなったり、Glyph のほうが拒否されなくなったりすると、ビルドが失敗します。どのケースも 2 つのコマンドで自分で実行できます。

fixture#

catches/ の下の各ディレクトリには、ts.ts、glyph.glyph、そしてそれぞれが何をするかを記した case.toml があります。scripts/check_catches.py は CI で実行されます。コンパイルできない TypeScript のプログラムでは何も証明できないので、すべての ts.ts が tsc --strict を通ることを要求し、Glyph のほうはケースの種類に応じて検査します。チェック済みのケースは全部で 51 件です。TypeScript のケースが 37 件、Glyph には存在しない JavaScript の落とし穴が 5 件、Glyph がまだ塞いでいない穴が 9 件です。そのうち 28 件はビルド時に Glyph が拒否します（TypeScript のケース 23 件と落とし穴 5 件）。 ゲートが検査する種類ごとに見ると、次のとおりです。

種類ケース数ゲートが Glyph のほうに求めること
refused28case.toml にあるコードでビルドが失敗する
warned3ビルドは通り、そのコードを警告として報告する
boundary9プログラムは実行され、境界での検査が不正なデータを Err に変える
runtime2プログラムはビルドされ、実行時に記載どおりの出力で停止する
gap9Glyph はプログラムを受け入れ、プログラムは誤った動作をする。穴が塞がるとゲートが失敗し、ケースを移すよう伝える

示せなくなったケースは、手加減して残すのではなく削除します。catches の README に、削除した 6 件とその理由が載っています。そのうち 1 件は tsc でも検出できると判明したもので、別の 1 件は TypeScript のほうが値を any として受け取っていたから成り立っていただけでした。

比較対象の TypeScript#

各ケースには、最も厳しく設定した TypeScript のプロジェクトならそのミスを検出できたかどうかも記されています。「TypeScript なら検出できるか」のタグはここから来ています。「最も厳しく設定した」とは、tsc --strict に、それをさらに厳しくするすべてのオプションを加え、typescript-eslint も実行する構成です。ゲートは実行のたびにパッケージを新しくインストールし（TypeScript 6、eslint 9、typescript-eslint 8、tsx 4、最新の @types/node）、ネットワークがなければ飛ばすのではなく失敗します。

strict に加える tsconfig のオプション 
noUncheckedIndexedAccess: true
noFallthroughCasesInSwitch: true
noUnusedLocals: true
noUnusedParameters: true
noImplicitReturns: true
noImplicitOverride: true
allowUnreachableCode: false
allowUnusedLabels: false
exactOptionalPropertyTypes: true
noPropertyAccessFromIndexSignature: true
eslint.config.mjs 
export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.strictTypeChecked,
  { rules: {
    "@typescript-eslint/switch-exhaustiveness-check": "error",
    "@typescript-eslint/strict-boolean-expressions": "error",
    "@typescript-eslint/require-array-sort-compare": "error",
    "require-atomic-updates": "error",
  } },
);

ケースのタグは、none、それを報告する 1 つのオプションを付けた flag:、またはルールを付けた lint: のいずれかです。修正後のプログラムも無関係な理由でルールに引っかかる場合、そのケースには ts_ok.ts があり、タグはミスに対して反応するものだけを数えます。たとえば non-exhaustive-match は lint:switch-exhaustiveness-check です。そのルールを有効にすれば typescript-eslint で検出でき、ページにもそう書かれています。

1 つのケースを再現する#

リポジトリを clone して 1 つのケースに対してゲートを実行するか、手で実行します。以下は、このページのために実行した non-exhaustive-match の両方の結果です。

ゲート、1 ケース 
$ python3 scripts/check_catches.py non-exhaustive-match

typescript-eslint 8.73.0 strictTypeChecked on eslint 9.39.5, run with
tsx 4.23.15, and @types/node 26.6.6.

このサイトのコード例はコンパイルできる#

scripts/check_docs_compile.py は CI で実行され、このサイトにある単独で成り立つ Glyph のコード例（module で始まり、何かを宣言しているもの）と、ドキュメントや llms.txt にあるものをすべてコンパイルします。失敗することを意図したコード例は、出すエラーの名前を書かなければならず、まさにそのエラーを出さなければなりません。React や npm パッケージが必要なコード例は、それらのパッケージの実際の型に対してコンパイルされます。断片は数えたうえで飛ばし、その件数を出力するので、飛ばした割合は見えるままです。

まだ検出できないもの#

gap のケース 9 件は、それぞれの gap 番号とともに検出できるもののページに載っています。Glyph でアプリを作って見つかった穴はすべて台帳 docs/dogfooding-gaps.md にあります。そこでは角括弧の印だけが現在の状態を表し（[FIXED]、[HALF FIXED]、未解決なら印なし）、未解決の項目の最後の再現が 5 リリース以上前だと scripts/check_gaps.py が CI を失敗させます。

リリースに Breaking の印を付ける方法#

前のバージョンが受け入れていたプログラムを拒否するリリースには Breaking の印が付きます。その判定は、影響を受ける最小のプログラムを書き、公開済みの前のリリースと新しいバイナリで実行して、終了コードを比べることで行います。リリースノートの文言から推測するのではありません。0.1.99 より前のリリースはこの方法で確認していないので、印のないものは安全なのではなく、未確認ということです。記録はバージョンのページにあります。

記録の残り#

おすすめ検出できるものすべてのケース：TypeScript のコード、Glyph のコード、エラー、そしてツールを揃えた TypeScript なら検出できたかどうか。すべてのケースを見る
堅牢化懐疑的なエンジニアを演じるエージェントがコンパイラをどう攻撃し、どんなバグを見つけたか。 ベンチマーク何を測定しているか（トークン密度、grep、差分）と、まだ終わっていない信頼性の調査。 バージョンすべてのリリースと、その変更内容、どれが Breaking か。
