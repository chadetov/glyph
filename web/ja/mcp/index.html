エージェント向け · Model Context Protocol

エージェントを Glyph のコンパイラにつなぐ

glyph mcp は、プロジェクトを対象に 11 個のツールを提供する Model Context Protocol サーバーを起動します。シンボルが何か、それを変更すると何が壊れるか、ある型の値を別の型が宣言された場所に置けるか、宣言が何に依存しているか、モジュールが何をエクスポートしているか、プロジェクトの中で検査した診断、カーソル位置の型、名前がどこで定義されているか、その名前へのすべての参照、ユニオンに対するすべての match の箇所、そしてシンボル検索です。どのツールにも対応する glyph query の動詞があるので、MCP クライアントを持たないエージェントも同じ質問をして、同じバイト列を受け取れます。

エージェントにとってなぜ必要か#

コードベースを編集するエージェントは、たいてい手探りで作業しています。ファイルを読み、型を推測し、何かを壊したかどうかはビルドした後にしかわかりません。Glyph はすでにエディタ向けにこれらの質問に答えています。glyph mcp は同じ答えを、ビルド出力をかき集めたり、誰が何を呼んでいるかを探すためにすべてのファイルを読んだりすることなく、コンパイラから直接エージェントに渡します。ツールのうち 2 つは、エディタが決して聞かない質問に答えます。glyph_symbol はユニオンのバリアントを、それぞれを構築する構文とともに返します。エージェントが match を書く前に必要なのはまさにこれです。glyph_impact は、編集が何を壊すかを、その編集が存在する前に答えます。

セットアップ#

どの MCP クライアントからでも起動できます。クライアントに glyph バイナリと mcp サブコマンドを指定し、プロジェクトのルートを引数で渡すか、プロジェクトのディレクトリから実行します。MCP を stdio で話すので、ポートもデーモンも不要です。

MCP クライアントの設定（汎用） 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp", "/path/to/your/project"]
    }
  }
}

最初の接続でクライアントは initialize と tools/list を呼び出し、サーバーは下の 11 個のツールを報告します。送る位置は LSP の慣例に従います。0 始まりの line と、UTF-16 のコード単位で数えた 0 始まりの character です。診断の範囲は glyph check --json が出力するのと同じ形で返ってきます。1 始まりの line と col、それにバイト単位の offset です。

各ツールの説明には、呼び出す時点で必要な約束事が書かれています。完全なマニュアルは glyph llms --json の tools の下にツール名をキーとして置かれ、各ツールに対応する glyph query の動詞も並んでいます。以前はこの応答がすべてのマニュアルを運んでいました。11 個のツールで、45,509 バイトの応答のうち説明が 31,446 バイトでした。今は 20,386 バイトの応答のうち 8,627 バイトで、削除したものは何もありません。どのセッションも接続時に tools/list の分を支払い、マニュアルの分は要求したときにだけ支払います。そのドキュメントはコンパイラ自身のテーブルから生成されており、このサーバーが提供していないツール名が書かれているとテストがビルドを失敗させます。

11 個のツール#

glyph mcp が公開するツール 
// everything the compiler holds about one symbol: kind, identity,
// visibility, a record's fields, a union's variants with payloads and
// construction syntax, parameters and return, interface members,
// whether a `match` over it must be exhaustive, its `@example`.
// The identity reaches the stdlib: std/result::Result answers with
// Ok(T) and Err(E), and `path` is null beside the reason why
glyph_symbol(entity)                       // or (path, line, character)

// what breaks if you make one named change to one declaration:
// add_variant, remove_variant, rename, change_arity,
// change_signature_type, remove. One verdict per site
glyph_impact(entity, change)

// can a value of `from` go where a `to` is declared? Asked of the
// checker's own comparison. Each side is a `module::name` or a
// Glyph type spelling read in the scope of `path`
glyph_assignable(path, from, to)

// every diagnostic for one file, checked inside its project, in the
// shape `glyph check --json` prints, plus what was not checked
glyph_diagnostics(path)

// the type at a position: an expression, a declaration name, a
// parameter, an annotation, a variant, or a binding
glyph_hover(path, line, character)

// where the name is defined, following imports across modules,
// with the `module::name` so the answer chains into glyph_impact
glyph_definition(path, line, character)

// every edge into a symbol across the project, split by relation
// (CALLS, REFERENCES, GENERATED_FROM), each with its provenance
glyph_references(path, name)               // or by position

// every `match` site over one tagged union and which variants each
// site's arms name, with the union's own variants
glyph_variants(path, name)

// search top-level declarations and union variants by name, each
// entry with its identity, `pub`, kind and one-line signature
glyph_symbols(query)

// what one declaration depends on: every declaration its own source
// names, split by relation (CALLS, REFERENCES, FIELD_ACCESS), each
// edge with both ends and its provenance. The mirror of references
glyph_dependencies(entity)

// what one module makes visible to an importer: every `pub`
// declaration and every variant a `pub` union hoists, each with
// its identity, kind and signature
glyph_exports(module)

実例#

フィールド名にタイポのあるファイルに対して glyph_diagnostics の tools/call を送ると、コンパイラ自身の診断が返ってきます。glyph check --json がシリアライズするのと同じ Rust の型で、検査が対象にしなかったものも記した封筒に入っています。

リクエスト 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": { "path": "src/user.glyph" }
  }
}
結果（ツールの JSON コンテンツ） 
{
  "path": "src/user.glyph",
  "module": "user",
  "project_root": "src",
  "member": true,
  "diagnostics": [
    {
      "code": "E0210",
      "severity": "error",
      "stage": "typecheck",
      "message": "type `U` has no field `naem`; did you mean `name`?",
      "help": "Check the field name for a typo,
        or add the field to the type.",
      "entity": "user::greet",
      "file": "user",
      "range": {
        "start": { "line": 9, "col": 10, "offset": 99 },
        "end":   { "line": 9, "col": 16, "offset": 105 }
      },
      "union": null,
      "missing_variants": null
    }
  ],
  "unindexed": [],
  "not_run": [ ... ]
}

ファイルはプロジェクトの中で検査されるので、インポートしたレコードの誤ったフィールドや、インポートしたユニオンに対してアームの足りない match も、glyph check と同じようにここで報告されます。ツールが対象にできなかったものは、推測に任せるのではなく答えに書かれています。member はプロジェクトの走査がそのファイルに届くかどうかを示し、unindexed はパースできないプロジェクト内のファイルを挙げ、not_run は glyph check が行いこのツールが行わない 3 つの検査を挙げます。tsc、どのモジュールも指さないインポートに対する E0104（ビルドから見た node_modules が必要です）、失敗する @example に対する E0400（出力したプロジェクトを実行して判定します）です。テストが 6 つのプロジェクトで両方の経路を実行し、JSON をキーごとに比較するので、両者がずれることはありません。

glyph_references はワークスペース全体が対象です。シンボルについて聞くと、その宣言、すべての使用箇所、インポートする各モジュールの import 束縛が、すべてのファイルにわたって返ります。エディタのリネームと同じファイル横断の同一性を使うので、答えは質問したファイルだけでなくプロジェクト全体を網羅します。

MCP クライアントがない場合：コマンドラインで同じ質問をする#

どのツールにも glyph query の動詞があり、ツールと同じ引数をフラグとして受け取り、ツールの JSON を stdout に出力します。答えられた質問は終了コード 0 で終わり、拒否された質問は理由を stderr に書いて終了コード 2 で終わります。動詞は MCP クライアントが到達するのと同じエントリポイントを通り、統合テストが両方の経路に同じ質問をして答えをテキストとして比較するので、整形し直したり要約したりする動詞があればテストが失敗します。

同じ 11 個の質問を、クライアントなしで 
glyph query symbol       --path src/main.glyph --entity orders::OrderStatus
glyph query impact       --entity orders::OrderStatus --change add_variant --variant Refunded
glyph query assignable   --path src/main.glyph --from 'Nullable<int>' --to int
glyph query diagnostics  --path src/main.glyph
glyph query hover        --path src/main.glyph --line 9 --character 6
glyph query definition   --path src/main.glyph --line 9 --character 6
glyph query references   --path src/orders.glyph --name create
glyph query variants     --path src/orders.glyph --name OrderStatus
glyph query symbols      --query order
glyph query dependencies --path src/main.glyph --entity main::build
glyph query exports      --path src/main.glyph --module orders

// the same two, asked about a module the compiler carries
glyph query symbol       --path src/main.glyph --entity std/result::Result
glyph query exports      --path src/main.glyph --module std/result

すでにビルドが赤いとき#

ツールは編集の前に聞く質問に答えます。編集した後に読むべきものは glyph check --agent です。これは check --json の診断に、それぞれ 2 つのキーを加えて出力します。constraints は修正の編集が守るべき不変条件、symbols は診断が名前を挙げたすべてのシンボルに対する glyph_symbol の答えで、次の編集に 2 回目の呼び出しは要りません。アームの足りない match なら、ユニオンのバリアントがペイロードとともに、それを求めたエラーと一緒に届きます。else のアームを使うとその診断が守ろうとしている保証を手放すことになる、という一文も添えられています。修正が完全に決まる場合は、glyph fix がそれを書き込み、何を見送ったかを伝えます。実際の出力を使ってループ全体を順に追った説明もあります。

現状#

提供中

stdio で動く glyph mcp [root] サーバーと 11 個のツール：glyph_symbol、glyph_impact、glyph_assignable、glyph_diagnostics、glyph_hover、glyph_definition、glyph_references（ワークスペース全体）、glyph_variants、glyph_symbols、glyph_dependencies、glyph_exports。それぞれに同じ JSON を出力する glyph query の動詞があります。答えはコンパイラ自身のクエリから得られ、ツールが持っていない事実はどれも null になり、その理由を述べる <key>_absent の一文が隣に付きます。ホバーは別のモジュールで宣言された名前でも答えるので、呼び出し箇所でのインポートした関数にも、インポートしたレコードから読んだフィールドにも型が表示されます。エンティティの同一性は標準ライブラリにも及びます。プレリュードの Result は std/result::Result で、これはリゾルバが登録するモジュールであり、エミッタがインポートを書くモジュールでもあります。そのため、それに対する glyph_symbol は Ok(T) と Err(E) を答え、std/result に対する glyph_exports は公開面を一覧します。その背後に Glyph のソースはないので、path と range は欠落するのではなく、その理由とともに null になります。

予定

ツールは読み取りだけです。MCP を通じてリネームしたり編集を適用したりはできません。書き込み側は代わりにコマンドラインの glyph fix にあります。サーバーはキャッシュしたインデックスを持たず、呼び出しのたびにプロジェクトを走査し直し、パースできないファイルは飛ばします。tools/list の応答は 45,509 バイトから 20,386 バイトに減りましたが、どのセッションも接続時にそのコンテキストを支払うことに変わりはありません。

ツールのほかに、エージェントは言語と診断の仕様をオフラインで読めます。llms.txt は文章で、glyph llms --json は同じ知識をコンパイラ自身のテーブルからデータとして出したもの、glyph build --json はツリー全体にわたるコード付き診断を一括で得る経路です。
