柱 02 · 突破口

grep しやすさ

1 つの名前、1 つの場所。すべてのシンボルは、宣言された場所でちょうど 1 つの構文上の形を持ちます。そのため、インデックスも言語サーバーも運も必要なく、普通の grep で必ず定義が見つかります。

「これはどこで定義されているのか」が難しい理由

成熟した TypeScript のコードベースでは、この名前はどこから来たのかという最も単純な質問が、しばしば最も難しくなります。

詳細 オーバーロード、デコレータ、マージ、拡張、バレル

この言語には、1 つのシンボルを多くの場所に散らばらせる方法がいくつもあります。オーバーロードは関数を複数のシグネチャに分け、デコレータは関数を別の何かで包み、namespace と interface のマージは型を複数のファイルに散らし、declare module は自分のものではないコードを拡張し、バレルファイルの index.ts はすべてを再エクスポートするので、インポート元のパスに実体があるとは限りません。

人間は LSP と慣れで対処します。エージェントは grep します。リポジトリをテキストとして読むので、これらの構文はどれも、コードの場所についてテキストが嘘をつく箇所になります。

Glyph はこれらを取り除きます。その結果、検索が経験則ではなく信頼できる基本操作になる言語になります。

01 1 つの宣言、1 つの形

関数、型、コンポーネントは、1 つの構文でちょうど 1 回だけ宣言されます。シグネチャを分けるオーバーロードも、名前を再宣言する方法もありません。トップレベルに同じ名前のものが 2 つあれば即エラーです（E0100）。

E0100

宣言のキーワードは、検索する名前の一部です。grep "fn parseUser" は、呼び出しにもインポートにも再エクスポートにもマッチせず、定義された唯一の場所にだけマッチします。

そのため、定義の検索には答えが 1 つしかありません。

02 バレルファイルはない：インポートパスが場所になる

Glyph のインポートは再エクスポートをせず、中身がインポートだけのモジュールは拒否されます（E0102）。出どころをわかりにくくする index.ts の層はありません。

インポートを見れば、どこを見ればよいかが正確にわかる 
import myapp/users { parseUser }
//     ^^^^^^^^^^^ the file is src/myapp/users.glyph.
//     not a re-export of a re-export of a barrel.
E0102

そのためインポートは、シンボルが実際にあるモジュールを指します。パスがそのままアドレスです。

03 振る舞いを付け加える隠れた方法はない

関数を見えない層で包むデコレータも、ツリーのあちこちからメンバーを集める namespace のマージも、開こうとも思わないファイルからサードパーティの型を拡張する declare module も、メソッドが指すものを付け替える暗黙の this もありません。

名前は 1 つの宣言に解決され、それを形づくるものはすべてその宣言の場所で見えます。

04 変更も grep できる

grep しやすさは定義を見つけることだけではなく、作用を見つけることでもあります。共有状態は std/store に置かれ、それへの変更はすべて文字どおりの .set( か .update( の呼び出しです。

$ grep -rn 'tasks\.\(set\|update\)' src/ 
src/tasks.glyph:16:  tasks.update(fn(cur) { ... })
src/tasks.glyph:24:  tasks.set([])
# every place the task list can change, enumerated.
# nothing hides in an ordinary `x = ...` elsewhere.

そのため、ファイル中に散らばった代入を探し回る代わりに、1 回の検索でその状態に書き込む箇所をすべて列挙できます。

コードベースが grep しやすいのは、テキストがその構造について真実を語っているときです。ここでの制約（名前ごとに 1 つの形、再エクスポートなし、マージなし）はすべて、検索が手がかりではなく答えを返すためにあります。

ベンチマーク：準備中

この主張を測れる形にすると、精度になります。あるシンボルについて、普通の grep のヒットのうち本当に探していたものの割合はどれくらいか、エージェントが定義にたどり着くまでに何ステップかかるか、です。

Glyph はまだ実運用で使われていないので、下のグラフはプレースホルダです。測定できる実際のコードベースができたら、実際の数値で埋まります。

この効果は、規模と自律性が増すほど大きくなります。人間はコードベースの隠れ場所を覚えていきますが、何も知らずに始めるエージェントはそうではありません。grep しやすさがあるから、ツール（や新しいチームメンバー）は、リポジトリの実際の姿のとおりに読んで移動できます。

「lint ルールでオーバーロードやデコレータは禁止できる」

自分のリポジトリでなら、できます。ESLint は namespace を禁止でき、チームはオーバーロードを使わないと取り決められます。

それでも言語はそのすべてを許しているので、保証は設定がある間だけ続き、その設定が適用されるコードにしか及びません。依存パッケージ、生成されたファイル、他人のリポジトリに対する grep は、それを当てにできません。

Glyph ではこれらの構文が存在しないので、grep はどの Glyph ファイルでも同じように機能します。チームの誰も設定していないファイルでもです。

これがエージェントの側からどう見えるか（1 回の検索で定義や値へのすべての書き込みを見つけること）は、エージェント（や自分）は、何がどこで定義されているかを見つけられるか で説明しています。
