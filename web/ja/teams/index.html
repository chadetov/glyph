チーム向け

何を保証し、導入にどれだけのコストがかかり、どうやめられるか

Glyph は、strict な TypeScript のプロジェクトが受け入れてしまうケースのうち、具体的で検証済みのリストにあるものを拒否します。そして TypeScript にコンパイルされるので、使うのをやめてもその出力を手元に残せます。現在はアーリープレビューです。1.0 前で、主に 1 人がメンテナンスしており、週に何度もリリースしています。

何を保証するか#

Glyph が何を検出するかについての主張は、どれもリポジトリの catches/ ディレクトリにあるケースです。同じプログラムを TypeScript と Glyph で書いたもので、どちらも CI のゲートが実行します。チェック済みのケースは全部で 45 件です。TypeScript のケースが 37 件、Glyph には存在しない JavaScript の落とし穴が 5 件、Glyph がまだ塞いでいない穴が 3 件です。そのうち 28 件はビルド時に Glyph が拒否します（TypeScript のケース 23 件と落とし穴 5 件）。 拒否しないミスのうち、3 件は警告が出て、9 件は実行時の境界での検査で止まる不正なデータで、2 件は実行時に止まります。エージェントが書いたコードをレビューする人が最も頼りにするのは次のものです。

コード拒否されるもの
E0200ユニオンのケースを 1 つ漏らした match。そのため、ケースを追加すると変更が必要な箇所がすべて一覧される
E0013キャスト（as、as unknown as）。キャストも any も存在しない
E0204検査されないまま型付きの名前に代入される、パースした JSON
E0224キーが常に存在するかのように型付けされたマップからの読み取り
E0217捨てられた Result（警告。let _ = と書けば意図したものだと示せる）

検出できるもののページには、すべてのケースが TypeScript のコード、Glyph のコード、エラーとともに載っており、最も厳しく設定した typescript-eslint でも検出できたものはどれかも書かれています。

限界#

保証の対象は Glyph で書いたコードです。npm の依存パッケージの中で throw された例外は今も Result を迂回し、パッケージの .d.ts からインポートした型には実行時の検査がありません。Glyph の中では、未解決の穴 3 件が gap 番号とともにまだ検出できないものに載っており、完全な一覧は docs/dogfooding-gaps.md にあります。strict な TypeScript に zod、eslint、ts-pattern を加えた構成との比較は、その構成がまだ優れている点も含めて、ツールを揃えた TypeScript ではなぜ駄目かを見てください。

既存のアプリの中で導入する#

書き直しは不要です。間違えるわけにはいかない部分（モデル、権限、状態遷移、お金）を Glyph で書き、アプリの残りは TypeScript のまま、出力されたモジュールを普通のローカルファイルと同じようにインポートします。手順の説明では標準的な Vite の雛形を使っています：既存のアプリの中で Glyph を導入できるか

やめるときの手段#

glyph build は、tsc --strict を通る、モジュールごとに 1 ファイルの普通の TypeScript を書き出します。Glyph の使用をやめるなら、その出力をコミットして tsc で開発を続ければよいだけです。ライセンスは MIT または Apache-2.0 なので、いつでもフォークできます。TypeScript から来た人へでは、モジュールと出力されたファイルを並べて示しています。

バージョンの固定とアップグレード#

glyph init は package.json でコンパイラを ^ なしの正確なバージョンに固定するので、どのリリースもうっかりビルドに入り込むことはありません。残りは 3 つのコマンドで扱います。

意図してアップグレードする 
glyph doctor     # your version against the latest release; never fails CI for that
glyph upgrade    # moves the project's pin, runs npm install, links the notes
glyph --update   # moves the installed compiler itself

詳しくは Glyph の新しいリリースでビルドが壊れることはあるか にあります。

Breaking のリリースがたいてい意味すること#

たいていは、もともと間違っていたプログラムをコンパイラが拒否するようになったということです。0.1.159 は ids.forEach(async fn(id) { await save(id) }) を拒否しました。forEach はコールバックを待たないので、各 save はばらばらに走り、どれかの失敗は失われていました。0.1.162 は array.find(xs, f) ?? 0 を拒否しました。Option は null にならないので、デフォルト値は一度も使われず、値は Option そのものでした。ルールを厳しくするものもあります。0.1.160 からは、xs.push(4) のように配列をその場で変更する呼び出しは mut 文として書く必要があり、動いていたコードも書き方を変えることになりました (glyph fix が mut を挿入します)。

リリースがプロジェクトに入るのは、固定したバージョンを自分で動かしたときだけです。アップグレードでまだ直せないコードが拒否されたら、元のバージョンのままでいられます。公開済みのバージョンが取り下げられることはありません。最後のビルドが出力した TypeScript は tsc だけでコンパイルできるので、コンパイラがどうなっても使い続けられます。

リリースの頻度と Breaking の印#

バージョンのページには、0.1.0 から 0.1.198 までのすべてのリリース、計 197 件の項目があり、そのうち 71 件は 2026年11月1日 から 2026年11月26日 までに出たものです。前のバージョンが受け入れていたプログラムを拒否するリリースには Breaking の印が付きます。正しさに関する修正の多くはこの形で入ります。印が付いている項目は 73 件です。印は差分を読んで付けるのではなく、影響を受ける最小のプログラムを両方のバージョンで実行して付けています。0.1.99 より前のリリースはこの方法で確認していないので、印のない古いリリースは安全なのではなく、未確認ということです。

Breaking のリリースが実際にどれだけのコストになったか：最近のリリースノートにはそれぞれ、リポジトリのサンプルアプリを古いバージョンと新しいバージョンで実行したときに何が起きたかが書かれています。以下は最新の Breaking リリースのノートからの引用です。

  • 0.1.197: リリースノートには記載がありません。
  • 0.1.196: リリースノートには記載がありません。
  • 0.1.194: リリースノートには記載がありません。
  • 0.1.193: リリースノートには記載がありません。
  • 0.1.192: リリースノートには記載がありません。
  • 0.1.190: リリースノートには記載がありません。

サンプルアプリはプロジェクト自身のコードで、リリースごとにコンパイルが通るように保たれているので、新たに拒否されるようになった書き方は、あなたのコードよりも出てきにくいはずです。各ノートには拒否するようになった書き方が書かれているので、アップグレードの前に読んでください。

現状#

Glyph は 1.0 前です。1.0 までは、構文、標準ライブラリ、出力される TypeScript の形が変わる可能性があり、以前はコンパイルが通ったコードをリリースが拒否することもあります。何が変わりうるか、何を安定に保つかは docs/stability.md に書かれています。MAINTAINERS.md には、現在このプロジェクトは主に 1 人でメンテナンスされていると率直に書かれています。その人が離れた場合にどうなるか、どのように意思決定するか、セキュリティ上の問題をどう報告するかは「Glyph のメンテナー」にまとめています。

よくある反論への回答#

AI はあまり使っていません。それでも価値はありますか？

検査は誰がコードを書いても同じです。実行時の想定外が減り、差分が小さくなり、grep できるコードになります。

 すでに strict な TypeScript と lint を使っています。

それらの検査はどれも任意で、1 行で無効にできます。Glyph の検査はできません。

 エージェントは、ほとんど見たこともない言語を書けますか？

モデルが TypeScript について知っていることの大半はそのまま通用し、残りはコンパイラが教えてくれます。

 そもそも、なぜ TypeScript にコンパイルするのですか？

npm も React も Node もそこにあるからです。導入を 1 ファイルずつ進められるのもそのためです。

 障害が起きたとき、オンコール担当者には何が見えますか？

読める TypeScript、.glyph ファイルに戻れるソースマップ、そして変わらないエラーコードです。

 これが本当だと、どうしてわかるのですか？

このサイトの各主張をどう検証しているか、そして自分で再現する方法。
