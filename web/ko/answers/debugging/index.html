  4. 30디버깅과 운영

직접 소유하는 읽을 수 있는 TypeScript이고, 생성된 모든 파일 옆에 .glyph로 연결되는 소스 맵이 있습니다. 디버거, 번들러, 오류 추적기가 실행 중인 코드를 소스까지 추적하며, Glyph를 한 번도 본 적 없는 사람도 생성된 TS를 읽을 수 있습니다. 그보다 먼저, glyph build와 glyph run은 같은 트리에 대해 같은 진단을 보고하므로, 빠른 루프가 빌드라면 잡았을 문제를 숨길 수 없습니다. 둘 다 glyph run 경로에 있는 한계 두 가지를 아래에 밝혀 두었습니다.

이 페이지의 내용

  1. 읽을 수 있는 TypeScript
  2. 소스 맵
  3. 빌드 오류와 타입 오류
  4. glyph run 진단
  5. 두 가지 한계
  6. 현재 상태

1 · 생성된 TypeScript는 직접 읽을 수 있습니다

Glyph는 불투명한 런타임을 배포하지 않습니다. 여느 TS처럼 커밋하고 배포하는 평범하고 포맷된 TypeScript를 생성합니다.

그래서 최악의 경우(새벽 3시에 Glyph를 모르는 온콜 엔지니어)에도 읽는 것은 방언이 아니라 평범한 TypeScript입니다. 소스와 프로덕션 사이에 블랙박스가 없습니다.

2 · .glyph로 연결되는 소스 맵

생성된 모든 .ts 옆에는 표준 v3 소스 맵(.ts.map)이 함께 있고, sourceMappingURL 주석과 Glyph 소스가 포함되어 있습니다(sourcesContent).

dist/main.ts (끝부분) 
// ...emitted TypeScript...
//# sourceMappingURL=main.ts.map    // v3 map, .glyph embedded

소스 맵을 읽는 도구(Chrome DevTools, Node 디버거, Sentry 같은 오류 추적기, 번들러)라면 이를 따라가서 생성된 줄이 아니라 .glyph 줄을 보여 줍니다.

3 · 빌드 오류와 타입 오류는 이미 Glyph를 가리킵니다

glyph build가 tsc --strict를 실행하고 모든 tsc 오류를 .glyph 소스로 다시 매핑하므로(같은 캐럿, TypeScript 오류 코드 유지), 타입 오류가 프로덕션까지 가는 일은 드뭅니다.

그리고 glyph build --json은 CI나 도구가 처리할 수 있도록 모든 진단을 구조화된 JSON(코드, 심각도, 파일, 1부터 시작하는 줄/열, 도움말)으로 출력합니다.

자세히 캐럿이 놓이는 곳

캐럿은 tsc가 거부한 코드에 해당하는 가장 작은 Glyph 표현식에 놓입니다. 잘못된 인자는 그 인자에, JSX 이벤트 핸들러 안의 철자가 틀린 필드는 주변 return 전체가 아니라 그 멤버 접근에 밑줄이 그어집니다.

4 · glyph run도 같은 것을 알려 줍니다

하루 종일 입력하는 명령은 glyph run인데, 0.1.40까지는 빌드보다 조용했습니다. 이제는 같은 진단을 보고합니다. 지정한 파일과 그 형제 파일에 대한 경고까지 포함해, 프로그램 출력 뒤에 한 줄짜리 개수와 함께 보여 줍니다.

사용하지 않는 import. 그것을 쓸 코드보다 한 단계 먼저 추가함 
$ printf 'look\nquit\n' | glyph run adventure.glyph
...the game plays and exits 0...

[E0106] Warning: lint: unused import `math`
    ╭─[adventure:21:1]
    │
 21 │ import std/math
    │         ╰─────── unused import `math`
    │ Help: Remove the import. Nothing in this module references it.

glyph run: 0 error(s), 1 warning(s) in the source tree
자세히 실행 캐시

실행 캐시가 진단을 함께 저장하므로, 바뀌지 않은 소스를 두 번째로 실행해도 조용해지지 않고 첫 번째와 같은 내용을 말하며, 진단이 빠진 캐시 항목은 캐시 미스로 취급해 다시 빌드합니다.

이력 0.1.40 이전

디렉터리 전체를 컴파일하고, 보고서에서 생성된 파일 목록만 꺼내고, 진단은 버렸습니다. glyph build가 문제를 지적한 트리가 깔끔하게 실행되고 0으로 종료했습니다.

현재 한계 두 가지

  • glyph run 자체의 충돌 스택은 여전히 .ts 줄 번호를 보여 줍니다.glyph run은 tsx로 실행하는데, tsx는 자체 .ts→.js 변환에서 소스 맵을 이어 주지 않으므로 glyph run 중에 잡히지 않은 예외는 생성된 줄을 보고합니다. 이 스택을 다시 매핑하는 것은 후속 작업입니다.
  • 형제 모듈의 오류는 glyph run의 종료 코드를 바꾸지 않습니다.컴파일에 실패한 모듈은 import할 수 없고, 그 모듈을 import하지 않은 프로그램은 그대로 실행됩니다. 이제 오류는 보이지만, 프로세스는 여전히 main이 반환한 값으로 종료합니다.
자세히 프로덕션 스택, 그리고 종료 코드를 그대로 두는 이유

로컬 run 루프에서는 문제가 되지만, 실제 배포에서는 glyph build로 .ts를 만들고 평소의 툴체인으로 번들하며 .ts.map이 평소처럼 이어지므로, 실제로 호출을 받는 프로덕션 스택은 .glyph로 매핑됩니다.

0이 아닌 값으로 종료하게 만들면 지금 잘 실행되는 트리가 실패하게 되므로, 실수가 아니라 아직 내리지 않은 결정입니다. 트리 상태가 종료 코드를 결정하게 하려면 glyph build를 쓰세요.

현재 상태

지금 제공되는 것

  • 커밋되는 읽을 수 있는 TS.
  • 파일마다 v3 .ts.map.
  • .glyph로 다시 매핑되는 tsc 오류.
  • --json 진단.
  • glyph run은 캐시가 있을 때도 glyph build가 보고하는 것을 똑같이 보고합니다.
  • 배포 툴체인의 소스 맵 체인은 .glyph까지 닿습니다.

앞으로 할 것

  • glyph run 충돌 스택 자체를 다시 매핑하는 것(로컬 실행 루프에서도 .glyph 프레임이 보이도록).
  • 형제 모듈의 오류가 glyph run을 0이 아닌 값으로 종료하게 할지에 대한 결정.
  • LSP를 통한 더 풍부한 에디터 디버깅.
