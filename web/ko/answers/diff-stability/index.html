왜 중요한가

에이전트가 풀 리퀘스트를 열면 diff가 곧 리뷰입니다. 진짜 한 줄 수정이 200줄짜리 재포맷으로 도착하면 무엇이 실제로 바뀌었는지 아무도 볼 수 없고, 버그가 빠져나가는 곳이 바로 그 잡음입니다.

diff 안정성이란 diff가 변경을, 그리고 변경만을 보여 준다는 뜻입니다.

규칙 두 가지가 대부분의 일을 합니다. 각각을 리뷰하게 될 diff로 보여 드립니다.

후행 쉼표, 한 줄에 항목 하나

후행 쉼표는 필수이고, 한 줄에 들어가지 않는 목록은 다시 묶이지 않고 요소마다 한 줄로 쓰므로, 항목을 삽입하거나, 제거하거나, 재정렬해도 이웃은 흔들리지 않습니다.

레코드 필드, 매개변수, match arm, import도 마찬가지입니다.

기준값에는 비용이 있습니다. 이름을 바꿔서 호출이 100열을 넘으면 인자 목록 전체가 한 줄에 하나씩 펼쳐집니다.

정해진 레이아웃 하나

올바른 포맷은 glyph fmt가 만드는 단 하나입니다. 공백, 줄바꿈, 정렬은 에이전트가 “정리”할 수 있는 선택지가 아니므로, 의미 있는 편집이 재배치를 끌고 올 수 없습니다. 필드 하나의 타입을 바꾸면 그것이 diff의 전부입니다.

user.glyph: 필드 하나를 바꾸고, 한 줄을 리뷰 
 type User = {
   id: string,
-  age: string,
+  age: number,
   email: string,
 }

레이아웃이 고정되어 있으므로 같은 파일을 편집하는 서로 다른 두 에이전트가 바이트 단위로 같은 포맷을 만듭니다. 재배치 변동도, “내 포매터와 네 포매터” 잡음도 없고, git blame은 재포맷한 커밋이 아니라 줄을 실제로 바꾼 커밋을 가리킵니다.

레이아웃이 하나라면, 포매터가 주석을 옮기나요?

예전에는 옮겼고, 짚고 넘어갈 만한 버그였습니다. 지금의 규칙은 이렇습니다. 주석은 레코드 본문, 유니언 variant 목록, 배열이나 객체 리터럴, 인자나 매개변수 목록, match 안에서 원래 위에 쓰였던 항목 위에 다시 출력됩니다.

이력 주석이 떠내려간 방식과, 이를 드러낸 앱

Glyph에는 블록 주석도 문서 주석 문법도 없으므로, 레코드 필드, 유니언 variant, match arm을 설명하는 방법은 // 줄뿐입니다. 포매터는 대기 중인 주석을 선언과 문장 경계에서만 내보냈으므로, 구문 안에 쓴 주석이 다음 선언까지 내려가서 그것이 도착한 곳의 문서처럼 읽혔습니다. Glyph로 지뢰찾기를 만들면서 드러났습니다. 아래 두 선언은 실제 앱에서 가져왔고(주석은 맞게 줄임), 예전 포매터와 새 포매터로 실행한 결과입니다.

0.1.37: fmt 한 번 실행 
type Visibility =
  | Hidden
  | Flagged
  | Revealed

// Face down. Prints as `.`.
// Face down and marked by the player.
// Face up. `Cell.adjacent` is what gets printed.
type Cell = { mine: bool, adjacent: int, visibility: Visibility }
// Number of mined neighbours. Only meaningful
// once mines are placed.
variant 주석 세 개가 이제 레코드를 설명함
0.1.38: 같은 파일 
type Visibility =
  // Face down. Prints as `.`.
  | Hidden
  // Face down and marked by the player.
  | Flagged
  // Face up. `Cell.adjacent` is what gets printed.
  | Revealed

type Cell = {
  mine: bool,
  // Number of mined neighbours. Only meaningful
  // once mines are placed.
  adjacent: int,
  visibility: Visibility,
}
모든 주석이 설명하는 대상 위에 있음

그리고 내부에 주석이 있는 구문은 크기와 상관없이 항상 요소마다 한 줄인 형태를 쓰므로, 주석이 위에 놓일 항목이 생깁니다. 그래서 type Shape = { w: int, h: int }는 여전히 한 줄로 접히고, h에 주석을 다는 순간 레코드는 펼쳐진 채로 남습니다.

자세히 이것이 정확성 버그로 치는 이유

이것이 겉모양 문제가 아니라 정확성 버그인 이유: 아무것도 실패하지 않았습니다. 빌드는 0으로 종료했고, tsc는 통과했고, 망가진 출력 자체가 고정점이었으므로, CI의 glyph fmt --check는 주석이 이제 거짓을 말하는 파일에 대해 통과했습니다. Glyph가 없애려고 존재하는 것과 같은 종류의 실패이며, 다만 타입 시스템이 아니라 포매터에 있었을 뿐입니다.

glyph fmt가 빌드되는 프로그램을 깨뜨릴 수 있나요?

그럴 수 있었고, 한 경우는 아직 열려 있습니다. 프로그램이 살아남아야 하는 포매터는 없는 기능보다 나쁩니다. 이미 동작하던 코드를 망가뜨리기 때문입니다.

  • arm 본문이제 출력기는 맨 왼쪽 토큰이 블록으로 다시 파싱될 {인 arm 본문, 즉 빈 객체와 그 위에 만든 모든 것에 괄호를 씌웁니다(({}).size는 ({}.size)로 돌아옵니다).
  • 퍼저이제 퍼저가 포맷된 파일을 파싱해서 원본의 트리와 비교하므로, 파일의 의미를 바꾸는 레이아웃은 누군가 알아채기를 기다리지 않고 첫 실행에서 실패합니다.
이력 빌드가 멈춘 빈 레코드

고친 것부터 보겠습니다. “빈 레코드”를 뜻하는 arm은 true => ({})로 씁니다. arm 본문 위치는 문법에서 맨 앞의 {가 모호한 유일한 곳이고, 파서는 중괄호 바로 뒤에 key:나 ...를 요구해서 이를 해결합니다. 빈 객체에는 둘 다 없으므로, 포매터가 괄호를 빼고 true => {}로 다시 출력하면 arm이 빈 블록으로 돌아와 파일이 빌드되지 않았습니다. arm이 값을 만들지 않는다는 E0223이었습니다. 동작하는 코드에 포매터를 실행했더니 더 이상 컴파일되지 않는 코드가 나온 것입니다.

false => { a: "x" }처럼 이미 모호하지 않은 arm 본문은 그대로 두므로, 다른 곳에서 읽어야 할 새 구두점은 없습니다. fmt는 결과에 대해 고정점이고 생성된 TypeScript는 바뀌지 않습니다.

이력 0.1.138에서 더 고친 두 가지

0.1.138에서 두 가지를 더 고쳤습니다. 블록 안에서 (로 시작하는 줄은 윗줄에 이어지는데, 0.1.137까지 포매터는 load()? 다음의 .run()을 (load()?).run()으로 출력했으므로, let a = 1 뒤에서 포맷된 파일은 let a = 1(…).run()을 뜻했습니다. 이제는 load()?를 두고 다음 줄에 .run()을 들여 쓰며, e?(x), e?[0], e? ?를 괄호 없이 씁니다. 다른 하나는 유니언의 where 정제를 포매터가 빠뜨린 것으로, check가 거부하던 프로그램을 받아들이는 프로그램으로 바꿨습니다.

이 뒤에 있는 포맷 규칙과 그 규칙이 하는 거래는 diff 안정성 기둥 페이지에 있습니다.

현재 상태

지금 제공되는 것

  • 필수 후행 쉼표, 한 줄에 항목 하나인 목록, 그리고 왕복해도 같고 멱등인 glyph fmt의 정해진 레이아웃 하나, 에디터에서의 저장 시 포맷.
  • glyph fmt는 주석을 맞지 않는 곳으로 절대 옮기지 않습니다.
  • 주석은 원래 위에 쓰였던 항목 위에 유지됩니다
    자세히

    주석은 레코드, 리터럴, 인자 목록, match 안, 연산자의 피연산자 사이, 메서드 체인의 단계 사이를 포함해 원래 위에 쓰였던 항목 위에 유지되며, 이때 메서드 체인은 점을 앞에 두고 한 줄에 한 단계씩 씁니다.

한계와 다음 단계

  • 코드 줄 끝의 주석은 다음 항목의 윗줄로 옮겨집니다
    자세히

    주석은 항상 자기 줄에 출력되므로, 코드 줄 끝에 쓴 주석(w: int, // width in cells)은 다음 항목의 윗줄로 옮겨집니다. 더 이상 선언 경계를 넘지는 않지만 위치는 바뀝니다. 줄 끝에 유지하려면 출력기가 주석이 어느 줄을 공유하는지 추적해야 합니다.

  • 레이아웃에 놓을 곳이 없는 주석은 옮기지 않고 거부합니다E0500
    자세히

    인덱스 안, 체인 중간에서 호출 인자 뒤, !나 await 피연산자 앞처럼 레이아웃에 놓을 곳이 없는 주석은 더 이상 옮기지 않습니다. glyph fmt는 파일을 거부하고 그대로 두며 줄 번호와 주석을 둘 곳을 알려 주고, glyph check도 같은 내용을 경고 E0500으로 보고합니다.

  • JSX 속성 사이나 객체 패턴의 필드 사이의 주석도 거부되는데, 이는 한 줄에 하나인 레이아웃이라면 놓을 수 있는 곳이며 해당 레이아웃은 할 일 목록에 있습니다.
  • 출력기에는 아직 긴 메서드 체인이나 + 체인을 나누는 규칙이 없으므로, 너무 긴 체인은 가장 안쪽 인자 목록에서 나뉘는데, 이는 잘못된 위치입니다.
  • TypeScript에서 같은 편집과 비교하는 diff 크기 벤치마크도 만들고 있으므로, 이 기둥은 확인할 수 있는 숫자가 될 것입니다.

이 페이지의 코드 예제는 빌드할 때마다 Glyph 0.1.153으로 검사합니다. 마지막 변경: 2026년 11월 21일.
