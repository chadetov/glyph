여섯 가지 편집에 대해서는 그렇습니다. glyph_impact는 바꾸려는 선언과 변경 자체(이름 바꾸기, variant 제거, 매개변수 타입 변경, 인자 개수 변경, 삭제)를 받아, 정해진 목록에서 고른 위치마다 하나의 판정을, 다른 판정이 아니라 그 판정인 이유와 함께 답합니다.

왜 중요한가#

함수 이름을 바꾸거나, 유니언을 넓히거나, 매개변수가 받는 것을 바꿀 때는 이전 이름을 grep하고 모든 호출을 찾았기를 바라거나, 편집한 뒤 컴파일러가 하는 말을 읽습니다. 어느 방법도 어떤 위치가 계속 컴파일되면서 조용히 틀리게 될지는 알려 주지 않습니다. catch-all arm이 있는 match는 variant를 추가해도 실패하지 않고, 새 case를 아무도 고르지 않은 곳으로 보내기 시작할 뿐입니다. 그런 위치는 빌드에 절대 나타나지 않습니다. glyph_impact는 컴파일러가 실행하는 것과 같은 분석으로 편집 전에 답합니다.

돌아오는 것#

요청은 엔티티를 module::name 식별자로, 변경을 정해진 목록에서 지정합니다: add_variant, remove_variant, rename, change_arity, change_signature_type, remove. 판정은 편집에 대한 사실이므로 변경은 필수입니다. 편집을 지정하지 않으면 모든 위치가 결과가 아니라 그저 참조로 돌아올 것입니다. 답에는 엔티티, 변경, 그리고 impact 목록이 있습니다. 위치마다 항목 하나이며, 각 항목에는 그 위치가 속한 선언, relation, verdict, because, 그리고 컴파일러가 내는 진단 코드가 정확히 하나일 때 그 코드가 들어 있습니다. 판정은 정해진 목록이고 각각 한 가지를 뜻합니다. WILL_FAIL(컴파일러가 그 위치가 컴파일되지 않게 된다는 것을 증명할 수 있음), ABSORBS(변경이 여기서 조용히 흡수된다는 것을 증명할 수 있음), SAFE(그 위치가 올바르게 유지된다는 것을 증명할 수 있음), UNDETERMINED(그 위치를 살펴봤지만 결과를 확정할 수 없음), NOT_INDEXED(이런 모양의 위치에 대해서는 애초에 물을 수 없는 질문임)입니다.

직접 보기#

어떤 모듈이 label(s: string) -> number를 선언합니다. 호출자 세 곳이 여기에 닿습니다. 하나는 문자열 리터럴을 넘기고, 하나는 다른 모듈에서 import한 string 별칭 타입의 값을 넘기고, 하나는 label을 값으로 읽기만 하고 호출하지 않습니다. 각각에 change_signature_type이 어떤 영향을 주는지 물으면 세 가지 다른 판정이 나옵니다. 세 가지 다른 주장이기 때문입니다.

요청 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_impact",
    "arguments": {
      "entity": "lib::label",
      "change": { "kind": "change_signature_type" }
    }
  }
}
결과, 세 위치만 남기고 줄임 
{
  "entity": "lib::label",
  "impact": [
    {
      "entity": "literal::probe",
      "verdict": "WILL_FAIL",
      "diagnostic": "E0211",
      "because": "every argument at this site is paired with
        a parameter the relation reads in full, so a
        replacement parameter type any of those pairings does
        not accept is E0211 here. The pairings: argument 1
        (`\"x\"`, `\"x\"`) against parameter `s: string`: ..."
    },
    {
      "entity": "imported::probe",
      "verdict": "UNDETERMINED",
      "diagnostic": null,
      "because": "argument 1 (`c`, `Cell`) against parameter
        `s: string`: `Cell` is declared in another module as
        an alias for a primitive, and the checker compares an
        imported declaration only when the declaration at the
        end of its chain of names is a tagged union or a
        record (G215, G226), so a replacement is compared
        against nothing here and only `tsc` on a full `glyph
        build` would see a mismatch"
    },
    {
      "entity": "reader::sizer",
      "verdict": "NOT_INDEXED",
      "diagnostic": null,
      "because": "this site reads the name rather than
        applying it, so no argument is paired with a
        parameter here, and Glyph does not compare a
        function value's parameter types against the type
        its use context expects"
    }
  ]
}

같은 편집, 세 위치, 세 판정이며, 각각의 because는 분류 레이블이 아니라 컴파일러가 실제로 만드는 문장입니다. 이는 이 변경에 대한 컴파일러 자체 테스트(glyph-cli/tests/agent_loop.rs의 a_signature_type_change_gets_one_verdict_per_kind_of_site)를 그대로 반영합니다. 테스트는 이후에 실제로 편집하고, WILL_FAIL이라고 한 곳에 정확히 E0211이 나는지, 나머지 두 곳에서는 컴파일러가 조용한지 확인합니다.

실제 애플리케이션에서#

이 저장소에 있는 파일 열한 개짜리 CSV 쿼리 엔진 examples/apps/csvql에는 현재 variant 네 개를 가진 태그 유니언 Value가 하나 있습니다. 다섯 번째(Blob)를 추가하면 어떻게 되는지 glyph_impact에 물으면 파일 4개에 걸쳐 match 위치 10곳을 찾습니다. 8곳은 컴파일에 실패하고, 2곳에는 새 variant를 조용히 흡수할 catch-all arm이 있습니다. 실제로 variant를 추가하면 컴파일러는 정확히 그 8곳에서 E0200 실패 8개를 보고하고, ABSORBS 2곳에 대해서는 전후 모두 아무 말도 하지 않습니다. 도구 없이 하게 될 방법인, 같은 앱에서 catch-all arm을 텍스트로 검색하면 같은 실제 위치 2곳이 결과 20개 속에 묻혀 나오고(정밀도 0.10), 실패하는 8곳에 대해서는 아무것도 알려 주지 않습니다. match가 어떤 타입을 검사하는지 전혀 모르기 때문입니다.

현재 상태#

지금 제공되는 것

정해진 변경 종류 여섯 가지(add_variant, remove_variant, rename, change_arity, change_signature_type, remove)와 정해진 판정 다섯 가지, 그리고 영향받는 위치마다 이유와 진단 코드를 담은 항목 하나. change_signature_type은 호출 인자마다 검사기 자체의 비교 규칙으로 판정하며, 위치의 판정은 인자 중 가장 약한 것입니다. JSX 요소는 변환된 호출로 판정합니다. <Card title="x" />는 Card에 넘기는 props 레코드 하나이고, 각 속성은 검사 대상 필드와 함께 같은 타입의 호출 인자가 받을 판정으로 나열됩니다. 커버리지(검색이 읽을 수 있었던 것과 없었던 것)는 답 전체에 대해 한 번이 아니라 검색마다 밝히고, 모든 노드에는 Glyph 소스, extern_ts 탈출구, 불투명한 .d.ts 중 어디서 왔는지가 표시됩니다.

한계

깊이는 한 단계에서 정확하고 그 너머는 비어 있습니다. Glyph는 선언의 타입을 본문에서 추론하지 않으므로 피호출자의 타입이 호출자의 시그니처에 닿을 수 없고, X에 대한 변경은 X를 언급하는 표현식만 무효화할 수 있습니다. 깊이 2를 요청하면 대신 정확한 질문을 짚는 next_query와 함께 답이 돌아옵니다. 두 번째 단계에 필요한 것은 누군가 첫 번째 위치에 하는 수정인데, 그 수정은 아직 존재하지 않기 때문입니다. UNDETERMINED와 NOT_INDEXED는 다른 주장입니다. 검사기가 타입을 갖고 있지 않은 인자나, 어떤 규칙도 읽지 않는 필드와 짝지어진 레코드는 UNDETERMINED(살펴봤지만 결정할 수 없음)이고, 호출하지 않고 값으로 읽은 함수는 NOT_INDEXED(거기서는 애초에 물을 수 없는 질문)입니다. 주의해서 볼 것은 ABSORBS입니다. 그 위치는 계속 컴파일되면서도 틀렸다고 증명되며, 통과한 빌드는 이를 결코 보여 주지 않습니다.

이 페이지의 코드 예제는 빌드할 때마다 Glyph 0.1.149으로 검사합니다. 마지막 변경: 2026년 11월 20일.
