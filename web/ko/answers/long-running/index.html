서버를 작성할 수 있습니다. main은 준비를 마치고 반환하며, 소켓과 타이머가 아직 대기 중인 동안 프로세스는 살아 있습니다. Node와 같은 규칙입니다. 0.1.63까지는 그렇지 않았습니다. 러너가 main이 반환하는 순간 프로세스를 종료했으므로, 서버는 포트를 바인딩하고 같은 틱에 죽었습니다.

  1. 왜 중요한가
  2. main이 반환한 뒤
  3. 채팅 서버
  4. 오래 실행되는 클라이언트
  5. 현재 상태

왜 중요한가

스크립트를 실행할 수 있는 언어와 서비스를 실행할 수 있는 언어의 차이가 여기 있습니다. 서버, 파일 감시기, 게이트웨이 연결을 유지하는 봇, 작업 실행기는 모두 main 안에서 끝나지 않습니다. 핸들러를 설정하고 프로세스를 이벤트에 넘깁니다.

이력 0.1.63 이전에 실패하던 방식

예전 동작은 가능한 최악의 방식, 즉 조용히 실패했습니다. glyph run app.glyph --serve 4100은 listen 콜백 안의 줄조차 출력하지 않고 0으로 종료했습니다. 소스에는 잘못된 것이 보이지 않았고 타입 검사도 통과했습니다. 이 상황을 만난 에이전트는 보고할 오류도, 무언가 실패했다고 생각할 이유도 없습니다.

main이 반환한 뒤

알아 둘 것이 두 가지 있습니다. return 0은 첫 클라이언트가 연결되기도 전에 실행됩니다. 이는 프로세스가 결국 종료할 때의 코드이지, 언제 종료하는지에 대한 문장이 아닙니다.

그리고 main이 반환한 뒤에 실패하는 것은 직접 종료 코드를 설정해야 합니다. main의 반환값은 이미 쓰였기 때문입니다. error 핸들러가 그 용도입니다. 핸들러가 없으면 포트를 바인딩하지 못한 서버는 이벤트 루프를 비우고 0으로 종료하며 성공을 보고합니다.

자세히 net import의 타입

net은 Node 내장 모듈이므로 평범한 import이지만, 컴파일러가 기본 타입을 제공하는 여섯 개(fs, http, path, os, crypto, url)에는 속하지 않습니다. @types/node를 설치하면 빌드가 이를 우선 사용하고, 아니면 소스 옆의 .types/net.d.ts에 선언을 두면 됩니다. 채팅 앱은 후자를 써서 의존성이 전혀 없습니다.

실제 사례

examples/apps/chat은 여러 TCP 클라이언트를 동시에 유지하는 채팅 서버입니다. 네트워크를 건드리지 않는 부분은 분리되어 있고 테스트할 수 있습니다. 줄 재조립, 라우팅, 방 엔진은 @example로 검사되는 순수 함수이고, 소켓과 통신하는 파일은 하나입니다.

동시에 연결된 클라이언트 세 개 
alice> /join #general
bob>   /join #general
carol> /join #random
alice> hello everyone

alice sees:  1  #general <alice> hello everyone
bob sees:    1  #general <alice> hello everyone
carol sees:  (nothing: she is in #random)

반대 방향: 오래 실행되는 클라이언트

봇은 같은 모양을 바깥으로 향하게 한 것입니다. examples/apps/discord는 Discord 게이트웨이 클라이언트입니다. WebSocket으로 연결하고, 식별하고, 서버가 지정한 간격으로 heartbeat를 보내고, 연결이 끊겼을 때 처음부터 다시 시작하지 않고 재개할 수 있도록 시퀀스 번호를 추적하고, 연결이 열려 있지만 죽은 상태를 알아채며, 재연결 사이에 대기 시간을 늘립니다.

따라 할 만한 부분은 로직이 있는 위치입니다. RECONNECT, 놓친 heartbeat, 거부된 토큰에 대해 무엇을 할지 결정하는 것은 세션과 이벤트 하나를 새 세션과 액션 목록으로 바꾸는 순수 함수입니다. 모듈 하나가 그 액션을 실제 소켓에서 수행합니다.

그래서 올바르게 만들기 가장 어려운 재연결 로직을 네트워크 케이블을 뽑는 대신 @example로 검사합니다.

이력 버그 세 개, mock 두 개

이 세 예제는 모두 먼저 코드에 있었던 버그입니다. 모의 게이트웨이를 만들어 봇을 연결해 보니 그중 하나가 잡혔습니다. 나머지 둘은 클라이언트가 아니라 Discord 문서를 보고 작성한 두 번째 모의 게이트웨이가 잡았습니다. 이 모의 게이트웨이는 협조적인 모의 객체가 절대 보내지 않는 것들을 보냅니다. 요청하지 않은 heartbeat 요청, 그리고 "토큰이 틀렸으니 그만 요청하라"는 뜻의 종료 코드입니다. 클라이언트 작성자가 만든 모의 객체는 작성자가 읽은 프로토콜 부분만 테스트합니다.

현재 상태

지금 제공되는 것

  • main에서 반환하면 프로세스를 멈추지 않고 종료 코드를 설정하므로, 서버, 감시기, 이벤트 루프가 실행됩니다.
  • 계산만 하는 프로그램은 여전히 main이 반환하는 순간 같은 코드로 종료하므로, 짧은 프로그램에 대해서는 바뀐 것이 없습니다.
  • net 같은 Node 내장 모듈은 평범한 import이고, 준비 중에 던진 예외는 여전히 프로세스를 종료합니다
    자세히

    net 같은 Node 내장 모듈은 평범한 import이고, 준비 중에 예외를 던지는 프로그램은 여전히 종료되는데, 이제는 진단이 종료 때문에 잘릴 수도 있는 대신 파이프로 연결된 stderr에 도달한 뒤에 종료합니다.

  • std/timers는 작업을 예약하고(after, every, cancel, unref) std/websocket은 연결을 열므로, 둘 다 직접 작성한 선언이 필요 없습니다.

개선 중

  • main이 반환한 뒤 바인딩에 실패한 리스너는 프로그램이 따로 말하지 않으면 0으로 종료합니다
    자세히

    main이 반환한 뒤 바인딩에 실패한 리스너는 프로그램이 따로 말하지 않으면 0으로 종료합니다. process.set_exit_code(1)은 진행 중인 작업을 중단하지 않고 실패를 기록하고, process.exit(1)은 즉시 멈춥니다.

  • 이를 잊었다고 컴파일러가 경고해 주지는 아직 못합니다.
  • 그리고 함수가 반환하지 않는다는 것을 적을 방법이 아직 없으므로, 서버의 main에는 도달하지 않는 return 0이 남아 있습니다.
