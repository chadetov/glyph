glyph lsp는 stdio로 Language Server Protocol을 주고받으므로, LSP 클라이언트가 있는 에디터라면 진단, hover 타입, 정의로 이동, 자동 완성, 저장 시 포맷을 쓸 수 있습니다. VS Code 확장은 저장소에 있지만 아직 Marketplace에는 없으므로 소스에서 빌드해야 합니다. 모든 오류에는 고정된 코드, 수정 방법, 이유가 있습니다.

왜 중요한가

에디터가 이해하지 못하는 언어를 편집하는 것은 뒷걸음질처럼 느껴지고, 초기에는 타당한 불만이었습니다. 이제는 아닙니다. 에디터에서 요즘 기대하는 편의 기능을 쓸 수 있고, 오류는 거부만 하는 것이 아니라 가르치도록 작성되어 있습니다.

진짜 LSP인가요, 아니면 VS Code 플러그인일 뿐인가요?

진짜입니다. 컴파일러에는 glyph lsp로 실행하는 언어 서버가 포함되어 있고, stdio로 Language Server Protocol(모든 LSP 클라이언트가 이해하는 표준 JSON-RPC 전송)을 주고받습니다.

함께 제공되는 VS Code 확장은 그 위의 얇은 클라이언트일 뿐이며, VS Code에 특화된 것은 없습니다. Neovim, Helix, Zed, Emacs(eglot) 등 LSP를 지원하는 어떤 에디터든 glyph lsp를 가리키게 하면 똑같이 동작합니다.

이미 설치한 바이너리(npx @glyphlang/glyph lsp)와 같으므로 따로 받을 서버가 없습니다.

서버가 구현하는 것

서버는 에디터에 필요한 것을 구현합니다. 아래의 고정된 코드를 가진 실시간 진단, hover 타입, 정의로 이동(이름 import를 통해 모듈 간에도 동작하지만, 네임스페이스를 통한 ui.Button은 아직 답하지 않습니다), 자동 완성, 개요와 심볼 검색을 위한 문서 및 워크스페이스 심볼, 워크스페이스 전체의 참조 찾기, 이름 바꾸기, 그리고 저장 시 포맷을 위한 정해진 glyph fmt 레이아웃 포맷입니다.

이름 바꾸기는 완전합니다. 모듈 수준 선언의 이름을 바꾸면 워크스페이스 전체에서 정의, 모든 참조, 그것을 import하는 각 모듈의 import 바인딩을 수정하며, 무엇이든 건드리기 전에 새 이름이 키워드가 아닌 올바른 식별자인지 확인합니다.

알아 둘 한계가 두 가지 있습니다. 파일 간 인덱스는 캐시하지 않고 요청마다 다시 만들며(일반적인 프로젝트에는 문제없고, 나중에 빠르게 할 만합니다), 현재 파싱되지 않는 파일은 건너뛰므로 이름 바꾸기가 그 자체로 망가진 파일 안의 참조에는 닿지 않습니다.

오류 메시지

에이전트와 처음 쓰는 사람이 가장 많이 걸려 넘어지는 곳에서 메시지를 다듬었습니다. if를 쓰면 일반적인 “unexpected token” 대신 match를 안내하고, 잘못된 인자 개수, 비망라적 match, 잘못 쓴 variant는 각각 코드가 붙은 고칠 수 있는 오류를 냅니다.

TypeScript 백엔드만 잡을 수 있는 타입 오류는 예전에는 생성된 .ts를 가리켰습니다. 이제는 .glyph로 다시 매핑되므로(같은 ariadne 캐럿, 같은 고정된 코드), tsc 오류도 Glyph 자체 오류처럼 읽힙니다.

디버깅

생성된 TypeScript를 Node 인스펙터, 브라우저 개발자 도구, IDE의 JS/TS 디버거처럼 이미 쓰는 도구로 디버깅합니다.

모든 빌드는 각 .ts 옆에 표준 v3 소스 맵(Glyph 소스 포함)을 두므로, 맵을 따라가는 디버거나 번들러는 .glyph 줄 번호로 돌아갑니다.

아직 다루지 않는 것이 하나 있습니다. glyph run 자체의 충돌 스택은 여전히 .ts 줄을 출력합니다. tsx가 변환 과정에서 맵을 이어 주지 않기 때문입니다. 이 스택을 다시 매핑하는 것이 다음 작업입니다.

실행하지 않고 “컴파일되나?” 묻기

glyph check path.glyph는 파일 하나나 디렉터리 전체를 타입 검사하고 종료합니다. 트리에 아무것도 쓰지 않으며, 이는 glyph run이 약속할 수 없었고 glyph build는 아예 하지 않던 것입니다(디렉터리가 아닌 것은 거부했습니다).

--no-tsc--json--no-test
자세히 무엇을 실행하는가, 그리고 플래그

생성된 TypeScript에 대한 tsc --strict를 포함해 빌드와 같은 파이프라인을 실행하며, 출력은 끝날 때 지우는 임시 디렉터리에 둡니다. 빠른 답이 필요하면 --no-tsc로 Glyph 단계 후에 멈추고, --json은 에이전트에게 glyph build --json과 같은 진단 형식을 줍니다. 파일은 자기 디렉터리 맥락에서 검사되므로, 망가진 형제 파일이 있으면 검사가 실패합니다. @example과 @doc @run 테스트도 glyph build와 같은 관문으로 여기서 실행되므로, 빌드라면 실패할 트리를 check가 깨끗하다고 보고할 수 없습니다. 아무것도 실행하지 않는 답을 원하면 --no-test로 건너뜁니다.

출력도 거짓말하지 않습니다

이제 요약은 빌드를 실패시킬 수 있는 모든 단계가 끝난 뒤에 출력되므로, 실패한 빌드가 통과 줄을 보여 주는 일은 없습니다.

이력 너무 일찍 나오던 요약

실패한 빌드가 예전에는 “no diagnostics”로 시작하고 그 아래에 tsc 오류를 출력했습니다. Glyph 단계 요약이 TypeScript 단계가 실행되기 전에 쓰였기 때문입니다.

같은 작업에서 glyph run app.glyph --min -12.50도 동작하게 되었습니다. 예전에는 앞의 하이픈 때문에 main이 보기도 전에 clap이 인자를 거부했습니다.

glyph가 가진 플래그는 여전히 glyph에 바인딩되므로, 그중 하나와 겹치는 프로그램 플래그 앞에는 --를 붙이세요.

그리고 루프 안의 에이전트를 위해

glyph build --json은 모든 진단을 구조화된 JSON으로 출력합니다. 고정된 코드, 심각도, 메시지, 파일, 1부터 시작하는 줄/열 범위, 그리고 도움말과 참고 사항이 있으며, Glyph 소스로 매핑된 tsc 오류도 포함됩니다. 에이전트는 터미널 텍스트를 긁어 오지 않고 이를 바로 읽고 처리합니다.

대화형 에이전트를 위한 glyph mcp

대화형 에이전트에게는 일괄 진단 이상의 것이 있습니다. glyph mcp는 stdio로 Model Context Protocol 서버를 실행하고(같은 바이너리, 에디터가 쓰는 것과 같은 분석), 언어 서버의 쿼리를 MCP 도구로 제공합니다. 에이전트는 전체 빌드를 실행하거나 모든 파일을 읽지 않고도 파일의 진단, 위치의 타입, 이름이 정의된 곳(import를 따라감), 프로젝트 전체에서 심볼에 대한 모든 참조, 또는 심볼 검색을 요청할 수 있습니다.

두 번째 구현이 아니라 같은 순수 분석 계층 위의 얇은 어댑터이므로, 컴파일러와 에디터가 보는 것과 어긋날 수 없습니다.

모든 것이 강한 오류는 아닙니다

Glyph에는 빌드를 실패시키지 않고 불필요한 것을 표시하는 경고 단계가 있습니다. 사용하지 않는 import(E0106), 사용하지 않는 let(E0107, _로 시작하는 이름은 제외), 그리고 return/break/continue 뒤의 도달할 수 없는 코드(E0108)입니다.

E0106E0107E0108

이 경고들은 모듈을 정직하게 유지합니다. 죽은 import는 코드에 실제로는 없는 의존성을 찾아 헤매게 만드는, 바로 그런 검색 잡음입니다. 경고는 같은 렌더링 출력과 --json 출력에 심각도와 함께 나타나며, TypeScript는 그대로 생성됩니다.

현재 상태

지금 제공되는 것

  • 모듈 경계를 넘어 답하는, 어떤 에디터에서든 쓰는 언어 서버0.1.124부터
    자세히

    구문 강조, 진단, hover, 정의로 이동, 자동 완성, 심볼, 워크스페이스 전체의 참조 찾기와 이름 바꾸기, 저장 시 포맷을 갖춘 언어 서버(stdio로 동작하는 glyph lsp, 어떤 에디터든 가능, VS Code 확장 포함). 0.1.124부터 모듈 경계를 넘어 답합니다. 서버는 프로젝트마다 디스크의 파일 위에 열린 버퍼를 겹친 데이터베이스 하나를 유지하므로, import한 함수나 import한 레코드의 필드에 hover하면 glyph query hover와 같은 답을 주고, 한 파일의 저장하지 않은 편집이 다른 파일에서 보이며, 키 입력 하나의 비용은 단일 파일일 때보다 1~9퍼센트 더 듭니다.

  • 도구 열한 개를 갖춘 glyph mcp Model Context Protocol 서버
    자세히

    도구 열한 개(에디터의 쿼리에 glyph_symbol, glyph_impact, glyph_assignable, glyph_dependencies, glyph_exports를 더한 것)를 갖춘 glyph mcp Model Context Protocol 서버가 있고, 각 도구에는 MCP 클라이언트가 없는 에이전트를 위해 같은 JSON을 출력하는 glyph query 동사가 있습니다.

  • 고정된 오류 코드, glyph --explain, .glyph 소스로 매핑되는 tsc 백엔드 오류, 경고 단계(사용하지 않는 import/바인딩, 도달할 수 없는 코드), --json 구조화 진단.
  • glyph check [path]는 실행하거나 출력을 쓰지 않고 파일 하나나 트리를 타입 검사합니다.
  • glyph fmt --check는 CI에서 포맷을 검사합니다. 아무것도 쓰지 않고, 파일이 정해진 레이아웃이 아니면 0이 아닌 값으로 종료합니다.

앞으로 할 것

  • 요청마다 다시 만드는 대신 파일 간 인덱스를 캐시하는 것(큰 트리에서 속도 향상).
  • glyph run 자체의 충돌 스택을 다시 매핑하는 것. tsx가 변환 과정에서 생성된 맵을 이어 주지 않으므로, 그 스택은 여전히 .glyph가 아니라 생성된 .ts를 가리킵니다.
