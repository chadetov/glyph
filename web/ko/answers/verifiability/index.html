왜 중요한가

에이전트는 보통 코드를 요란하게 깨뜨리지 않습니다. 자신 있게 깨뜨립니다. 상태를 추가하거나, 분기를 빠뜨리거나, 필드 이름을 바꾸고, 모든 것이 여전히 타입 검사를 통과하며, 버그는 프로덕션에서 드러납니다.

비용이 큰 실패는 컴파일되었는데 틀린 것입니다. Glyph는 “아마 처리했을 것”을 “처리했다는 것을 컴파일러가 증명함”으로 바꿔 그 틈을 막습니다.

  • 봉인된 유니언태그 유니언은 봉인되어 있으므로 match는 모든 case를 다뤄야 합니다.
  • 값으로서의 오류오류는 사라지는 예외가 아니라 꺼내 확인해야 하는 값입니다.
  • 검사되는 경계그리고 모든 타입은 런타임 디스크립터를 가지므로, 경계를 넘어오는 데이터는 그 모양에 맞는지 검사됩니다.

버려진 오류는 경고입니다

오류도 마찬가지입니다. Result<T, E>를 반환하는 함수는 match로 처리하거나 ?로 전달하도록 되어 있습니다(컴파일러는 오류 타입이 맞는지 검사합니다). 그리고 Result를 버리면(문장으로 호출하고 반환값을 무시하면) Glyph가 경고합니다(E0217). 버려진 오류는 삼켜진 실패이기 때문입니다.

glyph check --no-tsc, 0.1.149 (발췌) 
13 │   save("a")
[E0217] Warning: typecheck: this `Result` is discarded; its `Err` case is silently ignored
    │ Help: Handle it with `match`, propagate it with `?`, or bind it (`let _ = ...`) to say the discard is intentional.

경고는 let _ = ...로 의도적으로만 끌 수 있고, 실수로 꺼지는 일은 없습니다.

표준 라이브러리의 유니언도 봉인되어 있습니다

표준 라이브러리가 소유한 유니언에도 같은 기준이 적용됩니다. fs.ErrorKind는 여섯 가지 종류로 된 닫힌 집합이고 검사기가 그 모양을 알기 때문에, 파일 시스템 오류에 대한 match e.kind에는 else arm이 필요 없고, 종류 하나를 빠뜨리면 E0200으로 실패합니다.

E0200 빠진 종류E0210 알 수 없는 필드E0218 else 필요
자세히 필드 오타, 반환 타입, 숫자와 문자열 match

e.mesage는 tsc가 나중에 잡는 것이 아니라 E0210입니다. 반환 타입도 전달됩니다. string.split(text, ",")는 Array<string>이므로, for i, part in string.split(text, ",")는 타입 없는 반복 대상에서 얻게 되는 문자열 키가 아니라 숫자로 i를 바인딩합니다.

망라성은 유니언만을 위한 것이 아닙니다. 리터럴 arm만 있는 number나 string에 대한 match는 끝없는 정의역을 다 다룰 수 없으므로, Glyph는 다루지 않은 값이 런타임 예외로 흘러가게 두지 않고 else를 요구합니다(E0218).

규칙은 어디서나 같습니다. case 하나를 고려하지 않은 match는 컴파일되지 않습니다.

철자가 틀린 arm은 catch-all이 아니라 빠진 곳입니다

오타가 빠진 곳을 조용히 덮을 수도 없습니다. 대문자로 시작하는 arm 머리는 새 바인딩이 아니라 variant에 대한 참조입니다.

status.glyph: 철자가 틀린 arm은 catch-all이 아니라 빠진 곳 
fn label(s: Status) -> string {
  return match s {
    Loadign => "…",        // typo for Loading, read as a variant, not a binding
    Ready => "done",
    Failed(msg) => msg,
  }
}
glyph build 
[E0220] `Loadign` is not a variant of `Status`; did you mean `Loading`?
   ╰─ a lowercase name would be a binding; a PascalCase name is read as a variant
[E0200] non-exhaustive match on `Status`: missing variant `Loading`
이력 예전 Glyph가 오타를 처리한 방식

대문자로 시작하는 arm 머리는 새 바인딩이 아니라 variant에 대한 참조입니다. 예전 Glyph는 Loading을 Loadign으로 잘못 쓰면 그 오타를 모든 값을 바인딩하는 catch-all로 읽어서 match가 완전한 것처럼 보이게 했습니다. 이제 머리는 match 대상 유니언의 실제 variant를 가리켜야 합니다. 그렇지 않으면 빌드가 E0220으로 멈추고 가장 가까운 실제 이름을 가리키며, 실제로 빠뜨린 variant도 바로 옆에 E0200으로 나타납니다.

payload 안의 variant

variant가 다른 variant의 payload인 한 단계 아래에서도 같은 해석이 적용됩니다. 이제 arm은 바깥 variant가 무엇이든 payload 자신의 태그로 분기합니다.

repl.glyph: 안쪽 arm은 payload를 바인딩하지 않고 검사함 
fn step(z: Zipper, line: string) -> Zipper {
  return match parse_command(line) {
    Err(Blank) => z,                          // a comment or an empty line
    Err(e) => { io.println(explain(e)) z },   // every other parse error
    Ok(command) => execute(z, command),
  }
}
E0305 중복된 case 레이블
이력 0.1.93 이전의 죽은 arm과 E0305 방어

Err(e) 옆의 Err(Blank)는 "빈 줄은 무시하고 다른 모든 파싱 오류는 출력"으로 읽히는데, 0.1.93까지는 바깥 태그에 대한 case "Err": 레이블 두 개로 컴파일되었고, 첫 번째가 payload 전체를 Blank라는 이름으로 바인딩했습니다. 모든 오류가 첫 번째 arm으로 갔고 두 번째는 죽은 코드였는데, 아무것도 이를 알려 주지 않았습니다. Glyph는 진단을 내지 않았고 tsc --strict는 중복된 case 레이블을 받아들입니다. 이제 arm은 바깥 variant가 무엇이든 payload 자신의 태그로 분기하고, 컴파일러는 타입 검사기와 같은 방식으로 이름을 읽습니다. payload 유니언의 variant 목록이 결정하고, 그 목록에 닿을 수 없을 때만 이름의 모양이 결정합니다. 같은 파일에 선언된 유니언이라면 대소문자는 더 이상 상관없습니다. 다른 모듈에서 import한 유니언은 현재 variant 목록에 닿을 수 없으므로, 대문자 variant는 분기하고 소문자 variant는 빌드를 멈춥니다.

빌드가 멈추는 것은 이제 switch가 보호되기 때문입니다. 같은 case 레이블을 쓰게 되는 두 arm은 두 번째 레이블이 절대 실행되지 않는 switch가 아니라 E0305입니다. 이 덕분에 이 종류의 문제가 조용하지 않고 요란해집니다. 같은 태그를 두 번 사용하는 변환은 런타임에 엉뚱한 arm을 고르는 대신 빌드를 실패시킵니다.

import 표기 방식이 검사를 끄는 일은 없습니다

유니언이 어떻게 스코프에 들어왔는지는 이 모든 것을 바꾸지 않습니다. Glyph에서는 variant arm을 두 가지 방식으로 쓸 수 있고, 둘 다 똑같이 검사됩니다. import model { Cond, Yes, No }와 그냥 쓰는 arm, 또는 import model(또는 import model as m)과 model.Yes(_)입니다.

interp.glyph: import 목록은 사라졌지만 match는 여전히 검사됨 
import model { Action, All, Any, AtLeast, Clear, Condition, Context, Counter,
               Equals, Flag, FlagSet, Increment, Not, Set, Slot, Text }
import model
import std/result

pub fn evaluate(ctx: model.Context, c: model.Condition) -> result.Result<bool, SlotError> {
  return match c {
    model.Equals({ key, value }) => result.Ok(read_text(ctx, key, "equals")? == value),
    model.AtLeast({ key, least }) => result.Ok(read_count(ctx, key, "at-least")? >= least),
    model.FlagSet({ key }) => result.Ok(read_flag(ctx, key, "flag-set")?),
    model.All({ of }) => all_of(ctx, of),
    model.Any({ of }) => any_of(ctx, of),
    model.Not({ of }) => result.Ok(!(evaluate(ctx, of)?)),
  }
}
glyph build, 마지막 arm을 지운 뒤 
[E0200] non-exhaustive match on `Condition`: missing variants Not
자세히 표준 라이브러리 유니언, 문자열 enum, 그리고 그 목록이 있었던 이유

표준 라이브러리의 유니언에도 마찬가지이므로, option.Option<string>에 대한 match o { option.Some(s) => … }는 그냥 Some/None으로 쓴 것과 똑같이 빠진 None에 대해 E0200입니다. 0.1.56까지는 한정된 표기가 검사를 통째로 건너뛰었고, 런타임에 예외를 던지는 match에 대해 빌드가 아무 진단도 보고하지 않았습니다.

문자열 enum도 경계를 넘습니다. catalog.glyph에 선언하고 다른 모듈로 import한 type ColType = "text" | "int" | "real" | "bool"은 네 값을 유지하므로, 네 가지를 모두 다루는 match는 else 없이 컴파일되고, 하나를 빠뜨리면 빠뜨린 값을 짚는 E0200입니다. 0.1.57까지는 E0218이었고, 도움말은 else arm을 추가하라고 했습니다. 그 도움말은 눈앞의 코드에 대해 틀렸고, 그대로 따르면 컴파일 오류가 런타임 fallthrough로 바뀌었습니다. 세 가지 import 표기 모두 동작합니다: import catalog { ColType }, catalog.ColType을 쓰는 import catalog, 그리고 c.ColType을 쓰는 import catalog as c.

이 문제는 그 import 목록에서 시작되었습니다. statechart 엔진의 모든 모듈에 직접 작성되어 있었고, 그 위에는 유니언의 생성자는 타입과 함께 들어오지 않는다는 주석이 달려 있었습니다. 주석은 문법에 대해서는 맞았지만 이유에 대해서는 틀렸습니다. 목록이 있었던 이유는 더 짧은 표기가 검사를 꺼 버렸기 때문이고, 끄는 것이 조용했기 때문에 아무도 알아채지 못했습니다. 이제 어느 형태를 고르느냐는 함정이 아니라 실제 선택입니다. 이름을 나열하는 형태는 처리하는 모든 variant를 import 목록에 두므로 Equals를 grep하면 찾을 수 있습니다. 한정된 형태는 각 arm에서 variant가 어느 모듈에서 왔는지 보여 줍니다. 어느 쪽도 검사를 잃지 않습니다.

import한 레코드는 필드를 유지합니다

이제 레코드도 경계를 넘으며, 0.1.58까지는 그렇지 않았습니다. 따라서 레코드는 필드 집합을 유지하고, 잘못된 필드는 익명 모양에 대한 tsc 오류가 아니라 레코드 이름을 짚는 E0210입니다.

// Emitted TypeScript: sheet.rows.entries(), not Object.entries(sheet.rows).
자세히 line 11 버그, tsc가 놓치는 것, 식별이 경계를 넘는 방식

한 파일에서 선언하고 다른 파일에서 쓰는 타입은 아무 정보 없이 도착했고, 그 때문에 별개의 검사 두 개를 잃었습니다. 그 타입의 철자가 틀린 필드는 Glyph 오류를 전혀 내지 않았으므로 sheet.rowz는 tsc까지 넘어가서, 작성한 적도 없는 모양에 대한 TypeScript 메시지로 돌아왔습니다. 그리고 for i, r in sheet.rows는 rows가 배열인지 알 수 없어서 sheet.rows.entries() 대신 Object.entries(sheet.rows)를 생성했습니다. 그러면 i가 문자열 "0"에 바인딩됩니다. 그러면 i + 1은 더하기 대신 문자열을 이어 붙이고, line 2로 보고되어야 할 행이 line 11로 보고됩니다.

알아 둘 만한 부분은 tsc가 어느 쪽을 잡느냐입니다. 그 인덱스에 대한 산술 연산은 잡지만, Glyph가 대신 바인딩한 변수에 대해 생성된 TypeScript 기준으로 오류를 보고합니다. 잡지 못하는 것은 숫자를 의도한 곳에 문자열이 받아들여지는 모든 곳입니다. 문자열 보간, 이어 붙이기, record.get 키 같은 곳입니다. 이런 코드는 두 검사기에서 모두 깔끔하게 컴파일되고 잘못된 숫자를 출력합니다. 이 프로젝트가 없애려고 존재하는 바로 그 모양의 버그이므로, 이를 다시 들여오는 모듈 경계를 Glyph가 그냥 둘 수는 없습니다.

이제 import한 타입은 그것을 선언한 모듈과 선언된 이름을 키로 하는 식별 정보를 경계 너머로 가지고 가므로, 세 가지 import 표기 모두 같은 타입으로 해석됩니다. 선언 자체는 필요할 때 가져와서 선언한 모듈 쪽에서 변환되는데, 이것이 사용하는 쪽에서는 할 수 없는 절반입니다. 이름 해석은 소스 범위를 기준으로 실행되고, import한 선언의 범위는 다른 파일에 속하기 때문입니다.

이 문제가 드러난 곳은 examples/apps/csvql의 쿼리 엔진입니다. 여기에는 import한 필드의 타입을 emitter에 다시 알려 주는 것 말고는 하는 일이 없는 let 끌어올리기가 세 개 있었고, 그 위에는 이것이 없으면 오류 메시지의 행과 열 번호가 틀리게 나온다는 네 줄짜리 주석이 있었습니다. 세 개 모두 삭제했고, 앱은 열두 개 쿼리 모두에 대해 바이트 단위로 같은 출력을 냅니다.

경계에서 여전히 멈추는 것이 하나 있습니다. table.Row가 필요한 곳에 catalog.Sheet를 넘기면 두 타입을 모두 짚는 E0211이지만, interface의 멤버 목록은 경계를 넘지 않으므로 import한 인터페이스가 필요한 곳에 넘긴 레코드는 아무것과도 비교되지 않습니다. 레코드의 필드 집합과 같은 처리를 하면 구조적 만족이 무엇을 뜻하는지가 조용히 바뀌게 되는데, 이는 수정이 아니라 언어 차원의 결정입니다.

개인정보 마스킹은 타입에 있습니다

"관례가 아니라 타입 수준으로 만든다"는 같은 원칙이 개인정보에도 적용됩니다. 타입에 @redact fields: [ssn, dob]를 붙이면 컴파일러가 그 필드를 가리는 redact()를 디스크립터에 생성하므로, json.stringify(User.redact(u))는 그 필드를 유출할 수 없습니다.

E0219 @redact의 알 수 없는 필드

타입에 없는 필드를 지정하면 아무 일도 하지 않는 마스킹이 아니라 컴파일 오류(E0219)입니다.

정제 타입은 끝까지 검사됩니다

디스크립터는 타입이 선언한 검사를 끝까지 수행할 때만 가치가 있습니다. where 정제는 직접 호출한 Instant.parse에서만이 아니라 타입이 나타나는 모든 곳에서 조건식을 실행합니다. 레코드 필드, Array 요소, Option payload, 유니언 variant 안, 그리고 json.parse<T>를 통해서도 마찬가지입니다.

schedule.glyph: 조건식이 타입을 따라 필드 안까지 들어감 
fn is_instant(value: string) -> bool {
  return match time.parse_iso(value) {
    Some(_) => true,
    None => false,
  }
}

type Instant = string where is_instant(value)

type WireBlock = { start: Instant, end: Instant }
type WireParticipant = { name: string, busy: Array<WireBlock> }
type Calendar = { participants: Array<WireParticipant> }

// json.parse<Calendar>(text) on a file holding "start": "no"
//   => Err. It returned Ok before 0.1.41.
이력 0.1.41 이전의 자신만만하게 틀린 일정

다른 모듈에서 import한 레코드도 마찬가지입니다. 0.1.41까지는 둘 다 키가 있는지만 확인하는 것으로 대신했는데, 이는 아무것도 검사하지 않는 것입니다.

이 문제가 드러난 곳은 아래의 일정 관리 앱입니다. JSON 파일에서 캘린더를 읽고, 모든 타임스탬프가 실제 ISO-8601 시각이어야 합니다. 예전에는 정제가 최상위에서 멈췄기 때문에, 직접 수정한 파일에 "start": "no"가 있어도 문제없이 파싱되었고, 시각은 0으로 읽혔으며, 앱은 자신만만하게 일정을 출력하고 0으로 종료했습니다.

테스트는 빌드의 일부로 실행됩니다

테스트는 코드 옆에 있고 컴파일 과정의 일부로 실행됩니다. 함수 위의 @example이나 @doc 안의 ```glyph @run``` 블록은 기억해야 할 플래그 없이 glyph build가 실행합니다.

bracket.glyph: 시드 배치를 깨뜨리면 빌드가 멈춤 
@example seed_order(2) == [1, 2]
@example seed_order(4) == [1, 4, 2, 3]
@example seed_order(8) == [1, 8, 4, 5, 2, 7, 3, 6]
fn seed_order(size: int) -> Array<int> { … }

// glyph build src --out dist
example failed: bracket example #16:
  (seed_order(8)) != ([1, 2, 3, 4, 5, 6, 7, 8])
1 of 23 example(s) failed.            # exit 1, no "tsc passed" line

// glyph build src --out dist --json
{ "ok": false, "errors": 1, "tsc": "passed",
  "examples": { "total": 23, "ran": true, "skipped": false,
    "failures": ["bracket example #16: …"] } }
자세히 조용히 건너뛸 수 없는 이유와 JSON 채널

거짓인 예제는 타입 오류와 똑같이 빌드를 실패시키며, 그것이 핵심입니다. 함수 본문을 다시 쓰는 에이전트는 단언을 그대로 둔 채 빌드를 통과할 수 없습니다. --no-test로 건너뛸 수 있지만 건너뛴 테스트 수를 출력하므로, 우회한 사실이 로그에 남습니다.

에이전트가 읽는 JSON 출력도 같은 판정을 보고합니다. glyph build --json은 진단 옆에 examples 객체를 담고, 실패하는 예제가 있으면 ok가 false가 되고 종료 코드가 0이 아닙니다. 0.1.43까지는 예제가 --test에서만 실행되었고 JSON 경로는 예제를 실행하기도 전에 반환했으므로, 에이전트가 읽을 수 있는 유일한 채널이 자체 단언이 거짓인 프로젝트에 대해 "ok": true를 출력했습니다. PATH에 tsx가 없으면 검사하지도 않은 통과를 보고하는 대신 빌드가 실패합니다.

아래의 대진표 앱에는 이런 예제가 23개 있습니다. seed_order는 두 배로 늘려 가며 표준 대진 순서를 만드는데, 미묘하게 틀리기 쉽고 정확하게 설명하기도 쉬운 종류의 함수입니다. 두 배로 늘리는 규칙을 바꾸면 테스트 파일도, 러너도, 플래그도 없이 빌드가 멈춥니다.

직접 만들며 찾은 것

직접 만들며 찾은 네 가지 더

이것들은 모두 깔끔하게 컴파일되고 tsc --strict를 통과했으며, 모두 컴파일러를 읽어서가 아니라 애플리케이션을 작성하면서 발견했습니다. 세 곳에서 나타난 같은 실패입니다. 타입은 한 가지를 말했고 프로그램은 다른 일을 했습니다.

없을 수도 있는 키 읽기

없을 수도 있는 키 읽기: 이제 E0224 
fn name_of(row: Record<string, string>) -> string {
  return row.naem          // a typo. compiled, and returned undefined
}

이제 record.get을 가리키는 컴파일 오류입니다. 이 함수는 Option<V>를 반환하므로 키가 없는 경우를 처리할 자리가 생깁니다.

자세히 맵 읽기가 배열 인덱싱과 다른 이유

맵의 키는 임의적이므로 컴파일러는 키가 있는지 알 수 없습니다. 읽은 값의 타입을 string으로 지정하는 것은 검사하지 않은 것을 단언하는 것이었고, 값은 "undefined"라는 텍스트로 출력되었습니다. 키를 쓰는 것은 그대로이고 배열 인덱싱도 그대로입니다. 범위는 프로그램이 검사할 수 있는 값이지만 맵 키는 그렇지 않습니다.

undefined를 돌려주는 메서드

아무것도 찾지 못할 수 있는 조회: 이제 E0242 
let name = users.find(fn(u: User) -> bool { return u.id == id }).name
let last = xs.at(-1) ?? 0  // passed tsc --strict too

[E0242] the call to `users.find` returns `User | undefined`; Glyph writes a value that may be missing as an `Option`
Help: pass `users` and the same callback to `array.find`, which returns `Option<User>`, and `match` it

JavaScript의 몇몇 메서드는 "아무것도 없음"을 undefined로 알립니다. Glyph 자체 체커는 이것을 볼 수 없었기 때문에 에디터와 에이전트 도구는 .name 읽기를 통과시켰습니다. 이제 각 메서드는 Option을 반환하는 표준 라이브러리 함수를 가리키고, 배열 메서드는 glyph fix가 바꿔 씁니다.

자세히 어떤 메서드이고 무엇으로 바꾸는지

목록은 TypeScript 선언에서 읽어 옵니다. 배열의 find, findLast, at와 문자열의 at, codePointAt, match입니다. 대체 함수는 array.find, array.find_last, array.get, string.char_at, string.code_point_at, regex.matches입니다. ?? 기본값은 match의 None 갈래가 됩니다. array.get은 음수 인덱스에 None을 돌려주므로 xs.at(-1)에 대한 도움말은 array.get(xs, array.len(xs) - 1)로 씁니다. npm 값에서 호출한 메서드는 Glyph가 그 타입을 모르기 때문에 판단하지 않습니다.

==는 어디서나 값 비교입니다

코드는 실패했는데 통과한 테스트 
@example wrap("a") == wrap("a")   // passed: deep equality
fn same() -> bool {
  return wrap("a") == wrap("a")   // false. no diagnostic
}

==는 이제 어디서나 값 비교입니다. 원시 타입은 여전히 ===로 컴파일되므로 일반적인 비교는 바뀌지 않습니다.

이력 망가진 코드에서 테스트가 통과할 수 있었던 이유

==는 값 비교라고 문서화되어 있었지만 ===로 변환되었는데, 이는 어느 한쪽이 레코드, 태그 유니언, 배열이 되는 순간 참조 비교입니다. 같은 표현식이 테스트에서는 구조적으로, 바로 옆 프로그램에서는 동일성으로 비교했으므로, 동작하지 않는 코드에 대해 테스트가 성공을 보고할 수 있었습니다.

반복문 바인딩은 요소 타입을 유지합니다

반복문 안에서 사라진 망라성 
for t in tiers {
  match t {
    "free" => ...          // "pro" unhandled: once merely a warning to add `else`
  }
}

이제 처리하지 않은 variant를 짚어 주며, 이는 검사를 끄라는 조언이 아니라 검사를 만족시키라는 조언입니다.

이력 예전에 주던 catch-all 조언

반복문 바인딩에 요소 타입이 없었으므로, 문자열 리터럴 유니언에 대한 match가 string에 대한 match로 격하되었고 컴파일러는 catch-all을 추가하라고 조언했습니다.

인덱스로 읽은 값은 요소의 타입을 가집니다

xs[0]에서 낸 오타: 이제 E0210 
fn first_len(xs: Array<string>) -> number {
  let s = xs[0]
  return s.lenght
}

[E0210] type `string` has no field `lenght`; did you mean `length`?

Array<E>에 대한 xs[i]는 E이므로, 에디터와 glyph check --no-tsc, 에이전트 도구가 그 값으로 하는 일을 검사합니다. 필드 읽기, 메서드 호출, return, 인자, 타입을 표기한 let입니다.

이력 이전에는 무엇을 검사했는지

0.1.183까지는 인덱스로 읽은 요소가 Glyph 쪽에서 타입이 없었습니다. -> number 아래의 return xs[0], rows[0]의 철자가 틀린 필드, number 매개변수에 넘긴 xs[0]가 모두 통과했고, 전체 빌드의 tsc 단계에서만 잡혔습니다. 타입은 tsc가 생성된 코드에 주는 타입과 같습니다. 생성된 설정은 noUncheckedIndexedAccess를 끈 상태이므로 E | undefined가 아니라 E입니다. Glyph의 인덱스는 끝을 넘으면 undefined를 돌려주는 대신 RangeError를 던집니다. Option이 필요하면 array.get을 쓰세요. Record의 키 읽기는 값 타입이 unknown이 아니면 여전히 E0224이고, string이나 npm 값에 대한 인덱스는 판단하지 않습니다.

import한 제네릭 유니언도 검사됩니다

import한 제네릭 유니언에 대한 match에서 빠진 variant 
import tree { Tree, Node }

fn label(t: Tree<string>) -> string {
  return match t {
    Node({ key: k }) => k    // Leaf unhandled: built clean, threw at run time
  }
}

이제는 어느 경우든 E0200입니다. 두 가지 import 표기 모두, 열린 매개변수든 구체적인 인스턴스화든 마찬가지입니다.

이력 검사가 시작조차 되지 않았던 이유

자기 모듈이 선언한 유니언은 타입 매개변수가 있든 없든 검사됩니다. 형제 모듈에서 import한 유니언은 타입 매개변수가 없을 때만 검사되었습니다. Tree<string>은 import한 유니언 자체가 아니라 import한 유니언의 적용으로서 모듈 간 커버리지 경로에 도달하는데, 검사를 시작하는 관문은 전자를 찾고 있었으므로 match는 아예 세어지지 않았습니다. tsc --strict는 통과했고 Leaf가 예외를 던졌습니다. 두 파일에서 <K>를 지우면 같은 프로그램이 E0200이었습니다.

parse는 하지 않은 검사를 했다고 주장할 수 없습니다

검사하지 않고 성공을 보고한 parse: 이제 E0304 
type Conn = { id: number, sock: Socket }

Conn.parse(body)   // Ok. `sock` was never checked, and the message said it was

레코드에 소켓을 담는 것은 평범한 일이고 여전히 컴파일됩니다. 이를 검증하는 것은 이제 작성한 곳과 그 레코드를 import하는 모든 모듈에서 필드와 그 타입을 짚으며 거부되고, 거부는 모양을 따라갑니다. 중첩된 레코드, Array, Option을 통해서도 마찬가지입니다.

자세히 존재 여부가 검사가 아닌 이유와, 요구하는 수정

모든 레코드 타입은 런타임 디스크립터를 가집니다. 소켓이나 extern_ts를 통해 닿는 것처럼 컴파일러가 안을 들여다볼 수 없는 타입의 필드에 대해, 생성된 검사는 "있는가"였는데 보고 메시지는 field `sock` must be Socket이었습니다. 항상 참인 불리언은 쓸모가 없습니다. 아무것도 검사하지 않은 타입을 짚는 메시지 아래에서 항상 참인 불리언은 더 나쁩니다. 경계에서 믿으라고 하는 것이 바로 parse이기 때문입니다.

요구하는 수정은 어차피 작성했을 분리입니다. 모든 필드를 검사할 수 있는 wire 타입을 두고, 그로부터 도메인 레코드를 만드는 것입니다. unknown은 이 검사에 걸리지 않습니다. 아무것도 주장하지 않으며, 존재 여부가 정말로 검사의 전부이기 때문입니다.

호출 지점에서 보이지 않는 시그니처 변경: 0.1.116에서 막힘

함수가 원시 문자열 대신 payload를 받도록 바꿔도, 여전히 이전 모양을 넘기는 모든 호출이 깔끔하게 빌드되었습니다.

billing.glyph: 유니언이 아무도 모르게 `string` 매개변수를 통과함 
type PaymentResult = Settled(string) | Declined(string)

fn takes_string(s: string) -> number { return s.length }

fn charge(r: PaymentResult) -> number {
  return takes_string(r)   // compiled clean before 0.1.116
}
glyph build, 현재 
[E0211] argument type mismatch: expected `string`, found `PaymentResult`
   ╰─ Pass a value of the expected type, or change the parameter's type.
자세히 검사가 발생하는 곳과 조용한 곳

string, number, bool 타입의 매개변수는 선언된 유니언이나 레코드 값을 아무 불평 없이 받아들였습니다. 같은 호출에 맞지 않는 bool 인자를 넘기면 이미 E0211이었는데도 말입니다.

이 검사는 선언을 읽으므로 답이 확실한 곳에서만 발동합니다. type Id = string 같은 원시 타입 별칭은 그것이 가리키는 string으로 읽히므로 똑같이 판정됩니다. 문자열 리터럴 유니언(D30)은 리터럴로 비교되고, interface 값은 그 값이 객체이므로 string이 선언된 곳에서 거부됩니다. extern_ts나 typeof 본문은 여전히 아무 말도 하지 않고, void도 제외됩니다. 인자, return, let 주석에 똑같이 적용되는데, 셋 모두 하나의 관계를 공유하기 때문입니다.

반대 방향은 TypeScript처럼 값의 멤버를 거칩니다. interface HasName { name: string }이 선언된 곳에서 5는 거부되고, interface HasLen { length: number }이 선언된 곳에서 "abc"는 문자열에 length가 있으므로 받아들여집니다. bigint는 자기 멤버를 통해 읽히므로 그곳에서 거부됩니다. length가 없기 때문입니다. 아직 판정하지 않고 tsc에 맡기는 짝이 두 가지 있습니다. 멤버가 모두 선택적이고 값과 하나도 공유하지 않는 인터페이스(G526), 그리고 인터페이스에 대한 Option, Result, Record(G527)입니다.

타입 표기가 있는 const는 타입을 가집니다

const에는 받는 쪽에 같은 구멍이 있었습니다.

catalog.glyph: 타입 표기가 있는 const와, 그것에 없는 필드 
type Sheet = { rows: number, cols: number }
const ORIGIN: Sheet = { rows: 0, cols: 0 }

fn f() -> number {
  return ORIGIN.rowz   // compiled clean before 0.1.116
}
glyph build, 현재 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
자세히 타입 표기가 없는 const, 그리고 두 수정이 모두 breaking인 이유

타입 표기가 있는 모듈 수준 const는 표기가 무엇이든 Ty::Unknown으로 변환되었으므로, 함수 안의 같은 표기를 가진 let에서는 이미 보고되던 필드 오타가 거기서는 보이지 않았습니다.

0.1.166부터 주석 없는 const는 초기화식의 타입을 가집니다. 이미터가 쓰는 TypeScript const를 tsc가 읽는 방식 그대로입니다. const MODE = "read"는 리터럴 타입을 유지하고, 객체나 배열 안의 리터럴은 넓혀지므로 const ITEMS = [1, 2]는 Array<number>이고 mut 밖의 ITEMS.push(3)은 E0240입니다. 검사기가 타입을 정할 수 없는 초기화식은 그 const를 타입 없이 둡니다. 두 수정 모두 glyph check --no-tsc, 언어 서버, 플레이그라운드에서 호환성을 깨는 변경입니다. 각각 이전 릴리스가 받아들이던 프로그램을 잡기 시작하기 때문입니다. 전체 glyph build는 두 경우 모두 이미 tsc 때문에 빨간색이었습니다.

레코드가 선언하지 않은 필드

철자가 틀린 선택적 필드: 이제 E0210 
module profile

pub type Profile = {
  name: string,
  nick?: string,
}

pub fn guest() -> Profile {
  return { name: "guest", nik: "g" }   // [E0210] type `Profile` has no field `nik`; did you mean `nick`?
}

선언된 레코드에 없는 키는 예전에는 Glyph의 체커를 통과했습니다. 그래서 선택적 필드의 오타는 그 값을 버렸고, 알아챈 것은 tsc뿐이었습니다. 이제 편집기, 에이전트 도구, glyph check --no-tsc가 이를 거부하며, 같은 필드를 읽을 때와 같은 오류를 냅니다. glyph fix는 nik을 nick으로 바꿉니다.

자세히 어디서 판정하고 무엇을 그대로 두는지

작성한 리터럴이 선언된 타입과 만나는 곳이면 어디서든 판정합니다. let, return, 호출 인자, 변형의 페이로드, mut 대입, 중첩된 필드, 배열 요소, match 갈래, 그리고 tsc가 통과시키는 Some, Ok, Err의 인자입니다. 더 넓은 레코드를 담은 바인딩은 tsc처럼 계속 허용되며, spread에서 온 필드와 Record<K, V>를 위해 쓴 키도 마찬가지입니다.

    비동기 문맥은 Glyph가 tsc에 맡기던 유일한 규칙이었습니다. 이제 평범한 fn 안의 await는 여러분의 소스 기준의 E0222이며, 최상위 const 초기값만 여전히 허용되는 경우입니다. 이 규칙과 한 단계 앞으로 옮겨진 다른 두 규칙은 더 일찍 잡기에 있습니다.

이것이 Glyph의 네 가지 기둥 중 첫 번째인 이유와, 그 보장이 멈추는 곳은 검증 가능성 기둥 페이지에 있습니다.

이 페이지의 코드 예제는 빌드할 때마다 Glyph 0.1.196으로 검사합니다. 마지막 변경: 2026년 11월 26일.
