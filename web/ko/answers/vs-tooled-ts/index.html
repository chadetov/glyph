그 보장들은 모두 직접 켜야 하는 것이고, 에이전트는 각각을 한 줄로 우회할 수 있기 때문입니다. Glyph의 엄격함은 에이전트가 편집할 수 있는 설정 파일이 아닙니다. 언어 자체입니다. 강제되는 지점이 "이 파일에 lint를 돌리는 걸 잊지 않았나"에서 "컴파일되는가"로 옮겨 갑니다.

잘 설정된 TypeScript 환경으로 많은 것을 할 수 있고, 팀이 그 모두를 CI에서 돌리고 있다면 Glyph가 겨냥하는 빈틈 대부분은 이미 막은 것입니다. 진지하게 고려할 만한 대안이므로, 대응 관계를 정리하면 다음과 같습니다.

01 선택 사항이 아닌 것이 직접 켜는 것보다 낫습니다

이 탈출구들은 모두 에이전트가 편집할 수 있는 설정입니다. Glyph에는 손을 뻗을 그런 탈출구가 없습니다. as도, 무시 pragma도 없고, 컴파일러가 볼 수 있는 검사 없이 unknown에서 타입이 있는 값을 꺼낼 방법도 없습니다.

TypeScript: 탈출구가 있음 handler.ts 
const user = body as unknown as User;
// @ts-ignore
doThing(user.mispelled);
// eslint-disable-next-line
return anything as any;
Glyph: 끌 것이 없음 handler.glyph 
return match User.parse(body) {
  Ok(user) => use(user),
  Err(_) => fallback(),
}
// no `as`, no ignore pragma,
// no lint to switch off.

에이전트가 설정으로 끌 수 없는 엄격함은 끌 수 있는 엄격함과 강제되는 지점이 다릅니다. Glyph는 그 차이 위에 만들어졌습니다.

자세히 에이전트가 eslint를 지나쳐 쓸 수 있는 것

eslint 설정은 에이전트가 그것을 거쳐 가는 코드만 보호하며, 에이전트는 as unknown as User, @ts-ignore, // eslint-disable-next-line을 쓰거나 그냥 .exhaustive()를 잊을 수 있고, 그래도 컴파일되고 병합됩니다.

02 타입이 곧 검증기: 두 번째 산출물이 없음

Glyph에서는 타입이 곧 검증기입니다. type User = {...}를 선언하면 User.parse가 함께 생성됩니다. 산출물은 하나이고, 맞춰 둘 것도, 잊을 것도 없습니다.

  • zod: 스키마가 먼저zod는 기준을 뒤집습니다. 스키마를 작성하고 거기서 타입을 끌어낸 다음, 타입, 스키마, 직렬화 코드를 직접 맞춰 둬야 합니다.
  • 어긋남이 들어오는 곳이를 맞추는 곳이 바로 에이전트가 어긋남을 만드는 곳입니다. 타입에서는 필드 이름을 바꾸고 스키마에서는 바꾸지 않아도 둘 다 컴파일됩니다.

03 grep할 수 있는 변경

Glyph에서는 공유 상태가 store에 있고 모든 변경은 .set(/.update( 그대로이며, grep 'mut '은 모든 로컬 변경을 찾습니다. 기본 TypeScript에는 이에 해당하는 것이 없습니다.

자세히 TypeScript의 쓰기가 숨을 수 있는 곳

TypeScript에서는 상태 변경이 =, .push(), Object.assign, setter, spread 뒤에 숨을 수 있습니다. 검색할 토큰이 하나로 정해져 있지 않고, 어떤 lint 규칙도 이를 완전히 고치지 못합니다.

실패 방식 비교

같은 작업에서 에이전트가 유니언에 variant를 추가하고, 세 곳 중 한 곳에서 처리하는 것을 잊습니다.

도구를 갖춘 TS 
// ts-pattern .exhaustive() catches it,
// IF every site used ts-pattern and
// nobody wrote a default: case or a
// switch that only logs. Those
// compile green and skip the new case.
Glyph 
[E0200] non-exhaustive match on
`Feed`: missing variant `Archived`
// every unhandled match, everywhere,
// fails the build. No opt-in, no
// escape, no forgotten default.

도구를 갖춘 TypeScript가 여전히 앞서는 부분

현재 Glyph보다 앞서는 곳이 네 군데 있습니다.

  • 더 풍부한 검증.Glyph 디스크립터는 기본적으로 엄격하고(선언되지 않은 키를 거부합니다), where 정제는 원시 타입에 조건식을 붙이며(type Email = string where value.includes("@")), 디스크립터는 타입이 닿는 모든 경계에서 이를 실행합니다. zod는 여전히 두 가지에서 앞섭니다. Glyph에서는 직접 작성해야 하는 .email(), .url() 같은 기성 검사를 제공하고, 객체 전체를 정제할 수 있는 반면, 레코드에 대한 where(두 필드에 걸친 lo <= hi)는 현재 E0300입니다.
  • 더 깊은 매칭.ts-pattern의 가드와 깊은 구조적 패턴은 Glyph의 match가 표현하는 범위를 넘어섭니다.
  • "증명 가능한 부재"는 .ts 경계에서 멈춥니다.Glyph의 보장은 Glyph로 작성한 코드에 대해 성립합니다. npm 의존성에서 던진 예외는 여전히 Result를 우회하고, import한 .d.ts 타입에는 런타임 디스크립터가 없습니다.
  • 생태계와 채용.TypeScript의 도구, 커뮤니티, 채용 인력 풀은 훨씬 크고, 수년간의 프로덕션 사용이 뒷받침합니다. Glyph는 초기 프리뷰입니다.

도구를 갖춘 TypeScript를 완전히 연결했고 에이전트가 그 안에 머문다면 이 대부분을 이미 갖춘 것입니다. Glyph의 주장은 "그 안에 머문다"가 하중을 받는 구절이고, 에이전트가 깨뜨리는 것이 바로 그 구절이라는 것입니다. 선택 사항이 아닌 엄격함, 산출물 하나로 하는 검증, grep할 수 있는 변경은 직접 켜는 도구를 더 추가해서는 얻을 수 없는 부분입니다.

자세히 ReScript, Gleam, Elm

TypeScript를 떠나 JavaScript로 컴파일되는 더 오래된 타입 언어로 갈 생각이 있다면, 왜 ReScript, Gleam, Elm이 아닌가요?에서 Glyph와 비교합니다.
