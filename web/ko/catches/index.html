TypeScript가 통과시키는 사례

배포되기 전에 잡아냅니다

확인된 사례는 모두 53건입니다. TypeScript 실수 37건, Glyph에는 없는 JavaScript 함정 5건, Glyph가 아직 막지 못한 구멍 11건입니다. 그중 28건은 빌드할 때 Glyph가 거부합니다(실수 23건, 함정 5건).

목록에 있는 TypeScript 예제는 모두 tsc --strict를 오류 없이 통과합니다. 각 예제는 최대한 엄격하게 설정한 프로젝트에서도 다시 검사합니다. --strict보다 엄격한 컴파일러 플래그를 모두 켜고, typescript-eslint strictTypeChecked까지 적용한 설정입니다. 37개의 사례 중 21개는 이 설정의 어떤 것도 잡아내지 못합니다. 기본값이 꺼져 있는 컴파일러 플래그가 5개를, lint 규칙이 11개를 잡아냅니다. 이 플래그와 규칙은 프로젝트에서 하나하나 켜야 하고, 에이전트가 다시 끌 수도 있습니다. Glyph에서는 이 중 어느 것도 설정 옵션이 아닙니다.

각 항목은 catches/에 있는 두 프로그램이고, 각 프로그램 아래의 출력은 도구가 실제로 출력한 내용입니다. 빌드 게이트인 scripts/check_catches.py가 모든 사례를 다시 실행하고, 어느 한쪽이라도 페이지에 적힌 대로 동작하지 않으면 실패합니다. 검사에 쓰는 전체 TypeScript 설정은 이 스크립트에 있습니다.

프로그램 외부에서 온 데이터

발생 가능성 5점 중 5점심각도 5점 중 5점

요청 본문, 파일, API 응답.

TypeScript컴파일된 뒤 잘못된 데이터로 실행
ts.ts
const user = JSON.parse(body) as User;
console.log(sendInvoice(user.plan));
$ tsx ts.ts
invoice for the undefined plan

아무것도 데이터를 검사하지 않습니다. undefined가 요금제인 것처럼 계속 전달됩니다.

아무것도 잡지 못함모든 컴파일러 플래그와 strict 모드의 typescript-eslint를 켜도 잡지 못합니다

Glyph데이터가 들어올 때 검사
glyph.glyph
let out = match json.parse<User>(body) {
  Ok(user) => send_invoice(user.plan),
  Err(issues) => "rejected: ${json.stringify(issues)}",
}
$ glyph run
rejected: [{"path":["plan"],"message":"field `plan` is required","code":"missing"}]

올바른 User가 아닌 본문은 Err입니다. 프로그램이 가짜 값을 갖게 되는 일은 없습니다.

as User는 아무것도 검사하지 않습니다. 컴파일러에게 나를 믿으라고 말할 뿐입니다. Glyph에는 as가 없습니다.

2

아무도 처리하지 않은 case

발생 가능성 5점 중 5점심각도 5점 중 4점

에이전트가 "archived" 상태를 추가합니다. 각 상태를 알리는 핸들러는 이 상태가 생기기 전에 작성되었습니다.

TypeScript경고 없이 컴파일
ts.ts
switch (s) {
  case "todo":
    console.log("not started");
    break;
  case "doing":
    console.log("in progress");
    break;
  case "done":
    console.log("finished");
    break;
}
$ tsx ts.ts
finished
archived logged nothing

항목을 보관해도 아무 로그가 남지 않습니다. switch가 낡았다고 알려 주는 것이 없습니다.

lint로만lint 규칙 switch-exhaustiveness-check이(가) 잡아냅니다

Glyph빌드 시 거부
glyph.glyph
match s {
  "todo" => print("not started"),
  "doing" => print("in progress"),
  "done" => print("finished"),
}
$ glyph build
[E0200] Error: typecheck: non-exhaustive match on `"todo" | "doing" | "done" | "archived"`: missing variants "archived"
Help: Add an arm for each missing variant.

빌드가 멈추고 해당 case를 지목합니다.

TypeScript는 함수가 모든 분기에서 값을 반환하거나 assertNever 관용구를 쓸 때만 switch가 모든 case를 다루는지 검사합니다. 아무것도 반환하지 않는 핸들러는 둘 다 해당하지 않습니다. Glyph에서는 모든 match가 모든 case를 다뤄야 하므로, variant를 추가하면 바꿔야 할 곳이 모두 나열됩니다.

링크 복사재현하기점수에 동의하지 않나요?

await를 사이에 둔 갱신 손실

발생 가능성 5점 중 3점심각도 5점 중 5점

두 요청이 같은 계정에 동시에 요금을 부과하는 경우.

TypeScript컴파일된 뒤 실행 중에 돈이 사라짐
ts.ts
const before = a.balance;
const f = await fee();
a.balance = before - f;
$ tsx ts.ts
balance 90

요금 하나가 사라집니다. 어떤 테스트도 이를 안정적으로 잡지 못합니다.

lint로만lint 규칙 require-atomic-updates이(가) 잡아냅니다

Glyph빌드 시 거부
glyph.glyph
let before = a.balance
let f = await fee()
mut a.balance = before - f
$ glyph build
[E0225] Error: typecheck: `a.balance` is read before an `await` and written after it, so a concurrent write in between is lost
Help: Move the read after the `await`, so the value written is the one that is current when it is written.

Glyph에는 존재하지 않는 JavaScript 함정 5건

에이전트가 지금도 가끔 빠지는 오래된 함정들입니다. Glyph는 각 프로그램을 거부하지만, 실수를 찾아내서가 아닙니다. 그 원인이 되는 기능이 언어에 없고, 대신 쓸 것을 알려 줍니다.

  • "10,20,30".split(",").map(parseInt)의 결과는 [10, NaN, NaN]입니다. map이 인덱스를 진법으로 넘기기 때문입니다. Glyph에는 Result를 반환하는 number.parse가 있습니다.
  • /g 정규식을 .test에 재사용하면 lastIndex를 기억하기 때문에 두 번에 한 번은 매칭에 실패합니다. Glyph에는 정규식 객체가 없고, regex.matches(pattern, text)에는 상태가 없습니다.
  • [1, 2, 3].forEach(counter.increment)는 메서드를 객체 없이 실행합니다. Glyph에는 클래스도 this도 없습니다.
  • Math.max(...[])는 -Infinity입니다. Glyph의 array.max는 Option을 반환하며, 빈 목록이면 비어 있습니다.
  • Array(3).map(...)은 구멍 세 개를 반환합니다. map이 구멍을 건너뛰기 때문입니다. Glyph에는 Array(n)이 없고, 배열은 리터럴로 작성합니다.

Glyph가 아직 잡아내지 못하는 것

Glyph가 아직 막지 못한 구멍 11건입니다. 이 코드는 모두 현재 Glyph에서 컴파일되고, TypeScript에서와 똑같이 잘못 동작합니다. 각각 catches/에 재현 코드와 열린 gap 번호가 있고, 수정이 들어오면 게이트가 실패하므로 구멍이 막힌 뒤에도 항목이 남아 있을 수는 없습니다.

  • requested || 3은 실제 값인 0을 3으로 바꿉니다. G386
  • 레코드를 넣은 "Welcome back, ${user}!"는 [object Object]를 출력합니다. G385
  • forEach(async ...)는 모든 promise를 버리므로, 작업이 그 결과에 의존하는 코드보다 늦게 끝나는데도 아무 경고가 없습니다. G384
  • 선택 필드에 들어 있는 JSON null이 검사를 통과하므로, 기본값 위에 spread하면 null이 남습니다. G391
  • 헬퍼 안의 xs.sort(...)는 호출한 쪽의 배열 순서를 바꾸는데, 이를 표시하는 mut가 없습니다. G380
  • 숫자에 대한 .sort()는 숫자를 텍스트로 정렬합니다: 100,25,9. G388
  • ${name}으로 만든 SQL 쿼리를 std/sqlite가 받아들입니다. G387
  • c[0]에 대해 await를 사이에 둔 갱신 손실. 필드에 대한 같은 쓰기는 거부됩니다. G390
  • 문자열에 대한 input + 1, users.find(...).name, unknown에서 필드 읽기는 Glyph 자체 검사기가 아니라 tsc 단계에서만 잡히므로, 에디터와 에이전트 도구는 이를 놓칩니다. G381, G382, G392

에이전트가 작성한 코드에 관한 모든 연구에서 가장 큰 비중을 차지하는 것은 논리 오류이고, 어떤 타입 검사기도 이를 보지 못합니다. 잘못된 공식이나 잘못 이해한 작업은 TypeScript에서처럼 Glyph에서도 컴파일됩니다.

Glyph에는 TypeScript로만 표현할 수 있는 코드를 위한 탈출구가 하나 있습니다. extern_ts입니다. 고정된 키워드이므로 grep extern_ts로 규칙이 해제된 모든 곳을 찾을 수 있습니다.
