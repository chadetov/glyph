AI 에이전트가 작성하고, 컴파일러가 검사합니다.

Glyph는 TypeScript처럼 읽히지만 우회로가 없습니다. any도, 캐스트도, 검증되지 않은 데이터도 없고, 모든 경우를 처리해야 합니다. 읽기 쉬운 TypeScript로 컴파일되므로 node, npm, 기존 코드를 그대로 씁니다.

$ npx -y @glyphlang/glyph init hello && cd hello && npm install && npx glyph run

전역 설치가 필요 없습니다. glyph를 PATH에 두려면: npm install -g @glyphlang/glyph tsx typescript

37개 중 21개

목록에 있는 TypeScript 예제는 모두 tsc --strict를 오류 없이 통과합니다. 각 예제는 최대한 엄격하게 설정한 프로젝트에서도 다시 검사합니다. --strict보다 엄격한 컴파일러 플래그를 모두 켜고, typescript-eslint strictTypeChecked까지 적용한 설정입니다. 37개의 사례 중 21개는 이 설정의 어떤 것도 잡아내지 못합니다. 기본값이 꺼져 있는 컴파일러 플래그가 5개를, lint 규칙이 11개를 잡아냅니다. 이 플래그와 규칙은 프로젝트에서 하나하나 켜야 하고, 에이전트가 다시 끌 수도 있습니다. Glyph에서는 이 중 어느 것도 설정 옵션이 아닙니다. 확인된 사례는 모두 47건입니다. TypeScript 사례 37건, Glyph에는 없는 JavaScript 함정 5건, Glyph가 아직 막지 못한 구멍 5건입니다. 그중 28건은 빌드할 때 Glyph가 거부합니다(TypeScript 사례 23건, 함정 5건).

에이전트는 컴파일러에 먼저 물어볼 수 있습니다

examples/apps/csvql은 이 저장소에 있는 CSV 쿼리 엔진으로, 중심에 Value union이 있습니다. 여기에 Date 케이스를 추가하기 전에, 에이전트는 컴파일러의 MCP 서버에 이 수정이 무엇을 깨뜨리는지 묻습니다. 답변(여기서는 판정, 위치, 함수만 남겼습니다)은 파일 네 개에 걸친 match 지점 열 곳을 짚습니다.

WILL_FAIL 항목마다 거기서 날 오류가 함께 나옵니다. 케이스만 추가했을 때 나온 것도 정확히 그 여덟 개의 E0200 오류였습니다. ABSORBS 두 곳은 아무것도 내지 않습니다. render::literal_text는 날짜 리터럴을 따옴표 없이 출력했을 것이고, exec::total은 모든 날짜를 0으로 셌을 것입니다. 컴파일러 오류만 보고 일하는 에이전트는 여덟 곳을 고치고 초록색 빌드에서 멈춥니다. 수정 후 다시 물으면 컴파일러는 열 곳 모두에서 WILL_FAIL이라고 답하므로, 다음 케이스도 빠져나가지 못합니다.
