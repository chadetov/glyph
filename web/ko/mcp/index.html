에이전트를 위한 안내 · Model Context Protocol

에이전트를 Glyph 컴파일러에 연결하기

glyph mcp는 프로젝트를 대상으로 도구 열한 개를 제공하는 Model Context Protocol 서버를 실행합니다. 심볼이 무엇인지, 바꾸면 무엇이 깨지는지, 한 타입의 값을 다른 타입이 선언된 곳에 넣을 수 있는지, 선언이 무엇에 의존하는지, 모듈이 무엇을 export하는지, 프로젝트 안에서 검사한 진단, 커서 위치의 타입, 이름이 정의된 곳, 그 이름에 대한 모든 참조, 유니언에 대한 모든 match 위치, 그리고 심볼 검색입니다. 각 도구는 glyph query 동사로도 쓸 수 있으므로, MCP 클라이언트가 없는 에이전트도 같은 질문을 하고 바이트 단위로 같은 답을 받습니다.

에이전트에게 이것이 필요한 이유#

코드베이스를 편집하는 에이전트는 보통 눈을 가린 채 일합니다. 파일을 읽고, 타입을 추측하고, 무언가를 깨뜨렸는지는 빌드한 뒤에야 알게 됩니다. Glyph는 에디터를 위해 이미 이 질문들에 답하고 있습니다. glyph mcp는 빌드 출력을 긁어 오거나 누가 무엇을 호출하는지 찾으려고 모든 파일을 읽지 않아도, 같은 답을 컴파일러에서 바로 에이전트에게 줍니다. 도구 중 두 개는 에디터가 결코 묻지 않는 질문에 답합니다. glyph_symbol은 유니언의 variant와 각각을 생성하는 문법을 반환하는데, 에이전트가 match를 작성하기 전에 필요한 것이 바로 이것입니다. glyph_impact는 편집이 존재하기도 전에 그 편집이 무엇을 깨뜨리는지 답합니다.

설정하기#

어떤 MCP 클라이언트로도 실행할 수 있습니다. 클라이언트가 mcp 하위 명령과 함께 glyph 바이너리를 가리키게 하고, 프로젝트 루트를 인자로 넘기거나 프로젝트 디렉터리에서 실행하세요. stdio로 MCP를 주고받으므로 포트도 데몬도 없습니다.

MCP 클라이언트 설정 (일반) 
{
  "mcpServers": {
    "glyph": {
      "command": "glyph",
      "args": ["mcp", "/path/to/your/project"]
    }
  }
}

처음 연결할 때 클라이언트는 initialize와 tools/list를 호출하고, 서버는 아래의 도구 열한 개를 알려 줍니다. 보내는 위치는 LSP 규칙을 따릅니다. 0부터 시작하는 line과, UTF-16 코드 단위로 센 0부터 시작하는 character입니다. 진단 범위는 glyph check --json이 출력하는 형식 그대로, 1부터 시작하는 line과 col, 그리고 바이트 offset으로 돌아옵니다.

각 도구의 설명에는 호출하는 순간에 필요한 계약이 담겨 있고, 전체 설명서는 glyph llms --json의 tools 아래에 도구 이름을 키로, 각 도구의 glyph query 동사와 함께 들어 있습니다. 예전에는 그 응답에 모든 설명서가 들어 있었습니다. 도구 열한 개, 45,509바이트 응답 중 31,446바이트가 설명이었습니다. 지금은 20,386바이트 응답 중 8,627바이트이고, 삭제한 것은 없습니다. 모든 세션은 연결할 때 tools/list 비용을 치르고, 설명서 비용은 요청할 때만 치릅니다. 그 문서는 컴파일러 자체 테이블에서 생성되며, 이 서버가 제공하지 않는 도구를 언급하면 테스트가 빌드를 실패시킵니다.

도구 열한 개#

glyph mcp가 제공하는 도구 
// everything the compiler holds about one symbol: kind, identity,
// visibility, a record's fields, a union's variants with payloads and
// construction syntax, parameters and return, interface members,
// whether a `match` over it must be exhaustive, its `@example`.
// The identity reaches the stdlib: std/result::Result answers with
// Ok(T) and Err(E), and `path` is null beside the reason why
glyph_symbol(entity)                       // or (path, line, character)

// what breaks if you make one named change to one declaration:
// add_variant, remove_variant, rename, change_arity,
// change_signature_type, remove. One verdict per site
glyph_impact(entity, change)

// can a value of `from` go where a `to` is declared? Asked of the
// checker's own comparison. Each side is a `module::name` or a
// Glyph type spelling read in the scope of `path`
glyph_assignable(path, from, to)

// every diagnostic for one file, checked inside its project, in the
// shape `glyph check --json` prints, plus what was not checked
glyph_diagnostics(path)

// the type at a position: an expression, a declaration name, a
// parameter, an annotation, a variant, or a binding
glyph_hover(path, line, character)

// where the name is defined, following imports across modules,
// with the `module::name` so the answer chains into glyph_impact
glyph_definition(path, line, character)

// every edge into a symbol across the project, split by relation
// (CALLS, REFERENCES, GENERATED_FROM), each with its provenance
glyph_references(path, name)               // or by position

// every `match` site over one tagged union and which variants each
// site's arms name, with the union's own variants
glyph_variants(path, name)

// search top-level declarations and union variants by name, each
// entry with its identity, `pub`, kind and one-line signature
glyph_symbols(query)

// what one declaration depends on: every declaration its own source
// names, split by relation (CALLS, REFERENCES, FIELD_ACCESS), each
// edge with both ends and its provenance. The mirror of references
glyph_dependencies(entity)

// what one module makes visible to an importer: every `pub`
// declaration and every variant a `pub` union hoists, each with
// its identity, kind and signature
glyph_exports(module)

직접 보기#

필드 이름에 오타가 있는 파일에 대해 glyph_diagnostics를 tools/call로 호출하면, glyph check --json이 직렬화하는 것과 같은 Rust 타입인 컴파일러 자체 진단이, 검사가 다루지 않은 것까지 알려 주는 봉투에 담겨 돌아옵니다.

요청 
{
  "method": "tools/call",
  "params": {
    "name": "glyph_diagnostics",
    "arguments": { "path": "src/user.glyph" }
  }
}
결과 (도구의 JSON 내용) 
{
  "path": "src/user.glyph",
  "module": "user",
  "project_root": "src",
  "member": true,
  "diagnostics": [
    {
      "code": "E0210",
      "severity": "error",
      "stage": "typecheck",
      "message": "type `U` has no field `naem`; did you mean `name`?",
      "help": "Check the field name for a typo,
        or add the field to the type.",
      "entity": "user::greet",
      "file": "user",
      "range": {
        "start": { "line": 9, "col": 10, "offset": 99 },
        "end":   { "line": 9, "col": 16, "offset": 105 }
      },
      "union": null,
      "missing_variants": null
    }
  ],
  "unindexed": [],
  "not_run": [ ... ]
}

파일은 프로젝트 안에서 검사되므로, import한 레코드의 잘못된 필드나 import한 유니언에 대해 arm이 빠진 match도 glyph check와 똑같이 여기서 보고됩니다. 도구가 다루지 못한 것은 여러분이 추측하게 두지 않고 응답에 담깁니다. member는 프로젝트 탐색이 그 파일에 닿는지 알려 주고, unindexed는 파싱되지 않는 프로젝트 파일을 알려 주며, not_run은 glyph check는 하지만 이 도구는 하지 않는 검사 세 가지를 알려 줍니다. tsc, 빌드가 보는 node_modules가 필요한, 존재하지 않는 모듈을 import할 때의 E0104, 그리고 생성된 프로젝트를 실행해야 판정할 수 있는, 실패하는 @example에 대한 E0400입니다. 테스트가 프로젝트 여섯 개에서 두 경로를 모두 실행하고 JSON을 키 단위로 비교하므로 둘이 어긋날 수 없습니다.

glyph_references는 워크스페이스 전체를 대상으로 합니다. 심볼에 대해 물으면 모든 파일에 걸쳐 그 선언, 모든 사용처, 그리고 그것을 import하는 각 모듈의 import 바인딩을 받습니다. 에디터의 이름 바꾸기와 같은 파일 간 식별 방식을 쓰므로, 질문한 파일만이 아니라 프로젝트 전체를 다룹니다.

MCP 클라이언트가 없나요? 명령줄에서 같은 질문하기#

모든 도구에는 도구 자체의 인자를 플래그로 받아 도구의 JSON을 stdout으로 출력하는 glyph query 동사가 있습니다. 답한 질문은 0으로 종료하고, 거부한 질문은 이유를 stderr에 쓰고 2로 종료합니다. 동사는 MCP 클라이언트가 닿는 것과 같은 진입점을 거치며, 통합 테스트가 두 경로에 같은 질문을 하고 답을 텍스트로 비교하므로, 형식을 바꾸거나 요약하는 동사는 테스트에 실패합니다.

클라이언트 없이 묻는 같은 질문 열한 개 
glyph query symbol       --path src/main.glyph --entity orders::OrderStatus
glyph query impact       --entity orders::OrderStatus --change add_variant --variant Refunded
glyph query assignable   --path src/main.glyph --from 'Nullable<int>' --to int
glyph query diagnostics  --path src/main.glyph
glyph query hover        --path src/main.glyph --line 9 --character 6
glyph query definition   --path src/main.glyph --line 9 --character 6
glyph query references   --path src/orders.glyph --name create
glyph query variants     --path src/orders.glyph --name OrderStatus
glyph query symbols      --query order
glyph query dependencies --path src/main.glyph --entity main::build
glyph query exports      --path src/main.glyph --module orders

// the same two, asked about a module the compiler carries
glyph query symbol       --path src/main.glyph --entity std/result::Result
glyph query exports      --path src/main.glyph --module std/result

빌드가 이미 실패했을 때#

도구는 편집하기 전에 묻는 질문에 답합니다. 편집한 뒤에 읽을 것은 glyph check --agent입니다. 이 명령은 check --json의 진단에 키 두 개를 더해 출력합니다. 수정하는 편집이 지켜야 할 불변식인 constraints와, 진단이 언급한 모든 심볼에 대한 glyph_symbol 응답인 symbols입니다. 그래서 다음 편집에 두 번째 호출이 필요 없습니다. arm이 빠진 match라면, 유니언의 variant와 그 payload가 그것을 요구한 오류와 함께 도착하고, else arm을 쓰면 이 진단이 지키려는 보장을 잃는다는 문장도 함께 옵니다. 수정 방법이 완전히 정해지는 경우에는 glyph fix가 직접 수정하고 하지 않은 것을 알려 줍니다. 실제 출력으로 전체 루프를 따라가는 안내가 있습니다.

현재 상태#

지금 제공되는 것

stdio로 동작하는 glyph mcp [root] 서버와 도구 열한 개: glyph_symbol, glyph_impact, glyph_assignable, glyph_diagnostics, glyph_hover, glyph_definition, glyph_references(워크스페이스 전체), glyph_variants, glyph_symbols, glyph_dependencies, glyph_exports. 각 도구에는 같은 JSON을 출력하는 glyph query 동사가 있습니다. 답은 컴파일러 자체 쿼리에서 나오고, 도구가 갖고 있지 않은 사실은 모두 null이며 그 옆의 <key>_absent 문장이 이유를 알려 줍니다. hover는 다른 모듈에서 선언된 이름에서도 답하므로, 호출 위치의 import한 함수와 import한 레코드에서 읽은 필드 모두 타입을 가집니다. 엔티티 식별은 stdlib까지 이어집니다. prelude의 Result는 std/result::Result이며, 이는 resolver가 등록하는 모듈이자 emitter가 import를 쓰는 모듈입니다. 그래서 여기에 glyph_symbol을 호출하면 Ok(T)와 Err(E)로 답하고, std/result에 glyph_exports를 호출하면 그 공개 표면을 나열합니다. 그 뒤에는 Glyph 소스가 없으므로 path와 range는 빠지는 대신 그 이유와 함께 null입니다.

앞으로 할 것

도구는 읽기만 합니다. MCP를 통해 이름을 바꾸거나 편집을 적용할 수는 없습니다. 쓰기 쪽은 대신 명령줄의 glyph fix에 있습니다. 서버는 캐시된 인덱스를 유지하지 않고 호출할 때마다 프로젝트를 다시 탐색하며, 파싱되지 않는 파일은 건너뜁니다. tools/list 응답은 45,509바이트에서 줄어든 20,386바이트이고, 여전히 모든 세션이 연결할 때 치르는 컨텍스트 비용입니다.

도구 외에도 에이전트는 언어와 진단 표면을 오프라인으로 읽을 수 있습니다. llms.txt는 설명 글이고, glyph llms --json은 같은 지식을 컴파일러 자체 테이블에서 꺼낸 데이터이며, glyph build --json은 트리 전체에 대해 코드가 붙은 진단을 한 번에 얻는 방법입니다.

Glyph

TypeScript로 트랜스파일되는 타입 언어로, 에이전트가 코드를 깨뜨리지 않고 수정할 수 있도록 만들었습니다.
