Uma mudança de uma linha é um diff de uma linha, sempre. O Glyph tem um único layout canônico, então um agente não consegue esconder uma mudança real sob uma parede de reformatação.

Nesta página

Por que isso importa

Quando um agente abre um pull request, o diff é o review. Se uma correção legítima de uma linha chega como uma reformatação de 200 linhas, ninguém consegue ver o que mudou de fato, e é nesse ruído que um bug passa.

Estabilidade dos diffs significa que o diff mostra a mudança e nada além da mudança.

Duas regras fazem a maior parte do trabalho. Veja cada uma como o diff que você revisaria.

Vírgulas finais, um item por linha

Vírgulas finais são obrigatórias, e uma lista que não cabe numa linha fica com um elemento por linha em vez de ser reempacotada, então inserir, remover ou reordenar uma entrada nunca mexe nas vizinhas.

O mesmo vale para campos de record, parâmetros, braços de match e imports.

O limite tem um custo: um rename que empurra uma chamada para além de 100 colunas expande a lista de argumentos inteira para um por linha.

Um layout canônico

Existe exatamente uma formatação correta, produzida pelo glyph fmt. Espaçamento, quebras de linha e alinhamento não são escolhas que um agente possa “arrumar”, então uma edição semântica não arrasta reflow junto. Mude o tipo de um campo, e esse é o diff inteiro:

user.glyph: mude um campo, revise uma linha 
 type User = {
   id: string,
-  age: string,
+  age: number,
   email: string,
 }

Como o layout é fixo, dois agentes diferentes editando o mesmo arquivo produzem formatação idêntica byte a byte, sem ruído de reflow, sem “o meu formatter contra o seu”, e um git blame limpo que aponta para o commit que de fato mudou uma linha, não para o que a reformatou.

Um layout canônico: então o formatter mexe nos meus comentários?

Mexia, e isso era um bug que vale nomear. A regra agora: um comentário é reemitido acima do item sobre o qual foi escrito, dentro do corpo de um record, da lista de variantes de uma union, de um literal de array ou objeto, de uma lista de argumentos ou parâmetros, e de um match.

Histórico como os comentários escorregavam, e o app que revelou isso

O Glyph não tem comentários de bloco nem sintaxe de doc-comment, então uma linha // é a única forma de explicar um campo de record, uma variante de union ou um braço de match. O formatter só despejava os comentários pendentes nas fronteiras de declarações e statements, o que fazia um comentário escrito dentro de uma construção descer até a próxima declaração e passar a ser lido como documentação do que estivesse ali. Foi escrevendo um Campo Minado em Glyph que isso apareceu. Estas duas declarações vêm do app real (comentários encurtados para caber), passadas pelo formatter antigo e pelo novo.

0.1.37: uma passada do fmt 
type Visibility =
  | Hidden
  | Flagged
  | Revealed

// Face down. Prints as `.`.
// Face down and marked by the player.
// Face up. `Cell.adjacent` is what gets printed.
type Cell = { mine: bool, adjacent: int, visibility: Visibility }
// Number of mined neighbours. Only meaningful
// once mines are placed.
três comentários de variantes agora documentam um record
0.1.38: o mesmo arquivo 
type Visibility =
  // Face down. Prints as `.`.
  | Hidden
  // Face down and marked by the player.
  | Flagged
  // Face up. `Cell.adjacent` is what gets printed.
  | Revealed

type Cell = {
  mine: bool,
  // Number of mined neighbours. Only meaningful
  // once mines are placed.
  adjacent: int,
  visibility: Visibility,
}
cada comentário no que ele descreve

E uma construção que contém um comentário interno sempre fica na forma de um elemento por linha, de qualquer tamanho, para que o comentário tenha um item acima do qual ficar. Então type Shape = { w: int, h: int } ainda vira uma linha só, e no momento em que você documenta h o record fica expandido.

Detalhes por que isso conta como bug de correção

Por que isso conta como bug de correção e não cosmético: nada falhou. O build saiu com 0, o tsc passou, e a saída estragada era ela mesma um ponto fixo, então o glyph fmt --check no CI ficou verde num arquivo cujos comentários agora diziam algo falso. É a mesma classe de falha que o Glyph existe para eliminar, só que no formatter em vez do sistema de tipos.

O glyph fmt pode quebrar um programa que compila?

Podia, e um caso ainda está aberto. Um formatter ao qual o seu programa precisa sobreviver é pior do que uma feature que falta, porque estraga código que já funcionava.

  • Corpos de braçoO printer agora põe entre parênteses um corpo de braço cujo token mais à esquerda é um { que seria reinterpretado como bloco, ou seja, o objeto vazio e qualquer coisa construída em cima dele (({}).size volta como ({}.size)).
  • O fuzzerO fuzzer agora faz o parse do arquivo formatado e compara a árvore com a do original, então um layout que muda o significado de um arquivo falha na primeira passada em vez de esperar alguém perceber.
Histórico o record vazio que parou de compilar

Primeiro o que foi corrigido. Um braço que significa “o record vazio” se escreve true => ({}). A posição de corpo de braço é o único lugar da gramática em que um { no início é ambíguo, e o parser resolve isso exigindo key: ou ... logo depois da chave. Um objeto vazio não tem nenhum dos dois, então quando o formatter tirava os parênteses e reimprimia true => {}, o braço voltava como um bloco vazio e o arquivo parava de compilar: E0223, o braço não produz valor. Você rodava um formatter em código funcionando e recebia código que não compilava mais.

Um corpo de braço que já é inequívoco, como false => { a: "x" }, fica sem parênteses, então não aparece pontuação nova em nenhum outro lugar. O fmt é ponto fixo sobre o resultado e o TypeScript emitido não muda.

Histórico mais dois corrigidos na 0.1.138

Mais dois foram corrigidos na 0.1.138. Dentro de um bloco, uma linha que começa com ( continua a linha de cima, e até a 0.1.137 o formatter imprimia load()? seguido de .run() como (load()?).run(), então depois de let a = 1 o arquivo formatado significava let a = 1(…).run(). Agora ele mantém load()? com .run() indentado na linha seguinte, e escreve e?(x), e?[0] e e? ? sem parênteses. O outro era o refinamento where de uma union, que o formatter descartava, transformando um programa que o check recusava em um que ele aceitava.

As regras de formatação por trás disso, e a troca que elas fazem, estão na página do pilar de estabilidade dos diffs.

Situação atual

Disponível hoje

  • Vírgulas finais obrigatórias, listas com um item por linha e o layout canônico único do glyph fmt, com round-trip e idempotente, com format-on-save no editor.
  • O glyph fmt nunca move um comentário para um lugar onde ele não pertence.
  • Os comentários ficam acima do item sobre o qual foram escritos
    Detalhes

    Os comentários ficam acima do item sobre o qual foram escritos, inclusive dentro de um record, de um literal, de uma lista de argumentos, de um match, entre os operandos de um operador e entre os passos de uma cadeia de métodos, que então fica com um passo por linha, com o ponto na frente.

O limite, e o que vem depois

  • Um comentário no fim de uma linha de código vai para a linha acima do próximo item
    Detalhes

    Um comentário é sempre emitido na própria linha, então um escrito no fim de uma linha de código (w: int, // width in cells) vai para a linha acima do próximo item. Ele não cruza mais uma fronteira de declaração, mas se move; mantê-lo no fim da linha exige que o printer saiba com qual linha o comentário divide espaço.

  • Um comentário que o layout não tem onde colocar é recusado, não movidoE0500
    Detalhes

    Um comentário onde o layout não tem onde colocá-lo, como dentro de um índice, depois dos argumentos de uma chamada no meio de uma cadeia, ou antes de um operando de ! ou await, não é mais movido: o glyph fmt recusa o arquivo, deixa como estava e diz a linha e onde pôr o comentário, e o glyph check reporta a mesma coisa como warning E0500.

  • Um comentário entre atributos JSX ou entre os campos de um object pattern também é recusado, em casos em que um layout de um por linha poderia acomodá-lo; esses layouts estão na lista.
  • O printer também ainda não tem regra para quebrar uma cadeia longa de métodos ou de +, então uma cadeia comprida demais quebra a lista de argumentos mais interna, que é o lugar errado.
  • Também estamos montando um benchmark de tamanho de diff contra as mesmas edições em TypeScript, para que este pilar seja um número que você possa conferir.
