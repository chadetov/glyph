Sim. Um component compila para um function component do React, o JSX vira createElement, os hooks do próprio React são importados pelo nome e seus pares desestruturados, e o estado de um reducer ganha uma exaustividade que TypeScript puro não tem. A página em si (o título, o ponto de montagem, o estado salvo) é acessada por std/dom e std/storage. A limitação que vale conhecer primeiro: o checker do próprio Glyph não tipa o que um hook retorna, então quem confere esses valores é o tsc.

Por que isso importa

Boa parte do código que agentes escrevem é React. O Glyph o trata como alvo de primeira classe, não como um acessório: component é uma palavra-chave própria (então grep "^component " audita sua UI inteira).

Os hooks do React são importados de react e chamados com seus nomes e tipos reais, verificados pelo tsc contra as declarações do próprio React.

Reducers e hooks

Adicione uma action Double e o reducer para de compilar com um E0200 que a nomeia, algo que um switch em TypeScript puro deixaria ir para produção.

E0200

O checker do próprio Glyph não tipa valores que vêm do React, então um argumento errado para dispatch ou para um setter de estado é reportado pelo tsc no build, não pelo editor nem com --no-tsc.

Detalhes como o par do hook é desestruturado

O par é desestruturado com let [count, dispatch], e o TypeScript emitido adiciona satisfies readonly [unknown, unknown], então o tsc prova que o hook retornou um par e ainda infere o tipo de cada elemento.

Context e bibliotecas

Context do React já funciona via createContext / useContext, e nomes de elemento com acesso a membro (<ThemeContext.Provider>) funcionam diretamente: sem gambiarra.

  • Spread de propsSpread de props em JSX também funciona: <input {...register("email")} /> vira um spread de objeto nas props, então o idioma do react-hook-form não precisa de adaptador.
  • Tipos do ZodOs tipos derivados de valores do Zod são de primeira classe: type FormData = z.infer<typeof schema> funciona direto, sem válvula de escape.

A única coisa que muda: um component recebe um único record de props, não vários parâmetros posicionais. Veja usando suas bibliotecas e a página de hardening para saber exatamente onde fica essa fronteira.

As props são verificadas antes do tsc?

Sim. O próprio Glyph compara cada elemento com o record de props do seu component, então um valor errado, uma prop com nome errado e uma obrigatória faltando são erros do Glyph que nomeiam a prop. Funciona igual se o component foi importado pelo nome ou pelo módulo:

main.glyph, com Card declarado em ui.glyph 
import ui

pub component App() {
  return <div>
    <ui.Card title="Q3" />
    <ui.Card title="Q4" cout={2} />
  </div>
}

// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`
// E0210 type `CardProps` has no field `cout`; did you mean `count`?
// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`

Você os vê no editor e via MCP, não só num build completo.

Detalhes missing_fields em --json, e um único record de props (E0229)

O --json traz os nomes faltando numa lista missing_fields, para que um agente possa adicionar as props sem fazer parse da mensagem. Um component também precisa receber suas props como um único record: component Greeting(name: string) dá E0229 no parâmetro, porque o React só passa o objeto de props e esse elemento nunca passaria na checagem de tipos. Se você o chama como função em vez de renderizá-lo, declare-o com fn.

Um <match> em JSX é verificado como um match?

É a mesma coisa. Cada <case> recebe o pattern que um braço de match recebe, e o compilador o passa pelo mesmo código que usa para o braço.

  • Tipos do payloadOs nomes que um case vincula têm os tipos do payload, um campo que o record do payload não tem dá E0210, e uma variante faltando dá E0200.
  • Cases parciaisUm case que testa um valor só cobre parte da sua variante, então precisa de um case irmão ou de um <case else> para cobrir o resto.
results.glyph 
type Page =
  | Loading
  | Loaded({ users: Array<User>, total: number })
  | Failed(string)

component Results(props: { page: Page }) {
  return <match value={props.page}>
    <case Loading><p>Loading...</p></case>
    <case Loaded({ users, totl })><p>{users.length} of {totl}</p></case>
    <case Failed(message)><p>{message}</p></case>
  </match>
}

// E0210 type `{ users: Array<User>, total: number }` has no field `totl`; did you mean `total`?

Como uma página o inicia?

O Glyph não tem statements de nível superior, então a própria página chama um main exportado. A app tem dois módulos: um com os components, e outro que os monta em #root via std/dom e o createRoot do react-dom.

Atributos de evento são em snake case (on_change emite o onChange do React), um handler é uma lambda, e o texto de um input é e.currentTarget.value.

app.glyph 
module app

import react { useState }

pub component App() {
  let [name, set_name] = useState("")
  return <main>
    <input value={name} on_change={fn(e) { set_name(e.currentTarget.value) }} />
    <p>Hello, {name}</p>
  </main>
}
main.glyph 
module main

import react-dom/client { createRoot }
import std/dom
import std/console
import std/option { Some, None }
import app { App }

pub fn main() -> void {
  match dom.element_by_id("root") {
    Some(root) => createRoot(root).render(<App />),
    None => console.error("the page has no #root element"),
  }
}
index.html, ao lado dos dois módulos 
<div id="root"></div>
<script type="module">
  import { main } from "./dist/gen/main.ts";
  main();
</script>
  1. npx glyph build . --out dist/gen
  2. tsc --strict
  3. npx vite build --outDir dist/web
Detalhes o build, por que este main não recebe nada, o passo a passo

npx glyph build . --out dist/gen verifica os módulos, roda o tsc --strict contra as declarações do React e escreve o TypeScript em dist/gen. Em seguida, npx vite build --outDir dist/web lê o index.html, segue o import e faz o bundle junto com o React. Este main não recebe nada e não retorna nada, porque o script o chama sem argumentos; o main(argv) -> number que o glyph init escreve é o que o glyph run chama no node. O passo a passo completo, com o package.json e a linha de instalação, está em rodando Glyph numa página do navegador, na referência que o glyph llms imprime. O CI faz o build de examples/apps/todo do mesmo jeito e o renderiza num Chromium headless.

Situação atual

Disponível hoje

  • Components, JSX, fragments (<>...</>)
  • Nomes de elemento com acesso a membro (<Ctx.Provider>)
  • Spread de props em JSX ({...register()})
  • Props verificadas contra o component antes do tsc em qualquer forma de import
  • Hooks do próprio React importados pelo nome (useState, useReducer, useEffect) com o tsc conferindo seus tipos e seus pares desestruturados (let [count, set_count] = useState(0))
  • useReducer com actions exaustivas em union etiquetada
  • <match>/<case> verificado e compilado como um match com os patterns do braço
  • Context via createContext/useContext
  • A página via std/dom (título, ponto de montagem, endereço), std/storage e std/console
  • Texto em JSX é lido como o TSX lê, então <p>Don't stop</p> é texto simples; }, >, // e uma entidade HTML como &amp; são recusados no texto (E0012), com a forma a usar no lugar.E0012
  • A leitura de um membro num array é verificada, então {items.foo} num Array<string> dá E0210.E0210
  • examples/apps/todo é uma app inteira em React 18 que faz bundle com Vite e renderiza no navegador.

A caminho

  • O checker do Glyph não tipa o resultado de um hook, então set_count("x") num estado numérico é um erro do tsc no build e não um erro do Glyph no editor.
  • O std/dom se limita a ler a página e definir o título: o React é dono do DOM que renderiza, então não há setters de elementos nem event listeners.
  • Um effect precisa ser escrito como fn() -> void { ... }, porque uma lambda retorna sua última expressão e o React a chamaria como cleanup.
  • Um tipo de props escrito inline ainda aparece como record nessas mensagens; um tipo nomeado mostra o nome.
  • Embutir a saída do Glyph numa app Vite existente, com a UI em TypeScript, está no guia de deploy.
