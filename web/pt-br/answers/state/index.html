Com um store. O Glyph não tem variáveis globais mutáveis. Bindings de módulo são const. Estado compartilhado mora num std/store: um const no nível do módulo que guarda um valor que você lê com get() e muda com set()/update(). O binding nunca muda; só o valor dentro dele muda, por meio de uma chamada de método, então toda escrita é literalmente um .set( ou um .update( que dá para achar com grep.

Veja na prática

Declare o store uma vez no escopo do módulo. Todas as funções do módulo o compartilham. Nada de let passado adiante a partir do main, nada de closures capturando variáveis:

tasks.glyph 
import std/store { create }
import std/array

type Task = {
  id: number,
  title: string,
}

const tasks = create<Array<Task>>([])
const next_id = create(0)

fn add(title: string) -> Task {
  next_id.update(fn(n: number) -> number {
    return n + 1
  })
  let task = { id: next_id.get(), title: title }
  tasks.update(fn(cur: Array<Task>) -> Array<Task> {
    return array.push(cur, task)
  })
  return task
}

fn all() -> Array<Task> {
  return tasks.get()
}
toda a superfície de escrita, num só grep 
$ grep -rn 'tasks\.\(set\|update\)' src/

# every place the task list can change,
# enumerated. nothing hides in an
# ordinary `x = ...` assignment
# somewhere else in the file.

Por que um store, e não uma global mutável

É uma escolha de design deliberada. O Glyph mantém mut restrito a atribuições locais e os bindings de módulo como const, porque um monte de globais graváveis espalhadas é exatamente o que torna o estado difícil de entender e difícil de encontrar.

  • O binding nunca se moveUm store não exige afrouxar nenhuma das duas regras: o binding const s é imutável, e o valor dentro dele só muda via set/update.
  • Uma biblioteca, não sintaxeAssim o estado compartilhado chega como biblioteca, e não como sintaxe nova (sem tipos lineares, sem regras de mutação enfraquecidas), e a mutação fica num único lugar auditado em vez de espalhada pelo programa.

Um ponto de atenção, que o TypeScript também tem: uma coleção vazia não consegue inferir o tipo dos elementos, então inicialize com um argumento de tipo explícito: create<Array<Task>>([]). Um store escalar (create(0)) infere sem problema.

Situação atual

Disponível hoje

  • std/store com create, get, set e update: o lugar único, e que dá para achar com grep, do estado mutável compartilhado.

A caminho

  • Conveniências sobre a mesma primitiva (stores derivados/computados, assinaturas), construídas por cima sem mudar a linguagem.
