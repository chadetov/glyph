Não. Em Glyph um tipo é o seu próprio validador. Declare um type e o compilador gera um descritor de runtime ao lado dele, então um body de requisição ou de resposta não confiável é validado com uma chamada, sem um schema zod separado para escrever e manter sincronizado.

Por que isso importa

Na maioria das stacks TypeScript todo payload é descrito duas vezes: uma como type para o compilador, e outra como um validador escrito à mão para que o valor tenha de fato esse formato em runtime.

Os dois se distanciam, e é exatamente nessa diferença que dados ruins entram. O Glyph junta os dois numa declaração só: o tipo produz o validador, então eles não têm como discordar.

Veja na prática

Declare o DTO uma vez. O descritor dele dá a você .parse (valida um valor não confiável e o converte no tipo) e .is (um type guard), sem mais nada para escrever:

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}
o que você não escreveu 
// No zod schema:
const NewTask = z.object({
  title: z.string(),
  done: z.boolean(),
});
// No drift between the type and
// the validator, because there is
// only one declaration.

// A bad body, {"title": 123},
// takes the Err arm. Only a
// well-formed body reaches Ok.

Mantenha o valor tipado depois do match

Você também pode tirar o valor para fora, em vez de fazer o trabalho dentro do braço.

api.glyph: o valor sai do match tipado 
let task = match NewTask.parse(req.body) {
  Ok(t) => t,
  Err(issues) => { return bad_request(issues) },
}
task.titel   // E0210: type `NewTask` has no field `titel`; did you mean `title`?
desde a 0.1.45tipos genéricos: ainda não
Detalhes como o tipo é carregado, e a exceção dos genéricos

T.parse tem o tipo Result<T, Array<Issue>> e um match cujos braços concordam carrega o tipo deles, então let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, } dá a você um NewTask pelo resto da função, com os nomes dos campos verificados pelo Glyph, e não pelo tsc sobre o TypeScript gerado. Isso chegou na 0.1.45; antes, o valor perdia o tipo assim que saía do match. O parse de um tipo genérico é o único que ainda não carrega o tipo, porque o descritor dele recebe um verificador de runtime por parâmetro de tipo.

O resultado do parse é um Result comum

Em Glyph T.parse retorna o mesmo Result que toda função falível da linguagem retorna, então você o devolve direto, passa por map_err para transformar os problemas de validação no seu próprio tipo de erro, ou o propaga com ?.

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}
o que isso substituiu 
// Until 0.1.52 the generated descriptor

// tsc errors (TS2322 and TS2339) even

Detalhes o custo em runtime de usar Result aqui

Um validador que devolve um valor num formato próprio e privado só serve pela metade, porque o resto do seu tratamento de erros não consegue mexer nele. Não há nada de especial num resultado de parse.

O motivo de já ter sido diferente: um descritor é gerado ao lado do seu type, e emitir o objeto puro evitava que um módulo que declara um tipo dependesse de std/result em runtime. Essa troca agora é feita no sentido oposto. Um módulo com um pub type carrega um import de std/result mesmo que nunca escreva Result, e uma chamada a parse aloca as closures de combinadores que qualquer Ok(...) aloca. Em troca, a fronteira validada e o resto do seu tratamento de erros são a mesma API.

Compondo os seus: o tipo de saída é derivado, não presumido

O infer_output<Shape> do Glyph deriva o tipo de saída a partir do shape, e o tsc confere a sua anotação contra ele. Um shape que omite um campo do tipo que você declara não compila:

schema.glyph 
fn object_schema<Shape: Record<string, Schema<unknown>>>(
  shape: Shape,
) -> Schema<infer_output<Shape>> { ... }

type User = { name: string, age: number }

// The shape must produce a User, or this
// line does not compile:
const user_schema: Schema<User> =
  object_schema({
    name: string_schema(),
    age: number_schema(),
  })
a divergência que o Glyph elimina 
// TS/zod: shape and output type are two
// separate things you keep in sync by hand.
const s = z.object({ name: z.string() });
type User = { name: string; age: number };
// `s` is inferred { name }, but nothing
// checks it against User. The `age` you
// forgot is caught at runtime, if ever.

// Glyph: drop `age` from the shape and
// `Schema<User>` fails to compile. The
// shape is the single source of truth.
Detalhes a armadilha do TypeScript, e o cast que segue o return desde a 0.1.92

Às vezes você quer um combinador no estilo do zod: montar um validador compondo outros menores. A armadilha em TypeScript é que o tipo de saída do combinador e o shape que você passou para ele se distanciam. Você escreve o shape, depois se repete num segundo parâmetro de tipo, e nada confere se os dois concordam.

O tipo derivado vale independentemente de como o combinador retorna. O infer_output precisa de um cast na fronteira da função, porque o corpo monta um valor que o sistema de tipos não consegue provar que tem o tipo derivado do shape, e o compilador escreve esse cast para você. Até a 0.1.91 ele ficava preso a um return <value> simples. Coloque um match entre o return e o valor, ou termine o corpo em r?, e a mesma função deixava de compilar: um TS2322 contra o TypeScript gerado, sobre um Glyph que o compilador já tinha aceitado. Desde a 0.1.92 o cast segue o return, e não a forma como ele está escrito, então return match strict { ... } passa na checagem de tipos igual à forma com um único return do mesmo corpo.

O resto da fronteira não confiável

O descritor é o mesmo que torna seguro o json.parse<T>: passe uma string JSON e ele faz o parse e valida num passo só.

EntradaChamadaRetorna
Uma string JSONjson.parse<T>(text)Result<T, Array<Issue>>
Um body já decodificadoT.parse(value)Result<T, Array<Issue>>
Um headerheader(req, name)Option<string>
Um parâmetro de queryquery_param(req, name)Option<string>
Detalhes bodies de requisição, headers e parâmetros de query

Um body de requisição chega já decodificado como unknown, então ali você usa T.parse(value): mesma garantia, sem cast.

O resto da fronteira não confiável é tipado do mesmo jeito: header(req, name) e query_param(req, name) retornam Option<string>, então um header ou parâmetro de query ausente é None e o match obriga você a tratar o caso. Omita o braço None e não compila. Uma entrada ausente não pode ser lida como se estivesse presente. Um campo do body segue a mesma regra: timeout_ms?: number é uma chave ausente ou um número, então {"timeout_ms": null} é um Err em ["timeout_ms"], vindo de T.parse, de is T e de json.parse<T> igualmente. Declare timeout_ms?: Nullable<number> quando quem envia escreve null. Até a 0.1.152 esse null voltava dentro do Ok.

Um map com chaves de um enum verifica as chaves?

Sim, desde a 0.1.148. Um Record<Tier, int> com type Tier = "free" | "pro" só aceita no parse um objeto cujas chaves são exatamente free e pro: uma chave a mais e uma faltando são ambas um Err, que é também o que o tsc diz sobre o mesmo objeto escrito como literal.

Tipo da chaveO que o parse verifica em cada chave
Uma union de string literalsexatamente as chaves listadas, nenhuma faltando, nenhuma sobrando
Uma string ou um número refinados com whereo predicado
inta escrita simples de um número inteiro; "01" e "1.5" falham
stringnada de novo
Detalhes chaves refinadas e int, e o que o verificador garante

Um tipo de chave refinado com where roda o predicado em cada chave, e uma chave int precisa ser a escrita simples de um número inteiro, então "01" e "1.5" são recusados. Um Record<string, V> é verificado exatamente como antes. Um where não pode refinar uma union de string literals (type T2 = Tier where value != "pro" é E0300 desde a 0.1.152); escreva os membros que você quer como uma union própria, type T2 = "free", e ela serve de chave para um Record com a mesma verificação de chaves exatas. Desde a 0.1.153 o verificador do próprio Glyph também cobra a chave de um valor que você escreve no código: um Record<string, int> não serve onde um Record<Tier, int> está declarado, nem o contrário, então a passagem é um json.parse ou um braço is Record<Tier, int>, e record.set mantém a chave que recebeu. Um record genérico com chaves do seu próprio parâmetro de tipo é recusado, a menos que esse parâmetro seja string.

Se eu fizer o parse de uma data, recebo uma data de verdade?

Sim, e a parte interessante é o que você recebe de volta quando a entrada não é uma data. time.parse_iso retorna Option<number>, e o resultado é None para tudo o que não for ISO-8601.

aceito 
"2026-01-03"              // UTC midnight
"2026-07-25T18:33:08.000Z"
"2026-03-15T09:30:00-05:00"
"2028-02-29"              // a real leap day
None, todos eles 
"January 5 2026"   // not ISO
"2026-1-3"         // not padded
"2026-13-01"       // no month 13
"2026-02-31"       // no such day
"2026-02-29"       // not a leap year
"2026-01-03T10:00" // no offset

O último é o que surpreende as pessoas, e é justamente esse o ponto. Um datetime sem Z e sem offset +HH:MM é horário local pela gramática do ECMAScript, então aceitá-lo significaria que a mesma string indica um dia diferente do calendário dependendo da máquina que rodou o programa.

Detalhes o que o Date.parse faz no lugar, e por que UTC

É uma garantia mais forte que a do Date.parse do JavaScript, que aceita texto livre ("January 5 2026"), lê uma data sem zeros à esquerda como "2026-1-3" no fuso horário em que o processo estiver rodando, e reporta um dia impossível como sucesso, empurrando-o para frente: "2026-02-31" vira 3 de março, e você recebe um número de volta sem nenhum sinal de que algo aconteceu.

Os acessores de calendário do Glyph (time.year, time.month, time.day) são em UTC e dizem isso, e um validador que importasse em silêncio o fuso horário da máquina os faria mentir. Então a string é rejeitada, e você decide o que ela queria dizer.

A proteção foi para dentro da primitiva

Quando uma aplicação escreve uma proteção de correção em volta de uma primitiva da biblioteca padrão, essa proteção pertence à primitiva. Isto é o que o app apagou:

antes: o app protege a stdlib 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
depois: a primitiva segura a linha 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

O import std/regex foi junto. Mesmo razão contábil, mesmas linhas rejeitadas, mesmo relatório byte a byte.

Histórico o app de relatório de despesas de onde isso veio

Isso surgiu ao escrever uma CLI de relatório de despesas em Glyph. Cada linha do razão tem uma data, e lançar uma linha no mês errado é o bug que importa, então o app não confiava no antigo parse_iso: primeiro conferia o formato com uma regex, depois convertia o timestamp de volta para texto para pegar um dia que tivesse sido empurrado para frente.

Você nem precisa escrever os tipos

Se o formato já existe numa spec OpenAPI ou num arquivo de declaração TypeScript, gere os tipos Glyph a partir dele: declarações type reais, commitadas e que dá para achar com grep, cada uma com seu descritor, e não um tipo fantasma inferido:

a partir de uma spec OpenAPI / JSON Schema 
glyph gen openapi petstore.yaml \
  --out src/
a partir de um pacote instalado, pelo nome 
glyph gen dts api-types \
  --out src/types

Um tipo de wire vira uma fronteira validada, sem nada escrito à mão:

webhook.glyph 
import types/api_types { Customer }

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),
  Err(issues) => reject(issues),
}

A geração é fiel ao wire: o que a spec diz sobre um valor é o que o parse verifica.

Na spec ou no .d.tsGlyph gerado
Um enum de stringsuma union de string literals; o parse verifica se o valor pertence a ela
Um campo integerint; um 3.5 vindo do wire falha
Um schema de objetoum record marcado com @open; estrito com additionalProperties: false
interface Page<T>type Page<T>, cada item verificado como T
Uma union não discriminadaestreitada, com uma nota impressa
Um nome em dois arquivos alcançáveissinalizado com uma nota, sem vincular
Detalhes o que é materializado hoje, regeneração, tipos genéricos

Aponte o glyph gen dts para um arquivo .d.ts ou, como acima, para um pacote npm instalado pelo nome: ele resolve a entrada de declarações do próprio pacote em node_modules e escreve tipos commitados que você importa.

O que é materializado hoje: o gen dts lê as declarações interface e type que um pacote exporta, inclusive as que estão dentro de uma árvore declare namespace (referências cruzadas sem qualificação são resolvidas pelo escopo) e as de arquivos vizinhos que um barrel index reexporta (o .d.ts de entrada e todo .d.ts importado por caminho relativo são percorridos). Um genérico continua de primeira classe: interface Page<T> é materializada como type Page<T> e ganha um descritor que valida cada item como o seu argumento de tipo, e não só a presença. Reexports com alias e export * as são resolvidos por um mapa de bindings por arquivo. O único caso que ele não consegue tornar seguro, um nome de tipo que colide entre dois arquivos alcançáveis, ele sinaliza com uma nota em vez de vincular o formato errado em silêncio. Para o que o materializador não alcança, escreva à mão os formatos que cruzam a fronteira, ou use a válvula de escape extern_ts.

A regeneração é idempotente, então uma mudança na spec vira um diff limpo e revisável. A geração é fiel ao wire: um enum de strings é materializado como uma union de string literals ("free" | "pro"), então o parse verifica se o valor pertence a ela, e não só se é uma string, e um match sobre ela é exaustivo sem um else. Um campo integer vira int, então um 3.5 vindo do wire falha no parse onde um number comum passaria. Onde uma construção não tem forma exata em Glyph (uma union não discriminada), ele estreita o tipo e imprime uma nota, em vez de gerar um validador que rejeitaria dados reais. Os records gerados também levam @open, então o parse tolera um campo que a API adicione depois e continua validando todos os campos que declara; um schema que define additionalProperties: false continua estrito. Records são estritos por padrão em Glyph, e esse é o mesmo marcador no local da declaração, que dá para achar com grep, que um record escrito à mão usaria, então nada muda no que um record significa.

Tipos genéricos também são validados. Um Paginated<T> ganha um descritor cujo parse recebe o argumento de tipo: Paginated.parse<User>(body) verifica cada entrada de items como um User, e não só a presença, e match v { is Paginated<User> => ... } estreita do mesmo jeito. Isso vale através das fronteiras de módulo: defina Paginated<T> num arquivo, faça import dele em outro, e lá tanto Paginated.parse<User>(body) quanto is Paginated<User> continuam verificando cada elemento como um User. O compilador monta a verificação por elemento a partir do argumento de tipo no local da chamada, então o arquivo onde o tipo genérico mora não faz diferença no que é validado.

Onde para: os descritores cobrem os formatos de que a maioria dos payloads é feita: objetos, primitivos, arrays, referências, campos opcionais e nullable, e agora tipos genéricos numa dada instanciação. Um tipo que o Glyph não gerou (um pacote externo ou um .d.ts que você só importa) passa pela checagem de tipos, mas não tem descritor até você materializá-lo, o que agora é um comando contra o pacote instalado (glyph gen dts <package>, para as interfaces e type aliases de nível superior que ele exporta). Essa fronteira é deliberada: um tipo que o Glyph não emitiu não pode prometer validação em runtime, então você opta por pacote e o resultado fica commitado e acessível ao grep, e não conjurado a cada build.

O banco de dados também é uma fronteira

Uma linha lida de um banco de dados é não confiável exatamente do mesmo jeito que um body de requisição. O mesmo .parse que você usa num body de requisição valida uma linha.

tasks.glyph 
type Task    = { id: int, title: string, done: bool }
type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.
match TaskRow.parse(row) {
  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}
o bug que isso elimina 
// TS, better-sqlite3 / node:sqlite:
const row = stmt.get(id) as Task;
// `row.done` is really 0 or 1, a number.
// Nothing complains. Then:
if (row.done === true) { ... }   // never runs

// The row was `unknown`; the cast invented
// a type. Glyph makes you validate the row
// into TaskRow, and the int-to-bool step is
// a line of code, not a silent lie.
Detalhes std/sqlite, e o booleano 0 ou 1

Uma linha lida de um banco de dados é não confiável exatamente do mesmo jeito que um body de requisição: o schema do banco e a ideia que o seu código tem da linha podem discordar, e um cast (row as Task) esconde isso. O std/sqlite, o módulo de banco de dados sobre o SQLite embutido do Node, assume isso. Uma query retorna Array<Record<string, unknown>>, então não há como tratar uma linha como Task sem validá-la antes.

Isso pega um bug que vai para produção o tempo todo. O SQLite não tem tipo booleano, então uma coluna done volta como o inteiro 0 ou 1. Faça cast da linha para um record com um campo bool e task.done === true nunca é verdadeiro, sem aviso nenhum. Em Glyph o formato de armazenamento e o formato de domínio são tipos separados, e o mapeamento entre eles é uma linha que você vê:

Tudo isso é um exemplo que funciona: examples/apps/tasks/main.glyph é uma API de tarefas persistida, com std/sqlite para armazenamento e std/http para as rotas, com dados que sobrevivem a um restart e validação tanto do lado do wire quanto do banco. Nenhum validador escrito à mão em lugar nenhum.

Um webhook assinado também é uma fronteira

Verificar a assinatura de um webhook exige os bytes exatos que o remetente assinou, não uma cópia reserializada (reconverter em string um body já parseado muda espaços em branco e a ordem das chaves, então o HMAC nunca bateria). http.raw(req) entrega esses bytes, então a verificação fica em Glyph: 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
Detalhes bytes brutos para a assinatura, body parseado para o formato

req.body continua sendo o valor parseado para a verificação de formato; raw é o payload intacto sobre o qual a assinatura é calculada. Um receptor que verifica uma assinatura e valida o body não precisa de TypeScript escrito à mão.

Um tipo pode validar seus invariantes, não só o seu formato

Uma verificação de formato diz que um campo é um número. Ela não diz que o valor não é negativo, nem que a nota está entre 1 e 5. Um refinamento where coloca esse invariante no tipo, e o descritor o garante na fronteira:

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
o que você não está escrevendo 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.

Situação atual

Disponível hoje 10

Descritores

  • Todo record e toda union etiquetada declarados levam um descritor de runtime (.parse, .is, .schema), records genéricos incluídosuma union etiquetada genérica não leva
  • .parse retorna o mesmo Result que o resto da linguagem usa, então se compõe com map_err, com ? e com qualquer função que retorne um
  • Um refinamento where (int where value >= 0) valida um invariante na fronteira, não só um formato
  • json.parse<T> valida JSON
  • infer_output<Shape> deriva o tipo de saída de um combinador a partir do seu shape, para que os dois não se distanciem

Geração

  • glyph gen openapi / glyph gen dts geram tipos commitados, com descritor, a partir de uma spec, de um .d.ts ou de um pacote instalado pelo nome

Fronteiras

  • std/sqlite devolve as linhas como unknown, então o banco de dados é uma fronteira validada como qualquer outra
  • Um receptor de webhooks assinados fica inteiro em Glyph
    Detalhes

    http.raw(req) expõe o body da requisição sem parse, então a assinatura de um webhook é verificada sobre os bytes exatos e um receptor de webhooks assinados fica inteiro em Glyph.

  • Entrada não confiável não chega a um sink de SQL ou de shell sem sanitize
    Detalhes

    Os tipos Tainted/Trusted do std/taint impedem que entrada não confiável chegue a um sink de SQL ou de shell sem um sanitize explícito, então o tsc rejeita um caminho de injeção em tempo de compilação.

  • time.parse_iso aceita ISO-8601 e nada mais
    Detalhes

    As primitivas de fronteira menores seguem a mesma regra: time.parse_iso aceita ISO-8601 e retorna None para texto livre, para um dia impossível e para um datetime sem offset, que de outra forma seria lido no fuso horário local da máquina.

A caminho 3

  • Unions discriminadas são geradas a partir de uma spec e de um .d.ts; cobertura de enums e mapped types em seguida
    Detalhes

    Unions discriminadas agora são geradas tanto a partir de um discriminator do OpenAPI quanto de uma union de um .d.ts TypeScript (um dispatcher parse_<Name> lê a tag e valida para a variante certa). Próximo passo: cobertura mais completa de enums e mapped types.

  • Código de cliente e servidor tipado a partir de uma spec já está disponível Veja cliente e servidor
  • Um timestamp e uma duração são ambos number
    Detalhes

    Em datas, o rigor é a funcionalidade inteira, e ele para no parse: parse_iso devolve milissegundos desde a epoch, então um timestamp e uma duração são ambos number e nada impede você de somar um ao outro. Um tipo de data distinto é uma decisão para depois, e não uma pequena.
