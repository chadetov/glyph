Casos que o TypeScript deixa passar

Detectado antes de ir para produção

No total são 52 casos verificados: 37 casos de TypeScript, 5 armadilhas de JavaScript que não existem em Glyph e 10 brechas que o Glyph ainda não fecha. O Glyph recusa 28 deles no build (23 casos de TypeScript e 5 armadilhas).

Todos os exemplos de TypeScript da lista passam no tsc --strict sem erros. Cada um também é verificado contra um projeto configurado no máximo: todas as flags do compilador mais rígidas que --strict, mais o typescript-eslint strictTypeChecked. Em 21 dos 37 casos, nada nessa configuração detecta o problema. Uma flag do compilador que vem desativada por padrão detecta 5, e uma regra de lint detecta 11. Um projeto precisa ativar cada uma delas, e um agente pode desativá-la de novo. No Glyph, nenhuma delas é uma opção de configuração.

Cada entrada são dois programas em catches/, e a saída embaixo de cada um é o que as ferramentas imprimiram. Um gate do build, scripts/check_catches.py, roda cada caso de novo e falha se qualquer uma das metades deixar de fazer o que a página diz. A configuração completa de TypeScript usada na comparação está nesse script.

2

Um caso que ninguém tratou

Probabilidade 5 de 5Gravidade 4 de 5

Um agente adiciona um status "archived". O handler que anuncia cada status foi escrito antes de ele existir.

TypeScriptcompila sem nenhum aviso
ts.ts
switch (s) {
  case "todo":
    console.log("not started");
    break;
  case "doing":
    console.log("in progress");
    break;
  case "done":
    console.log("finished");
    break;
}
$ tsx ts.ts
finished
archived logged nothing

Arquivar um item não loga nada. Nada diz que o switch está desatualizado.

Só lintdetectado pela regra de lint switch-exhaustiveness-check

Glyphrecusado no build
glyph.glyph
match s {
  "todo" => print("not started"),
  "doing" => print("in progress"),
  "done" => print("finished"),
}
$ glyph build
[E0200] Error: typecheck: non-exhaustive match on `"todo" | "doing" | "done" | "archived"`: missing variants "archived"
Help: Add an arm for each missing variant.

O build para e diz qual é o caso.

O TypeScript só verifica se um switch cobre todos os casos quando a função retorna um valor em todo branch, ou com o idioma assertNever. Um handler que não retorna nada não tem nenhum dos dois. Em Glyph, todo match precisa cobrir todos os casos, então adicionar uma variante lista cada lugar que precisa mudar.

Confiar em find com !

Probabilidade 5 de 5Gravidade 4 de 5

Buscar um registro pelo id.

TypeScriptcompila e depois quebra em tempo de execução
ts.ts
return users.find((u) => u.id === id)!.name;
$ tsx ts.ts
TypeError: Cannot read properties of undefined (reading 'name')

! diz ao compilador "confia em mim". Em tempo de execução não faz nada.

Só lintdetectado pela regra de lint no-non-null-assertion

Sem o !, o tsc --strict recusa esta linha. É o ! que desliga essa verificação, e ele não faz nada em tempo de execução. O Glyph não tem !.

Probabilidade 4 de 5Gravidade 4 de 5

Verificar cada usuário com uma chamada async de permissão.

TypeScriptcompila e depois dá a resposta errada

5 armadilhas de JavaScript que não existem em Glyph

Armadilhas mais antigas em que os agentes ainda caem de vez em quando. O Glyph recusa cada um desses programas, mas não porque encontra o erro: o recurso por trás dele não existe na linguagem, e o substituto é indicado.

  • "10,20,30".split(",").map(parseInt) dá [10, NaN, NaN], porque map passa o índice como base numérica. O Glyph tem number.parse, que retorna um Result. Abrir no playground
  • Uma regex /g reutilizada com .test falha um match sim, um não, porque guarda o lastIndex. O Glyph não tem objetos de regex; regex.matches(pattern, text) não tem estado. Abrir no playground
  • [1, 2, 3].forEach(counter.increment) roda o método sem o seu objeto. O Glyph não tem classes nem this. Abrir no playground
  • Math.max(...[]) é -Infinity. O array.max do Glyph retorna um Option, vazio para uma lista vazia. Abrir no playground
  • Array(3).map(...) retorna três buracos, porque map pula os buracos. O Glyph não tem Array(n); arrays são escritos como literais. Abrir no playground

O que o Glyph ainda não detecta

10 falhas que o Glyph ainda não fecha. Cada uma compila em Glyph hoje e faz a mesma coisa errada que em TypeScript. Todas têm uma reprodução em catches/ e um número de gap aberto, e o gate falha quando uma correção entra, para que a entrada não sobreviva à falha.

  • requested || 3 transforma um 0 legítimo em 3. G386
  • "Welcome back, ${user}!" com um record imprime [object Object]. G385
  • forEach(async ...) descarta todas as promises, então o trabalho termina depois do código que depende dele, e nada avisa. G384
  • xs.sort(...) dentro de um helper reordena o array de quem chamou, e nenhum mut marca isso. G380
  • .sort() em números ordena como texto: 100,25,9. G388
  • Uma query SQL montada com ${name} é aceita pelo std/sqlite. G387
  • Uma atualização perdida através de await em c[0], enquanto a mesma escrita em um campo é recusada. G390
  • input + 1 em uma string, users.find(...).name e a leitura de um campo em unknown só são detectados pela etapa do tsc, não pelo checker do próprio Glyph, então o editor e as ferramentas de agente não os veem. G381, G382, G392

Erros de lógica são a maior categoria em todo estudo sobre código escrito por agentes, e nenhum verificador de tipos os enxerga: uma fórmula errada, ou uma tarefa mal entendida, compila em Glyph assim como compila em TypeScript.

O Glyph tem uma única válvula de escape, extern_ts, para o TypeScript que ele não consegue expressar. É uma palavra-chave fixa, então grep extern_ts lista todos os lugares onde as regras ficam suspensas.
