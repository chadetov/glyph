Como o compilador é feito, e como ajudar

O compilador é um workspace Rust com doze crates num repositório público, com licença MIT ou Apache-2.0. Relatos de bug com uma reprodução pequena são o que mais ajuda hoje. Uma mudança na linguagem começa como uma issue, porque toda regra remete a uma decisão de design numerada.

O pipeline#

O glyph build faz o lex, o parse, resolve nomes, checa tipos e emite TypeScript, depois roda tsc --strict no que escreveu. As etapas do meio rodam como queries incrementais no salsa, então uma nova checagem reaproveita os resultados que uma edição não invalidou.

um arquivo .glyph, passando pelos crates 
glyph-lexer → glyph-parser → glyph-resolver → glyph-typechecker → glyph-emit → tsc --strict
                (glyph-ast)        └──────── glyph-db (salsa) ────────┘
CrateO que faz
glyph-lexerTokens, palavras-chave, quebras de linha significativas, template literals
glyph-astTipos da árvore sintática, com um trecho do código-fonte em cada nó
glyph-parserParser Pratt para cada decisão da especificação, JSX incluído
glyph-resolverResolução de nomes, o grafo de módulos, checagens de import entre módulos, o prelude
glyph-dbO pipeline de queries do salsa e a invalidação entre arquivos
glyph-typecheckerExaustividade, ?, genéricos, owned, descritores de runtime, o modelo da stdlib
glyph-emitO gerador de TypeScript, a geração de descritores, source maps no nível de expressão
glyph-formatterglyph fmt: um único layout, preserva comentários, idempotente
glyph-lspO language server e o servidor MCP, compartilhando uma camada de análise
glyph-cliO binário glyph e todos os subcomandos
glyph-wasmO compilador em WebAssembly, que roda o playground
glyph-runtimeUm esboço; os testes rodam pelo emissor e pelo tsx

O glyph-compiler/README.md tem as notas completas de cada crate e a contagem atual de testes.

Compilar e testar#

O Rust 1.95 está fixado em rust-toolchain.toml. Alguns testes chamam tsc e tsx, então instale esses também. O CI roda o clippy com warnings tratados como erros, e nem cargo build nem cargo test o rodam, então rode o script antes de dar push.

a partir de um clone 
npm install -g tsx typescript
cd glyph-compiler
cargo build --release -p glyph-cli      # target/release/glyph
cargo test --workspace
cd .. && python3 scripts/check_clippy.py  # the exact clippy command CI runs

# after an intentional syntax-tree change
INSTA_UPDATE=always cargo test -p glyph-parser --test snapshots

Um diagnóstico novo vem com um programa em tests/negative/ que precisa falhar com aquele código. Uma afirmação de que o Glyph detecta algo que o TypeScript deixa passar vai em catches/, onde um gate roda as duas metades.

O que está planejado, e o que está quebrado#

O docs/roadmap/releases.md é o roadmap de releases: o que cada release publicada fez e para que servem as próximas. O docs/dogfooding-gaps.md é o registro de gaps, cada limitação encontrada ao construir aplicações reais, cada uma numerada (G mais um número) com um marcador de status. Um gap aberto com reprodução é um bom ponto de partida.

Issues e pull requests#

Correções de toolchain, diagnósticos, documentação e exemplos podem ir direto para um pull request. Uma mudança de sintaxe ou semântica começa com uma issue, e as maiores passam pelo processo de RFC em docs/rfcs/; um PR que relaxa uma regra "para ajudar" provavelmente será recusado, porque a restrição é o objetivo. Mantenha um pull request em um gap só, normalmente de um a três commits, e assine cada commit (git commit -s). A main é protegida e os merges são só por rebase. O CONTRIBUTING.md tem as regras completas, e as issues com o rótulo good first issue são pensadas para uma primeira mudança.
