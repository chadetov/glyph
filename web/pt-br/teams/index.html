Para times

O que garante, quanto custa adotar e como sair

O Glyph recusa uma lista específica e verificada de casos que um projeto TypeScript strict aceita, e compila para TypeScript que você pode manter se parar de usá-lo. É uma versão preliminar: pré-1.0, mantida principalmente por uma pessoa e com várias releases por semana.

O que garante#

Toda afirmação sobre o que o Glyph detecta é um caso no diretório catches/ do repositório: o mesmo programa em TypeScript e em Glyph, os dois rodados por um gate de CI. No total são 45 casos verificados: 37 casos de TypeScript, 5 armadilhas de JavaScript que não existem em Glyph e 3 brechas que o Glyph ainda não fecha. O Glyph recusa 28 deles no build (23 casos de TypeScript e 5 armadilhas). Dos erros que ele não recusa, 3 geram um aviso, 9 são dados ruins barrados numa checagem de fronteira em runtime e 2 param em tempo de execução. Os que mais pesam para quem revisa código escrito por agentes:

CódigoO que é recusado
E0200Um match que deixa de fora um caso de uma union, então adicionar um caso lista todos os lugares que precisam mudar
E0013Um cast (as, as unknown as); não existe cast, nem any
E0204JSON parseado atribuído a um nome tipado sem ser verificado
E0224Uma leitura de um map tipada como se a chave sempre existisse
E0217Um Result ignorado (um aviso; let _ = diz que foi de propósito)

A página de casos lista cada caso com seu TypeScript, seu Glyph e o erro, e diz quais deles uma configuração completa do typescript-eslint também teria pegado.

Onde para#

As garantias cobrem código escrito em Glyph. Uma exceção lançada dentro de uma dependência do npm ainda passa por fora do Result, e um tipo importado do .d.ts de um pacote não tem checagem em runtime. Dentro do Glyph, as 3 falhas conhecidas em aberto estão listadas com seus números de gap em o que ele ainda não detecta, e o registro completo está em docs/dogfooding-gaps.md. Para uma comparação com TypeScript strict mais zod, eslint e ts-pattern, incluindo onde essa configuração ainda está na frente, veja por que não TypeScript com ferramentas.

Adotando dentro de um app existente#

Não há reescrita. Você escreve em Glyph a parte que não pode dar errado (modelos, permissões, transições de estado, dinheiro), e o resto do app continua em TypeScript e importa os módulos gerados como qualquer arquivo local. O passo a passo usa um scaffold padrão do Vite: Posso adotar o Glyph dentro da minha aplicação atual?

Como sair#

glyph build gera TypeScript comum, um arquivo por módulo, que passa no tsc --strict. Se você parar de usar o Glyph, faz commit dessa saída e segue com tsc. A licença é MIT ou Apache-2.0, então um fork é sempre possível. Para quem vem do TypeScript mostra um módulo ao lado do arquivo gerado.

Versão fixada e upgrades#

glyph init fixa o compilador numa versão exata no package.json, sem ^, então nenhuma release chega ao seu build por acidente. Três comandos cuidam do resto:

fazendo upgrade de propósito 
glyph doctor     # your version against the latest release; never fails CI for that
glyph upgrade    # moves the project's pin, runs npm install, links the notes
glyph --update   # moves the installed compiler itself

Detalhes em Uma release nova do Glyph vai quebrar meu build?

O que uma release Breaking costuma significar#

Em geral, que o compilador passa a recusar um programa que já estava errado. A 0.1.159 recusou ids.forEach(async fn(id) { await save(id) }): forEach não espera o callback, então cada save rodava por conta própria e uma falha em um deles se perdia. A 0.1.162 recusou array.find(xs, f) ?? 0: um Option nunca é null, então o valor padrão nunca se aplicava e o resultado era o próprio Option. Algumas apertam uma regra. Desde a 0.1.160, uma chamada que altera um array no lugar, como xs.push(4), precisa ser escrita como uma instrução mut, então código que funcionava teve de mudar de grafia (glyph fix insere o mut).

Uma release só chega ao seu projeto quando você move a versão fixada. Se um upgrade recusar código que você ainda não pode corrigir, fique na versão que tinha, já que versões publicadas nunca são retiradas. O TypeScript que o seu último build emitiu compila só com tsc, então continua utilizável aconteça o que acontecer com o compilador.

Frequência de releases e a marca Breaking#

A página de versões tem uma entrada para cada release da 0.1.0 à 0.1.180, 179 no total, e 53 delas saíram entre 1 nov 2026 e 24 nov 2026. Uma release é marcada como Breaking quando recusa um programa que a versão anterior aceitava, que é como a maioria das correções de corretude chega. 60 entradas têm a marca. Ela é aplicada rodando o menor programa afetado nas duas versões, não lendo o diff, e as releases anteriores à 0.1.99 não foram testadas assim, então uma release antiga sem marca não foi testada, o que não quer dizer que seja segura.

O que uma release Breaking custou na prática: cada nota recente diz o que aconteceu quando a versão antiga e a nova foram rodadas sobre os apps de exemplo do repositório. Estas são as releases Breaking mais recentes, citadas das próprias notas:

  • 0.1.180: A nota não diz.
  • 0.1.179: “Without a fix, five of the example apps would have been refused for writing a different directory into dir.”
  • 0.1.177: A nota não diz.
  • 0.1.176: A nota não diz.
  • 0.1.175: A nota não diz.
  • 0.1.174: A nota não diz.

Os apps de exemplo são código do próprio projeto, mantido compilando release após release, então um formato recém-recusado tem menos chance de aparecer neles do que no seu código. Cada nota diz quais formatos recusa, então leia antes de fazer o upgrade.

Status#

O Glyph é pré-1.0. Antes da 1.0, a sintaxe, a biblioteca padrão e o formato do TypeScript gerado podem mudar, e uma release pode recusar código que compilava antes. docs/stability.md diz o que pode mudar e o que é mantido estável. MAINTAINERS.md diz com clareza que hoje o projeto é mantido principalmente por uma pessoa.

Objeções, respondidas#

Não usamos muita IA. Ainda vale a pena?

As checagens são as mesmas não importa quem escreve o código: menos surpresas em runtime, diffs menores, código que dá para buscar com grep.

 Já usamos TypeScript strict e lint.

Cada uma dessas checagens é opcional e pode ser desligada com uma linha. As do Glyph não podem.

 Nossos agentes conseguem escrever uma linguagem que quase nunca viram?

A maior parte do que um modelo sabe de TypeScript se aproveita, e o compilador aponta o resto.

 Por que compilar para TypeScript?

É onde estão o npm, o React e o Node, e é por isso que dá para adotar um arquivo de cada vez.

 O que o plantão vê quando algo quebra?

TypeScript legível, source maps de volta para o arquivo .glyph e códigos de erro estáveis.

 Como sabemos que tudo isso é verdade?

Como cada afirmação deste site é verificada, e como reproduzir uma você mesmo.
