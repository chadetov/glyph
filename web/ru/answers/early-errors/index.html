Почему это важно

Glyph компилируется в TypeScript, а затем проверяет типы результата через tsc --strict, так что ошибка, которую Glyph не моделирует, не теряется. Она возвращается на шаг позже, сформулированная в терминах сгенерированного файла: TS1308, указывающий на await в функции, которую вы не писали, или TS2366 о switch, которого вы не писали.

Строка отображается обратно в ваш .glyph, а объяснение нет. В этом зазоре компилятор перестаёт учить.

Поэтому каждое правило, которое Glyph может проверить сам, переносится раньше:

  • E0222await вне async fn
  • E0223ветка match, которая не даёт значения, когда match используется как значение
  • E0008Присваивание без mut

Каждая ошибка называет правило, ссылается на стоящее за ним решение и показывает код до и после.

Ветка, которая не даёт значения

До этого сгенерированный switch проваливался мимо своих case, и text содержал undefined, хотя его тип говорил string. tsc ловит одни формы этой ошибки и пропускает другие.

Теперь Glyph решает это везде, где позиция позволяет: в let, в mut, в return или в последнем выражении функции, объявляющей тип возврата. В match на уровне инструкции X => {} остаётся намеренным no-op, которым он и является.

await вне async fn

С await то же самое. В Glyph нет видимого пользователю Promise: async fn -> T при ожидании даёт T, поэтому await в любом другом месте нечего приостанавливать.

glyph build, для `fn total() -> number { return await fetch_count() }` 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

// before: no Glyph diagnostic, then
dist/main.ts:14:18 - error TS1308: 'await' expressions are only allowed
within async functions and at the top levels of modules.
Подробнее какая вызываемая конструкция решает

Раньше это была ошибка tsc TS1308 в сгенерированном файле. Теперь это E0222, и решает ближайшая охватывающая вызываемая конструкция, так что синхронная лямбда внутри async fn образует свой контекст, по тому же правилу, что и в TypeScript. Обратная ошибка, вызов, который никто не ждёт, это E0238: save(1) отдельной строкой, let _ = save(1) и let n: number = load() отклоняются, потому что вызов начинается, а программа идёт дальше без него. Синхронный колбэк, который хочет запустить работу и забыть о ней, пишет task.detach(async fn() -> void { await save(1) }); это сообщает об ошибке в stderr.

Присваивание без mut

Третья касается правила, которое нарушают в первый же день. Glyph помечает каждое изменение, поэтому переприсваивание привязки пишется mut x = e, а её введение let x = e.

E0008E0302E0303

Голое x = e раньше давало «unexpected token: Equals», что называет символ, а не правило. Теперь это E0008, и glyph --explain E0008 объясняет, зачем нужна пометка: каждое место, где меняется значение, начинается с mut, так что grep "mut total" находит их все.

Подробнее оператор ?, E0302 и E0303

Оператор ? получает то же обращение с другой стороны. ? раскрывается в привязку плюс ранний return, поставленный перед инструкцией, в которой он находится, поэтому ему нужна инструкция, в которую можно раскрыться. Он работает в let, в return, в аргументе, а теперь и в теле ветки match. Там, где он работать не может, сообщение говорит, что это за позиция и как вынести значение в привязку (E0302 и E0303), вместо того чтобы утверждать, что оператор не реализован.

Случай хуже: когда tsc тоже доволен

Ошибка tsc не в том месте раздражает. Чистая сборка программы, которая означает что-то другое, это настоящая проблема, и в Glyph такая была.

Каждое объявленное вами имя верхнего уровня попадает в сгенерированный модуль как есть, включая конструкторы вариантов размеченного объединения, поэтому вариант с именем Error даёт export function Error(...) на верхнем уровне модуля. И new Error(...), который компилятор пишет ниже, вызывает уже ваш вариант.

glyph build, для union с вариантом `Error` 
[E0110] `Error` cannot name a type, variant, or function: the emitted module
        references the JavaScript global `Error`, and this declaration would
        shadow it
 5 │   | Error(string)
   │     ──────┬─────
   ╰─ Rename it (e.g. `Error` -> `Failure`). The name is legal TypeScript, so
      nothing downstream catches the rebinding.

// before: no Glyph diagnostic, then, twenty lines later
dist/main.ts:31:12 - error TS2345: Argument of type 'string' is not
assignable to parameter of type ...
E0110E0111E0109
Подробнее type Key = string | number, список защищённых имён, E0111

type Key = string | number это тот же дефект с более дружелюбным лицом. В Glyph A | B объявляет размеченное объединение, члены которого это конструкторы вариантов, поэтому эта строка объявляет варианты с именами string и number. Она компилировалась, проходила tsc --strict и генерировала export const number, который перекрывал пространство имён number из прелюдии. Ничего не падало, пока не упал более поздний вызов number.to_string.

Ошибка указывает на объявление, потому что переименовывать нужно именно там. Защищаемый список берётся из эмиттера, а не из общего списка глобальных объектов JavaScript, и тест проходит grep по эмиттеру и падает, когда появляется новая ссылка на глобальный объект без соответствующей записи. В этом тесте весь смысл: Number был безобиден, пока не вышел int и не начал генерировать Number.isInteger, и именно так этот дефект вообще попал в выпуск. Date, Math и JSON остаются свободными, потому что ничто из генерируемого Glyph их не упоминает.

Для union из примитивов есть отдельный код, E0111, потому что отказ без объяснения ничему не учит. Он говорит, как на самом деле разобралась строка, указывает на именованные варианты и называет extern_ts("string | number") для границы, где вам нужен настоящий union из TypeScript. Каждое имя, которое Glyph не даст использовать, перечислено в docs/reference/reserved-words.md: 32 ключевых слова, 33 зарезервированных слова TypeScript, стоящих за E0109, и список перекрываемых имён, у каждого указано, почему имя занято.

Важно ясно сказать, чего это не делает. Назвать тип или вариант Error по-прежнему нельзя, и электронная таблица, на которой это обнаружилось, из-за этого содержит вариант Cellerr. Программу, которой она хотела быть, по-прежнему нельзя написать; изменилось то, что компилятор теперь говорит об этом на объявлении, а не даёт сборке позеленеть и означать что-то другое.

Подробнее почему имя просто не сделать доступным

Чтобы имя стало доступным, нужно искажать имена Glyph при переходе в TypeScript, а это меняет то, что видят стектрейс, grep по dist/ и рукописная прослойка в extern/, так что тихо такое не исправить.

Неверное сообщение хуже, чем никакого

Список перекрываемых имён начинался с имён, которые эмиттер пишет как значения. В нём не хватало тех, что он пишет как типы, и это дало самую острую версию всей проблемы.

Подробнее почему Issue конфликтует, и Record

parse каждого дескриптора возвращает Result<T, Issue[]>, поэтому сгенерированный модуль пишет Issue независимо от того, писали ли его вы. Объявите в своём модуле type Issue = { path: Array<string>, message: string }, и победит ваш тип, сгенерированные объекты Issue несут поле code, о котором ваш тип ничего не знает, и сборка падает с ошибкой tsc о сгенерированном коде, указывающей куда-то в другое место.

Record попал в список одновременно с ним, причём среди глобальных объектов JavaScript, а не среди имён прелюдии, потому что это встроенный тип TypeScript, и иначе сообщение неверно говорило бы, откуда взялось имя. Тест на расхождение, который проходит grep по эмиттеру, теперь покрывает и встроенные типы, и ему пришлось научиться видеть Issue[] в позиции типа: именно поэтому дефект дошёл до выпуска. Schema, Component и Option остаются допустимыми по тому же правилу, по которому свободен Date: эмиттер пишет их только потому, что вы написали их в аннотации, так что объявление такого имени ничего не перекрывает.

Импорт, из-за которого винили match

Другой случай этого класса касался импорта. Локальный путь импорта разрешается от корня сборки, каталога, который вы передаёте glyph build, а не от каталога импортирующего файла.

glyph build examples/apps, для `import catalog` внутри csvql/ 
[E0104] unresolved import `catalog`: no module `catalog` under the build
        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from
        the importing file's directory (D15)
   ╰─ Build that module's own directory as the root, or spell the import path
      as it reads from the root.

// before: no import diagnostic, then
[E0218] non-exhaustive match on string   // on a match over all four values
Подробнее что сообщалось раньше и как избегаются ложные срабатывания

Соберите охватывающее дерево, и import catalog ничего не находит, а до сих пор об этом ничего не сообщалось. Тип вырождался в unknown, match по нему терял варианты, которые сопоставлял, и вы получали E0218, неполный match, на match, который покрывал все случаи. Сделав то, что просило сообщение, вы добавили бы мёртвую ветку else в правильный код.

Риск такой проверки в том, что она срабатывает на нормальном коде, а проверка импортов, которая поднимает ложную тревогу на каждом пакете из npm, хуже молчания, которое она заменила. Поэтому сборка сначала собирает имена модулей, которые можно разрешить без файла .glyph: каждый declare module "X" в <root>/.types/ и во встроенной прослойке Node, плюс каждый пакет в node_modules проекта. Об имени из этого списка никогда не сообщается, даже если у локального файла случайно такое же базовое имя. Когда у проекта вообще нет node_modules, компилятор не может отличить неустановленную зависимость от опечатки, поэтому сообщает только то, что может доказать: импорт, которому соответствует какой-то файл .glyph под корнем.

Само разрешение не изменилось. Те же программы собираются, те же падают. Изменилось то, что ошибка теперь называет импорт, а не обвиняет match через два файла, и в этом всё дело: компилятор, который называет неверную причину, стоит вам часа на её поиски, а потом и доверия к каждому следующему сообщению.

Называть правило, а не токен

Более тихая версия той же проблемы это ошибка, которая верна и всё равно ничего вам не говорит.

glyph check, раньше и теперь 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.
Подробнее красно-чёрное дерево и как исправление называет вашу программу

Агент, писавший красно-чёрное дерево, потянулся к позиционному конструктору, который есть в каждом языке семейства ML, и парсер остановился на первой запятой с “expected )” и советом “add the expected token”. Если поставить там ), получится другая программа, а не работающая. Вариант в Glyph несёт одно содержимое, а содержимое с несколькими полями это запись. Ни одной из этих фраз в выводе не было.

Чтобы сказать это, парсеру пришлось прочитать весь список, прежде чем отказать, и это же позволяет ему считать. Подчёркнуты все шесть полей, а не разделитель, на котором он случайно остановился, а предлагаемая запись построена из имени варианта и шести типов из файла, так что исправление называет вашу программу, а не чей-то пример. Имена полей это единственное, что компилятор подставить не может, поэтому он оставляет на их месте пропуски.

Правило за этим сообщением это выбор, а не пробел. Node(Black, l, x, b, h, r) это перестановка аргументов, которая проходит проверку типов, а четвёртая позиция ничего не говорит читателю. Запись называет каждое поле, ветка match называет только те поля, которые использует, и и то и другое можно найти через grep.

История от E0108 к E0228 и к E0013

Раньше на такую строку компилятор говорил E0108, недостижимый код, при сборке, которая завершалась с кодом 0, потому что имя разрешалось в тип, а фигурные скобки разбирались как блок после return. Имя типа, записанное как значение, это E0228, а сообщение берётся из объявления, так что для записи перечисляются её поля, для размеченного объединения его варианты с формой содержимого, а для union строковых литералов его литералы. Order.parse(raw) и Order.is(v) остаются допустимыми, потому что получатель собственного дескриптора типа это единственная позиция выражения, где имени типа место.

Это исправило случай, когда имя было типом, но разбор остался прежним, так что return h() { k: 2 } по-прежнему возвращал h() и выбрасывал фигурные скобки с предупреждением. Начиная с 0.1.146 { на строке, где закончилась инструкция, это E0013 при разборе, каким бы ни было имя перед ней, и подсказка предлагает ту же переделку. Начиная с 0.1.149 правило покрывает любую инструкцию, а не только ту, что начинается с фигурной скобки: let s = "a" "b" раньше связывал "a" и выбрасывал "b", а return x as User был тремя инструкциями, потому что в Glyph нет приведения типов.

Каждая инструкция в блоке начинается с новой строки.

Контейнер там, где объявлен примитив

Другая касается контейнера из прелюдии, присвоенного примитиву. let x: string = o при o: Option<int> ничего не вызывал у проверки Glyph, как и передача Nullable<int> в параметр, объявленный как int.

Теперь пять контейнеров покрыты в обе стороны: Option, Result, Array, Record и Nullable никогда не являются string, number или bool, какими бы ни были их аргументы, а Nullable<T> против скаляра решается на уровень глубже, против T, так что let v: Nullable<int> = 3 остаётся правильным, а let v: Nullable<int> = "three" даёт E0204.

Подробнее случай, который может поймать только Glyph, и записи начиная с 0.1.130

Случаю с Nullable на этой странице место больше, чем остальным, потому что его tsc поймать не может: сгенерированный const v: number | null = 3 сужается обратно до number до проверки вызова, так что граничный тип, который существует, чтобы сделать null видимым, молча проходил там, где объявлен int, и поймать это могла только проверка Glyph.

Следующими стали те же контейнеры против объявленной записи или union. Начиная с 0.1.130 let user: User = json.parse(body) даёт E0204, ожидался User, найден Result<unknown, Array<Issue>>. Раньше об этом говорил только tsc, а значит glyph check --no-tsc, редактор и песочница показывали чистый файл ровно на той строке, ради правильности которой и существует граница.

Опечатка в имени члена массива или строки

Опечатка в имени члена массива или строки это другой случай, который раньше ждал tsc. xs.lenght даёт E0210 с «did you mean length», и проверяется по членам, которые библиотека TypeScript объявляет для массивов и строк, так же как чтение поля записи проверяется по её полям.

tsc отклонил бы оба случая, так что сборка, которая его запускала, и так была красной; изменилось то, что проверка Glyph и всё, что на ней построено, видят их первыми.

Опциональная цепочка на Result

Подробнее как сравнивается union

Это те же четыре ошибки, что сообщал tsc, на тех же четырёх инструкциях, без запуска tsc. Правило читает union как то, чем он является во время выполнения, то есть string, и задаёт проверке соответствующий вопрос о string в каждую сторону, так что наследует правила, которые уже отклоняют запись или контейнер против string, а не переписывает их для каждой формы. Два множества литералов сравниваются как множества, так что более узкий union можно передать туда, где объявлен более широкий; цепочка псевдонимов прослеживается с обеих сторон; импортированный union решается так же, как локальный; а внутрь Nullable<Mode> проверка спускается, сохраняя union.

Union, вложенный в поле записи или в аргумент дженерика, в 0.1.122 оставался на tsc, а в 0.1.123 решается сам. Смотрите ниже.

0.1.123: литерал, которым является значение, а не string, в который он генерируется

type Mode = "read" | "write" задавал множество в объявлении и ничего не задавал значению, так что "read" был string, а ["read", "write"] был Array<string>.

История от чего отказался 0.1.122

Из-за этого две программы были неразличимы: return ["read", "write"] там, где объявлен Array<Mode>, что tsc компилирует, и return xs для xs: Array<string>, что он отклоняет. 0.1.122 отказался решать такую пару, чтобы не решить её неправильно, и купил этим правильную программу ценой пропуска неправильной: { mode: "nope" } против { mode: Mode } ничего не вызывал.

Записанный строковый литерал теперь имеет тип из одного литерала, который он и записывает, тип элемента литерала массива это объединение типов его элементов, а записанный литерал массива или объекта проверяется против объявленного типа поэлементно и поле за полем, так что диагностика называет литерал и подчёркивает его.

glyph check --no-tsc, для литерала на уровень внутри контейнера 
type Mode = "read" | "write"
type Cfg = { mode: Mode }

fn ok() -> Array<Mode> { return ["read", "write"] }
fn bad() -> Array<Mode> { return ["read", "nope"] }
fn wrong() -> Cfg { return { mode: "nope" } }
// 0.1.122: nothing, on all three
[E0204] type mismatch: expected `Mode`, found `"nope"`   (twice)
Подробнее где литерал расширяется, и ключи Record начиная с 0.1.153

Литерал расширяется обратно до string там же, где его расширяет TypeScript: в let без аннотации, сгенерированный let которого в TypeScript расширяется так же, и в привязке элемента for по записанному массиву. Так что let l = "read", а затем takes_mode(l) отклоняется здесь и даёт TS2345 там. const генерирует const в TypeScript и сохраняет свой литерал, так что takes_mode(CM) компилируется в обоих. Литеральный тип, пришедший через имя, не расширяется: это собственное правило свежести TypeScript. Каждая строка этого была выяснена запуском tsc --strict на эквивалентном TypeScript, а не рассуждением.

Начиная с 0.1.153 аргумент-ключ Record проверяется строже, чем его проверяет tsc. TypeScript записывает Record<string, V> как индексную сигнатуру и принимает её против Record<Mode, V> в обе стороны. Glyph отклоняет оба направления: открытая таблица может содержать ключи вне Mode или не содержать какого-то из них, а в Record<Mode, V>, переданный дальше как открытый, можно записать лишний ключ. Переход от одного к другому идёт через ветку is или через json.parse.

О двух формах проверка пока ничего не говорит: литерал внутри Some(...), потому что у конструктора из прелюдии здесь пока нет типа, и литерал записи, привязанный к let без аннотации, потому что для объектного литерала тип записи не синтезируется.

Модуль под std/ был мёртвым кодом без диагностики

std/ и extern/ называют модули, которые несёт компилятор, и резолвер резервировал их для импортов. Но ничто не мешало файлу проекта объявить такой модуль.

glyph check --no-tsc, для src/io.glyph с объявлением `module std/io` 
// before: glyph check: 2 module(s) checked, no diagnostics.  (exit 0)

[E0113] `std/io` declares a module under `std/`, a prefix reserved for the
        modules the compiler carries (D15)
 1 │ module std/io
   │ ──────┬──────
   ╰─ Rename the module to a path of your own (`io`, `app/io`).
Подробнее что происходило раньше и какие пути зарезервированы

module std/io в вашем собственном src/io.glyph компилировался чисто, а затем import std/io { shout } разрешался в заглушку и сообщал, что shout не экспортируется: ваш файл ни разу не читался.

Префикс сопоставляется как целый первый сегмент, так что standard, externals/io, app/std и app/extern/helper не затронуты, а импорт под любым из префиксов работает как всегда.

Файл, который не вызывает ни одной диагностики и не выполняет ни строчки кода, это худшее, в чём компилятор может вас оставить, потому что ничего в нём не выглядит неправильным.

Вторая в 0.1.122

Предел глубины парсера

Вторая вообще не про tsc. Парсер это рекурсивный спуск без ограничения глубины, поэтому выражение с вложенностью в две тысячи уровней исчерпывало стек процесса и аварийно завершалось с кодом 134.

glyph check, для `const x = `, за которым идут 2,000 вложенных скобок 
// before: thread 'main' has overflowed its stack
//         fatal runtime error: stack overflow, aborting   (exit 134)

[E0011] this array literal nests deeper than the parser's limit of 64 levels
   ╰─ Name the inner levels: pull them out into `let` bindings, or into a
      `fn` that returns one of them, so no single expression, type or
      pattern is more than 64 levels deep.
Подробнее почему это было важно для языкового сервера

Это плохо для glyph check и ещё хуже для glyph lsp и glyph mcp, которые читают каждый файл под корнем: один патологический файл ронял сервер для всего рабочего пространства. Теперь это E0011, которое выдаётся на токене, открывшем бы 65-й уровень.

Предел равен 64, и он измерен, а не выбран наугад.

Подробнее как измеряли 64

Один уровень самой затратной конструкции, вложенного литерала массива, стоит 7,792 байта стека в release-сборке и 8,810 в debug, что выяснили двоичным поиском наименьшего стека потока, на котором разбирается заданная глубина. Самый тонкий стек, на котором работает парсер, это 2 MiB порождённого потока, столько получают воркеры языкового сервера, и 64 уровня тратят меньше трети этого в более затратной сборке. Самая глубокая вложенность среди 343 файлов .glyph в этом репозитории равна 16. Предел одинаково покрывает выражения, типы, паттерны, блоки и дочерние элементы JSX, а тысяча соседних массивов по-прежнему разбирается, потому что глубина это вложенность конструкций, а не бюджет, расходуемый по всему файлу.

Когда ни один компилятор не ошибается

Есть и третья форма, и выглядит она хуже всех. Glyph ничего не сообщает, tsc сообщает правду, а написанная вами программа была в порядке.

Сломался перевод между ними.

poll.glyph и что о нём говорил tsc до 0.1.89 
fn classify() -> int {
  let done = false
  match done {
    true => { return 1 },
    false => { return 0 },
  }
}

// no Glyph diagnostic, then
[TS2678] Type 'true' is not comparable to type 'false'.
Подробнее почему tsc видел false, и приложение, которое на это наткнулось

Привязка в Glyph имеет один тип на всё время жизни. TypeScript сужает привязку до того, что видел присвоенным последним, а его boolean это union true | false, поэтому let done = false доходил до tsc с типом false, и ветке true в сгенерированном switch не с чем было сопоставляться.

Тип, объявленный как множество строковых литералов, ломался так же, как и ==, только с TS2367: два сообщения, два кода, одна причина. Приложение, которое на это наткнулось, опрашивало флаг, выставляемый колбэком таймера: так превращают событийный API в значение, пока в Glyph нет Promise, который можно создать вручную. Колбэк оказался ни при чём: хватает четырёх строк без всякого колбэка.

Исправление не новая диагностика, потому что диагностировать нечего. Эмиттер теперь повторяет тип, который уже определила проверка, в двух местах, где значение различается по вариантам: в выражении, по которому идёт match, и с обеих сторон == или !=.

Подробнее какие проверки по-прежнему срабатывают и чего это стоит

Каждая сторона определяется своим типом и не зависит от соседней, так что сравнение двух привязок покрыто так же, как сравнение с литералом.

Нужные проверки по-прежнему срабатывают. m == "nope", где m это Mode, по-прежнему отклоняется, и теперь сообщение называет Mode, а не тот единственный член, который m случайно содержал. Сделать это в месте присваивания было бы меньше кода, и это бы всё испортило: приведение к Mode принимается там, где присваивание с аннотацией нет, а проверку принадлежности Glyph намеренно оставляет tsc.

Цена небольшая, но её стоит назвать. Приведение может как подтверждать тип, так и сужать его, поэтому значение, которое Glyph типизирует как bool, а его тип в TypeScript получился unknown, теперь проходит там, где раньше жаловался switch. Два типа всё ещё должны быть сравнимы, так что модель, разошедшаяся достаточно сильно, чтобы это имело значение (string против bool), даёт TS2352, а не тишину.

Одна опечатка, два ответа

Опечатка в имени функции стандартной библиотеки раньше получала разный ответ в зависимости от того, как вы написали импорт, а такая непоследовательность приучает не доверять ни одному из ответов.

именованный импорт, всегда E0105 
import std/string { repeeat }
[E0105] import: `repeeat` is not exported by `std/string`
чтение через пространство имён, до 0.1.72 
import std/string
string.repeeat(s, 2)
[TS2551] Property 'repeeat' does not exist on type ... Did you mean 'repeat'?

Теперь оба варианта проходят через список экспортов, и оба дают E0105, называя член и модуль, в котором его нет.

Подробнее почему два варианта записи различались и что нашлось, когда проверку включили

Первый вариант записи проверялся по списку экспортов модуля при разрешении имён. Второй не проверялся вообще, поэтому доходил до tsc, который видел обращение к свойству объекта и отвечал в этих терминах.

Включение проверки сразу нашло то, что никто не искал: тестовая фикстура вызывала fs.write, хотя функция называется write_text. Это месяцами проходило, потому что фикстура запускается с выключенной проверкой типов, а больше ничто в компиляторе не смотрело на члены пространств имён. Теперь список экспортов это авторитет для обоих вариантов записи, так что отдельная проверка следит, чтобы он совпадал с тем, что runtime на самом деле экспортирует. Эту проверку написали, а затем намеренно сломали, чтобы убедиться, что она падает, и так обнаружили, что её первая версия молча ничего не проверяла.

  • E0238 распознаёт вызов как async, только если у проверки Glyph есть его сигнатура
    Подробнее

    E0238 знает, что вызов async, только если у проверки Glyph есть его сигнатура, поэтому promise из npm-пакета или встроенного модуля node всё ещё может быть молча отброшен. Колбэк async, переданный в forEach или таймер, тоже пока не отклоняется: для этого правила нужно смоделировать позиции колбэков, и оно запланировано.

  • array.map, flat_map и zip по-прежнему без возражений принимают async-колбэк
    Подробнее

    array.map, flat_map и zip по-прежнему без возражений принимают async-колбэк и возвращают массив ожидающих значений, который печатается как [object Promise]; пять функций для массивов, принимающих предикат, это останавливают, выдавая E0211 на колбэке. Если смоделировать так же остальные три, будет отклонён и par.all(array.map(items, async fn ...)), а именно так Glyph выполняет работу конкурентно, потому что у массива ожидающих значений нет записи в языке. Это решение о системе типов, а не пропущенная запись, поэтому вопрос открыт.

  • await на верхнем уровне разрешён
    Подробнее

    У инициализатора const на уровне модуля нет охватывающей вызываемой конструкции, поэтому await на верхнем уровне разрешён, и сгенерированный ESM его выполняет; нужна ли Glyph неявная асинхронная инициализация модулей, пока открытый вопрос спецификации.

  • E0223 может оценить завершающий match, только когда функция объявляет тип возврата, так что ветка внутри лямбды без аннотации всё ещё доходит до tsc.
  • E0110 велит переименовать, а не позволяет сохранить имя
    Подробнее

    Со стороны перекрываемых имён две вещи сделаны наполовину. E0110 велит переименовать, а не позволяет сохранить имя, так что Error, Number, Object, Array и Promise по-прежнему недоступны для типа или варианта.

  • E0111 не даёт type Key = string | number означать не то, но и не даёт способа сказать то, что нужно
    Подробнее

    А E0111 не даёт type Key = string | number означать не то, но и не даёт способа сказать то, что нужно: у union из двух примитивных типов нет записи в Glyph, кроме extern_ts, содержимое которого собственная проверка считает непрозрачным. Неразмеченные union затрагивают исчерпываемость, дескрипторы для проверки во время выполнения и is, так что это решение о системе типов, и оно не запланировано.

  • E0104 доходит до glyph build и glyph check, но не до редактора
    Подробнее

    E0104 доходит до glyph build и glyph check, но не до редактора: LSP анализирует текст документа без корня сборки, а папка рабочего пространства корнем тоже не является, так что догадки дали бы те самые ложные срабатывания, которых проверка должна была избегать.

  • Параметр с зарезервированным именем по-прежнему прячется за посторонней ошибкой в том же файле, потому что сбой на проходе сбора пропускает проход разрешения имён, который бы его нашёл.
  • Закрепление типа в месте чтения следует за псевдонимом типа только внутри генерируемого модуля
    Подробнее

    Отдельно: закрепление типа в месте чтения, которое сохраняет возможность сопоставления для привязки bool или union строковых литералов, следует за псевдонимом типа только внутри генерируемого модуля, так что pub type Ready = bool в одном модуле и let r: catalog.Ready = false в другом всё ещё доходят до tsc как TS2678. Union строковых литералов покрыты между модулями во всех трёх вариантах записи импорта, и начиная с 0.1.123 диагностика при любой записи называет объявление (ожидался Mode), а не печатает множество литералов в одной из них.

Примеры кода на этой странице проверяются Glyph 0.1.156 при каждой сборке. Последнее изменение: 21 ноя 2026.
