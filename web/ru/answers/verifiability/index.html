Почему это важно

Агенты обычно ломают код не громко. Они ломают его уверенно: добавляют состояние, выкидывают ветку или переименовывают поле, всё по-прежнему проходит проверку типов, а баг всплывает в продакшене.

Дорого обходятся те ошибки, которые скомпилировались и оказались неверными. Glyph закрывает этот разрыв, превращая «вы, вероятно, это обработали» в «компилятор доказал, что вы это обработали».

  • Закрытые unionРазмеченные объединения закрыты, поэтому match обязан покрыть каждый вариант.
  • Ошибки как значенияОшибки это значения, которые нужно развернуть, а не исключения, которые бесследно пропадают.
  • Проверяемые границыКроме того, у каждого типа есть дескриптор времени выполнения, поэтому данные, пересекающие границу, проверяются на соответствие форме.

Отброшенная ошибка даёт предупреждение

С ошибками так же: функцию, которая возвращает Result<T, E>, предполагается обработать через match или пробросить через ? (и компилятор проверяет, что типы ошибок совпадают). А если вы отбросите Result (вызовете функцию как инструкцию и проигнорируете результат), Glyph предупредит вас (E0217), потому что выброшенная ошибка это проглоченный сбой.

glyph check --no-tsc, 0.1.149 (фрагмент) 
13 │   save("a")
[E0217] Warning: typecheck: this `Result` is discarded; its `Err` case is silently ignored
    │ Help: Handle it with `match`, propagate it with `?`, or bind it (`let _ = ...`) to say the discard is intentional.

Заглушить предупреждение можно намеренно, через let _ = ..., но не случайно.

Union из стандартной библиотеки тоже закрыты

Для union, которым владеет стандартная библиотека, планка та же. fs.ErrorKind это закрытый набор из шести видов, и проверка типов знает его форму, поэтому match e.kind по ошибке файловой системы не требует ветки else и падает с E0200, если вы пропустите какой-то вид.

E0200 пропущен видE0210 неизвестное полеE0218 нужен else
Подробнее опечатки в полях, возвращаемые типы, match по числам и строкам

e.mesage даёт E0210, а не то, что tsc поймает где-то дальше. Возвращаемые типы тоже распространяются: string.split(text, ",") имеет тип Array<string>, поэтому for i, part in string.split(text, ",") связывает i как число, а не как строковый ключ, который получился бы при нетипизированном итерируемом значении.

Исчерпываемость касается не только union. match по number или string только с литеральными ветками не может покрыть неограниченную область значений, поэтому Glyph требует else (E0218), а не позволяет непокрытому значению провалиться до исключения во время выполнения.

Правило везде одно: match, который не учитывает какой-то случай, не компилируется.

Ветка с опечаткой это дыра, а не catch-all

Опечатка тоже не может тихо замаскировать пропуск. Имя ветки с заглавной буквы это ссылка на вариант, а не новая переменная.

status.glyph: ветка с опечаткой это дыра, а не catch-all 
fn label(s: Status) -> string {
  return match s {
    Loadign => "…",        // typo for Loading, read as a variant, not a binding
    Ready => "done",
    Failed(msg) => msg,
  }
}
glyph build 
[E0220] `Loadign` is not a variant of `Status`; did you mean `Loading`?
   ╰─ a lowercase name would be a binding; a PascalCase name is read as a variant
[E0200] non-exhaustive match on `Status`: missing variant `Loading`
История что раньше Glyph делал с опечаткой

Имя ветки с заглавной буквы это ссылка на вариант, а не новая переменная, поэтому если вы напишете Loading как Loadign, старые версии Glyph читали опечатку как catch-all, который связывал любое значение, и match выглядел полным. Теперь имя ветки должно называть реальный вариант union, по которому идёт match. Если это не так, сборка останавливается с E0220 и указывает на ближайшее реальное имя, а вариант, который вы на самом деле пропустили, по-прежнему появляется рядом как E0200.

Варианты внутри полезной нагрузки

Это прочтение работает и на уровень ниже, где вариант является полезной нагрузкой другого варианта. Теперь ветка выбирается по собственному тегу полезной нагрузки, каким бы ни был внешний вариант.

repl.glyph: внутренняя ветка проверяет полезную нагрузку, а не связывает её 
fn step(z: Zipper, line: string) -> Zipper {
  return match parse_command(line) {
    Err(Blank) => z,                          // a comment or an empty line
    Err(e) => { io.println(explain(e)) z },   // every other parse error
    Ok(command) => execute(z, command),
  }
}
E0305 повторяющаяся метка case
История мёртвая ветка до 0.1.93 и защита E0305

Err(Blank) рядом с Err(e) читается как «пропусти пустую строку, напечатай все остальные ошибки разбора», но до 0.1.93 это компилировалось в две метки case "Err": по внешнему тегу, и первая связывала всю полезную нагрузку под именем Blank. Каждая ошибка попадала в первую ветку, вторая была мёртвым кодом, и ничто об этом не сообщало: Glyph не выдавал диагностик, а tsc --strict принимает повторяющуюся метку case. Теперь ветка выбирается по собственному тегу полезной нагрузки, каким бы ни был внешний вариант, и компилятор читает имя так же, как проверка типов: решает собственный список вариантов union полезной нагрузки, и только когда этот список недоступен, решает форма имени. Для union, объявленного в том же файле, регистр больше не важен. Для union, импортированного из другого модуля, список вариантов сейчас недоступен, поэтому вариант с заглавной буквы выбирается по тегу, а со строчной останавливает сборку.

Она останавливается потому, что switch теперь защищён. Две ветки, которые записали бы одну и ту же метку case, дают E0305, а не switch, вторая метка которого никогда не выполнится. Именно это делает этот класс ошибок громким, а не тихим: преобразование, которое дважды обращается к одному тегу, роняет сборку, а не выбирает не ту ветку во время выполнения.

Способ импорта никогда не отключает проверку

То, как union попал в область видимости, ничего здесь не меняет. В Glyph ветку варианта можно записать двумя способами, и оба проверяются одинаково: import model { Cond, Yes, No } с короткими ветками или import model (или import model as m) с model.Yes(_).

interp.glyph: список импорта убран, match по-прежнему проверяется 
import model { Action, All, Any, AtLeast, Clear, Condition, Context, Counter,
               Equals, Flag, FlagSet, Increment, Not, Set, Slot, Text }
import model
import std/result

pub fn evaluate(ctx: model.Context, c: model.Condition) -> result.Result<bool, SlotError> {
  return match c {
    model.Equals({ key, value }) => result.Ok(read_text(ctx, key, "equals")? == value),
    model.AtLeast({ key, least }) => result.Ok(read_count(ctx, key, "at-least")? >= least),
    model.FlagSet({ key }) => result.Ok(read_flag(ctx, key, "flag-set")?),
    model.All({ of }) => all_of(ctx, of),
    model.Any({ of }) => any_of(ctx, of),
    model.Not({ of }) => result.Ok(!(evaluate(ctx, of)?)),
  }
}
glyph build после удаления последней ветки 
[E0200] non-exhaustive match on `Condition`: missing variants Not
Подробнее union стандартной библиотеки, строковые перечисления и зачем был нужен список

Это верно и для union стандартной библиотеки, поэтому match o { option.Some(s) => … } по option.Option<string> даёт E0200 за пропущенный None точно так же, как короткая запись Some/None. До 0.1.56 полная запись полностью пропускала проверку, и сборка не выдавала диагностик для match, который падал во время выполнения.

Строковое перечисление тоже пересекает границу. type ColType = "text" | "int" | "real" | "bool", объявленный в catalog.glyph и импортированный в другой модуль, сохраняет свои четыре значения, поэтому match, покрывающий все четыре, компилируется без else, а пропуск одного даёт E0200 с названием пропущенного значения. До 0.1.57 это был E0218 с подсказкой добавить ветку else. Подсказка была неверна для кода, к которому относилась, и следование ей превращало ошибку компиляции в провал во время выполнения. Работают все три способа импорта: import catalog { ColType }, import catalog с catalog.ColType и import catalog as c с c.ColType.

Именно отсюда появился тот список импорта. Его вручную писали в каждом модуле движка statechart, с комментарием сверху: мол, конструкторы union не приходят вместе с его типом. Комментарий был прав насчёт синтаксиса и неправ насчёт причины: список был нужен потому, что короткая запись отключала проверку, и никто этого не замечал, потому что отключение происходит молча. Выбор формы теперь настоящий выбор, а не ловушка. Именованная форма помещает каждый обрабатываемый вариант в список импорта, и именно его найдёт grep по Equals. Полная форма в каждой ветке показывает, из какого модуля пришёл вариант. Ни одна из них не лишает вас проверки.

Импортированные записи сохраняют свои поля

Записи теперь тоже пересекают границу, а до 0.1.58 этого не было. Поэтому запись сохраняет свой набор полей, и неверное поле даёт E0210 с названием записи, а не ошибку tsc про анонимную форму.

glyph build на поле импортированной записи с опечаткой 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
// Before 0.1.58: no Glyph diagnostic at all, only a tsc error downstream.

// access is not enough: without the `let`, `i` and `j` come out as strings
// and the row/column numbers in a `BadCell` are wrong.
let raw_rows: Array<Array<string>> = sheet.rows
for i, raw_row in raw_rows {
for i, raw_row in sheet.rows {
  let typed: Array<Value> = []
  let cols: Array<ColumnSpec> = spec.columns
  for j, col in cols {
  for j, col in spec.columns {
    …
  }

// sheet: Sheet, declared in catalog.glyph and imported here.

Подробнее баг со строкой 11, что пропускает tsc, как переносится идентичность

Тип, объявленный в одном файле и используемый в другом, приходил без какой-либо информации о себе, и это стоило двух отдельных проверок. Опечатка в его поле вообще не вызывала ошибку Glyph, поэтому sheet.rowz проваливался до tsc и возвращался сообщением TypeScript о форме, которую вы никогда не писали. А for i, r in sheet.rows не мог понять, что rows это массив, поэтому генерировал Object.entries(sheet.rows) вместо sheet.rows.entries(). Это связывает i со строкой "0". Тогда i + 1 склеивает строки вместо сложения, и строка, о которой нужно сообщить как о line 2, сообщается как line 11.

Важно понимать, какую половину ловит tsc. Арифметику с таким индексом он ловит, хотя сообщает об ошибке в сгенерированном TypeScript, про переменную, которую Glyph объявил за вас. Чего он поймать не может, так это все места, где принимается строка там, где имелось в виду число: интерполяция строк, конкатенация, ключ record.get. Они компилируются без ошибок под обеими проверками и печатают неверное число. Это ровно тот тип багов, ради устранения которых существует этот проект, поэтому граница модулей, которая возвращает его обратно, не та граница, которую Glyph может оставить как есть.

Импортированный тип теперь переносит через границу свою идентичность, привязанную к модулю, который его объявляет, и к объявленному имени, поэтому все три способа импорта дают один и тот же тип. Само объявление загружается по требованию и обрабатывается на стороне объявляющего модуля, а это та половина, которую потребитель сделать не может: разрешение имён работает по позициям в исходнике, а позиции импортированного объявления принадлежат другому файлу.

Это всплыло в движке запросов в examples/apps/csvql. В нём было три вынесенных let, единственная задача которых состояла в том, чтобы повторить для эмиттера тип импортированного поля, а над ними четырёхстрочный комментарий о том, что без них номера строк и столбцов в сообщении об ошибке получаются неправильными. Все три удалены, и приложение выдаёт побайтно тот же вывод для всех двенадцати запросов.

Одна вещь всё ещё останавливается на границе. Передача catalog.Sheet туда, где ожидается table.Row, даёт E0211 с названием обоих типов, но список членов interface границу не пересекает, поэтому запись, переданная туда, где ожидается импортированный interface, ни с чем не сравнивается. Если обращаться с ним так же, как с набором полей записи, это тихо изменит смысл структурного соответствия, а это решение о языке, а не исправление.

Маскирование персональных данных задаётся в типе

Тот же принцип «на уровне типа, а не по соглашению» распространяется на персональные данные. Поставьте @redact fields: [ssn, dob] на тип, и компилятор сгенерирует в его дескрипторе redact(), который маскирует эти поля, так что json.stringify(User.redact(u)) не может их раскрыть.

E0219 неизвестное поле в @redact

Укажите поле, которого у типа нет, и получите ошибку компиляции (E0219), а не маскирование, которое молча ничего не делает.

Уточнения проверяются на всю глубину

Дескриптор чего-то стоит, только если это та проверка, которую объявляет тип, на всю глубину. Уточнение where выполняет свой предикат везде, где появляется тип, а не только при прямом Instant.parse: как поле записи, как элемент Array, как полезная нагрузка Option, внутри варианта union и через json.parse<T>.

schedule.glyph: предикат следует за типом внутрь поля 
fn is_instant(value: string) -> bool {
  return match time.parse_iso(value) {
    Some(_) => true,
    None => false,
  }
}

type Instant = string where is_instant(value)

type WireBlock = { start: Instant, end: Instant }
type WireParticipant = { name: string, busy: Array<WireBlock> }
type Calendar = { participants: Array<WireParticipant> }

// json.parse<Calendar>(text) on a file holding "start": "no"
//   => Err. It returned Ok before 0.1.41.
История уверенное неверное расписание до 0.1.41

То же относится к записи, импортированной из другого модуля. До 0.1.41 в обоих случаях проверялось только наличие ключа, а это ничего не проверяет.

Это всплыло в приложении-планировщике ниже. Оно читает календари из JSON-файла, и каждая метка времени в нём должна быть настоящим моментом ISO-8601. Раньше уточнение останавливалось на верхнем уровне, поэтому отредактированный вручную файл с "start": "no" разбирался без ошибок, момент читался как 0, а приложение уверенно печатало расписание и завершалось с кодом 0.

Тесты запускаются как часть сборки

Тесты лежат рядом с кодом и запускаются при его компиляции. @example над функцией или блок ```glyph @run``` внутри @doc выполняет glyph build, и никакой флаг помнить не нужно.

Подробнее почему их нельзя тихо пропустить, и канал JSON

Ложное утверждение роняет сборку так же, как ошибка типов, и в этом весь смысл: агент, переписывающий тело функции, не может пройти сборку, оставив утверждение позади. --no-test отключает их и печатает, сколько тестов пропущено, так что обход виден в логе.

JSON-вывод, который читают агенты, сообщает тот же вердикт. glyph build --json содержит объект examples рядом с диагностиками, а упавший пример делает ok ложным и код выхода ненулевым. До 0.1.43 примеры выполнялись только с --test, а путь JSON возвращал результат ещё до их запуска, так что единственный канал, который может прочитать агент, печатал "ok": true для проекта, собственное утверждение которого было ложным. Если tsx нет в PATH, сборка падает, а не сообщает об успехе, который она не проверяла.

В приложении турнирной сетки ниже таких 23. seed_order строит стандартный порядок сетки удвоением, а такую функцию легко незаметно сделать неправильно и легко точно описать. Поменяйте правило удвоения, и сборка остановится, без тестового файла, раннера и флага.

Найдено на практике

Ещё четыре случая, найденные при работе с языком

Каждый из них компилировался без ошибок и проходил tsc --strict, и каждый был найден при написании приложения, а не при чтении компилятора. Это один и тот же сбой в трёх местах: типы говорили одно, а программа делала другое.

Чтение ключа, которого может не быть

чтение ключа, которого может не быть: теперь E0224 
fn name_of(row: Record<string, string>) -> string {
  return row.naem          // a typo. compiled, and returned undefined
}

Теперь это ошибка компиляции, указывающая на record.get, который возвращает Option<V>, чтобы у случая отсутствия было куда деться.

Подробнее чем чтение из map отличается от индексации массива

Ключи map произвольные, поэтому компилятор не может знать, что ключ есть. Типизация чтения как string утверждала то, что не было проверено, и значение печаталось как текст "undefined". Запись по ключу не затронута, как и индексация массивов: границу программа может проверить, а ключ map нет.

== везде означает равенство значений

тест, который проходил, когда код не работал 
@example wrap("a") == wrap("a")   // passed: deep equality
fn same() -> bool {
  return wrap("a") == wrap("a")   // false. no diagnostic
}

== теперь везде означает равенство значений; примитивы по-прежнему компилируются в ===, так что обычные сравнения не изменились.

История как тест мог пройти на сломанном коде

== был задокументирован как равенство значений, а компилировался в ===, то есть в равенство ссылок, как только с любой стороны оказывалась запись, размеченное объединение или массив. Одно и то же выражение сравнивало структурно в тесте и по идентичности в программе рядом, поэтому тест мог сообщить об успехе для неработающего кода.

Переменная цикла сохраняет тип элемента

исчерпываемость, которая исчезала внутри цикла 
for t in tiers {
  match t {
    "free" => ...          // "pro" unhandled: once merely a warning to add `else`
  }
}

Теперь компилятор называет необработанный вариант, то есть советует выполнить проверку, а не отключить её.

История совет про catch-all, который он раньше давал

Переменная цикла не несла тип элемента, поэтому match по union строковых литералов деградировал до match по string, и компилятор советовал добавить catch-all.

Импортированные обобщённые union проверяются

вариант, пропущенный в match по импортированному обобщённому union 
import tree { Tree, Node }

fn label(t: Tree<string>) -> string {
  return match t {
    Node({ key: k }) => k    // Leaf unhandled: built clean, threw at run time
  }
}

Теперь в любом случае это E0200, при обоих способах импорта и одинаково для открытого параметра и для конкретной подстановки.

История почему проверка так и не начиналась

Union, объявленный в вашем собственном модуле, проверяется независимо от того, принимает ли он параметры типа. Union, импортированный из соседнего модуля, проверялся только если параметров у него не было. Tree<string> попадает в путь межмодульной проверки покрытия как применение импортированного union, а не как сам union, а условие, запускающее проверку, искало второе, поэтому match вообще не учитывался: tsc --strict проходил, а Leaf выбрасывал исключение. Удалите <K> из обоих файлов, и та же программа давала E0200.

parse не может заявлять о проверке, которую не делал

parse, который сообщал об успехе без проверки: теперь E0304 
type Conn = { id: number, sock: Socket }

Conn.parse(body)   // Ok. `sock` was never checked, and the message said it was

Хранить сокет в записи нормально, и это по-прежнему компилируется. А вот его валидация теперь отклоняется там, где она написана, и в каждом модуле, импортирующем запись, с названием поля и его типа, и отказ следует за формой: через вложенную запись, Array, Option.

Подробнее почему наличие не проверка и какое исправление предлагается

У каждого типа записи есть дескриптор времени выполнения. Для поля, тип которого компилятор не видит изнутри (сокет или что угодно, полученное через extern_ts), сгенерированная проверка была «присутствует ли поле», а сообщение гласило field `sock` must be Socket. Булево значение, которое всегда истинно, бесполезно. Значение, которое всегда истинно под сообщением с названием типа, который никто не проверял, ещё хуже, потому что именно parse граница должна доверять.

Предлагаемое исправление это разделение, которое вы бы и так написали: тип для передачи данных, все поля которого можно проверить, и доменная запись, которая строится из него. unknown эта проверка не ловит, потому что он ничего не утверждает, и наличие действительно составляет всю проверку.

Изменение сигнатуры, невидимое в месте вызова: закрыто в 0.1.116

Поменяйте функцию, чтобы она принимала полезную нагрузку вместо сырой строки, и каждый вызов, который всё ещё передаёт старую форму, собирался без ошибок.

billing.glyph: union незаметно проходит через параметр `string` 
type PaymentResult = Settled(string) | Declined(string)

fn takes_string(s: string) -> number { return s.length }

fn charge(r: PaymentResult) -> number {
  return takes_string(r)   // compiled clean before 0.1.116
}
glyph build, теперь 
[E0211] argument type mismatch: expected `string`, found `PaymentResult`
   ╰─ Pass a value of the expected type, or change the parameter's type.
Подробнее где проверка срабатывает и где молчит

Параметр с типом string, number или bool раньше без единой жалобы принимал значение объявленного union или записи, хотя тот же вызов с неподходящим аргументом bool уже давал E0211.

Проверка читает объявление, поэтому срабатывает только там, где ответ точно известен. Примитивный алиас, union строковых литералов (D30), тело extern_ts или typeof и interface по-прежнему ничего не дают, потому что ни про один из них нельзя доказать, что это не string, как про размеченное объединение или запись; void тоже исключён. Проверка одинаково работает для аргумента, для return и для аннотации let, поскольку все три используют одно отношение.

const с аннотацией типизирован

У const была такая же дыра с принимающей стороны.

[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
Подробнее const без аннотации и почему оба исправления ломающие

const уровня модуля с аннотацией типа превращался в Ty::Unknown, что бы ни говорила аннотация, поэтому опечатка в его поле была не видна ровно там, где такой же аннотированный let внутри функции уже давал ошибку.

const без аннотации ничего не утверждает и намеренно остаётся Unknown: вывод его типа из инициализатора это другой вопрос с другим набором ложных срабатываний. Оба исправления ломающие для glyph check --no-tsc, языкового сервера и песочницы, поскольку каждое начинает ловить программу, которую принимал предыдущий выпуск; полный glyph build в обоих случаях и так был красным из-за tsc.

  • У типа из обычного .d.ts нет дескриптора; материализуйте его через glyph gen dtsE0304
    Подробнее

    Тип, импортированный из другого модуля Glyph, теперь проверяется через собственный дескриптор, как и уточнение where в позиции поля; у типа, импортированного из обычного .d.ts, дескриптора нет, и parse для записи, которая его содержит, теперь отклоняется (E0304), а не сообщает об успехе, который не проверял; материализуйте его через glyph gen dts, чтобы получить тип с проверкой.

Инструменты и стандартная библиотека

  • Девять функций std/string и std/array всё ещё возвращают нетипизированные значения
    Подробнее

    Возвращаемые типы стандартной библиотеки, которые моделирует проверка, покрывают половину std/string и std/array с фиксированным числом аргументов; шесть функций с необязательным последним аргументом (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify) и array.map/flat_map/zip пока не типизированы, поэтому значению, полученному прямо из них, нужна аннотация, прежде чем перебирать его с индексом.

  • Обращение к членам примитивов и массивов не даёт диагностики там, где не запускается tsc
    Подробнее

    Обращение к членам и вызовы на string, number, bool и Array<T> оставлены tsc намеренно, это не дыра; Glyph разрешает там обычные члены JS, поэтому s.length и xs.length компилируются и проходят tsc --strict, а не хватает диагностики для четырёх мест, где tsc никогда не запускается: glyph check --no-tsc, языкового сервера, MCP-сервера и песочницы.

  • Офлайн-сборке с примерами нужен tsx или --no-test
    Подробнее

    Запуск примеров вызывает tsx, поэтому проект с примерами без tsx в PATH роняет сборку, а не пропускает их молча; это сделано намеренно, но значит, что для офлайн-сборки нужен установленный tsx или --no-test.

  • await в обычной fn ловится относительно вашего исходного кодаE0222
    Подробнее

    Асинхронный контекст был единственным правилом, которое Glyph оставлял tsc; await в обычной fn теперь даёт E0222 относительно вашего исходного кода, и единственный оставшийся разрешённый случай это инициализатор const верхнего уровня. Это и ещё два правила, которые переехали на стадию раньше, описаны на странице о ранних ошибках.

Почему это первый из четырёх принципов Glyph и где заканчивается его гарантия, рассказано на странице принципа проверяемости.

Примеры кода на этой странице проверяются Glyph 0.1.157 при каждой сборке. Последнее изменение: 20 ноя 2026.
