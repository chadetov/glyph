Участие в разработке

Как устроен компилятор и как помочь

Компилятор это рабочее пространство Rust из двенадцати крейтов в одном публичном репозитории под лицензией MIT или Apache-2.0. Сегодня больше всего помогают сообщения об ошибках с небольшим воспроизведением. Изменение языка начинается с issue, потому что каждое правило восходит к пронумерованному решению по дизайну.

Конвейер#

glyph build выполняет лексический и синтаксический разбор, разрешает имена, проверяет типы и генерирует TypeScript, а затем запускает tsc --strict на том, что записал. Средние этапы работают как инкрементальные запросы на salsa, так что повторная проверка переиспользует результаты, которые правка не сделала недействительными.

один файл .glyph через крейты 
glyph-lexer → glyph-parser → glyph-resolver → glyph-typechecker → glyph-emit → tsc --strict
                (glyph-ast)        └──────── glyph-db (salsa) ────────┘
КрейтЧто он делает
glyph-lexerТокены, ключевые слова, значимые переводы строк, шаблонные строки
glyph-astТипы синтаксического дерева, с диапазоном исходного кода на каждом узле
glyph-parserПарсер Пратта для каждого решения из спецификации, включая JSX
glyph-resolverРазрешение имён, граф модулей, проверки импорта между модулями, прелюдия
glyph-dbКонвейер запросов salsa и инвалидация между файлами
glyph-typecheckerИсчерпываемость, ?, дженерики, owned, дескрипторы для времени выполнения, модель стандартной библиотеки
glyph-emitГенератор TypeScript, генерация дескрипторов, source maps на уровне выражений
glyph-formatterglyph fmt: одна раскладка, сохраняет комментарии, идемпотентен
glyph-lspЯзыковой сервер и MCP-сервер с общим слоем анализа
glyph-cliБинарный файл glyph и все подкоманды
glyph-wasmКомпилятор в WebAssembly, на котором работает песочница
glyph-runtimeЗаглушка; тесты вместо этого идут через эмиттер и tsx

В glyph-compiler/README.md есть полные заметки по крейтам и текущее число тестов.

Сборка и тесты#

Rust 1.95 зафиксирован в rust-toolchain.toml. Некоторые тесты вызывают tsc и tsx, так что установите и их. CI запускает clippy с предупреждениями как ошибками, а ни cargo build, ни cargo test его не запускают, поэтому запускайте скрипт перед push.

из клона 
npm install -g tsx typescript
cd glyph-compiler
cargo build --release -p glyph-cli      # target/release/glyph
cargo test --workspace
cd .. && python3 scripts/check_clippy.py  # the exact clippy command CI runs

# after an intentional syntax-tree change
INSTA_UPDATE=always cargo test -p glyph-parser --test snapshots

Новая диагностика приходит вместе с программой в tests/negative/, которая должна падать с этим кодом. Утверждение, что Glyph ловит что-то, что пропускает TypeScript, кладётся в catches/, где гейт запускает обе половины.

Что запланировано и что сломано#

docs/roadmap/releases.md это план выпусков: что сделал каждый вышедший выпуск и для чего нужны следующие. docs/dogfooding-gaps.md это реестр gap: каждое ограничение, найденное при написании настоящих приложений, с номером (G плюс число) и пометкой статуса. Открытый gap с воспроизведением хорошее место для начала.

Issues и pull request#

Исправления инструментов, диагностик, документации и примеров можно сразу присылать pull request. Изменение синтаксиса или семантики начинается с issue, а крупные проходят процесс RFC в docs/rfcs/; PR, который ослабляет правило «для удобства», скорее всего, отклонят, потому что смысл именно в ограничении. Держите pull request в рамках одного gap, обычно от одного до трёх коммитов, и подписывайте каждый коммит (git commit -s). main защищена, а слияние только через rebase. Полные правила в CONTRIBUTING.md, а issues с меткой good first issue подобраны для первого изменения.
