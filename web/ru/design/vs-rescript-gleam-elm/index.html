Почему не ReScript, Gleam или Elm?

Все три это типизированные языки, которые компилируются в JavaScript, и все три старше, распространённее и устоявшиеся, чем Glyph. Если вы выбираете язык для новой кодовой базы и вам не нужно оставаться близко к TypeScript, сначала стоит посмотреть на них. Отличия Glyph уже: он генерирует исходный код на TypeScript, а не JavaScript, импортирует пакеты из npm с типами из их собственных .d.ts, генерирует валидаторы для времени выполнения из ваших типов, а его компилятор отвечает агенту на запросы о последствиях изменений.

Как каждый описывает себя#

Главная страница ReScript начинается со слов «JavaScript Made Simple for Humans and AI» и «Types > Vibes» и говорит, что он «compiles to clean, efficient JavaScript» с «No any, no magic types, no surprise undefined.» Он предлагает «automatically generate TypeScript types» (rescript-lang.org).

Главная страница Gleam называет его «a friendly language for building type-safe systems that scale» с «No null values, no exceptions, clear error messages». Он работает на виртуальной машине Erlang и «can additionally compile to JavaScript», а также «also generates TypeScript definitions» (gleam.run).

Главная страница Elm описывает «A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions» для «reliable web applications» и говорит, что Elm «detects all API changes automatically», чтобы «guarantee that every single Elm package follows semantic versioning» (elm-lang.org).

Эти цитаты прочитаны 2026-11-19.

Что Glyph делает иначе#

Каждый из этих примеров запущен на Glyph 0.1.149 для этой страницы.

Он генерирует исходный код на TypeScript

glyph build пишет по одному файлу .ts на модуль, который затем проверяет tsc --strict и который остаётся у вас, если вы перестанете использовать Glyph. ReScript и Gleam генерируют JavaScript и рядом с ним определения типов. Сгенерированный TypeScript показан на странице о TypeScript.

Он импортирует пакеты из npm с типами из их собственных деклараций

Модуль импортирует пакет по имени, и .d.ts пакета типизирует каждое использование. Сначала писать привязку не нужно. В ReScript «external is the primary ReScript feature for bringing in and using JavaScript values» (external), а типы объявляются на стороне ReScript. Внешним функциям в Gleam нужны аннотации типов, и компилятор «cannot verify that the function implemented in the other language returns the specified types» (externals). Elm общается с JavaScript через flags, ports и custom elements (interop). С установленными pg и @types/pg такой код отклоняется:

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

Код ошибки TS2322, потому что значения библиотеки проверяет tsc, а ошибка отображается обратно на строку Glyph. Собственная проверка Glyph их не видит, поэтому glyph check --no-tsc, редактор и инструменты MCP эту ошибку пропускают (G257). У типа, импортированного из .d.ts, также нет проверки во время выполнения.

Он генерирует валидатор из типа

Каждая запись и union несут проверку во время выполнения, сгенерированную из объявления, поэтому json.parse<User> возвращает Err, если данные не совпадают. В Elm для каждой формы пишется декодер, и его руководство отмечает, что «the decoders people write end up working as a validation phase» (JSON).

main.glyph: печатает "refused", потому что в JSON нет email 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

Его компилятор отвечает, что сломает изменение

Перед правкой агент может спросить, каких мест коснётся изменение, через MCP (glyph_impact) или командой glyph query impact. Для union Plan = Free | Pro | Team с одним исчерпывающим match и одним, который заканчивается на else, вопрос о новом варианте даёт ответ по каждому месту:

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

Второе место перестанет компилироваться после изменения, и об этом скажет любой из этих компиляторов, когда изменение будет сделано. Первое продолжит компилироваться и отправит новый вариант в свой else, и именно запрос его называет. Остальные инструменты перечислены в разделе для разработчиков агентов.
