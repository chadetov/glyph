Как Glyph проверяют на прочность

Агенты пытаются его сломать, а мы сохраняем то, что они находят.

Язык, который обещает, что агенты не сломают ваш код незаметно, нужно проверять именно на это. Мы запускаем ИИ-агентов, которые играют роль скептичных инженеров (раздражённый React-разработчик, бэкендер-спорщик, противник с упором на безопасность), просим их писать приложения и ломать гарантии, а затем исправляем найденное или заводим как открытый gap. Вот этот цикл и то, что он нашёл.

Случаи, которые проходят tsc --strict и не компилируются в Glyph

Каждый случай это два файла: .ts, который без ошибок проходит проверку типов под tsc --strict, и та же программа на Glyph, которая не компилируется. Проверка при сборке, scripts/check_catches.py, перезапускает каждый из них и падает, если какая-то половина перестаёт вести себя как ожидается, так что гарантия, которая тихо исчезает, роняет сборку. В таблице перечислены 23 из 37 случаев в TypeScript со страницы случаев, которые отклоняются таким образом; остальные есть на той странице: их Glyph проверяет при поступлении данных, о них предупреждает или останавливает их при выполнении. Всего проверенных случаев: 46. Из них случаев в TypeScript: 37, ловушек JavaScript, которых нет в Glyph: 5, и дыр, которые Glyph пока не закрывает: 4. При сборке Glyph отклоняет 28 из них (случаев TypeScript: 23, ловушек: 5).

Случаи, которые, как оказалось, ловит и TypeScript, или чьи две половины не были одной и той же программой, удалены, а не смягчены; catches/README.md перечисляет каждый из них и причину.

Чтение из map отклоняется, даже если ключ написан правильно, потому что Record<string, string> ничего не говорит о том, какие ключи существуют. TypeScript ловит это с noUncheckedIndexedAccess, который --strict не включает. Пропущенный вариант union тоже можно поймать в TypeScript правилом typescript-eslint switch-exhaustiveness-check или веткой default с assertNever, если проект их использует. В Glyph ни одна из этих проверок не является необязательной.

В случае с разобранным телом запроса json.parse в Glyph возвращает Result, а не User, поэтому присваивание остаётся несовпадением типов, пока тело не проверено. JSON.parse в TypeScript возвращает any, и аннотация у user его отмывает.

Состязательный цикл

Каждая находка воспроизводится на компиляторе, исправляется в корне и независимо перепроверяется, прежде чем засчитывается.

1

Исследование

Агенты-персонажи пишут программы (формы, бэкенды, UI с состоянием) и записывают каждое место, где язык им мешал.

2

Воспроизведение

Каждая находка сокращается до минимальной падающей программы и снова запускается на компиляторе. Всё, что не воспроизводится, отбрасывается.

3

Исправление

Исправление первопричины в компиляторе на Rust с регрессионным тестом, который падает до исправления и проходит после. Весь набор тестов должен оставаться зелёным, иначе изменение откатывается.

4

Проверка

Независимый проход заново запускает каждое воспроизведение на только что собранном компиляторе и ловит случаи «агенту казалось, что исправлено» до выпуска.

Самые важные: дыры в корректности, которые молчат

Каждый из этих случаев компилировался без ошибок и мог отправить в продакшен неверный код, прошедший проверку типов: ровно тот класс ошибок, ради предотвращения которого существует Glyph. Теперь каждый из них ловится при компиляции.

Критично, исправлено

Варианты ошибок без данных в match по Result

match по Result<T, Empty | BadQty(...)> превращался в две одинаковые ветки case "Err"; первая проглатывала все ошибки и молча направляла выполнение не в ту ветку.

Теперь: один сгруппированный case с правильным вложенным switch; каждый вариант попадает куда нужно.

Критично, исправлено

Конструктор с опечаткой как молчаливый catch-all

Вариант с опечаткой в ветке match (Loded вместо Loaded) молча связывался как неопровержимый catch-all, скрывая неполноту и направляя выполнение не туда во время работы, без какой-либо диагностики.

Теперь: неизвестный конструктор отклоняется на месте опечатки, как и любое настоящее имя.

Высокий приоритет, исправлено

Неполный match по bool проскакивал проверку полноты

match n > 0 { true => ... } (без ветки false) компилировался и проходил tsc, а потом бросал исключение во время выполнения.

Теперь: ошибка неполного match при компиляции.

Высокий приоритет, исправлено

Компоненты с несколькими параметрами неправильно связывали props

component C(a, b) генерировал позиционные параметры, но React передаёт компонентам сначала props, поэтому a молча связывался со всем объектом props. Это проходило tsc.

Теперь: понятная ошибка компиляции, которая указывает на форму с одной записью props.

Высокий приоритет, исправлено

JSX <match> пропускал проверку полноты

JSX <match> без одного <case> компилировался успешно и бросал исключение во время выполнения, в отличие от match на уровне значений, который проверялся.

Теперь: действует та же проверка полноты; пропущенный вариант это ошибка компиляции.

Высокий приоритет, исправлено

Данные записи связывались не с тем полем

Привязка варианта с данными-записью к имени (BadQty(b)) читала несуществующее .value из развёрнутых данных.

Теперь: данные связываются правильно, так что b.sku работает.

Правила, которые проверка теперь соблюдает

Корректность, которую компилятор раньше оставлял tsc, теперь ловит сам Glyph.

Исправлено

Число аргументов

Слишком мало или слишком много аргументов принималось (и приводило к NaN). Теперь E0213 отклоняет неверное число аргументов.

Исправлено

Тип ошибки для ? на границе стандартной библиотеки

Правило точного типа ошибки пропускалось, если ошибка приходила из обёртки стандартной библиотеки. Теперь оно соблюдается и там.

Исправлено

Псевдоним для дескриптора owned

let g = f на дескрипторе ресурса создавал вторую привязку, которая могла закрыть ресурс дважды. Теперь это отклоняется (E0215).

Исправлено

Недостижимые ветки и более глубокая валидация

Ветка после catch-all теперь помечается; json.parse<T> теперь структурно валидирует поля Record, а не только проверяет их наличие.

Трение при первом знакомстве, устранено

Мелочи, которые производили плохое первое впечатление и не служили никакой цели.

Исправлено

Доступность и data-атрибуты

aria-label и data-* разбирались как вычитание. Теперь они работают и генерируются как нормальные props React.

Исправлено

Имена пакетов npm

Спецификаторы с дефисами и scope (react-hook-form, @hookform/resolvers/zod) отклонялись. Теперь они импортируются напрямую.

Исправлено

Первый запуск браузерной сборки

Начальная загрузка среды выполнения не подключалась в браузерной сборке, и первый запуск падал. Теперь её подтягивает каждый сгенерированный модуль.

Исправлено

Сообщения об ошибках, которые сбивают с толку

Если написать if, теперь будет указание на match; про шаблон диапазона говорится прямо; пробелы в JSX и одиночный $ в тексте обрабатываются.

Всё ещё открыто: официально

Проверка на прочность означает и то, что мы называем несделанное. Это известно и отслеживается, а не спрятано.

Намеренно отложено или ждёт решения по дизайну:

Отклонение замыканий с неявным any в собственной проверке Glyph требует контекстного вывода, чтобы не давать ложных срабатываний на корректно типизированных колбэках. Удобный FFI, то есть использование TS-библиотеки со сложными типами без адаптера под каждую библиотеку, остаётся самым большим открытым вопросом совместимости, он отслеживается в открытых вопросах. Map, пришедший из другого модуля или из стандартной библиотеки, по-прежнему читается без проверки, так что E0224 пока не доходит до sqlite.Row, а for i, x in xs с двумя привязками всё ещё теряет типы элементов.
