For teams

What it guarantees, what adopting it costs, and how you get out

Glyph refuses a specific, checked list of cases that a strict TypeScript project accepts, and it compiles to TypeScript you can keep if you stop using it. It is an early preview: pre-1.0, maintained mainly by one person, and releasing several times a week.

What it guarantees#

Every claim about what Glyph catches is a case in the repository's catches/ directory: the same program in TypeScript and in Glyph, both run by a CI gate. There are 46 checked cases: 37 TypeScript cases, 5 JavaScript traps that do not exist in Glyph, and 4 holes Glyph does not close yet. Glyph refuses 28 of them when you build (23 TypeScript cases and 5 traps). Of the mistakes it does not refuse, 3 draw a warning, 9 are bad data stopped at a runtime boundary check, and 2 stop at run time. The ones a reviewer of agent-written code leans on most:

CodeWhat is refused
E0200A match that leaves out a case of a union, so adding a case lists every place that has to change
E0013A cast (as, as unknown as); there is no cast, and no any
E0204Parsed JSON assigned to a typed name without being checked
E0224A read from a map typed as if the key were always there
E0217A Result dropped on the floor (a warning; let _ = says it was deliberate)

The catches page lists every case with its TypeScript, its Glyph, and the error, and says which ones a fully configured typescript-eslint setup would also have caught.

Where it stops#

The guarantees cover code written in Glyph. An exception thrown inside an npm dependency still bypasses Result, and a type imported from a package's .d.ts has no runtime check. Inside Glyph, the 4 open holes are listed with their gap numbers in what it does not catch yet, and the full ledger is docs/dogfooding-gaps.md. For a comparison with strict TypeScript plus zod, eslint and ts-pattern, including where that setup is still ahead, see why not tooled TypeScript.

Adopting it inside an existing app#

There is no rewrite. You write the part you can't afford to get wrong (models, permissions, state transitions, money) in Glyph, and the rest of the app stays TypeScript and imports the emitted modules like any local file. The walkthrough uses a stock Vite scaffold: Can I adopt Glyph inside my existing app?

The exit story#

glyph build writes plain TypeScript, one file per module, that passes tsc --strict. If you stop using Glyph, you commit that output and keep going with tsc. The licence is MIT or Apache-2.0, so a fork is always possible. Coming from TypeScript shows a module next to its emitted file.

Pinning and upgrades#

glyph init pins the compiler to an exact version in package.json, with no ^, so no release reaches your build by accident. Three commands handle the rest:

upgrading on purpose 
glyph doctor     # your version against the latest release; never fails CI for that
glyph upgrade    # moves the project's pin, runs npm install, links the notes
glyph --update   # moves the installed compiler itself

What a Breaking release usually means#

Usually that the compiler starts refusing a program that was already wrong. 0.1.159 refused ids.forEach(async fn(id) { await save(id) }): forEach does not wait for its callback, so each save ran on its own and a failure in one was lost. 0.1.162 refused array.find(xs, f) ?? 0: an Option is never null, so the default never applied and the value was the Option itself. Some tighten a rule instead. Since 0.1.160, a call that changes an array in place, such as xs.push(4), has to be written as a mut statement, so code that worked had to change its spelling (glyph fix inserts the mut).

A release reaches your project only when you move the pin. If an upgrade refuses code you can't fix yet, stay on the version you had, since published versions are never yanked. The TypeScript your last build emitted compiles with tsc alone, so it stays usable whatever happens to the compiler.

Release cadence and the Breaking marker#

The versions page has an entry for every release from 0.1.0 to 0.1.176, 175 in all, and 49 of them shipped between 1 Nov 2026 and 24 Nov 2026. A release is marked Breaking when it rejects a program the previous version accepted, which is how most correctness fixes land. 57 entries carry the marker. It is applied by running the smallest affected program under both versions, not by reading the diff, and releases before 0.1.99 were not tested this way, so an unmarked old release is untested rather than safe.

What a Breaking release has cost in practice: each recent note says what happened when the old and new versions were run over the repository's example apps. These are the newest Breaking releases, quoted from their notes:

The example apps are the project's own code, kept compiling release by release, so a newly refused shape is less likely to turn up in them than in yours. Each note names the shapes it refuses, so read it before upgrading.

Status#

Glyph is pre-1.0. Before 1.0, syntax, the standard library and the shape of the emitted TypeScript may change, and a release may reject code that compiled before. docs/stability.md says what may change and what is held stable. MAINTAINERS.md says plainly that the project is maintained primarily by one person today.

Objections, answered#

We don't use AI much. Is it still worth it?

The checks are the same whoever writes the code: fewer runtime surprises, smaller diffs, code you can grep.

 We already run strict TypeScript and lint.

Every one of those checks is opt-in and can be turned off in one line. Glyph's can't.

 Can our agents write a language they've barely seen?

Most of what a model knows about TypeScript carries over, and the compiler names the rest.

 Why compile to TypeScript at all?

That is where npm, React and Node are, and it is why adoption can be one file at a time.

 What does on-call see when it breaks?

Readable TypeScript, source maps back to the .glyph file, and stable error codes.

 How do we know any of this is true?

How each claim on this site is checked, and how to reproduce one yourself.
