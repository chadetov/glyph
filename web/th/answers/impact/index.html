สำหรับการแก้หกแบบ ได้ glyph_impact รับ declaration ที่คุณกำลังจะเปลี่ยนและตัวการเปลี่ยนแปลง (เปลี่ยนชื่อ ลบ variant เปลี่ยน type ของ parameter เปลี่ยนจำนวน argument ลบทิ้ง) แล้วตอบด้วยคำตัดสินหนึ่งข้อต่อจุดจากรายการที่ปิดไว้ แต่ละข้อพร้อมเหตุผลว่าทำไมเป็นคำตัดสินนั้นและไม่ใช่ข้ออื่น

ในหน้านี้

  1. ทำไมเรื่องนี้สำคัญ
  2. สิ่งที่ได้กลับมา
  3. บนแอปจริง
  4. สถานะตอนนี้

ทำไมเรื่องนี้สำคัญ

เมื่อเปลี่ยนชื่อฟังก์ชัน ขยาย union หรือเปลี่ยนสิ่งที่ parameter รับ คุณจะ grep หาชื่อเก่าแล้วหวังว่าเจอทุกจุดที่เรียก หรือไม่ก็แก้ไปแล้วอ่านว่าคอมไพเลอร์บอกอะไรหลังจากนั้น

ไม่มีวิธีไหนบอกคุณได้ว่าจุดไหนจะยังคอมไพล์ผ่านแต่ผิดแบบเงียบๆ: match ที่มี arm แบบ catch-all ไม่ fail เมื่อคุณเพิ่ม variant มันแค่เริ่มส่ง case ใหม่ไปที่ที่ไม่มีใครเลือก จุดนั้นไม่เคยโผล่ใน build glyph_impact ตอบก่อนแก้ บนการวิเคราะห์เดียวกับที่คอมไพเลอร์รัน

สิ่งที่ได้กลับมา

request ระบุ entity ด้วยตัวตน module::name และการเปลี่ยนแปลงจากรายการที่ปิดไว้: add_variant, remove_variant, rename, change_arity, change_signature_type, remove คำตัดสินเป็นชุดปิดและแต่ละตัวมีความหมายเดียว:

คำตัดสินความหมาย
WILL_FAILคอมไพเลอร์พิสูจน์ได้ว่าจุดนั้นจะคอมไพล์ไม่ผ่าน
ABSORBSพิสูจน์ได้ว่าการเปลี่ยนแปลงถูกรับไว้ตรงนี้แบบเงียบๆ
SAFEพิสูจน์ได้ว่าจุดนั้นยังถูกต้อง
UNDETERMINEDดูจุดนี้แล้วแต่ยืนยันผลไม่ได้
NOT_INDEXEDคำถามนี้ถามไม่ได้เลยสำหรับจุดที่มีรูปแบบนี้
รายละเอียด ทำไมต้องระบุการเปลี่ยนแปลง และแต่ละรายการมีอะไร

การเปลี่ยนแปลงเป็นสิ่งบังคับ เพราะคำตัดสินคือข้อเท็จจริงเกี่ยวกับการแก้ ถ้าไม่ระบุการแก้ ทุกจุดจะกลับมาเป็นแค่ reference แทนที่จะเป็นผลที่ตามมา คำตอบระบุ entity การเปลี่ยนแปลง และรายการ impact: หนึ่งรายการต่อจุด แต่ละรายการมี declaration ที่มันอยู่ relation, verdict, because และรหัส diagnostic ที่คอมไพเลอร์จะแจ้งเมื่อมีอยู่ตัวเดียว

การเรียกภายใน @example หรือภายในบล็อก @doc ที่ติดแท็ก glyph @run ก็นับเป็นตำแหน่งเช่นกัน บิลด์รันเทสต์เหล่านี้ การเปลี่ยนชื่อจึงทำให้มันพังเหมือนผู้เรียกอื่น ทุกรายการมี context: "example" หรือ "doc_run" สำหรับตำแหน่งในเทสต์ และ null สำหรับตำแหน่งในโปรแกรม การเปลี่ยนชื่อ normalize ด้านล่างจะแสดงตัวอย่างของมันเองพร้อมกับการเรียกสองครั้งใน twice:

main.glyph 
module main

@example normalize("  Hi ") == "hi"
pub fn normalize(s: string) -> string {
  return s.trim().toLowerCase()
}

@example twice("a") == "aa"
pub fn twice(s: string) -> string {
  return normalize(s) + normalize(s)
}
glyph query impact --entity main::normalize --change rename รายการที่สาม 
{
  "entity": "main::normalize",
  "context": "example",
  "relation": "CALLS",
  "line": 2,
  "verdict": "WILL_FAIL",
  "diagnostic": "E0103"
}

บนแอปพลิเคชันจริง

examples/apps/csvql query engine สำหรับ CSV สิบเอ็ดไฟล์ใน repository นี้ มี tagged union หนึ่งตัวคือ Value ซึ่งวันนี้มีสี่ variant การถาม glyph_impact ว่าการเพิ่มตัวที่ห้า (Blob) ทำอะไร เจอจุดที่ match 10 จุดใน 4 ไฟล์: 8 จุดจะคอมไพล์ไม่ผ่าน และ 2 จุดมี arm แบบ catch-all ที่จะกลืน variant ใหม่ไปเงียบๆ

  • ตรวจด้วย buildเมื่อเพิ่ม variant จริงๆ คอมไพเลอร์รายงาน E0200 8 ตัวพอดี ที่ 8 จุดที่คาดไว้พอดี และไม่บอกอะไรเลยที่ 2 จุด ABSORBS ทั้งก่อนและหลัง
  • ถ้าใช้การค้นหาข้อความแทนการค้นหาข้อความหา arm แบบ catch-all ทั่วแอปเดียวกัน ซึ่งเป็นสิ่งที่คุณจะทำถ้าไม่มีเครื่องมือ เจอ 2 จุดจริงนั้นฝังอยู่ใน 20 ผลลัพธ์ (precision 0.10) และไม่บอกอะไรเลยเกี่ยวกับ 8 จุดที่ fail เพราะมันไม่รู้ว่า match ตรวจค่าที่เป็น type อะไร

สถานะตอนนี้

ใช้ได้วันนี้

  • การเปลี่ยนแปลงหกแบบที่เป็นชุดปิด (add_variant, remove_variant, rename, change_arity, change_signature_type, remove) และคำตัดสินห้าแบบที่เป็นชุดปิด หนึ่งรายการต่อจุดที่ได้รับผลกระทบพร้อมเหตุผลและรหัส diagnostic
  • change_signature_type ตัดสินทีละ argument ของการเรียกตามกฎการเปรียบเทียบของตัวตรวจเอง และแต่ละจุดได้คำตัดสินที่อ่อนที่สุดของ argument ทั้งหมด
  • element ของ JSX ตัดสินเหมือนการเรียกที่มันถูกแปลงไป
    รายละเอียด

    element ของ JSX ตัดสินเหมือนการเรียกที่มันถูกแปลงไป: <Card title="x" /> คือ props record หนึ่งตัวที่ส่งให้ Card และแต่ละ attribute แสดงคู่กับ field ที่มันถูกตรวจ พร้อมคำตัดสินที่ argument ของการเรียกที่มี type เดียวกันจะได้

  • ความครอบคลุมระบุทีละการค้นหา และทุก node บอกว่ามาจากไหน
    รายละเอียด

    ความครอบคลุม (การค้นหาอ่านอะไรได้และอะไรไม่ได้) ระบุทีละการค้นหา แทนที่จะระบุครั้งเดียวทั้งคำตอบ และทุก node บอกว่ามาจากซอร์ส Glyph, ทางออก extern_ts หรือ .d.ts ที่มองไม่เห็นข้างใน

  • การเรียกและชื่อภายใน @example หรือบล็อก @doc glyph @run จะแสดงพร้อม context และ glyph_references กับ glyph_dependencies ก็แสดงแบบเดียวกัน

หยุดตรงไหน

  • ความลึกแม่นยำที่หนึ่งขั้นและว่างเปล่าเลยจากนั้น
    รายละเอียด

    ความลึกแม่นยำที่หนึ่งขั้นและว่างเปล่าเลยจากนั้น: Glyph ไม่เคยอนุมาน type ของ declaration จาก body ของมัน type ของฟังก์ชันที่ถูกเรียกจึงไปไม่ถึง signature ของผู้เรียก และการเปลี่ยน X ทำให้เป็นโมฆะได้เฉพาะ expression ที่ระบุชื่อ X

  • ถ้าขอความลึก 2 คำตอบจะกลับมาพร้อม next_query ที่ระบุคำถามที่ถูกต้องแทน
    รายละเอียด

    ถ้าขอความลึก 2 คำตอบจะกลับมาพร้อม next_query ที่ระบุคำถามที่ถูกต้องแทน เพราะสิ่งที่ขั้นที่สองต้องใช้คือการแก้ที่ใครสักคนทำให้จุดแรก และการแก้นั้นยังไม่มี

  • UNDETERMINED และ NOT_INDEXED เป็นข้อกล่าวอ้างคนละแบบ
    รายละเอียด

    UNDETERMINED และ NOT_INDEXED เป็นข้อกล่าวอ้างคนละแบบ: argument ที่ตัวตรวจไม่มี type ให้ หรือ record ที่จับคู่กับ field ที่ไม่มีกฎไหนอ่าน คือ UNDETERMINED (ดูแล้วแต่ตัดสินไม่ได้) ฟังก์ชันที่ถูกอ่านเป็นค่าแทนที่จะถูกเรียกคือ NOT_INDEXED (คำถามถามไม่ได้ตรงนั้นตั้งแต่แรก)

  • การเปลี่ยนชื่อในเอดิเตอร์ยังไปไม่ถึงเทสต์ จึงทิ้ง @example ไว้ด้วยชื่อเดิม (G546) การเข้าถึงฟิลด์หรือ match ภายในเทสต์จะไม่ถูกแสดง การค้นหาเหล่านั้นระบุกรณีนี้ไว้ใน not_indexed (G547)
  • ABSORBS คือตัวที่ต้องจับตา: จุดนั้นยังคอมไพล์ผ่านและถูกพิสูจน์แล้วว่าผิด ซึ่ง build ที่เขียวจะไม่มีวันแสดงให้คุณเห็น

ตัวอย่างโค้ดในหน้านี้ถูกตรวจกับ Glyph 0.1.185 ทุกครั้งที่ build แก้ไขล่าสุด: 24 พ.ย. 2026

Glyph

ภาษาแบบมี type ที่คอมไพล์เป็น TypeScript สร้างมาให้เอเจนต์แก้โค้ดได้โดยไม่ทำให้พัง

เริ่มต้น

โปรแกรมแรกของคุณ สำหรับคนที่มาจาก TypeScript สำหรับทีม Playground ทัวร์ห้านาที

เรียนรู้

คำตอบ อ่านคำตอบตามลำดับ เครื่องมือสำหรับ editor และเอเจนต์ สำหรับเอเจนต์ เซิร์ฟเวอร์ MCP หน้าเว็บแบบ Markdown การออกแบบ สี่เสาหลัก สเปกของภาษา แถลงการณ์

หลักฐาน

สิ่งที่จับได้ ข้อกล่าวอ้างถูกตรวจสอบอย่างไร การทดสอบความแข็งแรง Benchmark เวอร์ชัน
