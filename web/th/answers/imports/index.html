ทำไมเรื่องนี้สำคัญ

ไม่มีใครเขียน codebase ใหม่ทั้งหมดเพื่อลองภาษา เพราะ output ของ Glyph คือ TypeScript ไฟล์ .glyph จึงวางลงในมุมหนึ่งของโปรเจกต์ TS/React/Node ที่มีอยู่ได้ import แพ็กเกจเดียวกัน และ export กลับไปให้ .ts รอบๆ

เส้นทางแบบค่อยเป็นค่อยไปนี้คือเหตุผลทั้งหมดที่เลือก TypeScript เป็นเป้าหมายแทนที่จะสร้าง runtime ใหม่

แพ็กเกจที่ติดตั้งไว้มี type มาเอง

ถ้าแพ็กเกจติดตั้งแล้วและมี type มาด้วย (หรือมี @types/...) ก็แค่นั้น ไม่มี stub ไม่มีไฟล์ adapter

glyph build หา node_modules ของโปรเจกต์และชี้ type-checker ไปที่นั่น type จริงของแพ็กเกจจึงตรวจโค้ดของคุณ และการเรียกที่ผิดเป็น error จริง

นี่คือการใช้ zod แบบ inline โดยไม่มีอะไรเขียนเอง:

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
การเรียกที่ zod ไม่ได้นิยามไว้ 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

glyph run รันโปรแกรมเดียวกันกับ zod ที่ติดตั้งไว้ จึงไม่ใช่แค่การตรวจ type: รายการ config เดียวที่ resolve แพ็กเกจให้ type-checker ก็ resolve ให้ runtime ด้วย

แพ็กเกจที่ไม่มี type มาและไม่มี @types/... ยังต้องมี declaration ที่คุณเขียนเอง ซึ่งเป็นหน้าที่ของโฟลเดอร์ .types/ (กลไก .d.ts เดียวกับที่ TypeScript ใช้อยู่แล้ว)

รายละเอียด import แบบ subpath และ type ที่ validate ได้จาก .d.ts

import แบบ subpath (pkg/sub) resolve ผ่าน map exports ของแพ็กเกจด้วย type ของ subpath จึงถูกตรวจ

และเมื่อคุณต้องการรูปร่างของไลบรารีเป็น type ของ Glyph เต็มตัวที่ถูก validate แทนที่จะเป็น import แค่ type glyph gen dts จะเปลี่ยน .d.ts เป็น type จริงที่มี descriptor ดูต้องเขียน validator ด้วยมือให้ทุก API ไหม?

type ที่ derive จากค่า, JSX spread และทางออกฉุกเฉิน

type ที่ derive จากค่าใช้ได้เต็มที่ JSX prop spread (<input {...register()} />) ก็ใช้ได้เต็มที่

ไลบรารีจึงไม่มีวันบังคับให้คุณเขียนไฟล์ adapter เอง

สำหรับ idiom ของ TypeScript ที่หายากซึ่ง Glyph ยังเขียนไม่ได้ extern_ts("...") คือทางออกฉุกเฉินที่มีขอบเขตและ grep หาได้: tsc ตรวจมัน แต่ต้องเข้าใจให้ถูก มันคือขอบเขตของความไว้ใจ ไม่ใช่ขอบเขตที่ validate ตอนรัน (Glyph มองไม่เห็นข้างใน ค่าที่ได้กลับมาเป็น unknown ให้ narrow ต่อ)

รายละเอียด z.infer<typeof s> resolve อย่างไร

type User = z.infer<typeof user_schema> ใช้ได้โดยตรง: typeof user_schema เป็น type query บน reference ของค่าจริง (พิมพ์ผิดจะเป็น error ชื่อที่ resolve ไม่ได้) และ z.infer<...> เป็น member-generic type ธรรมดา มันถูก emit ตรงตัวและ tsc ลดรูปมัน u.name จึงเป็น string validation มาจาก parse ของ schema เอง ซึ่งเป็นวิธีที่ zod ทำงานอยู่แล้ว

เมื่อต้องการ TypeScript ที่เขียนเองทั้งไฟล์

บางครั้งทางออกฉุกเฉินไม่ใช่ type หรือ expression แต่เป็นโค้ด runtime จริง: loop ของ node stream, new Promise, worker thread วาง .ts ไว้ใต้ <src>/extern/ แล้วเรียกถึงด้วย import extern/<name> 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

import แบบ relative ยังใช้ไม่ได้ในซอร์ส Glyph (เป็นกฎเรื่อง grep) extern/* จึงเป็น path เดียวที่สงวนไว้ และ grep -rn 'import extern/' เจอทุกจุดที่คุณออกจากภาษา

รายละเอียด การนำเข้า output ทิศทางกลับ และ node shim

build นำ <src>/extern/** เข้าไปใน output และ emit specifier แบบ relative tsc จึงตรวจ type ของ extern ไปพร้อมกับโค้ด Glyph และการ build ใหม่ไม่มีวันตัดมันทิ้ง

มันเป็นทิศตรงข้ามกับทางที่ง่าย คือไฟล์ .ts ที่ import Glyph ที่คอมไพล์แล้ว ซึ่งไม่ต้องทำอะไรเลย extern ทั่วไป (http server, fs) ตรวจ type กับ node shim ที่มาด้วยได้โดยไม่ต้องติดตั้งอะไร

เฝ้าดู subprocess โดยไม่ต้องติดตั้งอะไร

declaration ของ node ที่มาด้วยมีครึ่งที่เป็น async ของ child_process ไม่ใช่แค่แบบ blocking เครื่องมือที่รายงาน output ของคำสั่งที่ใช้เวลานานระหว่างที่มันรันจึงเป็น Glyph แทนที่จะเป็น extern: 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

io.print ไม่ใช่ io.println: chunk คือชิ้นหนึ่งของ stream ไม่ใช่บรรทัด และบรรทัดหนึ่งอาจมาข้ามสอง chunk

overload ทำตาม @types/node pipe จึงกลับมาเป็นค่าที่ไม่ใช่ null จาก spawn(command, args) ธรรมดา และเป็น nullable เมื่อคุณส่ง stdio การอ่าน child.stdout หลัง stdio: "inherit" เป็น TS18047 ที่นี่ และเป็น TS18047 กับ typing จริง แทนที่จะเป็นสองเรื่องที่ต่างกันเกี่ยวกับค่าเดียวกัน: 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

แก้ shim แล้วการรันครั้งถัดไปก็ใช้ shim ที่คุณแก้

shim เป็นไฟล์ที่คุณแก้ไปเรื่อยๆ จึงต้องนับเป็นซอร์ส

glyph run cache build ไว้ภายใต้ fingerprint ของซอร์ส และ fingerprint นั้นครอบคลุมทุก .ts และ .tsx ใต้ extern/ ทั้งตาม path และตามเนื้อหา

รายละเอียด อะไรทำให้ build ใหม่

แก้ เปลี่ยนชื่อ เพิ่ม หรือลบสักไฟล์ การรันครั้งถัดไปจะ build ใหม่และรัน tsc ใหม่ shim ที่เป็น symlink จะถูกตามไป .ts ที่เก็บไว้นอก source tree จึงถูก hash ตามเนื้อหาจริง

นั่นคือสิ่งที่ทำให้ shim เป็นเจ้าของ type ได้ แทนที่ทั้งสองไฟล์จะประกาศสำเนาของตัวเอง export รูปร่างจาก shim แล้ว import มันใน module ของ Glyph คอมไพเลอร์จะยึดทั้งสองให้ตรงกันทุกครั้งที่รัน:

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
shim เปลี่ยนชื่อ field และ build ก็บอก 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3
ที่มา ก่อน 0.1.44 และไฟล์ที่ไม่นับ

จนถึง 0.1.44 fingerprint ข้าม extern/ ไปทั้งหมด การเปลี่ยนชื่อนั้นจึงได้ build ที่สะอาดและตรวจ type ผ่าน ซึ่งรัน shim สำเนาเก่า ไฟล์ใต้ extern/ ที่ไม่ใช่ .ts หรือ .tsx ยังไม่กระทบ cache ซึ่งเป็นความตั้งใจ: README.md ข้าง shim ถูกคัดลอกไปใน output ด้วย แต่ไม่มีอะไรตรวจ type หรือรันมัน จึงไม่มีอะไรต้อง build ใหม่

client แบบ class: ตัวที่ใช้กับฐานข้อมูลและ messaging

client ของฐานข้อมูลและ messaging ส่วนใหญ่เป็นแบบ class: คุณเขียน new Kafka(...), new MongoClient(url), new Redis(), new Pool(cfg) Glyph มี new สำหรับเรื่องนี้โดยเฉพาะ

client แบบ class (kafkajs) 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
client แบบ factory ไม่ต้องใช้ new 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

มัน emit new ของ TypeScript ตรงตัว และ tsc ตรวจมันกับ constructor จริงของแพ็กเกจ argument ที่ผิดจึงเป็น error จริง และ callee ที่ไม่ได้นิยามถูกจับด้วยชื่อ

มันใช้ได้เฉพาะ interop: Glyph ไม่มี class ของตัวเอง และ new สร้างได้เฉพาะ type ที่มาจากแพ็กเกจ declaration ใน .types หรือ extern_ts

สถานะตอนนี้

ใช้ได้วันนี้

  • import แพ็กเกจ npm ไหนก็ได้ (รวมชื่อที่มีขีดและมี scope)
  • แพ็กเกจที่ติดตั้งแล้วซึ่งมี type มาเอง (หรือมี @types/...) ตรวจ type และรันได้โดยไม่มี stub
  • client แบบ class สร้างด้วย new ซึ่ง tsc ตรวจกับ constructor จริง client แบบ factory import และเรียกได้ตรงๆ
  • builtin ของ Node ตรวจ type ได้ทันที
    รายละเอียด

    builtin ของ Node (fs, path, http, child_process รวมถึง spawn แบบ streaming และตัวอื่นๆ) ตรวจ type ได้ทันที โดยโหลด @types/node อัตโนมัติเมื่อคุณติดตั้ง และ CI build runtime ของคอมไพเลอร์เองกับแพ็กเกจนั้นที่ latest declaration ที่ stdlib พึ่งพาจึงเพี้ยนจากของจริงของ node ไม่ได้

  • declaration ที่มีแค่โค้ดของคุณเรียกถึงยังไม่อยู่ในการตรวจนั้น และบางตัวยังกว้างกว่าของ node
  • declaration แบบ ambient ใน .types/ สำหรับอย่างอื่น
  • glyph gen dts สำหรับเปลี่ยน .d.ts เป็น type ของ Glyph ที่ validate ได้
  • output .ts ที่สะอาดซึ่ง TypeScript ที่มีอยู่ import กลับได้
  • import extern/<name> เรียกถึง TypeScript ที่เขียนเองใต้ <src>/extern/
    รายละเอียด

    เมื่อต้องการ TypeScript ที่เขียนเองทั้งไฟล์ import extern/<name> เรียกถึง .ts ใต้ <src>/extern/ ซึ่งถูกนำเข้าและตรวจ type ไปพร้อมโค้ดของคุณ และถูกติดตามโดย cache ของ glyph run การแก้มันจึงทำให้ build ใหม่

กำลังมา

  • การ materialize จัดการรูปร่างที่ SDK จริงมีได้ และ type ที่ derive จากค่าใช้ได้เต็มที่
    รายละเอียด

    ตอนนี้การ materialize จัดการรูปร่างที่ SDK จริงมีได้ (namespace, re-export ข้ามไฟล์และแบบ alias/namespace, exports แบบ subpath และ generic เต็มรูปแบบ) และ type ที่ derive จากค่า (z.infer<typeof s>) ก็ใช้ได้เต็มที่

  • ช่องว่างหลักที่เหลือคือ output ของแพ็กเกจที่ไม่ได้ materialize ถูกตรวจ type กับ .d.ts ของมัน แต่ไม่ถูก validate ตอนรันถ้าคุณไม่ materialize
  • ฝั่ง extern/ root ของซอร์สต่างกันระหว่าง glyph run และ glyph build
    รายละเอียด

    ฝั่ง extern/ root ของซอร์สต่างกันระหว่างสองคำสั่ง: glyph run app.glyph ใช้ไดเรกทอรีของไฟล์เป็น root ส่วน glyph build src/ ใช้ไดเรกทอรีที่คุณระบุ โปรแกรมในไดเรกทอรีย่อยจึงหา shim ในสองที่ต่างกัน และจนกว่าเราจะเลือก root เดียว โปรเจกต์ที่จัดแบบนั้นต้องให้ shim เข้าถึงได้จากทั้งสองที่ มันจะ fail อย่างชัดเจนเมื่อเข้าถึงไม่ได้

ตัวอย่างโค้ดในหน้านี้ถูกตรวจกับ Glyph 0.1.156 ทุกครั้งที่ build แก้ไขล่าสุด: 21 พ.ย. 2026
