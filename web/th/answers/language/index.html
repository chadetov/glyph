ทำไมเรื่องนี้สำคัญ

ภาษาที่เขียนไฟล์เดียวได้แต่จัดโครงสร้างโปรเจกต์ไม่ได้ ไม่ใช่ภาษาที่คุณจะเดิมพัน codebase ด้วย ช่องว่างที่สำคัญไม่ได้แปลกประหลาด:

  • การมองเห็นซ่อน helper ได้ไหม?
  • ข้อจำกัดของ genericgeneric กำหนดความสามารถได้ไหม?
  • Cleanupปล่อย file handle ในทุกทางออกได้ไหม?
  • การทำงานพร้อมกันรันสองอย่างพร้อมกันแล้วรอทั้งคู่ได้ไหม?

Glyph ตอบทั้งสี่ข้อ โดยไม่ย้อนกลับไปทางที่เต็มไปด้วย annotation ซึ่งตั้งใจทิ้งไปแล้ว

interface กำหนดข้อจำกัดของ generic

interface เป็นเชิงโครงสร้างเหมือนของ TypeScript: เป็นชุดของ signature ของ member ที่ generic กำหนดได้ ไม่มี implements ไม่มีพิธีแบบ nominal ค่าใดที่มี member ครบก็ผ่าน และ tsc บังคับใช้

interface จำกัด generic 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer และ structured concurrency

defer รัน cleanup เมื่อออกจาก block ในทุกเส้นทาง รวมถึงการ return ก่อนเวลาหรือ error ที่ถูก throw และ std/task รวมงานที่ทำพร้อมกันให้มีอายุเดียว แทนที่จะปล่อย promise ที่หลุดลอยไว้

defer + structured concurrency 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])
รายละเอียด ลำดับการรัน และ handle แบบ owned

defer หลายตัวรันแบบเข้าหลังออกก่อน และใช้ร่วมกับ handle แบบ owned ได้

สิ่งที่สืบทอดมาจาก JavaScript

Glyph คอมไพล์เป็น TypeScript และรันบนเอนจิน JavaScript จึงรับลำดับการประเมินผล ความหมายแบบ reference เมื่อมีการแก้ไขค่า และโมเดลเธรดเดียวที่มี garbage collection มาด้วย สเปกระบุเรื่องเหล่านี้เป็นการรับประกัน แทนที่จะปล่อยให้คุณค้นพบเอง

จุดที่ต่างคือการเปรียบเทียบความเท่ากัน: == เปรียบเทียบค่า โดย record จะเทียบทีละฟิลด์ ส่วน === ของ JavaScript เปรียบเทียบ reference

การจัดการหน่วยความจำเองและโมเดลที่ไม่มี GC ไม่อยู่ในโรดแมป เพราะอยู่นอกขอบเขตของภาษาที่ทรานสไพล์เป็น TypeScript

ไม่มี if match จึงต้องแบกทุกอย่าง

สิ่งแรกที่นักพัฒนา TypeScript ถามหลังจากได้ฟังเรื่องความครบถ้วนคือ match เป็นเงื่อนไขทั่วไปจริงหรือแค่วิธีสวยๆ ในการ destructure union คำตอบคืออย่างแรก และที่ที่พิสูจน์ได้คือการ assign

match ที่เป็นค่าทั้งหมดของ let หรือ mut รับทุกอย่างที่ statement รับได้: arm เป็น block ได้ arm await ได้ arm break ออกจาก loop รอบนอกได้ และ arm อ่าน binding ที่มันกำลัง assign ได้ ซึ่งเป็นวิธีพับ state ผ่าน loop โดยไม่มี if

จากตัวตรวจลิงก์: การติดตาม fence และ arm ที่ await 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}
รายละเอียด มันคอมไพล์เป็นอะไร และโค้ดตัวอย่างมาจากไหน

ทั้งคู่คอมไพล์เป็น switch ธรรมดาที่ assign binding ในแต่ละ arm await จึงอยู่ในฟังก์ชัน async ที่ครอบอยู่ และตัวสะสมเป็นตัวแปรปกติที่ TypeScript อนุมานได้ โค้ดทั้งสองชิ้นมาจาก examples/apps/linkcheck/main.glyph ตัวตรวจลิงก์ใน Markdown ที่เขียนขึ้นเพื่อหาเรื่องแบบนี้โดยเฉพาะ

match ที่ใช้ภายใน expression ที่ใหญ่กว่า เป็น argument หรือ operand ยังกลายเป็น closure ซึ่งหมายความว่า arm ต้องเป็น expression เดียว การยกมันออกมาเป็น let ของตัวเองปลดข้อจำกัดนั้น

pattern ระบุรูปร่างที่ลึกกว่าหนึ่งชั้นได้

variant ที่มีหลาย field ถือ record ไว้ arm ที่ต้องการจำรูปร่างหนึ่งจึงต้องเอื้อมผ่าน field ของ record ตอนนี้ field รับ pattern ใดก็ได้: tag ของ variant, constructor ที่ซ้อนกัน, destructure ที่ซ้อนกัน, literal, array pattern

case การหมุนหนึ่งแบบของการปรับสมดุล red-black เป็น arm เดียว 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}
ที่มา วิธีเลี่ยงก่อน 0.1.90

จนถึง 0.1.90 ตำแหน่ง field รับแค่ชื่อและไม่มีอย่างอื่น: คุณเปลี่ยนชื่อได้ และแค่นั้น การ match tag ตรงนั้นเป็น compile error และ constructor ที่ซ้อนกันทำให้ parser ล้ม วิธีเลี่ยงคือ bind ทุก field แล้วเขียน match ซ้อนกันทีละชั้น ซึ่งสำหรับอะไรอย่างการปรับสมดุล red-black tree ก็กลายเป็นอีกโปรแกรมหนึ่ง: arm ไม่ตรงกับ case อีกต่อไป และแต่ละชั้นต้องร้อย binding ข้างบนใหม่

มีผลที่ตามมาที่ควรรู้ก่อนเขียน field ที่ทดสอบค่าอาจไม่ match arm จึงไม่นับว่าครอบคลุม variant ของมันอีกต่อไป และ match ที่มี arm Node แค่ Node({ color: Red, ... }) จะถูกรายงานว่าไม่ครบจนกว่าจะมี arm ข้างเคียงหรือ else รับส่วนที่เหลือ

รายละเอียด ทำไมมันขอ catch-all และตำแหน่งของ array

ตัวตรวจพิสูจน์ความครอบคลุมบนชุดของ tag ไม่ใช่บนผลคูณของ field มันจึงไม่คำนวณว่า arm Red กับ arm Black รวมกันครบ Node การขอ catch-all คือการตีความที่ไม่มีทางปล่อยให้ match หลุดท้ายตอนรัน เช่นเดียวกับที่ที่ไม่มี variant ให้นับเลย: match บน record ธรรมดาที่ทุก arm ทดสอบ field ต้องมี else ตามหลัง

ที่หนึ่งที่สิ่งนี้ไปถึงซึ่งคุณอาจไม่คาดคิดคือตำแหน่งใน array [Black] ทั้ง arm เคยนับว่า match กับ array หนึ่ง element ใดก็ได้ match ที่พึ่งมันจึงถูกรับรองว่าครบ แล้วก็ใช้ arm นั้นกับ [Red] ด้วย element ที่เป็น PascalCase เป็นการอ้างถึง variant ที่นี่เช่นกัน match แบบนั้นตอนนี้จึงเป็น E0208 บน array ความยาว 1 ให้ bind element แล้ว match มันแยกต่างหาก การแปลงข้างใต้ยังเป็นแบบเก่า ซึ่งเป็นเหตุผลที่การตรวจเป็นครึ่งที่ออกมาก่อน

E0208

และคอมไพเลอร์รู้ว่า match ให้อะไรออกมา

คำถามต่อมาคือตัวที่ตัดสินว่าทั้งหมดนี้รับน้ำหนักได้จริงหรือไม่: เมื่อคุณ bind ค่าออกมาจาก branch แล้ว Glyph รู้ type ของมันไหม หรือยักไหล่แล้วปล่อยให้ tsc จัดการทีหลัง? ตอนนี้ match ได้ type ของ arm เมื่อมันตรงกัน และรู้ว่า T.parse คืน Result<T, Array<Issue>> ซึ่งเป็นรูปร่างที่โค้ดจริงส่วนใหญ่แตก branch

จากตัวแบ่งค่าใช้จ่าย: ไม่มี annotation และ i เป็นตัวเลข 
let wire = match WireLedger.parse(decoded) {
  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },
}

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...
}
ที่มา ก่อน 0.1.45

จนถึง 0.1.45 มันยักไหล่ match expression ทุกตัวมี type เป็น unknown ค่าที่ออกมาจาก construct แตก branch เพียงตัวเดียวในภาษาจึงไม่มี type ตั้งแต่ตรงนั้น

รายละเอียด อะไรเคยผิดแบบเงียบๆ และการรวม type ทำงานอย่างไร

ทั้งสองส่วนนั้นเป็นเรื่องที่เคยผิดแบบเงียบๆ loop emit wire.expenses.entries() เมื่อ type ของสิ่งที่วนเป็น unknown มันจะ emit Object.entries(...) แทน และ i เป็นstring "0" ซึ่งเป็น TypeScript ที่ถูกต้อง build จึงสะอาด และโปรแกรมพิมพ์ 01:a ทั้งที่หมายถึง 1:a และ wire.expensez ตอนนี้เป็น [E0210] type WireLedger has no field expensez จาก Glyph บนบรรทัดของ .glyph แทนที่จะเป็น TS2339 บน TypeScript ที่ generate

การรวม type คือความเท่ากันที่ส่วนหัว: arm ที่ลงท้ายด้วย return ไม่ได้ร่วมโหวต และ arm ที่ type ไม่ตรงกันทำให้ผลเป็น unknown เหมือนเดิม มันมองลึกลงไปอีกชั้นเฉพาะที่ type argument None => [] จึงตรงกับ arm ที่เป็น Array<string> แทนที่จะทำให้ทั้ง match จม และ loop ที่ตามมายัง bind ตัวเลขได้ chain เดียวกันบน record.get ใช้ได้ด้วยเหตุผลเดียวกัน: ฟังก์ชันทั้งหกตัวของ std/record พา type ของค่าออกมาจาก record ที่คุณส่ง โค้ดนี้มาจาก examples/apps/settle/main.glyph ซึ่งเคยมี annotation ที่สิ่งนี้ลบออกไป

การค้นหาที่มีค่าสำรองเป็นค่าว่าง

FsError.kind เคยเป็น { tag: string } โดยมี NotFound เป็นการจำแนกทั้งหมด การแยก “path นั้นเป็นไดเรกทอรี” ออกจาก “path นั้นไม่มีอยู่” จึงต้องเทียบ string ของ errno

ส่วนเพิ่มเล็กๆ สองอย่าง

มีสองอย่างเล็กกว่าที่มาพร้อมกัน ทั้งคู่มาจากแอปเดียวกัน

  • task.pool_settledtask.pool_settled คือ task.pool ที่มีพฤติกรรมเมื่อล้มเหลวแบบ all_settled: concurrency ที่มีขอบเขต ผลลัพธ์หนึ่งตัวต่องาน และ host ที่ตายไปหนึ่งตัวทำให้เสียแค่ผลของ host นั้น ไม่ใช่ทุกผลที่ pool เก็บไว้

รู้ได้อย่างไรว่าฟังก์ชันเหล่านี้ถูกตัว?

เพราะแอปที่ขอมันต้องเลิกใช้ทางเลี่ยงเสียก่อน รุ่นนั้นจึงจะนับว่าเสร็จ

ฟังก์ชันในไลบรารีที่ออกมาแล้วกับทางเลี่ยงที่ยังอยู่ต่อเป็นข้อกล่าวอ้างคนละแบบ การเปลี่ยนแปลงเดียวกันที่เพิ่มสี่ตัวนี้จึงลบสำเนาของตัวตรวจลิงก์ไปด้วย: import readdirSync, การเทียบ string ของ errno ทั้งสองจุด, scanner ที่เขียนเอง 97 บรรทัด และ pool แบบ fail-fast รวมแล้วลบออกไป 122 บรรทัด

พฤติกรรมที่เปลี่ยนสองอย่าง วัดผลแล้ว

การลบสองอย่างในนั้นเปลี่ยนสิ่งที่โปรแกรมทำ และความต่างถูกวัด ไม่ใช่ถูกเถียง

  • ไดเรกทอรีที่อ่านไม่ได้ชี้ทั้งรุ่นเก่าและรุ่นใหม่ไปที่ tree ที่มีไดเรกทอรีที่คุณอ่านไม่ได้: รุ่นใหม่พิมพ์ permission denied และนับ path นั้นว่าอ่านไม่ได้ ส่วนรุ่นเก่าซึ่งถามได้แค่ว่า errno เป็น EISDIR หรือไม่ ไม่ใส่มันในรายงานเลย
  • URL ที่ล้มเหลวทำให้หนึ่งในสาม URL throw: pool_settled พิมพ์ครบสามแถวและระบุความล้มเหลว ส่วน pool ไม่พิมพ์อะไรเลยและตายไปด้วย rejection ที่ไม่ถูกจัดการ พาผลที่ดีสองตัวไปด้วย
รายละเอียด การเขียน scanner ใหม่ และความกังวลเรื่อง alternation

การเขียน scanner ใหม่ยังคลายความกังวลด้านการออกแบบด้วย เพราะ capture group ที่ไม่ได้มีส่วนร่วมอ่านได้เป็น "" เหมือนกับตัวที่ match ค่าว่าง captures_all จึงดูเหมือนบอกไม่ได้ว่า branch ไหนของ alternation ทำงาน แต่บอกได้ ถ้าคุณเขียน group ของแต่ละ branch ครอบทั้ง construct แทนที่จะครอบแค่ส่วนที่ต้องการ: group ที่ทำงานจะเริ่มด้วย `, [, ! หรือ < และว่างไม่ได้ ชิ้นที่อาจว่าง คือปลายทางของลิงก์ ซ้อนอยู่ข้างในและไม่เคยเป็นสิ่งที่คุณถามถึง นั่นเปลี่ยนการเดินทีละอักขระ 180 บรรทัดให้เหลือสอง pattern และการ dispatch 12 บรรทัด โดย output เหมือนกันทุกไบต์ทั้งบนเอกสารของ repo เองและบน fixture ที่สร้างมาเพื่อทำให้มันพัง

เงินไม่ได้คำนวณด้วย float

ช่องว่างที่จะจบการประเมินด้าน fintech ทันทีคือการคำนวณเงินด้วย number แบบ IEEE-754 ซึ่ง 0.1 + 0.2 ไม่ใช่ 0.3 และค่าที่เกิน 253 เสียความแม่นยำไปเงียบๆ

std/decimal เป็น fixed-point ฐานสิบที่แม่นยำบน BigInt: จำนวนเต็มความแม่นยำไม่จำกัดที่มีจำนวนหลักทศนิยมตายตัว การบวก ลบ และคูณจึงแม่นยำ และการหารต้องระบุ scale และการปัดเศษ จำนวนเงินที่ผิดรูป parse ได้เป็น Err ไม่มีวันเป็น NaN แบบเงียบๆ

จำนวนเต็มขนาดใหญ่

สำหรับจำนวนเต็มขนาดใหญ่ที่แม่นยำ อย่าง id บัญชีและตัวนับ มี type bigint: literal เป็น 123n มัน emit เป็น bigint จริงของ TypeScript และ field ของ record ที่มี type เป็น bigint จะ validate typeof === "bigint" ที่ขอบเขต id ที่ส่งมาเป็น number ใน JSON จึงถูกปฏิเสธแทนที่จะถูกปัดเงียบๆ เมื่อเกิน 253

callback แบบ async มี type ในที่สุด

type ของฟังก์ชันเคยเป็น fn(A) -> T และไม่มีอย่างอื่น ซึ่ง emit เป็น (a: A) => T body แบบ async ไม่เข้ากับสิ่งนั้น ฟังก์ชันที่คืนงานที่เลื่อนไว้ หรือ record ของ handler แบบ async จึงต้องปล่อยไว้โดยไม่มี annotation และตัวตรวจก็เลิกดู

async fn(A) -> T คือ type ที่ขาดไปนั้น มัน emit เป็น (a0: A) => Promise<T> และ async fn() ที่ไม่มี return emit เป็น () => Promise<void>

งานที่เลื่อนไว้ และ map ของ handler

  • การมองเห็นแบบ pub ที่บังคับใช้กับทั้งสองวิธีในการอ้างถึง type ของ module ข้างเคียง (import ด้วยชื่อ และ annotation lib.Secret)
  • ข้อจำกัดแบบ interface เชิงโครงสร้าง
  • async fn(A) -> T เป็น type ที่เขียนได้
  • union ที่อ้างถึงตัวเองใน payload ซึ่ง match ได้ด้วย arm ที่ซ้อน constructor pattern ไว้ใน field ของอีกตัว

control flow และ match

  • defer
  • std/task (all/race/all_settled/pool/pool_settled)
  • match เป็นค่าของ let หรือ mut โดยมี block, await และการควบคุม loop ใน arm
  • match ที่ arm ตรงกันพา type ไปใช้ในส่วนที่เหลือของโปรแกรม
  • T.parse ที่มี type

ตัวเลขและ semantics

  • std/decimal สำหรับคำนวณเงินอย่างแม่นยำ
  • bigint สำหรับจำนวนเต็มขนาดใหญ่ที่แม่นยำ
  • ตัวคั่นหลัก
  • ส่วนของสเปกที่รับผิดชอบ semantics ที่สืบทอดจาก JS

standard library

  • standard library ที่มี string.slice, index_of, repeat, pad_start, pad_end, replace_all, trim_start, trim_end และ array.fold, index_of, flat_map
  • fs.read_dir, fs.is_dir, fs.stat
  • การจำแนก FsError.kind ที่ตัวตรวจบังคับคุณ
  • regex.captures_all
  • ส่วนใหญ่ของ std/string และ std/array พา return type เข้ามาในโปรแกรมของคุณ
    รายละเอียด

    ส่วนใหญ่ของ std/string และ std/array พา return type เข้ามาในโปรแกรมของคุณแล้ว string.split จึงเป็น Array<string> และ loop บนมันก็ bind index เป็นตัวเลข

  • std/record ถูก model โดยอ่าน type ของค่าจาก record ที่คุณส่ง
    รายละเอียด

    std/record ก็ถูก model ด้วย โดยอ่าน type ของค่าจาก record ที่คุณส่ง: record.get(t, k) บน Record<string, Array<string>> เป็น Option<Array<string>> และ record.keys(t) เป็น Array<string> array.sort(record.keys(t), cmp) จึงรักษา type ของ element ไว้

หยุดตรงไหน 11

การมองเห็น

  • import ที่เป็น private รายงานข้อความเดียวกับชื่อที่ไม่มีอยู่
    รายละเอียด

    import ที่เป็น private รายงานว่า “not exported by M” ซึ่งเป็นข้อความเดียวกับชื่อที่ไม่มีอยู่ การแยก “เป็น private ให้ทำเครื่องหมาย pub” ออกจาก “ไม่มีชื่อนี้” เป็นการปรับปรุงที่อยู่ในคิว

  • ค่า private ที่อ่านผ่าน namespace เป็น error ของ tsc ไม่ใช่ของ Glyph
    รายละเอียด

    การมองเห็นถูกตรวจบน type annotation ไม่ใช่บนค่าที่อ่านผ่าน namespace: lib.helper() ที่ helper เป็น private ยังเป็น error ของ tsc ไม่ใช่ของ Glyph

async

  • await ระดับบนสุดใน initializer ของ const ระดับ module ได้รับอนุญาตE0222
    รายละเอียด

    บริบทของ async ถูกตรวจแล้ว (E0222) ยกเว้นจุดเดียว: initializer ของ const ระดับ module ไม่มีสิ่งที่เรียกได้ครอบอยู่ await ระดับบนสุดตรงนั้นจึงได้รับอนุญาต และ ESM ที่ emit ออกมาก็รันมัน

type ที่อนุมานได้

  • arm ที่ไม่ตรงกันที่ส่วนหัวของ type ทำให้ผลเป็น unknown สำหรับ Glyph
    รายละเอียด

    การรวม type ของ arm ยังต้องให้ arm ตรงกันที่ส่วนหัวของ type: เมื่อได้ type ต่างกัน ผลจะเป็น unknown สำหรับ Glyph และมีแค่ tsc ที่ตรวจสิ่งที่คุณทำกับมัน

  • ฟังก์ชันใน stdlib เก้าตัวอยู่ในสถานะเดียวกัน
    รายละเอียด

    ฟังก์ชันใน stdlib เก้าตัวอยู่ในสถานะเดียวกัน หกตัวรับ argument ท้ายที่ไม่บังคับ (array.slice, string.slice, string.index_of, string.pad_start, string.pad_end, json.stringify) และการตรวจจำนวน argument เทียบตัวเลขหนึ่งตัวกับตัวเลขหนึ่งตัว การ model มันจึงจะรายงาน error ผิดๆ ทุกครั้งที่เรียกโดยไม่ใส่ argument ตัวสุดท้าย ส่วน array.map, flat_map และ zip ได้ type ของ element จาก callback ที่ตัวตรวจไม่ได้เดินเข้าไป

    ค่าที่ออกมาจากเก้าตัวนี้โดยตรงต้องมี annotation ก่อนวนด้วย index และ match บน string.index_of ที่ไม่มี arm None ยัง build ผ่านสะอาดและ throw ตอนรัน array.index_of ถูก model แล้วและรายงาน E0200

  • member และจำนวน argument ของการเรียกบนค่าที่ตัวตรวจให้ type ไม่ได้ยังไม่ถูกตรวจ
    รายละเอียด

    member และจำนวน argument ของการเรียกบนค่าที่ตัวตรวจให้ type ไม่ได้ยังไม่ถูกตรวจที่ขอบเขตนั้น แทนที่จะเป็น error

ไลบรารี

  • string ใช้ index เป็นหน่วย code unit ของ UTF-16 และไม่มีแผนจะทำ chars หรือ char_at
    รายละเอียด

    ฝั่งไลบรารี string ใช้ index เป็นหน่วย code unit ของ UTF-16 แบบเดียวกับที่ len และ split ใช้มาตลอด และเรื่องนี้ตัดสินแล้ว: ไม่มี chars หรือ char_at และไม่มีแผนจะทำ เพราะครึ่งหนึ่งของ surrogate ที่ถูกคืนมาดูเหมือนอักขระจนกระทั่งถูกเขียนออกไป ให้เข้ารหัสด้วย encoding.hex_encode แล้วอ่านทีละสองหลัก hex

  • captures_all ไม่ให้ offset และ fs.read_dir คงลำดับของ OS
    รายละเอียด

    captures_all คืน group แต่ไม่มี offset scanner ที่ต้องรู้ว่า match เริ่มตรงไหนในบรรทัดจึงยังต้องเขียน loop เอง และ fs.read_dir ให้รายการตามลำดับของ OS จึงต้องเรียงเองเมื่อ output ต้องทำซ้ำได้

pattern

  • constructor ที่มี payload ใน field ใช้ไม่ได้บน union ที่เข้าถึงผ่าน namespace importE0300
    รายละเอียด

    pattern ของ field ที่ซ้อนกันยังเหลือขอบหนึ่งจุด: constructor ที่มี payload อยู่ใน field บน union ที่เข้าถึงผ่าน namespace import import tree { Node } แล้ว Node({ left: Node({ key: k }) }) คอมไพล์ผ่าน แต่ import tree แล้ว tree.Node({ left: tree.Node({ key: k }) }) เป็น E0300 บน union เดียวกัน

  • union ที่เป็น generic บน parameter ของตัวเองรับ arm ที่ซ้อนกัน และถูกตรวจหา variant ที่ขาดE0200
    รายละเอียด

    ขอบอีกจุดหายไปแล้ว: union ที่เป็น generic บน parameter ของตัวเอง (type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> })) เคยปฏิเสธ arm ที่ซ้อนกัน ซึ่ง union เดียวกันที่ไม่มี parameter ยอมรับ ตอนนี้รับได้แล้ว ทั้งที่ type parameter ที่ยังเปิดอยู่และที่ instantiation ที่ระบุจริง การค้นหาเดียวกันนี้เป็นตัวตัดสินด้วยว่า match ถูกตรวจหา variant ที่ขาดหรือไม่ จนถึงรุ่นนี้ match บน Tree<K> จึงละ Leaf ได้ build ผ่านสะอาด ผ่าน tsc --strict และ throw ตอนรัน ขณะที่การเขียนแบบไม่ generic เป็น E0200

    ตอนนี้ทั้งสองแบบรายงาน และการย้าย union ไปอยู่ห่างออกไปหนึ่ง import ก็ไม่เปลี่ยนคำตอบอีกต่อไป: match บน Tree<string> ที่ import มาซึ่งละ Leaf เป็น E0200 ที่ระบุ Leaf เหมือนกับ Tree ที่ไม่ generic ที่ import มา นั่นเป็นอีกเส้นทางโค้ดที่ตรวจแยกกัน และมันเป็นไปในทางตรงข้ามจนถึงรุ่นนี้ คือ build ผ่านสะอาดแล้ว throw ตอนรัน

  • ความครอบคลุมของ union ที่ import มาไม่เคยตรวจ payload ของ variant
    รายละเอียด

    มีอย่างหนึ่งเกี่ยวกับความครอบคลุมของ union ที่ import มาที่ควรรู้ก่อนพึ่งพามัน: payload ของ variant ไม่เคยถูกตรวจเช่นกัน B(X) ที่ X เป็น variant ของ union ใน payload เองจึง match กับ B ทุกตัวแทนที่จะรายงาน Y ที่ขาดไป และเรื่องนั้นไม่เกี่ยวกับ generic

    การ bind field หรือการ match tag ที่ไม่มี payload ในนั้นใช้ได้ทุกกรณี
