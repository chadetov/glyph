รู้ ทุกปัญหาบอกชื่อ field บอกว่าค่าผิดกฎข้อไหน และมี code ที่ใช้แตก branch ได้ field ที่ถูกจำกัดด้วย predicate where จะรายงานตัว predicate เอง การปฏิเสธจึง grep ย้อนกลับไปหาบรรทัดที่กำหนดกฎนั้นได้

ทำไมเรื่องนี้สำคัญ#

validator ที่บอกว่า "payload นี้ผิด" ทำงานได้แค่ครึ่งเดียว handler ยังต้องตัดสินว่า นี่คือ client ที่ลืม field หรือ client ที่ส่งรหัสผ่านยาวสี่ตัวอักษร? อันหนึ่งคือ 400 อีกอันคือ 422 และถ้า validator ไม่บอก คุณก็ต้อง parse body เดิมสองรอบด้วย type สองแบบเพื่อกู้ข้อมูลหนึ่งบิตที่ validator มีอยู่แล้ว

นั่นคือสิ่งที่เกิดขึ้นจริงตอนสร้าง auth API ด้วย Glyph การสมัครที่ไม่มี key password เลยกลับมาเป็น weak_password เพราะกรณีไม่มีกับกรณีสั้นเกินไปให้ string เดียวกัน

ดูของจริง#

type เดียว ข้อจำกัดเดียว:

signup.glyph 
pub type Password = string where value.length >= 8

pub type Signup = {
  email: string,
  password: Password,
}

payload ที่ผิดสี่แบบ คำตอบสี่แบบ แต่ละแบบคือ Issue หนึ่งตัว แสดงเป็น code | path | message:

Signup.parse(...) 
// { "email": "user@example.com" }
missing     ["password"]  field `password` is required

// { "email": "user@example.com", "password": "short" }
refinement  ["password"]  expected Password (string where value.length >= 8)

// { "email": 42, "password": "longenough" }
type        ["email"]     field `email` must be string

// [1, 2, 3]
type        []            expected Signup (an object), got an array

ตัวที่สองคือประเด็น value.length >= 8 เขียนครั้งเดียวที่ type และการปฏิเสธยกมันมาตรงตัว คัด string นั้นจาก body ของ HTTP 422 ไปใส่ grep แล้วคุณจะเจอ declaration ที่สร้างมัน ไม่มีใครต้องเก็บสำเนาของกฎไว้ในชั้นข้อความ error ซึ่งเป็นวิธีที่ทั้งสองเพี้ยนออกจากกัน

ตัวที่สี่เคยแย่กว่าแค่ข้อความที่ไม่ดี array เป็น object สำหรับ typeof record ที่ไม่มี field บังคับจึงยอมรับมันทันที และ [1, 2, 3] ที่ถูกส่งมาได้ปัญหาที่ชวนงงหนึ่งข้อต่อ field ที่ประกาศไว้ ไม่มีข้อไหนบอกว่าคุณส่ง list มา

type ที่ซ้อนกันตอบแทนตัวเองได้#

field ที่ type ของมันมี descriptor ของตัวเองจะถูก validate ด้วย parse ของ type นั้น และปัญหาของมันกลับมาพร้อมชื่อ field นำหน้า path Password ที่ซ้อนลงไปสองชั้นจึงรายงาน ["body", "password"] และยังมีข้อความของตัวเอง คุณได้ทั้งตำแหน่งและเหตุผลจากปัญหาเดียวกัน โดยไม่ต้องรันอะไรซ้ำ

ใช้รหัส ไม่ใช่ string#

Issue มี code ที่ไม่บังคับ: "missing", "type", "refinement" หรือ "unexpected" ให้แตก branch ด้วยสิ่งนั้น การ match ด้วยข้อความคือความเปราะบางที่ Glyph มีไว้กำจัด และข้อความมีไว้ให้คนที่อ่าน response body

การแยก 400/422 โดยไม่อ่านข้อความ 
fn status_for(issues: Array<Issue>) -> number {
  let first = issues[0]
  return match first.code == "refinement" {
    true => 422,
    false => 400,
  }
}

code ไม่บังคับ Issue ที่คุณสร้างเอง และทุกโค้ดที่ใช้มันซึ่งเขียนก่อนที่มันจะมี จึงยังคอมไพล์ได้โดยไม่ต้องแก้

สถานะตอนนี้#

ใช้ได้วันนี้

record และ type แบบ where รายงานกฎที่ล้มเหลว ไม่ใช่แค่ field ที่ล้มเหลว: "missing" สำหรับ field บังคับที่ไม่มี, "type" สำหรับรูปร่างที่ผิด (รวมถึงสิ่งที่ไม่ใช่ object หรือเป็น array), "refinement" สำหรับค่าที่ผ่าน type พื้นฐานแต่ไม่ผ่าน predicate และ "unexpected" สำหรับ key ที่ type ไม่ได้ประกาศ refinement ยก predicate ของมันมาให้ field ที่ type มี descriptor จะส่งต่อให้ descriptor นั้น ปัญหาที่ซ้อนกันจึงมาพร้อม path เต็ม field ที่ไม่บังคับ (f?: T) ไม่เคยถูกรายงานว่าหายไป

กำลังคมขึ้น

มีสองขอบ field ที่ type ไม่มี descriptor ของตัวเอง เช่น type parameter ที่ไม่มีข้อจำกัด หรือ type ที่ import จาก .d.ts ที่เขียนเอง ยังได้การตรวจแบบแบนและปัญหา "type" คอมไพเลอร์ไม่สังเคราะห์ descriptor ให้สิ่งเหล่านั้น และการรัน glyph gen dts กับ declaration คือสิ่งที่ให้ descriptor แก่มัน module ที่ประกาศ type ของตัวเองชื่อ Issue เคยบังตัวใน prelude ภายในไฟล์ที่ emit และทำให้ทุก descriptor ใน module นั้นพัง ตั้งแต่ 0.1.60 declaration นั้นเป็น E0110 ที่บรรทัดที่ตั้งชื่อ type คุณจึงรู้ว่าปัญหาอยู่ตรงไหน แทนที่จะต้องอ่าน error ของ tsc เกี่ยวกับโค้ดที่ generate
