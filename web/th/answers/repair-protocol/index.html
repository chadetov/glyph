มันบอกว่าอะไรผิดในรูปข้อมูล ไม่ใช่ประโยคที่ต้อง parse: type ทั้งสอง สัญลักษณ์ที่ผิดในรูป module::name และรายการจำกัดของสิ่งที่วางแทนตรงที่ผิดได้อย่างถูกต้อง glyph check --agent เพิ่มสิ่งที่การแก้ต้องไม่ทำพัง ในกรณีที่คำตอบถูกกำหนดไว้ชัดเจน glyph fix จะเขียนให้

ทำไมเรื่องนี้สำคัญ#

loop ของเอเจนต์รอบคอมไพเลอร์คือ อ่าน error เดาการแก้ build ใหม่ ขั้นเดาคือจุดที่ความเสียหายเกิด และมันเกิดเพราะ error เป็น string เอเจนต์ที่อ่าน "non-exhaustive match on OrderStatus" รู้ว่า match ขาด arm ไปบางตัว แต่ไม่รู้ว่า variant ที่ขาดถืออะไรไว้ มันจึงเขียน Paid("tx_1") แล้วไปรู้จาก diagnostic ถัดไป หรือมันอ่านคำว่า "exhaustive" เพิ่ม arm else แล้ว build ก็เขียว โดยทิ้งการรับประกันที่ diagnostic มีไว้ปกป้องไปแล้ว

คอมไพเลอร์รู้ทั้งหมดนั้น มันรู้ variant ของ union และ payload ของแต่ละตัว รู้ว่า else จะทำให้เสียการปิดผนึก และทิ้งทั้งสองอย่างไปหนึ่งบรรทัดก่อนตอบ

ดูของจริง#

โปรเจกต์สอง module orders ประกาศ union ส่วน main เขียน match บนมันและจัดการแค่ case เดียว glyph check --agent ตัดเหลือเฉพาะ key ที่สำคัญตรงนี้:

glyph check --agent --no-tsc src 
{
  "code": "E0200",
  "severity": "error",
  "stage": "typecheck",
  "message": "non-exhaustive match on `OrderStatus`: missing variants
              `Paid`, `Cancelled`",
  "help": "Add an arm for each missing variant.",
  "file":   "main.glyph",
  "module": "main",
  "entity": "main::describe",
  "cause":  "orders::OrderStatus",
  "related": ["Pending", "Paid", "Cancelled"],
  "missing_variants": ["Paid", "Cancelled"],
  "expected": null, "actual": null, "alternatives": null,

  "constraints": [
    "preserve exhaustiveness: this match must name every case of
     `OrderStatus`, so add one arm for each of `Paid`, `Cancelled`.",
    "do not add an `else` arm: `OrderStatus` is declared in this project,
     and a catch-all forfeits the guarantee that adding a variant to it
     later forces this match to be updated (D9)."
  ],

  "symbols": [
    { "entity": "orders::OrderStatus", "kind": "union", "pub": true,
      "type": "Pending | Paid({ transaction_id: string }) | Cancelled",
      "exhaustive_match": true,
      "variants": [
        { "name": "Pending", "payload": null, "construct": "Pending" },
        { "name": "Paid",    "payload": "{ transaction_id: string }",
          "construct": "Paid({ transaction_id: string })" },
        { "name": "Cancelled", "payload": null, "construct": "Cancelled" }
      ] }
  ],
  "symbols_absent": [],

  "explain": { "command": "glyph --explain E0200",
               "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200" }
}

มีสามเรื่องที่ควรดึงออกมา cause คือสัญลักษณ์ที่ผิด และเป็นคนละอย่างกับ entity ซึ่งคือ declaration ที่ diagnostic อยู่ ตรงนี้การแก้เกิดใน main::describe และรูปร่างที่ต้องตรงมาจาก orders::OrderStatus ทั้งสองเป็นที่อยู่ที่เครื่องมืออื่นรับได้ คำตอบจึงต่อกันได้โดยไม่ต้องหาอะไรใหม่

constraints ไม่ใช่การแก้ แต่ละข้อคือสิ่งที่คอมไพเลอร์บังคับใช้อยู่แล้ว เขียนออกมาเพื่อให้การแก้ที่ทำให้ diagnostic หายไปไม่ทำลายการรับประกันที่อยู่เบื้องหลัง ข้อจำกัดข้อที่สองคือเหตุผลที่ key นี้มีอยู่: arm แบบ else ถูกต้องตามกฎ มันจะทำให้ build เขียว และข้อจำกัดบอกว่าการเลือกมันต้องแลกกับอะไร

symbols คือคำตอบของ glyph_symbol สำหรับทุกสัญลักษณ์ที่ diagnostic อ้างถึง การแก้ครั้งถัดไปของเอเจนต์จึงไม่ต้องเรียกซ้ำ สัญลักษณ์ที่เครื่องมือปฏิเสธจะอยู่ใน symbols_absent พร้อมเหตุผล ซึ่งแยก "เราไม่ได้ดู" ออกจาก "เราดูแล้วและมันไม่มี"

ทุก key มีอยู่เสมอ ข้อเท็จจริงที่คอมไพเลอร์ไม่มีจะมาเป็น null อย่างชัดแจ้ง ไม่เคยเป็น key ที่หายไป การไม่มีจึงมีวิธีเขียนแบบเดียวในทุกรหัส และทั้งบน CLI และ MCP

เมื่อคำตอบถูกกำหนดไว้ชัดเจน คอมไพเลอร์เขียนให้#

glyph fix ใช้เฉพาะการแก้ที่คอมไพเลอร์ตัดสินได้เอง: import ที่ไม่ได้ใช้, หัวของ arm ที่ไม่ใช่ variant เมื่อตัวตรวจคำนวณคำแนะนำได้ตัวเดียวพอดี และ field ที่ record ไม่ได้ประกาศเมื่อมี field ที่ประกาศไว้ตัวเดียวพอดีที่ห่างไปหนึ่งตัวอักษร match ข้างบนไม่ใช่หนึ่งในนั้น

glyph fix src กับ match ข้างบน 
glyph fix: removed 0 unused import(s) across 0 file(s).
glyph fix: declined E0200 in src/main.glyph: the compiler does not
           determine what a missing arm should do, so `glyph fix`
           writes none: add an arm for each of `Paid`, `Cancelled`.
           `glyph check --agent` gives the pattern each case takes.

// src/main.glyph is unchanged, and glyph check still fails with E0200.

คอมไพเลอร์รู้ว่า case ไหนขาดไป และ pattern ที่แต่ละตัวใช้ แต่ไม่รู้ว่าโปรแกรมควรทำอะไรเมื่อคำสั่งซื้อเป็น Paid และ body ใดๆ ที่มันเขียนก็คือการเดาที่คอมไพล์ผ่าน จนถึง 0.1.128 glyph fix เขียนการเดานั้น: หนึ่ง arm ต่อ case โดย body พิมพ์ชื่อ case แล้วเรียก process.exit(1) จากนั้นโปรแกรมก็ผ่าน check, tsc และ build และ glyph query variants รายงานว่า match ครบทุกกรณี case ที่ขาดจึงย้ายจาก compile error ไปเป็น crash ตอนรัน โดยไม่เหลืออะไรคอยเตือน

กฎจึงปฏิเสธ และระบุชื่อ case ทุกอย่างที่ต้องใช้เขียน arm อยู่ในคำตอบ --agent ข้างบนแล้ว: missing_variants และวิธีเขียน construct ของแต่ละ variant ใต้ symbols arm เป็นสิ่งที่คุณหรือเอเจนต์ของคุณต้องเขียน เหมือนโค้ดอื่นที่คอมไพเลอร์อนุมานพฤติกรรมไม่ได้

สิ่งที่ glyph fix เขียน มันเขียนโดยไม่เดา และทุกกฎที่ตัดสินคำตอบไม่ได้จะพิมพ์การปฏิเสธพร้อมเหตุผลลงใน output เดียวกับสิ่งที่มันทำ field สองตัวที่ห่างจากคำผิดหนึ่งตัวอักษรคือสองตัว ไม่ใช่ตัวเดียว และมันจะบอกแบบนั้นแทนที่จะเลือกเอง

คำอธิบายของรหัสเอง ในรูปข้อมูล#

glyph --explain <CODE> --json ตอบด้วยคำอธิบายแบบยาว help หนึ่งบรรทัด URL ของเอกสาร และโปรแกรมที่ผิดจากชุดตัวอย่างเชิงลบของคอมไพเลอร์ คู่กับ diagnostic ที่คอมไพเลอร์ตัวนี้ให้กับมัน diagnostic ถูกคอมไพล์เมื่อคุณถาม ไม่ได้เก็บไว้ มันจึงไม่เพี้ยนจากสิ่งที่คอมไพเลอร์พูดจริง

glyph --explain E0200 --json 
{
  "code": "E0200",
  "title": "non-exhaustive match",
  "explanation": "A `match` over a tagged union must handle every variant.
    Unions are sealed (D9): adding a variant later forces every match to be
    updated, so a missing variant cannot silently fall through at runtime ...",
  "help": "Add an arm for each missing variant.",
  "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200",
  "counter_example": {
    "name": "alias_of_local_union_not_exhaustive",
    "expected_error": "E0200",
    "files": [ { "path": "alias_of_local_union_not_exhaustive.glyph",
                 "source": "module main\n\ntype Shape =\n  | Circle\n ..." } ],
    "diagnostic": { "code": "E0200",
                    "message": "non-exhaustive match on `Shape`: missing variants `Tri`",
                    "cause": "alias_of_local_union_not_exhaustive::Shape",
                    "related": ["Circle", "Square", "Tri"],
                    "missing_variants": ["Tri"] },
    "corrected": null,
    "corrected_absent": "`tests/negative/` pairs no repaired program with a case:
      an entry is a wrong program and the code it draws. A fix invented here would
      compile nowhere and be checked by nothing."
  }
}

รหัสที่ชุดตัวอย่างไม่ครอบคลุมจะกลับมาพร้อม counter_example: null และประโยคที่บอกว่าชุดตัวอย่างไม่มีกรณีสำหรับมัน แทนที่จะเป็นตัวอย่างที่แต่งขึ้น ชุดตัวอย่างอ้างเฉพาะสิ่งที่มันครอบคลุม และไม่อ้างอะไรเกี่ยวกับส่วนที่เหลือ

glyph --explain ให้หนึ่งกรณีต่อรหัส ชุดตัวอย่างทั้งหมดก็อ่านได้: glyph llms --negative E0200 พิมพ์ทุกโปรแกรมที่ผิดที่ได้รหัสนั้น แต่ละตัวคอมไพล์เมื่อคุณถาม และในกรณีที่ชุดที่สองจับคู่โปรแกรมที่ tsc --strict ยอมรับกับ Glyph ที่ปฏิเสธมัน ก็จะกลับมาข้างๆ ถ้าไม่ระบุรหัส มันแสดง 102 กรณีบน 46 จาก 70 รหัส และระบุชื่อ 24 รหัสที่ไม่มี ความครอบคลุมจึงถูกระบุไว้ ไม่ใช่อนุมานจากสิ่งที่กลับมา สิ่งนั้นและส่วนที่เหลือที่คอมไพเลอร์เผยแพร่เกี่ยวกับตัวเองอยู่ในหน้าของมันเอง

สถานะตอนนี้#

ใช้ได้วันนี้

ทุก diagnostic มี expected, actual, cause, alternatives (พร้อม alternatives_kind ที่บอกว่ามันแสดง fields, members, variants, literals หรือ exports ซึ่งตั้งไว้ตรงที่ error ถูกแจ้ง), related, module, file และ explain เติมจาก error ที่คอมไพเลอร์แจ้งจริง ไม่ได้หาใหม่ และแต่ละตัวเป็น null อย่างชัดแจ้งเมื่อคอมไพเลอร์ไม่มีข้อเท็จจริงนั้น file เป็น path ที่สัมพัทธ์กับ resolution root และรายงานระบุ root นั้นใน project_root จึงเปิดได้ glyph check --agent เพิ่ม constraints และ symbols ต่อ diagnostic glyph fix ใช้สามกฎ (E0106, E0210, E0220) และระบุทุกการปฏิเสธพร้อมเหตุผล รวมถึง E0200 ทุกตัว ซึ่งมันรายงานและไม่เคยเขียน glyph --explain <CODE> --json คืนคำอธิบายพร้อมตัวอย่างค้านที่คอมไพล์แล้ว และ glyph llms --negative <CODE> คืนชุดโปรแกรมที่ผิดทั้งหมดที่ได้รหัสนั้น

หยุดตรงไหน

cause ของ E0211 เป็น null: สัญลักษณ์ที่ผิดที่ argument ของการเรียกคือ parameter และ module::fn.param ไม่ใช่สิ่งที่คำศัพท์ของตัวตนเขียนได้ null นั้นจึงเป็นความตั้งใจ ไม่ใช่การตกหล่น corrected ในตัวอย่างค้านเป็น null เสมอ เพราะชุดตัวอย่างเชิงลบไม่ได้จับคู่โปรแกรมที่แก้แล้วกับกรณีใด และ 24 จาก 70 รหัสไม่มีกรณีเลย glyph fix เขียนสามกฎและไม่มีอย่างอื่น และไม่เขียน arm ให้ match ที่ไม่ครบ: สิ่งเหล่านั้นเหลือไว้ให้คุณหรือเอเจนต์ของคุณ โดยมี case และ pattern อยู่ใน diagnostic ทุกอย่างที่มันปฏิเสธ มันปฏิเสธอย่างเปิดเผย
