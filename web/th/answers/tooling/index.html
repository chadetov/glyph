ทำไมเรื่องนี้สำคัญ

การแก้ภาษาที่ editor ไม่เข้าใจให้ความรู้สึกเหมือนถอยหลัง และช่วงแรกนั่นเป็นข้อตำหนิที่ยุติธรรม ตอนนี้ไม่ใช่แล้ว: editor ให้ความสะดวกสมัยใหม่ครบ และ error ถูกเขียนมาเพื่อสอน ไม่ใช่แค่ปฏิเสธ

เป็น LSP จริง หรือแค่ plugin ของ VS Code?

เป็นของจริง คอมไพเลอร์มาพร้อม language server ที่คุณเปิดด้วย glyph lsp ซึ่งสื่อสาร Language Server Protocol ผ่าน stdio (transport JSON-RPC มาตรฐานที่ LSP client ทุกตัวเข้าใจ)

extension ของ VS Code ที่มาด้วยเป็นแค่ client บางๆ ครอบมัน แต่ไม่มีอะไรผูกกับ VS Code: ชี้ editor ใดก็ได้ที่รองรับ LSP เช่น Neovim, Helix, Zed, Emacs (eglot) ไปที่ glyph lsp แล้วมันทำงานเหมือนกัน

มันคือ binary ตัวเดียวกับที่คุณติดตั้งไว้แล้ว (npx @glyphlang/glyph lsp) จึงไม่มี server แยกให้ดึงมา

สิ่งที่ server ทำได้

server ทำสิ่งที่ editor ต้องการ: diagnostic สดพร้อมรหัสคงที่ด้านล่าง, type ตอน hover, go-to-definition (ข้าม module ผ่าน import ด้วยชื่อ ส่วนผ่าน namespace อย่าง ui.Button ยังไม่ตอบอะไร), completion, symbol ของเอกสารและของ workspace สำหรับ outline และการค้นหาสัญลักษณ์, find-references ทั้ง workspace, rename และการจัดรูปแบบตาม layout มาตรฐานของ glyph fmt สำหรับ format-on-save

rename ครบถ้วน: การเปลี่ยนชื่อ declaration ระดับ module แก้นิยามของมัน ทุก reference และ binding ของ import ในแต่ละ module ที่ import มันทั่ว workspace และตรวจชื่อใหม่ (ต้องเป็น identifier จริง ไม่ใช่ keyword) ก่อนจะแตะอะไร

มีสองข้อจำกัดที่ควรรู้: index ข้ามไฟล์ถูกสร้างใหม่ทุก request แทนที่จะ cache ไว้ (ใช้ได้ดีกับโปรเจกต์ปกติ ควรทำให้เร็วขึ้นทีหลัง) และไฟล์ที่ตอนนี้ parse ไม่ผ่านจะถูกข้าม rename จึงไปไม่ถึง reference ในไฟล์ที่พังอยู่เอง

ข้อความ error

เราปรับข้อความให้คมขึ้นตรงจุดที่เอเจนต์และคนใหม่สะดุดบ่อยที่สุด: การเขียน if ตอนนี้ชี้คุณไปที่ match แทนที่จะเป็น “unexpected token” ทั่วไป และจำนวน argument ที่ผิด match ที่ไม่ครบ หรือ variant ที่พิมพ์ผิด ต่างก็ได้ error ที่มีรหัสและแก้ได้ของตัวเอง

type error ที่ back-end TypeScript เท่านั้นจับได้เคยชี้ไปที่ .ts ที่ generate ตอนนี้มันถูก map กลับไปยัง .glyph ของคุณ (เครื่องหมายชี้ของ ariadne แบบเดียวกัน รหัสคงที่เดียวกัน) error ของ tsc จึงอ่านเหมือนเป็นของ Glyph เอง

การดีบัก

คุณดีบัก TypeScript ที่ emit ออกมาด้วยเครื่องมือที่ใช้อยู่แล้ว อย่าง inspector ของ Node, devtools ของเบราว์เซอร์ หรือ debugger JS/TS ของ IDE

ทุก build มี source map มาตรฐาน v3 ข้างแต่ละ .ts (พร้อมฝังซอร์ส Glyph) debugger หรือ bundler ที่ไล่ map ต่อกันจึงก้าวกลับไปยังเลขบรรทัดใน .glyph ได้

มีอย่างหนึ่งที่ยังไม่ครอบคลุม: stack ตอน crash ของ glyph run เองยังพิมพ์บรรทัดของ .ts เพราะ tsx ไม่ได้ไล่ map ต่อผ่านการแปลงของมัน การ remap stack นั้นคือสิ่งถัดไป

ถามว่า “มันคอมไพล์ผ่านไหม?” โดยไม่ต้องรัน

glyph check path.glyph ตรวจ type ไฟล์เดียวหรือทั้งไดเรกทอรีแล้วจบ มันไม่เขียนอะไรลง tree ของคุณ ซึ่ง glyph run สัญญาไม่ได้ และ glyph build ก็ไม่ทำเลย (มันปฏิเสธทุกอย่างที่ไม่ใช่ไดเรกทอรี)

--no-tsc--json--no-test
รายละเอียด มันรันอะไร และ flag ต่างๆ

มันรัน pipeline เดียวกับที่ build รัน รวมถึง tsc --strict บน TypeScript ที่ emit ออกมา ลงในไดเรกทอรีชั่วคราวที่มันลบตอนออก --no-tsc หยุดหลังขั้นของ Glyph เมื่อคุณต้องการคำตอบเร็ว --json ให้เอเจนต์ได้รูปแบบ diagnostic เดียวกับที่ glyph build --json ให้ ไฟล์ถูกตรวจในบริบทของไดเรกทอรีของมันเอง ไฟล์ข้างเคียงที่พังจึงยังทำให้การตรวจ fail เทสต์ @example และ @doc @run ก็รันที่นี่ด้วย เป็น gate เดียวกับที่ glyph build ใช้ การตรวจจึงรายงานว่า tree สะอาดในขณะที่ build จะ fail ไม่ได้ --no-test ข้ามมันเมื่อคุณต้องการคำตอบที่ไม่รันอะไรเลย

transcript ก็ไม่โกหกคุณเช่นกัน

ตอนนี้สรุปพิมพ์หลังทุกขั้นที่อาจทำให้ build แดง build ที่แดงจึงไม่มีวันแสดงบรรทัดสีเขียว

ที่มา สรุปที่มาเร็วเกินไป

build ที่ fail เคยเปิดด้วย “no diagnostics” แล้วพิมพ์ error ของ tsc ข้างใต้ เพราะสรุปของขั้น Glyph ถูกเขียนก่อนที่ขั้น TypeScript จะรัน

ในรอบเดียวกัน glyph run app.glyph --min -12.50 ก็เริ่มใช้ได้: ขีดนำหน้าเคยทำให้ clap ปฏิเสธ argument ก่อนที่ main ของคุณจะได้เห็น

flag ที่ glyph เป็นเจ้าของยังผูกกับ glyph จึงต้องใส่ -- หน้า flag ของโปรแกรมที่ชนกับตัวใดตัวหนึ่ง

และสำหรับเอเจนต์ใน loop

glyph build --json emit ทุก diagnostic เป็น JSON ที่มีโครงสร้าง: รหัสคงที่ severity ข้อความ ไฟล์ และช่วง line/column เริ่มจาก 1 พร้อม help และ note รวมถึง error ของ tsc ที่ map ไปยังซอร์ส Glyph เอเจนต์อ่านและใช้ได้โดยตรงแทนที่จะขูดข้อความจาก terminal

glyph mcp สำหรับเอเจนต์แบบโต้ตอบ

สำหรับเอเจนต์แบบโต้ตอบ มีมากกว่า diagnostic แบบ batch: glyph mcp รันเซิร์ฟเวอร์ Model Context Protocol ผ่าน stdio (binary ตัวเดียวกัน การวิเคราะห์เดียวกับที่ editor ใช้) เปิดคิวรีของ language server ให้เป็นเครื่องมือ MCP เอเจนต์ถามได้ทั้ง diagnostic ของไฟล์, type ที่ตำแหน่งหนึ่ง, ชื่อหนึ่งถูกนิยามไว้ที่ไหน (ตาม import ไป), ทุกการอ้างอิงถึงสัญลักษณ์ทั่วทั้งโปรเจกต์ หรือการค้นหาสัญลักษณ์ โดยไม่ต้องรัน build เต็มหรืออ่านทุกไฟล์

มันเป็น adapter บางๆ บนชั้นวิเคราะห์ที่บริสุทธิ์ชั้นเดียวกัน ไม่ใช่ implementation ตัวที่สอง จึงเพี้ยนจากสิ่งที่คอมไพเลอร์และ editor เห็นไม่ได้

ไม่ใช่ทุกอย่างเป็น error ที่หยุด build

Glyph มีระดับคำเตือนที่ชี้ส่วนที่ไม่มีประโยชน์โดยไม่ทำให้ build fail: import ที่ไม่ได้ใช้ (E0106), let ที่ไม่ได้ใช้ (E0107 ยกเว้นชื่อที่ขึ้นต้นด้วย _) และโค้ดที่ไปไม่ถึงหลัง return/break/continue (E0108)

E0106E0107E0108

สิ่งเหล่านี้รักษา module ให้ซื่อตรง: import ที่ไม่ได้ใช้คือความรกที่ขัดกับการค้นหาด้วย grep ซึ่งทำให้คนอ่านต้องไล่หา dependency ที่โค้ดไม่ได้มีจริง คำเตือนแสดงใน output แบบ render และแบบ --json เหมือนกัน ทำเครื่องหมายด้วย severity และยัง emit TypeScript ออกมา

สถานะตอนนี้

ใช้ได้วันนี้

  • language server สำหรับทุก editor ที่ตอบข้ามขอบเขต moduleตั้งแต่ 0.1.124
    รายละเอียด

    language server (glyph lsp ผ่าน stdio ใช้ได้กับทุก editor มี extension ของ VS Code มาด้วย) ที่มี highlighting, diagnostic, hover, go-to-def, completion, symbol, find-references และ rename ทั้ง workspace และ format-on-save ตอบข้ามขอบเขต module ได้ตั้งแต่ 0.1.124: server ถือ database หนึ่งชุดต่อโปรเจกต์ โดยมี buffer ที่เปิดอยู่ซ้อนบนไฟล์ในดิสก์ การ hover ฟังก์ชันที่ import มาหรือ field ของ record ที่ import มาจึงได้คำตอบเดียวกับ glyph query hover การแก้ที่ยังไม่บันทึกในไฟล์หนึ่งมองเห็นได้จากอีกไฟล์ และการกดแป้นแต่ละครั้งใช้เวลามากขึ้นหนึ่งถึงเก้าเปอร์เซ็นต์จากตอนที่ทำงานไฟล์เดียว;

  • เซิร์ฟเวอร์ Model Context Protocol glyph mcp ที่มีสิบเอ็ดเครื่องมือ
    รายละเอียด

    เซิร์ฟเวอร์ Model Context Protocol glyph mcp ที่มีสิบเอ็ดเครื่องมือ คือคิวรีของ editor บวก glyph_symbol, glyph_impact, glyph_assignable, glyph_dependencies และ glyph_exports แต่ละตัวมีคำสั่งย่อยของ glyph query ที่พิมพ์ JSON เดียวกันให้เอเจนต์ที่ไม่มี MCP client;

  • รหัส error ที่คงที่, glyph --explain, error จาก back-end tsc ที่ map ไปยังซอร์ส .glyph, ระดับคำเตือน (import/binding ที่ไม่ได้ใช้, โค้ดที่ไปไม่ถึง) และ diagnostic แบบมีโครงสร้าง --json
  • glyph check [path] ตรวจ type ไฟล์เดียวหรือทั้ง tree โดยไม่รันและไม่เขียน output
  • glyph fmt --check เป็น gate การจัดรูปแบบใน CI: ไม่เขียนอะไรและ exit ไม่เป็นศูนย์เมื่อไฟล์ยังไม่อยู่ใน layout มาตรฐานแบบเดียว

กำลังมา

  • cache index ข้ามไฟล์แทนที่จะสร้างใหม่ทุก request (เร็วขึ้นบน tree ขนาดใหญ่)
  • remap stack ตอน crash ของ glyph run เอง เพราะ tsx ไม่ได้ไล่ map ที่ emit ต่อผ่านการแปลงของมัน stack นั้นจึงยังอ้างถึง .ts ที่ emit แทนที่จะเป็น .glyph ของคุณ
