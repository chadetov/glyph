ทำไมเรื่องนี้สำคัญ

ใน TypeScript stack ส่วนใหญ่ ทุก payload ถูกอธิบายสองครั้ง: ครั้งหนึ่งเป็น type สำหรับคอมไพเลอร์ และอีกครั้งเป็น validator ที่เขียนเองเพื่อให้ค่ามีรูปร่างนั้นจริงตอนรัน

ทั้งสองเพี้ยนออกจากกัน และความเพี้ยนคือที่ที่ข้อมูลผิดเล็ดลอดเข้ามา Glyph รวมมันเป็น declaration เดียว: type สร้าง validator ทั้งสองจึงขัดแย้งกันไม่ได้

ดูของจริง

ประกาศ DTO ครั้งเดียว descriptor ของมันให้ .parse (validate ค่าที่ไม่น่าไว้ใจให้เป็น type นั้น) และ .is (type guard) โดยไม่ต้องเขียนอะไรอีก:

api.glyph 
type NewTask = {
  title: string,
  done: bool,
}

fn create(req: Request)
  -> Result<Response, string> {
  return match NewTask.parse(req.body) {
    Ok(task) => Ok(json(201, task)),
    Err(issues) => Ok(json(400, {
      error: "invalid task",
    })),
  }
}
สิ่งที่คุณไม่ได้เขียน 
// No zod schema:
const NewTask = z.object({
  title: z.string(),
  done: z.boolean(),
});
// No drift between the type and
// the validator, because there is
// only one declaration.

// A bad body, {"title": 123},
// takes the Err arm. Only a
// well-formed body reaches Ok.

เก็บค่าที่มี type ไว้หลัง match

คุณดึงค่าออกมาแทนที่จะทำงานภายใน arm ก็ได้

api.glyph: ค่าออกจาก match พร้อม type 
let task = match NewTask.parse(req.body) {
  Ok(t) => t,
  Err(issues) => { return bad_request(issues) },
}
task.titel   // E0210: type `NewTask` has no field `titel`; did you mean `title`?
ตั้งแต่ 0.1.45type แบบ generic: ยังไม่ได้
รายละเอียด type ถูกพาไปอย่างไร และข้อยกเว้นของ generic

T.parse มี type เป็น Result<T, Array<Issue>> และ match ที่ arm ตรงกันพา type ของมันไปด้วย let task = match NewTask.parse(req.body) { Ok(t) => t, Err(issues) => { return bad_request(issues) }, } จึงให้ NewTask สำหรับส่วนที่เหลือของฟังก์ชัน โดยชื่อ field ถูกตรวจโดย Glyph แทนที่จะเป็น tsc บน TypeScript ที่ generate สิ่งนี้มาใน 0.1.45 ก่อนหน้านั้นค่าไม่มี type ทันทีที่ออกจาก match parse ของ type แบบ generic คือตัวที่ยังไม่ได้ เพราะ descriptor ของมันต้องรับตัวตรวจตอนรันหนึ่งตัวต่อ type parameter

ผลของการ parse เป็น Result ธรรมดา

ใน Glyph T.parse คืน Result แบบเดียวกับที่ทุกฟังก์ชันที่อาจล้มเหลวในภาษาคืน คุณจึงส่งมันกลับไปได้เลย ส่งผ่าน map_err เพื่อเปลี่ยนปัญหาจาก validation เป็น error type ของคุณ หรือส่งต่อขึ้นไปด้วย ?

boundary.glyph 
// Hand it straight back.
fn read_task(body: unknown)
  -> Result<NewTask, Array<Issue>> {
  return NewTask.parse(body)
}

// Or restate the failure in your own terms.
fn read_checked(body: unknown)
  -> Result<NewTask, string> {
  return NewTask.parse(body).map_err(
    fn(issues: Array<Issue>) -> string {
      return "invalid task: ${issue_text(issues)}"
    },
  )
}

// Or propagate it and get on with the work.
fn create(body: unknown) -> Result<Response, string> {
  let task = read_checked(body)?
  return Ok(json(201, save(task)))
}
สิ่งที่สิ่งนี้มาแทน 
// Until 0.1.52 the generated descriptor
// returned a bare { tag, value } object,
// so both of the first two shapes were
// tsc errors (TS2322 and TS2339) even
// though Glyph's own checker reported
// Result<T, Array<Issue>>. The workaround
// was an identity re-wrap:

match NewTask.parse(body) {
  Ok(t)  => Ok(t),          // does nothing
  Err(e) => Err(reword(e)),
}

// Four lines to say map_err. bracket.glyph
// carried this twice until the fix landed.
รายละเอียด ต้นทุนตอนรันของการใช้ Result ที่นี่

validator ที่คืนค่าในรูปร่างเฉพาะของมันเองมีประโยชน์แค่ครึ่งเดียว เพราะการจัดการ error ส่วนอื่นของคุณแตะมันไม่ได้ ผลของการ parse ไม่มีอะไรพิเศษ

เหตุผลที่เคยไม่เป็นแบบนี้: descriptor ถูก generate ข้าง type ของคุณ และการ emit object เปล่าๆ ทำให้ module ที่ประกาศ type ไม่ต้องพึ่ง std/result ตอนรัน ตอนนี้การแลกเปลี่ยนกลับด้าน module ที่มี pub type จะ import std/result ไม่ว่าจะเขียน Result หรือไม่ และการเรียก parse จะจอง closure ของ combinator แบบเดียวกับที่ Ok(...) ใดๆ จอง สิ่งที่ได้คือขอบเขตที่ validate แล้วกับการจัดการ error ส่วนที่เหลือเป็น API เดียวกัน

ประกอบเอง: output type ถูก derive ไม่ใช่ถูกเชื่อตามคำบอก

infer_output<Shape> ของ Glyph derive output type จาก shape และ tsc ตรวจ annotation ของคุณเทียบกับมัน shape ที่ขาด field ของ type ที่คุณอ้างจะคอมไพล์ไม่ผ่าน:

schema.glyph 
fn object_schema<Shape: Record<string, Schema<unknown>>>(
  shape: Shape,
) -> Schema<infer_output<Shape>> { ... }

type User = { name: string, age: number }

// The shape must produce a User, or this
// line does not compile:
const user_schema: Schema<User> =
  object_schema({
    name: string_schema(),
    age: number_schema(),
  })
ความเพี้ยนที่ Glyph กำจัด 
// TS/zod: shape and output type are two
// separate things you keep in sync by hand.
const s = z.object({ name: z.string() });
type User = { name: string; age: number };
// `s` is inferred { name }, but nothing
// checks it against User. The `age` you
// forgot is caught at runtime, if ever.

// Glyph: drop `age` from the shape and
// `Schema<User>` fails to compile. The
// shape is the single source of truth.
รายละเอียด กับดักของ TypeScript และ cast ที่ตามการ return ตั้งแต่ 0.1.92

บางครั้งคุณต้องการ combinator แบบ zod: สร้าง validator โดยประกอบตัวเล็กๆ เข้าด้วยกัน กับดักใน TypeScript คือoutput type ของ combinator กับshape ที่คุณส่งให้มันเพี้ยนออกจากกัน คุณเขียน shape แล้วเขียนซ้ำใน type parameter ตัวที่สอง และไม่มีอะไรตรวจว่ามันตรงกัน

type ที่ derive มาใช้ได้ไม่ว่า combinator จะ return อย่างไร infer_output ต้องมี cast หนึ่งตัวที่ขอบของฟังก์ชัน เพราะ body สร้างค่าที่ type system พิสูจน์ไม่ได้ว่ามี type ที่ derive จาก shape และคอมไพเลอร์เขียน cast นั้นให้คุณ จนถึง 0.1.91 มันถูกผูกกับ return <value> ธรรมดา ใส่ match ระหว่าง return กับค่า หรือจบ body ด้วย r? แล้วฟังก์ชันเดียวกันก็คอมไพล์ไม่ผ่าน: TS2322 บน TypeScript ที่ generate ทับ Glyph ที่คอมไพเลอร์ยอมรับไปแล้ว ตั้งแต่ 0.1.92 cast ตามการ return ไม่ใช่ตามวิธีเขียน return match strict { ... } จึงตรวจ type ได้เหมือนการเขียน return แบบเดียวของ body เดียวกัน

ส่วนที่เหลือของขอบเขตที่ไม่น่าไว้ใจ

descriptor ตัวเดียวกันคือสิ่งที่ทำให้ json.parse<T> ปลอดภัย: ให้ string JSON กับมัน แล้วมัน parse และ validate ในขั้นเดียว

Inputการเรียกคืนค่า
string JSONjson.parse<T>(text)Result<T, Array<Issue>>
body ที่ decode แล้วT.parse(value)Result<T, Array<Issue>>
headerheader(req, name)Option<string>
query parameterquery_param(req, name)Option<string>
รายละเอียด request body, header และ query parameter

request body มาถึงในรูปที่ decode แล้วเป็น unknown ตรงนั้นจึงใช้ T.parse(value) แทน: การรับประกันเดียวกัน ไม่มี cast

ส่วนที่เหลือของขอบเขตที่ไม่น่าไว้ใจมี type แบบเดียวกัน: header(req, name) และ query_param(req, name) คืน Option<string> header หรือ query parameter ที่ไม่มีจึงเป็น None และ match บังคับให้คุณจัดการ ละ arm None แล้วจะคอมไพล์ไม่ผ่าน input ที่ไม่มีจึงถูกอ่านราวกับว่ามีอยู่ไม่ได้ field ใน body ก็ใช้กฎเดียวกัน: timeout_ms?: number คือ key ที่ไม่มีหรือเป็นตัวเลข {"timeout_ms": null} จึงเป็น Err ที่ ["timeout_ms"] ไม่ว่าจะมาจาก T.parse, is T หรือ json.parse<T> ประกาศ timeout_ms?: Nullable<number> เมื่อฝั่งส่งเขียน null มา ก่อน 0.1.152 ค่า null นั้นกลับมาอยู่ใน Ok

map ที่ใช้ enum เป็น key ตรวจ key ไหม?

ตรวจ ตั้งแต่ 0.1.148 Record<Tier, int> ที่ type Tier = "free" | "pro" จะ parse ได้เฉพาะ object ที่มี key เป็น free และ pro พอดี: key ที่เกินและ key ที่ขาดต่างก็เป็น Err ซึ่งก็เป็นสิ่งที่ tsc บอกเกี่ยวกับ object เดียวกันที่เขียนเป็น literal

type ของ keyสิ่งที่ parse ตรวจกับแต่ละ key
union ของ string literalkey ตามรายการพอดี ไม่ขาด ไม่เกิน
string หรือตัวเลขที่ refine ด้วย wherepredicate
intการเขียนจำนวนเต็มแบบธรรมดา "01" และ "1.5" ไม่ผ่าน
stringไม่มีอะไรใหม่
รายละเอียด key แบบ refine และแบบ int และสิ่งที่ตัวตรวจยึดไว้

type ของ key ที่ refine ด้วย where รัน predicate กับทุก key และ key แบบ int ต้องเป็นการเขียนจำนวนเต็มแบบธรรมดา "01" และ "1.5" จึงถูกปฏิเสธ Record<string, V> ถูกตรวจเหมือนเดิมทุกประการ where refine union ของ string literal ไม่ได้ (type T2 = Tier where value != "pro" เป็น E0300 ตั้งแต่ 0.1.152) ให้เขียนสมาชิกที่คุณต้องการเป็น union ของมันเอง type T2 = "free" แล้วมันจะเป็น key ของ Record พร้อมการตรวจ key ให้ตรงเป๊ะแบบเดียวกัน ตั้งแต่ 0.1.153 ตัวตรวจของ Glyph เองก็ยึด key ของค่าที่คุณเขียนในโค้ดด้วย: Record<string, int> ใช้แทนที่ที่ประกาศเป็น Record<Tier, int> ไม่ได้ และกลับกันก็ไม่ได้ การข้ามไปมาจึงต้องผ่าน json.parse หรือ arm is Record<Tier, int> และ record.set รักษา key ที่ได้รับไว้ record แบบ generic ที่ใช้ type parameter ของตัวเองเป็น key จะถูกปฏิเสธ เว้นแต่ parameter นั้นเป็น string

ถ้า parse วันที่ จะได้วันที่จริงไหม?

ได้ และส่วนที่น่าสนใจคือสิ่งที่ได้กลับมาเมื่อ input ไม่ใช่วันที่ time.parse_iso คืน Option<number> และเป็น None สำหรับทุกอย่างที่ไม่ใช่ ISO-8601

ตัวสุดท้ายคือตัวที่ทำให้คนแปลกใจ และมันคือประเด็นทั้งหมด datetime ที่ไม่มี Z และไม่มี offset +HH:MM เป็นเวลาท้องถิ่นตาม grammar ของ ECMAScript การยอมรับมันจึงหมายความว่า string เดียวกันระบุวันในปฏิทินต่างกันขึ้นกับว่าเครื่องไหนรันโปรแกรม

รายละเอียด Date.parse ทำอะไรแทน และทำไมต้อง UTC

นั่นเป็นข้อกล่าวอ้างที่แข็งกว่า Date.parse ของ JavaScript ซึ่งรับข้อความรูปแบบอิสระ ("January 5 2026") อ่านวันที่ที่ไม่เติมศูนย์อย่าง "2026-1-3" ตาม timezone ที่ process บังเอิญรันอยู่ และรายงานวันที่เป็นไปไม่ได้ว่าสำเร็จโดยเลื่อนไปข้างหน้า: "2026-02-31" กลายเป็น 3 มีนาคม และคุณได้ตัวเลขกลับมาโดยไม่มีสัญญาณว่าเกิดอะไรขึ้น

ตัวอ่านปฏิทินของ Glyph (time.year, time.month, time.day) เป็น UTC และบอกไว้ชัด validator ที่แอบนำ timezone ของ host เข้ามาจะทำให้มันโกหก string จึงถูกปฏิเสธแทน และคุณเป็นคนตัดสินว่ามันหมายถึงอะไร

การป้องกันย้ายเข้าไปอยู่ใน primitive

เมื่อแอปเขียนการป้องกันความถูกต้องครอบ primitive ของ standard library การป้องกันนั้นควรอยู่ใน primitive นี่คือสิ่งที่แอปลบทิ้ง:

ก่อน: แอปป้องกัน stdlib 
const ISO_DATE = "^\\d{4}-\\d{2}-\\d{2}$"

fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match regex.matches(ISO_DATE, value) {
    false => Err(BadDate({ line: line, value: value })),
    true => match time.parse_iso(value) {
      Some(ms) => match string.starts_with(
        time.format_iso(ms), value
      ) {
        true => Ok(ms),
        false => Err(BadDate({ line: line, value: value })),
      },
      None => Err(BadDate({ line: line, value: value })),
    },
  }
}
หลัง: primitive รักษาเส้นเอง 
fn parse_date(line: int, value: string)
  -> Result<number, RowError> {
  return match time.parse_iso(value) {
    Some(ms) => Ok(ms),
    None => Err(BadDate({ line: line, value: value })),
  }
}

import std/regex หายไปด้วย บัญชีเดิม แถวที่ถูกปฏิเสธเดิม รายงานเหมือนเดิมทุกไบต์

ที่มา แอปรายงานค่าใช้จ่ายที่เป็นต้นเรื่อง

เรื่องนี้มาจากการเขียน CLI รายงานค่าใช้จ่ายด้วย Glyph ทุกแถวในบัญชีมีวันที่ และการบันทึกแถวผิดเดือนคือบั๊กที่สำคัญ แอปจึงไม่เชื่อ parse_iso ตัวเก่า: มันตรวจรูปร่างด้วย regex ก่อน แล้วแปลง timestamp กลับเป็นข้อความเพื่อจับวันที่ที่ถูกเลื่อน

คุณไม่ต้องเขียน type เองด้วยซ้ำ

ถ้ารูปร่างมีอยู่แล้วในสเปก OpenAPI หรือไฟล์ declaration ของ TypeScript ให้ generate type ของ Glyph จากมัน: declaration type จริงที่ commit ได้และ grep หาได้ แต่ละตัวมี descriptor ไม่ใช่สิ่งที่อนุมานขึ้นมาแบบมองไม่เห็น:

จากสเปก OpenAPI / JSON Schema

  --out src/
จากแพ็กเกจที่ติดตั้งไว้ ด้วยชื่อ 
glyph gen dts api-types \

type ของข้อมูลบน wire กลายเป็นขอบเขตที่ validate แล้ว โดยไม่มีอะไรเขียนเอง:

match Customer.parse(webhook_body) {
  Ok(c) => handle(c),

ชี้ glyph gen dts ไปที่ไฟล์ .d.ts หรือ อย่างข้างบน ไปที่แพ็กเกจ npm ที่ติดตั้งไว้ด้วยชื่อ: มัน resolve entry ของ declaration ของแพ็กเกจเองจาก node_modules และเขียน type ที่ commit ได้ให้คุณ import

สิ่งที่ materialize ได้วันนี้: gen dts อ่าน declaration interface และ type ที่แพ็กเกจ export รวมถึงที่อยู่ใน tree ของ declare namespace (reference ข้ามกันแบบเปล่าๆ resolve ผ่าน scope) และที่อยู่ในไฟล์ข้างเคียงที่ barrel index re-export (เดินทั้ง .d.ts ที่เป็น entry และทุก .d.ts ที่ import แบบ relative) generic ถูกรักษาไว้เต็มที่: interface Page<T> materialize เป็น type Page<T> และได้ descriptor ที่ validate แต่ละรายการตาม type argument ไม่ใช่แค่ว่ามีอยู่ re-export แบบ alias และ export * as resolve ผ่าน map ของ binding ต่อไฟล์ กรณีเดียวที่มันทำให้ปลอดภัยไม่ได้ คือชื่อ type ที่ชนกันข้ามสองไฟล์ที่เข้าถึงได้ มันจะแจ้งพร้อมหมายเหตุแทนที่จะ bind รูปร่างผิดไปเงียบๆ สำหรับสิ่งที่ materializer เข้าไม่ถึง ให้เขียนรูปร่างที่คุณใช้ข้ามขอบเขตเอง หรือใช้ทางออกฉุกเฉิน extern_ts

การ generate ใหม่ให้ผลเท่าเดิม การเปลี่ยนสเปกจึงเป็น diff ที่สะอาดและรีวิวได้ การ generate ซื่อตรงต่อ wire: string enum materialize เป็น union ของ string literal ("free" | "pro") parse จึงตรวจว่าเป็นสมาชิก ไม่ใช่แค่ว่าเป็น string และ match บนมันครบทุกกรณีได้โดยไม่ต้องมี else field แบบ integer กลายเป็น int ค่า 3.5 บน wire จึงไม่ผ่าน parse ในขณะที่ number ธรรมดาจะผ่าน ตรงไหนที่ construct ไม่มีรูปแบบ Glyph ที่ตรงพอดี (union ที่ไม่มี discriminator) มันจะทำให้แคบลงและพิมพ์หมายเหตุ แทนที่จะ emit validator ที่ปฏิเสธข้อมูลจริง record ที่ generate ยังมี @open parse จึงยอมรับ field ที่ API เพิ่มทีหลังได้ ขณะที่ยัง validate ทุก field ที่ประกาศไว้ schema ที่ตั้ง additionalProperties: false ยังเข้มอยู่ record ใน Glyph เข้มโดยค่าเริ่มต้น และนี่คือเครื่องหมายที่ตำแหน่งประกาศซึ่ง grep หาได้แบบเดียวกับที่ record ที่เขียนเองใช้ จึงไม่มีอะไรเปลี่ยนในความหมายของ record

type แบบ generic ก็ validate ได้ Paginated<T> ได้ descriptor ที่ parse รับ type argument: Paginated.parse<User>(body) ตรวจทุกรายการใน items ในฐานะ User ไม่ใช่แค่ว่ามีอยู่ และ match v { is Paginated<User> => ... } narrow แบบเดียวกัน สิ่งนี้ใช้ได้ข้ามขอบเขต module: นิยาม Paginated<T> ในไฟล์หนึ่ง import มันเข้าอีกไฟล์ แล้วทั้ง Paginated.parse<User>(body) และ is Paginated<User> ตรงนั้นยังตรวจแต่ละ element ในฐานะ User คอมไพเลอร์สร้างการตรวจต่อ element จาก type argument ที่จุดเรียก type แบบ generic อยู่ในไฟล์ไหนจึงไม่ต่างในสิ่งที่ถูก validate

จุดที่หยุด: descriptor ครอบคลุมรูปร่างที่ payload ส่วนใหญ่ประกอบขึ้น: object, primitive, array, reference, field ที่ไม่บังคับและ nullable และตอนนี้รวม type แบบ generic ที่ instantiation หนึ่งๆ type ที่ Glyph ไม่ได้ generate (แพ็กเกจภายนอกหรือ .d.ts ที่คุณแค่ import) ถูกตรวจ type แต่ไม่มี descriptor จนกว่าคุณจะ materialize ซึ่งตอนนี้ใช้คำสั่งเดียวกับแพ็กเกจที่ติดตั้งไว้ (glyph gen dts <package> สำหรับ interface และ type alias ระดับบนสุดที่มัน export) ขอบนั้นเป็นความตั้งใจ: type ที่ Glyph ไม่ได้ emit สัญญาการ validate ตอนรันไม่ได้ คุณจึงเลือกเปิดทีละแพ็กเกจ และผลลัพธ์ commit ได้และ grep หาได้ ไม่ใช่เสกขึ้นมาทุกครั้งที่ build

ฐานข้อมูลก็เป็นขอบเขตเช่นกัน

แถวที่อ่านจากฐานข้อมูลไม่น่าไว้ใจแบบเดียวกับ request body .parse ตัวเดียวกับที่ใช้กับ request body validate แถวได้

tasks.glyph 
type Task    = { id: int, title: string, done: bool }
type TaskRow = { id: int, title: string, done: int }

fn row_to_task(r: TaskRow) -> Task {
  return { id: r.id, title: r.title,
           done: r.done != 0 }
}

// A row is validated, then mapped. No cast.
match TaskRow.parse(row) {
  Ok(r)  => Ok(row_to_task(r)),
  Err(_) => Err("row failed validation"),
}
บั๊กที่สิ่งนี้กำจัด 
// TS, better-sqlite3 / node:sqlite:
const row = stmt.get(id) as Task;
// `row.done` is really 0 or 1, a number.
// Nothing complains. Then:
if (row.done === true) { ... }   // never runs

// The row was `unknown`; the cast invented
// a type. Glyph makes you validate the row
// into TaskRow, and the int-to-bool step is
// a line of code, not a silent lie.
รายละเอียด std/sqlite และ boolean แบบ 0 หรือ 1

แถวที่อ่านจากฐานข้อมูลไม่น่าไว้ใจแบบเดียวกับ request body: schema ของฐานข้อมูลกับความเข้าใจของโค้ดเกี่ยวกับแถวอาจไม่ตรงกัน และ cast (row as Task) ก็กลบมันไว้ std/sqlite ซึ่งเป็น module ฐานข้อมูลบน SQLite ที่มาในตัวของ Node เน้นเรื่องนี้ query คืน Array<Record<string, unknown>> จึงไม่มีทางใช้แถวเป็น Task โดยไม่ validate ก่อน

สิ่งนี้จับบั๊กที่คนปล่อยออกไปอยู่ตลอด SQLite ไม่มี type boolean คอลัมน์ done จึงกลับมาเป็นจำนวนเต็ม 0 หรือ 1 cast แถวเป็น record ที่มี field แบบ bool แล้ว task.done === true จะไม่มีวันเป็นจริงแบบเงียบๆ ใน Glyph รูปร่างของที่เก็บกับรูปร่างของโดเมนเป็นคนละ type และการแปลงระหว่างกันคือบรรทัดเดียวที่คุณมองเห็นจริง:

ทั้งหมดเป็นตัวอย่างที่ใช้งานได้: examples/apps/tasks/main.glyph คือ task API ที่เก็บข้อมูลถาวร ใช้ std/sqlite สำหรับเก็บข้อมูลและ std/http สำหรับ route ข้อมูลอยู่รอดข้ามการ restart และมีการ validate ทั้งฝั่ง wire และฝั่งฐานข้อมูล ไม่มี validator ที่เขียนเองเลย

webhook ที่มีลายเซ็นก็เป็นขอบเขตเช่นกัน

การตรวจลายเซ็นของ webhook ต้องใช้ไบต์ตรงตัวที่ผู้ส่งลงนาม ไม่ใช่สำเนาที่ serialize ใหม่ (การแปลง body ที่ parse แล้วกลับเป็น string เปลี่ยน whitespace และลำดับ key ทำให้ HMAC ไม่มีวันตรงกัน) http.raw(req) ให้ไบต์เหล่านั้นแก่คุณ การตรวจจึงอยู่ใน Glyph ได้: 

fn handle(req: Request) -> Result<Response, string> {
  let expected = crypto.hmac_sha256(secret, raw(req))
  return match header(req, "x-hook-signature") {
    Some(sig) => match sig == expected {
      true  => accept(req),          // then validate req.body with T.parse
      false => Ok(text(401, "bad signature")),
    },
    None => Ok(text(401, "missing signature")),
  }
}
รายละเอียด ไบต์ดิบสำหรับลายเซ็น body ที่ parse แล้วสำหรับรูปร่าง

req.body ยังเป็นค่าที่ parse แล้วสำหรับการตรวจรูปร่าง raw คือ payload ที่ไม่ถูกแตะต้องซึ่งลายเซ็นคำนวณจากมัน ตัวรับที่ตรวจลายเซ็นและ validate body ไม่ต้องมี TypeScript ที่เขียนเอง

type validate invariant ของมันได้ ไม่ใช่แค่รูปร่าง

การตรวจรูปร่างบอกคุณว่า field เป็นตัวเลข แต่ไม่บอกว่าจำนวนเงินไม่ติดลบ หรือคะแนนอยู่ระหว่าง 1 ถึง 5 refinement แบบ where ใส่ invariant นั้นไว้ใน type และ descriptor บังคับใช้มันที่ขอบเขต:

refinements.glyph 
type Amount   = int where value >= 0
type Rating   = int where value >= 1 && value <= 5
type NonEmpty = string where value.length > 0

// Amount.parse(-1)  -> Err   (not just "is a number")
// Rating.parse(6)   -> Err
// Amount.parse(3.5) -> Err   (int check too)

type Line = { amount: Amount, }
// Line.parse({ amount: -1 }) -> Err too:
// the predicate follows the type into
// the field, and across modules.
สิ่งที่คุณไม่ต้องเขียน 
// The check that usually lives three
// functions away from the boundary,
// if someone remembers it:
if (amount < 0) throw new Error(...);

// In Glyph it's the type. A value that
// fails the predicate never becomes an
// Amount in the first place.

    ตอนนี้ discriminated union generate ได้ทั้งจาก discriminator ของ OpenAPI และจาก union ใน .d.ts ของ TypeScript (dispatcher parse_<Name> อ่าน tag แล้ว validate เข้า variant ที่ถูก) ต่อไป: การครอบคลุม enum และ mapped type ที่ละเอียดขึ้น

  • โค้ด client และ server ที่มี type จากสเปกมีให้ใช้แล้ว ดู client และ server
  • timestamp กับ duration เป็น number ทั้งคู่
    รายละเอียด

    เรื่องวันที่ ความเข้มงวดคือฟีเจอร์ทั้งหมด และมันหยุดที่การ parse: parse_iso คืนค่าเป็นมิลลิวินาทีนับจาก epoch timestamp กับ duration จึงเป็น number ทั้งคู่ และไม่มีอะไรห้ามคุณบวกตัวหนึ่งเข้ากับอีกตัว type วันที่แยกต่างหากเป็นการตัดสินใจในอนาคต และไม่ใช่เรื่องเล็ก
