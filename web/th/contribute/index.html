    เหมาะกับใคร

    • Glyph เทียบกับ TypeScript ที่ใส่เครื่องมือครบสิ่งที่ tsc แบบ strict, zod และ eslint ยังปล่อยผ่าน

อ่านเป็นภาษาอังกฤษ

ภาษา: ไทย·อ่านเป็นภาษาอังกฤษ

หน้านี้เป็นฉบับแปล ฉบับภาษาอังกฤษคือฉบับอ้างอิง แจ้งปัญหาเกี่ยวกับคำแปล

ร่วมพัฒนา

คอมไพเลอร์สร้างขึ้นอย่างไร และช่วยได้อย่างไร

คอมไพเลอร์เป็น Rust workspace ที่มีสิบสอง crate อยู่ใน repository สาธารณะเดียว license เป็น MIT หรือ Apache-2.0 ตอนนี้ bug report ที่มีโค้ดทำซ้ำสั้นๆ ช่วยได้มากที่สุด การเปลี่ยนแปลงตัวภาษาเริ่มจาก issue เพราะทุกกฎย้อนกลับไปหา design decision ที่มีหมายเลขได้

pipeline#

glyph build ทำ lex, parse, resolve ชื่อ, ตรวจ type และ emit TypeScript แล้วรัน tsc --strict กับสิ่งที่มันเขียน ขั้นกลางๆ รันเป็นคิวรีแบบ incremental บน salsa การตรวจซ้ำจึงใช้ผลลัพธ์ที่การแก้ไม่ได้ทำให้เป็นโมฆะซ้ำได้

ไฟล์ .glyph หนึ่งไฟล์ ผ่าน crate ต่างๆ 
glyph-lexer → glyph-parser → glyph-resolver → glyph-typechecker → glyph-emit → tsc --strict
                (glyph-ast)        └──────── glyph-db (salsa) ────────┘
Crateทำอะไร
glyph-lexertoken, keyword, ขึ้นบรรทัดใหม่ที่มีความหมาย, template literal
glyph-asttype ของ syntax tree พร้อม source span บนทุก node
glyph-parserPratt parser สำหรับทุก decision ในสเปก รวม JSX
glyph-resolverการ resolve ชื่อ, กราฟของ module, การตรวจ import ข้าม module, prelude
glyph-dbpipeline คิวรีของ salsa และการทำให้เป็นโมฆะข้ามไฟล์
glyph-typecheckerการตรวจความครบถ้วน, ?, generic, owned, runtime descriptor, model ของ stdlib
glyph-emitตัวเขียน TypeScript, การ generate descriptor, source map ระดับ expression
glyph-formatterglyph fmt: layout เดียว รักษา comment ไว้ รันซ้ำได้ผลเท่าเดิม
glyph-lsplanguage server และเซิร์ฟเวอร์ MCP ใช้ชั้นวิเคราะห์ร่วมกัน
glyph-clibinary glyph และทุกคำสั่งย่อย
glyph-wasmคอมไพเลอร์ใน WebAssembly ซึ่งรัน playground
glyph-runtimeเป็น stub เทสต์รันผ่าน emitter และ tsx แทน

glyph-compiler/README.md มีบันทึกของทุก crate และจำนวนเทสต์ปัจจุบัน

build และทดสอบ#

Rust 1.95 ถูก pin ไว้ใน rust-toolchain.toml เทสต์บางตัวเรียก tsc และ tsx จึงต้องติดตั้งด้วย CI รัน clippy โดยถือ warning เป็น error และทั้ง cargo build และ cargo test ไม่ได้รันมัน จึงควรรันสคริปต์ก่อน push

จาก clone 
npm install -g tsx typescript
cd glyph-compiler
cargo build --release -p glyph-cli      # target/release/glyph
cargo test --workspace
cd .. && python3 scripts/check_clippy.py  # the exact clippy command CI runs

# after an intentional syntax-tree change
INSTA_UPDATE=always cargo test -p glyph-parser --test snapshots

diagnostic ใหม่ต้องมาพร้อมโปรแกรมใต้ tests/negative/ ที่ต้อง fail ด้วยรหัสนั้น ข้อกล่าวอ้างว่า Glyph จับอะไรที่ TypeScript พลาดได้ต้องอยู่ใน catches/ ซึ่งมี gate รันทั้งสองฝั่ง

อะไรที่วางแผนไว้ และอะไรที่ยังพัง#

docs/roadmap/releases.md คือ roadmap ของการออกรุ่น: แต่ละรุ่นที่ออกไปแล้วทำอะไร และรุ่นถัดๆ ไปมีไว้ทำอะไร docs/dogfooding-gaps.md คือบัญชี gap ข้อจำกัดทุกข้อที่เจอจากการสร้างแอปจริง แต่ละข้อมีหมายเลข (G ตามด้วยตัวเลข) พร้อมเครื่องหมายสถานะ gap ที่ยังเปิดอยู่และมีโค้ดทำซ้ำเป็นจุดเริ่มต้นที่ดี

issue และ pull request#

การแก้ toolchain, diagnostic, เอกสาร และตัวอย่าง ส่ง pull request ได้เลย การเปลี่ยน syntax หรือ semantics ต้องเริ่มจาก issue และเรื่องที่ใหญ่กว่านั้นต้องผ่านกระบวนการ RFC ใน docs/rfcs/ PR ที่ผ่อนกฎลง "เพื่อให้ใช้ง่ายขึ้น" น่าจะถูกปฏิเสธ เพราะข้อจำกัดคือหัวใจของเรื่อง ให้ pull request หนึ่งตัวแก้ gap เดียว ปกติหนึ่งถึงสาม commit และ sign ทุก commit (git commit -s) main ถูกป้องกันไว้และ merge ได้แบบ rebase เท่านั้น CONTRIBUTING.md มีกฎทั้งหมด และ issue ที่ติดป้าย good first issue ถูกกำหนดขอบเขตไว้สำหรับการเปลี่ยนแปลงครั้งแรก
