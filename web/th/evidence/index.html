Glyph v0.1.157
  • ทำไมต้อง Glyph

    เหมาะกับใคร

    • สำหรับคนสร้างเอเจนต์เซิร์ฟเวอร์ MCP และคิวรีที่ตอบได้
    • สำหรับคนที่มาจาก TypeScriptอะไรเปลี่ยน และอะไรเหมือนเดิม
    • สำหรับทีมรับประกันอะไร และการนำมาใช้ต้องแลกกับอะไร

    การออกแบบ

    • การออกแบบหลักสี่ข้อ และสิ่งที่ตั้งใจตัดออกไป
    • สี่เสาหลักตรวจสอบได้ ค้นหาได้ด้วย grep นามธรรม และ diff ที่คงที่
    • Glyph เทียบกับ Effectเปรียบเทียบภาษากับไลบรารี
    • ทำไมไม่ใช้ ReScript, Gleam หรือ Elm?ภาษาที่มีชนิดข้อมูลสามภาษาที่คอมไพล์เป็น JavaScript
    • Glyph เทียบกับ TypeScript ที่ใส่เครื่องมือครบสิ่งที่ tsc แบบ strict, zod และ eslint ยังปล่อยผ่าน
  • เรียนรู้

    เริ่มต้นใช้งาน

    • เริ่มได้ใน 10 นาทีติดตั้ง เขียนโปรแกรม แล้วรัน
    • คำตอบ 28คำถามที่วิศวกรถามบ่อย พร้อมตัวอย่างประกอบ
    • เอกสารอ้างอิงภาษาสเปกฉบับเต็มบน GitHub
    • ร่วมพัฒนาคอมไพเลอร์สร้างขึ้นอย่างไร และช่วยได้อย่างไร

    เชื่อมต่อเอเจนต์

    • เซิร์ฟเวอร์ MCPเชื่อมเอเจนต์ของคุณเข้ากับคิวรีของคอมไพเลอร์
    • ถามคอมไพเลอร์ค้นสัญลักษณ์ ชนิด หรือผลของการเปลี่ยนแปลงก่อนแก้ไข
    • llms.txt สำหรับเอเจนต์ทั้งภาษาในไฟล์เดียวที่เอเจนต์อ่านได้
  • จับอะไรได้บ้าง

    • ข้อกล่าวอ้างถูกตรวจสอบอย่างไรfixture และ CI gate ที่อยู่เบื้องหลังแต่ละข้อกล่าวอ้าง
    • การทดสอบความแข็งแรงเอเจนต์ที่พยายามทำให้พัง และสิ่งที่พวกมันเจอ
    • Benchmarkหลักสี่ข้อในรูปตัวเลข พร้อมข้อควรระวัง
    • สิ่งที่ยังจับไม่ได้ช่องโหว่ที่รู้แล้ว แต่ละจุดมีโค้ดสำหรับทำซ้ำ
    21 จาก 37กรณีของ TypeScript ที่ไม่มีอะไรในโปรเจกต์ที่ตั้งค่าเต็มที่จับได้ดูว่าจับอะไรได้บ้าง

อ่านเป็นภาษาอังกฤษ

ภาษา: ไทย·อ่านเป็นภาษาอังกฤษ

หน้านี้เป็นฉบับแปล ฉบับภาษาอังกฤษคือฉบับอ้างอิง แจ้งปัญหาเกี่ยวกับคำแปล

หลักฐาน

แต่ละข้อกล่าวอ้างบนเว็บนี้ถูกตรวจอย่างไร

ข้อกล่าวอ้างว่า Glyph จับอะไรได้ คือโปรแกรมคู่หนึ่งใน repository ตัวหนึ่งเป็น TypeScript อีกตัวเป็น Glyph และมี CI gate รันทั้งคู่ทุกครั้งที่มีการเปลี่ยนแปลง ถ้า TypeScript คอมไพล์ไม่ผ่าน หรือ Glyph ไม่ปฏิเสธอีกต่อไป build จะ fail คุณรันกรณีไหนก็ได้เองด้วยสองคำสั่ง

fixture#

แต่ละไดเรกทอรีใต้ catches/ มี ts.ts, glyph.glyph และ case.toml ที่บอกว่าแต่ละตัวทำอะไร scripts/check_catches.py รันใน CI มันกำหนดให้ ts.ts ทุกตัวต้องผ่าน tsc --strict เพราะโปรแกรม TypeScript ที่คอมไพล์ไม่ผ่านไม่ได้พิสูจน์อะไร และตรวจฝั่ง Glyph ตามชนิดของกรณี รวมทั้งหมดมี 50 กรณีที่ตรวจแล้ว ได้แก่ กรณีของ TypeScript 37 กรณี กับดักของ JavaScript ที่ไม่มีใน Glyph 5 กรณี และช่องโหว่ที่ Glyph ยังปิดไม่ได้ 8 กรณี Glyph ปฏิเสธ 28 กรณีในจำนวนนี้ตอน build (กรณีของ TypeScript 23 กรณี และกับดัก 5 กรณี) แยกตามชนิดที่ gate ตรวจ:

ชนิดกรณีสิ่งที่ gate กำหนดให้ฝั่ง Glyph
refused28build fail ด้วยรหัสที่อยู่ใน case.toml
warned3build ผ่าน และรายงานรหัสนั้นเป็นคำเตือน
boundary9โปรแกรมรัน และการตรวจที่ขอบเขตเปลี่ยนข้อมูลที่ผิดให้เป็น Err
runtime2โปรแกรม build ผ่าน แล้วหยุดตอนรัน พร้อม output ที่ระบุไว้
gap8Glyph ยอมรับโปรแกรมและมันทำสิ่งที่ผิด เมื่อช่องโหว่ถูกปิด gate จะ fail และบอกให้ย้ายกรณีนั้น

กรณีที่แสดงให้เห็นไม่ได้อีกต่อไปจะถูกลบทิ้ง ไม่ใช่ถูกทำให้อ่อนลง และ README ของ catches แสดงหกกรณีที่ถูกลบพร้อมเหตุผล หนึ่งในนั้นกลายเป็นว่า tsc ก็จับได้ อีกกรณีใช้ได้แค่เพราะ TypeScript ของมันรับค่ามาเป็น any

TypeScript ที่ใช้เปรียบเทียบ#

แต่ละกรณีบอกด้วยว่าโปรเจกต์ TypeScript ที่ตั้งค่าเต็มที่จะจับความผิดพลาดนั้นได้หรือไม่ ซึ่งเป็นที่มาของป้าย "TypeScript จะจับได้ไหม" "ตั้งค่าเต็มที่" หมายถึง tsc --strict บวกทุก option ที่ทำให้เข้มขึ้น และการรัน typescript-eslint gate ติดตั้งแพ็กเกจใหม่ทุกครั้งที่รัน (TypeScript 6, eslint 9, typescript-eslint 8, tsx 4 และ @types/node ล่าสุด) และจะ fail แทนที่จะข้ามเมื่อไม่มี network

option ของ tsconfig ที่เพิ่มจาก strict 
noUncheckedIndexedAccess: true
noFallthroughCasesInSwitch: true
noUnusedLocals: true
noUnusedParameters: true
noImplicitReturns: true
noImplicitOverride: true
allowUnreachableCode: false
allowUnusedLabels: false
exactOptionalPropertyTypes: true
noPropertyAccessFromIndexSignature: true
eslint.config.mjs 
export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.strictTypeChecked,
  { rules: {
    "@typescript-eslint/switch-exhaustiveness-check": "error",
    "@typescript-eslint/strict-boolean-expressions": "error",
    "@typescript-eslint/require-array-sort-compare": "error",
    "require-atomic-updates": "error",
  } },
);

ป้ายของแต่ละกรณีคือ none, flag: ตามด้วย option ตัวเดียวที่รายงานมัน หรือ lint: ตามด้วยกฎ เมื่อโปรแกรมที่แก้แล้วไปโดนกฎด้วยเหตุผลที่ไม่เกี่ยวข้อง กรณีนั้นจะมี ts_ok.ts และป้ายจะนับเฉพาะสิ่งที่ทำงานกับความผิดพลาดนั้น ตัวอย่างเช่น non-exhaustive-match คือ lint:switch-exhaustiveness-check: typescript-eslint จับได้ถ้าคุณเปิดกฎนั้น และหน้าเว็บก็บอกไว้แบบนั้น

ทำซ้ำหนึ่งกรณี#

รัน gate กับกรณีเดียวจาก clone ของ repository หรือทำด้วยมือ ทั้งสองฝั่งของ non-exhaustive-match ตามที่รันสำหรับหน้านี้:

gate กรณีเดียว 
$ python3 scripts/check_catches.py non-exhaustive-match
catches: 1/1 cases hold every claim they make.
TypeScript checked with tsc --strict and the full flag set (typescript 6.0.3),
typescript-eslint 8.73.0 strictTypeChecked on eslint 9.39.5, run with
tsx 4.23.15, and @types/node 26.6.6.
ฝั่ง TypeScript ทำด้วยมือ 
$ npm i -D typescript@6 tsx@4
$ npx tsc --strict --noEmit ts.ts
$ echo $?
0
$ npx tsx ts.ts
finished
archived logged nothing
ฝั่ง Glyph ทำด้วยมือ 
$ glyph check --no-tsc catches/non-exhaustive-match
[E0200] Error: typecheck: non-exhaustive match
  on `"todo" | "doing" | "done" | "archived"`:
  missing variants "archived"
glyph check: 1 error(s) across 1 module(s)

โค้ดตัวอย่างบนเว็บนี้คอมไพล์ได้#

scripts/check_docs_compile.py รันใน CI และคอมไพล์โค้ดตัวอย่าง Glyph ทุกชิ้นบนเว็บที่ยืนได้ด้วยตัวเอง (เปิดด้วย module และประกาศอะไรบางอย่าง) รวมถึงชิ้นที่อยู่ในเอกสารและ llms.txt โค้ดตัวอย่างที่ตั้งใจให้ fail ต้องระบุ error ที่มันได้ และต้องได้ error นั้นพอดี โค้ดที่ต้องใช้ React หรือแพ็กเกจ npm จะคอมไพล์กับ type จริงของแพ็กเกจเหล่านั้น ชิ้นส่วนที่ไม่สมบูรณ์จะถูกนับและข้าม และจำนวนจะถูกพิมพ์ออกมา สัดส่วนที่ข้ามจึงยังมองเห็นได้

สิ่งที่ยังจับไม่ได้#

กรณี gap 8 กรณีอยู่ในหน้าสิ่งที่จับได้ แต่ละกรณีมีหมายเลข gap ทุก gap ที่เจอจากการสร้างแอปด้วย Glyph อยู่ในบัญชี docs/dogfooding-gaps.md ซึ่งเครื่องหมายในวงเล็บเหลี่ยมเป็นสถานะปัจจุบันเพียงอย่างเดียว ([FIXED], [HALF FIXED] หรือไม่มีเลยสำหรับที่ยังเปิด) และ scripts/check_gaps.py ทำให้ CI fail เมื่อรายการที่ยังเปิดอยู่ถูกทำซ้ำครั้งล่าสุดเกินห้ารุ่นมาแล้ว

รุ่นถูกทำเครื่องหมาย Breaking อย่างไร#

รุ่นจะถูกทำเครื่องหมาย Breaking เมื่อมันปฏิเสธโปรแกรมที่รุ่นก่อนยอมรับ การตัดสินทำโดยเขียนโปรแกรมที่เล็กที่สุดที่ได้รับผลกระทบ แล้วรันด้วยรุ่นก่อนที่เผยแพร่แล้วและ binary ใหม่ จากนั้นเทียบ exit code ไม่ได้อนุมานจากถ้อยคำในบันทึก รุ่นก่อน 0.1.99 ไม่เคยถูกทดสอบด้วยวิธีนี้ รุ่นที่ไม่มีเครื่องหมายจึงหมายถึงยังไม่ได้ทดสอบ ไม่ใช่ปลอดภัย บันทึกอยู่ในหน้าเวอร์ชัน

ส่วนที่เหลือของบันทึก#

แนะนำสิ่งที่จับได้ทุกกรณี: TypeScript, Glyph, error และ TypeScript ที่ใส่เครื่องมือครบจะจับได้หรือไม่ดูทุกกรณี
การทดสอบความแข็งแรงเอเจนต์ที่สวมบทวิศวกรขี้สงสัยโจมตีคอมไพเลอร์อย่างไร และบั๊กที่พวกมันเจอ Benchmarkอะไรที่วัดแล้ว (ความหนาแน่นของ token, grep, diff) และงานศึกษาเรื่องความน่าเชื่อถือที่ยังไม่เสร็จ เวอร์ชันทุกรุ่น เปลี่ยนอะไรบ้าง และรุ่นไหนเป็น Breaking
