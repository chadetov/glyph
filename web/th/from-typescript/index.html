สำหรับคนที่มาจาก TypeScript

อะไรเปลี่ยนไปเมื่อคุณเขียน TypeScript อยู่แล้ว

น้อยกว่าที่คิด Glyph คอมไพล์เป็น TypeScript ที่ผ่าน tsc --strict ใช้ npm และวิธี deploy เดิมได้ และอ่านแล้วแทบเหมือนกัน ความต่างมีอยู่ไม่กี่จุด และแต่ละจุดแลกช่องทางที่จะเขียนผิดกับการตรวจที่คอมไพเลอร์ทำให้

ถ้ารู้ TypeScript คุณก็รู้เกือบทั้งหมดแล้ว#

คุณไม่ต้องเรียนภาษาใหม่ แค่สี่อย่างนี้ ซึ่งเป็นสิ่งที่อยู่ในทุกตัวอย่างบนเว็บนี้

match
switch ที่ต้องครบทุกกรณี: เมื่อใช้กับ union คอมไพเลอร์บังคับให้คุณจัดการทุก case และในคำสั่งกับนิพจน์ มันเป็นเงื่อนไขแบบเดียวที่มี: ไม่มี if/else และไม่มี ternary อธิบายไว้ด้านล่าง ส่วน JSX มีอิลิเมนต์ <if> และ <match>
Result<T, E>
error เป็นค่าที่ return ออกมา ไม่ใช่ exception ที่ throw คุณจัดการด้วย match หรือส่งต่อขึ้นไปด้วย operator ?
fn f() -> T
ฟังก์ชัน โดย -> คือ return type ของมัน type X = {...} คือ record และ type X = A | B คือ tagged union
mut x = e
การ assign ค่าใหม่ต้องเขียนให้ชัดและ grep หาได้ binding แบบ let ธรรมดาจะไม่เปลี่ยนค่าลับหลังคุณ ถ้าจะเปลี่ยนต้องเขียน mut

คอมโพเนนต์ React ตัวเดียวกันในทั้งสองภาษา#

คอมโพเนนต์เดียวกันเขียนสองแบบ: รายการคำเชิญที่มีสถานะว่าง บรรทัดที่นับคนที่ยังรอตอบ และป้ายกำกับในแต่ละแถว ตรงที่ TSX ใช้ && และ ? : ฝั่ง Glyph ใช้อิลิเมนต์ JSX: <match> ซึ่งรับค่าหนึ่งค่าและมี <case> หนึ่งตัวต่อหนึ่งแพตเทิร์น และ <if> ที่มี <else> หรือไม่ก็ได้ ซึ่งเป็นรูปแบบที่เบากว่าสำหรับ boolean ธรรมดา รายการเขียนด้วย <for> และแอตทริบิวต์คือ class ซึ่งคอมไพล์เป็น className

InviteList.tsx 
export type Invite = { email: string; accepted: boolean };

export function InviteList(props: { invites: Invite[] }) {
  const waiting = props.invites.filter((i) => !i.accepted).length;
  return (
    <section>
      {waiting > 0 && <p className="note">{waiting} waiting for a reply</p>}
      {props.invites.length === 0 ? (
        <p className="empty">No invites sent yet.</p>
      ) : (
        <ul>
          {props.invites.map((invite) => (
            <li key={invite.email}>
              {invite.email}
              {invite.accepted ? (
                <span className="ok">joined</span>
              ) : (
                <span className="wait">pending</span>
              )}
            </li>
          ))}
        </ul>
      )}
    </section>
  );
}
invites.glyph 
module invites

import std/array

pub type Invite = { email: string, accepted: bool }

pub component InviteList(props: { invites: Array<Invite> }) {
  let waiting = array.filter(props.invites, fn(i: Invite) { return !i.accepted }).length
  return <section>
    <if cond={waiting > 0}>
      <p class="note">{waiting} waiting for a reply</p>
    </if>
    <match value={props.invites.length}>
      <case 0>
        <p class="empty">No invites sent yet.</p>
      </case>
      <case else>
        <ul>
          <for invite in={props.invites} key={invite.email}>
            <li>
              {invite.email}
              <if cond={invite.accepted}>
                <span class="ok">joined</span>
              </if>
              <else>
                <span class="wait">pending</span>
              </else>
            </li>
          </for>
        </ul>
      </case>
    </match>
  </section>
}

ฝั่ง Glyph ยาวกว่า ส่วนใหญ่เพราะแต่ละ branch เป็นอิลิเมนต์ของตัวเอง <match> ต้องครอบคลุมทุกค่า: ถ้าเอา <case else> ตรงนี้ออก build จะหยุดด้วย E0218 ถ้าเป็น union มันต้องครอบคลุมทุก variant (E0200) และตรงนั้นแหละที่บรรทัดที่เพิ่มขึ้นคุ้มค่า ใช้กับ React ได้ไหม? มีตัวอย่างพร้อม hooks และ Context

การรองรับในเอดิเตอร์และการดีบักมีคำตอบแยกไว้แล้ว: คำตอบเรื่องเครื่องมือ อธิบาย language server และส่วนขยาย VS Code ส่วน คำตอบเรื่องการดีบัก อธิบาย source map ที่ชี้กลับไปยังไฟล์ .glyph ระหว่างพัฒนา glyph build --watch จะ build TypeScript ใหม่ทุกครั้งที่คุณบันทึกไฟล์ .glyph dev server ของ Vite ที่ import ผลลัพธ์นั้นจะโหลดทั้งหน้าใหม่หลัง build แต่ละครั้งแทนการสลับคอมโพเนนต์แบบ hot ดังนั้น state ของคอมโพเนนต์จะถูกรีเซ็ต ส่วนไฟล์ .tsx ของคุณเองยังได้ hot reload ของ Vite ตามเดิม ให้เขียนผลลัพธ์ไว้นอกไดเรกทอรี build ของ Vite (ค่าเริ่มต้นคือ dist/) เพราะ dev server ไม่เฝ้าดูไดเรกทอรีนั้น

"เอเจนต์" ในเว็บนี้หมายถึงผู้ช่วยเขียนโค้ดด้วย AI อย่าง Claude, Copilot และ Cursor Glyph ช่วยพวกมันได้มากที่สุด แต่การตรวจเหมือนกันไม่ว่าคนหรือโมเดลจะเป็นคนเขียนโค้ด ถ้าคุณใช้ TypeScript แบบ strict ร่วมกับ zod และ eslint อยู่แล้ว นี่คือสิ่งที่ภาษาเพิ่มให้จากตรงนั้น

ไม่มีคำสั่ง if#

การแตก branch ตาม boolean คือ match บน true และ false ถ้าต้องทำอะไรแค่ฝั่งเดียว arm อีกฝั่งก็เป็น block ว่าง JSX เป็นข้อยกเว้น: อิลิเมนต์ <if> ในคอมโพเนนต์ด้านบนจะเรนเดอร์ลูกของมันเมื่อเงื่อนไขเป็นจริง และไม่เรนเดอร์อะไรเลยเมื่อไม่จริง

TypeScript 
function label(admin: boolean): string {
  return admin ? "admin" : "member";
}

if (verbose) {
  console.log("starting");
}
Glyph 
fn label(admin: bool) -> string {
  return match admin {
    true => "admin",
    false => "member",
  }
}

match verbose {
  true => io.println("starting"),
  false => {},
}

เหตุผลคือ decision D3 ในสเปก: มี construct เดียวสำหรับแตก branch ตามค่า จึงมีรูปแบบเดียวให้อ่าน เขียน และค้นหา ค่าที่ออกมาจาก branch จะออกมาจาก match เสมอ ซึ่งตัวตรวจของ Glyph เองหา result type ให้ แทนที่จะโยนให้ tsc สำหรับ union construct เดียวกันนี้ต้องครอบคลุมทุก case (E0200) สำหรับ boolean ได้ประโยชน์ไม่มาก เพราะ false => {} ก็ไม่ได้บอกอะไรมากกว่าการไม่เขียน else

มันมีต้นทุน ternary บรรทัดเดียวกลายเป็น match สี่บรรทัด การ return ก่อนเวลาตามเงื่อนไขคือ match ที่มี arm ว่าง และเป็นสิ่งแรกที่คนอ่าน TypeScript รู้สึกว่าแปลก สเปกบันทึกความยืดยาวนี้ไว้ว่าเป็นต้นทุนที่ยอมรับ ถ้ายังเขียน if จะได้ error E0006 ซึ่งข้อความช่วยเหลือแสดงรูปแบบ match ให้ ส่วน ternary จะได้ E0013 พร้อมข้อความช่วยเหลือแบบเดียวกัน

ภาษีที่คุณจ่ายอยู่แล้ว#

ถ้าคุณใช้เอเจนต์ AI สร้างโค้ดบน codebase ที่เป็น TypeScript นี่คือต้นทุนรายวัน แต่ละข้อมีคำตอบเฉพาะใน Glyph ลิงก์ไว้จากรายการ

  • เอเจนต์มโน API ขึ้นมา เพราะ TypeScript ลบ type ทิ้งและ runtime ก็ไม่ตรงกับตอนคอมไพล์อีกต่อไป type ของ Glyph มีการตรวจตอนรันติดมาด้วย (T.parse, T.is) ดูAPI ที่มี type
  • เอเจนต์กลบความไม่แน่ใจด้วย any และ as unknown as T และคอมไพเลอร์ก็ยอม ทั้งสองอย่างไม่มีใน Glyph ดูตารางด้านล่าง
  • คุณขอให้แก้บรรทัดเดียว แต่ได้ไฟล์ที่ถูกเขียนใหม่ทั้งไฟล์ เพราะ formatter ลามไปทุกครั้งที่แก้ glyph fmt มี layout เดียวและไม่มีตัวเลือก ดูdiff ที่สะอาด
  • คุณดูแล validator ที่เขียนด้วยมือไว้ข้างทุก type (zod และ serializer) แล้วเอเจนต์เปลี่ยนชื่อ field ในที่หนึ่งแต่ไม่เปลี่ยนในที่อื่น ทุกอย่างยังคอมไพล์ผ่าน ใน Glyph type คือ validator
  • คุณ grep หาสัญลักษณ์แล้วเจอสิบจุดที่ไม่เกี่ยวข้อง: overload, decorator, namespace ที่ merge กัน Glyph ไม่มีสิ่งเหล่านั้นเลย ดูการค้นหาโค้ด

สวิตช์ปิดการตรวจที่ TypeScript ให้มา และสิ่งที่ Glyph มีแทน#

construct ของ TypeScript แต่ละตัวด้านล่างสั่งให้ตัวตรวจหยุดตรวจ ไม่มีตัวไหนเป็น syntax ของ Glyph คอลัมน์กลางคือสิ่งที่ glyph check --no-tsc พิมพ์ออกมาสำหรับแต่ละตัวบน 0.1.149

TypeScriptใน Glyphสิ่งที่เขียนแทน
x!ไม่ใช่ syntax: E0013Option<T> ที่จัดการด้วย match หรือส่งต่อขึ้นไปด้วย ?
x as T, as unknown as Tไม่มี cast: E0013 ซึ่งข้อความช่วยเหลือบอกให้ validateT.parse(x) ซึ่งคืนค่าเป็น Result
anyไม่ใช่ type: E0103 ชื่อที่ resolve ไม่ได้unknown ที่ถูก narrow ด้วย T.parse, T.is หรือ arm ของ match แบบ is T
(v): v is Tไม่มี type guard ที่ผู้ใช้เขียนเอง: E0002T.is(v) ที่ถูก generate ขึ้นมา ซึ่งตรวจตามรูปร่างที่ประกาศไว้ guard จึงตรวจน้อยกว่าที่อ้างไม่ได้
// @ts-ignore, // eslint-disablecomment ธรรมดา error ใต้มันยังทำงานอยู่ไม่มี ไม่มี comment หรือ flag ไหนปิด diagnostic ของ Glyph ได้

glyph check มี flag ที่ข้ามทั้ง pass (--no-tsc ข้ามการรัน tsc --strict และ --no-test ข้ามเทสต์ @example) แต่ไม่มีตัวไหนปิดการตรวจเพียงข้อเดียว รายการเต็มของสิ่งที่โปรเจกต์ TypeScript ยอมรับแต่ Glyph ปฏิเสธ โดยแต่ละกรณีรันกับคอมไพเลอร์ทั้งสองตัว อยู่ในหน้าสิ่งที่จับได้

ทางออกฉุกเฉินทางเดียว และคุณ grep หาได้#

เมื่อต้องการ TypeScript ที่ Glyph เขียนไม่ได้ extern_ts("...") รับ type หรือ expression แบบ inline หนึ่งตัว และ tsc ยังตรวจมันอยู่ ถ้าเป็นทั้ง module ให้วางไฟล์ .ts ไว้ใต้ src/extern/ แล้วเขียน import extern/name นอกจากนี้ import แบบ relative ใช้ไม่ได้ เส้นทางนี้จึงเป็นทางเข้าทางเดียว ทั้งสองแบบมีคำว่า extern อยู่ grep -rn extern src/ จึงแสดงทุกจุดที่ตัวตรวจส่งต่อให้ TypeScript

src/clock.glyph 
module clock

pub fn now_ms() -> number {
  return extern_ts("Date.now()")
}

TypeScript ที่ถูก emit ออกมาหน้าตาเป็นอย่างไร#

TypeScript ธรรมดา หนึ่งไฟล์ต่อหนึ่ง module ที่คุณอ่านและ commit ได้ union กลายเป็น discriminated union บวกกับค่าที่ถือการตรวจตอนรันของมัน และ match กลายเป็น switch บน tag นี่คือ output ของ glyph build สำหรับ module ทางซ้าย โดยตัดบรรทัด import ออก

plan.glyph 
module plan

pub type Plan = Free | Pro | Team

pub fn seats(p: Plan) -> number {
  return match p {
    Free => 1,
    Pro => 5,
    Team => 50,
  }
}
plan.ts (emit ออกมา ตัดบางส่วน) 
export type Plan =
  | { tag: "Free" }
  | { tag: "Pro" }
  | { tag: "Team" };

export const Free: Plan = { tag: "Free" };
export const Pro: Plan = { tag: "Pro" };
export const Team: Plan = { tag: "Team" };
export const Plan = {
  is(value: unknown): value is Plan { ... },
  parse(value: unknown) { ... },
  schema: ...,
};

export function seats(p: Plan): number {
  const __m0 = p;
  switch (__m0.tag) {
    case "Free": { return 1; }
    case "Pro": { return 5; }
    case "Team": { return 50; }
    default: throw new Error("non-exhaustive match");
  }
}

ถ้าคุณเลิกใช้ Glyph ไฟล์ .ts ที่ emit ออกมาคือสิ่งที่คุณเก็บไว้ มันไม่มี dependency ตอนรันนอกจากไดเรกทอรี support เล็กๆ ที่ build เขียนไว้ข้างๆ

npm และ TypeScript ที่คุณมีอยู่แล้ว#

module .glyph import แพ็กเกจ npm ด้วยชื่อ (import kafkajs { Kafka }) โดยได้ type จาก declaration ของแพ็กเกจเอง และไฟล์ .ts ที่มีอยู่ก็ import module Glyph ที่ emit ออกมาได้เหมือนไฟล์ในเครื่องทั่วไป คุณจึงเริ่มจาก module เดียวในแอปที่ยังเป็น TypeScript ได้ รายละเอียดอยู่ในสามคำตอบ

ใช้ TypeScript, JavaScript และไลบรารี npm ที่มีอยู่ได้ไหม?

การ import แพ็กเกจ การเก็บ shim ที่เป็น .ts ไว้ และการ import Glyph กลับเข้าไปใน .ts

 นำ Glyph มาใช้ในแอปที่มีอยู่ได้ไหม?

แกนของโดเมนเป็น Glyph ส่วนที่เหลือเป็น TypeScript ใน Vite scaffold แบบมาตรฐาน

 ใช้กับ React ได้ไหม?

component, JSX, hook, Context และจุดที่ tsc ยังเป็นคนตรวจ

ไปต่อที่ไหน#

แนะนำดูว่า TypeScript ปล่อยอะไรผ่านแต่ละกรณีรันทั้งใน tsc --strict และใน Glyph พร้อม errorดูสิ่งที่จับได้
