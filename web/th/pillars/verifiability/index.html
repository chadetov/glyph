เสาหลัก 01 · จุดหลัก

ตรวจสอบได้

Glyph ปิดช่องโหว่ที่เอเจนต์ตกลงไป: ไม่มี any และไม่มี as ให้เขียน match พิสูจน์ได้ว่าครบทุกกรณี และ type ที่คุณประกาศได้validator ตอนรันแบบเข้ม ทั้งหมดบังคับใช้เป็นชั้นที่เข้มอยู่บน tsc มันไม่ได้ตรวจทุกอย่างเอง และด้านล่างบอกไว้ตรงๆ ว่าการรับประกันหยุดตรงไหนพอดี

คำโกหกที่ type บอกได้

ใน TypeScript type คือคำสัญญาตอนคอมไพล์ที่ระเหยหายไปก่อนโค้ดจะรัน annotation User ถูกลบจนไม่เหลืออะไร object ที่คุณได้จริงจากการเรียก network การ parse JSON หรือช่องในฟอร์มอาจเป็นรูปร่างอะไรก็ได้

แย่กว่านั้น ภาษาให้วิธีที่ถูกกฎหมายสามทางในการโกหกตัวตรวจ: any, cast แบบ as และ ! แบบ non-null เอเจนต์ที่ทำงานเร็วหยิบทั้งสามมาใช้ และ tsc --strict ก็ยังเขียวขณะที่บั๊กถูกปล่อยออกไป

งานแรกของ Glyph คือปิดช่องโหว่เหล่านั้น ไม่ใช่ด้วย annotation ที่มากขึ้น แต่ด้วยการเอาทางหนีทีไล่ออกไปและทำให้ทุก type พกหลักฐานของมันไปถึงตอนรัน นี่คือความหมายของมัน ทีละการรับประกัน

01 ไม่มี any

Glyph ไม่มีมัน top type คือ unknown และ unknown ทำอะไรไม่ได้: คุณเรียกมัน index มัน หรือส่งมันไปที่ที่มี type ไม่ได้ จนกว่าคุณจะพิสูจน์ว่ามันคืออะไร

รายละเอียด ทำไม any ตัวเดียวจึงแพงขนาดนั้น

any คือ keyword ที่แพงที่สุดใน TypeScript: มันปิด type system สำหรับค่าหนึ่งและทุกอย่างที่ค่านั้นแตะ any ตัวเดียวที่ขอบเขตวางยาพิษให้ call graph ปลายน้ำแบบเงียบๆ

คุณได้ค่าที่มี type ออกมาจาก unknown ไม่ได้ถ้าไม่มีการตรวจที่คอมไพเลอร์มองเห็น ใน Glyph การ narrow คือหลักฐานตอนรัน ไม่มี syntax สำหรับข้ามมัน

02 type มีอยู่จริงตอนรัน

User.parse มีอยู่ได้อย่างไร? เพราะทุก record type และทุก tagged union ที่ไม่ใช่ generic จะ generate runtime descriptor มาด้วย: guard is, parse ที่ validate unknown ให้เป็น Result และ schema ที่ประกอบต่อได้

type ที่คุณเขียน และ descriptor ที่ generate จากมัน 
type User = {
  id: number,
  name: string,
  email: string,
}

// generated: User.is(v), User.parse(v) -> Result<User, ...>, User.schema

fn create(req: Request) -> Result<Response, string> {
  return match User.parse(req.body) {   // untrusted input, validated
    Ok(user) => Ok(json(201, user)),
    Err(issues) => Ok(json(400, issues)),
  }
}

นี่คือคำตอบของ "ทุก API ต้องมี validator ที่เขียนเอง" type คือ validator

รายละเอียด descriptor ตรวจอะไร

รูปร่างของ record ถูกตรวจจริงตอนรัน ไม่ใช่ถูกสันนิษฐาน การตรวจ is User จึงเป็นการตรวจจริง ไม่ใช่สิ่งที่ถูกลบทิ้งจนไม่ทำอะไร

ขอบเขต (request body, ไฟล์ config, response จาก third-party) จะมี type ได้ก็ต่อเมื่อผ่านการตรวจที่ปฏิเสธข้อมูลผิดได้จริง

จุดที่สิ่งนี้หยุด: descriptor ของ record เข้มโดยค่าเริ่มต้น มันยืนยัน field ที่ประกาศไว้และปฏิเสธค่าที่มี key ที่ไม่ได้ประกาศ (ใส่ @open บน type เพื่อยอมให้มีส่วนเกิน) record type ได้ descriptor รวมถึงตัวที่เป็น generic Paginated<User> จึงตรวจแต่ละ element ในฐานะ User และ descriptor ของ tagged union ตรวจ tag แล้วตรวจ field ของ payload ของ variant นั้น

สิ่งที่ยังไม่ได้ descriptor คือ tagged union ที่เป็น generic (Box<T> = Empty | Full({ value: T }) ไม่มี Box.parse) หรือ type ที่ import จาก .d.ts ที่คุณแค่อ้างถึง ในกรณีที่การตรวจพิสูจน์ได้แค่บางส่วนของรูปร่าง คอมไพเลอร์จะบอกไว้ แทนที่จะสื่อเป็นนัยถึงการรับประกันที่มันให้ไม่ได้

03 ครบทุก case ไม่อย่างนั้นคอมไพล์ไม่ผ่าน

match บน union ที่ปิดผนึกต้องจัดการทุก variant เพิ่ม variant ทีหลังแล้ว match ทุกตัวที่ไม่ได้รองรับมันจะคอมไพล์ไม่ผ่าน (E0200)

status.glyph 
type Status = Active | Paused | Cancelled

fn label(s: Status) -> string {
  return match s {
    Active => "on",
    Paused => "hold",
    // forgot Cancelled...
  }
}
compile error ไม่ใช่ undefined ตอนรัน $ glyph build

รายละเอียด match บน number และ string

case ใหม่ตกทะลุไปเป็น undefined แบบเงียบๆ เหมือน branch ของ switch ที่ถูกลืมไม่ได้ และไม่ใช่แค่ union: การ match number หรือ string ด้วยค่า literal ต้องมี else (E0218) เพราะโดเมนเหล่านั้นไม่มีขอบเขต และชุดของ literal ไม่มีวันครบ

04 error เป็นค่า ไม่ใช่เรื่องไม่คาดฝัน

ฟังก์ชันที่อาจล้มเหลวคืนค่า Result<T, E> คุณจัดการด้วย match หรือส่งต่อขึ้นไปด้วย operator ? และ error type ต้องตรงกัน (ไม่มีการแปลงแฝงที่ซ่อนความไม่ตรง)

pipeline.glyph 
fn load(id: string) -> Result<User, AppError> {
  let raw = fetch_user(id)?           // Err short-circuits to the caller
  let user = User.parse(raw.body)?    // validation Err propagates too
  return Ok(user)
}

fn main() -> number {
  save(user)   // E0217: this returns a Result whose Err is dropped
  return 0
}

ถ้าเพิกเฉยต่อ Result ไปเลย (เรียกเพื่อผลข้างเคียงแล้วทิ้งสิ่งที่มันคืนมา) Glyph จะเตือน (E0217) เพราะ error ที่ถูกทิ้งคือความล้มเหลวที่ถูกกลืน คุณปิดเสียงมันได้อย่างตั้งใจด้วย let _ = ... ไม่ใช่โดยบังเอิญ

05 แม้แต่ PII ก็อยู่ระดับ type

สัญชาตญาณเดียวกันคือ "ให้เป็นงานของคอมไพเลอร์ ไม่ใช่ธรรมเนียม" ไปถึงข้อมูลอ่อนไหวด้วย ใส่ @redact บน type แล้ว descriptor ของมันจะได้ redact() ที่ปิดบัง field เหล่านั้น json.stringify(User.redact(u)) ที่หลงมาจึงทำข้อมูลรั่วไม่ได้

patient.glyph 
@redact fields: [diagnosis, notes]
type Patient = {
  name: string,
  diagnosis: string,
  notes: string,
}

// json.stringify(Patient.redact(p)) ->
// {"name":"Ada","diagnosis":"[REDACTED]","notes":"[REDACTED]"}

ระบุ field ที่ type ไม่มีแล้วจะเป็น compile error (E0219) ไม่ใช่การปิดบังที่ไม่ได้ปกป้องอะไรแบบเงียบๆ

ความล้มเหลวห้าแบบ (input ที่ไม่ถูกตรวจ case ที่พลาด error ที่ถูกทิ้ง secret ที่รั่ว key ที่ไม่ถูก validate) และทุกแบบการแก้มีรูปเดียวกัน: คอมไพเลอร์ไม่ยอมแกล้งทำเป็น

บังคับใช้อย่างไร และการรับประกันหยุดตรงไหน

พูดให้แม่นยำ เพราะความต่างสำคัญ: Glyph เป็นภาษาย่อยที่เข้มและบังคับใช้บน tsc ไม่ใช่ตัวตรวจอิสระ

  • Glyph พิสูจน์เองบางอย่างมันพิสูจน์เอง: ความครบถ้วน error type ของ ? การไม่มี any/as ในซอร์สของคุณ การ validate key แบบเข้ม
  • บังคับใช้ผ่าน tscความเข้ากันได้ของ type ส่วนที่เหลือมันบังคับใช้โดย emit TypeScript แล้วรัน tsc --strict ซึ่งทำให้ build fail

จุดหลักคือการตรวจเหล่านี้เป็นภาษา ไม่ใช่ lint ที่ต้องเลือกเปิดซึ่งเอเจนต์ปิดได้ ไม่ใช่ว่า Glyph เขียน type checker ขึ้นใหม่

ที่มา ขอบที่ปิดใน 0.1.10 และการ validate generic แบบลึก

ขอบสองจุดก่อนหน้านี้ถูกปิดใน 0.1.10 emitter เคยแทรก return cast ที่ตรวจโดย Glyph ไม่ใช่ tsc ในทุกฟังก์ชัน generic ตอนนี้มันเกิดเฉพาะที่ combinator ของ validator ประกอบค่าของ type ที่ derive จาก shape (infer_output<Shape>) และ generic ที่ตรงไปตรงมาทุกตัว emit โดยไม่มี cast เลย และ output type ของ validator ไม่ถูกเชื่อตามคำบอกอีกต่อไป: infer_output derive มันจาก shape ที่คุณส่ง และ tsc ตรวจ annotation ของคุณเทียบกับมัน shape ที่ขาด field ของ type ที่คุณอ้างจึงคอมไพล์ไม่ผ่าน

type แบบ generic ก็ validate แบบลึกแล้ว: descriptor ของ Paginated<User> ตรวจทุก element ในฐานะ User ไม่ใช่แค่ว่ามีอยู่

ยังเหลือขอบหนึ่งจุด บอกไว้ตรงๆ: type ที่ import จาก .d.ts ภายนอกที่คุณแค่อ้างถึงไม่มี descriptor จนกว่าคุณจะ materialize มันด้วย glyph gen dts field ของ type นั้นจึงถูกตรวจแค่ว่ามีอยู่ ไม่ได้ตรวจรูปร่าง ขอบนั้นเป็นความตั้งใจ (type ที่ Glyph ไม่ได้ emit สัญญาการ validate ตอนรันไม่ได้) และการ materialize ปิดมันได้

benchmark: กำลังมา

ข้อกล่าวอ้างนี้เป็นเชิงประจักษ์ เราจึงตั้งใจจะวัด: เอาชุดการเปลี่ยนแปลงจริงที่เอเจนต์เขียน รันแต่ละตัวผ่าน tsc --strict และผ่าน Glyph แล้วนับว่าแต่ละตัวจับอะไรได้จริง

Glyph ยังไม่ได้ใช้งานจริงในโลกภายนอก จึงยังไม่มีตัวเลขให้รายงาน กราฟด้านล่างเป็นที่ว่างรอไว้ และจะเติมด้วยข้อมูลจริงทันทีที่มีการใช้งานจริง

"TypeScript แบบ strict กับ config ของ lint ก็ทำแบบนี้ได้"

ภายในโปรแกรม มันเข้าใกล้ strict, noUncheckedIndexedAccess และกฎที่ห้าม any แบบชัดแจ้ง จับสิ่งที่เอเจนต์จะเล็ดลอดไปได้ส่วนใหญ่ แต่หยุดที่ขอบ

  • ที่ขอบเขตJSON.parse(body) as User คอมไพล์ผ่านทุกการตั้งค่าที่มี และวิธีแก้ที่ใช้กันคือ schema ของ zod ซึ่งเป็นคำอธิบาย User ชุดที่สองที่ต้องรักษาให้ตรงกับชุดแรกด้วยมือ ใน Glyph type คือ validator: json.parse<User>(body) ถูกตรวจเทียบกับ User เอง และ type ที่ Glyph ตรวจตอนรันไม่ได้จะถูกปฏิเสธแทนที่จะถูกเชื่อ
  • ข้าม repositoryอีกความต่างคือใครพึ่งพามันได้ config ของ lint คือตัวเลือกที่ repository หนึ่งเลือก เอเจนต์ที่เปิด codebase TypeScript ที่ไม่คุ้นเคยสันนิษฐานไม่ได้ว่า any ถูกห้ามที่นั่น ใน Glyph มันเขียนไม่ได้ที่ไหนเลย

การรับประกันเดียวกันในรูปความผิดพลาดที่เอเจนต์ทำและ error ที่หยุดมัน ตอบไว้ใน อะไรกันเอเจนต์ไม่ให้ทำโค้ดของฉันพังแบบเงียบๆ?
