อ่านเป็นภาษาอังกฤษ

ภาษา: ไทย·อ่านเป็นภาษาอังกฤษ

หน้านี้เป็นฉบับแปล ฉบับภาษาอังกฤษคือฉบับอ้างอิง แจ้งปัญหาเกี่ยวกับคำแปล

สำหรับทีม

รับประกันอะไร การนำมาใช้ต้องแลกกับอะไร และจะออกอย่างไร

Glyph ปฏิเสธรายการกรณีที่เจาะจงและตรวจแล้ว ซึ่งโปรเจกต์ TypeScript แบบ strict ยอมรับ และคอมไพล์เป็น TypeScript ที่คุณเก็บไว้ใช้ต่อได้ถ้าเลิกใช้ ตอนนี้ยังเป็นพรีวิวช่วงแรก: ยังไม่ถึง 1.0 ดูแลหลักๆ โดยคนคนเดียว และออกรุ่นใหม่หลายครั้งต่อสัปดาห์

รับประกันอะไร#

ทุกข้อกล่าวอ้างว่า Glyph จับอะไรได้ คือกรณีหนึ่งในไดเรกทอรี catches/ ของ repository: โปรแกรมเดียวกันใน TypeScript และใน Glyph ซึ่ง CI gate รันทั้งคู่ รวมทั้งหมดมี 47 กรณีที่ตรวจแล้ว ได้แก่ กรณีของ TypeScript 37 กรณี กับดักของ JavaScript ที่ไม่มีใน Glyph 5 กรณี และช่องโหว่ที่ Glyph ยังปิดไม่ได้ 5 กรณี Glyph ปฏิเสธ 28 กรณีในจำนวนนี้ตอน build (กรณีของ TypeScript 23 กรณี และกับดัก 5 กรณี) ในบรรดาข้อผิดพลาดที่ไม่ถูกปฏิเสธ 3 ข้อได้คำเตือน 9 ข้อเป็นข้อมูลผิดที่ถูกหยุดโดยการตรวจที่ขอบเขตตอนรัน และ 2 ข้อหยุดตอนรัน ข้อที่คนรีวิวโค้ดจากเอเจนต์พึ่งพามากที่สุด:

โค้ดสิ่งที่ถูกปฏิเสธ
E0200match ที่ขาด case ของ union ไป การเพิ่ม case จึงแสดงรายการทุกจุดที่ต้องแก้
E0013cast (as, as unknown as) ไม่มี cast และไม่มี any
E0204JSON ที่ parse แล้วถูก assign ให้ชื่อที่มี type โดยไม่ได้ตรวจ
E0224การอ่านจาก map ที่มี type ราวกับว่า key มีอยู่เสมอ
E0217Result ที่ถูกทิ้งไปเฉยๆ (เป็นคำเตือน let _ = บอกว่าตั้งใจ)

หน้าสิ่งที่จับได้ แสดงทุกกรณีพร้อม TypeScript, Glyph และ error และบอกว่ากรณีไหนที่ typescript-eslint ที่ตั้งค่าเต็มที่ก็จับได้เช่นกัน

หยุดตรงไหน#

การรับประกันครอบคลุมโค้ดที่เขียนด้วย Glyph exception ที่ throw จากภายใน dependency ของ npm ยังข้าม Result ไปได้ และ type ที่ import จาก .d.ts ของแพ็กเกจไม่มีการตรวจตอนรัน ภายใน Glyph ช่องโหว่ที่ยังเปิดอยู่ 5 ข้อแสดงพร้อมหมายเลข gap ในสิ่งที่ยังจับไม่ได้ และบัญชีฉบับเต็มอยู่ที่ docs/dogfooding-gaps.md สำหรับการเปรียบเทียบกับ TypeScript แบบ strict บวก zod, eslint และ ts-pattern รวมถึงจุดที่ชุดนั้นยังทำได้ดีกว่า ดูทำไมไม่ใช้ TypeScript ที่ใส่เครื่องมือครบ

นำมาใช้ในแอปที่มีอยู่#

ไม่ต้องเขียนใหม่ คุณเขียนส่วนที่พลาดไม่ได้ (model, สิทธิ์, การเปลี่ยนสถานะ, เงิน) ด้วย Glyph ส่วนที่เหลือของแอปยังเป็น TypeScript และ import module ที่ emit ออกมาเหมือนไฟล์ในเครื่องทั่วไป ตัวอย่างทีละขั้นใช้ Vite scaffold แบบมาตรฐาน: นำ Glyph มาใช้ในแอปที่มีอยู่ได้ไหม?

ทางออกถ้าจะเลิกใช้#

glyph build เขียน TypeScript ธรรมดา หนึ่งไฟล์ต่อหนึ่ง module ที่ผ่าน tsc --strict ถ้าคุณเลิกใช้ Glyph ก็ commit output นั้นแล้วใช้ tsc ต่อไป license เป็น MIT หรือ Apache-2.0 จึง fork ได้เสมอ สำหรับคนที่มาจาก TypeScript แสดง module คู่กับไฟล์ที่ emit ออกมา

การ pin และการอัปเกรด#

glyph init pin คอมไพเลอร์เป็นเวอร์ชันที่แน่นอนใน package.json โดยไม่มี ^ จึงไม่มีรุ่นไหนหลุดเข้ามาใน build ของคุณโดยบังเอิญ ส่วนที่เหลือใช้สามคำสั่ง:

อัปเกรดอย่างตั้งใจ 
glyph doctor     # your version against the latest release; never fails CI for that
glyph upgrade    # moves the project's pin, runs npm install, links the notes
glyph --update   # moves the installed compiler itself

รายละเอียดใน รุ่นใหม่ของ Glyph จะทำให้ build ของฉันพังไหม?

ความถี่ในการออกรุ่น และเครื่องหมาย Breaking#

หน้าเวอร์ชัน มีรายการของทุกรุ่นตั้งแต่ 0.1.0 ถึง 0.1.161 รวม 160 รุ่น และ 34 รุ่นในนั้นออกระหว่าง 1 พ.ย. 2026 ถึง 22 พ.ย. 2026 รุ่นจะถูกทำเครื่องหมาย Breaking เมื่อมันปฏิเสธโปรแกรมที่รุ่นก่อนยอมรับ ซึ่งเป็นวิธีที่การแก้ความถูกต้องส่วนใหญ่ลงมา มี 44 รายการที่มีเครื่องหมายนี้ เครื่องหมายได้มาจากการรันโปรแกรมที่เล็กที่สุดที่ได้รับผลกระทบด้วยทั้งสองรุ่น ไม่ใช่จากการอ่าน diff และรุ่นก่อน 0.1.99 ไม่ได้ทดสอบด้วยวิธีนี้ รุ่นเก่าที่ไม่มีเครื่องหมายจึงหมายถึงยังไม่ได้ทดสอบ ไม่ใช่ปลอดภัย

รุ่น Breaking มีต้นทุนจริงแค่ไหน: บันทึกของรุ่นล่าสุดแต่ละรุ่นบอกว่าเกิดอะไรขึ้นเมื่อรันรุ่นเก่าและรุ่นใหม่กับแอปตัวอย่างใน repository นี่คือรุ่น Breaking ล่าสุด ยกมาจากบันทึกของแต่ละรุ่น:

  • 0.1.161: “Across the 97 example apps and standalone files, nothing changes except the catch case for this mistake.”
  • 0.1.160: “Across the 394 example apps and standalone files, the only new diagnostic is on the catch case for this mistake.”
  • 0.1.159: บันทึกประจำรุ่นไม่ได้ระบุไว้
  • 0.1.158: บันทึกประจำรุ่นไม่ได้ระบุไว้
  • 0.1.157: “Writing this rule turned up a real bug in one of the example apps.”
  • 0.1.156: บันทึกประจำรุ่นไม่ได้ระบุไว้

แอปตัวอย่างเป็นโค้ดของโปรเจกต์เอง ซึ่งถูกดูแลให้คอมไพล์ผ่านทุกรุ่น รูปแบบที่เพิ่งถูกปฏิเสธจึงมีโอกาสโผล่ในนั้นน้อยกว่าในโค้ดของคุณ บันทึกแต่ละรุ่นระบุรูปแบบที่ปฏิเสธไว้ ควรอ่านก่อนอัปเกรด

สถานะ#

Glyph ยังไม่ถึง 1.0 ก่อน 1.0 syntax, standard library และรูปร่างของ TypeScript ที่ emit ออกมาอาจเปลี่ยน และรุ่นใหม่อาจปฏิเสธโค้ดที่เคยคอมไพล์ผ่าน docs/stability.md บอกว่าอะไรอาจเปลี่ยนและอะไรถูกรักษาให้คงที่ MAINTAINERS.md บอกตรงๆ ว่าตอนนี้โปรเจกต์ดูแลหลักๆ โดยคนคนเดียว

ข้อโต้แย้งและคำตอบ#

เราไม่ค่อยใช้ AI ยังคุ้มอยู่ไหม?

การตรวจเหมือนกันไม่ว่าใครจะเขียนโค้ด: เจอเรื่องไม่คาดคิดตอนรันน้อยลง diff เล็กลง และโค้ดที่ grep หาได้

 เราใช้ TypeScript แบบ strict กับ lint อยู่แล้ว

การตรวจพวกนั้นทุกข้อต้องเลือกเปิดเอง และปิดได้ในบรรทัดเดียว ของ Glyph ปิดไม่ได้

 เอเจนต์ของเราจะเขียนภาษาที่แทบไม่เคยเห็นได้หรือ?

สิ่งที่โมเดลรู้เกี่ยวกับ TypeScript ส่วนใหญ่ใช้ต่อได้ และคอมไพเลอร์บอกชื่อส่วนที่เหลือให้

 ทำไมต้องคอมไพล์เป็น TypeScript?

เพราะ npm, React และ Node อยู่ตรงนั้น และนั่นคือเหตุผลที่นำมาใช้ทีละไฟล์ได้

 คนที่ on-call เห็นอะไรเมื่อมันพัง?

TypeScript ที่อ่านได้ source map ที่ชี้กลับไปยังไฟล์ .glyph และรหัส error ที่คงที่

 เรารู้ได้อย่างไรว่าทั้งหมดนี้เป็นจริง?

แต่ละข้อกล่าวอ้างบนเว็บนี้ถูกตรวจอย่างไร และจะทำซ้ำเองได้อย่างไร

ไปต่อที่ไหน#

แนะนำดูว่า TypeScript ปล่อยอะไรผ่านกรณีที่โปรเจกต์ TypeScript แบบ strict ยอมรับ เรียงอันดับแล้ว แต่ละกรณีรันทั้งใน tsc --strict และใน Glyphดูสิ่งที่จับได้
เขียนโปรแกรมแรกติดตั้ง สร้างโปรเจกต์ รัน ตั้งใจทำให้พัง แล้วอ่าน error ใช้เวลาประมาณสิบนาที ลองในเบราว์เซอร์คอมไพเลอร์รันในหน้าเว็บ ไม่ต้องติดตั้งอะไร
Glyph

ภาษาแบบมี type ที่คอมไพล์เป็น TypeScript สร้างมาให้เอเจนต์แก้โค้ดได้โดยไม่ทำให้พัง
