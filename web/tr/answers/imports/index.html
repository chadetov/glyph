Evet. Glyph sıradan TypeScript'e derlenir ve npm üzerinde çalışır: bir .glyph modülü herhangi bir paketten import eder ve kendisi de mevcut .ts dosyalarınızdan import edilebilir. Onu dosya dosya benimsersiniz.

Bu sayfada

  1. Neden önemli
  2. Kurulu paketler
  3. Değerden türetilen tipler

  5. Alt süreçler

Neden önemli

Kimse bir dili denemek için kod tabanını yeniden yazmaz. Glyph'in çıktısı TypeScript'in ta kendisi olduğu için bir .glyph dosyası mevcut bir TS/React/Node projesinin bir köşesine yerleşir, aynı paketleri import eder ve etrafındaki .ts dosyalarına geri export eder.

Yeni bir runtime çıkarmak yerine TypeScript'i hedeflemenin tek nedeni bu kademeli yol.

Kurulu paketler kendi tiplerini getirir

Paket kuruluysa ve kendi tiplerini getiriyorsa (ya da bir @types/... paketi varsa) yapmanız gereken bu kadar. Stub yok, adaptör dosyası yok.

glyph build projenizin node_modules dizinini bulur ve tip denetleyicisini ona yöneltir; böylece paketin gerçek tipleri kodunuzu kontrol eder ve yanlış bir çağrı gerçek bir hatadır.

İşte hiçbir şey elle yazılmadan, satır içinde kullanılan zod:

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
zod'un tanımlamadığı bir çağrı 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

glyph run aynı programı kurulu zod'a karşı çalıştırır, yani bu yalnızca bir tip kontrolü değil: paketi tip denetleyicisi için çözen tek yapılandırma girdisi onu runtime için de çözer.

Hiç tip getirmeyen ve @types/... paketi de olmayan bir paket hâlâ sizin yazacağınız bir tanıma ihtiyaç duyar; .types/ klasörü bunun içindir (TypeScript'in zaten kullandığı .d.ts mekanizmasının aynısı).

Ayrıntılar alt yol import'ları ve bir .d.ts'ten doğrulanan tipler

Alt yol import'ları (pkg/sub) da paketin exports map'i üzerinden çözülür, böylece bir alt yolun kendi tipleri kontrol edilir.

Bir kütüphanenin şeklini yalnızca tip import'u olarak değil, birinci sınıf, doğrulanan bir Glyph tipi olarak istediğinizde glyph gen dts bir .d.ts dosyasını descriptor taşıyan gerçek tiplere dönüştürür: bkz. her API için elle validator yazmam gerekiyor mu?

Değerden türetilen tipler, JSX spread ve kaçış kapısı

Değerden türetilen tipler birinci sınıftır. JSX prop spread (<input {...register()} />) de birinci sınıftır.

Dolayısıyla bir kütüphane sizi asla elle yazılmış bir adaptör dosyasına zorlamaz.

Glyph'in hâlâ yazamadığı nadir TypeScript kalıpları için extern_ts("...") kapsamı sınırlı, grep'lenebilir kaçış kapısıdır: tsc onu kontrol eder, ama net olalım, bu çalışma zamanında doğrulanan değil, güvene dayalı bir sınırdır (Glyph için opaktır, değer daraltılmak üzere unknown olarak geri gelir).

Ayrıntılar z.infer<typeof s> nasıl çözülür

type User = z.infer<typeof user_schema> doğrudan çalışır: typeof user_schema gerçek bir değer referansı üzerinde bir tip sorgusudur (bir yazım hatası çözülemeyen isim hatası olur) ve z.infer<...> sıradan bir üye-generic tiptir. Olduğu gibi üretilir ve tsc onu indirger, böylece u.name bir string olur; doğrulama, zod'un zaten çalıştığı şekilde şemanın kendi parse'ından gelir.

Tamamen elle yazılmış TypeScript gerektiğinde

Bazen kaçış kapısı bir tip ya da ifade değil, gerçek runtime kodudur: bir node-stream döngüsü, bir new Promise, bir worker thread. .ts dosyasını <src>/extern/ altına koyun ve ona import extern/<name> ile ulaşın. 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

Göreli import'lar Glyph kaynağında yasak kalmaya devam eder (bir grep'lenebilirlik kuralı), bu yüzden extern/* ayrılmış tek yoldur ve grep -rn 'import extern/' dilden çıktığınız her yeri bulur.

Ayrıntılar kopyalama, diğer yön ve node shim'i

Build, <src>/extern/**'ı çıktıya kopyalar ve göreli bir specifier üretir; böylece tsc extern'i Glyph kodunuzla birlikte tip kontrolünden geçirir ve bir yeniden build onu asla silmez.

Bu, kolay yönün tersidir: derlenmiş Glyph'inizi import eden bir .ts dosyası hiçbir şeye ihtiyaç duymaz. Yaygın bir extern (bir http sunucusu, fs), hiçbir şey kurulmadan paketle gelen node shim'ine karşı tip kontrolünden geçer.

Hiçbir şey kurmadan bir alt süreci izlemek

Paketle gelen node tanımları child_process'in yalnızca bloklayan yarısını değil async yarısını da taşır; böylece uzun bir komutun çıktısını o çalışırken raporlayan bir araç extern değil Glyph olur: 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

io.println değil io.print: bir chunk satır değil, akışın bir dilimidir ve bir satır ikisine bölünmüş olarak gelebilir.

Overload'lar @types/node'u izler; böylece pipe'lar düz bir spawn(command, args)'tan non-null, stdio verdiğiniz anda nullable olarak gelir. stdio: "inherit"'ten sonra child.stdout'u okumak burada TS18047, gerçek tiplerle de TS18047'dir; aynı değer hakkında iki farklı hikâye yoktur: 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

Shim'i düzenleyin, bir sonraki çalıştırma düzenlediğiniz shim olur

Bir shim üzerinde yineleyerek çalıştığınız bir dosyadır, bu yüzden kaynak sayılması gerekir.

glyph run bir build'i kaynaklarınızın parmak izi altında önbelleğe alır ve bu parmak izi extern/ altındaki her .ts ve .tsx dosyasını hem yoluyla hem içeriğiyle kapsar.

Ayrıntılar yeniden build'i neyin tetiklediği

Birini düzenleyin, yeniden adlandırın, ekleyin ya da silin; bir sonraki çalıştırma yeniden build alır ve tsc'yi yeniden çalıştırır. Sembolik bağlantılı bir shim takip edilir, böylece kaynak ağacının dışında tutulan bir .ts gerçekte içerdiğine göre hash'lenir.

Bu, iki dosyanın da kendi kopyasını tanımlaması yerine bir tipin sahibinin shim olmasını mümkün kılar. Şekli shim'den export edin, Glyph modülünde import edin; derleyici her çalıştırmada ikisini birbirine bağlı tutar:

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
shim bir alanı yeniden adlandırdı, build bunu söylüyor 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3
Geçmiş 0.1.44 öncesi ve sayılmayan dosyalar

0.1.44'e kadar parmak izi extern/'i tamamen atlıyordu; dolayısıyla o yeniden adlandırma, shim'in önceki kopyasını çalıştıran temiz, tip kontrolünden geçmiş bir build üretiyordu. extern/ altındaki .ts ya da .tsx olmayan dosyalar hâlâ önbelleği etkilemez ve bu bilinçli: shim'inizin yanındaki bir README.md onunla birlikte çıktıya kopyalanır, ama hiçbir şey onu tip kontrolünden geçirmez ya da çalıştırmaz, yani yeniden build alınacak bir şey yoktur.

Sınıf tabanlı istemciler: veritabanı ve mesajlaşma istemcileri

Çoğu veritabanı ve mesajlaşma istemcisi sınıf tabanlıdır: new Kafka(...), new MongoClient(url), new Redis(), new Pool(cfg) yazarsınız. Glyph'te tam olarak bunun için new var.

sınıf tabanlı bir istemci (kafkajs) 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
bir factory istemcinin new'e ihtiyacı yok 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

Olduğu gibi bir TypeScript new'i üretir ve tsc onu paketin gerçek constructor'ına karşı kontrol eder; böylece yanlış bir argüman gerçek bir hatadır ve tanımsız bir çağrılan adıyla yakalanır.

Yalnızca interop için kalır: Glyph'in kendine ait bir class'ı yoktur ve new yalnızca bir paketten, bir .types tanımından ya da extern_ts'ten gelen bir tipi oluşturur.

Şu anki durum

Bugün yayında

  • Herhangi bir npm paketini import edin (tireli ve scope'lu isimler dahil).
  • Kendi tiplerini getiren (ya da @types/... paketi olan) kurulu bir paket stub olmadan tip kontrolünden geçer ve çalışır.
  • Sınıf tabanlı istemciler new ile oluşturulur ve tsc tarafından gerçek constructor'a karşı kontrol edilir; factory istemciler doğrudan import edilip çağrılır.
  • Node yerleşikleri kutudan çıktığı gibi tip kontrolünden geçer
    Ayrıntılar

    Node yerleşikleri (fs, path, http, akış yapan spawn dahil child_process ve diğerleri) kutudan çıktığı gibi tip kontrolünden geçer; @types/node'u kurduğunuzda otomatik olarak yüklenir ve CI, derleyicinin kendi runtime'ını o paketin latest sürümüne karşı build eder; böylece stdlib'in bağlı olduğu bir tanım node'un gerçek tanımından ayrışamaz.

  • Yalnızca sizin kodunuzun ulaştığı bir tanım henüz bu kontrolün kapsamında değil ve birkaçı hâlâ node'dakinden geniş.
  • Diğer her şey için .types/ ambient tanımları.
  • Bir .d.ts dosyasını doğrulanan Glyph tiplerine dönüştürmek için glyph gen dts.
  • Mevcut TypeScript'inizin geri import ettiği temiz .ts çıktısı.
  • import extern/<name>, <src>/extern/ altındaki elle yazılmış TypeScript'e ulaşır
    Ayrıntılar

    Tamamen elle yazılmış TypeScript gerektiğinde import extern/<name>, <src>/extern/ altındaki bir .ts dosyasına ulaşır; bu dosya kodunuzla birlikte kopyalanır ve tip kontrolünden geçer, glyph run önbelleği tarafından da izlenir, böylece onu düzenlemek yeniden build tetikler.

Yolda olanlar

  • Üretim gerçek SDK'ların getirdiği şekilleri ele alıyor ve değerden türetilen tipler birinci sınıf
    Ayrıntılar

    Üretim artık gerçek SDK'ların getirdiği şekilleri ele alıyor (namespace'ler, dosyalar arası ve takma adlı/namespace yeniden export'ları, alt yol exports'u ve birinci sınıf generic'ler) ve değerden türetilen tipler (z.infer<typeof s>) birinci sınıf.

  • Kalan ana eksik şu: üretilmemiş bir paketin çıktıları .d.ts'ine karşı tip kontrolünden geçer, ama siz onları üretmedikçe çalışma zamanında doğrulanmaz.
  • extern/ tarafında kaynak kökü glyph run ile glyph build arasında farklıdır
    Ayrıntılar

    extern/ tarafında kaynak kökü iki komut arasında farklıdır: glyph run app.glyph kökü dosyanın kendi dizinine koyar, glyph build src/ ise adını verdiğiniz dizine. Dolayısıyla bir alt dizindeki program shim'ini iki farklı yerde arar ve biz tek bir kök seçene kadar, bu şekilde düzenlenmiş bir projede shim'in iki yerden de erişilebilir olması gerekir. Erişilemediğinde açıkça hata verir.

Bu sayfadaki kod örnekleri her build'de Glyph 0.1.157 ile kontrol edilir. Son değişiklik: 21 Kas 2026.
