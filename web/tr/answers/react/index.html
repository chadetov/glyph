Neden önemli

Ajanların yazdığı kodun büyük kısmı React. Glyph onu sonradan eklenmiş bir şey olarak değil, birinci sınıf bir hedef olarak ele alır: component kendi anahtar kelimesidir (bu yüzden grep "^component " tüm arayüzünüzü denetler).

React'in hook'ları react'ten import edilir ve gerçek isimleri ve tipleriyle çağrılır; tsc bunları React'in kendi tanımlarına göre kontrol eder.

Reducer'lar ve hook'lar

Bir Double action'ı ekleyin; reducer, onu adıyla söyleyen E0200 ile derlenmeyi bırakır. Düz bir TypeScript switch'i bunun yayına çıkmasına izin verirdi.

E0200

Glyph'in kendi checker'ı React'ten gelen değerlerin tipini belirlemez, bu yüzden dispatch'e ya da bir state setter'ına verilen yanlış bir argüman editör ya da --no-tsc tarafından değil, build sırasında tsc tarafından bildirilir.

Ayrıntılar hook'un döndürdüğü çiftin nasıl destructure edildiği

Çift let [count, dispatch] ile destructure edilir ve üretilen TypeScript satisfies readonly [unknown, unknown] ekler; böylece tsc hook'un bir çift döndürdüğünü kanıtlar ve her elemanın tipini yine de çıkarır.

Context ve kütüphaneler

React Context bugün createContext / useContext üzerinden çalışıyor ve member-expression eleman isimleri (<ThemeContext.Provider>) doğrudan çalışıyor: geçici bir çözüme gerek yok.

  • Prop spreadJSX prop spread de çalışıyor: <input {...register("email")} />, props içinde bir object spread'e indirgenir, yani react-hook-form deyimi bir adaptöre ihtiyaç duymaz.
  • Zod tipleriZod'un değerden türetilen tipleri birinci sınıftır: type FormData = z.infer<typeof schema> doğrudan çalışır, kaçış yoluna gerek yok.

Farklı olan tek şey: bir component birden fazla konumsal parametre değil, tek bir props record'u alır. Bu sınırın tam olarak nerede olduğu için kütüphanelerinizi kullanmak ve sağlamlaştırma sayfasına bakın.

Props tsc'den önce kontrol ediliyor mu?

Evet. Glyph her elemanı component'inin props record'uyla kendisi karşılaştırır; böylece yanlış bir değer, yanlış yazılmış bir prop ve eksik bir zorunlu prop, prop'u adıyla söyleyen Glyph hatalarıdır. Component ister adıyla ister modülü üzerinden import edilmiş olsun, aynı şekilde çalışır:

main.glyph, Card ui.glyph içinde tanımlı 
import ui

pub component App() {
  return <div>
    <ui.Card title="Q3" />
    <ui.Card title="Q4" cout={2} />
  </div>
}

// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`
// E0210 type `CardProps` has no field `cout`; did you mean `count`?
// E0211 argument type mismatch: expected `CardProps`, found `record`: missing field `count`

Bunları yalnızca tam bir build'de değil, editörde ve MCP üzerinden de görürsünüz.

Ayrıntılar --json içinde missing_fields ve tek bir props record'u (E0229)

--json eksik isimleri bir missing_fields listesi olarak taşır; böylece bir ajan mesajı parse etmeden prop'ları ekleyebilir. Bir component ayrıca props'larını tek bir record olarak almak zorundadır: component Greeting(name: string) parametrede E0229'dur, çünkü React yalnızca props object'ini geçirir ve o eleman hiçbir zaman tip kontrolünden geçemezdi. Onu render etmek yerine bir fonksiyon olarak çağırıyorsanız fn ile tanımlayın.

JSX'teki bir <match> bir match gibi mi kontrol ediliyor?

İkisi aynı şey. Her <case>, bir match arm'ının aldığı pattern'i alır ve derleyici onu arm için kullandığı kodun içinden geçirir.

  • Payload tipleriBir case'in bağladığı isimler payload'un tiplerine sahiptir, payload record'unda olmayan bir alan E0210'dur ve eksik bir variant E0200'dür.
  • Kısmi case'lerBir değeri test eden bir case, variant'ının yalnızca bir kısmını kapsar; bu yüzden geri kalanını alacak kardeş bir case'e ya da bir <case else>'e ihtiyaç duyar.
results.glyph 
type Page =
  | Loading
  | Loaded({ users: Array<User>, total: number })
  | Failed(string)

component Results(props: { page: Page }) {
  return <match value={props.page}>
    <case Loading><p>Loading...</p></case>
    <case Loaded({ users, totl })><p>{users.length} of {totl}</p></case>
    <case Failed(message)><p>{message}</p></case>
  </match>
}

// E0210 type `{ users: Array<User>, total: number }` has no field `totl`; did you mean `total`?

Bir sayfa onu nasıl başlatır?

Glyph'te üst seviye ifadeler yoktur, bu yüzden sayfa export edilmiş bir main'i kendisi çağırır. Uygulama iki modüldür: biri component'leri tutar, diğeri onları std/dom ve react-dom'un createRoot'u üzerinden #root'a mount eder.

Event attribute'ları snake case'tir (on_change, React'in onChange'ini üretir), bir handler bir lambda'dır ve bir input'un metni e.currentTarget.value'dur.

app.glyph 
module app

import react { useState }

pub component App() {
  let [name, set_name] = useState("")
  return <main>
    <input value={name} on_change={fn(e) { set_name(e.currentTarget.value) }} />
    <p>Hello, {name}</p>
  </main>
}
main.glyph 
module main

import react-dom/client { createRoot }
import std/dom
import std/console
import std/option { Some, None }
import app { App }

pub fn main() -> void {
  match dom.element_by_id("root") {
    Some(root) => createRoot(root).render(<App />),
    None => console.error("the page has no #root element"),
  }
}
index.html, iki modülün yanında 
<div id="root"></div>
<script type="module">
  import { main } from "./dist/gen/main.ts";
  main();
</script>

Ayrıntılar build, bu main'in neden hiçbir şey almadığı ve adım adım anlatım

npx glyph build . --out dist/gen modülleri kontrol eder, React'in tanımlarına karşı tsc --strict çalıştırır ve TypeScript'i dist/gen'e yazar. Ardından npx vite build --outDir dist/web, index.html'i okur, import'u takip eder ve onu React ile paketler. Bu main hiçbir şey almaz ve hiçbir şey döndürmez, çünkü script onu argümansız çağırır; glyph init'in yazdığı main(argv) -> number, glyph run'ın node altında çağırdığıdır. package.json ve kurulum satırıyla birlikte tam adım adım anlatım, glyph llms'in yazdırdığı referanstaki Glyph'i bir tarayıcı sayfasında çalıştırmak bölümünde. CI, examples/apps/todo'yu aynı şekilde build eder ve headless Chromium'da render eder.

Şu anki durum

Bugün yayında

  • Component'ler, JSX, fragment'lar (<>...</>)
  • Member-expression eleman isimleri (<Ctx.Provider>)
  • JSX prop spread ({...register()})
  • Her import yazılışında tsc'den önce component'e karşı kontrol edilen props
  • Adıyla import edilen React'in kendi hook'ları (useState, useReducer, useEffect); tiplerini tsc kontrol eder ve çiftleri destructure edilir (let [count, set_count] = useState(0))
  • Kapsamı tam tagged union action'larıyla useReducer
  • Arm pattern'leriyle bir match olarak kontrol edilip indirgenen <match>/<case>
  • createContext/useContext ile Context
  • std/dom (başlık, mount noktası, adres), std/storage ve std/console üzerinden sayfa
  • JSX metni TSX'in okuduğu gibi okunur, yani <p>Don't stop</p> düz metindir; }, >, // ve &amp; gibi bir HTML entity'si metinde reddedilir (E0012) ve yerine kullanılacak yazılış söylenir.E0012
  • Bir array üzerindeki üye okuması kontrol edilir, yani bir Array<string> üzerinde {items.foo} E0210'dur.E0210
  • examples/apps/todo, React 18 üzerinde Vite ile paketlenen ve bir tarayıcıda render edilen eksiksiz bir uygulamadır.

Yolda olanlar

  • Glyph'in henüz desteklemediği her React kalıbı, gap numarası ve o zamana kadar ne yazılacağıyla birlikte Glyph React için henüz neyi yapmıyor? sayfasında listeleniyor.
  • Glyph'in checker'ı bir hook'un sonucunun tipini belirlemez, bu yüzden sayı tipindeki bir state üzerinde set_count("x"), editörde bir Glyph hatası değil build sırasında bir tsc hatasıdır.
  • std/dom sayfayı okumak ve başlığını ayarlamakla sınırlı: render ettiği DOM'un sahibi React'tir, bu yüzden eleman setter'ları ya da event listener'ları yoktur.
  • Bir effect fn() -> void { ... } olarak yazılmak zorundadır, çünkü bir lambda son ifadesini döndürür ve React onu bir cleanup olarak çağırırdı.
  • Satır içi yazılmış bir props tipi bu mesajlarda hâlâ record olarak görünür; adlandırılmış bir tip ise adıyla görünür.
  • Arayüzü TypeScript'te olan mevcut bir Vite uygulamasına Glyph çıktısını gömmek deployment kılavuzunda anlatılıyor.
