TypeScript'ten geliyorsanız

Zaten TypeScript yazıyorsanız neler değişir

Beklediğinizden az. Glyph, tsc --strict'ten geçen TypeScript'e derlenir, npm'i ve deploy sürecinizi korur ve neredeyse aynı okunur. Farklar bir avuç değişiklikten ibaret ve her biri yanılmanın bir yolunu derleyicinin yaptığı bir kontrolle takas eder.

TypeScript biliyorsanız bunun çoğunu biliyorsunuz#

Yeni bir dil öğrenmiyorsunuz, yalnızca şu dördünü. Bu sitedeki her örnekte bunlar var.

match
Kapsamı tam bir switch: bir union üzerinde, derleyici her durumu ele almanızı zorunlu kılar. Aynı zamanda tek koşul yapısıdır: if/else ve ternary yoktur, aşağıda açıklanıyor.
Result<T, E>
Fırlatılan exception'lar yerine dönüş değeri olarak hatalar. Birini match ile ele alırsınız ya da ? operatörüyle yukarı iletirsiniz.
fn f() -> T
Bir fonksiyon; -> onun dönüş tipidir. type X = {...} bir record, type X = A | B ise bir tagged union'dır.
mut x = e
Yeniden atama açıktır ve grep'lenebilir. Düz bir let bağlaması siz fark etmeden asla değişmez; birini değiştirmek için mut yazarsınız.

Bu sitede "ajanlar", Claude, Copilot ve Cursor gibi yapay zekâ kodlama asistanları anlamına gelir. Glyph en çok onlara yardım eder, ama kodu bir insan da yazsa bir model de yazsa kontroller aynıdır. Zaten zod ve eslint ile strict TypeScript kullanıyorsanız, bir dilin bunun üzerine neler eklediği burada.

if yok#

Bir boolean üzerindeki dallanma, true ve false üzerinde bir match'tir. Yalnızca bir tarafta işlem yapıyorsanız, diğer arm boş bir bloktur.

TypeScript 
function label(admin: boolean): string {
  return admin ? "admin" : "member";
}

if (verbose) {
  console.log("starting");
}
Glyph 
fn label(admin: bool) -> string {
  return match admin {
    true => "admin",
    false => "member",
  }
}

match verbose {
  true => io.println("starting"),
  false => {},
}

Nedeni spesifikasyondaki D3 kararı: bir değer üzerinde dallanmak için tek bir yapı, böylece okunacak, yazılacak ve aranacak tek bir biçim olur. Bir daldan çıkan değer her zaman bir match'ten çıkar ve onun sonuç tipini tsc'ye bırakmak yerine Glyph'in kendi checker'ı hesaplar. Bir union için her durumu kapsamak zorunda olan yapı da aynısıdır (E0200). Bir boolean için bunun getirisi azdır, çünkü false => {}, bir else'i yazmamaktan fazlasını söylemez.

Bunun bir bedeli var. Tek satırlık bir ternary dört satırlık bir match olur, bir koşula bağlı erken dönüş boş arm'lı bir match olur ve bir TypeScript okuyucusuna ilk tuhaf gelen şey budur. Spesifikasyon bu uzunluğu kabul edilmiş bir bedel olarak kaydeder. Yine de if yazmak E0006 hatasıdır ve yardım metni match biçimini gösterir; ternary ise aynı yardımla E0013'tür.

Zaten ödediğiniz bedel#

Bir TypeScript kod tabanında yapay zekâ ajanlarıyla geliştiriyorsanız, günlük maliyetler bunlar. Her birinin Glyph'te somut bir karşılığı var, listeden bağlantısı verildi.

  • Ajanlar var olmayan API'ler uydurur, çünkü TypeScript tiplerini siler ve çalışma zamanı artık derleme zamanıyla örtüşmez. Glyph tipleri bir çalışma zamanı kontrolü taşır (T.parse, T.is), bkz. tipli API'ler.
  • Ajanlar belirsizliği any ve as unknown as T ile örtbas eder ve derleyici buna izin verir. Glyph'te ikisi de yoktur, aşağıdaki tabloya bakın.
  • Tek satırlık bir değişiklik istersiniz ve tüm dosya yeniden yazılmış olarak gelir, çünkü formatter her düzenlemede zincirleme değişiklik yapar. glyph fmt'nin seçeneği olmayan tek bir düzeni vardır, bkz. temiz diff'ler.
  • Her tipin yanında elle yazılmış bir validator tutarsınız (zod ve bir serializer) ve bir ajan bir alanın adını birinde değiştirir ama diğerlerinde değiştirmez; hepsi yine de derlenir. Glyph'te tip, validator'ın kendisidir.
  • Bir sembol için grep yaparsınız ve alakasız on eşleşme bulursunuz: overload'lar, decorator'lar, birleştirilmiş namespace'ler. Glyph'te bunların hiçbiri yoktur, bkz. bir şeyi bulmak.

TypeScript'in size verdiği kapatma düğmeleri ve Glyph'teki karşılıkları#

Aşağıdaki her TypeScript yapısı, tip denetleyicisine kontrolü bırakmasını söyler. Hiçbiri Glyph sözdizimi değildir. Ortadaki sütun, glyph check --no-tsc'nin 0.1.149'da her biri için yazdırdığı çıktıdır.

glyph check'in tüm bir aşamayı atlayan flag'leri var (--no-tsc, tsc --strict çalıştırmasını, --no-test ise @example testlerini atlar), ama tek bir kontrolü susturan hiçbir flag yok. Bir TypeScript projesinin kabul edip Glyph'in reddettiği her şeyin tam listesi, her vaka iki derleyicide de çalıştırılmış olarak, yakaladıkları sayfasında.

Tek bir kaçış yolu var ve onu grep'leyebilirsiniz#

Glyph'in yazamadığı bir TypeScript'e ihtiyacınız olduğunda, extern_ts("...") tek bir satır içi tip ya da ifade alır ve tsc onu yine kontrol eder. Bütün bir modül için .ts dosyasını src/extern/ altına koyun ve import extern/name yazın; bunun dışında relative import'lar geçersizdir, yani tek giriş yolu budur. İki biçim de extern kelimesini içerir, bu yüzden grep -rn extern src/, denetleyicinin işi TypeScript'e devrettiği her yeri listeler.

src/clock.glyph 
module clock

pub fn now_ms() -> number {
  return extern_ts("Date.now()")
}

Üretilen TypeScript neye benziyor#

Düz TypeScript, modül başına bir dosya, okuyup commit edebileceğiniz şekilde. Bir union, discriminated union artı çalışma zamanı kontrolünü taşıyan bir değere dönüşür; bir match ise tag üzerinde bir switch olur. Bu, soldaki modül için glyph build'in çıktısıdır, import satırları kırpılmış hâlde.

plan.glyph 
module plan

pub type Plan = Free | Pro | Team

pub fn seats(p: Plan) -> number {
  return match p {
    Free => 1,
    Pro => 5,
    Team => 50,
  }
}
plan.ts (üretilmiş, kırpılmış) 
export type Plan =
  | { tag: "Free" }
  | { tag: "Pro" }
  | { tag: "Team" };

export const Free: Plan = { tag: "Free" };
export const Pro: Plan = { tag: "Pro" };
export const Team: Plan = { tag: "Team" };
export const Plan = {
  is(value: unknown): value is Plan { ... },
  parse(value: unknown) { ... },
  schema: ...,
};

export function seats(p: Plan): number {
  const __m0 = p;
  switch (__m0.tag) {
    case "Free": { return 1; }
    case "Pro": { return 5; }
    case "Team": { return 50; }
    default: throw new Error("non-exhaustive match");
  }
}

Team arm'ını silin; build, herhangi bir TypeScript yazılmadan durur:

Glyph'i kullanmayı bırakırsanız elinizde kalan, üretilmiş .ts dosyalarıdır. Build'in yanına yazdığı küçük, paketlenmiş bir destek dizini dışında hiçbir çalışma zamanı bağımlılığı yoktur.

npm ve zaten sahip olduğunuz TypeScript#

Bir .glyph modülü bir npm paketini adıyla import eder (import kafkajs { Kafka }), tipleri paketin kendi tanımlarından gelir; mevcut .ts dosyalarınız da üretilmiş Glyph modüllerini herhangi bir yerel dosya gibi import eder. Yani TypeScript olarak kalan bir uygulamanın içinde tek bir modülle başlayabilirsiniz. Ayrıntılar üç yanıtta.

Mevcut TypeScript, JavaScript ve npm kütüphanelerimi kullanabilir miyim?

Paketleri import etmek, bir .ts shim'i tutmak ve Glyph'i .ts'ye geri import etmek.

 Glyph'i mevcut uygulamamın içinde benimseyebilir miyim?

Domain çekirdeği Glyph'te, geri kalanı TypeScript'te, standart bir Vite iskeletinde.

 React ile çalışıyor mu?

Component'ler, JSX, hook'lar, Context ve kontrolü hâlâ tsc'nin yaptığı yerler.
