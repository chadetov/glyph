Versions & changelog

October 2026 releases

Glyph is an early preview and moves fast. Every release is here with what it fixed and added, so you can see what is in the version you're running and what changed since.

Stability, pre-1.0: the language can still change between 0.1.x releases. We hold two lines: your code stays runnable (it always compiles to plain TypeScript you own and can keep if you stop using Glyph), and when syntax changes we aim to make glyph fmt migrate it for you. The full policy is in docs/stability.md.

A release marked Breaking rejects code an earlier version accepted. Usually because the compiler started catching something it had been missing, which is the point of the language, but it can turn a green build red on an upgrade. Read that release's note before taking it.

The marker is applied only where both versions were run and the older one accepted the program. It is not inferred from how a note is worded, and an unmarked release older than 0.1.99 has not been tested rather than been found safe. Every release from here on states which it is.

October 2026

3 releases, 3 breaking, 0.1.125 to 0.1.127

0.1.127

Breaking 29 Oct 2026 Link
This release is about records.

This release is about records. Glyph checked the top level of a record against its declaration and then compared what was inside it with a weaker rule, so a record nested in another record could be the wrong shape and pass glyph check --no-tsc. It is breaking for that reason: programs that 0.1.126 accepted and tsc refuses are now refused by Glyph too. That was established by running 0.1.126 and this build on each program below.

Records are compared all the way down

Every field of a record is now compared by the same rule as the record itself, so a nested record, a declared type and a string-literal union inside a record are checked the way they are at the top. The same gap reached four other places, and they are closed too: a field the value may not have (a?: number) where the declaration requires it, a declared record passed where an inline one is declared, a function whose return type doesn't fit, and an interface's members.

glyph check --no-tsc 
type Other = { a: number, }
fn tx(x: { o: Other, }) -> number { return 1 }
pub fn g() -> number {
  let v = { o: { b: "x", }, }
  return tx(v)
}
// 0.1.126: nothing                                         (exit 0)
// 0.1.127: [E0211] argument type mismatch: expected `record`, found `record`
//                                                           (exit 1)

The message still calls both sides record when neither has a name, which is a known display gap. One program goes the other way: a record that refers to itself through a field, such as type Node = { kids: Array<Node>, }, passed to an interface shaped the same way used to be refused by name one level down. tsc accepts it, and now Glyph does too.

A record of only optional fields

A record whose fields are all optional accepts almost anything, so TypeScript refuses a value that shares none of its fields (TS2559). Glyph now applies the same rule, with the same edges: an empty value is accepted, and one shared field is enough.

glyph check --no-tsc 
fn ti(x: { hint?: string, }) -> number { return 1 }
pub fn g() -> number {
  let v = { x: 1, }
  return ti(v)
}
// 0.1.126: nothing                                         (exit 0)
// 0.1.127: [E0211] ... it has no field in common with `record`, whose fields
//          are all optional                                 (exit 1)

An extra field on a fresh object literal is still accepted. tsc refuses it (TS2353) and Glyph doesn't yet; that's recorded as G273.

Impact on components

glyph_impact answered "not indexed" for a JSX element under a change to a component's props. It now treats <Card title="x" /> as the call it compiles to, one props record passed to Card, and lists each attribute against the field it is checked against. An attribute and a call argument of the same types now get the same verdict, because they go through the same code. With the record rule complete, glyph_assignable answers COMPATIBLE or WILL_FAIL for a record against a declared record, where it used to say it had no rule.

Breaking, measured

Across the 31 apps and examples/, with and without tsc, every exit code and every list of diagnostic codes is the same under 0.1.126 and this build. An early cut of this release refused two of the apps, shortlink and zipper: array.fold(xs, "", ...) inferred the accumulator as the literal type "" instead of string. That was fixed before release, and it is now inferred as string, which is what tsc infers.

0.1.126

Breaking 17 Oct 2026 Link
This release finishes what 0.1.125 started on React components: the type a component returns now means something to tsc, go-to-definition works through a namespace import, and impact answers the same for a call however its callee was imported.

This release finishes what 0.1.125 started on React components: the type a component returns now means something to tsc, go-to-definition works through a namespace import, and impact answers the same for a call however its callee was imported. It is breaking in two places, each established by running 0.1.125 and this build on the same program: a component whose parameter is unknown or an unbounded type parameter is E0229, and ? inside a component body is E0201.

A component returns a type tsc can read

Component is a prelude name, and -> Component is how a component declares that it returns a rendered element. The emitter wrote the bare word into the TypeScript, which tsc could not resolve. The flagship React example only got past that by importing React's Component class over the prelude name, which tsc refuses for a different reason.

glyph check, with React 18's types 
fn view() -> Component { return <p>hi</p> }
pub component App() -> Component { return <div>{view()}</div> }
// 0.1.125: [TS2304] Cannot find name 'Component'      (twice, exit 1)
// 0.1.126: tsc --strict passed                         (exit 0)

The prelude Component now lowers to React.ReactNode. It was picked by running tsc on every value a component can return in Glyph: an element, a fragment, an <if> without an <else> (which yields null), a <match> and a <for> list. ReactNode is the narrowest type that accepts all of them. A component with no annotation now returns Component too, where the checker used to record void, so hover and glyph_symbol read fn(Props) -> Component. A module whose JSX lives only in plain functions now gets its import * as React line. One edge: React's types before 18.2.8 refuse a function component that returns ReactNode.

Two things a component cannot be

A component whose parameter is unknown or an unbounded type parameter receives a props object it can read nothing from, and tsc refuses its elements once they write attributes. Both are E0229 now, like a primitive. A type parameter bounded by a record or interface is still allowed. And ? in a component body used to compile and hand React the Err object to render; now that a component's return type is Component, it is E0201 like ? anywhere that does not return a Result.

glyph check --no-tsc 
component G(p: unknown) { return <p>x</p> }
pub component App() {
  let v = get()?
  return <p>{v}</p>
}
// 0.1.125: nothing                                            (exit 0)
// 0.1.126: [E0229] ... parameter `p` is `unknown`, which gives it nothing it can read
//          [E0201] ...                                         (exit 1)

Go-to-definition through a namespace

Under import ui, go-to-definition on Button in ui.Button or <ui.Button> answered nothing, and on Props in ui.Props it jumped to the import line. It now answers the declaration in ui.glyph, as the named import import ui { Button } always did, in the editor and in glyph_definition alike. A test drives it over the language server protocol under all three import spellings.

Impact, and a missing children prop

A call written ui.fmt(1) was filed as a reference and answered "not indexed", where fmt(1) under a named import was a call that will fail. Both are calls now, with the same verdict and reason. An import line under an edit that keeps the name (a changed parameter type, an added parameter) is SAFE: an import checks only that the name exists and is exported, which was confirmed by reading every check at an import line and by making the edits. And when a required children prop is reported missing on an element that writes children, the help now says why: children between the tags are passed outside the props object, so declare children?: or pass children={...}.

The React page, corrected

The React answer page showed hooks named use_state and use_reducer. They existed only in a stub this repository uses for CI, not in React. A round that built a small app against real React 18 found it, along with what does not work yet. Browser globals such as document can't be named, so an effect that sets the page title can't be written. And a hook's tuple has to be read by index. The page now shows React's real useReducer and says both of those plainly. A typed std/dom module and let [a, b] = ... are planned. Across the 31 apps and the examples, the only verdict that changed is the React example, which went from failing tsc to passing.

0.1.125

Breaking 11 Oct 2026 Link
This release is about React components.

This release is about React components. Three programs passed glyph check with tsc in the loop under 0.1.124 and were broken when they ran: a component reached through import ui was emitted as a string tag and never called, an element with no attributes passed null as its props, and an unexported component reached through a namespace was accepted. All three are Glyph diagnostics now. It is breaking for that reason, and for two more programs that 0.1.124 left to tsc: a component whose parameter is not a record, and an element missing a required prop. Each was established by running 0.1.124 and this build on the same program.

A dotted element is a component

An element was classified by the first character of its name, so <ui.Button /> under import ui was treated like <div> and emitted as createElement("ui.Button", ...). React rendered an unknown tag, tsc accepted a string tag with any props, and the only diagnostic was a wrong "unused import ui".

import ui, then a wrong attribute 
<ui.Button variant="nope" label="go" />
// 0.1.124: [E0106] unused import `ui`     tsc --strict passed  (exit 0)
//          renders <ui.Button variant="nope" label="go"></ui.Button>
// 0.1.125: [E0211] expected `Variant`, found `"nope"`           (exit 1)
//          renders <button>go</button> once the value is fixed

A dotted name is a component whatever the case of its base, which is TypeScript's rule for a member-expression tag. One classifier now decides it, where the resolver and the emitter each kept their own copy. The base resolves like any name, the props check reaches the component through a namespace or an aliased import, and the member goes through the same export check ui.Button does as a value, so <ui.Nope /> and an unexported component are E0105.

A missing required prop is named, even with no attributes

A record literal or an element missing a required field was refused as found `record`, or at the element not at all. The diagnostic now names what is missing, in the message and in a missing_fields list on --json, --agent and the MCP diagnostics.

glyph check, with tsc 
<Button label="go" />
<Button />
// 0.1.124: first line caught by tsc only; second line passes  (exit 0)
// 0.1.125: [E0211] expected `Props`, found `record`: missing field `variant`
//          [E0211] expected `Props`, found `record`: missing fields `variant`, `label`

The second line is the one that mattered. An element with no attributes was emitted with null props, and React's types accept null for any component, so <Button /> against required props passed tsc --strict and the component read undefined when it rendered. It passes {} now, so tsc refuses it too, and Glyph asks every component element without a spread for its required props. A ? prop may be left out. A required children prop is reported missing even when children are written between the tags, because they are passed outside the props object; tsc says the same, and the message should explain it and does not yet.

A component takes one props record

component Greeting(name: string) was accepted, and no element could ever render it: React hands a component the one props object its element builds. It is E0229 at the parameter now, for a primitive, a string-literal union, a tagged union, an array, a Nullable or a function type. A record, an alias of one, an imported record and an interface are props records. unknown and a bare generic draw nothing, because the checker cannot prove they are not records. A function that returns JSX and is called directly is an fn.

References, rename and impact see an element at its name

After the classification fix, glyph query references on a component still listed a use written <Button> under a named import and missed the same use written <ui.Button>, so the answer depended on how the component was imported, and glyph_impact missed the site. The named case was wrong too: it recorded the whole element, so a rename wrote the new name over the attributes and children, and the closing tag was never recorded. Every element is now recorded at its name, in the opening and closing tag alike. Rename rewrites both tags, and impact counts one site per element. Hover on Button in <ui.Button> answers the component's type instead of null. Two explanations in the impact table were false for an element and an import line, and each now has its own; the verdicts did not change.

Smaller things

Two glyph check runs at the same time could fail each other with io error reading .../glyph-check-scratch/<pid>-0/: Invalid argument: each staged under a shared temp directory and removed it on the way out. 2,000 concurrent checks gave 3 such failures; each check now owns its own directory, and 4,000 gave none. Publishing moved to npm trusted publishing, so no npm token is stored anywhere, and before the first package is published the release job proves each of the six packages' publisher through the same OIDC exchange a publish makes. Across the 31 apps and the examples, every exit code and diagnostic code is the same under both versions, with and without tsc.

No release in October 2026 is marked Breaking.
