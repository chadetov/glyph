Versions & changelog

What changed, newest first.

Glyph is an early preview and moves fast. Every release is here with what it fixed and added, so you can see exactly what's in the version you're running, and what's waiting for you in the next one.

Stability, pre-1.0: the language can still change between 0.1.x releases. We hold two lines: your code stays runnable (it always compiles to plain TypeScript you own, a permanent escape hatch), and when syntax changes we aim to make glyph fmt migrate it for you. The full policy is in docs/stability.md.

A release marked Breaking rejects code an earlier version accepted. Usually because the compiler started catching something it had been missing, which is the point of the language, but it can turn a green build red on an upgrade. Read that release's note before taking it.

The marker is applied only where both versions were actually run and the older one accepted the program. It is not inferred from how a note is worded, and an unmarked release older than 0.1.99 has not been tested rather than been found safe. Every release from here on states which it is.

November 2026

22 releases, 18 breaking, 0.1.128 to 0.1.149

0.1.149

Latest Breaking November 2026 Link
A statement can no longer start on the line where the one before it ended.

A statement can no longer start on the line where the one before it ended. let s = "a" "b" used to bind "a" and drop "b", let x = h() g bound h(), and return x as User was three statements, since Glyph has no cast. All of them compiled, and tsc accepted them.

Each is now E0013, with help that fits what came second: Glyph has no as, adjacent strings are not joined (write "a" + "b"), or the statement needs its own line. 0.1.146 did this for {; this release does it for everything else. One-line bodies like fn f() -> int { return 1 } and for x in xs { f(x) } are unaffected.

Breaking

Programs with two statements on one line inside a block no longer compile. On every .glyph file in the repository and all 32 example apps, the only changes are three files that were already refused (two test fixtures and a benchmark that demonstrates a refusal, which still passes), and the emitted TypeScript is identical.

0.1.148

Breaking November 2026 Link
A map's keys are checked at run time now.

A map's keys are checked at run time now. With type Tier = "free" | "pro", json.parse<Record<Tier, int>> returns Ok only for an object whose keys are exactly free and pro. A stray key or a missing one is an Err; before, both came back Ok, and the program went on believing every member was there.

A where-refined key type runs its predicate on each key, and an int key must be the plain spelling of a whole number, so "01" and "1.5" are refused. The same check runs in T.parse, T.is, is patterns, record fields and everywhere else a value is validated. Record<string, V> behaves exactly as before, and its emitted code is unchanged.

Breaking

Programs that compiled still compile, but a map that does not match its key type is now refused where it used to be accepted. Two shapes stop compiling with E0304: a Record whose key type has no runtime check, and a generic record whose Record field is keyed by its own type parameter, unless that parameter is string. On every .glyph file in the repository and all 32 example apps, glyph check and the emitted TypeScript are unchanged.

Still open: a Record<string, V> can still be passed where Record<Tier, V> is declared, which 0.1.151 addresses, and Glyph's own checker leaves a map's keys to tsc, which is on the list after that.

0.1.147

Breaking November 2026 Link
A check that names a type parameter is now E0304, because a type parameter has no runtime check.

A check that names a type parameter is now E0304, because a type parameter has no runtime check. This covers is T, is Array<T>, json.parse<T>, Box.parse<T>(v), and T.parse(v) or T.is(v) where T is the parameter.

Before, inside fn h<Doc> in a module that also declares a type Doc, these quietly ran the record's check while the code treated the result as the type parameter. Some passed glyph check and tsc outright and checked values against the wrong type; others crashed at run time. The parameter is now found by scope, so a module-level type with the same name never stands in for it.

Breaking

We ran 0.1.146 and this build on each shape: those that exited 0 before now exit 1, with and without tsc. On every .glyph file in the repository and all 32 example apps, nothing changes. To validate a value whose type is a parameter, take a Schema<T> argument and use json.parse_with.

0.1.146

Breaking November 2026 Link
A { on the line where a statement just ended is now a parse error, E0013.

A { on the line where a statement just ended is now a parse error, E0013. Before, return h() { k: 2 } compiled as return h() followed by an object literal that never ran, and the only hint was an unreachable-code warning. The value the line was written to return was silently dropped.

`{` cannot begin a new statement on the line where `return h()` ends

The help gives the fix. Glyph has no Order { … } form, so write the literal on its own and put the type on the annotation, or drop the braces if they were not meant to be the value. return Order { … } now reports this error instead of E0228.

Breaking

We ran 0.1.145 and this build on each shape: return h() { … }, let o = h() { … } and a bare h() { … }, in a function, a match arm or a lambda, exited 0 before and exit 1 now, and tsc accepted all of them. glyph fmt refuses such a file instead of splitting it across two lines. On every other .glyph file in the repository and all 32 example apps, nothing changes.

0.1.145

Breaking November 2026 Link
is Record<K, V> and is Array<X> now check what the container holds.

is Record<K, V> and is Array<X> now check what the container holds. Before, match v { is Record<string, int> => … } took the arm for any object, including {"a": "x"}, and is Array<int> took it for any array. Now every value or element is checked against V or X, at any depth. A pattern whose part type has no runtime check, such as is Array<H> with H an extern_ts type, is E0304. is Record<string, unknown> and is Array<unknown> work as before.

While doing this we found that a generic named through an import alias, like w.Box<int>, was checked against a different Box when the module declared its own. json.parse<w.Box<int>> compiled, rejected a real w.Box value and accepted a local one. That is now E0304. When the bare name refers to the same generic (m.Page<m.User> beside import model { Page, User }), it is still checked as before.

Breaking

We ran 0.1.144 and this build on each affected shape. Patterns over a part with no runtime check, and the mislabelled namespaced generics, went from exit 0 to 1, with and without tsc. Some programs still compile but now behave differently at run time: a value that does not match the declared element or value type falls through to the next arm instead of taking this one. On every .glyph file in the repository and all 32 example apps, glyph check and the emitted TypeScript are identical to 0.1.144.

A record's keys are not checked yet, here or by json.parse: Record<Tier, int> accepts a key outside Tier. That is 0.1.148.

0.1.144

November 2026 Link
A generic record imported from another module is now judged by the module that declares it, the way an imported record already was.

A generic record imported from another module is now judged by the module that declares it, the way an imported record already was. If Page<T> has a field typed by a record its module keeps private, json.parse<Page<User>>, Page.parse<User>, is Page<User> and the other uses of Page now compile and check that field at run time. 0.1.141 to 0.1.143 refused them with E0304 and suggested marking the record pub; that is no longer needed.

A private record that holds a field nothing can check at run time is still refused, and the message now names that field instead of the record's privacy.

This release is not breaking: nothing that compiled before stops compiling. We ran 0.1.143 and this build on every .glyph file in the repository and on all 32 example apps, and found no differences.

0.1.143

Breaking November 2026 Link
An is pattern is now checked the same way T.is(v) is.

An is pattern is now checked the same way T.is(v) is. Before, match v { is Doc => … } compiled even when Doc had a field nothing could check at run time, such as an extern_ts type, and the arm then matched any value with that key present. Doc.is(v) refused the same type. Now both are E0304 with the same message, naming the field. This covers records, unions, nested records, generics like is Page<User>, and <case is T> in JSX.

One spelling ran the wrong check entirely: in a module that declares its own Box, a pattern is w.Box<int> naming the imported one was compiled as a check against the local Box. It is now refused (E0300), as a namespaced pattern without a type argument already was.

Breaking

We ran the published 0.1.142 and this build on each refused shape: every one exited 0 before and exits 1 now, with and without tsc, and tsc accepts all of them. On every .glyph file in the repository and all 32 example apps, glyph check gives the same result apart from the reworded E0304 note on one file that already failed, and the emitted TypeScript is identical.

Still open: is Record<string, int> and is Array<X> check only that the value is an object or an array, not what it holds; that is 0.1.145. A namespaced pattern like is w.P has no lowering yet, so import the type by name to match on it.

0.1.142

Breaking November 2026 Link
Lint warnings (unused import, unused binding, unreachable code, unreachable module) now show up on a file that has a type error, as long as it parses and its names resolve.

Lint warnings (unused import, unused binding, unreachable code, unreachable module) now show up on a file that has a type error, as long as it parses and its names resolve. Before, they appeared only after the last type error was fixed, so an edit could add an unused binding to a broken file and nothing said so until later. This applies in glyph check, glyph build, the editor and the playground. No exit code changes.

glyph/applyEdit follows the same rule. It now refuses an edit that adds one of those warnings to a file with a type error, and every answer carries stages, the stages that ran on the edited file, so an agent can see when the emitter did not run. An edit that adds a _ => arm is no longer refused because of import warnings the file already had.

If an import is unused only because a missing match arm would use it, glyph --explain E0106 now says to write the arm rather than delete the import. And when glyph fix declines to rename an arm head, it now names the arm that already handles the case.

Breaking

For the applyEdit protocol, as above, and for anything that counts warnings: a file that already fails glyph check can now print more of them. We compared the published 0.1.141 with this build on every .glyph file in the repository and on all 32 example apps: the only differences are 32 added warnings on 27 files that already had a type error. Formatting, builds and the emitted TypeScript are identical.

Still open: return h() { k: 2 } is read as return h() followed by an object literal that never runs, and only warns (G351); the playground still shows emitted TypeScript for a file with a type error (G352); and applyEdit refuses an edit that writes one of several missing match arms (G353).

0.1.141

Breaking November 2026 Link
json.parse now checks a generic record's own fields and a union's variant payloads, and refuses with E0304 when one of them has no runtime check.

json.parse now checks a generic record's own fields and a union's variant payloads, and refuses with E0304 when one of them has no runtime check. Before, such a field was only tested for being present, so a document with the wrong value in it came back Ok:

page.glyph 
pub type Page<T> = { items: Array<T>, h: Handle }

let page = json.parse<Page<User>>(body)
cannot validate `Page<User>`: `Page`'s field `h` has type `Handle`, which has no runtime check

Here Handle is an extern_ts type, which Glyph cannot check at run time. A record with the same field was already refused; a generic one and a union variant carrying it now get the same answer, whether you call json.parse, Page.parse, U.is or json.parse_with with its schema, put the type inside another record, an Option or an Array, pass it as a generic's type argument, or reach it through another module.

Breaking

We ran 0.1.140 and this build on each refused shape: every one exited 0 before and exits 1 now, with and without tsc, and tsc accepts all of them. One case is refused although it was safe: an imported generic whose field is a record its module keeps private. This module cannot see into that record, so it refuses rather than guess; the message says so, and marking the record pub fixes it. 0.1.144 will judge it from the module that declares it instead. Nothing else changes. On every .glyph file in the repository and all 32 example apps, glyph check, glyph fmt and the emitted TypeScript are identical to 0.1.140.

A match arm written is Page is not covered by this check yet; that is 0.1.143.

0.1.140

November 2026 Link
json.parse<Rows> now works when Rows comes from another module and names a type that module imports.

json.parse<Rows> now works when Rows comes from another module and names a type that module imports. Earlier releases refused this with E0304:

rows.glyph 
module rows

import user { User }

pub type Rows = Array<User>

The check follows User into the module that declares it, by name or through a namespace, through as many modules as it takes, and a generic such as Page<User> is checked the same way. Names are always read where they were written. If the file calling json.parse has its own User with different fields, the document is checked against rows's User, and one shaped like yours comes back Err.

A generic reached this way is checked field by field first. If one of its own fields has a type nothing can check at run time, such as an extern_ts type, it is still E0304, and the message now names that field. The same generic parsed directly, imported by name, or used as a record field still gets only a presence check on that field. So does a union whose variant carries such a field (A({ h: H })), on every path, now including one reached through another module. The next release closes both, and will be breaking.

This release is not breaking: nothing accepted before is refused now. We ran the published 0.1.137 and this build on every .glyph file in the repository and on all 32 example apps, and the only differences are the ones 0.1.138 and 0.1.139 already list.

0.1.139

Breaking November 2026 Link
Reading a member off an Option or a Result is now checked.

Reading a member off an Option or a Result is now checked. An Option has no members, and a Result has two, map and map_err. Anything else is E0210, and the message says which members exist:

type `Result<Note, string>` has no field `value`: a `Result`'s only members are `map` and `map_err`

Before, r.value, r.tag and o.tag passed glyph check and the full build, because they are how the emitted TypeScript stores the value and tsc could see them. They are not part of the language: reading r.value on an Err gives you the error where you expected the success value, and nothing warns you. Open the value with match, or bind a Result with ? first and read the field after:

note.glyph 
let note = load()?
return Ok(note.name)

A misspelled method gets a suggestion (r.mapp(f) points at map). .map_err(f)?, the most common way to use a Result, is unchanged.

The check needs to know the value is an Option or a Result. A value built with Ok(x) or Some(x) and never annotated is not typed that way yet, so let r = Ok(x) followed by r.value still passes, and so does r["value"]. Both are on the list.

Breaking

We ran the published 0.1.137 and this build on the same programs. o.tag, r.tag and r.value passed glyph check with tsc and now fail. Other reads, such as o.name or r.unwrap(), were already refused by tsc in a full check and are now also caught under --no-tsc, in the editor and over MCP. On every .glyph file in the repository except the two test files added to be refused, and on all 32 example apps, glyph check gives the same result as before, and the emitted TypeScript is identical.

0.1.138

Breaking November 2026 Link
Two ways for glyph fmt to change what a program means are fixed, and the fuzzer now checks for that directly.

Two ways for glyph fmt to change what a program means are fixed, and the fuzzer now checks for that directly.

The first is G335. Inside a block, a line that starts with ( continues the line above. 0.1.137 printed load()? followed by .run() as (load()?).run(), so after let a = 1 the formatted file meant let a = 1(…).run(). The formatter now keeps the step on its own line:

job.glyph 
pub fn f() -> Result<number, string> {
  let a = 1
  load()?
    .run()
  return Ok(a)
}

It also stops adding parentheses around a ? that the source did not need: f()?(x), f()?[0] and f()? ? are written as they are. The two ? in the last one are a space apart, because ?? is the nullish operator. Inside an expression, (f()?).name keeps its parentheses, since f()?.name is optional chaining.

The second is G338. A where refinement on a union type was dropped, so a program glyph check refused (E0300) came out of the formatter as one it accepted. The refinement now prints on its own line after the last variant and the error stays.

The fuzzer used to check that formatting twice gives the same text. It now also parses the formatted file and compares the syntax tree with the original's, so a layout that changes what a file means fails on the first run. A test runs the same comparison over every example and test file in the repository.

A method chain with two ? in a row can now hold comments between its steps, like any other chain. 0.1.137 refused such a file.

Breaking

Only for glyph fmt --check. We ran the published 0.1.137 and this build on each layout the formatter now writes differently: (e?)(x) and (e?)[i] become e?(x) and e?[i], (e?)? becomes e? ? wherever it appears, and a statement that starts with (e?).f, including the body of a one-line lambda, is split across two lines. A file containing one of these passed fmt --check under 0.1.137 and fails it now; running glyph fmt once fixes it. No program's meaning changes, and glyph check, glyph build and the emitted TypeScript are the same. On every .glyph file in the repository and all 32 example apps, the only formatting changes are on the two new test files, and no file that 0.1.137 had already formatted is touched.

0.1.137

Breaking November 2026 Link
glyph fmt no longer moves a comment.

glyph fmt no longer moves a comment. When a comment sits somewhere the canonical layout has no line for, the formatter refuses the file, leaves it exactly as it was, and tells you where to put the comment:

first.glyph 
module first

pub fn first(xs: Array<number>) -> number {
  return xs[
    // the oldest entry
    0
  ]
}
first.glyph:5:5: comment inside an index expression has no canonical place; move it above the statement

Before, the formatter printed xs[0] and put the comment below the statement, or inside the next argument list, where it described something else, and the result looked deliberate. A comment you write is a claim about the line it sits on, and a formatter that moves it makes the file say something false about itself.

Places with no line for a comment include an index, a ! or await operand, a type annotation or a generic argument, a pattern, the inside of a JSX tag, an import list, the middle of a method chain after a call's arguments, and the space between let x = or return and the value, which is the one people write most. Where the formatter has a one-per-line layout (a block, a match, a record or union body, a literal, an argument list, an operator chain, a method chain between steps), comments are placed exactly as in 0.1.136. Only the first refused comment in a file is reported; fix it and run again to see the next.

The editor and glyph check see it too

The same message is warning E0500, in a new formatter range of error codes. glyph check, check --json, the MCP diagnostics tool and the editor all report it, so an agent finds the comment without running fmt. It is a warning because where a comment sits does not change what the program does: glyph check still exits 0. glyph/applyEdit refuses an edit that introduces one.

Breaking

We ran the published 0.1.136 and this build on the same files. On a file whose comment the formatter used to move, glyph fmt now exits 1 and leaves the file alone, where 0.1.136 exited 0 and rewrote it. The editor's format command returns an error instead of edits on such a file. A pre-commit hook that runs glyph fmt will stop on it until the comment is moved. glyph canonical, and the canonical view the editor and agents read, now fail on such a file instead of printing it. glyph fmt --check exits as before, but its output changes: it prints the refusal and refused first.glyph (left unchanged) where it printed would reformat first.glyph, and the summary gains a refused count.

What does not change: glyph fmt --check exits as it did, since 0.1.136 already failed a file it would have rewritten; a file 0.1.136 had already formatted is never refused; and glyph check, glyph build and the emitted TypeScript are the same apart from the new warning. Apart from the test case written to be refused, no file in the repository or its 32 example apps is.

Known issues

The fuzzer found that glyph fmt deletes a where refinement on a union type (G338). Glyph refuses that refinement (E0300), and the formatted file drops it and compiles. G335, described under 0.1.136, is still open. Both are fixed in 0.1.138.

0.1.136

November 2026 Link
glyph fmt keeps a comment written between the steps of a method chain.

glyph fmt keeps a comment written between the steps of a method chain. It used to print the chain on one line and move the comment below the statement, where it described nothing.

count.glyph 
fn count(s: string) -> number {
  return s
    .trim()
    // then count what is left
    .length
}

A comment between two steps, or between a dot and the name after it, breaks the chain one step per line, with the dot leading and the comment above its step. A step is a dot with the calls, indexes and ? that follow it. A comment inside an argument list or a lambda stays where it was and breaks nothing, so files that were already formatted stay as they are.

Some comments in a chain have no step line to sit above: one after a call's arguments and before an index (.split(",") // first then [0]), one between the function name at the head of a chain and its arguments, or one inside an index. A chain holding one of those keeps its old one-line layout, even if another comment in it could be placed, because breaking it would put the stray comment somewhere that looks deliberate. Those comments are still moved, below the statement or into the next argument list. The next release makes glyph fmt refuse the file and name the line instead.

Known issue

While testing this, the fuzzer found a way for glyph fmt to change a program. Inside a block, a line that starts with ( continues the line above, and the formatter prints load()? followed by .run() as (load()?).run(). After a line such as let a = 1, the formatted file means let a = 1(…).run(). A full build catches it here (tsc reports TS2349, since a number cannot be called), but not when the line above ends in something callable; glyph check --no-tsc catches neither. This was already in 0.1.135. Until it is fixed (G335), bind the result first: let job = load()?, then job.run().

This release is not breaking. We ran the published 0.1.135 and this build on every .glyph file in the repository and on all 32 example apps: glyph check and the emitted TypeScript are the same everywhere, and glyph fmt output differs only on the new test file written to exercise the layout.

0.1.135

Breaking November 2026 Link
JSX text is read as text.

JSX text is read as text. Until now it went through the same lexer as code, so an apostrophe started a string, // started a comment, and a " could swallow markup up to the next one. The parser now asks the lexer to read text raw, from a tag up to the next { or <, the way TypeScript does.

notes.glyph 
pub component Notes() {
  return <div>
    {
      // the heading comes from the route
    }
    <h1>Notes</h1>
    <p>Don't stop; 50% off "today"</p>
  </div>
}

What text can hold

Anything except { and <, with four refusals, all reported as E0012 with the character named:

  • } and >, which TSX refuses too. Write {"}"} or {">"}.
  • //. TSX reads it as text and Glyph used to read it as a comment, so either reading would silently change some program. Write a string child, {"see http://example.com"}, or put a comment in a child of its own as above.
  • An HTML entity such as &amp; or &nbsp;. TSX decodes entities and Glyph emits text as written, so the same characters would render differently. Write the character itself, or {"\u{A0}"} for an invisible one; the error names the character the entity stands for and how to write it. An & that does not start an entity, as in Tom & Jerry, is text.

A >= glued to a tag is split where text follows it, so <p>=x</p> is the text =x. After the outermost element it is still an error.

Breaking

We ran the published 0.1.134 and this build on the same programs. These compiled before and are refused now (E0012): } or > in text, // in text when the closing tag is on a later line, and // inside quotes in text, as in see "http://x.com" now. These were refused and compile now: an apostrophe, an unpaired ", \, /*, ;, # or a backtick in text, and = right after a tag. Any non-ASCII character in JSX text (é, ’, —, an emoji) crashed 0.1.134 with exit code 101 and compiles now. An entity was E0001 and is E0012.

Same program, different output

Some programs compile under both versions and emit different TypeScript. In each case the new output is what Babel's JSX whitespace rule gives:

  • Whitespace on one line between or around children is kept as a child. <p>{first} {last}</p> renders John Doe; 0.1.134 dropped the space and rendered JohnDoe. The same goes for <b>x</b> <i>y</i>, a space before </p>, and <p> </p>. Whitespace that contains a line break, like the indentation between tags, is still dropped.
  • Text over several lines in a module-level const is one child, "a b". It was two, "a", "b", which rendered as ab. Inside a function it was already right.
  • A pair of " across tags, as in say "<b>hi</b>" now, gives the <b> element. It used to be one string with the markup inside it.

None of these shapes occurs in the repository: every .glyph file in it and all 32 example apps emit byte for byte what 0.1.134 emitted. Our release review found the whitespace case, so before upgrading look in your own components for spaces that sit on one line between a } or > and the next { or <, and between a tag and an {expression} it holds.

Also fixed

A character the lexer does not accept, such as é in code outside a string, crashed glyph check with exit code 101 in 0.1.134. It is reported as an error at that character now.

0.1.134

November 2026 Link
This release changes how the parser reads a file and nothing about what a program means.

This release changes how the parser reads a file and nothing about what a program means. It is the groundwork for reading JSX text as text in 0.1.135, which today goes through the ordinary token lexer: that is why <p>don't stop</p> does not compile and // inside JSX text is read as a comment.

The lexer runs on demand

The whole file used to be split into tokens before parsing started. The parser now asks the lexer for each token as it needs one, and the lexer can resume from any point in the file. A lex error waits until the parser reaches it, so a lookahead that strays into one backs off without failing.

For every program that compiles, nothing changes. We checked that by running 0.1.133 and 0.1.134 on every .glyph file in the repository and on all 32 example apps, built as projects: the emitted TypeScript (2795 files for the single files, 616 for the apps) and the glyph fmt output are byte for byte the same, and no exit code changes.

Changed: which error you see first

A file with two errors reports the first one the parser reaches. Before, a lex error (an unterminated string, a stray character) was always reported first, even when a parse error came earlier in the file. So x = 1 # 2 in a function body used to report the # (E0001) and now reports the missing mut (E0008), which is the earlier mistake. The program fails either way; the message is what changed. One file in our test corpus changed this way, and it turned out to hold a second error the old order hid.

One case reads worse than before. When the parser looks ahead to decide what it is reading and runs into a lex error, it backs off and tries the other reading, and that reading can fail on code that is fine. In let x = f<a, "\q">(x) the invalid escape \q used to be reported; now the parser reports an unexpected ,, because it read f < a as a comparison. If an error points at code that looks correct, look for a bad string or character further along the line. It is filed as G329.

This release is not breaking: no program that compiled stops compiling, and no exit code changes.

json.parse never casts

read.glyph 
fn read<T>(s: string) -> Result<T, Array<Issue>> {
  return json.parse(s)
}

let user = read<User>("42")   // Ok, and then a crash

That program passed glyph check and tsc in 0.1.132 and crashed on the first field read. The emitter wrote json.parse(s) with no type argument, and tsc inferred T from the return type, which made the unchecked read a cast with no as anywhere. A call with no type argument is now emitted as json.parse<unknown>(s), so tsc refuses it there, at a let annotated Result<User, ...>, at an argument and in a record field. glyph check --no-tsc does not refuse an unknown value where another type is declared yet; that is 0.1.158.

json.parse<T> with a T nothing can check at run time is E0304: a type parameter, an extern_ts or package type, an interface, Result, a generic union, an Option, Nullable or Record of one, or a generic record applied to one (Pair<Shape>, whose check tested a only for being there). The note says which. A container of unknown is checked by its shape, so json.parse<Array<unknown>>("{}") is an Err. An Array alias imported from another module validates when its body names types that module declares. If it names one the module imports, that is E0304 for now. It used to look the name up in your module, and validate against your own User if you had one. Assigning json.parse to a variable gives you the unchecked read: let p = json.parse takes no type arguments.

?. on an Option or a Result

An Option and a Result are never null, so ?. on one never skips anything; it reads off the wrapper. An agent writing csvql wrote bind_agg(...)?.label meaning "propagate the error, then read the field", and the error was not propagated. That is E0236 now, with help that says to bind first (let a = bind_agg(...)?) or to match. A plain . on them is still unchecked; that is 0.1.139.

Methods of arrays and strings

The checker knows what xs.indexOf(2) and s.trim() return, from a table generated out of TypeScript's own declarations and checked for drift in CI. A method read without calling it, let up = s.toUpperCase, is E0234: the read loses its receiver and throws when called. .bind(s) is refused the same way; write fn() -> string { return s.toUpperCase() }. Type arguments on a function you stored in a variable are read now: let g = id then g<number>("x") is an error, as it is on id itself.

The editor and agents

glyph/applyEdit checks every module of the project, not just the edited file, so an edit that breaks an importer is refused, and the other files' diagnostics come back under elsewhere. An edit can span files through the new changes form, checked as one. A pre-existing error elsewhere whose suggestion the edit happened to change (adding an export rewrites another file's "did you mean") stays pre-existing. glyph fix repairs a misspelled string-literal arm the way it repairs a variant, and declines when the repair is not determined: when the error that lists the missing case belongs to another match, or two arms would take the same value.

Fixes

glyph fmt cut a run of spaces at the edge of JSX text to one, which changed what the page renders; it writes such a text as one string child now, and formatting leaves the emitted TypeScript byte for byte the same. It also moved a comment written between the operands of a multi-line expression below the statement; the comment stays with its operand. A match with no arms crashed the playground. An alias is the type it names, however you import it

pub type Page = Doc was already a second name for Doc. Written through a namespace, pub type Page = a.Doc, it was a different type: Page and a.Doc did not match, Page.parse did not exist, and a misspelled field passed. Reading through a Nullable

note.glyph 
pub fn label(n: Nullable<Note>) -> string {
  return n?.name ?? "none"
}

n?.name is now checked against Note's fields. Its value is the name or JavaScript's undefined, and Glyph has no type for undefined, so it can only be the left side of ?? or compared with ==. Anywhere else, such as a let or a "${...}", it is the new E0235. That catches "${n?.name}" printing the text "undefined", which tsc accepts. n.name without the ? is E0235 too.

A match arm for a string outside its union is E0220. xs.length is a number. A record where Record<string, V> is declared is compared field by field. kinds.type works as a type name.

The editor

The emitter's errors no longer disappear while you type; they move with your edits until the next check. Editing one file refreshes the other open files that import it. For agents, glyph/applyEdit now refuses only what an edit introduces, warnings included, and returns what the file already had under preexisting. So ok: true no longer means the file is clean; it means the edit introduced nothing, and the file is clean only when preexisting is empty too. While the file has an error, the warnings and the emitter's checks do not run, so an edit to it can add one of those and still get ok: true (G313). It still checks only the edited file, so glyph check remains the authority for changes that affect other modules.

In the editor protocol: glyph/applyEdit answers ok: true for an edit that introduces nothing to a file that already had a diagnostic, where 0.1.131 answered ok: false. The record was accepted and the read was not: e.type was E0002, because type is a reserved word. A JSON discriminator is usually called exactly that. view.glyph 
<match value={props.load}>
  <case Loading><p>loading</p></case>
  <case Loaded({ users, total })><p>{total} users</p></case>
  <case Failed(message)><p>{message}</p></case>

The bindings are typed, and a case that only matches some values of its variant does not count as covering it. bind= is now E0231, and its help writes the pattern for you.
