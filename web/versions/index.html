Versions & changelog

What changed, newest first.

Glyph is an early preview and moves fast. Every release is here with what it fixed and added, so you can see what is in the version you're running and what changed since.

Stability, pre-1.0: the language can still change between 0.1.x releases. We hold two lines: your code stays runnable (it always compiles to plain TypeScript you own and can keep if you stop using Glyph), and when syntax changes we aim to make glyph fmt migrate it for you. The full policy is in docs/stability.md.

A release marked Breaking rejects code an earlier version accepted. Usually because the compiler started catching something it had been missing, which is the point of the language, but it can turn a green build red on an upgrade. Read that release's note before taking it.

The marker is applied only where both versions were run and the older one accepted the program. It is not inferred from how a note is worded, and an unmarked release older than 0.1.99 has not been tested rather than been found safe. Every release from here on states which it is.

0.1.173

Latest Breaking 24 Nov 2026 Link
A generic bound is resolved, and a bounded T is checked as its bound

Glyph never resolved the bound on a type parameter. fn f<T: Nope>(x: T) -> T passed with no error even though Nope does not exist, and inside the function a T: Named was treated as if nothing was known about it. So x.nmae on a T: Named passed, and returning a T: Named where an unrelated Other is declared passed too. Only tsc caught these.

Now a bound resolves like any other type name: an unknown name is E0103, and l.Nope through a namespace is E0105. An import used only in a bound no longer draws a false "unused import" warning. A circular bound such as <T: T> or <T: U, U: T> is the new E0114, which tsc also refuses. A bound that refers to its own parameter, such as T: Cmp<T>, is still legal.

Inside its function, a bounded T passes where T or unknown is declared, and everywhere else it is checked as its bound would be. Member reads, method calls, index reads and loops over a T: B are checked against B. One false refusal goes: a Box<T> with T: Named where Record<string, Named> is declared.

Calls that pass the wrong type to a bounded parameter, such as label(5) where label<T: Named>, are not checked yet. That is 0.1.179. A generic interface's members are not checked on a value either (G461), so a bound like T: Cmp<T> does not yet guarantee anything about x.cmp(y).

Breaking

Yes. fn c<T: Nope>(x: T) -> T, a T: Named returned where Other is declared, and <T: U, U: T> each exit 0 under 0.1.172 and 1 under 0.1.173. Across 286 tracked programs the only change is the new test case for circular bounds.

Breaking 23 Nov 2026 Link
Inside a generic function, its own T is a type of its own

Glyph's checker did not hold a generic function to its own type parameter. Inside fn g<T>(x: Array<T>) -> Array<string>, return x passed, and so did return 5 where T is declared. Only tsc refused them, so the editor, the MCP tools and the applyEdit gate let them through. Building on 0.1.171, which records the declaration that owns each type parameter, the checker now decides a function's own T wherever that function checks a value.

A T stands where T, unknown or Nullable<T> is declared, and nowhere else. An Array<T> returned as Array<string>, a number returned as T, a U passed where T is declared, and f(5) with f: fn(T) -> T are now E0204 or E0211. A parameter a callee leaves unbound is not yours to decide and stays open, as before. A T field where Record<string, Nullable<T>> is declared is now accepted, which was a false refusal.

Two edges remain. A bounded parameter such as T: Named is decided where T is declared, but not yet as a value, because bounds are not resolved; that is the next release, 0.1.173. And a function's last expression is not yet compared with its declared return type at all, so fn f<T>(x: T) -> string { x } still passes; that is 0.1.174.

Breaking

Under check --no-tsc only. Every new refusal is one tsc already makes: fn g<T>(x: Array<T>) -> Array<string> { return x } exits 0 under 0.1.171's --no-tsc and 1 under 0.1.172, and full check was red on both. Across 285 tracked programs nothing changed.

23 Nov 2026 Link
Each type parameter knows the declaration it belongs to

Glyph's checker compared type parameters by name alone, so the T of one generic function could be mistaken for the T of another. With type One<T> = { v: T, } and fn wrap<T>(xs: Array<T>) -> One<T>, a function returning wrap([]) where Record<string, string> is declared was refused with "found One<?>", and inside a generic function whose own parameter was also called T the callee's T was read as the caller's. tsc accepts both.

Now every type parameter carries the declaration that owns it: the function, component, type or interface that declares it, a stdlib function for the stdlib's rows, and the union for Option and Result. Parameters are compared by owner and name. The answer is the same whether the callee is local, imported by name, reached through a namespace or held in a const. With 0.1.170's alias expansion, the same holds through a second name, and one more false refusal goes: Record<string, Same<T>> where a field of type T is returned.

This release adds no refusals. Across 285 tracked programs the output is byte-identical to 0.1.169 and 0.1.170. The next release uses the owner to decide a function's own type parameter.

Not breaking

Every change removes a refusal that tsc does not make.

Breaking 23 Nov 2026 Link
A second name for a type gives the same answer as the plain spelling

Glyph treated a type alias as a type with its own identity, even when its body was just another type. So type Id = string and type Name = string could not be passed for each other, Maybe<Note> (with type Maybe<T> = Nullable<T>) was refused where Nullable<Note> is declared, and L<string> (with type L<T> = Array<T>) was refused where Array<string> is declared. tsc accepts all of these. In the other direction, type Same<T> = T hid mismatches: a number passed where Same<string> is declared went through.

Now a declaration whose body is a primitive, unknown, a type parameter or a generic application is read as that body, with its arguments filled in, before two types are compared. Records, unions, extern_ts, typeof, function types and refinements with where keep their own identity. The answer is the same for an alias declared in another module, imported by name or through a namespace. Diagnostics still name the type as you wrote it.

An alias that refers to itself, such as type F = Array<F>, is not expanded and keeps the treatment it had before. Comparing two such types by their shape is G455.

Breaking

Under check --no-tsc. The new refusals are all ones tsc already makes: a number where Same<string> is declared, an Array<number> where type Strs = Array<string> is declared, and the same through records and imports. Several false refusals go away. One refusal that goes away was a real one: W<G> where Array<number> is declared, with type W<X> = Array<X> and type G = Array<G>, was refused only because W had its own name; tsc still refuses it. Across 285 tracked programs nothing changed.

Breaking 23 Nov 2026 Link
An escape inside the ${} of a "..." string is a parse error

A nested string literal inside the ${} of a "..." string could only be written with escapes, as in "a${f(\"x\")}". That spelling existed to get around the rule that says to bind such a value with let first. It also left every position after the escape a few bytes early, so 0.1.165 had to stop glyph fix from touching anything there.

Now a backslash inside the ${} of a "..." string is E0002, pointing at the escape, and the help is written from your code:

[E0002] `\"` is an escape inside the `${}` of a `"..."` string, which Glyph does not allow
Help: ... Bind the value with `let` and interpolate the name: `let label = x + "é"`, then `"a${label}"`. Or write the whole string as `"""a${x + "é"}"""`, which reads a string literal inside `${}` as written.

Triple-quoted strings are unchanged, and so is an escape outside the ${}, such as "a\n${x}" or "\${x}". When the text around the ${} holds an escape, the help names the """ form only in words, since a """ string would not decode it.

Two related changes. glyph fmt no longer rewrites a one-line """ template into the "..." spelling; it used to turn valid code into the form this release refuses. And with that region gone, the guard that stopped glyph fix after an escape is removed, so a rename inside a """ interpolation that holds an escape now applies instead of being declined.

Breaking

Yes, under full check as well as --no-tsc: "a${f(\"x\")}" exits 0 under 0.1.168 and 1 under 0.1.169. No tracked program had such an escape, so nothing in the corpus changed.

Breaking 23 Nov 2026 Link
Writes to a Set, Store or Deque are mut statements, like array writes

Since 0.1.160, xs.push(4) has to be written mut xs.push(4), so grep -n "^\s*mut " finds every change to an array. The stdlib Set, Store and Deque were the exception: seen.add(x) and hits.set(n) changed state with no mut line. 0.1.163 gave the checker their types, and 0.1.166 typed values held in an unannotated const. Now their writing members follow the same rule:

[E0240] `seen.add("a")` changes `seen` in place, and a call that changes a value is written as a `mut` statement
Help: write `mut seen.add("a")`, so `grep "^\s*mut "` finds every change to `seen`

The writing members are Set.add and remove, Store.set and update, and the four push_ and pop_ members of Deque. Readers such as has, get, peek_front and len are not, and putting mut in front of one is E0241. Every decimal.Decimal method returns a new value, so mut d.add(e) is E0241 too, with help to write mut d = d.add(e), or to bind a new name when d is a const. sqlite.Db calls change state outside the program and are judged in neither direction.

The help depends on what the value is used for. let had = seen.remove(1) is told to read seen.has(1) first, and a pop_front used as a value is told to read peek_front first. A write to the set or array a Store holds goes through mut st.update(...). glyph fix inserts the mut where the value has nowhere to go, and now also turns let _ = q.pop_front() into mut q.pop_front(), for arrays as well.

Which members write is checked twice. Every method of each type has to be classified, and node calls each one on a fresh instance to confirm the split. A write through an interface that names the method (interface Adder { add: fn(number) -> void, }) is not covered yet; that is G448, and D5 lists it.

Breaking

Yes, under full check as well as --no-tsc: a bare seen.add("a") and a mut d.add(d) on a Decimal exit 0 under 0.1.166 and 1 under 0.1.167. Seven example apps had 43 such writes, migrated in the same change; across 285 tracked programs nothing else differs.

Breaking 22 Nov 2026 Link
An unannotated const has the type of its value

Glyph's own checker gave a module const with no annotation no type at all. So const ITEMS = [1, 2] followed by ITEMS.push(3) slipped past the mut rule, let x: string = CFG.n on const CFG = { n: 1, } passed, and a store.create(0) held in a const was invisible to the checks 0.1.163 added. Only tsc caught any of it, so the editor, the MCP tools and the applyEdit gate let it through.

Now an unannotated const has the type tsc gives it. A string literal that is the whole value keeps its literal type, so const MODE = "read" still passes where a "read" | "write" is declared. Literals inside an object or array widen, so CFG is { n: number } and ITEMS is Array<number>. A value the checker cannot type stays untyped. An imported pub const gets the same type whether it is imported by name or through a namespace, and hover and the MCP tools report it.

That makes ITEMS.push(3) E0240, the field reads above E0204, and a Set, Store or Deque held in a const is judged the way it is in a let. Breaking

Yes, under full check as well as --no-tsc. ITEMS.push(3) on an unannotated const exits 0 under 0.1.165 and 1 under 0.1.166, and so does FOUND ?? 0 with const FOUND = array.find(...), which 0.1.162's rule now reaches. 22 Nov 2026 Link
Positions inside ${} point at the text they name

Every position inside a ${} was off. In "n=${b.nik} end", E0210 underlined {b.ni instead of b.nik, because each interpolation was placed from the opening quote plus its index in the decoded string, which skipped the quote. An escape, a \${ or a non-ASCII character earlier in the string pushed it further. The editor's ranges, hover and go-to-definition inside a template were off by the same amount, and so were the ranges agents edit against.

The lexer now records which source bytes produced each character of a string, and each interpolation is placed at its exact bytes. Underlines, hover, definition and glyph fix land on the right text after an escape, a \${, accented text, an emoji or a line break, in plain and triple-quoted strings. A one-letter typo inside a template is now renamed by glyph fix instead of declined.

It also fixes a crash. A diagnostic inside a ${} after an emoji made 0.1.162 and 0.1.163 panic with "end byte index ... is not a char boundary" (exit 101). It is now reported normally.

One case is left: an escape written inside the interpolation itself, such as "a${f(\"x\") + zz}", still leaves later positions early, and glyph fix declines there. That spelling only exists to get a nested string past the rule that says to bind it with let first, so 0.1.168 makes it a parse error (G441).

Not breaking

Nothing that compiled before is refused. Across 283 example apps, files, catch cases and test programs, every diagnostic's code and message is the same as on 0.1.163; four positions move by one column, all inside a ${}. The emitted TypeScript is byte-identical; source maps change only inside interpolations.

Breaking 22 Nov 2026 Link

An Option and a Result are tagged objects at run time, never null or undefined. So let v = array.find(xs, f) ?? 0 never used its default: v was the Option itself, and ${v} printed [object Object]. Both Glyph's checker and tsc passed it. 0.1.161 steered every lookup onto Option, which made this spelling more likely, so it is refused now, with the same code as ?. on these types:

[E0236] `??` on an `Option<number>`: an `Option` is never null or undefined, so `?? 0` never applies and the value is the `Option` itself
Help: Open it with `match u { Some(n) => n, None => 0 }`

The type of the expression changes too, so the fix checks the file again after each rewrite and puts it back if a new error appears. Positions inside a ${} are reported one column early. In 0.1.161 two fixes wrote at those positions, and every check passed afterwards. The E0242 rewrite turned "t=${xs.find(f) ?? 0}" into t=$match array.find({x, ... inside the string, and the field-rename fix turned "v=${b.name} w=${b.nikc}" into b.nickc. Now the rewrites decline inside a ${} and the help says to bind the value with let first. Every fix rule also re-reads the text it is about to replace and declines if it does not parse to the expression the fix was planned against. The position bug itself is G435, scheduled for 0.1.164.

Breaking

A ?? on an Option or Result that cannot be absent now fails to compile, under full check as well as --no-tsc. The probe with array.find(...) ?? 0 and its neighbours exits 0 under 0.1.161 and 1 under 0.1.162. Across the 285 example apps, standalone files, catch cases and test programs, the only new diagnostic is on the catch case for this mistake.

Breaking 21 Nov 2026 Link
A call that changes an array is written as a mut statement

Glyph has always said that grep -n "^\s*mut " lists every change a program makes. That held for assignment and not for methods: xs.push(4) and xs.sort(cmp) compiled without mut, so a helper like this one reordered its caller's array and nothing in the source said so:

fn smallest(xs: Array<number>) -> number {
  return xs.sort(cmp)[0]
}

Now the nine array methods that change the array in place (push, pop, shift, unshift, splice, sort, reverse, fill, copyWithin) may only stand as the whole call of a mut statement. Anywhere else the call is E0240, and the help is worked out from the call:

[E0240] `xs.sort(cmp)` changes `xs` in place, and its value is used here
Help: `array.sort(xs, cmp)` returns a sorted copy and leaves `xs` alone (with `import std/array`)

A bare statement such as xs.push(4) gets the help write `mut xs.push(4)`, and glyph fix inserts the mut for you. It only does that where the value has nowhere to go. The last expression of a function that returns a number is a value, so there the help says to write the statement and return explicitly, and fix leaves the file alone. The receiver has to be something mut x = ... could write to: a name, a field, an index. mut make().push(1) and xs.filter(f).sort(cmp) change an array nothing keeps, and are refused. A write through an optional field is spelled mut s.opt?.push(1), and a deferred change goes in a small function that defer calls.

The opposite mistake is E0241: mut in front of a call that changes nothing. mut xs.concat(ys) looked like a write and threw away the new array; the help says mut xs = xs.concat(...). The same goes for a function through a module, such as mut array.push(xs, 1).

Which methods count is a column in the method table generated from TypeScript's library. It is classified by hand, since lib.d.ts has no marker for it, and two checks keep it honest: every method must be classified exactly once, and node calls each array method on a fresh array to confirm the split.

What the audit does not cover yet: calls on npm values and anything else Glyph's checker cannot type, where mut is allowed and not required, and the stdlib Set, Store and Deque, whose receivers the checker does not type yet. That last one is G423, scheduled next.

Breaking

A program that calls one of the nine methods outside a mut statement, or puts mut before a call that changes nothing, now fails to compile. The smallest such program, with xs.push(4), let n = xs.pop() and the helper above, exits 0 under 0.1.159 and 1 under 0.1.160 with check --no-tsc. Across the 394 example apps and standalone files, the only new diagnostic is on the catch case for this mistake.

A keyword used as a type, like fn f(x: match), says it is reserved instead of giving a generic parse error.

The editor shows what glyph check shows

The language server stopped after the type checker, so the emitter's errors (E0302 to E0305, including an unverifiable parse) appeared in glyph check and the MCP tools but not in the editor. The editor now shows them. The checker's errors still arrive on every keystroke; the emitter's follow once you stop typing for 300 ms, and straight away when a file is opened or saved. While you type they drop out and come back at the pause. The editor still does not run tsc, the @example gate or the missing-module check (E0104), so it shows what glyph check --no-tsc --no-test shows, not the full glyph check. Lint findings now appear as warnings, as glyph check reports them.

json.parse refuses what it cannot validate

Doc.parse(v) was already refused when a field of Doc has no runtime check. json.parse<Doc>(body) validates through the same check and was not refused, so it returned Ok for a field nothing had looked at. It is E0304 now, and so is json.parse_with(body, Doc.schema). json.parse<w.Doc> through import w used to compile to a cast and now validates, which changes what a running program gets back (see below). Two forms still cast without validating: parse<Doc> through import std/json { parse }, and a type argument wrapped in Option, Nullable or Record.

Types the checker used to skip

Explicit type arguments on your own generic functions are used: id<number>("x") is an argument mismatch. A record where a Result, Option or Array is declared is a type mismatch, the reverse of 0.1.130's rule. A match over http.RedirectPolicy or log.Level compiles without an else, and a missing value is named. n.toFixd(2) on a number says "did you mean toFixed", and a misspelled record field suggests the nearest field. A second name for an imported record, pub type Page = Doc, has a working Page.parse; written through a namespace, pub type Page = a.Doc, it still does not (G302).

Some of this is partial. A wrong number of explicit type arguments is still left to tsc, and so are type arguments on a function stored in a variable. Record<K, V> where a declared record is the value is left undecided.

This release is breaking, at compile time and at run time.

At run time: json.parse<w.Fine>(body) through import w returned Ok in 0.1.130 for a body with a key Fine does not declare, and returns Err here, because it now validates and a record is closed. The exit code does not change, so nothing tells you. Put @open above the type if the API sends keys you do not declare.

Under glyph check, these exit 0 in 0.1.130 and 1 here: json.parse<Doc>(body), json.parse<w.Doc>(body) and json.parse_with(body, Doc.schema) where Doc holds an extern_ts field; and let o: Option<number> = m where m is your own union | None | Some(number), which tsc accepts because the two emit the same TypeScript, and which Glyph refuses because a declared union is its own type (D49).

Under --no-tsc only, six programs that tsc already refused exit 0 in 0.1.130 and 1 here: a misspelled number member, a wrong explicit type argument, a record where a Result is declared, a misspelled RedirectPolicy literal, an HttpErrorKind returned as a ServerErrorKind, and RawPage.parse where type RawPage = Raw aliases an imported record holding an extern_ts field. A full match over RedirectPolicy goes the other way, from 1 to 0.

The preview announcement makes five claims of the form "TypeScript accepts this and Glyph refuses it". A review of the draft against 0.1.129 found two of them weaker than they read: one held only inside the module that declared the type, and one was refused by tsc rather than by Glyph. This release makes both hold, and fixes the things a newcomer would hit first.

An unverifiable parse is refused across an import

E0304 refuses Doc.parse(v) when a field of Doc has no runtime check, because the validator would report success for a value it never looked at. It only fired in the module that declared Doc. Called from a module that imported it, the same call compiled and returned Ok. The refusal now follows the record across modules, including records a field check hands off to.

Glyph's own checker refuses an unchecked boundary read

user.glyph 
let user: User = json.parse(body)

json.parse returns a Result, so this was always an error, but only tsc reported it. glyph check --no-tsc, the editor and the playground said nothing. It is E0204 now: a Result, Option, Array, Record or Nullable where a declared record or union is expected is a type mismatch in the checker. All five catches/ programs are now refused by Glyph itself, and all five reproduce in the playground.

Member reads on arrays and strings

xs.lenght on an array was left to tsc. It is E0210 with "did you mean length", checked against the members TypeScript's library declares for arrays and strings. A CI check compares those lists with the TypeScript the project pins, in both directions, so moving the pin to a release that adds a method fails CI until the lists catch up. A TypeScript newer than the pin can still have a member Glyph does not know yet.

Errors point at the expression

A tsc error in Glyph code used to underline the whole statement it came from: a wrong argument marked the entire let, and a typo in a JSX handler marked eight lines. The emitter now maps every expression it writes, so the caret lands on the argument. The emitted TypeScript is unchanged.

let where = 1 now says where is a reserved word instead of giving a generic parse error, and glyph llms lists the 32 reserved words. A match on string literals whose type the checker cannot see is E0232, which says that, instead of E0218 suggesting an else arm, which would have switched the check off.

The playground and the docs

The playground opens on a program it refuses, has a picker of the catches/ cases, and can share a program by URL. The docs check now compiles fences whose point is a tsc error, and fences that import zod, pg or mongodb against those packages' real types. E0400 to E0404 have glyph --explain pages, and a test requires every code the compiler can emit to have one.

This release is breaking. Bag.parse(v) on an imported record with an Array<unknown> field exits 0 under glyph check in 0.1.129 and 1 here. let s: Sized = xs, where Sized is the record { length: number } and xs is an array, exits 0 in 0.1.129 and 1 here, although tsc accepts it: a declared record is its own type, and Sized.parse(xs) already refused the array. Declaring interface Sized { length: number } instead keeps the program. A misspelled array or string member was already a tsc error; under --no-tsc it exits 0 in 0.1.129 and 1 here.

Breaking 2 Nov 2026 Link

Before announcing a preview I had two agents start from npx @glyphlang/glyph init with nothing but the shipped docs, one building a small React page and one a Node CLI. Both got to a clean tsc build. This release fixes what they ran into, and one bug the Node run found that matters more than any of it.

Examples now run in a module that imports an npm package

In a module that imported an npm package, a failing @example passed. The example gate builds a copy of the project in a temp directory, the package could not be found from there, and the test harness died before running anything. The runner took the absence of a failure as success. The copy now resolves packages from your project, and a harness that does not report a result for every example it was given fails the build as "not run". The same check now covers glyph bench, which reported zero benchmarks and exited 0 when its module threw.

<case> takes a match pattern

<case Loaded bind={items}> read a field called items whatever the payload was, so on a positional payload it bound undefined, and the checker never typed the name. A case now takes the pattern a match arm takes:

view.glyph 
<match value={props.load}>
  <case Loading><p>loading</p></case>
  <case Loaded({ users, total })><p>{total} users</p></case>
  <case Failed(message)><p>{message}</p></case>
</match>

The bindings are typed, and a case that only matches some values of its variant does not count as covering it. bind= is now E0231, and its help writes the pattern for you. The same change closed a hole in ordinary match arms: Loaded({ totl }) on a record with no totl field passed the checker and only tsc complained. It is E0210 now, listing the fields the record has.

glyph fix no longer writes match arms

On a non-exhaustive match, glyph fix used to add one arm per missing case that printed the case and exited the process. The program then passed every check, and the match counted as exhaustive in glyph query variants. The compiler knows which cases are missing, not what your program should do in them, so fix now reports them and writes nothing. The E0200 help also stopped suggesting an else arm.

The docs the agents needed

The agent docs (what glyph llms prints and glyph init copies) now show a whole browser page: the app module, the entry that mounts it, the index.html, and building then bundling with Vite. Both modules are compiled against React's types in CI. An HTTP recipe that imported a serve std/http does not export is fixed, and every std import written in those docs is now compiled by a CI check. The scaffold's .types README no longer tells you to write .d.ts files for packages that ship their own types, and the getting-started guide begins with glyph init.

glyph run -- in.json now runs the current project with in.json as an argument, and a new scaffold's start script is glyph run --, so npm start -- in.json works. In a project made before this release, change the start script to glyph run --.

Smaller fixes

A U+E000 character inside a string compiled to $, because the lexer used that codepoint as an internal marker; the scheduled fuzzer found it. The catches/ folder is down to five programs, each one the same program in TypeScript and Glyph, after a review found four that compared two different programs or that tsc also catches. Tests that need tsc or node now fail in CI when the tool is missing instead of quietly passing, and on their first run they found ten glyph gen dts tests that had been skipping: gen dts replaced the caller's NODE_PATH with the global npm root, so a TypeScript found only through NODE_PATH was reported missing. It now adds the global root after it.

This release is breaking. A bind= case, an arm naming a field the record does not have, a failing example in a module that imports an npm package, and a benchmark that throws all exit 0 under 0.1.128 and 1 here. One spelling changes meaning without an error: glyph run -- tools/other.glyph ran that file under 0.1.128, and now runs the current project with tools/other.glyph as an argument. Write the path before the --.

This release is about writing a React app in Glyph against real React.

This release is about writing a React app in Glyph against real React. The last attempt stopped at document.title, because browser globals are unresolved names in Glyph and nothing in the standard library reached the page. Now a counter and a todo list using React 18's own hooks builds, bundles with Vite and runs in a browser. It's in the repo as examples/apps/todo, and CI now drives it in headless Chromium and checks the text on the page.

The page, through the standard library

Three small modules. std/dom reads and sets the title, finds an element by id and gives you the page's address. std/storage wraps localStorage: a read is an Option and a write is a Result, because a full or blocked store is an ordinary failure in a real browser. std/console writes a line at three levels. An element is opaque to Glyph: you hand it to React, you don't poke at it.

main.glyph 
pub fn main() -> void {
  match dom.element_by_id("root") {
    Some(root) => createRoot(root).render(<App />),
    None => console.error("the page has no #root element"),
  }
}

Writing document or localStorage is still E0103, and the message now names the module to import.

A hook's pair, destructured

let [count, set_count] = useState(0) works now. The pattern can't test anything, so it always matches, and the length has to be provable: a written array is counted, an Array<T> is refused because it might be shorter, and a value from npm gets a satisfies clause in the emitted TypeScript so tsc checks it is really a pair. That makes const [user, host] = s.split("@"), which tsc --strict accepts, an error in Glyph (E0230).

Two formatter and parser fixes in JSX

glyph fmt trimmed JSX text, so <p>{n} left</p> came back as {n}left and the page read "2left". It now keeps every space JSX renders. Separately, text on its own line below an element kept its indentation in the output; it's dropped now, as in TSX. Neither fix changes the TypeScript emitted for any example.
