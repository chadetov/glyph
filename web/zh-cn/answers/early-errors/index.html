为什么这很重要

Glyph 编译成 TypeScript，然后用 tsc --strict 对输出做类型检查，所以 Glyph 没有建模的错误不会丢失。它会在下一个阶段出现，用生成文件的说法来表述：一个 TS1308 指向某个你从没写过的函数里的 await，或者一个 TS2366 说的是你没写过的 switch。

行号会映射回你的 .glyph，但解释不会。编译器就是在这个缺口处不再起到教学作用的。

所以 Glyph 能自行判定的每条规则都被提前了：

  • E0222async fn 之外的 await
  • E0223match 被当作值使用时不产生值的 match 分支
  • E0008没有写 mut 的赋值

每条诊断都会说出规则，引用背后的设计决定，并给出修改前后的对比。

不产生值的分支

在此之前，生成的 switch 会从自己的各个 case 中掉出去，text 的值是 undefined，而它的类型写的是 string。tsc 能发现其中一些形态，漏掉另一些。

现在只要位置可判定，Glyph 就会判定：let、mut、return，或者声明了返回类型的函数的末尾表达式。语句形式的 match 仍然把 X => {} 当作有意为之的空操作。

async fn 之外的 await

await 也是同样的处理。Glyph 没有用户可见的 Promise：async fn -> T 被 await 后得到 T，所以在其他任何地方使用 await 都没有东西可挂起。

glyph build，针对 `fn total() -> number { return await fetch_count() }` 
[E0222] `await` is only valid inside an `async fn`
   ╰─ Mark the enclosing function `async fn`, or call a non-async function here.

// before: no Glyph diagnostic, then
dist/main.ts:14:18 - error TS1308: 'await' expressions are only allowed
within async functions and at the top levels of modules.
详情 由哪个可调用体决定

这以前是生成文件上的 tsc 的 TS1308，现在是 E0222，由最内层的外围可调用体决定，所以 async fn 里的同步 lambda 是它自己的上下文，规则和 TypeScript 相同。 相反的错误，即没有任何地方 await 的调用，是 E0238：单独一行的 save(1)、let _ = save(1) 和 let n: number = load() 都会被拒绝，因为调用开始了，程序却不等它就继续往下走。想要“发出后不管”的同步回调写成 task.detach(async fn() -> void { await save(1) })，它会在 stderr 上报告失败。

没有 mut 的赋值

第三个规则，人们第一天就会违反。Glyph 会标记每一次修改，所以重新赋值一个绑定写作 mut x = e，引入一个绑定写作 let x = e。

E0008E0302E0303

单独的 x = e 以前报告的是 "unexpected token: Equals"，说的是一个字符而不是规则。现在它是 E0008，glyph --explain E0008 会说明这个标记为什么存在：值发生变化的每个地方都以 mut 开头，所以 grep "mut total" 能把它们全部找出来。

详情 ? 运算符、E0302 和 E0303

? 运算符从另一个方向得到了同样的处理。? 会展开为一个绑定加上一个提前 return，放在它所在语句的前面，所以它需要一条可以展开进去的语句。它可以用在 let、return、参数中，现在也可以用在 match 分支体里。在不能使用的地方，报错会说明是哪个位置，以及怎样先绑定出来（E0302 和 E0303），而不是声称这个运算符尚未实现。

更糟的情况：tsc 也没报错

tsc 的错误报在错误的位置令人烦恼。而一个意思已经变了的程序却构建通过，才是真正的问题，Glyph 就出现过一个。

你声明的每个顶层名字都会原样进入生成的模块，包括标签联合的变体构造函数，所以一个名为 Error 的变体会在模块顶层生成 export function Error(...)。编译器在它下面写的 new Error(...) 随后调用的就是你的变体。

glyph build，针对带有 `Error` 变体的联合类型 
[E0110] `Error` cannot name a type, variant, or function: the emitted module
        references the JavaScript global `Error`, and this declaration would
        shadow it
 5 │   | Error(string)
   │     ──────┬─────
   ╰─ Rename it (e.g. `Error` -> `Failure`). The name is legal TypeScript, so
      nothing downstream catches the rebinding.

// before: no Glyph diagnostic, then, twenty lines later
dist/main.ts:31:12 - error TS2345: Argument of type 'string' is not
assignable to parameter of type ...
E0110E0111E0109
详情 type Key = string | number、受保护的名字列表、E0111

type Key = string | number 是同一个缺陷，只是看起来更友好。在 Glyph 中，A | B 声明的是一个标签联合，其成员是变体构造函数，所以这一行声明了名为 string 和 number 的变体。它能编译，能通过 tsc --strict，并生成了一个 export const number，遮蔽了 prelude 中的 number 命名空间。直到后来某次 number.to_string 调用失败之前，什么都没有报错。

报错范围是声明本身，也就是需要改名的地方。受保护的名字列表来自代码生成器，而不是一份通用的 JavaScript 全局名字列表，并且有一个测试会 grep 代码生成器，一旦出现新的全局引用却没有对应条目就失败。这个测试才是关键：int 发布并开始生成 Number.isInteger 之前，Number 一直是无害的，这个问题当初就是这样进入了一个版本。Date、Math 和 JSON 仍然可以使用，因为 Glyph 生成的代码从不提到它们。

原始类型联合的情况有自己的错误码 E0111，因为只拒绝而不解释，什么也教不会。它会说明这一行实际被解析成了什么，指向具名变体，并给出 extern_ts("string | number")，用于你在边界上需要原始 TypeScript 联合类型的情况。Glyph 不允许你使用的每个名字都列在 docs/reference/reserved-words.md 中：32 个关键字、E0109 背后的 33 个 TypeScript 保留字，以及遮蔽列表，每一项都写明了这个名字被占用的原因。

需要说清楚这不能做到什么。你仍然不能把类型或变体命名为 Error，发现这个问题的那个电子表格应用也因此把一个变体叫作 Cellerr。它原本想写的程序仍然写不出来；变化在于，编译器现在会在声明处直接指出这一点，而不是让构建通过却表达了别的意思。

详情 为什么不直接让这个名字可用

要让这个名字可用，就得在进入 TypeScript 时对 Glyph 名字做改写，这会改变堆栈跟踪、对 dist/ 的 grep 以及手写的 extern/ 适配层所看到的内容，所以这不是一个可以悄悄打上的补丁。

错误的报错比没有报错更糟

遮蔽列表最初只包含代码生成器作为值写出的名字，漏掉了它作为类型写出的名字，而这造成了整个问题中最尖锐的一个版本。

glyph build，修改前：十五条这样的报错，没有一条靠近原因 
dist/corpus/infer_output.ts:52:9 - error TS2353: Object literal may only
specify known properties, and 'code' does not exist in type 'Issue'.
glyph build，现在 
[E0110] `Issue` cannot name a type, variant, or function: the emitted module
        references the Glyph prelude global `Issue`, and this declaration
        would shadow it
   ╰─ Rename it. The name is legal TypeScript, so nothing downstream catches
      the rebinding.
详情 Issue 为什么会冲突，以及 Record

每个描述符的 parse 都返回 Result<T, Issue[]>，所以无论你写没写，生成的模块里都会出现 Issue。如果在你自己的模块里声明 type Issue = { path: Array<string>, message: string }，你的声明就会胜出，生成的 Issue 对象带着一个你的类型从未听说过的 code 字段，构建失败时给出的是一个关于生成代码的 tsc 错误，位置指向别处。

Record 也在同一时间加入了列表，归在 JavaScript 全局名字下而不是 prelude 名字下，因为它是 TypeScript 内置类型，归错了会让报错在名字来源上说错话。grep 代码生成器的那个偏差测试现在也覆盖了环境类型，而且它必须学会在类型位置上识别 Issue[]，这正是这个问题进入版本的原因。Schema、Component 和 Option 仍然合法，依据的是让 Date 可用的同一条规则：代码生成器只是因为你在注解里写了它们才会写出它们，所以声明其中一个不会遮蔽任何东西。

归咎于 match 的导入

这一类中的另一个是导入。本地导入路径从构建根目录解析，也就是你交给 glyph build 的那个目录，而不是从发起导入的文件所在目录解析。

glyph build examples/apps，针对 csvql/ 中的 `import catalog` 
[E0104] unresolved import `catalog`: no module `catalog` under the build
        root `examples/apps`. There is a `csvql/catalog.glyph` under the
        root; a local import path is resolved from the build root, not from
        the importing file's directory (D15)
   ╰─ Build that module's own directory as the root, or spell the import path
      as it reads from the root.

// before: no import diagnostic, then
[E0218] non-exhaustive match on string   // on a match over all four values
详情 它以前报告什么，以及它如何避免误报

构建一个外层目录树时，import catalog 什么也找不到，而直到现在都没有任何提示。类型退化成 unknown，对它的 match 丢失了要匹配的变体，你得到的是 E0218（match 不穷尽），而这个 match 其实覆盖了所有情况。照着那条报错去做，会给正确的代码加上一个永远不会执行的 else 分支。

这类检查的风险在于对没问题的东西也报错，而一个对每个 npm 包都喊“狼来了”的导入检查器，比它取代的沉默还要糟。所以构建会先收集不需要 .glyph 文件就能解析的模块名：<root>/.types/ 下和内置 Node 适配层中的每个 declare module "X"，以及项目 node_modules 中的每个包。这个列表上的名字永远不会被报告，即使某个本地文件恰好和它同名。如果项目根本没有 node_modules，编译器无法区分未安装的依赖和拼写错误，所以只报告它能证明的情况：根目录下确实有某个 .glyph 文件与之对应的导入。

解析本身没有变化。能构建的程序还是那些，失败的程序也还是那些。变化在于失败时报错会指出导入，而不是去指责两个文件之外的一个 match，全部改动就是这些：一个报错原因说错的编译器，会让你花一个小时去追查，之后的每条报错你也不会再轻易相信。

说出规则，而不是记号

同一个问题更隐蔽的版本，是一个正确却什么也没告诉你的错误。

glyph check，修改前与现在 
[E0002] parse: expected `)` after variant payload, found Comma
   ╰─ Add the expected token.

[E0010] a union variant carries one payload, but `Node` lists 6 positional
        fields
   ╰─ Glyph has no tuple payload. Put the fields in one record and name them:
      `Node({ /* name */: Color, /* name */: Tree<K, V>, /* name */: K,
              /* name */: V, /* name */: int, /* name */: Tree<K, V> })`,
      and destructure it by those names in a match arm.
详情 红黑树，以及修复方法如何用上你的程序

一个编写红黑树的智能体使用了每个 ML 系语言都有的位置参数构造函数，解析器在第一个逗号处停下，报出 “expected )”，并建议 “add the expected token”。在那里加一个 ) 只会得到另一个程序，而不是一个能工作的程序。Glyph 的变体只携带一个负载，含有多个字段的负载是一个记录。这两句话在输出中都找不到。

为了说出这些，解析器必须先读完整个列表再拒绝它，这也让它能够计数。报错范围标出全部六个字段，而不是它恰好停下的那个分隔符；建议的记录是根据变体名和文件中的六个类型构造的，所以修复方法用的是你的程序，而不是别人的示例。字段名是编译器唯一无法提供的东西，所以它把这些留作空位。

这条报错背后的规则是一个选择，而不是缺口。Node(Black, l, x, b, h, r) 是那种参数调换后照样能通过类型检查的写法，第四个位置对读者来说什么也没说明。记录写法给每个字段命名，match 分支只命名它用到的字段，这两者都是 grep 能找到的。

0.1.121 中检查器接手的另外两项

Order { id: "a", total: 1 } 是从 TypeScript 过来的人构造记录时会写的，而 Glyph 没有这种形式：值单独书写，类型写在注解上。

glyph check，针对按 TypeScript 方式构造的记录 
[E0013] a statement cannot begin on the line where
        `return Order` ends
   ╰─ Glyph has no `TypeName { ... }` construction form. Write the literal
      alone and put the type on the annotation: `let o: Order = { id: "a" }`.

// 0.1.121 to 0.1.145: [E0228] on `Order`, then [E0108] on the braces
// before that: [E0108] Warning: lint: unreachable code, and exit 0
E0228E0013自 0.1.146 起
历史 从 E0108 到 E0228 再到 E0013

编译器以前对这一行报告的是 E0108（不可达代码），而构建退出码为 0，因为这个名字解析成了类型，花括号被解析成 return 之后的一个代码块。把类型名当作值来写现在是 E0228，报错内容从声明中读取，所以记录会列出它的字段，标签联合会列出它的变体及负载形态，字符串字面量联合会列出它的字面量。Order.parse(raw) 和 Order.is(v) 仍然合法，因为类型自身描述符的接收者，是类型名唯一应该出现的表达式位置。

这修复了名字是类型的情况，但没有改变解析，所以 return h() { k: 2 } 仍然返回 h()，并带着一条警告丢掉花括号。从 0.1.146 起，在一条语句结束的那一行上出现的 { 在解析阶段就是 E0013，无论它前面的名字是什么，帮助信息给出同样的改写。从 0.1.149 起，这条规则覆盖所有语句，而不只是以花括号开头的语句：let s = "a" "b" 以前会绑定 "a" 并丢掉 "b"，return x as User 则是三条语句，因为 Glyph 没有类型断言。

代码块中的每条语句都要另起一行。

在声明为原始类型的地方出现容器

另一项是把 prelude 容器赋给原始类型。o: Option<int> 时，let x: string = o 在 Glyph 检查器那里没有任何报错，把 Nullable<int> 传给声明为 int 的参数也没有。

现在五种容器在两个方向上都有覆盖：Option、Result、Array、Record 和 Nullable 无论类型参数是什么，都绝不是 string、number 或 bool；Nullable<T> 与标量比较时会深入一层，针对 T 判定，所以 let v: Nullable<int> = 3 仍然正确，而 let v: Nullable<int> = "three" 是 E0204。

详情 只有 Glyph 能发现的情况，以及自 0.1.130 起的记录

Nullable 这种情况比其他几种更应该放在这一页，因为它是 tsc 无法判定的：生成的 const v: number | null = 3 在检查调用之前就收窄回了 number，所以一个本来为了让 null 可见而存在的边界类型，在声明为 int 的地方悄无声息地通过了，而 Glyph 检查器是唯一能发现它的地方。

接下来是同样这些容器与声明的记录或联合类型的比较。从 0.1.130 起，let user: User = json.parse(body) 是 E0204，期望 User，实际是 Result<unknown, Array<Issue>>。以前只有 tsc 会指出这一点，也就是说 glyph check --no-tsc、编辑器和 playground 在边界最需要写对的那一行上显示的是一个干净的文件。

数组或字符串上拼错的成员名

数组或字符串上拼错的成员名，是另一种以前要等 tsc 才发现的情况。xs.lenght 是 E0210，并提示 "did you mean length"，检查依据是 TypeScript 库为数组和字符串声明的成员，就像读取记录字段时依据它的字段来检查一样。参数没有写类型的回调里也是如此：参数取它所在位置期望的类型，所以在 users.map(fn(u) -> string { return u.nmae }) 中 u 是 User，拼写错误是 E0210。

tsc 本来也会拒绝这三种情况，所以运行它的构建本来就已经失败；变化在于检查器以及构建在它之上的一切会先看到它们。

从 0.1.133 起，还有三项

从字符串上取下的方法

详情 方法的类型从哪里来

Result 上的 r?.label 读起来像是“传播错误，然后读取字段”。实际上它是可选链，而 Result 永远不是 null，所以它从 Result 对象上读取字段，什么也没有传播。

未经检查的 json.parse

不带类型参数的 json.parse(body) 是未经检查的读取，得到 Result<unknown, ...>。把它写在声明为 Result<User, ...> 的地方时，tsc 以前会根据声明推断出 User，程序在第一次读取字段时崩溃。

0.1.122 中还有两项

type Mode = "read" | "write" 声明了一个有限的字符串集合，而 Glyph 检查器在把值与它比较时根本没有做任何比较。数字、bool、记录以及集合之外的字符串，都能通过 glyph check --no-tsc，只有未使用变量的警告，而 tsc 在生成的 TypeScript 上会拒绝其中每一个。

所以完整的 glyph build 在这一点上从未出错，但不经过 tsc 的四个地方会出错：--no-tsc、语言服务器、MCP 工具和 playground。

glyph check --no-tsc，针对一个列出其合法字符串的类型 
type Mode = "read" | "write"

let a: Mode = 3
let b: Mode = "rw"
let c: Mode = takes_mode(true)
let d: Mode = { x: 1 }
// before: four unused-variable warnings, exit 0
[E0204] type mismatch: expected `Mode`, found `number`
[E0204] type mismatch: expected `Mode`, found `"rw"`
[E0211] argument type mismatch: expected `Mode`, found `bool`
[E0204] type mismatch: expected `Mode`, found `record`
详情 联合类型如何比较

这就是 tsc 报告的那四条，在相同的四条语句上，而且不需要运行 tsc。这条规则把联合类型按它在运行时的本来面目看待，也就是一个 string，并在每个方向上向检查器提出相应的 string 问题，所以它继承了已有的、拒绝把记录或容器当作 string 的规则，而不是逐个形态重新陈述一遍。两个字面量集合按集合比较，所以更窄的联合类型可以放在声明为更宽联合类型的地方；别名链在两侧都会被追踪；导入的联合类型和本地的一样判定；Nullable<Mode> 会被展开，联合类型保持不变。

嵌套在记录字段或泛型参数中的联合类型，在 0.1.122 中留给了 tsc，在 0.1.123 中由 Glyph 判定。见下文。

0.1.123：值本身是哪个字面量，而不是它生成后的 string

type Mode = "read" | "write" 把集合放在声明上，而值上什么也没有，所以 "read" 是 string，["read", "write"] 是 Array<string>。

历史 0.1.122 放弃了什么

这让两个程序无法区分：在声明为 Array<Mode> 的地方 return ["read", "write"]，tsc 能编译通过；而对 xs: Array<string> 写 return xs，它会拒绝。0.1.122 选择不判定这种配对，而不是判错，这样保住了正确的程序，代价是放过了错误的程序：{ mode: "nope" } 对照 { mode: Mode } 不会有任何报错。

现在写出的字符串字面量具有它所写的那个单一字面量类型，数组字面量的元素类型是其各元素类型的并，写出的数组或对象字面量会针对声明的类型逐个元素、逐个字段地检查，所以诊断会指出那个字面量并给它加上下划线。

glyph check --no-tsc，针对容器内一层的字面量 
type Mode = "read" | "write"
type Cfg = { mode: Mode }

fn ok() -> Array<Mode> { return ["read", "write"] }
fn bad() -> Array<Mode> { return ["read", "nope"] }
fn wrong() -> Cfg { return { mode: "nope" } }
// 0.1.122: nothing, on all three
[E0204] type mismatch: expected `Mode`, found `"nope"`   (twice)
详情 字面量在哪里放宽，以及自 0.1.153 起的 Record 键

字面量在 TypeScript 放宽它的地方也会放宽回 string：在没有注解的 let 处，它生成的 TypeScript let 也以同样的方式放宽；以及在遍历写出的数组的 for 的元素绑定处。所以 let l = "read" 之后接 takes_mode(l) 在这里被拒绝，在那边是 TS2345。const 生成 TypeScript 的 const，保留其字面量，所以 takes_mode(CM) 在两边都能编译。通过名字传来的字面量类型不会被放宽，这是 TypeScript 自己的新鲜度规则。上面的每一条都是通过对等价的 TypeScript 运行 tsc --strict 确定的，而不是推理出来的。

从 0.1.153 起，Record 的键类型参数受到比 tsc 更严格的检查。TypeScript 把 Record<string, V> 写成一个索引签名，并在两个方向上都接受它与 Record<Mode, V> 互换。Glyph 两个方向都拒绝：开放的映射可能含有 Mode 之外的键，也可能缺少某个键；而被当作开放映射传出去的 Record<Mode, V> 可能被写入一个多余的键。要从一种转换到另一种，用一个 is 分支或 json.parse。

检查器还有两种形态什么也不说：Some(...) 里的字面量，因为 prelude 构造函数在这里还没有类型；以及绑定到无注解 let 的记录字面量，因为不会为对象字面量合成记录类型。

std/ 下的模块成了没有诊断的死代码

std/ 和 extern/ 指的是编译器自带的模块，解析器为导入保留了它们。但没有任何东西阻止项目文件声明这样一个模块。

glyph check --no-tsc，针对声明了 `module std/io` 的 src/io.glyph 
// before: glyph check: 2 module(s) checked, no diagnostics.  (exit 0)

[E0113] `std/io` declares a module under `std/`, a prefix reserved for the
        modules the compiler carries (D15)
 1 │ module std/io
   │ ──────┬──────
   ╰─ Rename the module to a path of your own (`io`, `app/io`).
详情 以前会发生什么，以及哪些路径被保留

在你自己的 src/io.glyph 中写 module std/io 能干净地编译，然后 import std/io { shout } 解析到了内置的存根，并报告 shout 没有被导出：你的文件从来没被读取。

前缀按完整的第一段匹配，所以 standard、externals/io、app/std 和 app/extern/helper 不受影响，在这两个前缀下的导入也和以前一样工作。

一个不产生任何诊断、也不运行任何代码的文件，是编译器能留给你的最糟的局面，因为它看起来没有任何问题。

0.1.122 中的第二项

解析器深度上限

第二项与 tsc 完全无关。解析器是递归下降的，没有深度保护，所以嵌套两千层的表达式会耗尽进程的栈，以退出码 134 中止。

glyph check，针对 `const x = ` 后跟 2,000 层嵌套括号 
// before: thread 'main' has overflowed its stack
//         fatal runtime error: stack overflow, aborting   (exit 134)

[E0011] this array literal nests deeper than the parser's limit of 64 levels
   ╰─ Name the inner levels: pull them out into `let` bindings, or into a
      `fn` that returns one of them, so no single expression, type or
      pattern is more than 64 levels deep.
详情 为什么这对语言服务器很重要

这在 glyph check 上很糟，在 glyph lsp 和 glyph mcp 上更糟，因为它们会读取根目录下的每个文件：一个病态文件就能让整个工作区的服务器崩溃。现在它是 E0011，在本会打开第 65 层的那个记号处报告。

上限是 64，这个数字是测量出来的，而不是随便选的。

详情 64 是怎么测出来的

最耗栈的构造是嵌套数组字面量，每一层在 release 构建中消耗 7,792 字节栈空间，在 debug 构建中消耗 8,810 字节，这是通过二分查找给定深度能够解析所需的最小线程栈得出的。解析器运行时最小的栈是新建线程的 2 MiB，也就是语言服务器工作线程得到的大小，64 层在更耗栈的构建中用掉的不到其三分之一。本仓库 343 个 .glyph 文件中最深的嵌套是 16 层。这个上限同样适用于表达式、类型、模式、代码块和 JSX 子节点，一千个并列的数组仍然可以解析，因为深度指的是单个构造的嵌套层数，而不是整个文件共用的额度。

当两个编译器都没错时

还有第三种形态，读起来最糟。Glyph 什么也不报，tsc 报告的内容是真的，而你写的程序没有问题。

出错的是两者之间的翻译。

poll.glyph，以及 0.1.89 之前 tsc 对它的报错 
fn classify() -> int {
  let done = false
  match done {
    true => { return 1 },
    false => { return 0 },
  }
}

// no Glyph diagnostic, then
[TS2678] Type 'true' is not comparable to type 'false'.
详情 tsc 为什么看到的是 false，以及遇到这个问题的应用

在 Glyph 中，一个绑定在整个生命周期内只有一种类型。TypeScript 会把绑定收窄成它最后看到的赋值，它的 boolean 是联合类型 true | false，所以 let done = false 到达 tsc 时类型是 false，生成的 switch 中 true 那个分支就没有东西可匹配了。

声明为字符串字面量集合的类型也以同样的方式失败，== 也是，只是报的是 TS2367：两条报错，两个错误码，一个原因。遇到这个问题的应用在轮询一个由定时器回调设置的标志，在 Glyph 没有可手动构造的 Promise 的情况下，这就是把基于事件的 API 变成一个值的做法。后来发现回调与此无关：四行没有回调的代码就能复现。

修复不是一条新诊断，因为没有什么可诊断的。代码生成器现在会在对值做区分的两个地方，重新写出检查器已经判定的类型：match 的被匹配值，以及 == 或 != 的两侧。

详情 仍会触发的检查，以及代价

每一侧都由它自己的类型决定，不管旁边是什么，所以两个绑定之间的比较和与字面量的比较一样被覆盖。

你需要的检查仍然会触发。m 是 Mode 时，m == "nope" 仍然会被拒绝，而且现在报错指出的是 Mode，而不是 m 碰巧持有的那个单一成员。在赋值处做这件事代码会更少，但会把这一点丢掉：在带注解的赋值不被接受的地方，转换到 Mode 的类型断言会被接受，而成员检查正是 Glyph 有意留给 tsc 的部分。

代价很小，但值得说明。类型断言既能确认类型，也能收窄类型，所以一个 Glyph 定为 bool、而 TypeScript 类型最终是 unknown 的值，现在能在 switch 以前报错的地方通过。两个类型仍然必须可比较，所以如果模型偏差大到真正有影响，比如 string 对 bool，就会报告 TS2352，而不是什么也不报。

同一个拼写错误，两种答案

拼错的标准库函数名，以前会因为导入写法不同而得到不同的答案，这种不一致会让你两个答案都不再信任。

具名导入，一直是 E0105 
import std/string { repeeat }
[E0105] import: `repeeat` is not exported by `std/string`
命名空间读取，0.1.72 之前 
import std/string
string.repeeat(s, 2)
[TS2551] Property 'repeeat' does not exist on type ... Did you mean 'repeat'?

现在两种写法都会经过导出列表，都会报告 E0105，指出缺少的成员及其所在模块。

详情 两种写法为什么不同，以及启用后发现了什么

第一种写法在解析阶段会对照模块的导出列表检查。第二种写法根本没有检查，所以落到了 tsc 那里，它看到的是对一个对象的属性访问，并以此作答。

这项检查一启用，就发现了一个没人在找的问题：一个测试夹具一直在调用 fs.write，而函数名其实是 write_text。它通过了好几个月，因为那个夹具在关闭类型检查的情况下运行，而编译器中没有其他地方会查看命名空间成员。导出列表现在是两种写法的唯一依据，所以另有一项检查让它与运行时实际导出的内容保持一致。那项检查写好之后，又被故意弄坏以确认它会失败，我们正是这样发现它的第一版一直在悄无声息地什么也没检查。

正在改进

  • 只有当 Glyph 的检查器知道某个调用的签名时，E0238 才能认出它是异步的
    详情

    E0238 只有在 Glyph 的检查器拿到调用的签名时才知道它是 async 的，所以来自 npm 包或 node 内置模块的 promise 仍可能被悄悄丢弃。传给 forEach、定时器、socket 处理函数或任何 fn(...) -> void 参数的 async 回调会被 E0211 拒绝，因为没有任何东西等待它。

  • 在调用之外混用 fn 和 async fn 会被拒绝，但只给出通用的消息
    详情

    在调用处，类型不对的函数会得到一条可以直接粘贴的帮助：传给 task.detach 的同步 tick 会被告知传入 async fn() -> void { tick() } 或声明为 async fn tick()。在 let 中绑定到 fn(...) -> void、被返回或存进字段的 async fn 也会被拒绝，但消息只说 expected `function`, found `async function`，修复留给你自己。

  • 允许顶层 await
    详情

    模块级 const 初始化表达式没有外围可调用体，所以顶层 await 是允许的，生成的 ESM 会执行它；Glyph 是否需要隐式的异步模块初始化，仍是一个开放的规范问题。

  • E0223 只有在函数声明了返回类型时才能判断末尾的 match，所以无注解 lambda 内的分支仍然会落到 tsc。
  • E0110 让你改名，而不是让你保留这个名字
    详情

    在遮蔽这一边，有两件事只做了一半。E0110 让你改名，而不是让你保留这个名字，所以 Error、Number、Object、Array 和 Promise 仍然不能用作类型或变体名。

  • E0111 阻止了 type Key = string | number 表达错误的意思，却没有给你正确表达的方法
    详情

    E0111 阻止了 type Key = string | number 表达错误的意思，却没有给你正确表达的方法：两个原始类型的联合在 Glyph 中除了 extern_ts 之外没有写法，而它的内容对 Glyph 自己的检查器是不透明的。非标签联合涉及穷尽性、运行时描述符和 is，所以这是一个类型系统层面的决定，尚未排期。

  • E0104 会出现在 glyph build 和 glyph check 中，但不会出现在编辑器中
    详情

    E0104 会出现在 glyph build 和 glyph check 中，但不会出现在编辑器中：LSP 分析文档文本时没有构建根目录，工作区文件夹也不是构建根目录，靠猜测只会产生这项检查本来要避免的误报。

  • 保留字参数仍然会被同一文件中一个无关的错误掩盖，因为收集阶段的失败会跳过本可以发现它的解析阶段。
  • 读取点类型固定只在正在生成的模块内部追踪类型别名
    详情

    此外，让 bool 或字符串字面量联合绑定保持可匹配的读取点类型固定，只在正在生成的模块内部追踪类型别名，所以一个模块中的 pub type Ready = bool 加上另一个模块中的 let r: catalog.Ready = false，仍然会以 TS2678 落到 tsc。字符串字面量联合在三种导入写法下都能跨模块覆盖，并且从 0.1.123 起，无论哪种写法，诊断都会指出声明（期望 Mode），而不是在其中一种写法下打印它的字面量集合。
