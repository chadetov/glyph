为什么重要

没有人会为了试一门语言而重写代码库。因为 Glyph 的输出就是 TypeScript，一个 .glyph 文件可以放进现有 TS/React/Node 项目的某个角落，导入同样的包，并导出给周围的 .ts 使用。

正是这条渐进的路径，让我们选择以 TypeScript 为目标，而不是发布一个新的运行时。

已安装的包自带类型

如果包已经安装，并且自带类型（或者有 @types/...），你要做的就只有这些。不需要存根，也不需要适配文件。

glyph build 会找到项目的 node_modules，并让类型检查器使用它，所以检查你代码的是这个包的真实类型，错误的调用就是真正的错误。

下面是直接使用 zod 的例子，没有任何手写的东西：

main.glyph 
import zod { z }

let user_schema = z.object({
  name: z.string(),
  age: z.number(),
})
let user = user_schema.parse(input)
print(user.name)
调用 zod 没有定义的方法 
module main

import zod { z }

pub fn main() -> number {
  // ZodString has no such method:
  let n = z.string().nonexistent_method()
  return 0
}

// [TS2339] Property 'nonexistent_method'
//   does not exist on type 'ZodString'.
//   mapped back onto main.glyph:7

glyph run 会针对已安装的 zod 执行同一个程序，所以这不只是类型检查：为类型检查器解析这个包的那一项配置，同样为运行时解析它。

不带类型、也没有 @types/... 的包，仍然需要你写一份声明，这就是 .types/ 文件夹的用途（与 TypeScript 已有的 .d.ts 机制相同）。

详情 子路径导入，以及从 .d.ts 得到经过校验的类型

子路径导入（pkg/sub）也会通过包的 exports 映射解析，所以子路径自己的类型也会被检查。

如果你想把一个库的形状变成一等的、经过校验的 Glyph 类型，而不是只做类型导入，glyph gen dts 可以把 .d.ts 实化为带描述符的真实类型：见每个 API 都要手写校验器吗？

由值派生的类型、JSX 展开和逃生口

由值派生的类型是一等的。JSX 属性展开（<input {...register()} />）也是一等的。

所以库永远不会迫使你手写适配文件。

对于 Glyph 仍然写不出来的少数 TypeScript 惯用法，extern_ts("...") 是作用域受限、可以 grep 的逃生口：tsc 会检查它，但要说清楚，它是信任边界，而不是经过运行时校验的边界（对 Glyph 不透明，返回的值是 unknown，需要自己收窄）。

详情 z.infer<typeof s> 是如何解析的

type User = z.infer<typeof user_schema> 可以直接使用：typeof user_schema 是对一个真实值引用的类型查询（拼错了会报未解析名字的错误），z.infer<...> 是普通的成员泛型类型。它会原样生成，由 tsc 化简，所以 u.name 是 string；校验来自 schema 自己的 parse，zod 本来就是这样工作的。

需要整段手写 TypeScript 时

有时逃生口不是一个类型或表达式，而是真正的运行时代码：一个 node stream 循环、一个 new Promise、一个 worker 线程。把 .ts 放在 <src>/extern/ 下，然后用 import extern/<name> 引用它。 

// src/extern/raw_server.ts   (hand-written TypeScript)
export function serve_raw(port: number, handler: (raw: string) => string): void { ... }

// src/main.glyph
import extern/raw_server { serve_raw }   // typed from the .ts; a wrong arg is a real tsc error

相对导入在 Glyph 源码中仍然是非法的（这是一条可检索性规则），所以 extern/* 是唯一保留的路径，grep -rn 'import extern/' 能找出你离开这门语言的每一处。

详情 放入输出、另一个方向，以及 node 适配层

构建会把 <src>/extern/** 放进输出目录并生成相对路径的导入，所以 tsc 会把 extern 和你的 Glyph 代码一起做类型检查，重新构建也不会把它清理掉。

它和简单的那个方向正好相反：.ts 文件导入编译后的 Glyph 代码，什么都不需要。常见的 extern（http 服务器、fs）不用安装任何东西，就能针对内置的 node 适配层做类型检查。

监视子进程，无需安装任何东西

内置的 node 声明包含了 child_process 的异步部分，而不只是阻塞的部分，所以一个在长命令运行时报告其输出的工具，可以用 Glyph 写，而不必写成 extern： 

module main

import child_process { spawn }
import std/io

pub async fn main(argv: Array<string>) -> number {
  let child = spawn("git", ["status", "--short"])

  // Ask for text and node decodes for you, holding back a character whose
  // bytes straddle two chunks. Decoding a raw chunk yourself does not.
  child.stdout.setEncoding("utf8")
  child.stdout.on("data", fn(chunk) {
    io.print("${chunk}")
  })
  child.on("close", fn(code) {
    io.println("git exited ${code}")
  })
  return 0
}

用 io.print 而不是 io.println：一个数据块是流的一个片段，而不是一行，一行可能分成两个数据块到达。

重载遵循 @types/node，所以普通的 spawn(command, args) 返回的管道不为 null，传入 stdio 后则可能为 null。在 stdio: "inherit" 之后读取 child.stdout，在这里是 TS18047，使用真实类型定义时也是 TS18047，而不是对同一个值给出两种说法： 

module main

import child_process { spawn }

pub fn main() -> void {
  let child = spawn("git", ["status"], { stdio: "inherit" })
  // [TS18047] 'child.stdout' is possibly 'null'.
  child.stdout.setEncoding("utf8")
}

修改适配层，下一次运行用的就是你改过的适配层

适配层是你会反复修改的文件，所以它必须算作源码。

glyph run 按源码的指纹缓存构建结果，这个指纹覆盖 extern/ 下的每个 .ts 和 .tsx，既看路径也看内容。

详情 什么会触发重新构建

修改、重命名、新增或删除其中一个，下一次运行都会重新构建并重新运行 tsc。符号链接的适配层会被跟随，所以放在源码树之外的 .ts 会按它的实际内容计算哈希。

正因如此，类型可以由适配层持有，而不必两个文件各自声明一份。从适配层导出这个形状，在 Glyph 模块中导入它，编译器在每次运行时都会让两者保持一致：

src/extern/web.ts 
export type WebResponse = {
  status: number;
  content_type: string;
  location: string;   // "" when not a redirect
  body: string;
};
适配层改了字段名，构建会指出来 
import extern/web { serve_web, WebResponse }

// location -> redirect_to in web.ts, nothing
// touched here, and glyph run stops:
[TS2353] Object literal may only specify
known properties, and 'location' does not
exist in type 'WebResponse'.
   ╰─ server:53:3
历史 0.1.44 之前的情况，以及不算数的文件

在 0.1.44 之前，指纹完全跳过 extern/，所以那次重命名会得到一次干净、通过类型检查的构建，运行的却是旧版本的适配层。extern/ 下不是 .ts 或 .tsx 的文件仍然不影响缓存，这是有意为之：适配层旁边的 README.md 会随它一起复制到输出目录，但没有任何东西会对它做类型检查或运行它，所以没有什么需要重新构建。

基于类的客户端：数据库和消息队列客户端

大多数数据库和消息队列客户端都是基于类的：你要写 new Kafka(...)、new MongoClient(url)、new Redis()、new Pool(cfg)。Glyph 的 new 正是为此准备的。

基于类的客户端（kafkajs） 
import kafkajs { Kafka }

let kafka = new Kafka({
  clientId: "app",
  brokers: ["localhost:9092"],
})
let producer = kafka.producer()
await producer.connect()
工厂函数式的客户端不需要 new 
import redis { createClient }

// createClient() is a function, so you
// just call it. No new, no wrapper.
let client = createClient()
await client.connect()
await client.set("k", "v")

它原样生成 TypeScript 的 new，由 tsc 对照包的真实构造函数检查，所以错误的参数就是真正的错误，未定义的被调用者会按名字报出来。

它只用于互操作：Glyph 自己没有 class，new 只能构造来自包、.types 声明或 extern_ts 的类型。

当前状态

现已提供

  • 导入任何 npm 包（包括带连字符的名字和作用域包）。
  • 已安装并自带类型（或有 @types/...）的包，不需要存根就能做类型检查和运行。
  • 基于类的客户端用 new 构造，由 tsc 对照真实构造函数检查；工厂函数式客户端直接导入并调用。
  • Node 内置模块开箱即可做类型检查
    详情

    Node 内置模块（fs、path、http、包含流式 spawn 的 child_process，以及其他模块）开箱即可做类型检查，安装 @types/node 后会自动加载它；CI 会针对该包的 latest 版本构建编译器自己的运行时，所以标准库依赖的声明不会与 node 的真实声明产生偏差。

  • 只有你的代码用到的声明暂时还不在这项检查的覆盖范围内，还有少数声明仍比 node 的更宽松。
  • 其他任何东西都可以用 .types/ 环境声明。
  • glyph gen dts 把 .d.ts 实化为经过校验的 Glyph 类型。
  • 输出干净的 .ts，你现有的 TypeScript 可以反过来导入。
  • import extern/<name> 引用 <src>/extern/ 下手写的 TypeScript
    详情

    需要整段手写 TypeScript 时，import extern/<name> 引用 <src>/extern/ 下的 .ts，它会和你的代码一起放入输出并做类型检查，并被 glyph run 的缓存跟踪，修改后会重新构建。

正在进行

  • 实化可以处理真实 SDK 中出现的各种形状，由值派生的类型也是一等的
    详情

    实化现在可以处理真实 SDK 中出现的各种形状（命名空间、跨文件以及别名/命名空间形式的重导出、子路径 exports、一等泛型），由值派生的类型（z.infer<typeof s>）也是一等的。

  • 剩下的主要 gap 是：未实化的包，其输出会对照它的 .d.ts 做类型检查，但除非你把它实化，否则不会做运行时校验。
  • 在 extern/ 这一边，glyph run 和 glyph build 的源码根目录不同
    详情

    在 extern/ 这一边，两个命令的源码根目录不同：glyph run app.glyph 以文件自己所在的目录为根，glyph build src/ 以你指定的目录为根。因此位于子目录中的程序会在两个不同的位置寻找它的适配层，在我们确定使用哪一个根目录之前，这样布局的项目需要让两个位置都能找到适配层。找不到时会明确报错。
