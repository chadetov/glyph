能。io.read_line 在完整的一行到达时就返回，不会等 stdin 关闭，所以 REPL、游戏循环或聊天客户端会先回应每一行，再读取下一行。在 0.1.62 之前它确实会等，这一点值得明说，因为它让所有交互式程序都无法实现。

为什么这很重要

只在输入结束时才返回的行读取器，其实是顶着行读取器名字的文件读取器。

用管道传入一个文件时它工作得很好，所以一直没人发现：仓库里每个读取 stdin 的应用读的都是管道。后来有人写了一个聊天客户端，它在用户输入时毫无反应，直到按下 Ctrl-D 才一次性打印所有回复。

历史 围绕它塑造的应用

那个应用最终是以回放录制好的 JSON 文件的会话回放器形式发布的，源码里有一条注释说明原因。另外三个应用也围绕同一个问题调整了形态，只是没人点明：扫雷无法在两步之间重绘，文字冒险游戏无法回应 look，REPL 在你挂断之前什么都不求值。

实际使用中容易踩坑的地方

  • CRLF末尾的 \r 会被去掉，所以 CRLF 文件和 LF 文件得到相同的行，你不用在 Windows 输入上调试一个看不见的字符。
  • 没有结尾换行没有以换行结尾的输入，仍会在返回 None 之前把最后一行交还一次，所以没有结尾换行的文件的最后一行不会被悄悄丢掉。
  • 被拆开的 UTF-8跨读取边界被拆开的多字节 UTF-8 会被暂存并补全，而不是变成替换字符。

先 read_line，再 read_to_string

read_to_string 读取的是同一个缓冲区，所以两者可以组合：先用 read_line 读标题行，再用 read_to_string 读正文，得到的是剩下的内容，而不是第二份副本，也不是空字符串。如果先调用它，它仍然返回整个 stdin。

先读一行标题，再读正文 
let header = io.read_line()
let body = io.read_to_string()

通过管道传入 200,000 行，计数大约需要 20ms，所以逐行读取不需要牺牲吞吐量。

当前状态

现已提供

  • io.read_line 在一行到达时返回，而不是在流关闭时返回，所以“提示/读取/回应”循环在终端上和通过管道时都能工作。
  • CRLF 会被规范化，没有终止符的最后一行会交付一次，多字节字符能跨越分块边界保持完整，read_to_string 读取同一缓冲区中剩下的内容。
  • 有一个回归测试会保持 stdin 打开并要求得到回显
    详情

    有一个回归测试会保持 stdin 打开并要求得到回显，因为用管道传入文件的测试在有问题的实现上也能通过。

  • io.print 和 io.eprint 输出时不带换行
  • io.is_terminal / io.stdin_is_terminal 告诉程序它面对的是人还是管道
    详情

    io.print 和 io.eprint 输出时不带换行，所以 REPL 的 > 提示符和用户输入的答案在同一行；io.is_terminal / io.stdin_is_terminal 告诉程序它面对的是人还是管道，所以像聊天应用的 --stdin 这样的 flag 不再是唯一的判断方式。

仍不完善

  • 想要重绘屏幕的程序还没有光标控制
    详情

    想要重绘屏幕的程序没有光标控制：std/io 没有光标或屏幕函数，也没有其他标准库模块提供，所以全屏终端界面仍然需要自己写转义序列。
