为什么这很重要

一门能写单个文件、却无法组织一个项目的语言，你不会把代码库押在它身上。真正要紧的缺口并不罕见：

  • 可见性能不能隐藏一个辅助函数？
  • 泛型约束泛型能不能要求某种能力？
  • 清理能不能在每条退出路径上释放文件句柄？
  • 并发能不能同时运行两件事并等待两者完成？

Glyph 回答了这四个问题，而且没有重新走回它有意放弃的大量注解的方向。

接口约束泛型

interface 是结构化的，和 TypeScript 一样：它是一组泛型可以要求的成员签名。没有 implements，没有名义类型的繁琐手续。任何具有这些成员的值都符合要求，由 tsc 强制检查。

接口约束泛型 
interface Named {
  fn name() -> string
}

pub fn label<T: Named>(x: T) -> string {
  x.name()
}

defer 与结构化并发

defer 在代码块退出时运行清理，覆盖每条路径，包括提前返回和抛出错误。std/task 让并发任务共享同一个生命周期并汇合，而不是留下游离的 promise。

defer + 结构化并发 
defer file.close()          # runs on the way out, however you leave

let both = await task.all([fn() { fetch_a() }, fn() { fetch_b() }])
详情 执行顺序，以及 owned 句柄

多个 defer 按后进先出的顺序运行，并且能与 owned 句柄组合使用。

它从 JavaScript 继承了什么

Glyph 编译为 TypeScript 并运行在 JavaScript 引擎上，因此继承了求值顺序、可变操作的引用语义，以及单线程、带垃圾回收的模型。规范把这些写成保证，而不是让你事后才发现。

不同之处在于相等性：== 比较的是值，record 逐字段比较；而 JavaScript 的 === 比较的是引用。

手动内存管理和无 GC 的模型不在路线图上，它们超出了一门编译为 TypeScript 的语言的范围。

没有 if，所以 match 必须承担一切

听完穷尽性的介绍之后，TypeScript 开发者问的第一个问题是：match 真的是一个通用条件结构，还是只是解构联合类型的一种好看写法？答案是前者，而最能证明这一点的地方是赋值。

作为 let 或 mut 完整值的 match 可以接受语句能接受的任何东西：分支可以是代码块，分支可以 await，分支可以 break 跳出外层循环，分支还可以读取它正在赋值的那个绑定，这就是在没有 if 的情况下在循环中累积状态的方法。

来自链接检查器：代码围栏跟踪，以及一个被 await 的分支 
for raw in lines {
  let fence = is_fence(raw)
  mut in_fence = match fence {      # reads the binding it assigns
    true => !in_fence,
    false => in_fence,
  }
}

let cache = match args.offline {
  true => no_cache(),
  false => await fetch_unique(external(links), args.max_concurrency),
}
详情 它编译成什么，以及代码片段的来源

两者都编译成一个普通的 switch，在每个分支中为绑定赋值，所以 await 位于外层的 async 函数中，累加器是一个 TypeScript 可以推断的普通变量。两段代码都来自 examples/apps/linkcheck/main.glyph，这是一个 Markdown 链接检查器，写它正是为了发现这类问题。

在更大的表达式内部使用的 match，比如作为参数或操作数，仍然会变成一个闭包，这意味着它的分支必须是单个表达式。把它提到单独的 let 中就没有这个限制了。

模式可以描述不止一层深的形态

带多个字段的变体携带的是一个记录，所以想识别某种形态的分支必须深入记录的字段。现在字段可以接受任何模式：变体标签、嵌套构造函数、嵌套解构、字面量、数组模式。

红黑树再平衡中的一种旋转情况，写成一个分支 
type Tree =
  | Leaf
  | Node({ color: Color, left: Tree, value: number, right: Tree })

match t {
  Node({ color: Black, left: Node({ color: Red, left: a, value: x, right: b }), value: y, right: c }) =>
    Node({ color: Red, left: Node({ color: Black, left: a, value: x, right: b }), value: y, right: c }),
  other => other,
}
历史 0.1.90 之前的变通做法

在 0.1.90 之前，字段位置只能写一个名字：你可以给它改名，仅此而已。在那里匹配标签是编译错误，嵌套的构造函数会让解析器失败。变通做法是绑定每个字段，然后每一层写一个嵌套的 match，而对于红黑树再平衡这样的代码，这就成了另一个程序：分支不再与各种情况一一对应，每一层都要重新传递上一层的绑定。

写之前有一个后果值得了解。检测值的字段可能匹配失败，所以这个分支不再被算作覆盖了它的变体；如果一个 match 中唯一的 Node 分支是 Node({ color: Red, ... })，它会被报告为不穷尽，直到有兄弟分支或 else 处理其余情况。

详情 为什么要求兜底分支，以及数组位置

检查器证明的是对一组标签的覆盖，而不是对字段乘积的覆盖，所以它不会推断出一个 Red 分支和一个 Black 分支合起来穷尽了 Node。要求兜底分支，是唯一不会让 match 在运行时从末尾掉出去的解读。在根本没有变体可数的地方也一样：对一个普通记录做 match，如果每个分支都检测某个字段，后面就需要一个 else。

它延伸到的一个可能出乎意料的地方是数组位置。以前 [Black] 作为整个分支会被当作匹配任意单元素数组，所以依赖它的 match 被认证为穷尽，然后对 [Red] 也走了这个分支。PascalCase 的元素在这里同样是变体引用，所以这样的 match 现在在长度为 1 的数组上报告 E0208。先绑定元素，再单独对它做匹配。底层的降级实现仍然是旧的，这也是为什么检查是先发布的那一半。

E0208

编译器也知道 match 产生了什么

接下来的问题决定了这一切是否真的起作用：一旦你从某个分支中绑定出一个值，Glyph 知道它的类型吗，还是耸耸肩，让 tsc 以后再处理？现在当各分支的类型一致时，match 就采用这个类型，并且已知 T.parse 返回 Result<T, Array<Issue>>，这正是大多数真实代码会据以分支的形态。

来自费用分摊应用：没有注解，i 也是 number 
let wire = match WireLedger.parse(decoded) {
  Ok(w) => w,
  Err(issues) => {
    return Err(BadInput({ message: "${path} is not a settle ledger: ${describe_issues(issues)}" }))
  },
}

for i, w in wire.expenses {        # i is 0, 1, 2 ... not "0", "1", "2"
  ...
}
历史 0.1.45 之前

在 0.1.45 之前它就是耸耸肩。每个 match 表达式的类型都是 unknown，所以从语言中唯一的分支结构里出来的值，从那一刻起就没有类型了。

详情 什么会悄悄出错，以及合并规则如何工作

这两部分以前都会悄无声息地出错。这个循环生成的是 wire.expenses.entries()；当被迭代对象的类型未知时，它会改为生成 Object.entries(...)，i 就成了字符串 "0"，这在 TypeScript 中是合法的，所以构建是干净的，而程序在本该打印 1:a 的地方打印了 01:a。而 wire.expensez 现在由 Glyph 在 .glyph 那一行报告为 [E0210] type WireLedger has no field expensez，而不是生成的 TypeScript 上的 TS2339。

合并规则是比较类型头部是否相等：以 return 结束的分支不参与，类型不一致的分支会让结果和以前一样是 unknown。它只在类型参数处多看一层，所以 None => [] 与一个 Array<string> 分支是一致的，而不会拖垮整个 match，之后的循环仍然绑定一个 number。基于 record.get 的同样链条也出于同样的原因能工作：std/record 的全部六个函数都会从你传入的记录上带出值的类型。这段代码来自 examples/apps/settle/main.glyph，它原本带着这次删掉的那个注解。

带空回退值的查找

这是代价最大的形态。对 Record<string, Array<string>> 调用 record.get 得到 Option<Array<string>>，而 [] 是一个元素类型不确定的数组，所以两个分支在 Array 上一致，元素类型来自有元素类型的那个分支。

来自依赖解析器：一次查找，一个空的回退值，一次按索引遍历 
let path = match record.get(res.reached, name) {
  Some(p) => p,
  None => [],
}

for i, hop in path {               # i is a number, so the indent nests
  let indent = string.repeat(STEP, i + 1)
  mut out = array.push(out, "${indent}${hop}")
}
历史 0.1.55 之前

在 0.1.55 之前，它们是按相等比较的，[] 被算作不一致，下面的循环在一个没有诊断、通过了 tsc --strict 的构建上打印出 01:x。代码在 examples/apps/depsolve/main.glyph 中，它以前以 let path: Array<string> 开头，上面还有三行注释解释这个注解不可或缺。

pad_start 要我自己写吗？

在真实程序中最先碰到的缺口不是类型系统特性，而是想用 string.slice 却发现什么也没有。

这十一个函数现在都已提供，七个应用中的副本也已全部删除。

历史 0.1.47 之前各应用自带的副本

连续五轮内部试用都提交了同样的清单，在 0.1.47 之前，本仓库有六个应用自带 repeat，五个自带 pad_start，而且每个应用都有一个本该用 fold 的循环。

与 TypeScript 的不同之处

其中三个有意与同名的 TypeScript 函数不同。

  • repeatrepeat 在次数为负时返回 ""，而 TS 会抛出异常，这让 repeat(pad, width - len(s)) 在字符串已经过长时也是安全的。
  • index_of两个 index_of 函数都返回 Option<number> 而不是 -1，因为 -1 是一个在所有真实索引能出现的地方都能通过类型检查的数字，出错的地方离调用处很远。
  • replace_all替换只提供 replace_all，所以没有只替换第一处的形式，不会与 String.prototype.replace 混淆，后者只会悄悄替换一处。

fold 为什么重要

fold 换来的是一个支柱，而不只是少打几个字。mut 是每个状态变化位置的可检索记录，没有 fold 的话，grep mut 返回的结果里满是计数循环，它们修改的东西审查者根本不关心。

删掉手写版本后，examples/apps/ 中的修改位置从 192 个减少到 161 个。

详情 改写是怎么验证的

这次改写是通过输出验证的，而不是靠审查：七个应用在改写前后都用固定输入运行，26 个文件的 stdout、退出码和 HTTP 响应，全部逐字节相同。

能遍历目录并知道哪里出错了吗？

std/fs 最初提供了六个函数，没有一个能列出目录。

  • fs.read_dirfs.read_dir 返回下一层的条目名。
  • fs.is_dirfs.is_dir 像 fs.exists 一样返回一个 bool。
  • fs.statfs.stat 返回一个 FileInfo，包含 is_dir、is_file、以字节计的 size，以及以纪元毫秒计的 modified，可以直接交给 time.format_iso 格式化。

没有递归的 walk，也没有 glob；用这三个函数加上 path.join，大约十行就能写出遍历。

历史 它们取代的变通做法

本仓库中的链接检查器绕过标准库，直接调用 node 的 readdirSync，并通过尝试读取路径、检查返回的 errno 来判断哪些路径是目录。这两部分都已修复。

失败有了名字

失败这一侧的变化更大。现在程序真正会从中恢复的五种错误都有了名字，没有名字的 errno 会完整地放在 Other 这个兜底变体上。

检查器知道这个分类是封闭的，所以对 err.kind 的 match 和对你自己声明的联合类型要求一样：覆盖全部六种就不需要 else，漏掉一种，构建就会失败，报告指出 fs.ErrorKind 的 E0200。

E0200E0210
遍历目录树，并说出哪里出了错 
let names = fs.read_dir(dir)?
for name in names {
  let child = path.join([dir, name])
  match fs.is_dir(child) {
    true  => visit(child),
    false => {
      let info = fs.stat(child)?
      report_size(child, info.size)
    },
  }
}

match err.kind {                        # no else arm: E0200 if you miss one
  fs.ErrorKind.NotFound         => io.eprintln("no such path"),
  fs.ErrorKind.NotADirectory    => io.eprintln("that is a file"),
  fs.ErrorKind.IsADirectory     => io.eprintln("that is a directory"),
  fs.ErrorKind.AlreadyExists    => io.eprintln("already there"),
  fs.ErrorKind.PermissionDenied => io.eprintln("cannot read it"),
  fs.ErrorKind.Other({ code })   => io.eprintln("errno ${code}"),
}
详情 旧的分类、受检字段，以及自己试试这项检查

FsError.kind 以前是 { tag: string }，整个分类只有 NotFound，所以要区分 “该路径是目录” 和 “该路径不存在”，就得比较 errno 字符串。

fs.FsError 和 fs.FileInfo 的字段也会被检查，所以 err.mesage 是针对你的 Glyph 源码的 E0210，而不是针对生成的 TypeScript 的 tsc 错误。

这项检查是生效的。把上面 match 中的 PermissionDenied 分支删掉，glyph check --no-tsc 就会以 E0200 停下：对 fs.ErrorKind 的 match 不穷尽，缺少变体 PermissionDenied。标准库模型最初编写时只覆盖返回类型，像这样的 match 能干净地编译，却在运行时抛出异常；现在 fs.FsError、fs.FileInfo 和 fs.ErrorKind 的字段和变体形态都已建模。

两个较小的新增功能

同时还加入了两个较小的功能，都来自同一个应用。

  • regex.captures_allregex.captures_all 返回每次匹配的捕获组，而不只是匹配到的文本，所以扁平的 key=value 扫描不再需要手写循环。
  • task.pool_settledtask.pool_settled 是带有 all_settled 失败行为的 task.pool：并发数有上限，每个任务一个结果，一个挂掉的主机只会让你失去这个主机的结果，而不是池子已经收集到的所有结果。

怎么知道这些函数选得对？

因为提出需求的那个应用必须停止绕开它们，这个版本才算完成。

一个库函数发布了，和一个变通写法在它发布后仍然存在，是两回事，所以加入这四个函数的同一次改动也删掉了链接检查器里的副本：readdirSync 导入、两处 errno 字符串比较、97 行手写的扫描器，以及遇错即停的任务池。一共删掉了 122 行。

两处行为变化，经过测量

其中两处删除改变了程序的行为，而这种差别是测量出来的，而不是争论出来的。

  • 不可读的目录把新旧两个版本指向一个包含不可读目录的目录树：新版本打印 permission denied，并把该路径计为不可读；旧版本只能判断 errno 是否为 EISDIR，于是把它完全排除在报告之外。
  • 失败的 URL让三个 URL 中的一个抛出异常：pool_settled 打印了全部三行，并指出了失败的那个；pool 什么也没打印，因一个未处理的 rejection 而退出，两个正常的结果也随之丢失。
详情 扫描器的改写，以及关于多选结构的顾虑

扫描器的改写也解决了一个设计上的顾虑。由于没有参与匹配的捕获组读出来是 ""，和匹配到空串的捕获组一样，captures_all 看起来无法告诉你多选结构中哪个分支命中了。其实可以，只要把每个分支的捕获组包在整个结构外面，而不是只包住你想要的那部分：命中的组就会以 `、[、! 或 < 开头，不可能为空。可能为空的那部分，也就是链接目标，嵌套在里面，从来不是你要判断的对象。这把一个 180 行的逐字符遍历变成了两个模式加上 12 行的分派代码，在仓库自己的文档和一个专门用来破坏它的测试夹具上，输出都逐字节相同。

金额不用浮点数计算

能当场终结一次金融科技评估的缺口，是用 IEEE-754 的 number 处理金额：0.1 + 0.2 不等于 0.3，超过 253 的值会悄悄丢失精度。

std/decimal 是基于 BigInt 的精确十进制定点数：一个任意精度整数加上固定的小数位数，所以加、减、乘都是精确的，除法则需要显式指定小数位数和舍入方式。格式错误的金额会解析为 Err，绝不会悄悄变成 NaN。

std/decimal 
let price = decimal("10.50")?
let tax   = decimal("0.84")?
price.add(tax).to_string()        # "11.34", exact

decimal("2")?.div(decimal("3")?, 2).to_string()   # "0.67", half away from zero
decimal("9007199254740993")?.add(decimal("2")?)   # exact past 2^53

大整数

对于精确的大整数，比如账户 id 和计数器，有 bigint 类型：字面量写作 123n，生成真正的 TypeScript bigint，类型为 bigint 的记录字段会在边界上校验 typeof === "bigint"，所以以 JSON number 发送的 id 会被拒绝，而不是在超过 253 后被悄悄舍入。

异步回调终于有了类型

函数类型以前只有 fn(A) -> T 一种，生成 (a: A) => T。async 函数体不符合这个类型，所以返回延迟任务的函数，或者由 async 处理函数组成的记录，只能不写注解，检查器也就不再检查。

async fn(A) -> T 就是缺少的那个类型。它生成 (a0: A) => Promise<T>，没有返回值的 async fn() 生成 () => Promise<void>。

一个延迟任务，以及一个处理函数映射 
fn task_for(url: string) -> async fn() -> Fetched {
  return async fn() -> Fetched { return { url: url, body: await fetch_one(url) } }
}

type Handler = async fn(string) -> string

async fn dispatch(routes: Record<string, Handler>, name: string, arg: string) -> string {
  return match record.get(routes, name) {
    Some(h) => await h(arg),
    None    => "no route",
  }
}
详情 Glyph 如何区分普通函数和 async 函数

Glyph 自己区分这两者，而不是留给 tsc：在需要 async 函数的地方给出普通函数，在 return 处是 E0204，在调用参数处是 E0211，报错会同时指出两边的类型。

它唯一不判断的情况是 void 返回，在那里 TypeScript 允许任何函数。

递归类型，一直匹配到底

联合类型可以在自己的负载中连同类型参数引用自身，match 分支可以在一个构造函数模式的字段中嵌套另一个构造函数模式。把这两点结合起来，红黑树的平衡规则就是四个分支：每个分支都写出它要改写的确切形态，由编译器检查这个形态，而不是由上方的一段注释声称它是什么。

四种旋转情况之一 
type Tree<K, V> =
  | Leaf
  | Node({ color: Color, left: Tree<K, V>, key: K, value: V, size: int, right: Tree<K, V> })

fn balance<K, V>(t: Tree<K, V>) -> Tree<K, V> {
  return match t {
    Node({ color: Black, left: Node({ color: Red, left: Node({ color: Red, left: a, key: xk, value: xv, right: b }), key: yk, value: yv, right: c }), key: zk, value: zv, right: d }) => node(
      Red,
      node(Black, a, xk, xv, b),
      yk,
      yv,
      node(Black, c, zk, zv, d),
    ),
    // the other three cases, then:
    other => other,
  }
}

examples/apps/leaderboard/main.glyph 是完整程序，一个把所有分数保存在树中的排行榜，通过遍历树来回答排名、前 N 名和区间查询，而不是重新排序一份日志。

可见性

  • 导入私有名字时的报错与名字不存在时相同
    详情

    导入私有名字时报告的是 “not exported by M”，和名字不存在时的报错相同；区分 “私有，请标记为 pub” 和 “没有这个名字” 是一项已排队的改进。

  • 通过命名空间读取私有值是 tsc 错误，而不是 Glyph 错误
    详情

    可见性在类型注解上检查，而不检查通过命名空间读取的值：helper 是私有的时候，lib.helper() 仍然是 tsc 错误，而不是 Glyph 错误。

异步

  • 模块级 const 初始化表达式中允许顶层 awaitE0222
    详情

    异步上下文现在会检查（E0222），只有一处例外：模块级 const 初始化表达式没有外围可调用体，所以那里允许顶层 await，生成的 ESM 会执行它。

推断的类型

  • 类型头部不一致的分支会让结果对 Glyph 来说是未知的
    详情

    分支类型合并仍然要求各分支的类型头部一致：当它们产生不同类型时，结果对 Glyph 来说是未知的，只有 tsc 会检查你怎样使用它。

  • 九个标准库函数处于同样的境地
    详情

    九个标准库函数处于同样的境地。其中六个接受一个可选的末尾参数（array.slice、string.slice、string.index_of、string.pad_start、string.pad_end、json.stringify），而参数个数检查只是拿一个数字和一个数字比较，所以为它们建模会在每个省略最后一个参数的调用上报出误报；array.map、flat_map 和 zip 的元素类型来自回调，而检查器不会深入回调。

    直接从这九个函数得到的值，在按索引遍历之前需要加注解，对 string.index_of 的 match 如果没有 None 分支，仍然能干净地构建，并在运行时抛出异常。array.index_of 已经建模，确实会报告 E0200。

  • 对检查器无法确定类型的值，成员和调用参数个数不检查
    详情

    对检查器无法确定类型的值，成员和调用参数个数在这个边界上仍不检查，而不是报错。

库

  • string 按 UTF-16 码元索引，不打算提供 chars 或 char_at
    详情

    在库这一侧，string 按 UTF-16 码元索引，和 len 与 split 一直以来的做法一样，这一点已经定下来：没有 chars 或 char_at，也不打算提供，因为返回的半个代理对在被写出之前看起来都像一个字符。用 encoding.hex_encode 编码，然后每次读取两个十六进制数字。

  • captures_all 不返回偏移量；fs.read_dir 保留操作系统的顺序
    详情

    captures_all 只返回捕获组，不返回偏移量，所以需要知道匹配从行中哪个位置开始的扫描器仍然要自己写循环；fs.read_dir 按操作系统的顺序返回条目，当输出需要可复现时请自行排序。

模式

  • 通过命名空间导入访问的联合类型上，字段中携带负载的构造函数会失败E0300
    详情

    嵌套字段模式还剩一个边界情况：通过命名空间导入访问的联合类型上，位于字段中、携带负载的构造函数。import tree { Node } 之后写 Node({ left: Node({ key: k }) }) 能编译，而 import tree 之后写 tree.Node({ left: tree.Node({ key: k }) }) 在同一个联合类型上报告 E0300。

  • 对自身类型参数泛型的联合类型接受嵌套分支，并检查缺少的变体E0200
    详情

    另一个边界情况已经解决：对自身类型参数泛型的联合类型（type Tree<K> = Leaf | Node({ left: Tree<K>, key: K, right: Tree<K> })）以前会拒绝不带参数的同一联合类型所接受的嵌套分支，现在无论是开放的类型参数还是具体的实例化都能接受。同一个查找过程还决定着 match 是否会检查缺少的变体，所以在这个版本之前，对 Tree<K> 的 match 可以省略 Leaf，干净地构建，通过 tsc --strict，然后在运行时抛出异常，而非泛型写法会报告 E0200。

    现在两种写法都会报告，而且把联合类型移到另一个模块再导入也不会改变答案：对导入的 Tree<string> 做 match 而省略 Leaf，会报告指出 Leaf 的 E0200，和导入的非泛型 Tree 一样。那是另一条代码路径，单独检查，在这个版本之前结果正好相反：干净地构建，在运行时抛出异常。

  • 对导入联合类型的覆盖检查从不检查其变体负载
    详情

    关于导入的联合类型的覆盖检查，在依赖它之前还有一点值得了解：它的变体负载也从不检查，所以当 X 是负载自身联合类型的一个变体时，B(X) 会匹配每个 B，而不是报告缺少 Y，这一点与泛型无关。

    绑定字段，或者在字段中匹配不带负载的标签，在所有情况下都能工作。
