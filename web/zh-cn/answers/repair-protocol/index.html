为什么重要

智能体围绕编译器的循环是：读错误，猜编辑，重新构建。损害就发生在猜的这一步，而之所以会发生，是因为错误只是一个字符串。

  1. 读错误
  2. 猜编辑
  3. 重新构建

这些编译器全都知道。它知道联合类型的各个变体和它们的负载，也知道 else 会放弃封闭性保证，却在回复前一行把这两样都丢掉了。

详情 字符串会招来的两种错误编辑

读到“non-exhaustive match on OrderStatus”的智能体知道某个 match 少了几个分支，但不知道缺少的变体携带什么，于是写出 Paid("tx_1")，等下一条诊断才发现不对。或者它读到“exhaustive”这个词，加一个 else 分支，构建通过了，却丢掉了这条诊断本来要保护的保证。

解读答案

有三点值得单独说明。

  • causecause 是出错的符号，它和 entity 不是一回事，后者是诊断所在的声明：这里编辑发生在 main::describe 中，而它必须匹配的形状来自 orders::OrderStatus。
  • constraintsconstraints 不是修复方案。每一条都是编译器已经在强制执行的东西，把它写出来，是为了让满足诊断的编辑不会破坏诊断背后的保证。
  • symbolssymbols 是诊断中提到的每个符号的 glyph_symbol 答案，所以智能体的下一次编辑不需要再调用一次。

每个键总是存在。编译器不掌握的事实会以显式的 null 出现，而不会缺少这个键，所以“缺失”在每个错误码上、在命令行和 MCP 两种方式上都只有一种写法。

详情 可串联的地址、else 约束、symbols_absent

两者都是其他工具接受的地址，所以答案可以直接串联，不需要重新推导任何东西。

第二条约束说明了这个键存在的原因：else 分支是合法的，它能让构建通过，而这条约束说明了这样做的代价。

工具拒绝回答的符号会出现在 symbols_absent 中并附上原因，这样“我们没有查”和“我们查了，它不存在”就能区分开。

答案确定时，由编译器写入

glyph fix 只应用编译器能自行确定的修复：未使用的导入；不是变体的分支头，且检查器恰好算出一个建议；以及记录没有声明的字段，且恰好有一个已声明字段与它只差一个字符。上面的 match 不属于其中任何一种。

对上面的 match 运行 glyph fix src 
glyph fix: removed 0 unused import(s) across 0 file(s).
glyph fix: declined E0200 in src/main.glyph: the compiler does not
           determine what a missing arm should do, so `glyph fix`
           writes none: add an arm for each of `Paid`, `Cancelled`.
           `glyph check --agent` gives the pattern each case takes.

// src/main.glyph is unchanged, and glyph check still fails with E0200.

编译器知道缺少哪些情况，以及每种情况的模式怎么写。它不知道订单为 Paid 时程序应该做什么，它写出的任何分支体都只是一个能通过编译的猜测。

历史 0.1.128 及之前 glyph fix 写了什么

在 0.1.128 及之前，glyph fix 会写出这种猜测：每种情况一个分支，分支体打印这种情况并调用 process.exit(1)。这样程序能通过 check、tsc 和 build，glyph query variants 也会报告这个 match 是穷尽的，于是缺少的情况从编译错误变成了运行时崩溃，再也没有任何东西会标记它。

详情 分支从哪里来，以及如何报告拒绝

所以这条规则会拒绝修复，并列出这些情况。写这些分支需要的信息都已经在上面的 --agent 答案里：missing_variants，以及 symbols 下每个变体的 construct 写法。这些分支由你或你的智能体来写，就像其他任何编译器无法推断其行为的代码一样。

glyph fix 写入的东西都不靠猜测，每条无法确定答案的规则都会把拒绝及原因打印在与已应用修改相同的输出中。如果有两个字段都与拼写错误只差一个字符，那就是两个而不是一个，它会如实说明，而不是从中挑一个。

错误码自己的解释，以数据形式提供

glyph --explain <CODE> --json 会返回详细解释、一行的 help、文档 URL，以及编译器反例语料库中的一个错误程序，并附上本编译器对它给出的诊断。

这条诊断是在你询问时现场编译得到的，而不是存储下来的，所以不会与编译器的实际输出产生偏差。

glyph --explain E0200 --json 
{
  "code": "E0200",
  "title": "non-exhaustive match",
  "explanation": "A `match` over a tagged union must handle every variant.
    Unions are sealed (D9): adding a variant later forces every match to be
    updated, so a missing variant cannot silently fall through at runtime ...",
  "help": "Add an arm for each missing variant.",
  "docs": "https://github.com/chadetov/glyph/blob/main/docs/error-codes.md#e0200",
  "counter_example": {
    "name": "alias_of_local_union_not_exhaustive",
    "expected_error": "E0200",
    "files": [ { "path": "alias_of_local_union_not_exhaustive.glyph",
                 "source": "module main\n\ntype Shape =\n  | Circle\n ..." } ],
    "diagnostic": { "code": "E0200",
                    "message": "non-exhaustive match on `Shape`: missing variants `Tri`",
                    "cause": "alias_of_local_union_not_exhaustive::Shape",
                    "related": ["Circle", "Square", "Tri"],
                    "missing_variants": ["Tri"] },
    "corrected": null,
    "corrected_absent": "`tests/negative/` pairs no repaired program with a case:
      an entry is a wrong program and the code it draws. A fix invented here would
      compile nowhere and be checked by nothing."
  }
}

语料库没有覆盖的错误码会返回 counter_example: null，并附一句话说明语料库中没有它的案例，而不是编一个示例。语料库只声明它覆盖了什么，对其余部分不做任何声明。

详情 通过 glyph llms --negative 获取完整语料库

glyph --explain 为每个错误码给出一个案例。整个语料库也可以读取：glyph llms --negative E0200 会打印触发这个错误码的每一个错误程序，每个都在你询问时现场编译；如果另一个语料库里有一个被 tsc --strict 接受、而对应的 Glyph 版本被拒绝的程序，也会一并返回。不指定错误码时，它列出覆盖 70 个错误码中 46 个的 102 个案例，并列出没有案例的 24 个，所以覆盖范围是明确声明的，而不是从返回结果中推断出来的。这一点以及编译器发布的关于它自身的其他信息，见单独的一页。

当前状态

现已提供

  • 每条诊断都带有 expected、actual、cause、alternatives、related、module、file 和 explain，编译器不掌握的事实一律是显式的 null
    详情

    每条诊断都带有 expected、actual、cause、alternatives（由 alternatives_kind 说明它列出的是 fields、members、variants、literals 还是 exports，在报错处设置）、related、module、file 和 explain，这些值来自编译器抛出的错误本身，而不是重新推导的；编译器不掌握的事实一律是显式的 null。

  • file 是相对于解析根目录的路径，报告会在 project_root 中给出这个根目录，所以可以直接打开。
  • glyph check --agent 为每条诊断加上 constraints 和 symbols。
  • glyph fix 应用三条规则（E0106、E0210、E0220），并说明每一次拒绝及其原因，包括每一个 E0200：它只报告，从不写入。E0106E0210E0220
  • glyph --explain <CODE> --json 返回带有现场编译反例的解释，glyph llms --negative <CODE> 返回触发该错误码的完整错误程序语料库。

它的边界

  • E0211 上的 cause 是 null：调用参数处的出错符号是一个参数，而标识词汇无法表达 module::fn.param，所以这个 null 是有意为之，而不是遗漏。E0211
  • 反例上的 corrected 总是 null，因为反例语料库没有为案例配上修复后的程序，而且 70 个错误码中有 24 个根本没有案例。
  • glyph fix 只写三条规则，别的都不写，它也不会为不穷尽的 match 写分支：这些留给你或你的智能体，诊断中已给出各个情况及其模式。
  • 它拒绝的每一项，都会明确说出来。
