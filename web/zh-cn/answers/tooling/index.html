glyph lsp 通过 stdio 使用 Language Server Protocol，所以任何带 LSP 客户端的编辑器都能获得诊断、悬停类型、跳转到定义、补全和保存时格式化。仓库里有一个 VS Code 扩展；它还没有上架 Marketplace，所以需要你从源码构建。每个错误都带有稳定的错误码、修复方法和原因。

为什么这很重要

在编辑器不理解的语言里写代码，感觉像是在倒退，早期这确实是合理的抱怨。现在不是了：编辑器提供现代的便利功能，报错的写法是为了教会你，而不只是拒绝你。

它是真正的 LSP，还是只是一个 VS Code 插件？

是真正的 LSP。编译器自带一个语言服务器，用 glyph lsp 启动，它通过 stdio 使用 Language Server Protocol（每个 LSP 客户端都支持的标准 JSON-RPC 传输方式）。

随附的 VS Code 扩展只是它外面的一层薄客户端，没有任何东西是 VS Code 专属的：把任何支持 LSP 的编辑器，比如 Neovim、Helix、Zed、Emacs（eglot），指向 glyph lsp，行为都一样。

它就是你已经安装的那个二进制文件（npx @glyphlang/glyph lsp），所以不需要另外获取服务器。

服务器实现了什么

服务器实现了编辑器需要的功能：带有下面这些稳定错误码的实时诊断、悬停类型、跳转到定义（通过具名导入可跨模块跳转；通过命名空间时，ui.Button 仍然没有结果）、补全、用于大纲和符号搜索的文档符号与工作区符号、覆盖整个工作区的查找引用、重命名，以及用于保存时格式化的标准 glyph fmt 排版。

重命名是完整的：重命名一个模块级声明，会修改它的定义、每一处引用，以及工作区中每个导入它的模块的 import 绑定，并且在改动任何东西之前先检查新名字（必须是真正的标识符，而不是关键字）。

有两个限制值得了解：跨文件索引在每次请求时重建，而不是缓存（对普通项目没问题，以后值得加速）；当前无法解析的文件会被跳过，所以重命名不会触及本身已经损坏的文件里的引用。

错误信息

我们正是在智能体和新手最容易绊倒的地方改进了报错信息：写 if 时现在会指引你使用 match，而不是笼统的“意外的 token”；参数数量错误、不穷尽的 match、拼错的变体，各自都有带错误码、可修复的报错。

只有 TypeScript 后端才能发现的类型错误，过去指向的是生成的 .ts。现在它们会映射回你的 .glyph（同样的 ariadne 插入符，同样的稳定错误码），所以 tsc 错误读起来就像原生的 Glyph 错误。

调试

你用已经在用的工具调试生成的 TypeScript，比如 Node 的 inspector、浏览器 devtools 或 IDE 的 JS/TS 调试器。

每次构建都会在每个 .ts 旁边附上一个标准的 v3 source map（嵌入了 Glyph 源码），所以能串联 source map 的调试器或打包工具会定位回你的 .glyph 行号。

还有一点没覆盖到：glyph run 自身的崩溃堆栈仍然打印 .ts 的行，因为 tsx 不会把 source map 串过它的转换。下一步就是重新映射这个堆栈。

不运行就问“这能编译吗？”

glyph check path.glyph 对单个文件或整个目录做类型检查，然后退出。它不会往你的目录树里写任何东西，这是 glyph run 无法保证的，而 glyph build 根本不会这样做（它拒绝任何不是目录的参数）。

--no-tsc--json--no-test
详情 它运行什么，以及各个 flag

它运行的流水线和构建相同，包括对生成的 TypeScript 运行 tsc --strict，输出到一个退出时会删除的临时目录。想要快速得到答案时，--no-tsc 会在 Glyph 阶段之后停止；--json 给智能体提供和 glyph build --json 相同格式的诊断。文件会在它所在目录的上下文中检查，所以有问题的同级文件仍然会让检查失败。你的 @example 和 @doc @run 测试也在这里运行，与 glyph build 使用的是同一道关卡，所以检查不可能对一棵构建会失败的目录树报告通过；如果你想要一个不执行任何代码的答案，--no-test 会跳过它们。

终端输出也不会骗你

现在摘要会在所有可能让构建失败的阶段之后才打印，所以失败的构建永远不会显示一行成功信息。

历史 打印得太早的摘要

失败的构建过去会以“没有诊断”开头，然后在下面打印 tsc 错误，因为 Glyph 阶段的摘要是在 TypeScript 阶段运行之前写出的。

同一轮改进中，glyph run app.glyph --min -12.50 也能用了：以前开头的连字符会让 clap 在你的 main 看到参数之前就拒绝它。

属于 glyph 自己的 flag 仍然由 glyph 解析，所以如果程序的 flag 和其中某个冲突，在它前面加上 --。

对于循环中的智能体

glyph build --json 把每条诊断输出为结构化 JSON：稳定的错误码、严重程度、信息、文件、从 1 开始的行/列范围，以及帮助和注释，其中包括映射到你的 Glyph 源码上的 tsc 错误。智能体直接读取并据此行动，而不用从终端文本里抓取。

面向交互式智能体的 glyph mcp

对于交互式智能体，除了批量诊断还有更多：glyph mcp 通过 stdio 运行一个 Model Context Protocol 服务器（同一个二进制文件，与编辑器使用相同的分析），把语言服务器的查询作为 MCP 工具提供。智能体可以询问一个文件的诊断、某个位置的类型、一个名字在哪里定义（会跟随导入）、某个符号在整个项目中的每一处引用，或者进行符号搜索，不需要运行完整构建，也不需要读遍每个文件。

它是同一个纯分析层之上的薄适配层，而不是第二套实现，所以不会和编译器、编辑器看到的内容产生偏差。

并非一切都是硬错误

Glyph 有一个警告级别，用来标出无用的代码而不让构建失败：未使用的导入（E0106）、未使用的 let（E0107，以 _ 开头的名字除外），以及 return/break/continue 之后的不可达代码（E0108）。

E0106E0107E0108

它们让模块保持如实：一个无用的导入正是那种损害可检索性的噪音，会让读者去寻找代码实际上并不存在的依赖。警告会出现在同样的渲染输出和 --json 输出中，以严重程度标记，并且仍然会生成 TypeScript。

当前状态

现已提供

  • 适用于任何编辑器、可跨模块边界回答的语言服务器自 0.1.124 起
    详情

    一个语言服务器（通过 stdio 运行 glyph lsp，适用于任何编辑器；随附 VS Code 扩展），提供高亮、诊断、悬停、跳转到定义、补全、符号、覆盖整个工作区的查找引用和重命名，以及保存时格式化；从 0.1.124 开始可以跨模块边界回答：服务器为每个项目维护一个数据库，你打开的缓冲区叠加在磁盘上的文件之上，所以悬停在导入的函数或导入记录的字段上，得到的答案与 glyph query hover 相同，一个文件中未保存的编辑能被另一个文件看到，每次按键的开销比单文件时多 1% 到 9%；

  • 提供十一个工具的 glyph mcp Model Context Protocol 服务器
    详情

    一个 glyph mcp Model Context Protocol 服务器，提供十一个工具，即编辑器的查询加上 glyph_symbol、glyph_impact、glyph_assignable、glyph_dependencies 和 glyph_exports，每个工具都有一个打印相同 JSON 的 glyph query 子命令，供没有 MCP 客户端的智能体使用；

  • 稳定的错误码、glyph --explain、映射到 .glyph 源码的 tsc 后端错误、警告级别（未使用的导入/绑定、不可达代码），以及 --json 结构化诊断。
  • glyph check [path] 对单个文件或目录树做类型检查，不运行，也不写输出。
  • glyph fmt --check 在 CI 中把关格式：它不写任何东西，当某个文件不符合唯一的标准排版时以非零退出。

正在进行

  • 缓存跨文件索引，而不是每次请求都重建（在大型目录树上能提速）。
  • 重新映射 glyph run 自身的崩溃堆栈：由于 tsx 不会把生成的 source map 串过它的转换，这个堆栈仍然指向生成的 .ts，而不是你的 .glyph。
