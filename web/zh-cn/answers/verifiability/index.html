为什么重要

智能体通常不会大张旗鼓地改坏代码。它们改坏代码时信心十足：加一个状态，删掉一个分支，或者给字段改个名，一切照样通过类型检查，bug 到了生产环境才暴露出来。

代价最高的失败是那些编译通过却是错的。Glyph 把“你大概处理了这种情况”变成“编译器证明了你处理了”，以此堵上这个缺口。

  • 封闭的联合类型标签联合是封闭的，所以 match 必须覆盖每一种情况。
  • 错误即值错误是你必须解包的值，而不是会凭空消失的异常。
  • 受检的边界每个类型都带有运行时描述符，所以跨越边界的数据会按它的形状进行检查。

丢弃的错误会产生警告

错误也一样：返回 Result<T, E> 的函数应当用 match 处理，或者用 ? 向上传递（编译器会检查错误类型是否对得上）。如果你把一个 Result 丢掉（把调用当作语句，忽略它的返回值），Glyph 会发出警告（E0217），因为被丢弃的错误就是被吞掉的失败。

glyph check --no-tsc，0.1.149（节选） 
13 │   save("a")
[E0217] Warning: typecheck: this `Result` is discarded; its `Err` case is silently ignored
    │ Help: Handle it with `match`, propagate it with `?`, or bind it (`let _ = ...`) to say the discard is intentional.

要消除警告，你得用 let _ = ... 有意为之，而不会是无意的。

标准库的联合类型同样是封闭的

对标准库拥有的联合类型，标准也一样。fs.ErrorKind 是一个包含六种类型的封闭集合，检查器知道它的形状，所以对文件系统错误做 match e.kind 不需要 else 分支，漏掉某一种时会以 E0200 失败。

E0200 缺少某种类型E0210 未知字段E0218 需要 else
详情 字段拼写错误、返回类型、数字与字符串的 match

e.mesage 是 E0210，而不是等到下游由 tsc 发现。返回类型也会传递：string.split(text, ",") 是 Array<string>，所以 for i, part in string.split(text, ",") 把 i 绑定为数字，而不是未标注类型的迭代对象会给出的字符串键。

穷尽检查不只针对联合类型。对 number 或 string 的 match 如果只有字面量分支，就无法覆盖无界的取值范围，所以 Glyph 要求一个 else（E0218），而不是让未覆盖的值落到运行时抛出异常。

规则处处相同：没有考虑到某种情况的 match 无法编译。

拼错的分支是一处遗漏，而不是兜底分支

拼写错误也无法悄悄掩盖遗漏。首字母大写的分支头是对变体的引用，而不是新的绑定。

status.glyph：拼错的分支是一处遗漏，而不是兜底分支 
fn label(s: Status) -> string {
  return match s {
    Loadign => "…",        // typo for Loading, read as a variant, not a binding
    Ready => "done",
    Failed(msg) => msg,
  }
}
glyph build 
[E0220] `Loadign` is not a variant of `Status`; did you mean `Loading`?
   ╰─ a lowercase name would be a binding; a PascalCase name is read as a variant
[E0200] non-exhaustive match on `Status`: missing variant `Loading`
历史 旧版 Glyph 如何处理这个拼写错误

首字母大写的分支头是对变体的引用，而不是新的绑定。所以如果你把 Loading 拼成 Loadign，旧版 Glyph 会把这个错误拼写当作绑定所有值的兜底分支，让这个 match 看起来是完整的。现在分支头必须是被匹配的联合类型中真实存在的变体。不是的话，构建会以 E0220 停止并指出最接近的真实名字，而你真正漏掉的变体仍然会以 E0200 出现在旁边。

负载中的变体

往下一层也是同样的理解，即变体是另一个变体的负载时。无论外层变体是什么，分支现在都按负载自身的标签分派。

repl.glyph：内层分支检测负载，而不是绑定它 
fn step(z: Zipper, line: string) -> Zipper {
  return match parse_command(line) {
    Err(Blank) => z,                          // a comment or an empty line
    Err(e) => { io.println(explain(e)) z },   // every other parse error
    Ok(command) => execute(z, command),
  }
}
E0305 重复的 case 标签
历史 0.1.93 之前的死分支，以及 E0305 防护

Err(Blank) 写在 Err(e) 旁边，读起来是“忽略空行，打印其他所有解析错误”。直到 0.1.93，它会被编译成外层标签上的两个 case "Err": 标签，第一个把整个负载绑定到名字 Blank 上。所有错误都走第一个分支，第二个成了死代码，而且没有任何提示：Glyph 不报任何诊断，tsc --strict 也接受重复的 case 标签。现在无论外层变体是什么，分支都按负载自身的标签分派，编译器理解这个名字的方式也与类型检查器相同：由负载联合类型自己的变体列表决定，只有拿不到这个列表时才由名字的形式决定。对同一文件中声明的联合类型，大小写已经无关紧要。对从其他模块导入的联合类型，目前拿不到变体列表，所以首字母大写的变体会分派，小写的则让构建停止。

构建之所以停止，是因为 switch 现在有了防护。两个会写出相同 case 标签的分支是 E0305，而不是一个第二个标签永远不会执行的 switch。这让这类问题从悄无声息变成大声报错：一次两次用到同一标签的代码降级会让构建失败，而不是在运行时选错分支。

导入的写法永远不会关闭检查

联合类型是怎么进入作用域的，不会改变上面任何一点。Glyph 允许用两种方式写变体分支，两者的检查完全相同：import model { Cond, Yes, No } 配合不带前缀的分支，或者 import model（或 import model as m）配合 model.Yes(_)。

interp.glyph：导入列表删掉了，match 仍然受检 
import model { Action, All, Any, AtLeast, Clear, Condition, Context, Counter,
               Equals, Flag, FlagSet, Increment, Not, Set, Slot, Text }
import model
import std/result

pub fn evaluate(ctx: model.Context, c: model.Condition) -> result.Result<bool, SlotError> {
  return match c {
    model.Equals({ key, value }) => result.Ok(read_text(ctx, key, "equals")? == value),
    model.AtLeast({ key, least }) => result.Ok(read_count(ctx, key, "at-least")? >= least),
    model.FlagSet({ key }) => result.Ok(read_flag(ctx, key, "flag-set")?),
    model.All({ of }) => all_of(ctx, of),
    model.Any({ of }) => any_of(ctx, of),
    model.Not({ of }) => result.Ok(!(evaluate(ctx, of)?)),
  }
}
glyph build，删掉最后一个分支之后 
[E0200] non-exhaustive match on `Condition`: missing variants Not
详情 标准库的联合类型、字符串枚举，以及那个列表为什么存在

标准库的联合类型也是如此，所以对 option.Option<string> 写 match o { option.Some(s) => … }，会因为缺少 None 而得到 E0200，与不带前缀的 Some/None 写法完全一样。直到 0.1.56，带限定的写法会完全跳过检查，构建对一个运行时会抛异常的 match 不报任何诊断。

字符串枚举同样能跨越边界。在 catalog.glyph 中声明并导入到另一个模块的 type ColType = "text" | "int" | "real" | "bool" 保留它的四个值，所以覆盖全部四个值的 match 无需 else 就能编译，漏掉一个则是 E0200，并指出漏掉的值。直到 0.1.57 它还是 E0218，帮助文本让你加一个 else 分支。那条帮助对眼前的代码判断有误，照做会把编译错误变成运行时的落空。三种导入写法都有效：import catalog { ColType }，import catalog 配合 catalog.ColType，以及 import catalog as c 配合 c.ColType。

这个问题正是从那个导入列表发现的。一个状态图引擎的每个模块里都手写了这个列表，上面还有一条注释，说联合类型的构造器不会随类型一起导入。这条注释对语法的描述是对的，对原因的解释是错的：之所以需要这个列表，是因为更短的写法会关闭检查，而没有人注意到，因为关闭检查是悄无声息的。现在选哪种写法是一个实际的选择，而不是一个陷阱。具名写法把你处理的每个变体都放在导入列表里，grep 搜 Equals 时能找到它。限定写法在每个分支上标明变体来自哪个模块。两种都不会让你失去检查。

导入的记录保留它的字段

记录现在也能跨越边界，而在 0.1.58 之前不行。因此记录保留它的字段集合，错误的字段是指出该记录的 E0210，而不是一条关于匿名形状的 tsc 错误。

glyph build，针对导入记录上拼错的字段 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
// Before 0.1.58: no Glyph diagnostic at all, only a tsc error downstream.
table.glyph：提升的 let 以及解释它们的注释都删掉了 
// Both annotations are load-bearing. `for i, x in <record field>` picks its
// lowering from the iterand's type as the checker knows it, and a field
// access is not enough: without the `let`, `i` and `j` come out as strings
// and the row/column numbers in a `BadCell` are wrong.
let raw_rows: Array<Array<string>> = sheet.rows
for i, raw_row in raw_rows {
for i, raw_row in sheet.rows {
  let typed: Array<Value> = []
  let cols: Array<ColumnSpec> = spec.columns
  for j, col in cols {
  for j, col in spec.columns {
    …
  }
}

// sheet: Sheet, declared in catalog.glyph and imported here.
// Emitted TypeScript: sheet.rows.entries(), not Object.entries(sheet.rows).
详情 line 11 的 bug、tsc 漏掉了什么、标识如何跨越边界

在一个文件中声明、在另一个文件中使用的类型，到达时没有任何已知信息，这导致两项检查失效。它上面拼错的字段不会引发任何 Glyph 错误，所以 sheet.rowz 落到 tsc，返回的是一条关于你从没写过的形状的 TypeScript 信息。而 for i, r in sheet.rows 无法判断 rows 是数组，于是生成 Object.entries(sheet.rows) 而不是 sheet.rows.entries()。这会把 i 绑定为字符串 "0"。接着 i + 1 变成拼接而不是相加，本应报告为 line 2 的行被报告为 line 11。

值得了解的是 tsc 能发现其中哪一半。对这个索引做算术运算它能发现，不过报告的错误针对的是生成的 TypeScript，涉及的是 Glyph 替你绑定的一个变量。它发现不了的是所有本该用数字却接受了字符串的地方：字符串插值、拼接、record.get 的键。这些在两个检查器下都能干净地编译通过，却打印出错误的数字。这正是本项目要消除的那类 bug，所以一个重新引入它的模块边界，Glyph 不能置之不理。

导入的类型现在会带着一个标识跨越边界，以声明它的模块和它声明的名字为键，所以三种导入写法都解析到同一个类型。声明本身按需获取，并在声明模块那一侧完成降级，这一半是使用方做不了的：解析是基于源码区间进行的，而导入声明的区间属于另一个文件。

这个问题是在 examples/apps/csvql 的查询引擎中发现的。它带着三个提升出来的 let，唯一作用是为代码生成器重新声明一个导入字段的类型，上面还有四行注释，解释没有它们的话错误信息里的行号和列号会出错。这三个都删掉了，应用对全部十二个查询的输出逐字节相同。

仍有一样东西停在边界上。在需要 table.Row 的地方传入 catalog.Sheet 是同时指出两个类型的 E0211，但 interface 的成员列表不会跨越边界，所以在需要导入接口的地方传入的记录，没有可比较的对象。给它与记录字段集合相同的处理，会悄悄改变结构满足的含义，这是一个语言设计决定，而不是一个修复。

PII 脱敏定义在类型上

同样是“让它成为类型层面的东西，而不是约定”的思路，也用在了 PII 上。在类型上写 @redact fields: [ssn, dob]，编译器会在它的描述符上生成一个屏蔽这些字段的 redact()，所以 json.stringify(User.redact(u)) 不会泄露它们。

E0219 @redact 中的未知字段

写了一个类型中没有的字段就是编译错误（E0219），而不是一个悄悄什么都不做的脱敏。

精化类型会一路检查到底

描述符只有在一路到底都执行类型所声明的检查时才有价值。where 精化会在类型出现的任何地方运行它的谓词，而不只是在直接调用 Instant.parse 时：作为记录字段、作为 Array 元素、作为 Option 负载、在联合类型的变体中，以及通过 json.parse<T>。

schedule.glyph：谓词跟着类型进入字段 
fn is_instant(value: string) -> bool {
  return match time.parse_iso(value) {
    Some(_) => true,
    None => false,
  }
}

type Instant = string where is_instant(value)

type WireBlock = { start: Instant, end: Instant }
type WireParticipant = { name: string, busy: Array<WireBlock> }
type Calendar = { participants: Array<WireParticipant> }

// json.parse<Calendar>(text) on a file holding "start": "no"
//   => Err. It returned Ok before 0.1.41.
历史 0.1.41 之前那份信心十足的错误日程

从另一个模块导入的记录也是如此。直到 0.1.41，这两种情况都退化为只检查键是否存在，这实际上什么也没检查。

这个问题是在下面的排程应用中发现的。它从 JSON 文件读取日历，要求每个时间戳都是合法的 ISO-8601 时刻。以前精化只在顶层生效，所以一个手动编辑过、写着 "start": "no" 的文件能顺利解析，时刻被读成 0，应用信心十足地打印出一份日程，并以 0 退出。

详情 为什么不能悄悄跳过，以及 JSON 通道

一个不成立的断言会像类型错误一样让构建失败，这正是目的所在：重写函数体的智能体不可能通过丢下断言来通过构建。--no-test 可以选择跳过，并打印跳过了多少个测试，所以绕过行为会在日志中留下痕迹。

智能体读取的 JSON 输出报告同样的结论。glyph build --json 在诊断旁边带有一个 examples 对象，失败的示例会让 ok 为 false，退出码非零。直到 0.1.43，示例只在 --test 下运行，JSON 路径在它们运行之前就返回了，所以智能体唯一能读的通道，对一个自身断言不成立的项目打印出 "ok": true。如果 PATH 上没有 tsx，构建会失败，而不是报告一个它从未检查过的通过。

下面的 bracket 应用带有 23 个这样的测试。seed_order 通过倍增构建标准的对阵顺序，这类函数很容易写出细微的错误，又很容易精确描述。改动倍增规则，构建就会停止，不需要测试文件、测试运行器或 flag。

读取可能不存在的键

读取可能不存在的键：现在是 E0224 
fn name_of(row: Record<string, string>) -> string {
  return row.naem          // a typo. compiled, and returned undefined
}

现在它是一个指向 record.get 的编译错误，该函数返回 Option<V>，让不存在的情况有处可去。

详情 为什么读取 map 与数组索引不同

map 的键是任意的，所以编译器无法知道键是否存在。把读取的类型定为 string，等于断言了一件没有检查过的事，而这个值被打印成文本 "undefined"。写入键不受影响，数组索引也不受影响：边界是程序可以检查的值，map 的键则不是。

返回 undefined 的方法

可能什么都找不到的查找：现在是 E0242 
let name = users.find(fn(u: User) -> bool { return u.id == id }).name
let last = xs.at(-1) ?? 0  // passed tsc --strict too

[E0242] the call to `users.find` returns `User | undefined`; Glyph writes a value that may be missing as an `Option`
Help: pass `users` and the same callback to `array.find`, which returns `Option<User>`, and `match` it

有几个 JavaScript 方法用 undefined 表示“什么都没有”，Glyph 自己的检查器看不到它，所以编辑器和代理工具会放过对 .name 的读取。现在每个方法都会指向返回 Option 的标准库函数，数组上的那几个由 glyph fix 直接改写。

详情 涉及哪些方法，以及用什么替代

这份列表读自 TypeScript 的声明：数组上的 find、findLast 和 at，以及字符串上的 at、codePointAt 和 match。替代写法是 array.find、array.find_last、array.get、string.char_at、string.code_point_at 和 regex.matches。?? 的默认值会变成 match 的 None 分支。array.get 对负数索引返回 None，所以 xs.at(-1) 的帮助会写成 array.get(xs, array.len(xs) - 1)。在 npm 值上调用的方法不做判定，因为 Glyph 不知道它的类型。

== 在任何地方都是值相等

代码失败时测试却通过了 
@example wrap("a") == wrap("a")   // passed: deep equality
fn same() -> bool {
  return wrap("a") == wrap("a")   // false. no diagnostic
}

== 现在在任何地方都是值相等；基本类型仍然编译为 ===，所以普通的比较不受影响。

历史 测试是怎么在有问题的代码上通过的

== 在文档中写的是值相等，却被降级为 ===，而只要任何一边是记录、标签联合或数组，这就是引用相等。同一个表达式在测试中按结构比较，在旁边的程序中却按标识比较，所以测试可能在不能工作的代码上报告成功。

循环绑定保留其元素类型

在循环中消失的穷尽检查 
for t in tiers {
  match t {
    "free" => ...          // "pro" unhandled: once merely a warning to add `else`
  }
}

现在它会指出你没有处理的变体，这是让你满足检查的建议，而不是让你关掉检查。

历史 它以前给出的兜底分支建议

循环绑定不带元素类型，所以对字符串字面量联合类型的 match 退化成了对 string 的 match，编译器还建议加一个兜底分支。

按下标读取的值具有元素的类型

xs[0] 后的拼写错误：现在是 E0210 
fn first_len(xs: Array<string>) -> number {
  let s = xs[0]
  return s.lenght
}

[E0210] type `string` has no field `lenght`; did you mean `length`?

Array<E> 上的 xs[i] 是一个 E，所以编辑器、glyph check --no-tsc 和智能体工具都会检查你怎么用它：读取字段、调用方法、return、作为参数、带标注的 let。

历史 以前检查了什么

在 0.1.183 及以前，按下标读取的元素在 Glyph 这边没有类型。-> number 下的 return xs[0]、rows[0] 上拼错的字段、传给 number 参数的 xs[0] 都能通过，只有完整构建中的 tsc 步骤才会发现。这个类型就是 tsc 给生成代码的类型，生成的配置没有打开 noUncheckedIndexedAccess：是 E，不是 E | undefined。Glyph 的下标越界时抛出 RangeError，而不是返回 undefined；想要 Option 时用 array.get。对 Record 按键读取仍然是 E0224，除非它的值类型是 unknown；对 string 或 npm 值的下标不做判断。

导入的泛型联合类型受检

对导入的泛型联合类型做 match 时漏掉的变体 
import tree { Tree, Node }

fn label(t: Tree<string>) -> string {
  return match t {
    Node({ key: k }) => k    // Leaf unhandled: built clean, threw at run time
  }
}

现在无论哪种情况都是 E0200，两种导入写法都一样，无论是开放的类型参数还是具体的实例化。

历史 检查为什么从未启动

你自己模块声明的联合类型，无论是否带类型参数都会受检。从相邻模块导入的，只有不带类型参数时才受检。Tree<string> 进入跨模块覆盖检查路径时，是作为导入联合类型的一个应用，而不是联合类型本身，而启动检查的入口找的是后者，所以这个 match 根本没被计入：tsc --strict 通过，一个 Leaf 抛出了异常。把两个文件中的 <K> 删掉，同一个程序就是 E0200。

parse 不能声称做了它没做的检查

未经检查就报告成功的 parse：现在是 E0304 
type Conn = { id: number, sock: Socket }

Conn.parse(body)   // Ok. `sock` was never checked, and the message said it was

在记录中持有 socket 是正常的，仍然可以编译。现在在写出校验的地方，以及每个导入该记录的模块中，校验它都会被拒绝，并指出字段及其类型，而且拒绝会沿着形状传递：穿过嵌套记录、Array、Option。

详情 为什么检查存在与否不算检查，以及它要求的修复

每个记录类型都带有运行时描述符。对于编译器无法看清其类型的字段，比如 socket 或任何通过 extern_ts 得到的东西，生成的检查只是“它是否存在”，报告的信息却写着 field `sock` must be Socket。一个总是为真的布尔值没有用。一个总是为真、信息却声称检查了某个类型的布尔值更糟，因为 parse 正是边界被告知要信任的东西。

它要求的修复，就是你本来也会写的拆分：一个所有字段都可检查的线上类型，再由它构建一个领域记录。unknown 不会被这条规则拦下，因为它什么也不声称，检查是否存在确实就是全部检查。

在调用处看不见的签名变化：已在 0.1.116 修复

把一个函数改为接收负载而不是原始字符串，每一处仍在传旧形状的调用都照样构建通过。

billing.glyph：联合类型悄悄穿过一个 `string` 参数 
type PaymentResult = Settled(string) | Declined(string)

fn takes_string(s: string) -> number { return s.length }

fn charge(r: PaymentResult) -> number {
  return takes_string(r)   // compiled clean before 0.1.116
}
glyph build，现在 
[E0211] argument type mismatch: expected `string`, found `PaymentResult`
   ╰─ Pass a value of the expected type, or change the parameter's type.
详情 检查在哪里触发，在哪里保持沉默

类型为 string、number 或 bool 的参数，以前会毫无异议地接受一个已声明的联合类型或记录的值，而同样的调用如果传入不匹配的 bool 参数，早就是 E0211 了。

这项检查读取声明，所以只在答案确定的地方触发。像 type Id = string 这样的原始类型别名会被读成它所指的 string，因此判定方式相同。字符串字面量联合 (D30) 按其字面量比较，而 interface 的值在声明了 string 的地方会被拒绝，因为它的值是一个对象。extern_ts 或 typeof 主体仍然不作判断，void 也被排除在外。它对参数、return 和 let 注解一视同仁，因为三者共用同一个关系。

反方向则和 TypeScript 一样，经过值的成员来判断：在声明了 interface HasName { name: string } 的地方，5 会被拒绝；在声明了 interface HasLen { length: number } 的地方，"abc" 会被接受，因为字符串有 length。bigint 按它自己的成员来读，所以在那里会被拒绝：它没有 length。有两种配对还没有判定，交给 tsc：成员全部可选且与该值没有任何共同成员的接口 (G526)，以及 Option、Result 和 Record 对接口 (G527)。

带标注的 const 有类型

const 在接收一侧有对应的漏洞。

catalog.glyph：带标注的 const，以及它没有的字段 
type Sheet = { rows: number, cols: number }
const ORIGIN: Sheet = { rows: 0, cols: 0 }

fn f() -> number {
  return ORIGIN.rowz   // compiled clean before 0.1.116
}
glyph build，现在 
[E0210] type `Sheet` has no field `rowz`; did you mean `rows`?
详情 不带标注的 const，以及为什么两个修复都是 Breaking

带类型标注的模块级 const，无论标注写的是什么，都会降级为 Ty::Unknown，所以它上面的字段拼写错误不可见，而函数内部同样带标注的 let 早就能报告这个错误。

从 0.1.166 起，没有注解的 const 具有其初始化表达式的类型，读法与 tsc 读取发射器写出的 TypeScript const 相同：const MODE = "read" 保留其字面量类型，而对象或数组中的字面量会被拓宽，所以 const ITEMS = [1, 2] 是 Array<number>，在 mut 之外的 ITEMS.push(3) 是 E0240。检查器无法确定类型的初始化表达式会让该 const 保持无类型。两项修复在 glyph check --no-tsc、语言服务器和 playground 下都是破坏性的，因为每一项都开始捕获上一个版本接受的程序；完整的 glyph build 在两种情况下早已因 tsc 而报红。

记录没有声明的字段

拼错的可选字段：现在是 E0210 
module profile

pub type Profile = {
  name: string,
  nick?: string,
}

pub fn guest() -> Profile {
  return { name: "guest", nik: "g" }   // [E0210] type `Profile` has no field `nik`; did you mean `nick`?
}

声明的记录中没有的键，过去能通过 Glyph 的检查器，所以可选字段里的拼写错误会丢掉它的值，只有 tsc 会发现。现在编辑器、智能体工具和 glyph check --no-tsc 都会拒绝它，报出与读取同一字段相同的错误，glyph fix 会把 nik 改名为 nick。

详情 在哪里判定，哪些不判定

凡是写出的字面量遇到声明类型的地方都会判定：let、return、调用参数、变体的载荷、mut 赋值、嵌套字段、数组元素、match 分支，以及 tsc 放过的 Some、Ok 或 Err 的参数。持有更宽记录的绑定仍被接受，与 tsc 一致；来自展开的字段和为 Record<K, V> 写的键也一样。

  • 对导入联合类型的覆盖检查还不会深入变体的负载下一步要加深
    详情

    类型参数曾经会关闭检查：直到 0.1.90，对 Tree<K> 的 match 可以漏掉一个变体，构建通过，通过 tsc --strict，然后在运行时抛出异常，而同样的 match 作用在 Tree 上则是 E0200。对你自己模块声明的联合类型，这已经修复；从 0.1.95 起，对跨一次导入的联合类型也已修复。导入路径上仍然较浅的是深度而不是入口：为导入联合类型运行的检查从不深入变体的负载，所以当导入联合类型的负载本身也是联合类型时，B(X) 会匹配所有 B，而不是报告缺少的 Y，这与类型参数无关。这是下一步要加深的地方。

  • 导入联合类型的小写负载变体会让构建停止E0305
    详情

    负载位置上的变体现在按负载联合类型的变体列表来读，所以对你模块中声明的联合类型，名字的大小写不再重要。对从其他模块导入的联合类型，没有可读的列表，仍然由名字的形式决定，这意味着 Err(Blank) 会分派，而 Err(blank) 会让构建在 E0305 停止：对一个合法程序大声失败，修复它需要与上面浅层覆盖检查相同的导入联合类型注册表。

    详情
