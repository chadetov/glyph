列表中所有 TypeScript 示例都能零错误通过 tsc --strict。每个示例还会在一个配置拉满的项目里再检查一遍：比 --strict 更严格的所有编译器 flag，再加上 typescript-eslint 的 strictTypeChecked。在 37 个案例中，有 21 个是这套配置里没有任何一项能发现的。有 5 个能被默认关闭的编译器 flag 发现，11 个能被某条 lint 规则发现。这些都需要项目自己去打开，而智能体也可以再把它们关掉。在 Glyph 里，这些都不是配置项。

每个条目都是 catches/ 中的两个程序，每个程序下方的输出就是工具实际打印的内容。构建检查 scripts/check_catches.py 会重新运行每个案例，只要任何一半不再符合页面的描述就会失败。它用来对照的完整 TypeScript 配置就在这个脚本里。

1

来自程序外部的数据

可能性 5/5严重程度 5/5

请求体、文件、API 响应。

TypeScript能编译，运行时用的是错误数据
ts.ts
const user = JSON.parse(body) as User;
console.log(sendInvoice(user.plan));
$ tsx ts.ts
invoice for the undefined plan

没有任何东西检查数据。undefined 被当作套餐一路传下去。

没有任何工具能发现即使打开所有编译器 flag 并启用严格模式的 typescript-eslint 也不行

Glyph数据到达时检查
glyph.glyph
let out = match json.parse<User>(body) {
  Ok(user) => send_invoice(user.plan),
  Err(issues) => "rejected: ${json.stringify(issues)}",
}
$ glyph run
rejected: [{"path":["plan"],"message":"field `plan` is required","code":"missing"}]

不是真正 User 的请求体会得到 Err。程序里永远不会出现假的 User。

as User 什么都不检查，只是让编译器相信你。Glyph 没有 as。

2

没人处理的情况

可能性 5/5严重程度 4/5

智能体新增了 "archived" 状态。负责通报每种状态的处理函数写于它出现之前。

TypeScript能编译，没有任何警告
ts.ts
switch (s) {
  case "todo":
    console.log("not started");
    break;
  case "doing":
    console.log("in progress");
    break;
  case "done":
    console.log("finished");
    break;
}
$ tsx ts.ts
finished
archived logged nothing

归档一个条目时什么日志都没有。没有任何提示说这个 switch 已经过时。

仅 lint可由 lint 规则 switch-exhaustiveness-check 发现

Glyph构建时拒绝
glyph.glyph
match s {
  "todo" => print("not started"),
  "doing" => print("in progress"),
  "done" => print("finished"),
}
$ glyph build
[E0200] Error: typecheck: non-exhaustive match on `"todo" | "doing" | "done" | "archived"`: missing variants "archived"
Help: Add an arm for each missing variant.

构建停止，并指出是哪种情况。

只有当函数在每个分支都返回值，或者使用 assertNever 惯用法时，TypeScript 才会检查 switch 是否覆盖了每种情况。不返回任何值的处理函数两者都得不到。在 Glyph 中每个 match 都必须覆盖所有情况，所以新增一个变体就会列出每个需要修改的地方。

3

用 ! 信任 find 的结果

可能性 5/5严重程度 4/5

按 id 查找一条记录。

TypeScript能编译，运行时崩溃
ts.ts
return users.find((u) => u.id === id)!.name;
$ tsx ts.ts
TypeError: Cannot read properties of undefined (reading 'name')

! 告诉编译器“相信我”。运行时它什么也不做。

仅 lint可由 lint 规则 no-non-null-assertion 发现

Glyph构建时拒绝
glyph.glyph
return array.find(users, fn(u: User) -> bool { u.id == id }).name
$ glyph build
[E0210] Error: typecheck: type `Option<User>` has no field `name`: an `Option` has no members
Help: Open it with `match array.find(...) { Some(u) => u.name, None => <default> }`. If the absence is a JSON `null` from the wire, declare the type `Nullable<User>` (D45).

find 返回 Option，所以必须处理为空的情况。

没有 ! 时，tsc --strict 会拒绝这一行。正是 ! 关掉了这项检查，而它在运行时什么也不做。Glyph 没有 !。

4

函数签名隐藏的错误

可能性 4/5严重程度 4/5

一个可能失败的函数，调用它的代码却不知道它会失败。

TypeScript能编译，运行时崩溃
ts.ts
function loadConfig(): Config {
  throw new Error("missing file");
}

const cfg = loadConfig(); // no try
$ tsx ts.ts
Error: missing file

类型写的是 Config。没有任何地方说明它会抛异常。

没有任何工具能发现即使打开所有编译器 flag 并启用严格模式的 typescript-eslint 也不行

Glyph构建时拒绝
glyph.glyph
fn load_config() -> Result<Config, string> {
  return Err("missing file")
}

let cfg: Config = load_config()
$ glyph build
[E0204] Error: typecheck: type mismatch: expected `Config`, found `Result<Config, string>`
Help: Change the value, or the declared type, so the two agree.

失败是返回类型的一部分，所以调用方必须处理它。

TypeScript 函数的类型只列出它返回什么，从不列出它抛出什么。在 Glyph 中，失败是返回类型的一部分，每个调用方都能看到。

谁都能通过的过滤器

可能性 4/5严重程度 4/5

对每个用户调用异步的权限检查。

TypeScript能编译，但结果是错的
ts.ts
const active = names.filter(
  async (n) => await isActive(n));
$ tsx ts.ts
[ 'ada', 'mallory' ]

什么都没被过滤掉。

仅 lint可由 lint 规则 no-misused-promises 发现

Glyph构建时拒绝
glyph.glyph

$ glyph build
[E0211] Error: typecheck: argument type mismatch: expected `function`, found `async function`
Help: Pass a value of the expected type, or change the parameter's type.

异步函数不是一个是/否的答案。

异步函数返回 Promise，而任何 Promise 都算作 true。这样写的权限过滤器会放所有人通过。

10

跨 await 的丢失更新

可能性 3/5严重程度 5/5

两个请求同时向同一个账户扣款。

TypeScript能编译，运行时丢钱
ts.ts
const before = a.balance;
const f = await fee();
a.balance = before - f;
$ tsx ts.ts
balance 90

有一笔扣款消失了。没有哪个测试能稳定地发现它。

仅 lint可由 lint 规则 require-atomic-updates 发现

Glyph构建时拒绝
glyph.glyph
let before = a.balance
let f = await fee()
mut a.balance = before - f
$ glyph build
[E0225] Error: typecheck: `a.balance` is read before an `await` and written after it, so a concurrent write in between is lost
Help: Move the read after the `await`, so the value written is the one that is current when it is written.

Glyph 能发现跨等待的先读后写。

一个调用在等待 fee() 时，另一个调用可能更新了余额。随后第一个调用写回的是过期的值。

解构 split 的结果

可能性 5/5严重程度 3/5

把邮箱地址拆成用户名和主机。

ts.ts
const [user, host] = s.split("@");

TypeScript 假定第二部分一定存在。没有 @ 时，文本显示为“nobody at undefined”。

split 可能只返回一段。TypeScript 却照样把 host 的类型定为 string。

12

列表之外的值

可能性 3/5严重程度 4/5

某个 API 开始返回你的代码从没见过的状态。

TypeScript能编译，运行时用的是错误数据
ts.ts
type Account = { status: "active" | "banned" };

const body = '{"status":"deleted"}';
const acc = JSON.parse(body) as Account;
$ tsx ts.ts
status deleted

"deleted" 被当作两者之一。此后每一处对 status 的检查都是错的。

没有任何工具能发现即使打开所有编译器 flag 并启用严格模式的 typescript-eslint 也不行

Glyph数据到达时检查
glyph.glyph
type Account = { status: "active" | "banned" }

let out = match json.parse<Account>(body) {
  Ok(acc) => "status ${acc.status}",

$ glyph run
rejected: [{"path":["status"],"message":"field `status` must be \"active\" | \"banned\"","code":"type"}]

只有列出的值才能通过。

在 TypeScript 中，"active" | "banned" 这样的联合类型只在编译时存在。运行时没有任何东西能阻止第三个值。Glyph 在数据进来时检查它。

TypeScript能编译，运行时用的是错误数据
ts.ts
const limits = JSON.parse(text) as Record<Plan, number>;

没关闭的连接

可能性 3/5严重程度 4/5

在清理之前提前返回。

TypeScript能编译，运行时泄漏连接
ts.ts
const c = openConn();
if (!valid) return "rejected";
closeConn(c);
$ tsx ts.ts
rejected 1 still open

每个被拒绝的请求都会泄漏一个连接。

没有任何工具能发现即使打开所有编译器 flag 并启用严格模式的 typescript-eslint 也不行

let owned c: Conn = open()
match valid {
  false => { return "rejected" },
  true => close(c),
}

[E0206] Error: typecheck: `owned` resource `c` is not consumed on every path before the function returns
Help: Consume the handle on every path (move it into an `owned` parameter) before the function returns.

每条路径都必须关闭它。

这项检查只针对声明为 owned 的值。没有声明的资源不会被跟踪。

16

没人发现的拼写错误

可能性 4/5严重程度 3/5

从响应里读取字段。

TypeScript能编译，运行时失败
ts.ts
const data = await res.json();
return data.usr.name;
$ tsx ts.ts
TypeError: Cannot read properties of undefined (reading 'name')

res.json() 是 any，所以它的任何部分都不会被检查。

仅 lint可由 lint 规则 no-unsafe-member-access 发现

Glyph构建时拒绝被 glyph check 拒绝
glyph.glyph
return match json.parse(text) {
  Ok(data) => data.usr.name,
  Err(_) => "unreadable",
}
$ glyph build
[TS18046] Error: tsc: 'data' is of type 'unknown'.
Help: TypeScript's checker rejected the code this expression compiles to. The caret is on the Glyph expression that produced it.

没有 any。没人检查过的数据是 unknown；json.parse<User> 给它一个类型。

any 会关掉它碰到的一切的类型检查，而且会扩散：data.usr 也是 any。Glyph 没有 any。这里的拒绝来自 glyph check 和 glyph build 运行的 tsc 步骤；Glyph 自己的检查器目前还看不到它（G381）。

17

可能不存在的键

可能性 4/5严重程度 3/5

从一行字符串里读取字段，字段名拼错了。

TypeScript能编译，运行时打印 undefined
ts.ts
export function nameOf(row: Record<string, string>): string {
  return row.naem;
}
$ tsx ts.ts
undefined

任何键读出来都是 string，即使键根本不存在，所以拼错的字段打印出 undefined。

默认关闭可由编译器 flag noUncheckedIndexedAccess 发现

Glyph构建时拒绝
glyph.glyph
pub fn name_of(row: Record<string, string>) -> string {
  return row.naem
}
$ glyph build
[E0224] Error: typecheck: `Record<string, string>` is a map, so `naem` may not be there
Help: Use `record.get(map, "key")`, which returns `Option<V>` so the absent case has somewhere to go. `record.has` tests for the key alone.

5 个在 Glyph 中不存在的 JavaScript 陷阱

一些老陷阱，智能体仍然时不时会踩到。Glyph 会拒绝每个这样的程序，但不是因为发现了错误：导致错误的特性根本不在语言里，并且会给出替代写法。

  • "10,20,30".split(",").map(parseInt) 的结果是 [10, NaN, NaN]，因为 map 把下标当作进制传了进去。Glyph 有 number.parse，它返回 Result。
  • 用 .test 重复使用带 /g 的正则，每隔一次匹配就会失败，因为它记住了 lastIndex。Glyph 没有正则对象；regex.matches(pattern, text) 没有状态。
  • [1, 2, 3].forEach(counter.increment) 在没有对象的情况下执行方法。Glyph 没有类，也没有 this。
  • Math.max(...[]) 是 -Infinity。Glyph 的 array.max 返回 Option，空列表得到空值。
  • Array(3).map(...) 返回三个空位，因为 map 会跳过空位。Glyph 没有 Array(n)；数组用字面量书写。

Glyph 还发现不了的问题

11 个 Glyph 尚未堵上的漏洞。这些程序今天在 Glyph 中都能编译，并且和在 TypeScript 中一样出错。每个都在 catches/ 中有复现，并有一个未关闭的 gap 编号；修复落地时检查会失败，所以条目不会比漏洞活得更久。

  • requested || 3 会把真实的 0 变成 3。 G386
  • 把记录放进 "Welcome back, ${user}!" 会打印出 [object Object]。 G385
  • forEach(async ...) 会丢掉每个 promise，于是这些工作在依赖它的代码之后才完成，而且没有任何警告。 G384
  • 可选字段里的 JSON null 能通过检查，所以用展开覆盖默认值时会留下 null。 G391
  • 辅助函数里的 xs.sort(...) 会重排调用方的数组，却没有 mut 标记。 G380
  • 对数字调用 .sort() 会按文本排序：100,25,9。 G388
  • 用 ${name} 拼出来的 SQL 查询会被 std/sqlite 接受。 G387
  • 在 c[0] 上跨 await 的丢失更新，而对字段做同样的写入会被拒绝。 G390
  • 对字符串做 input + 1、users.find(...).name，以及在 unknown 上读取字段，这些只有 tsc 这一步能发现，Glyph 自己的检查器发现不了，所以编辑器和智能体工具都会漏掉。 G381, G382, G392

在每一项关于智能体所写代码的研究中，逻辑错误都是最大的一类，而任何类型检查器都看不到它们：写错的公式、理解错的任务，在 Glyph 中和在 TypeScript 中一样能编译。
