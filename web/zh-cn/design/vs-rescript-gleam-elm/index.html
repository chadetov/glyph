设计 · 比较

为什么不用 ReScript、Gleam 或 Elm？

这三门都是编译到 JavaScript 的类型化语言，都比 Glyph 更早、用的人更多、也更稳定。如果你在为一个新代码库选语言，又不需要贴近 TypeScript，应该先看看它们。Glyph 的不同之处更窄一些：它生成的是 TypeScript 源码而不是 JavaScript，它导入 npm 包时使用包自带的 .d.ts 类型，它根据你的类型生成运行时校验器，它的编译器还能为智能体回答影响范围查询。

它们如何描述自己#

ReScript 首页的标题是 "JavaScript Made Simple for Humans and AI" 和 "Types > Vibes"，并称它 "compiles to clean, efficient JavaScript"，"No any, no magic types, no surprise undefined."。它还提供 "automatically generate TypeScript types"（rescript-lang.org）。

Gleam 首页称它是 "a friendly language for building type-safe systems that scale"，并且 "No null values, no exceptions, clear error messages"。它运行在 Erlang VM 上，"can additionally compile to JavaScript"，并且 "also generates TypeScript definitions"（gleam.run）。

Elm 首页描述的是 "A delightful language with friendly error messages, great performance, small assets, and no runtime exceptions"，用于 "reliable web applications"，并称 Elm "detects all API changes automatically"，以 "guarantee that every single Elm package follows semantic versioning"（elm-lang.org）。

这些引文读取于 2026-11-19。

Glyph 有什么不同#

下面每一项都是为本页在 Glyph 0.1.149 上运行过的。

它生成 TypeScript 源码

glyph build 为每个模块写出一个 .ts 文件，随后由 tsc --strict 检查，你停用 Glyph 后也可以保留这些文件。ReScript 和 Gleam 生成 JavaScript，并在旁边生成类型定义。生成的 TypeScript 在 TypeScript 页面上有展示。

它导入 npm 包时使用包自带的声明作为类型

模块按名字导入包，包的 .d.ts 为每处使用提供类型。不需要先写绑定。在 ReScript 中，"external is the primary ReScript feature for bringing in and using JavaScript values"（external），类型在 ReScript 一侧声明。Gleam 的 external 需要类型标注，而编译器 "cannot verify that the function implemented in the other language returns the specified types"（externals）。Elm 通过 flags、ports 和自定义元素与 JavaScript 交互（interop）。装好 pg 和 @types/pg 后，下面这段会被拒绝：

main.glyph 
module main

import pg { Pool }

fn main(argv: Array<string>) -> number {
  let _pool = new Pool({ max: "two", })
  return 0
}
$ glyph check (trimmed) 
[TS2322] Error: tsc: Type 'string' is not assignable to type 'number'.
   ╭─[ main:6:24 ]
   │
 6 │   let _pool = new Pool({ max: "two", })
   │                        ───────┬───────
   │                               ╰───────── Type 'string' is not assignable to type 'number'.

错误码是 TS2322，因为检查库中的值的是 tsc，结果再映射回 Glyph 的那一行。Glyph 自己的检查器看不到这些值，所以 glyph check --no-tsc、编辑器和 MCP 工具都会漏掉这个错误（G257）。从 .d.ts 导入的类型也没有运行时检查。

它根据类型生成校验器

每个记录和联合类型都带有根据声明生成的运行时检查，所以数据不匹配时 json.parse<User> 返回 Err。在 Elm 中你要为每种结构写一个解码器，它的指南写道："the decoders people write end up working as a validation phase"（JSON）。

main.glyph：打印 "refused"，因为 JSON 中没有 email 
module main

import std/io
import std/json

type User = {
  id: number,
  email: string,
}

fn main(argv: Array<string>) -> number {
  return match json.parse<User>("{\"id\": 1}") {
    Ok(u) => {
      io.println(u.email)
      return 0
    },
    Err(_) => {
      io.println("refused")
      return 1
    },
  }
}

它的编译器能回答一个改动会破坏什么

编辑之前，智能体可以通过 MCP（glyph_impact）或 glyph query impact 询问一个改动会波及哪些地方。对于联合类型 Plan = Free | Pro | Team，其中一个 match 是穷尽的，另一个以 else 结尾，询问新增一个变体会得到每个位置的回答：

$ glyph query impact --entity main::Plan --change add_variant --variant Enterprise (three fields of each site) 
{"entity": "main::seats", "verdict": "ABSORBS", "diagnostic": null}
{"entity": "main::label", "verdict": "WILL_FAIL", "diagnostic": "E0200"}

改动之后，第二个位置将无法编译，改动一旦做出，这几个编译器中任何一个也都会告诉你这一点。第一个位置会继续编译，并把新情况送进它的 else，正是这个查询把它点了出来。面向智能体开发者列出了其他工具。

本页没有断言的内容#

本页没有比较错误信息、编译速度或运行时性能，也没有尝试从 Glyph 调用这三门语言中的任何一门，或者反过来调用。引文是各个项目用自己的话对自己的描述；它们做得如何，需要你自己去检验，就像 Glyph 自己的说法也需要你在证据页面上检验一样。
