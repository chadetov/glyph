证据

本站的每条说法是怎样验证的

“Glyph 能发现某个问题”这样的说法，对应仓库中的一对程序，一个用 TypeScript 写，一个用 Glyph 写，每次改动 CI 检查都会运行这两个程序。如果 TypeScript 版不再能编译，或者 Glyph 版不再被拒绝，构建就会失败。你可以用两条命令自己运行任何一个案例。

测试用例#

catches/ 下的每个目录都包含 ts.ts、glyph.glyph，以及一个说明两者各自行为的 case.toml。scripts/check_catches.py 在 CI 中运行。它要求每个 ts.ts 都能通过 tsc --strict，因为不能编译的 TypeScript 程序什么也证明不了；然后按案例的类型检查 Glyph 那一半。共有 45 个经过检验的案例：37 个 TypeScript 案例、5 个在 Glyph 中不存在的 JavaScript 陷阱，以及 3 个 Glyph 尚未堵上的漏洞。其中 28 个在构建时就被 Glyph 拒绝（23 个 TypeScript 案例和 5 个陷阱）。 按检查的类型划分：

类型案例数检查对 Glyph 版的要求
refused28构建失败，并报出 case.toml 中的错误码
warned3构建通过，并把该错误码作为警告报告
boundary9程序能运行，边界处的检查把错误数据变成 Err
runtime2程序能构建，运行时停下，并给出指定的输出
gap3Glyph 接受这个程序，而它的行为是错的。漏洞堵上时，检查会失败并提示把案例移走

不再能演示的案例会被删除，而不是被弱化，catches README 列出了被删除的六个案例及原因。其中一个后来发现 tsc 也能发现；另一个之所以成立，只是因为它的 TypeScript 版把某个值当作了 any。

用来对比的 TypeScript#

每个案例还会说明一个配置拉满的 TypeScript 项目能否发现这个错误，“TypeScript 能否发现”这个标签就来自这里。“配置拉满”指 tsc --strict，加上所有能让它更严格的选项，再运行一次 typescript-eslint。检查每次运行都会重新安装这些包（TypeScript 6、eslint 9、typescript-eslint 8、tsx 4 和最新的 @types/node），没有网络时会失败，而不是跳过。

在 strict 之上额外打开的 tsconfig 选项 
noUncheckedIndexedAccess: true
noFallthroughCasesInSwitch: true
noUnusedLocals: true
noUnusedParameters: true
noImplicitReturns: true
noImplicitOverride: true
allowUnreachableCode: false
allowUnusedLabels: false
exactOptionalPropertyTypes: true
noPropertyAccessFromIndexSignature: true
eslint.config.mjs 
export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.strictTypeChecked,
  { rules: {
    "@typescript-eslint/switch-exhaustiveness-check": "error",
    "@typescript-eslint/strict-boolean-expressions": "error",
    "@typescript-eslint/require-array-sort-compare": "error",
    "require-atomic-updates": "error",
  } },
);

案例的标签是 none、flag: 加上能报出它的那个选项，或者 lint: 加上对应的规则。如果改正后的程序也因为无关的原因触发了某条规则，案例会带一个 ts_ok.ts，标签只统计因这个错误而触发的部分。例如，non-exhaustive-match 是 lint:switch-exhaustiveness-check：只要打开这条规则，typescript-eslint 就能发现它，页面上也是这么写的。

本站的代码片段都能编译#

scripts/check_docs_compile.py 在 CI 中运行，编译本站上每个独立的 Glyph 代码片段（以 module 开头并声明了内容的片段），以及文档和 llms.txt 中的片段。本来就应该失败的片段必须注明它触发的错误，而且必须恰好触发那一个错误。需要 React 或某个 npm 包的片段会对照这些包的真实类型编译。不完整的片段会被计数并跳过，计数会打印出来，让跳过的比例一直可见。

它还发现不了的问题#

3 个 gap 案例在案例页面上，每个都带有 gap 编号。用 Glyph 构建应用时发现的每个漏洞都记录在清单 docs/dogfooding-gaps.md 中，其中方括号标记是唯一有效的状态（[FIXED]、[HALF FIXED]，没有标记表示未解决）；如果某个未解决条目的最近一次复现已经是五个版本以前，scripts/check_gaps.py 会让 CI 失败。

版本如何被标记为 Breaking#

如果一个版本拒绝了上一版本接受的程序，它就会被标记为 Breaking。判断方法是写出受影响的最小程序，分别用已发布的上一版本和新的二进制文件运行，然后比较退出码。不是根据说明的措辞推断出来的。0.1.99 之前的版本从未这样测试过，所以没有标记的旧版本只是未经测试，并不代表安全。记录见版本页面。
