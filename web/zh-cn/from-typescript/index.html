从 TypeScript 迁移过来

已经在写 TypeScript 的话，会有哪些变化

比你想象的少。Glyph 编译出能通过 tsc --strict 的 TypeScript，保留 npm 和你的部署方式，读起来也几乎一样。差异只有几处，每一处都是把一种犯错的方式换成一项由编译器完成的检查。

懂 TypeScript，就已经懂了大部分#

你不需要学一门新语言，只要学这四样。本站每个示例里都有它们。

match
穷尽的 switch：对联合类型分支时，编译器要求你处理每一种情况。它也是唯一的条件结构：没有 if/else，也没有三元运算符，原因见下文。
Result<T, E>
错误是返回值，而不是抛出的异常。你可以用 match 处理它，或者用 ? 运算符向上传递。
fn f() -> T
函数；-> 后面是返回类型。type X = {...} 是记录，type X = A | B 是标签联合。
mut x = e
重新赋值是显式的，可以 grep 到。普通的 let 绑定不会在你背后改变；要修改它就写 mut。

本站说的“智能体”指 Claude、Copilot、Cursor 这样的 AI 编程助手。Glyph 对它们帮助最大，但无论代码是人写的还是模型写的，检查都一样。如果你已经在用严格模式的 TypeScript 加 zod 和 eslint，这里说明一门语言能在此之上多带来什么。

没有 if#

对布尔值分支，就是对 true 和 false 做 match。如果只需处理其中一边，另一个分支写成空块。

TypeScript 
function label(admin: boolean): string {
  return admin ? "admin" : "member";
}

if (verbose) {
  console.log("starting");
}
Glyph 
fn label(admin: bool) -> string {
  return match admin {
    true => "admin",
    false => "member",
  }
}

match verbose {
  true => io.println("starting"),
  false => {},
}

原因是规范中的决策 D3：对值做分支只用一种结构，所以读、写、搜索时都只有一种形式。从分支中得出的值总是来自 match，其结果类型由 Glyph 自己的检查器推导，而不是交给 tsc。对联合类型来说，正是这个结构必须覆盖每一种情况（E0200）。对布尔值来说收益不大，因为 false => {} 和省略 else 表达的意思一样。

这是有代价的。一行三元表达式会变成四行 match，按条件提前返回会变成带一个空分支的 match，而这也是 TypeScript 读者第一眼会觉得别扭的地方。规范把这种啰嗦记为一项可接受的代价。硬要写 if 会得到错误 E0006，其帮助信息会给出 match 写法；三元运算符是 E0013，帮助信息相同。

你已经在付的代价#

如果你在 TypeScript 代码库上用 AI 智能体开发，下面这些就是日常成本。每一项在 Glyph 中都有具体的应对，链接见列表。

  • 智能体会臆造 API，因为 TypeScript 会擦除类型，运行时和编译时不再一致。Glyph 的类型带有运行时检查（T.parse、T.is），见类型化的 API。
  • 智能体用 any 和 as unknown as T 掩盖不确定性，而编译器任由它们这样做。这两者在 Glyph 中都不存在，见下表。
  • 你只要求改一行，结果整个文件都被重写了，因为格式化工具在每次编辑时都会连锁改动。glyph fmt 只有一种排版，没有任何选项，见干净的 diff。
  • 你在每个类型旁边维护一个手写的校验器（zod，再加一个序列化器），智能体在其中一处改了字段名，其他地方却没改，而这一切照样能编译。在 Glyph 中，类型本身就是校验器。
  • 你 grep 一个符号，却找到十个不相关的匹配：重载、装饰器、合并的命名空间。Glyph 这些都没有，见查找代码。

TypeScript 提供的关闭开关，以及 Glyph 的替代做法#

下面每个 TypeScript 结构都是在让检查器停止检查。它们都不是 Glyph 语法。中间一列是 glyph check --no-tsc 在 0.1.149 上对每一项打印的内容。

TypeScript在 Glyph 中改成怎么写
x!不是合法语法：E0013用 match 处理 Option<T>，或者用 ? 向上传递
x as T, as unknown as T没有类型断言：E0013，帮助信息建议去做校验T.parse(x)，返回 Result
any不是类型：E0103，名称无法解析unknown，通过 T.parse、T.is 或 match 分支 is T 收窄
(v): v is T不能自己写类型守卫：E0002生成的 T.is(v)，按声明的结构检查，所以守卫不会检查得比它声称的少
// @ts-ignore, // eslint-disable只是普通注释；下面的错误照样报出没有。任何注释或 flag 都关不掉 Glyph 的诊断

glyph check 有一些跳过整个阶段的 flag（--no-tsc 跳过 tsc --strict，--no-test 跳过 @example 测试），但没有能屏蔽单项检查的 flag。TypeScript 项目接受而 Glyph 拒绝的完整列表，每个案例都在两个编译器下运行过，见案例页面。

只有一个逃生口，而且可以 grep 到#

需要写 Glyph 表达不了的 TypeScript 时，extern_ts("...") 接受一个内联的类型或表达式，tsc 仍然会检查它。对整个模块，把 .ts 放在 src/extern/ 下，然后写 import extern/name；除此之外相对导入都不合法，所以这条路径是唯一的入口。两种形式都包含 extern 这个词，所以 grep -rn extern src/ 能列出检查器把控制权交给 TypeScript 的每一处。

src/clock.glyph 
module clock

pub fn now_ms() -> number {
  return extern_ts("Date.now()")
}

生成的 TypeScript 是什么样子#

普通的 TypeScript，每个模块一个文件，可以阅读，也可以提交。联合类型会变成可辨识联合，外加一个带运行时检查的值；match 会变成对标签的 switch。下面是 glyph build 对左边模块的输出，省略了 import 行。

plan.glyph 
module plan

pub type Plan = Free | Pro | Team

pub fn seats(p: Plan) -> number {
  return match p {
    Free => 1,
    Pro => 5,
    Team => 50,
  }
}
plan.ts（生成的代码，有删节） 
export type Plan =
  | { tag: "Free" }
  | { tag: "Pro" }
  | { tag: "Team" };

export const Free: Plan = { tag: "Free" };
export const Pro: Plan = { tag: "Pro" };
export const Team: Plan = { tag: "Team" };
export const Plan = {
  is(value: unknown): value is Plan { ... },
  parse(value: unknown) { ... },
  schema: ...,
};

export function seats(p: Plan): number {
  const __m0 = p;
  switch (__m0.tag) {
    case "Free": { return 1; }
    case "Pro": { return 5; }
    case "Team": { return 50; }
    default: throw new Error("non-exhaustive match");
  }
}

删掉 Team 分支，构建会在写出任何 TypeScript 之前停止：

glyph check --no-tsc（有删节）

如果你不再使用 Glyph，留下的就是生成的 .ts。除了构建时写在旁边的一个小的支持目录，它没有任何运行时依赖。

npm，以及你已有的 TypeScript#

.glyph 模块按名字导入 npm 包（import kafkajs { Kafka }），类型来自包自带的声明；你现有的 .ts 也能像导入本地文件一样导入生成的 Glyph 模块。所以你可以先在一个仍然是 TypeScript 的应用里写一个模块。具体细节见下面三个问答。

我能使用现有的 TypeScript、JavaScript 和 npm 库吗？

导入包、保留一个 .ts 适配层，以及在 .ts 中反过来导入 Glyph。

 能在现有应用里引入 Glyph 吗？

领域核心用 Glyph，其余用 TypeScript，基于一个标准的 Vite 脚手架。

 能和 React 一起用吗？

组件、JSX、hooks、Context，以及哪些地方仍由 tsc 负责检查。
