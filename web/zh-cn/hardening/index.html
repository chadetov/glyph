Glyph 如何加固

智能体尝试攻破它，我们记下它们的发现。

一门声称智能体没法悄悄改坏它的语言，必须经受这方面的检验。我们让 AI 智能体扮演多疑的工程师（一个受够了的 React 开发者、一个爱唱反调的后端工程师、一个专挑安全漏洞的对手），让它们构建应用并尝试打破这些保证，然后修复它们的发现，或者记为未解决的 gap。下面是这个循环，以及它的发现。

能通过 tsc --strict、在 Glyph 中却无法编译的案例

每个案例都是两个文件：一个在 tsc --strict 下类型检查干净的 .ts，以及同一个程序的 Glyph 版本，它无法编译。构建检查 scripts/check_catches.py 会重新运行每个案例，只要任何一半的行为变了就会失败，所以一项悄悄消失的保证会连带让构建失败。下表列出了案例页面上 37 个 TypeScript 案例中以这种方式被拒绝的 23 个；其余的见那个页面，Glyph 会在数据到达时检查它们、给出警告，或者在运行时拦下。共有 45 个经过检验的案例：37 个 TypeScript 案例、5 个在 Glyph 中不存在的 JavaScript 陷阱，以及 3 个 Glyph 尚未堵上的漏洞。其中 28 个在构建时就被 Glyph 拒绝（23 个 TypeScript 案例和 5 个陷阱）。

后来发现 TypeScript 也能发现的案例，或者两半其实不是同一个程序的案例，都被删除了，而不是被弱化；catches/README.md 列出了每一个及其原因。

即使键拼写正确，map 读取也会被拒绝，因为 Record<string, string> 并没有说明哪些键存在。TypeScript 可以用 noUncheckedIndexedAccess 发现它，但 --strict 不会打开这个选项。缺失的联合类型情况在 TypeScript 中也能发现，只要项目采用 typescript-eslint 的 switch-exhaustiveness-check 或 assertNever 默认分支。在 Glyph 中，这两项检查都不是可选的。

在解析请求体的案例中，Glyph 的 json.parse 返回的是 Result，不是 User，所以在请求体被检查之前，这个赋值都是类型不匹配。TypeScript 的 JSON.parse 返回 any，user 上的类型标注把它“洗白”了。

对抗循环

每项发现都要针对编译器复现，从根源修复，并经过独立的再次验证，才算数。

1

探索

扮演不同角色的智能体构建程序（表单、后端、有状态的 UI），并记录语言给它们添堵的每一处。

2

复现

每项发现都被缩减成最小的失败程序，再针对编译器重新运行。无法复现的一律丢弃。

3

修复

在 Rust 编译器中从根源修复，并附带一个修复前失败、修复后通过的回归测试。完整测试套件必须保持全绿，否则改动会被回退。

4

验证

一轮独立的检查会针对新构建的编译器重新运行每个复现，在发布之前揪出“智能体以为已经修好了”的漏洞。

最重要的一类：悄无声息的正确性漏洞

下面每一个都能干净地编译，并且可能发布出通过了类型检查的错误代码：这正是 Glyph 要防止的那一类 bug。现在每一个都会在编译时被发现。

严重，已修复

Result match 中无负载的错误变体

对 Result<T, Empty | BadQty(...)> 的 match 被转换成两个重复的 case "Err" 分支；第一个吞掉了所有错误，并悄悄地分派到了错误的分支。

现在：合并成一个 case，内部有正确的 switch；每个变体都能正确分派。

严重，已修复

拼错的构造器变成了悄无声息的兜底分支

match 分支中拼错的变体（把 Loaded 写成 Loded）被悄悄当作不可反驳的兜底绑定，掩盖了不穷尽的问题，运行时分派错误，而且没有任何诊断。

现在：未知的构造器会在拼错的地方被拒绝，和真实的名字一样处理。

高，已修复

不完整的 bool match 绕过了穷尽性检查

match n > 0 { true => ... }（缺少 false 分支）能编译并通过 tsc，然后在运行时抛出异常。

现在：编译时报出不穷尽 match 错误。

高，已修复

多参数组件绑错了 props

component C(a, b) 生成的是位置参数，但 React 调用组件时第一个参数是 props，所以 a 悄悄绑定到了整个 props 对象。它通过了 tsc。

现在：清晰的编译错误，指向单个 props 记录的写法。

高，已修复

JSX <match> 跳过了穷尽性检查

缺少某个 <case> 的 JSX <match> 能顺利编译，然后在运行时抛出异常；而值层面的 match 是有检查的。

现在：适用同样的穷尽性检查；缺少的情况是编译错误。

高，已修复

记录负载绑定到了错误的字段

把带记录负载的变体绑定到一个名字上（BadQty(b)）时，会从展平后的负载上读取一个不存在的 .value。

现在：负载能正确绑定，所以 b.sku 可以正常使用。

检查器现在强制执行的规则

编译器过去交给 tsc 的可靠性检查，现在由 Glyph 自己发现。

已修复

调用参数个数

参数过少或过多都会被接受（运行结果是 NaN）。现在 E0213 会拒绝错误的参数个数。

已修复

跨标准库边界的 ? 错误类型

当错误来自标准库包装函数时，精确错误类型规则会被跳过。现在那里也会强制执行。

已修复

给 owned 句柄起别名

对资源句柄写 let g = f 会创建第二个绑定，可能导致重复关闭。现在会被拒绝（E0215）。

已修复

不可达分支与更深入的校验

兜底分支之后的分支现在会被标出；json.parse<T> 现在会按结构校验 Record 字段，而不只是检查是否存在。

初次使用时的阻碍，已移除

那些给人留下糟糕第一印象、又毫无用处的小问题。

已修复

无障碍属性与 data 属性

aria-label 和 data-* 被解析成了减法。现在它们能正常工作，并生成正确的 React props。

已修复

npm 包名

带连字符和带作用域的说明符（react-hook-form、@hookform/resolvers/zod）会被拒绝。现在可以直接导入。

已修复

浏览器打包后的首次运行

浏览器构建中没有加载运行时引导代码，首次运行就崩溃。现在每个生成的模块都会引入它。

已修复

误导人的错误信息

写 if 现在会提示使用 match；范围模式会直接说明；JSX 中的空白和文本中单独的 $ 都能正确处理。

仍未解决：记录在案

加固也意味着说清楚哪些还没做。下面这些都是已知并在跟踪的问题，没有隐瞒。

有意推迟，或者在等待设计决策：

要在 Glyph 自己的检查器中拒绝隐式 any 的闭包，需要上下文推断，以免对类型正确的回调误报。易用的 FFI，也就是不为每个库写适配层就能使用类型复杂的 TS 库，是仍未解决的最大互操作问题，记录在未决问题中。来自其他模块或标准库的 map 仍然会被不加检查地读取，所以 E0224 还管不到 sqlite.Row；双绑定的 for i, x in xs 仍会丢失元素类型。
