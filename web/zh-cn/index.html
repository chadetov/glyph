AI 智能体来写， 编译器来查。

Glyph 读起来像 TypeScript，只是去掉了逃生口：没有 any，没有类型断言，没有未经校验的数据，每种情况都要处理。它编译为可读的 TypeScript，node、npm 和你现有的代码都照常使用。

$ npx -y @glyphlang/glyph init hello && cd hello && npm install && npx glyph run

无需全局安装。若想把 glyph 放进 PATH：npm install -g @glyphlang/glyph tsx typescript

37 个中有 21 个

列表中所有 TypeScript 示例都能零错误通过 tsc --strict。每个示例还会在一个配置拉满的项目里再检查一遍：比 --strict 更严格的所有编译器 flag，再加上 typescript-eslint 的 strictTypeChecked。在 37 个案例中，有 21 个是这套配置里没有任何一项能发现的。有 5 个能被默认关闭的编译器 flag 发现，11 个能被某条 lint 规则发现。这些都需要项目自己去打开，而智能体也可以再把它们关掉。在 Glyph 里，这些都不是配置项。共有 46 个经过检验的案例：37 个 TypeScript 案例、5 个在 Glyph 中不存在的 JavaScript 陷阱，以及 4 个 Glyph 尚未堵上的漏洞。其中 28 个在构建时就被 Glyph 拒绝（23 个 TypeScript 案例和 5 个陷阱）。

你的智能体可以先问编译器

examples/apps/csvql 是本仓库里的一个 CSV 查询引擎，核心是一个 Value 联合类型。给它加一个 Date case 之前，智能体先问编译器的 MCP 服务器：这次修改会弄坏什么。回答（这里只保留判定、位置和函数）列出了四个文件中的十处 match。

在 ABSORBS 处的修改：catch-all 换成逐个命名的分支 
 fn literal_text(v: Value) -> string {
   return match v {
     Text({ text }) => "'${text}'",
-    else => value.render(v),
+    Date({ iso }) => "'${iso}'",
+    Num({ n }) => value.render(v),
+    Bool({ flag }) => value.render(v),
+    Null => value.render(v),
   }
 }

每条 WILL_FAIL 都附带它会触发的错误；只加这个 case 时，得到的正好是这八个 E0200 错误。两处 ABSORBS 什么都不报：render::literal_text 会把日期字面量打印成不带引号的样子，exec::total 会把每个日期都算作零。只看编译器错误工作的智能体会修好八处，然后带着通过的构建停手。修完之后再问一次，编译器在全部十处都回答 WILL_FAIL，所以下一个 case 也漏不过去。
