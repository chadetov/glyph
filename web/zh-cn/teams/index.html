面向团队

它保证什么，引入它的成本是什么，以及如何退出

Glyph 会拒绝一份具体的、经过检验的案例清单，这些案例在严格模式的 TypeScript 项目中都能通过；它编译出的 TypeScript 在你停用 Glyph 后也可以保留。它还是早期预览版：尚未到 1.0，主要由一个人维护，每周发布好几次。

它保证什么#

关于 Glyph 能发现什么的每一条说法，都对应仓库 catches/ 目录中的一个案例：同一个程序的 TypeScript 版和 Glyph 版，都由 CI 检查运行。共有 51 个经过检验的案例：37 个 TypeScript 案例、5 个在 Glyph 中不存在的 JavaScript 陷阱，以及 9 个 Glyph 尚未堵上的漏洞。其中 28 个在构建时就被 Glyph 拒绝（23 个 TypeScript 案例和 5 个陷阱）。 在它不拒绝的错误中，3 个会给出警告，9 个是在运行时边界检查处被拦下的错误数据，2 个在运行时停下。审查智能体所写代码的人最依赖的是这些：

代码被拒绝的内容
E0200漏掉联合类型某种情况的 match，所以新增一种情况就会列出每个需要修改的地方
E0013类型断言（as、as unknown as）；没有类型断言，也没有 any
E0204未经检查就赋给有类型的名字的 JSON 解析结果
E0224从 map 中读取，却当作键一定存在来对待
E0217被直接丢掉的 Result（警告；let _ = 表示是有意为之）

案例页面列出了每个案例的 TypeScript 版、Glyph 版和报错，并说明哪些用配置拉满的 typescript-eslint 也能发现。

它在哪里止步#

这些保证只覆盖用 Glyph 写的代码。npm 依赖内部抛出的异常仍然会绕过 Result，从包的 .d.ts 导入的类型也没有运行时检查。在 Glyph 内部，9 个尚未堵上的漏洞连同 gap 编号都列在还发现不了的问题中，完整清单见 docs/dogfooding-gaps.md。与严格模式 TypeScript 加 zod、eslint 和 ts-pattern 的比较（包括那套方案仍然领先的地方），见为什么不用配齐工具的 TypeScript。

在现有应用中引入#

不需要重写。你把最不能出错的部分（模型、权限、状态转换、金额）用 Glyph 写，应用的其余部分仍是 TypeScript，像导入本地文件一样导入生成的模块。演示用的是一个标准的 Vite 脚手架：能在现有应用里引入 Glyph 吗？

如何退出#

glyph build 写出普通的 TypeScript，每个模块一个文件，能通过 tsc --strict。如果你不再使用 Glyph，就把这些输出提交，然后继续用 tsc。许可证是 MIT 或 Apache-2.0，所以随时都可以 fork。从 TypeScript 迁移过来展示了一个模块和它生成的文件。

版本固定与升级#

glyph init 会在 package.json 中把编译器固定到确切版本，不带 ^，所以不会有哪个版本意外进入你的构建。剩下的由三条命令处理：

有意识地升级 
glyph doctor     # your version against the latest release; never fails CI for that
glyph upgrade    # moves the project's pin, runs npm install, links the notes
glyph --update   # moves the installed compiler itself

详见新的 Glyph 版本会破坏我的构建吗？

发布节奏和 Breaking 标记#

版本页面为从 0.1.0 到 0.1.155 的每个版本都写了条目，共 154 个，其中 28 个发布于 2026年11月1日 至 2026年11月21日 之间。如果一个版本拒绝了上一版本接受的程序，它就会被标记为 Breaking，大多数正确性修复都是这样落地的。共有 38 个条目带有这个标记。标记的依据是在两个版本下分别运行受影响的最小程序，而不是阅读 diff；0.1.99 之前的版本没有这样测试过，所以没有标记的旧版本只是未经测试，并不代表安全。

Breaking 版本在实践中造成了多少影响：最近的每条说明都写了用新旧两个版本运行仓库示例应用时发生了什么。下面是最新的几个 Breaking 版本，引自它们的说明：

  • 0.1.155: 版本说明里没有提到。
  • 0.1.154: “In the repository, two example apps did, and both were real bugs: the chat server's main started daemon.serve(port) and returned before the server bound, and the job queue's timer dropped each drain.”
  • 0.1.153: “No tracked .glyph file and none of the 32 example apps changed exit code.”
  • 0.1.152: “No file in the repository, none of the 32 example apps and neither outside app we test against decodes a null into an optional field.”
  • 0.1.151: “No tracked .glyph file and none of the 32 example apps changed exit code.”
  • 0.1.150: 版本说明里没有提到。

示例应用是项目自己的代码，每个版本都保持能编译，所以新拒绝的写法出现在它们里面的可能性，比出现在你的代码里要小。每条说明都会列出它拒绝的写法，升级前请先读一读。

状态#

Glyph 还在 1.0 之前。1.0 之前，语法、标准库和生成的 TypeScript 的形式都可能变化，某个版本也可能拒绝以前能编译的代码。docs/stability.md 说明了哪些可能变化、哪些保持稳定。MAINTAINERS.md 直接写明，项目目前主要由一个人维护。

常见顾虑#

我们不怎么用 AI，还值得用吗？

无论代码是谁写的，检查都一样：更少的运行时意外，更小的 diff，可以 grep 的代码。

 我们已经在用严格模式的 TypeScript 和 lint 了。

那些检查每一项都需要主动打开，而且一行就能关掉。Glyph 的检查关不掉。

 我们的智能体能写一门它们几乎没见过的语言吗？

模型对 TypeScript 的了解大多能直接沿用，其余的由编译器指出来。

 为什么要编译到 TypeScript？

npm、React 和 Node 都在那里，这也是为什么可以一个文件一个文件地引入。

 出问题时，值班的人会看到什么？

可读的 TypeScript，指回 .glyph 文件的 source map，以及稳定的错误码。

 我们怎么知道这些都是真的？

本站每条说法是怎样验证的，以及如何自己复现。
